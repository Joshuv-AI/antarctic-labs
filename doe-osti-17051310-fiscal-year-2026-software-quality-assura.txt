 EXECUTIVE SUMMARY
 The continued goal of the Argonne Reactor Computation (ARC) SQA project in the U. S.
Department of Energy Office of Nuclear Energy (DOE-NE) Fast Reactor Program is to resolve the
Quality Assurance (QA) gaps for the ARC software that limit, or prevent, commercialization of the
software for industry users. This project started in earnest in fiscal year 2023 which saw the entire
code system moved from a SVN repository to a GitLab repository and an associated software
quality assurance plan (SQAP) developed and ratified. Most of the QA gaps in the ARC software
were identified in collaboration with industry partners and work begin in fiscal year 2023 and
continues today.

 The three top goals of this year were to start software cleanup of the ARC software to
remove BPOINTER and the antiquated file layer, create a software verification report for DASSH,
and create a manual for NUBOW-3D. Considerable work was done to clean up the iterative solver
portion of DIF3D by removing BPOINTER and the partitioned to disk strategy for many small
arrays. While BPOINTER was fully removed from DIF3D-VARIANT and DIF3D-Nodal, more work
remains on DIF3D-FD which will carry into the next fiscal year. Additional effort is also underway
to replace entire sections of the original source code in favor of using the well tested F90 modules
along with replacing the input processing section of the code.

 After review of the unique capabilities of SE2RCT against DASSH, the special features of
SE2RCT were added to DASSH this fiscal year. SE2ANL was scheduled for deprecation at the end
of the previous fiscal year as it yielded no additional functionality from DASSH. By adding the
SE2RCT functionality to DASSH, we can also now deprecate SE2RCT. The rationale for deprecation
of SE2ANL and SE2RCT is the cost associated with maintaining three pieces of software that
basically do the same thing (SE2RCT, SE2ANL, and DASSH) and generating the necessary missing
documentation for all three (verification reports and code coverage). It is also noted that GAMSOR
was supposed to be deprecated this fiscal year, but the completion of that modification to PyARC
will result in it being deprecated in the early part of the next fiscal year.

 The primary missing documentation to resolve this year was a manual for NUBOW-3D and
a software verification report for DASSH. The user manual for NUBOW-3D is complete and has
been released [Error! Reference source not found.]. The DASSH software verification work was
not completed this year as the planned effort to complete it was well below what it actually
required. Because major changes were made to DIF3D this year, the code coverage reports for
DIF3D, REBUS, and RCT will have to be updated after all of the source code cleanup is completed
in the coming fiscal year.

 Non-trivial industry partner software development funds were provided this year. Funding
was provided to incorporate CMFD (coarse mesh finite difference) acceleration in DIF3D-VARIANT
to improve its performance which was unable to be fully completed this year. Funds were also
provided to support the inclusion of clad damage evaluations in VARPOW and the documentation
was updated consistently. It is noted that this allowed DASSH to incorporate the clad damage

capability as will be covered in this manuscript. Overall progress on resolving the QA gaps has
been good this year.

1. Introduction
 The Argonne Reactor Computation (ARC) software suite [1-18] has been developed by
Argonne researchers for fast reactor design and analysis since the 1970s. With the ARC software
suite, a user can quickly build a model of a proposed or existing fast spectrum reactor and carry
out fuel cycle, nominal thermal analysis, and assess, as is appropriate, whether the core design
and constraint system yield an acceptable mechanical behavior. For transient reactor analysis with
SAS4A/SASSYS-1 (SAS) [19], the ARC software suite can be used to generate reactivity coefficients
and kinetics parameters at any modeled fuel cycle time point which forms part of the input to
SAS.

 The ARC suite was regularly being developed into the 1990s and followed a software QA
program which was an appropriate standard for the time. In the 1990s, the DOE funding to fast
reactor research and development was all but eliminated and the ARC software was put into
maintenance mode. In the early 2000s, the software quality assurance (SQA) program for ARC was
still in place to define an official version, but by 2005 it all but was abandoned as there were
insufficient staff to fill the work roles.

 Since 2005, there has been a considerable increase in research and design work on fast
spectrum reactors. The ARC software as a whole has since been exported to many universities
and commercial companies and ANL support has been given to the various projects over the years
[20-24]. Further, MC2-3, PERSENT, and DASSH were all developed after 2005 without any
adherence to a software standard. In recent time, the DOE VTR project [23] paid for verification
work to be done on the ARC software as part of the goal of making it NQA-1 complaint. The VTR
project was not considered the appropriate pathway to fund and maintain a SQA program for the
ARC software and while software developments (DASSH) were made and several manuals were
updated and software verification work was carried out, the ARC software is not NQA-1 compliant.

 More recently the Advanced Reactor Demonstration Program (ARDP [24,25]) has funded
the creation of manuals for some ARC utility programs and funded additional software verification
work on DIF3D [6, 7], MC2-3 [2-5], and PERSENT [9] for the purpose of commercial grade
dedication. Additional funding through the DOE Technology Commercialization fund [26] motived
work on DASSH, PERSENT, and NUBOW-3D all of which was connected in PyARC [27]. Because of
the VTR and ARDP projects, software verification work was completed on MC2-3 [28-31], DIF3D
[32], EvaluateFlux [33], GAMSOR [34], VARPOW [35], REBUS [36], and PERSENT [37]. These
reports discuss the inputs for and outputs from the codes that are covered by the verification
work and link various analytic, code-to-code, and hand calculation-based verification work
presented in the report with verification test problems provided with the software. This is a key
part of the commercial grade dedication work and constitutes the bulk of the cost to get the ARC
software to commercial grade.

 With the support of the Advanced Reactor Technologies (ART) Fast Reactor Program (FRP)
in DOE [38], the software quality assurance program on ARC was rebuilt in 2023 [39] based upon

 6

GitLab [40,41]. As inferred from the preceding discussion, the ARC software suite is a valuable
asset as a fast reactor design and analysis tool set that has been reasonably well verified and
validated with various fast reactor benchmark problems and experiments over several decades.
Some or all of the ARC software suite has been utilized for designing the IFR [21], PGSFR [22], VTR
[23], and Natrium [24] reactors and we can expect it to continue to be used for advanced fast
reactor design and/or confirmatory calculation purposes in the future.

 Due to increased interest by commercial companies and regulatory bodies, it is becoming
more important to make the ARC software suite complete and ready-to-use in terms of its SQA
pedigree and commercial grade dedication needs. The three top goals of this year were to start
software cleanup of the ARC software to remove BPOINTER and the antiquated file layer, create
a software verification report for DASSH, and create a manual for NUBOW-3D.

 Considerable work was done modifying DIF3D to eliminate BPOINTER and the file layer
usage within the iterative portion of each solver. BPOINTER was a scheme used in the 1970s and
1980s to allow dynamic memory allocation when the Fortran standard did not allow it. With the
release of Fortran 90 in 1990, that aspect was resolved, but no changes were made to DIF3D to
take advantage. The file layer in DIF3D was written in the late 1960s and abstracted away READ
and WRITE statements in favor of interface subroutines. This was done as file reading/writing on
different platforms at the time was cumbersome and the abstraction simplified the coding. While
BPIONTER was removed from DIF3D-VARIANT, more work remains to be completed on DIF3D-
Nodal and DIF3D-FD which will carry into the next fiscal year. Ongoing effort is also underway to
replace entire sections of the original source code in favor of using the well tested F90 modules
along with rebuilding the input processor.

 The user manual for NUBOW-3D is complete and has been released []. The DASSH software
verification work was not completed this year as the planned effort to complete it was well below
what it actually required. The DASSH, RCT, and NUBOW-3D codes are the ones that still need
software verification to be completed at this time. GAMSOR, SE2ANL, and SE2RCT are all
scheduled to be deprecated in the coming year.

 This report discusses the achievements made in fiscal year 2026 under the SQA program
on the ARC software and dealing with outstanding identified QA gaps. It also summarizes the
development work done on the ARC software as part of this project or collaborative efforts with
industry partners to improve the ARC software.

2. ARC Software Quality Assurance Work
 The ARC software suite consists of many individual software products usable on, and in
some cases specifically tailored for, fast reactor design and analysis. As the software suite was
developed with small computational resources compared with today, most of the analysis
capability is not on explicit geometry modeling. Instead, the software focuses on providing an
analysis capability based upon a homogenized geometry treatment or simplified geometry
definition on an assembly basis. With this in mind, the main software of note for the current
external stakeholders includes the multi-group cross section library generation codes (ETOE2 [4]
and MC2-3 [2-3]), neutron and gamma transport calculation (GAMSOR [10]), fuel cycle analysis
calculation with REBUS [8], pin power reconstruction and depletion analysis (RCT [11]), steady
state thermal analysis (SE2ANL [17], SE2RCT [16], and DASSH [13,14]), perturbation and sensitivity
analysis (PERSENT [9]) and a mechanics code to assess the impact of structural forces and
irradiation induced creep during nominal reactor operations (NUBOW-3D [Error! Reference
source not found.]). Figure 2.1 shows the ARC software component (orange boxes) workflow and
their connections for typical fuel cycle analysis work.

2.1 Status of the restarted QA Program for ARC

 As stated earlier, the ARC suite was consistently being developed until the early 1990s and
had a SQA program in place up to around 2005. With funding from NEAMS [42], the ARC software
was pulled from the Source Code Control System (SCCS) repository on SunOS in 2009 and put into
a SubVersioN (SVN) repository on Linux. The NEAMS program funded the development of an
automated nightly regression testing package for UNIC and via that program the existing
regression test suite for ARC was reorganized and included. There is thus digital traceability of the
ARC software changes made since 2009, including nightly software verification reports, although
there are scant paper records to document the various release versions or software changes.
Some of the ARC software such as SE2RCT [16], SE2ANL [17], RCT [11], and NUBOW-3D [Error!
Reference source not found.] were not added to this repository until later as they were simply

 9

not being used or had only a single user and maintainer. The EBR-II Fuels Irradiation & Physics
Database (FIPD) project [20] under ART required a more rigorous QA be applied to the RCT and
SE2RCT (also known as SE2P) codes and thus they were added to the repository and the nightly
regression testing in 2017, but the funding was cut before the NQA-1 program could be put in
place. The current effort on FIPD starting in 2020 was focused on restarting the QA program for
FIPD and thus performing the necessary verification work on RCT and SE2RCT.

 The fiscal year 2023 focused on building the QA program for ARC started from the end
point of the existing development progress. In 2023, a new SQAP [39] was created around the
GitLab software version control system and it was implemented for all of the ARC software.
Considerable time was spent in fiscal year 2024 to update the automated regression testing. In a
previous program, an automated regression or continuous integration (CI) capability was put in
place for ARC which would compile and run the verification test suite for each ARC code each
night. That infrastructure used an execution and output checking methodology that was tailored
for each ARC code which was not done consistently nor documented. With the move to GitLab
and the new SQAP, this process was generalized in fiscal year 2023 but only applied to the DIF3D
software and its utility programs. In fiscal year 2024, time was spent modifying that CI version to
make a single output checking methodology viable for all of the ARC software. This will result in a
single document to describe the CI methodology for the ARC software and minor documentation
to detail the tolerance settings applied to the output for each ARC code which will be created
when we are confident that it is robust across all of the ARC codes. The previous SVN based
methodology would have required a separate document for each ARC code to detail the output
checking methodology and the tolerance settings for the output from each code. In the current
fiscal year, the CI capability was extended to all of the ARC codes. In addition, many QA gaps were
resolved by creating the necessary reports and software manuals that were previously not
available.

 As shown in Figure 2.1 and Figure 2.2, there are several different software components in
the ARC software and up to this point, VARI3D, DIF3D-K, and DPT are not presently included in
the QA program. This is primarily because the usage of these pieces of software is virtually non-
existent today and no path forward for commercialization has been identified. As this is a QA
program, one of the important tasks is to identify the commercialization needs of each piece of
software and identify the QA gaps for those pieces of software.

2.2 QA and Commercialization Assessment of the ARC Software

 Table 2.1 lists the primary pieces of the ARC software and their function where most of
these appear in the workflow of Figure 2.1 and Figure 2.2. This section will review the past
discussion on the QA assessment and give updates on the accomplished work in the current fiscal
year. From the descriptions in Table 2.1, it should be clear that the ARC software is used to do
steady state and transient analysis of a fast reactor. Steady state characterization is required to
ensure the reactor, and its associated systems, behave as expected during normal operation. This
analysis step is also important to the definition of plant conditions prior to the onset of transients.

 10

Assessments of the neutronic performance of the core, progression of the fuel cycle and fuel
performance, and status of the heat transport systems must be performed. Additionally,
performance of the plant and supporting systems during transients must be characterized to
predict the degree of satisfaction of predetermined safety metrics (e.g., peak clad temperature,
margin to sodium boiling, etc.). Accordingly, the fuel performance, including fission gas behavior
and fuel/clad motion, status of heat transport systems, structural response, and source term must
be analyzed.

 Phenomena unique to SFRs, including sodium-water interactions, sodium fire, and
inherent reactivity feedback, must also be assessed. Not all of these areas are covered by the ARC
software suite, but the pieces that have been identified with outstanding commercialization
needs are listed in Table 2.1.

3. DIF3D Software Upgrades
 The file layer in DIF3D was written in the 1960s and improved in the 1970s and 1980s.
Essentially the idea behind the capability was to abstract away regular Fortran READ and WRITE
statements to binary files in favor of interface subroutines. While the Fortran standard today has
clear unit number assignments for opened files and the Fortran OPEN statement easily allows the
user to define files, this was not the case 60 years ago and thus all of these concepts were
abstracted away to allow the software to work on different platforms with different approaches
to writing data. Further, the standard approach to executing codes in the 60s and 70s was to
partition some part of the memory to disk as the entire problem could rarely be contained in the
limited computer fast memory.

 The existing implementation is mostly used everywhere in the source code except when
reading ASCII data from the input files. Figure 3.1 shows an excerpt from DIF3D for reading such
a file. The upper section associated with the variable “NOFORM” indicates that for unformatted
input, the code is to jump to line 100 while fixed format reading continues. The Fortran READ
statement with format line number 1000 is used to read the variables NC, CB44LB, etc. The
subsequent lines convert the real precision read values CB44LB, etc. into a character string stored
in B44LAB(IC) where IC is the index position in the array. This is an artifact of 1960s and 1970s
limits on data import. The SQUEZE function removes spaces between character strings where
inputs of “FE 56” become “FE56”. For the free format section, the subroutine FFORM is used to
read a line from the input file and convert it into a string of variables. The outcome is entirely
formulaic and the error handling for input issues are handled later in the subroutine or source
code when the variables are checked for sanity. This particular convoluted method for managing
input has proven extremely problematic when debugging user inputs as the origin line of the input
error is not entirely clear.

 With the release of Fortran 90, the need for BPOINTER was eliminated, but no changes
were made to DIF3D to really take advantage of this aspect other than DIF3D-VARIANT which was
done to simply facilitate calculations. Moreover, computer memory since 2010 has become so
large that most of the concerns of the 1970s with regard to executing a DIF3D-FD or DIF3D-Nodal
calculation are completely irrelevant. Thus retaining the displayed partitioning of arrays to disk
that can easily fit into CPU memory today combined with BPOINTER severely complicates the
source code, makes it difficult to read and maintain.

 As an example of this, let’s assume the mesh to region array is a simple integer*4 array of
size 20x20x50 which is 20000 integer*4 words (~78 kilobytes). Everywhere in the entire iterative
solver part of DIF3D-FD, this array was setup to only load 20x20 or 400 words where the file layer
was used as detailed in Figure 3.4 to load the data for each plane. For each inner iteration over
planes within each Gauss-Siedel iteration over energy within each (fission source) outer iteration,
DIF3D would rewind the binary file, read to the point where the desired data was, and then read
in the data to the local memory. It does this for 10-20 arrays and most of the effort has been
focused on removing this across the entire ARC system. Figure 3.6 shows an example of the
removal of whole sections of source code to insert simple allocated arrays (DN_VOLNOD) in place
of the previous approach. As can be seen, the software is considerably simplified.

 Figure 3.6. Example Source Code Change in DIF3D to Remove BPOINTER and File Layer

 We are working either subroutine by subroutine or array by array across multiple
subroutines and use a mixture of AI and experience to clean up the source code and push all of
these arrays into memory. Periodic merges are being done as a few arrays are removed in each
code branch (FD, Nodal, VARIANT) to avoid having large merge conflicts between staff as they
work.

 Thus far, no additional arrays have been identified that need to be redone as LMA arrays
as the conceivable size of those arrays is simply way below the available memory today. To explain

 33

why, the DIF3D-FD flux vector memory requirement is proportional to the number of meshes
Assuming 230 groups, 400 assemblies with 6 triangles per assembly, and 100 axial meshes results
in an array size of 27.6 million words. This is 210 megabytes where the typical server class machine
memory exceeds 524288 megabytes today. Even if we refine the mesh to increase this by a factor
of 100, it is still irrelevant to the memory available on the machine. DIF3D-Nodal has a similar
story where it needs fewer meshes and has fewer degrees of freedom per assembly mesh than
DIF3D-FD. Only DIF3D-VARIANT has arrays that are concerning and those have been implemented
as LMA arrays since 2009. It is worth noting that when DIF3D has to switch to disk partitioned
memory in VARIANT, it so negatively impacts the performance of the server that it is very
noticeable it is happening.

 As a final statement, earlier in Figure 3.2 a partial read of the ISOTXS, COMPXS, and
GEODST files was displayed. The DIF3D and REBUS software is littered with partial reads of files
like this in subroutines all over the place. All of these binary files today have a structure to store
the entire data set and associated read, write, and print operations. Because the memory usage
of all such files, except for the NHFLUX and NAFLUX files of DIF3D-VARIANT, are unimportant, we
have made source code changes to delete the partial file reads with access to the structure, stored
perpetually, as the code executes thereby further simplifying and cleaning up the code. Thus far,
thousands of lines of antiquated source code have been discarded and we anticipate a good
twenty thousand more will be discarded in the coming year, which has and will significantly
improve the long-term maintainability of the code.

4.1.1 Adding Coarse Mesh Finite Difference to DIF3D

 Work begun on adding a coarse mesh finite difference (CMFD) acceleration to the DIF3D-
VARIANT solver to improve performance. The initial implementation followed the conventional
CMFD framework in which a low-order multigroup diffusion problem is constructed to preserve
the high-order balance through a net current correction factor ( 𝐷 ). This correction makes
equivalence between the low-order CMFD solution and the higher-order VARIANT solution at the
mesh interfaces. Once a CMFD solution is obtained, the DIF3D-VARIANT mesh-wise flux solution
is multiplicatively scaled (ratio of CMFD to DIF3D-VARIANT mesh-wise flux) to apply the
acceleration. The initial implementation has focused on using the same spatial mesh and
macroscopic cross sections as those used by DIF3D-VARIANT which avoids restriction and
prolongation operations.

 The conventional framework does work, but the efficiency degraded as the problem
became complex and the stability was strongly limited by the convergence on the partial currents

 34

at each outer. While increasing the number of partial current iterations did improve the stability
of the CMFD acceleration, this degrades the effectiveness of the acceleration as the
computational cost for each outer is artificially driven up. An assessment of the work indicated
that both the flux and partial currents in DIF3D-VARIANT must be accelerated as DIF3D-VARIANT
is fundamentally based upon the partial currents. As an alternative, a CMFD acceleration of the
partial current was introduced based upon the p-CMFD formulation [52]. At the end of each CMFD
solve, the outgoing partial currents are updated using a partial current correction factor:

where 𝐽 denotes the high order partial outgoing current result at surface 𝑢. The performance of
the CMFD acceleration was assessed using the Takeda Model 3 benchmark. This benchmark is
based upon and ZPPR experiment and consists of an axially heterogeneous small core containing
inner and outer cores, blankets, and reflectors, and comes with a 4-group cross section set with
an isotropic scattering kernel. The 160 × 160 × 90 cm domain is discretized into 32 × 32 ×

fission source error falls below 10 . The reference calculation converges in 34 outer iterations
with an effective multiplication factor of 𝑘 being 1.021973. The converged CMFD accelerated
calculation reproduces this to within 0.05 pcm.

 Figure 4.1 compares the fission source convergence behavior of DIF3D-VARIANT (termed
nodal-only) and the conventional CMFD accelerated scheme (orange and green curves) and the
p-CMFD accelerated scheme (blue curve). With the default number of partial current sweeps
(NZSWP=2), the conventional CMFD accelerated result converges much slower. The fission source
error stagnates at approximately 10 and shows no further reduction even after 60 outer
iterations. Increasing the fixed number of partial current sweeps from 2 to 5 stabilizes the CMFD
acceleration and reduces the required number of outer iterations from 34 to 17, demonstrating
that the CMFD acceleration itself remains effective when additional effort is expended on the
partial current convergence. However, the reduction in outer iterations does not translate to a
comparable reduction in total computing time because each outer iteration takes more than twice
as much effort as the default algorithm because of the higher partial current iteration count. The
p-CMFD acceleration relaxes the partial current convergence requirements completing the task
in 25 outer iterations rather than 34. This demonstrates the potential of p-CMFD acceleration, but
the overall acceleration is modest given that the CMFD solve time is non-trivial.

 Further work needs to focus on establishing a generally robust and computationally
efficient CMFD acceleration strategy for DIF3D-VARIANT. The testing on the verification work has
only been done on Cartesian geometry, and the implementation needs to be extended and tested
on hexagonal geometry. Additional parametric studies are also needed to better assess
convergence behavior and determine suitable coupling parameters that provide stable CMFD
acceleration and robust low-order convergence across a wide range of problems, including more
challenging configurations. For certain the CMFD algorithm will excel when solving high
dominance ratio problems which at present was not tested.

4.1.3 DASSH Geometry Changes and Clad Damage Evaluation.

 The geometry handling detail was modified previously to allow the user to specify different
pin geometry (or porous body medium) models for each axial segment of each assembly. This
year, the tube geometry capability was added to DASSH. Figure 4.2 shows the basic detail on how
the tube geometry model differs from the pin geometry setup. The subchannel meshing strategy
is rather different from the pin-cell geometry which is viewable in the figure as the fuel pin lattice
on the left has 18 coolant subchannels and 12 duct wall subchannels while the reflector block
picture on the right has 7 coolant subchannels and 6 duct wall subchannels.

 Figure 4.2. Two Pin Ring Fuel (left) and Seven Coolant Channel Reflector (right).

 For the reflector assembly, the coolant flows through the seven cylindrical holes instead
of around the fuel pins, thus necessitating a different connection between the duct wall and the

 37

coolant subchannels and the different meshing scheme. Because the typical design involves
loading solid blocks of reflector material inside of a duct, there is a slight tolerance gap which is
filled with coolant between the reflector block and the duct wall in Figure 3. This is not treated in
DASSH but is assumed to be handled by a user adjustment of the duct wall conductivity as is
needed.

 To allow the new geometry, multiple sections of DASSH had to be updated from the
subchannel meshing to the temperature solver. The axial interpolation scheme also had to be
updated to facilitate interpolation from a tube geometry to a pin lattice one and vice versa. The
existing algorithm uses the same power distribution model as the pin lattice such that the power
is not delivered to the gray block structures around the coolant channels in Figure 4.2, but directly
to the coolant channels. This poses somewhat of an error as the heat transfer coefficient will act
in the reverse manner of its intention in the physics, but given the power delivered to the block
must be removed by the adjacent coolant channel or a coolant channel in an adjacent assembly,
it is not expected to be an egregious error. This again can be adjusted by manual modification of
the heat transfer coefficient in the input assuming some measurement exists to justify it.

 Figure 4.3 shows the difference in the coolant temperature distribution at the active core
midplane for a test problem to display the differences in solution from using the tube and pin
lattice geometry options. The flow area of the tube geometry and the reflector lattice are
equivalent in this problem, and one should understand that the tube geometry has a substantially
lower pressure drop than the pin lattice geometry. In this example, various states of the pin lattice
geometry are used with and without LFC (low flow conduction) and are compared against the
tube geometry model with and without heat delivered to the duct wall. The LFC was introduced
in DASSH to counter the errors that occur in low flow regimes when using the forced convection
algorithm in DASSH. The tube geometry model with heat delivered to the duct wall (middle right)
is the best one to use and it should be clear that none of the pin lattice approaches (with or
without LFC) produce a comparable solution to it, especially for the assembly bypass gap region.

 In addition to this change, the DASSH software was modified to provide the user with a
clad damage assessment everywhere in the domain. The VARPOW manual [18] details the clad
damage functionality where VARPOW is called as a subroutine by DASSH to get the spatial
distribution of power, fast flux, and now clad damage. The damage evaluation should consider
dehomogenization and thus one should recognize that the VARPOW approach is a measure of the
global gradient in the clad damage cross section evaluation and does not consider local gradients
(i.e. same as the pin power approach). For further details, it is recommended the user consult the
VARPOW manual on how to properly generate clad damage output from DASSH. The damage
evaluation in VARPOW provides the user a table of peak dpa/year (displacements per atom per
year) for a given time point in the DASSH calculation, an example of which is shown in Figure 4.4.
While the width of the table is truncated, one can easily identify the assembly ID and the assembly
location in each line along with the column information indicating which pin in the pin lattice of
that assembly and axial location had the peak clad damage evaluation. It should be noted that
clad damage is a function of flux magnitude and that the values can change dramatically from one

4.1.4 PyARC Activities

 In FY26, PyARC underwent several upgrades and saw three version releases (v3.0.1 in
March 2026, v3.1.0 in June 2026, and v4.0.0 in September 2026). Four major code integration
upgrades were completed: DASSH free-form geometry support, support for SCALE 6.3 for coupled
REBUS/ORIGEN-S calculations, transition to using GAMSRC instead of GAMSOR, and bowing worth
calculations with NUBOW-3D and PERSENT.

 As noted in Section 2.2, the GAMSOR code is planned for deprecation and therefore
needed to be removed from PyARC. PyARC updated the DIF3D/GAMSOR workflow to use a
GAMSRC based workflow instead, allowing for GAMSOR to be fully deprecated.

 The DASSH integration was upgraded to support free-form geometry definitions, which
was added in the ARC v12.2.0 release. This eliminated virtually all DASSH-imposed restrictions
that previously limited the number and location of axial zones allowed in each assembly.
Additionally, PyARC added the option to use grid spacers instead of wire wrap and define tube
lattices for DASSH.

 The connection between NUBOW-3D and PERSENT was added to do core bowing reactivity
worth calculations based on the workflow demonstrated with the ARC codes in [53]. This is a 7-
step workflow involving REBUS, DIF3D, MC2-3, GAMSRC, DASSH, NUBOW-3D, and PERSENT
calculations. The calculation workflow for the first 6 steps (REBUS to NUBOW-3D) is already
established in PyARC as of v3.0.0. The final connection between NUBOW-3D and PERSENT in
which the strain data from NUBOW-3D is given to PERSENT to perform a bowing worth calculation
was established this fiscal year in PyARC.

 SCALE’s ORIGEN-S is integrated into PyARC for coupled REBUS/ORIGEN-S detailed nuclide
tracking. The original integration supported SCALE 6.1 [54] and SCALE 6.2 [55], both of which use
a legacy SCALE input form. With the release of SCALE 6.3 [56], the input form for ORIGEN-S
changed entirely and thus PyARC was incompatible. A significant upgrade to this integration was
completed to support both the SCALE 6.1 and 6.2 legacy input form and the SCALE 6.3 modern
input form.

 Along with these major upgrades, there were several minor, but still significant, user-
experienced updates. PyARC saw the completion of the language server upgrade that was started
in FY25 [57] with the added support for autocompletion in the Workbench GUI. The support for
running the ARC codes on Windows was improved. The user setup experience was improved for
better reliability. Additionally, many minor changes or bug fixes were completed driven by
engagement with users, and several modules were refactored to support long-term
maintainability.

 In addition to the extensive code developments, the PyARC team also started formalizing
a SQA program with the creation of an initial SQA Plan (undergoing internal review at the time of
this report), independent of the ARC SQA program. An initial gap analysis is reported separately
in the dedicated FY26 PyARC status report.

5. Conclusions
 Considerable work was done this year to start the clean up process on the older parts of
the ARC system. The main focus was to remove BPOINTER usage from the solvers along with the
antiquated file layer that underpins DIF3D. The arrays fully contained in BPOINTER were relatively
easy to remove, but those that were intertwined with the file layer proved to be difficult to
remove. As an example, all of the solvers were setup to assume that only a single plane of
geometry data and single group of cross section data was available at any time. Thus in every
planer iteration in every axial inner iteration of every outer iteration, the data from multiple arrays
was retrieved from disk which impacts performance of the software. Removal of all of these
aspects was completed with DIF3D-VARIANT with DIF3D-Nodal almost fully complete. DIF3D-FD
is the simplest algorithm of all of them, but it proved to be the most difficult to deal with as it has
multiple pathways (and setups) the solver algorithm takes through the source code depending
upon how starved it is for memory. The work to remove the older source code aspects will
continue into the next fiscal year where we will likely truncate the DIF3D-FD tree to avoid updating
low memory solver algorithms that will never be used again.

 The preceding work was focused on the solvers and not the input and output aspects.
Additional work was started this fiscal year to rebuild the entire input interface. By rebuilding this
capability, we can completely discard the old approach in favor of an input capability that can be
tested independently of the code that uses it. Replacing the input interface of DIF3D in the next
fiscal year is a major goal of this project.

 Time was also invested on doing commercial grade dedication software verification work
on DASSH. The cost to complete the work was underestimated which was due to the sheer
number of the outputs and capabilities that needed to be verified. It is worth noting that the
verification work on DASSH expanded this year because a tube geometry model was added along
with a clad damage output. This latter feature was added so that we can move towards
deprecating SE2RCT in addition to providing users valuable information. Work will continue in the
next fiscal year to complete the software verification on DASSH noting that deprecating SE2RCT
will avoid having to duplicate the software verification effort on DASSH on SE2RCT.

 A manual for NUBOW-3D was created this year to detail the present capabilities of the
software. Many changes were made to NUBOW-3D in the past few years to improve the user
interface and fix various source code issues. The SE2ANL software was deprecated this year and
because the GAMSOR workflow in PyARC was replaced with a GAMSRC workflow, the GAMSOR
software will be deprecated at the end of the current fiscal year or early in the next fiscal year.

 The focus on resolving the QA gaps in the ARC software cited in this report will continue
in the coming year as more missing documentation is created. At present only a fraction of the
originally missing documentation is still missing. One aspect to resolve next year is the software
verification work for NUBOW-3D and complete it for DASSH. In the coming years, the remaining

 42

QA gaps identified in this report will be addressed which should yield an ARC software product
that can better facilitate the commercialization needs of industry.

 Non-trivial industry partner software development funds were provided this year. Funding
was provided to incorporate CMFD (coarse mesh finite difference) acceleration in DIF3D-VARIANT
to improve its performance. This work showed promise but was unable to be fully completed this
year. Funds were also provided to support the inclusion of clad damage evaluations in VARPOW
and the documentation was updated consistently. Overall progress on resolving the QA gaps has
been good this year.
