1 Introduction
This report presents the modeling and simulation capabilities of Argonne National Laboratory’s
VARPOW code [1] that is used in present reactor analysis activities. These capabilities will then
be used to establish the set of VARPOW verification tasks necessary to verify VARPOW for usage
on commercial projects. A similar approach was taken for the PERSENT [2], REBUS [3] and
DIF3D [4] [5] [6] [7] software packages.

The VARPOW program is a post-processing utility program for DIF3D, specifically DIF3D-
VARIANT [6] [7]. As covered in [1], the VARPOW program was built to provide input for follow-
on steady state thermal-hydraulic analysis. Its primary purpose is to act as the interface between
DASSH [8] and DIF3D-VARIANT. The outputs from VARPOW are contained in three output
files: Output.VARPOW, VariantMonoExponents.out, and MaterialPower.out. Recently the clad
neutron damage calculation capability was introduced into VARPOW, and it now allows a
pathway to get distributions of clad DPA. This newly added DPA calculation also needs
verification.

2 Commercial Usage of the VARPOW Software
Because the VARPOW utility program is not an integral part of the ARC (Argonne Reactor Code)
system [9], its usage by commercial entities is neither guaranteed or constrained. Figure 1 shows
the present connections of DIF3D, noting that it is a necessary component if the overall goal is to
perform safety analysis of a proposed reactor design in the ARC system. VARPOW is not a
necessary component in that same context unless the commercial entity chooses to make it part of
their workflow, which would be covered by their own version of Figure 1. The breakdown in
identifying the critical engineering outputs of the VARPOW software normally starts by looking
at which outputs from VARPOW are being used by the analysts in the design process. Because it
does not have a defined role, we simply focus on verifying all of the existing output.

 2.1 VARPOW Inputs and Outputs to Verify
VARPOW is a utility program and has no required input file as it just runs from command line
arguments. The input format is based on whether GAMSOR or DIF3D output files are being used,
with the main difference being that GAMSOR output includes both PMATRX and GHFLUX files
and DIF3D output includes a ISOTXS file. When VARPOW is executed without a valid number
of arguments, it provides the input syntax format description as seen in Figure 2. From this brief
description, one can see that there are two ways, via the provided input, to execute the VARPOW
program:
 1) For GAMSOR: varpow.x <iTypeFuel> <iTypeCool> <iOutput> <PMATRX>
 <LABELS> <GEODST> <NDXSRF> <ZNATDN> <NHFLUX> <GHFLUX>
 2) For DIF3D: varpow.x <iTypeFuel> <iTypeCool> <iOutput> <ISOTXS> <LABELS>
 <GEODST> <NDXSRF> <ZNATDN> <NHFLUX>
The PMATRX, ISOTXS, LABELS, GEODST, NDXSRF, ZNATDN, NHFLUX, and GHFLUX
files are all interface files generated by the Argonne codes DIF3D, MC 2-3, REBUS, and
GAMSOR. A detailed description of each input can be found in the VARPOW user manual [1]
with test cases in [10], and so further discussion is not necessary here. All of the other input options
shown in Figure 2 must be verified as part of this work. All of the input options used to execute
VARPOW must be tested as part of this work. Their impact upon the output should also be verified.
The required VARPOW specific input parameters are:
 1) iTypeFuel
 2) iTypeCool
 3) iOutput
iTypeFuel refers to the fuel form, with four options for: Zr-alloyed metal fuel (1), oxide (e.g., UO2
or PuO2) (2), nitride (e.g., UN or PuN) (3), and aluminum-alloyed (e.g., U-Al) (4). Note that the
list of options is not exhaustive for all possible fast reactor fuel forms. iTypeCool refers to the
system coolant, with five options for: sodium (Na) (1), molten salt (NaCl) (2), lead (Pb) (3), lead-
bismuth eutectic (Pb-Bi) (4), and molten tin (Sn) (5). Again, the list of available coolants is not
exhaustive but should serve the needs of most designs. iOutput refers to how the output files should
be formatted. There are four possible options: either (normalized) monomial (options M and S) or
(unnormalized) polynomial (options P and T) for power distribution, with either mesh-averaged
neutron heating and gamma heating (options M and P) or fuel-, cladding-, and coolant-specific
neutron heating and gamma heating spatial distributions (options S and T). The fast flux and clad
DPA spatial distribution in each mesh are also printed in the last column regardless of the option
selected. In summary, the neutron and gamma heating distributions are given in either two or six
components, with the option to be normalized or unnormalized, by choosing one of the four
options. Initial testing between two- and six-component cases showed that the temperature
distribution impact was in the fourth significant digit (a sodium cooled, metal fueled fast reactor),
showing minimal advantage in using the six-component option [1]. Further, DASSH prefers to use
normalized results so that it does not need to needlessly normalize the results itself when running,
so option M is recommended for DASSH applications.
 In addition to these required command line input arguments, VARPOW has an optional input
file called AssignIsotope.inp which allows the user to directly assign isotopes to a particular

material classification (fuel, cladding, or coolant). To calculate the clad DPA correctly, the
displacement energy (in unit eV) of the clad isotopes must be provided in AssignIsotope.inp,
otherwise a default value of 109 eV displacement energy is applied thereby yielding clad damage
outputs of ~zero. An example input file is provided in Figure 3. This input assumes the user is
interested in the S and T iOutput options. When processing region-homogenized isotopic results
from DIF3D or REBUS, AssignIsotope.inp allows the individual results to be regrouped
accordingly to their respective classification. If not explicitly assigned in AssignIsotope.inp, then
VARPOW will use the algorithm in
 Table 1 to determine where each isotope should be grouped.
The output from VARPOW is a series of files identifiable in Figure 2 as:
 1) Output.VARPOW
 2) VariantMonoExponents.out
 3) MaterialPower.out
Figure 4 through Figure 7 show output excerpts of VARPOW terminal output and output files.
Output from the terminal when running VARPOW can be found in Figure 4 and Figure 5. Figure
4 deals with terminal output for cases involving the optional AssignIsotope.inp input file. Figure
5 shows power results using the six-component option without normalization (iOutput option T).
Output.VARPOW is a NHFLUX formatted file. A description of how an NHFLUX file is
formatted can be found in [5,6]. VariantMonoExponents.out output is virtually identical to the
output file of the same name coming from running the program EvaluateFlux. An example output
from VARPOW is shown in Figure 6. MaterialPower.out contains data for the power density using
the six-component format (fuel, cladding, and coolant neutron heating and fuel, cladding, and
coolant gamma heating). There is data for each mesh in the original DIF3D or REBUS model
(same xy radial indices and z axial indices). An excerpt from the MaterialPower.out file is provided
in Figure 7.

 2.2 VARPOW Identified Verification Tasks

From all of the outputs, it should be clear that the power distribution (from both neutron and
gamma heating) is the primary piece of data to verify. The mesh index and fast flux associated
with each evaluation point are also important aspects to verify. The preceding dissection and
identification of the output from VARPOW yields a set of tasks to accomplish as part of the
verification work. Table 2 gives the identified task list for the verification work where the category
number refers to a specific functional use of the VARPOW software.

 Table 2. VARPOW Identified Verification Tasks
  Category Verification Tasks
 Verify the terminal output from VARPOW is correct
 1 a) Verify the isotope selection adheres to the provided input
 b) Verify the material power output is correct
 Verify the Output.VARPOW file is correct
 a) Verify the power distributions are correct
 2 b) Verify the fast flux distribution is correct
 c) Verify the clad DPA distribution is correct

As seen, the set of verification tasks correspond to each output file and the engineering outputs
appearing in each file are listed as verifiable tasks. As this pertains to the entire output available

problem and which output from VARPOW is being verified.

3 Planned Verification Exercises
This section will summarize the anticipated test problems and how they will satisfy the verification
tasks in each of the three categories identified in Table 2.

 3.1 Verification Methodology for the File Output.VARPOW
The DIF3D-VARIANT code will produce an NHFLUX file required for running VARPOW.
VARPOW will produce Output.VARPOW, an NHFLUX-formatted file with power distributions
formatted one of four ways: normalized or unnormalized and using two components (neutron and
gamma heating) or six components (fuel, cladding, and coolant neutron heating and fuel, cladding,
and coolant gamma heating). Regardless of option, this file will also contain the fast flux
distribution. Verify these results agree with the NHFLUX file. Repeat this process when using
GAMSOR derived input.

 3.2 Verification Methodology for the File VariantMonoExponents.out
Pick points that are known to intersect specific meshes in the domain and verify that VARPOW is
producing the same flux solution at those points. Use the VariantMonoExponents.out data from
VARPOW to define the basis and the PrintTables program to display the NHFLUX-formatted file
to facilitate a hand calculation. Note that the work done to verify this output in EvaluateFlux can
be used to verify the VARPOW output without additional work.

 3.3 Verification Methodology for the File MaterialPower.out
The power density in each mesh is specified in the six-component heating format. Verify that these
power densities agree with the REBUS and GAMSOR input path options to VARPOW.

4 Conclusion
This manuscript described the VARPOW capabilities that can be used by commercial entities. In
that process, the engineering output created by the VARPOW capabilities were displayed and
discussed. These engineering outputs define requirements from the software that were used to
create a verification task list. A potential means to test the various aspects was presented. The
verification work is planned to be performed using the latest release of the VARPOW software
version 11.0, release 3284, however the final report will clearly state the version of VARPOW and
system that was utilized. Further, the verification work will yield a set of new verification test
problems which will be included in the routine verification of the software such that it is both
repeated and distributed for all future VARPOW releases and operating environments.
