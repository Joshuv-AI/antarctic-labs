ABSTRACT
This report documents the work done as part of the “Enhancing Developer Productivity” level 2
milestone. The team for this project was assembled from multiple SIERRA teams and worked
throughout the year on several different productivity initiatives and scoping studies.
The team surveyed developers about impediments and successes; improved our CI pipeline
monitoring and reporting; developed tools for line coverage reporting and analysis; improved
compiler warning adherence in SIERRA; prototyped static analysis, AI, and mutation testing tooling
in SIERRA; and developed a 3-5 year SIERRA plan document to help these initiatives continue past
this milestone. Many of these efforts involved various teams testing out the new tools and as a result
there were multiple improvements to the SIERRA code and test suite realized this year, with more
planned as part of the 3-5 year plan.
The milestone team presented their results to the developer community at reviews during most
sprint weeks, as well as to the milestone panel throughout the year. This document summarizes the
content of those presentations and the final milestone results.

EXECUTIVE SUMMARY
The Compsim Collab Team was assembled from developers across SIERRA to make broad cross-
team changes that would improve developer productivity and better position SIERRA for continued
use as a primary ModSim tool for the ND mission at Sandia. The key accomplishments of this team
were:
Data Collection – One recurring theme of the milestone work was collection or more data to
inform decisions by developers. The milestone team developed tools for extracting granular line
coverage data from our code and test suite. This data was used to generate regularly updated HTML
line coverage reports, developer tools for examining impacts and usefulness of specific tests, and
deploying an optimized set of tests for use in our CI processes that has measurably reduced CI
turnaround time (often by 1-2 hours for coupled code changes). The team also expanded our data
collection for both CI and nightly test processes to both monitor for issues and quantify potential
impacts of new changes/practices. This data collection is automated, reported to an accessible
HTML page, and fully open to the development community.
Code Quality – As a part of adopting modern software development practices, the Collab team
focused on addressing compiler warnings and using line coverage data to improve both our code
and test suite. We reduced the number of warnings in SIERRA by a factor of 5 (about 25,000 down
to less than 5,000 warnings, mostly remaining in external code) and are well positioned to move to a
fully clean build state with the new Spack build system. We implemented changes to prevent
recurrence of these warnings, and in the process of addressing them found and fixed numerous
actual code bugs. We were also able to use these tools to identify large sections of code that could be
completely deleted (more than 50,000 lines worth), reducing build and maintenance costs. We have
also deleted approximately 100 tests that were quickly identified as duplicates or not providing
unique or valuable coverage as a pilot using the new tooling – work that we plan to continue in the
coming years.
Developer Tools – In this milestone we evaluated using the Sandia Atlas AI interface as a
developer assistant in Visual Studio Code, tested new static analysis workflows, and developed tools
for using the line coverage data collected from the code repository in local workflows to assess
individual tests. The team also developed new developer documentation of our CI process and
presented it to the development community to help gain a better understanding of the automated CI
processes by all developers who use them. The team also deployed a mutation testing workflow in
SIERRA using an open-source mutation testing library for C++ code and piloted using it on a
subset of SIERRA to improve the quality of our unit tests. Further use of this tool is planned for
future years.
Roadmap – To ensure that these changes continue to have positive impact on SIERRA developers,
the team worked with the SIERRA PO leadership team and the SIERRA Chief Architect to put
together a 3-5 year plan for SIERRA to continue to use these tools and move towards some of the
longer term goals the team identified, such as sustainable test suite, performant CI, further
integration of AI tools, and continued software practice improvements.

1. INTRODUCTION

“Compsim Collaboration Team”, was assembled with members across multiple Compsim/Sierra
teams to help jump-start developer innovation by focusing on potential new practices and
capabilities developers can use to improve both productivity and software quality. The work was not
meant to complete every task identified – some are long-term practices and maintenance tasks that
will require multi-year efforts across teams. To facilitate such tasks, the team also prepared a 3-5 year
SIERRA roadmap for including such tasks and adapting to new emerging technologies like AI tools.

 As ModSim becomes more critical to accelerating model development for weapon design and qualification, integrated

 modernizing software development and deployment by removing inefficiencies in the software engineering process and
 toolchain. Through a cross-team effort, this milestone will seek to modernize and improve the development, testing,
 and deployment of the core SIERRA codes.

2. MOTIVATION
SIERRA is a finite element software suite consisting of many applications and libraries. The code
repository is largely stored in a single repository with a single build system. It is used for a wide
range of Sandia mission areas and by partners outside the lab (both government and commercial).
SIERRA also includes many software libraries shared with tools outside SIERRA (e.g. RAMSES)
and with contributors from multiple areas/teams. The SIERRA codebase currently has O(100)
developers of varying levels of involvement making regular contributions.
SIERRA continues to grow over time (Figure 1) in both lines of code and number of executables.
Adapting to new computing architectures and build paradigms while adding new capabilities and
maintaining legacy capabilities becomes more costly as the codebase grows.

 Figure 1. SIERRA growth over time

As the software products in SIERRA have become more coupled the development and testing
practices have evolved as well. The older practice of manual local testing of a single product has
been replaced with per-change automatic testing and building of multiple products in an automatic
CI system.
The size of the SIERRA test suite also continues to grow (Figure 2) and the frequency of running
tests has also increased. Instead of just running nightly tests, we run O(100) CI pipelines per day that
target multiple compilers and do both builds and tests. The loss of machines in the CI and
distributed build/test pools have increased the cost of running these tests.

 11

 Figure 2. SIERRA test suite size

Most legacy codes in SIERRA rely heavily on regression tests – tests that run a complete application
case and usually compare the exodus output with a saved exodus gold file. These tests are relatively
expensive, and when they fail can be difficult to track down the reason for the failure or specific
software component that caused the failure. Many of the newer products in SIERRA have embraced
a more modern unit testing approach for their software, creating a larger number of faster running
tests of specific parts of the code itself. These unit tests typically run orders of magnitude faster than
regression tests (milliseconds instead of minutes) and provide much more targeted information
when they fail (usually pointing to a specific function or software component).
The objectives of this milestone are:
 • Reduce the cost of developing new features
 • Reduce the cost of maintaining existing capabilities
 • Improve the quality of our software products
 • Ensure SIERRA uses appropriate state-of-the-art modern software development practices

4. CI METRICS AND USABILITY
Usability and performance of the SIERRA CI system was a topic identified in both the Collab Team
brainstorming sessions and by the initial developer survey. As a result, the team focused on several
different improvements to the CI process.

4.1. Documentation & Metrics
One frequent developer complaint is that they do not know what CI is doing, or why it reported
what it did. To try to improve this and reduce the load of support tickets on the SIERRA DevOps
team, the Collab Team put together a set of “live” slides documenting the CI process and did several
presentations to the developer community sharing how it works. The documentation is archived on
Teams and available to all developers and will be kept up to date going forward as CI changes.
Additionally, a new Gitlab label was created that developers can add to a merge request when there
is a CI issue to get help triaging it without having to file tickets.
Prior to this Collab Team work, the CI scripts had been instrumented to begin to collect some
timing data for the various steps of the CI process (configure, build, test). As part of the Collab
Team work the data collected was expanded to include additional information about dependencies
and the amount of work done in each of those steps. A daily scheduled Gitlab pipeline was set up in
the 1540 Insights repository which reads this data, generates plots, and updates a Gitlab pages web
page accessible to all developers (http://1540-compsim.cee-gitlab.lan/sierra/insights/). This page
includes developer resources (including a link to the CI documentation), daily timing plots for CI,
and plots for nightly test costs per team.

data was used to improve our process. For example, Figure 7 shows that prior to September 2024 a
large fraction of test runs were hanging for the 4 hour limit before being restarted. That issue was
resolved, and that data artifact has not reoccurred. These plots show the times for all CI runs over a
long time window, with black lines indicating the weekly 10, 50, and 75th percentiles.

4.2. Reliability
Another common complaint about CI is reliability. The SIERRA CI process uses a tool called
LARRY to determine which tests should be run for a given code change. This tool uses the LLVM
sanitizer coverage feature to generate an instrumented build of SIERRA that is run nightly on all

 18

tests (with a few exceptions). When a function is executed by a test, the file it is contained in gets
written to a log file for that test, and all the log files are collected to generate a mapping of source
files to tests. When a merge request modifies a given source file, it is located in the LARRY database
and the tests associated with that file are added to the list of assigned tests.
Unfortunately, this process had several known gaps that could lead to broken builds or test failure
that would pass CI but show up as failures in nightly testing. The primary gaps identified in this
process are listed in Table 3, along with their resolution status to date. Many of the gaps are listed as
“Mitigated” since the changes in LARRY Fix 1 substantially reduce the ways those gaps could cause
failures in CI, but they do not completely eliminate them for all cases.

4.2.1.     LARRY Fix 1
The first fix to LARRY was a change for how tests are assigned when a source file is not present in
the LARRY database (non-C, header, new file, etc). The former behavior would just assign 0 tests
for that file, and then after processing all changed files if the total number of tests was 0 CI would
assign a fallback of all unit or distribution tests for all products.
As a part of this fix, the LARRY database generation process was modified to use the dependency
information that already existed in LARRY to determine a set of default tests to assign to each
product, including dependency information (Figure 10).

 19

 Figure 10. LARRY augmentation for setting default tests per product to handle missing files

If a modified file is not in the LARRY database, we first check if it is a “high risk” file (related to the
build system or parser). If so, we assign the complete list of unit and distribution tests for all
products to that file. This way even if that file’s change is mixed in with other source files the
appropriately wide set of tests is assigned. If the file is a new file, we assign only unit tests for the
product the file is being added to. If the file meets none of those criteria, we assign the unit and
distribution tests for the modified product and anything that depends on the modified product (as
identified by the scheme in Figure 10). This prevents issues with cross-library dependencies while
avoiding an expensive “all of SIERRA” build.
While these fixes remove many commonly encountered gaps in LARRY, they do not completely
eliminate them. As an example, consider the two change sets in the figure below, where we change
an interface in a library header file and its use in that library’s unit test. In Change Set 1, the header
file only defines the interface and would not be present in LARRY. With this LARRY fix, this
change would fall back to finding unit and distribution tests for the library and anything that
depends on the library (preventing build errors in any apps that are implementing that interface).
However, for Change Set 2, since the template function in the header file is used in the library unit
test, the header file would be in the LARRY database (with only the library unit test listed if that is
the only place it was used) and the fallback to find dependencies would not happen. Any
downstream apps that were using that interface could be broken by this change and would be
missed in CI. As such, while this LARRY fix mitigates many issues, it is not a complete solution.
Using a pattern of “one definition per file” can also mitigate issues like this since LARRY entries are
collected per source file. The changes made in LARRY Fix 2 to properly map inline functions in the
LARRY database may also make this gap more common than it currently is (although it is still
expected to be rare).

 Figure 11. Example change sets with potential LARRY gaps

4.2.2.    LARRY Fix 2
The second fix to LARRY was implemented in the new Spack build system only, so it is not
available in the current LARRY database yet (which is still generated by bake). This fix modified the
build flags used in the CMake LARRY build to add LLVM sanitizer hooks into Fortran files and
turn off inlining of functions so that inline functions are correctly mapped in the database. These
changes will have an adverse impact on runtime performance of the LARRY-instrumented build,
which has yet to be assessed. In addition, install-time checks were added to the Spack build to run
several simple instrumented executables that ensure that the LARRY instrumentation works
correctly for several conditions (including Fortran functions, inlined header functions, template
functions, and library functions). Once the nightly LARRY build switches to using a Spack build,
these improvements will show up in the LARRY database used in CI immediately.

4.3. Performance
Another recurring complaint about the SIERRA CI system is the turnaround time (TAT). It can
often take several hours for all the CI pipelines to complete, which can inhibit rapid development
cycles. The Collab team implemented several improvements here, and continuing to improve this is
a long-term goal in the 3-5 year SIERRA plan. The Collab team efforts in this area focused on using
line coverage data to define a reduced set of tests to run in CI (described in a following section).
Current work on the new Spack build system by the SIERRA DevOps team is focused on package
reuse to reduce build times in CI. Combined with reduced test load from this team’s work and use
of faster HPC resources for CI we believe substantial improvements in CI TAT are possible for
SIERRA.

5. LINE-COVERAGE TOOLS
Line coverage data (lines of code hit by a set of tests) was identified by the team as a data set that
could provide a substantial amount of useful information about strengths, weaknesses, and general
gaps in our test suite. SIERRA used to have a daily HTML line coverage report, but it relied on
custom tooling for processing the coverage data that stopped working after GCC 7, so it hasn’t been
available for several years. The collab team investigated alternate approaches that would let us start
acquiring that data again using modern tooling. The “gcovr” python package (originally developed at
Sandia, and now open source) was tested on our codebase and found to work reliably and have the
feature set needed not only for generating HTML reports but also for generating more granular data
needed for more in-depth coverage analysis workflows described in the following sections.

5.1. Line Coverage Reports
One of the requested capabilities identified in the developer survey was a regularly updated
automatic line coverage report for SIERRA. The necessary build system flags for activating a
coverage run were still present in our bjam build system, so the collab team was able to use those to
set up a scheduled line coverage job that runs once a week and updates a line coverage HTML
report using gcovr deployed on the previously mentioned Insights Gitlab pages web site.
Development teams have been using this for much of the year and have found it useful for
discovering gaps and making improvements in our test suite. A few examples of specific actions
taken from this information are:
 • Discovery of a set of unit tests designed to be run on X cores that was only being run on Y
 cores and was just exiting early instead of actually testing anything (shown by having zero
 line coverage)
 • Discovery of thousands of lines of “abandoned code” – which is not called or callable from
 anywhere and can simply be deleted
A more in-depth example of the usefulness of the Sierra line coverage report in ensuring code
correctness is provided in the next section.

5.1.1. Sandia Toolkit
The Sandia Toolkit (STK) provides foundational infrastructures for the multi-physics products
developed under the SIERRA umbrella; it is also distributed as a Trilinos package, where it is utilized
by other software packages inside and outside of SANDIA. STK packages include unstructured
mesh data generation, input/output tools, geometric proximity search, transfers, MPMD coupling
support, and various other utilities. Since these products are widely used across a large range of
software products, bugs that “slip” through due to inadequate testing can lead to serious
consequences out in the wider software community. To prevent this from happening, the STK team
heavy emphasizes code development that can be easily, inexpensively, and thoroughly tested through
application-agnostic unit testing. This section serves as a demonstration of how the new SIERRA
line coverage tool can help the team maintain extensive test coverage of all their products.

5.2. Coverage Matrix Test Analysis Tools
In addition to generating HTML line coverage reports, the output from gcovr can also be used to
generate a test coverage matrix. To do so, each test must be run individually, and its coverage
information saved off. This contrasts with the process for generating the HTML reports where we
run all the tests, then wait until they are done to process the merged coverage data (a much faster
process). An example of how the data in a coverage matrix is arranged is shown in Figure 19 below.
Each column in the matrix corresponds to a single test, and each row corresponds to a line of code.
For SIERRA, the coverage matrix has about 1 million rows. The number of columns will depend on
the tests selected – all of SIERRA would have about 20,000 columns. From this matrix, a “Test Set”
can be defined based on a 1D array of 0/1 or True/False values equal to the number of columns in
the coverage matrix. Additionally, the matrix can be filtered down by only including rows matching
some specific pattern - for example starting with “app/” to only include lines from a given app. The
actual entries in the matrix (numeric values) are the number of times that line was hit by that test.
The matrix can also be represented more compactly with True/False values corresponding to

 27

whether the number of hits is greater than 0 or not. The actual number of hits does not come into
play in any of the algorithms used in this work.

 Figure 19. Coverage matrix schematic
Given a coverage matrix of this form, there are several operations one can perform. For example, a
set of multiple tests (e.g. all small tests) can be summed into a single column. Any given column can
be converted into an html report using gcov. Multiple columns can be differenced using standard
Numpy operations to show things like coverage from one column/set that is not covered by
another column/set. This lets us easily do things like find what unique lines a given medium test
covers that the set of small and unit tests do not.
Some examples of how this tool can be used locally by developers are:
 • Find the most expensive test and generate an HTML reporting showing what unique
 coverage that test provides relative to the small and unit tests, or showing the full coverage
 of that test.
 • Look at whether any core libraries (like STK) are getting code coverage from downstream
 app tests that their own tests miss.
 • Scanning the test repo for duplicate or highly similar tests (described in a following section).
These tools will need to be adapted once we move to a Spack build in order to keep them working
properly for SIERRA.

5.2.1. Optimized CI Test Set Tool
Using the coverage matrices and nightly test cost data, a CI test optimizer Jupyter notebook was
prepared in this work and archived in the Insights Gitlab repository. This tool uses a greedy
algorithm to determine a reduced set of tests to use in CI, using the following approach:
 1. Determine the baseline line coverage for a given product from all small or medium tests (all
 columns in the coverage matrix)

 28

 2. Set an allowable delta in line coverage for the CI set (e.g. allowing a 1% drop in line
 coverage, so if the original test set had 80% line coverage, the CI set must have at least 79%
 coverage)
 3. Sort the tests by cost (archived nightly), starting iteration from the most expensive test
 4. Remove the most expensive test from the optimized set and check the coverage. If it has
 fallen below the allowable limit, add the test back in
 5. Continue down the list of tests applying the same criteria from the prior step
Certain tests, such as those with the “ci_keep” keyword or unit tests are always kept in the
optimized CI test set. The results of this algorithm were applied to the SIERRA apps with the
highest test usage, described in next chapter.

6.2. Mutation Testing
Relying on line coverage alone to determine test coverage can miss cases where a test trivially
exercises code – for example, running a function but not checking its output in the test, or only
running certain branches from within a given function. Mutation testing is a way of stress-testing an
existing test suite by synthetically injecting bugs (mutations) into the code at compile time and
ensuring that the tests fail appropriately with the mutated code. If the tests do not fail, the mutant
has “survived” and the mutated code is flagged in an output summary.
For this work we evaluated using the “mull” library, which uses LLVM tooling to inject mutations
into C++ codes and run tests while activating these mutations. There is a long list of possible code
mutations available in mull, a sample of which are shown in Figure 24. Mull also allows source
filtering, so the mutations can be applied just to a part of the codebase instead of all files, which is
important for keeping it tractable.

 34

 Figure 24. Mull example mutations
To exercise the mutated code, one must activate each mutation one at a time and run the tests.
When there are thousands of mutations, the cost of this step can be prohibitive for a large test suite.
For this evaluation, we only considered unit tests to focus specifically on how robustly our unit tests
cover a section of code.
To evaluate this, we used the new Spack build system to easily inject a new dependency. After
defining a Spack package for mull, we added it as an optional variant to all Sierra packages. With this
change, doing a mull build of Aria is as simple as

 spack add aria+mull
 spack install

Once built, one must use the mull runner to run your tests. This uses threaded execution to run
many mutations at once (Figure 24).

 Figure 25. Mull runner output

For testing, we picked a specific family of expressions in Aria (density models) that have high unit
test coverage to evaluate how well those unit tests actually tested the code in question. The surviving
mutants could largely be categorized into the following three groups:
 6. Mutants that survived for things we do test, but not exhaustively

 7. Mutants that survived for code we execute but do not test the result of
 8. Trivial mutations
An example of one of the failures identified by Mull that falls into the first group is shown in the
figure below. In this case, the mutation replacing a multiply by a divide survived because in every
test we use “1” for the “rho_e” parameter being multiplied there.

 Figure 26. Example surviving mutant
An example surviving mutation that falls into the second category showed up in the testing of
sensitivities for some expressions. The expression class in Aria defines a “compute_values” method
and a “compute_sensitivities” method. The unit test fixture for testing expressions calls both
methods, but some tests were not checking the return value of “compute_sensitivities”. The
“compute_sensitivities” function showed up as covered in the line coverage report because it was
being run, but all mutations in that method survived.
There were also some trivial mutations that survived, such as replacing “>=” with “>” when a
function had a behavior branch that was continuous at the transition point, calling a no-op function,
or filling an array with 0s when it was already initialized with 0s.
The latest version of Mull supports using annotations in the code to disable specific mutations in
parts of the code, so if Mull is more widely adopted, these trivial mutations can be identified and
suppressed.
The result of this experiment was the identification and fixing of dozens of unit test deficiencies in
the Aria density model unit tests and could be repeated for other targeted portions of the code that
have high unit test coverage already.

6.2.1. Remaining Obstacles
This work has shown that mutation testing works in SIERRA, however there are a few blockers to
more widespread adoption we have encountered in this milestone work.
 • Build Cost – A fully mutated build is very expensive to build and runs into size/memory
 issues in some of our “globbed C file” build artifacts since the number of mutations in the
 single object gets very large. Once we have transitioned fully to CMake we may be able to
 remove these globs, since their creation was largely done to get around build system
 limitations with bjam.
 • Tooling/compiler Support – The current AUE Clang modules are not properly built for
 use with the LLVM tools needed to run Mull, so a custom Clang toolchain was used in these
 evaluations. Fixing that will be needed for production adoption.

 36

 • Signal/Noise – Prototyping this on a small set of code produced a small enough number of
 mutations to evaluate them individually and judge which were real and which were
 trivial/could be ignored. A mutation of a larger set of code would likely produce an
 intractably large amount of information that could be overwhelming to parse or pare down.
 • Test Cost – Currently mutation testing is only feasible with fast unit tests. To run on the full
 SIERRA code suite would require controlling mutations down to a small number and using
 LARRY to identify which tests to run and could likely only be run on a small portion of the
 code at once that way. Moving towards higher and better coverage of SIERRA code with
 fast unit tests is a long term goal for SIERRA that is complementary with using mutation
 testing, but will require sustained work.
 • Tool Support – Mull is an open-source tool that is currently actively maintained; however it
 is largely from one contributor. If that person stops working on developing and maintaining
 Mull there is a risk the tool may stop working with future clang versions. If this happens, we
 would either have to make changes ourselves, or switch tools.
We believe many of these obstacles can be mitigated, and that Mull should remain a tool developers
have access to and can use. However, it is not clear long-term how Mull will be integrated into
developer workflows yet. Mull does provide an interface to use a git change set to run mutations
only on modified code, so one potential path would be to include it in merge request checks, but the
cost and noise issues would need to be resolved first.
Long term, mutation testing scores could be combined with line coverage data to provide higher
confidence rankings to some line coverage over others to help decide which tests are safer to
remove when we have identified duplicate coverage between unit tests and regression tests.

7. STATIC ANALYSIS
One of the areas the Collab team investigated in this work was static analysis tools for C++ codes.
In the past, SIERRA has used tools like C++test and Klocworks to provide static analysis reports of
our codes, but no such tools have been used or available in recent years. Many developers have been
using Clang Tidy tools through the Visual Studio Code IDE, which provides helpful annotation in
real-time in the source files for common code issues. Each product also has the ability to customize
the list of checks they want to have active per directory by adding a Clang Tidy configuration file in

focused initially on integrating Clang Tidy into our CI workflows and providing additional local
tools developers could use besides the Visual Studio Code IDE interface.
The reasons the team were interested in static analysis were:
 • Early Bug Detection
 o Identifies potential issues before runtime, reducing the cost and effort of fixing bugs
 later in the development cycle.
 o Helps catch logical errors, memory leaks, and undefined behavior early
 • Improved Code Quality
 o Encourages adherence to coding standards and best practices, leading to cleaner,
 more maintainable code.
 o Promotes consistency across the code base, making it easier for teams to collaborate.
 • Facilitates Code Reviews
 o Automates repetitive checks, allowing developers to focus on more complex aspects
 of code reviews.

9. COMPILER WARNINGS

Introducing stricter warnings offers benefits for code quality, maintainability, and reliability. These
warnings help developers identify potential issues early in the development process, such as
unintended variable shadowing, missing virtual destructors in base classes, or non-standard code
practices that may lead to undefined behavior. With a low warning level, subtle errors can go
unnoticed, leading to hard-to-debug runtime issues, security vulnerabilities, and technical debt that
can hinder long-term project success. Adopting a stricter warning policy is a proactive step toward
building robust and maintainable software.

For this work, we focused on the GCC and Clang compilers, and the following set of warnings were
chosen as the target set:
-Wall -Wextra -Wshadow -Wnon-virtual-dtor -pedantic
These warnings comprise the “core” set of warnings recommended by Jason Turner (host of C++
Weekly, ex-co-host of CppCast, frequent CppCon speaker, and instructor of 2 short courses at
SNL).

9.1. Methodology
Currently, the Sierra code suite uses a bjam-derived build system, “bake”, that has the ability to
conveniently select different warning levels via the command-line option “warnings”, e.g.
bake warnings=off|on|all

As an initial step, the target set of warnings (-Wall -Wextra -Wshadow -Wnon-
virtual-dtor -pedantic) was enabled for warnings=all. This approach allows
developers to easily compile with the full/target set of warnings without invasive changes to the
code base or complex build commands. Several scripts were also developed to aid in post-
processing & sorting the list of warnings.
The same desired set of warnings was also enabled for warnings=on (the default), but with the
individual warnings that are currently failing disabled (e.g. -Wno-unused-but-set-
parameter from -Wextra). As individual categories of warnings are fixed, they are then
removed from the list of disabled warnings, ensuring that the code will not regress in the future.

The Sierra code suite is also in the process of migrating to Spack, which doesn’t have a standard way
to select warning levels similarly to bake. Consequently, one aspect of this work was to add an
equivalent capability to Spack. This was accomplished by adding a variant to the base Sierra Spack
package from which all other Sierra packages derive. This enables a nearly-identical syntax that can
be specified when calling spack add, e.g.
spack add <package> warnings=none|default|all

Another useful switch provided by bake is the ability to change all warnings to errors (warnings-
as-errors=on). An equivalent variant was also added to Spack, which can be enabled by adding
“+warnings_as_errors”, e.g.

 43

spack add <package> +warnings_as_errors

Work on cleaning up warnings is ongoing. However, at the time of writing this document, the

warning level of the other apps.

9.4.      Impact
Enabling a stricter set of warnings in Sierra has highlighted many instances of poorly written or
confusing code, exposed compiler-dependent and undefined behavior, and even uncovered several
bugs that had previously gone unnoticed. In several instances it has also enabled the deletion of
large swaths of unused/unnecessary code, including the deletion of almost 40,000 lines of code in a
single app, comprising about 8% of the codebase.

9.5. Future Work
Going forward, we would like to continue to address the remaining warnings, with the ultimate goal
of enabling the complete set of targeted warnings for all Sierra apps. As mentioned previously, the
transition to Spack should make addressing the remaining warnings much more feasible.

10. SIERRA 3-5 YEAR PLAN
To maximize the long-term impact of this year’s milestone it will be critical to include continued
efforts to improve SIERRA developer productivity in future years and engrain a culture of
continuous improvement in the developer community. To that end we propose several efforts
including both the future work presented in prior sections of this report, as well as additional related
efforts not addressed as part of this milestone to be included in the scope of SIERRA development
work over the next several years. As SIERRA follows an agile development process we both
recommend and expect that this list will be updated over time as circumstances change.
The first set of recommendations with a goal of addressing them in the next year are:
 • Requiring package owner code review and approval in order to merge changes that modify
 any package within SIERRA.
 • Finish the extended warning set future work building on this milestone.
 • Have all teams adopt the practice of re-evaluating the CI keyword once per year, and an
 ongoing practice that any nightly test failures or user reported bugs must be covered by a CI
 test (preferably unit, small if necessary).
 • Finish build system transition so that all supported platforms (both internal & external) are
 delivered via spack and cmake.
 • Add production support for some containerized builds.
The second set with a goal of being addressed in the next 1-3 years are:
 • Reduce build and test turnaround time so that the 95th percentile time for all CI builds is < 2
 hours, and all nightly platforms complete in < 8 hours.
 • Code coverage & mutation testing driven reduction of all team’s test suites (not just CI
 tests).
 • Develop a consistent & lower maintenance performance testing infrastructure that is shared
 by all teams to replace the multiple different ad-hoc solutions used by multiple teams.
 • Explore AI and other automated tools for refactoring legacy code & generating unit tests.
And the final set of goals to achieve in the next 3-5 years are:
 • Move towards staged testing & merge trains to have an always-releasable main branch.
 • Adopt pre-merge static analysis requirements with some per-package flexibility on which
 checks are required.
 • Explore improving compile times by adopting C++20 modules.
 • Improve SIERRA usage metrics collection to have sufficient information to inform
 prioritization of performance improvements & feature deprecations.

11. SUMMARY
The Compsim Collab Team made substantial progress this year in modernizing our development
practices and improving our CI test cost and data collection. We began the year with a developer
survey to collect data on the primary pain points identified by SIERRA developers and also to find
out which practices and tools were working well and should be continued.
We deployed a weekly line coverage report for all of SIERRA that has proven useful to multiple
teams for focusing test development on areas of most need, identifying unused code, and fixing
issues with current test execution. In addition to the line coverage report, we deployed tooling to
collect full line coverage matrices mapping coverage to specific tests. This lets us perform more
detailed analysis of specific tests in our test repository and was used to deploy a test optimizer to
reduce the number of tests run in CI while keeping high line coverage of the CI test set.
We added new data collection to our CI and nightly test processes and deployed automated
processes to collect, analyze, and plot that data on a web page accessible to SIERRA developers.
This data has already helped quickly identify performance regressions as they happen, which has
made fixing them much easier.
As part of this work, we assessed the state of SIERRA with respect to a set of modern
recommended compiler errors. We have made substantial progress in reducing the warning level in
SIERRA and have been able to activate a stricter warning check on several of the warning categories
to prevent their recurrence. We have also worked in the new Spack build system to position us to
get clean warning levels quickly when we have fully deployed the new system and removed BJam.
We prototyped a static analysis workflow using Clang-Tidy for this work, both as a local tool
developers can run and as a CI pipeline. Going forward, we are focused on using the Coverty static
analysis tools Sandia recently purchased licenses for. If successful in our prototyping, we can help
with adoption of common tools across ASC and potentially leverage security screening tools in the
same suite to speed up processes like CNARS.
New developer AI tools we can use at Sandia are currently in development, and the team evaluated
using some tools that were specifically focused on developer tasks – using the Atlas AI code
assistant through a plugin to Visual Studio Code. While this has currently not shown high impact for
C++ development many have found it useful for other scripting tasks and as we get access to newer
LLM models we will continue to assess its usefulness as an assistant for SIERRA developers.
In order to ensure that the changes made in this work continue to have impact past the end of the
milestone we have also worked to produce a 3-4 year SIERRA plan for improvements to
development practices. The SIERRA PO leadership team will continue to apply these plans in future
year activities with the goal of not regressing, and tackling some of the longer-term issues identified
such as sustainable testing and CI.
