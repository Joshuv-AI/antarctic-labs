 1. ABSTRACT
This brief documents how agentic Artificial Intelligence (AI) coding assistants can compress the
onboarding curve for legacy High-Performance Computing (HPC) systems software, allowing a single
contributor to provide bug-finding and maintenance support for projects whose traditional stewardship
is thinnning as long-time maintainers retire. The concern is broad: foundational HPC packages such as
Performance Application Programming Interface (PAPI), HPCToolkit, and Lawrence Livermore National
Laboratory (LLNL)’s Spindle all sit on this trajectory, and the cost of letting them silently bit-rot is large
because they are dependencies of many scientific workloads at scale.
We use Spindle [4], a userspace dynamic-library and Python-module loader used to mitigage metadata-server
contention on Frontier-class HPC systems, as a concrete case study, and Claude Code [1] as a representative
agentic coding assistant. The author had no prior Spindle experience at the start of the engagement. The
protocol described here is tool-agnostic; equivalent agentic systems should perform similarly with the same
scaffolding.
The work was carried out under a two-pass protocol: a documentation pass in which the agent generated
individualized markdown summaries of every subsystem, followed by a bug-hunt pass with context of
the relevant generated summaries and the full source tree. Findings were triaged into a project-local
ISSUES.md and verified by the human author before any upstream artifact was filed.
Under this protocol, seventeen distinct defects were filed against the upstream LLNL/Spindle repository
and have since been merged [3] and four additional issues remain open against devel. The audit also
produced eight findings that were withdrawn after closer reading; these “retracted” entries are an important
calibration signal and are reported alongside the merged work.
The principal finding is operational, not technical. The agent does not replace the human contributor;
it functions as a high-recall index over a codebase the contributor has not yet internalized, surfacing
candidate defects at a rate the contributor can triage in days rather than weeks. We recommend that Oak
Ridge National Laboratory (ORNL) treat agentic AI coding assistants as a standard part of the toolchain
for sustaining academically maintained HPC systems software, subject to the calibration and policy
guardrails described in §7.

 2. BACKGROUND
2.1 SUSTAINABILITY FOR ACADEMICALLY MAINTAINED HPC SOFTWARE
A non-trivial fraction of the systems software that production HPC centers depend on was authored, and
is still principally maintained, by small teams at universities or in single national-lab groups. Performance
counters and profiling can be served by PAPI (long maintained at the University of Tennessee’s Innovative
Computing Laboratory) and HPCToolKit (Rice University); userspace dynamic-loader scaling at extreme
node counts is served by Spindle (LLNL). These projects share three structural features: they are small in
general size, deep in domain assumptions, and historically maintained by limited personnel.
The retirement and project-end attrition of those personnel is an active concern for HPC. When a primary
maintainer steps back, the institutional knowledge of why a particular configure.ac switch exists, or
why a given #ifdef block was added a decade ago to provide a work-around for a since patched kernel
bug, leaves with them. The code keeps working until a tool-chain or kernel update breaks it; from that
point a center-side contributor must reconstruct that context. This report describes one such reconstruction,
performed against Spindle, using an agentic AI coding assistant to compress the reconstruction time from
months to days. The same protocol is intended to apply to other similarly maintained academic HPC
packages on which ORNL’s production stack depends.

2.2 WHY SPINDLE MATTERS AT ORNL
On Frontier-class systems, a single Python-heavy job at 𝑁 = 9408 nodes can issue on the order of

 𝑅naive (𝑁, 𝐿) = 𝑁 · 𝐿 · 𝑘 search (1)

open()/stat() calls against Lustre, where 𝐿 is the number of libraries or .py/.pyc files and 𝑘 search is
the average number of LD_LIBRARY_PATH or sys.path entries probed per import. With 𝐿 ∼ 103 and
𝑘 search ∼ 10, this approaches 108 metadata operations during job startup — historically sufficient to disrupt
other tenants of the filesystem. Spindle reduces this to

 𝑅spindle (𝑁, 𝐿) = 𝐿 + 𝐿 · log𝑏 𝑁 (2)

by electing one process per file to read from disk and propagating bytes over a 𝑏-ary tree overlay [2].
Spindle is therefore on the critical path for any large dynamically linked or Python workload on Frontier
and its successors. ORNL has a direct operational interest in its continued correctness on the architectures
we run x86_64 in production and aarch64 in testbeds.

2.3 THE ONBOARDING PROBLEM
Spindle is small by HPC-systems-software standards but unusually deep and intricately connected to
lower-level Unix operations. Several loosely coupled subsystems (src/client/, src/cobo/, src/fe/,
src/logging/, plus src/flux/ and src/utils/) communicate through three different Interprocess
Communication (IPC) channels (UNIX-domain socket between the audit client and biterd; in-process
handoff between biterd and the audit server; the COBO TCP overlay between servers). Library
interception is driven by glibc rtld-audit callbacks, so a grep for “where is this function called” returns
nothing useful for the entire client side. Roughly a dozen configure.ac switches gate large #ifdef
blocks; the real call graph depends on the build.
A new contributor who is fluent in C and MPI can still spend weeks reading before they can confidently
propose a correctness fix.

 3. METHODOLOGY
The work described here was structured as a two-pass, AI-assisted code audit of an unfamiliar codebase,
undertaken with the explicit goal of producing upstream-quality patches. The two passes are conceptually
distinct and were run in different Claude Code sessions to maintain context compactness.

3.1 PASS 1 - PER-DIRECTORY DOCUMENTATION
For this audit the agent was Claude Code; nothing in the protocol below assumes that specific implementation.
A single agent session was given read access to the entire Spindle repository. The agent was then walked
through each subdirectory of src/ in turn, and for each subdirectory the agent was asked to produce
a single markdown file documenting (a) the general structure of the directory, (b) the build steps and
configure.ac switches that affect it, and (c) the operational purpose of the code it contains. Each output
was reviewed by the human author and corrected where needed before the session moved on to the next
directory.
The output of this pass is a set of per-subsystem markdown files (src/client/CLAUDE.md, src/cobo/CLAUDE.md,
etc.) that serve as durable, human-validated mental models of the codebase. These files are checked into
the project alongside a root CLAUDE.md that provides global orientation.
The point of Pass 1 is not strictly the artifacts themselves; rather, the pass serves as a forcing function. The
agent cannot produce a correct one-page summary of src/cobo/ without actually reading the COBO
state machine, the handshake protocol, and the tree-construction code. Pass 1 ensures that the conceptual
ground is built before the bug hunt begins, and that the resulting context is reusable, by both the human
contributor and subsequent agent sessions.

3.2 PASS 2 - PER-DIRECTORY BUG HUNT WITH FRESH CONTEXT
For each subdirectory, a fresh agent session was opened with three pieces of context: the root CLAUDE.md,
the directory-specific markdown produced in Pass 1, and read access to the entire src/ tree. The agent
was then asked to systematically work through the target directory and report potential bugs and areas of
possible improvement, ranked by severity and overall impact.
The fresh-session-per-directory structure is deliberate. It prevents context pollution from earlier directories’
findings, it keeps the agent’s working set small enough to read carefully, and it allows the same prompt
template to be applied uniformly across the codebase. The directory-specific markdown from Pass 1
substitutes for the orientation phase that would otherwise consume the first half of each session.

3.3 TRIAGE AND MANUAL VERIFICATION
Each candidate finding from Pass 2 was manually verified by the human author before being filed
upstream. Verification was not a re-read; it was a deliberate code-flow trace. The author opened the
implicated file, located the cited line, and walked the surrounding control flow to its terminus — entry to
the function, every branch the value of interest could take, and every site where the suspected defect would
manifest.
The verification was tractable because the majority of candidate findings were structural: they concerned
the shape of the code rather than its intent. A realloc whose return value is never assigned back, a
strncpy whose third argument is the destination size rather than the remaining space, a free() on
a pointer that was set to a string literal. These are correct or incorrect on inspection, regardless of the

 3

context. The author did not need full operational context to confirm them, following the data flow was
sufficient.
A smaller subset of findings did depend on context: whether a global was actually shared across threads,
whether an exit() path was reachable in normal operation, whether a buffer’s invariants were enforced
by an upstream caller. For these, the verification loop included a follow-up query to the agent using the
per-directory markdown from Pass 1 as primed context to clarify the surrounding semantics. Findings
that survived this loop were filed with the maintainers accompanied by detailed reproduction notes and a
proposed resolution; findings that did not were either retracted (recorded in ISSUES.md as false positives)
or marked as latent issues not worth filing in the current cycle.
This combination of manual code-flow tracing on the structural majority and agent-assisted contextual
clarification on the remainder is what allowed the upstream issue tracker to see a 0% false-positive rate
while the initial-finding false-positive rate was non-trivial (see §6). Findings recorded in ISSUES.md
carry severity and impact annotations; false positives are retained as calibration data and as markers of
fragile code. Filed upstream issues were minimal and reproduction-grounded: each names the file, the
line, the failure mode, and the architecture or toolchain on which it manifests. All upstream submissions
were authored by the human contributor; the agent’s output was treated as a draft to be fully flesh out by
the contributor.
This protocol is deliberately conservative. The agent’s role is to narrow the search space; correctness,
idiom-fit, and upstream acceptability remain the contributor’s responsibility.

 5. REPRESENTATIVE CASE STUDIES
5.1 CASE A: LA_VERSION() RETURNS HARDCODED 1, BREAKING GLIBC ≥ 2.35 ON AARCH64
Issue #143 1 describes how both spindle_la_version() implementations (auditclient.c:30 and
subaudit.c:28) returned 1 unconditionally, discarding the version argument supplied by the dynamic
linker. glibc 2.35 bumped LAV_CURRENT to 2; on systems that enforce a minimum-version check, Spindle’s
audit library was silently rejected at load time. A secondary defect compounded the first: return -1 from
a function declared unsigned int silently yields 0xFFFFFFFF.
The defect is a perfect example of the kind of issue an agentic AI reader is unusually good at finding:
it is two functions in two files, both ten lines long, both correct on the platform Spindle was originally
developed against, and both quietly wrong on the platform we now run. A human reading the source
linearly would likely accept the function as an obvious one-liner and move on. The agent flagged it on a
grep for LAV_CURRENT and the author confirmed by reading the glibc release notes.
Patch. Return version on success, 0 on the error path.

5.2 CASE B: CUSTOM_GETENV DECLARED WITH EMPTY PARAMETER LIST, BREAKS GCC 15
Issue #141 2 shows src/utils/parseloc.c:46 declared extern char *custom_getenv() (empty
parameter list, K&R-style) while the actual definition in slurm_plugin.c:509 took one argument.
Empty parameter lists are obsolete in C23 and GCC 15 rejects the declaration/definition mismatch as a
hard error. Spindle would not build on a current Rocky or RHEL 10 release.
Patch. Update the declaration to extern char *custom_getenv(char *envname).
This case illustrates a class of defect that scales poorly with codebase age: small, deferred-compatibility
issues that accumulate quietly across toolchain versions. Identifying them requires a reader who is
simultaneously familiar with the codebase and the current state of the C standard. An AI coding assistant
closes the second half of that gap on day one.

5.3 CASE C: TRANSLATE_MAPS.C:163 USES WRONG POINTER AS SENTINEL, OOB READ
Issue #156 3 shows translate_line() in src/client/client/translate_maps.c walked backward
through the spindle_dir buffer using line (a pointer into a different buffer) as the lower-bound sentinel.
The sentinel never fired; when no ’/’ was found, the loop read past spindle_dir[0] into adjacent heap
memory. The defect was confirmed under AddressSanitizer (ASan) (heap-buffer-overflow).
Patch. Use spindle_dir itself as the sentinel.
This is the case study most representative of an agent’s value on memory-safety work. The bug is real,
exploitable in principle, dormant in practice (because the contents of the adjacent heap buffer are usually
benign), and very hard to spot by reading. The agent noticed it because a sentinel pointer of one buffer
being used to bound a walk through another buffer is a syntactic pattern it can search for; the human author
confirmed it by writing a four-line ASan reproducer.

5.4 CASE D: INTERCEPT_EXEC.C:74 COMPARES STRING LITERAL "SPINDLE" WITH STRING LITERAL
 "0"
Issue #157 4 shows the check intended to honor SPINDLE=0 (a documented mechanism to disable
interception for a specific process) compared the literal string "spindle" with "0" instead of comparing
the value of the SPINDLE environment variable with "0". The disable path was therefore non-functional
in production: setting SPINDLE=0 had no effect, and users relying on it were getting interception they had
explicitly opted out of.
Patch. strcmp(spindle, "0") == 0.
This case is included not because the diff is interesting (it is two characters) but because the failure mode
is operationally consequential: any user-facing knob that is silently broken degrades trust in the entire tool.
It is also the case where the value of an outside reader is most evident; the surrounding code "looked right"
to everyone who had reviewed it previously.

5.5 CASE E: VARARG_TO_ARGV DOES NOT ASSIGN THE REALLOC RESULT, WRITES TO FREED MEMORY
In issue #169 5 , src/utils/handle_vararg.h:41–46 used spindle_realloc when the argv buffer
needed to grow but never assigned the returned pointer back to argv. Subsequent writes in the same loop
went to the freed allocation. The macro is invoked across the codebase for any function that accepts more
than ARGV_MAX = 1024 arguments. The corruption is silent until the freed region is reused.
Patch. Assign argv = newp; after the null check.
This case illustrates a structural strength of an LLM-based reader: macros that are correct in isolation but
expand into subtly wrong code across many call sites are exactly the kind of artifact a human dismisses but
that an Large Language Model (LLM)-based reader processes as if the macro had been inlined at every call
site.

Three observations are worth flagging.
The false-positive rate at the initial-finding stage of the audit was non-trivial. Of the 30 critical/high
findings the agent surfaced across src/cobo/, eight (roughly 25%) were withdrawn on review. None
reached upstream. Each retraction was the result of the manual code-flow trace described in §3 — the
author followed the implicated control flow to its terminus and observed that the defect did not manifest.
For findings whose status depended on surrounding context (ownership transfer through output parameters,
buffer-size invariants enforced by #define), the agent itself was queried for clarification before the finding
was either filed or retracted. The combined loop drove the upstream false-positive rate to zero.
Several retractions had a useful secondary property: the act of disproving the initial finding led to a
different, real finding in the same vicinity (the accept() timeout in cobo.c:823; the malloc(0)-then-assert
issue in handshake.c:1360). The agent’s wrong answers are still informative about where the fragile
code lives.
The retractions cluster in idioms the agent does not yet read precisely: ownership transfer through output
parameters, buffer-size invariants enforced by #define, and the difference between a function being unsafe
in isolation and unsafe in context. Contributors should be told to pay particular attention to these patterns
when triaging agent output.

 7. LIMITATIONS AND RECOMMENDATIONS
The agent’s understanding is bounded by the source it reads. Configuration-gated code paths excluded
from the build are also excluded from the agent’s working model, and it will silently extrapolate. Contributors
should ask for the agent’s reasoning, not just its conclusion.
Spindle is licensed under LGPL-2.1. Contributions generated with AI assistance are valid under this
license; however, contributors should verify case by case that the recipient project accepts AI-assisted
work, as policies on this point vary across upstream maintainers.
Whichever AI coding assistant is used, its network access should remain restricted on ORNL development
hosts. The workflow described here uses only the local repository, the local test suite, and ASan; no
external services are required at the agent layer.
The recommended workflow for future ORNL contributors performing maintenance support on academically
maintained upstream HPC systems software is the two-pass structure described in §3, with an emphasis on
the creation of markdown artifacts to ground the agent and keep context size within a manageable range.
A new contributor should clone and fork the target repository and build it once by hand, then run Pass 1 —
a single agent session that walks through each top-level source subdirectory and produces a per-directory
markdown file describing the structure, build inputs, and operational purpose of the code there. These
files are reviewed and corrected, then committed to a project folder alongside a root orientation file (e.g.
CLAUDE.md or whatever convention the agent expects) that provides global orientation.
The contributor then runs Pass 2 — one fresh agent session per subdirectory, each given the root CLAUDE.md,
the directory-specific markdown from Pass 1, and read access to the full source tree. Each Pass 2 session
is asked for a ranked list of potential bugs and improvements scoped to its target directory. Findings are
accumulated in a project-local ISSUES.md with severity and impact annotations.
Every finding is reviewed by the human contributor before any upstream artifact (issue, PR, commit) is
created. False positives are retained in ISSUES.md as calibration data and as markers of fragile code.
The agent’s confidence ranking should be requested explicitly alongside severity; in our experience, the
highest-severity findings were not always the highest-confidence ones, and conflating the two would have
raised the upstream false-positive rate materially.

 8. CONCLUSION
Spindle is high-leverage HPC systems software whose maintenance burden is disproportionate to its line
count, primarily because of the depth of its IPC layering, the indirectness of its control flow, and a long tail
of cross-architecture and toolchain-compatibility issues. It is also a representative member of a wider class
of academically maintained HPC packages, alongside PAPI, HPCToolkit, and similar, whose long term
stewardship is increasingly fragile. A single ORNL contributor, new to the codebase, used an AI coding
assistant (Claude Code, in this instance) to identify and merge seventeen upstream defects in this category
over one audit pass, with four additional findings still open and eight retracted false positives along the
way. The merged defects span the four bug families most consequential for ORNL’s actual deployment
surface: aarch64/ppc64le portability, modern toolchain compatibility, memory and resource safety, and
logic errors in user-facing core paths.
We recommend that ORNL adopt agentic AI coding assistants as a standard part of the toolchain for
sustaining academically maintained upstream HPC systems software, subject to the calibration protocol
and policy guardrails described in §7. The specific assistant should be selected on the basis of cost,
security posture, and alignment with center policy; Claude Code was used here, but the protocol does
not depend on it. The principal value of the approach is not autonomous patch generation; it is the
compression of the time-to-first-credible-upstream-contribution from the months traditionally required
for a codebase like Spindle to days - a multiplier that matters most precisely when the codebase’s original
maintainers are no longer available to answer questions.

A.1 FIXED BUGS (CLOSED GITHUB ISSUES)
The following issues were identified and resolved.
#139 — DATA_GOT_TYPE undeclared: writablegot.c defined DATA_GOT_TYPE only inside the
 arch_x86_64 guard block but used it unconditionally. Fixed by adding R_PPC64_GLOB_DAT and
 R_AARCH64_GLOB_DAT definitions.
#141 — custom_getenv breaks GCC 15 / C23: src/utils/parseloc.c declared extern char
 *custom_getenv() while the definition in slurm_plugin.c takes one argument. Fixed by
 updating the declaration to extern char *custom_getenv(char *envname).
#142 — REL_TYPE undeclared in testsuite: testsuite/symbind_test.c defined REL_TYPE only
 for x86_64, triggering errors on aarch64. Fixed by extending the guard block to cover aarch64
 (ElfW(Rela)).
#143 — la_version() breaking glibc ≥ 2.35: spindle_la_version() implementations returned 1
 unconditionally. Fixed by returning the requested version in the success path and 0 in the error
 path.
#153 — msgbundle.c EINTR retry logic: Code compared the write() return value directly to EINTR
 rather than checking errno. Fixed by retrying when result == -1 && errno == EINTR.
#154 — translate_maps.c wrong FD check: Code checked and closed the original fd instead of the
 replacement newfd on error. Fixed to check/close newfd.
#155 — translate_maps.c null terminator offset: Null terminator was written at MAX_NAME_LEN
 (255) instead of the actual buffer size (4096), truncating long paths.
#156 — translate_maps.c OOB read: translate_line() used an incorrect pointer as a backward-walk
 sentinel. Fixed by using spindle_dir itself as the sentinel.
#157 — intercept_exec.c env var comparison: The check for SPINDLE=0 compared the string to
 "spindle" instead of "0". Fixed to check strcmp(spindle, "0") == 0.
#158 — shmcache_add_worker strncpy into NULL: On malloc failure, the code fell through to a
 strncpy with a NULL destination. Fixed by adding a return -1 after cleanup.
#159 — lookup.c free() on string literal: free(exist_str) was called on the literal "y" or "n".
 Fixed by guarding the free with a heap-allocation flag.
#164 — jobtask.h memory leak: Bitwise & instead of logical && in the JobTask destructor caused
 cleanup to be skipped for even app_argc.
#165 — procmgr.c read_pidfile() truncation: File opened with "w" (truncating) instead of "r",
 preventing the PID from ever being read correctly.
#166 — procmgr.c init_readymsg() diagnostic error: error was assigned the result (-1) instead
 of errno, leading to "Unknown error" messages.
#167 — flux-spindle.c parse_yesno() flag error: *opt |= 1 was used unconditionally instead of
 using the provided flag argument, setting the wrong bits.
#169 — handle_vararg.h realloc pointer leak: VARARG_TO_ARGV failed to assign the realloc
 result back to argv, causing a use-after-free.
#170 — exitnote.c FD 0 leak: pingExitNote used if (sockfd) instead of if (sockfd != -1),
 failing to close the socket if it was assigned FD 0.

A.3 SYSTEMIC OPTIMIZATION OPPORTUNITIES
Agent identified areas of interest.

A.3.1 Client Subsystem (src/client/)
 • Syscall Caching: Replace direct gettid() syscalls in lock() with a cached __thread variable to
 reduce latency.
 • Hashing Efficiency: Update str_hash in shmcache.c to use bitwise masking (&) rather than
 modulo (%) for power-of-two hash sizes.
 • Redundant Logic: Remove readlink calls in auditclient.c as the resulting exe_name is
 currently unused.

A.3.2 Collective Tree (src/cobo/)
 • Integer Overflows: Upgrade sendcount from int to size_t to prevent massive heap corruption
 during large-scale gathers.
 • Error Handling: Replace exit() calls with proper error returns to allow library consumers to
 recover from failures.
 • Concurrency: Global state in cobo.c is currently thread-unsafe and requires mutex protection for
 multi-threaded clients.

A.3.3 Front-End and Utilities (src/fe/)

 from arbitrarily long environment lines.
 • Initialization Order: Ensure flauncher is set before registering SIGCHLD handlers in launcher.cc
 to prevent NULL dereferences.
