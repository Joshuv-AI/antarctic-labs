ABSTRACT
Sandia Message Rate is a long-standing MPI benchmark designed to measure message-rate be-
havior under communication patterns representative of production high-performance computing
applications. This report documents the benchmark and recent extensions that enable evaluation
of both host-memory and accelerator-resident communication. In addition to the original CPU
execution path, the benchmark now supports CUDA, HIP, and Kokkos modalities, allowing users
to exercise GPU-aware MPI communication with NVIDIA GPU buffers, AMD GPU buffers, and
Kokkos-managed memory. These extensions preserve the benchmark’s core nonblocking point-to-
point MPI communication structure while enabling comparisons across programming models and
memory-residency configurations.
The report describes the four Sandia Message Rate communication patterns—single direction, pair-
based, pre-post, and all-start—and explains the deterministic peer-selection logic used to generate
repeatable multi-peer communication workloads. It also summarizes the implementation approach
for CPU, CUDA, HIP, and Kokkos backends, including accelerator buffer allocation, synchro-
nization, data movement, and device selection. An optional message-content verification mode
is introduced to help confirm correctness when communicating directly from accelerator-resident
buffers. Example CPU results from the Eldorado system are presented for the pre-post pattern,
illustrating the effects of message size, process placement, and peer count on communication
performance.

1. INTRODUCTION

Sandia Message Rate is a long-standing MPI benchmark developed to measure message-rate be-
havior under communication patterns that are more representative of production HPC applications
than simple latency or bandwidth tests. The benchmark stresses multi-peer, nonblocking point-to-
point communication with many outstanding MPI requests. As a result, it provides insight into
message injection rate, request management, message matching, MPI progress, and the cost of
communicating with multiple peers.

This report documents recent extensions to Sandia Message Rate that enable the benchmark to
evaluate both host-memory and accelerator-resident communication. Modern HPC applications
increasingly keep data resident in GPU memory, making host-only MPI measurements insufficient
for understanding application communication behavior. GPU-aware MPI allows MPI calls to accept
accelerator pointers directly, ideally avoiding explicit host staging and enabling communication
along the path
 accelerator memory → MPI → accelerator memory.

However, the correctness and performance of this path depend on the full system software stack,
including the MPI implementation, accelerator runtime, device driver, network transport, memory
type, process placement, and launch configuration. The extended benchmark is therefore intended
to exercise the integrated communication path actually used by accelerator-enabled applications.

The benchmark now supports four execution modalities: CPU, CUDA, HIP, and Kokkos. The
CPU modality provides the host-memory baseline. The CUDA and HIP modalities use NVIDIA
and AMD GPU-resident buffers, respectively, while preserving the original MPI communication
structure. The Kokkos modality is implemented as a separate executable using Kokkos-managed
memory, allowing the benchmark to better represent applications written with performance-portable
abstractions. Optional message-content verification has also been added to check that completed
MPI operations produce the expected data, which is particularly important when testing accelerator-
resident buffers.

The remainder of this report describes the benchmark behavior and current implementation
state. Section 2 explains the four communication patterns: single direction, pair-based,
pre-post, and all-start. Section 3 documents the deterministic peer-selection logic used to
construct communication partners. Section 4 summarizes the CPU, CUDA, HIP, and Kokkos
implementation approaches and describes the verification method. Section 5 presents example
Eldorado CPU results.

2. COMMUNICATION PATTERNS

Sandia Message Rate includes four communication tests: single direction, pair-based,
pre-post, and all-start. These tests use the same communication buffers and peer lists, but
differ in how messages are paired, ordered, posted, and completed. These differences are important
because MPI message rate depends not only on message size and peer count, but also on whether
receives are already available, whether messages arrive unexpectedly, and how many requests are
outstanding at once.

2.1. single direction

The single direction test splits the participating ranks into two halves. Ranks in the lower half
act as senders, and ranks in the upper half act as receivers. Each lower-half rank is paired with
a corresponding rank in the upper half. During each iteration, the lower-rank process sends the
configured number of messages to its partner in the upper half, while the corresponding upper-half
rank posts matching receives.

This pattern provides a directed one-way message-rate measurement. It is useful for measuring
message injection behavior when communication flows from one group of ranks to another rather
than bidirectionally among all peers.

 7

2.2. pair-based

The pair-based test, historically associated with the “same direction” communication pattern in
the implementation, communicates with multiple peers one peer at a time. For each peer, a rank
posts the receives for that peer, posts all sends for the corresponding destination peer, and then
waits for those operations to complete before continuing to the next peer.
Thus, the benchmark does not start communication to all peers at once in this test. Instead, it
serializes the peer groups:

 peer 0 → Waitall → peer 1 → Waitall → · · ·

This pattern stresses repeated nonblocking communication and completion behavior while limiting
the number of outstanding requests to one peer group at a time.

2.3.        pre-post

The pre-post test ensures that receives are posted before the timed send phase. Before the main
iteration loop begins, the benchmark posts all receives for the first iteration. Each timed iteration
then performs a barrier, posts all sends, waits for all currently outstanding communication to
complete, and posts the receives for the next iteration.
The structure is: post all receives for iteration 1 followed by the repeated loop MPI_Barrier →
post all sends → MPI_Waitall → post all receives for next iteration.
This structure means that, at the start of each timed send phase, matching receives from the previous
preparation step should already be posted. The test therefore reduces or avoids unexpected-message
behavior and measures communication performance when receives are available before sends are
issued.

2.4. all-start

The all-start test removes the synchronization separation between posting receives and issuing
sends. Each rank posts its receives and then immediately posts its sends, without a global barrier
ensuring that all ranks have completed receive posting before any rank begins sending. After all
local receives and sends have been posted, the benchmark waits for completion.
This pattern starts all communication as aggressively as possible and creates a larger set of out-
standing requests. Because there is no global synchronization between receive posting and send
posting, some messages may arrive at a destination before the matching receive has been posted.
Therefore, all-start can exercise unexpected-message paths in addition to stressing MPI request
management, message matching, and progress behavior.

3. PEER SELECTION

Sandia Message Rate uses deterministic peer selection to choose communication partners. The goal
is to avoid trivial nearest-rank-only communication and to create repeatable communication patterns
that can stress the MPI implementation and system interconnect. There are two peer-selection
cases: the single direction test and the multi-peer tests used by pair-based, pre-post, and
all-start.
The benchmark uses the process-per-node parameter, -n, denoted here as 𝑝 pn , as the stride between
peer ranks. Under a typical rank layout, adding or subtracting 𝑝 pn moves to the same local rank
position on a neighboring node. Thus, peer offsets are selected in multiples of 𝑝 pn , rather than
simply using adjacent MPI ranks.

3.1. single direction peer selection

The single direction test splits the job into lower-rank and upper-rank halves. Each rank in the
lower half sends to the corresponding rank in the upper half: 𝑟 dst = 𝑟 + 𝑁2 , where 𝑟 is the sender rank
and 𝑁 is the MPI job size. The corresponding upper-half rank posts receives from: 𝑟 src = 𝑟 − 𝑁2 . If
the job size is odd, the final rank is excluded from the single direction communicator so that
the remaining ranks can be paired evenly.

All multi-peer destinations are computed modulo the MPI job size, so peer selection wraps around

4. IMPLEMENTATION SUMMARY

The native CUDA and HIP extensions preserve the original MPI communication structure while
changing the allocation and management of the communication buffers. Backend-specific behavior
is isolated behind a small helper layer, summarized in Table 4-1.

 Table 4-1. Backend helper functions.

 Function Purpose
 bench_gpu_init Select accelerator device when needed
 bench_alloc Allocate communication buffers
 bench_free Free communication buffers
 bench_memcpy_to_host Copy buffer contents to host
 bench_memcpy_from_host Copy host contents to benchmark buffer
 bench_sync Synchronize accelerator work
 bench_cleanup Final backend cleanup/synchronization

In the CUDA modality, buffers are allocated with cudaMalloc, initialized with cudaMemset,
copied with cudaMemcpy, synchronized with cudaDeviceSynchronize, and freed with cudaFree.
In the HIP modality, the analogous routines are hipMalloc, hipMemset, hipMemcpy,
hipDeviceSynchronize, and hipFree. The CPU modality uses standard host allocation and
copy routines.
The MPI calls remain standard nonblocking point-to-point operations:

MPI_Isend(send_buf + offset, nbytes, MPI_CHAR, dst, tag, comm, &req);
MPI_Irecv(recv_buf + offset, nbytes, MPI_CHAR, src, tag, comm, &req);

When CUDA or HIP is enabled, send_buf and recv_buf are accelerator device pointers. These
modalities therefore require GPU-aware MPI support from the system software stack.
On multi-GPU nodes, the CUDA and HIP backends use LOCAL_RANK when available. The selected
device is:
 𝑑 = LOCAL_RANK mod 𝑁devices .
Production and procurement runs should record the actual rank-to-device mapping and launch
configuration.
The Kokkos modality is implemented as a separate executable. It replaces backend-specific alloca-
tion, copy, and synchronization operations with Kokkos::kokkos_malloc, Kokkos::deep_copy,
and Kokkos::fence. MPI remains responsible for communication. If the selected Kokkos mem-
ory space is accelerator memory, GPU-aware MPI is still required.

4.1. Verification

Verification was added because successful MPI completion does not necessarily prove correct
accelerator-resident communication. A system may complete MPI calls while using an incorrect
configuration, mishandling accelerator pointers, or corrupting message contents.
The send buffer is initialized with a deterministic byte pattern based on source rank 𝑟, message
index 𝑘, and byte index 𝑏:

                         𝑃(𝑟, 𝑘, 𝑏) = (((𝑟 · 131 + 𝑘) · 131 + 𝑏) mod 256) .

For receive peer slot 𝑗, the expected source rank is recv_peers[j]. The expected byte for message
𝑘 and byte 𝑏 is therefore
 𝑃(recv_peers[j], 𝑘, 𝑏).

If the receive buffer is accelerator-resident, it is copied back to host before validation. On mismatch,
the benchmark reports the rank, receive slot, message index, byte index, observed value, expected
value, and expected source rank, then calls MPI_Abort. If all ranks pass, the benchmark prints:

verification: PASSED

The current verification mode validates the final peer-based receive-buffer layout, most directly the
result left by all-start. Future work should extend verification to validate each communica-
tion test independently. The single direction test has a distinct layout and requires separate
validation logic.

5. SANDIA MICROBENCHMARK ANALYSIS: ELDORADO CPU

The communication performance of the Eldorado system was evaluated using the Sandia Message
Rate benchmarks. To analyze the system under high-contention scenarios, we focus on configura-
tions with 8 peers.

 (a) Message Rate vs. Size (b) PPN Scaling (c) Peer Count Comparison

Figure 5-1. Communication performance on Eldorado CPU for the pre-post pattern. (a) shows the impact
of message size under high peer count, (b) illustrates the effect of increasing processes per node (PPN)
 at maximum peer density, and (c) compares performance across different peer counts for a fixed PPN.

As shown in Figure 5-1, the system maintains a relatively consistent message rate across the size
sweep for 8 peers, indicating that the communication overhead is dominated by latency rather than
bandwidth for the tested range. The PPN scaling (Figure 5-1b) reveals a performance degradation
as PPN increases to 8, likely due to increased resource contention on the node. Finally, the peer
comparison (Figure 5-1c) demonstrates the throughput penalty incurred as the number of peers
increases, reflecting the cost of managing additional communication endpoints.
