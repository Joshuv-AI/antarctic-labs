 1. Introduction and Background

The U.S. Department of Veterans Affairs (VA) places the health and well-being of our nation’s veterans
as its top priority. VA is dedicated to offering timely access to high-quality, evidence-based mental health
care that meets the needs of veterans and supports their reintegration into society. One of our core
missions is to prevent suicide among veterans through innovative approaches and resources.
With funding from the VA Office of Mental Health and Suicide Prevention (OMHSP), the Community
Determinants of Health (EDH) Data project has developed innovative datasets associated with specific
health outcomes, a methodology for transforming spatiotemporal data from one spatial reference (e.g., a 1
km grid) to another (e.g., U.S. Census Tracts), and capabilities for modeling health outcomes. These
datasets represent an enhancement of the Agency for Healthcare Research and Quality (AHRQ),
addressing key gaps by introducing finer spatial resolution (Census Tract) and additional geographical
covariates into existing data.
The curation and standardization of these datasets is a complex task since they often originate from
various sources and are measured at different spatial and temporal resolutions. For example, U.S. Census
data products typically use census blocks, block groups, or counties, while data like weather data are
available on 1 km grids. Some economic data may only be available at the ZIP code level. In this context,
‘standardized’ means that all datasets share the same spatial extent (e.g., U.S. Census Tract and/or
County), and ‘curated’ implies a repeatable process with data provenance and the use of appropriate
methodologies for covariate conversion.
The Community Determinants of Health datasets draw from multiple sources, resulting in variables with
varying degrees of availability, patterns of missing data, and methodological considerations across
different sources, geographies, and years.

 3. Contents and Structure

3.1 Dataset Curation Documentation Standard Format

Each data source description adheres to a standardized format with the following fields:

  1. Source: The name of the organization that provided the raw data (e.g., Health Resources and
 Services Administration [HRSA] for the Area Health Resources Files [AHRF]). Note: Prior to the
 FY23Q4 release, we referred to the source organization as the “sponsor.”

  2. Description: A brief, general description of the data.

 – Inclusion in the datasets: Lists the determinants of health domains to which the data
 source has contributed variables. Includes additional information relevant to the dataset.

  3. Resources: Links to original data source documentation, data download sites, and other pertinent
 information.

  4. Update Frequency: Indicates how often each dataset will be updated.

  5. Variable Definitions and Specifications (in tabular format):

 – Variable name (column name)

 – Variable label (optional, if different from the variable or column name)

 – Source table (optional, if multiple data tables were available from the original data
 source)

 – Numerator (for derived variables; optional)

 – Denominator (for derived variables) or original variable (when renamed for the EDH
 dataset; optional)

 – Total_rows: Indicates the number of rows in each column within each dataset (Starting in
 FY23Q2).

 5

 – Null_rows: Specifies the count of null rows for each column in each dataset (Starting in
 FY23Q2).

  6. Variable Availability Across Years (in tabular format):

 – Variable name (column name)

 – Data year availability (e.g., 2009 to 2018)

This standardized format supports consistency, traceability, and ease of reference across data sources.

3.2 Dataset Conventions

3.2.1 Overview of Variable Derivation

The variables within the Determinants of Health datasets are derived from various data sources through
one of two methods:

  • Direct extraction from the original data source: When the data was readily available from the
 source, we renamed the original variables to ensure clarity and consistency across years, aligning
 them with the naming conventions of the Determinants of Health data files.

  • Derivation using data from the original data source: In certain cases, we calculated
 percentages or rates for inclusion in the data files. We provide the numerators and denominators
 for these variables, along with their respective sources, in the data source descriptions.

3.2.2 Standardization of Table Names

Since FY24Q1, all datasets have followed the naming convention:
<dataset_name>_<spatial_resolution>_<year(s)>.

Example: hidta_county_2018_2021.

Beginning in FY25Q4, we were requested to also include the cmty_ prefix in table names.

Example: [OMHSP_FY25Q4].[cmty_parks_access_county].

3.2.3 Variable Assignment to Annual Datasets

Variables appear in the annual datasets corresponding to:

  1. The single year represented by the original data source
 (e.g., U.S. Area Deprivation Index 2020), or

  2. The final year in a period represented by the data
 (e.g., American Community Survey 2012–2016 is included in the 2016 dataset).

When possible, we also provide the unioned data along with a year column for each row.

 6

3.2.4 Variable Availability

Variable availability varies across data years. Following each data source description in this report, you
will find a table outlining the availability of each variable in the annual datasets. If a variable is not
available, it is marked as NA (not available) or a null value.

3.2.5 Variable Naming Conventions

With the exception of geographic identifiers (typically named fips), variable names use descriptive titles,
generally retained from the original source column names.

3.2.6 Handling of Missing Values

In the datasets, missing values are represented by a blank, with one exception: Provider ratio variables
from the County Health Rankings (CHR) data use negative values when the number of providers is
zero. This detail is further explained in the CHR data description.

For comprehensive information about each data source, please refer to the subsequent sections of this
report.

3.3 Dataset Versioning

In terms of dataset versioning, we utilize the Microsoft SQL Server database system to provide these
datasets to be consistent with the VA’s CDW work environment. Each dataset is stored in a dedicated
table within a schema in the database. The quarterly releases are organized under distinct schema names
in the database, such as OMHSP_FY22Q1, OMHSP_FY22Q2, OMHSP_FY22Q3, OMHSP_FY22Q4,
OMHSP_FY23Q1, and so forth. These schema names facilitate distinguishing between releases when we
deliver the same dataset, albeit updated, from one release to the next. Our approach to naming schemas
with fiscal year and quarter identifiers (e.g., FY25Q1) was designed to ensure precise tracking of datasets
over time. It provides an unambiguous record of when datasets were delivered, which is critical for
project management and accountability.

3.4 Metadata

As noted above, the project’s metadata tables were renamed starting in FY25Q2 to enhance clarity and
consistency in the data curation process. The following two paragraphs outline previous changes made in
prior fiscal years, providing context for the evolution of our metadata structure before detailing the
current organization of metadata tables.

Starting from FY23Q1, the ORNL team provided an updated metadata table, the original name of this
table was SEDH_meta_table, and it was located in the OMHSP schema.

Continuing our efforts to simplify and improve our data curation documentation, in the FY24Q3 delivery,
the ORNL team performed a reorganization of the metadata table. The original SEDH_meta_table,
located in the OMHSP schema, has been refactored into two tables: OMHSP.SEDH_table_metadata and
OMHSP.SEDH_column_metadata. The division of the columns is descrived in the followin section.

3.4.1 Data Dictionary

3.4.1.1 OMHSP.table_metadata Table

This table contains the following columns:

  a) dataset_id: Primary Key, an integer (starting in FY25Q4).

  b) table_id: The ID of the table that this column belongs to, using the schema name and table name
 to facilitate identification of the source.

  c) schema_name: Quarterly release schema names in the database (e.g., OMHSP_FY22Q4,
 OMHSP_FY23Q1, OMHSP_FY23Q2, OMHSP_FY23Q3, and so on).

  d) table_name: The table name as it appears in the Microsoft SQL Server database.

  e) table_name_description: A description of the table name.

  f) availability_across_years: The years for which data are available.

  g) data_source: The name of the source organization that provided the raw data (starting in
 FY23Q4).

  h) data_source_description: Description of the source organization (starting in FY23Q4).

  i) data_source_url: URL of the source organization (starting in FY23Q4).

  j) spatial_resolution: Spatial resolution or geography (e.g., state, county, block group, census tract,
 and ZIP code) (starting in FY23Q4).

  k) determinant: Using the ontology from Dang, Yifang, et al. “Systematic Design and Evaluation
 of Social Determinants of Health Ontology (SDoHO).” arXiv preprint arXiv:2212.01941 (2022).
 Current options used are: health care, neighborhood, social and community context, economic
 stability, food, and education.

  l) source_attribute: Two option values: derivative (datasets produced from other datasets by
 applying a model and creating an index value) and authoritative (datasets that have not been
 modified other than ensuring the inclusion of required geographic administrative boundary
 identifiers such as FIPS codes) (started in FY24Q2).

  m) dimension: Two option values: social and environmental (started in FY24Q2).

  n) osti_id: All our reports are publicly available at the U.S. Department of Energy Office of
 Scientific and Technical Information (osti) at osti.gov. The osti_id is the unique identifier
 assigned to each report (started in FY24Q2).

  o) ornl_res_pub_id: All our reports are available at ORNL in the Resolution Publication System;
 this column provides this unique identifier (started in FY24Q2).

  p) edh_project_exclusive: This flag indicates whether the dataset can be shared outside the VA
 OMHSP EDH project. Datasets (i.e., tables and their columns) with this flag set to ‘Y’ should not
 be shared outside the OMHSP EDH project (Column added in FY24Q3).

 8

  q) archive: For deprecated datasets that should no longer be used; Y (Yes) / N (No) (starting in
 FY25Q4). The archive flag indicates that a newer version of the dataset is available. When set,
 the dataset remains accessible in the database but is considered archived or deprecated and should
 be used with appropriate caution.

  r) archive_reason: Details of archival reason (starting in FY25Q4).

  s) notes: Notes on unioning/stacking or other relevant information (starting in FY25Q4).

  t) dataset_title: Title of the dataset. Its purpose is to simplify the display of dataset titles in the
 VA’s intranet (starting in FY25Q4).

  u) accessed_date: Dataset accessed date. The accessed_date field represents the end of the fiscal
 quarter in which the dataset was finalized and delivered to the sponsor. This standard provides a
 consistent temporal reference across all quarterly releases. Accordingly, datasets associated with
 FY25Q1, FY25Q2, FY25Q3, and FY25Q4 are assigned accessed dates of December 31, March
 31, June 30, and September 30 of the corresponding fiscal year, respectively. This convention
 aligns with federal reporting practices and ensures comparability and clarity in dataset versioning
 over time (starting in FY26Q1).

 Example: For the dataset [OMHSP_FY25Q4].[cmty_parks_access_county], the accessed_date is
 recorded as September 30, 2025.

  22. source_update_frequency: Dataset’s source update frequency. The source_update_frequency
 values were assigned based on the documented update schedules of each dataset’s original source.
 Where official release frequencies were available from the data provider (e.g., federal agencies,
 national surveys, or curated registries), those were used. For sources with irregular or ad-hoc
 updates, the value as-needed was applied. This column provides a standardized, categorical
 representation of how often each dataset is expected to be refreshed, facilitating planning for
 analyses, interpretation of results, and reproducibility of studies using OMHSP data (starting in
 FY26Q1).

The following table lists the possible values for the source_update_frequency column

 Value Description

 daily Dataset is updated every day (e.g., daily weather measurements).

 weekly Dataset is updated weekly (e.g., weekly administrative reports).

 monthly Dataset is updated once per month (e.g., healthcare claims data).

 quarterly Dataset is updated every three months (e.g., quarterly economic
 indicators).

 annual Dataset is updated once per year (e.g., most public health annual
 surveys).

 biennial Dataset is updated every two years (e.g., some national health
 surveys).

 9

 every population census Dataset updates align with decennial or other population censuses.

 continuous Dataset is continuously updated as new data becomes available
 (e.g., live registries).

 as-needed Dataset updates are irregular or ad-hoc (e.g., special reports, curated

Examples:

  a) SAMHSA National Survey on Drug Use and Health (NSDUH):

 – source_update_frequency: annual

 – Description: The NSDUH publishes updated estimates of substance use prevalence on an
 annual basis.

  b) U.S. Census American Community Survey (ACS):

 – source_update_frequency: every population census

 – Description: Census-derived population and housing estimates are updated based on the
 decennial census or ACS releases.

  23. sharepoint_description: Short, sponsor-facing summary used for display in the VA SharePoint
 or intranet interface. This field is intended to provide a concise overview of the dataset (summary,
 creator, and primary applications) suitable for mixed technical and leadership audiences. Content
 should be plain-language and avoid implementation details (starting in FY26Q2).

  24. source_citation: APA-style citation(s) for the original data source(s) used to create the dataset
 (e.g., U.S. Census Bureau ACS tables, USDA ERS RUCA, OpenStreetMap, ShelterList.com).
 For dynamic web sources, include a retrieval date as appropriate. This field supports transparency
 and reproducibility by documenting where the raw data originated (starting in FY26Q2).

  25. dataset_citation: APA-style citation for the dataset as delivered by ORNL to the VA EDH
 repository. This citation should identify ORNL as the dataset curator/producer when ORNL
 performed extraction, standardization, harmonization, geocoding, aggregation, or other
 processing. Use this field to cite the VA-delivered dataset version rather than the upstream source
 (starting in FY26Q2).

  26. related_publications: Bibliographic references (APA style) for publications related to the
 dataset’s subject area. This may include peer-reviewed articles, technical reports, or other
 credible references that provide context, methods, or interpretation relevant to the dataset’s
 domain. Publications do not need to directly use the dataset, but should be clearly relevant to the
 dataset topic (starting in FY26Q2).

 10

  27. advanced_information: Technical narrative captured from the dataset documentation under the
 “Advanced information” section. This field stores processing notes, version history, methodology
 details, harmonization steps, and other implementation information intended for technical
 reviewers. Content should begin after the “Advanced information” heading and end immediately
 before the “Source Citation” heading in the dataset documentation (starting in FY26Q2).

3.4.1.2 OMHSP.column_metadata Table

This table contains the following columns:

  1. column_id: A sequential number.

  2. dataset_id: FK to table_metadata, in numeric format (starting in FY25Q4).

  3. table_id: FK to table_metadata in non-numeric format. The ID of the table that this column
 belongs to, using the schema name and table name to facilitate identification of the source.

  4. column_name: Column names within each dataset as they appear in the Microsoft SQL Server
 table.

  5. column_name_description: Descriptions of each column name.

  6. column_type: The column type in the Microsoft SQL Server table.

  7. column_length: The column length in the Microsoft SQL Server table.

  8. total_rows: The number of rows in each column in each dataset (starting in FY23Q2).

  9. null_rows: The number of null rows for each column in each dataset (starting in FY23Q2).

  10. code_set_id: Foreign key reference to [OMHSP].[code_set].[code_set_id]. Identifies the
 categorical value set associated with the column. Null indicates the column does not use a
 controlled code set (starting in FY26Q2).

  11. null_reason_code: Foreign key reference to [OMHSP].[code_set_values].[code_value_id] for the
 “Null Reasons” code set. Identifies the primary, standardized reason why null values appear in
 the column (e.g., disclosure avoidance in ACS, missing fields in source records, or
 geocoding/mapping limitations). Null indicates either the column contains no null values or a
 standardized reason has not been assigned (starting in FY26Q2).

3.5 FIPS as Geographic Identifiers and Primary Keys

At ORNL, we utilize the Federal Information Processing Standards (FIPS) as geographic identifiers and
primary keys in each dataset or table for this project. FIPS codes are publicly recognized standards
developed by the National Institute of Standards and Technology (NIST) for computer systems and non-
military applications, particularly for standardizing codes of geographical areas. FIPS specifications
encompass various geographical areas:

  • FIPS 10-4 for country and region codes

  • FIPS 5-2 for state codes

  • FIPS 6-4 for county codes

These codes are unique within their respective geographic entities. For example, FIPS state codes are
unique within a country, and FIPS county codes are unique within a state. Since counties nest within
states, a complete county FIPS code combines the state and county identifiers. For instance, if multiple
counties end with “001,” the state FIPS code is added to make each county FIPS code distinct (e.g.,
01001, 02001, 04001), where the first two digits indicate the state, and the last three digits represent the
county.

Although NIST initiated the replacement of FIPS with the Geographical Name Information System
(GNIS) Feature ID in 2002, many federal organizations in the United States, including the U.S. Census
Bureau, continued to use FIPS due to its broader coverage and precision in identifying geographic

 16

entities, especially smaller areas with uncertain natural boundaries. The U.S. Census Bureau maintains a
comprehensive hierarchy of census geographic entities for reference.

As the primary key in all datasets for this project, we consistently use the column “FIPS” to ensure unique
data identification, regardless of the source FIPS granularity. We specify the FIPS granularity, such as
region, state, county, census division, tracts, block groups, etc., in the metadata table and reports’
descriptions. Users are presumed to be familiar with joining datasets using FIPS columns at different
geographic levels.

It’s worth noting that only a few datasets since the inception of this project do not include a FIPS column.
These exceptions are the following:

  8. The National Mental Health Services Survey (table: national_mental_health_services_survey),
 delivered in FY22Q4.

  9. The Veterans Service Organizations (VSO) 2010-2022, by ZIP code, delivered in FY24Q1.

  10. HUD USPS ZIP code Crosswalk Files, ZIP-to-tract for 2023, delivered in FY24Q2.

These datasets were provided at the sponsor’s special request.

3.6 Mapping Zip Codes to FIPS Codes for Counties: Our Methods

When realigning spatial data to different boundaries that do not perfectly match or nest within the original
spatial units, some data loss is inevitable. This occurs because the spatial distribution of data at higher
resolutions than the native unit is often unknown. For example, certain ZIP code boundaries overlap with
multiple county boundaries. When attempting to map ZIP code-level data to counties, there are situations
where data must be reassigned to two or more counties with limited knowledge of how to allocate it
accurately. Various methods exist to mitigate the degree of data loss, each with its strengths and
weaknesses based on the data’s nature. For social data, one effective approach is to allocate data based on
population distribution or addresses within those boundaries to reduce misallocation.

The circle on the left symbolizes this mapping process, where the location information from the cohort is

several methods to perform this conversion and join process. Different tools and techniques may be
employed based on the specific requirements and characteristics of the datasets and cohort.

By effectively joining the cohort data with our datasets using FIPS codes, we can integrate and analyze
information from various sources, enhancing the depth and breadth of our insights. This process of
intersection and integration facilitates comprehensive analysis and decision-making, enabling us to
leverage the full potential of our datasets in addressing research questions and informing strategic
initiatives. As we proceed, it’s crucial to prioritize data integrity and accuracy throughout the conversion
and join process, ensuring reliable and meaningful outcomes from our analyses.

One method for converting and joining a cohort to the datasets. This approach involves using addresses
and/or ZIP codes from the cohort data and mapping them to FIPS codes, which serve as the common
identifier in our datasets. To facilitate this mapping process, we rely on crosswalk tables provided by the
U.S. Housing and Urban Development’s Office of Policy Development and Research.

These crosswalk tables offer a reference point for associating ZIP codes with corresponding FIPS codes,
enabling integration with our datasets. However, it’s important to acknowledge that this process is not
without its limitations. In approximately 45% of cases, ZIP codes cannot be perfectly mapped to FIPS
codes at the county level. This imperfection underscores the challenges inherent in geographic data
integration and highlights the need for careful consideration and validation when performing these
conversions.

Despite its imperfections, leveraging crosswalk tables remains a valuable approach for linking cohort data
to our datasets, providing a foundational step in the analysis and interpretation of determinants of health.
As we navigate through this process, it’s essential to remain mindful of these limitations and explore
alternative methods for data integration where necessary, ensuring the accuracy and reliability of our
analyses.

The second method for utilizing our datasets, which involves leveraging latitude and longitude
coordinates for conversion and joining purposes. SQL Server offers support for two spatial data types:
Geometry and Geography. These data types enable a more precise conversion of latitude and longitude
coordinates to FIPS codes. Unlike the first method which relies on crosswalk tables, this approach
provides a higher level of accuracy in mapping locations to FIPS codes.

However, it’s important to note that implementing this method requires a higher level of expertise and
experience in working with Geometry and Geography files within SQL Server. Users must possess a
deeper understanding of spatial data manipulation techniques and SQL Server functionalities to
effectively execute this conversion process. Despite the complexity involved, leveraging latitude and
longitude coordinates through SQL Server’s spatial data types offers the advantage of increased precision
and accuracy in data integration.

Organizations with skilled personnel and advanced technical capabilities may opt for this method to
ensure the highest level of spatial data accuracy in their analyses. As with any advanced technique,
thorough testing and validation are essential to verify the integrity of the converted data and ensure its
suitability for analysis and decision-making purposes.

3.8 Error Checking

Beginning with the FY23Q1 release, the ORNL team will additionally give succinct information
regarding error-checking activities in order to provide formal evidence that the datasets supplied have
been thoroughly error checked. Our data profiling process is described in our project’s overview
manuscript [12]:

“Following standard data and software development methodologies, data profiling is performed in four
different work environments: 1) a team-shared work environment for selection, extraction, and refinement
of raw data (development); 2) an ORNL intranet work environment focused on quality assurance testing
(QA-Intra); 3) an ORNL Knowledge Discovery Infrastructure (KDI) secure work environment that stores
highly sensitive data and ensures its security (QA-KDI). And finally, 4) a production environment housed
within the KDI environment and accessible to our VA sponsors, (Production). We carried out test
iterations in each of the four work environments as the datasets moved through them to confirm data
integrity and system compatibility.

All datasets were error-checked using a data profiling strategy that includes at least two reviewers and the
following test groups:

  1. evaluating missingness: i.e. determining the amount of missing data by randomly checking for
 them;

  2. compiling descriptive statistics, such as the number of rows, columns, and types of variable data;

  3. appending checksums to a subset of the columns on both the source and destination copies to
 ensure consistency;

  4. consistently representing the social and physical environment using FIPS codes as geographic
 administrative boundaries and confirming that the FIPS codes correspond to the geographic
 administrative boundaries of the original data;

  5. manually comparing the first, last, and five additional randomly selected rows for consistency
 between the source and target datasets.

When datasets are developed at ORNL, which we call ‘derivative’, ORNL will provide extra error-
checking utilizing a combination of statistical methodologies based on each dataset’s properties, in
addition to the data profiling methodology described above.” [12]

4.1 Data Source

ORNL, VA, and OpenStreetMap

4.2 Description

The Drive-Time dataset calculates driving distance and estimated travel time from patient addresses to the
nearest VA healthcare facilities. It also assigns county-level FIPS codes based on geocoded address
locations to improve geographic accuracy. The dataset is developed and maintained by ORNL in
collaboration with the VA. It integrates data from the VA Corporate Data Warehouse (CDW) and
refreshed OpenStreetMap (OSM) road network data to ensure accurate routing. The dataset supports
analyses of patient access to VA facilities and healthcare accessibility. It informs resource allocation,
facility planning, and transportation decisions within the VA’s Community EDH Data initiative.

This update mirrors previous deliveries. ORNL did not change the underlying methodology; the only
updates reflect refreshed source tables provided by the VA and updated OSM data, as detailed below.

Limitations

Proximity measures are based on modeled drive times rather than actual travel behavior, which may be
affected by traffic, safety conditions, or temporary road changes. Additionally, this dataset is restricted to
use within the VA’s EDH initiative, and access is coordinated through program managers to ensure
compliance with usage guidelines.

Method for Identifying the Nearest Facility

  11. The process begins by identifying the three nearest VA facilities using straight-line (Euclidean)
 distance between geographic coordinates.

  12. Routing algorithms are then applied using the most recent version of the OpenStreetMap (OSM)
 road network—updated by ORNL for each dataset release. These algorithms estimate drive times
 to each candidate facility.

  13. The facility with the shortest estimated drive time is selected, and the remaining two are excluded
 from the final dataset.

 7. Food Bank and Pantry List

7.1 Data Source

FoodPantries.org and FreeFood.org

7.2 Description

The Food Bank and Pantry dataset contains a crowd-sourced list of food pantries, food banks, soup
kitchens, and nonprofit organizations across the U.S. It uses two sources (FreeFood.org and
FoodPantries.org) which were compiled and prepared by Oak Ridge National Laboratory (ORNL). This
dataset can be used to locate free food resources, assist individuals and families in need, support
community outreach efforts, and facilitate research and planning related to food insecurity programs.

Separate food pantry and food bank datasets were originally delivered in FY25Q1. Due to significant
overlap between the two tables, even though they originated from different websites, the VA sponsor
requested that they be merged into a single dataset. In addition, the FY25Q1 datasets were provided at the
census tract level.

This release provides one unified list at the county level based on 2024 Census boundaries.

Definitions

  • A food bank is a warehouse and distribution center where food is collected, stored, and
 distributed to local pantries and soup kitchens.

  • A food pantry is a charitable organization that directly distributes food and groceries to
 individuals and families in need.

FoodPantries.org is a comprehensive directory of food pantries, food banks, soup kitchens, and nonprofit
organizations in the United States dedicated to combating hunger. The website provides detailed
information about local resources, including addresses, hours of operation, contact details, and services
offered. Entries are submitted by members of the community and curated to ensure the information is as
accurate and current as possible.

By connecting individuals and families with essential food resources in their communities,
FoodPantries.org supports food security and assists organizations in their mission to reduce hunger.
However, as a crowd-sourced platform, some data may be unstructured or contain inaccuracies and entry
errors.

FreeFood.org is an independent organization dedicated to helping individuals locate and contribute free
food resources locally and nationwide. The organization is not affiliated with any government agency or
nonprofit organization.

These organizations differ in purpose and structure, and FreeFood.org’s listings reflect this distinction.
Some data sources prioritize food pantries, while others emphasize food banks.

 8. 2020 Rural-Urban Commuting Area (RUCA) Codes

8.1 Data Source

U.S. Department of Agriculture (USDA)

8.2 Description

The Rural-Urban Commuting Area (RUCA) Codes dataset provides a detailed rural–urban classification
scheme based on population density, urbanization, and daily commuting patterns. It was sourced from the
U.S. Department of Agriculture (USDA) Economic Research Service (ERS) and prepared by Oak Ridge
National Laboratory (ORNL). This dataset can be used to map service availability, support outreach
efforts, and examine disparities related to access to care, infrastructure, workforce distribution, and social
and environmental determinants of health across rural and urban settings.

Note: This dataset represents 2020 RUCA codes but is expressed using 2023 county FIPS codes.
Therefore, modern Connecticut planning region codes are reflected in these files.

The 2020 RUCA classification consists of 10 primary codes and 21 secondary codes. This release delivers
primary RUCA codes only.

Although the RUCA framework includes secondary codes that describe additional commuting
relationships, secondary RUCA codes are not included as variables in the FY26Q2 dataset and were not
used in the county-level aggregation. The secondary code table is included solely as background
documentation, and metadata tables, to support interpretation of RUCA definitions and terminology.

Controlled vocabularies for RUCA are also maintained in the repository metadata tables. RUCA code
definitions, including the secondary codes and the broad rural–urban grouping, are stored in
[OMHSP].[code_set] and [OMHSP].[code_set_values] to support consistent labeling, reporting, and
downstream user interfaces. For example, code_set_id = 2 (“RUCA Broad Classification (2020)”) defines
two categories (Urban/Metropolitan (RUCA 1–3) and Rural/Nonmetropolitan (RUCA 4–10)) which
are used for documentation and interpretation, even though only primary RUCA-derived measures are
included in the dataset outputs.

Primary RUCA Codes (2020)
Primary RUCA codes define urban cores and identify census tracts that are most economically integrated
with those cores based on commuting flows. Secondary RUCA codes capture additional commuting
relationships to larger urban cores, allowing for finer differentiation of rural–urban connectivity.

This two-level structure provides flexibility for aggregating or disaggregating classifications depending
on analytic needs. While RUCA codes were originally developed using census tract-level data, the ORNL
team converted the source data to county-level FIPS codes for this dataset.

Limitations

RUCA codes are derived from commuting patterns and population thresholds that may not fully capture
local contextual factors, recent development, or seasonal population changes. County-level aggregation
may obscure intra-county variation, particularly in geographically large or socioeconomically diverse
counties.

 9. Homeless Shelter List

9.1 Data Source

ShelterList.com

9.2 Description

The Homeless Shelter List dataset provides the locations of homeless shelters across the U.S. and
includes facility-level data. It was sourced from ShelterList.com and prepared by Oak Ridge National
Laboratory (ORNL). This dataset can be used to map service availability, support outreach efforts, and
analyze shelter access in relation to Veteran housing instability.

The homeless shelter dataset was initially delivered in FY24Q4. In FY25Q1, an updated version was
provided using an enhanced algorithm that leverages Nominatim.org along with custom code for address
formatting, standardization, and census tract mapping. As a result, the number of shelter entries increased
from 2,308 in FY24Q4 to 3,277 in that release. The FY24Q4 dataset is now considered deprecated, and
the updated dataset is designated as Version 2 (v2).

The dataset is sourced from ShelterList.com, a national resource for locating emergency and transitional
housing for individuals and families across the United States. ShelterList.com includes detailed
information on various types of shelters, such as homeless shelters, women’s shelters, family shelters, and
youth shelters.

The website categorizes shelters by city and state and provides details such as contact information,
available services, eligibility requirements, and operating hours. Its mission is to assist individuals in need
by connecting them with safe and reliable shelter options.

For the FY25Q1 dataset, addresses and phone numbers were standardized, and duplicates were removed
to improve data quality.

The FY26Q2 delivery presents data standardized to county-level FIPS codes based on 2024 Census
boundaries, differing from the FY25Q1 release, which was provided at the census tract level. This release
also reflects updates identified on the source website.

The data are not downloaded directly from the website; instead, they are web-scraped and compiled from
hosted pages into a structured tabular format.

  • The data have been assigned county FIPS codes based on 2024 Census boundaries. These FIPS
 codes were determined using ORNL’s internal ADDRESS/Nominatim tool to geolocate the street
 addresses provided on the website. The website provides only street-level address information
 and does not supply aggregate geographic data.

  • No calculations were performed on the data.

  • The web-scraped values for name, phone_number, address, and description were edited to correct
 typographical errors and formatting inconsistencies in the crowd-sourced data.

APPENDIX B. ERROR CHECKING

 Appendix B. Error Checking

The following descriptive statistics were obtained using the Python describe function. The definitions of
the main statistics included are as follows:
• count: The number of non-null (or non-missing) values in the series or column.
• mean: The arithmetic average of all values in the series or column.
• std: The standard deviation, which measures the amount of variation or dispersion of a set of values. A
low standard deviation indicates that the values tend to be close to the mean, while a high standard
deviation indicates that the values are spread out over a wider range.
• min: The smallest value in the series or column.
• 25% (First Quartile / Q1): The 25th percentile, meaning 25% of the data points are less than or equal to
this value.
• 50% (Median / Second Quartile / Q2): The 50th percentile, which is the middle value when the data is
ordered. Half of the data points are below this value, and half are above.
• 75% (Third Quartile / Q3): The 75th percentile, meaning 75% of the data points are less than or equal to
this value.
• max: The largest value in the series or column.
