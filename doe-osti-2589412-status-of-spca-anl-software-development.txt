1 Introduction
 SPCA-ANL is a simulation tool used to perform deterministic analyses of sodium spray and
pool fires. Development of the SPCA-II (Spray Pool Combustion Analysis) code began in the mid-
1980s as part of the Clinch River Breeder Reactor (CRBR) Project. At that time, development of
SPCA-II [1], which was led by Rockwell International, was focused on treatment of large-scale
sodium spray, stream, and pool fires that were anticipated to be prototypic of the steam generator
building cells in CRBR. Under more recent DOE NE programmatic activities, the SPCA-II code
was recovered from existing literature and underwent minor modifications to generate a stable
executable. This recovered version of the code was not formally released. As part of the Versatile
Test Reactor (VTR) Project in the 2010s, the SPCA-II code underwent key modifications to
improve stability, address modeling deficiencies, improve consistency between the code manual
and software, and address numerous bugs. At this point, SPCA-II was renamed SPCA-ANL [2].
Given that SPCA-II served as the original basis for SPCA-ANL, both codes share an integrated
history. Following termination of the VTR Project, the DOE NE Fast Reactor Program resumed
support of the software with the goal of building and maintaining software infrastructure that can
enable commercial-grade dedication of SPCA-ANL by an end user. Version 1.0, the first external
release of SPCA-ANL, was generated in June 2024.
 This report summarizes the development and maintenance activities completed for SPCA-
ANL in FY2025. This year’s work was focused on improving quality and usability of the code.
The provisional Software Quality Assurance (SQA) program has been established and was used
to test the procedures for infrastructure improvements, code development, bug fixes, and code
releases, as described in the following sections of this report.
 A code Version 1.0.1 was released in FY25, as described in Chapter 4.

2 Current Status
2.1 License Agreements
 In FY24, the only licensing pathway for external users of SPCA-ANL included government
use. To increase the flexibility of end use of the software, a path forward for commercial licensing
of the software has been developed in conjunction with the current joint copyright holder of SPCA-
II, L3Harris. In FY25, the first commercial license of the SPCA-ANL code was issued to industry
in compliance with this process. Government use and commercial licenses can be obtained for
SPCA-ANL through direct engagement with Argonne’s Science and Technology Partnerships and
Outreach directorate.

2.2 Current Repository and Supporting Infrastructure
 The SPCA-ANL source code is stored in a Subversion (SVN) [3] version control repository
that is integrated with Trac [4], a web-based software management tool that can be used to track
software issues and enhancements. The repository stores the main development line of the code
along with development branches and tags of previously released versions of the code. A Makefile
and a Visual Studio project file are both stored in the repository, providing two methods to compile
the source code into an executable using different Fortran compilers (GNU Fortran or Intel
Fortran). The input and output files for the test cases described in Chapter 4 of the code manual
[2] are also stored in the repository, as well as tools that allow for automated execution and
comparison of test case results with reference solutions.
 In FY25, the code manual has been moved from a Lab-approved cloud storage system to the
SPCA-ANL version control repository and is now being updated along with the code
developments.

3 Code and Infrastructure Improvements
 The focus of the SPCA-ANL developments in FY25 was on improving the code quality and
usability by means of continued improvement of the code infrastructure, code developments
(which were mostly related to supporting infrastructure improvements), and establishment of the
provisional SQA program. These developments follow the recommended activities list and rating
identified in FY24 [5], obtained feedback from the code users, and new improvement needs
discovered during the work in FY25. The infrastructure, code, and SQA developments in FY25
are described in the corresponding subsections below.

3.1 Infrastructure Improvements
 The SPCA-ANL supporting infrastructure consists of SVN/TRAC, the acceptance test suite
and associated tools, and the code compilation tools. A robust infrastructure is needed to facilitate
efficient, collaborative code development under the SQA procedures.

3.1.1 TRAC Improvements
 In FY25, improvements to the SPCA-ANL TRAC configuration were made primarily to
facilitate compliance with the provisional SQA program described in Section 3.3. Settings were
also updated so that developers associated with a TRAC ticket receive email notifications when
changes are made to the ticket.
 The workflow for TRAC tickets was configured consistent with the review and approve steps
outlined in the SQA procedures. This allows developers to send tickets for review to an
independent technical reviewer, who can either reject the ticket back to the developer or approve
it to the code manager. After merging the code development into the main development line, the
code manager can then send the ticket to the SQA reviewer, who can either reject the ticket or
approve it to the code manager to be closed. The code manager can then close the ticket.
 TRAC was also used to configure permissions for the SVN repository consistent with the SQA
procedures. The main changes were to limit write permissions to certain protected areas of the
repository to the code manager and the SQA coordinator, as appropriate. The TRAC server was
also connected to an Argonne system that is capable of managing the creation of user accounts.
This gives the code manager and the SQA coordinator the ability to add users without having to
modify or restart the web server. The Argonne system also automatically manages removal of
accounts if a user leaves the laboratory.

3.1.2 Acceptance Test Suite Improvements
 The SPCA-ANL acceptance test suite consists of test problems and reference output files. The
test suite is used during code development to ensure that any changes to code outputs as a result
of code changes are well understood and intentional. Improvements to the acceptance test suite
infrastructure have been made that make it easier to execute and determine if tests pass or if any
results differ from reference outputs. The acceptance test suite on the repository was also expanded
to include more tests which had been previously developed but stored in another location.
 Prior to FY25, a single Makefile was used both for code compilation and executing the
acceptance testing suite. The test suite was stored with the code, and test cases were run in the
same directory where the code was stored. For better usability, the test suite was separated from
the source code and a dedicated acceptance test Makefile was created. The existing infrastructure

for comparing numerical outputs to reference results was also expanded (as part of the
development described in Section 3.2.2) to compare all output files the code generates with
reference output files. This new capability helps developers who are working on code changes that
don’t impact numerical results but do impact other information printed in the output file such as
warning messages.
 The reference outputs previously stored on the repository were out of date, so they were
updated to be consistent with Version 1.0 and will stay in sync with code changes going forward.
Previously developed test cases that exercise different output unit options were also moved onto
the repository. These cases add testing coverage of all combinations of unit options. With these
improvements, the acceptance test suite and supporting infrastructure is more robust and will help
with future code development and SQA.

3.1.3 Code Compilation and Infrastructure Improvements
 Previously, the code compilation Makefile used gfortran to compile the code, while some
developers were separately utilizing Intel Fortran through Visual Studio to compile the code. In
order to unify developers and users around a single supported Fortran compiler and allow for
multiple supported operating system platforms (Windows, Linux, and Mac), the code compilation
Makefile was updated to use Intel Fortran (consistent with Version 1.0 of SPCA-ANL) and to be
compatible with all supported platforms. The ability to compile the code on all supported platforms
from a unified Makefile is important for regression testing during code development, ensuring that
the code produces the same results on all platforms.
 Text files stored with the source code documenting historical changes and potential future
development items were deleted and TRAC tickets were opened to track any pertinent items from
these files. Build files from the compilation of the code were also removed from the repository, as
these are not needed once they can be consistently created by any developer using the improved
Makefile.

3.1.4 Code Manual Infrastructure Improvements
 In FY25 the code manual was moved onto the repository, where it can be modified as code
changes are made. The example input given in the code manual was also stored as a text file, as
well as its outputs, alongside the code manual in the repository. This example input file is
distributed with the code releases, so it needs to be maintained in the repository. References that
had been stored on the repository but do not need to be under version control were moved to
another file storage location.

3.2 Software Improvements
 The code developments completed in FY25 were focused on supporting the code infrastructure
improvements described in previous section. All the code developments in FY25 were carried out
in the TRAC ticket system and followed the provisional SQA program described in the next
section.

3.2.1 Code Fix for Array Size Matching
 An issue with array size matching that prevented the code from compiling on the latest Fortran
compilers was identified and fixed. This fix, implemented as part of compiler updates described
in Section 3.1.3, did not affect the results of any acceptance testing and V&V cases and was only
related to the compilation issue.

3.2.2 VCELL Input
 In FY24, an issue was identified where one of the code’s inputs, VCELL for the room total
volume, was overwritten in the code. This issue was investigated and fixed in FY25. The VCELL
was internally calculated by the code based on the room height and cross-sectional (ceiling) area.
However, few examples were identified where the volume could be either smaller than area times
height, e.g. if there is a lot of equipment in the room, or larger, e.g. in non-uniform geometries.
Therefore, it was decided to retain the cell volume as an independent user input, by eliminating
default calculations of this variable in the code. Still, an option was left for user to let the code
calculate the volume as area times height, if the volume input is not provided, i.e., the user input
is zero. In this case, the cell volume calculated by the code is reported to user in the output file.
Since the cell volume input was already included in all V&V and acceptance testing inputs, no
changes to the input files were needed. However, since this input was previously overwritten by
the code, new reference solutions were recalculated for all inputs. For the V&V cases, it was found
that the provided cell volume input was already close to the product of height and ceiling area
(within 3% at most), such that the change discussed here did not affect the agreement of the code
results with any of the test data.

3.2.3 Code Version Check
 A new feature was introduced to the code to specify the code version (in “X.Y” format) in the
input file. This is done to ensure that each input file is used with the intended version of the code.
The code now reads this input and compares it with the version stored in the code. An error
message is generated if the code version input is either not provided or does not match the internal
code version. The code proceeds to calculations only when the two versions match. In the case of
matching code versions, there is no impact on the code results. However, printout to the output file
was updated to include the code release version.
 The code’s Acceptance Testing database was updated to include checking for missing,
misaligned (i.e., provided at the wrong location), or incorrect (not matching) code version input.
Since this feature was only related to version checking, it did not change the code results, as was
confirmed by Acceptance Testing procedure.
 This development exercised the provisional SQA procedures for software development
features. To that end, the Software Requirements Specifications (SRS), Software Design
Documentation (SDD), and Software Test Plan (STP) documents were prepared, reviewed and
stored in the TRAC system. The SQA procedures for Software Development and Modifications,
SPCA-SWP-2, and Software Testing, SPCA-SWP-3, were followed and tested in implementation
of the new feature.

3.2.4 Suppression of On-screen Warnings for Minimum Time Step
 In SPCA-ANL, the time step is calculated internally by the code on each time step to select the
maximum time step while still satisfying the solution stability criteria for all differential equations
solved by the code. At the same time, user provides the maximum and minimum time step the code
should not exceed. Although there are issues with limiting the maximum time step, other than
increased calculation runtime, imposing a user-defined limit on the minimum time step could lead
to potentially unstable numerical solutions. For this reason, when the minimum time step was
overwritten by the user input, a warning was displayed to the user that the selected time step is in
violation of the stability criteria. This warning was provided at each instance of time step limitation
and was meant to warn a user either to accept the difference or modify the input for minimum time
step.
 Although this warning is important, displaying it on the screen complicated execution of some
Acceptance Testing cases, where the results of the acceptance testing were hard to find among the
numerous time step warnings. To resolve this issue, the minimum time step warnings were moved
to the output file (and are no longer displayed on the screen). Still, to warn user if the minimum
time step was overwritten at any time during an execution, a flag was introduced in the code, and
a warning message is displayed to the user to check the output files for details of when the
minimum time step change was implemented. This warning message is now displayed only one
time at the end of code’s execution and does not clutter the screen during Acceptance Testing runs.
Since this change was only related to warning display, it did not change the code results, as was
confirmed by Acceptance Testing procedure.

3.2.5 Code Manual Updates
 The user manual was updated to reflect the code changes described above, such as to include
the description of the new input VER for the code version, explain an option to let the code
calculated cell volume VCELL (if this input is zero), and to update all V&V results with the
corrected input for the cell volume. The example input files in the manual were also updated to
reflect new input for the code version.

3.3 Establishment of Provisional SQA Program
 Given the long-term goal of this work to develop an infrastructure for SPCA-ANL that enables
commercial-grade dedication of the code by an end user, efforts were continued this fiscal year to
develop and mature an SQA Program that would align with the aforementioned goal. A full set of
SQA Program documentation, including plans and procedures, has been developed and
implemented on a provisional basis. Enactment on a provisional level allows the development team
to exercise and test the Program features and requirements and generate feedback on aspects of the
Program which may need updated to facilitate more efficient workflows. At present, the SPCA-
ANL SQA Program scopes all aspects of the typical software life cycle with the exception of
software retirement. The SQA Program is designed to be implemented with efficient resources
while also targeting alignment with key regulatory requirements, including DOE Order 414.1D
[6], DOE Guide 414.1-4 [7], and ASME NQA-1-2022 [8].
 The documentation proposed for the SPCA-ANL SQA Program is listed in Table 3.1. Drafts
of these materials have been completed and are being used on a provisional basis. All ticket types
(task, development, and release) have been exercised by the team and feedback on the process has
been documented for possible inclusion in Program documentation revision. Following

5 Summary and Path Forward
 The FY25 work on development of SPCA-ANL was focused on improving quality and
usability of the code. The improvements to the SPCA-ANL supporting infrastructure included
updates to the SVN/TRAC configurations, the acceptance test suite and associated tools, the code
compilation tools, and code manual infrastructure. Implemented software improvements include
several bug fixes, resolution of one input being overwritten by the code, and implementation of
code version check in the input file. The code manual was updated according to the implemented
code changes. The provisional Software Quality Assurance (SQA) program has been established
and was used to test the procedures for infrastructure improvements, code developments, bug fixes,
and code releases.
 A code Version 1.0.1 was released in FY25, with the main improvement over the previous
release (Version 1.0) being the ability to compile the code on three supported platforms, -
Windows, Linux, and Mac, - using the supported Intel Fortran compilers. The release also includes
recent improvements to the acceptance testing tool. The release was also used to exercise
provisional SQA procedures for code release.
 Future activities will include continuing implementation of code and infrastructure updates
identified in FY24, which were not implemented yet in FY25, as well as new code development
needs identified in FY25, including feedback from the external code users. Some of these future
needs are already documented and planned in corresponding tickets that were created in the TRAC
system for future implementation. Development of the SQA program will be completed, with a
formal implementation of the Program planned for Q1 FY26.
