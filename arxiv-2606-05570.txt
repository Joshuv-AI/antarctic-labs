TensorBench: Benchmarking Coding Agents on a Compiler-Based Tensor Framework
Bobby Yan, Fredrik Kjolstad

Abstract
Repository-level coding benchmarks face a trade-off between task difficulty and evaluation reliability: tasks that challenge frontier models often involve large codebases with incomplete test coverage, while human review does not scale. We introduce TensorBench , a benchmark of 199 199 feature-addition and refactoring tasks on an open-source compiler-based tensor framework that extends PyTorch with first-class support for dense and sparse tensors. Tasks cover new sparse formats, dense optimization passes, IR transformations, scheduler changes, runtime components, and high-level numerical operators. TensorBench grades each run by applying the agent’s patch and running the framework’s test suite, which includes the pre-existing randomized regression tests and any tests the agent adds. For feature-addition tasks, a pass means that the patched repository preserves the tested pre-existing behavior and satisfies the agent-added checks for the requested feature. We evaluate seven coding agents spanning three frontier model families and one open-weight model. Pass rates under this criterion range from 64.8 % 64.8\% for the strongest agent to 22.1 % 22.1\% for the weakest. Agents pass different subsets of tasks: pairwise Cohen’s κ \kappa ranges from − 0.07 -0.07 to 0.43 0.43 , with κ = 0.05 \kappa=0.05 for the two strongest agents.

Introduction

Code generation benchmarks face a trade-off between task difficulty and evaluation reliability. Simple tasks such as completing a function or fixing a localized bug can be evaluated reliably with unit tests,
but as model performance approaches saturation on these benchmarks,
the field has moved toward harder repository-level tasks. The evaluation signal is weaker in this setting because repository test suites are not designed to catch the bugs that agents introduce
[
1
]
, and manual review does not scale.
To separate capability gains from grading noise, repository-level benchmarks need difficult tasks paired with evaluation criteria that superficial edits are unlikely to satisfy.

We present
TensorBench
, a repository-level benchmark built around a compiler-based tensor framework.
Tensor compilation is well suited to this setting:
many changes require repository-scale engineering, and externally visible behaviors have well-defined reference outputs.
Implementing a new tensor operation, sparse tensor format, internal representation (IR) transform, scheduler optimization pass, or code-generation feature often requires coordinated changes across the compiler pipeline.
For many tasks, the resulting kernels can be checked against a trusted reference; for structural compiler changes, the same tests also exercise whether existing lowering, scheduling, and code-generation invariants remain intact.

TensorBench grades final repository behavior rather than similarity to a reference patch. Many tasks require edits to shared compiler machinery—sparse-format handling, iteration lattices, IR lowering, scheduling, code generation, or runtime kernels—so the inherited regression suite is an important signal: mistakes in these paths often affect many existing operators and are exposed by randomized, parametrized tests. For sparse and mixed sparse-dense operators, these tests usually compare against dense PyTorch; for dense optimization and scheduling changes, they may compare against an existing unoptimized path.
This signal is still only a compatibility check. New-feature behavior is constrained mainly by any tests the agent adds, so a pass should not be interpreted as evidence that the patch satisfies every reasonable interpretation or corner case of the natural-language request.

TensorBench grades the final repository state rather than similarity to a reference patch.
Although the tasks ask for new features, many of them require edits to shared compiler machinery: sparse-format handling, iteration lattices, IR lowering, scheduling, code generation, or runtime kernels.
Hence, the inherited test suite is an important correctness signal: a small mistake in a shared lowering, scheduling, or code-generation path can propagate to many generated kernels and tensor expressions, and is likely to be exposed by randomized and parametrized tests over existing operators. For sparse and mixed sparse-dense operators, those tests usually compare against dense PyTorch; for dense optimization and scheduling changes, they may compare against an existing unoptimized path.
A pass therefore means the patch preserves tested existing behavior and satisfies the tests the agent wrote for the new feature.
Since behavior on the new feature is checked primarily by the tests written by the agent, a pass should not be interpreted as evidence of feature completeness.

We evaluate seven coding agents from four CLI scaffolds (Claude Code, Codex CLI, Gemini CLI, OpenHands). The agents cover three frontier model families and an open-weight model.
All runs are graded with a Docker-based harness that applies the agent’s unified diff in a fresh container, builds the C++ runtime, and runs the full test suite.
The strongest agent (Claude 4.7) passes
64.8\%
of tasks under the post-patch test-suite criterion, improving by
22.1
points over Claude 4.6 on the same task set; its rate of breaking pre-existing tests is
16\%
, down from
27\%
for Claude 4.6.
Per-task pairwise agreement across agents is low (
\kappa\in[-0.07,0.43]
), and the union pass rate of any two agents exceeds the better of the two by
6\textrm{--}20
points.
The benchmark code, predictions, and agent trajectories are available at
https://tensorbench.org
.

TensorBench

TensorBench asks an agent to extend the target framework in six areas: user-facing APIs (
API
), sparse tensor formats (

), intermediate representation changes (
IR
), scheduler optimization passes (

), code generation features (

Two properties of the codebase make the benchmark possible: an architecture that supports non-trivial extensions along each axis, and a randomized regression suite that exercises many shapes, sparsity patterns, formats, and compiler paths.

2.1
Target Framework

Scorch
[
20
]
is a publicly released, open-source compiler-based tensor framework (
\sim 11{,}000
lines of Python and a
\sim{}450
-line C++ runtime header that is prepended to every JIT-emitted kernel).
It extends PyTorch with first-class support for both sparse
and
dense tensors and is designed as a drop-in replacement:
import scorch as torch
provides PyTorch’s interface backed by compiled kernels, with additional support for calling
einsum
,
matmul
, and other tensor operations on sparse tensors in arbitrary per-dimension format combinations.
The compiler uses a three-level IR (CIN
\to
LLIR
\to
JIT-compiled C++). The same lowering pipeline emits sparse-sparse contractions, dense matmuls, and hybrid sparse-dense kernels.
Optimization passes such as loop reordering, tiling, workspace insertion, and sparse prefetch insertion apply across both regimes, and TensorBench tasks often ask agents to add or extend these passes.

gives the full architecture.

2.2
Task Formulation

Each TensorBench task pairs a natural-language feature or refactoring description with a pinned base commit that identifies the repository state to be edited.
Success is measured by the post-patch test suite: a run passes iff every test in that suite passes, including inherited regression tests and any task-specific tests added by the agent. We report this pass/fail label throughout the paper.

2.4
Grading Methodology

The upstream test suite (
160
–
280
test functions per base commit, after parametrization) consists primarily of randomized correctness tests.
A typical test allocates operand tensors with random values and a chosen sparsity pattern, which may be
0\%
for the dense case, runs the operation under test, and compares the result against an appropriate reference implementation. For sparse and mixed sparse-dense operators, the reference is usually dense PyTorch via
torch.allclose
; for optimization and scheduling changes, the reference may be an existing unoptimized execution path. Random seeds are explicit, sparsity ratios and shapes vary across tests, and parametrization sweeps multiple format combinations, including CSR, DCSR, COO, and dense tensors.
These randomized sweeps catch bugs that isolated hand-written examples often miss: off-by-one errors in coordinate-list iteration, missing terms in iteration lattices, broken intersection logic for sparse-sparse multiplication, and miscompiled inner loops in dense-dense matmul. The upstream developers maintain this suite as the project’s primary regression-prevention mechanism, and we use it directly for grading;
Appendix

G
reproduces a canonical test verbatim. A passing patch must therefore preserve kernel behavior across the inputs, formats, and compiler paths covered by this suite, not only on examples the agent inspected.

Post-patch test-suite criterion.

We require every post-patch test to pass. The pre-existing randomized suite checks preservation of existing compiler behavior across sparse format conversions, iteration logic, code generation paths, and supported tensor operators. For newly requested behavior, the task-specific checks come from tests added by the agent.
A passing run therefore shows that the implementation and the agent-added tests are internally consistent while preserving the repository’s existing behavior.
It does not establish the stronger claim that the patch satisfies all possible interpretations or corner cases of the natural-language request.
The adversarial-behavior audit in
Section

3.6
checks whether the agent-added tests or patch structure exploit the criterion, for example through vacuous tests, API mismatches, weakened existing tests, or patches that make no substantive code changes. The audit does not judge functional correctness.
The pass rates in
Table

1
should be read alongside the audit rates in
Table

6
.

Robustness to task quality.

TensorBench is less sensitive to imperfect task descriptions because it grades the final repository state, rather than compliance with a fully specified implementation recipe.
For an underspecified request, a capable agent can choose a reasonable interpretation, implement it, and add tests that make that interpretation explicit; the regression suite then checks that the change preserves existing behavior across randomized, parametrized compiler paths. For an infeasible request, the appropriate behavior is to avoid unsupported code changes rather than force an implementation that breaks the repository.
In both cases, the grading condition is the same: inherited regression tests must pass, and any agent-added tests must pass as well.
This grading setup makes LLM-generated descriptions usable as candidate work items, but it does not make task quality irrelevant.
Infeasible, underspecified, or misleading descriptions still affect how passes and failures should be interpreted, especially because feature behavior is partly constrained by agent-added tests.
We therefore inspected all
199
task descriptions. Some closely resemble tasks we would have written manually; others include more implementation detail than we would normally provide, but each describes a plausible change for a competent contributor to attempt.

2.6
Patch Memorization and Contamination

Behavioral grading also changes the benchmark’s contamination profile.
Public coding benchmarks face contamination risk because their tasks and reference solutions are often published on the web, where later training corpora may include them.
This concern motivates private held-out splits such as SWE-Bench Live
[
25
]
.
TensorBench reduces incentives on memorizing a canonical solution because any behaviorally adequate solution can pass. This does not eliminate contamination risk: task descriptions, trajectories, tests, and successful patches can still enter future training corpora.
Standard contamination safeguards are necessary: benchmark artifacts should not be deliberately included in training data.

3.6
Adversarial-Behavior Audit

To check whether runs exploit weaknesses in the test criterion, especially in ways that could inflate pass rates, two LLM judges (Claude Opus 4.7 and GPT-5.5) examine every run for four patterns: agent-added tests that do not exercise the API named by the task, pre-existing tests modified or weakened, empty or cosmetic patches on tasks that require new code, and added tests that pass regardless of the implementation.
Each flag is a local check on the diff and added tests: the judges are not asked to determine whether the patch is functionally correct. The audit therefore does not require the judges to solve the underlying tasks.

The audit suggests that this distinction is especially important for Qwen3 and Gemini 3.1: vacuous added tests, weakened pre-existing tests, and empty patches can let a trial pass the suite without correctly implementing the task, so their

4
Limitations

Post-patch test-suite oracle.

TensorBench does not use independent hidden tests or human review to certify feature correctness. For feature-addition tasks, the post-patch suite combines pre-existing randomized regression tests with tests written by the same agent that wrote the implementation.
A pass therefore indicates that the implementation and tests are mutually consistent and preserve existing behavior for the cases tested by the suite.
It may miss untested cases required by the requested feature.
TensorBench should be read as measuring an agent’s combined ability to implement a substantive change, add tests for the intended change, and avoid regressions. Hidden validation tests for a representative subset would provide a direct estimate of the false-positive rate.

Benchmark scope.

TensorBench is built on a single codebase. The results therefore do not measure generalization to other compiler-based projects or to other software domains.
We expect the evaluation methodology to transfer to codebases where changes can be validated through runnable outputs, because it evaluates the artifacts produced by the code changes rather than judging the patch directly.

Adversarial agents.

An agent optimizing for pass rate rather than task completion could in principle write tests that do not exercise the requested API, weaken or delete pre-existing tests, or make no substantive edits on tasks where the existing suite does not cover the new functionality.
In the audit reported in
Section

3.6
, the LLM judges found at most
1.5\%
of the trajectories adversarial for five of the seven agents. The exceptions are Qwen3 and Gemini 3.1 (
17.0\%
and
5.4\%

and

To the extent these patterns produce passes that do not constrain the implementation, the pass rates of
22.1\%
and
31.7\%
in
Table

1
are upper bounds on these agents’ true solve rates. A determined adversary is a separate threat model. For future agent submissions, the same audit can run alongside the output-based grader to flag such behavior.

Conclusion

TensorBench is a benchmark of
199
feature-addition and refactoring tasks for a compiler-based tensor framework. It grades the patched repository, requiring both inherited regression tests and agent-added tests to pass.
For feature-addition tasks, this measures whether an agent can produce an implementation and accompanying tests that pass the post-patch suite while preserving existing compiler behaviors on the tested kernels.
Across seven coding agents, pass rates range from
22.1\%
to
64.8\%
; the leading Claude agent improves by
22.1
points over the previous generation while the regression-introduction rate falls from
27\%
to
16\%
. Per-task agreement is low (
\kappa\in[-0.07,0.43]
), but the tasks every agent fails concentrate on changes that alter core compiler internals: new IR passes, hierarchical sparse formats, and cross-stack infrastructure.

Why an agent-generated dataset is useful.

Datasets built with LLM assistance raise two concerns: descriptions that are subtly underspecified, and descriptions that are infeasible against the actual codebase.

Section

2
addresses part of the underspecification risk: grading depends on the tested behavior of the resulting codebase, rather than on a single intended solution for each description. Dataset growth via the prompts above reduces authoring cost, but does not by itself validate feasibility or completeness. The present benchmark relies on author inspection of all task descriptions; future versions would be stronger with reference implementations or maintainer-written validation tests for a representative subset.

Description structure.

Each generated feature description follows a four-part structure: (i) a one-sentence statement of the goal, (ii) an implementation sketch that names the affected files, the public surface or internal component to change, and any non-trivial design decisions, (iii) validation requirements describing what the agent-added tests should cover, and (iv) a fixed trailing note instructing the implementing agent not to invoke the test suite directly.
The refactoring variant keeps the goal, implementation sketch, and trailing note, but specifies behavior-preserving restructurings rather than new feature tests:

“Note: Do not run the test suite to verify your implementation. You may run build commands (e.g.,
pip install -e .
) to check that the code compiles, but do not execute any pytest commands. The full test suite will be run separately during evaluation.”

During dataset construction, the note was appended verbatim to every task description. The harness does not add it separately; it simply wraps the stored description in the prompt template shown in
Appendix

C
. The note is an instruction to agents, not an enforced disqualification rule.
It is an instruction to agents, not an enforced disqualification rule. We record pytest invocations in trajectory analysis, but final grading always occurs in a fresh container from the extracted diff. The implementation-sketch portion frequently overspecifies file paths, function signatures, and helper-class names: this is a consequence of the authoring prompt directing the agent to explore the codebase first, so generated descriptions tend to be anchored to concrete module names.
Any remaining under- or overspecification is reflected only indirectly through the post-patch test outcome; no additional judge resolves the intended task specification.

Feature/refactor split.

The
194/5
split reflects the primary purpose of the benchmark: code synthesis on novel functionality, where requested behaviors can be checked against reference outputs on randomized inputs.
The five refactoring tasks (one hand-written, four authored under the variant prompt in
) are included as a small controlled comparison: they leave the test surface unchanged and make the grading question primarily about behavior preservation rather than new-feature design (
Appendix

D
).
Although small, this subset gives a preliminary view of how agents handle behavior-preserving restructuring without shifting the benchmark’s focus away from feature tasks.

The
199

•

API
(
99

•

Scheduler
(
37

Loop transformations (tiling, fusion, reorder/restructure) are the largest subgroup; the remainder is IR analyses and scalar optimizations (LICM, DCE, CSE, simplification, prefetch, dependence analysis), sparse-specific passes (workspace transforms, format adaptation, iteration-space pruning), dense-only passes (BLAS pattern match, broadcast specialization, dataflow selection, layout rewrite), and contraction-order planning.

•

Format
(
20
tasks): new sparse formats. The block/ELL family (BSR, ELL, DIA, CSC, hybrid, N:M), compressed-style formats (bitmap, hash-map, RLE, Morton, packed coords, SINGLETON), and hierarchical or multi-dimensional formats (CSF, ragged, octree, nested) account for most of the group; the rest covers semantic extensions (symmetric matrices, configurable fill value).

•

Runtime
(
28

Appendix B
Evaluation Pipeline Detail

The harness performs the following steps for each task:

1.

Build a Docker image based on
python:3.11-slim
with PyTorch, the Scorch git tree pinned to the task’s
base_commit
, and the C++ runtime built once at image-build time.

2.

Mount the agent’s environment (system prompt, agent CLI, model credentials) and start the agent with the task description and a frozen working copy of the repo.

3.

Capture a unified diff covering all the agent’s edits at the end of the session.

4.

Start a fresh container, apply the diff, clear the JIT-compiled-extension cache, rebuild the C++ runtime (idempotent if unchanged), and execute

.

5.

Parse verbose pytest output line-by-line to count passed / failed / errored tests by name, falling back to the summary line if no verbose lines are found.

6.

Mark the task as successful iff
after.failed == 0
and
after.error == 0
.

, a task-agnostic harness. The benchmark-specific code is limited to: (1) the dataset of

Appendix F
Scorch Framework Background

Compilation pipeline.

Scorch uses several internal representations. (1)
Concrete Index Notation (CIN)
expresses a tensor computation as a nest of
ForAll
loops over abstract index variables, with
TensorAssign
leaves that read and write
TensorAccess
terms. (2)
Lower-Level Internal Representation (LLIR)
is a pre-C++ IR with explicit memory allocations, while-loops, and array accesses. (3) The codegen backend lowers LLIR to a C++ string, which is JIT-compiled by PyTorch’s
torch.utils.cpp_extension
loader and dlopened. The lowering is decomposed across three Python modules totaling
\sim 4{,}500
lines:
cin_lowerer.py
,
iter_lattice.py
(for constructing per-loop iteration spaces from format types), and
codegen.py
. The same pipeline emits a sparse-sparse contraction, a dense matmul, and a hybrid sparse-dense convolution; many of the optimization passes (loop reordering, mode-order constraint solving, tiling, workspace insertion, sparse prefetch insertion, etc.) apply to both regimes.

Format system.

Sparse formats are described per dimension following the format-abstractions design of
Chou et al. 2018
: each dimension is annotated with a storage mode (
DENSE
,
COMPRESSED
,
SINGLETON
,
COORDINATE
), and familiar layouts correspond to specific combinations—a pure-dense tensor is
DENSE
in every dimension, CSR is
[DENSE, COMPRESSED]
, COO is
[COORDINATE, COORDINATE]
, and so on. The system is open: many TensorBench tasks ask the agent to add a new mode (RLE, Morton, ragged, hash-map, octree, bitmap) and integrate it throughout the pipeline.

Lineage.

Scorch’s design follows the TACO
[
10
]
lineage of sparse compilers, with CIN echoing the concrete index notation of
Kjolstad et al. 2019
; it is reimplemented in Python with an emphasis on extensibility for research and broadened to treat dense codegen as a first-class concern (rather than a special case of fully-dense formats).

Audit design.

The audit reads every run, passing or failing (

), and flags four patterns independently: agent-added tests that do not exercise the API the task names (
api_mismatch
), pre-existing tests modified or deleted in ways that weaken them (

a per-run overall verdict of

, or

None of the flags require the judge to determine whether the patch correctly implements the requested behavior; that would amount to re-solving the underlying task rather than auditing local evidence in the diff and tests.
Both judges receive the agent’s unified diff, the bodies of any agent-added tests, and the list of pre-existing tests the diff modifies or deletes. The verbatim system prompt appears in
Section

J.3

J.5
Reproducibility

The audit harness is released alongside the dataset and harness in the same repository (
Appendix

K
) under the
audits/
subdirectory.
It re-reads the per-(agent, task) evaluation artifacts published with the predictions and produces verdicts independently of any agent execution, so re-running the audit on a frozen evaluation set requires only judge calls.
Pinned model identifiers (
claude-opus-4-7
,
gpt-5.5
), the seven-agent registry, and the binding-judge rules live in a single configuration file; the prompt in
is loaded from
audits/prompts/
. Per-call results are cached on disk by
(audit, agent, judge, instance, prompt_sha8)
, so reruns reuse the cached results and changing the prompt changes the cache key. Running the audit end-to-end against a new submission requires only the submission’s
evaluation_results/<agent>/<instance_id>/
directories in the layout the released artifacts use, plus an
ANTHROPIC_API_KEY
and an
OPENAI_API_KEY
; total provider spend for the seven-agent run reported in this paper was approximately
\$650
(averaging
\sim\$0.23
per judge invocation).
