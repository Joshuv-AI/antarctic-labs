 Abstract
 This manual documents an end-to-end workflow for converting production cost modeling
 (PCM) outputs into alternating current (AC)-feasible power-flow base cases and geospatial
 visualizations using the C-PAGE, BPS-TUNE™, EGRET, and QGIS toolchain. Starting from
 GridView PCM results, the process standardizes data to HDF5, samples representative hours,
 and constructs direct current (DC) PowerWorld snapshots that are benchmarked against the
 original PCM flows. These DC cases are then transformed into EGRET-ready inputs, solved
 with a two-stage AC optimal power flow that adjusts reactive power and loss allocations to
 obtain AC-feasible solutions, and mapped back into converged AC PowerWorld.pwb cases.
 Dedicated benchmarking steps validate DC and AC consistency (PCM↔PowerWorld and
 EGRET↔PowerWorld) using comparison utilities available in BPS-TUNE™. The workflow is
 completed by database-backed and QGIS-based visualization capabilities that generate map
 projects and analytics outputs. The manual is written for power-system practitioners with limited
 software engineering background and provides tested commands, configuration templates, and
 practical guidance for running the C-PAGE process on Windows with Conda-managed Python
 environments.

 Summary
 This document translates the chronological alternating current (AC) power flow automated
 generation tool (C-PAGE) framework and associated software packages into a concrete,
 reproducible process for users who need to turn production cost model (PCM; GridView)
 runs into validated AC PowerWorld cases and visual products. The emphasis is on operational
 instructions rather than algorithms. Each step is presented with its purpose, required tools and
 branches, expected inputs and outputs, and the exact commands and Tom's Obvious Minimal
 Language (TOML) configuration patterns used on real project data.

 Section 1 introduces an overview of the C-PAGE process and its role in bridging PCM outputs
 and AC power-flow models.

 Section 2 is a preparation section that covers installation and configuration on Windows,
 including Conda environment setup, cloning and updating the relevant BPS-TUNE™ and
 EGRET repositories, branch management (e.g., cpage, dataset_comparison, pwparser,
 pcm_acopf, qgis), and access to local and HyperText Markup Language documentation.

 Subsequent sections follow the numbered C-PAGE workflow steps: conversion of PCM .mdb
 results to .h5 (section 3), sampling and creation of direct current (DC) PowerWorld cases, DC
 benchmarking against PCM (section 4), construction of EGRET inputs (section 5), EGRET AC
 optimal power flow runs (section 6), conversion of EGRET AC solutions back to AC .pwb
 (section 7), and AC benchmarking between PowerWorld and EGRET (section 8). Each of these
 steps is backed by configuration file templates and examples that have been executed and
 verified on representative cases.

 Section 9 documents the visualization and analytics phase using QGIS integration in BPS-
 TUNE™. It focuses on the Python-CLI pathway, using make_qgis_data and build_qgz to
 produce QGIS projects driven by database-backed views and configuration TOMLs.
 Throughout, the manual is structured for beginner users of these tools: detailed shell contexts
 (Git Bash vs. Command Prompt), explicit environment activation, and validation checkpoints are
 included to reduce friction and make the C-PAGE workflow repeatable across projects and
 users.

 1.0 Introduction
 1.1 Purpose and Scope.
 C-PAGE, integrated within Bulk Power System - Transformation via Upgraded Network
 Evaluation (BPS-TUNE™), converts direct current (DC)-based production-cost outputs into
 converged alternating current (AC) power-flow cases and associated visual analytics.1 BPS-
 TUNE™ is a collection of PNNL’s grid planning capabilities. It is intended to be a tool (or library
 of tools) that support the simulation and analysis involved in various grid planning activities
 (e.g., national transmission planning study,2 value of nuclear energy to the reliability of the North
 American power system,3,4 and west coast offshore wind transmission study5). The workflow
 automates hour selection6, DC→AC translation, reactive support decisions, and case generation
 in commercial power flow (PF) tools, reducing a months-long manual process to hours while
 preserving fidelity to the original production cost model (PCM) solution.

 1.1.1 High-Level Flow

 Starting from PCM time-series (e.g., GridView), BPS-TUNE™ leverages the unified
 data-exchange module enabling tool interoperability (UniGrid) to acquire the necessary PCM
 time-series data. Smart sampling is performed to select representative PCM hours and hands
 those hours to C-PAGE. C-PAGE first builds DC-consistent snapshots that match PCM dispatch
 and flows in the PF model, then uses the Electrical Grid Research and Engineering Tools
 (EGRET) AC optimal power flow (ACOPF) feature to obtain a feasible AC solution with targeted
 reactive support. EGRET7 is a package that offers tools and models for optimizing electric grid
 operations. The EGRET solution is mapped back into a commercial PF case (PowerWorld),
 benchmarked, harmonized across hours, and finalized through planning based on reactive
 power vs. voltage analysis. Analytics and visualization modules summarize results and prepare
 geospatial/ Hyper Text Markup Language (HTML) outputs, with DC snapshot as the bridge.

 Because PCM is DC-linear and PF is AC-nonlinear, the first conversion step constructs a DC
 power-flow case in the PF tool that reproduces the PCM operating point. This reconciliation
 distributes region-level load to buses, disaggregates plant-level injections to units, aligns

 1.1.2 AC Solution via EGRET (two stages)

 EGRET solves an ACOPF in two stages. First, a feasibility phase adjusts for losses
 (i.e., area-coupled curtailment proxies) and provides broad reactive slack (proxy shunts)
 so a converged AC solution exists. Then, an optimization phase tightens criteria, penalizes
 deviations from PCM dispatch, and drives a sparser, more realistic reactive footprint. HVDC
 elements are modeled as coupled proxy generators during optimization and later mapped back
 to explicit DC equipment.

 1.1.3 From optimization Back to a PF Case

 C-PAGE translates the EGRET solution into a PowerWorld .pwb file by updating buses,
 generators, loads, phase shifters, and DC lines in a defined order. HVDC proxy results are
 converted into terminal injections that account for converter losses, and variable shunts from
 EGRET are discretized into actual step sizes. This produces an AC case that reflects the
 optimized solution and is ready for benchmarking.

 1.1.4 Benchmarking, Harmonization, and Planning

 The generated AC case is compared against the EGRET target (voltage magnitudes, slack
 accounting, HVDC transfers) and checked against solution-quality criteria, such as the absolute
 mismatch or mismatch percentage thresholds of branch flows, generator power, bus voltages,
 etc. Across multiple hours, C-PAGE consolidates added reactive devices, ranks candidates by
 frequency and local Q–V margins, and re-optimizes to minimize the device set while preserving
 performance. A reactive power vs. voltage analysis–based planning stage assesses reserves,
 tunes existing assets, and adds support only where sensitivity justifies it; an automated
 base-case selector improves robustness when large operating changes are present.

 1.1.5 Outputs and Visuals

 Final PF cases, metrics, and maps are written back through UniGrid for downstream use. The
 UniGrid model unifies data structure to standardize the reading and writing of grid related data
 in BPS-TUNE™. The Analytics and Visualization module produces utilization metrics,
 voltage/flow visuals, geographic information system (GIS)/Quantum geographic information
 system (QGIS) layers, and HTML reports, thus enabling transparent review and communication
 of results.

 1.2 Process at a Glance
 C-PAGE workflow steps are described below and shown graphically in Figure 1.1.
 1. PCM production cost run (input): The process assumes a completed GridView PCM study
 that produces a yearly or multi-period database (e.g., an .mdb case directory) with unit
 commitment, dispatch, and hourly flows. This PCM run is treated as the upstream source
 and provides the sole input to Step 2.

Introduction 2

 2. Convert PCM output to HDF5: The user begins with a GridView PCM run (stored as an
 .mdb case directory) and uses BPS-TUNE™ (gv_make_h5) to extract and standardize the
 results to a UniGrid HDF5 file (.h5) for downstream processing.
 3. PCM sampling and C-PAGE DC outputs: The user selects representative hours from
 the PCM run and, using BPS-TUNE™/C-PAGE (cpageautomation), builds DC
 PowerWorld snapshots (.pwb) that are consistent with PCM dispatch and flows in the
 selected power-flow topology.8
 4. DC benchmarking: PowerWorld vs PCM: The user validates DC fidelity by comparing
 the DC PowerWorld cases from Step 3 against the PCM hour targets in the .h5 file,
 using dataset comparison utilities available in BPS-TUNE™. The comparison is performed
 on flows, injections, and bus angles, with thresholds controlled via a TOML (Tom's
 Obvious, Minimal Language) file configuration.
 5. Create EGRET inputs from DC cases: The user converts each DC PowerWorld case to an
 EGRET-compatible DC JSON input using EGRET’s PowerWorld parser
 (make_acopf_from_dcpf.py), capturing both the DC operating point and the associated AC
 network description for the subsequent ACOPF.
 6. Run EGRET ACOPF (loss adjustment and reactive support): EGRET’s pcm_acopf
 extension is used to solve an AC optimal PF for each DC snapshot, adjusting reactive
 power and, where configured, loss allocations and small active power/load corrections to
 obtain an AC-feasible operating point.
 7. Convert EGRET AC results to AC PowerWorld cases: C-PAGE maps the EGRET AC
 solution back into converged AC PowerWorld cases (.pwb) using cpageautomation,
 including treatment of HVDC, switched shunts, and discretization of reactive devices
 where required.
 8. AC benchmarking: PowerWorld vs EGRET: The user compares the AC PowerWorld
 cases from Step 7 against the EGRET AC solutions from Step 6 using the same dataset
 comparison framework, focusing on voltage magnitudes, angles, active/reactive flows,
 slack accounting, and HVDC transfers, with configurable AC-specific thresholds.
 9. Reactive power harmonization across hours (advanced): Across multiple hours, C-PAGE
 is used to build an “Added Equipment Store,” rank candidate reactive devices by selection
 frequency and Q–V margin contribution, and re-optimize to minimize the number of
 devices while meeting voltage and reserve criteria. This step is still under development for
 future release versions.
 10. Fine-tuning with Q–V analysis (advanced): Q–V analysis is applied to quantify reactive
 reserves, identify weak locations, and apply targeted local corrections. Automated
 base-case selection is used where large operating changes would hinder convergence,
 and the analysis can be extended across seasons and consolidated. This step is covered
 in Reference no. 1.
 11. Visualization and analytics: Final AC cases and comparison results are used to create
 maps, time-series plots, and HTML reports via BPS-TUNE™ analytics and QGIS
 integration. Outputs can be written through UniGrid for use in other tools and downstream
 workflows.

 3.0 Step 3 – Build DC Power-Flow Snapshots From PCM
 3.1 Purpose
 Build a DC power-flow snapshots from PCM outputs to have a representative PF model of a
 particular state of the system from PCM. This ensures that components dispatch set points
 and PFs match the PCM solution before any AC physics are introduced. This is the “DC
 snapshot” in the robust-convergence workflow (see Section 4.1 and Figure 4.1). The output is a
 PF case that 1) solves DC and 2) reproduces the PCM hour’s dispatch and interface/branch
 flows within configured tolerances. This validated DC seed is the hand-off to ACOPF in the
 next stage. It is worth noting that several reconciliation tasks take place as follows:
 • Loads (regional → bus level): PCM often reports load at region/area level and distributes to
 buses with factors; the PF model holds explicit bus loads. Step 3 applies the distribution so
 total P and Q at buses sum to the PCM hour and appear at the correct buses used by the
 PF case.
 • Generators (aggregated → unit level): PCM may represent a plant or combined-cycle block
 as one injection, whereas the PF model has individual representation of each unit at specific
 buses. Step 3 disaggregates the PCM injection into unit setpoints using plant-specific ratios
 (or a mapping file) so each PF unit receives its share.
 • High-Voltage DC lines (bidirectional → unidirectional): PCM treats HVDC as directed flows
 on a single branch. On the other hand, the PF model contains explicit DC elements (or will
 later use ACOPF proxies) or equivalent representation for DC. In Step 3, the DC snapshot
 sets HVDC transfers so that terminal injections/withdrawals match the PCM flow direction
 and magnitude at the connected buses. (Figure 3.1 shows the ACOPF proxy model used
 later; Step 3 simply honors the PCM transfer at the PF terminals.)
 • Component relocation: PCM sometimes reduces the connectivity of generators by omitting
 collector systems, step-up transformers, or other fine-grain elements, that exist in PF,
 yielding an aggregated or simplified representation of some generators. Step 3 imprints the
 PCM operating point onto the PF topology that actually exists (bus numbers, kV levels,
 branch IDs), so the DC solution replicates PCM flows in that network.
 • Solution settings statuses and controls for a DC solve: Upon updating setpoints in the PF
 model, a DC-solution is required. Specific solver settings are enforced to ensure a DC
 power-flow solve in the PF tool, without engaging AC voltage-control behavior yet. This
 includes transformers tap controls, shunts controls, or DC converters controls.

 The CPAGEAutomation class is built to automate the process of using CPAGE tool. CPAGE
 module workflow is illustrated using the simplified diagram in Figure 3.2.

 It provides:
 • Automated creation of C-PAGE data and chronological PF models
 • Flexible configuration through a TOML file
 • Generates detailed logs and reports for analysis
 Uses command-line arguments for ease of execution.

 6.0 Step 6 – Run EGRET ACOPF to produce AC-feasible
 cases
 6.1 Step 6 – Purpose
 Step 6 takes the DC power-flow snapshots (JSON files) produced in Step 5 and uses EGRET’s
 pcm_acopf extension to compute an AC-feasible operating point for each case.

 At a high level, this step:
 • Builds an AC network model for each timestamp, using:
 – The network topology and equipment data from the PowerWorld / reference model.
 – The real-power dispatch and flows from the DC JSON (Step 5 output).
 • Solves an ACOPF using Pyomo + IPOPT, where the decision variables include:
 – Bus voltage magnitudes and angles.
 – Generator reactive power injections (and, within configured limits, small adjustments to
 real power if allowed).
 – Switched shunt and other reactive controls, where enabled in the configuration.
 – Load adjustments to account for losses or enforce feasibility, when permitted by the
 configuration.
 • Enforces AC constraints:
 – Power-balance at each bus (P and Q).
 – Voltage magnitude limits.
 – Generator and shunt reactive power limits.
 – Thermal limits and, where modeled, HVDC constraints.
 • Produces a converged AC solution written as a JSON results file, structurally similar to the
 DC JSON but enriched with AC quantities (voltages, reactive power, loss-consistent flows,
 etc.).

 In other words, Step 6 optimizes reactive power and, where configured, small active power/load
 adjustments so that each DC snapshot becomes a physically consistent AC case that can later
 be mapped back into a PowerWorld .pwb in Step 7.

 7.0 Step 7 – Build AC Power Flow Cases from EGRET
 Output
 7.1 Step 7 – Purpose
 Build an AC power-flow snapshots from EGRET ACOPF solution ensuring that components
 dispatch set points, PFs, and voltage profile match the EGRET solution (see Section 4.1 and
 Figure 4.1). In this step, cpage module will use the EGRETData parser to prepare data received
 from EGRET (.json) file properly. The process involves updating bus; voltages and angles,
 generator; P,Q, and Vreg, load; P,Q, phase-shifter angles, HVDC; real power setpoint and
 converter reactive power compensation, and shunt reactive setpoints onto a reference PF
 model of the same topology. The cpagemapping will not be needed because there is no special
 component mapping from EGRET to PowerWorld. The output is a solved AC .pwb case for
 each requested hour. (Report Sec. 4.2.6, pp. 29–30.). It is worth noting that several
 reconciliation tasks take place as follows:
 • High-Voltage DC lines (proxy generator → unidirectional branch): EGRET treats HVDC as
 two independent generators at the AC-bus terminals. On the other hand, the PF model
 contains explicit DC converters and branches. It is essential to map each two equivalent
 generator back to their corresponding DC branch flow. no special mapping files are needed
 since all information reside the egret (.json) file.
 • High-Voltage DC converter losses (proxy generator → switched shunt): EGRET assumes
 that each DC converter can supply reactive power up to 0.9 power factor of their real power
 capacity. This reactive power has to be converted into new shunt components in the PF
 model with the proper setpoints.
 • Switched shunts (continuous → discrete): EGRET assumes all reactive shunts have
 continuous nature to reduce the complexity of the ACOPF problem into linear formulation,
 and hence proper discretization is applied to revert the shunt setpoints to actual steps.

 Appendix B – Create Mapping Files
 This appendix provides guidance for creating mapping files that define the special relationships
 needed to translate power system components from a production cost model representation
 into a power flow (PF) model representation. The purpose of this guidance is to help users
 understand how to build or update the required mapping files when working with new power
 system models. In particular, it focuses on how to represent component correspondences,
 naming differences, and any model-specific exceptions so that the automated mapping process
 can be applied correctly and consistently.

 The mapping process is organized into the following categories:
 1. Gen: Handles mapping operations for generation tables, including both PCM and PF
 mappings.
 2. HVDCGen: Handles mapping operations to convert HVDC lines into equivalent generators
 at AC terminals.
 3. HVDCDir: Handles mapping operations to convert bi-directional HVDC lines into uni-
 directional HVDC lines.
 4. HVDCVSC: Handles mapping operations to convert HVDC lines into voltage source
 controlled (VSC) HVDC lines.
 5. MTDC: Handles mapping operations to convert HVDC lines into multi-terminal DC (MTDC)
 lines.

 Detailed explanations of the needed files and context of each file for proper mapping are
 provided here:
 1. Hydro: The Hydro category is used to map a hydro plant in the production cost model
 (PCM) to the corresponding individual hydro generating units in the PF model. This mapping
 is needed because hydro resources are often represented differently in the two models. In
 the PCM, a hydro plant may be modeled as a single aggregated resource at the plant level,
 while in the PF model the same plant may be represented by many separate generating
 units connected at one or more buses. Also, in the PF model, hydro generators are
 dispatched based on a pre-defined order list based on their ratings and availability. The
 hydro mapping file defines how the aggregated plant should be associated with its detailed
 PF generator records.

 • plant_id: A unique identifier for the hydro plant.
 • plant_name: The name of the hydro plant.
 • bus: The bus number of the hydro generator in the PF model.
 • name: The generator name in the PF model.
 • genid: The generator ID in the PF model.
 • cap: The generating capacity of the individual hydro unit.
 • res_abs: The absolute reserve value assigned to the hydro unit.
 • res_per: The reserve percentage assigned to the hydro unit.
 • load_order: The loading priority or dispatch order for the hydro unit within the plant.

                 1          Plant1      4        C4     1      200       50          0           2

 2. Generation
 The Gen category is used to map generator representations between the PCM and the
 PF model. This category is needed to address two main issues:
 1. Generators that exist at different bus locations between the PCM and the PF
 model
 2. Generators that are aggregated or disaggregated at different levels in each
 model
 In both cases, the same physical plant may not appear identically in the two models. The
 Gen mapping files provide a consistent way to link the PCM generator records to the
 corresponding PF generator records.
 This category requires two files:
 • gen_pcm_map.csv
 • gen_pf_map.csv
 The generators are matched using the first three columns in each file:
 • poi
 • shape
 • type
 These three columns together represent the identification of the power plant and are
 used as the common key between the PCM and PF mapping files.
 The first file “gen_pcm_map.csv” defines how the generator or plant appears in the
 production cost model. The columns are:
 • poi: The point-of-interconnection or plant location identifier.
 • shape: A plant grouping or shape identifier used to distinguish units or configurations
 within the same plant.
 • type: The generator technology or plant type.
 • gbus: The generator bus number in the PCM model.
 • id: The generator identifier in the PCM model.
 • pmax: The maximum active power capacity of the generator in the PCM model.

 3. HVDC to Generators
 The HVDCGen category is used to map an HVDC line in the PCM to equivalent
 generators at the AC terminals in the PF model. This type of mapping is needed when the
 PF representation does not model the HVDC link directly as an HVDC element but instead
 represents its behavior using generator records at the connected AC buses. To ensure the
 mapping is recognized by the code, the file must be named “hvdc_gen_map.csv”.

 • from_bus: The sending-end bus number of the HVDC line in the PCM model.
 • to_bus: The receiving-end bus number of the HVDC line in the PCM model.
 • ID: The identifier of the HVDC line in the PCM model.
 These first three columns uniquely identify the HVDC line in the production cost model.
 • from_gbus: The generator bus number in the PF model that represents the from-side
 AC terminal of the HVDC line.
 • from_id: The generator identifier in the PF model for the from-side equivalent generator.
 • to_gbus: The generator bus number in the PF model that represents the to-side AC
 terminal of the HVDC line.
 • to_id: The generator identifier in the PF model for the to-side equivalent generator.
 • pmax: The maximum transfer capability or maximum active power associated with the
 HVDC link, typically used as the capacity of the equivalent representation.

 4. HVDC to bi-directional HVDC
 The HVDCDir category is used to map a bi-directional HVDC line in the PCM to its
 corresponding unidirectional HVDC representations in the PF model. In some cases,
 a single HVDC connection in the PCM is modeled as one logical line that can transfer
 power in either direction, while in the PF model the same connection is represented
 using two separate directional records—one for the forward direction and one for the
 reverse direction. The file name must be “hvdc_direction_map.csv”.

 • from_bus: The sending-end bus number of the HVDC line in the PCM model.
 • to_bus: The receiving-end bus number of the HVDC line in the PCM model.
 • ID: The circuit identifier of the HVDC line in the PCM model.
 These first three columns uniquely identify the HVDC line in the PCM.
 • from_bus_pf: The sending-end bus number of the corresponding HVDC line in the PF
 model for the forward direction.
 • to_bus_pf: The receiving-end bus number of the corresponding HVDC line in the PF
 model for the forward direction.
 • ID_pf: The circuit identifier of the corresponding HVDC line in the PF model for the
 forward direction.
 These three columns identify the HVDC record in the PF model that represents flow in the
 same direction as the PCM line definition.
 • from_bus_pf_reverse: The sending-end bus number of the corresponding HVDC line in
 the PF model for the reverse direction.
 • to_bus_pf_reverse: The receiving-end bus number of the corresponding HVDC line in
 the PF model for the reverse direction.
 • ID_pf_reverse: The circuit identifier of the corresponding HVDC line in the PF model for
 the reverse direction.
 These final three columns identify the HVDC record in the PF model that represents flow in
 the opposite direction.
