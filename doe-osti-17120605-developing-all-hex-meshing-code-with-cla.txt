 i

 Summary
With the rapid development of large language models (LLMs), it has become significantly easier to
obtain working code quickly. This report is an outcome of the Claude Code Hackathon at Argonne
National Laboratory (ANL), which provided an opportunity to test how well Claude Code, and
LLMs more generally, can accelerate the development of meshing code. We used Claude Code to
implement a published meshing strategy for bifurcating geometries as MATLAB/Octave scripts,
starting from the reference paper and no existing code. Claude was given access to write and run
code, read its output, and inspect the plots it generated, which allowed it to test, debug, and visually
verify its own work with minimal user intervention. Within six hours of prompting, and without
writing or reading any code, we went from an STL surface to a hexahedral mesh that ran in Nek5000.
The exercise also showed where the user’s expertise remains essential: Claude struggled with vague
or complex instructions but completed smaller, specific steps reliably, and domain knowledge was
needed to decompose the task and specify the correct mesh topology. The resulting code is not yet
production-ready, but the results demonstrate the potential of this workflow for developing meshing
tools.

 ii

1 Introduction
With the rapid development of large language models (LLMs), it has become significantly easier to
obtain working code quickly. The Claude Code Hackathon hosted at Argonne National Laboratory
(ANL) on July 13–14, 2026 by Sven Leyffer and Rebecca Durst provided an opportunity to test how
well Claude Code, and LLMs more generally, can accelerate the development of meshing code.
 We emphasize that Claude was not used to generate meshes directly. Instead, it was used
to write MATLAB/Octave scripts that compute the mesh. This approach is much closer to how
Claude is designed and trained to be used, and it extends naturally to other meshing frameworks
such as Gmsh [1].
 The LLM was also not used to devise the meshing strategy itself; rather, it assisted with
implementing an existing strategy for bifurcating geometries [2]. Nevertheless, as the transcript
shows, it proposed many variants of the strategy, and it could not only implement these variants
but also test and compare them automatically.

 Figure 1: Plot of the bifurcation geometry STL provided as input for Claude.

 Claude Code was installed locally on a laptop and given permission to read and write files, run

 1

code, and read the output. These capabilities are essential for it to test and debug its own work.
For meshing, it is equally important that the LLM can generate and view images, so that it can
inspect the mesh visually, either through MATLAB plotting functions that save figures to files or
through screenshot tools. As the transcript illustrates, these capabilities allow the LLM to debug
and iterate with minimal intervention from the user.
 Throughout the process, we did not need to write any code, read the MATLAB code, or copy
anything into files. The entire workflow was carried out through the Claude Code chat interface:
describing the task, running the main driver script, and visually inspecting the resulting plots.
 A similar workflow would be much less effective in a chat interface that cannot access the user’s
local environment. There, the LLM cannot run the meshing code or inspect its output directly, so
the user must repeatedly copy the generated code to their machine, run it, and paste the results
back into the conversation.

 Figure 2: Topology of the bifurcation in the reference paper [2].

2 Background
The meshing strategy used in this exercise is the same as [2]. Claude is used to implement the
meshing strategy. The goal is for Claude to implement a meshing code, that when given an STL of

 2

a bifurcating geometry, it can output an all-hex mesh that is ready to be used in CFD simulations.
 As a start, we provide an STL surface of a vascular bifurcation geometry found in [2]. The plot
of the STL surface geometry is shown in Figure 1. The STL is open at the each of the endpoint, so
the edge boundary can be easily detected by counting the number of elements sharing the edge. We
will refer to the lower opening as the trunk, and the two top opening as top branches.
 The model is not given anything else to start with, and is tasked sequentially by the user to
follow the steps layout in the reference paper. The strategy will results in the topology shown in
Figure 2, which will results in well-shaped elements and smoothly transition between the three
branches. The strategy from the paper is layout here

  1. Mesh the volume with a tet mesh
  2. Solve a conduction problem for each pair of endpoints.
  3. Obtain three principal isosurfaces from the three fields from the conduction problem
  4. Map O-grid quad mesh to the half-chips form by the principal isosurfaces
  5. Mesh the rest of each branch by mapping O-grid quad mesh to isosurfaces
  6. Orient each slice so they can transit smoothly

Figure 3: Conduction field solved on the vessel mesh, with the bottom held at 0, one top branch at
1, and homogeneous Neumann conditions elsewhere.

 3

 The approach in this report is slightly different, which avoid meshing the full volumetric tet
and experiment working with only the surface. Claude is also prompted to implement the full
volumetric and run comparisions later.

3 Process
Here is the summary of the script of the major important prompts only. Some of the more minor
prompts, like asking Claude clarification, code clean up or refactors are omitted. The full transcript
can be found in claude-archive folder.
 Almost every plot in this transcript is produced automatically by Claude. It writes the plotting
code, runs it locally, renders the figure, and then looks at the result to decide the next step. The
tight loop of write → run → plot → inspect → iterate is what let Claude debug a the problem
largely on its own.

3.1 Conduction Problem

We started with a simple prompt asking for a basic script to solve the steady-state conduction
(Laplace) equation. The input geometry is an STL file in the local directory. We also plotted the
STL geometry and included the image in the prompt, so that Claude could see the topology it had
to work with.
 Prompt

 [Image] here is how the mesh look. solve the laplace equation setting the bottom to 0, one
 branch on the top to 1, and everything else be homogeneous neumann

 Claude began by checking the local Octave version, then wrote a short script, solve laplace.m,
and tested it immediately. After confirming that the script ran correctly, it plotted the resulting
field, shown in Figure 3. Notably, Claude did not stop there: it also examined the plot. Judging the
field to look suspicious, it sampled the solution along a profile to check it, and concluded that the
solution was in fact correct and had only appeared wrong because of an unusual viewing angle.
 We acknowledge that the solution in Figure 3 does not look correct, but we deliberately pressed
on to see whether Claude could find the problem on its own. The viewing angle of these plots is
also poor: it confused not only Claude but also, likely, the reader. In later steps, Claude began to
orient its plots at better angles.
 We next asked Claude to slice the field along isocontours and mesh each slice.
 Prompt
 after solving for the field, take 50 isocontour slices of the field, and for each slice, mesh it as an
 o-grid quad mesh, then plot all the slices on a 3d plot

 Claude implemented a script, ran it, and plotted the result, again inspecting the rendered
image before moving on. The result is shown in Figure 4.
 Setting aside the poor attempt on the second branch and the viewing angle, Figure 4 shows

 4

that Claude mapped the O-grid mesh onto the STL surface correctly. The conduction field also
looks more plausible than in Figure 3, because in the meantime Claude had identified the bug in
the solver and corrected it.
  Prompt
  are each slice oriented continuously so one can connect to the next seemlessly?

 Instead of simply answering yes or no, Claude wrote code to measure the phase jump between
neighboring slices, that is, the angular offset between the starting points of their O-grids, and
confirmed that the slices were not consistently oriented. It plotted the slice orientations, shown in
Figure 5. Claude then implemented a consistent orientation, resolved a few problems along the way,
and after running the new version, reported that the maximum phase jump between neighbors had
dropped from 168◦ to 8.24◦ .

 Figure 4: Fifty isocontour slices of the conduction field, each meshed as an O-grid quad mesh.

 At this point, the mesh topology is not yet bifurcating: the slices follow the isosurfaces from
the trunk into one of the top branches, so most of the other branch is missed. Nevertheless, Claude
had completed every step successfully so far, and each step was checked against a plot that Claude
generated and inspected itself. The next step was to help Claude mesh the bifurcation.

3.3 Principal Isosurface Cut: Second Attempt

We started a new Claude session and again began by finding the principal isosurface, this time
giving more detailed, step-by-step instructions. We first gave Claude a simple task of the kind it
had already completed successfully: the conduction problem for the three cases shown in Figure 7.
  Prompt

  [Image] refactor the code and plot 3 different bifurcation flow case

 7

 Figure 7: The three bifurcating flow cases used to find the principal cut, taken from [2].

 Figure 8: Conduction solutions for the three flow cases A, B, and C.

 Since this was a fresh session, Claude spent some time exploring the existing code. The prompt
was also quite vague, as we had not defined Γ or the parameters α, β, and γ that appear in the
image. Nevertheless, presumably by inspecting the existing code, Claude worked out what the three
cases meant, wrote code to solve them, and plotted the results, shown in Figure 8.
 We then followed the procedure of the reference paper, in which the zero isocontours of the
three solutions together mark the principal cut. This required two further prompts:
  Prompt
  subtract out the mean u of the neumann loop

  Prompt
  plot the mesh with the isocontour 0 of the 3 cases on the same plot

 Figure 9 shows that the isocontours were computed and plotted correctly. In the reference
paper, additional steps are taken to ensure that the three isocontours coincide. When we asked
Claude to ensure this, it produced a plot showing the isocontours coinciding, along with a test
confirming that they agree to within a tolerance of approximately 10−7 .

 All the prompts after this point are only for improving the quality of the mesh, by smoothing

3.5 Mesh smoothing and volumetric meshing

A later session focused on mesh quality. Again, every decision was driven by a quantitative test that
Claude wrote or a plot that it generated itself. Claude chose the scaled Jacobian as the mesh-quality
metric and carried out a series of comparisons to identify better methods.
  Prompt
  run mesh smoothing on the hex mesh, make sure the surface points are projected to the original
  stl properly

 Claude implemented Laplacian smoothing, projecting the surface points back onto the original
STL surface after each iteration. It reported that the minimum scaled Jacobian increased from
0.1119 to 0.2260.

 15

 We then asked Claude to try several methods for filling in the slices in the interior of the
volume, since the isocontours had originally been computed only on the surface. Claude proposed
several approaches: bilinear blending, solving a harmonic (Laplace) problem on each slice, Winslow
elliptic smoothing [3], and solving the conduction problem on the full volume using a tetrahedral
mesh. Claude then automatically implemented all the method, debug any issue, and compare the
resulting mesh quality, as summarized in Table 1.

Table 1: Scaled Jacobian of the hex mesh for each interior-fill method compared by Claude (higher
is better).

 Interior method min scaled Jac. mean scaled Jac.
                      bilinear               0.070             0.819
                      harmonic              0.333             0.877
                      winslow                0.132             0.864
                      volumetric             0.224             0.798

 The harmonic method gives the best quality in Table 1, and the resulting final mesh is shown
in Figure 19.

 Figure 19: Final hex mesh of the vessel bifurcation, consisting of 3840 hexahedral elements.

4 Conclusion
We used Claude Code to implement a meshing strategy for bifurcating geometries in MATLAB/Oc-
tave, starting from a reference paper and no existing code. Within six hours of prompting, we went
from an STL surface to a hexahedral mesh that ran in Nek5000. Throughout the process, we did not
write any code, read the generated MATLAB code, or copy anything into files; the work consisted
entirely of prompting Claude, running the main driver script, and inspecting the resulting plots.
The same approach should extend readily to other meshing frameworks, such as Gmsh.
 The key enabling factor was giving Claude the ability to write and run code, read its output,
and inspect plots. With these capabilities, Claude tested its own code, found and fixed bugs, and
detected visual anomalies in the mesh, iterating with minimal intervention from the user. In a chat
interface without access to the local environment, the user would instead have to run every version
of the code and relay the output back, which would make the process far slower.
 At the same time, the exercise showed clearly where the user’s expertise remains essential.
Claude struggled when instructions were vague or the task was complex, as in the first attempt at
the principal isosurface cut. When the task was broken into smaller, specific steps, it completed
them reliably. Coding experience was not needed, but meshing knowledge was: deciding how to
decompose the task, recognizing when an approach was unsuitable, such as slicing along a global
conduction solution, and specifying the correct mesh topology all came from the user.
 The resulting code is not yet ready for production use, as this was a short exercise to assess
Claude’s capabilities. It still needs to be reviewed for correctness and code quality, tested on more
general bifurcating geometries, and checked for workarounds that satisfy tests without solving the
underlying problem, such as the method used to make the three isocontours coincide. Nevertheless,
obtaining a working, simulation-ready mesh from a reference paper in a single short session
demonstrates the potential of this workflow for developing meshing tools.
