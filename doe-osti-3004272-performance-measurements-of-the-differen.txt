 ABSTRACT

 The performance characteristics of the different DAOS interfaces for POSIX containers are
evaluated and reported.

 1. INTRODUCTION

 In this report, we analyze the performance of the Distributed Asynchronous Object Storage (DAOS)
software via its DAOS POSIX Filesystem interface, DFS. DAOS is designed specifically to work with
NVMes and persistent memory technologies (like Intel Optane) as opposed to older disk-based parallel
filesystems. It provides a high-performance distributed, scalable, and declustered key-value-array store
that supports containers offering POSIX namespaces, HDF5 datasets, and python objects. Data is stored
within global namespace containers spread across distributed asynchronous storage node engines and is
versioned at the individual I/O level. There is no centralized metadata server like with Lustre. Storage is
organized and reserved into pools that can span multiple storage engines. A pool contains one or more
containers that function as datasets. Each dataset is a collection of data objects including files and
directories. A dataset can be a POSIX filesystem, a set of python objects, an S3 bucket, a HDF5 dataset,
graph data, or direct key-value store. DFS is the DAOS Filesystem that provides the aforementioned
POSIX filesystem abstraction through the libdfs library that runs on the client. Libdfs runs over top of the
libdaos library that provides the key-value store access to the DAOS engines. [1]

 ORNL has interest in deploying DAOS for its end-users as it offers several advantages. It provides
high performance utilization of NVMe drives, efficient non-POSIX access to containers, and POSIX
containers to the majority of users that require a POSIX-like API. It is crucial for us to understand its
performance characteristics for the users to utilize it successfully.

 DAOS currently offers four different methods for accessing a POSIX container: the DFS API,
DFuse, libioil, and pil4dfs. The DFS API provides POSIX-like programmatic access through libdfs that
can offer the similar semantics to POSIX. DFuse is a FUSE, filesystem in user space, implementation. It
is a mountable filesystem connected to a user process that backs it via hooks for handling the Linux VFS
callbacks. It sits over top of libdfs and and uses the methods provided in the library to provide a seamless
POSIX filesystem. Libioil is an intercept library that redirects basic read/write calls to the DFS API.
Normally, this is used along with DFuse to speed up read/write calls by bypassing DFuse while allowing
DFuse to continue to handle simple metadata calls. Pil4dfs is a newer and more robust intercept library
that handles more I/O and metadata calls than the libioil library. It works along similar lines as the prior
library. We’ll be testing both intercept libraries as pil4dfs is still in preview release form.

 Each of these methods offers advantages and disadvantages. The DFS API offers the greatest
performance but requires users to rewrite their applications replacing POSIX calls with DFS ones. DFuse
as a mounted filesystem requires no application changes for users but has significant latency overhead
that may impede performance. Finally, libioil and pil4dfs offer a compromise between the two previous
approaches. They can directly intercept read/write calls and translate them to DFS calls in userspace,
bypassing the FUSE layer, for greater performance. However, they require users to successfully use the
intercept library with their application through techniques like LD_PRELOAD which can be brittle.
Thus it is important for us to understand the performance characteristics of each method so that users can
evaluate the tradeoffs for each of their individual application use cases. The report analyzes read and
write bandwidth capabilities for each of these methods using simulated FIO workloads. In addition to the
bandwidth, it also examines the performance of metadata operations generated by MDtest.

 2. METHODOLOGY

 This section discusses the methodology we used to examine and analyze the bandwidth and metadata
operations for DFS, DFuse, libioil, and pil4dfs. To measure raw read/write performance, we used the FIO
benchmarking tool, and to measure metadata performance we used the traditional MDtest benchmark
[2],[3]. FIO has the advantage of simulating different I/O workloads and has an I/O engine that explicitly
uses the DFS library, as well as an I/O engine for traditional POSIX I/O calls. MDtest is similar in that it
can access DAOS through traditional POSIX calls or the DFS interface. This enables us to directly test
each of the 4 access methods, DFS library, DFuse, libioil, and pil4dfs, to draw the most accurate
comparisons.

 DAOS was run on 8 servers with version 2.6.3 of the software. Each server has 2 Intel Xeon Gold
6338 processors with 512 GB of RAM and ten Micron Technology 7450 PRO NVMe SSDs with 3.8 TB
of capacity. An NVMe supports up to 6800 MB/s and 5600 MB/s read and write, respectively. Each
server is connected to the Infiniband network via two NDR 200 Gbps cards. The client nodes from the
quokka cluster each contain dual 24-core Intel Xeon Silver 4516Y+ processors, 256 GB of RAM, and 400
Gbps Infiniband connections. To reduce the complexity of the testing, DFuse configuration parameters
on each node were set to the standard defaults which includes 16 worker threads.

 We used version 3.40 of FIO, the most recent version at the time of this report, on a single client node
with the DFS, Psync, and PosixAIO I/O engines. Psync offers the basic POSIX pread/pwrite calls. Also
we utilized the PosixAIO engine in addition to Psync to compare higher I/O depths since Psync only has
an I/O depth of 1. We chose two I/O depths for DFS and PosixAIO engines, 1 and 32. An I/O depth of 1
simulates traditional synchronous POSIX calls and is the only valid setting for the Psync I/O engine. An
I/O depth of 32 allows the DFS library to completely saturate our Infiniband NIC. This allows us to
compare the maximum DFS performance against the other access methods using the PosixAIO engine.
We used 32K and 1M block sizes, independently, to represent small and large I/O. Finally, we ran four
different I/O patterns: sequential read, sequential write, random read, and random write.

 MDtest used version 4.4.0, also the most recent version, on 10 client nodes using slurm and OpenMPI
for scheduling and communication. Settings similar to the IO 500 10-node test were employed: “mdtest -i
10 -n 1000 -L -F -w 3901 -e 3901 -D -N 1” [4]. This ran 10 iterations of each test with each mdtest
process creating 1000 directories and files at leaf nodes. Also 3901 bytes were written to and read from
each file. To avoid caching effects a stride of 1 neighbor was used.

 3. RESULTS

 In this section, we analyze bandwidth and metadata operation results for DFS, DFuse, libioil and
pil4dfs. For read and write bandwidth, we utilize four FIO I/O workloads simulating sequential and
random read and write patterns. We also employ three different I/O engines: DFS, PosixAIO, and Psync.
The DFS I/O engine will enable us to directly access DAOS natively and to use various I/O depths to
emulate different use cases. The PosixAIO I/O engine also allows us to use various I/O depths and to
emulate multithreaded I/O patterns. Finally, the Psync I/O engine provides synchronous pread and pwrite
calls for I/O tests similar to what most users employ. This I/O engine is also important because it allows
for interception by the libioil library while PosixAIO does not. For the I/O depths we chose two values: 1
(for standard synchronous behavior) and 32 (to saturate the network interface for maximum performance).

 2

 For metadata performance and comparision, we employed MDtest which enabled us to get results for
directory creation, directory stat, directory rename, directory removal, file creation, file stat, file read, file
removal, tree creation and tree removal. Unlike FIO, which were single node tests, we used 10 client
nodes with OpenMPI running MDtest to perform as many metadata operations as possible.

3.1 FIO

 Figure 1: Bandwidth results of DFS and DFuse using an I/O depth of 32 for the different I/O patterns with block sizes of 1MB
 and 32KB.

 From Figure 1, we can see that utilizing the DFS API for 1 MB I/O and an I/O depth of 32 allows
a node to obtain well over 40 GiB/s essentially saturating the Infiniband NIC. All I/O access patterns,
sequential read/write and random read/write, obtained nearly the same result ranging from 44 GiB/s to
almost 47 GiB/s. In contrast, moving to DFuse with PosixAIO and the same I/O depth of 32 incurred a
significant performance penalty with none of the I/O patterns doing much better than 8.4 GiB/s. This
means that DFuse can only obtain about a fifth of the performance of DFS in this scenario. Moving on to
the 32 KB block size use case, we can see the difference between DFS and DFuse improves, largely due
to the diminished performance of DFS. With a smaller block size, the performance of DFS drops to
between 8.3 and 11 GiB/s depending on the I/O access pattern. While DFuse also drops to between 2.5
and 4 GiB/s, the ratio of the performance penalty is much less (roughly a quarter for read access and half
for write access). Unfortunately, we were not able to test if the libioil and pil4dfs intercept libraries could
improve DFuse performance as those libraries does not support the PosixAIO calls used by FIO for this
workload.

 3

 Figure 2: Bandwidth results of DFS, DFuse, libioil, and pil4dfs using an I/O depth of 1 for the different I/O patterns with
 block sizes of 1MB

 Figure 2 shows the 1 MB block size results when dropping the I/O depth for FIO to 1 and
switching to the synchronous psync I/O engine for DFuse, libioil, and pil4dfs. Not surprisingly, there is a
significant drop in performance for DFS and DFuse because a low I/O depth is not able to mask the
latency of each I/O request. DFS is able to obtain 7.5 to 7.7 GB/s. DFuse suffers even more with a
drastic decrease in performance for each I/O workload especially read operations. DFuse is only able to
obtain 4.1 and 4.7 GB/s for the respective sequential and random write workloads. Worse still is the read
performance that DFuse achieves at 1.6 and 1 GB/s without any cache assistance.

 The intercept libraries drastically improve upon DFuse. When paired with DFuse, we are able to
obtain read/write workload results on par with the direct use of DFS, and in some instances, even slightly
exceed them although this is likely just due to normal test fluctuations. The 1 MB block size workloads
ranged between 7.7 to 8.5 GB/s for both these intercept libraries.

 4

 Figure 3: Bandwidth results of DFS, DFuse, Libioil, and pil4dfs using an I/O depth of 1 for the different I/O patterns with
 block sizes of 32 KB.

 Moving on to the FIO 32 KB block size workloads, Figure 3 provides the performance numbers
for each of the DAOS access techniques. As before we are using the Psync I/O engine with an I/O depth
of 1. DFS was able to get 2.66 GiB/s to 4.58 GiB/s for the various I/O workload patterns. The write
workloads perform far better than the read workloads probably due to some caching occurring and latency
on retrieving reads.

 The performance of DFuse, in comparison to the 1 MB block size, is even worse. There was a
single read workload that broke 1 GiB/s at 1.36 GiB/s. The rest were all far below 1 GiB/s ranging from
0.48 GiB/s to 0.65 GiB/s. At best DFuse was able to achieve 50% of the bandwidth of the corresponding
read workload and at worse only 13% for the sequential write workload. The random read and write were
only 15% and 17% of their respective workloads as well.

 As before, the libioil and pil4dfs intercept libraries were able to achieve significantly better
bandwidth performance than DFuse, although this time not quite as well as DFS. The sequential and
random write workloads took the largest hit, comparatively speaking, at 3.69 and 3.03 GiB/s. This means
libioil was able to deliver 78% and 71% of the write performance for small I/O. The case for sequential
and random reads was even better with results of 2.63 and 2.32 GiB/s, meaning that libioil was able to
obtain 97% and 87% of DFS. Pil4dfs was able to do even better with write I/O from 4.25 to 4.34 GiB/s
and read I/O of 2.77 to 2.71 GiB/s for the sequential and random workloads, respectively. The pil4dfs
library achieved slightly better than 100% of the performance of DFS for all workloads except sequential
write which was 93% of DFS performance.

3.2 MDTEST

 Figure 4: Operations per second results for the various MDtest operations when using DFS, DFuse, libioil, and pil4dfs.

 The MDtest results of DFS, DFuse, libioil, and pil4dfs are shown in Figure 4. We can see, in
general, native DFS outperforms DFuse and libioil, while DFuse and libioil perform at nearly the same
level. This is not surprising as libioil is not intercepting metadata calls, and they are being passed along
to DFuse to execute. Pil4dfs, which intercepts metadata calls, does much better and almost always
matches the performance of DFS.

 For directory operations, DFS performance exceeds DFuse and libioil except for stat operations
where they are equal. Directory stat had the highest performance of all with 91,504.85 operations per
second. Directory creation, rename, and removal for DFS were 36,664.47, 13,044.56, and 31,312.46 op/s.
DFuse was able to achieve 75%, 87%, and 61% of DFS for the respective operations. Pil4dfs, however,
obtains 102%, 100%, 100%, and 97% of DFS performance rates.

 For file creation, stat and removal operations, DFS obtained 25,214.98, 37890.53, and 11,604.09
op/s exceeding DFuse performance. DFuse only obtained 61%, 58%, 65% of the DFS results for file
operations. Except for file removal with only 81%, pil4dfs was able to return much of the same
performance with 102% and 95% for creation and stat operations.

 DFuse also underperformed for tree creation at 66% and tree removal at a mere 18% of what DFS
achieved. DFS created 3,399.74 trees per second and removed 244.03 of them per second. As before,
pil4dfs matched the performance of DFS with 105% and 100% for these operations.

 Finally, MDtest also performed a small read test of 3901 bytes to a file. As with FIO, DFS
achieved far better results with 62,797.77 reads per second compared to DFuse with only 11,981.92 and
libioil with 13918.51 reads per second. In this case, libioil, by intercepting the calls, does better than
DFuse but not nearly as well as DFS. Pil4dfs does nearly as well as DFS with 99% of the read bandwidth
returned.

 4. CONCLUSION

 In this report, we have analyzed the bandwidth and metadata operations for various workloads
using FIO and MDtest against four different DAOS access interfaces. The four different interfaces
included: native access using the DFS API; DFuse, a FUSE implementation; libioil, an intercept library
that directly handles read and write calls bypassing DFuse; and pil4dfs, a newer intercept library that
handles more POSIX calls.

 FIO tests were carried out using several different workloads and I/O engines. FIO was run with 1
MB and 32 KB block sizes doing sequential and random read and write I/O on a single quokka cluster
node. Each of these configurations was executed using the DFS, PosixAIO, and Psync I/O engines to
replicate the ways that the DAOS container could be accessed by the users. The DFS and PosixAIO
engines let us also test multithreaded, simultaneous I/O accesses with I/O depths of 32, while the Psync
engine tested more traditional synchronous pread and pwrite calls.

 MDtest was run using a configuration similar to the 10-node I/O 500 test. It was executed across
10 nodes on the quokka cluster using OpenMPI. MDtest used the DFS module to directly access the
DAOS container and the more traditional POSIX module for DFuse and the intercept libraries. It
provided timing rate results for various metadata operations including directory creation, directory stat,
directory rename, directory removal, file creation, file stat, small file read, file removal, tree creation and
tree removal.

 From all of these tests, we have witnessed that to achieve maximum performance one must use
either the DFS native API or pil4dfs. DFuse performs poorly in comparison in every I/O bandwidth test
regardless of configuration. DFuse should only be seen as a convenience tool for small accesses by users.
The I/O bypasses provided by libioil can assist greatly. For synchronous accesses of traditional I/O calls,
it can provide nearly the same performance as simple DFS calls. However, with its inability to handle
newer I/O calls like those provided by AIO, it cannot compete with the DFS API when issuing multiple
read and write I/O operations simultaneously. The preview release of pil4dfs does even better. It is
almost always able to match the read and write performance of the native DFS API. However, it is still a
work in progress and does not yet intercept all I/O library calls.

 For metadata operations, DFuse performed better and was even able to obtain 87% of the DFS
directory rename operation rate. For file and directory operations, it was able to execute between 87% to
58% of the performance of the DFS API. Only when performing tree removal operations was DFuse
really slow at 18%. Libioil, which is not engineered to intercept metadata calls, obtained essentially the
same results as DFuse. Pil4dfs, which does intercept metadata calls, roughly matched the performance of
the DFS API except for file removal which was 81% of the DFS rate.
