ABSTRACT
This document provides a step-by-step tutorial on how to set up OpenCSP for both users and
developers. It is meant to support novice users and does not require software engineering
experience. It is a detailed extension of the OpenCSP getting started on-line documentation,
found here:
 https://opencsp.readthedocs.io/en/main/contributing.html#getting-started
For an overview of OpenCSP overall, see the OpenCSP website: https://opencsp.sandia.gov.
For details on OpenCSP components and algorithms, see the references.

1. INTRODUCTION
This document is intended to provide a step-by-step tutorial on how to set up OpenCSP for
development purposes. If you are a user who only intends to use OpenCSP without ever editing
code, then you can skip some of these steps. However, since over time you might encounter a
desire to adjust or extend the code, we suggest you consider setting up all of the components.
We suggest you become familiar with the OpenCSP website (https://opencsp.sandia.gov) to gain an
overall understanding of OpenCSP content.
This document is a more detailed version of OpenCSP getting started on-line documentation,
found here:
 https://opencsp.readthedocs.io/en/main/contributing.html#getting-started
The above is a good source of a more terse setup overview.
This document employs a few formatting conventions:
 • User name. The string <user_id> is used to denote an individual’s username. Substitute your

 • Machine name. In some situations, the console output includes the machine name. We will
 denote this <user_id>@<machine_id>. Since this is output by the computer, you don’t
 need to do anything.
 • Web site navigation. Navigating from page to page is indicated by “” arrows.
 Example:

1.1. Code Practices
OpenCSP welcomes developers with varying levels of experience to contribute. Some basic
guidelines:
 • The opencsp/ directory structure is intended to contain more mature code, such as the
 SOFAST 2.0 program (opencsp/app/sofast), and mature foundation classes (such as
 opencsp/common/lib/csp/Facet.py). Meanwhile, the contrib/ directory structure is meant
 to contain less mature code under development. If you would like to contribute code,
 placing it in contrib/ is a good start.
 • We use branches to differentiate code maturity. The “main” branch is reserved for the most
 mature code; most code resides in the “develop” branch.
 • When you develop new code or improvements to existing code, we request that you work
 with a fork of the repository and create a new branch. Once the functionality is ready,
 submit a pull request to have it merged into develop branch the central repository. This
 reduces clutter on the main repository’s branch history. Section 2.10 explains how to set this
 up, and Sections 4.3-4.4 explain the steps required to merge changes back to the main
 repository.
 • We encourage revisions executed in small steps where practical, because this makes pull
 request reviews more manageable. Section 4 below further explains recommended
 development practice, and the steps required to merge code changes into the central
 OpenCSP repository.
 • See OpenCSP web site for additional guidance:
 https://opencsp.readthedocs.io/en/main/contributing.html#coding-standards

2.4. Setup HDF View
OpenCSP programs such as SOFAST 2.0 store complex data structures to disk in HDF5 format.
The resulting .h5 files cannot be read in a text editor, producing gibberish if you try. To inspect
an .h5 HDF file, various viewing programs are available. The OpenCSP team uses HDF View,
available here:
 https://www.hdfgroup.org/download-hdfview/
The OpenCSP Team is using HDFView version 3.3.2, but this is not critical. To install, download
HDFView-3.3.2-win64.zip, extract, then copy HDFView-3.3.2.exe to a directory on your local
machine, and run HDFView-3.3.2.exe. The result will appear in:
 C:\Users\<user_id>\AppData\Local\HDFView
You can then double-click on “HDFView.exe” to run HDF View; we suggest pinning this to your
task bar for convenience.

2.6. Setup SolidWorks (optional)
The SOFAST CAD Layout Tool is implemented SolidWorks, which is very helpful when designing
new SOFAST installations. In addition, OpenCSP has released many SolidWorks CAD files to
assist in the design of various CSP metrology systems. If you are interested in these activities,
installing SolidWorks is recommended.
Note that SolidWorks is not required for running OpenCSP Code, nor is it required for utilizing
OpenCSP Data, except for CAD models.
Install SolidWorks
The OpenCSP team standardized on SolidWorks 2022 for the SOFAST CAD Layout Tool and all
metrology CAD models. This ensures that users running SolidWorks 2022 or higher can read and
use the models. Historically the reverse was not true – due to the SolidWorks version policy, users
with higher versions could not save edited models in a form that lower versions of SolidWorks can
read. However, we have been told that starting with SolidWorks 2024, successive versions of
SolidWorks have been able to save files in versions are compatible with up to two versions earlier.
Thus SolidWorks 2024 can write models in SolidWorks 2022 and 2023 format. Similarly,
SolidWorks 2025 can write models in SolidWorks 2023 and 2024 format, etc. Note that we have not
tested this.

Non-Sandia users can obtain SolidWorks on the open marketplace, from various resellers.

2.7. Setup Visio (optional)
The OpenCSP team uses Visio to create and edit graphical illustrations. For example, most of the
ground truth optical targets in OpenCSP were created using Visio (although some were generated by
OpenCSP code).
If you wish to create edited new versions of these or create new similar targets or other graphics,
you will need Visio. However, the published targets have also been provided in .pdf format, so you
can use the targets without installing Visio.
Install Visio
The OpenCSP team is currently using Microsoft Visio 2016, version 2408. To obtain the latest
version of Visio, non-Sandia users can start here:
 Install Visio or access Visio for the web
 https://support.microsoft.com/en-us/office/install-visio-or-access-visio-for-the-web-
     f98f21e3-aa02-4827-9167-ddab5b025710
The OpenCSP team has not tested “Visio for the web” to determine whether it is capable of
supporting OpenCSP drawing requirements.
Microsoft has made some recent changes that make Visio more difficult to access and install.
Further, Visio must be purchased. Meanwhile, OpenCSP does not need or utilize many Visio
features, such as support for flow chart generation. For these reasons, ideas for switching OpenCSP
to a free alternative program for generating illustrations is welcome. Note that the ability to produce
numerically accurate illustrations with strong hierarchical object grouping capabilities are essential.

2.8. Setup Git
Git is a version control system for development of software and other text-based data. It supports
version control, allowing users to save the current version of a file set with an annotated label.
Earlier versions can be recovered on demand. Git is typically implemented with repository storage
on another file system, which means that such version save operations also accomplish file backup.
Git keeps track of changes, and also tracks code development history for each team member. In
addition, git supports the concept of branching, which allows teams of developers to collaborate
effectively while modifying a code base to incorporate new functionality without interfering with
each other’s modifications in progress.
Git is also the method of interfacing with GitHub, which holds the OpenCSP code base
(https://github.com/sandialabs/OpenCSP). In addition to supporting all of git’s features, GitHub
also provides multi-user management, forks to streamline development of large systems by large
teams, automated code testing to ensure that deviations are detected a systematic method for
supporting code review before proposed changes are integrated into the master code base, issue
tracking, and discussion forums.
The following explains how to install git and configure it for OpenCSP, starting with the pointer
from the OpenCSP on-line document “Setting up your development environment.”
Install Git
 1. https://git-scm.com/downloads
  Windows
  Click here to download
 2. Download and save .exe file.
 3. Run .exe file.
 4. Accept all defaults. (For example, don’t select rebase option for git pull.)
Start a git bash Shell
In the taskbar, type “Git Bash” and select the icon:

We suggest pinning this to your task bar, as you will want to use it frequently.
Determine Your Home Directory
Your home directory is denoted “~” in a git bash shell:
 <user_id>@<machine_id> MINGW64 ~
 $ cd ~
 <user_id>@<machine_id> MINGW64 ~
 $ pwd
 /c/Users/<user_id>

Configure git User Name and Email
Check to see if ~/.gitconfig exists and contains name and username already. If so, then do nothing.
 <user_id>@<machine_id> MINGW64 ~
 $ ls -a ~

 …

 …

If ~/.gitconfig does not exist, then in a git bash shell:
 $ git config --global user.name "<user_id>"
 $ git config --global user.email "<user_id>@<user_email_server>"

Verify
Either way, verify that your git name and username are set correctly:
 <user_id>@<machine_id> MINGW64 ~
 $ git config user.name

 <user_id>@<machine_id> MINGW64 ~

These commands should work from any directory.
You can also check the contents of the ~/.gitconfig file. In a git bash shell:

2.9. Setup OpenCSP Account
Anyone in the public can use or contribute to OpenCSP, as long as you have a GitHub account.
You can pull, write code, make improvements or additions, and submit pull requests to have the
code merged into the central OpenCSP repository.

2.9.1. GitHub Account
To establish a GitHub account, go to GitHub (https://github.com/), and press the “Sign Up”
button in the upper right corner.

2.9.2. Approver Access
If you become a member of the GitHub approver team, then it changes your permissions to enable

2.9.3.     SSH Keys
Git stores code and related data in a git repository. To develop code, you create a clone of the
repository on your local machine, make changes and additions, and when ready, write the new code
back to the repository. If others change the repository code in the meantime, you can read those
changes into your local copy. Initialization of your local copy is accomplished using “clone”
commands, reading from the repository is accomplished via “pull” commands, and writing to the
repository is accomplished via “push” commands.
The OpenCSP repository is served by GitHub, which authenticates your identity with each pull and
push command. GitHub must therefore have a record of your identity to do this. The OpenCSP
team recommends accomplishing this using SSH keys.
An SSH key is associated with your user id when logged onto a particular machine. Thus each SSH
key is specific to a user and a machine. If you work with multiple machines, then you need a
different SSH key for each machine. After creating your SSH key(s), you then register them with
GitHub, so it has the information needed to authenticate your clone, pull, and push requests.
The follow subsections will explain how to create an SSH key for your machine, how to register this
SSH key with GitHub, and then how to use the ssh-agent to reduce the number of times you have
to enter your SSH passphrase.

Register Passphrase with SSH Agent
As things stand now, each git pull and push command will require you to enter your passphrase.
You can reduce the number of times you need to enter this by starting the SSH agent, and adding
your new SSH key to its registry.
To get started, try this:

 <user_id>@<machine_id> MINGW64 ~
 $ ssh-agent
 SSH_AUTH_SOCK=…;
 SSH_AGENT_PID=…; export SSH_AGENT_PID;
 echo Agent pid …;

This executed the “ssh-agent” command. This command generated some output lines, defining
how the SSH agent should run. However, to properly start the agent, you must call it in a way that it
consumes this as input.

 <user_id>@<machine_id> MINGW64 ~
 $ eval $(ssh-agent)
 Agent pid <agent_process_id>;

This indicates that the agent process is running. Progress! Next we add your SSH key.

 <user_id>@<machine_id> MINGW64 ~
 $ ssh-add ~/.ssh/id_rsa
 Enter passphrase for /c/Users/<user_id>/.ssh/id_rsa: <Enter, no echo>
 Identity added: /c/Users/<user_id>/.ssh/id_rsa (<user_email>)

3. VERIFYING CORRECT EXECUTION
OpenCSP contains many components which accomplish different goals. It is also written and
maintained by multiple developers. Over time, some OpenCSP functionality is finished and stays
relatively stable, while work proceeds creating new functionality. During all this, sometimes changes
can be made which cause prior code to stop running correctly. Such problems accumulating over
time is sometimes called “bit rot,” and it can undermine the usefulness of OpenCSP.
To combat this, we have implemented many automated tests which verify proper operation of
important OpenCSP functionality. Some of these are small unit tests, which are run interactively by
developers. These typically check focused portions of the code, usually with very small input and
output data. We also have larger “examples,” which provide more comprehensive testing and also
serve to provide an illustrative examples of how to use OpenCSP to solve various problems. The
smaller unit tests are run manually by each developer before submitting new or revised code for
merging into OpenCSP (see below), and are also executed automatically each night. The larger
examples are run on demand by developers, and also execute automatically once per week.
OpenCSP also supports automatic document generation, which enables new code and code
revisions to automatically propagate to the on-line documentation. Document generation is also
performed automatically on a regular basis, keeping the on-line documentation up to date.
It is essential that all OpenCSP developers understand how to run the unit tests, example suite, and
document generation, so that they can verify that their code is working correctly before submitting
pull requests (see below). This test suite also makes it easier to understand how the code works, by
providing a wide variety of working examples.
The sections below will explain how to run the small unit tests, larger examples, and automatic
document generation.
