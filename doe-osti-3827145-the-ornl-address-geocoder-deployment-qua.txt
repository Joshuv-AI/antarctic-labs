 FOREWORD
This technical report documents lessons learned from deploying the Automated Determination of Detailed
Regional and Exact Spatial Segments (ADDRESS) geocoder for two large-scale residential history
projects: (1) the National Cancer Institute (NCI)/Surveillance Epidemiology and End Results (SEER)
multi-state residential history data spanning four cancer registries (New Jersey, Kentucky, Louisiana,
and Iowa), and (2) a Pennsylvania (PA) indoor-radon data. The report is intended to serve as a reference
document for National Institute of Environmental Health Sciences (NIEHS), NCI, and other research
projects that utilize the ADDRESS geocoding system.
For (1), ADDRESS system was deployed on Oak Ridge National Laboratory (ORNL)’s H100 GPUs
(storm) machines within the Knowledge Discovery Infrastructure (KDI) enclave, providing the computational
resources and data security protocols required for processing protected health information (PHI). For (2),
ADDRESS was deployed to an internal ORNL server.
The original NCI dataset comprised approximately 6,218,788 patient addresses, of which 2,982,472
records met inclusion criteria (1995–2024), within Continental United States (CONUS) and were
processed through the geocoding pipeline. Quality assessment showed that 44.9% of addresses fell within
a 1,000-meter threshold relative to NCI reference coordinates.

 ABSTRACT
The Automated Determination of Detailed Regional and Exact Spatial Segments geocoder, developed at
ORNL, was applied to standardize geocoding of multi-state cancer registry residential history data for
the NCI Cancer Outcomes and Neighborhood Environmental Correlations Tracker (CONNECT) project
and the PA geocoding assessment of residential addresses associated with indoor radon measurements.
This report documents the system architecture, deployment parameters, data filtering decisions, geocoding
quality assessment, and identified failure scenarios. Of 2,982,472 retained records from four registries,
44.9% achieved geocoding coordinates within 1,000 meters of NCI reference coordinates.
For the PA radon dataset with ∼1.5 million residential address-level records, ADDRESS achieved
house-level matches for approximately 45% of addresses from 2014 onward. Across all years, we have
96.3% of house-level results and 74.3% of residential-level results validated within the address ZIP’s
buffered ZIP Code Tabulation Area (ZCTA) proxy.
Systematic issues were identified including city-name ambiguity in the fallback matching logic and
ZIP code instability for historical addresses. This report consolidates lessons learned to support future
deployments of ADDRESS for health research geocoding.

 1. INTRODUCTION
Accurate geocoding of residential address histories is a requirement for spatial epidemiology research,
enabling the linkage of patient location data to environmental exposure datasets [6]. The National Cancer
Institute (NCI), through the Surveillance Epidemiology and End Results (SEER) program [12], maintains
longitudinal residential history data for cancer patients across multiple state registries. These records
had been geocoded at various points in time using different geocoders (including AGGIE (Texas A&M
University (TAMU)), Geocodio, and internal registry tools) — resulting in heterogeneous positional
accuracy, inconsistent spatial resolutions, and temporal data mismatches across registries.
To resolve this inconsistency, Oak Ridge National Laboratory (ORNL) through the Cancer Outcomes
and Neighborhood Environmental Correlations Tracker (CONNECT) geocoding project undertook
standardized re-geocoding using Automated Determination of Detailed Regional and Exact Spatial
Segments (ADDRESS), an internally developed geocoding service designed for high-throughput,
privacy-sensitive processing of address data. This report documents the full lifecycle of that geocoding
effort – from system architecture and deployment to parameter selection, and quality assessment, and is
intended to serve as both a technical reference and a lessons-learned document for National Institute of
Environmental Health Sciences (NIEHS), NCI, and future projects using the ADDRESS system.

 2. ADDRESS SYSTEM ARCHITECTURE AND DEPLOYMENT
2.1 SYSTEM OVERVIEW
ADDRESS (Automated Determination of Detailed Regional and Exact Spatial Segments) is a custom
geocoding system developed at ORNL, built around a Nominatim [9] instance that utilizes OpenStreetMap
(OSM) [10] data. The system aims to strengthen the fragile geocoding capabilities of Nominatim through
intelligent address parsing and multi-level geographic matching strategies.
ADDRESS operates is designed to operate as a three-container architecture. The standard mechanism
for deployment is via Docker[4] outside of the Knowledge Discovery Infrastructure (KDI), or Podman[11]
inside it.
 1. PostgreSQL database container with PostgreSQL Geographic Information System extension
 (PostGIS): Stores the OSM address data and census boundary geometries. PostGIS spatial queries
 are used to map lat/lon coordinates to census administrative boundaries.
 2. Nominatim geocoding instance: A custom-configured Nominatim [9] server that performs the core
 forward and reverse geocoding operations against the OSM database.
 3. application programming interface (API) service container: A FastAPI application that exposes
 the geocoding functionality via HTTP endpoints, handles address parsing, component permutation
 logic, and multi-level geographic ID lookup.
This containerized approach was deployed on ORNL’s storm computing environment within the KDI
enclave, providing the necessary computational resources and security protocols for processing protected
health information (PHI) [8] in compliance with data use agreements. Storm created an additional
requirement of using Apptainer[7][1].
2.2 GEOCODING WORKFLOW
The ADDRESS geocoding workflow systematically processes addresses through the following steps:
 1. Component decomposition: Each input address is broken down into constituent elements: house
 number, street name, city, state, and postal code.
 2. Permutation matching: The system creates permutations of these components, starting with
 the most specific address string (all components present) and gradually expanding scope by
 systematically dropping components until a successful match is achieved in the OSM database.
 3. Coordinate retrieval: When an exact OSM place match is found, ADDRESS returns latitude
 and longitude coordinates corresponding to that specific location. For place matches which span
 a larger area, the system provides centroid coordinates for the entire geometry.
 4. Census boundary assignment: Using PostGIS spatial queries, the returned coordinates are mapped
 to the requested census administrative boundary (tract, county, state, or ZIP Code Tabulation Area
 (ZCTA)) or Uber H3 Index.
Step 2: Permutation was introduced due to the fragility of the Nominatim geocoder on its own. An address
which is included in the OSM database may return no matches due to the inclusion of a zipcode which
does not exactly match the entry in database.

2.3 MATCH SPECIFICITY ASSESSMENT
A key enhancement in the current ADDRESS deployment is the verbose=True parameter, which
returns the entire Nominatim place object including bounding box information and OSM type. The
recommended approach for assessing match specificity is to use the dict query format and evaluate how
many of the key address components (street, city, state, ZIP) are present in the successful_address
field:
 • Most specific: All of street, city, state, and ZIP are present in the returned address object.
 • Decreasing specificity: Match quality degrades as components are missing from the returned result.
This approach allows automated assessment of match quality beyond the simple geo_level field and is
particularly useful for identifying the city-drop failure.

 3. BACKGROUND: PRIOR GEOCODING LANDSCAPE
3.1 GEOCODING SERVICES EVALUATED
Prior to this effort, the NCI residential history data had been geocoded using multiple tools at different
points in time and the related metadata were not recoverable. Table 2 compares the three geocoding
services used by NCI and relevant to this project.
3.1.1 ADDRESS (ORNL)
ADDRESS is an internal ORNL service providing privacy-preserving geocoding within the KDI enclave.
Key advantages include internal deployment (no data leaves ORNL infrastructure), multi-level census
boundary output in a single API call, and support for the geoid2geoid endpoint for cross-year census
boundary conversion.
3.1.2 Geocodio
Geocodio (https://www.geocod.io/ [5]) is a commercial geocoding service supporting forward and
reverse geocoding for the United States, Canada, Mexico, and the United Kingdom addresses. It matches
validated addresses against a reference database including United States Postal Service (USPS), OSM,
TIGER/Line, and local government data. It does not have specific historical address matching features.
For PO Boxes, it assigns coordinates to the ZIP code centroid.
3.1.3 AGGIE (Texas A&M University Geocoding Services)
TAMU Geocoding Services (https://geoservices.tamu.edu/ [14]) is a research-grade geospatial
platform developed at Texas A&M University uses strictly deterministic matching with hierarchical
attribute relaxation. It uses multiple years of TIGER/Line files but has known limitations including loss
of leading zeros in ZIP codes and the need for pre-normalization of city names [13].
3.2 AGGIE VS. GEOCODIO REGISTRY COMPARISON
An internal comparison evaluated AGGIE and Geocodio across several SEER cancer registries [3]. Key
findings:
 • 96.81% agreement in census tract assignment in Idaho (2016–2020 data); the vast majority of
 records across all registries were geocoded by either geocoder
 • Urban accuracy (∼96%) substantially higher than rural (∼88%) within a 0.1-mile threshold (New
 York comparison against a gold standard – NYS SAM geocoder, Google Maps).
 • AGGIE marginally better in Idaho and New York; Geocodio better in Louisiana and Texas
 • Both struggled with PO Box and rural route addresses; manual review rates ranged from 0.4% (NY
 urban) to 50.5% (MA rural) across registries
 • Distance thresholds varied by registry: 0.1 mile (New York), 2 km (Idaho); Louisiana used a
 Geocodio accuracy score threshold of >0.90
 • Results excluded PO Box, Rural Route, and other addresses that could not be satisfactorily geocoded
The multi-geocoder history introduced spatial inconsistencies that motivated re-geocoding with a single
standardized system.

4.3 ADDRESS SOURCES AND HISTORICAL GEOCODING
The address data in each registry came from up to three sources [12]:
 1. CTC (Cancer Treatment Center) registry data: The standard registry data record. Historically,
 Cancer Treatment Center (CTC) data used various geocoding methods over time — beginning with
 manual geocoding, transitioning to in-house geocoders, and subsequently using external geocoders.
 When a geocoder returned low quality results, the address was manually geocoded. Some CTC
 addresses date back to as early as 1911.
 2. LexisNexis (LN) data: LexisNexis residential history records predominantly geocoded using
 AGGIE (TAMU).
 3. Consolidated group: A merged record where both registry and LN data were combined, flagged
 accordingly in Addr_Source.

4.5 RESIDENTIAL HISTORY PATTERNS
In order to assess longitudinal quality of the data, patient residential histories were grouped into categories
that reflect varying patterns of residence inside and outside the US:
 1. Pattern 1 (in): Full Continental United States (CONUS) residential history
 2. Pattern 2 (out-in): Began outside US, moved to US
 3. Pattern 3 (in-out): Began in US, moved outside
 4. Pattern 4 (in-out-in): Multiple movements, beginning and ending in US
 5. Pattern 5 (out-in-out): Multiple movements, beginning and ending outside US
Each pattern is characterized by first/last date of record, total months inside the US, and total months
outside the US. Patients outside CONUS represent an additional geocoding complexity. These addresses
were filtered out.

5.3 MULTI-LEVEL GEOCODING STRATEGY
Rather than submitting each address multiple times at different geographic levels, the pipeline separated
forward geocoding from geographic boundary lookup into two distinct steps. Each address was geocoded
once using the /bulk-address2latlon endpoint to retrieve coordinates. Those coordinates were then
submitted to to the /latlon endpoint four times – once per geographic level – to obtain all required
geographic identifiers:
 1. Census tract (level: "tract"): Primary geographic identifier.
 2. State (level: "state"): Used to verify that the geocoded location falls within the expected state
 boundary. The returned state Federal Information Processing Standards (FIPS) code was compared
 against the addr_st field from the input record (addr_state_match) and against the state derived
 from the original NCI reference coordinates (state_match).
 3. H3 hexagon (level: "h3_index"): The spatial join key for environmental exposure linkage at
      H8 resolution (∼0.74 km2 ).
 4. ZCTA (level: "zcta"): For ZIP-based geographic analysis; note that ZCTA lookups return the
 centroid of the ZCTA polygon.
The same four lookups were also performed on the original NCI reference coordinates (lat, lon) to obtain
original_point_state and original_hex, enabling direct comparison between ADDRESS-derived
and NCI-derived geographic identifiers.
5.4 ZIP CODE PREPROCESSING PARAMETERS
ZIP code correction was applied conditionally using the National ZIP Code Crosswalk (1990–2020) [2]
from OpenICPSR (Project 194404, Version V2), and only triggered when the geocoder signaled a fallback
to ZIP code centroid matching. When a ZIP centroid fallback was detected, the ZIP code was checked
against the crosswalk files in chronological order:
 1. ZIP_Code_Changes_1990–2000_Documentation.csv
 2. ZIP_Code_Changes_2000–2010_Documentation.csv
 3. ZIP_Code_Changes_2010–2020_Documentation.csv
The ZIP code was checked against the “Old ZIP Code” column in each file. If a match was found, it
was updated to the “New ZIP Code” value. This process cascades through all three periods to capture
multi-step historical changes – cases where a ZIP code was changed more than once across the three-decade
period.

 7. ISSUES IDENTIFIED
7.1 DATA QUALITY ISSUES IN SOURCE DATA
The following data quality issues were identified during preliminary profiling of the source dataset prior to
geocoding:
 1. PO Box and rural route addresses: Systematically poorly geocoded by all evaluated geocoders.
 Both ADDRESS and commercial geocoders default to ZIP centroid coordinates for PO Box
 addresses.
 2. Multiple historical geocoders: The CTC data used various geocoding methods at different points
 in time, including manual geocoding. This produced heterogeneous coordinate accuracy across the
 dataset. Most CTC addresses used various geocoding methods, while those from LN predominantly
 used AGGIE.
 3. Historical addresses: Some CTC addresses date back as far as 1911. These records present
 challenges for any modern geocoder because street networks, city boundaries, and ZIP codes may
 have changed substantially.
 4. Point and state mismatches: A subset of the original NCI coordinates fell outside their expected
 state boundary.
 5. Points located in water: Some NCI coordinates were positioned in water bodies.
 6. Averaged coordinates from two addresses: The NCI residential history data applies a consolidation
 procedure when a patient has multiple geocoded addresses recorded for the same time period. Under
 this procedure, if multiple addresses share the best geocoding accuracy level, their latitude and
 longitude values are arithmetically averaged to produce a single representative coordinate. While
 this approach resolves ambiguity in the source data, averaged coordinates do not correspond to any
 real physical location.
 7. Invalid and incorrect ZIP codes: A number of records contained invalid ZIP codes, historically
 obsolete codes, or ZIP codes that had been discontinued or had boundary changes since the address
 was recorded.
7.2 GEOCODING FAILURE SCENARIOS IDENTIFIED THROUGH QA/QC
A targeted QA/QC review identified two primary failure scenarios.
Scenario 1: Correct Street, offset point location (1–2 km): When an exact house number is not found in
OSM, ADDRESS falls back to a street centroid of the matched street segment, returning a coordinate that
lies on the correct street but is displaced from the true address location. Displacements for this scenario
were observed in the approximately 1–2 km range, likely reflecting the length of the street segment in
OSM and the position of the true address along it.
Scenario 2: Street Name matched in wrong city (point_unmatch_city): When the same street name
exists in multiple cities within a state, ADDRESS may return coordinates in the wrong city. This arises
from the component-dropping fallback logic: ADDRESS initially attempts to match the full address
including city; when no exact match is found, components are progressively dropped; the street name may
then be found in a different city within the same state, returning geographically incorrect coordinates. This
behavior was identified in approximately 0.34% of total addresses.

 14

appear in the address_found field of the ADDRESS response. A distance-based threshold distinguishes
likely correct from likely incorrect city-drop cases:
 • Likely correct (city dropped but location valid): distance ≤ 𝑋 m → retain original geo_level
 • Likely incorrect (city dropped and wrong location): distance > 𝑋 m → flag as point_unmatch_city
 for re-geocoding

Scenario 3: Original Address matched incorrectly: OSM data is opensource: that means anyone and
everyone can enter data. That comes with a lot of complications around dirty data. Because of that, OSM
and by extension Nominatim apply weights to place entries which are more popular. So, sometimes, an

For example, Even when we explicitly enter an address with city=Anchorage, state=Alaska, Nominatim
will sometimes return a place entry from Alaska, Wisconsin (which is an unincorporated community in
Kewaunee County, Wisconsin) because the algorithm determines that it is far more likely that a user would
be interested in Wisconsin than the state of Alaska.
7.3 ZIP CODE CROSSWALK LIMITATIONS
The National ZIP Code Crosswalk applied during preprocessing does not currently distinguish between
two distinct types of ZIP code changes:
 1. Discontinued ZIP codes: ZIP codes that no longer exist and have been assigned a replacement
 code. These can generally be updated to the new code.
 2. Realigned ZIP code boundaries: ZIP codes that still exist but have had their delivery area
 boundaries adjusted. Updating these for historical addresses may introduce inaccuracy, as the
 original ZIP code may still be valid for the specific address.
The current implementation updates any matching ZIP code regardless of change type. Future development
will parse the “Comment” or “Change Type” fields in the crosswalk to apply updates only for discontinued
codes.

 8. LESSONS LEARNED AND RECOMMENDATIONS
1. Verbose mode is essential for QA/QC: The ADDRESS API returns a verbose parameter that,
 when set to True, exposes the full Nominatim match object in the response. This includes the
 OSM object type (house, residential, postcode, city, etc.), the bounding box of the matched
 feature, and a structured breakdown of all matched address components. Without verbose mode,
 the response returns only coordinates and a geographic identifier, making it impossible to determine
 whether the geocoder matched the full address, fell back to a street centroid, or returned a ZIP code
 centroid. Evaluating which components (street, city, state, ZIP) appear in the successful_address
 field provides a richer and more granular match quality signal than the geo_level field alone, and
 was essential for identifying both the ZIP centroid fallback cases (Scenario 1) and the wrong-city
 matches (Scenario 2) documented in this report.
2. Component-dropping is a double-edged sword: Component-dropping improves match rates but
 introduces wrong-city risk When ADDRESS cannot find an exact match for a submitted address,
 it progressively drops components from the query – first directional prefixes, then street suffix,
 then city, then ZIP – and retries until a match is found in OSM. This permutation-based fallback
 logic is valuable because it substantially increases the proportion of addresses that return some
 geocoded result rather than a complete failure. However, when the city component is dropped,
 ADDRESS may match a street name in a different city within the same state, returning coordinates
 for the wrong location entirely. This behavior was identified in 10,228 records where the city name
 was absent from the address_found response field. Future users of ADDRESS should inspect
 address_found for any successful geocoding response especially when cutoff parameter is not
 used.
3. Cutoff parameter: The ADDRESS single-address endpoint (/address2latlon) exposes a
 cutoff boolean parameter that, when enabled, restricts the permutation-based matching logic and
 prevents ADDRESS from dropping certain address components – such as the city name – during the
 fallback search sequence. This parameter would directly prevent the wrong-city matching behavior
 described in Lesson 2. However, at the time of processing, the cutoff parameter was not available
 in the bulk geocoding endpoint (/bulk-address2latlon) used by this pipeline. As a result, the
 10,228 city-drop cases identified in this dataset may have been preventable. Future deployments
 of ADDRESS for bulk geocoding should request this parameter in the /bulk-address2latlon
 endpoint, which would simplify the QA/QC workflow considerably by reducing or eliminating
 wrong-city matches at the geocoding stage rather than requiring post-hoc detection or re-geocoding.
4. ZIP code preprocessing can improve historical geocoding but must be applied with care:
 For addresses with dates prior to the 1990s, ZIP codes recorded at the time of residence may no
 longer exist or may have been affected by subsequent USPS changes. Applying the National ZIP
 Code Crosswalk (1990–2020) before geocoding, or conditionally when a ZIP-code-level fallback
 is detected, can improve geocoding resolution by providing the geocoder with a current, valid ZIP
 code. However, this preprocessing may introduced a specific risk because not all ZIP code changes
 represent discontinuations. Some crosswalk entries reflect delivery-area realignments or the creation
 of a “new” ZIP code for only a portion of the deliveries previously associated with an existing
 ZIP code. In these cases, replacing the “old” ZIP code may reduce accuracy because the original
 ZIP code may still be correct for the patient’s specific street address, while the “new” ZIP code
 applies only to addresses affected by the change. The current implementation does not distinguish
 between discontinued ZIP codes and partial delivery-area changes. This distinction is not currently

 17

 made because the crosswalk “Comments” field describing the change type was not parsed. Future
 implementations should incorporate the change type when determining whether a historical ZIP
 code should be updated.
5. Averaged coordinates are challenging to validate: Some NCI residential history data carries a
 consolidation procedure when a patient has multiple geocoded addresses recorded for the same
 time period. When two or more addresses share the same best geocoding quality level, their latitude
 and longitude values were averaged to produce a single representative coordinate. These averaged
 coordinates do not correspond to any real physical location. As a result, when ADDRESS geocodes
 the same address and returns precise rooftop-level coordinates, the distance between the ADDRESS
 coordinate and the NCI reference coordinate will reflect the averaging displacement rather than a
 geocoding error. Future quality assessment should distinguish between addresses with averaged
 coordinates and addresses with genuine geocoding failures.
6. Comparison with multiple-geocoder: The NCI residential history dataset was geocoded over
 multiple decades using a mix of methods including AGGIE (TAMU), Geocodio, manual geocoding,
 and registry-specific tools, with no single geocoder applied uniformly across all registries or time
 periods. As a result, the NCI reference coordinates do not constitute a uniform gold standard against
 which ADDRESS results can be objectively evaluated. A large distance between ADDRESS and
 NCI coordinates does not necessarily mean ADDRESS is wrong; it may equally reflect an error,
 centroid assignment, or methodological artifact in the original NCI geocoding. Conversely, a small
 distance does not confirm that ADDRESS is correct, it may simply mean both geocoders are correct
 or made the same error or defaulted to the same centroid. The practical implication is that the
 distance-based quality categories used in the CONNECT project (within 50 m, 100 m, 1,000 m)
 characterize the degree of agreement between two the systems.
7. The geoid2geoid endpoint is valuable for temporal analysis: Census tract boundaries are
 redefined every ten years following the US decennial census, meaning that the same physical
 location may fall in different census tracts depending on whether 2010 or 2020 boundaries are
 used. For longitudinal residential history data spanning the 2010–2020 boundary change, using
 a single census year consistently across all records may introduce artificial discontinuities in tract
 assignments for patients whose addresses predate or postdate the boundary change. The ADDRESS
 geoid2geoid endpoint converts geographic identifiers between different census years, enabling
 analysts to harmonize tract assignments to a single reference year. This endpoint should be used
 when constructing longitudinal exposure linkages that require consistent geographic units across
 time.
8. PO Box and rural route addresses remain unresolved: PO Box and rural route addresses do not
 correspond to physical street locations and therefore cannot be geocoded to rooftop or street level
 by any geocoder, including ADDRESS. Both ADDRESS and the commercial geocoders evaluated
 in this project (AGGIE and Geocodio) default to assigning ZIP code centroid coordinates for
 these address types, producing large spatial uncertainties that are particularly problematic for rural
 populations where PO Box usage is common and where ZIP code areas can span hundreds of square
 kilometers. The recommended approach is to pre-process PO Box and rural route addresses using
 a physical address conversion tool such as LN or a USPS address standardization service; before
 geocoding, to obtain a deliverable street address that can be geocoded at higher precision.

 9. CONCLUSION
This report documents the deployment of the ORNL ADDRESS geocoding system for the NCI/SEER
multi-state cancer registry residential history for the CONNECT geocoding project [6]. Key accomplishments
include:
 • Standardized re-geocoding of ∼3 million address records using a single privacy-preserving internal
 geocoder
 • Development and application of a historical ZIP code preprocessing step using the 1990–2020
 national crosswalk
 • Spatial validation relative to NCI reference coordinates with 44.9% of addresses within the 1,000 m
 threshold
 • Identification, characterization, and partial remediation of two geocoding failure scenarios.
Ongoing work focuses on resolving the city-drop ambiguity by introducing the cutoff parameter in the
bulk endpoint and targeted re-geocoding, refining ZIP crosswalk logic, and systematically investigating
the addresses with high distance divergence. This report, combined with the Pennsylvania geocoding
assessment, constitutes the foundational lessons-learned documentation for ADDRESS deployment in
health research contexts.

 APPENDIX B. ZIP CODE CROSSWALK DETAILS
The National ZIP Code Crosswalk (1990–2020) from OpenICPSR Project 194404, Version V2 (Bailey
and Helmuth) was applied in three sequential steps. For each address, the ZIP code was checked against
“Old ZIP Code”; if matched, it was updated to “New ZIP Code.” This cascades through all three decades
to capture multi-step historical changes.
A known limitation is that the crosswalk includes both discontinued ZIP codes and ZIP codes with
boundary adjustments only. The current implementation updates any matching ZIP code regardless of
type. Future development will parse the “Comment” or “Change Type” fields to apply updates only for
discontinued codes, preserving historically valid ZIP codes for boundary-adjustment cases.
