 Abstract
 In this report, we evaluate the trade-offs between accuracy and performance in three equation of state interpola-
 tion strategies– EOSPAC, SpinerEOSDependsRhoT, and SpinerEOSDependsRhoSie—using SESAME tabular data.
 We also investigate ways to reduce nonlinearity in the data through invertible transformations within the SpinerEOS-
 DependsRhoSie class with the goal of impacting interpolation accuracy. We include a variety of benchmarking tests
 that vary the grid densities and how memory is accessed.

1 Introduction
  For continuous materials where viscosity is treated to be zero, the laws of conservation of mass, energy, and mo-
mentum form the Euler equations. In order to reach a solution for this system of undetermined equations, the system
must be closed. This closure is achieved through an “equation of state” (EOS) model in either analytic or tabular for-
mats. Broadly, EOS models describe relationships between a material’s thermodynamic properties, such as pressure
(P ), temperature (T ), density (ρ), and specific internal energy (ϵ). These relationships are essential for predicting a
material’s state under varying physical conditions. For example, the Mie-Grüneisen EOS relates the pressure of a solid
to its volume (or density) and internal energy, and is commonly used to model the behavior of materials subjected to
shock compression. Ideally, such EOS models would be as efficient and accurate as possible. In this project, we aim to
expose trade-offs between the accuracy and performance of three equation of state interpolation strategies: EOSPAC,
SpinerEOSDependsRhoT, and SpinerEOSDependsRhoSie1 . Each have numerous options that can be tuned to optimize
trade-offs between performance, accuracy, and memory cost.
  We work with the SESAME library, a database of over 170 materials [2]. This dataset provides tabulated thermo-
dynamic and property data for a broad range of elements, compounds, composites, and rocks [2]. SESAME data is
considered “semi-empirical” because tables are generated from both experiments and theory. It is important to note
that gaps and irregularities in the data can still occur. SESAME data is tabulated on a density-temperature grid span-
ning microscopic to astronomical scales. For illustration, Figure 1 shows EOS data for copper (material ID: 3337)
and highlights the vast ranges in temperature and energy across constant-density isochores. Given the large dynamic
ranges, we adopt a log-log scaling in this report. This choice helps visualize structure across orders of magnitude and
facilitates comparison within “decades.” 2 Figure 2 summarizes key characteristics of the SESAME library.

 The Singularity-EOS models, SpinerEOSDependsRhoT and SpinerEOSDependsRhoSie, are built on the Spiner data
format. Spiner is library used for storing, indexing, and interpolating multidimensional data in a portable way (e.g.
it can run on both NVIDIA GPU and Intel CPU) [1]. Moreover, Singularity-EOS doesn’t use log-spaced grids as
those are computationally expensive. Singularity-EOS models use “regular gridding” to prevent the need for costly
bracketing algorithms to locate points. Regular gridding refers to the fact that Spiner’s look-up equation depends
on the index i, meaning, given a density-temperature value, you can find the desired index with O(C) complexity.
This allows for fast and deterministic look-ups which is ideal for GPUs. However, regular grids can struggle with
nonlinear features unless you make the grid resolution finer (which is not always possible due to computational costs)
or we transform the coordinate system so that the data becomes more uniform. The latter solution motivates the
implementation of data transformations within SpinerEOSDependsRhoSie described in Section 3.2.

3 EOSPAC vs. Singularity-EOS
  For the most clear overview of the three EOS interpolation strategies used in this study, refer to Figure 2. EOSPAC
is a utility library used to access and interpolate SESAME data. It is considered the “gold standard” for accurate
inversions because it uses a rational-function interpolator to reconstruct sparse SESAME tables. However, this model
is not the most performant model due to its irregular spaced grids. Since the grid is irregular, it relies on bracketing
searches of complexity O(log(n)) to find values.
  Singularity-EOS contains two independent EOS interpolation strategies, SpinerEOSDependsRhoT and SpinerEOS-
DependsRhoSie. The Singularity-EOS interpolation strategies are high-performance equation of state models because
they provide a unified, portable interface for solving EOSs on a regular grid, see Section 2. While these interpolation
strategies are highly performant, they suffer from inaccuracies due to the necessary inversions. In the sections that
follow, we describe the differences between SpinerEOSDependsRhoT and SpinerEOSDependsRhoSie and provide our
methodology for comparing their accuracy and performance.

3.2 SpinerEOSDependsRhoSie
  As in the case of SpinerEOSDependsRhoT, some EOS models need to be inverted to solve the Euler equations. On
the contrary, SpinerEOSDependsRhoSie “pre-inverts” tabular data to bypass this costly computation. However, this
can cause interpolation inaccuracies because in ρ-ϵ space (the space of this model), valid data only exists in specific
regions. We hypothesize that suitable transformations can increase the number of valid (ρ, ϵ) pairs. To test this,
we add data transformations to the SpinerEOSDependsRhoSie class to present data in a more uniform way before
linear interpolation. We wrap the class in a template that allows for three optional, invertible transformations: a
subtraction of the cold curve from specific internal energy, a division of specific internal energy by heat capacity, and
a division of the data by temperature cubed. Further motivation for the choice of transformation is provided below.
In addition, readers can gain a better sense of the impact of each transformation by referring to Figure 3. For the
effects of the transformations on other materials, see Appendix A. For additional information on how we integrated
these transformations into the code base, refer to Appendix B. All of our transformations can be summarized in the
following equation where ϵ̂ is our transformed ϵ:

We break down each component of this equation in subsections B-D that follow. Note that we focus on transforming
specific internal energy (ϵ) due to the nature of how the Euler equations are posed in this problem 3 .
  A. The Null Transformation
The null transformation is an available option in the event that users do not wish to transform the data. The original
data is returned.
  B. Subtraction of the Cold Curve
We provide the option to subtract the cold curve, the zero temperature isotherm, from all of the specific energy data
points. The cold curve primarily captures the harmonic response of the material. For the purpose of explanation and
motivation, we will adopt the model in which atoms within a dense fluid are treated as balls with springs connecting
them. As atoms are pushed together, pressure increases linearly. By removing this baseline response, we can isolate
the thermal contributions and better observe degeneracy pressure, a quantum effect where there is a force that arises
from two particles trying to occupy the same quantum mechanical state.
  C. Dividing Specific Internal Energy by Heat Capacity
We were motivated to divide the specific internal energy (ϵ) by heat capacity (CV = dE  dT ) due to dimensional analysis
revealing this would return Kelvins, the unit of temperature. This would make a pseudo temperature-temperature
grid with constant isochore densities. However, it is important to note that dividing by CV can introduce or amplify
discontinuities if it is not smooth. To explore the effects of this, we attempted to smooth the heat capacity prior to
division using models such as Einstein, Debye, Chebyshev polynomial fits, as well as filters like median, Gaussian,
and Savitzky-Golay. Ultimately, we found that smoothing had minimal impact on the overall data shape and did not
justify implementing it due to the additional computational cost.
  D. Dividing by Temperature Cubed
For solids, after transformations B. and C., we believe most of the nonlinearity is due to the rapidly changing heat
capacity. Going back to the ball and spring model, if you push the atoms too close together, you start to lose the linear

3.3 Transforming the Grid space
  In order for the SpinerEOSDependsRhoSie interpolation strategy to perform accurate look-ups, we need to trans-
form the grid itself with the transformations described in Section 3.2. As referenced in Figure 2, the SpinerEOSDe-
pendsRhoSie class obtains its Spiner DataBoxes in tabulated (ρ, T ) space as well as (ρ, ϵ) space [1]. Now that the
interpolation strategy is performing ϵ look-ups in log-space using transformed energy, we need to ensure that the grids
in (ρ, ϵ) are built on the same transformed energy space before interpolation. Before Singularity-EOS can make use of
the Spiner-based interpolation methods, an executable called sesame2spiner must be called. This executable receives
any number of .dat files as inputs. A .dat file acts as an info deck that, at a minimum, provides the material name and
matid (material id) corresponding to a substance in the SESAME database. Piecewise grid sizes, bounds, and other
SP5 file creation parameters can be altered. Sesame2spiner uses these input decks to create an .SP5 file that holds the
SESAME data tabulated in (ρ, T ) for Spiner temperature interpolation methods and in (ρ, ϵ) for Spiner ϵ interpolation
methods. We targeted this process so that the computational cost of transforming large grids is isolated to the file
creation system. Here we take the (ρ, ϵ) tabulated grid spaces, interpolate onto them using the untransformed energy,
then get the transformed energy, and directly map the results of the interpolation back onto the grid. This now gives
the Spiner interpolation method a transformed energy grid space with each accurate result, mapped to the transformed

3.4 Unit Test
  Catch2 is a modern, open-source C++ testing framework that simplifies writing and running unit tests. It is header-
only and has no external dependencies beyond the C++ standard library, making it easy to integrate into projects. The
key strength of Catch2 is its support for Behavior Driven Development (BDD) style testing. This allows for writing
test in a TESTCASE-GIVEN-WHEN-THEN manner which provides top to bottom scoping. In other words, this gives
the ability to test individual segment of code without affecting other aspects of the code. The REQUIRE macro is
used for comparisons and decomposes the full expression, showing both left- and right-hand values when an assertion
fails. The test can be named using descriptive strings, making the output as explanatory as needed. An included INFO
macro, designed to activate if an REQUIRE fails, can be used to provide even more description.

  In this example, the scenario name “Ideal gas mean atomic properties” describes the purpose of the test. Tags (such
as [EOS],[IdealGas], or [GibbsFreeEnergy]) could be used to group or filter this test. SCENARIO is a Singularity-EOS
created macro that simply aliases CATCH2 TESTCASE. The GIVEN section sets up a specific EOS object (here an
ideal gas with certain parameters).The WHEN section executes the code under test (which we run on host). The THEN
section uses a REQUIRE assertion to verify the result meets our expectation. Catch2’s syntax makes the test read like
a specification. This improves clarity for developers and scientists reviewing the test. Notably, you can have multiple
THEN blocks under a single WHEN to check several outcomes; Catch2 will rerun the GIVEN/WHEN setup for each
THEN, isolating the checks. This means that each assertion is evaluated in a fresh context, preventing one failing
check from contaminating the next.

  We use a unit test to confirm that our coded transformations correctly interpolate and perform the correct look-up in
log space. By using CATCH2’s framework, we can confirm that our stand alone transformations work properly. This

  The baseline for comparisons of accuracy and performance is EOSPAC set to its default settings: rational interpo-
lation, no pre-inversion and no insertion of additional points to the table prior to inversion, and interpolation. We
run each test while varying grid density. We also evaluate the impact of memory layout by testing both ordered and
random input.
  We tested the performance of the models when accessing data that are adjacent in memory (contiguous sampling).
We achieve randomization by shuffling the indexes of the grid. A previous study found that EOSPAC was barely
affected by randomization of the indices, unlike the other two models that suffered in performance [3]. We reach the
same conclusion, as seem in the copper example Table 4 which shows the time it took each model and look-up type
with random vs. ordered indices. For the timing comparison tests, we perform 20 trials per model and look-up type.
We discard the first 5 trials and average the remaining 15 to obtain a stable measurement. This accounts for caching
effects: during initial iterations, data must be fetched from main memory (RAM) to the CPU. Anticipating sequential
access, the system pre-fetches adjacent memory locations into the CPU cache. Subsequent iterations benefit from
faster access to this cached data, resulting in more consistent and representative timing.

  We also explored the effects of using a base-2 and base-10 grid. In computer architecture, data is stored and accessed
in base-2 units, and cache sizes are typically powers of two. Modern processors leverage vectorization, which operates
most efficiently on power of two data size (for example, operations like 28 /26 simplify to the bitwise shift 8–6 = 2).
We test the impact of this using base 2 (nRho, nT) grids of sizes of (32, 32), (64, 64), (128, 128), (256, 256), (512,
512), (1024, 1024)) and base 10 grids of (10, 10), (50, 50), (100, 100), (300, 300), (500, 500), (1050, 1050) on the
ϵ(ρ, T ) look-up. Overall, we found nominal differences between using either sample size grids. One notable feature
is the exponential relationship between the number of grid points and computational time for EOSPAC due to costly
searches.

5 Future Works
  For some materials, the data transformations implemented in this study produced sharp features. An example of this
is deuterium (material ID: 5267), refer to Appendix A for a visual representation of its data under various transfor-
mations. Ideally, there there would be routines in our code base to detect whether a material is gas (like deuterium)
or solid and appropriately choose how to transform it. Moreover, although we have confidence that our transforma-
tions work as intended using the tests described in Section 3.4, implementing them into SpinerEOSDependsRhoSie
has proven to be a challenge. If given more time, we would have liked to compare the post-transformation accuracy of
SpinerEOSDependsRhoSie against the other interpolation strategies.
