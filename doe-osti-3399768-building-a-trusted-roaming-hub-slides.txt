 Roaming Business Case

 A roaming hub is the network switchboard
 of the connected infrastructure charging
 ecosystem. It doesn’t store data or dictate
 policy; it ensures verified messages move
 securely and efficiently between the
 right platforms.

By combining Representational State Transfer
(REST) simplicity with centralized trust
enforcement, the hub enables scalable, secure,
and interoperable roaming across thousands of
sites, vehicles, and energy actors.

 eMSP = eMobility Service Provider

 Software Design HUB

The Roaming Hub is a REST API implementing the OCPI 2.3.0 specification, written in Rust using the
Axum web framework.
 • It is specification and domain-driven. The architecture is completely guided by the OCPI 2.3.0
 specification. By rigorously building out the core domain models first, the business logic and
 algorithms naturally follow.
 • It is extensible and DRY (don’t repeat yourself). Leveraging Rust features—specifically
 macros (for common trait implementations) and polymorphic functions—to eliminate
 boilerplate, maximize code reuse, and ensure long-term maintainability.
 • It offers production-grade performance. Architected from the ground up for scale. Strictly
 focuses on high-throughput, low-memory constraints to deliver a highly efficient, enterprise-
 ready roaming hub.

 Security Principles

Isolation: Each platform retains control of its
own data and credentials.
Authentication: Authorization token negotiated
through the OCPI Credentials module.
Integrity: Communication uses HTTPS with
mutual validation of platform and role identities.
Auditability: Transactions logged and verified
independently for nonrepudiation and
compliance.
Per-session access: Access is given on a per-
session basis and is continually requested and
validated.
 NIST SP 800-207, Zero Trust Architecture

 Security Principles

Deny-by-default: Blocking all inbound and
outbound traffic that has not been permitted by
firewall policy.
Least privilege: Enabling the user to have only
necessary privileges and access.
Trust algorithm: Weighing various factors of trust
instead of using a single trust vector.
Data and control pane separation: Separation of
the communication pathways in the network.
Key management: Public Key Infrastructure
management and governance.

DESIGN ARCHITECTURE:
Zero Trust Risk
Assessment
Stage 1: Attribute-based access control (ABAC;
 binary allow/deny). Stop if denied.
 Proceed to Stage 2 if allowed.

Stage 2: Risk assessment scores computed
 from validators:
 • 0.8–1.0: LOW—Allow all checks passed
 • 0.6–0.8: MEDIUM—Allow with logging
 • 0.4–0.6: HIGH—Block or escalate
 • 0.0–0.4: CRITICAL—Deny (likely malicious).

 STAGE 2: Validators
Examples of types of attacks the Stage 2 validators will flag and score:
• Authentication attacks: Missing bearer token, low-complexity tokens
• Injection attacks: Json sql, injectio, overflow, command injection
• Session and fraud detection: Bearer token swap, IP address changes mid-
  session, impossible charge rates, status rollback
• Source reputation: Trusted IP list enforcement, user-agent header presence check
• Payload structure anomalies: Suspiciously long ID/code fields, oversized arrays, data
  consistency violations
• Multiparty roaming and identity attacks: Party ID/country code spoofing, cross-party CDR
  data leakage.
