Executive Summary
Intel AMX is a built-in component of recent Intel CPU architectures, first supported by the Intel Sapphire Rapids
in 2023, that enables efficient dense matrix multiplications using mixed precision with low-precision data types.
The popularity of mixed-precision algorithms has grown recently, primarily due to their use on GPUs to enhance
the efficiency of HPC applications, particularly for the training of large language models. The availability of mixed
precision on CPUs represents a cost-effective solution for applications where high speed is not critical. This report
shows how to use the Intel AMX accelerator through examples in C++ and Python. The examples will focus on
mixed-precision floating-point operations obtained by the use of bfloat16 (or BF16) to accelerate code in single
precision. We employ a bottom-up methodology, starting from specific register instructions (TMUL operation)
to higher-level applications in libraries such as Intel MKL, PyTorch, and TensorFlow, ensuring a comprehensive
understanding of the accelerator’s potential. Additionally, we provide insights into the expected performance gains
when leveraging the accelerator on the Kestrel HPC machine at the National Renewable Energy Laboratory.

1 Introduction
In recent years, the rapid evolution of hardware accelerators has significantly influenced the field of high-performance
computing (HPC), particularly in machine learning and artificial intelligence. Graphics Processing Units (GPUs)
have been at the forefront of this shift, offering substantial computational power for parallelizable tasks, especially
in neural network training. A notable advancement contributing to this trend is the increasing adoption of mixed-
precision computing using Tensor Cores, which balances computational efficiency with memory usage (Micikevicius
et al. 2018). The introduction of Intel Advanced Matrix Extensions (AMX) (Intel Corporation 2022) in the Intel
Sapphire Rapids architecture, launched in 2023, marks a significant step forward in bringing mixed-precision ca-
pabilities to CPUs (Nassif et al. 2022). While GPUs have long dominated the machine learning landscape due to
their efficiency in matrix operations, the availability of mixed-precision processing on CPUs presents a cost-effective
alternative for applications where peak speed is not critical (IBM Cloud Education 2025). This expansion provides
developers and researchers with more accessible hardware options, particularly when leveraging existing CPU infras-
tructure.
Mixed-precision computing is an approach that leverages numerical representations with different bit widths to
achieve specific goals, e.g. higher accuracy within a time budget. A typical use of mixed precision, supported by
NVIDIA Tensor Cores and Intel AMX, is the combination of 16-bit floating-point data types with the IEEE sin-
gle precision standard type, or FP32. The two 16-bit types largely used are the FP16 from the IEEE 754-2019
standard (IEEE 2019) and the bfloat16 (or BF16) proposed by Google (Abadi et al. 2016; Kalamkar et al. 2019).
The former, FP16, has 10 bits for the mantissa, or fractional part, and 5 bits for the exponent while BF16 has only
7 bits for the mantissa, which makes BF16 less precise but able to approximate a wider range of real numbers. The
main advantage of BF16 is that it has the same number of exponent bits as FP32, which means type casts between
those types are trivial by using, for instance, bit shifts available in hardware. By strategically utilizing reduced preci-
sion where full precision is not necessary, mixed-precision computing can accelerate processing speeds and decrease
energy consumption without significantly impacting the accuracy of results (c.f., Higham and Mary 2022). This is
especially valuable in neural network training, where vast amounts of matrix multiplications can benefit from the
increased throughput of lower-precision operations (Micikevicius et al. 2018).
This report aims to provide a practical guide on utilizing the Intel AMX accelerator in the fourth generation of Xeon
processors (Sapphire Rapids architecture), demonstrating its integration in both C++ and Python environments.
Those processors only support mixed precision operations with BF16 and 8-bit integers, as support to FP16 only
started in the 6th generation of processors, launched in September 2024. We employ a bottom-up methodology,
beginning with the low-level register instruction TMUL in Chapter 2, and extending to high-level libraries, including
Intel MKL in Chapter 3, and PyTorch and TensorFlow in Chapter 4. Additionally, we offer insights into expected
performance gains when using Intel AMX within the Kestrel HPC machine, contributing to a deeper understanding
of the potential benefits and trade-offs of this technology. Chapter 5 summarizes the conclusions obtained through
the experiments.

The results presented in this report were generated using Jupyter notebooks, and Python and C++ code from https:
//github.com/NREL/amx-fp-tests/. The repository is a complimentary material for this report.

2 The Intel AMX accelerator
The Intel AMX accelerator is a processing unit designed to enable fast matrix multiplications in the form C :=
AB +C. These multiplications utilize low-precision (8- or 16-bit) inputs matrices A and B, while the output matrix C
is in 32-bit precision. The AMX technology comprises two main components:
 1. Tiles: Eight 1 KB two-dimensional registers.
 2. TMUL (Tile Matrix Multiplication): An accelerator engine that operates on the tiles to perform matrix
 multiplications.

In the following sections, we demonstrate how to use TMUL to multiply two matrices stored in BF16 precision. The
code is written in C++ and is based on (Villarreal 2024). Prior knowledge of C++ is not required to understand the
workflow.
Remark 1. One can verify the availability of Intel AMX support by executing lscpu | grep amx in a Linux
terminal. If the flags amx_bf16, amx_tile, and amx_int8 appear in the output, that means the AMX accelerator is
supported by the system.

 Using GFLOPS (Floating-Point Operations per Second) as a performance metric is generally preferable to raw ex-
 ecution time, as it offers a more hardware-agnostic measure of computational efficiency. This metric can be derived
 whenever the number of floating-point operations is known. For matrices A (m-by-k), B (k-by-n) and C (m-by-n), the
 dense matrix multiplication C := AB +C involves exactly mnk multiplications and mnk additions, resulting in a total
 of 2mnk floating-point operations.

 2.2 Single-core matrix multiplications on Kestrel
 The experiments conducted using test_bf16.cpp demonstrate a performance of approximately 589 GFLOPS
 when accounting for data transfers to and from the accelerator before and after each TMUL call. This measurement
 was obtained using -O3 -march=native compiler optimization flags with GNU Compiler Collection (GCC)
 version 13.1.0 on a Kestrel compute node. Since the memory transfers occur at the register level, we expected that
 enabling or disabling io_on_every_call would not affect execution time significantly. However, when matrix
 operations are performed without register movement overhead, performance improves dramatically, reaching 3470
 GFLOPS.

 We also benchmarked the FP32 matrix multiplication implementation from Intel (intel-oneapi-mkl/2024.0.0-
 intel), achieving up to 214 GFLOPS using a single CPU core. This measurement was obtained by either setting
 MKL_NUM_THREADS=1 or linking against libmkl_sequential.a instead of libmkl_intel_thread.a. Addi-
 tionally, the single-core performance of cblas_gemm_bf16bf16f32() reached 1350 GFLOPS in our experiments,
 representing a speedup of 6.3x over cblas_sgemm() (the FP32-only implementation). This performance is also
 well within the expected range [589 GFLOPS, 3470 GFLOPS] based on the results we obtained above. Based on
 these results, we estimate that compute-bound applications relying on dense matrix multiplications should expect
 a speedup between 2.75x and 6.3x when running in mixed precision on a single core of Kestrel. Intel reports (Intel
 Corporation 2022) that BF16 is 16x faster than FP32 in terms of operations per cycle, which approximately what we
 get when computing the ratio 3470 / 214 from above. This ratio helps verify the accuracy of our estimates.
 While single-core performance might seem less impactful given that each Kestrel CPU node offers 104 cores, our
 focus will shift to a multicore performance analysis in the following chapters. Furthermore, accuracy loss was not
 assessed in these experiments, as such analysis is more relevant for larger matrices. See Section 4.1 for results
 concerning accuracy.

3 Mixed precision using Intel MKL
Intel MKL (Wang et al. 2014) (version 2023 an above) provides a high-level interface for matrix multiplications
of BF16 matrices with accumulation in FP32, namely cblas_gemm_bf16bf16f32(). The tests presented in this
chapter use Intel MKL from intel-oneapi-mkl/2024.0.0-intel. All the experiments use Intel compilers
(Intel oneAPI DPC++/C++ Compiler 2023.2.0) with the -O3 optimization flag. We denote, as usual, the general
matrix-matrix multiplications by the acronym GEMM.

3.1 MKL GEMM with multiple threads
Figure 1 shows the results for using MKL with all available (104) cores. The black line represents the approximate
peak performance for FP32 computed as follows:
 • The range per usable CPU node on Kestrel was 5.8 - 6.2 TFLOPS in double precision (provided by Intel using
 the HPL benchmark on August 2023). Hyperthreading was off.
 • We assume every node peak performance is 5.8 TFLOPS for double precision.
 • FP32 operations are roughly 2x faster than FP64, so 11.6 TFLOPS for FP32.
As one can see, the FP32 matrix multiplication (MKL FP32 GEMM) peak performance is close (15% off) to the
estimated peak for FP32, which serves as verification of our estimate. The peak performance for mixed-precision
matrix multiplication (MKL BF16 GEMM) is 2.74x higher than the peak for FP32. Notice how close this value is
from the one obtained in Section 2.2 for the single core case (2.75x). This shows good accordance between single
core and multiple core results.

3.2 A blocked mixed-precision TRMM
Dense matrix multiplications have a high arithmetic intensity, meaning the computational complexity, O(2n3 ), is
significantly higher than the amount of data moved in memory, O(3n2 ). The arithmetic intensity is the ratio 2n/3.
Therefore, the volume of data movement is small compared to the number of operations performed by the computing
unit, making this operation ideal for computing performance benchmarks. Many algorithms with high arithmetic
intensity either rely on matrix multiplications or can be reformulated, so that most of the computation is achieved
through matrix multiplications. This concept underpins the implementation of packages like LAPACK (Anderson
et al. 1999), Intel MKL, and Cray LibSci (Cray LibSci 2025). As an example, we study the effect of mixed-precision
dense matrix multiplications on another routine, TRMM (triangular matrix multiplication). This serves as a step
forward, aiming to demonstrate the potential of mixed precision in generic scientific applications.

 5

Intel MKL only offers cblas_gemm_bf16bf16f32() as a mixed-precision algorithm utilizing Intel AMX as of
oneAPI v2024.1. In order to explore the mixed precision in algorithms other than GEMM, third-party libraries
should either use the provided GEMM kernel or use AMX instructions directly. Consequently, as a proof of concept
of the former strategy, we implemented a blocked version of TRMM released with ⟨T⟩LAPACK v0.1.2 (⟨T⟩LAPACK
2025) that relies on cblas_gemm_bf16bf16f32() for performance. In brief, the algorithm computes the multi-
plication B := AX of a triangular matrix A by a dense matrix X using a sequence of dense matrix multiplications in
mixed precision, among other operations in single precision (FP32). The algorithm leverages the mixed-precision
implementation from MKL and uses native C++ code for the remaining computation.
Figure 2 compares the performance of our implementation in ⟨T⟩LAPACK against the performance of Intel MKL,
and the code can be found at https://github.com/NREL/amx-fp-tests/tree/v2025-07/trmm-in-tlapack. We tested
various column sizes for matrix B and used block sizes of 128 in bTRMM. Two additional points are plotted for one
of the bTRMM curves to illustrate that performance continues to improve for sizes larger than 105 . The results show
that the blocked mixed-precision TRMM (bTRMM) outperforms the single-precision implementation from MKL for
larger matrices. The bTRMM curve is notably distinct, with the algorithm’s performance continuously increasing as
the matrix size grows. This indicates a promising use case for mixed-precision implementations.

Figure 3 displays the (forward) error ∥B − B̂∥1 /∥B∥1 in triangular matrix multiplication, where B is the reference
value computed using FP64, and B̂ is the matrix computed in either FP32 or mixed precision (using BF16). The
matrices A and X are generated in FP32 following a normal distribution. As expected, the error in FP32 increases
with the size of the triangular matrix
 √ (m). Given the normal distribution used to generate matrix data, the error is
expected to grow at the rate of m. Interestingly, the error in the mixed-precision TRMM stays constant at 2.3 ×
10−3 as m increases, a value 3.4x smaller than the BF16 precision (7.8125 × 10−3 ). We believe this behavior is due
to the accumulation being performed in FP32 and the fixed block size of bTRMM. As a result, a higher m implies a
greater number of intermediate accumulation operations. A more in-depth numerical analysis is needed to validate
this hypothesis. In conclusion, the forward error is under control in the mixed-precision operation and the sensitivity
to the lower precision gets smaller as m grows.

4 Enabling Intel AMX for PyTorch and TensorFlow
PyTorch provides a list of operators that can be accelerated using AMX technology, as outlined in (PyTorch 2023).
This list includes the function torch.matmul, which is the dense matrix-matrix multiplication routine, as well as
torch.nn.functional.conv2d, which performs convolution operations. Additionally, Intel offers a tutorial on
leveraging PyTorch with AMX for accelerating the training and inference of neural networks in (Intel Corporation
2024a).
Before diving into this topic, however, we will establish a baseline for comparison by demonstrating how to use
PyTorch v2.5.1 to perform matrix multiplication with AMX technology at https://github.com/NREL/amx-fp-tests/
blob/v2025-07/notebooks/matmul_pytorch.ipynb. We apply the same matrix multiplication example with Tensor-
Flow v2.18.0 accelerated by AMX in https://github.com/NREL/amx-fp-tests/blob/v2025-07/notebooks/matmul_
tensorflow.ipynb.

4.1 Matrix multiplications
Table 1 summarizes the results obtained with the codes mentioned above. The results represent the best of 30 runs.
At first, one can say the performance of PyTorch and TensorFlow is similar, in terms of orders of magnitude. Matrix
multiplication using BF16 is roughly 1.8x faster than using FP32, which holds true for both the scenarios where
accumulation is done in BF16 and where it is done in FP32. The speedup here is more modest than the 2.75 value
obtained with Intel MKL in Section 3.1, although Intel MKL is the backend for both PyTorch and TensorFlow. In
PyTorch, for example, support to cblas_gemm_bf16bf16f32() was included in 2023 1 .
We could not execute the mixed-precision algorithm (mixed_precision.Policy set to mixed_bfloat16)
with TensorFlow, and we suspect TensorFlow lacks this functionality for the CPU implementation when calling
linalg.matmul() directly. The implementation in FP16 performs similarly to the FP32 one, and that is because
the tests were performed in the Sapphire Rapids architecture, which does not have acceleration for FP16. Finally, the
performance of the FP32 and FP64 implementations in PyTorch do not differ much from its backend (Intel MKL).
TensorFlow’s implementations, however, are significantly slower in our tests, with the FP64 implementation being
more than 2x slower than the one in Intel MKL.

In terms of accuracy, the error for BF16 is eight times larger than FP16. This is the expected behavior since the
mantissa of BF16 is eight times smaller (7 bits) than the one of FP16 (10 bits). When accumulation is performed
in FP32 and multiplications using BF16, the error is similar to the observed with the mixed-precision TRMM in
Section 3.2, and you can compare with figures 3 and 4. The constant value of 2.4 × 10−3 is achieved for two different
matrix multiplication algorithms, and this is something that could be investigated in future work or by a deeper
search in the literature of mixed precision linear algebra algorithms.
Remark 2. We ran the same Python notebooks in a computing node with NVIDIA H100 GPU, and the results are
shown in Table 2. The implementations achieve up to 795 TFLOPS using BF16 only and 366 TFLOPS with accu-
mulation in FP32. Surprisingly, the performance of the FP32 algorithm is lower than that of the FP64 algorithm in
PyTorch. If we consider the FP64 implementation as a reference, using mixed precision can speed up computation by
a factor between 5 and 6. Mind that the performance for BF16 and FP16 are 20% smaller than the reported peak in
(NVIDIA Corporation 2023), and the one for FP64 is only 5% smaller.

algorithm with BF16. Following the example provided by Intel in (Intel Corporation 2024a), we created the

The first example demonstrates how to train a ResNet-50 neural network with mixed precision using the CIFAR10
dataset. We use the mini-batch Stochastic Gradient Descent as optimizer with: batch size of 256, learning rate of
0.001, momentum of 0.9. Those values were taken from (He et al. 2016), where they were used to train a ResNet-50
for the ImageNet dataset. We use cross entropy as loss function. The results show a speedup of 1.70(± 0.02) per
epoch using mixed precision in the first ten epochs. This number is in accordance to the speedup we obtain by just
measuring the matrix multiplications (1.8) in Section 4.1. The average relative difference between the running loss
values was 0.004 (or 0.4% of difference) with lower values in average for the single precision execution, as expected.
The speedup is smaller than the 2.36x reported by Intel at (Intel Corporation 2023). After the tenth epoch, however,
the loss values were 1.289 and 1.278 for single and mixed precision, relatively. A recent study conducted by interns
at NREL suggests that the accuracy loss is also negligible for a larger number of epochs (De Oliveira Silva, Tahmid,
and da Silva Pereira 2024). In comparison, Intel reports an accuracy loss of less than 2% for the training of a BERT
deep learning model (Intel Corporation 2023).
For inference, we use the DEFAULT weights from PyTorch v2.5.1, which classifies images according to the ImageNet
1000 image classes (Deng et al. 2009). Each evaluation set, or batch, consists of perturbations of images of kites
and macaws using Gaussian noise, rotation, reflection, color jitter, and affine transformations. Figure 5 illustrates
the speedup achieved by using mixed precision during the inference of a ResNet-50. On the x-axis, we vary the size
of the set used for inference. As the number of samples increases, so does the speedup of the mixed-precision code.
Enabling mixed precision with Intel AMX can provide a speedup of 2x when evaluating at least 16 samples simulta-
neously. The speedup remains between 2 and 3 with high confidence for larger batches, which is in accordance with
the 2.8x speedup reported at (Intel Corporation 2023) obtained for a batch of 1000. Figure 6 shows how one should
expect little deviations in the predicted classes by the use of mixed precision. In this example, the maximum top-1
and top-5 errors relative to the batch size were both equal to 0.625%.

5 Conclusions
This report shows how to use the BF16 data type on Intel CPUs with the AMX technology available on the Kestrel
HPC system at the National Renewable Energy Laboratory. We adopt a bottom-up strategy, covering: (1) the low-
level C++ API for the TMUL kernel, (2) the Intel MKL API for mixed-precision operations, (3) an example of using
Intel MKL mixed precision for a triangular matrix multiplication algorithm, (4) the application of mixed precision in
PyTorch and TensorFlow for matrix multiplications, and (5) the utilization of mixed precision in PyTorch for infer-
ence and training of neural networks. We believe these examples will serve as a source of motivation and guidance,
helping readers develop their own applications using mixed precision to achieve improved performance.

From the results presented, we can draw a few conclusions for the fourth generation of Intel Xeon processors:
 • Both single-core and multicore peak performances of the mixed-precision matrix multiplication are approxi-
 mately 2.75x faster than their FP32 matrix multiplication counterparts.
 • The mixed-precision triangular matrix multiplication algorithm presented in this report scales very well with
 matrix size, achieving over 1 TFLOPS for sufficiently large matrices. In contrast, the scalability of Intel MKL
 TRMM peaks at 1 TFLOP for matrices of size 1024 and 2048, and remains in the range of 100-500 GFLOPS
 for larger matrices.
 • The performance of our PyTorch and TensorFlow installed libraries with mixed-precision matrix multiplica-
 tions is more modest, offering a speedup of 1.8x in the examples provided.

 • For neural networks, mixed precision provides a speedup of 1.7x for a single epoch of training and 2 to 3x for
 batch inference, both using the ResNet-50 architecture. The 1.7 value is similar to the respective value of 1.8
 obtained for matrix multiplications. The range from 2 to 3x is closely related to the 2.75x speedup obtained
 when using Intel MKL.
More generically, we can add the following conclusions:

 • The Intel AMX accelerator TMUL instruction can be accessed from C++, enabling third-party libraries to
 implement their own algorithms.
 • The errors in the mixed-precision GEMM and TRMM algorithms remain constant at 0.0023 as the matrix
 size increases. A wider literature review followed by an error analysis is needed to verify the observed phe-
 nomenon.

 • TensorFlow v2.18 mixed precision policy implementation seems to lack support for Intel Sapphire Rapids
 when directly using the function linalg.matmul().
