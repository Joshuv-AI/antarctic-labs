Single-Thread JPEG Decoder Benchmarks Mis-Evaluate ML Data Loaders
Vladimir Iglovikov, Dmitry Kosarevsky

Abstract
JPEG decode is routine ML infrastructure, but Python decoder choices are often justified by single-process, single-thread microbenchmarks. We audit this evaluation assumption with thirteen Python-accessible JPEG decode paths on five matched 16 vCPU Google Cloud CPUs: Intel Emerald Rapids, AMD Zen 4, AMD Zen 5, ARM Neoverse V2, and ARM Neoverse N1. ImageNet validation is the workload, not a new dataset contribution: each run decodes the full 50,000-image split from memory and reports single-thread throughput for all decoders, PyTorch DataLoader throughput for eligible decoders at worker counts { 0 , 2 , 4 , 8 } \{0,2,4,8\} , and decoder skip behavior. The evaluation protocol changes the supported conclusion. On Neoverse V2, imageio is ninth in single-thread throughput yet lands in the top DataLoader tier with torchvision ; on Zen 4, torchvision rises from seventh single-thread to the top measured DataLoader tier; on Neoverse N1, imagecodecs is the single-thread leader but fifth at peak DataLoader throughput. We also find that worker-count conclusions differ between Zen 4 and Zen 5, TensorFlow has a large single-thread ARM penalty, and strict native JPEG decoders/wrappers reject the same rare ImageNet JPEG. For PyTorch DataLoader workloads, torchvision and simplejpeg form the strongest measured zero-skip tier: torchvision has the highest mean normalized throughput, while simplejpeg has the highest minimum. OpenCV remains a robust general-purpose fallback above 90% of the platform-local winner on every tested CPU. We release raw JSON, generated tables/figures, and an executable local/cloud benchmark framework.



1
Introduction

Image loading becomes visible when it caps training throughput. When decode cannot feed the learner, GPUs idle, queue depth collapses, and adding model-side compute stops helping. A natural response is to benchmark decoders in a tight loop, choose the fastest images/s number, and move on. That workflow is attractive because single-thread microbenchmarks are cheap, deterministic, and easy to compare.

The problem is that the evaluation design encodes a claim: single-thread decoder throughput identifies the right decoder for training data loaders. That claim is often false. Training pipelines usually pay JPEG decode cost inside a
DataLoader
, with multiple worker processes, batches, Python/C boundary effects, library thread pools, fork behavior, and CPU-specific scheduling. A benchmark that collapses those conditions into one isolated decoder call can support the wrong library choice or hide a robustness policy that matters operationally.

This paper treats the decoder benchmark itself as the object of evaluation. Evaluation practice in ML includes the processes, tools, datasets, benchmarks, and assumptions used to test, compare, and interpret systems. Our contribution is in that category: we compare a common evaluation shortcut against a loader-aware protocol, show where the shortcut fails under loader parallelism, CPU generation, and robustness policy, and ship a runnable framework for evaluating the claim locally and on cloud CPUs.

Results

4.1
Single-thread protocol supports only component speed

Single-thread measurements produce the expected component-speed picture: libjpeg-turbo-family decoders and OpenCV are usually near the top. By mean throughput,
simplejpeg

4.4
Robustness accounting changes operational conclusions

Failure handling is part of the evaluation, not cleanup after the fact. Strict decoders expose the same robustness failure on every platform:
ajpegli
,
jpeg4py
,
kornia-rs
, and
turbojpeg
each skip ImageNet validation index 19876, one image out of 50,000. Their DataLoader results are therefore throughput over 49,999 images, with the skip recorded in JSON. OpenCV, Pillow, scikit-image, imageio, imagecodecs, torchvision, TensorFlow, PyVips, and simplejpeg have zero observed skips in single-thread mode. The shared failure is also an actionable decoder-maintainer test case: adding support or a fallback for this uncommon color-transform/four-channel JPEG case would change a strict decoder’s operational eligibility without changing the benchmark protocol.

TensorFlow is also a named single-thread portability warning. It reaches 689 img/s on Intel and 836 img/s on Zen 5, but only 391 img/s on Neoverse V2 and 268 img/s on Neoverse N1.

5
Discussion

The main lesson is methodological: report the evaluation setting that matches the deployment claim. If the claim is about isolated decoder implementation speed, a single-thread table is appropriate. If the claim is about training input pipelines, the benchmark must include loader parallelism, target CPU information, and decoder failure behavior.

For PyTorch DataLoader workloads in this measured matrix, the recommended tier is:
torchvision
when optimizing for mean normalized throughput;
simplejpeg
when optimizing for the strongest worst-platform floor among zero-skip decoders; and OpenCV as a robust general-purpose fallback with broad non-JPEG image-processing utility. Platform-specific peak chasing should use the full generated tables rather than extrapolating from single-thread results or another CPU generation.

We do not claim a universal fastest decoder, that AMD CPUs generally scale poorly, that ARM is slow for JPEG decode, that TensorFlow is always slow, or that OpenCV is the best measured PyTorch DataLoader default. We also do not claim PyVips is broken or that strict native JPEG decoders/wrappers are wrong. The supported claims are narrower: under this fork-based PyTorch DataLoader harness, PyVips has no loader-scale recommendation; strict decoders need an explicit fallback policy for uncommon JPEG modes;
ajpegli
is an important example of DataLoader scaling but not a zero-skip default in this matrix;
torchvision
and
simplejpeg
form the strongest measured zero-skip tier; and OpenCV is a robust near-optimal fallback.

6
Reproducibility and limitations

The artifact is required to inspect the scientific claim: the paper argues about which evaluation protocol supports which conclusion, so readers must be able to rerun the protocol and regenerate the evidence rather than trust a static table. The public artifact is available at
https://github.com/ternaus/imread_benchmark
. The released package exposes
imread-benchmark list-libs
,
imread-benchmark run
,
imread-benchmark plot
, and
imread-benchmark render-readme
. The cloud path uses scripts to launch benchmark VMs, pull ImageNet from object storage, run the same CLI, upload JSON outputs, cache environments keyed by
uv.lock
, and self-delete the VM. The measurements describe the spring 2026 Python decoder ecosystem captured by the artifact: each raw JSON records Python, OS, CPU metadata, and the exact decoder package version for that run, while
uv.lock
pins the package resolution used by the local and cloud environments.

The supported claims are limited to CPU JPEG bytes-to-RGB decoding under a PyTorch
DataLoader
, ImageNet-val-like JPEG workloads, the measured worker counts, and the five matched 16 vCPU GCP platforms. The results do not claim universal behavior across all image formats, all training systems, TensorFlow-native pipelines, GPU decode paths, storage-format redesigns, or every CPU and NUMA topology.

Image content and encoding can affect absolute decode throughput: resolution, chroma subsampling, quality, progressive encoding, metadata, and color modes all matter. We therefore do not claim rank invariance across image distributions. The narrower claim is that even on a standard RGB JPEG workload, protocol choice changes the supported decoder recommendation. Synthetic RGB JPEGs, 1024
\times
1024 crops, or domain-specific JPEGs can be evaluated with the same artifact; PNG and very large 10000
\times
10000 images are outside this JPEG-focused benchmark claim.

7
Conclusion

Single-thread JPEG decoder benchmarks are useful component measurements, but they are not a valid standalone evaluation protocol for ML training data loaders. Under PyTorch DataLoader, decoder rankings can invert, worker-count choices can interact with CPU generation, and robustness policies can change the practical default. A benchmark that claims to guide training pipelines should therefore report loader-scale throughput, target microarchitecture, and decode-failure behavior together.
