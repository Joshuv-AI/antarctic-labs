 GPU Acceleration in SRW: Design and Considerations

Abstract: Synchrotron Radiation Workshop (SRW) is a powerful tool for simulation synchrotron
radiation emission and propagation through beamline elements, enabling advanced beamline
design and experimental optimization. Recently, GPU acceleration has been developed for SRW
to support highly detailed end-to-end simulations of experiments at synchrotron light sources.
This work documents the design and implementation of this GPU acceleration support,
addressing the complexities of adapting CPU-based components to heterogeneous computing
architectures.

1. Introduction
Synchrotron Radiation Workshop (SRW) [1] code uses electrodynamics based computational methods to
simulate the emission of synchrotron radiation and uses physical optics methods to simulate its
propagation through optical elements. It is commonly used for beamline design at synchrotron light
source facilities around the world. As the demand for access to synchrotron light sources and the
complexity of experiments increases, SRW is well-placed to help improve light source capabilities and
utilization by enabling simulations to be performed faster and enabling significantly more detailed
simulations, considering factors such as the source’s partial coherence, and performing end-to-end
simulations of experiments to more directly evaluate beamline performance.

The integration of GPU acceleration into the Synchrotron Radiation Workshop (SRW) represents a key
step in enabling high-performance simulations of synchrotron light sources. As computational demands
in this field grow, leveraging the parallel processing capabilities of GPUs through CUDA has become
essential for handling complex, large-scale simulations. This work documents the design and
implementation of GPU acceleration support in SRW, addressing the challenges of adapting CPU-based
components to modern heterogeneous computing architectures.

SRW consists of many optical propagators to model elements within beamlines. While many of these
propagators have been successfully ported to CUDA, the process involves navigating intricate trade-offs
between code reuse, performance optimization, and compatibility with existing workflows. This
document explores the design decisions, implementation strategies, and practical considerations that
have underpinned the GPU acceleration of SRW thus far, having supported end-to-end simulations of X-
ray photon correlation spectroscopy (XPCS) [2,3] and Ptychography [4].

2. Design of GPU support in SRW
GPU acceleration in SRW is implemented at the C/C++ level using CUDA, which restricts support to
NVIDIA GPUs but enables leveraging the mature and optimized CUDA ecosystem (e.g., cuBLAS, cuFFT,
and Thrust libraries) [5][6] to accelerate computationally intensive tasks.

To maintain compatibility with existing SRW workflows and deployments, the GPU acceleration module
is designed to use conditional compilation. GPU-related code is excluded from the build process unless
explicitly enabled via a compilation flag, ensuring that CPU-only builds remain unaffected. This approach
preserves the integrity of legacy scripts.

Since not all SRW components are GPU-portable, the design supports hybrid CPU-GPU execution by
allowing seamless integration of CPU- and GPU-accelerated propagators. This requires careful
abstraction of computational kernels, data management, and interface definitions to ensure
interoperability. These design choices collectively shape the architecture, balancing performance gains
with maintainability and backward compatibility.

2.1. Code Structure
SRW is designed with modular architecture, where bindings to higher-level tools (e.g., for Igor Pro or
Python clients) interface with a C++ core responsible for computationally intensive tasks. The core is
organized into multiple C++ source and header files, with optical propagators encapsulated in separate
files for modularity. For CUDA integration, a consistent naming convention was adopted: GPU

implementations of existing functionality are suffixed with _gpu, ensuring clear differentiation from the
rest of SRW.

The CUDA-specific code is carefully integrated into the C++ core using preprocessor directives to manage
compilation context:

 - _OFFLOAD_GPU: Enables GPU-support compilation. Code within this block is excluded from
 CPU-only builds.
 - __CUDA_ARCH__: Indicates code targeting the GPU. This is used to rename functions shared
 between CPU and GPU to avoid symbol conflicts.
 - __CUDACC__: Ensures CUDA-specific code (e.g., kernel definitions in headers) is only compiled
 by NVCC, avoiding compatibility issues with GCC [7].

GPU-ported functions are split into two components:

 - CPU-side routines: These handle memory management and kernel launches. They are marked
 with the _GPU suffix and are members of the class corresponding to the original SRW function.
 - CUDA kernels: These implement the parallelized computation on the GPU. They are suffixed
 with _Kernel and are restricted to their compilation unit.

This separation ensures that GPU code remains decoupled from the CPU codebase while maintaining
interoperability.

2.2. Memory Management
GPUs feature a complex memory hierarchy with distinct memory types (e.g., global, shared, constant,
texture and unified memory) that vary in size, bandwidth, and accessibility [8]. Effective utilization of
these memory layers is critical for optimizing performance, but this requires careful coordination with
C++'s flat memory model, which assumes contiguous, uniform memory access. To bridge this gap, an
auxgpu component was designed to manage GPU-CPU memory interactions, enabling seamless data
transfer, stream management, and synchronization. The auxgpu module provides a comprehensive set
of utilities to handle memory mapping, kernel execution, and data consistency across CPU and GPU. Key
functionalities include:

Memory Allocation & Mapping

T* ToDevice(TGPUUsageArg* arg, T* hostPtr, size_t elemCount, int flags)

 Allocates GPU-accessible memory, optionally mapping it to a host pointer (hostPtr). If
 hostPtr is non-NULL, an asynchronous CPU-to-GPU copy is initiated by default. The
 DONT_COPY flag suppresses this behavior.

 Pinning logic: The host pointer is pinned (registered with CUDA) under the following conditions:

 - PIN_ON_HOST flag is set.
 - The requested memory exceeds 30% of available GPU memory.
 - GPU memory allocation fails.
void Memset(TGPUUsageArg* arg, T* devicePtr, T value, size_t elemCount)

 Fills a GPU-allocated array (devicePtr) with elemCount copies of value.

void EnsureDeviceMemoryReady(TGPUUsageArg* arg, T*… ptrs)

 Ensures all pending GPU operations on the specified pointers are completed before the next
 kernel launch on the default stream.

Data Synchronization & Dependency Management
void MarkUpdated(TGPUUsageArg* arg, void* ptr, int flags)

 Notifies the system that the memory at ptr has been updated.

 HOST flag: Indicates CPU memory has been modified and needs to be copied to the GPU.

 DEVICE flag: Indicates GPU memory has been modified and needs to be copied to the CPU.

T* ToHostAndFree(TGPUUsageArg* arg, T* devicePtr, size_t elemCount)

 Transfers data from GPU to CPU if the memory has been marked as updated. If not, it simply
 frees the GPU memory. Returns the CPU pointer.

T* GetHostPtr(TGPUUsageArg* arg, T* devicePtr)

 Retrieves the corresponding CPU pointer for a given GPU pointer. Returns NULL if no mapping
 exists.
 void SetHostPtr(TGPUUsageArg* arg, void* origPtr, void* newPtr)

 Updates the CPU pointer associated with origPtr to newPtr, copying data if necessary.

Stream Management

long long GetComputeStream(TGPUUsageArg* arg, int idx)

 Retrieves a compute stream object for the specified index.

void SyncComputeStream(TGPUUsageArg* arg, long long targetStreamIdx, long
long waitingStreamIdx)

 Ensures waitingStreamIdx waits for targetStreamIdx to complete before proceeding.

Kernel Launch Configuration

void CalcLaunchDims(T* kern, dim3 grid, dim3& blocks, dim3& threads, int
max_x_bs, int max_bs_total, bool warpMultiple)

 Computes optimal kernel launch dimensions (blocks and threads) based on:

 grid: Desired grid dimensions.

 max_x_bs: Maximum number of threads per block in the X dimension (optional).

 max_bs_total: Maximum total threads per block (optional).

 warpMultiple: If true, ensures the thread count is a multiple of the GPU warp size (32)
 (optional).

These utilities are integrated into the GPU-accelerated functions (with the _GPU suffix) to manage
memory dependencies, ensure data consistency, and optimize kernel execution. The TGPUUsageArg
argument serves as a context object, encapsulating state and configuration for the GPU operations.

2.4. Compilation
SRW supports GPU-enabled builds using both Makefile-based and CMake-based workflows. To enable
GPU support in a Makefile-based build, set the MODE variable to CUDA and specify the following
environment variables:

 • CUDA_PATH: Path to the CUDA Toolkit installation (e.g., /usr/local/cuda). This directory
 must contain the nvcc compiler executable.

 • CUDA_MATHLIBS_PATH: Path to the directory containing CUDA math libraries (e.g., cufft).

The build process proceeds as follows:

 1. CPU Code: All non-GPU source files are compiled using the standard C/C++ compiler (e.g., gcc
 or g++).

 2. CUDA Code: CUDA source files are compiled using nvcc with separable compilation, which
 generates device code object files.

 3. Linking: The compiled CPU object files and CUDA device code are linked into a single shared
 library.

In a CMake-based build, GPU support is enabled by setting the USE_CUDA option to ON. CMake typically
auto-detects the CUDA Toolkit installation, but manual configuration is possible by setting the
CUDAToolkit_ROOT variable to the path of the CUDA Toolkit [9]. The CMake build process follows a
similar build process as the Makefile-based build.

3. Design factors when porting functionality from CPU to GPU
When porting SRW code from CPU to GPU, several design considerations are critical to ensure efficient
GPU utilization, maintain numerical precision, and simplify code maintenance.

3.1. Function Specialization using templating
GPU architectures are highly sensitive to branch divergence (where threads in a warp take different
execution paths), which can significantly degrade performance. To mitigate this, CUDA/C++ templates
can be used to precompute and specialize kernels for some critical parameter combinations, reducing
runtime branching and allowing the compiler to optimize each specialization.

3.2. Memory Usage – Pinning vs Copying
Two primary strategies are used for efficient data access via the GPU. A portion of dedicated GPU
memory can be allocated, and an explicit copy of the corresponding CPU memory is maintained. This is
limited by the amount of dedicated GPU memory available and has the overhead of a CPU-to-GPU
memory copy at the beginning and a GPU-to-CPU copy to retrieve results. Alternatively, page-locked
CPU memory can be used. Virtual memory pages on the CPU in which the data resides are ‘pinned’,
enabling the GPU to directly access this memory without requiring any copying. However, access to
pinned memory is slower than to dedicated GPU memory, but there is no overhead of copying a large
amount of data back-and-forth.

The auxgpu component in SRW is designed to automatically balance between these two strategies
based on workload characteristics like GPU memory size and source data size. However, manual
intervention may be necessary in specific scenarios to optimize performance.

One such example is of ExtractRadSliceConstE, where a single 2D slice of data is extracted from a
large 3D volume, and the full volume is not expected to be accessed for proceeding calculations. Explicit
copying may be inefficient, as transferring the entire 3D volume may either not be possible – if the size
is larger than available GPU memory – or copying all the data may take longer than just directly reading
the required subset using pinned memory [10].

3.3. Floating Point Precision
Scientific computation codes must maintain a careful balance between speed and accuracy. SRW
calculations involve floating point numbers spanning many orders of magnitudes, which can pose a
challenge for maintaining floating point precision while preventing accumulation of errors. Additionally,
parallelized algorithms can have different orders of floating-point operations, changing precision
compared to the sequential equivalent.

GPU-based calculations were sometimes found to be more precise than the original CPU
implementations due to elimination of error accumulation for coordinate calculations and aggressive
use of Fused Multiply-Add (FMA) operations by the CUDA compiler [11]. FMA implements 𝑥𝑥 = 𝑎𝑎 + (𝑏𝑏 ∗
𝑐𝑐) as one instruction, rounding the result only once, achieving higher performance and precision than
using separate multiplication and addition instructions. While FMA instructions are generated by default
for CUDA code, they may not be generated by default for CPU-builds. The effect of explicitly enabling
FMA instructions for CPU-builds needs further investigation [12].

what might be encountered in SRW, and a coordinate dependent transformation is applied to each

3.4. Increasing Code Reuse
Reimplementing SRW components into CUDA introduces significant code duplication, which increases
maintenance complexity. However, many core SRW helper functions are inherently platform-agnostic,
making them ideal candidates for reuse between implementations. CUDA enables this with ‘__host__

__device__’ decorators [13], which allows the function to be compiled for both CPU and GPU. SRW
employs the ‘GPU_PORTABLE’ macro as a shorthand for these decorators.

A challenge arises from the frequent use of virtual function calls in SRW’s ‘TraverseRadZXE’
mechanism. This iterates over the simulation grid and calls the propagator’s implementation of the
virtual function ‘RadPointModifier’ for each point. While porting RadPointModifier to CUDA
often seems straightforward (by applying the GPU_PORTABLE decorator) to it, CUDA cannot resolve
virtual function calls at runtime due to its lack of dynamic dispatch support for objects created on CPU.

To address this, SRW introduces the RadPointModifierParallel function, a virtual function with a
default implementation that returns −1. This indicates that the optical propagator does not support
GPU execution, and CPU-based processing should be used.

specialized GPU-implementation of TraverseRadZXE tailored to the optical propagator.
RadPointModifierParallel also acts as an optimal location to prepare any additional memory
dependencies of the corresponding RadPointModifier.

The RadPointModifierParallelImpl function causes kernel specialization and configures the
kernel launch. A key optimization has been introduced for optical propagators like apertures, where the
subset of the wavefront that will be modified can be trivially determined. For example, an aperture
larger than the wavefront can skip processing all points, as they are unaffected. This optimization
reduces unnecessary computation and improves performance by avoiding redundant kernel launches.

3.5. Batch Processing
When GPU kernels perform minimal computation per thread (e.g., simple arithmetic or data access), the
overhead of thread management and memory latency can dominate execution time. To mitigate this,
batch processing is employed, where each thread processes multiple data points in a single invocation.
This increases instruction-level parallelism and reduces the per-thread overhead, leading to better GPU
utilization. Code listing 7 shows how batch processing is used to improve the performance of the GPU
implementation of IntegrateOverX.
Code Listing 7. CUDA implementation of IntegrateOverX (cpp/src/core/srmatsta_gpu.cu) [16]

3.7. Parallel Kernel Execution
GPU utilization can be further enhanced by executing multiple kernels concurrently. For example,
functions that perform identical operations independently on separate data (e.g., transverse wavefront
components) can be split into separate kernels, enabling parallel execution. This design utilizes stream-
based concurrency in CUDA [14], where work is partitioned into asynchronous tasks, improving memory
access patterns, allowing the compiler to optimize kernel execution more effectively, and leveraging idle
GPU compute units by distributing workloads.

A typical example is the CUDA implementation of RadResizeCore, where the X and Z components of
the wavefront are resized in parallel. The SyncComputeStream call on line 33 ensures both kernels
execute after prior operations in the default stream complete. The X-component resize is launched on
the default stream, while the Z-component resize is executed on a second stream. Finally, a subsequent
SyncComputeStream call on line 38 ensures that all subsequent operations on the default stream wait
for the Z-component resize to finish.

The analogy to multiprocessing is not exact, but the SyncComputeStream calls act as synchronization
points to enforce ordering constraints, ensuring correctness while maximizing parallelism.

Conclusion & Future Steps
Adding GPU acceleration to SRW is an important step for enabling more sophisticated simulations to be
performed, which can further contribute to advancing synchrotron radiation exploiting science in many
ways. We documented the detailed design of SRW’s GPU acceleration support and discussed with
examples, the different factors that influence the CUDA implementations of various components. These
should be a useful guide for future CUDA ports, not only for SRW, but also for other scientific computing
codes.

While many of the most used optical propagators in SRW have received CUDA implementations, there
are still more propagators to port over, and new ones to implement on both CPU and GPU.
Furthermore, there is room for improvement in understanding of factors such as management of
floating-point precision to ensure that results on both CPU and GPU minimize floating point error, and

the potential of using profile-guided optimization during compilation to further improve performance
[15].
