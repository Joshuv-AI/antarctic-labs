$ Introduction to Evaluations

One of the most fundamental quantities in nuclear physics is the reaction cross section. A cross
section represents the probability that a nuclear reaction will resolve through a given channel given
a target nucleus and a projectile with a certain energy. A nuclear evaluation is a set of discrete
data and interpolation rules to convert those discrete nuclear reaction data—such as the cross
section—into a continuous function at arbitrary energies. Evaluated nuclear data ’les that can
appear in Evaluated Nuclear Data File (ENDF; [$]) and Generalized Nuclear Data Structure (GNDS;
[#]) formats, storing a “most-complete” discretized representation of nuclear data, based on both
experimental measurements and theory models.

A complete evaluation for a projectile-target combination—a “protare” (portmanteau of PROjectile
TARget Evaluation)—is given as a multivariate normal distribution, which consists of cross section
data (the “mean” of the evaluated data) and covariance data (the uncertainty on the evaluated
data). The covariance matrix for a cross section describes the relationship between projectiles
at different energies. Figure $ shows a covariance matrix for reaction channels in the n+#!) Pu
reaction as an example. Essentially, the covariance matrix describes how the cross section should
vary across energies. If the cross section at one energy is varied, then the neighboring cross section
points vary according to the off-diagonals of the matrix. The goal of the Evaluations with Means
and Uncertainties—EMU—software is to generate realizations of nuclear reaction cross sections by
sampling from the covariance data so that uncertainties from the cross section (and other reaction

! EMU implementation at a glance
Given a GNDS reaction suite (the evaluated mean data) and an associated covariance suite, EMU
constructs a new GNDS realization style by perturbing evaluated quantities in a way that is con-
sistent with the covariance structure. In practice, EMU has two options for generating these real-
izations: stochastic or systematic. In stochastic studies, EMU samples correlated Gaussian pertur-
bations and produces randomized realizations. In systematic studies, EMU applies deterministic
perturbations (e.g., multiples of standard deviations or constant fractional scalings) to probe sen-
sitivity. In both cases, EMU must reconcile mismatched grids between mean data and covariance
data, preserve internal relationships such as derived/summed channels, and enforce basic physi-
cal constraints (e.g., nonnegativity). For this discussion, we will focus on the mathematics behind
stochastic sampling.

To make matters more complicated, cross sections can be stored in ENDF/GNDS as a mixture
between direct and sum types. For example, a total cross section may have been measured by
an experiment within a certain energy range, producing an evaluation following the expression in
Eqn. $. If individual cross section channels were evaluated in another energy range, then the total
cross section would be stored according to Eqn. $8 for those energies. Keep this in mind as cross
section sums and mixed types have special handling in EMU.
The same reaction channel may have energy regions which are derived and others which are not.
For these “mixed” reaction channel types, EMU breaks the covariance matrix into its mixed and
summed types and performs a proportional back-propagation into summands for coherent sums
after sampling in the energy region(s) for which the cross section is a derived type. The regions
which are not derived are sampled normally, and the realization stitches the mixed types together
again.
Short-range self-scaling interactions exist in some “multigroup” evaluations. Such interactions
were added to ensure that the total cross section does not change upon drawing new realizations.
However, EMU is structured to account for preservation of the total cross section, and short-range
self-scaling interactions are therefore ignored.

".$ Accessing on Livermore Computing (LC)
EMU exists within a ’xed Python! environment that has tested versions of EMU dependencies (e.g.,
FUDGE) installed alongside EMU. You must be a member of the emu-users UNIX group on the LC
enclave (CZ, RZ, SCF) you will be using. You can request this role by navigating to lc-idm.llnl.
gov, then selecting “Start New Request” or “Request,” and “Add Account Roles” under “Manage
Account.” Once permission is granted, start a new LC session to update your groups.
To activate the EMU Python environment, run: source /usr/gapps/emu/activate. This command
activates the most recent, stable version of EMU.# To deactivate the environment, run: source
/usr/gapps/EMU/deactivate.

".! Local installation
Installing EMU into your own private environment is relatively straightforward. If you are start-
ing from scratch, EMU includes conda environment con’g ’les that will help install all of EMU’s
dependences—including FUDGE—for you! You can start by cloning the EMU repository and enter-
ing the cloned folder:
$ git clone https :// lc . llnl . gov / gitlab / nuclear / EMU / emu
$ cd emu

From there, use the YAML ’les in the emu/conda folder to set up your environment with EMU’s de-
pendencies:
$ conda env create -f conda / user . yaml -n < env_name >
$ conda activate < env_name >
$ pip install .

where <env_name> should be replaced by a unique name for your new conda environment.
EMU depends upon a smaller version of itself called emu_graph. This code is installed in the same
way:
( < env_name >) $ git clone https :// lc . llnl . gov / gitlab / nuclear / EMU / emu_graph
( < env_name >) $ cd emu_graph
( < env_name >) $ pip install .

Lastly, initialize EMU with
( < env_name >) $ emu init

This creates a private environment with EMU and FUDGE installed, and you are ready to go!

%.’ study
The most-used command in EMU is study, which is the command to actually generate data varia-
tions. Within emu study are four options:
 • diag gnds -j
 • setup
 • run
 • process
The ’rst command on this list, emu study diag, is an optional diagnostic tool that can be called
on the evaluated ’les that the user would like to generate variations for. Speci’cally, the diag
command will check if a protare has covariance matrices that can be sampled by EMU. This tool is
still in development and only works with the gnds and -j options, the ’rst of which speci’es that
the evaluation library is formatted in GNDS, and the second to print the output to the terminal in
JSON format. Other input and output formats are currently being developed.
The ’rst command in a production study is emu study setup, which initializes the study by reading
the control ’le and ’nding which reaction channels can be varied. Next, emu study run creates
the variations and launches the code to process the data using PROTEA. Although emu study run
automatically launches processing by default, it can also be launched manually with emu study
process, e.g., if the processing step was disabled during run.

’ Running a basic EMU study
The only input EMU needs is a control ’le formatted in YAML: a human-readable format for informa-
tion storage consisting of keys and values. The entire EMU study occurs in a two-step process:
  $. emu study setup <my_study>.yaml
  #. emu study run <my_study>.yaml
where <my_study> should be replaced by the name of a user-created control ’le. The ’rst command—
emu study setup—initializes the study by reading the control ’le and ’nding which reaction chan-
nels can be varied. The second command—emu study run—creates the variations and launches
the code to process the data using PROTEA. Note that due to how resources are allocated, emu
study run should not be launched with a SLURM (or equivalent) script if processing is to be done.
In this case, the resources required by the processing step will not be allocated correctly, and the
processing script will fail.

’.$.$ Basic con(guration

The minimum con’guration needed for an EMU study is what evaluation to use, where to store the
variations, what type of study (stochastic or systematic), and—if stochastic—how many samples
to draw. In order, these options are dictated with
 • source / source map / map / map path
 • study type / type
 • number of samples / n samples / num
The ’rst line of the control ’le, source, indicates the evaluation library to start from. To see the
available options, run:
$ emu config aliases

You may pass the alias, the whole library path, or the path to a custom map ’le to source. The next
line, study type, tells EMU which type of study to run: stochastic (random samples) or systematic
(fraction/percentage of the mean or number of sigmas from the mean). If stochastic is chosen,
the next line, number of samples, will tell EMU how many random samples to draw. If systematic
is chosen, number of samples will be ignored.
There are a few more options that can be set in this ’rst block:
 • workspace / output (default: emu-workspace)
 • seed (default: None)
 • variations prefix / prefix / directory prefix (default: None)
 • clip (default: true)
 • reject (default: false)
Next, the workspace key sets the directory where this study will be organized. EMU will write all ’les
required to fully describe the study to this directory, including the processed ’les. The workspace
option can be relative (as shown here) or absolute. If the workspace already exists, EMU will prompt
the user for whether the directory should be over-written or not, though this can also be controlled
by command-line arguments passed to emu study setup, described in the next section.
A value for the random seed to use can be passed to seed for stochastic studies to initialize the
random variable. If none is set, one will be chosen by EMU automatically. Next, variations prefix
is an optional pre’x that can be prepended to each of these directory names with the “variations
prefix” key, resulting in, e.g, “prefix0,” “prefix1,” etc. By default, stochastic variations will be
stored under integer-named directories, e.g., “0,” “1,” etc. For some codes and ’le systems, this type

rors. The clip option de’nes whether to clip values in the cross section realization that go negative.
By virtue of the covariances being expressed with multivariate Gaussian statistics, it is possible for
the cross section to go negative unphysically. This option sets such values to ". Alternatively, the
user may wish to reject any realization where at least one cross section point goes negative. In this
case, the reject option *ags EMU to resample. In practice, it is not advised to use reject: true,
as this option may produce distributions of realizations that are inconsistent with the covariance
matrix and thus arti’cially low uncertainties.

’.$.! processing

Once EMU generates cross-section realizations from the evaluated data, the data need to be pro-
cessed before they can be used in a transport problem. The next block of options (processing)
de’nes options for this processing step of EMU. Processing is handled by the FUDGE nuclear data
processing code, and is managed by maestro-workflow that submits jobs to your LC queue. The
processing block is where typical information required for submitting jobs to LC/HPC is indicated.
Although the processing step may be bypassed, this block must still be present in the study con-
trol ’le. A future version of EMU may automatically skip processing if this block is not present. At
minimum, the processing block requires

 • workspace / output
 • queue / partition

The value passed to workspace is the subdirectory which will launch and store PROTEA output. This
workspace will be placed within the overall study’s workspace, study-workspace/processing-workspace,
in this example. Processing jobs are launched with a SLURM script, the queue indicates which par-
tition to use.

Other options that can be passed to processing are

 • runtime / walltime
 • bank / account
 • processes / concurrency / concurrent jobs / single job concurrency

The runtime option speci’es the maximum run time for each SLURM job. If left black, runtime
will be dynamically determined based on the LC machine to which the jobs have been sent. It is
strongly advised that the user veri’es the job limits for the requested queue. Note that processing
may take longer than one hour per protare, and therefore common debug queues are insuf’cient.

Next, the bank option indicates what account is to be used for the SLURM script. If left blank this
information will also be determined dynamically by EMU based on the current user and machine.

Lastly, processes or concurrency refers to the parallelization option “singleJobConcurrency” in
PROTEA. It is advised that this value should be set to the number of temperatures in each protare,
as PROTEA will heat every zero-temperature EMU realization to these temperatures. As with the
previous two options, EMU can also determine this value in the setup phase by checking the number
of temperature points in the ’rst protare in the evaluation. For ENDF/B-VIII.$, this value is typically
#!.

’.$." protares

The last block, protares, is the list of projectile-targets that EMU will vary. The minimum information
required for an emu study is
 • target
which speci’es the reaction target for which the user would like the nuclear data to be varied. The
target may instead be expressed as any combination of chemical symbol and atomic mass, e.g.,
“Pu#!),” “#!)pu,” “pu-#!),” “Pu-#!),” etc.
There are multiple options that can be passed to protares, and each entry in this block represents
a dictionary with multiple entries.
 • projectile (default: n)
 • channels (default: all channels)
 • ignored channels (default: None)
 • exclude angular (default: false)
 • exclude resonances (default: false)
 • exclude pfns (default: false)
 • exclude cross channels (default: false)
 • sigma (systematic studies only) (default: [$.", #.", !."])
 • fractional (systematic studies only) (default: None)
At minimum, the target must be speci’ed, and the user may also specify the projectile. However,
if no projectile is speci’ed, a neutron will be used by default. (In many existing evaluation libraries,
the covariances for neutron-induced reactions are the most complete.)
By default, all reaction channels that have a covariance matrix in the evaluation will be varied.
(The only exception is if a systematic study is being run, where EMU uses “fractional” sampling if
a covariance matrix is not found.) The user may, however, specify only certain channels to vary
by passing the channel labels to channels. On the other hand, the user may want to skip some
channels, and these can be speci’ed by ignored channels. In both cases, the reaction label is
used instead of, e.g., the ENDF MT numbers. Channels can also be removed in a later step, before
the EMU study is launched. This will be discussed below.
By default, EMU will vary the cross section, angular distributions, PFNS, and resolved resonance pa-
rameters, if covariance matrices exist for these quantities. For some nuclear data, there may also
be covariances between different channels for these data, most commonly for cross sections. The
user may want to skip varying some of the non-cross section data or skip the use of cross-channel
covariances. For such *exibility, the exclude angular, exclude resonances, exclude pfns, and
exclude cross channels can be used. Note that EMU is not capable of not varying the cross sec-
tion.
Lastly, the sigma and fractional keys are used in systematic studies to specify how many standard
deviations or by what multiplicative factor to vary the data.
The order in which these components is listed is not important, as long as the ’rst entry is speci’ed
with “–” and the following entries for that protare are properly indented, for example:

- target: pu239
  projectile: n

 $&

  ignored channels:
 - (z , n )
 - total

The target and projectile lines can also be directly replaced by the reaction itself, in which case
the projectile must be ’rst: [projectile] + [target], e.g., n + Pu239:

  n + 239 Pu:
 channels:
 - 240 Pu + photon

Note that in YAML format, spacing is meaningful; “channels” is a key in the dictionary of “n +
239Pu.”

By default, if neither sigma nor fractional are declared in the systematic study ’le, a list of $.", #.",
and !." will be passed to sigma by default, assuming the covariance suite exists for the protare.
If no covariances are present, fractional may be used instead, though no values are chosen by
default in this case.

’.! Setup
After the user creates their yaml control ’le, the ’rst step of running EMU is the setup phase. In this
step, EMU will initialize the study and create some relevant study directories and ’les to use later.
The only required input to emu study setup is the study ’le.
If emu study setup <my_study>.yaml ran smoothly, then there will now be a directory with the
name speci’ed by “workspace” in the study ’le: in this example, “study-workspace.” Within this di-
rectory will be a single ’le named “study.yaml.” This ’le is an expanded version of <my_study>.yaml

 $6

and is discussed next. The user may edit the study.yaml ’le to customize their study, e.g., by re-
moving channels that the user does not want varied. It is highly encouraged to check this ’le before
proceeding.
There are also some command-line options for emu study setup to handle the case that EMU is
being called on the same input control ’le:
$ emu study setup < my_study >. yaml -- remove
$ emu study setup < my_study >. yaml -- overwrite

Both options can be used if the workspace already exists. The --remove option removes the ex-

other ’les in place. If the workspace exists but neither option has been set, then EMU will prompt
the user for a yes/no input on the command line.

’." Run
After running emu study setup <my_study>.yaml and checking the created <workspace>/study.yaml
’le, the study is ’nally launched with
$ emu study run < my_study >. yaml

Note that the ’le <my_study>.yaml is still called rather than the potentially edited <workspace>/study.yaml.
Rather than call emu study setup <my_study>.yaml and emu study run <my_study>.yaml suc-
cessively, the user may alternatively execute only emu study run <my_study>.yaml. This optional
invocation will run EMU completely with default options. Although convenient, is not advised to use
EMU this way.
There are also some command-line options for emu study run:

 $8

$ emu study run < my_study >. yaml - sp -d

The -sp or --skip-processing *ag tells EMU to skip the processing step. If emu study run is
launched from a SLURM script without the -sp *ag, the resources required by the processing
step may not be allocated correctly if the number of cores requested is less than that declared
by processes in the processing block of the study ’le. Alternatively, the sampling itself can be run
from either SLURM or the command line with the -sp or --skip-processing *ag, but the user will
have to call the processLib script manually. The -d or --dump *ag will optionally store a sampled
version of the variations to an .h& ’le in the user-speci’ed <workspace> directory. This option in-
creases runtime by about a factor of two but makes for convenient visualization of the variations
later. By default, variations are not saved unless this *ag is set.

’.".$ processing

If everything went well after emu study run and the -sp *ag was not used, then the processing
script should now be activated. This script lives in the workspace de’ned by the processing:
workspace option in the study ’le (“processing-workspace” in the example above). A script called
“run_process_lib.sh” will be created in a protea/ directory in the processing workspace. The op-
tions passed to the processing block in the study ’le are used to con’gure this SLURM script.
After EMU ’nishes sampling, this script is executed, and PROTEA will run in the background in this
directory.

After the processing script completes, the processed variations will be copied into their respective
variations folders within the study workspace. Currently, no noti’cation is passed to the user to
indicate completion of processing. Once ’nished, there will now be both “raw” and processed
variations stored in separate directories in <workspace>/variations, where <workspace> is the
name of the directory passed to the “workspace” key in the study ’le. In addition, there is a ’le with
a long hash name also ending in “.raw.xml.” This ’le is a symbolic link to <protare>.raw.xml, and
the name is a unique string given to that ’le. The processing script requires unique names; in other
words, several variations that all have the same name of “n-Pu239.raw.xml” will cause problems
for the script. Therefore, these hash names allow the processing script to run by generating unique
aliases for each variation. These symbolic link ’les can be ignored by the user once the processing
script has completed. If -sp was passed to emu study run, then only the raw ’les will exist in the
variations directory. The processing script can be launched post-facto with emu study process
<my_study>.yaml.

etc. In the systematic example from §&.$.%, a ↑#-ω variation to the 239 Pu(n,#n) reaction rate will ap-
pear in the directory “2n_plus_Pu238_plus_photon_-2.00sigma” within “study-workspace/variations/.”
