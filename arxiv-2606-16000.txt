GRACE-DS: a Guarded Reward-guided Agent Correction Environment in Data Science
Aleksandr Tsymbalov, Danis Zaripov, Artem Epifanov, Anastasiya Palienko

Abstract
We introduce GRACE-DS, a Guarded Reward-guided Agent Correction Environment in Data Science 1 1 1 The code is public and available here: https://github.com/Alexx221x/GRACE-DS for pre-deployment evaluation of LLM-powered AutoML agents. GRACE-DS is a set of evaluation metrics in an isolated environment that can be applied to tabular ML tasks specific to a particular organization. It exposes agents to realistic workflow stages, from planning and data inspection through feature engineering, model development, validation, and code repair to final submission, while hidden executable validators measure not only final predictive performance but also leakage avoidance, reproducibility, protocol validity, correction behavior, and reward alignment. The strongest structured regime, flexible-iterative interaction (ours ), achieves higher end-to-end normalized hidden-test quality than single-shot generation, the unstructured-agent , and restart-based baselines, while also improving protocol-valid completion. Validated across more than 7,000 episodes, these results establish GRACE-DS as a robust platform for assessing the capacity of LLM-based AutoML agents to execute machine learning workflows under production-like conditions and in accordance with organization-specific requirements.



1
Introduction

Organizations are beginning to evaluate LLM-powered agents not only as coding assistants, but as potential participants in data-science and machine-learning workflows
2
. In an enterprise setting, such agents may be asked to inspect internal datasets, propose modeling strategies, engineer features, train predictive models, debug failures, compare candidates, and produce deployable artifacts. This creates a practical pre-deployment problem: a company does not merely need to know whether an agent performs well on a public leaderboard. It needs to know whether the agent can solve the company’s own ML tasks, data, environment, while respecting governance, privacy, reproducibility, and validation constraints
14
.

This problem is especially important for tabular ML, which remains central to many industrial applications: churn prediction, risk scoring, demand forecasting, fraud detection, etc. These tasks often use sensitive production data and domain-specific feature spaces. Sending such data to public benchmark infrastructure is usually impossible, and evaluating agents only on public datasets can give a misleading estimate of deployment readiness. A model that performs well on external benchmarks may still fail when faced with messy internal schemas, unstable data distributions, organization-specific validation rules, protected columns, leakage risks, or strict reproducibility requirements.

Existing benchmarks (Section
2
) for ML agents and data-science code generation provide valuable measures of general capability, but they are not sufficient as enterprise deployment gates. Final-score benchmarks can tell whether an agent obtained a good result, but they often do not reveal how the result was obtained. This is a serious limitation in production ML. An agent may improve a metric by leaking target information, tuning against validation labels, accessing protected files, hard-coding dataset-specific assumptions, producing non-reproducible code, or generating a pipeline that cannot be rerun on future data. On the other hand, an agent may fail not because it lacks modeling ability, but because it cannot recover from execution errors, interpret validation feedback, or revise an earlier workflow decision. For companies, these distinctions matter operationally: the relevant question is not only what score the agent obtained but also whether the process that produced that score can be trusted.

GRACE-DS addresses this gap with a controlled evaluation harness that runs around tabular ML tasks inside an organization’s own environment. Instead of treating the evaluation as a single final submission, GRACE-DS structures the agent’s interaction with the task as an iterative workflow. Agents can plan, inspect data, engineer features, train models, validate candidates, repair code, and submit a final predictor. At each stage, hidden executable validators assess not only predictive progress but also process reliability: whether the agent avoids leakage, follows valid validation practices, produces reproducible code, respects protected data boundaries, and corrects errors after feedback.

The key design principle behind GRACE-DS is that enterprise evaluation of AutoML agents must measure correction behavior under constraints. In real ML work, the first attempt is rarely the final solution. Analysts and ML engineers inspect data, revise assumptions, fix code, compare models, and improve pipelines over several iterations. An LLM AutoML agent should therefore be evaluated not only by whether it can generate a plausible model in one shot, but by whether it can use feedback to improve while remaining within methodological and operational boundaries. GRACE-DS makes this measurable by combining hidden validation, process-level reward, workflow-stage instrumentation, and final held-out scoring.

GRACE-DS differs from final-score-only evaluations in several ways: (i) separates evaluator-owned validation from agent-visible data: agents may receive feedback, but they do not receive private validation labels or hidden test targets; (ii) requires final submissions to be reproducible on raw input data, ensuring that an agent produces a reusable prediction artifact rather than a script tied to one static file; (iii) records process-level diagnostics, including validation improvement, reward decomposition, terminal-path reliability, protocol violations, critical errors, recovery behavior, runtime, iteration count, and cost-related measures; (iv) supports stress tests such as reward-optimization prompts and red-team prompts, allowing organizations to examine whether an agent is robust to incentives that may produce superficially valid but substantively poor solutions.

GRACE-DS supports several industrial scenarios: comparing LLMs on internal ML tasks, deciding whether an AutoML agent is ready to be connected to production data sources, detecting leakage-prone behavior and invalid validation patterns before deployment, and comparing workflow designs, feedback policies, and operating budgets for an internal data-science copilot. In each case the purpose is not a public leaderboard score, but a deployment decision under company-specific constraints.

We evaluate GRACE-DS across multiple LLM families, model sizes, tabular datasets, workflow regimes, ablations, reward-optimization settings, and red-team conditions. The results show that structured flexible iteration provides the strongest end-to-end performance among the evaluated regimes. In the merged experiments, the
flexible-iterative
regime reaches an end-to-end normalized hidden-test quality of
0.754
, compared with 0.536 for
single-shot
generation, 0.527 for the
unstructured-agent
, 0.672 for
restarts-from-scratch
, and 0.686 for a call-matched restart upper bound. The structured regime also improves protocol-valid completion, indicating that the benefit is not limited to successful runs but extends to the reliability of the whole agent loop.

GRACE-DS does not rely on a single final score or a single safety check, it combines hidden process validators, reward-guided correction, and isolated held-out evaluation in one controlled workflow. The validators blocked every deployment-critical failure mode attempted in our red-team prompt suite — no target leakage, evaluator-private access, snapshot tampering, or forbidden-action attempts were observed — while the hidden test still exposed the resulting quality loss, though this prompt suite is not an exhaustive adversarial audit. The agent must therefore be safe, reproducible, protocol-compliant, and effective on held-out production-like tasks before deployment.

2
Related Work

LLM-powered agents are increasingly evaluated in settings that require tool use, code execution, and iterative debugging. Data-science and ML workflows are a particularly important case because success depends not only on generating executable code, but on following a valid modeling process: inspecting data, avoiding leakage, choosing appropriate validation, etc. Existing benchmarks have made substantial progress on these capabilities, but most emphasize final task performance, code correctness, or broad research-style experimentation. GRACE-DS targets a complementary problem: pre-deployment evaluation of LLM-powered AutoML agents on production-like tabular workflows, where organizations must verify both predictive performance and process reliability before allowing agents to operate on internal data.

2.1
Executable data-science benchmarks

DS-1000
15
and DS-Bench
13
evaluate code generation for realistic data-science problems through executable tests, and DA-Code
10
and DataSciBench
27
extend this to broader agent-style data-wrangling, EDA, and ML prompts, including settings with uncertain or non-unique ground truth. These benchmarks made executable data-science evaluation measurable and reproducible, but they do not capture the workflow structure of production ML — iteration through planning, EDA, feature engineering, validation, correction, and submission, or methodological failures such as target leakage and non-reproducible artifacts. GRACE-DS builds on the executable-evaluation tradition but shifts the unit of evaluation from isolated code snippets to an interactive tabular ML workflow.

2.2
Final-score and competition-style benchmarks

MLE-bench
2
evaluates ML agents on a large set of Kaggle competitions and offers a realistic measure of broad ML engineering ability. TML-Bench
21
is closer to GRACE-DS in domain, focusing on tabular ML competitions with hidden-label private-holdout scoring. The limitation of final-score benchmarks is that they reveal little about how a score was obtained: a high score may rest on leakage, invalid validation, or brittle code, while a low score may reflect poor error recovery rather than weak modeling knowledge. GRACE-DS retains hidden final-test evaluation but adds workflow-stage instrumentation, hidden process validators, reward decomposition, error statistics, and reproducibility checks — less broad and less competition-oriented, but more diagnostic for enterprise pre-deployment decisions.

2.3

18

19

but makes a different trade-off
: instead of maximizing task breadth, it narrows the scope to tabular supervised ML and governs the workflow explicitly, with named stages, evaluator-owned validation, hidden checklist validators, hard penalties for critical methodological errors, and a reproducible submission requirement.

2.4
Data-analysis and scientific-discovery benchmarks

InfiAgent-DABench
8

GRACE-DS adopts the interaction idea but applies it to a different target: rather than scoring answers to analytical questions or discovery novelty, it measures whether the agent generates a stable predictor that generalizes to unseen data while satisfying the process constraints, using low-cost, reproducible, and feasible tests.

2.5
AutoML benchmarking and agent systems

Classical AutoML benchmarking, notably the OpenML AutoML Benchmark
5
, established how to compare automated modeling systems across many tabular tasks with controlled splits and standardized metrics. GRACE-DS adds an LLM-agent interaction layer on top of this problem: the evaluated system is not a fixed modeling algorithm but an agent that writes code, interprets feedback, chooses workflow actions, and must produce a reproducible final artifact under organizational constraints. Agent systems such as Data Interpreter
7
and AIDE
12
are complementary: they propose ways to build stronger agents, whereas GRACE-DS provides an architecture-neutral environment in which any such agent — hierarchical, tree-search, ReAct-style, or a company-internal copilot — can be evaluated under the same hidden validation and scoring protocol.

2.6
Positioning of GRACE-DS

The works closest to GRACE-DS are MLE-bench, TML-Bench, MLE-Dojo, MLGym, and DSGym: the former two provide strong hidden-score evaluation but limited process-level diagnosis, while the latter three provide broad interactive environments without GRACE-DS’s specialization in the tabular supervised-learning workflow and its deployment-specific risks. GRACE-DS combines five properties in a single platform: it is
stage-aware
(explicit workflow stages from planning to final submission),
guarded
(hidden validators for leakage, protocol validity, reproducibility, and submission validity),
reward-guided
(process-level feedback whose alignment with hidden-test quality can be analyzed),
deployment-oriented
(final submissions must reproduce on raw input records), and
experimentally controlled
(the same tasks support single-shot, unstructured, iterative, restart, ablation, reward-optimization, and red-team comparisons).

3.7
Validator Structure

The validator layer in GRACE-DS is designed as a set of narrow, auditable checks rather than as a single monolithic judge. This design serves two purposes.
(i)
it makes the reward and failure analysis decomposable: an episode can fail because of execution, reproducibility, leakage, weak validation discipline, poor feature handling, or terminal submission errors, and these failure modes are recorded separately.
(ii)
it limits reward hacking: no individual checklist item can by itself produce a high final score, and deployment-critical violations override the ordinary reward calculation.

Formally, each validator
v
maps the current runtime session
s_{t}
to a structured result

\displaystyle z_{v}(s_{t})=(

\displaystyle\mathrm{name}_{v},\,\mathrm{passed}_{v},\,\mathrm{score}_{v},\,\mathrm{penalty}_{v},

(4)

\displaystyle\mathrm{status}_{v},\,\mathrm{details}_{v}).

where
\texttt{score}_{v}\in[0,1]
,
\texttt{penalty}_{v}\geq 0
, and
\texttt{status}_{v}
indicates whether the validator is inactive, unresolved, or resolved at the current step. Inactive validators are ignored by the reward calculation. Active non-plan validators contribute to the code-quality/process term, while the dedicated plan validator contributes to the plan term. The performance term is supplied only by evaluator-owned scoring actions, i.e. validation or final hidden-test evaluation. Thus, validators shape the agent’s process, but they do not replace held-out predictive evaluation.

Phase-gated activation.

Validators are activated according to the workflow phase reached by the agent. This prevents the environment from penalizing an agent for not yet satisfying requirements that are only meaningful later in the episode. The phase is inferred from the session state: before a plan the phase is zero; after a submitted plan it becomes the planning phase; after EDA it becomes the data-inspection phase; after feature engineering it becomes the preprocessing phase; after a model or reproducible candidate appears it becomes the modeling phase; and after terminal submission it becomes the final-scoring phase. For example, missing-value and feature-pipeline validators activate only after feature construction is possible, whereas leakage, execution, intactness, efficiency, and iteration-budget checks are active from the beginning. Evaluator-owned validators such as model evaluation, feature-importance diagnostics, correctness, target-leakage model checks, and baseline comparison are additionally gated until a scoring action is requested and a reproducible candidate exists.

Sandbox and protocol guards.

The first layer is enforced before ordinary validators run. The action parser requires every agent response to begin with exactly one action label. Executable actions, such as
EDA
,
FEATURE
ENGINEERING
,
MODEL
,
CODE
, and
CODE
FIX
, must contain exactly one fenced Python block. Evaluator-trigger actions,
VALIDATE
and
FINAL
SUBMIT
, must contain no code. This prevents agents from mixing scoring requests with hidden side effects.

The sandbox also performs static policy checks over the submitted code. It blocks file and network access, subprocesses, serialization/deserialization modules, direct environment access, and unsafe builtins such as
open
,
exec
,
eval
, and
import
. Calls to scikit-learn metric functions are allowed only for train-local diagnostics; attempts to score evaluator-owned validation or hidden-test objects are rejected. Failed or rejected actions are transactional: the workspace is rolled back to its previous snapshot, so partially executed code cannot corrupt later steps. Protected raw snapshots are hash-checked after each executable action and restored if tampering is detected.

Integrity and leakage validators.

The second layer targets deployment-critical methodological errors. The
IntactnessValidator
checks that protected raw snapshots are unchanged. The
LeakageValidator
scans executed code for unsafe use of evaluator-reserved objects, fitting on validation/test frames, and using the target column as a feature. The
TrainValidRefitLeakageValidator
catches the common pattern in which the agent concatenates training and validation frames and then fits or transforms on the combined object. The
TargetLeakageModelValidator
adds an evaluator-side diagnostic: it searches for suspicious single-feature predictors and large train-validation gaps that suggest leakage or severe overfitting. These validators are deliberately redundant: leakage can be caught by namespace restrictions, code-pattern checks, snapshot integrity, and evaluator-side scoring behavior.

A small set of critical errors is treated specially. Target leakage, train+validation refit leakage, evaluator-private access attempts, and protected-snapshot tampering force the final reward for that step to zero. This is stricter than an ordinary soft penalty: the agent cannot compensate for a critical methodological error by satisfying checklist items or obtaining a high intermediate process score.

Data-condition validators.

The third layer is task-conditioned. Before the agent begins, the environment computes a private data profile from the training split: missing-value structure, categorical columns, duplicate rows, high correlations, outliers, skew, feature-scale disparities, class imbalance, identifier-like columns, and high-cardinality columns. This profile is used to compile a hidden checklist whose criteria are included only when the corresponding condition is present in the task. For example, missing-value criteria are added only for datasets with missing features; imbalance criteria are added only for classification tasks with skewed class proportions; correlation and outlier criteria are added only when the training data exhibits those patterns.

These validators check both inspection and mitigation. The EDA criteria look for evidence that the agent examined schema, target behavior, missingness, duplicates, correlations, distributions, scale, imbalance, or suspicious identifier-like fields. The feature-engineering criteria then check whether the corresponding issue was addressed in a reusable way, for example by placing imputers, encoders, scalers, or feature derivation logic inside the submitted pipeline or prediction function. This two-level design separates merely noticing a data condition from producing a replayable modeling artifact that handles it.

Submission and reproducibility validators.

The fourth layer enforces the raw-input submission contract. GRACE-DS accepts only two terminal artifact types: a callable
predict_fn(raw_dataframe)
or a fitted scikit-learn
Pipeline
named
pipeline
or
submission_pipeline

After each candidate-changing action, the environment performs a target-free smoke check on raw validation rows. This smoke check does not compute or reveal a metric; it only verifies that the candidate can reproduce preprocessing from raw input.

Several validators support this contract. The
NamespaceCheckValidator
checks that expected model artifacts exist and expose prediction methods. The
FeaturePipelineValidator
penalizes unresolved NaNs, unencoded categorical variables, missing scale-sensitive preprocessing when appropriate, and transformations that are not packaged into a reusable artifact. The
ReproducibilityValidator
checks for fixed seeds in stochastic estimators. The
CorrectnessValidator
verifies terminal prediction length and numerical validity. The
BaselineComparisonValidator
compares the terminal model against the task baseline when a hidden-test score is available. Together, these checks prevent the agent from submitting a notebook-local solution that depends on transformed arrays, temporary variables, or validation-only state.

Modeling and efficiency validators.

The modeling validators encourage simple, controlled model development rather than uncontrolled automated search. The
ModelChoiceValidator
rewards conventional tabular estimators and penalizes missing models, inappropriate custom estimators, or neural-network choices that are poorly matched to the low-budget tabular setting. The
HyperparamValidator
checks whether the agent specifies a small number of explicit, sensible hyperparameters, while penalizing automated search APIs such as exhaustive grid search, randomized search, Bayesian search, or external tuning frameworks. The
EfficiencyValidator
penalizes excessive elapsed execution time and search-heavy code. These checks keep the comparison focused on agent planning, correction, reproducibility, and validation-driven improvement rather than on expensive AutoML search.

Process validators.

The fifth layer tracks the agent’s correction behavior. The
PlanCoverageValidator
checks whether the plan acknowledges the metric, validation discipline, reproducibility, iteration, and task-specific risks. The
BacktrackingValidator
detects repeated destructive transformations or unstable workflow reversals. The
IterativeCycleValidator
evaluates whether additional cycles produce useful validation improvement rather than repeated regressions. Candidate diversity is also rewarded through a lightweight model-family signal: before stopping, the agent is encouraged to validate a small number of meaningfully different manual candidates, such as a tree ensemble and a linear/logistic baseline, without running automated search.

Hidden checklist feedback.

The exact detectors, thresholds, and recognition patterns are never revealed to the agent. At each step, the environment computes the relevant stage assessment internally and exposes only a stage score and a bounded list of abstract unresolved hints. For instance, the agent may be told that missing values remain unresolved or that transformations are not demonstrably reproducible, but it is not shown the regular expressions, object-inspection rules, or numerical thresholds used by the evaluator. This hidden-checklist design reduces direct pattern matching against the evaluator while still giving the agent enough information to repair its workflow.

The agent receives three kinds of feedback.
Execution feedback
reports
success/failure, the captured
stdout
, and on failure a traceback with targeted
hints (e.g. missing imports, engineered columns left outside the pipeline, an unfitted
pipeline).
Stage-aware feedback
is compiled from the dataset conditions actually
present (missing values, categoricals, duplicates, correlations, outliers and skew,
imbalance, identifier-like columns, …) into a
hidden checklist
: criteria are
added only for conditions a task exhibits, so the rubric varies per task and cannot be
memorized. Each step yields a stage score in
[0,1]
and, for every unresolved
criterion, an abstract hint that says what is unresolved and
which
direction
to move but never reveals the detector (its regexes, thresholds, or checks).

Metric feedback
is
gated
: the validation metric appears only after an
explicit
VALIDATE
(or harness auto-validation),
MODEL
never discloses
quality, and the hidden-test metric is computed once at terminal scoring.

Why the rubric stays hidden?

Disclosing the exact rubric would let an agent pattern-match the checker — e.g. calling
df.isna().sum()
to tick the EDA missing-value box without ever
reasoning about whether those values matter or handling them inside a reproducible
pipeline. Hiding it while surfacing only abstract hints pushes the agent to
reason about the data. The reward reinforces this: checklist compliance feeds
only the plan (
0.15
) and code-quality (
0.30
) terms and cannot move the performance
term (
0.55
), which the evaluator computes on held-out data. The process reward is
therefore a
proxy
for task quality, not an independent target, under ordinary
task-solving the two move together, but the adversarial regimes
(Section
3.8
) show that rewards cannot fully replace test metrics.

Evaluator-owned scoring validators.

Metric-bearing validators are evaluator-owned. The validation target and hidden-test labels are never placed in the agent-visible namespace. During
VALIDATE
, the evaluator resolves the active reproducible candidate, runs it on raw validation rows, computes the task metric privately, and returns only the scalar validation score. During
FINAL
SUBMIT
, the evaluator runs the active candidate once on the hidden-test split. The final hidden-test score is therefore isolated from the agent’s code and from the process reward. This separation is essential: process validators measure whether the workflow is methodologically acceptable, while the hidden test remains the final arbiter of predictive quality.

Reward integration.

Validator outputs are combined with the normalized performance score in the decomposed reward. The performance term has the largest weight and is nonzero only on evaluator scoring actions. The plan term is supplied by plan coverage. The code-quality term is the mean score of active non-plan validators, including both explicit validators and hidden stage-checklist aggregates. Soft validator penalties are summed and capped as a fraction of the weighted reward, while critical errors override the ordinary calculation and force zero reward. This produces a reward signal that is informative for correction but bounded enough that checklist compliance alone cannot substitute for solving the task.

Overall, the validator structure makes GRACE-DS a guarded evaluation environment rather than a leaderboard wrapper. The agent must satisfy interface constraints, preserve evaluator-owned data boundaries, produce a reproducible raw-input artifact, respond to task-specific data conditions, and improve through valid feedback. At the same time, the final held-out score is reported separately from process reward, so the framework can expose cases where a trajectory is superficially compliant but predictively weak, or predictively strong but methodologically invalid.

5.4

H5 is confirmed with the anticipated caveat.
Computed per

Section
4

Conclusion

We introduced GRACE-DS, a controlled pre-deployment evaluation harness for
LLM-powered AutoML agents on tabular supervised-learning workflows, and
used it to compare 15 harness regimes across eight frontier LLMs
and ten production-like tasks. The central finding is that how an
agent is allowed to work matters as much as which model runs it:

flexible-iterative
reaches an end-to-end normalized
hidden-test quality of
0.754
, against
0.536
for
single-shot

generation,
0.527
for the
unstructured-agent
, and
0.672
and
0.686

for the restart baselines, while raising protocol-valid completion to

96.9\%
. The paired advantage is
+0.218
E2E Q over
single-shot
and

+0.227
over the
unstructured-agent
, and the
flexible-iterative
regime dominates
even the most conservative call-matched restart upper bound on quality
and wall-clock (Tables
4
,

5
,
11
).

Table
21
summarizes the
verdicts with the primary supporting evidence for each hypothesis.
These results also substantiate the positioning claims of
Section
2.6
against final-score and gym-style
benchmarks. Every deployment-relevant distinction reported above is
invisible to a final-score-only evaluation: the
unstructured-agent
and
the fixed schedule essentially match the
flexible-iterative
regime on the observed
quality of completed runs (Obs. Q
0.762
–
0.779
vs.
0.779
) and
would look competitive on a leaderboard, yet they lose
10
–
23
points
of protocol-valid end-to-end quality to terminal failures, the restart
baselines look strong on aggregate score while committing
25
–
34

leakage-class critical-error episodes, against at most one in the
structured regimes, and the reward maximizers and the red team keep
their scores superficially respectable while the combination of hidden
validators and isolated held-out scoring localizes exactly what they
sacrificed.

It is precisely the GRACE-DS combination — staged interaction, hidden
executable validators, decomposed process reward, reproducible submission,
and a single isolated hidden-test scoring — that turns these
distinctions into measurements, which is the capability an enterprise
pre-deployment gate requires and which the related benchmarks of
Section
2
do not provide in one platform. By measuring
the full agent loop rather than only its final score, GRACE-DS lets a team
choose not just a model but a way of running it, and surfaces the
reliability and reward-hacking failure modes that determine whether an
AutoML agent is safe to put into production.

Future Work

GRACE-DS is a controlled pre-deployment evaluation harness for LLM-powered AutoML agents on tabular supervised-learning workflows, its directions for future work therefore follow directly from the design choices that define its current scope.

Scope

GRACE-DS currently targets tabular ML because of its central role in industrial applications such as risk scoring, churn prediction, forecasting, fraud detection, and operations analytics. Extending the harness to deep learning training loops, multimodal modeling, reinforcement learning, large-scale distributed training, architecture search, and open-ended scientific discovery would test whether the process-level, deployment-relevant distinctions GRACE-DS surfaces generalize beyond tabular AutoML and move it toward a more universal benchmark for ML agents.

Relation to production readiness

Integrating GRACE-DS into the broader MLOps lifecycle. Passing GRACE-DS does not by itself certify a model as production-ready: monitoring, probabilistic calibration, robustness to future distribution shift, latency constraints, explainability, security review, and approval workflows.

Governance coverage

The constraints GRACE-DS enforces (Table
13
) are a selected, deployment-relevant subset, not full governance readiness. It does not yet model personally identifiable information detection and handling, role-based access control, data-retention and audit-logging policies, fairness or bias auditing, or regulatory-compliance checks (e.g. GDPR). Extending the manifest and validator suite to express and enforce such organization-specific policies is a natural direction for future work.

Adversarial coverage

Our red-team evaluation is prompt-based and not an exhaustive adversarial audit. It does not yet cover validator-aware attacks, manual or obfuscated leakage (e.g. via serialization, indirect imports, or feature-name encodings), data-copying, or attempts to infer validation labels from feedback. Strengthening the adversarial suite along these axes, and treating it as an open red-team benchmark rather than a fixed prompt set, is left to future work.
