ABSTRACT
Recent advances in probabilistic programming languages (PPLs) have provided the capability for
exact inference: computing a closed-form probability distribution for a given probabilistic program.
In particular, the new language Roulette uses a language oriented programming (LOP) approach,
wherein analysts build new programming languages on top of a set of primitives provided by
Roulette, which then translates these structures into a weighted model counting problem which
can be solved by automated reasoning tools. However, because Roulette provides few convenience
features, developing these new languages is challenging even for expert users.
We developed a standard library of common probability functions for Roulette with the goal
of improved usability. This included approximation of continuous probability density functions
using discrete probability mass functions. We demonstrated this approach by modeling a cosmic
ray striking a RAM controller. We found that Roulette provides a powerful interface for highly
expressive probabilistic programs to be generated. In collaboration with the NNSA Advanced
Simulation and Computing program, which resulted in development of a tool called Circulette,
we were able to model complex circuits expressed in Verilog using probabilistic programs with an
expressivity not previously possible.
Our research question that motivated the development of a Roulette standard library was to deter-
mine whether non-experts could use a PPL to model relevant problems regarding radiation effects
on microelectronics. This standard library improved the expressivity of Roulette by implement-
ing common probability density functions, mathematical operators on distributions, and support
for empirical distributions. While Roulette is a powerful modeling language, the untyped, LOP
approach makes error messages difficult to understand and requires expert aid. We recommend
further research on Roulette, especially with its error messages, to enable improved usability. At the
same time, this project demonstrated that for users familiar with Roulette and the LOP approach,
Roulette provides powerful new capabilities that can be integrated with other Sandia modeling
capabilities.

SUMMARY

Radiation-hardened hardware design requires system-wide understanding about the probabilities
and consequences of failures in harsh environments such as outer space. This is a challenging
design problem for cyber-physical systems. The challenge lies in the difficulty of modeling these
systems accurately because events such as radiation upsets shatter the analog-digital boundary that
make digital systems so valuable. Recent advances in probabilistic programming languages (PPLs)
provide an opportunity to model cyber-physical systems with a precision not previously possible.
However, these PPLs, being newly-developed, can suffer from scalability and usability limitations.
We developed a general-purpose PPL library and applied this library to the problem of failure
consequence modeling using the exemplar of a cosmic ray radiation upset event. We demonstrate
how this capability enables modeling and verification of hardware components with a precision
not previously possible. This project identifies key scalability and usability limitations to motivate
further research on PPLs.

PRACTICAL PROBABILISTIC PROGRAMMING

1. Background

This project began with the observation that probabilistic programming languages (PPLs) provide
an opportunity to model failure behavior for hardware systems. PPLs aim to provide probabilistic
constructs like random variables and probability distributions as first-class values and translate
these constructs through data structures that are more sophisticated than simple floating-point
arithmetic. PPLs generally take one of two approaches when computing probabilistic values: exact
inference and approximation. Exact inference is when the language can compute the exact (i.e.,
closed-form) probabilities in the program and approximation is when techniques such as random
sampling are used to approximate the probabilities in the program. Exact inference is ideal because
it provides high precision, but it is complex to implement and struggles from scalability issues,
while sampling struggles with accuracy but is much more scalable for most problems. Different
PPLs handle the tradeoffs between scalability, accuracy, and expressivity differently. Languages
like PSI [6] and Hakaru [10] support exact inference over a broad class of programs (i.e., programs
with observation, loops, conditionals, etc.) but suffer from scalability issues. Some languages
like Dice [8], ProbLog [3], and SPPL [12] still support exact inference but restrict expressivity,
permitting more scalability. Languages that use sampling like Stan [14] and WebPPL [7] are able
to support expressive programs scalably at the cost of accuracy.

Roulette is a language which attempts to have all three: expressivity, scalability, and accuracy (via
exact inference). However, compared to these more mature languages, Roulette is difficult to use
since it provides only a host language with the only primitive being the ability to flip a weighted
coin (a Bernoulli trial). In order to model failure behavior for hardware systems, we need more
sophisticated distributions. The goal of this project is to create a standard library for Roulette that
contains these more sophisticated distributions as well as leaving room for future expansion and
addition of features.

2. Roulette

Roulette supports exact inference that allows finite discrete random variables to be first-class values
using a novel combination of symbolic evaluation and knowledge compilation. It does so by
utilizing the Rosette [15] language, which adds solver-aided symbolic execution capabilities to
Racket [4], and the RSDD [11] library, which models a knowledge compilation data structures
called Binary Decision Diagram (BDD) and Sentential Decision Diagrams. We will not go into
detail about RSDD, but one important thing to note is, while BDDs do scale well on many practical

 15

problems, they are in fact #P-complete, so some classes of problems may be intractable due to
theoretical limitations.
The fact that Roulette only supports finite discrete random variables means that we cannot model
continuous random variables directly and must approximate them via other means. Also, some of
the internal workings of Roulette (primarily its use of Rosette) “leak out” and require Roulette code
to be written in a certain way that in some cases reduces usability.

2.1. Discrete versus Continuous Probability Distributions

One important concept to understand when talking about PPLs in general is the distinction between
discrete and continuous random variables. These terms refer to the support of a random variable,
i.e., the range over which the random variable is defined. A range is discrete if any possible value
in the range is at least some positive minimum distance away from all other permissible values. An
example of this are the integers {. . . , −1, 0, 1, . . . }. A range is continuous if any finite subrange
has an infinite number of possible values, for example, the real numbers (there are infinitely many
points between any unequal real numbers). Since Roulette only supports finite discrete random
variables, we must approximate continuous random variables. We discuss this approximation in
Section 3.2.

2.2. Rosette

Understanding Rosette is important when programming in Roulette, so we discuss it in more detail
here. Rosette is a language built on top of Racket that allows a program to contain symbolic
variables and operators that are lifted to work for arbitrary programs. The term lifting comes from
category theory which we do not define here, but intuitively, lifting refers to the capability of a
program to execute using a more sophisticated datatype—in this case, symbolic values instead of
concrete values.
Rosette then symbolically executes the program, resulting in a symbolic union containing all of the
possible execution paths of the program and their return values. In essence, this symbolic union
contains all possible values a program may take (e.g., all possible assignments of true/false to
bernoulli random variables). Roulette utilizes these symbolic variables by attaching probabilities
to each of the symbolic variables as shown in Figure 1, which was adapted from a PLDI talk by
Moy [9]. This extended symbolic union representation is compiled into a BDD.
The usage of symbolic variables has some important implications for how we write Roulette code.
Take for example this naive implementation of the binomial distribution:
 (define (binomial n p)
         (for/fold ([acc 0])
                   ([_ (in-range n)])
           (if (flip p) (+ acc 1) acc)))

Running this function with n set to as low as 30 times out after 30 minutes on an M4 Mac. There
are two reasons for this.

The first is that the way Rosette represents this program is very inefficient by default. By default
the program is represented as a nested series of conditionals over symbolic variables (e.g. (ite
x$5 (ite x$2 2 1) (ite x$2 1 0))), which means that the number of possible program paths
increases exponentially, thus significantly increasing the runtime of the program. In order to solve
this, we need to force Rosette to create symbolic unions by directly using symbols instead of
numbers:
 (define (add a b)
 (number->symbol (+ (symbol->number a) (symbol->number b))))

 (define (binomial n p)
      (for/fold ([acc ’|0|]) ; ’|<term>| creates a symbol
                ([_ (in-range n)])
        (if (flip p) (add acc ’|1|) acc)))

Notice how we can no longer use the builtin + operator but must now define our own operator add
that works on these “number symbols.”
The second reason this code struggles to scale is because of the computations present in the if-
statement. When an if-statement is evaluated, Rosette must merge the two paths. Therefore, the
more complex the expression within an if-statement, the longer the program will take to complete.
In order to solve this, we need to “push down” the if-statements as far as possible, i.e., we want to
put as simple expressions as possible within if-statements:
 (define (binomial n p)
         (for/fold ([acc ’|0|])
                   ([(in-range n)])
 ; Note the change to the branches of the if-statement
           (add acc (if (flip p) ’|1| ’|0|))))

The fact that the internal workings of Roulette “leak out” and force the programmer to write their
code in this way is an issue with Domain Specific Languages (DSLs) in general; this can create
difficulty for new users. Another complexity is that having numbers as symbols “infects” the entire
program; everything must be a number symbol or must be converted to/from a number or symbol.
One design decision we made for the standard library is making every construct symbolic (rather
than concrete or numeric). This has implications which we discuss in Section 5.1.

2.3. Disrupt and Domain-Specific Languages within Roulette

As mentioned in Section 1, Roulette is a host language within which other domain-specific languages
(DSLs) are written. In fact, all of the previous code blocks have been written in Roulette’s default
default DSL called Disrupt. Disrupt supports the 3 operations flip, query, and observe! as well
as a couple of utility functions [1]. We could have built a new DSL on top of Roulette, but instead
we leveraged the existing constructs within Disrupt because they provided enough capability for
our needs. Because of this, we use the terms “Roulette” and “Disrupt” interchangeably in this
report.

3. Roulette Standard Library

Our goal for the project was to create a standard library of probabilistic distributions and to see
if we could use this standard library to model some existing examples developed at Sandia in
Roulette. An important property we wanted was the ability to use a mix of discrete and continuous
distributions within one program. Since Roulette only supports finite discrete random variables,
we had to approximate continuous random variables by discretizing them. This introduced error
into results computed using the discretized continuous random variables. We identified 3 possible
sources of error: error due to how we approximate integrals, floating-point error, and error due
to the discretization itself. We explored various possibilities to quantify these sources of error,
eventually implementing the ability to quantify the first source of error. After more investigation,
we came to the conclusion that quantifying floating-point error was out of scope for the project

 18

and that quantifying discretization error within the standard library would impact expressivity too
much. Therefore, quantifying these sources of error must be done manually.

3.1. Discrete Distributions

Since Roulette performs exact inference, we can directly and completely model discrete distributions
with finite support (such as uniform and binomial distributions) via Bernoulli trials (coin flips).
For discrete distributions with infinite support like the geometric distribution, we explored two
options: lazy evaluation and truncating the support range to make it finite. The Roulette paper
had an example implementation of the geometric distribution which uses lazily evaluated Peano
numbers to exactly compute the probability masses when the values are needed, similar to lazy
languages like Haskell.
We tried to use lazy Peano numbers and came to the conclusion that there are multiple issues with
this approach. The main issue is that working with lazily-evaluated Peano numbers is difficult,
especially when interacting with other datatypes like regular numbers and number symbols. Another
issue is that lazily-evaluated Peano numbers are inefficient compared to number symbols. Lastly,
since we wanted to provide a consistent interface and return types for all of our distributions, it
did not make sense to have one distribution that was drastically different from the rest. Therefore,
we proceeded design decision to truncate the support based on a parameter given by the user. As
the support range becomes larger, at some point the probability reduces to 0 since the probability
is lower than what can be represented by floating point values. We give the user the ability to
pick where to truncate and we recommend that they pick the range such that it ends somewhere
after the point where the probability drops to zero. If large, rare events need to be represented,
possible workarounds include representing probabilities in the logarithmic space, however, these
values were not necessary for our applications.
The other discrete distribution worth mentioning is the Poisson distribution, which we do not
directly model using Bernoulli trials. Instead, we use the closed form equation of the probability
mass function and generate a list of densities. This is because the Poisson distribution is a special
case: even though it has a discrete support, it is infinitely divisible, i.e., it is expressed as the
probability distribution of an arbitrary number of independent and identically distributed (iid)
random variables.

3.2. Continuous Distributions

There are generally three different ways PPLs model continuous distributions. The first is by
sampling (e.g., Markov Chain Monte Carlo, MCMC). The second is via direct symbolic inference
(e.g., via a computer algebra system), and the third is via discretization; we chose the last option.
Our decision was informed by the fact that supporting sampling or direct symbolic inference in
Roulette would require large changes to the language that would not fit within the time constraints
of the project. Recent work about discretization by Garg and Holtzen [5] provides precedence for
this approach. Our approach is simpler than one proposed by Garg and Holtzen but is based on a
similar core idea.

Given the parameters for a distribution, for example, the normal distribution, we create a number
of points linearly spaced across the finite support range provided by the user. We then calculate
the probability at each point using the probability density function (PDF) of that distribution. For
each pair of points, we calculate the integral between those points by splitting the interval into 1000
slices and using the trapezoid rule to calculate the area of each slice, then summing up all of the
slices. We then assign that integral to a new point that is the midpoint between the two original
points; a visualization of this process is shown in Figure 2. Therefore, we end up with about
half of the number of points we originally generated, with each point containing some computed
integral value. An important implication of using this technique is that checking for equality (i.e.,
Pr(𝑋 = 𝑥)) over these discretized distributions will more often than not return #f (false in Racket),
since unless the queried value exactly matches up with one of the discrete points in the distribution,
it will not be part of the support. The second implication is that we now introduce some amount of
error, partly by approximating the integral using the trapezoid rule, but mainly due to discretization
error, where querying the distribution at two similar points may get you very different answers.
This issue is most present when the number of discretized points is low and/or the support range is
insufficient. We will discuss discretization error in more detail in the next section.

3.3. Error Bounds and Propagation

There are three different sources of error that affect the results our standard library computes. The
first is floating-point errors which affect both discrete and continuous distributions. Racket actually
supports exact rational numbers, but RSDD is written in Rust and only supports floating-point
numbers, so once the program gets dispatched to RSDD, the exact rational number information is
lost and cannot be recovered. Since we use double-precision floating-point numbers, this error is
small for our use cases. The second error source affects only continuous distributions and is the
error accrued when using the trapezoid rule. It is important to note that this error does not measure
the error seen when performing operations like CDF on the distribution, but instead measures how
much of the total integral has been captured by the distribution. This error tends to be very small

since we run the trapezoid rule on a relatively large number of slices. The last source of error
only affects continuous distributions and is the most important: it is the discretization error we
mentioned in the previous section. The discretization error is directly tied to the number of bins we
create and has the potential to be very high. A simplified illustration of this can be seen in Figure
3, where we have a uniform distribution (assume that it was discretized from a continuous uniform
distribution) with 4 points in the support, where each point contains 25% of the probability. When
we query the CDF at point 2.9, we do not include the probability at point 3, so the discretization
error is close to 25%.

The only error we currently compute is the error incurred when using the trapezoid rule. We do
not compute the floating point error accrued in Racket and RSDD because other sources will likely
dominate. We also do not compute the discretization error explicity for two reasons. The first is
that in order to analyze the error we must have some source of truth to compare against, which
would require the ability to do get the exact result of any arbitrary PPL computation. This is a
difficult problem and it is unclear how to do this generically, since the closed form equation that
we would use as the source of truth may be unknown or nonexistant for some distributions. The
second is a software engineering concern: how to structure the API to deal with error propagation.
This is a spectrum from low expressivity (using restrictive APIs) with automatic error propagation
to high expressivity with completely manual error propagation. We considered a few different
solutions within this spectrum, but came to the conclusion that since the main strength of Roulette
is the expressivity afforded by the language, it didn’t make sense to restrict the expressivity to get
automatic error propagation. Also, users may not want or need error propagation so this library
does not add in the overhead where it may not be necessary. We decided to go with the high
expressivity with completely manual error propagation, so if a user wants to get error bounds on
operations over continuous distributions, they must calculate those themselves.

3.4. Summary of Work

In conclusion, the standard library supports 8 discrete and 7 continuous distributions with the ability
to easily add more in the future. We show our implemented distributions in Table 4. The library
also supports common arithmetic of operations such as >, <, +, etc., that have been lifted to work
on these distributions with the ability to easily add more in the future. There are also a collection
of utility functions, which include functions for plotting discrete and continuous distributions,
functions for use in testing, and other useful functions.

4. Applications

We were able to model four example applications: the outputs of an error correcting code chip with
probabilistic inputs, the effects of cosmic radiation on a single-port RAM chip [2], netlists with
probabilistic perturbation of data, and empirically-derived probabilistic distributions. For the first
example, we were able to reach accuracy parity with an original implementation written in WebPPL.
In the second example, we exactly model the probability of all potential outputs of a chip given the
parameters for where and at what angle it was hit by a cosmic ray. The third example application
is a Sandia-developed project called Circulette which also uses Roulette to probabilistically model
fault tolerance in netlists generated directly from Verilog. For the last example, we showcase how
to create distributions using empirical data that may not have a closed form equation.

4.1. Error Correcting Code

The first example we implemented was an example that we originally wrote in WebPPL:
 var geometric = function() {
 return flip(.5) ? 0 : geometric() + 1;
 }
 var model = function() {
 var max_errors = 3;
 var nrm = gaussian(0, 1);
 var g = geometric();

 22

 return (g + (nrm > 2)) > max_errors;

 };
 var dist = Infer({method: ’MCMC’,
                         samples: 5000000,
                         burn: 2000}, model)
 print(dist);
 viz.auto(dist);

This program was a good candidate since it contained both a discrete and continuous distribution,
and these distributions interact with one another. Using the standard library we were able to create
a version of it in Roulette:
       (define max-errors ’|3|)
 (match-define (cons nrm trapezoid-err) (rlt-normal 0 1 #:trials 300))
 (define g (rlt-geometric 1/2 50))
       (define nrm-gt-2 (sym-gt nrm ’|2|))
 (define coerced-nrm-gt-2 (bool-support->num-support nrm-gt-2))
 (define g-add-nrm (sym-add g coerced-nrm-gt-2))
 (query (sym-gt g-add-nrm max-errors))
       ; Returns: (pmf: | #f -> 0.936078 | #t -> 0.063922 )

This program is quite similar to the WebPPL example (other than the syntax differences and number
symbols), and the result we get has the same number of significant digits. A major advantage of
using Roulette over WebPPL is that the result we get is deterministic, whereas the result we get
from WebPPL is not deterministic due to the randomness used to sample the distributions. Another
major advantage is: since all of the computations in the program and the standard library are pure
(in the functional sense), we have the ability to reason about the error (as discussed in Section 3.3)
while in WebPPL the use of sampling makes it much more difficult to even begin to do this. Overall,
the advantage of Roulette in this application is that it is much easier to reason about deterministic
pure computational systems than systems based on random sampling.

4.2. Testbed: Single-Port RAM Under Cosmic Radiation

The second application is a model of the effects of cosmic rays on a single port RAM chip’s memory.
Cosmic rays are high-energy particles that come from space and can cause bit flips. Modeling this
can be split into a spatial model (Figure 5) that models which memory cells are affected by a cosmic
ray and a semantic model for how being hit by a cosmic ray affects the output. Therefore, our model
can be thought of as answering the question: “if a cosmic ray hits address X at angle 𝜃 during
some operation, what is the probability that the operation will result in the correct output?” We
will not describe the spatial model in detail since it does not require probabilities and is extremely
simplified, but an important note is that Roulette’s expressivity allows for the spatial model to also
be written in Roulette itself.
We show below a listing of the most relevant part of the semantic model.

 (define (single-port-ram prob-env addr we oe data tmp_data mem)

 (if (flip (list-ref prob-env addr))
 (perturbed-data DATA_WIDTH)

 (perturbed-data DATA_WIDTH)

 (set! tmp_data maybe-perturbed-tmp_data))

 (set! data maybe-perturbed-mem))

This code defines a function single-port-ram with 7 arguments. prob-env is a mapping
of addresses to the probability that they return a perturbed result. We populate this using the
information from the spatial model, so if an address is hit by a cosmic ray, the probability that it
returns a perturbed result goes up. One advantage for doing it this way is that we can have some
baseline probability for a perturbed result to model the fact that sometimes bits flip due to hardware
failures unrelated to cosmic rays. The addr, we (write enable), and oe (output enable) arguments
are just integer and boolean inputs to the chip, respectively. data is also an input to the chip,
but like tmp_data and mem, its state must be maintained between clock cycles (i.e., calls to the
single-port-ram function), so it is returned from the function to be used in any subsequent calls
to the function. The perturbed-data function returns all possible combinations of bit vectors of
length DATA_WIDTH as the possibilities of a uniform distribution.
Therefore, when the single-port-ram function is called, taking into account the probabilities
associated with the addresses in prob-env, it returns back a Roulette PMF containing all of the
possible return values and their probabilities. The reason we return all possible combinations of
bit vectors is that since the number of combinations increases exponentially, we can get an upper
bound on performance. For a large-scale system, we would want to shrink the space of possibilities

 24

to avoid this worst case performance. An important piece of information that we can compute from
this output is the probability of getting a given number of bit flips (from 0–4 in our example), which
is extremely useful to know in the context of error correction. Another advantage of this approach
is that it is relatively modular; creating different behaviors for how data is perturbed, how memory
cells behave between clock cycles, and how we model the effects of a cosmic ray on the probability
of an incorrect result is easy using this approach.

the resulting data returned had 3 errors) be able to get a distribution on the most likely angles and
addresses hit that would cause for there to be 3 errors. This showcases the power of Roulette’s
features, which gives users the ability to compute data which would ordinarily be very difficult to
compute without manual derivation.

4.3. Modeling Netlists with Probability

Electronic design automation typically makes use of a netlist representation of hardware com-
ponents, which is a list of the electronic components on a chip and how they connect. Netlists
don’t contain any spatial information, but their advantage is code written in a hardware description
language (e.g., Verilog code) can be translated into a netlist automatically. There is a separate
Sandia-developed project called Circulette which uses Roulette in order to probabilistically model
fault tolerance of netlists. Circulette is able to take in Verilog code and transform it into a netlist
represented in Roulette. It then uses an interpreter written in Roulette that models the probability
of an operation in the chip returning an incorrect result. As an example, see the following code,
which represents a read operation to memory returning a bit vector that is all zeros:
 (define (mem-perturb mem i bitwidth)
 (vector-set! mem i
                      (if (flip 0.9999)
 (vector-ref mem i)
 (bv-zero bitwidth))))

There are a couple advantages this approach has over the bespoke approach shown in the previous
section. The first is that automatically generating netlists from Verilog code is much more efficient
and scalable than translating a hardware specification into Roulette by hand. The second advantage
is that using an interpreter allows for a lot of flexibility in what kinds of phenomena can be modelled
since we have precise control over the semantics. One similarity between the two approaches is
that spatial information can be computed separately from and fed into the semantic model. One
disadvantage of this approach is its genericity makes it not possible to optimize chip and data being
modeled for sybolic execution. This means that the underlying solver, RSDD, does not scale as well
to larger problem sizes. This could restrict the size of the netlists that can be modeled. However,
further work is needed to determine which designs scale well for this approach.

5. Evaluation, Impacts, & Future Work

While we were able to implement multiple complex examples in Roulette, we found that its usability
must be improved before it could be used without consulting a Roulette expert. The two main
challenges are dealing with Rosette’s symbolic values and having to approximate continuous random
variables using discretization. Despite these challenges, this project demonstrates that with more
work PPLs have great potential for both modeling existing systems and developingsophisticated
failure models on these systems.

5.1. Lessons Learned and Evaluation

Our primary research question for this project was the following: Can someone who knows proba-
bilities or hardware model a system in a PPL without consulting an expert? While this project made
significant steps towards improving the usability and developing the maturity of Roulette, Roulette
still requires expert guidance for effective modeling. However, as demonstrated in Sections 3 and 4,
the new standard library presents powerful abstractions that allow modeling of realistic real-world
scenarios and builds significantly upon the capabilities provided by Roulette.

Now, we evaluate Roulette’s usability and point out potential confusions that could affect people
who are not experts in PPLs or Roulette.

 27

We note several challenges we encountered during development of the standard library and ap-
plications. The first is that Rosette’s peculiarities “leak” into and affect how Roulette developers
must implement programs. Specifically, in order to have scalability, Roulette programs must use
symbolic values for the support of random variables. Using symbolic values adds complexity and
makes refactoring more challenging because all operations must be lifted to their symbolic forms.
Operations in Racket are not lifted by default, so many standard operations must be reimplemented
to work with symbolic values. This subtlety is surprising to beginners and results in them having
a difficult time understanding why their programs error or do not scale. We give one example.
Suppose one wishes to build a probability distribution from two random variables 𝑥 and 𝑦 from the
following formula: |𝑥 − 𝑦| > 1. A first attempt is as follows:
 1 (define (model)
 2 (define x (rlt-poisson 4 50))
 3 (define y (rlt-poisson 4 50))
 4 (query (sym-gt (sym-abs (sym-sub x y)) 1)))
 5 (model)

Notice that the operations >, ∥ · ∥, and − are symbolic versions provided by our standard library.
The error here is that we have written the concrete number 1 instead of the symbolic value ’|1| on
line 4. This is a simple error that is easy to make (especially for beginners) but produces an error
message as follows (which has been edited to anonymize directory names and maintain column
width):

[merge] failed
  context...:
 path/to/rosette/pkg/exn.rkt:59:11: raise-exn:fail:svm:merge
 <dir>/roulette-stdlib/examples/backoff.rkt:5:0
 body of "<dir>/roulette-stdlib/examples/backoff.rkt"

This error does not give any information as to what went wrong and points to the wrong line; it
points to the call to model instead of the root of the problem at line 4. This issue becomes worse as
the size of a codebase increases. That said, this “leakage” is common to many LOP-based methods
or domain specific languages in general. When a user encounters an error in Roulette, which is
built on top of Rosette, which is itself embedded in Racket, an error message could manifest at any
of these levels of abstraction. This means error messages that are purely syntactic can appear as
complex as those which result in a misunderstanding of the semantics of either Racket, Rosette,
Roulette, or its standard library.
Another challenge is with building propert symbolic values without destructuring the distribution
in a way that creates disjoint BDDs. Assume we want to create a distribution where the support
consists of Racket lists (e.g., ’(1 2 3)). Racket lists (and most other “container” datatypes) are
actually symbols that are treated in a special way in Racket and Rosette; this means that they are
represented in Roulette as large blobs of Rosette code which are difficult to reason about and may
not interact with other symbolic values as expected (similar to what was shown for numbers in
Section 2.2). In order to turn these lists into a symbolic union, the distribution must be completely
destructured via the in-pmf function provided by Roulette. This destructuring converts each of the

 28

values into strings, then those strings into symbols, and finally constructs a new distribution that
contains these symbols. This process causes the resulting BDDs to be disjoint, which means that
some features like observation and conditioning will not work if they attempt to span the disjoint
BDDs. However, one of the encouraging lessons of this project is that our close collaboration with
Northeastern University allowed for us to progress relatively quickly despite these challenges, and
we are confident that these challenges can be mitigated as Roulette matures.
The second challenge was implementing continuous random variables in Roulette using discretiza-
tion. The performance of discretized continuous distributions varies widely between programs and
can introduce large error in the results. This is discussed in more detail in section 3.3.
The third challenge that we encountered was opaque scaling. By “opaque scaling,” we mean in
some cases the relationship between how the code is written and how performance scales is difficult
to predict. We were able to understand and mitigate some of the factors behind bad scalability (e.g.,
making numbers symbolic and “pushing down” if-statements), but there were many instances, even
after using these techniques, small changes to the program resulted in vastly different performance.
This is because solving the BDDs that Roulette programs are translated to is a #P-hard problem, so
sometimes the size of the resulting BDD is exponential in the number of terms. In order to be able
to accurately predict the performance of Roulette programs, an expert understanding of how it is
implemented and of BDDs is necessary.
There were also some positive lessons learned. The first, which we discussed previously, was
that the close collaboration with Northeastern allowed us to make quick progress and affect future
research. Roulette is a new project and therefore does not have much documentation or any large-
scale examples to compare with when attempting to learn it. With the assistance of the developers
of Roulette, a researcher with no knowledge of probabilistic programming languages was able to, in
the span of 3 months, develop a small standard library and create examples for multiple application
domains, which is an encouraging sign for the effectiveness of this approach. In addition, there is
currently a lot of interest in developing probabilistic languages and tools, so Sandia being an early
adopter and close collaborator in this space gives Sandia influence over future research. The second
positive lesson learned was that embedding Roulette within Racket allows for an extremely high
level of expressivity compared to other probabilistic languages. Racket is a very mature programing
language, so being able to easily use all of its features makes writing complex programs in Roulette
much easier compared to other PPLs. Also, there are many cases where the non-probabilistic parts
of a program are much larger than the probabilistic parts, and in these cases the expressivity of the
language becomes even more important.

5.2. Impacts

This work demonstrates that modeling complex systems is much more tractable and efficient with
PPLs, and even more so with exact inference because of their precision when modeling complex
systems. We also demonstrated that Roulette’s discrete-only model can still effectively model
interesting phenomena while maintaining expressiveness. This work also indicates areas of future
research into scalability and accuracy analysis of programs using continuous distribution approx-
imations. We found that the usability challenges of domain-specific probabilistic programming

 29

languages (via the LOP approach) can be mitigated by a standard library of relevant functions.
While LOP-based approaches permit the flexibility to encode probabilistic data in a wide variety
of domains, the lack of built-in primitives can make development difficult.
Our development of a standard library means the domain-specific language approach is more fully-
featured. When performing statistical analysis, users expect a baseline level of functionality in line
with pen-and-paper techniques that this library implements. This work also indicated directions for
future study: because systems are often analyzed using both discrete and continuous probability
distributions, Roulette’s discrete-only model can still effectively model interesting phenomena.
This work demonstrates the expressiveness of Roulette while indicating areas of future research into
scalability and accuracy analysis of programs using these continuous distribution approximations.
We demonstrated the effectiveness of LOP paired with a standard library approach by comparing
Roulette with an existing probabilistic programming language, WebPPL, and showed that exact
inference can provide benefits over the sampling-based approach of WebPPL.
Our modeling of a cosmic ray’s effect on a RAM controller demonstrates, with further develop-
ment, this approach can be used to model more realistic microelectronics under harsh radiation
environments such as outer space.
Even so, this work shows that with relatively low development effort, users can quickly and
effectively model complex systems using probabilistic programming languages. This preliminary
study can help guide future improvements to Roulette. The design questions with precision,
scalability, symbolic values, and discretization error opened up an interesting design space for
how probabilistic programming language libraries can be designed in future languages to be most
effective for developers.

5.3. Future Work

We have identified three possible categories for future work: usability improvements, new features,
and novel capabilities. Improving usability can take many forms, the most obvious of which is to
make the error messages better. One possible way to do this would be to add types to Roulette,
which would have the effect of turning what would have been Rosette error messages into type
errors that the Roulette developers have control over. Types could also help one of the other barriers
to usability we mentioned, which is the need to manually turn the support of a distribution into a
symbolic union. Removing the need to manually create symbolic unions would reduce overhead
and make writing Roulette code more intuitive. Additionally, as we discussed previously, one of the
roadblocks preventing Roulette’s use for industrial scale systems is its difficulty scaling. One of the
ways that scaling could be improved is by improving RSDD or adding new knowledge compilation
backends that may scale better on certain types of problems.
There are many new features that could be added, but one of the most impactful would be to
support continuous random variables natively. This could include creating more sophisticated
discretization, supporting exact symbolic inference via a computer algebra system, or some other
techniques. There could even be multiple backends for continuous random variables that the user
could easily switch between depending on their requirements. One existing project that is related

 30

to this and could serve as a useful comparison is a project called MultiPPL [13], which describes
and implements the semantics of interaction between a language that supports discrete random
variables and a language that supports continuous random variables. By decoupling the languages
that support the two different types of variables, it might be easier to have multiple separate backends
for each one. Another possible extension to the language could be incorporating automatic error
bounds propagation directly into Roulette and RSDD in order to provide greater guarantees over
the results Roulette programs can generate. This could include adding support for exact rational
numbers in RSDD via one of the many Rust packages which provide rational numbers.
Instead of developing features in the underlying host language, RSDD, or the standard library,
further development could focus instead on building multiple more specialized domain-specific
libraries and languages. This is the LOP approach where each problem domain has its own new
language with features tailored to each application. Given the dissimilarity of the many possible
application domains for which PPLs are useful and the fact that Racket provides a very powerful
system for creating and using domain specific languages via the #lang directive, it might make
more sense to create many small DSLs instead of adding more features to a monolithic standard
library.
One last possible direction would be to develop unique novel capabilities that are more experimental
in nature. An example of this would be to use Roulette’s native notion of semirings to allow for
probabilistic reasoning of special types of numbers. Semirings are sets equipped with addition and
multiplication (with respect to the type of the elements in the set). The base Roulette implementation
currently only has a semiring defined for the real numbers, but the notion of semirings is generic
over the type they are defined on. There are other special types of numbers (e.g., dual numbers) that
have unique and interesting properties, and having probabilistic reasoning capabilities over such
numbers would be extremely novel. Another interesting project could be implementing sensitivity
analysis in Roulette. Sensitivity analysis is related to the uncertainty/error propagation we discussed
previously, but instead of measuring the overall uncertainty, it measures the relative impact different
inputs to some “black box” program have on the uncertainty of the result.

6. Conclusion

Overall, in three months, in collaboration with the developers of Roulette, we were able to develop
a standard library containing 15 distributions and modeled multiple complex examples spanning
multiple application domains. This indicates that PPLs have high potential to be a cost-effective and
efficient way to reason about complex systems in mission-critical domains. However, PPLs still face
usability and scalability challenges that make them difficult for non-experts to use effectively. We
believe that with more development these challenges can be mitigated and there is great potential
to build novel capabilities using PPLs. Sandia is in the unique position to guide the development
of PPLs towards mitigating these challenges, model mission-scale systems, and the development
of analysis for robust microelectronics.
