1 Optimizing MPI Communication. First report
1.1 Context
I worked on optimizing the scaling of our application in HARD using the MPI backend. Us-
ing Hydro as a reference, the benchmark below shows that MPI communications introduce a
significant overhead between 1 and 2 processes. Note that in our application, the number of
communications per process does not scale with the total number of processes, which explains
the decrease in overhead between 3 and 4 processes.

 Figure 1: Benchmark showing MPI communication overhead

 Based on these observations, I propose several contributions to optimize MPI communica-
tions. Hydro is a good application to evaluate these optimizations because, as shown in the
timeline below, execution is dominated by MPI communications (red) rather than computation
(blue).

 2

 Figure 2: Timeline showing MPI communications (red) vs computation (blue)

 The optimizations I implemented and evaluated are:

  1. Reuse the same device gather buffer across all field iterations (one-buffer)

  2. Avoid zero-initializing the host buffers used for MPI communications (one-buffer-host)

  3. Use pinned host memory allocated from a local MPI backend pool (one-buffer-pool)

  4. Replace MPI_Waitall with MPI_Waitsome (pool-waitsome)

 Each optimization builds on the previous one. The code for all versions is available on the
following branch: mpi_one_buffer.

1.2 one-buffer
The timeline below shows that a new device buffer is allocated several times, even though exe-
cution is sequential and not asynchronous with the GPU. Therefore, there is no reason not to
reuse the same device buffer across field iterations.

 Figure 3: Timeline showing multiple buffer allocations

 To fix this, I first iterate over all MPI_Send operations to compute the maximum required
buffer size. I then allocate a single device buffer outside the two loops.

 3

 Figure 4: Timeline with single buffer allocation

 This also reduces the number of expensive CUDA API calls.

 Figure 5: Statistics showing reduced CUDA API calls

1.3 one-buffer-host
We can also look at what the CPU does between CUDA calls during gather operations. Unlike
scatter operations, gather operations contain noticeable gaps.

 Figure 6: Timeline showing gaps during gather operations

 Zooming in shows that the CPU spends this time performing memset operations. These come
from zero-initializing the host buffers used for MPI communications.

 4

 Figure 7: Detailed view showing memset operations

 This initialization is unnecessary because these buffers are immediately overwritten by the
communication. I replaced the std::vector allocations with manual allocations that do not
initialize the memory. As a result, the CUDA calls are now contiguous.

 Figure 8: Timeline with contiguous CUDA calls

1.4 one-buffer-pool
As Maxime previously showed, transfers using pinned memory are much faster than transfers
using pageable memory. The goal is therefore to use pinned memory for CPU-GPU copies.
Unlike Maxime’s work, I only apply this optimization to MPI communications. This limits the
scope of the changes to the MPI backend and avoids any impact on Legion or HPX.
 Replacing the host buffers with pinned memory (Kokkos::SharedHostPinnedSpace) intro-
duces additional allocation (cudaHostAlloc, green) and deallocation (cudaFreeHost, pink) over-
head. As a result, performance becomes worse instead of better.

 Figure 9: Timeline showing allocation overhead with pinned memory

 To avoid this overhead, the buffers must be reused and allocated only once during the appli-
cation lifetime. I implemented a local MPI buffer pool that allocates pinned buffers on demand
and reuses them after release.
 This provides several benefits:

 5

  1. CPU-GPU transfers become faster.

  2. Pinned memory allows asynchronous GPU operations, unlike pageable memory. As a result,
 copies and kernels during the scatter phase can now be launched asynchronously, reducing
 GPU launch overhead.

 Figure 10: Asynchronous operations during scatter phase

 For gather operations, a synchronization (cudaDeviceSynchronize, highlighted in gold) is
 still required after the copy to ensure it completes before issuing the MPI_Isend.

 Figure 11: Synchronization during gather operations

  3. In the previous versions, host buffers were deallocated immediately after the MPI commu-
 nications, making this cost visible in the timeline.

 Figure 12: Timeline showing deallocation cost

 With the pool implementation, buffers are simply returned to the pool and kept for future
 reuse.

1.5 pool-waitsome
To further improve communication overlap, we can observe that MPI_Waitall still represents a
significant period where both the CPU and GPU wait for all communications to complete before
continuing.

 6

 Figure 13: Timeline showing MPI_Waitall blocking period

 Instead, the CPU should process messages as soon as they arrive. Replacing MPI_Waitall
with MPI_Waitany allows each completed message to be processed immediately.

 Figure 14: Timeline with MPI_Waitany

 Sometimes, several consecutive MPI_Waitany calls are observed, suggesting that multiple
messages are already available but are still processed one at a time. Using MPI_Waitsome allows
several completed messages to be returned in a single MPI call, reducing MPI overhead.

 Figure 15: Timeline with MPI_Waitsome

 In the current application, MPI_Waitsome rarely returns multiple completed messages, so its
benefit over MPI_Waitany is limited. However, this behavior strongly depends on the application
and the communication pattern.

1.6 Results
The figure below shows the performance of the different versions. Each optimization improves
performance, with the largest speedup obtained by the pool version. The benchmarks were
executed on the cn2 node of Darwin (4 GPUs), and each configuration was run four times.

 7

 Figure 16: Performance comparison of different optimization versions

 The largest speedups are observed with 3 processes, where our application has the highest
communication-to-computation ratio per process.
 The MPI_Waitsome version does not improve performance and is slightly slower. In theory,
it should almost hide the scatter phase by overlapping it with MPI_Wait. However, this is not
what we observe in practice, and I do not currently have an explanation.
 Based on these results, I recommend keeping the optimizations up to the pool version only.

1.7 Future Work
The timeline below shows that the GPU is either computing or copying data, but not both at
the same time.
 One possible direction would be to use two independent streams (Kokkos::ExecutionSpace).
Half of the work could be scheduled on each stream so that one stream executes computation
while the other performs memory transfers. This could improve GPU utilization by overlapping
computation and memory. The same idea could also be applied during the scatter phase.

 Figure 17: Potential for overlapping computation and memory transfers

 The optimizations still need to be evaluated for CPU-only execution. They should remain
beneficial, although pinned memory would no longer provide any advantage. In that case, the
buffer pool should instead allocate pageable host memory.

2 Optimizing MPI Communication. Second report
2.1 Proposed Integration
To evaluate whether these optimizations can be adopted more broadly, I review how they could
be integrated into the FleCSI architecture and discuss their implications.

2.2 Algorithmic Optimizations
The one-buffer and one-buffer-host optimizations are entirely confined to data/mpi/copy.hh
and should not impact the rest of the codebase. They are purely algorithmic improvements that
make better use of the communication buffers without modifying the overall behavior of the
application. As a result, I do not see any limitation to adopting these changes since they only
provide performance improvements.

2.3 Pinned Memory
The one-buffer-pool optimization relies on pinned host memory (Kokkos::SharedHostPinnedSpace).
To make this optimization beneficial, the communication buffers must be reused across MPI it-
erations to avoid the cost of repeated allocations and deallocations. This naturally requires the
introduction of a memory allocator.

2.3.1 Implementation
I recommend implementing this allocator as a memory pool. MPI communications are static,
making a pool well suited since the same buffers can be quickly reassigned between itera-
tions. Other allocator designs remain possible. I also recommend restricting its usage to
data/mpi/copy.hh, ensuring that the optimization remains isolated from the other backends
(Legion and HPX).
 The allocator could be implemented as a singleton since copy_engine : local::copy_engine
is not used concurrently. A single allocator instance is therefore sufficient for the entire applica-
tion lifetime. This singleton could be attached to the global context_t singleton, more specif-
ically to the local MPI context (struct context_t : local::context). The MPI context
initialization callback could initialize the allocator, which would then be destroyed together with
the MPI context.

2.3.2 Implications
Introducing a pinned memory allocator raises several points that should be considered.

 1. The memory allocated by the allocator would not be used by the rest of the FleCSI ap-
 plication (task execution), since that part allocates buffers independently of the backend.
 However, the allocator allocates “pinned” memory which is currently unused by the FleCSI
 application, thereby avoiding contention for this memory between task execution and MPI
 communications.

 2. My current implementation implicitly assumes that pinned memory is unlimited. In prac-
 tice, this is not true since pinned memory cannot be paged and is therefore a limited
 resource. The allocator must determine whether a pinned allocation can succeed. Two
 approaches are possible:

 • Define a fixed portable upper bound on the amount of pinned memory that can be
 allocated.

 9

  • Attempt the allocation and catch the std::runtime_error exception raised by Kokkos
 if the allocation fails.

I recommend the second approach since it delegates the decision to Kokkos rather than
relying on an arbitrary limit. When a pinned allocation fails, a fallback strategy is required.
One possible implementation is:

  • Synchronize the current MPI communications to ensure that temporary buffers are
 released.
  • Fall back to allocating pageable host memory instead of pinned memory.

This first approach has one limitation. If the application repeatedly requests very large
communication buffers, these additional synchronizations may reduce the overlap between
successive communications. Therefore, I recommend the second solution because it is
straightforward to implement and its downside is limited to slower transfers for the affected
communications, while preserving correctness and avoiding allocation failures.

3 Optimizing MPI Communication. Third report
3.1 Application Behavior
By profiling and benchmarking different workloads on Hydro and MM-Hydro (multi-material),
I observed several communication patterns. Each pattern is affected differently by the opti-
mizations I propose. Evaluating a diverse set of patterns ensures, at a minimum, that these
optimizations do not degrade performance for end users across different applications.
 My evaluation strategy is to first identify the different communication patterns and analyze
how each optimization changes their behavior. This allows me to verify that the expected
execution behavior is observed. I then validate the optimizations experimentally through a
series of benchmarks.

MPI communication phase.

3.2.1   Scatter
To overlap computation and memory transfers, I use two execution streams (Kokkos::partition_space(2,
...)). Each stream executes alternating copy-kernel pairs.
 The expected speedup is bounded by the total kernel execution time during the scatter phase,
as these kernels can potentially be hidden behind the memory transfers.
 Across all previous workloads, Host-to-Device transfers are consistently longer than the ker-
nels themselves. Therefore, the theoretical speedup corresponds approximately to the cumulative
kernel execution time in the scatter phase.
 For the many-large workloads, computation and memory transfers clearly overlap, leading
to much higher GPU utilization. However, using two streams requires a dedicated device buffer
per stream. For the 7x8x8 workload, the additional allocations and deallocations introduce a
noticeable overhead.

3.2.2   Gather
The gather phase follows the same two-stream strategy but is more challenging because each
pair of device operations must eventually trigger an MPI_Isend.
 Instead of synchronizing immediately after launching work on one stream, I first submit
one pair of operations to the first stream, then another pair to the second stream. Only when
returning to the first stream do I synchronize it and issue the corresponding MPI_Isend. The
process is then repeated. This approach is inspired by the pipelined execution model used in
modern CPUs.
 This optimization can accelerate the gather phase and increase the rate at which MPI_Isend
operations are issued. However, if the MPI network becomes saturated, part of the expected
gain may be lost due to increased network contention.
 For the many-large Hydro (10x9x9) workload, GPU utilization is almost ideal.

From the previous observations, device buffer allocation represents a significant overhead, espe-

when using two streams.

This version combines the previously introduced wait-some implementation with the two-stream

3.6 Future Work
I presented several communication patterns to evaluate the impact of these optimizations. A nat-
ural next step would be to evaluate them using dedicated microbenchmarks. This would isolate
the communication layer from the application itself and provide a more precise understanding of
each optimization.
 Another promising direction is the use of Kokkos::Graph for applications with static com-
munication patterns. Graph execution would allow all GPU operations to be submitted at once,
reducing launch overhead and potentially providing additional benefits, especially for smaller
workloads.

4 Out-of-Core Issue
4.1 Context
Scaling the size of a FleCSI problem requires scaling the number of nodes to provide enough
memory. This is particularly important for GPUs, where memory is significantly more limited
than on CPUs. This raises two concerns:
 • Dependence on cluster availability, where even a short simulation may require waiting
 several hours or days for enough nodes.
 • Limited scalability, since the total number of available nodes is finite.
 Similar constraints also motivate other data structures, such as Ragged. However, solutions
are still needed to enable large-scale simulations under limited memory capacity.
 One possible approach is inspired by out-of-core computing, a concept I originally en-
countered in large-scene rendering, where data that is not currently needed is temporarily moved
to disk. A similar mechanism could be introduced in FleCSI at two levels:
 • GPU data that is not currently needed could be temporarily moved to host memory.
 • GPU or host data that is not currently needed could be temporarily moved to disk.

4.2 Conceptual Proposal
Building on FleCSI’s color-based partitioning, a second level of decomposition could be intro-
duced. The hierarchy could look like:
 • Distribution across cluster nodes.
 • Subdivision of each color into smaller local blocks.
 These smaller blocks could be processed sequentially, with only the current block resident
in memory while the remaining blocks are stored on disk, or potentially in host memory when
using GPUs.
 One potential bottleneck involves ghost-cell exchanges in distributed MPI computations.
With this approach, ghost cells should remain resident in processor memory and be read-only
during block processing. Otherwise, processing the first block could update ghost values before
its neighboring block has been processed. Therefore, the relevant ghost-cell values must be
preserved before processing begins.
 Disk I/O would likely be one of the main performance bottlenecks. Its latency could be
hidden through asynchronous pipelining:
 • Prefetch block N + 1 while processing block N .
 • Write block N − 1 while processing block N .
 This would overlap disk I/O with computation.
 Finally, regardless of the implementation, the traditional in-memory execution path must
remain unaffected in terms of performance when out-of-core execution is not used.

4.3 Legion Alternative
From my understanding, the Legion backend may provide an alternative approach. More colors
could be assigned to each processor, reducing the size of each individual domain. Legion could
then serialize tasks to execute these domains sequentially.
 This could be an attractive solution because it might require no changes to FleCSI itself,
potentially only an appropriate Legion configuration.
