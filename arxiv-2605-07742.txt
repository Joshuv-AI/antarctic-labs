Suitability of the Data Distribution Service for Next-Generation Ethernet-Based Agricultural Machinery Networking
Samuel Brodie, Henri Hornburg, Daniel Ostermeier, Maksim Pavlov, Timo Oksanen

Abstract
The current state of the art in the agricultural industry for inter-manufacturer, plug-and-play communications is the ISO 11783 standard series, which mandates the use of 250 Kb/s CAN bus. To support higher data rates, the ISO 23870 series is under development, defining a gigabit automotive Ethernet physical layer for next-generation machine-to-machine communication networks. However, middleware is needed to handle the complexity of the system by providing an additional layer of abstraction. It should address the future needs of the industry such as higher levels of automation, additional data logging, modern data types, quality of service configuration, and best-practice cybersecurity. Data Distribution Service (DDS) is a potential middleware for use in such a network. DDS provides many features not present in the current ISO 11783, it is a standardised protocol for data sharing between distributed applications. This work analyses the extent to which DDS can be used to develop a system which meets the requirements for next-generation communication networking for agricultural machinery. A proof-of-concept design is presented, including a Task Controller and implement and it is shown that the requirements are fulfilled. A new DDI concept is proposed that decomposes the monolithic numeric DDI of ISO 11783 into separate typed Enums for handling group, handling feature, and SI units, enabling more flexible signal definitions. Four security configurations are tested in the proof-of-concept implementation and it is shown that enabling security features has a significant impact on throughput.



keywords

ISO 11783, DDS, ISOBUS, Agricultural and off-highway vehicle networking, Machine-to-machine communication

1
Introduction

The ISO 11783 standard series defines an inter-manufacturer, plug-and-play communications interface for agricultural vehicles; it enables various functionalities such as automatic implement control and user interface uploads. The standardised physical layer is 250 Kb/s CAN bus
[
14
]
. ISO 11783 has been standardised since 2001
[
7
]
and a new standard series, ISO 23870, is under development to address the industry’s future plug-and-play use cases, such as improved Task Controller (TC), camera integration
[
21
]
, advanced automation, and modern cybersecurity.

ISO 23870 is a spiritual successor to ISO 11783 and standardises Ethernet and IP for the lower OSI layers. The added complexity of an Ethernet network and IP layers means that instead of standardising individual Ethernet/IP packets (as is done with CAN in ISO 11783), the complexity can be better managed by using a standardised middleware layer to benefit from the large community of products and vendors which exist to solve similar connectivity challenges. Middleware is a class of generic software components which typically supports standardised interfaces and protocols, and enables distributed computing
[
5
]
.

Various middlewares exist, and each has unique benefits and drawbacks. One such middleware to be considered is the Data Distribution Service (DDS), a middleware standardised by the Object Management Group (OMG) for interoperable, data-centric communication.

This work investigates to what extent DDS is a suitable middleware for development of a next-generation, wired, machine-to-machine interoperability network for agricultural machinery (such as that shown in Figure
1
, for example), with a particular focus on the ISO 11783 TC functionality.

Figure 1:
A typical use case for next-generation agricultural machinery networking. An Ethernet network connecting a tractor (T-ECU), implement, Virtual Terminal (VT), and Task Controller (TC), which could all be from different manufacturers. The topology uses peer-to-peer connections via Ethernet switches.

This article addresses in-vehicle networking for agricultural machinery using the upcoming ISO 23870 lower OSI layers (UDP/IP). It assumes that devices connecting to the network are able to obtain an IP address (e.g. via SLAAC) before the middleware discovery begins. The article focuses on how the DDS middleware layer can be used from that point onwards, including the use of predefined multicast IP addresses and port numbers for the DDS discovery messaging. The ISO 23870 standard under preparation is intended for multiple industry groups in addition to agriculture: Construction, earth moving machinery, mining, forestry, and on-road truck & trailer. This article focuses on the needs of the agricultural industry, although there is overlap between the needs of all groups.

In this article, the comparison of the performance of different DDS libraries, and performance benchmarks of DDS for embedded hardware in general are not considered. The objectives of this work are to:

•

Analyse whether DDS meets the minimum requirements for next-generation agricultural machinery networking, including inter-manufacturer plug-and-play with service discovery, support for existing ISO 11783 functionalities, and a black-channel approach to functional safety

•

Design and implement a proof-of-concept DDS-based Task Controller system to demonstrate plug-and-play interoperability.

•

Assess and evaluate whether DDS information modelling capabilities are suitable for modelling the Device Descriptor Object Pool (DDOP) with at least the same level of detail as in ISO 11783.

•

Evaluate the impact of DDS security configurations on runtime throughput.

•

Evaluate to what extent DDS meets the requirements for next-generation agricultural networking in general.

1.1
Research gaps

Middlewares such as OPC UA have been researched for agricultural machinery and ISO 11783 Task Controller
[
40
]
. However, no reported studies were found that address the use of DDS in plug-and-play systems of this nature where a non-technical end user connects two or more
DomainParticipants
. The scenario presents unique challenges which are not considered in automotive environments where all sub-systems are produced together at the factory and the end customer is not changing the network by adding or removing nodes.

Specifically, the agricultural machinery scenario presents unique technical challenges that distinguish it from other DDS application domains such as automotive or robotics: 1) the network topology is unknown at build time and changes when implements are connected or disconnected, 2) devices from independent manufacturers must interoperate without prior coordination, 3) the end customer is non-technical and cannot perform manual network configuration, 4) machines may operate without internet connectivity and 5) equipment has long product lifecycles (10-20 years), requiring forward-compatible designs. These challenges are not present in automotive environments, where all sub-systems are produced together at the factory.

2
ISO 11783 Task Controller

The ISO 11783 TC is a functionality whereby a TC client (implement) connects to a TC server; the TC server issues commands to the implement, and the implement sends logging data to the TC server
[
13
]
. The TC server uses its internal proprietary algorithm, based on the field boundaries, the GNSS position, velocity, and turn-on/off delay times to send commands at the appropriate time as the driver manoeuvres the tractor through the field. The TC server plays no part in route planning, or control of the driving.

To enable interoperability, ISO 11783 defines how a TC server should discover the properties of the connected implement and this is via the Device Descriptor Object Pool (DDOP) which defines the geometry, and controllable aspects of the implement (on/off sections, controllable application rates etc.). Then, the runtime process data is updated by transmitting CAN frames.

3
DDS

3.1
DDS overview

The Data Distribution Service (DDS) is a middleware standardised by the Object Management Group (OMG)
[
23
,
24
,
25
]
which enables a data-centric, real-time publish-subscribe architecture between nodes, which are called
DomainParticipants
.

3.1.1
Endpoints

Endpoints are either readers or writers. A single endpoint is never both a reader and a writer; to both read and write to a topic therefore requires at least two endpoints. Each endpoint read/writes to a single topic. Readers are organised by subscribers, and writers are organised by publishers. The publishers and subscribers are themselves organised by a
DomainParticipant
.

3.1.2
Topics

A topic is an abstraction for organisation of data which is uniquely identified by a topic name, topic partition, and data type. Data samples (data updates) associated with a particular topic will be sent to the endpoints associated with it and therefore the topic is not an entity that exists on any particular participant.

From the application’s point of view, applications interact with topics solely by sending data to or reading data from their local endpoint, without requiring direct awareness of the remote endpoints on other devices as this is handled at the middleware layer.

Conceptually, an application may be designed to remain agnostic to the presence of other participants, relying instead on the middleware to maintain and present a consistent view of the topic’s data. Alternatively, an application is still able to verify who is publishing each data sample if required, and the security concept provides tools to avoid spoofing of messages.

Figure 2:
The DDS middleware maintains a matrix for each topic which represents the current state of the system. Applications can either react to each sample update or can query the whole state of the topic as required. The columns are defined by the topic’s data type and the rows are defined by the different keyed values.

3.1.3
QoS profiles

Quality of Service (QoS) profiles can affect network-level messaging by setting data transfer to reliable, or best effort, or configuring the data update frequency.

QoS profiles affect not only network-level messaging but also memory management. Each topic can be thought of as a matrix, with a row for each key field value and a column for each field in the data type. The middleware automatically handles the memory management such that DDS is maintaining the state of the topic for the application. For example, the history QoS allows the application to define how many previous samples should be stored. In the case of "HISTORY=1" then the middleware can automatically drop old data and replace it with the most recent data. In the case of "HISTORY=ALL" then the middleware will store all previously sent samples that its memory allows.

When a data type is a struct, key fields can be defined for the topic. When a new DDS sample is received, it can be known if this is a new source writing for the first time (adding a new row) or if it is an update of an existing source. In the example in Figure
2
, data from different sources (different valve numbers, or front-hitch/rear-hitch) should be sent on the same topic while being distinguished through a key, instead of being sent on multiple different topics. A DataReader that only needs data from a particular source can then filter on the key to obtain only this data. If it should be enforced that only one DataWriter can write to a topic using a specific key field value, the OWNERSHIP QoS should be used.

3.1.4
DDS discovery

When dynamic discovery is used, rather than having fixed participants and addresses, the DDS domain participants discover one another on the network and then coordinate the connections between their endpoints and share their QoS policies. The DDS standard specifies a discovery protocol called the Simple Discovery Protocol (SDP). It is stated in the specification that all implementations must support this. The SDP is a completely peer-to-peer discovery mechanism, which does not need any server or broker. The SDP is split into two phases, the Simple Participant Discovery Protocol and the Simple Endpoint Discovery Protocol.

In the participant discovery phase, the domain participants announce themselves to one another. In the participant announcement message the domain participants announce the IP addresses and ports that they have open to receive the endpoint discovery messages in the next phase. As the domain participants are not known at compile time, they use a pre-known multicast IP address and port number to send these messages. Therefore, as a minimum in the Simple Participant Discovery Protocol, each participant must send one multicast packet and receive a multicast packet from each other domain participant.

3.2
DDS security

The OMG DDS Security Specification defines a security model and a Service Plugin Interface (SPI) which enables a zero-trust architecture. The configuration is defined in each
DomainParticipant
’s Governance Document which defines which parts of the security framework it enables. The entity being secured is a specific DDS domain and, within the domain, the ability to access (read or write) information within the domain. The DDS Security Specification also defines builtin interoperable plugins for authentication, access control, and cryptography
[
25
]
which allow for mutual authentication of
DomainParticipant
identities using a central root Identity CA which signs x509 certificates. The security is robust
[
19
]
, however, metadata such as topic names and permissions can be leaked to eavesdroppers
[
27
]
and enabling DDS’ security features has been shown to reduce both discovery
[
33
]
and runtime
[
10
]
performance.

Using the builtin Access Control plugin,
DomainParticipants
have a Permissions Document which is signed by a central root Permissions CA and linked to the
DomainParticipant
’s identity. The permissions document gives a list of rules and actions that each
DomainParticipant
should be allowed to do in the network.

4
Minimum requirements of DDS for next-generation networking

The minimum requirements for next-generation networking are:

•

Conform to ISO 23870 lower layers:
The middleware must use the physical and data link layers (OSI layers 1-2) which are already agreed and standardised i.e. it must conform to the (draft) ISO 23870 standard documents which mandate the use of 1000BASE-T1
[
16
]
. In addition, standard technologies for the Network and Transport layers should be used, i.e. Internet Protocol (IP).

•

Provide inter-manufacturer, plug-and-play with service discovery and identification of device types:
The network must not require any manual configuration by the user to enable communications between connected devices. Services (e.g. TC client/server) should be discoverable dynamically.

•

Enable existing ISO 11783 functionalities:
The next-generation middleware must support the full functionality the TC clients and servers defined in ISO 11783. The ISO 11783 and SAE J1939 series collectively define over 10,000 signals, known as Suspect Parameter Numbers (SPNs). Although most implementations only use a subset at any given time, a future-proof middleware must be able to accommodate the potential presence of any SPN during network operation.

•

Enable a black-channel approach to functional safety:
In ISO 11783 CAN bus networks, the communication medium is trusted for safety and thus is a white-channel, which does not require functional safety of the communications at the application level. However, the new ISO 23870 network is not a trusted white-channel, therefore a black-channel approach to functional safety is required instead, adhering to the functional safety concepts in ISO 25119. In a black-channel approach end-to-end safety-related elements need to be added to communications at the application (middleware) layer e.g. message authentication codes.

The design allows for a DDOP to be automatically uploaded to the server by setting the DURABILITY QoS to DURABLE in the
t_ddop_hierarchy
and
t_ddi_linking
topics without the need for a periodic TC-status message as in ISO 11783.

The element numbers in a DDOP are only unique within each implement. To identify a DDOP element in a globally unique way it is not enough to have the topic key based solely on the element number, because if two implements connect to the topic, there could be a mismatch. There are two methods to address this, either a NAME field is added to the topic data type as a key field, or the implements join topic partitions based on their NAME. The first scenario is simpler, however the implements would be able to read the information shared with other implements, and origin authentication would be required to stop spoofing of messages. In the second scenario, each implement needs to configure a partition based on its name, and cease sending and flag an error if another TC client is detected connecting to the partition. This is more complex but origin authentication is not required because only endpoints from the two devices are present, the TC server and one implement. Presented for this paper is the second option without origin authentication.

DDS does not allow modelling of the transferred data as a parent-child relationship. However, this type of relationship is required for maintaining at least the same modelling functionality as in the ISO 11783 DDOP, which is a hierarchy of parent and child elements with DDIs attached to them. Therefore, this parent-child relationship needs to be constructed on the application layer by including an additional “parent reference” in the
DeviceElement_t
struct. In this way, the developed equivalent to an ISO 11783 DDOP upload is publishing to the
t_ddop_hierarchy
and
t_ddi_linking
topics after joining the domain.

5.3.3
New DDI concept

The TC concept presented here implements a new style of DDIs. In current ISOBUS, there is a numeric DDI that defines: the physical group that the signal belongs to (e.g., application rate, tillage depth), the feature of the signal (e.g. setpoint, actual), and the units (mass per time [mg/s], volume per time [mL/s], mass per area [mg/mˆ2]).

In the presented concept these elements are split out into separate Enums:
HandlingFeature_e
,
HandlingGroup_e
and
Unit_t
(which contains two Enums for unit numerator and unit denominator). The units are only permitted to be defined in SI units, as the purpose for this is not to handle different units used by farmers in different regions, e.g., tonnes versus ounces, but instead to handle the units in terms of volume, mass, count, etc.

5.3.4
Process data

After the DDOP hierarchy and the respective DDIs are written to the
t_ddop_hierarchy
and
t_ddi_linking
topics respectively, control can begin, i.e., the implement can notify that it is ready to work, and the TC server can begin to send setpoints, and receive actuals.

Some of the process data values shared between the TC server and implement such as application rates are generally sent with a high update frequency. Other process data values, such as geometry values, are sent infrequently and it is important to ensure that they are received correctly. This split between frequently updated and rarely updated leads to a split of wanting some values to be sent with best-effort and some values to be sent reliably. Since best-effort and reliable are different QoS values, the process data is split into two topics with different QoS settings. These topics are called
t_pd_values_best_effort
and
t_pd_values_reliable
. This is done to avoid the system being designed to contain endpoints with mismatched QoS which fail to connect and make future troubleshooting more complex. The transfer of setpoints and actuals (process data variables) uses the
ControlHandlingValues_t
data type as shown in Table
11
and Figure
3

The
ControlHandlingValues_t
data type is used in both the reliable and best-effort process data topics. The element reference of controlled/reported process acts as the key field, the handling group Enum indicates the real-world process attached to the value, the units represents what type of units are used (e.g., mass or volume) and finally the value itself, whose interpretation depends on the handling feature (e.g., setpoint, actual, minimum). 5.3.5
Topic partitions

Figure 4:
The data streams to and from the TC server are separated between each implement using partitions. Reliable and best-effort data is also separated.

Topic partitions are used to separate the data from each implement. The NAME in the key field distinguishes data relating to separate implements, which allows the TC server to send commands and log data to multiple implements and the implements to filter the data relevant for them within a single topic without partitioning. However, the builtin DDS Access Control security plugin does not prescribe a mechanism for restricting access to a subset of the data within a topic. This means that any implement would be able to subscribe to the information of the other implements which is a risk for safety and secrecy. To account for this, the relevant TC topics use DDS partitions to separate the data. The builtin DDS Access Control security plugin is able to restrict access to particular partitions and in this way the data of each implement are shared with the TC server and not the other implements. This concept is visualised in Figure
4
.

6
DDS applications benchmarking

6.1
Setup

The design was verified by creating an implementation in C++ using the FastDDS library version 3.2.2 and benchmarked using two devices (Windows 10 laptop, Intel Core i5-8265U CPU@1.60GHz and Windows 11 tablet, Intel Core m3-8100Y CPU@1.10GHz) which were connected via a gigabit switch. The laptop acted as TC server and the tablet acted as TC client.

A root CA was configured locally which acted as both the Identity CA and Permissions CA. Identity and Permissions Documents were configured for each application to grant them access to the domain and permission to read and write to the appropriate topics.

Multiple governance documents were created, each for testing a separate security policy. The values of discovery_protection_kind, liveliness_protection_kind, rtps_protection_kind, metadata_protection_kind, and data_protection_kind were all set to be either ENCRYPT, SIGN, or NONE. The security settings of the application could be selected from the command line to instruct the application to load the corresponding governance document, or to forego loading of the security plugins entirely (so called “Not Used” in the results).

7.2
Requirements conformance analysis

7.2.1
Conform to ISO 23870 lower layers

DDS works over standard Ethernet/IP networks and the DDS standard allows for both multicast and unicast discovery. A common discovery multicast address is required to enable discovery without prior knowledge of what other devices are to be connected.

7.2.2
Provide inter-manufacturer, plug-and-play with service discovery and identification of device types

DDS is an open standard and libraries are available from multiple different vendors. If the topic names are standardised and a strategy for QoS is in place then DDS offers plug-and-play for machine-to-machine networking.

Interoperability tests are provided by OMG which outline test scenarios. Vendors of DDS libraries may upload their library’s implementation of the tests to have them included in the interoperability tests
[
31
]
. However, currently the compatibility between some implementations is not 100% and the security tests are outdated.

Care must be taken that some QoS policies are incompatible and so a minimum level of offered QoS must be standardised for all devices, and a device which is requesting a QoS level which is higher than that must therefore have the capability of lowering its requested QoS to enable the connection, otherwise interoperability is harmed. For example, a reader may request a DEADLINE QoS of 10ms, and a writer may only be capable of offering data every 100ms, then the QoS policies of the reader and writer are incompatible and communication does not start. In this situation, to maintain plug-and-play, the reader must change and request a DEADLINE of 100ms.

Each topic has a data type, which for practical purposes should be set at compile time. Although are methods in the DDS standard to share this information at run-time with Dynamic Language Binding, this is unsuitable for machine-to-machine operation for several reasons: a strong link needs to be created between the topic and the physical process it represents, functionally safe programming standard ISO 25119-3 does not allow for dynamic memory allocation
[
15
]
, and at time of writing this is not widely supported in DDS libraries.

The SDP allows for dynamic discovery of
DomainParticipants
. For service discovery, using a dedicated topic for service announcement is possible as shown in Section
5.2
. Additional information about
DomainParticipants
can be given in their metadata fields to enable service discovery at the middleware level.

7.2.3
Enable existing ISO 11783 functionalities

As shown in Section
5.3
, it is possible to both model TC client implements and recreate the ISO 11783 TC functionality with DDS. Parent-child relationships, that are not a standard information modelling feature of DDS, are possible by writing the DDOP hierarchy, supported DDIs, and process data values to separate topics. Reliable communication of process data is possible by setting the corresponding QoS, a feature absent from ISO 11783.

1-to-1 addressing is provided by using topic partitions for directed data transfer. Using partitions means that security plugins which do not support the Origin Authentication options can still verify the sender of each command.

The publish-subscribe architecture is beneficial for broadcast SPNs and the data-centric architecture of DDS allows flexibility in data sharing. For example, by setting QoS policies for negotiating the update frequency and filters.

7.2.4
Enable a black-channel approach to functional safety

The DDS Builtin Security Plugins enable application-layer message integrity checks. The Builtin Cryptography Plugin adds hash-based message authentication codes (HMACs) to messages when the SIGN, ENCRYPT, SIGN_WITH_ORIGIN_AUTHENTICATION, or ENCRYPT_WITH_ORIGIN_AUTHENTICATION protection kinds are used to protect discovery, liveliness, and simple (RTPS) data. In this way a black-channel with end-to-end authentication of message integrity is enabled over a network of unknown characteristics.

7.3
Results overview

DDS is suitable for use with ISO 23870 because of its compatibility with IP networks and the security plugins’ ability to provide end-to-end message integrity checks. It is possible to recreate the ISO 11783 TC functionality and model implements with the same level of detail. The functioning of the plug-and-play nature of the design was demonstrated with a proof-of-concept implementation and benchmarking results show that a throughput of over 4000 samples/s, corresponding to 4000 setpoint updates is possible for best-effort communication, even when encrypting the messages.

8.1
Results discussion

8.1.1
Throughput reduction with security policies

The difference in throughput between None and Not Used was negligible in all cases. This indicates that loading the security plugins but not using them for message signing or encryption did not affect runtime performance. Signing messages showed a slight improvement in throughput compared to encrypting.

There was a large difference in throughput when using cryptography (encrypt or sign) compared to not. The messages sent by the TC and received by the implement increased tenfold when security was disabled, while the impact was much lesser for the reverse case (messages sent by the implement and received by the TC) where throughput approximately doubled. The TC and implement were running on different hardware and it is probable that the difference in impact from the cryptography was due to the hardware and not the applications. The results indicate that the ability to promptly compute encrypted messages and/or signatures has a larger effect on throughput than physical layer speed. In the best-effort scenarios, more messages were received by the implement than the TC in the Encrypt and Sign scenarios, while the reverse was true for the None and Not Used scenarios. The Ethernet adapter of the laptop is Intel Ethernet Connection I219-V and the adapter of the tablet is Realtek Surface Ethernet Adaptor. It may be the case that the mismatch in processing power of the two devices resulted in the large differences in the different scenarios. It is not only on the sender side that messages need to be processed, the receiver must also decrypt and check the signatures of messages. Therefore, future work should consider the same benchmarking scenarios in embedded devices.

8.1.2
Difference in DDS implementations

Some DDS libraries do not implement the DDS standard in its entirety and so some features are not available in all vendors’ implementations and can be assumed to not be entirely interoperable, concurring with the findings of Bode, et al.
[
6
]
. For example, time-based filtering and Origin Authentication are not supported by FastDDS
[

8.1.3
Distributed systems (multiple
DomainParticipants
)

Due to the data-centric design of the middleware, the TC server and implement are not limited to being a single device each, and may instead be distributed across several ECUs and
DomainParticipants
. For example, rather than a centralised ECU within a sprayer that controls all functions, ECUs could be distributed along the boom and each could publish and subscribe to the relevant data in a distributed fashion as shown in Figure
9
. The split to per-implement topic partitions still allows for implements to be formed of multiple ECUs and/or
DomainParticipants
as the partitioned topic is not limited to any number of participants.

8.1.4
Access control permissions authority

The builtin Authentication and Access Control plugins each utilise a single central Identity CA and Permissions CA respectively. Requiring a centralised CA means that a trusted organisation is required to administer the document signatures. For the AEF TIM functionality, it has been deemed acceptable that the AEF acts as the CA for all member companies, however, for the other industries involved in ISO 23870 no equivalent organisation exists and manufacturers must organise their own one-to-one trust relationships

The purpose of the permissions document is to limit the access that a device has and stop it from being able to escalate its privileges if taken over. This also means that manufacturers who want to have proprietary and/or secret topics will need to do so in a different domain to the interoperability domain. They can then pair with only
DomainParticipants
which present their proprietary certificate and operate their own permissions CAs.

9
Conclusions

This work has demonstrated that the standardised features of DDS are suitable for allowing plug-and-play connectivity in agricultural machinery communications and for substituting the ISO 11783 lower OSI layers. The standardised Simple Discovery Protocol and predefined topics and data types allow for connections to be initialised and data to be shared without user input or prior collaborations between manufacturers of the different devices on the network.

This paper has shown through the proof-of-concept design that Task Controller functionality and the corresponding information modelling are possible using DDS and that DDS is suitable for modelling the DDOP with more detail than in ISO 11783. The system demonstrated that the use of DDS is suitable for TC server and client functionalities and plug-and-play control of implements with differing structures that are only discovered at runtime and unknown at build-time. Furthermore, benchmarking results showed the impact of different security and transport settings. Even when encrypting all data, the throughput of best-effort process data setpoints and actuals is sufficient for future use cases.

While DDS largely meets the requirements for the next-generation agricultural machine-to-machine network, there are weak areas such as limited interoperability tests and the fact that the DDS-TSN standard is still in the beta stage.

This article focused exclusively on DDS. For comparison purposes, further research is needed to focus on the relative merits of the most promising middlewares.
