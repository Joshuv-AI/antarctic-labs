ABSTRACT
The Analytic Discovery Venture Data Discovery system finds relevant or novel data in sources that
are effectively infinite, streaming, and costly to query, when the target is real but underspecified. This
report demonstrates a second kind of novelty: not novelty as retrieval, but novelty as revealed
structure. Because the discovery policy must express its hypotheses as queries executable by the data
source, the fitted decision tree at its core is inherently interpretable: every split is a readable query
clause. Across three controlled benchmarks—geospatial (OpenStreetMap), textual (Wikipedia), and
temporally drifting (Stack Overflow)—the same mechanism surfaces structure it was never told to
consider: restaurant names shifting with latitude, album articles betrayed by a document footer
phrase, and a machine-learning vocabulary self-assembling as the field's terminology emerges over
time. In each case, reading the learned structure turns retrieval into discovery, bounded ultimately by
what the source's query capability makes discoverable at all.

1. INTRODUCTION
Discovery often manifests as an "I know it when I see it" process. In contrast to detection, the target
of interest is difficult to describe ahead of time. The Analytic Discovery Venture (ADVenture) Data
Discovery system exists to find relevant or novel data in sources that are effectively infinite,
streaming, and costly to query when we cannot say in advance exactly what we are looking for. In
Data Discovery problems, the target is real but underspecified, so the system's job is to spend a
finite query budget (expressed as wall time, number of queries, or compute) on the records most
likely to be worth further analysis.
This report showcases three examples of Data Discovery finding novelty as revealed structure in
controlled benchmark experiments spanning geospatial, textual, and temporally drifting datasets.

1.1. Finding Novelty
There are two ways to read "novelty" in what Data Discovery produces. The first is novelty as
retrieval. An explicit novelty-incentivized reward steers the loop toward data that is new relative to
what has already been seen. In this setup, the system intentionally surfaces likely-target records
under a budget.
The second, and the subject of this report, is novelty as revealed structure. The discovery policy
must create plausibly useful queries and select from among them. The nature of these queries is that
they must be executable by the target data sources. This execution constraint makes Data Discovery
policies inherently interpretable. Policies necessarily encode their own hypotheses and expectations
about likely interesting pockets of data, and in so doing capture structure about the data and target
reward signal that were not specifically encoded into the discovery task. This structure reveals how
and where to look for interesting data, often exposing unexpected patterns and pockets.

1.2. Minimized Data Discovery Loop

The novelty demonstrations in this report rely upon a simplified Data Discovery feedback loop:

 1. Data sources are hosted within an OpenShift environment using realistic data-serving
 APIs, pagination, and rate limits: Wikipedia-english in Elasticsearch, OpenStreetMap
 features served over PostGIS/WFS, and Stack Exchange in Postgres through a
 deliberately impoverished REST API.
 2. Simple, directly measurable rewards are derived from records for benchmarking
 performance and revealing more direct structure.
 3. A streaming Very Fast Decision Tree (VFDT) grows over the records fetched so far, each
 one scored according to the measurable reward used for that experiment.
 4. A contextual bandit (an inverse-gap / SquareCB policy) decides which leaf-query to page
 next, balancing exploiting known-good pockets against exploring for new ones, under a
 fixed query budget.

 9

 Figure 1 - the simplified data discovery loop (data source → reward → VFDT → SquareCB policy
 → back to source).

The policy's encoding of data structure is well captured by the learned decision tree from the VFDT
module. Every split predicate in the decision tree can be translated into a real query clause: a text
token becomes a search term, a number becomes a range filter, and a category becomes a
membership test. Consequently, every root-to-leaf path in the tree is an executable query, and each
leaf is a candidate pocket of interesting data. Because a split maps to a query clause, a fitted tree
reads as a stack of hypotheses about the data (e.g., this token, in that latitude band, marks the thing
we are hunting). A discovery becomes unexpected when the system splits on something we never
told it to care about, and the split points turn out to line up with real structure in the world.

2. VIGNETTE 1 — RESTAURANT NAMES SHIFT WITH LATITUDE
In the first vignette, the Data Discovery system reveals how restaurant names in North America
depend upon latitudinal cultural-geographic boundaries. This vignette serves geospatial data through
the same interfaces used in mission-relevant data sources, and requires both spatial and feature-
attribute exploitation for successful discovery.

2.1. Setup
 • Data Source - 3,428,420 OpenStreetMap features from North America, hosted in PostGIS
 and served via WFS (GeoServer)
 • Target (Reward) - kind == 'restaurant' (185,823 positives, a 5.4% base rate)
 • Policy Setup - VFDT + SquareCB, but VFDT is intentionally blinded to the kind field.
 • Retrieval Budget - 16,000 documents

2.2. Performance
We compare three performance benchmarks in Vignette 1, shown in Figure 2, which plots the
performance of each implementation at retrieving interesting items as a function of budget
expended. First, Figure 2 shows a perfect, oracle-level retrieval given by the dashed line. This
represents perfect retrieval, with every item retrieved being interesting.
Next, we consider a reference implementation in which Data Discovery is allowed to see the kind
field directly (gray curve). This gives the policy direct querying access to the labels. The rarity of
restaurants (5.4%) means there is still a warm-up phase before the first relevant records are retrieved.
However, upon finding relevant records, the policy quickly associates kind='restaurant' with
reward and begins to exploit this directly via querying. From 2,000 to 16,000 documents retrieved,
the slope of the gray line matches the perfect oracle, which represents maximum possible
exploitation.
The final and more interesting implementation is blind to the kind label and is represented by the
blue curve in Figure 2. This system is required to learn other structure to identify pockets of label
information. As expected, it yields lower performance than the label-exploiting reference ceiling, but
from 10,000 to 16,000 documents fetched it achieves a retrieval slope nearly as good as the reference
ceiling, indicating highly performant retrieval.

Data Discovery has access to the `kind` field (gray curve) and when it is intentionally blind to the
 `kind` field (blue curve).

2.3. Analysis
The tree learns that "restaurant-ness" is not a property of the name or the location, but of the two
together, and the latitude splits it makes trace out a cultural geography of how restaurants in North
America are named. The tree encodes these policy-learned relationships on the fly without being
specifically instructed (see Figure 3).

The root of the tree funnels on an English-language restaurant vocabulary (bar, pizza, pizzeria,
restaurant, sushi). Within that English-named world, the tree further splits north/south at
latitude ≈ 40.08 (approximately the Mason-Dixon line), but both sides stay predominantly restaurant
(each leaf predicts restaurant). This cut is therefore not a change of vocabulary but a change of
target density: the same English words mark a restaurant more cleanly south of the line (an 84% hit
rate) than north of it (74%), where those tokens more often attach to bars, bakeries, and shops. The
more telling branch is the one for points that carry no English restaurant token. There, the tree splits
at latitude ≈ 21.01 (approximately Guadalajara, Mexico), and below it restaurants reappear under
Spanish and Portuguese spellings (restaurante, pizzaria, pizzas). The system discovered,
entirely on its own, that south of roughly 21°N you find restaurante and north of it restaurant.
A small easter egg rides along in that split set: apizza, a genuine New Haven, Connecticut
regionalism for pizza, which the tree picked up as a real, if hyper-local, naming signal.

3. VIGNETTE 2 – ALBUM ARTICLES REVEAL THEMSELVES
 THROUGH DOCUMENT STRUCTURE
The second vignette highlights the first text-tokenization capabilities within Data Discovery, finding
Wikipedia articles about "albums" based on the structure of those articles. This vignette serves a
bundle of text documents through Elasticsearch, a mission-relevant data source deployment.

3.1. Setup

 • Data Source - 300,000 Wikipedia English articles served via Elasticsearch
 • Target (Reward) - title contains 'album' (3,270 positives, 1.1% base rate)
 • Policy Setup - VFDT + SquareCB, but VFDT is intentionally blinded to the title field.
 • Retrieval Budget - 16,000 documents

3.2. Performance
As in Vignette 1, we compare two performance benchmarks, shown in Figure 4, which again plots
the performance of each implementation at retrieving interesting items as a function of budget
expended.
First, we consider a reference implementation where Data Discovery is allowed to see the title
field directly (gray curve). This gives the policy direct querying access to the labels. The positive
target class is considerably rarer in Vignette 2 than in Vignette 1, and consequently there is a longer
warm-up phase before relevant documents are retrieved. However, upon finding relevant records,
the policy quickly associates title contains 'album' with the reward signal and exploits this
directly via querying. Also in contrast to Vignette 1, the target population in Vignette 2 is much
smaller than the retrieval budget (3,270 positives for a 16k budget), allowing the system to fully
retrieve the interesting documents, followed by a flat line as no more target samples are available.
Next is the more interesting implementation, again blind to the title field used for labeling. The
rarity of the data yields the same long ramp-up as in the reference ceiling. However, once interesting
records have been identified, Data Discovery exploits other correlational signals to successfully
retrieve most of the interesting data within the allocated budget. This stands in stark contrast to the
typical random-paging performance floor for search, which yields just a small fraction of the target
data within the budget window.

when Data Discovery has access to the `title` field (gray curve) and when it is intentionally blind to
 the `title` field (blue curve).

3.3. Analysis
Denied the obvious reference signal in the title field, the system identifies and leverages a proxy
from the document body. In particular, it latches on to a combination of Wikipedia-assigned
categorical metadata and structural heading markers frequently used in articles about albums (see
Figure 5).

A secondary funnel keys on listing then albums, catching the track-listing and discography
section headers. Both are interpretable as "this document is shaped like an album article," which is
exactly the concept the hidden title encodes.

  Figure 7 - Example track-listing section for an album article. Data Discovery secondarily relied

These splits based on metadata and structure beat every topical single word the system tried, and
they were invisible to the phrase-extraction strategy on VFDT. Future versions may additionally
include structural markings, such as heading formatting, in the tokenization strategy. The same
"records albums" root appears in three distinct experiment seeds (recovering a 0.901 ± 0.006
fraction of the oracle).
At a 1.1% base rate, every leaf in the tree still predicts "not an album": as a classifier the tree performs
poorly. But as a target concentrator it is excellent. The "records albums" query returns about 1,529 on-
target articles out of ~3,749, a 41% hit rate against a 1.1% background, which represents a ~38×
concentration. The system did not learn to label album articles; it learned where they live, which is all
the discovery loop needs.

4. VIGNETTE 3 – FOLLOWING A GROWING CORPUS GROWS THE
 VOCABULARY
The third vignette intentionally introduces large topic drifts and nonstationary behavior to the
served data, on top of an intentionally limited and impoverished API. Here the source is a replayed
Stack Exchange archive whose "visibility clock" streams the 2010 → 2024 timeline underneath the
running system (at a 10⁶× speed-up), so the corpus visibly grows and its topic mix drifts over the
course of the run. The revealed structure of the tree can be assigned to approximate "eras" of the
data, and it highlights the system's adaptability to large drifts.

4.1. Setup
 • Data Source - Stack Overflow posts stored in Postgres and served through an intentionally
 restricted and heavily rate-limited REST API.
 • Target (Reward) - posts tagged with machine-learning
 • Policy Setup - VFDT + SquareCB, but VFDT is intentionally blinded to post tags.
 • Retrieval Budget - 450s of wall time. Over the course of the run, the API simulated data
 temporally spanning 2010 → 2024.

4.2. Performance
In contrast to Vignettes 1 and 2, in Vignette 3 the data source interface is deliberately impoverished
with no text push-down, so the absolute retrieval fractions are much smaller. Figure 8 shows the
performance of the system when the data source drifts over time (blue curve), which tracks variable
retrievals. In contrast, a statically frozen setup without drift, combined with the extremely limited
API capabilities (gray curve), shows poor performance reflective of the inability to penetrate beyond
the first few, most-recent sorted pages.

 18

Figure 8 - Retrieval performance for finding Stack Overflow posts tagged with `machine-learning`
when exposed through an extremely limited API, both when the data source drifts over time (blue
 curve) and when it is held static (gray curve).

4.3. Analysis
The discovery here is what the data drift itself does to the learned structure. Against the growing
corpus, the tree self-assembles a machine-learning vocabulary as the field's own terminology comes
into existence over time: rooting at title contains "machine" and then branching on token sets
such as {adaboost, algorithms, bandit, bayes, supervised, svm, validation} and
body tokens {classification, neural, svm, svms}. When the tree learns a filter, it changes
what it is able to catch. On the growing feed, the system had to keep re-deciding what "machine
learning" looked like as the vocabulary matured, and that ongoing adaptation is apparent in the tree.
Against the static, finished corpus, the tree grows something entirely different: only
author_reputation numeric splits, and no ML vocabulary at all.

This type of synthetically introduced drift is representative of real-world, continually updating data
sources. The machine-learning tag rises sharply after 2015. On a source that only ever serves
newest-first (this was enforced by the rate limits, and is a common real-world data-serving pattern), a
static run is pinned to the recent end and a chronological run to the old end. But on a growing feed,
every document is near the top at some point, so following the drift neutralizes the ordering
limitations imposed by the data serving: the replay run reaches roughly 4–5× more on-target posts in
equal wall-clock time than the static run.

5. CONCLUSION
Across a geospatial, a textual, and an impoverished temporal source, the same mechanism produced
the discovery. The tree produced the system's hypotheses as readable queries, and the bandit
concentrated the budget on the ones that paid off. In every case the unexpected insight fell out of a
structural combination the system was never told to consider: a name token crossed with a latitude
band, a body phrase standing in for a hidden title, and a vocabulary crossed with time. The common
thread is interpretability against real-world structure. Because each split is a real query clause rather
than an opaque weight, the fitted structure can be read, and reading it is what turns retrieval into
novel discovery. Ultimately, what is discoverable at all is bounded by the source's query capability;
on a truly impoverished source, even a perfect policy has little structure to find.
