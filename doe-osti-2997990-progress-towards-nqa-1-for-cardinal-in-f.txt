 Summary

Cardinal is a wrapping of the GPU-oriented spectral element Computational Fluid Dynamics (CFD)
code NekRS and the Monte Carlo particle transport code OpenMC within the Multiphysics Object-
Oriented Simulation Environment (MOOSE). Cardinal provides high-resolution thermal-hydraulics
and/or radiation transport feedback to MOOSE multiphysics simulations. Multiphysics feedback
is implemented in a geometry-agnostic manner which eliminates the need for rigid one-to-one map-
pings. A generic data transfer implementation also allows NekRS and OpenMC to couple to any
MOOSE application, enabling a broad set of multiphysics capabilities. Cardinal simulations can
also leverage combinations of MPI, OpenMP, and GPU resources.
 Cardinal continuous development and improvement efforts have led to the software being con-
sidered as a high-fidelity design and licensing tool for key areas of nuclear reactor relevant physics,
including neutron transport, fluid flow, heat transfer, and mechanical processes. The fast devel-
opment and expansion of the software from a pure R&D framework towards its application in the
nuclear industry and regulation require a focus on developing, enhancing,and maintaining Cardi-
nal’s software quality through strict adherence to a Software Quality Assurance (SQA) framework
and SQA program.
 To facilitate compliance with SQA standards, the Cardinal SQA Program was initiated during
Fiscal Year 2023 (FY23). During the development of the Cardinal SQA Program, multiple gaps
have been identified. These gaps are primarily related to model verification and code pedigree
as they relate to the use of Cardinal as an analysis tool. These gaps were captured in a report
published in 2023. A second report highlighted the progress made during Fiscal Year 2024 (FY24)
and described Argonne’s effort to document and integrate software verification within Cardinal’s
software development process.
 This report documents the progress made towards NQA-1 for Cardinal in the Fiscal Year
2025 (FY25). All cases in the expanded Continuous Integration (CI) suite of NekRS are included
in this report which test the solvers and modules available in NekRS exhaustively. The NekRS
tests are integrated with the Cardinal CI suite and made available in publicly accessible Github
documentation. Following the CI practice permits integrating of source code changes frequently
and ensuring that the integrated codebase clears the verification testing for the software. Also in
this report is a brief overview of the development of the Cardinal Software Quality Assurance Plan
(SQAP) that was done in FY25, though it should be noted that the rest of the documentation for
the SQA program needs to be developed in a future step of this task.

1 Introduction

Cardinal [1] is an open source, advanced, and modern multiphysics analysis software tool with high-
resolution thermal-hydraulics and radiation transport capabilities. Cardinal is under development
at Argonne National Laboratory (ANL) under the U.S. Department of Energy - Office of Nuclear
Energy’s Nuclear Energy Advanced Modeling and Simulation (NEAMS) program.

 Cardinal is a wrapping of the GPU-oriented spectral element Computational Fluid Dynamics
(CFD) code NekRS [2] and the Monte Carlo particle transport code OpenMC [3] within the
Multiphysics Object-Oriented Simulation Environment (MOOSE) [4]. Multiphysics feedback is
implemented in a geometry-agnostic manner which (i) eliminates the need for rigid one-to-one
mappings and (ii) allows NekRS and OpenMC to couple to any MOOSE application, enabling a
broad set of multiphysics capabilities. Simulations can also leverage combinations of MPI, OpenMP,
and GPU resources.

 Cardinal development aims for advances in physical modeling, numerical methods, and software
engineering to enhance its user experience and usability for reactor analyses. Cardinal utilizes an
object-oriented application framework (MOOSE), and its underlying meshing and finite-element
library (libMesh) and linear and non-linear solvers (PETSc) to leverage modern advanced software
environments and numerical methods. This approach facilitates code development as well as
capability expansion and standardization.

 Supported physics capabilities for NekRS include conjugate heat transfer, volumetric power/
temperature/density feedback, and 1-D/3-D coupling to systems codes. Cardinal also interfaces
NekRS to MOOSE’s stochastic tools module for forward uncertainty quantification. For OpenMC,
Cardinal supports both cell- and mesh-based tallies coupled to MOOSE for Constructive Solid
Geometry (CSG) and DAGMC Computer-Aided Design (CAD) geometry. By interfacing NekRS
and OpenMC with MOOSE’s postprocessing, stochastic simulation, and other modules, users have
a wide range of data analysis, multiscale closure development, and engineering workflow capabilities
at their disposal.

 The key features of Cardinal include:

 • Robust and high-order spatial and temporal discretization methods for fluid flow, heat transfer,
 and radiation transport modeling.
 • Multi-scale modeling and flexible coupling between multiple physics, enabling a wide range of
 engineering analyses and convenient integration with other advanced or conventional simulation
 tools.
 • Engineering postprocessing utilities for generating multiscale closure data and simulation
 analysis.

 The initial steps to developing a rigorous and resilient Software Quality Assurance (SQA)
framework consists in defining the software functional requirements and identifying the corresponding
gaps in the Cardinal development as well as verification process. Additionally, necessary controls
and processes need to be established for ensuring continuous, high-quality software development

 1

that meets user and program sponsor requirements. In particular, with regard to the development
and improvement of the software, it is expected that all new implementations and testing will be
conducted in accordance with SQA program guidelines.

 The ultimate goal of this task is to develop an SQA framework that satisfies the fundamental
requirements of relevant SQA standards and guidance while still maintaining sufficient flexibility
and efficiency such that the framework can be sustained with modest resources.

 This report presents the progress in developing the Cardinal SQA Program. Such a program
needs to be established to guarantee continuous software quality during the software development
process with a focus on maintaining and enhancing the code pedigree. The Cardinal SQA Program
aims to provide the controls and processes necessary to enable continuous, high-quality software
development while meeting user and program sponsor requirements. During the development of the
SQA Program, gaps in the Cardinal Quality Assurance (QA) processes were identified and prioritized
[5]. This report outlines the progress made in FY25 in resolving the identified gaps focusing on
porting additional NekRS testing directly into Cardinal to satisfy the identified requirements.

2 Verification

2.1 Verification Overview

Software Verification and Validation (V&V) holds an important role in the safety analysis for
nuclear facilities, as the codes and models utilized in calculations demonstrating the safety basis
must demonstrate an acceptable pedigree and qualification process. To that end, a strategy to
support V&V of Cardinal as applied to nuclear component design and applications needs to be
developed. The overall goal of the software V&V effort is to demonstrate the suitability of Cardinal
against its functional requirements, to evaluate its safety performance and to quantify the computed
safety margins for nuclear components. To that end, a V&V methodology needs to be used to
demonstrate the adequacy of the component and physical models of Cardinal for the corresponding
nuclear design elements to which the code is applied.

 Because Cardinal primarily exists in the R&D space and is currently in active development, the
most significant challenge facing Cardinal for use is the availability of a documentation and V&V
bases that describes the pedigree of the code. To that end, the majority of the V&V activities for
Cardinal focus on the definition of software critical characteristics and requirements, development
of documentation, and gap identification to support the V&V basis.

2.2 Cardinal Verification Progress

Cardinal uses an automated test suite that runs upon each new pull request opened on GitHub.
This regression test suite includes (i) verification tests against analytic solutions or comparable
physics solvers (e.g. MOOSE), (ii) error/warning checks to ensure that user messages are correctly
displayed, and (iii) syntax checks for tutorials to ensure documentation remains up to date. The

 2

baseline test suite contains 36 unit tests and 804 regression tests. The connection between each
test and a code requirement can be found in Cardinal’s web-base SQA documentation (https:
//cardinal.cels.anl.gov/sqa/cardinal rtm.html). Most of the requirements on the functionality of
Cardinal itself are focused on aspects of code coupling, such as the coupling modes, solution transfers,
post-processing capabilities, etc. These requirements were discussed previously [6] and are not
repeated here.

 As part of this progress report, additional verification cases that test the NekRS software
requirements have been ported into Cardinal to run as an integrated part of this overall test
suite. Therefore, all details on these test cases are covered in Section 2.4 and the NekRS software
requirements are repeated from the previous report [6] for reference below.

2.3 NekRS Software Requirements

NekRS shall maintain a general Navier-Stokes solution capability and shall provide a method
for implementing a stable interface with Cardinal. Specific capabilities of NekRS, e.g. variable
fluid property formulations, turbulence modeling options, magnetohydrodynamics, etc. shall be
determined and qualified on an as-needed basis. NekRS has an independent test suite which includes
tests relevant to Cardinal’s SQA Plan, in addition to other functionality. Those tests deemed
relevant to SQA of Cardinal’s code requirements are summarized in Table 2.1. These tests have been
adapted to run via Cardinal’s test harness directly in order to provide an additional evaluation of
the necessary capabilities and to provide greater flexibility in addressing concerns in the gap analysis

2.4 NekRS Verification Progress

The glossary of NekRS verification and validation tests included in this report are enumerated in
Table 2.1. Work in this FY has been focused on reviewing the available NekRS CI tests, generating
a basis for acceptance criteria (i.e. determining appropriate pass/fail values) for each test, and
porting them directly into Cardinal. Appropriate acceptance criteria are based on demonstrating
that each case converges towards a consistent solution. For verification cases, we demonstrate
that the cases converge towards an analytic solution and that the error is controllable and can be
driven towards machine zero (typically assumed as a normalized error of 10−16 ) based on either
mesh refinement (polynomial order) or time-step size refinement as applicable. We then select a
reasonable expected normalized error value based on problem size and runtime constraints as an
acceptance criterion. For non-verification tests, we still demonstrate that the case converges towards
a consistent solution with increasing polynomial order and select a value from literature to generate
an acceptance criterion.

2.4.2 ethier Case: Navier-Stokes

4 Conclusions

This report summarized FY25 efforts towards resolving gaps in Cardinal’s SQA plan to attain
NQA-1 compliance. The primary contribution is the inclusion of the NekRS CI test cases, ported
into Cardinal’s test suite, to ensure continuous coverage of NekRS’s software requirements via
Cardinal. These capabilities have been added in a public GitHub repository (https://github.com/
neams-th-coe/nek ci) such that they can run via Cardinal’s automated test suite upon any pull
request into Cardinal.

5 Future Work

This section provides additional information on activities planned for the next FY and the longer
term gaps that need to be addressed as the Cardinal SQA Program is finalized. While not specifically
stated in the content that follows, continued SQA Program maintenance and compliance are assumed
to be performed for the lifetime of the code. While the Cardinal SQA Program aims to avoid being
overly burdensome and hinder maintenance and development activities, additional resources and
lead times will be required to comply with the SQA Program. While Cardinal previously utilized an
informal design and review process, configuration management protocols, and some documentation
requirements, planning for future development activities will require resources beyond what was
historically available. The following table summarizes the gaps identified in FY23 [5]. Several test
