 ABSTRACT

To date, most Additive Manufacturing (AM) systems run open-loop with no data collection or feedback
on how the printing process is going. This requires an operator to manage the print at all times, or risk
failing a build. Ahead Wind and ORNL plan to close the gap by improving software capabilities and
adding sensors to existing polymer 3D printers so that data can be collected in real-time and used to
monitor and adjust the printing process without human intervention. Ahead Wind, makers of a 3D
printing toolkit to collect thermal data from existing filament 3D printer sensors, is looking to expand
their software capabilities by using their collected data to influence the toolpath generation step. ORNL
has developed toolpath generation software, ORNL Slicer 2, that can be used to close the loop for the 3D
printing process. This project will provide the resources to collect data from more sensors in real-time so
that the printing process can be more accurately modeled and logged to minimize human involvement.
The two programs will also be connected to allow for a closed loop control of systems. This new
framework for closed loop control will be easily adaptable to other 3D printers and manufacturers. All
modifications to ORNL Slicer 2 will immediately be available open source.

 1. ADVANCED SOFTWARE FOR EXTRUSION ADDITIVE MANUFACTURING DATA
 COLLECTION

This technical collaboration project (MDF-UP-2022-247) began on June 28, 2022, and concluded in
August 2025. The collaboration partner, Ahead Wind, is a small business. The results from phase 1
included developing and testing a framework for advanced network communication both within the
ORNL Slicer software and the Ahead Wind software. Phase 2 was unable to be completed by Ahead
Wind due to changes within the organization and employee transitions. ORNL was able to complete many
tasks including printer selection, connection capabilities within ORNL Slicer 2, and many significant
modifications to ORNL Slicer 2 for connectivity and modularity. While the connection to the Ahead
Wind Toolkit was not completed, the framework developed and implemented within ORNL Slicer 2 is
available open-source and can be utilized for future research with other organizations.

1.1 BACKGROUND

The focus of this project revolves around data collection and transmission between two separate pieces of
software: ORNL Slicer 2 and the Ahead Wind Toolkit. The ORNL Slicer 2 program is used for
toolpathing. It is capable of importing an STL file, slicing into layers, planning toolpaths, and exporting
g-code for the 3D printer. The Ahead Wind Toolkit is capable of importing g-code to do basic thermal
simulation as well as error checking. The toolkit is also being developed to allow for data collection and
processing based on sensor feedback during the printing process. This includes data from optical cameras,
thermal cameras, and laser scanners. These two disparate pieces of software are essential for developing
and enhancing the 3D printing process but would be more powerful if they worked together to share data.
The goal of this project is to connect the programs to allow bi-directional data transfer. With this data
exchange, toolpathing can be simulated and improved during the printing process. Future work will
enable data collection to monitor for anomalies during the printing process that can be resolved by
reslicing and creating new toolpaths.

 2. PHASE 1 TECHNICAL RESULTS

2.1 FUNCTIONAL REQUIREMENTS

Together, ORNL and Ahead Wind held several meetings to outline the functional requirements needed
for the two software packages to exchange data. This included discussions about communication
methods, data exchange format, and the printer to be used for testing. It was quickly decided that
communication would be initialized via TCP sockets. TCP, transmission control protocol, is a standard
for communication used for sharing data over a network by sending messages. Once established, the
communication channel remains active until both ends finish sending messages.

For the data exchange, commands and a common structure had to be determined. To do this, naming and
response conventions were defined based on existing standards from HTTP. Figure 1 shows the
handshake initialization and response commands needed to begin communication between programs.

//Handshake command
{
    "header": {
        "request-id": "00000000-0000-0000-0000-000000000000", //(UUID
for current operation - alphanumeric, hex)
        "date": "Mon Aug 30 09:25:00 2023", //formatted Qt datetime
stamp - DoW M D hh::mm::ss YYYY
 "command": "1" //(current command id - int)
 }
}

//Handshake response
{
    "header": {
        "request-id": "00000000-0000-0000-0000-000000000000",
        "date": "Mon Aug 30 09:25:00 2023",
        "command": "1"
 }
 "data": {
        "response": "200" //HTTP OK
 }
}
 Figure 1: Handshake commands for initializing communication.

After communication has been established and slicing has been completed, communication is needed to
pass the g-code from slicer to toolkit. This can be seen in Figure 2.

//Gcode Processing Request
{
    "header": {
        "request-id": "00000000-0000-0000-0000-000000000000",
        "date": "Mon Aug 30 09:25:00 2021",
 "command": "5" //Command for gcode transmission
 },
 "data": {
 "gcode": "" //full g-code payload

 }
}

//Gcode Processing Response
{
    "header": {
        "request-id": "00000000-0000-0000-0000-000000000000",
        "date": "Mon Aug 30 09:25:00 2021",
        "command": "5"
 },
 "data": {
        "response": "200",
 "gcode": "" //fully optimized g-code payload
 }
}
 Figure 2: G-code communication commands between slicer and toolkit.

The packets of data being shared via this TCP communication are JSON formatted (JavaScript Object
Notation) which can encounter issues with files larger than 1GB. G-code from ORNL Slicer is often
significantly smaller than 1GB due to it being a plain text file, but it is still possible to encounter a file
that exceeds this 1GB limit. To handle this, the team outlined a strategy for splitting large files and
writing packet sequence information so that the receiver can assemble the separated packets.

After defining the functional requirements for the framework, ORNL and Ahead Wind needed to outline
the 3D printer to be used for initial testing. Ahead Wind uses and supports a variety of small-scale
desktop printers but wanted to look at integrating a larger industrial printer to fully showcase the
capabilities of their software as well as the partnership with ORNL. Ultimately, ORNL and Ahead Wind
planned on using the Cincinnati BAAM Platform for testing due to ease of access and availability at
ORNL. Ahead Wind reached out to CI to procure copies of all source code for both the PLC and HMI
(human machine interface) on BAAM. Ahead Wind also partnered with other BAAM operators to do
some basic software setup and integration testing on the BAAM platform.

2.2 MODIFICATION OF ORNL SLICER 2

Based on the functional requirements, ORNL Slicer 2 needed to be modified for TCP communication.
Modifications included adding TCP communication capability and creating necessary data structures for
the information exchange. Because the process typically starts with slicing and toolpathing via the slicing
software, it was determined that ORNL Slicer 2 should act as the server in the TCP communication
relationship. This meant that the ORNL Slicer software needed to initialize a server and open a port for
communication. For the basis of this testing, port 12345 was used. After the slicing process is completed,
the g-code can be shared via this port for the Ahead Wind Toolkit to receive and begin simulating.

2.3 MODIFICATION OF AHEAD WIND TOOLKIT

Like the ORNL Slicer 2 software, the Ahead Wind toolkit needed to be modified to allow for data to be
transmitted back and forth. As previously mentioned, the ORNL Slicer 2 software was going to act as the
TCP server, so the Ahead Wind toolkit needed to be configured to act as the client. After slicing is
completed, a handshake is initiated between the two programs to confirm the initialization of the data
transfer. Again, the data structures on each system don’t perfectly align due to different methodologies,
but the Ahead Wind team was able to modify the toolkit to operate based on the data exchange commands

outlined in the functional requirements. In addition, the toolkit was programmed to parse the header of the
g-code file to determine the machine configuration used for the slicing.

2.4 TESTING

To test the functionality and prove the data transmission capabilities are working sufficiently to move
ahead with the research, a simple test slice and data exchange was setup. A hexagon object was sliced
with default settings and a configuration prepared for TCP communication. Figure 3 shows the status
window output from ORNL Slicer 2 including the starting of a TCP server at port 12345.

 Figure 3: Status window from ORNL Slicer 2 showing a TCP server being initialized.

Once ORNL Slicer was properly modified and successfully opened a port during the slicing operation, the
Ahead Wind Toolkit needed to be connected to complete the transfer testing. As shown in the terminal
output in Figure 4, the toolkit receives the incoming connection, then begins to receive the g-code file.
This file is parsed, and the machine type is output to the terminal. In this scenario, the Cincinnati BAAM

 3. PHASE 2 TECHNICAL RESULTS

3.1 3D PRINTER SELECTION

Integration and testing of the software developments in ORNL Slicer 2 and Ahead Wind Toolkit require a
3D printer that is compatible with both software packages. In addition, it is important to select a printer
that is easy to upgrade and modify with the addition of new sensors. The original plan was to use BAAM;
however, Ahead Wind has limited access to BAAM without working through ORNL or a partner. The
Ahead Wind team can’t work locally from a BAAM or have complete control over modifications to a
system. BAAM is also a discontinued platform, so significant development specific to BAAM may have
less impact than with a system that is commercially available.

Ahead Wind has experience with systems from Modix, Creality, Prusa, and Voron. Modix and Creality
are closed source and can be difficult for new firmware modifications. Prusa and Voron are both open-
source, but Voron is considered more “open” due to the limited commercial availability of the systems
and the primary DIY approach to development. Due to the ease of construction and fully open-source
hardware and software design of the Voron, it was the best selection for this project. Voron has two
primary models, the 0.2 and the 2.4. The 0.2 is a small machine meant for compact operations whereas
the 2.4 is much larger and open, with many sizes and configurations available. This project warranted a
larger machine with sufficient space for many sensors, so the 300mm x 300mm (XY build plate size)
Voron 2.4 was selected. During the project, a 300mm Voron kit could be purchased for $1400.

3.2 SENSOR SELECTION

3D printers natively include many temperature sensors that are typically thermistors or thermocouples.
These are used to monitor hot end temperatures, bed temperature, and chamber temperature. With the
Ahead Wind Toolkit, the printer and its native sensors can be connected to the software for immediate
data logging for a full temperature history based on location and time.

Together, ORNL and Ahead Wind discussed and reviewed many additional sensors for data collection,
primarily for capturing geometric information of the print. ORNL has extensive research experience with
laser profilometers and line scanners, both large and small, for process monitoring on large format
polymer systems. These sensors are available through a variety of manufacturers such as Teledyne and
Keyence. They capture high fidelity data suitable for the applications of this project but require a non-
trivial amount of computing power to act on the data quickly. In addition, these sensors often cost more
than $10,000, a significant premium over the $1400 cost of the 3D printer.

Ahead Wind pivoted their research to lower fidelity and lower cost sensors. One such solution was the
portable paper scanner (Figure 5). These handheld scanners cost less than $100 and can scan up to
250mm wide, nearly the width of the Voron print bed. The scanners typically work using charge coupled
devices as an optical sensor to roll across the top of a surface and collect images. While resolution isn’t
high, it’s suitable to collect enough geometric data when scanning a layer to determine if the layer has
printed successfully.

Figure 5: The underside of a handheld scanner showing the rollers and the long optical sensor positioned under the clear lens.

Additional sensors were not pursued due to Ahead Wind’s inability to continue the research and
development efforts.

3.3 CONNECTING MACHINE AND SENSORS TO AHEAD WIND TOOLKIT

ORNL and Ahead Wind each procured Voron 2.4 systems for testing and integration. Ahead Wind was
able to develop a preliminary mount for a scanner and conduct some initial tests with the Voron to prove
the concept. Unfortunately, this is where the research stopped. This task was not able to be completed by
Ahead Wind due to employee and company changes.

3.4 MODIFICATION OF ORNL SLICER 2

Phase 1 proved the ability to create a communication interface with the Ahead Wind Toolkit by
establishing a handshake to transfer data. With this initial proof of concept completed, ORNL needed to
make more rigorous changes to the Slicer to allow for more efficient bi-directional data transfer, provide
more cross-platform support, and improve modularity. Many of these changes were wrapped up in the
development of a new build system.

The new build system was developed around standardized tools to maximize compatibility. Nix was
chosen as the package manager because of its reliability, reproducibility, and dependency management.
With Nix, the development and compilation allow for independent package management so that all
systems, even when working on different versions, can maintain consistency and functionality in ORNL
Slicer 2. It’s also important because as new modules are developed, such as the new g-code writing for
the Voron system, these packages can be easily transferred to Ahead Wind for testing and integration
without concern of whether the modules will properly integrate or compile.

Using Nix also allowed the build properties to be tweaked to enable cross-compilation from Linux to
Windows. This meant development needed to be from a Linux environment, or it could be implemented
in the Windows development environment by using WSL (Windows Subsystem for Linux) which allows
a Linux development environment to run in Windows without dual booting and virtualization. This
change, along with many other changes to the build system, allowed for easier integration with all Linux-
based operations. This simplifies the connection to ROS (Robot Operating System) for real-time data
collection and data streaming during the printing process.

Another advantage of this build system is the automatic error checking and build management. When
collaborating on development with a small team of internal researchers, resolving bugs and build issues
can be quite simple. When expanding the development team to other companies and external
organizations relying on our code changes, an automated system to check and report errors is critical. This
automated system also has the ability to generate installers for Windows and App Images for Linux. With
this, every code commit results in a new installable version of ORNL Slicer 2 for immediate testing. This
also simplifies the process of creating new releases for partners and collaborators by defining releases
after large code merges. Figure 6 shows the output of the automated code checking and installer
generation as part of the new build system on the public GitHub page. With this new build system in
place, new development guides were required to help transition the new environment to all of our
developers and collaborators.

 Figure 6: Automated error checking and installer generation for every code commit.

 4. IMPACTS

Presently, slicing, simulation, and data collection are viewed as individual steps and individual pieces of
software in the industry. Connecting these pieces of software requires a skilled operator to manually
transfer data among the steps and generate the desired outcome for 3D printing. The work in this project

seeks to define and realize the capability of connecting these steps and streamlining the process. This
project will lead to commercialization opportunities for ORNL Slicer 2 as well as broader impacts on the
entire industry by demonstrating the benefits of optimizing the software pipeline for a more data rich 3D
printing process.

While this project was not able to see 100% completion, the ORNL tasks were all completed. All of those
tasks were developed within ORNL Slicer 2 and have been published via open-source license on a public
GitHub page for others to adopt and integrate.

 6. CONCLUSIONS

Phase 1 was completed and focused on defining the functional requirements to connect the ORNL Slicer
2 and Ahead Wind Toolkit pieces of software. This meant defining a network communication, using TCP
sockets, to exchange the data. With the TCP framework in place, the teams were able to define the
necessary commands for a handshake to initialize communication then begin g-code transfer. ORNL
Slicer 2 was configured to act as the server in this relationship with the Ahead Wind Toolkit acting as the
client. Once the g-code is passed from slicer to toolkit, the data can begin being parsed and key
information such as machine type and printing parameters can be identified.

Phase 2 of this project was not entirely completed, but it focused on sensor selection and integration as
well as upgrades and modifications to ORNL Slicer 2 to improve modularity and communication. This
meant development of a new build system for ORNL Slicer 2 allowing for more network capability and
cross-platform development. ORNL was able to develop the necessary communication to print on the
selected Voron system, but full integration with the Ahead Wind Toolkit and new sensors could not be
completed due to changes within Ahead Wind. All ORNL software developments have been published
via open-source license for others to build on.

 7. AHEAD WIND BACKGROUND

Ahead Wind is a small startup company focused on data collection and analysis for extrusion-based
additive manufacturing (AM) processes. Ahead Wind creates an AM toolbox using AI to analyze
collected data during the printing process in real-time giving the user feedback about the status of the
print. This data can be used after the print to create a model of the as-printed part for verification and
validation.

Ahead Wind is an American company based in Washington, DC.
