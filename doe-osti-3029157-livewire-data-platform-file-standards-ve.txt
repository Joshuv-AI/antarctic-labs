1 Introduction
This living document describes required and recommended standards for data additions
to the Livewire Data Platform (livewire.energy.gov/). Adherence to the standards
described enables development of automated analysis and discovery tools for Livewire
data and will facilitate development of future capabilities for delivering data that can be
tailored to meet user needs.

Additional benefits of adhering to these standards include:

 • Consistency across data products.
 • Enabling the use of consistent software to read all standardized files.
 • Creating both human- and machine-readable files.
 • Self-describing data files containing descriptive project/dataset metadata.

2 Dataset Contents
2.1 File Size
To keep both file sizes manageable and content convenient for end users, the data
within a single file should consider the normal usage pattern and balance size versus
number of files. Generally, files greater than 1 GB should be avoided. Similarly, millions
of files can be a challenge for data users. Structuring data into files of 10–100 MB
enables a good balance for many use cases. Data that need to include millions of files
or files larger than 1 GB should include an intentional plan to mitigate use issues for
most users.

2.2 Raw Data
Raw data are the original data produced for a dataset. Preserve all raw data in case
there is a need to reprocess due to changes in calibration or configuration of the
instrument. Raw data should be documented and marked so it is clear to users. The
format should be documented sufficiently so that a capable user can make use of the
data. It may be sufficiently standardized such that no further updates are needed for
normal use.

2.3 Processed Data
Datasets that are created from raw data should be standardized and formatted for ease
of use. In addition to describing the data and how to use them, the derivation used in
processing should also be clearly documented. Additional variables to assist the user in
understanding data quality should be considered. If data are filtered or removed,
ancillary variables should indicate why. If data are averaged or interpolated, ancillary
variables should include the averaging interval and the averaging bin width. All
processing should be repeatable. Higher versions of processed data may be
created/stored based on updates to the processing algorithm.

2.4 Human Data
All personally identifiable information must be removed or sufficiently anonymized.

3 File Naming Conventions
To facilitate the management of data stored in the Livewire Data Platform, a standard
file naming format has been established for observational data and model output. It is
highly recommended that the principal investigator consult with the Livewire team
before finalizing a file name.

3.1 Requirements
 • File names must be unique within a project.
 • File names must adhere to standards that can be parsed.
 • File names must be less than 255 characters.
 • File names must consist of alphanumeric characters with the addition of “-,” “_,”
 and “.”
 • File names should be all lowercase.
 • File names use “.” as a delimiter to parse naming fields (e.g.,
        bus.yellow.2024.00.csv).

3.2 Data Levels
Data levels are based on the life cycle maturity of the dataset from raw to highly
derived. Intermediate steps of standardized format, quality checks, or summary
products could be produced for a dataset. The data levels are determined in
coordination with the Livewire team and included in the dataset and file naming for a
dataset. The normal data levels are:

 • 00: Raw; original from source.
 • a0: Standardized format.
 • b0: Reviewed or quality checked data.
 • c0: Derived, combined, extracted, and/or summarized advanced products.

3.3 Date and Time
When necessary to distinguish files within a time series, the date and time should be
added to the file name (e.g., sa2.ecor.bao1_300nw.00.20150101.000000.csv). The start
date is the UTC (Coordinated Universal Time) date in YYYYMMDD format, consisting of
exactly eight characters that indicate the start date of the first data point in the file.
Single-digit month and day values are padded with a “0.” For example, Feb. 4, 2025, is
expressed as “20250204.”

The start time is the UTC time in HHMMSS format, consisting of exactly six characters
that indicate the start time of the first data point in the file. Single-digit values are
padded with a “0.” Sub-second times are truncated to the integer of the second’s value.

exceed 23:59:59.

Optional file name attributes might be necessary to indicate unique files within a project
if two files are generated from the same instrument and location.

Examples:

      • sa2.ecor.bao1_300nw.00.20150101.000000.humid.csv

4 File Types
The file type should be in a format that is documented and can be understood by
available software tools:

 • CSV: Comma-separated values format.
 • ASC: American Standard Code for Information Interchange (ASCII) data format.
 • HDF: Hierarchical data format (limited to satellite data).
 • PNG: Portable network graphics data format, recommended for drawings,
 sketches, and data plots.
 • JPG: Joint photographic experts group data format, recommended for
 photographs.
 • MPG: Moving picture experts group format, recommended for movies.
 • PDF: Portable document format, recommended for formatted and graphics-rich
 documents.

5 Fields
5.1 Field Names
A field name should convey a basic understanding of the associated data. File space is
not an issue, so cryptic field names that are typically only understood by the person who
chose the name should not be used.

 • The first character must be a letter. Uppercase letters should be used sparingly.
 • The field name is constructed by joining the names to the qualifiers using
 underscores (_).
 • Field names should be concise. Be reasonable when selecting field names.
 • Abbreviations are recommended only when needed for limiting excessively long
 variable names, for following previous conventions, or for clarity.
 • To comply with archive database storage requirements, field name lengths must
 not exceed 255 characters.
 • Use of single-character names is not recommended.
 • The singular form of field names and dimensions are recommended (e.g.,
 “temperature,” not “temperatures”).
Again, field names should be as concise as possible. For example, “temperature” fully
spelled out is recommended unless the full field name becomes unreasonably long. In
addition, the field name “atmospheric_temperature” is more descriptive of the
measurement than “temperature” alone. A field labeled “temperature” could describe air
temperature, instrument temperature, derived temperature, etc.

5.2 Field Name Descriptors
Some abbreviations are common and will be used often:

 • temp = temperature
 • lat = latitude
 • lon = longitude
 • std = standard deviation
 • mean = arithmetic mean
 • avg = arithmetic average (mean is preferable to average when the two are used
 interchangeably)
 • mode = arithmetic mode
 • med = arithmetic median

 • var = variance
 • sum = summation
 • min = minimum
 • max = maximum
 • stderr = standard error
 • log = logarithm
 • ln = natural logarithm
 • cat = categorical data.

5.3 Time Fields
Time in an ASCII file is indicated with year, day of year, and time of year. Please avoid
composite fields if it is possible to split time data into multiple fields. It is recommended
to use Unix time stamps, or to follow ISO 8601 (en.wikipedia.org/wiki/ISO_8601). If time
zone information is not provided, the time will assume to be in UTC+00:00. If there are
multiple time fields of the same type per row, please specify which fields are linked
together in their field name.

5.4 Location Fields
Location is described using latitude, longitude, and altitude fields. If there are multiple
location fields of the same type per row, please specify which fields are linked together
in their field name. It is recommended to include information regarding the coordinate
reference system. If applicable, it is recommended to follow ISO 6709
(en.wikipedia.org/wiki/ISO_6709).

 • The requirements for latitude are units of degrees north and a field name of “lat.”
 • The requirements for longitude are units of degrees east and a field name of
 “lon.”
 • The recommended units of altitude are meters above mean sea level, and the
 required field name is “alt.”
 • The recommended field name for the coordinate reference system, if included, is
 “crs.”
 • The altitude measurement references the altitude of ground level to mean sea
 level.
 • The lat, lon, and alt fields can be dimensioned by time for mobile platforms when
 needed.

6 Global Attributes
All global attributes must have a value. If a value is unknown at the time the file is
created, the attribute must clearly indicate that no known value exists. A standard value
of “unknown” or −9999 set to the proper data type is recommended (127 for type byte).
Recommended attributes may be omitted if the value is expected to be unknown. If
required attributes must be written but a value is not expected to exist, use “N/A.”

6.1 Recommended Global Attributes
 1. title

 This attribute contains a succinct English language description of what is in the
 dataset. The value would be similar to a publication title.

 Example: title = “Planetary boundary layer height”

 2. institution

 This attribute specifies which institution was responsible for producing the
 original data.

 Example: institution = “United States Department of Energy - Atmospheric
 Radiation Measurement (ARM) program”

 3. description

 This attribute records a longer English language description of the data.

 Example: description = “Cross Prompt Injection Attack hourly averaged quality-
 controlled product, derived from scanning lidar”

 4. reference

 This attribute records the published or web-based references that describe the
 dataset or the methods used to produce it.

 Example: reference =
 “https://app.box.com/embed/s/dh840rhp4u3b1btopg4p8iiqqox1m2ee/file/679306
 09033”

7 Example Data File
7.1 ASCII Header Requirements
All ASCII files should be in CSV format and adhere to the following requirements:

 • The global and variable attributes must be listed in the header section.
 • The first row of the header must contain the number of rows in the header.
 • The last row of the header must contain a comma-separated list of the variable
 names.
 • Strings of characters containing commas must be fully enclosed in quotation
 marks (e.g., "location=Block Island, RI" and "qc_energy:flag_masks=[1, 2, 4]").
 • Variable attributes must be entered on separate rows and formatted as
 <variable_name>:<attribute_name>=<attribute_value>.

8 Plots
Plots should adhere to the following guidelines whenever possible:

 • Label each plot with a short, self-explanatory title.
 • Indicate the name of the dataset containing the data in the plot.
 • Include the date and time of creation.
 • Format text in a sans serif font between 8 and 14 points.
 • Plot the dependent variable on the vertical axis and the independent variable on
 the horizontal axis.
 • Label both axes with descriptive variable names and units.
 • Divide the axes into 4–10 units with a range that makes full use of the plot area.
 • Label divisions with a meaningful numbering system.
 • Use zero as the origin of both axes. (If the scaling of any axis prohibits the
 inclusion of the origin, a broken axis should indicate the offset.)
 • Use a single linear scale whenever possible, or a common scale if a single scale
 is not possible.
 • Add gridlines on major divisions, ideally white gridlines on a gray background.
 • Show different sets of data by using different plotting symbols that are defined in
 a legend.
 • Avoid conveying information only through color, or use color palettes that are
 colorblind accessible.
