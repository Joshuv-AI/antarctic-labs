 PREFACE

The Workbench Analysis Sequence Processor (WASP) provides a common foundation for applications
that interpret, examine, validate, navigate, and generate structured text. The first WASP Technical
Memorandum, published in 2017 as ORNL/TM-2017/698, documented the framework during an earlier
stage of its development [1]. That report established the technical basis for the present work and recorded
many of the core concepts on which the framework continues to depend.
This publication describes the architecture of WASP 4.4 [2]. It is a new architectural reference rather than
an incremental revision of the 2017 report. Since the first release, WASP has evolved from its original
document processing foundation into a framework the interpreters, semantic services, presentation
capabilities, and application interfaces of which operate through shared hierarchical representations. This
publication therefore organizes the expanded framework by architectural responsibility rather than by
package history.
The central subject of this memorandum is the common, source-aware parse tree representation
constructed by WASP interpreters. It preserves document hierarchy, values, identifiers, relationships,
lexical structure, and source provenance. The Core Framework also provides a complementary Object
model for typed, application-oriented data. Semantic validation, declarative navigation, document
generation, Language Services, and application interfaces operate on this shared foundation. The resulting
separation between input syntax, application semantics, and integration services permits the same
architectural capabilities to be applied across multiple textual formats.
The memorandum is intended for application developers, computational scientists, software architects,
advanced users integrating WASP, and future maintainers of the framework. It explains why the principal
capabilities exist, how they relate to one another, and how applications use them. Exhaustive API
descriptions, interpreter implementation details, and contributor procedures are outside the scope of this
document.

 ABSTRACT

The Workbench Analysis Sequence Processor (WASP) is a software framework for interpreting,
representing, validating, navigating, and generating structured text used by scientific and engineering
applications. Its architectural foundation is a common parse tree representation that preserves document
structure, typed values, identifiers, relationships, and source provenance. Interpreters for structured and
definition-driven input languages construct this representation, allowing framework services to operate
independently of the original document syntax. WASP provides three principal framework services: the
Hierarchical Input Validation Engine, Sequence Input Retrieval Engine, and Hierarchical Input Template
Engine, which apply semantic validation, declarative navigation, and document presentation to that
shared representation. The same representation also supports Language Services, Python application
integration, plotting, and command-line transformation and analysis utilities. This memorandum describes
the architecture of WASP release 4.4, the responsibilities of its principal layers, and the relationships that
permit its components to be combined in application workflows. It supersedes the architectural
description in the 2017 WASP Technical Memorandum, which documents the earlier development of the
framework.

 1. INTRODUCTION

Scientific and engineering applications frequently depend on text documents for configuration, model
definition, data exchange, and generated input. These documents may use different syntactic conventions
even though they require the same fundamental operations, such as interpretation, structural access,
semantic validation, selective retrieval, transformation, and interactive assistance. Implementing these
operations separately for each input language duplicates application logic and couples software behavior
to document syntax. WASP addresses this problem by separating the interpretation of text from the
services applied after interpretation. This separation allows WASP’s language-specific interpreters to use
the framework’s shared validation, navigation, generation, and integration capabilities. This section
establishes that architectural principle and defines the scope of the WASP 4.4 architecture.
WASP is a framework for constructing and using hierarchical representations of structured text. Each
supported interpreter recognizes the syntax of an input language and constructs a source-aware parse tree
that exposes document hierarchy, node identity, values, relationships, and source provenance through
common interfaces. Framework services consume that representation rather than operating directly on the
original syntax. Once constructed, the common parse tree becomes the boundary between input syntax
and downstream source-oriented framework behavior. HIVE schemas and SIREN paths apply semantics
and navigation without depending on the originating language. The complementary Object model
provides typed data to HALITE templates, plotting structures, and other value-oriented consumers.
Language Services, Python interfaces, command-line utilities, and application integrations expose the
appropriate representation and services through different operating boundaries. These reusable and
extensible capabilities are intended to improve research software engineering and accelerate software
adoption, maintenance, and impact.

1.1 COMMON PARSE-TREE REPRESENTATION

Downstream services cannot behave consistently if every interpreter exposes only language-specific
constructs. WASP’s interpreters therefore construct a common, source-aware parse tree through which
those services can access structure, values, relationships, and source provenance.
WASP provides complementary representations for different uses. The parse tree retains the structural
and lexical organization of a document. A NodeView provides lightweight access to nodes without
duplicating the underlying storage. The common parse tree representation allows a service to traverse an
interpreted Standard Object Notation (SON) document, a Hierarchical Input Text (HIT) document, a
definition-driven document, or supported MCNP input through compatible concepts. Language-specific
details remain available where needed, but they do not determine the organization of every downstream
operation.

1.2 SEPARATION OF SYNTAX AND SEMANTICS

A document can conform to the structural rules of an input language without being meaningful for a
particular application. A syntactically valid numeric value may violate an application limit, and a valid
identifier may refer to an object that does not exist. The interpreter establishes the document hierarchy,
but application semantics require a separate source of knowledge. WASP assigns these concerns to
separate layers. Interpreters recognize syntax; schemas express application semantics. HIVE applies those
schemas to the common parse tree and produces diagnostics associated with document locations. This
separation permits a syntax to be reused by multiple applications and enables application constraints to
evolve without changing the interpreter.

1.3 DECLARATIVE FRAMEWORK SERVICES

Validation rules, document relationships, and presentation logic often encode application knowledge that
must be reused across batch processing, interactive authoring, and generated input. Implementing that
knowledge procedurally at each integration boundary produces duplicated behavior that is difficult to
keep consistent. Application developers or domain specialists normally author and maintain these assets
as part of the application integration. The integration supplies the applicable schemas, selection
expressions, and templates when configuring a validation, navigation, generation, or interactive
workflow; WASP interprets or evaluates them at runtime. Later sections describe component-specific
cases in which assets are embedded, submitted directly, or generated as part of a workflow. HIVE
schemas describe permitted structure, occurrence, values, references, aggregates, ordering, consistency,
and authoring assistance. SIREN expressions identify nodes through paths and predicates, and HALITE
templates describe how hierarchical data are presented as text. The Expression Engine supplies computed
conditions and values where those assets require more than direct retrieval. Because schemas, selection
expressions, and templates remain separate from application control flow, the same application
knowledge can support validation, Language Services, generation, command-line utilities, and embedded
integrations. Because HIVE schemas, SIREN expressions, and HALITE templates are separate from
application code, the same validation, navigation, and presentation rules can be reused by Language
Services, command-line utilities, and embedded applications.

1.4 PRESERVATION OF PROVENANCE

WASP retains source locations and lexical distinctions so that processing results remain connected to the
text a user can inspect and modify. HIVE attaches source locations to diagnostics, Language Services
returns definition locations to editors, and source-aware reconstruction and transformation distinguish
values from punctuation, comments, and other decorative text. During multi-file processing, nodes from
included or imported documents retain the identity of their originating source. To support efficient

 2

provenance connections, WASP retains byte offsets and newline information in its core storage so that
source locations can be derived without duplicating position data throughout the parse tree. Nodes
preserve structural relationships and identifiers, whereas interpreter and NodeView interfaces expose the
originating source, line, column, and nested-document context needed by consumers.
By preserving provenance in the common parse tree, WASP allows semantic and interactive services to
return results that remain connected to the text that a user can inspect and modify. HIVE diagnostics,
Language Services navigation, document reconstruction, and multi-file processing can therefore share one
source model rather than reconstructing locations independently for each input language.

1.5 INTEGRATION THROUGH SHARED SERVICES

Scientific applications use document processing capabilities in different operating contexts. A simulation
may embed WASP directly, an automation workflow may invoke a command-line utility, a Python
application may require native data access, and an editor may communicate with a language server. These
environments require different interfaces, but they should not require separate implementations of
interpretation, semantics, or navigation. WASP provides embedded C++, Python, command-line, and
Language Services interfaces. Each interface adapts ownership, data exchange, and lifecycle behavior to
its operating environment while retaining the framework’s interpretation and semantic services.
These interfaces differ in deployment and audience, but they use the same underlying representations and
services. As a result, the integration layer provides different ways to access the same underlying WASP
capabilities rather than reimplementing document processing for each environment.

1.6 REPRESENTATIVE WORKFLOW

The architectural value of the common parse tree becomes most apparent when multiple services
participate in one workflow. Consider an application that accepts a hierarchical model description. During
integration, the application developer selects a supported input language and defines the application's
schema. At runtime, the application passes user input to the corresponding interpreter constructing the
common parse tree and recording source provenance. HIVE applies the schema to check structural, value,
and referential constraints. SIREN expressions locate related model elements needed by validation or
application logic. If the application must produce input for another program, then HALITE generates that
text from hierarchical data.
The same interpreter, schema, navigation expressions, and templates can also support interactive editing.
When a user opens or modifies a document, WASP’s Language Services interpret the current version and
return syntax and semantic diagnostics to the editor. They also respond to editor requests for completion
suggestions, descriptive information, and navigation to definitions. These interactive features use the
same document representation and application rules as the corresponding application workflows.

1.7 ORGANIZATION OF THIS REPORT

The principles established in this section provide the organizing logic for the remainder of this report. The
section sequence follows the architectural flow introduced in Figure 1. Section 2 defines the architectural
layers and their dependencies. Sections 3 and 4 describe the Core Framework and Expression Engine.
Section 5 describes the input languages that construct the common parse tree. Sections 6 through 8
address semantic validation, declarative navigation, and document generation. Sections 9 through 12
describe Language Services, Python interfaces, command-line utilities, and framework integration.
It should be noted that the organization of this report follows architectural responsibility rather than
package chronology. Each component is introduced according to the problem it solves, the representation
it consumes or produces, and its relationship to the complete processing workflow.

1.8 SUMMARY

WASP separates textual syntax from the services required to use structured documents. Its supported
interpreters construct a common parse-tree representation that preserves structure, values, relationships,
and provenance. HIVE, SIREN, HALITE, the Expression Engine, and integration interfaces build on this
shared foundation. This architecture permits multiple input languages and operating environments to use
consistent semantic, navigation, generation, and assistance capabilities.

 2. ARCHITECTURE OVERVIEW

WASP supports several input languages and a range of services as part of a processing architecture in
which each layer has a defined responsibility and communicates through shared representations. This
section describes that architecture, the direction of information flow, and the boundaries that keep syntax,
semantics, navigation, generation, and integration distinct.
The architecture prevents language-specific concerns from propagating into semantic services and
integration interfaces from redefining document behavior. It consists of four principal layers:
 1. The interpretation layer recognizes supported input languages and constructs hierarchical
 document representations.
 2. The representation layer stores document structure, values, identifiers, relationships, and source
 provenance, and it exposes them through common access forms.
 3. The framework services layer applies semantic validation, declarative navigation, expression
 evaluation, and document generation.
 4. The integration layer makes these capabilities available to applications, editors, Python
 programs, plotting workflows, and command-line processes.

Information generally enters as text and moves through interpretation into the common representation.
Services inspect or transform that representation, and integration interfaces deliver results to an
application or user. Some workflows reverse the final direction by using Objects and templates to
generate text. The shared representation remains the point at which these workflows meet. Figure 2
depicts the WASP architectural layers and shows how they are connected.

2.1 INTERPRETATION LAYER

The interpretation layer isolates user-facing syntax from the rest of the framework. WASP 4.4 includes
interpreters for structured formats such as SON, HIT, JavaScript Object Notation (JSON), and Tom’s
Obvious, Minimal Language (TOML); for the Definition-Driven Interpreter (DDI) and Extra Definition-
Driven Interpreter (EDDI) formats; and for domain-specific MCNP input. Each language provides
different conventions for expressing hierarchy and values. Definition-driven formats use external
knowledge to resolve structure that the input text does not state explicitly, and the MCNP interpreter
supports the domain-specific input language used by the MCNP Monte Carlo radiation transport code [3].
All the interpreters perform the same architectural role: they recognize document syntax, construct a
hierarchy, retain relevant lexical information, and report syntax diagnostics. As a result, downstream
services can operate on the resulting common representation without requiring language-specific text
processing.

2.2 REPRESENTATION LAYER

Interpretation produces information that must support two different classes of consumers. Source-aware
services need document structure, lexical form, and provenance, whereas data-oriented applications need
typed values independent of source syntax. The representation layer provides the stable boundary through
which both classes of consumers access interpreted information. In the Core Framework, document text,
tokens, and tree nodes are stored in shared data structures that preserve byte offsets and parent–child
relationships, from which source locations can be determined. The parse tree preserves both meaningful
document elements and, where required, decorative elements (e.g., delimiters, assignment symbols, and
comments) needed to understand or reconstruct the original text.
NodeView is the principal lightweight access mechanism for the stored hierarchy. It supports traversal,
parent and child relationships, names, types, data, and source-related queries without copying the tree.
When a service or application traverses the hierarchy through NodeView, it can follow nodes into

 5

included or imported documents. This allows multi-file input to be treated as one connected hierarchy and
for the source file associated with each node to be preserved.
The Object model represents typed hierarchical data as objects, arrays, and scalar values. It is suited to
application access, serialization, template data, plotting structures, and Python-facing models. The parse
tree and object model serve different purposes: the parse tree retains document structure, lexical
information, and source provenance, whereas the Object model represents typed data without preserving
the full textual form of the source document. Their shared hierarchy permits services to select the form
appropriate to their responsibility.

using the valid SON input solver { tolerance = 1e-6 methods [ newton gmres ] } . The
interpreted tree gives the solver, tolerance, and methods constructs hierarchical paths while retaining

These representation forms allow source-oriented and value-oriented services to share one interpreted
document without imposing the same information model on every consumer. HIVE, SIREN, and
Language Services can retain structure and provenance through NodeView access, whereas HALITE,
WaspPy, plotting, and serialization workflows can use Objects when lexical form is not required. The
representation layer thus isolates downstream responsibilities from both input syntax and storage
implementation.

2.3 SEMANTIC LAYER

An interpreted hierarchy establishes what the document contains, but it cannot determine whether that
content satisfies the requirements of a particular application. The semantic layer supplies application
knowledge without embedding those requirements in an input language interpreter. A HIVE schema
describes the hierarchy accepted by an application and associates that hierarchy with constraints and
assistance information. Semantic checks cover structure, occurrence, scalar values, references, aggregates,
ordering, and consistency. Because the schema is separate from the interpreter, a single input language

 6

can support different application models, and a single semantic approach can be applied across supported
languages.
Semantic analysis operates on interpreted nodes and produces diagnostics connected to source locations.
Schema assistance metadata also contribute information used by interactive tools, including candidate
values, descriptions, defaults, and input forms. HIVE therefore connects batch validation and interactive
authoring through a common declarative model.

2.4 NAVIGATION LAYER

Documents frequently express relationships across different parts of a hierarchy. A component may refer
to a material declared elsewhere, a constraint may depend on values under a sibling collection, or an
application may need to retrieve every node satisfying a structural condition. Implementing these
relationships as procedural traversal in each consumer would duplicate application knowledge.
The navigation layer provides a common way for WASP services and applications to locate and relate
elements within the hierarchical representation. SIREN provides declarative navigation over the common
representation. Path expressions select nodes relative to a context or from the document root and may
include positional, value-based, and wildcard predicates. Services use these selections to describe
relationships without embedding traversal procedures throughout application code.
Other WASP components use SIREN selections rather than implementing their own traversal logic.
HIVE uses those selections to evaluate reference and collection constraints. Applications use selections to
retrieve relevant subsets of input. Language Services use document relationships to support operations
such as definition navigation and completion. A shared navigation language keeps these relationships
consistent across consumers.

2.5 GENERATION LAYER

Applications that consume structured data often must also produce input decks, configuration fragments,
reports, or other text. Encoding target syntax and layout directly in application code couples the data
model to one presentation and makes format changes procedural. HALITE, WASP’s document generation
component, separates structured data from its textual presentation. Objects supply typed hierarchical data,
while templates define static text, substitutions, expressions, iteration, conditional regions, and reusable
imports. The application constructs or obtains the data without assembling target language strings.
Generation complements interpretation. Interpreters map text into hierarchical representations; HALITE
maps hierarchical data into text. The Expression Engine supplies computations and conditions used
during template evaluation. In interactive workflows, templates can also contribute completion text,
connecting document generation with authoring assistance.

2.6 INTEGRATION LAYER

WASP’s interpretation, validation, navigation, and generation capabilities can be used in several
application environments. The integration layer provides interfaces that make these shared capabilities
available to editors, Python applications, command-line workflows, and other software without requiring
separate implementations for each environment. Several WASP components provide these interfaces.

Language Services support editor-based workflows by coordinating WASP interpreters with HIVE
validation, SIREN navigation, and HALITE templates for features such as diagnostics, completion, hover
information, and navigation to definitions. WaspPy provides Python access to WASP interpreters,
hierarchical data, deserialization, and selected framework services. Command-line utilities make

 7

individual WASP operations available to scripts and automated workflows. WASP also provides
serializable Plot Objects for exchanging visualization data between applications and Language Services.

2.9 SUMMARY

The layered WASP architecture localizes change while preserving shared document behavior. Interpreters
isolate language syntax, the common parse tree establishes a stable boundary, framework services apply
reusable semantics and transformations, and integration interfaces expose those capabilities without
redefining them. Because the layers share common representations and declarative assets, developers can
add support for new languages, services, and application interfaces by reusing existing WASP
capabilities. The following sections describe these architectural components and the relationships among
them in greater detail.

 3. CORE FRAMEWORK

Every WASP interpreter must preserve enough information to support structural access, diagnostics,
navigation, semantic analysis, and, when required, reconstruction of the source document. If each
interpreter implemented its own storage and access model, downstream services would remain coupled to
individual input languages. The Core Framework provides the shared data structures and interfaces that
prevent this duplication. This section describes how the Core Framework represents text, tokens,
hierarchy, source provenance, and typed data. The emphasis is on the architectural responsibilities of its
data structures and interfaces rather than on their complete APIs.
The Core Framework connects interpretation to all subsequent WASP services. During interpretation,
recognized text is stored in a string pool, lexical information is stored in a token pool, and hierarchical
relationships are stored in a tree node pool. An interpreter coordinates construction of these structures and
identifies the root of the resulting parse tree. NodeView exposes node information and traversal without
copying the stored hierarchy.
Not every workflow requires lexical detail or source provenance. Data-oriented applications instead need
typed values that can be exchanged, transformed, and serialized independently of document syntax. For
these workflows, the Core Framework provides an Object model. Value, DataArray, and DataObject
represent scalar values, ordered collections, and named collections. A shared formatting API and common
utilities support expression evaluation, document generation, serialization, and other framework
operations.
These representations address two related requirements. The parse tree the common interpreter output and
preserves document structure, lexical form, and source provenance. The Object model represents typed
hierarchical data in a form suited to application processing. Both participate in the common representation
described in Section 2.

3.1 INDEXED STORAGE

Scientific input documents may contain large numbers of short names, values, and delimiters. Storing
every item as an independently allocated object introduces memory overhead and fragments the
relationship between text and its metadata. WASP instead uses indexed pools to consolidate storage and
refer to elements by position.
The string pool stores null-terminated character data in one contiguous buffer and records each string’s
starting position in a parallel index array. A token pool owns this string storage together with a
contiguous token array and a newline-offset array. Each token record contains a token type and source
byte offset; its position in the token array also selects the corresponding stored string. Line and column
values are derived from the token offset and newline offsets rather than stored on every token.
The implementation names its per-node record BasicNodeData. Despite basic in the type name, this
record carries the information needed to connect every node to the other pools: the node type, the index of
its enclosing parent node, and either a token index for a leaf or an index into the parent-record array for a
node with children.

Nodes with children have an additional ParentNodeData record. This record does not describe the
node’s own parent; it describes the node in its role as a parent by storing the position of its first entry in
the ordered child-index array and the number of child entries that follow. The child index array, in turn,
stores indices into the BasicNodeData array. Separating these records avoids reserving child-range
fields for leaf nodes.
For a leaf node, the token index in BasicNodeData identifies the corresponding record in the token
pool. The token supplies the leaf's lexical type, source byte offset, and pooled text. Node names are stored
separately in their own contiguous string pool. The tree therefore records relationships as compact indices
rather than embedding child objects or duplicating token text.

Figure 6 illustrates the contiguous character buffer and the parallel indices that connect stored strings to
token metadata.

The pool design is an implementation choice with architectural consequences. Indices provide compact
relationships among strings, tokens, nodes, and ordered children; storage remains owned by the
interpreter; and lightweight views can refer to nodes without reproducing their data. Pool index and type
widths are template parameters, allowing an integration to select storage appropriate to its expected
document scale.

3.2 TOKENS AND SOURCE PROVENANCE

A token connects recognized text to its lexical role and source position. The token pool records a byte
offset and maintains newline offsets for the interpreted source. Line and column values can then be
derived when requested instead of being repeated for every token. Locations for inner nodes are obtained
through their first and last leaf descendants, allowing diagnostics to refer to complete structural constructs
as well as individual tokens. This association preserves provenance throughout document processing. A
tree node can be related to the text from which it was constructed, and a service can report a diagnostic at
a user-recognizable location. The same information supports editor navigation and source-aware analysis.
Interpreter support for nested files retains the originating stream or file and permits traversal across
included or imported content without treating all nodes as though they came from one physical document.
Preserving this connection to the source does not require every source character to be represented by a
separate tree node. Interpreters retain the elements required by their language and can identify
nonsemantic elements, such as delimiters, comments, and similar elements, as decorative. This distinction
allows a consumer to examine textual form when needed or traverse only semantically significant
children when operating on document content. Thus, consumers can choose the level of document detail
appropriate to their responsibility. HIVE and Language Services can associate results with user-visible
locations, reconstruction workflows can retain textual form, and application-oriented traversal can ignore
decorative children. These consumers therefore share one provenance model without requiring each input
language interpreter to expose a different location or filtering interface.

3.3 TREE NODES AND HIERARCHY

Tree nodes convert a sequence of tokens into a structural representation. An inner node has a name, a
type, a parent, and an ordered range of children. A leaf node represents a token. The resulting parent–
child relationships express document constructs independently of their physical layout. For example, an
assignment such as temperature = 900 can be represented by an inner node for the keyed value and leaf
children for the declarator, assignment symbol, and value. A consumer interested in source form can
inspect all children. A consumer interested in application data can select the meaningful value. More
complex blocks, objects, and arrays use the same parent–child model.
Node names and types serve different purposes. A name identifies a node within the document hierarchy
and supports path-oriented access. A type classifies its role, such as a value, declarator, or terminator.
Preserving both permits generic services to navigate by hierarchy while allowing language-aware
behavior where lexical context matters.
Figure 7 relates the logical tree to its physical backing stores. Inner nodes retain ranges in the child index
array, leaf nodes refer to tokens, and tokens connect types and offsets to pooled text. The node, child
reference, token, and string index spaces remain distinct even when their numeric values coincide. A
NodeView combines a node index with the owning interpreter rather than duplicating any of these records.

This separation between logical hierarchy and physical storage allows every interpreter to construct
source-aware trees without imposing its storage details on consumers. Framework services operate

3.4 INTERPRETER RESPONSIBILITY

The Core Framework interpreter coordinates construction and ownership of the parse tree. Language-
specific interpreters supply recognition logic, while the shared interpreter implementation manages
tokens, nodes, diagnostics, stream identity, and the root node.
For some input languages supported by WASP, the interpreter cannot determine a component’s final
parent when the component is first recognized. In these cases, the interpreter uses temporary staging to
hold the prospective node and its children until their position in the hierarchy can be determined. Once the
hierarchy is resolved, the interpreter commits the staged node to the pool and attaches its index to the
enclosing stage. DDI uses this capability when schema context determines whether subsequent text
continues the current hierarchy or returns to a parent context.
For nested documents, there exists a second ownership boundary. A file node may be associated with
another interpreter that owns the included document’s pools and root. File-aware iteration descends
through that root so consumers can traverse one logical hierarchy, while each NodeView continues to
identify the interpreter and physical source that own its storage. This division establishes the boundary
between the Core Framework and the input language architecture described in Section 5. A language
interpreter determines which constructs the text expresses. The Core Framework determines how those
constructs are stored and exposed to the rest of WASP. Consequently, HIVE, SIREN, Language Services,
and utilities can accept interpreter results through common concepts.

 13

3.5 NODEVIEW ACCESS

Applications and framework services must traverse interpreted hierarchy without copying the tree or
assuming ownership of interpreter storage. NodeView provides that boundary as a lightweight reference to
an interpreter-owned node. It exposes node data, name, type, source position, parent, children, and
hierarchical path and supports iteration and named child selection. A null view represents the absence of a
node without requiring a separate tree allocation or sentinel node.
Views preserve the ownership boundary: applications and services traverse the hierarchy while the
interpreter continues to manage its storage. A view is therefore valid only while its owning interpreter and
pools remain alive. Index-based identity remains stable across internal storage reallocations because the
view resolves data through the interpreter rather than retaining pointers to individual vector elements.
Operations that exclude decorative children allow semantic consumers to focus on content, while token
and source queries remain available to consumers that need textual detail.
Leaf data can be modified through a view, but such mutation has consequences for textual reconstruction
and formatting. Replacement data may no longer preserve the spacing implied by original source offsets,
and newlines introduced by a replacement are not incorporated into the original newline-offset model.
The primary architectural role of NodeView is access to an interpreted document and its provenance;
transformations that require a value-oriented structure are often better served by the Object model.

3.6 OBJECT MODEL

While the parse tree preserves the structural and lexical form of an input document, many applications
ultimately require a representation that more naturally models application data. The Object model
provides this abstraction as a language-independent hierarchy of typed values. The model represents data
using Value, DataArray, and DataObject. A Value may contain null, Boolean, integer, unsigned-size,
real, string, array, or object data. A DataArray preserves an ordered sequence of values, and a
DataObject associates names with values. Nested arrays and objects form an application-oriented
hierarchy.
Unlike the parse tree, this model does not primarily represent delimiters or source layout. It supports
typed access, construction, serialization, template input, plotting structures, and Python application
models. JSON serialization and packing operations allow an object hierarchy to be exchanged in a widely
supported textual form.
Object construction is explicit rather than an automatic phase of every interpreter. JSON and TOML
provide format-specific conversion paths from their interpreted content, HALITE can load JSON data
through an Object parser, and applications can construct DataObject and DataArray values directly.
Other workflows may deserialize represented nodes into application domain objects without first
producing a Core Framework Object. Developers choose whether and when to create an Object. JSON
and TOML provide conversion paths. For example, HALITE can parse JSON into an Object according to
the originating representation and the information it can safely discard.
The Object model complements the parse tree. A parse tree is appropriate when source location,
decorative text, or interpreter-specific structure matters. Conversely, an Object is appropriate when an
application needs typed hierarchical data. Keeping these responsibilities distinct allows WASP to use the
simplified Object model for value-oriented tasks without losing the source provenance retained by the
parse tree and needed by diagnostics and Language Services.
The Object model forms the exchange representation used by HALITE, WaspPy, plotting, and
serialization workflows. By separating source-oriented representation from application data, the
framework permits these downstream components to operate independently of the originating input

language. Figure 8 distinguishes the parse tree path from the explicit construction paths that lead to an

3.7 COMMON FORMATTING AND UTILITIES

The shared formatting API provides type-aware conversion of values to text using the
%[flags][width][.precision]conversion form. The Expression Engine and HALITE use this API
where evaluated values must be presented with controlled width, precision, alignment, sign, or numeric
form. Common utilities provide recurring string, traversal, serialization, and diagnostic operations.
Format::fmt accepts an output stream, an error stream, a format string, and a typed value. Literal
characters in the format string are copied to the output, and the conversion controls presentation of the
value. For example,
std::ostringstream output;
std::ostringstream error;
bool ok = wasp::Format::fmt(output, error, "density=%8.3f", 7.85);
produces density= 7.850. The width is a minimum field width, so it adds three leading spaces but
would not truncate a longer result. The precision specifies three digits after the decimal point for the f
conversion. The Boolean result reports success; otherwise, an incompatible value, flag, or conversion
writes a diagnostic to the error stream.
Centralizing these operations improves consistency among framework services. A value evaluated in an
expression and emitted by a template can use the same formatting conventions, while common node and
string operations do not need to be reimplemented by each interpreter. Section 8.11 shows the same
formatting behavior in HALITE attributes.

3.11 RELATIONSHIP TO THE FRAMEWORK

The Core Framework provides the shared representations and services used by the other major
components of WASP. Every input language interpreter described in Section 5 builds on Core Framework
storage and interpreter services. HIVE and SIREN use NodeView access to apply semantics and navigate
relationships. Language Services depend on node hierarchy and provenance to produce diagnostics,
symbols, hover information, and definition locations. HALITE, WaspPy, plotting, and serialization use
Objects where typed data are the principal concern. The Expression Engine and HALITE share common
formatting support.
The Core Framework therefore provides the stable representation boundary of WASP. Its pooled parse-
tree representation preserves document structure and origin, while the Object model supports application
data. Later sections build specialized behavior without redefining either foundation.

3.12 SUMMARY

The Core Framework stores text, lexical metadata, and hierarchy in indexed pools coordinated by
interpreters. Tokens preserve source provenance, tree nodes express document structure, and NodeView
supplies lightweight traversal and access. The Object model supplies typed values for application-oriented
workflows. Together, these data structures and interfaces implement the common representation on which
WASP interpretation, semantic validation, navigation, generation, and integration depend.

 4. EXPRESSION ENGINE

Semantic rules and document templates frequently require values that are derived rather than copied
directly from an input document. Conditions must be tested, quantities compared, arrays indexed, and
numeric or string results formatted. Embedding separate evaluation logic in every framework service
would produce inconsistent behavior and make schemas and templates dependent on application code.
WASP’s Expression Engine provides a shared evaluation capability for these operations. This section
explains its role, evaluation model, supported categories of expression, and relationship to the semantic
and generation services of WASP.
The Expression Engine interprets expression text into a hierarchy and evaluates that hierarchy within a
context. The context supplies named variables and functions. Evaluation produces a typed result or an
evaluation diagnostic associated with the relevant expression construct. Expressions can combine
Boolean, integer, real, and string values. They support arithmetic, comparison, Boolean operations,
variable assignment and reference, function invocation, and indexed access to rank-one arrays. Default
constants and mathematical functions can be installed in a context, and an integration can provide
additional variables or functions appropriate to its domain.
It should be noted that the engine is a supporting service rather than an independent application language.
HALITE uses it to compute substitutions, conditions, iteration values, and formatted output. Other
integrations can use the same context-and-result model when schemas or templates require computation.

 Figure 9. Expression evaluation combines an interpreted expression, an evaluation context, and registered
 functions to produce a typed result.

4.1 INTERPRETED EXPRESSIONS

Expression text must first be recognized and represented before it can be evaluated. The expression
interpreter constructs a parse tree whose nodes identify literals, variables, operators, assignments, function
calls, and array access. When a WASP service or application requests evaluation, the engine traverses this
tree, resolves variables and functions using the supplied evaluation context, performs the indicated
operations, and returns a typed result or an evaluation diagnostic.

 19

Separating interpretation from evaluation has the same benefit as that described for document languages
in Section 1. Syntax recognition determines the structure of the expression, while the evaluation context
determines the meaning of names and available functions. The expression hierarchy also provides source
context for reporting failures such as an unknown variable, invalid index, incompatible operand, or
unavailable function.

4.2 EVALUATION CONTEXT

The evaluation context supplies the application data available to a general expression. It stores or
references named Boolean, integer, real, and string values and homogeneous vectors of those values.
Variables may be queried, assigned, and indexed during evaluation subject to their types.
Contexts make expressions reusable. A template can contain the same expression while different
evaluations supply different object values. An application can expose selected domain quantities without
giving the evaluator unrestricted access to its internal state. Reference-backed variables also allow a
developer to configure an integration so that controlled updates remain visible across evaluations.
The base context can install default constants, including representations of pi and Euler’s number, and a
newline string. These defaults are conveniences, not implicit application semantics. The application or
consuming service remains responsible for constructing the context appropriate to a workflow.

4.3 TYPED RESULTS AND CONVERSION

Evaluation produces a result classified as Boolean, integer, real, string, or error. Operators and functions
check the types of their operands and perform supported numeric conversions where appropriate. The
result can then participate in a subsequent operation or be returned to the consuming service.
Typed results prevent an expression from being treated as unstructured text. A conditional consumes a
Boolean interpretation, an array index requires an integral value, and a mathematical function requires
numeric arguments. When a conversion or operation is not valid, the evaluator returns an error result with
information about the failing construct rather than silently inventing a value.

4.4 OPERATORS AND CONTROL EXPRESSIONS

WASP’s Expression Engine supports arithmetic expressions that use addition, subtraction, multiplication,
division, exponentiation, and grouping. Relational operators compare values, and Boolean operators
combine or negate conditions. These operations allow a service to express derived values and decisions
without embedding a procedural callback for each calculation.
The reserved if function evaluates a condition and then evaluates the selected result branch. This
conditional evaluation is important for templates because an unused branch may refer to data that are not
present. The reserved defined function tests whether a variable is available in the context, and size
reports the number of elements in an array. Together, these constructs support optional and variable-
length hierarchical data.

4.5 FUNCTIONS AND EXTENSION

The default function set includes trigonometric, logarithmic, rounding, comparison, conversion, and other
common mathematical operations. The Expression Engine can also format evaluated values according to
a supplied format specification for use in generated text. These functions cover recurring computations
needed by templates and scientific input generation without requiring every consumer to provide them.
A context can also register functions supplied by an integration. Registered functions declare a result
category and validate their arguments during evaluation. This mechanism extends computation while

preserving the engine’s parsing, type checking, and result handling. Applications can therefore add
domain-specific functions without modifying the expression language.

4.6 ARRAY ACCESS

Contexts may expose homogeneous, rank-one arrays. An expression selects an element with a zero-based
integral index and can obtain the array length through size. Bounds, index type, and element availability
are checked during evaluation.
Array access allows a template or integration to apply an expression to ordered application data. More
complex hierarchical traversal remains the responsibility of the Object model or SIREN. This separation
keeps the Expression Engine focused on evaluation rather than turning it into a second document
navigation language.

4.7 DIAGNOSTICS

Evaluation can fail even when an expression is syntactically valid. A referenced variable may be absent, a
function may not exist, an argument may have the wrong type, or an array index may be invalid. The
engine represents these conditions as error results and relates the diagnostic text to the expression node
that caused the failure.
This behavior is essential when expressions occur inside templates or other WASP descriptions. The
consuming service can distinguish an invalid computation from a legitimate string or numeric result and
can report the failure at the template construct being evaluated.

4.8 SUPPORTED COMPUTATION

consumer. It can derive scalar values, form conditions, maintain local variables, and access ordered data
supplied by the context. It does not provide document traversal or application semantics; those

4.12 RELATIONSHIP TO THE FRAMEWORK

The Expression Engine depends on the Core Framework for expression tree representation, formatting,
and common utilities. HALITE is its principal architectural consumer: attributes, conditional blocks,
iterations, and formatted substitutions use expressions to derive output from hierarchical data. Integrations
may also create contexts and evaluate expressions directly when configurable computation is required.
Whereas SIREN describes navigation through document hierarchy and HIVE describes application
semantics and uses declarative rules tied to schema elements, the Expression Engine evaluates
computations within a supplied context. Keeping these responsibilities separate prevents navigation,
semantic validation, and calculation from collapsing into one language.

4.13 SUMMARY

The Expression Engine supplies shared computation to WASP services. It interprets expression syntax,
resolves variables and functions through an explicit context, evaluates typed operations, supports rank-
one arrays, and reports failures as error results. Applications can extend a context with controlled
variables and functions. HALITE uses the same evaluator and Core Framework formatting API when
generating text.

 5. INPUT LANGUAGES

Applications select textual formats for different reasons. Some require explicit, broadly recognizable
structure; others prioritize concise domain-oriented input in which a schema supplies information omitted
from the text. Without a common interpretation layer, each choice would require separate
implementations of validation, navigation, diagnostics, and integration. This section describes the input
language families supported by WASP 4.4 and explains how their interpreters construct compatible
hierarchical representations. It focuses on the purpose and architectural role of each language rather than
exhaustively documenting syntax.
WASP input languages fall into three groups. Structured languages state hierarchy directly through
delimiters, keys, tables, blocks, Objects, or arrays. SON, HIT, JSON, and TOML belong to this group.
Definition-driven languages use a schema to resolve hierarchy or assign semantic names to concise
positional input. DDI and EDDI belong to this group. The MCNP interpreter is domain-specific: it
recognizes the supported records and layout conventions of an established scientific application format
and constructs the same common parse tree representation.
All interpreters use the Core Framework described in Section 3. They construct parse trees, expose node
views, preserve source locations, and issue syntax diagnostics. Their language-specific node views
identify meaningful and decorative constructs, while common traversal enables downstream services to
operate without reading the source syntax themselves.
Interpretation does not establish complete application validity. A document may conform to SON, HIT, or
another supported syntax while violating required application structure or relationships. HIVE applies that
semantic layer after interpretation, as described in Section 6.

 Figure 10. Structured, definition-driven, and domain-specific input languages converge on the common

5.1 STRUCTURED LANGUAGES

A structured language makes its principal hierarchy apparent from the document. Delimiters and naming
conventions identify objects, blocks, arrays, tables, and keyed values. The interpreter can therefore

 25

construct the hierarchy without an application schema, although a schema may subsequently be used for
semantic validation and assistance. Applications may choose among WASP’s structured input languages
based on factors such as readability, existing interchange conventions, and compatibility with surrounding
tools. Regardless of that choice, the same downstream WASP services remain available.

5.2 STANDARD OBJECT NOTATION

Applications often need a human-authored format that expresses hierarchy without requiring the
punctuation and interchange constraints of an external standard. SON is a lightweight structured input
language for application data that supports blocks, objects, arrays, and keyed values. Identifiers can
distinguish repeated objects, arrays, or values that share a structural name. File imports allow a logical
document to be assembled from multiple sources while retaining source provenance.
SON is also the schema language used by HIVE. This role does not make ordinary SON input inherently
semantic; rather, it provides a hierarchical syntax capable of representing schema elements, rules, paths,
and assistance metadata. The same SON interpreter constructs the representation before HIVE interprets
that content as a schema.

5.3 HIERARCHICAL INPUT TEXT

HIT represents nested blocks, keyed values, arrays, comments, shorthand hierarchy, and file inclusion. It
is used by applications in the MOOSE ecosystem [4] and supports override notation associated with
keyed values. HIT error recovery can retain a partial parse tree when selected syntax elements are
missing, allowing diagnostics and interactive analysis to continue where possible.
HIT replaced the original GetPot interpreter beginning with WASP 2.0. The current memorandum treats
HIT as the supported architectural component; the earlier interpreter is relevant only to this transition.
HIT demonstrates why the common representation matters. Its block and assignment conventions differ
from SON, but HIVE, SIREN, utilities, Python interfaces, and Language Services can consume its
interpreted hierarchy through shared concepts.

5.4 JAVASCRIPT OBJECT NOTATION

JSON provides a standardized object, array, and scalar representation commonly used for interchange [5].
The WASP JSON interpreter retains a parse tree for source-oriented operations and can also support
conversion to the Object model. JSON is useful when a workflow already exchanges structured data with
external tools or services.
JSON does not provide comments or the domain-oriented block conventions of SON and HIT. Those
differences affect authoring but not the role of its interpreter: JSON text is converted into the same
architectural hierarchy required by navigation, transformation, and integration services.

5.5 TOM’S OBVIOUS MINIMAL LANGUAGE

Configuration workflows may already use TOML and benefit from retaining that established syntax while
adopting WASP services. WASP 4.4 therefore includes a TOML interpreter for key–value pairs, arrays,
tables, inline tables, arrays of tables, numeric and Boolean values, and supported string forms drawn from
the TOML 1.0.0 language [6]. The interpreted hierarchy can also be converted to JSON data by
command-line utilities.
The 4.4 interpreter does not implement every TOML 1.0 feature. Date and time values, multiline basic
and literal strings, and complete string-escaping behavior are not supported. Applications should select
TOML only when their required constructs fall within the implemented subset.

 26

5.6 DEFINITION-DRIVEN LANGUAGES

Definition-driven languages minimize explicit syntax by relying on a schema to determine how text maps
to hierarchy. The same text sequence may be structurally ambiguous without knowledge of the elements
permitted at the current location. The interpreter consults the schema to resolve that ambiguity and assign
node names and relationships.
This approach is appropriate for established scientific formats in which compactness, positional
conventions, or domain familiarity are more important than self-describing structure. The resulting parse
tree is not less structured than one produced from explicit delimiters; the structure has been supplied
jointly by text and schema.

5.7 DEFINITION-DRIVEN INTERPRETER

DDI supports hierarchy, scalar values, and arrays with minimal required punctuation. Section names and
values alone may not reveal whether a subsequent element is a child or sibling. DDI uses the schema
hierarchy to determine which interpretation is valid at the current context and moves through parent
contexts as necessary.
DDI is therefore an example of syntax and semantics cooperating without becoming identical. The
interpreter requires schema structure to construct the tree, while HIVE separately applies semantic
constraints to the constructed nodes. The schema informs interpretation, but successful interpretation does
not imply that every application rule has been satisfied.

5.8 EXTRA DEFINITION-DRIVEN INTERPRETER

EDDI supports concise blocks, commands, arrays, named and indexed fields, sectioned values,
comments, and included files. Schema aliases annotate positional data with meaningful node names.
Index, stride, and section aliases can describe repeated tuples and visually grouped values that would
otherwise appear as generic array elements.
EDDI is suited to formats that combine domain-specific commands with dense positional data. By
applying schema-supplied names during interpretation, it produces a hierarchy on which HIVE can
enforce field-specific rules and SIREN can navigate by meaningful paths. Source locations and included
file identities remain available through the resulting views.

5.9 MCNP INPUT

The MCNP interpreter recognizes the supported subset of MCNP 6.2 input and constructs a Core
Framework parse tree. MCNP documents combine line-oriented records, block organization,
continuations, comments, geometry expressions, materials, surfaces, tallies, and other domain-specific
cards defined by the application input language [3]. These conventions do not fit the general-purpose
structured or schema-driven language categories, so MCNP forms a domain-specific interpreter family
within the same interpretation layer.
The resulting hierarchy is available through NodeView, SIREN selection, and format-specific command-
line utilities. An MCNP model layer consumes that hierarchy to construct cells, materials, surfaces,
transforms, and constructive solid geometry relationships for supported records. After the MCNP
interpreter constructs the common parse tree representation, the MCNP model layer can use that hierarchy
to extract domain-specific information such as materials. This allows WASP to support an MCNP-
specific semantic model without modifying the Core Framework representation.
The MCNP interpreter documentation lists supported and unsupported card forms. That inventory defines
implementation coverage; the presence of MCNPInterpreter must not be interpreted as complete support

 27

for every MCNP input feature or version. Developers should evaluate their required card set against the
release-specific support table.

5.10 MULTI-FILE INTERPRETATION AND PROVENANCE

SON imports and HIT or EDDI includes allow a logical input to span physical files. WASP interpreters
connect these documents for traversal and can report recursively included paths. The node hierarchy
retains the originating source so that a consumer can distinguish where each component was written.
This capability is essential for Language Services and diagnostics. A semantic relationship may cross a
file boundary, but a user action must still target the correct file and location. The common iterator and
provenance model allow services to treat the content as one logical hierarchy without erasing physical
document boundaries.

5.12 INTERPRETATION OUTCOMES

Every language interpreter is expected to produce a root hierarchy, node names and types, ordered
relationships, source locations, and syntax diagnostics. Language-specific views add the knowledge
needed to distinguish meaningful and decorative constructs. A successful result means that the interpreter
constructed the supported syntax; it does not mean that HIVE semantics have passed.
Recovery behavior also affects integration. HIT can retain a partial hierarchy for selected incomplete
constructs, which is valuable during editing. Definition-driven interpretation can fail when schema
context cannot resolve abbreviated input. Applications should therefore preserve both the partial
representation and diagnostics when interactive tooling can still use them, while batch execution may
require a stricter success policy.

5.14 RELATIONSHIP TO THE FRAMEWORK

Input-language interpreters are producers of the common parse-tree representation. They depend on the
Core Framework for storage, views, diagnostics, and provenance. HIVE consumes their results to apply
application semantics. SIREN navigates their hierarchies, Language Services use their source-aware
nodes, and command-line utilities list, select, validate, or convert their content. WaspPy exposes selected
interpreters and their results to Python applications.
The input language is therefore an application choice at the boundary of WASP, not a separate
architecture. Once interpretation is complete, shared services provide consistent behavior across
supported formats.

5.15 SUMMARY

WASP 4.4 supports structured SON, HIT, JSON, and TOML input; definition-driven DDI and EDDI
input; and a domain-specific MCNP interpreter. Structured languages state hierarchy directly, definition-
driven languages combine concise text with schema knowledge, and MCNP interpretation maps an
established scientific format into supported hierarchical constructs. Every interpreter constructs a source-
aware representation that allows applicable navigation, modeling, utilities, and integration services to
operate through common concepts.

 6. HIERARCHICAL INPUT VALIDATION ENGINE

Syntactic interpretation establishes document structure but cannot determine whether that structure is
meaningful for a particular application. Applications must define required elements, legal values,
references, aggregate relationships, ordering, mutually constrained choices, and information used to assist
authors. Encoding these requirements procedurally for each input language would couple application
semantics to syntax and duplicate logic across batch, editor, and Python workflows.
HIVE is the semantic layer of WASP. It applies a declarative schema to the common parse tree
representation. HIVE supplies the schema language and evaluation machinery, but it does not infer an
application’s requirements. An application developer or another maintainer with authority over the
application’s input model must author the schema and update it as accepted structures, constraints, and
authoring guidance evolve.
This division of responsibility separates domain policy from framework mechanism. The application team
defines what constitutes valid and useful input; HIVE consistently interprets that definition during batch
validation, interactive authoring, and other integrations. This section organizes HIVE around the semantic
concepts a schema author can express rather than around an alphabetical inventory of rule names.
A HIVE schema is a SON document whose hierarchy represents the union of input structures accepted by
an application. Schema elements correspond to input paths and contain rules or metadata describing their
semantics. HIVE relates interpreted input nodes to this schema, evaluates the declared constraints, and
produces diagnostics associated with the relevant input or schema locations.
Rules are applied only when declared. Some operate on a single node or its siblings; others use SIREN
paths to select related nodes elsewhere in the hierarchy. The schema also contains assistance information
used for completion, descriptions, default text, variants, and documentation. This common semantic
source allows batch validation and interactive authoring to remain consistent.
HIVE validates an interpreted hierarchy. It does not replace an input-language interpreter, and it does not
require application semantics to be embedded in that interpreter. This separation allows the same
validation model to be used with structured and definition-driven languages.

 32

 Figure 12. HIVE applies an application-maintained declarative schema to an interpreted hierarchy and
 produces source-associated diagnostics and authoring assistance.

6.1 SCHEMA STRUCTURE

The schema hierarchy defines the structural model of an application. Each accepted input element must
have a corresponding schema element at the same hierarchical context. An input node with no valid
schema mapping is diagnosed as unsupported input. A schema can also mark a node as unknown so that
syntactically recognized but unsupported content receives a deliberate diagnostic.
Schema traversal follows the input that exists. If an optional parent is absent, HIVE can evaluate whether
that parent was required without attempting to validate children that cannot occur independently. This
behavior keeps diagnostics focused on the missing structural cause rather than producing secondary
failures for every descendant.
Definition-driven interpreters also use selected schema information to construct meaningful hierarchy.
That use precedes HIVE semantic validation. The same schema artifact can consequently contribute
structural interpretation, semantic constraints, and authoring assistance while those responsibilities remain
distinct.
Figure 13 shows how HIVE aligns nodes by hierarchical context. Rules attached to the schema’s
component/material/value node apply to the corresponding input value. A failed referential rule
produces a diagnostic on the input leaf, while an invalid rule would instead be associated with the schema
tree.

 33

 Figure 13. HIVE mapping between corresponding input and schema-tree contexts.

Path-aligned schema structure allows HIVE to apply one semantic model across supported interpreters
while retaining the provenance of both the application input and the schema. The schema can therefore
guide interpretation where required, govern validation, and supply authoring assistance without collapsing
those responsibilities into one operation.

6.2 OCCURRENCE CONSTRAINTS

Occurrence constraints describe how many times an element may appear under a parent. Minimum and
maximum bounds express required, optional, singular, and repeated input. A bound may be a literal value
or, where supported, a value selected from the surrounding input.
Occurrence checks are contextual. The number of matching children is evaluated at the relevant parent,
not across unrelated parts of the document. Maximum occurrence also informs completion: once the
allowed count is present, an authoring tool can omit that element from further suggestions.

6.3 VALUE CONSTRAINTS

Value constraints limit the content of scalar nodes. A schema can require an integer, real, or string form;
list accepted values; and apply inclusive or exclusive numeric bounds. A token may be a valid number in
the input language but still fall outside the range permitted by the application.
Enumerations serve both enforcement and assistance. During validation, a value outside the declared set
produces a diagnostic. During authoring, the same set supplies completion candidates. Type information
can also provide a suitable placeholder when no explicit default is present.

6.4 REFERENCE CONSTRAINTS

Many scientific inputs define an object in one location and refer to it elsewhere. HIVE expresses these
relationships with inclusion and exclusion constraints over SIREN paths and optional constant values. A
referenced value may be required to exist within selected nodes or prohibited from appearing there.

 34

Reference rules describe relationships while retaining source locations. HIVE can identify an invalid
reference, while Language Services can reuse the same path to offer candidates or navigate to a definition.
One rule therefore supports both validation and interactive authoring.

6.5 COLLECTION CONSTRAINTS

Collection constraints apply a condition to a selected set of nodes rather than to one scalar. Sum
constraints require selected values to produce a declared total. Grouped sums apply the relationship
within groups determined by related input. Count-equality constraints require selected collections to
contain matching numbers of elements.
These checks address relationships common in scientific models, such as normalized fractions, balanced
allocations, or parallel arrays. SIREN supplies the selected nodes; HIVE converts and combines their
values according to the declared rule and reports the relevant context when the relationship fails.

6.6 ORDERING CONSTRAINTS

Ordering rules require selected values to increase or decrease in document order. They are useful for
grids, time sequences, boundaries, and other inputs whose meaning depends on progression rather than
membership alone.
Because the common representation preserves child order, HIVE can evaluate the sequence as authored.
A failure can be associated with the element at which the required progression is violated, preserving a
direct connection between the semantic condition and source text.

6.7 STRUCTURAL CONSISTENCY

Some constraints govern combinations of children. A schema can require at most one, exactly one, or at
least one member of a set of alternatives. It can require selected collections to have equal counts and
values to be unique across one or more paths. These rules express consistency within a model rather than
the validity of one isolated scalar.
Choice constraints also improve assistance. Once an exclusive alternative is present, incompatible
alternatives can be removed from completion candidates. Uniqueness and count relationships remain
validation concerns because they depend on the assembled document rather than on one insertion point.

6.8 AUTHORING ASSISTANCE

A schema serves authors as well as validators. Assistance metadata can identify completion templates,
override names supplied to those templates, describe input types, offer variants, provide defaults,
recommend choices, and attach concise descriptions. Constraint rules such as maximum occurrence,
enumerations, type, references, and exclusive choices also contribute assistance information.
Recommended choices differ from enforced enumerations. An InputChoices declaration can suggest
static values or values selected from the document while allowing other values to remain legal. An
enumeration defines the accepted set. Maintaining this distinction prevents an editor recommendation
from becoming an unintended semantic restriction.
Template metadata connects HIVE to HALITE. A schema context can select a template and provide the
name, type, variant, or default data used to expand completion text. The schema describes when and why
the completion is applicable; HALITE describes its textual presentation.

 35

6.9 DIAGNOSTICS AND INVALID SCHEMAS

HIVE distinguishes a violation in application input from an invalid rule in the schema. Input diagnostics
identify the source location and describe the failed semantic condition. Schema diagnostics identify the
invalid schema rule and its schema location. This distinction is necessary because correcting application
input cannot resolve a malformed semantic specification.
Diagnostics retain the provenance supplied by the interpreter. In multi-file documents, the reported node
remains associated with its originating source. Consumers can present the same semantic result in
command-line output, Python diagnostics, or editor navigation.

6.12 REPRESENTATIVE EXAMPLES

6.12.1 Reference Integrity

Purpose. Require a use-site identifier to refer to an object declared elsewhere in the input.
Example. A model contains named materials and components whose material values must match one of
those names. An application developer records that requirement by associating the component value with
an ExistsIn path selecting the material identifiers. HIVE evaluates each component value against the
selected declarations.
The essential schema relationship is:
component {
 material {
 value {
 ExistsIn = [ "../../../materials/name/value" ]
 }
 }
}
The path is evaluated from the component’s value context. It moves to the document root and selects
every declared material name. A component that refers to steel is valid when that material is declared. A
component that instead refers to undeclared uranium fails the constraint.

 37

Discussion. An unknown material produces a diagnostic at the component reference. The same declared
relationship can provide completion candidates and support definition navigation in Language Services,
avoiding separate implementations of reference knowledge.

6.12.2 Collection and Ordering Constraints

Purpose. Validate relationships across an ordered collection rather than one value at a time.
Example. A composition contains fractions that must sum to one, and its associated temperature points
must increase. The application team encodes those domain requirements in the schema by applying a sum
rule to the fraction values and an increasing-order rule to the temperature sequence. HIVE evaluates the
declared rules for each interpreted input document.
Discussion. Every individual number may be lexically and numerically valid while the collection still
violates an application rule. Collection and ordering constraints express that relationship and allow HIVE
to report where it fails.

6.12.3 Assisted Exclusive Choice

Purpose. Keep validation and interactive assistance consistent for mutually exclusive input alternatives.
Example. A solver accepts exactly one of absolute_tolerance or relative_tolerance. A schema
maintainer declares the exclusive requirement and provides descriptions and defaults for both alternatives.
Before either is present, an editor can offer both completions. After one is inserted, the other can be
removed from the candidate list.
Discussion. The schema remains authoritative whether the document is created in an editor or validated in
a batch process. Assistance guides the author toward valid input, and HIVE still diagnoses documents
created without that assistance.

6.13 RELATIONSHIP TO THE FRAMEWORK

HIVE consumes application-maintained schemas together with parse trees and node views produced by
the input-language interpreters in Section 5. It uses SIREN, described in Section 7, to select nodes for
reference, collection, and consistency checks. Its schema metadata supplies descriptions, candidates,
defaults, and template selection to Language Services. HALITE, described in Section 8, expands
templates used for completion text. Command-line utilities and WaspPy expose the same validation in
non-editor workflows.
This position makes HIVE the semantic layer rather than a collection of unrelated checks. The application
team owns the meaning recorded in the schema; HIVE connects that meaning to the common
representation, and other framework services reuse that meaning for navigation, generation, diagnostics,
and assistance.

6.14 SUMMARY

HIVE expresses application semantics declaratively in a SON schema. Schema hierarchy defines
accepted structure; rules describe occurrence, values, references, aggregates, ordering, and consistency;
and metadata supports authoring assistance. HIVE applies the maintained specification to the common
parse-tree representation and preserves source provenance in its diagnostics. By separating application-
owned semantics from input syntax and framework evaluation, it provides one application model for
batch validation, Language Services, Python integration, and utilities.

 7. SEQUENCE INPUT RETRIEVAL ENGINE

Hierarchical documents are useful only if applications and framework services can identify the elements
relevant to a task. Direct traversal code ties each relationship to a procedure, obscures intent, and must be
repeated wherever the relationship is used. SIREN separates the description of a relationship from the
code that evaluates it.
SIREN is the declarative navigation language of WASP. Its expressions enter a workflow through two
principal authoring routes. A schema author embeds SIREN paths in HIVE rules when a semantic
constraint or authoring aid must relate one input location to another. HIVE evaluates those paths from the
node being validated and assigns meaning to the resulting selection—for example, whether a reference
must match one of the selected declarations.
An application developer may instead submit a SIREN expression directly when an application, utility, or
integration needs to retrieve nodes from an interpreted document. In that route, the application supplies
both the expression and its starting node, receives a SIREN result set, and decides how to use the selected
nodes. The two routes use the same path language and evaluator; they differ in where the expression is
authored and which consumer assigns meaning to its result.
This section describes SIREN’s path model, selection contexts, predicates, wildcards, and roles in
schema-driven relationships and direct retrieval. It does not present SIREN as an implementation of
another navigation standard; its architectural purpose is to express relationships within the WASP
common representation.
A SIREN expression is evaluated from a node context and produces an ordered collection of matching
nodes. A path may begin at the document root or remain relative to the current node. Each path step
selects children by name, moves to the current or parent context, or uses a wildcard when a name is not
known in advance. Predicates further restrict a step by position, range, stride, or child value.
An empty result is a normal selection outcome when no node matches. The consuming service determines
whether absence is acceptable. HIVE, for example, may treat an empty selection as a failed referential
constraint, while an application query may simply return no data.
SIREN operates on interpreted hierarchy rather than source text. It therefore applies consistently across
SON, HIT, JSON, TOML, DDI, and EDDI documents and can traverse logical hierarchies that include
nested files.

 39

 Figure 14. SIREN evaluates a declarative path from a document context to an ordered selection of nodes in
 the common representation.

7.1 NAVIGATION CONTEXT

Every relative expression has a starting context. A named step selects matching children of that node. The
current node step retains the context, and the parent step moves one level toward the root. An expression
beginning at the document root is independent of the caller’s current node.
Context makes one relationship reusable at repeated locations. A schema rule attached to each component
can select a sibling identifier relative to that component without embedding its complete document path.
Absolute paths are appropriate when the relationship is defined from a stable global location.

7.2 PATH COMPOSITION

A path composes simple selections into a traversal. The result of one step becomes the context for the
next. This composition expresses a structural relationship directly: a path identifies where relevant nodes
occur, while the evaluator performs the iteration required to reach them.
Selections preserve document order. This property matters for rules and applications whose meaning
depends on sequence. It also allows multiple matching parents to contribute children to the final
collection without replacing the hierarchy with a flat, language-specific index.
Figure 15 traces a complete selection. The rooted steps first establish the materials collection, the
predicate retains the material whose identifier is steel, and the final step selects its density leaf. The
result remains a view into the original tree rather than a copied scalar.

Figure 15. Evaluation of a rooted, predicated SIREN path over a parse tree; the predicate excludes the water
 material, and the final step selects the steel density.

7.3 POSITIONAL PREDICATES

Positional predicates restrict matches according to their position among selected nodes. A predicate can
select one position, a range, or a strided range. These forms support common operations such as selecting
the first occurrence, a bounded segment, or every repeated element at a regular interval.
Position is evaluated within the selection context represented by the path step. It is not a source-line
calculation. This distinction keeps navigation based on document structure even when formatting or
included-file boundaries change.

7.4 VALUE PREDICATES

A value predicate retains a node when one of its children satisfies a declared comparison. Successive
predicates can refine a selection through multiple child conditions. This permits an expression to select a
named object by an identifier or to locate a repeated element with a particular property.
The predicate describes a relationship among represented nodes rather than scanning raw text. Typed or
application-specific validity remains the responsibility of the interpreter and HIVE; SIREN determines
which nodes meet the expressed structural and value criteria.

7.5 WILDCARD SELECTION

Some document paths contain names that cannot be known when an expression is authored. Wildcards
allow a step to match unknown node names or name patterns. This is useful when an application permits
user-defined identifiers or when the schema relationship depends on structure rather than a literal child
name.
Wildcards should be scoped narrowly enough to preserve the intended relationship. A broad selection
may include decorative or semantically unrelated nodes depending on the supplied view. Consumers

 41

should begin from the closest stable context and apply subsequent predicates or named steps to refine the
result.

7.6 SELECTION AND PROVENANCE

SIREN results remain node views into the interpreted document. A selected node retains its parent
relationships, source, line, column, name, type, and data. Navigation therefore does not discard the
provenance established by the interpreter.
This property distinguishes declarative navigation from value extraction alone. HIVE can diagnose the
selected node, Language Services can navigate to it, and an application can retrieve its value while all
consumers refer to the same represented element.

7.7 RELATIONSHIP TO SEMANTICS

SIREN does not decide whether a relationship is required or valid. It supplies the node set to which
another service assigns meaning. HIVE uses SIREN paths for existence, exclusion, aggregation, ordering,
choice, count, and uniqueness relationships. Language Services can reuse referential selections to offer
completion candidates or locate definitions.
In the direct query route, the calling application supplies the expression and determines whether the result
represents data to process, a location to display, or simply an empty selection. Direct use therefore
provides retrieval without implicitly applying HIVE semantics.
Keeping navigation separate from semantics allows a path to be tested and reused independently. It also
prevents HIVE from embedding bespoke traversal algorithms for each semantic rule.

how it crosses hierarchy, and how much node-name knowledge the author possesses. Making these
choices explicit allows the same relationship to be reused by HIVE, Language Services, utilities, and

7.9 REPRESENTATIVE EXAMPLES

7.9.1 Schema-Authored Relative Reference Selection

Purpose. Allow a schema author to declare where HIVE should find legal targets for a reference.
Example. Each component contains a material reference, while material declarations occur under a
sibling collection. The schema author places a relative path in the HIVE rule associated with the
component’s material value:
ExistsIn = [ "../../../materials/name/value" ]
When HIVE validates a component, it evaluates the SIREN path from that component’s value context.
The path moves to the shared model context and selects the identifiers beneath the material declarations.

 43

Discussion. HIVE assigns semantic meaning to the selection by requiring the component value to match
one of the selected identifiers. Language Services can reuse the same schema-authored relationship for
completion and definition navigation. The path states where declarations are found without embedding an
application traversal procedure.

7.9.2 Direct Predicated Retrieval

Purpose. Allow an application developer to retrieve one category from a repeated set without defining a
HIVE rule.
Example. A document contains repeated boundary objects with a child named type and id.
After interpreting the document, an application submits the following SIREN query from the root node:
/boundaries/boundary[type = 'vacuum']/id
The expression selects boundary nodes whose type child has the value vacuum, then continues to their
identifier children.
Discussion. The application receives the matching identifiers as an ordered SIREN result set and decides
how to process them. No semantic requirement follows merely from running the query: an empty result
can be acceptable unless the application assigns a different meaning. The selected nodes retain source
provenance and document order.

7.10 RELATIONSHIP TO THE FRAMEWORK

SIREN consumes node views supplied by the Core Framework and input-language interpreters. HIVE is
its principal semantic consumer, using paths to relate schema contexts to sets of input nodes. Command-
line selection utilities expose the same navigation capability for direct document queries. Language
Services reuse declared relationships for candidates and definitions, and applications can retrieve selected
data without implementing language-specific traversal.
SIREN complements rather than replaces other declarative services. HIVE assigns semantic meaning to
selected nodes, the Expression Engine calculates values in an evaluation context, and HALITE presents
Object data as text. SIREN’s responsibility is navigation through represented document hierarchy.

7.11 SUMMARY

SIREN expresses navigation as declarative paths over the common representation. Relative and absolute
contexts, composed steps, positional and value predicates, and wildcards produce ordered collections of
source-aware nodes. By separating relationships from traversal procedures, SIREN supplies consistent
navigation to HIVE, Language Services, utilities, and application integrations.

 8. HIERARCHICAL INPUT TEMPLATE ENGINE

Applications often transform structured data into input decks, reports, configuration fragments, or other
text. Implementing presentation directly in application code couples data acquisition to the syntax and
layout of each target. Small presentation changes then require code changes, and supporting another target
requires another procedural generator.
HALITE provides declarative presentation and document generation. It separates Objects from the
templates that determine their textual form. This section describes the evaluation model, data access,
expressions, iteration, formatting, composition, and conditional presentation supported by HALITE.
A HALITE workflow consists of a template, an optional Object containing data, an evaluation context,
and an output stream. Static template text is copied to the stream. Attributes and expressions obtain or
compute values and emit formatted text. Scoped evaluation changes the active Object context. Iteration
repeats substitutions or subtemplates, conditional blocks select content, and imports compose a
presentation from reusable files.
HALITE uses the Expression Engine described in Section 4. Template data are made available through an
evaluation context, and expressions produce typed results before formatting and emission. Evaluation
diagnostics identify malformed constructs, unavailable data, expression failures, import problems, and
invalid formatting.
HALITE is not the semantic layer of WASP. HIVE determines whether application input satisfies a
schema. HALITE determines how available data are presented. Language Services connect these
responsibilities when schema assistance metadata selects a template for completion text.

 Figure 16. HALITE combines an Object, a template hierarchy, and expression evaluation to produce
 presented text.

8.1 STATIC TEXT AND ATTRIBUTES

Static text is emitted without transformation. Attributes identify named values in the active Object and
substitute their evaluated form between configurable delimiters. Delimiter controls allow HALITE to
generate text that would otherwise conflict with its default attribute notation.
An attribute may be ordinary, optional, or silent. An optional attribute emits nothing when its value is
absent, permitting surrounding presentation to appear only with the data. A silent attribute evaluates
without writing its result and can establish an intermediate value for later expressions. Intrinsic attributes
provide common constants and delimiter or newline values.

8.2 EXPRESSION EVALUATION

An attribute position can contain an Expression Engine calculation rather than one named value.
Arithmetic, comparison, Boolean logic, string concatenation, functions, conditional selection, and array
access allow the template to derive presentation values without application-specific glue code.
The template specifies the desired result in terms of available data. The application supplies the Object,
the Expression Engine performs computations, and HALITE writes the output. Applications can register
domain-specific functions in the evaluation context when the default function set is insufficient.

8.3 OBJECT AND ARRAY SCOPE

Template evaluation begins at an Object context. Member access can descend through named Objects,
and a use scope evaluates a construct against another Object while retaining access to enclosing contexts.
This supports local names within reusable template fragments without flattening the source data.
Using an array as a scope implies iteration over its elements. Each array element becomes the active
Object for the evaluated construct. Parent data remain available, allowing repeated output to combine
local fields with information shared by the enclosing Object.

8.4 ITERATION

HALITE can iterate array attributes over an index range and can define explicit start, end, and stride
values. Separators control text between results, while periodic emission inserts text after a configured
number of elements. These iteration and emission controls support comma-separated data, line wrapping,
and fixed-column scientific formats.
Iteration also occurs through array-scoped evaluation and repeated imports. The appropriate form depends
on the unit being repeated: an attribute iteration repeats one expression, an array scope repeats a construct
for Object elements, and a repeated import applies an entire subtemplate over ranges.

8.5 FORMATTING

Formatting converts an evaluated value into its final textual representation. HALITE supports string,
signed-integer, decimal floating-point, and scientific-notation conversions with applicable flags, width,
and precision. A format may also include surrounding literal text, which is emitted only when the
associated optional value is available.
Formatting is part of presentation, not application semantics. A numeric value remains numeric during
evaluation; width and precision determine how that value appears in the target document. Invalid
combinations of value, flag, and conversion produce evaluation diagnostics instead of silently malformed
output.

 46

8.6 TEMPLATE IMPORTS

Imports compose a document from reusable templates. An imported path may be relative to the current
template, relative to the working environment, or absolute, and may itself depend on available attributes.
The imported template inherits access to data in the current and enclosing contexts.
An import can use a selected Object as its local data or iterate implicitly over an array. Explicit repeat
constructs import a subtemplate over one or more ranges and make their range variables available during
evaluation. Nested composition separates the output for one component from the output for the complete
document.

8.7 CONDITIONAL BLOCKS

Conditional blocks select template regions according to a defined variable or Boolean expression. Initial
conditions, alternate conditions, and fallback content provide mutually exclusive presentation paths. Only
the selected content contributes to the output.
Conditions permit one template to handle optional data or controlled variants without moving
presentation decisions into application code. HIVE remains responsible for determining which variants
are semantically legal; HALITE expresses how a selected or available variant appears.

8.8 COMPLETION TEXT

HIVE assistance metadata can associate a schema element with a HALITE template, input name, type,
variant, or default. Language Services evaluate the selected template to construct completion text for the
current document node. Snippet-capable clients can receive interactive placeholder forms when the
integration enables them.
This use demonstrates HALITE’s architectural role beyond batch file generation. The template still
describes how data should appear, but the output is sent to an editor instead of a file. Schema rules
determine whether the completion is allowed, and Language Services deliver the result.

8.9 TEMPLATE CONSTRUCTS

HALITE constructs operate at different scales. Some determine whether one value is emitted, some repeat
a local expression, and others compose or select entire template regions. Choosing the smallest
appropriate construct keeps the presentation legible and limits the context on which it depends.

8.12 TEMPLATE IMPORTS AND RESOLUTION

Imports establish a template hierarchy analogous to component composition in application architecture. A
relative import can resolve from the current template or working environment, while an absolute path
identifies a fixed asset. Attribute-dependent paths permit a context to select a presentation variant.
Parameterized imports select an Object or array as the subtemplate’s local context. Parent contexts remain
visible, which allows a subtemplate to combine component data with document-wide settings. This
inheritance is useful but also creates a dependency: a reusable template should make its required local and
parent attributes explicit in its documentation and tests.
Conditional blocks and imports can be combined to choose among component presentations. HIVE
InputVariants and InputTmpl metadata use this compositional model for completion. The schema
decides which presentation is appropriate at a document location; HALITE resolves and expands the
selected asset.

8.13 REPRESENTATIVE EXAMPLES

8.13.1 Reusable Component Output

Purpose. Generate repeated component text without embedding target syntax in application code.
Example. An Object contains an array of components, each with a name, material, and numeric
properties. A root template imports a component subtemplate using the array. HALITE evaluates the
subtemplate once for each component, formats the numeric properties, and emits the repeated target-
language blocks.
Suppose the components array contains two component Objects. The root template delegates both
component scope and component representation:
#import component.tmpl using components
The subtemplate defines the target structure and numeric formatting:
component (<name>) {
 material = <material>
 density = <density:fmt=%.3f>
}
Because components is an array, HALITE evaluates the imported template once for each element and
makes that element the active Object. The subtemplate can therefore refer to name, material, and
density without embedding either the parent path or an array index. The format option writes each
density with three fractional digits while leaving the stored value unchanged.
Result. The import produces two complete blocks in array order:
component (primary_loop) {
 material = steel
    density = 7.850
}
component (reflector) {
 material = graphite
    density = 1.720
}

 50

Discussion. The application supplies one data model while the subtemplate owns component
presentation. Adding another component changes the data rather than the root template, and a different
subtemplate can produce another target format without changing Object construction logic.

8.13.2 Optional Formatted Field

Purpose. Emit a field and its surrounding syntax only when data are present.
Example. The following template can be evaluated against Objects with and without comment:
record <x> <y> <z><comment:?fmt= com="%s">
When comment is present, the format writes both the value and its surrounding target-language text:
record 1 2 3 com="inlet"
When comment is absent, the optional construct emits nothing, including the leading space and com=""
punctuation carried by the format:
record 1 2 3
Discussion. This behavior does more than suppress a missing value. By placing dependent punctuation
inside the format, the template treats the complete field as one unit. Optional presentation prevents
dangling syntax and avoids assembling partial strings in application code.

8.13.3 Fixed-Width Array Layout

Purpose. Format an arbitrary-length numeric array under a target’s field-width and line-length
constraints.
Example. The following template derives its inclusive upper index from the data, formats every value in
an eight-column field, suppresses inter-element separators, and inserts a newline after each group of four:
times = <times[j]:j=0,<size(times)-1>;fmt=%8.3f;sep=;emit=<nl>,4>
Five values are realized as:
times =      1.000      2.000    3.000     4.000
 5.000
Discussion. The data determine the range, while the target format determines width and wrapping. The
Object retains the numeric values and array length; the template controls their textual arrangement. The
emit option inserts text only after completed intervals that precede more values, so the final element does
not add an unnecessary newline.

8.13.4 Conditional Document Region

Purpose. Select a complete target-language region according to data availability.
Example. The following template uses #ifdef because the decision concerns whether comment exists,
not whether its value satisfies a domain rule:
#ifdef comment
annotation {
 text = <comment>
}
#else
annotation = none
#endif
With comment defined, the block form is emitted; without it, the single-line fallback is emitted. Only the
selected branch contributes text.

 51

Discussion. An optional attribute is appropriate when one value and its immediate punctuation can
disappear. A conditional region is appropriate when presence changes the surrounding document
structure. This distinction keeps large structural alternatives explicit and prevents optional-value notation
from obscuring target grammar.

8.13.5 Repeated Multidimensional Component

Purpose. Generate a structured block over explicit ranges when repetition is not represented by an input
array.
Example. A root template can define two ranges and delegate each range combination to cell.tmpl:
#repeat cell.tmpl using i=1,2; j=0,2,2
The subtemplate uses the range variables as ordinary expression variables:
cell(<i>,<j>)
HALITE evaluates the inner j range for each i, producing:
cell(1,0)
cell(1,2)
cell(2,0)
cell(2,2)
Discussion. Array-scoped imports repeat existing data; #repeat creates indices for generated output. This
is useful for regular grids and generated records, but the range variables do not become members of the
source Object.

8.13.6 Schema-Selected Completion

Purpose. Present valid input scaffolding during interactive authoring.
Example. A HIVE schema associates a solver context with a HALITE completion template and provides
a default tolerance. When completion is requested, Language Services select the template and supply the
schema-derived context. HALITE expands the solver block and its initial value for insertion by the editor.
Discussion. HIVE determines that the solver is applicable and supplies semantic metadata. HALITE
determines the textual form. This separation keeps validation and presentation consistent without
combining them into one component.

8.14 RELATIONSHIP TO THE FRAMEWORK

HALITE consumes Objects from the Core Framework and uses the Expression Engine for computation
and conditions. HIVE assistance metadata selects templates and supplies completion information.
Language Services invoke this combination for interactive authoring, while command-line utilities and
applications use HALITE for file generation. WaspPy and other integrations can construct or deserialize
the Objects supplied to templates.
HALITE completes a bidirectional architectural pattern. Input-language interpreters construct common
representations from text; HALITE presents Object data as text. The two directions share types and
services but retain distinct responsibilities for interpretation and presentation.

8.15 SUMMARY

HALITE provides declarative presentation by evaluating templates against Objects. Attributes,
expressions, scope, iteration, formatting, imports, repeats, and conditional blocks compose generated text
without application-specific presentation code. Integration with HIVE and Language Services applies the

same mechanism to completion text, while the separation between semantics and presentation remains
explicit.

 9. LANGUAGE SERVICES

Interactive authoring requires more than a protocol connection between an editor and a server. Useful
diagnostics, completion candidates, descriptions, symbols, and definition locations depend on knowledge
of document syntax, application semantics, hierarchical relationships, and presentation. Implementing that
knowledge independently in an editor would duplicate the framework and produce behavior inconsistent
with batch processing.
WASP Language Services coordinate existing framework capabilities for interactive use. The Language
Server Protocol (LSP) provides the transport and operation model, but the architectural contribution is the
orchestration of interpreters, HIVE, SIREN, HALITE, schemas, and source provenance. This section
describes that orchestration and the supported service boundaries in release 4.4.
In the usual interactive workflow, the end user works in an LSP-capable editor, and the editor occupies
the protocol’s client role. The editor sends document notifications and feature requests to an application-
specific WASP language server. That server coordinates a WASP interpreter, HIVE, SIREN, and
HALITE, then returns diagnostics and authoring assistance through the editor. The term LSP client in this
section therefore refers to the editor or another program occupying the same protocol role; it does not
refer to the end user.
When a document is opened or changed, the application-specific WASP language server interprets its
text, applies the application schema, and publishes syntax and semantic diagnostics. On request, it derives
hierarchical document symbols from the parse tree, descriptions from schema metadata, completion
candidates from constraints and assistance metadata, completion text from HALITE templates, and
definition locations from declared relationships. These operations use LSP 3.17 structures [7].
WASP also supplies a programmatic client implementation for applications that need to occupy the LSP
client role without an editor. LSPInterpreter builds on that implementation for a different integration
case: it makes the document symbols and diagnostics produced by a conforming language server available
through a WASP interpreter interface. Neither component is required when an editor already
communicates directly with an application-specific WASP language server.
Release 4.4 also supports custom protocol extensions, snippet-aware completion, workspace file
watching, hover content, multiple documents, and Python access to server and connection
implementations. These capabilities extend deployment without changing the underlying sources of
syntax and semantic knowledge.

 54

 Figure 17. Language Services orchestrate interpreters, HIVE, SIREN, HALITE, and schemas across an
 editor protocol boundary.

9.1 SERVICE ORCHESTRATION

Language Services reuse the same processing path as other WASP integrations. The selected interpreter
constructs the parse tree and records source locations. HIVE applies the application schema. SIREN
resolves relationships. HALITE expands schema-selected completion templates. The server converts the
resulting information into protocol messages.
This orchestration keeps application-language knowledge out of editor-specific code. Interactive guidance
and batch enforcement remain aligned because both derive from the same interpreted hierarchy, schema
constraints, and presentation assets.

9.2 DOCUMENT LIFECYCLE

The protocol lifecycle establishes capabilities, opens documents, communicates changes, closes
documents, and performs orderly shutdown. WASP retains state for multiple open documents and
reprocesses text as updates arrive. Diagnostics are published after interpretation and semantic validation.
In release 4.4, WASP server change handling uses full-document text replacement rather than incremental
line-and-column edits. This limitation affects transport efficiency, not the interpretation and validation
architecture. Workspace watch-file registration is enabled only by servers that require it.

9.3 DIAGNOSTICS

Syntax diagnostics originate with the interpreter, and semantic diagnostics originate with HIVE or an
application integration. Their line, column, range, source, severity, and text are converted to protocol
diagnostics for presentation by the client.
Because the common representation preserves provenance, diagnostics can identify content in included or
imported files. The server does not need to rediscover positions by scanning text after validation. The
same diagnostic meaning remains available to command-line and Python consumers.

 55

9.4 COMPLETION

Completion combines structural context with schema semantics and presentation. Occurrence and
exclusive-choice constraints filter candidates. Enumerations, reference paths, recommended choices,
defaults, types, variants, and descriptions supply candidate data. HALITE templates construct the text to
insert for complex elements.
Snippet support adds tab stops or placeholders when the client advertises the corresponding capability and
the server enables it. Plain-text completion remains available when snippet support is absent. The schema
determines what may be offered; the template determines how the candidate is presented.

9.5 HOVER AND DOCUMENT SYMBOLS

Schema descriptions provide context-sensitive hover content. The server relates the requested source
position to a represented node and its schema element, then returns the associated explanation. Array
content can also participate in hover responses where supported.
Document symbols translate the parse tree hierarchy into the protocol’s hierarchical symbol form. This
preserves the document’s structural organization for editor outlines and for clients that reconstruct a
WASP-like tree. Symbols provide names, kinds, detail, and ranges but do not necessarily carry leaf
values.
Figure 18 illustrates this projection. Structural nodes become nested document symbols, and source
provenance becomes protocol ranges. The projection is sufficient for outlines and location-aware
navigation even though the protocol response does not reproduce the complete lexical tree.

 Figure 18. Projection of a WASP parse tree into hierarchical LSP document symbols.

This projection illustrates the Language Services boundary: WASP retains the richer parse tree internally
and exports only the structure and source ranges required by the protocol operation. Other services can
continue to use lexical detail and values without requiring the protocol representation to reproduce the
complete common representation.

 56

9.6 DEFINITION NAVIGATION

Definition navigation reuses reference constraints declared in the schema. An existence relationship
identifies the paths at which legal target values are defined. Given a reference under the cursor, Language
Services select the matching declaration and return its source location.
This reuse is important: validation, completion, and navigation agree on what constitutes a valid target.
References are not separately hard-coded into the server. General reference-list requests are not
implemented by the WASP server in release 4.4, and document formatting is likewise not provided.

9.7 CLIENT AND LSPINTERPRETER

The WASP client manages protocol connections, initialization, document notifications, requests, and
typed response access. It allows applications to interact with a conforming server without implementing
message construction and lifecycle control independently.
LSPInterpreter adapts a language server to the WASP interpreter model. When the remote server
supplies hierarchical document symbols, the adapter constructs a parse-tree-like hierarchy with source
ranges. Because protocol symbols do not include the original leaf values, the adapted tree may preserve
structure and location without complete data content.

9.8 CUSTOM EXTENSIONS AND CONNECTIONS

Applications can define custom client and server extensions for capabilities outside the standard protocol.
The plotting structures described in Section 12 are one use of this extension boundary. Connection
abstractions separate protocol handling from a particular stream or process arrangement, and Python
interfaces make server and connection implementations available to Python integrations.
When implementing a custom extension, developers should add application operations without bypassing
the common representation and semantic model. A custom visualization request, for example, can select
or compute data through application services and return a serializable Object while retaining standard
diagnostics and document lifecycle behavior.

9.9 REPRESENTATIVE EXAMPLES

9.9.1 Schema-Driven Completion

Purpose. Assist an author in adding a valid structured element.
Example. At a solver context, the server identifies schema children that remain legal under occurrence
and choice constraints. It supplies descriptions and defaults, selects a HALITE template for the chosen
solver type, and returns plain text or a snippet according to client capability.
Discussion. The editor receives useful insertion text without containing application rules. Subsequent
HIVE validation uses the same schema, keeping guidance and enforcement aligned.

9.9.2 Definition Navigation Across Files

Purpose. Navigate from a use-site identifier to its declaration in an included document.
Example. A material reference occurs in the primary file, while the matching material declaration occurs
in an included file. The schema’s referential path identifies candidate declarations, SIREN selects the
matching value, and the server returns the declaration’s source and range.

 57

Discussion. Navigation succeeds because interpretation preserves physical provenance while exposing
one logical hierarchy. The relationship used to navigate is also the relationship used to validate the
reference.

9.10 RELATIONSHIP TO THE FRAMEWORK

Language Services form an orchestration layer. Input-language interpreters supply syntax and source-
aware hierarchy; HIVE supplies application semantics and assistance metadata; SIREN supplies
document relationships; HALITE supplies completion presentation; and the Core Framework supplies
diagnostics, views, and Objects. LSP transports the resulting operations between servers and clients.
This arrangement allows interactive behavior to evolve with the schema and templates rather than with
editor-specific code. It also allows the same framework knowledge to serve command-line, C++, and
Python workflows.

9.11 SUMMARY

WASP Language Services integrate interpretation, semantic validation, declarative navigation, and
template-based presentation for interactive authoring. The protocol carries diagnostics, completion, hover,
symbols, definitions, lifecycle events, and extensions, while the framework supplies their meaning.
Release 4.4 supports multi-document operation, snippets, hover, workspace watching, custom extensions,
and Python integration, with full-document change processing and no WASP server support for general
references or formatting.
 10. PYTHON INTERFACES

Python applications need access to structured scientific input without reproducing WASP interpretation
and semantic behavior in Python. They also need a natural means of traversing hierarchy, converting
values, defining application input, constructing domain objects, and reporting diagnostics at source
locations.
WaspPy provides Python application integration with WASP and is distributed with the WASP 4.4
Python package [2]. It adapts interpreters and NodeView access to Python patterns and supplies a Python-
native input definition and deserialization layer. The broader WASP software identity is also preserved
through a DOE CODE record and persistent DOI [8]. This section describes those architectural interfaces
without enumerating the complete generated API.
The WaspPy interpreter facade selects a supported syntax, reads text from a path or stream, optionally
applies a schema, and exposes diagnostics and a root WaspNode. Python applications traverse named
children through attribute or bracket access, iterate repeated nodes, inspect provenance, and convert
values to Python scalar types.
For applications that want a domain-oriented data model, InputObject defines expected hierarchy,
occurrences, defaults, value constraints, relationships, and conversion actions in Python. Deserialization
applies that definition to interpreted nodes and produces DeserializedResult objects containing source-
aware results and converted values. Application factories can then construct domain objects and add
diagnostics through the originating interpreter.
WaspPy also exposes selected HIVE and Language Services capabilities. Release 4.4 includes Python
server and connection implementations, allowing Python applications to participate in the same
integration architecture described in Section 9.

 58

 Figure 19. WaspPy connects Python applications to interpreters, source-aware nodes, schemas,
 deserialization, diagnostics, and Language Services.

10.1 INTERPRETER FACADE

The Python Interpreter encapsulates selection and setup of WASP interpreters. It accepts structured or
definition-driven syntax, input content or a path, and schema information when required. The facade
collects syntax, schema, and deserialization diagnostics through one application-facing object.
This boundary allows a Python application to change supported input syntax without replacing its
traversal and diagnostic logic. Definition-driven formats still require schema knowledge, and semantic
validation remains explicit, but the resulting root uses the same Python node abstraction.

10.2 WASPNODE

WaspNode adapts NodeView to Python. It exposes the node name, type, data, path, parent and children, line
and column range, originating source, and decorative or leaf status. Iteration traverses children, while
named access returns one or more matching child nodes.
Attribute access supports concise traversal such as moving from a document to a named block and its
values. Bracket access provides the same capability when a node name conflicts with Python syntax or
when an index is required. Numeric and string conversion obtain a node’s value in a Python form while
the node itself retains provenance.

10.3 COLLECTIONS AND REPEATED INPUT

Repeated named children are represented as node collections that remain iterable and support continued
named traversal. An application can therefore request one path across every repeated parent and receive
the matching descendants without writing a nested search for each level.
This convenience does not flatten the underlying representation. Individual results remain WaspNode
instances connected to their parents and sources. Applications can choose concise vector-style access or
explicit traversal depending on whether structural context matters.

Figure 20 shows how chained attribute access traverses repeated tree nodes. The expression shortens the
navigation syntax, but the resulting collection retains separate WaspNode objects with their own parents,
paths, and source positions.

10.4 INPUTOBJECT

InputObject is a Python-native description of application input. Definitions compose named child
objects and describe required or optional occurrence, single or repeated input, defaults, descriptions,
enumerations, numeric bounds, uniqueness, existence, and constrained alternatives. Terminal definitions
may associate an action that converts or stores an interpreted value.
The definition mirrors important HIVE semantic concepts but serves a Python deserialization workflow.
It allows application classes to keep their expected input structure close to their construction logic and to
generate diagnostics through represented nodes. A utility can generate Python database classes from a
SON schema when maintaining the definition manually is not appropriate.

10.5 DESERIALIZATION AND DESERIALIZEDRESULT

Deserialization walks an interpreted hierarchy according to an InputObject definition. It checks expected
children and constraints, applies defaults and terminal actions, and records results under their input
names. A DeserializedResult retains the associated node and interpreter so converted values remain
connected to their source and diagnostic channel.
Application factory methods can consume these results to construct domain objects. Post-deserialization
checks may compare fields or apply domain logic that is not represented by the basic definition. When
such a check fails, the factory can create an error or warning diagnostic on the relevant source node rather
than raising an unlocated text message.

 60

10.6 DIAGNOSTICS

The interpreter facade consolidates diagnostics from interpretation, HIVE, deserialization, and application
checks. Diagnostics preserve severity and node location. Applications can stop on errors, present
warnings, or report the complete set through their own interface.
Allowing application code to create diagnostics is important for semantic checks that require domain
objects or computations outside the declarative schema. The application extends the semantic workflow
without losing the provenance and presentation conventions used by WASP.

10.7 LANGUAGE SERVICES IN PYTHON

Python integrations can use WASP language-server and connection interfaces to provide interactive
behavior without moving application orchestration into C++. The same schema, interpreter, and
completion assets remain applicable. Python code can also implement application-specific server behavior
or custom extensions while reusing protocol lifecycle and common message structures.
This interface complements the direct interpreter workflow. A batch Python program may deserialize one
file, while a Python language server maintains multiple changing documents. Both workflows depend on
the same represented hierarchy and semantic assets.

10.8 REPRESENTATIVE EXAMPLES

10.8.1 Direct Node Access

Purpose. Read repeated scientific input while retaining access to its source hierarchy.
Example. A Python application opens a SON or HIT document containing repeated material objects. It
iterates the material nodes, converts each density value to a floating-point value, and records each
identifier. If a calculation fails, the application retains the original WaspNode for location-aware reporting.
Discussion. The application uses Python iteration and conversion without losing the structure or
provenance constructed by WASP. Changing between supported structured syntaxes does not require a
new domain traversal model.

10.8.2 Domain Object Construction

Purpose. Convert validated input into application classes with defaults and domain diagnostics.
Example. An InputObject definition describes a required material name, optional density model,
numeric coefficient bounds, and a default model type. Deserialization produces source-aware results and
applies conversion actions. A factory constructs the material class and adds a diagnostic if the combined
coefficients violate a relationship requiring domain computation.
Discussion. Declarative structure and simple constraints remain in the definition, while domain behavior
remains in the class factory. Both layers report through the same interpreter and source nodes.

10.9 RELATIONSHIP TO THE FRAMEWORK

WaspPy exposes Core Framework views, input-language interpreters, HIVE validation, Python input
definitions, and Language Services to Python applications. WaspNode preserves the common
representation and provenance. InputObject and DeserializedResult connect represented input to
application data. Diagnostic creation allows Python domain semantics to participate in the same reporting
model.

The interface therefore adapts WASP architecture to Python rather than reimplementing it. Applications
gain Python-native access while sharing schemas, interpreters, relationships, and diagnostics with C++,
command-line, and editor workflows.

10.10 SUMMARY

WaspPy provides Python application integration through an interpreter facade, source-aware WaspNode
traversal, typed conversion, InputObject definitions, deserialization results, diagnostics, and Language
Services. These interfaces allow Python programs to consume and validate multiple input syntaxes,
construct domain objects, and extend semantic reporting while preserving the common representation.

 11. COMMAND-LINE UTILITIES

Not every document-processing task requires an application to embed WASP. Developers and analysts
need to inspect parse trees, test selections, validate input, convert formats, generate text, and derive initial
schema or documentation artifacts from scripts and interactive shells. Implementing separate tools for
those tasks would duplicate interpreter and service behavior.
WASP command-line utilities expose framework capabilities as focused processes. This section organizes
the utilities by workflow and explains how they support development, automation, and interoperability. It
does not enumerate every option or executable invocation.
Command-line integration follows one common pattern: select an interpreter, construct the shared
representation, and apply one focused framework operation. Depending on the workflow, that operation
may inspect hierarchy, evaluate a SIREN expression, apply a HIVE schema, convert represented data,
evaluate a HALITE template, or invoke a schema development or domain adapter. The utility remains a
thin process boundary over the same component used by embedded integrations.
Standard input, standard output, standard error, and process exit status make these operations usable in
shell pipelines and automated workflows. Diagnostics remain tied to source locations because the utilities
call the same interpreters and services used by embedded applications.

 Figure 21. Command-line utilities expose interpretation, navigation, validation, conversion, generation, and
 documentation as composable processes.

11.1 HIERARCHY INSPECTION

Listing utilities emit an ordered, path-oriented view of a parse tree. They show how the interpreter named
and nested document components and may include node data or lexical constructs. Format-specific tools
are available for the principal supported languages, including SON, HIT, DDI, EDDI, JSON, TOML, and
MCNP input.
Inspection is particularly useful when developing a schema or SIREN expression. It reveals the hierarchy
consumed by downstream services without requiring a diagnostic program or debugger. Decorative nodes

 63

remain visible where the selected listing mode includes them, allowing source structure to be
distinguished from semantic content.

11.2 DECLARATIVE SELECTION

Selection utilities interpret a document and evaluate a supplied SIREN expression. The result contains the
selected document components in source order. Corresponding tools allow the same navigation approach
to be applied across supported input languages.
These utilities provide a direct way to develop and test paths used by HIVE or application logic. A path
can be checked against representative input before it is placed in a schema. Selection output can also feed
a later process when only one part of a larger document is relevant.

11.3 SEMANTIC VALIDATION

Validation utilities accept an input document and a HIVE schema. They report syntax, schema, and
semantic diagnostics and return a process status suitable for automation. SON, HIT, DDI, EDDI, and
JSON validation workflows are provided in release 4.4.
Command-line validation uses the same separation described in Section 6: the language interpreter
constructs the hierarchy, and HIVE applies application semantics. Build systems, regression tests, and
data-ingestion scripts can therefore enforce the same schema used by Language Services or embedded
applications.

11.4 XML AND JSON INTERCHANGE

XML conversion utilities serialize interpreted hierarchy with data and location information. They provide
an interoperability boundary for scripts and external systems that can consume XML but do not embed
WASP. The retained location metadata allows a downstream tool to relate converted elements to source
text.
JSON conversion utilities produce value-oriented data from SON, DDI, HIT, or TOML input as
supported by the corresponding executable. Some variants validate against a schema before or while
producing JSON and use standard error and exit status to distinguish diagnostics from converted output.
Conversion may omit decorative text or format-specific information that is not represented by the target
data model.

11.5 DECLARATIVE GENERATION

The halite utility evaluates a template with optional JSON-formatted data and writes the generated text.
It makes the declarative presentation capability in Section 8 available to scripts, build workflows, and
users who do not need a C++ or Python application.
Template diagnostics and expression failures are reported through the command-line workflow. Because
templates can import and repeat other templates, one invocation can generate a composed document from
reusable presentation assets.

11.6 SCHEMA DEVELOPMENT AND DOCUMENTATION

The SON schema-skeleton utility derives an initial schema hierarchy from representative SON input. The
result is a starting point: application authors must still add occurrence, value, reference, collection,
consistency, and authoring-assistance rules. A sample document cannot by itself establish the union of all
accepted input.

 64

The documentation utility reads a schema and emits reference material describing names, types,
occurrence, restrictions, choices, and descriptions. This reuses the semantic source maintained for
validation and assistance. It reduces divergence between a schema and generated input reference material,
while the architectural explanations in this memorandum remain separate.

11.7 DOMAIN WORKFLOW UTILITIES

The Dakota substitution utility reads the standard parameters format used by Sandia National
Laboratories’ Dakota analysis and optimization tool [9] and applies those values to a template workflow.
This connects an external uncertainty-quantification process to WASP generation without requiring a
custom parameter reader for every application.
MCNP utilities list and select represented input and can extract material information. They operate on the
MCNP interpreter’s supported subset; they should not be interpreted as a claim that every MCNP input
construct is implemented. Domain tools demonstrate how the common representation can support focused
operations while retaining a specialized interpreter boundary.

11.8 REPRESENTATIVE EXAMPLES

11.8.1 Schema Development Pipeline

Purpose. Develop and verify a semantic schema from representative input.
Example. An author lists a SON document to inspect its hierarchy, generates a schema skeleton, adds
semantic constraints, validates several accepted and rejected documents, and tests referential paths with a
selection utility. The documentation utility then produces schema-derived reference material.
Discussion. Each step uses the same represented paths and semantics. The skeleton accelerates structural
setup but does not replace the author’s responsibility to describe all accepted structures and application
relationships.

11.8.2 Validated Conversion

Purpose. Supply JSON data to a downstream process while enforcing application semantics.
Example. An automation script invokes a validated JSON conversion utility with an input file and
schema. Converted data are written to standard output, diagnostics are written to standard error, and the
exit status determines whether the downstream process should continue.
Discussion. The workflow separates machine-readable data from diagnostics and applies the same HIVE
semantics used elsewhere. The downstream process receives a common data form without implementing
the source language.

11.9 RELATIONSHIP TO THE FRAMEWORK

Command-line utilities are thin integration surfaces over interpreters, NodeView, SIREN, HIVE, HALITE,
serialization, and domain adapters. Their behavior should remain consistent with library, Python, and
Language Services workflows because they invoke the same architectural components.
The utilities also support development of those other integrations. Listing reveals paths, selection tests
relationships, validation tests schemas, generation tests templates, and conversion supplies fixtures or
exchange data. They make the framework observable and composable without becoming a separate
processing architecture.

11.10 SUMMARY

WASP command-line utilities expose hierarchy inspection, declarative selection, semantic validation,
XML and JSON conversion, HALITE generation, schema development, documentation, and selected
domain workflows. Standard process interfaces make these capabilities suitable for interactive use and
automation.

 12. FRAMEWORK INTEGRATION

WASP provides value when its common representation and declarative services become part of a larger
application workflow. The integrating developer selects the input language and deployment boundary,
supplies application-owned schemas, paths, templates, and domain logic, and decides how results reach
users or other software. WASP interprets input, owns and exposes the resulting parse tree, evaluates
configured semantic and navigation assets, presents Object data through templates, and returns
diagnostics or other structured results.
This section describes the principal integration boundaries in WASP 4.4 and assigns responsibility for the
actions in each workflow. Where an API imposes a requirement, such as the lifetime relationship between
an interpreter and its node views, the text identifies it as a requirement. Statements about sharing assets,
retaining provenance, or separating concerns are integration practices recommended to preserve WASP’s
architectural benefits rather than conditions imposed by every API.
An application may integrate WASP by embedding C++ interpreters and services, supplying schemas and
templates as application assets, using WaspPy, invoking command-line processes, providing Language
Services, or exchanging serializable Objects. These approaches differ in deployment but share the same
processing model.
A typical integration begins when a developer configures an interpreter and supplies the document and
any application assets required by the workflow. WASP constructs the common parse tree, applies the
requested services, and returns nodes, Objects, generated text, diagnostics, or protocol results. Application
code consumes those results and controls domain behavior, execution policy, and presentation to the user.
Generation, editor assistance, plotting, and external workflow coordination are selected only when the
application requires them.

  Figure 22. Applications integrate WASP through library, asset, process, Python, Language Services, and
 serializable Object boundaries.

 67

12.1 EMBEDDED LIBRARY INTEGRATION

Applications that require direct control over storage lifetime, streams, diagnostics, and data conversion
can integrate WASP as an embedded C++ library. The developer constructs and configures a language-
specific interpreter, supplies its input stream, and selects any subsequent HIVE, SIREN, Object-
conversion, or HALITE operations. The interpreter recognizes the configured syntax, stores the parse
tree, exposes its root through NodeView, and reports syntax diagnostics. The selected services then
operate on the tree or on explicitly supplied Object data..
The ownership relationship is an API requirement: an interpreter owns its parse tree storage and must
remain alive while any NodeView referring to that storage is used. Choosing when to retain a source-
aware view and when to construct an Object is an integration decision. Retaining the view preserves
lexical form and provenance; constructing an Object provides typed, value-oriented data but does not by
itself preserve the complete source representation.

12.2 SCHEMAS AND TEMPLATES AS APPLICATION ASSETS

Schemas, SIREN expressions, and templates are executable architectural assets normally authored and
maintained by application developers or domain specialists. The integration supplies a schema to HIVE,
embeds or submits SIREN expressions where relationships or retrieval are required, and supplies
templates and Object data to HALITE. HIVE evaluates the declared semantics, SIREN returns selected
nodes, and HALITE produces text; WASP does not infer the application's rules or presentation policy.
WASP APIs do not require these assets to be stored or versioned together. Doing so is recommended
because Language Services and command-line validation can then consume the same schema, while
HALITE utilities and embedded generation can consume the same templates. Reusing the assets avoids
duplicating constraints in editor configuration or conversion code. Application code remains responsible
for domain checks and policies that are not expressed by the configured WASP services.

12.3 INPUT LANGUAGE INTEGRATION

The developer selects an input language according to the application’s users, existing formats, and
interoperability needs. SON, JSON, or TOML may suit explicit configuration and interchange. HIT
supports hierarchical application input in the MOOSE ecosystem. DDI and EDDI support concise,
schema-informed scientific formats. The MCNP interpreter preserves an established domain-specific
format while exposing its supported constructs through the common representation.
Definition-driven interpretation requires the integration to supply the schema information used to resolve
structure; this is part of configuring those interpreters, not an optional validation recommendation. By
contrast, insulating source-oriented downstream code from a selected syntax is recommended
architectural practice. This permits an application to support more than one input language or migrate its
user-facing format without replacing semantic validation and integration logic.

12.4 PYTHON APPLICATION INTEGRATION

WaspPy is appropriate when domain orchestration and data processing occur in Python. The developer
selects and configures an exposed interpreter and chooses either source-aware WaspNode traversal or
application-authored InputObject definitions and deserialization. WaspPy invokes the underlying
WASP interpretation and conversion behavior; the application owns its Python domain classes and
decides how converted values enter its workflow. Python-created diagnostics can retain the source
connection established by the interpreter when the application associates them with represented nodes.

 68

The Python boundary also exposes Language Services server and connection implementations. The
developer supplies the application-specific configuration and extensions, while WASP provides the
interpretation services and common protocol structures. Using Python for that orchestration is a
deployment choice rather than a requirement of the Language Services architecture.

12.5 PROCESS INTEGRATION

The command-line utilities described in Section 11 provide a process boundary for scripts, build systems,
regression tests, tools written in other languages, and focused external workflows. The invoking process
selects a utility, supplies its input files and options, captures standard output and diagnostics, and
interprets the exit status. The utility performs the requested interpretation, selection, validation,
conversion, or generation operation. Dakota parameter files, for example, can drive template substitution
whose output becomes input to another scientific code. A reproducible integration preserves its input data,
templates, schema versions, diagnostics, and process status.

12.6 LANGUAGE SERVICES INTEGRATION

For Language Services integration, the developer configures an application-specific WASP language
server with an interpreter, schema, templates, and optional custom operations. Editors connect through
LSP without embedding application semantics. The server can provide diagnostics, symbols, completion,
hover, and definitions from the same assets used by batch workflows.
Custom extensions permit domain operations not defined by the standard protocol. Such extensions
should return structured, serializable data and reuse application services rather than establishing a parallel
document model. Workspace file watching can be enabled when changes outside the active document
affect interpretation or semantics.

12.7 SERIALIZABLE VISUALIZATION

The Plot package allows an application to describe a two-dimensional visualization without binding the
application or Language Services server to a rendering library. Its CustomPlot data model can be
converted to and from the Core Framework DataObject representation, so plot content can be serialized
and transferred through the same value-oriented interfaces used elsewhere in WASP. The receiving client
remains responsible for rendering.
A plot contains a title, legend, as many as four axes (x1, x2, y1, and y2), and a collection of data series.
Axis metadata identifies labels, visible ranges, linear or logarithmic scaling, numeric or date-time labels,
tick presentation, and main-grid and subgrid styling. Title and legend metadata control their text or
visibility and associated fonts and colors. Pens, brushes, fonts, and RGBA colors provide reusable
presentation descriptions without introducing a direct dependency on a specific rendering library.

Each series also carries a name, key- and value-axis assignments, and normal and selected presentation
styles. This common series information permits one plot to combine different visual forms and permits an
interactive client to distinguish selected data without altering the underlying values. The serialized
DataObject records the plot title, legend, four axes, series collection, principal styling, and graph

As a custom Language Services extension, this model allows an application to return derived
visualization data through an existing connection while preserving standard document diagnostics and
lifecycle behavior. Representing the plot as data also permits different clients to choose their own
rendering backends.

12.8 SPECIALIZED SCIENTIFIC WORKFLOWS

Specialized integrations illustrate how domain components participate in the broader architecture. The
Dakota package interprets the tool’s standard parameters format for substitution and coupled analyses [9].
The MCNP interpreter described in Section 5 supplies a formal interpretation boundary, and its model
layer and utilities consume the resulting hierarchy for geometry-, material-, and selection-oriented
workflows. HIT supports direct integration with MOOSE-oriented input workflows.
These adapters do not redefine HIVE, SIREN, HALITE, or the Core Framework. They provide an
interpretation or process boundary and then reuse shared services where appropriate. Their supported
syntax and version constraints must be stated independently from the general WASP architecture.

12.9 REPRESENTATIVE EXAMPLES

12.9.1 External Parameter Study

Purpose. Connect an external parameter source to generated application input.
Example. A study driver supplies a Dakota parameters file. WASP interprets the parameters and applies
them to reusable HALITE templates, producing an input document for a scientific application. The
application validates the generated document with its normal schema before execution.
Discussion. Parameter interpretation, presentation, and semantic validation remain separate steps. The
same templates and schema can be tested independently with command-line utilities.

12.9.2 Interactive Plot Extension

Purpose. Return application-derived visualization data through a Language Services connection.
Example. A custom server request identifies selected model data, constructs a CustomPlot with axes and
one or more series, serializes it as an Object, and returns it to a client that renders the plot.
Discussion. The server controls the data and plot description without depending on one graphical toolkit.
The client controls rendering, and standard document diagnostics and navigation remain available through
the same connection.

12.10 RELATIONSHIP TO THE FRAMEWORK

Framework integration assembles the layers described throughout this memorandum. Interpreters and the
Core Framework construct representations; HIVE supplies semantics; SIREN supplies navigation; the
Expression Engine supplies computation; HALITE supplies presentation; and library, Python, command-
line, and Language Services boundaries deliver those capabilities to applications.
The common representation is the stable center of these combinations. An effective integration selects
only the boundaries it needs while preserving shared schemas, templates, relationships, Objects, and
provenance.

12.11 SUMMARY

WASP integrates through embedded libraries, versioned schemas and templates, Python interfaces,
command-line processes, Language Services, serializable Plot Objects, and specialized scientific adapters.
These boundaries allow applications to choose deployment and user interfaces without duplicating
document-processing architecture.
