  NSLS-II Technical Note CSS-to-Phoebus Conversion

  Abstract
  This technical note documents the migration of medium- and high-complexity NSLS-II operational applications from
  Control System Studio (CSS/BOY) to Phoebus and establishes a reusable production conversion protocol. The work is
  treated as physics-controls integration rather than display-format translation. Required operator workflows and physics
  behavior are preserved; operational display-local PVs are replaced by globally visible IOC PVs; legacy Python 2
  applications are modernized for Python 3; and production actions are moved from Phoebus Execute Command or
  EmbeddedPy to IOC-managed command PVs or native EPICS logic. The completed scope includes booster ramp-
  magnet controls, booster synchrotron-light-monitor burst acquisition, and core booster BPM functions. Storage-ring
  turn-by-turn tune measurement and tune adjustment are functionally working, with final production activation pending
  a controlled IOC restart and post-restart verification of the prepared command-PV records. The protocol defined here
  provides decision rules, staged work products, validation stages, release evidence, ownership, deployment, and
  rollback requirements so that similar CSS-to-Phoebus tasks can be executed consistently.
  Keywords: CSS/BOY, Phoebus, EPICS, IOC, global PV, command PV, Python 3, conversion protocol, BR-MG, BR-SLM,
  BR-BPM, tune measurement

 Protocol outcome: The display becomes a replaceable user interface. Global PVs define the application contract, the IOC
 controls execution, and acceptance evidence demonstrates that the physics, controls, and operational behavior are correct.

1. Purpose, Scope, and Completion Definition
This work supports NSLS-II operations by migrating operational CSS/BOY applications to Phoebus without losing the
machine-relevant behavior that operators and physicists rely on. The conversion therefore includes display behavior,
physics logic, EPICS interfaces, application runtime, security, data products, deployment, and support ownership.

1.1 Purpose and objectives
• Functional migration: Reproduce the required CSS operator workflow in Phoebus, including navigation, macros, widgets,
 alarms, plots, and data entry.
• Physics verification: Validate calculations, spectra, waveform transformations, acquisition timing, file content, and
 device behavior.
• Controls integration: Represent operational parameters and commands through global IOC PVs with defined access and
 ownership.
• Application modernization: Convert required Python 2 applications to Python 3 and validate them in the approved
 IOC/service environment.
• Repeatability: Provide a protocol, evidence package, and rollback method that can be reused for future conversions.

1.3 Completion definition
 Completion criterion: A converted application is complete only when its required operator workflow, physics behavior, PV
 contract, runtime environment, access control, status/error feedback, deployment evidence, and rollback path have been
 validated.

• Unused functions: A legacy feature may be removed or deferred only after the subsystem owner confirms that it is not
 required and the decision is documented.
• Missing infrastructure: A missing production PV, incorrect write permission, or unavailable IOC service is assigned as a
 controls dependency; it is not replaced by an unprotected local substitute.
• Hardware boundary: Device firmware, timing hardware, magnet hardware, and machine-protection logic are not
 redesigned by this project.

2. Design Rules and Target Architecture
The following rules separate user-interface concerns from machine-control responsibilities. In this section, MUST
identifies a production release requirement, SHOULD identifies the preferred design unless an approved exception is
documented, and MAY identifies an optional practice.

2.1 Production design rules
• MUST - Global operational state: Machine-control parameters, modes, command selections, and results are
 represented by globally visible IOC PVs.
• MUST - IOC-managed actions: Production Phoebus displays do not use Execute Command or EmbeddedPy to perform
 machine actions or launch external scripts.
• MUST - Controlled runtime: Required Python applications run as Python 3 in an approved IOC/service environment with
 controlled paths, packages, permissions, and logs.
• MUST - Security and feedback: Commands that write waveforms, settings, files, or hardware states have defined access
 security, busy/status/error feedback, and an owner.
• MUST - Recovery: Any function that modifies a waveform or persistent configuration has a documented restore or
 rollback path.
• SHOULD - Native EPICS for simple logic: Deterministic scalar or array operations should be implemented in IOC records
 when practical and reviewable.
• MAY - Local display state: A loc:// PV may be used for temporary, non-operational UI state that does not control the
 machine and does not need facility-wide visibility.

In the target pattern, Phoebus is the operator interface and global EPICS PVs are the application contract. The IOC owns
the record definitions, access security, startup environment, and execution semantics. Validated Python 3 or native
EPICS records perform the application logic. Status, results, files, alarms, and logs remain visible through controlled

2.4 Runtime sequence
 1. The operator enters parameters in Phoebus; values are written to global parameter PVs.
 2. Phoebus writes 1 to a command PV or processes the command record.
 3. The IOC record loaded by st.cmd starts one validated application instance or executes native EPICS logic.
 4. The application performs the required EPICS I/O, calculation, acquisition, file operation, or controlled hardware
 action.
 5. Busy, status, error, timestamp, output path, and result information are returned through PVs and logs.

• File naming is timestamped and unique; an incomplete acquisition produces an explicit error rather than an accepted
 partial file.

5.1 Standard diagnostic sequence
 1. Confirm that the PV exists and identify its IOC host with cainfo.
 2. Check read and write access separately.

• Restore the archived .db and st.cmd revisions and repeat the approved IOC restart/reload procedure.

• For waveform-changing functions, restore the archived pre-change waveform and confirm the normal operating mode.
• Document the failure mode, logs, affected PVs, operational impact, corrective-action owner, and re-test criterion.

8. Conclusion and Applicability
The NSLS-II CSS-to-Phoebus effort has progressed from screen translation to physics-aware controls integration.
Booster ramp-magnet controls and BR-SLM burst acquisition are completed for the defined scope, BR-BPM core
functions are converted, and the SR tune applications work at the display and Python 3 levels with command-PV
deployment prepared. The main technical result is a durable architecture: Phoebus supplies the operator interface,
global EPICS PVs define the contract, the IOC controls execution and security, and validated Python 3 or native EPICS
records perform the logic.
 The staged protocol in Section 3 is applicable to other migrated diagnostic, save/restore, analysis, and
machine-study applications. It requires an inventory, an owner-approved functional baseline, a global PV contract,
independently validated application logic, controlled IOC integration, five-gate acceptance, and documented rollback.
Applying the same protocol prevents display-local workarounds from becoming production dependencies and makes
future conversions easier to review, support, and transfer to other maintainers.

8.1 Remaining actions at submission
• Perform the controlled IOC restart for the prepared SR tune and tune-adjustment command-PV records.
• Complete post-restart connectivity, access, single-launch, environment, output, file, and log verification.
• Update production Phoebus actions to use the command PVs exclusively and remove remaining direct Python 3
 command actions.
• Complete lower-priority online/live model pages after the required global PVs are restored or created.
• Archive validation evidence and obtain the applicable Physics, DSSI/Controls, and subsystem-owner approvals.

 Reusable rule: Similar CSS-to-Phoebus tasks should follow the same global-PV, IOC-managed execution, Python 3/native
 EPICS, validation, ownership, deployment, and rollback protocol.
