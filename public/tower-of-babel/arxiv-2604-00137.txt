Open, Reliable, and Collective: A Community-Driven Framework for Tool-Using AI Agents
Hy Dang, Quang Dao, Meng Jiang

Abstract
Tool-integrated LLMs can retrieve, compute, and take real-world actions via external tools, but reliability remains a key bottleneck. We argue that failures stem from both tool-use accuracy (how well an agent invokes a tool) and intrinsic tool accuracy (the tool’s own correctness), while most prior work emphasizes the former. We introduce OpenTools 1 1 1 Source Code/Project Implementation: https://github.com/hydang99/opentools , a community-driven toolbox that standardizes tool schemas, provides lightweight plug-and-play wrappers, and evaluates tools with automated test suites and continuous monitoring. We also release a public web demo 2 2 2 Web Demonstration Demo: https://huggingface.co/spaces/opentools/opentools where users can run predefined agents and tools and contribute test cases, enabling reliability reports to evolve as tools change. OpenTools includes the core framework, an initial tool set, evaluation pipelines, and a contribution protocol. Experiments and evaluations show improved end-to-end reproducibility and task performance; community-contributed, higher-quality task-specific tools deliver 6%–22% relative gains over an existing toolbox across multiple agent architectures on downstream tasks and benchmarks, highlighting the importance of intrinsic tool accuracy. The source code is released under the Apache 2.0 license. We also provide a system demonstration video at the following link: https://www.youtube.com/watch?v=MXVyDvXzh_o .

Introduction

Large language models (LLMs) have rapidly evolved from purely generative systems into general-purpose “agents” that can plan, reason, and interact with users over extended contexts
Grattafiori et al. 2024
. Recent agentic frameworks show that LLMs can decompose high-level goals into multi-step workflows through organized thoughts
Yao et al. 2023a
;
Li et al. 2024b
;
Zhang and Ding 2024
or self-reflection
Ji et al. 2023
;
Liu et al. 2025
, enabling tasks that go beyond simple question answering and helping mitigate issues such as hallucinations
Yao et al. 2023a
;
Li et al. 2024b
;
Zhang et al. 2024
;
Zhu et al. 2025
.

Despite progress in agentic LLMs, token-only generation remains brittle when tasks require fresh knowledge or grounded interaction with external systems
Paranjape et al. 2023
;
Qin et al. 2023
, often leading to errors and hallucinations in domain-specific settings
Huang et al. 2024
;
Kokane et al.
;
Agrawal et al. 2024
. Tool-augmented language models (TALMs) address this by letting LLMs delegate problems to external tools (e.g., retrieval
Gao et al. 2023
;
Jin et al. 2025
), calculators
Schick et al. 2023
, code interpreters
Wang et al. 2024a
, and domain APIs in chemistry/physics/medicine
Wu et al. 2025
;
Arlt et al. 2025
;
Jang et al. 2025
. This delegation improves factuality and extends agents to real-world tasks.

We argue that TALM reliability has two failure modes:
(i) tool-use accuracy
(choosing and invoking tools correctly) and
(ii) intrinsic tool accuracy
(tool correctness, stability, and robustness to drift). However, today’s tool ecosystem is fragmented: most work emphasizes tool learning
Qin et al. 2024
;
Patil et al. 2024
while largely assuming tools and documentation are reliable. In practice, tool-side failures are common such as missing coverage, API changes, nondeterminism, silent errors, and version drift, and tool access can introduce security risks
Winston and Just 2025
;
Milev et al. 2025
. This undermines reproducibility because systems may break across tool versions or environments even when agent policies are unchanged, and continuous monitoring and testing is rarely available. Moreover, there is no widely adopted open framework for community contribution of tools and stress tests, or for continuously updating reliability signals as tools evolve.

To address this gap, we introduce
OpenTools
, an open-source, community-driven toolbox for tool-integrated LLMs.
OpenTools
(i) standardizes tool schemas and lightweight wrappers for plug-and-play use across agent frameworks, (ii) provides an intrinsic tool evaluation suite that tracks correctness, robustness, and regressions via community-contributed tests, and (iii) releases a public demo interface and contribution protocol to support iterative updates of tools and reliability reports. The demo interface lowers the barrier to community feedback when local setup is impractical (e.g., dependencies, API keys), accelerating iteration on tool reliability and agent behavior. Across diverse domains, our experiments show that higher-quality, task-specific tool coverage in
OpenTools
yields
6%–22%
relative gains over an existing toolbox across multiple agent architectures.

We hope
OpenTools
enables open, reliable, continuously maintained tool ecosystems for reproducible, trustworthy research and deployment.

OpenTools
Framework

OpenTools
is an open-source, community-driven framework for building, evaluating, and deploying tools for tool-integrated language models. It operationalizes the reliability distinction introduced above by providing two workflows: (1) a Tool Accuracy/Maintenance Loop for continuous validation and regression testing, and (2) an Agentic Workflow for integrating tool collections into LLM agents to solve user tasks as depicted in Figure
1
.
OpenTools
is guided by four design goals:

Standardization

Tools should be defined with a consistent schema so they can be plugged into diverse agent frameworks with minimal adaptation.

Continuous, community-driven reliability evaluation

Tool quality should be measurable and monitored over time.
OpenTools
makes intrinsic tool accuracy first-class by supporting tests, robustness checks, and repeatable evaluation reports.

Separation of concerns between tools and agents

Tool maintenance and tool orchestration should be decoupled: tools can be improved and re-tested independently of agent policies, and agents can be swapped without rewriting tools.

Transparency and debuggability.

Tool evaluation and agent runs emit structured logs to support debugging, reproducibility, and failure analysis.

2.1
Tool Accuracy / Maintenance Loop

In tool-integrated LLM systems, tools are often assumed to be reliable. However, tool behavior can change over time due to API updates, backend changes, nondeterminism, rate limits. As a result, an agent may select the correct tool and arguments but still obtain incorrect or unstable outputs. Workflow 1 therefore treats
intrinsic tool accuracy
as a primary objective and introduces an evaluation-and-maintenance loop that continuously measures and updates tool reliability signals.

Problem Definition:

Given a tool
\tau
and a suite of test cases
\mathcal{T}
, the goal is to estimate and maintain an up-to-date reliability profile
R(\tau)
that reflects the tool’s correctness and robustness under realistic conditions.
OpenTools
treats this as an ongoing, community-driven regression testing task, where test suites evolve over time and reliability estimates are recomputed as tools or environments change.

Workflow Overview.

The tool-accuracy workflow forms a closed loop with two phases:
(i) reliability evaluation
and
(ii) community maintenance
.

2.1.1
Tool Reliability Evaluation

Tool Standardization.

To enable consistent evaluation across heterogeneous tools (e.g., calculators, retrievers, API wrappers),
OpenTools
uses a unified interface consisting of (1) a natural-language tool description, (2) a typed argument schema with
JSON-serialized parameter inputs
and (3) a structured output contract.
Different from OctoTools

Lu et al. 2025
, which relies on toolbox-specific metadata and formats,
OpenTools
adopts this common JSON-parameter convention to ensure consistent invocation across tools and agent frameworks. Tools may also expose an optional
intrinsic-accuracy
summary from prior evaluations (e.g., current-suite accuracy), enabling comparable reliability signals before usage.

Test Suites and Verification.

OpenTools
maintains a repository of test cases specifying expected tool behavior by pairing each tool with an input and an expected output (or verifiable property), optionally with tool-specific checks (e.g., pattern matching). A verification module then scores tool outputs using task-appropriate criteria (exact match, tolerance, property validation, or semantic equivalence). Test suites combine curated baselines with community contributions, expanding coverage as new failures and edge cases emerge.

2.1.2
Community-Driven Maintenance

Tool reliability is non-stationary: APIs evolve, dependencies drift, and new edge cases arise in deployment.
OpenTools
treats test suites as living artifacts maintained by the community. Users submit test cases that reproduce failures or expand coverage; accepted cases become part of the shared benchmark and run in subsequent evaluation rounds. Reliability reports are thus continuously updated, enabling tracking and monitoring.

Tool Contributions.

Beyond tests, users can contribute new tools through the shared repository. All tools follow the same standardized schema, enabling immediate evaluation against curated and community suites and providing an initial reliability snapshot upon release.

2.2
Agentic Workflow

Whereas the Maintenance Loop focuses on intrinsic tool reliability, the agentic workflow uses
OpenTools
as a toolbox for tool-integrated LLM agents. It packages tool collections for general use across agent frameworks and provides end-to-end execution with transparent, debuggable traces.

Problem Definition.

Given a user query
q
, a toolbox
\mathcal{S}
, and an agent policy
\pi
(e.g., prompting-based planning/routing or custom control flow), the agentic workflow produces an answer
y
by executing tool calls and intermediate reasoning steps. It also outputs an execution trace
\mathcal{L}
that records tool usage and outcomes for reproducibility and failure diagnosis:
(q,\mathcal{S},\pi)\rightarrow(y,\mathcal{L}).

Workflow Overview.

The agentic workflow has two phases:
(i) Agent Setup and Tool Access
and
(ii) Interactive Task Execution
.

2.2.1
Agent Setup and Tool Access

The setup phase specifies which tools the agent can use and how they are exposed.

Toolbox Interface.

OpenTools
wraps heterogeneous tools behind a unified interface (descriptions and schemas), enabling invocation without tool-specific glue code and integration into external agent frameworks via lightweight adapters.

Tool Subsetting and Prioritization.

Users can restrict the agent to task-relevant tools. When available and enabled, reliability signals from Workflow 1 can guide selection or routing (e.g., prefer higher-accuracy tools or avoid regressed ones).

Agent Policy Selection.

OpenTools
includes several standard agent policies (e.g., ReAct
Yao et al. 2023b
, OctoTools
Lu et al. 2025
, and MultiAgent) and supports user-defined agents via custom controllers and workflows. The policy module determines action selection, and policies are treated as plug-and-play components, decoupling
tool access
from
decision logic
.

2.2.2
Interactive Task Execution

During execution, the agent iteratively updates the task state, invokes tools, and produces the final answer. An execution manager mediates between the policy and toolbox: it validates arguments against schemas, executes tool calls, returns results as observations, and records failures (e.g., exceptions, rate limits, timeouts).
OpenTools
logs a structured trace of tool invocations, inputs/outputs, and error states, enabling reproducibility and attribution of failures to either policy errors (tool-use) or tool-side issues (intrinsic reliability), and linking behavior to Workflow 1 reliability signals. The system outputs the answer and trace for interactive inspection and offline analysis.

Web Demonstration Interface

Beyond the open-source repository,
OpenTools
provides a public
web demonstration interface

The demo exposes the two workflows described above: (1) the tool accuracy / maintenance loop and (2) the agentic workflow, through an interactive UI that requires no local setup and enables rapid testing, feedback, and contribution. Tool Accuracy Interaction.

For Workflow 1, the web interface lets users (i) browse tools and inspect tool cards (description, argument schema, usage notes), (ii) run tools on custom inputs, and (iii) view each tool’s
current intrinsic accuracy
when available (from the latest evaluation report).

Crucially, users can
turn observed failures into tests
: they contribute new test cases by specifying inputs and expected outputs (or verifiable properties) and optionally annotating mismatches. Accepted cases are added to the shared suite and executed in future evaluation rounds, expanding coverage and enabling continuous monitoring.

Agentic Workflow Interaction.

For Workflow 2, the demo provides an end-to-end sandbox where users can input a task query, optionally restrict the tool subset, and run a
predefined
agent configuration (e.g., ReAct
Yao et al. 2023b
, OctoTools
Lu et al. 2025
). The interface returns both the final response and a structured execution trace, including the sequence of tool calls, tool arguments, intermediate observations, and errors if any. Users can provide feedback on both tool-level outputs and the overall agent response, facilitating diagnosis of whether failures arise from tool-use decisions or from intrinsic tool issues.

Community Feedback and Transparency.

The web interface is designed to make reliability signals actionable: it surfaces current accuracy summaries, and presents execution traces to support debugging. By integrating contribution (tests and feedback), evaluation (accuracy reporting), and execution (agent runs) in a single interactive environment, the demo operationalizes our community-driven goal and streamlines the loop from observed failures to cover test cases and tool improvements.

3.1.2
Baselines

Toolboxes.

We compare two toolboxes:
(i) OctoTools-T
A toolbox from the OctoTools testbed design, including a generalist solution generator and a set of domain-specific tools (e.g., image captioning, web search, python code generation, specialized classifiers) and
(ii)
OpenTools-T
Our community-driven toolbox consisting of (i) a core set of general-purpose tools (e.g., search, calculator/code execution), (ii) collected domain tools (e.g., vision/perception, chemistry helpers), and (iii)
community-contributed tools
(e.g., maze solvers). Tools are exposed through a standardized interface and are continuously evaluated using Workflow 1. The more detailed information of the ToolBoxes are represented in Appendix
A.2

Agent Frameworks.

We evaluate our systems under multiple agent frameworks:
(i) Prompting:
the LLM answers directly without tool use. We experiment with both zero-shot and chain of thought prompting (CoT), which are step-by-step reasoning without external tools). In preliminary experiments, zero-shot performs better overall for both gpt-4o-mini and gpt-5-mini; therefore, we report zero-shot as
Prompting
in the main results and provide the full zero-shot/CoT comparison in Appendix
A.2
.
(ii) ReAct Agent
Yao et al. 2023b
:
an iterative reason-and-act agent that interleaves natural-language reasoning with tool calls.
(iii) OctoTools Agent
Lu et al. 2025
:
the planner–executor style agent as defined in the OctoTools framework.
(iv) MultiAgent Framework:
Inspired by LemonAgent
Jiang et al. 2026
, we use a hierarchical pipeline that decomposes a query and routes sub-problems to specialized sub-agents. Unlike LemonAgent, we (i) perform explicit reasoning-based decomposition before routing and (ii) use a
Verifier
/guardrail to store only validated intermediate results in shared memory. A
Planner
decomposes the query, a
Generator
issues tool calls, tools are executed and verified, validated results are written to memory, and a
Composer
generates the final answer with a brief memory-based summary.

For tool-using agents, we run each framework with (i) the OctoTools toolbox (OctoTools-T) and (ii) our
OpenTools
toolbox (OpenTools-T), enabling a controlled comparison of toolsets under the same decision logic. Following OctoTools
Lu et al. 2025
, we perform greedy tool selection for OpenTools-T to choose task-appropriate tool subsets. For OctoTools-T, we use the tool sets reported in the OctoTools paper that achieve the best performance for each task.

Related Work

Tool use and agentic LLMs.

Prior work on tool use and agentic LLMs focuses on how models plan, and invoke external tools through training or prompting, including Toolformer-style learning
Schick et al. 2023
, ReAct reasoning-and-acting
Yao et al. 2023b
, and agent controllers that add reflection/search and multi-step tool execution
Patil et al. 2024
;
Dang et al. 2025
. These lines of work primarily improve tool-use accuracy, while often assuming the underlying tools are correct and stable.

In parallel, tool libraries and evaluations (e.g., LangChain
4
4

4

https://github.com/langchain-ai/langchain
, AutoGen
5
5

5

https://github.com/microsoft/autogen
) broaden tool access and provide domain-specific suites (e.g., chemistry
Wu et al. 2025
, medical
Li et al. 2024a
, vision
Hu et al. 2024
). Existing benchmarks assess end-to-end task success and tool-calling competence
Huang et al. 2023
;
Guo et al. 2024
, but frequently conflate model mistakes with tool-side failures and seldom measure tool drift or regressions over time.
OpenTools
addresses this infrastructure gap by standardizing JSON-schema tool interfaces, providing community-maintained wrappers, and enabling intrinsic tool evaluation with reliability signals and regression tracking—supporting plug-and-play use across agent frameworks while separating tool-use from tool reliability.

6
Conclusion and Future Work

We introduced
OpenTools
, a community-driven toolbox and evaluation framework for tool-integrated LLM agents that explicitly separates
tool-use accuracy
from
intrinsic tool accuracy
.
OpenTools
standardizes tool interfaces and wrappers for plug-and-play use across agent frameworks, and provides an evaluation suite that tracks tool correctness, robustness, and regressions over time. Our experiments show that improving tool quality and task coverage yields consistent downstream gains across multiple agent policies, with the largest benefits on tool-intensive end-goal tasks.

Future work.

We plan to expand
OpenTools
in three directions: (1) broaden tool coverage by curating additional tools and supporting community contributions, with emphasis on specialized domains (e.g., science, medicine, engineering); (2) strengthen intrinsic reliability benchmarking via more stress tests and real-world failure cases, improved regression tracking, and continuous evaluation as APIs evolve; and (3) keep pace with advancing agent frameworks by adding pre-defined agent policies and reference implementations so the same tool ecosystem can be evaluated and deployed under emerging architectures.

Toolboxes Statistics and Definitions

OpenTools
groups tools into three categories:
Program-based
tools perform deterministic local computation with explicit inputs and reproducible outputs;
API-based
tools wrap external services accessed via HTTP APIs, typically returning up-to-date, domain-specific information; and
Prompting-based
tools implement LLM-mediated functions via fixed prompt templates that enforce specific behaviors. We report toolbox statistics in Table
