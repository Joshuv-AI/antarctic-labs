 EVALUATION OF LLM-GENERATED KOKKOS CODE USING
 COMPILE-TIME AND RUN-TIME TESTING
 EMIL JERMANN∗ , NATHAN ELLINGWOOD† , AND CHRISTOPHER M. SIEFERT‡

 Abstract.
 Due to the growing use of large language models (LLMs) by developers and researchers, it has become
essential to reliably evaluate their ability to generate code that uses specialized libraries. We explore the
use of compile-time and run-time evaluation of LLM-generated Kokkos code through extending the methods
used by OpenAI with the HumanEval dataset. Our evaluation framework is based on the first 40 prompts
from the Kokkos138 dataset. We start by discussing two different forms of LLM prompting, using entirely
plain English or providing pseudocode for added context. These two methods are used to generate Kokkos
code with the Llama-3.1-8B-Instruct and CodeQwen1.5-7B-Chat models. We found that both forms of
prompting led to high failure rates and difficulties with reliably parsing LLM-generated code, while prompts
with pseudocode for context generally led to improved results on more complicated tests.

2 Introduction and Motivation

This paper explains an approach to extending the compilation and run-time testing frame-
work used with the HumanEval dataset [?] to evaluate LLM-generated Kokkos library [?]
code in C++. OpenAI released the HumanEval dataset in 2021 to evaluate their large
language model Codex using handwritten Python prompts. For each HumanEval test, the
LLM is tasked with writing a function based on a prompt that includes accepted important
statements, a function declaration, and a docstring (e.g. Fig 2.1). Each LLM completion is
tested in a Python script with 7.7 test cases on average.

3 Methodology and Implementation

The adaptation of the HumanEval dataset testing framework to the Kokkos138 dataset
required changes to the evaluation harness (the Python script that compiles and runs the
test cases), as well as to the prompts to make testing more reliable and consistent. The
explanation of this approach is separated into different subsections. In section 2.1 we explain
the file structure used during development and deployment. In section 2.2 we explain the
first method of LLM prompting using plain English (defined as descriptive prompting). In
section 2.3 we explain the second method of LLM prompting using code for context (defined
as contextual prompting). In section 2.4 we explain our use of system prompts and how
they were used during development and deployment. Lastly, in section 2.5, we explain the
use of compile-time and run-time tests on LLM-generated code.
 3.1 Evaluation Suite The evaluation suite is divided into a set of files to make
development more intuitive, prompt an LLM, and evaluate an LLM’s responses. To make
writing test cases more efficient, each prompt and test case was written in a .cpp file that
was formatted with comment-separated sections for the test header, body, and footer. An
example of this can be seen below in Fig 3.1. The header (labeled in blue) and the footer
(labeled in red) contain include statements, test functions, and any necessary additional
setup or wrapping for the inserted LLM response. The body (labeled in green) contains
either the developer-provided completion (used when developing the test case) or the LLM’s
response (when testing the LLM’s response). All imports or functions shared across test
cases were included in a generic header file, which was parsed and added to the beginning
of each test case’s individual header during testing.

 3.2 Descriptive Prompting The list of Kokkos138 prompt-response pairs were
written by Kokkos experts. The prompts for each test were general and open-ended, in-
tended to resemble an actual prompt written by a Kokkos user in order to get help from an
LLM. However, this approach proved to be ineffective for compilation and run-time testing.
ChatGPT 4o and Llama-3.2-70B-Instruct regularly provided wordy or multiple answers,
with extra unnecessary code that made response parsing and testing difficult and inaccu-
rate. An example can be seen in Fig 6.1 in the appendix. In order for the tested LLM to
output a result that could be tested in a reproducible way, almost all prompts had to be
edited to be very specific in what they were asking for and clearly describe the expected
format of the result.

 Figure 3.2: Kokkos/21 Descriptive Prompt

 Initial Prompt: Show me how to increment each element of a Kokkos 1D view of 10
 elements using the default execution space.

 Descriptive Prompt: Write a code snippet that increments each element of a Kokkos 1D
 view of 10 elements named ’b’ using the default execution space. b is already declared and
 initialized. Do not surround your answer in a function.

 For example, unlike the initial prompt for Kokkos Test 21 (shown in Fig 3.2), the
edited prompt, labeled as “Descriptive Prompt,” specifies the name of the Kokkos View to
edit, and aims to be more specific in how it wants the code to be outputted (as a stand-
alone code snippet, not surrounded by a function). This allows for a Kokkos View ’b’ to
be initialized, and later tested to see if these values have been correctly incremented. The
prompts discussed here, that describe the test requirements in plain English, will be referred

to as descriptive prompts.
 3.3 Contextual Prompting While descriptive prompting is closer to what is used
by most LLM users, adding code for the LLM to use as context when responding allows for
a more explicit prompt. As described previously, HumanEval prompts include code context
rather than exclusively relying on plain English. To test the effectiveness of including code
alongside a plain English description, the descriptive prompts were edited to include example
pseudocode that contained:
 • Header and include statements necessary to answer the prompt
 • Function, class, or struct wrappers (if applicable)
 • An example of setup implementation (if applicable)
 • An example of testing or use implementation (if applicable)
 • A clearly commented section for the LLM to input its code.
Prompts with a plain english problem statement, followed by code in this format, will be
referred to as contextual prompts. This method was used to help the LLM gain clearer
context as to the formatting of its answer in order to lower the chance of a failed test due
to incorrectly parsing the answer from the LLM’s response, or unspecific prompt descrip-
tions. The contextual prompt for Kokkos Test 21 (shown in Fig 3.3) illustrates how this is
implemented in practice. Pseudo functions, types, and variables are used as placeholders
for code with descriptive names.

 Figure 3.3: Kokkos/21 Contextual Prompt

 Descriptive Prompt: Write a code snippet that increments each element of a Kokkos 1D
 view of 10 elements named ’b’ using the default execution space. b is already declared and
 initialized. Do not surround your answer in a function.

 Context Prompt: Write a code snippet that increments each element of a Kokkos 1D
 View of 10 elements named ’b’ using the default execution space. Example code:

 }

 }

 3.4 System Prompts During initial testing, LLMs often generated responses that
were difficult to evaluate, for example, by adding unnecessary text and giving multiple an-
swers. To further control the LLM-generated output, different system prompts [Fig 3.4]
were used for descriptive prompts and contextual prompts. During development and de-
ployment, these were added as a prefix to the current Kokkos prompt before being input to
the LLM. The system prompts established a role for the LLM, as well as any restrictions
on the expected output. In practice, this helped lead to more reproducible LLM responses
and made testing more reliable.

 Figure 3.4: System Prompts
 Descriptive Prompt: You are being tested on your ability to write correct Kokkos library
 code in C++ using best practices. When answering the prompt, give your single best answer
 without adding any code that was not explicitly asked for. For example, do not add include
 statements, do not surround you code in a main function body, do not provide an example
 of how to use your code, and do not wrap your response in a function unless explicitly asked
 to. Respond to this prompt with only your code answer and no extra text:

 Contextual Prompt: You are being tested on your ability to write correct Kokkos library
 code in C++ using best practices. Answer the prompt by modifying the provided code.
 Write your response between the two comments ”// YOUR CODE STARTS HERE //”
 and ”// YOUR CODE ENDS HERE //”. Do not delete these comments and do not add
 any text or code before or after these comments. Your response should only include the
 example code with your answer inside the specified comments and nothing extra

 3.5 Testing Each LLM responses was inserted into its respective test script and
compiled. If compiled successfully, each test script was run to ensure the LLM response
satisfied a number of test cases. During initial testing, it was rare to see code compile and not
run correctly. This suggests that an incorrect response was generally due to hallucination
on topics it had not been trained on, rather than incomplete understanding of a certain
topic. There were, however, a few examples of repeated misapplication of a Kokkos library
function, the clearest example of this being Kokkos Prompt 6, shown in Fig 3.5.

 Figure 3.5: KOKKOS/6 Test

 Descriptive Prompt: Write a code snippet that copies the contents of a Kokkos::View
 called ”src” into a Kokkos::View called ”dest” without fencing. Do not surround your
 answer with a function.

 Completion: Kokkos::deep copy(Kokkos::DefaultExecutionSpace(), dest, src);

 The Kokkos documentation states that when calling Kokkos::deep copy(), if a third ex-
ecution space argument is provided, the function call will return without fencing. ChatGPT
4o and Llama-3.2-70B-Instruct regularly either returned a two argument Kokkos::deep copy()
without an ExecutionSpace argument, or assumed a 1 dimensional Kokkos::View and used a
Kokkos::parallel for() to copy without fencing. Both of these examples show failures by these
models to understand more nuanced uses of Kokkos::deep copy(), and therefore highlights
the importance of run-time tests on top of compiling the test script.
4 Results

The first 40 Kokkos prompts (Kokkos/0–Kokkos/39) were tested on Llama-3.1-8B-Instruct
and CodeQwen1.5-7B-Chat using the adapted evaluation suite. The LLM-generated re-
sponses from the original Kokkos prompts consistently outputted extra code, used unex-
pected variable names, and outputted unexpected code formatting, all of which caused
them to fail testing. For this reason, we only show the results from the descriptive and
contextual prompts. The descriptive prompts were parsed using a Python script that at-
tempted to remove all text outside of code markdown, strip header code, and join multiple
code markdown sections, if present. The contextual prompts were parsed using a Python
script that looked for code between the two comments denoting where the LLM was to put
its response, defaulting to the same script as the descriptive prompts if the comments were

not found. Then, all responses were run through the evaluation harness.
 In order to get a better understanding of where the evaluation suite could be improved,
all test responses were then manually categorized into 4 different groups, shown in Fig 4.1.

 All test results were also manually reviewed to identify parsing errors, the summary of
which is presented in Table 4.2. Parsing errors are defined as instances where the LLM-
generated responses presented code in an unexpected format, and in the case of contextual
prompts, incorporated code that was outside the comments indicating the scope of the
intended response. For example, this included a case where the LLM provided an entire
functor when only asked for an overloaded function operator. While there were few in-
stances of parsing errors incorrectly failing a test (7 instances out of all 160 LLM-generated
responses) these errors must be considered to ensure reliable and reproducible results moving
forward.
 There were far fewer parsing failures when prompting both models with descriptive
prompts, rather than contextual prompts. In the case of contextual prompting, there were
several issues of note. The LLMs frequently incorporated elements from the contextual
prompt, such as pseudocode functions or variables defined within the prompt but absent
from the problem statement. For instance, pseudocode dimension variables were often refer-
enced. Additionally, for prompts requiring templating based on specific parameters, such as
for prompt Kokkos/38 which templates ”on the input Kokkos Views type, the resulting dot
product Kokkos View type, and the Kokkos execution space, in that order”, both the Cod-
eQwen and Llama models consistently generated separate template types for each Kokkos
View, rather than a single type as expected. This persisted even when contextual prompts
demonstrated implementations using a single Kokkos View template type. There were also

multiple LLM-generated responses that incorrectly returned the main function body from
the contextual prompt it was responding to, along with its answer to the prompt.
 Despite these challenges, the CodeQwen model performed comparatively better in gen-
erating compilable code for complex test cases. Specifically, when prompted with contextual
prompts, CodeQwen successfully produced three compilable code responses for the final five
and most complex test cases, compared with zero for the Llama model with descriptive and
contextual prompting, and the CodeQwen model with descriptive prompting. This suggests
that contextual prompts might help some models perform better on complex programming
tasks.

5 Discussion

The use of pseudocode examples in the contextual prompts confounded the LLM-generated
responses in multiple instances. In fact, the descriptive prompts generally led to more
consistent and easily parsed results. However, they also led to responses that were more
likely to fail to compile, and perhaps more importantly, fail to match the expected format for
testing. When writing test cases for C++ code, it is extremely important to have a prompt
that restricts the LLM-generated format to be easily tested for its Kokkos knowledge, while
not being incorrectly failed for responding in an unexpected format. As prompts became
more complex, both descriptive and contextual prompts increasingly produced code that was
difficult to test. This was particularly evident in prompts Kokkos/35 through Kokkos/39,
where each prompt built upon the code from the previous one. By the final prompts, it was
necessary to provide the implementation for a function and a struct to ensure the LLM had
enough context to understand how to use them correctly and generate compilable code.
 Due to the specificity required to test the first 40 prompt-completion pairs from the
Kokkos/138 dataset, passing LLM responses were often limited to very few approaches. This

suggests that n-gram and syntax tree tests might be more sufficient and reliable methods of
testing accuracy of LLM results. In order to continue compile-time and run-time testing with
the Kokkos/138 dataset, it would likely be necessary to separate prompts by their response
format (i.e. struct, function, variable declaration) and design a separate prompting method
for each.
