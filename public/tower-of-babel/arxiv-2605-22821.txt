Tokenisation via Convex Relaxations
Jan Tempus, Philip Whittington, Craig W. Schmidt, Dennis Komm, Tiago Pimentel

Abstract
Tokenisation is an integral part of the current NLP pipeline. Current tokenisation algorithms such as BPE and Unigram are greedy algorithms—they make locally optimal decisions without considering the resulting vocabulary as a whole. We instead formulate tokeniser construction as a linear program and solve it using convex optimisation tools, yielding a new algorithm we call ConvexTok . We find ConvexTok consistently improves intrinsic tokenisation metrics and the bits-per-byte ( BpB ) achieved by language models; it also improves downstream task performance, but less consistently. Furthermore, ConvexTok allows the user to certify how far their tokeniser is from optimal (at a certain objective) via a lower bound, and we empirically found it to be within 1% of optimal at common vocabulary sizes. code in this link tokenisers in this link

Introduction

Tokenisation is an integral part of every language modelling pipeline, taking sequences of
bytes
as input, and converting them into sequences of
tokens
, which serve as input to a language model (LM).
Notably, while it is generally an open research question what makes a good tokeniser
(
14
;
7
;
1
;
33
)
, a number of recent works show that a tokeniser’s compression correlates (at least to some extent) with its downstream performance in LLMs
(
12
;
42
)
.
Given these results, we might expect researchers to test how LMs would perform given a compression-optimal tokeniser.
Unfortunately, finding such optimal tokenisers is
\mathsf{NP}
-hard
(
21
;
39
;
25
;
19
)
.
Hence, in practice approximate optimisation methods are employed.

Currently, the de-facto standard tokenisation algorithm is byte-pair encoding
(
11
;
34
,
BPE
;)
, which originated as a compression algorithm.
It is a simple greedy algorithm that iteratively merges the most frequent pair of tokens in a dataset into a new token until a desired vocabulary size is reached.

BPE
’s use of greedily chosen pair-wise token-merging means that unnecessary intermediate tokens are created and compressive ability is lost.
Many approaches have been proposed as possible fixes to this problem
(
6
;
5
;
24
;
26
;
32
)
, but they all rely on relatively minor modifications or extensions to
BPE
, and do not consider optimising tokenisation beyond greedy solutions.

The core technical contribution of this paper is showing how to solve tokenisation using
polyhedral techniques
.

Polyhedral techniques are a branch of mathematics which translates combinatorial problems into studying the geometry of objects called polyhedra, or polytopes when the set is bounded. Polytopes are simply higher-dimensional version of polygons.

We first identify an integer program (IP) which is equivalent to the optimisation problem solved by tokenisation algorithms.
Second, we relax this problem into a linear program (LP),
2
2

2

Integer programming optimises problems over discrete sets, while linear programming optimises problems over continuous sets. If an integer program requires a variable
x\in\{0,1\}
, we can relax it into a linear program to allow
x\in[0,1]
.
for which we can efficiently compute exact (or near-exact) solutions using a common solver.
Such an LP solution, however, includes ‘partial’ tokens, which need to be discretised before we can convert it into a functional tokeniser.
To this end, we propose three simple rounding schemes.
After rounding, constructing a tokeniser from this solution is trivial.
Additionally, solving the LP provides a lower bound on the compression achieved by any tokeniser on the used dataset.
Our method thus allows us to compute tight bounds on how close-to-optimal any tokeniser is.

Empirically, we evaluate our proposed tokeniser’s performance in five parts, using
BPE
as a baseline.
First, we natively analyse the behaviour of our constructed LP and the effect of different rounding techniques on its solutions’ quality.
We see that even though the problem is
\mathsf{NP}
-hard, the LP’s solution is not far from integral (especially at larger vocabulary sizes).
Second, we use our LP’s solution to certify how close the various tokenisers are to being optimal compressors.
We see that already at common vocabulary sizes the various tokenisers we consider are within
1\%
of optimal.
Third, we study how stable tokenisers are to a specific choice of training dataset, finding that
BPE
is consistently more stable than
ConvexTok
.
Fourth, we evaluate our tokenisers using common intrinsic metrics, including compression rate, vocabulary utilisation, and Rényi entropy.
For these metrics, one of our rounding schemes (
Bias
) consistently outperforms all other tokenisers.
Finally, we evaluate the effect of our tokenisers on downstream language modelling performance.
In these experiments, a deterministic rounding scheme (
Det
) consistently performed best on bits-per-byte (
BpB
), and often (although not always) outperformed
BPE
on downstream (
CORE
) tasks
(
23
)
.

\cup_{i=1}^{\infty}{\color[rgb]{0.3281,0.4961,0.9375}\Sigma}^{i}

.
Second, let a dataset be a multi-set of byte-strings, denoted by
{\color[rgb]{0,0,0}\mathcal{D}}=\{{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}^{(n)}\}^{N}_{n=1}

A tokeniser’s job is to

{\color[rgb]{0.3281,0.4961,0.9375}\Sigma}\subseteq{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}

In practice, we then often fix the size of the vocabulary given a
budget

K

|{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}|=|{\color[rgb]{0.3281,0.4961,0.9375}\Sigma}|+K

Finally, we term
{\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}}\in{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}^{*}

Formally, we can now define a tokeniser as the 3-tuple
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}\langle{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}},{\color[rgb]{0.9961,0.3789,0}\mathtt{tok}},{\color[rgb]{0.9961,0.3789,0}\mathtt{detok}}\rangle

As we say an encoding function

{\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}}={\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}({\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}})

Further, the decoding function simply undoes the encoding mapping, being thus defined as
{\color[rgb]{0.9961,0.3789,0}\mathtt{detok}}({\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}})\smash{\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}}{\color[rgb]{0.8633,0.1484,0.4961}t}_{1}\circ{\color[rgb]{0.8633,0.1484,0.4961}t}_{2}\circ\cdots\circ{\color[rgb]{0.8633,0.1484,0.4961}t}_{|{\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}}|}

Notably, for a fixed vocabulary, many different encoding functions may successfully segment a byte-string;

{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}=\{{\color[rgb]{0.8633,0.1484,0.4961}d},{\color[rgb]{0.8633,0.1484,0.4961}o},{\color[rgb]{0.8633,0.1484,0.4961}g},{\color[rgb]{0.8633,0.1484,0.4961}do},{\color[rgb]{0.8633,0.1484,0.4961}og}\}

{\color[rgb]{0.3281,0.4961,0.9375}dog}

{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}

2.1
What Do We Want from Our Tokeniser?

Given the description above, we are left with a question: how should we select a tokeniser?
If
{\color[rgb]{0.9961,0.3789,0}f}
is an objective function, which, given a tokeniser, returns a score associated with it, we would ideally choose a tokeniser by computing a solution to the optimisation problem:
\argmin_{{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}}{\color[rgb]{0.9961,0.3789,0}f}({\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}})
.
Unfortunately, there are two issues with this approach: (i) it is not obvious which objective function to use, and (ii) given an objective, we don’t know how to solve this optimisation problem efficiently.

Several objective functions have been proposed in response to (i), including compression
(
12
)
, unigram log-likelihood
(
22
)
, or Rényi efficiency
(
42
)
.
While we believe that more research should go into what optimisation function to use, we will focus on compression here, following a battery of prior work either proposing new tokenisers
(
6
;
5
;
24
)
or theoretically analysing them
(
43
)
.
Given a dataset (
{\color[rgb]{0,0,0}\mathcal{D}}
), we write our
compression objective function
as

\displaystyle{\color[rgb]{0.9961,0.3789,0}f}({\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}})=\sum_{{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}\in{\color[rgb]{0,0,0}\mathcal{D}}}{\color[rgb]{0.9961,0.3789,0}\mathtt{length}}\big({\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}({\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}})\big)\;,

(1)

where we note that the encoding function (
{\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}
) implicitly depends on the tokeniser’s vocabulary (
{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}
).

Even with an objective in hand, challenge (ii) remains: finding a tokeniser that optimises it, and doing so efficiently.
Unfortunately, as mentioned above, this optimisation problem is
\mathsf{NP}
-hard, meaning that we cannot solve it efficiently, unless
\mathsf{P}=\mathsf{NP}
.
We thus focus on approximation algorithms instead.
The most popular such method is
byte-pair encoding
(BPE), a greedy algorithm used in virtually all modern LLMs
(
30
;
37
;
3
;
36
)
.
Notably,
BPE
is a greedy algorithm which iteratively chooses locally-optimal tokens to be merged one at a time; in general, however, these tokens may not be optimal globally, which may lead to the choice of a suboptimal vocabulary.
(See
Appendix

A
for a more formal description of

As a small example, consider the dataset
{\color[rgb]{0,0,0}\mathcal{D}}=\{{\color[rgb]{0.3281,0.4961,0.9375}abc},{\color[rgb]{0.3281,0.4961,0.9375}abd},{\color[rgb]{0.3281,0.4961,0.9375}abe},{\color[rgb]{0.3281,0.4961,0.9375}bc},{\color[rgb]{0.3281,0.4961,0.9375}bd},{\color[rgb]{0.3281,0.4961,0.9375}be}\}
and

.

BPE
would first choose to merge
{\color[rgb]{0.8633,0.1484,0.4961}\langle a\rangle}
and
{\color[rgb]{0.8633,0.1484,0.4961}\langle b\rangle}
into a new token
{\color[rgb]{0.8633,0.1484,0.4961}\langle ab\rangle}
for a saving of 3 symbols, and any further merge can save only 1 symbol, so with two more arbitrary merges,

manages to save 5.
It would however be optimal to choose the new tokens
{\color[rgb]{0.8633,0.1484,0.4961}\langle bc\rangle},{\color[rgb]{0.8633,0.1484,0.4961}\langle bd\rangle},{\color[rgb]{0.8633,0.1484,0.4961}\langle be\rangle}

Tokenisation via Convex Relaxations

Our paper’s main contribution is an LP-based tokenisation algorithm which directly
approximates
a globally-optimal tokeniser; thus, avoiding locally-optimal solutions.
As our tokeniser relies on a convex relation, we term it
ConvexTok
.
Before we get to our LP, however, we first express the problem as a shortest path problem in a directed acyclic graph, which will make the LP more intuitive.
More specifically, given a dataset (
{\color[rgb]{0,0,0}\mathcal{D}}
), we construct a graph problem whose solutions can be easily translated into tokenisers, and then use this graph problem to build the LP.

We first define the graph.
For each byte-string in our dataset, we introduce a vertex for every position in between two bytes in the string; we also introduce a vertex for the position before the first and after the last byte in the string.
A string of length
n
thus contributes
n+1
vertices, with the first and last vertices designated as its start and end vertices, respectively.
We then merge the last vertex of each byte-string with the the first vertex of the next, essentially making them a single vertex.
Next, we connect each adjacent vertex within a byte-string with what we call a
byte-edge
.
Finally, we connect each non-adjacent vertex within byte-strings with a
token-edge
;
this is denoted formally as:

Given a graph-vocabulary and graph-segmentation, we can thus construct an equivalent tokeniser

.

\langle{\color[rgb]{0,0.88,0}\mathcal{V}},{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{all}},{\color[rgb]{0,0.88,0}\mathcal{C}}\rangle

({\color[rgb]{0,0.88,0}\mathcal{V}},{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{all}})
with shortest path from

to
{\color[rgb]{0,0.88,0}v}^{N}_{L}
using a graph-vocabulary of at most

colours.

3.1
Generalising the Tokenisation Problem

The construction above creates a tokenisation graph that is equivalent to a typical tokenisation problem.
We now mildly generalise this construction to allow for more flexibility in the tokeniser’s optimisation.
Starting from the set of vertices
{\color[rgb]{0,0.88,0}\mathcal{V}}
and edges
{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{all}}
as constructed above (in
Eq.

2
), we select any subset of
{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{all}}
to form a set of
free edges

{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}\subseteq{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{all}}
.
These edges represent tokens which must always be included in a tokeniser’s vocabulary, and which are thus available for “free”; in the standard definition above, these would consist of the byte-edges
{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{byte}}
.
6
6

6

When we say “free” here, this is in terms of not occupying a part of the allowed budget
K
. These edges are still costly in terms of increasing a path’s length in a graph-segmentation.

We then define a set of
priced edges
as
{\color[rgb]{0,0.88,0}\mathcal{P}}\subseteq{\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{all}}\setminus{\color[rgb]{0,0.88,0}\mathcal{F}}
; these edges represent the tokens which can be added to the vocabulary—and are thus “priced”—typically containing the entire set of token-edges.
Whenever
{\color[rgb]{0,0.88,0}\mathcal{P}}={\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{tok}}
, we have a graph with edges between all possible byte-sequences in the dataset as before.
However, it could be reasonable to consider in
{\color[rgb]{0,0.88,0}\mathcal{P}}
only edges that do not cross unicode,
grapheme or morpheme boundaries (analogously to
BoundlessBPE
;
32
), or that represent tokens with non-negligible frequencies.
7
7

7

Our method can in fact be used to solve tokenisation with any set of candidate tokens, as defined by
25
.

We then denote this (sub)set of “interesting” edges by
{\color[rgb]{0,0.88,0}\mathcal{E}}\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}\cup{\color[rgb]{0,0.88,0}\mathcal{P}}
.

Definition 3.3
.

We define a
generalised tokenisation graph
as a 4-tuple
\langle{\color[rgb]{0,0.88,0}\mathcal{V}},{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}},{\color[rgb]{0,0.88,0}\mathcal{P}},{\color[rgb]{0,0.88,0}\mathcal{C}}\rangle
, where

({\color[rgb]{0,0.88,0}\mathcal{V}},{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}\cup{\color[rgb]{0,0.88,0}\mathcal{P}})
represents a directed acyclic graph with free and priced edges, and

{\color[rgb]{0,0.88,0}\mathcal{C}}
is a colour-partition of the priced edges.
As before, a
graph-vocabulary
is any subset of the colours
{\color[rgb]{0,0.88,0}\mathcal{C}}
in this graph, and a
graph-segmentation
is a path from
{\color[rgb]{0,0.88,0}v}^{0}_{0}
to
{\color[rgb]{0,0.88,0}v}^{N}_{L}
using only edges from this graph-vocabulary or free edges.

Note that the relationship discussed in the previous section (between compression and graph-segmentation length) is preserved when working with generalized tokenisation graphs.

3.2
Tokenisation as an Integer Program

The sections above build a graph problem which is, in a sense, equivalent to the problem of finding compression-optimal tokenisers.
This graph problem, however, is not necessarily easier to solve than the original problem over strings.
We now leverage it to build yet another equivalent problem using integer programming.
While the resulting IP is still
\mathsf{NP}
-hard, we will relax it into an LP which we can solve efficiently.
Later we will rely on rounding schemes to recover an approximately globally-optimal tokeniser.
Notably, relaxing the integral constraints to continuous ones is a design choice we take here.
Please see
Appendix

B
for an alternative approach.
Furthermore, we note that linear programming has a long history of use in approximating algorithms for combinatorial problems
(
40
;
38
;
35
;
31
)
.

Consider a generalised tokenisation graph
\langle{\color[rgb]{0,0.88,0}\mathcal{V}},{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}},{\color[rgb]{0,0.88,0}\mathcal{P}},{\color[rgb]{0,0.88,0}\mathcal{C}}\rangle
.
To convert it into an IP, we first define a
free incidence matrix
8
8

8

We follow the convention that when a matrix is defined as
\{0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{V}}\times{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}}
we may index it using elements of
{\color[rgb]{0,0.88,0}\mathcal{V}}
and
{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}
.

{\color[rgb]{0.75,0,0.25}\mathbf{F}}\in\{-1,0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{V}}\times{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}}
and a
priced incidence matrix

{\color[rgb]{0.75,0,0.25}\mathbf{P}}\in\{-1,0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{V}}\times{\color[rgb]{0,0.88,0}\mathcal{P}}}
to have elements
{\color[rgb]{0.75,0,0.25}\mathbf{F}}_{{\color[rgb]{0,0.88,0}v},{\color[rgb]{0,0.88,0}e}}
and
{\color[rgb]{0.75,0,0.25}\mathbf{P}}_{{\color[rgb]{0,0.88,0}v},{\color[rgb]{0,0.88,0}e}}
which encode whether an edge (
{\color[rgb]{0,0.88,0}e}\in{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}
or
{\color[rgb]{0,0.88,0}e}\in{\color[rgb]{0,0.88,0}\mathcal{P}}
, respectively) starts or ends at some vertex (
{\color[rgb]{0,0.88,0}v}\in{\color[rgb]{0,0.88,0}\mathcal{V}}
).
Second, we define an
edge-colour matrix

{\color[rgb]{0.75,0,0.25}\mathbf{C}}\in\{0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{P}}\times{\color[rgb]{0,0.88,0}\mathcal{C}}}
to have elements
{\color[rgb]{0.75,0,0.25}\mathbf{C}}_{{\color[rgb]{0,0.88,0}e},{\color[rgb]{0,0.88,0}c}}
encoding whether a priced edge
{\color[rgb]{0,0.88,0}e}\in{\color[rgb]{0,0.88,0}\mathcal{P}}
has a specific colour
{\color[rgb]{0,0.88,0}c}\in{\color[rgb]{0,0.88,0}\mathcal{C}}
.
Formally:

\displaystyle{\color[rgb]{0.75,0,0.25}\mathbf{F}}_{{\color[rgb]{0,0.88,0}v},{\color[rgb]{0,0.88,0}e}}\!\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}\!\left\{\!\!\!\!\begin{array}[]{rr}-1&\texttt{if }{\color[rgb]{0,0.88,0}e}=\langle{\color[rgb]{0,0.88,0}v},{\color[rgb]{0,0.88,0}v}^{\prime}\rangle\\
1&\texttt{elif }{\color[rgb]{0,0.88,0}e}=\langle{\color[rgb]{0,0.88,0}v}^{\prime},{\color[rgb]{0,0.88,0}v}\rangle\\
0&\texttt{else}\end{array}\right.\!\!\!\!,\,\,{\color[rgb]{0.75,0,0.25}\mathbf{P}}_{{\color[rgb]{0,0.88,0}v},{\color[rgb]{0,0.88,0}e}}\!\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}\!\left\{\!\!\!\!\begin{array}[]{rr}-1&\texttt{if }{\color[rgb]{0,0.88,0}e}=\langle{\color[rgb]{0,0.88,0}v},{\color[rgb]{0,0.88,0}v}^{\prime}\rangle\\
1&\texttt{elif }{\color[rgb]{0,0.88,0}e}=\langle{\color[rgb]{0,0.88,0}v}^{\prime},{\color[rgb]{0,0.88,0}v}\rangle\\
0&\texttt{else}\end{array}\right.\!\!\!\!,\,\,{\color[rgb]{0.75,0,0.25}\mathbf{C}}_{{\color[rgb]{0,0.88,0}e},{\color[rgb]{0,0.88,0}c}}\!\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}\!\left\{\!\!\begin{array}[]{rr}1&\texttt{if }{\color[rgb]{0,0.88,0}e}\in{\color[rgb]{0,0.88,0}c}\\
0&\texttt{else}\end{array}\right.\!\!

Recall that each colour
{\color[rgb]{0,0.88,0}c}\in{\color[rgb]{0,0.88,0}\mathcal{C}}
represents a potential token;
{\color[rgb]{0.75,0,0.25}\mathbf{C}}_{{\color[rgb]{0,0.88,0}e},{\color[rgb]{0,0.88,0}c}}=1
then means that an edge
{\color[rgb]{0,0.88,0}e}
represents an instance of
{\color[rgb]{0,0.88,0}c}
’s token.
Notably, these matrices represent the structural constraints of a tokenisation problem.
We now define three vectors which we will use to define a specific tokeniser:
(i) a
free token-instance vector

{\color[rgb]{0.75,0,0.25}\mathbf{f}}\in\{0,1\}^{{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}}
;
(ii) a
priced token-instance vector

{\color[rgb]{0.75,0,0.25}\mathbf{p}}\in\{0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{P}}}
; and
(iii) a
priced-colour vector

{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in\{0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{C}}}
.
These vectors represent, respectively, which free and priced edges are being used to segment a tokenisation-graph (forming, together, a graph-segmentation) and which tokens are selected as colours (forming a graph-vocabulary).
As we can choose at most
K
colours, we introduce the constraint
\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{c}}\right\rangle\leq K
.
Further, a priced token-instance can only be used if its priced-colour is a part of the vocabulary, motivating the constraint
{\color[rgb]{0.75,0,0.25}\mathbf{p}}-{\color[rgb]{0.75,0,0.25}\mathbf{C}}{\color[rgb]{0.75,0,0.25}\mathbf{c}}\leq 0
.
Finally, we introduce flow-constraints
(
10
;
8
, from)
to guarantee that the solution
{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{f}}
forms a valid path (or segmentation) over the graph.
To this end, we define a
flow-difference
vector
{\color[rgb]{0.75,0,0.25}\mathbf{d}}\in\{-1,0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{V}}}
which is defined as
{\color[rgb]{0.75,0,0.25}\mathbf{d}}_{{\color[rgb]{0,0.88,0}v}^{0}_{0}}=-1
,
{\color[rgb]{0.75,0,0.25}\mathbf{d}}_{{\color[rgb]{0,0.88,0}v}^{N}_{L}}=1
for the starting and ending vertices, and as
{\color[rgb]{0.75,0,0.25}\mathbf{d}}_{{\color[rgb]{0,0.88,0}v}}=0
for other vertices.
This vector can then be used to guarantee that the input-output flow difference in all vertices is zero, except for the starting vertex (with a
-1
flow difference) and the ending vertex (with a
+1
flow difference):

{\color[rgb]{0.75,0,0.25}\mathbf{P}}{\color[rgb]{0.75,0,0.25}\mathbf{p}}+{\color[rgb]{0.75,0,0.25}\mathbf{F}}{\color[rgb]{0.75,0,0.25}\mathbf{f}}={\color[rgb]{0.75,0,0.25}\mathbf{d}}
.
Together, these constraints enforce that any choice of
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}
corresponds to a valid graph-segmentation and graph-vocabulary.
The length of this graph-segmentation can then be measured as
\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{p}}\right\rangle+\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{f}}\right\rangle
.
We can now define the IP as:

\displaystyle\!\!\begin{array}[]{cc}\min&\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{p}}\right\rangle+\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{f}}\right\rangle\\[1.99997pt]
\text{s.t.}&{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}\end{array}\!\!\!\!,\texttt{ where }{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}\left\{\begin{aligned} {\color[rgb]{0.75,0,0.25}\mathbf{f}}\in&\{0,1\}^{{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}}\\
{\color[rgb]{0.75,0,0.25}\mathbf{p}}\in&\{0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{P}}}\\
{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in&\{0,1\}^{{\color[rgb]{0,0.88,0}\mathcal{C}}}\end{aligned}\!:\,\,\begin{aligned} {\color[rgb]{0.75,0,0.25}\mathbf{P}}{\color[rgb]{0.75,0,0.25}\mathbf{p}}+{\color[rgb]{0.75,0,0.25}\mathbf{F}}{\color[rgb]{0.75,0,0.25}\mathbf{f}}&={\color[rgb]{0.75,0,0.25}\mathbf{d}}&\!{\color[rgb]{0.5,0.5,0.5}\text{\# valid segmentation}}\\
{\color[rgb]{0.75,0,0.25}\mathbf{p}}-{\color[rgb]{0.75,0,0.25}\mathbf{C}}{\color[rgb]{0.75,0,0.25}\mathbf{c}}&\leq 0&\!\!\!{\color[rgb]{0.5,0.5,0.5}\text{\# token in vocabulary}}\\
\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{c}}\right\rangle&\leq K&{\color[rgb]{0.5,0.5,0.5}\text{\# vocabulary budget}}\end{aligned}\right\}\!\!

Note that, as mentioned above, any choice of
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}
corresponds to a valid graph-vocabulary and graph-segmentation, which, in turn, correspond to a valid tokeniser.
We make two observations regarding this IP.

Observation 3.4
.

Let
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}
be any element of
{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}
(as defined in
Section

3.2
).
We can convert this instance into a tokeniser
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}
with compression
{\color[rgb]{0.9961,0.3789,0}f}({\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}})=\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{p}}\right\rangle+\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{f}}\right\rangle
.

Observation 3.5
.

Let
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}
be any valid tokeniser with budget
K
.
If
{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}={\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{byte}}
and
{\color[rgb]{0,0.88,0}\mathcal{P}}={\color[rgb]{0,0.88,0}\mathcal{E}}_{\mathtt{tok}}
, we can convert this tokeniser into an instance of
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}
with path length

These observations guarantee that all elements in the space of solutions
{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}
correspond to valid tokenisers with equivalent compressions, and that all valid tokenisers correspond to elements in the non-relaxed polytope
{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}
with equivalent path-lengths. Please see

3.3
Approximating the Integer Program via Convex Relaxations

As mentioned above, the IP in
Section

3.2
is still an
\mathsf{NP}
-hard optimisation problem.
We can, however, use a convex relaxation to transform it into an LP, which can be solved efficiently.
To this end, we simply relax all variables
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}
from being optimised over the discrete space
\{0,1\}
to be optimised over the continuous
[0,1]
interval instead.
The priced-colour vector, for instance, becomes
{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in[0,1]^{{\color[rgb]{0,0.88,0}\mathcal{C}}}
, allowing for partial tokens to be selected for a tokeniser.
Similarly, the priced token-instance vector allows for edges to be partially included in the solution.
Formally, we write:

\displaystyle\begin{array}[]{cc}\min&\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{p}}\right\rangle+\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{f}}\right\rangle\\
\text{s.t.}&{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in{\color[rgb]{0.75,0,0.25}\mathcal{Q}}\end{array}\!\!\!\!,\texttt{ where }{\color[rgb]{0.75,0,0.25}\mathcal{Q}}\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}\left\{\begin{aligned} {\color[rgb]{0.75,0,0.25}\mathbf{f}}\in&[0,1]^{{\color[rgb]{0,0.88,0}{\color[rgb]{0,0.88,0}\mathcal{F}}}}\\
{\color[rgb]{0.75,0,0.25}\mathbf{p}}\in&[0,1]^{{\color[rgb]{0,0.88,0}\mathcal{P}}}\\
{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in&[0,1]^{{\color[rgb]{0,0.88,0}\mathcal{C}}}\end{aligned}:\,\,\begin{aligned} {\color[rgb]{0.75,0,0.25}\mathbf{P}}{\color[rgb]{0.75,0,0.25}\mathbf{p}}+{\color[rgb]{0.75,0,0.25}\mathbf{F}}{\color[rgb]{0.75,0,0.25}\mathbf{f}}&={\color[rgb]{0.75,0,0.25}\mathbf{d}}&{\color[rgb]{0.5,0.5,0.5}\text{\# valid segmentation}}\\
{\color[rgb]{0.75,0,0.25}\mathbf{p}}-{\color[rgb]{0.75,0,0.25}\mathbf{C}}{\color[rgb]{0.75,0,0.25}\mathbf{c}}&\leq 0&\!\!{\color[rgb]{0.5,0.5,0.5}\text{\# token in vocabulary}}\\
\left\langle 1,{\color[rgb]{0.75,0,0.25}\mathbf{c}}\right\rangle&\leq K&{\color[rgb]{0.5,0.5,0.5}\text{\# vocabulary budget}}\end{aligned}\right\}

We term this relaxation of
{\color[rgb]{0.75,0,0.25}\mathcal{Q}}
the
tokenisation polytope
.
9
9

9

A polytope is defined as the finite closed intersection of halfspaces.

Notably, this problem can be solved efficiently (or near-exactly, up to numeric approximation).
Tokenisers’ vocabularies, however, are discrete sets; thus, we cannot straightforwardly convert instances
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in{\color[rgb]{0.75,0,0.25}\mathcal{Q}}
of this LP that involve fractional variables into a tokeniser.
Hence, we will need to discretise the output of this LP, a process typically known as
rounding
.
We consider three rounding schemes here, noting that this is far from an exhaustive list: deterministic, biased, and integral-only rounding.

Deterministic rounding (
Det
)
rounds the
K
colours in
{\color[rgb]{0.75,0,0.25}\mathbf{c}}
with the largest value to 1, and sets others to zero.

Biased rounding (
Bias
)
, instead ranks each colour in
{\color[rgb]{0.75,0,0.25}\mathbf{c}}
by its value divided by the length of the token it represents (
{\color[rgb]{0.75,0,0.25}\mathbf{c}}/{\color[rgb]{0.9961,0.3789,0}\mathtt{length}}({\color[rgb]{0,0.88,0}c})
, with a slight abuse of notation to let
{\color[rgb]{0.9961,0.3789,0}\mathtt{length}}({\color[rgb]{0,0.88,0}c})
denote the length of the corresponding token), and then rounds these values (to 1 or 0) as before.
This biases the selection towards shorter tokens when LP scores are comparable, and is motivated by the fact that shorter tokens are more likely to occur outside the training strings in
{\color[rgb]{0,0,0}\mathcal{D}}
.
Finally,
integral-only rounding (
Int
)
keeps only the colours
{\color[rgb]{0.75,0,0.25}\mathbf{c}}
whose value is already essentially one, setting others to zero.
This can be interpreted as selecting the tokens that the LP relaxation treats as forced, but it will typically return a vocabulary with fewer tokens than the allowed budget
K
.

Data.

We used ClimbMix400B
(

for training both tokenisers and LMs. ClimbMix400B is a large-scale pretraining corpus derived from NVIDIA’s Nemotron-ClimbMix dataset
(

As is common when tokenising, the text is first pre-tokenised using a regular expression that splits the input into linguistically and typographically meaningful chunks. Tokenisers.

Throughout our experiments, we use
BPE
as a baseline. We compare it to
ConvexTok
with the three rounding schemes presented above:
Bias
,
Det
, and
Int
. Further,
we train all tokenisers with
593{,}920
documents and with vocabulary sizes from
8k
to
256k
, in power-of-two increments.
We note that we abbreviate powers of 2 in the vocabulary sizes below, e.g., 8
k
corresponds to 8192. Furthermore, in practice, we may want to include a number of special tokens
{\color[rgb]{0.3281,0.4961,0.9375}\Phi}
(e.g., end-of-sequence, padding, masking, or output-start) in our tokeniser. We thus enforce
{\color[rgb]{0.3281,0.4961,0.9375}\Sigma}\cup{\color[rgb]{0.3281,0.4961,0.9375}\Phi}\subset{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}

|{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}|=|{\color[rgb]{0.3281,0.4961,0.9375}\Sigma}|+|{\color[rgb]{0.3281,0.4961,0.9375}\Phi}|+K,
where
|{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}|
is our vocabulary size.
Finally, at inference, our tokenisers use a standard shortest path algorithm (similar to UnigramLM’s;
22
) to produce token-strings;
ConvexTok
thus has a similar runtime as UnigramLM and
BPE
.

(

Behaviour of Solving the Linear Programs.

Table
1
reports several optimisation statistics obtained when solving the LP relaxation for different vocabulary sizes.
Unsurprisingly, the primal objective (i.e., the LP value) decreases monotonically as the vocabulary size increases.
More interestingly, the solution becomes more integral as the vocabulary size increases.
12
12

12

In practice, we used 0.999 as an approximation for 1 and 0.001 as an approximation for 0, due to numerical imprecision.

This suggests that, at larger vocabulary sizes, the optimisation problem becomes less ambiguous, and therefore more tokens are already determined by the LP solution, leaving less work for the subsequent rounding procedure. Another thing to note is the relative stability of the running time, with the obvious exception of the much slower run with a vocabulary size of
8k
. This could be due to the small vocabulary budget making the feasible region substantially more constrained, causing the solver to spend much longer resolving the trade-offs between competing token choices.
Finally, we also note how small the number of non-zero entries are in comparison to how many variables exist.

Stability of Tokenisers to Randomness on the Training Sample.

In
Figure

3
, we study our tokenisers’ stability relating to a specific choice of training set.
To this end, we train tokenisers using independently sampled subsets of our training data, and compare their vocabularies using the Jaccard similarity, defined, for two vocabularies
{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{1}
and
{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{2}
, as
\frac{|{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{1}\cap{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{2}|}{|{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{1}\cup{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{2}|}
.
Further, we repeat this procedure for different training dataset sizes.
We say a tokeniser is more
stable
, if its Jaccard similarity is higher.

Figure

3
shows that stability decreases as the vocabulary size increases.
As this trend is consistent for both
BPE
and
ConvexTok
, it is likely due to larger vocabularies containing more low-frequency tokens, which are more sensitive to the sampled dataset.
Another thing to note is that
BPE
is consistently more stable than
ConvexTok
tokenisers.
This aligns with
BPE
being a local and frequency driven method; due to the power-law nature of natural language distributions, high-frequency merges are unlikely to change due to resampling.
The higher stability of
Int
compared to
Bias
or
Det
is also to be expected, as
Int
includes only tokens which the LP deems “critical”.

Conclusion

In this paper, we reinterpreted tokenisation as a graph problem and formulated the resulting compression objective as an IP.
We then studied its corresponding relaxed formulation (i.e., its LP) experimentally, including both its solvability and three rounding procedures for converting fractional LP solutions into discrete tokenisers.
Our experiments show that the
ConvexTok
tokenisers are strong both in terms of intrinsic metrics and
BpB
; results on
CORE
metrics are more mixed, but suggest
ConvexTok
still at least matches
BPE
’s performance.
Overall, our results suggest that globally optimised tokenisation is a promising alternative to locally greedy merge-based methods such as
BPE
.

Limitations and Future Work.

The focus of this paper is on compression; however,
Table

2
shows that getting tokenisers with near-optimal compression on a dataset is not too hard, as at
128k
and
256k
our approach achieves results within
1\,\%
of the LP lower bound.
Significantly improving training-data compression is thus senseless under similar constraints.
Recent approaches like SuperBPE
(
26
)
, however, propose methods which partially ignore pretokenisation; it would be interesting to extend our analyses to those settings.
Further, extending our LP-based approach to other objective functions
{\color[rgb]{0.9961,0.3789,0}f}
could also lead to novel and interesting tokenisers.

Appendix A
Formal description of
BPE

Let
{\color[rgb]{0.9961,0.3789,0}\mathtt{merge}}_{{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime},{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime\prime}}
be a function which, given a token-string, replaces all occurrences of the bigram
{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime},{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime\prime}
in it with the merged token
{\color[rgb]{0.8633,0.1484,0.4961}t}^{\texttt{new}}\stackrel{{\scriptstyle\texttt{\tiny def}}}{{=}}{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime}\circ{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime\prime}
.
The
BPE
algorithm then works as follows:
it initialises a character-level tokeniser,
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}_{0}=\langle{\color[rgb]{0.3281,0.4961,0.9375}\Sigma},{\color[rgb]{0.9961,0.3789,0}\mathtt{id}},{\color[rgb]{0.9961,0.3789,0}\mathtt{detok}}\rangle
, where
{\color[rgb]{0.9961,0.3789,0}\mathtt{id}}
is the identity function;
for a pre-specified number of steps
K
,
it then takes the current tokeniser
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}_{k-1}=\langle{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{k-1},{\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}_{k-1},{\color[rgb]{0.9961,0.3789,0}\mathtt{detok}}\rangle
and selects the pair of existing tokens
{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime},{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime\prime}\in{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{k-1}
which, if merged, will lead to maximal compression, and adds it to the vocabulary, as
{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{k}={\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}_{k-1}\cup\{{\color[rgb]{0.8633,0.1484,0.4961}t}^{\texttt{new}}\}
, and the encoding function as
{\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}_{k}({\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}})={\color[rgb]{0.9961,0.3789,0}\mathtt{merge}}_{{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime},{\color[rgb]{0.8633,0.1484,0.4961}t}^{\prime\prime}}({\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}_{k-1}({\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}))
.

Appendix B
Alternatives to Linear Programming for solving IPs

An alterative choice to linear programming is to use methods such as branch-and-bound methods to solve the IP directly.
While branch-and-bound algorithms perform well in practice on highly structured IPs, such the travelling salesman problems
(
2
)
, they exhibit poor scaling behaviours.
Hence, we decided to use linear programming with rounding, as this method scales better
(
20
)
.
We hope future work explores other approaches to investigate this IP.

Appendix C
Mapping Between Vectors of the IP and the Token Sequence

In this section, we describe how to map an element of
{\color[rgb]{0.75,0,0.25}\mathcal{Q}}
to a tokeniser
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}
, and back.
We give an informal sketch here, as the process is relatively simple and doing it formally would drown the reader with technical details which would obscure the idea.

C.1
From an IP Solution to a Tokeniser

Consider some free token-instance vector, priced token-instance vector, and priced-colour vector
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}},{\color[rgb]{0.75,0,0.25}\mathbf{c}}\in{\color[rgb]{0.75,0,0.25}\mathcal{Q}}^{\texttt{IP}}
.
First, we can recover the vocabulary by taking the union of all elements of
{\color[rgb]{0.75,0,0.25}\mathbf{c}}
which are equal to 1 and the alphabet.
Formally, the vocabulary is
\{{\color[rgb]{0.8633,0.1484,0.4961}t}_{\color[rgb]{0,0.88,0}c}\in{\color[rgb]{0,0.88,0}\mathcal{C}}\mid{\color[rgb]{0.75,0,0.25}\mathbf{c}}_{{\color[rgb]{0,0.88,0}c}}=1\}\cup{\color[rgb]{0.3281,0.4961,0.9375}\Sigma}
, where we denote as
{\color[rgb]{0.8633,0.1484,0.4961}t}_{\color[rgb]{0,0.88,0}c}
the token corresponding to colour
{\color[rgb]{0,0.88,0}c}
.
Second, with the free and priced vectors
{\color[rgb]{0.75,0,0.25}\mathbf{f}},{\color[rgb]{0.75,0,0.25}\mathbf{p}}
one can recover a valid segmentation of the dataset
{\color[rgb]{0,0,0}\mathcal{D}}
.
Recall that each potential use of a token to encode a byte-string
{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}\in{\color[rgb]{0,0,0}\mathcal{D}}
corresponds to exactly one edge in either
{\color[rgb]{0.75,0,0.25}\mathbf{f}}
or
{\color[rgb]{0.75,0,0.25}\mathbf{p}}
.
As such, to recover the segmentation of
{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}\in{\color[rgb]{0,0,0}\mathcal{D}}
by selecting a token if and only if its corresponding edge from
{\color[rgb]{0.75,0,0.25}\mathbf{f}}\cup{\color[rgb]{0.75,0,0.25}\mathbf{p}}
is equal to 1.
For completeness, given the extracted vocabulary, we use PathPiece
(
33
)
to define the encoding function’s behaviour on other byte-strings not in the dataset, computing:

\displaystyle\forall_{{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}\notin{\color[rgb]{0,0,0}\mathcal{D}}}:{\color[rgb]{0.9961,0.3789,0}\mathtt{tok}}({\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}})=\argmin_{{\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}}\in{\color[rgb]{0.8633,0.1484,0.4961}\mathcal{T}}^{*}}|{\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}}|,\texttt{ s.t. }{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}{\color[rgb]{0.9961,0.3789,0}\stackrel{{\scriptstyle{\circ}}}{{=}}}{\color[rgb]{0.8633,0.1484,0.4961}\mathbf{{\color[rgb]{0.8633,0.1484,0.4961}t}}}

(16)

C.2
From a Tokeniser to an IP Solution

Now we sketch how to take a tokeniser
{\color[rgb]{0.8633,0.1484,0.4961}\mathbb{T}}
and convert it to vectors contained within the IP.
This is simply the process described above, but in reverse.
Given the tokeniser’s vocabulary, we set each element
{\color[rgb]{0.75,0,0.25}\mathbf{c}}_{\color[rgb]{0,0.88,0}c}
in vector
{\color[rgb]{0.75,0,0.25}\mathbf{c}}
to 1 if and only if its corresponding token
{\color[rgb]{0.8633,0.1484,0.4961}t}_{\color[rgb]{0,0.88,0}c}
is included in the vocabulary.
For the dataset
{\color[rgb]{0,0,0}\mathcal{D}}
then, we consider each of its byte-strings
{\color[rgb]{0.3281,0.4961,0.9375}\mathbf{{\color[rgb]{0.3281,0.4961,0.9375}b}}}\in{\color[rgb]{0,0,0}\mathcal{D}}
and run it under the tokeniser’s encoding function to get a token-string.
For each token in this token-string, we then find its correspondence in either
{\color[rgb]{0.75,0,0.25}\mathbf{f}}
or
{\color[rgb]{0.75,0,0.25}\mathbf{p}}
and set it
to
1
; the rest of these vectors are all zero.
