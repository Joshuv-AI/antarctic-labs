 i

 Summary
This report presents NekMeshPy, a fully type-annotated Python toolkit for high-order, conformal
all-hexahedral meshing, developed following an earlier exercise in which Claude Code implemented
a published meshing strategy for a bifurcating geometry [1]. The toolkit is not a general-purpose
mesher but a collection of building blocks, such as lofting, morphing, merging, skinning, and
smoothing, together with a high-order data structure, flexible boundary tagging, Nek5000/RS [2, 3]
readers and writers, and built-in quality and conformality checks that guide an LLM toward valid
meshes. We then used Claude to build a set of examples to assess how well an LLM can use the
toolkit. For topologically simple meshes, such as the Chimera example, the LLM could reuse existing
examples, for instance a T-junction, and assemble a large conformal mesh from brief prompts. For
more complex topologies, a user who knows how to mesh the geometry is still needed to guide the
LLM step by step. The main drawback we found is code quality: LLM-written code tends to be
hard to read and maintain, so frequent human review and restructuring are essential. For example,
a wire-coil example written by Claude in about 2,500 lines was reduced to fewer than 500 lines
when restructured by a human.

1 Introduction
Recently, there has been growing interests in using LLM agents to streamline some of the pipelines
in going from a design to a numerical simulation result. Meshing is one of the most difficult steps in
this pipeline, and several efforts are underway to develop frameworks that LLM agents can use to
generate all-hexahedral meshes [1]. This report describes one such attempt.
 In our previous report [1], we used Claude Code to implement a meshing strategy for a
bifurcation geometry. Starting from an STL surface of the geometry and a reference paper describing
the strategy, with no existing code, we obtained a hexahedral mesh and ran a simulation on it in
Nek5000/RS [2, 3] within about six hours of prompting.
 This report covers NekMeshPy, a general toolkit for high-order, conformal all-hex meshing. This
is not meant to be a mesher like Gmsh [4] that can mesh arbitrary geometry, but is just a collection
of functions that user and LLM can use to write a mesher, like lofting, morphing, merging, skinning,
smoothing operations, along with a data structure that can accomodate high-order connectivity
and versatile tagging capability, as well as writer and reader that can work with Nek5000/RS mesh
format. A lot of mesh quality checks and conformality check is also built into the toolkit, which
serves as a guide or objective for user or LLM to optimize for.
 LLM is then used to help implementing meshing examples that covers a few different geometries.
This help us understand how LLM’s capability and how it can utilize the toolkit. A big part of the
toolkit is a diverse set of examples. These examples serve as reference on how to utilize the toolkit,
and also as a guide for toolkit development. With a big enough set of examples, LLM should be
able to pull from common techniques in examples and use them for more arbitrary geometries. An
example to illustrate this is T-junction. It is quite difficult to get LLM to mesh T-junction from
scratch, but once a T-junction example is available for reference, LLM is able to trivially use the
same technique everywhere in a much more complex mesh, i.e. Chimera. More impressively, with
multiple topologies for the same T-junction, LLM agents can swap out the topology in one single
prompt, changing the rest of the mesh topology correspondingly, and able to write “adapter meshes”
that connect sections with wildly different topologies.
 For simple enough geometries, LLM shouldn’t have much problem meshing just from a brief
description of the geometry. But for more complex topologies, user still need to know how to mesh
it and how to code or describe the meshing strategy to LLM, for which case LLM is only there to
aid in the implementation.
 From the exercies in this report, we observe that one significant downside of using LLM is that
the code end up pretty much unreadable and unmaintanable by a human. For example, complex
meshes like wire-coil is initially coded entirely by Claude in 2500 lines. A human later reorganized
the strategies and structures properly, before manually wrote code that ended up only less than
500 lines. LLM frequently invent weird hacks that significantly destroy any codebase. Very careful
review must be done by human frequently to keep the codebase in check if they want to keep a
maintainable and clean code.
 NekMeshPy is written in strongly typed Python on numpy and scipy. There is also small
support to utilize Gmsh [4] for cases that requires an initial tet mesh for conduction solve, or
unstructured quad mesh.

2 Toolkit overview
2.1 Levels

The toolkit is structured bottom-up and follows four levels: PointMesh, LineMesh, QuadMesh, and
HexMesh. Each level contains connectivity (which points to elements at the lower level), tags, the
lower level, high-order nodes. This enforce connectivity and conformal mesh that force each level
to be also made up of elements from the lower level. Higher order nodes are also enforced to be
conformal this way, making sure that two elements sharing one face can be certain that their face
are curved exactly the same.

2.2 Tagging

Tags are important for a few uses, more specifically for specifying boundary conditions and attaching
components. It is also important for periodic boundary condition, which is prescribed by the user
by two tags of the two periodic boundary, followed by prescribing a transform function from one to
the other.

2.3 Lofting

Lofting construct a level by connecting slices of a lower level. There is built in function to also
sweep one slice along a path, for example to construct a bending pipe along an arbitrary path.
 Lofting also propagates the tagging from the lower level along its sides, for example to tag the
wall of the pipe as it is extruded, or tagging fluid-solid elements when extruding from a QuadMesh.
The toolkit is designed to accommodate several different use cases, but any arbitrary usage can be
work around since it is just Python.

2.4 Attach

To connect two seperate mesh conformally, user can either let the toolkit match exposed faces by
coordinate with a kdtree, or manually specify a tag from each mesh to be connected together, which
prompt the code to match them one-to-one.

2.5 Boundary layer skinning

Offset is an operation built in the toolkit that can take any arbitrary surface and offet it along the
surface normal. This can be used to skin a mesh to create thin boundary layers that only wrap
along the wall.

2.6 Examples and tests

We build several examples in the toolkit and will continue to expand the example pool. This set of
examples should be a helpful reference for both other users and LLMs, and we hope to build a big
enough library that can cover a vast majority of geometries.

 There is also a big test suite, which is mostly written by LLM, just to make sure the toolkit
continue to behave as expected as the toolkit develops.

3 The CHIMERA example
CHIMERA [5] stands for Combined Heating and Magnetic Research Apparatus, a fusion system
developed by the UK Atomic Energy Authority (UKAEA). CHIMERA is a world-first testing facility
located at the Fusion Technology Facility in South Yorkshire, UK.
 There has been previous NekRS simulation of CHIMERA [6]. However, the mesh used in that
simulation is a tet–to–hex mesh that will not give as good mesh quality as a structured mesh. The
tet–to–hex mesh results in a total of 1,691,729,664 elements, where as the structured mesh generated
in this example only has 821,248 elements.
 CHIMERA is not a very difficult mesh topologically. It comes down to a series of bending pipes
and connecting T-junctions. Solid domain of chimera is still a challenge to be meshed conformally
with the fluid domain, but any gap in meshing can still be overcome by overlapping meshes, which

this toolkit will also be designed to support for.
 CHIMERA has a simple topology but writing up all the code to build the geometry, bifurcation,
bending pipes, and connect everything conformally is still very tedious, and a big blocker for someone
who are not into meshing. With a well-designed meshing toolkit, for example, that has built-in path
sweeping to sweep a quad mesh to hex mesh along a path, these tedious operations could be less
painful, but meshing remains a laborous task.
 Tedious but simple tasks like this is where LLM shines. CHIMERA is chosen to illustrate
a typical mesh that is simple topologically, but no human want to sit down and write codes to
place down 40 T-junctions and try and bends them to correct shape and connect them so they
all connected conformally. Given that the topology is simple enough, the ideal scenario would be
simply giving LLM a STEP file and LLM just figure out how to write the code to make a hex mesh;
this is the first step toward that. The full example is shown in Figure 1.

3.1 Front panel

In this example, the mesh is built up component by component by prompting with Claude. The
first place we start with was one unit in the front panel of CHIMERA (Figures 2 and 3), which are
two series of T-junctions connected together by these pill-shaped bends.

 The front panel is made up of 5 of such units, connected via pipe A and pipe B alternately.

3.4 Connecting all the panels

The connected result is shown in Figure 6.

 The best strategy we found for describing these to LLM is to first, tell it to place down all four
panels and all T-junctions needed to connect them in space, correcting the coordinate or orientations
if needed. Then, the prompt to LLM would simply be: ”Connect T-junction pipe A to inlet B” one
by one. LLM’s job here is simply figure out the path that bends pipe from A to B, and make sure
that all the connections are conformal.

 An interesting thing here is there are two different T-junctions topology in these connections

means the element numbering in each differs. The toolkit has been designed for these usages in
mind, and the LLM has no problem connecting these and even can perform skinning throughout
the mesh.

3.5 The boundary layer

Figure 8: Boundary-layer mesh in the CHIMERA front panel: full view (left) and close-up (right).
The cross-section contains 80 elements: 48 in the core and 32 in the two boundary-layer rings. Over
the whole front panel, the boundary-layer (skin) elements account for 228,320 of the 501,600 fluid
elements, or about 46%.

Everything fluid is meshed at a slightly smaller radius. Then, skinning operation is performed on the
surface to grow and create thin boundary layers through out the whole mesh (Figure 8). Skinning
operation is already implemented in the toolkit, so the LLM job in this case would simply be making
all the geometry slightly smaller and decide which surface to include in skinning operation.

4 The wire-coil example
This geometry is based on experiments from [7], more specifically, coil #34 in the paper.
 There are a few approaches to mesh this geometry. You can mesh the coil as a pipe swept
along the helical path, which will result in singularity at the center that can be resolved by using
an overlapping mesh to handle the center. Another approach is to mesh the 2D cross-section at a
constant z, then extrude with twist. This approach is good for long pitch, but for short pitch it will
result in very skewed elements as the twist needs to be more drastic.
 This example present a different topology, which is fully conformal and suitable for both long
and short pitch. The key is to not enforce a structured mesh to the coil, but instead allows varying
topology along the coil. This topology is analogous to starting from a cylindrical background mesh,
deleting elements near the coil, then project the deleted faces toward the coil surface; though there
are some slight differences.

 Figure 10: Staircase pattern of mesh faces along the coil surface.

 The topology is much more complex in this case, and the user has to know how to mesh and
describe instructions to LLM from bottom-up.
 We start with the inner most cylindrical core at the center (Figure 9). On the coil surface, a

which then helps the topology climbing up along the cylindrical core side. By varying this staircasing
pattern, user can control how fast the mesh climbs depending on the pitch. Figures 11, 12 and 13

 The prompt to LLM to construct this mesh is in the same order as presented, meshing from

particular, with good structure manually coded by human, the meshing code can go from around
2500 lines to less than 500 lines.

5 Early user experience
Several users have tried the toolkit together with an LLM and found that a good initial mesh can be
obtained within a few prompts. By their estimates, building a comparable mesh in a conventional
tool such as Gmsh would take two to three days.
 These initial meshes are not yet ideal: further prompts are typically needed to smooth the
elements, add boundary layers, apply skinning, and so on. However, they are already topologically
correct, conformal, and watertight, with well-shaped elements, and they can be used directly in
Nek5000/RS.
 These early results suggest that agentic meshing is viable and can significantly accelerate the

6 Conclusion
NekMeshPy is a library for conformal, high-order, all-hexahedral meshing, intended as one of the
building blocks toward agentic all-hex meshing. Using a range of example geometries, we assessed
how effectively an LLM can use the toolkit.
 For topologically simple meshes, the LLM can draw on an existing pool of examples and
topologies and assemble a large mesh with little guidance, as the Chimera example shows. For more
complex topologies, it still requires a user who knows how to mesh the geometry and can guide
it through the strategy step by step, from the bottom up. In the future, we aim to build a large
collection of examples that an LLM can draw on and apply to more general geometries.
 The design of the meshing framework is critical. It should be interactive and highly extensible,
so that the LLM can freely try different approaches without reimplementing standard operations,
while the framework enforces the essential constraints of full conformality and an all-hexahedral
mesh.
 LLMs are well suited to obtaining a working mesh quickly, iterating rapidly, tuning parameters,
tagging boundaries, and performing tedious tasks such as projecting onto helical surfaces and
connecting junctions conformally. However, as discussed above, the code they produce is often
difficult to read and maintain: the wire-coil example was reduced from about 2,500 lines to fewer
than 500 when restructured by a human. We therefore recommend that users review LLM-generated
code frequently and restructure it early, in order to keep the codebase clean.
