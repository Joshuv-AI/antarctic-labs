Cross-Ecosystem Vulnerability Analysis for Python Applications
Georgios Alexopoulos, Nikolaos Alexopoulos, Thodoris Sotiropoulos, Charalambos Mitropoulos, Zhendong Su, Dimitris Mitropoulos, [1mm] University of Athens, National Infrastructures for Research, Technology

Abstract
Python applications depend on native libraries that may be vendored within package distributions or installed on the host system. When vulnerabilities are discovered in these libraries, determining which Python packages are affected requires cross-ecosystem analysis spanning Python dependency graphs and OS package versions. Current vulnerability scanners produce false negatives by missing vendored vulnerabilities and false positives by ignoring security patches backported by OS distributions. We present a provenance-aware vulnerability analysis approach that resolves vendored libraries to specific OS package versions or upstream releases. Our approach queries vendored libraries against a database of historical OS package artifacts using content-based hashing, and applies library-specific dynamic analyses to extract version information from binaries built from upstream source. We then construct cross-ecosystem call graphs by stitching together Python and binary call graphs across dependency boundaries, enabling reachability analysis of vulnerable functions. Evaluating on 100,000 Python packages and 10 known CVEs associated with third-party native dependencies, we identify 39 directly vulnerable packages (47M+ monthly downloads) and 312 indirectly vulnerable client packages affected through dependency chains. Our analysis achieves up to 97% false positive reduction compared to upstream version matching. We responsibly disclosed all findings to maintainers.

When vulnerabilities are discovered in native libraries,

Performing this cross-ecosystem analysis

Solving this problem requires

Approach:

Our key insight is that accurate vulnerability

We leverage the observation that many

For libraries built from upstream source,
we perform lightweight library-specific

directly from the binary.
Once provenance is established,
we construct a
cross-ecosystem call graph

that spans Python code,
native extensions,
vendored libraries,
and system libraries.
This enables reachability analysis
to determine whether vulnerable

Background

2.1
Python and OS Package Distribution

Python package distribution:

Python packages are distributed
as source distributions (sdists)
or
wheels
,
which are pre-built artifacts
[
32
]

that may bundle Python code together
with compiled native extensions
and shared libraries.
Since the Python package manager
pip
installs
wheels by default when available
[
60
]
,
most deployments rely on these pre-built artifacts.
The 2024 Python Developer Survey shows
that 75% of developers install packages from PyPI,
compared to only 11% from OS repositories
[
34
]
,
showing that Python software is mainly distributed through PyPI wheels
rather than OS-managed packages.

The
manylinux
specification
[
45
,
73
]
enables
cross-distribution compatibility
by restricting which system libraries
wheels may link against.
The
auditwheel
tool
[
57
]

enforces compliance by
vendoring
,
i.e., copying and bundling
external shared libraries directly into wheels,
as shown in Figure
2
.
Concretely,

auditwheel repair
copies
each external library into a

.libs
subdirectory within the wheel,
renaming it with an
8-character hash derived from its contents
(e.g.,
libxml.so.2.9.1

becomes
libxml-3998bec4.so.2.9.1
).
It then patches the compiled

.so
files to update
DT_NEEDED
entries
and
RPATH
to reference
the bundled copies
[
58
]
.
The standard pipeline,
widely adopted via

cibuildwheel

[
59
]
,
compiles inside
manylinux

Docker containers
[
61
]

and vendors native dependencies
into self-contained artifacts.
Vendored libraries originate from the build environment
at
compilation time
;

manylinux
containers,
historically based on CentOS and now on AlmaLinux or Debian,
supply system libraries,
while project-specific dependencies are typically compiled
from source or installed via the base image’s OS package manager
during the build.

This achieves an effect similar to static linking
[
57
]
,
trading central library maintenance for portability.
PEP 513 acknowledges the tradeoff:
wheels bundling libraries like OpenSSL

“assume responsibility for prompt updates”

[
45
]
.
In practice,
however,
vendored dependencies fragment security,
as the same vulnerability may persist across many independent copies
that remain invisible to
system package managers
[
28
,
25
]
.

OS package distribution:

Operating system (OS) distributions
such as Debian GNU/Linux and RHEL,
organize a wide array of useful software
components from a wide array of sources,
in collections of files called packages.
For the remainder of this paper, we refer to
those packages as
OS packages
to differentiate
them from Python packages.
The sources of these packages
are commonly referred to
as their
upstream
.
For example, the development of the
OpenSSL toolkit takes place on Github
[
52
]

(this is the upstream),
while Debian maintainers package and maintain
the corresponding Debian package in
a downstream repository
[
18
]
.
The installation, updating, and removal
of OS packages
is done by a package management system,
such as
the
apt
front-end for Debian-based distributions,
and
yum
/
dnf
for RHEL-based ones.

In pursuit of stability, usability, and security,
distributions publish and maintain
releases
.
A release snapshots packages at specific upstream versions,
and over its lifetime
only security and
critical bug fixes are applied
[
17
]
.
Distribution maintainers are responsible for triaging
vulnerabilities and,
when necessary,
backporting fixes
from the upstream repository
to each version included in a supported release
[
19
]
.
Therefore,
a library shipped in an OS distribution has two relevant versions:
(1) its
upstream version
,
referring to the original project release,
and (2) its
OS package version
,
typically an increasing integer number
that reflects distribution-specific updates over time.
For example,
Debian 9 includes OpenSSL (upstream)
version 1.1.0l as its
openssl
package,
and the last version of the package for Debian 9
is
1.1.0l-1~deb9u11
,
containing 25 patches since the 2017 upstream release.

2.2
Motivating Study

To quantify the prevalence
and
impact of binary code in the PyPI ecosystem,
we study the top 100,000 PyPI packages by monthly downloads as of
January 2026
[
62
]
.
All packages in this set have at least 1,000 monthly downloads.
We distinguish between
(1)
native extensions
,
which are native Python modules
co-developed with the pure Python code,
and (2) other binary files.
The latter category includes both auxiliary
binaries that are still part of the project and third-party
libraries from external upstream projects.
For example,

pytorch
ships
(a) a native extension
_C.cpython-linux-gnu.so
,
(b) an auxiliary binary

libtorch.so
,
and (c) a third-party library
libgomp.so.1
from
GCC. Vulnerabilities in (a) and (b) are attributed to

pytorch
,
whereas vulnerabilities in (c) are attributed to
the GCC project.

Results:

Table
1
shows
that although only 8,152 of
the top 100,000 Python packages ship native extensions,
they impact a much larger part of the ecosystem:
58.9% of packages depend on at least one of them,
directly or transitively.
Similarly,
only 2,088 packages bundle additional binaries beyond native extensions,
yet 29% of the examined Python packages depend on them.
Among these 2,088 packages,
1,878 bundle vendored libraries
that are available on OS distribution packages (DA),
affecting 28% of the ecosystem through transitive dependencies.
Interestingly,
the auxiliary binaries
that are not available in OS packages
stem from derivative libraries of
core ML-related projects like TensorFlow.

This study shows that
although only a small fraction of packages vendor third-party libraries,
they affect more than a quarter of the PyPI ecosystem
through transitive dependencies.
This motivates our goal:

to reason about how vulnerabilities
in such third-party native dependencies propagate across PyPI
.
Moreover,
we observe that third-party libraries are typically also shipped
as OS distribution packages
Therefore,
we focus on distro-available libraries,
i.e., vendored binaries whose base name is provided by at least one Debian,
Ubuntu,
or Red Hat package
(technical details in Section
3.3.1
).

Assume that the Python package

Trivy

,
but is oblivious to the vulnerability
in the vendored

,

Challenges:

Assessing the impact of vulnerabilities
across different ecosystems
involves several technical challenges.

[C1]
Upstream versions are misleading.

Debian 9 “Stretch”
packages OpenSSL version 1.1.0l,
released on September 2019.
However,
Debian continues to backport security fixes
for up to a decade through its LTS and Extended LTS (ELTS) programs.
For example,
Debian released
1.1.0l-1 deb9u11
in October 2025,
which backports a fix
[
16
]
for CVE-2025-9230,
and ELTS support continues until June 2027.
Therefore,
the
upstream
version string alone is insufficient to determine
whether a library binary includes security patches.
Accurate vulnerability assessment requires
identifying the binary’s provenance,
i.e., its exact OS package revision of origin.

[C2]
Complex build procedures complicate provenance tracking

Although many vendored libraries are pulled from popular
Linux-based OSs (CentOS, Debian/Ubuntu etc.) the build
procedures often modify the binary files meaning there is
no longer a 1-1 byte-level match with the original, and
therefore exact hash matching is not directly possible
(Section
2
).
In less common cases,
developers manually build vendored libraries
from upstream source code instead of
reusing OS distribution packages.

[C3]
Long dependency chains

Although approaches
exist for the construction of call graphs for Python
scripts
[
69
]
and binary files
[
47
]
,
as well as for their cross-language linking
[
4
]
,
it is unclear how to combine them to efficiently extract
reachability information for
large cross-ecosystem call chains.

Threat Model:

We consider package maintainers who do not act as active adversaries.
Specifically, we assume that vendored libraries
have not been deliberately obfuscated,
stripped beyond standard build defaults,
or otherwise tampered with to evade detection.
Packages that intentionally manipulate
vendored binaries to conceal their identity
or provenance fall outside the scope of our analysis.
This model reflects the common case in open-source ecosystems,
where vendoring is a byproduct of the build pipeline
rather than an evasion strategy,
and aligns with the predominant behavior in PyPI.

Cross-Ecosystem Vulnerability Scanning

Figure 3

and

Overview:

Figure
3
summarizes our approach
for assessing the impact of vulnerabilities in OS packages
and shared libraries on Python packages and applications.
The inputs to our method are
(1) a Python package or application under analysis
and (2) a set of vulnerable binary symbols (function names),
derived from known vulnerabilities
and associated with specific OS package versions
or upstream project releases.
Our approach outputs a set of
cross-ecosystem
call chains
that originate in the Python ecosystem,
traverse native and OS-level components,
and eventually reach the provided vulnerable symbols.

The Python package/application under analysis
is in the form of a wheel file
(
.whl
, Section
2
).
Given such a
.whl
file,
the starting point is the construction of a

Python dependency tree

that captures all Python-level dependencies of the input package
by analyzing its wheel metadata.
Next,
our method expands each node in the Python dependency tree
into a corresponding
binary dependency tree
,
which captures all binary files
included in the package distribution
along with their inter-dependencies.
Then,
the third step is to perform a
provenance analysis

to identify the origin and version of each binary,
determining whether it is part of the Python package’s own codebase,
copied from a specific OS package and version,
or manually built from the source code of a third-party project
at a corresponding version.

This process results in an
enhanced Python dependency tree

that includes both Python- and binary-level dependencies,
with every binary explicitly tagged with
its provenance and version information.
This enhanced tree is then provided
as input to the
cross-ecosystem call graph (XECG) construction
step,
where our approach employs state-of-the-art Python
and binary call-graph generators
and stitches the resulting call graphs
according to the enhanced dependency tree.
Finally,
the approach performs a
reachability analysis
on
the constructed XECG to determine
whether the original Python package
or application can reach a vulnerable symbol in
any of its native dependencies.
In the following,
we explain every step of our approach in detail.

This is achieved by examining

.

3.2
Step 2: Binary Dependency Tree

In this step,
each node in the Python dependency tree
(Section
3.1
) is expanded into
a
binary dependency tree

that captures all ELF binaries included
in the corresponding Python package
and their inter-dependencies.
Each node in this tree represents an ELF binary,
identified by its location in the system and its type
(i.e., native extension,
vendored dependency,
or system dependency;
see Section
2
).
An edge
b_{1}\rightarrow b_{2}

indicates that the binary
b_{1}
depends on
(i.e., is dynamically linked against)
binary
b_{2}
.

To expand a package node in the Python dependency tree,
our approach proceeds as follows.
It analyzes the package’s
.whl
file,
detects all ELF binaries it contains,
and adds each binary as
a node in the binary dependency tree.
Next,
for each ELF binary,
the approach examines the binary’s
DT_NEEDED
header
to determine the list of
the dynamically linked libraries of the binary.
If the
DT_NEEDED
header contains shared libraries
that are not included in the wheel,
these binaries are added to the graph as additional nodes.
Finally,
for each reported dependency,
our method adds a directed edge from the dependent binary
to the corresponding shared library.

Identifying the type of binary dependencies:

To determine the type of each binary node in the expanded tree,
our approach classifies binaries
whose paths lie outside the extracted
.whl
directory
as
system dependencies

(e.g.,
/lib64/libcap.so.2
),
since they are not part of the Python wheel
but are dynamically linked by other binaries.
For binaries included in the wheel,
we distinguish between native extensions
and vendored dependencies.
Specifically,
we inspect exported symbols:
binaries defining a
PyInit_<pkgname>
symbol are classified
as
native extensions
,
as required by Python’s extension interface,
while all remaining binaries are classified
as
vendored dependencies
.

3.3
Step 3: Provenance Analysis

Figure 6
:
Resolving the provenance
of vendored libraries.

The next step is to determine the provenance of each binary.
We define provenance as
the specific version of source code
from which a binary was built.
Determining provenance is essential for
constructing precise cross-ecosystem call graphs
(Section
3.4
)
and for accurately assessing whether a Python package
or application is affected by a known vulnerability
in its binary dependencies
(Section
3.5
).

Provenance of native extensions and system libraries:

Resolving the provenance of native extensions is straightforward
because they are built as part of a specific Python package release.
Therefore,
their provenance corresponds to the Python package
and version to which they belong.
For example,
the provenance of the native extension

_igraph.abi3.so
in Figure
5
is
the Python package
igraph
version 0.11.9
(shown in bold).
Similarly,
the provenance of system libraries
(e.g.,
libz.so.1
in Figure
5
)
are easily determined,
since these libraries are managed
and versioned by the host OS
on which the Python package
or application is
deployed
.

Provenance of vendored libraries:

Resolving the provenance of
vendored libraries

is challenging though.
Vendored libraries are bundled inside
Python wheels and may originate
either from OS distribution packages
or from custom builds of upstream projects,
often with modified binary metadata
(Section
2
).
This obscures their original source and version information.
To address these challenges,
we employ two complementary provenance resolution procedures,
illustrated in Figure
6
:
(1) resolution to a specific OS package and version,
and (2) resolution to an upstream project and version.

3.3.1
Resolution of OS Package

Prior work
[
82
]
resolves
the provenance of vendored libraries
by identifying their upstream project versions.
Vendored libraries in Python are typically sourced from
OS distribution packages
that apply additional patches on top of
upstream versions to fix bugs and vulnerabilities.
Consequently,
two binaries built from the same
upstream version may differ depending on the OS package revision
(
Challenge 1
, Section
2
).
Contrary to prior work,
our approach resolves the exact OS distribution package
and version from which the binary originates.

Key idea:

Our approach
relies on the following insight:
Vendored libraries included in Python wheels
are copied
verbatim
(as compiled binaries),
from OS distribution packages.
By comparing these vendored libraries against
historical OS package artifacts,
our approach recovers the exact OS package and version
from which a vendored library was sourced.
To do so,
our method performs the following steps:

Step 1: extract libname(
\cdot
):

Given the binary file of a vendored library,
our approach extracts the
base
name of each vendored library
by removing any embedded hash
(see next paragraph)
or version identifiers from its file name.
This normalization step is necessary
because vendored libraries are often renamed during packaging
(e.g., by
auditwheel
,
Section
2
),
although they originate from OS libraries.
Recovering the base name allows us to match
the vendored binary
against candidate OS packages
that provide libraries with similar names.
For example,
the name of

libxml2-3998bec4.so.2.9.1
is normalized to
libxml2.so
.

Step 2: extract hash from name(
\cdot
) and compute hash(
\cdot
):

The next step is to compute a
content-based identifier
for a vendored binary by
deriving an 8-hexadecimal-digit hash.
We distinguish two cases.
If the library is produced
by the
auditwheel
utility
(Section
2
),
we cannot recompute the original library’s full hash
from the contents of vendored binary
because
auditwheel
rewrites ELF metadata
(e.g.,
RPATH
),
thereby modifying the binary contents.
However,

auditwheel
embeds in the file name
the first 8 hexadecimal digits of the SHA-256 hash of the original,
unmodified library
(e.g.,
libxml2-39f609e7.so.2.9.7
).
In this case,
our method extracts this hash prefix from the file name
(e.g.,
39f609e7
).

Otherwise (e.g.,
libcrypto.so.3
),
our approach computes the SHA-256 hash
of the vendored binary’s contents
and retains its first 8 hexadecimal digits.
We discuss the implications of using
a truncated hash in Section
4.1

(“Hash collisions”).

Step 3: query hash DB(
\cdot
):

Using (1) the extracted 8-hexadecimal-digit hash
and (2) the base name of each vendored library
computed from the previous steps,
the next step queries a
hash database
of
OS package-provided shared libraries.
This database contains entries for shared libraries
shipped in historical versions of major OS distributions
(e.g., Debian, Fedora, Ubuntu).
We defer the implementation details of how this database
is constructed to Appendix
A
.
Each database entry corresponds to
a specific shared library instance
and records (1) the OS package name and version that provide it,
(2) the base name of the shared library,
and (3) the first 8 hexadecimal digits of the SHA-256 hash
of its binary contents.
For example,
an entry may indicate that
the library
libxml2.so

(hash prefix
3998bec4
) is provided by
the Red Hat package
libxml2

version 2.9.1-6.el7_9.6

By matching both the base name
and the hash of a vendored binary
against this database,
we find the specific OS package
and version from
which the vendored binary comes.

Example:

Consider the vendored library

libxml2-3998bec4.so.2.9.1

shown in Figure
5
.
Its base name is
libxml2.so
,
and the extracted hash is
3998bec4
.
Querying the hash database with these values reveals
that the library originates
from the Red Hat package
libxml2
,
version 2.9.1-6.el7_9.6
(Figure
6
).

3.3.2
Resolution of Upstream Project

Python packages may bundle vendored libraries
built through custom build processes,
rather than directly copying binaries
from OS distribution packages
(
Challenge 2
, Section
2
).
In such cases,
although the vendored library may share
the same base name as a library provided by an OS package,
differences in the binary contents lead to hash mismatches,
causing queries to the hash database to return
empty results.

Key idea:

To handle the cases where our hash-based resolution fails
(Section
3.3.1
),
our approach determines the provenance of vendored libraries
by exploiting three practical observations:

•

Insight 1 (custom builds vs. OS packages):

If a vendored library’s base name matches
that of a library distributed by an OS package,
but its hash does not match any known OS package version,
then it is likely that the vendored library is built
from upstream source code,
rather than originating from the corresponding OS distribution package.

•

Insight 2 (machine-readable OS package metadata)
.
OS distribution packages,
such as those from Debian and Red Hat,
include machine-readable metadata
that specifies the upstream project
from which the package is derived
[
2
,
3
]
.
For example,
Debian packages (
.deb
files) include
a copyright specification
that contains a
Source
field pointing to
the upstream project
(e.g., a URL to the project’s source code repository).
For Red Hat packages
(
.rpm
files),
the corresponding metadata file with information about
the upstream project is called
spec
.

•

Insight 3 (embedded version information of upstream project):

Shared libraries often embed
version information in their binaries
(e.g., as string or integer constants in the
.rodata
segment),
which may be exposed via command-line options
(e.g.,
--version
)
or library APIs
(e.g.,
get_version()
).
Notably,
this version reflects the upstream project,

not
an OS package version.

Based on these insights,
our approach resolves the provenance
of vendored libraries
that are manually built from source
by locating the upstream project
from which the library originates
and extracting its version information
from the binary using library-specific
dynamic analysis.
The key steps are:

Step 1: resolve upstream project(
\cdot
):

Given the base name of a vendored library
with no matching OS package version,
our approach resolves its upstream project
by first identifying the binary OS package
that ships the library
(e.g., using
apt search
,

dnf provides
,
or similar package manager queries).
It then retrieves the corresponding source package
for that binary package and
examines its machine-readable metadata to extract
the upstream project information
(
Insight 2
).

Step 2: resolve upstream project version(
\cdot
):

To extract the version of the upstream project
from which a vendored library is built,
our approach performs
library-specific binary analysis
,
based on the base name of the vendored library.
For each supported library,
we develop a small analysis routine
that extracts version information directly from the binary,
either by invoking exported version-reporting symbols
(e.g.,
get_version
, when available) or
by reading global variables that embed version information
(
Insight 3
).

This is based on the fact that
shared libraries typically
(e.g.,
libcrypto.so
)
encode their version information in a consistent,
project-specific format across releases.
Therefore,
these analyses need to be implemented only once per library,
although the same library may appear
across many Python packages and distributions.
Section
4
provides
implementation details for these library-specific analyses.

Example:

In Figure
6
,
consider that the vendored library
libcrypto.so.3
is
manually built from the upstream project’s source code,
causing the hash-based lookup to fail.
Using OS package manager searches,
we determine that this library is provided by
the Red Hat package
openssl-libs

on top of the upstream project
openssl.org
.
We then analyze the binary contents of

libcrypto.so.3

(Appendix
A
,
Figure
8(b)
)
and extract the version information by invoking

OpenSSL_version()
,
determining that the library was built
from OpenSSL version 3.3.0.

At the end of the provenance analysis procedure,
every binary node in the dependency graph
is annotated with its provenance.
This leads to the
enhanced Python dependency tree

as shown in Figure
5
,
where provenance information is highlighted in bold.

3.4
Step 4: Cross-Ecosystem Call Graph

Next,
our approach moves to the construction
of the
cross-ecosystem call graph (XECG)

of the input Python package.
The XECG captures call edges across
the package and all of its Python- and binary-level dependencies.
We build this graph incrementally
by leveraging state-of-the-art call graph generators,
as described next.

Python call graph:

We use a state-of-the-art Python call graph generator
[
69
]

to construct the Python call graph of every individual
Python package in the enhanced dependency tree.
These call graphs are initially disjoint,
but are subsequently stitched together
using well-established stitching techniques
[
40
,
22
]
.
This process yields a unified Python call graph
that represents the entire dependency network
of the application,
but does not yet incorporate binary-level dependencies.

Binary call graph:

We feed each binary into a state-of-the-art
binary call graph generator
[
47
]
to construct its call graph.
As in the Python case,
these binary call graphs are initially disjoint.
We then stitch them together using
the dependency information provided
by the enhanced dependency tree,
resulting in a unified binary call graph.

Merging Python and Binary call graphs:

The final step of our pipeline merges
the Python and binary call graphs
into a single representation.
The merge points are the leaf nodes in the Python call graph
that correspond to Python-visible functions
whose implementations reside in native code.
To identify these transition points,
we use
PyXray

[
4
]
,
which detects the “bridges” between Python functions
and their corresponding native implementations.
Using this bridge information,
we connect those leaf nodes in the Python call graph
that map to a source node in the binary call graph.
This merging process produces
the final cross-ecosystem call graph (XECG)
of the input Python package or application
(Figure
1
).

3.5
Step 5: Reachability Analysis

After constructing the XECG,
the final step of our approach performs
a reachability analysis
[
22
,
4
]
to determine
whether source nodes corresponding to
the client Python package can reach any vulnerable symbols
(i.e., functions) located in native libraries.
These vulnerable symbols are provided as input to our analysis
and are derived based on the provenance information
obtained in the previous step
(Section
3.3
).
Specifically,
for each shared library,
we determined whether its provenance is associated with
any CVE identifier.
In such a case,
we identify the affected functions by parsing CVE descriptions
and inspecting the corresponding fixing commits.
A Python package or application is considered affected
if any vulnerable symbol is reachable in the XECG.

Example:

In Figure
1
,
the vendored library
libxml2-3998bec4.so.2.9.1

shipped with the Python library
pycairo
is resolved,
through our provenance analysis
(Section
3.3
),
to the Red Hat package
libxml2
version
2.9.1-6.el7_9.6
.
This package is affected by a CVE involving
the function
xmlBuildQName
.
According to the XECG in Figure
1
,
this vulnerable symbol is reachable
from the client Python package
scppin
,
and therefore the package is affected by the vulnerability.
Our approach reports all the vulnerable call chains,
from
scppin

to
xmlBuildQName
.

To extract the version of the upstream project

Our analyses generalize prior techniques
based on the Unix

Reachability analysis

requires access to function-level information
and therefore cannot be performed on stripped binaries.
When encountering stripped

we substitute them with unstripped equivalents
before constructing the call graph.

(Section

),
we obtain unstripped versions
using the debugging symbol packages
provided by the distribution
(e.g.,

/

For libraries that resolve to a specific upstream project version
(Section
3.3.2
),
we rebuild the library from source with debug symbols enabled
before constructing XECG.

4.1
Limitations

Exhaustiveness of hash database:

Our current implementation targets
ELF binaries on Linux.
While our approach could be extended to Windows libraries,
such binaries are less common on PyPI.
The effectiveness of our provenance analysis also depends on
the completeness of the hash database.
A fully exhaustive alternative would be to fetch
and analyze complete OS distribution mirrors
containing all historical package versions.
However,
this would require terabytes of storage and substantial processing.
Instead,
we construct the hash database on demand.

Custom repositories:

Another limitation of
PyXSieve
is
that it can currently resolve the provenance of vendored libraries
only when they have a corresponding OS package.
Even when a library is built from upstream source,
our approach relies on OS package metadata to identify
its upstream project.
Vendored libraries may instead originate from projects
that are not packaged in mainstream OS distribution repositories,
or are available only in custom repositories.
Some of these cases could be addressed by
extending the hash database to include
packages beyond the main repositories.

Hash collisions:

Using
auditwheel
’s 32-bit hash
as a library identifier implies
a hash space of

2^{32}
values,
which would make collisions
theoretically unavoidable
when indexing libraries across
thousands of packages and versions.
To mitigate this risk,
hash values are never used in isolation.
After a hash lookup,
we additionally require the base library name
of the matched OS package to exactly match
the queried vendored library name before accepting a result.
In practice,
our system emits a warning whenever two versions of the same
package produce an identical hash.
We observed no such collisions during our evaluation
(Section
5
).

Version information in binaries:

Although it is less common
(we have not encountered such cases in our evaluation),
some binaries may not embed version information.
In such cases,
our implementation can also leverage
existing binary similarity-based
version identification techniques
[
21
]
.

6
Discussion

End-of-Life build environments:

When the OS underlying a build environment reaches End of Life (EOL),
it no longer receives security patches. For example,

manylinux2014
is based on CentOS 7, which reached EOL in
June 2024
[
30
]
. Wheels built in such environments after
the EOL date inherit unpatched vulnerabilities.
Maintainers who knowingly use EOL images for compatibility reasons
should manually patch vendored libraries by building from source or
extracting them from a supported OS. All other
should migrate to a supported
manylinux
variant,
such as
manylinux_2_28
(based on AlmaLinux 8,
EOL 2029
[
79
]
).

Stale packages in pinned build configurations:

Even on supported systems,
vulnerabilities arise when CI workflows
pin
cibuildwheel
versions without updating OS packages
before building.
Each
cibuildwheel
release maps to fixed
container image tags
[
65
]
, and

auditwheel
copies shared libraries from the container into
the wheel at build time
[
57
]
.
Without an explicit update step,
these libraries may contain known vulnerabilities.
A concrete example is
skia-python:138.0
,
which ships a vulnerable
libfreetype

[
46
,
14
]
. Its CI workflow
pins
cibuildwheel@2.21.3

[
71
,
63
]
,
and the build installs
dependencies that transitively require

freetype

[
72
]
.
Because the pre-installed

freetype-2.9.1-9
satisfies RPM version constraints, it is
not upgraded to the patched
freetype-2.9.1-10

release
[
68
]
.
Version pinning itself is a recommended security
practice
[
27
]
; the root cause is the
missing package-update step. To mitigate this, maintainers should
add either a targeted update (e.g.,
yum update freetype
) or
a full
yum update
as a
before-all
command in their

cibuildwheel
configuration
[
65
]
,
accepting a trade-off between strict reproducibility and timely
security patches.
To assess the prevalence of stale
container images
across our dataset of 1,878 packages,
we extract the project URL
from wheel metadata and
analyze the corresponding
source repositories.
Among 1,380 packages
with an analyzable repository,
872 (63.2%) use
cibuildwheel
,
and
654 of those (75.0%)
pin a specific
cibuildwheel
version;
pinned projects lag by a median of 12 releases (286 days) and a mean of 15.3 (398 days),
with the oldest 5% lagging about 44.8 releases or 1,176.8 days.

Unattended libraries built from source:

Some projects compile vendored libraries directly from source rather
than relying on OS packages. This approach offers greater control
over build flags and versions, but shifts responsibility for
tracking security patches entirely to the maintainers. Unlike
OS-packaged libraries, which are updated automatically when the
build environment runs a package upgrade, source-built dependencies
receive updates only when maintainers manually bump versions.
To mitigate this, projects should monitor upstream security
advisories and subscribe to CVE feeds for their vendored libraries.
Alternatively, they could migrate
to an OS-sourced building workflow (e.g., using
manylinux
).

More broadly, all projects shipping vendored
third-party code, regardless of how it is sourced, should establish a
policy for promptly rebuilding and releasing wheels when
vulnerabilities are disclosed.

This is also acknowledged by Python package maintainers.
One of them stated after our disclosure:

“This is a good wake-up call
that wheels need to be recreated more regularly,
even when the actual project hasn’t seen any updates,
because of possible vulnerabilities in vendored dependencies”
.

Support for SBOM generation:

Since September 2025,

auditwheel

(used by 881/1,878 of packages)
provides
the option to generate
SBOMs (Software Bill Of Materials)

binaries copied from
OS packages on the build host
[
64
]
.
This mechanism only covers libraries
copied from OS packages
and
does not capture
libraries built from upstream source.
The absence of other binaries may
therefore create a false sense of completeness.
Finally,
SBOM generation applies only to newly built artifacts
and has no retroactive effect,
leaving vendored vulnerabilities
in older package versions
undetected.

Threats to validity:

Reachability of vulnerable code is a proxy for security risk,
but does not guarantee exploitability,
as a reachable vulnerability
may still require attacker-controlled input
or other preconditions to be exploited.
Testing-based approaches
[
20
]
can be
used to assess exploitability.
Our reachability analysis relies on static call graph construction,
which by design may overestimate reachable vulnerabilities due to infeasible paths,
or miss vulnerabilities due to dynamic language features
and indirect calls
[
75
]
.
Our overall approach is not tied to any specific reachability
analysis method and other approaches (e.g., based on dynamic tracing)
could be directly plugged in our architecture to trade precision with recall.

Although our work focuses on the
Python ecosystem, the main concepts of
our approach apply to other ecosystems
which commonly use native libraries
and do not obfuscate
them when bundling them in packages,
e.g. Node.js.
However,
careful consideration of the
packaging conventions of the
specific ecosystem is required to
achieve practical utility.
Our work
may be directly applicable
to R’s Portable Linux Binary Packages
since their distribution approach
draws inspiration from Python’s

manylinux/auditwheel
workflow
[
53
]
.

7
Related work

The most closely related work to ours
is
Insight

[
82
]
,
which is discussed in detail in Section
5.2
.

Library version Identification:

Two main methods exist for identifying the
version of a given library from a binary.
Either constructing rules to match
string literals in the binary,
or constructing several features
(from source-code or binaries)
and calculating similarity metrics.
Generally, the first, simpler approach
is preferred when version information
is available in the binary.
There are several approaches
that use
string-matching
[
90
]
,
feature-matching
[
8
,
89
,
21
,
86
,
81
]
,
or a combination of these methods

[
24
,
6
]
,
mainly targeting library identification in
Android applications.
In contrast to the Android ecosystem,
where default build tools like R8
[
78
]

and ProGuard
[
29
]

strip identifiers, shrink code, and flatten
package hierarchies, necessitating an
entire line of obfuscation-resilient
detection research,
PyPI’s vendoring pipeline preserves symbol tables,
sonames, and ELF structure largely intact.
This makes heavyweight semantic or graph-based matching
unnecessary in our setting.

In our system, as mentioned before,
we utilize both string-matching
rules and dynamic analysis
(e.g. calling a
get_version

or equivalent function)
to address cases like
freetype

which stores its version as three separate
integers (Figure
7
).
Coincidentally, this library is used as the motivating
example of LibvDiff
[
21
]
to showcase that
version strings are sometimes not present in binaries.
Overall, our results indicate that for the Python
ecosystem, our approach is sufficient.

Patch Identification:

There exists a notable line of work
on the identification of whether or not
a given patch has been applied to a binary.
These approaches are generally
resource-intensive and complex
and are applied in scenarios where
version information is either not
available, or is meaningless.
Much of this work is focused on
Android kernels, with

FIBER

[
87
]
and
PDiff

[
38
]
,
as representative examples of approaches which
extract semantic signatures from fixes
and perform similarity-based matching.

Lares
[
42
]
performs semantic search,
also employing an LLM in several steps of the process,
and is shown to outperform
other similar approaches
[
83
,
84
,
85
]
.
Such approaches, while imprecise,
could be employed by our approach
as a temporary solution in cases
where we do not provide binary
analyses for version extraction.

Cross-language analysis:

Several works exist
on constructing cross-language
graphs between runtime-based programming
languages (Python, Javascript, Java)
and native components
[
4
,
70
,
5
]
.
To the best of our knowledge,
these tools have only been used to
investigate native extensions,
i.e. native code that is part of the application,
and not third-party native code as we do.
In our implementation, we employ
PyXray

[
4
]

for cross-language analysis.

8
Conclusion

Modern software increasingly relies
on cross-ecosystem dependencies.
The Python ecosystem exemplifies
this trend through its pervasive
use of vendored native libraries.
Our work demonstrates that
accurate vulnerability assessment
in such settings requires reasoning
about provenance,
i.e.,
not just
what version of a library is present,
but where it came from
and what patches it includes.

Our findings have immediate implications.
Package maintainers must recognize
that vendored dependencies
require active security maintenance,
not passive inheritance
from build environments.
Security tool developers must
move beyond version-string
matching to account for backported
patches and vendored copies.
The broader lesson extends beyond Python:
as ecosystems increasingly interoperate,
security analysis must effectively bridge
their boundaries.

Appendix A
Implementation Details and Discussion

We have implemented our approach
as a command-line tool called
PyXSieve

in roughly 15K lines of Python code.

PyXSieve
takes as input a Python wheel
along with a set of vulnerable symbols
and vulnerable package/upstream project versions,
and implements all the steps described in Section
3
.
The input wheels are obtained either directly
from PyPI via the
pip download
command,
when the target package is available there.
Otherwise,
they are locally generated for Python applications
not hosted on PyPI by building a wheel from
the application’s setup configuration
(e.g., using
pip install .

or
python setup.py
).
We next discuss key implementation details
and the limitations of
PyXSieve
.

PyXSieve
employs PyCG
[
69
]

for building the unified Python call graph,
and Ghidra
[
47
]
for the binary one.
Other call graph generators could be used with minimal changes,
as this choice is an implementation detail.

Library-specific analyses for version extraction:

To extract the version of the upstream project
from which a vendored library originates,
our approach employs library-specific binary analyses
that dynamically retrieve version information
(Section
3.3.2
).
Our analyses generalize prior techniques
based on the Unix
strings
utility
[
6
]
,
which extract ASCII substrings from binaries
and match version patterns,
but fail when version information is encoded
in non-string formats.

Figure

shows
our analysis for extracting version information
from the
libfreetype.so
library.
The analysis loads the library
(lines 1) and invokes the function
FT_Library_Version
,
which populates integer variables representing
the major,
minor,
and patch components of the version
(lines 8–9).
While this version information is not recoverable via string matching,
it is still accessible through the library’s API.

For our evaluation
(Section
5
)
we have implemented such analyses
for 50 widely used libraries.
Each analysis is lightweight,
typically requiring only 10–20 lines of code,
and additional analyses can be added on demand.
Figure

presents
the corresponding analysis for
libcrypto.so
.

Stripped binaries:

Reachability analysis
(Section
3.5
)
requires access to function-level information
and therefore cannot be performed on stripped binaries.
When encountering stripped
but potentially vulnerable shared libraries,
we substitute them with unstripped equivalents
before constructing the call graph.
For libraries originating from OS distribution packages
(Section
3.3.1
),
we obtain unstripped versions
using the debugging symbol packages
provided by the distribution
(e.g.,
*-dbg
/
*-dbgsym
packages in Debian-based systems).
For libraries that resolve to a specific upstream project version
(Section
3.3.2
),
we rebuild the library from source with debug symbols enabled
before constructing XECG.

A.1
Limitations

Exhaustiveness of hash database:

Our current implementation targets
ELF binaries on Linux.
While our approach could be extended to Windows libraries,
such binaries are less common on PyPI.
The effectiveness of our provenance analysis also depends on
the completeness of the hash database.
A fully exhaustive alternative would be to fetch
and analyze complete OS distribution mirrors
containing all historical package versions.
However,
this would require terabytes of storage and substantial processing.
Instead,
we construct the hash database on demand
(Appendix
A
).
The database construction strategy is an implementation detail
and can be replaced by alternative mechanisms in the future.

Custom repositories:

Another limitation of
PyXSieve
is
that it can currently resolve the provenance of vendored libraries
only when they have a corresponding OS package.
Even when a library is built from upstream source,
our approach relies on OS package metadata to identify
its upstream project.
Vendored libraries may instead originate from projects
that are not packaged in mainstream OS distribution repositories,
or are available only in custom repositories.
Some of these cases could be addressed by
extending the hash database to include
packages beyond the main repositories.

Hash collisions:

Using a 32-bit hash as a library identifier implies
a hash space of

2^{32}
values,
making collisions theoretically unavoidable
when indexing libraries across
thousands of packages and versions.
To mitigate this risk,
hash values are never used in isolation.
After a hash lookup,
we additionally require the base library name
of the matched OS package to exactly match
the queried vendored library name before accepting a result.
This is why our database queries
use both the hash and the base library name
(Figure
6
).

As a worst-case example in our dataset,

libxml2.so
appears in 398 different versions
(243 Debian, 145 RedHat)
of the
libxml2
package.
Under the birthday bound, for
n=398
samples the probability of at least one
collision is

p\approx 1-e^{-\frac{n(n-1)}{2\cdot 2^{32}}}\approx 1.84\times 10^{-5}.

In practice, our system emits a warning whenever two versions of the same
package produce an identical hash.
We observed no such collisions during our evaluation
(Section
5
).

Version information in binaries:

Although it is less common
(we have not encountered such cases in our evaluation),
some binaries may not embed version information.
In such cases,
our implementation can also leverage
existing binary similarity-based
version identification techniques
[
21
]
.
