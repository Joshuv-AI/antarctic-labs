SciDER: Scientific Data-centric End-to-end Researcher
Ke Lin, Yilin Lu, Shreyas Bhat, Xuehang Guo, Junier Oliva, Qingyun Wang

Abstract
Automated scientific discovery with large language models is transforming the research lifecycle from ideation to experimentation, yet existing agents struggle to autonomously process raw data collected from scientific experiments. We introduce SciDER, a data-centric end-to-end system that automates the research lifecycle. Unlike traditional frameworks, our specialized agents collaboratively parse and analyze raw scientific data, generate hypotheses and experimental designs grounded in specific data characteristics, and write and execute corresponding code. Evaluation on three benchmarks shows SciDER excels in specialized data-driven scientific discovery and outperforms general-purpose agents and state-of-the-art models through its self-evolving memory and critic-led feedback loop. Distributed as a modular Python package, we also provide easy-to-use PyPI packages with a lightweight web interface to accelerate autonomous, data-driven research and aim to be accessible to all researchers and developers.

System Architecture and Workflow

SciDER is designed as a data-centric end-to-end system that flexibly automates the scientific research lifecycle.
The system integrates a research framework comprising ideation, data analysis, experimentation, and iterative improvement. It supports flexible inputs such as text, raw data, code, and prior papers and codebases.
SciDER also offers a lightweight web interface where researchers can upload their data and research topics, allowing the system to automatically create a closed-loop research cycle to propose and verify new ideas.
The automated research task can be formalized as follows: given datasets
\mathcal{D}
and a research query
\mathcal{Q}
, the system generates ideas
\mathcal{I}
(i.e., hypothesis and experiment outlines), an analysis report
\mathcal{R}
of data, an experiment codebase
\mathcal{C}
, and results
\mathcal{T}
.

3.1
LLM-based Agents

Ideation:
\mathcal{I}\leftarrow\mathrm{Ideation}(\mathcal{D},\mathcal{Q})
.

SciDER integrated an ideation agent for automatic literature review, idea generation, and novelty assessment. The system allows users to propose an initial thought
\mathcal{Q}
as a programmable task given
\mathcal{D}
. The ideation agent automatically synthesizes insights from the scientific literature and retrieves related online datasets to generate proposals tailored to the specific experimental context. Each idea proposed by the ideation agent contains (1) a hypothesis about the dataset, (2) an experiment outline, and (3) a comparative analysis with existing work.

Specifically, the ideation agent generates keywords from the input, retrieves and analyzes relevant literature from
arXiv

Cornell University 2024

Semantic Scholar

Allen Institute for AI 2024

PubMed

National Center for Biotechnology Information 2024

An LLM-as-Judge evaluates these proposals for novelty across four categories:
Uniqueness

,
Gap Addresses
, and
Impact
with a total score of 10 (App.
A.2
).
A revision report will be generated for self-refinement
Madaan et al. 2023
to determine whether the idea proposal
\mathcal{I}
will be forwarded to the next agent.

Data Analysis:
\mathcal{R}\leftarrow\mathrm{Data}(\mathcal{D},\mathcal{Q},\mathcal{I})
.

SciDER allows researchers to upload experimental data from various scientific domains for automated analysis and the generation of well-organized data reports, serving as input to the
experiment agent
.
Although the pipeline may automatically preprocess and clean the data as
\mathcal{D}^{\prime}
, we refer to the dataset as
\mathcal{D}
for simplicity.
This stage is the core of SciDER’s data-centric paradigm, in which raw data is transformed into structured knowledge that guides subsequent research.
The interface also accepts an optional user instruction to provide additional information or guide data reading and parsing.
The agent iterates over the dataset’s folder structure, then uses tools to read and parse various file formats.
Textual data is organized in formats like Parquet, JSON, and CSV, while custom readers are developed for non-standard image formats.
The final data report
\mathcal{R}
assesses data from multiple perspectives: structure, quality, semantics, and dependency (App.
A.3
).

Experimentation.

The experimentation stage includes code generation and execution. Given the idea proposal
\mathcal{I}
, the coding agent generates executable scripts
\mathcal{C}
tailored to the data structures and dependencies identified in the data-centric analysis report
\mathcal{R}
, thereby ensuring high success rates for domain-specific tasks. The entire codebase is then transferred to the execution agent for full execution.

•

Coding Phase:

\mathcal{C}\leftarrow\mathrm{Coding}(\mathcal{D},\mathcal{Q},\mathcal{I},\mathcal{R})
.
The coding agent leverages external frameworks (i.e.,
OpenHands
from
Wang et al. 2025
and
Claude Code
from
Anthropic 2025

•

Execution Phase:

\mathcal{T}\leftarrow\mathrm{Exec}(\mathcal{D},\mathcal{C})
.
Once the coding workspace is provided with executable scripts and properly configured, the execution agent begins execution and periodically monitors progress.
Typically, agents wait for executions to complete. However, if errors occur or the execution output indicates a potential failure (e.g., a timeout, consistently high loss, failed unit tests, or a frozen screen), the execution agent terminates the running process and provides feedback to the coding agent.

Critics & Feedback.

After each stage of the data analysis and experimentation, a critic agent will judge the performance of each stage and provide feedback for iterative reflection and self-refinement.
The critic agent assesses the accuracy, completeness, and potential biases of the preceding process, identifying information gaps and logical inconsistencies (App.
A.4
). The agent then proposes improvements or alternative solutions to achieve a balanced and comprehensive final revision.

3.2
Self-evolving Memory

To improve test-time performance, SciDER integrates a self-evolving memory mechanism adapted from ReasoningBank
Ouyang et al. 2026
for continuous test-time learning and memorization.
Unlike ReasoningBank, SciDER further organizes memory into short-term and long-term categories and categorizes long-term memory as task- and project-specific (Fig.
2
).
Project-specific memory dynamically captures ideation and experimental results, while task-specific memory stores general guidance for similar tasks within a domain.
As the system runs, the memory module stores reasoning in a local memory bank. For new chat sessions, relevant memory chunks are retrieved (e.g., via a semantic vector or keyword search) and inserted into the context as background knowledge.

Case Study

We present a case study demonstrating the usefulness and effectiveness of SciDER and its potential to automate the traditional data science workflow in the natural sciences domain. In this case study, an astrophysicist with little machine learning experience can use SciDER to develop a fully functional ML pipeline for astrophysics tasks.
The astrophysicist aims to use the Kepler Exoplanet Dataset
Akeson et al. 2013
to determine whether a candidate signal is an exoplanet from noisy time-series data. The astrophysicist first selects the “Full Workflow” and inputs a query (Fig.

After finishing the configuration, the astrophysicist clicks on “Run the full workflow” to launch the workflow. After SciDER completed the final steps, it generated a report. SciDER conducted a comparative experiment among three distinct models with feature engineering and achieved an

Through the case study, we demonstrate how domain experts can use SciDER to build high-performance machine learning pipelines for domain-specific tasks with minimal interventions and auditing the working process SciDER with minimal effort. 5
Conclusion

In this work, we present SciDER, a useful end-to-end system that automates the scientific research lifecycle. By combining ideation, data analysis, and iterative experimentation with a self-evolving memory mechanism, SciDER bridges the gap between abstract scientific reasoning, data-centric insights, and executable code synthesis.
SciDER outperforms earlier efforts on idea-generation judgment, general machine-learning benchmarks, and multidisciplinary scientific coding tasks.
We provide a lightweight web interface and distribute SciDER as a modular Python package to ensure accessibility, helping researchers to initiate a complete, closed-loop research cycle with a single click.
We believe that SciDER will reduce the technical barriers for researchers, ultimately improving research effectiveness and promoting the broader adoption of autonomous research agents.

Ethical Considerations

Although SciDER is intended to automate and expedite the scientific research lifecycle, its implementation entails ethical obligations.
The system is prone to hallucinations or logical inconsistencies because it depends on LLMs for core reasoning and code synthesis. This could lead to incorrect hypotheses, biased experiments, and hallucinated results.
Data privacy is also at risk when processing tasks rely on external LLM APIs; misconfigurations or operations may inadvertently upload private or sensitive experimental data to unaffiliated platforms.
In addition to preventing potential copyright violations, automated collection of literature and data from online repositories must be conducted carefully.
Instead of completely replacing human expertise, SciDER should be used as a collaborative assistant to reduce these risks.
To ensure scientific integrity and legal compliance, it is recommended that researchers manually validate all AI-generated reports, code, and findings.

A.1
Human Evaluation

To evaluate the practical utility of SciDER as an autonomous research assistant, we define a specialized “helpfulness” rubric. This metric assesses how effectively the system reduces the human researcher’s workload across the research lifecycle, from data parsing to experimental execution.

•

Score 1 — Very Poor (Obstacle):
The system fails to provide any useful output. It either generates incoherent research ideas, fails to parse the provided raw data, or produces non-executable code. Human intervention is required to restart the entire process from scratch.

•

Score 2 — Poor (Low Utility):
The system provides generic or shallow insights that do not reflect the specific characteristics of the experimental data. Despite generating some output, the design or code requires significant manual correction to function.

•

Score 3 — Average (Moderate Assistance):
The system successfully automates routine tasks, such as basic data profiling and literature keyword searching. The experimental plan is feasible but lacks depth or novelty. It functions as a baseline assistant but requires moderate human guidance and revision.

•

Score 4 — Good (Significant Assistance):
The system demonstrates a clear understanding of the data-centric paradigm. It generates well-structured data reports and executable scripts with only minor gaps. The critic agent provides relevant feedback that noticeably improves the research quality. It effectively saves the researcher time in the exploration phase.

•

Score 5 — Excellent (Autonomous Collaborator):
The system acts as a high-level research collaborator. It provides deep scientific insights grounded in the raw data, identifies non-obvious patterns, and generates high-fidelity code/reports that are ready for immediate use. The self-evolving memory effectively utilizes project-specific context to refine subsequent steps without human input.

A.2
Ideation Criteria

The ideation evaluates the idea proposals based on the following criteria:

•

Uniqueness
: This criterion measures the degree of differentiation from existing work, assigned a score of 0–3 points, ranging from simple replication to the introduction of entirely new concepts.

•

Innovation
: This assesses the originality of the methodology or theoretical framework, with a score of 0–3 reflecting the transition from standard methods to the proposal of novel approaches.

•

Gap Addressing
: This evaluates how effectively the proposal tackles identified research gaps or limitations, with a score of 0–2 based on the significance of the gap being filled.

•

Impact
: This quantifies the potential contribution of the research to the field, ranging from 0–2 points from minimal expected contribution to high-impact potential.

A.3
Data Analysis Criteria

The data analysis agent assesses the data by:

•

Structure
: Evaluates file formats, data types, and organizational patterns like schemas and encodings to define the data’s technical framework.

•

Quality
: Analyzes data integrity by identifying missing values, outliers, and inconsistencies through sample inspection and summaries.

•

Semantics
: Interprets the domain-specific meaning and logical significance of data fields to ensure the information is correctly understood.

•

Dependency
: Maps relationships between data entities, such as foreign keys and file links, to establish cross-references and the required processing sequence.

A.4
Critic Criteria

We present the rules for the critic agent to evaluate and provide feedback for each sub-agent:

•

Accuracy:
Verify that all factual claims, data points, and references are precise and verified against reliable sources.

•

Completeness:
Ensure the response addresses every component of the prompt and satisfies all user requirements without omission.

•

Bias:
Identify and eliminate any subjective leanings, cultural prejudices, or non-neutral viewpoints in the content.

•

Information Gap:
Specify any missing context, depth, or technical details required for a comprehensive understanding.

•

Misinformation:
Detect any logical hallucinations, fabricated facts, or misleading statements.

•

Suggested Improvement:
Provide clear, actionable instructions to correct the identified flaws and enhance the output quality.

Appendix C
Limitations

While SciDER demonstrates capabilities in automating the research lifecycle, there are several limitations that we aim to address in future work.

First, the current system lacks a module for the automated generation of scientific papers. This design choice stems from our primary focus on the more critical challenges of data-centric research: autonomous data analysis, experimental planning, and the synthesis of executable code. Given that prior work has established the feasibility of automated manuscript writing, we consider the perfection of the experimental lifecycle to be of higher priority for a data-centric agent. We intend to include paper-writing functionality in subsequent iterations of the system.

Second, SciDER is currently dependent on external LLM APIs for its core reasoning and experimentation tasks. This reliance introduces potential constraints regarding operational costs, API availability, and data privacy when processing sensitive or proprietary experimental datasets.
