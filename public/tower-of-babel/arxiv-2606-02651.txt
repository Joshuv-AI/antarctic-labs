From Rocq to Metal: A Pipeline for Formally Verified Microcontroller Firmware
Valentin Bergeron, Karolina Gorna

Abstract
Enforcing invariants in safety-critical firmware is increasingly urgent as generated code becomes widespread, but standard extraction targets for proof assistants require runtimes too large for many embedded devices. We present a pipeline for running formally verified Rocq firmware logic on Cortex-M microcontrollers. The pipeline extracts Gallina to Scheme, compiles it with Encore! , a bare-metal Continuation-Passing Style (CPS) bytecode virtual machine, and embeds the result in no_std Rust firmware. We structure applications as pure state-transition functions, so the business logic is proved in Rocq while the event/effect boundary, host callbacks, compiler, and VM remain explicit trusted components: no proof yet relates bytecode execution to Gallina semantics. On eight firmware workloads, from APDU parsing to a credential store, Encore! runs unmodified Rocq-extracted code within the 50 KiB RAM budget of ST33-class targets on every input size, where CertiRocq’s generated code runs out of memory on the larger ones, at the price of up to 10 × \times more executed instructions than CertiRocq; a transaction-signing application is validated on physical Ledger Flex hardware.

Introduction

Generated code is changing how software is written, including firmware.
For safety-critical devices, lower code-generation cost increases the amount of code that must be reviewed, while the required assurance level remains high.
Formal verification has already demonstrated its value for operating-system kernels, and similar rigor is increasingly sought for firmware.
Formal specifications offer a scalable response: generated implementations can be checked against theorem statements, and proof obligations become part of the development interface.

However, the hardware constraints of embedded firmware prevent straightforward use of standard specification language extraction.
The runtimes required to execute extracted code exceed the resource budget of most microcontrollers.
Standard practice is therefore to translate specifications into the host language, automate that translation, or use host-language extensions, weakening the connection to the proof assistant.

We first present an architecture for structuring firmware so its core is fully verifiable, illustrated on a concrete transaction-signing application.
Next, we introduce

We then survey the existing extraction paths from theorem provers to embedded targets, and characterize why they fall short on this class of hardware.
Finally, we evaluate the pipeline on eight firmware workloads and outline remaining steps toward extending trust further up the toolchain.

This work makes three contributions:

•

We show that code extracted from Rocq can run on Cortex-M microcontrollers, by choosing Scheme as the extraction target and building a purpose-built bare-metal runtime.

•

We present
Encore!
, a
no_std

•

We introduce a firmware architecture structured as a pure state-transition function, making the business-logic core fully provable in Rocq while confining the unverified trusted computing base (TCB) to the event/effect boundary, which grows with the hardware interface rather than with application logic.

2
An Architecture for Verified Firmware

This section answers
what
to run on the MCU and how to structure it so correctness is fully provable in Rocq.

2.1
The State Transition Model

The model below is not imported from an existing specification: we define it for this work.
Its shape follows the well-established reactive state-machine pattern (an application reduced to a transition over an explicit state driven by input events), which we instantiate for firmware.
We choose this formulation because it maximizes the area that can be proven: modeling the application as a pure state transition function, effectively treating the whole embedded device as a state machine, confines all impurity to the event and effect boundary and leaves the transition itself as pure Gallina we can reason about directly.

Before diving into the modeling details, we assume that a Scheme VM is deployed as part of what we call a Formal Software Development Kit (FSDK) that bridges the virtual machine and the host device.
The FSDK contains both host code (it
is
the real firmware that gets deployed) and Rocq code to provide the necessary bridge abstractions.

With this in mind, we define the state transition function as:

\texttt{step}:\texttt{State}\times\texttt{Event}\rightarrow\texttt{State}\times\texttt{list}\ \texttt{Effect}.

Given the types:

State

represents the application state. This will depend on what problem the application is solving, independently from the FSDK.

Event

is an incoming event from the device. Device events are linked to the underlying hardware and can be network packets, user interface signals such as pressed buttons or specific touch screen positions, etc.

Effect

is the description of an effectful computation that needs to be interpreted to be realized. A critical part of the FSDK is then to interpret the effects to perform them.

At run time, the FSDK loops: it polls an event
E_{i}
, computes
(S_{i+1},F_{i})=\texttt{step}(S_{i},E_{i})
, performs the effects
F_{i}
, and repeats with the new state.

This model applies two key functional programming principles, copying instead of mutating and describing effects rather than performing them directly, to firmware code, effectively maximizing the provable business logic part.

The remaining parts, the
Event poller
and the
Effect interpreter
, form the TCB.
Their size is independent of firmware complexity unless new hardware operations and capabilities are added.
The verified core grows with the application; the unverified boundary grows only with the hardware interface.

Moreover, in a VM-based deployment the application logic can be fully specified in the VM input code, allowing the same carefully reviewed base firmware to host custom, verified business logic, which is a particularly powerful combination for safety-critical devices.

2.2
Admitted Axioms and the Trust Chain

Some operations are observationally pure from Rocq’s perspective but would be impractical to implement fully from a business point of view.
Examples include hash functions, polynomial operations (CRC), and more generally any finite field operation involved in cryptographic algorithms.

Rather than relying on an Effect/Event pair with little added value, we choose to admit them in Rocq as axioms and provide them as host callbacks before the application run loop starts.
VM primitive operations, such as the byte-string operations
bytes_len
and
bytes_concat
, are treated the same way: Rocq parameters with axiomatized equations, mapped to the VM’s implementations by extraction directives.
This bridge is manual: each host primitive is declared in Rocq as an axiom, with its behavior stated as a further axiom when a proof needs it, and linked to its Rust callback by an extraction directive, which keeps the trusted axioms few and auditable at the cost of keeping both sides in sync by hand.

The FSDK can also fix what every application must prove.
A typeclass over
State
,
Event
, and
step
can request a baseline set of theorems, for example that no signing effect is emitted outside an approved state; an application is then accepted only with an instance of that class, and reviewing a firmware application amounts to reviewing the statements of the class, which the Rocq kernel checks for every instance.

2.3
Trust Assumptions

The verified part of the system is the Rocq model of the application logic and its stated properties.
The trusted computing base includes the Rocq kernel and extraction mechanism, the Scheme frontend, the
Encore!
compiler and VM, the Rust compiler, host callbacks implementing admitted axioms, and the event poller/effect interpreter supplied by the device firmware.
This boundary is deliberate: application growth extends the proved
step
function and its lemmas, whereas the unverified boundary changes only when new hardware actions, externs, or runtime primitives are added.
The current work therefore establishes verified firmware logic running on bare metal; Sect.
3.4
states a compiler correctness conjecture whose proof, together with a proof that the Rust interpreter implements its abstract machine, would remove the compiler and VM from this list; both are future work, discussed in Sect.
6
.

3
The
Encore!
VM and Compiler

Encore!
is a Scheme runtime built for the code Rocq extraction emits.
That code is heavily curried and close to CPS form, which suits a register-based virtual machine: the CPS rewrite eliminates the call stack
semantically
and the register VM eliminates it
physically
, so there is no hidden control flow and no frame management at run time, and every intermediate value is named, which makes register allocation direct.
Extracted code relies on a
macros_extr.scm
file of macros for curried definition, application, and constructor matching; rather than support Scheme macros in general,
Encore!
implements these as core primitives.
Its only addition to Scheme is the
(extern (slot
N
) …)
form, which declares a function provided by the host: Rocq poses it as an axiom, and the host registers it in slot
N
before running the program.
We use a dedicated form because standard Scheme has no portable notion of a host-provided function, and the FFI forms of full implementations presuppose a hosted C runtime and dynamic loading.

3.2
Compiler Pipeline

The parser recognizes the extraction macros and produces a direct-style IR.
A first pass uncurries saturated applications, which are frequent in extracted code, saving the allocation of intermediate closures.
Variables are then replaced by de Bruijn indices, and the program is converted to CPS.
The CPS IR is optimized by iterating shrinking and growth-enabling passes to a fixed point, in the style of Appel
[
2
]
, before register allocation, a peephole pass, and bytecode emission.

3.3
Host–VM Interface

Encore!
is a library embedded in a Rust application that keeps control of the execution context, memory budget, and I/O.
The VM exposes two entry points: calling a global or a closure handle with typed arguments, and registering typed host callbacks invoked by EXTERN.
Values crossing the boundary are converted by the procedural macros
#[derive(ValueEncode)]
and
#[derive(ValueDecode)]
, whose
#[ctor(tag)]
annotations use constructor tags from a
bindings.rs
file that
build.rs
generates together with the bytecode, so host code and bytecode cannot disagree on tags.

VmList<T>
and
VmBytes
give bounded, allocation-free access to lists and byte strings in the VM heap.

4
Related Work

Our targets are ST33 secure microcontrollers (Cortex-M35P): the ST33K1M5 has 64 KiB of RAM and 1.5 MiB of flash, and the tighter ST33J2M0, 50 KiB of RAM, which sets the binding constraint.
Applications on this class of device ship with no runtime and cannot rely on libc, libm, or the Rust standard library, which excludes many proof-to-code paths.

Lean 4
[
5
]
has mature native code generation, but its runtime assumes C++ library support, reference counting, tasks, and hosted I/O, and no port targets bare-metal devices of this size.
Rocq extraction to OCaml
[
12
]
is mature, but the OCaml runtime requires a generational GC, libc/libm support, and native-code assumptions mismatched with Cortex-M object formats; OMicroB
[
18
]
, a bytecode VM for microcontrollers, supports AVR and PIC32 but not the full Thumb-2 of our targets.

CertiRocq (formerly CertiCoq)
[
1
]
is the most principled Rocq compilation path: it compiles Gallina to Clight through a largely verified compiler chain.
Its runtime does not carry over unchanged to our targets.
The generated Clight allocates inductive values, and correctness is stated against the heap of its own collector; on a microcontroller, the collector must run over a static arena, outside that proof.
CertiRocq also ignores Rocq’s extraction directives: mapping
nat
to machine integers requires registering primitives, applied by an erasure pass that is itself trusted, and its code is in direct style, so deep recursion consumes the C stack (Sect.
5
).

Rocq also supports extraction to Scheme
[
12
]
.
Although less mature than OCaml extraction, Scheme has compact semantics and no mandatory hosted runtime.
Small Scheme systems such as Ribbit
[
19
]
show that complete implementations fit microcontroller budgets, but none accepts the code Rocq extracts: Ribbit, for instance, does not support the quasiquote that extraction emits to build constructors.

Encore!
is a runtime built for that code.

Verified compilers such as CompCert
[
10
]
and CakeML
[
9
]
carry a machine-checked proof that the generated code refines its source, and Œuf
[
13
]
applies this idea to a subset of Gallina to shrink the extraction TCB.
Another line of work obtains verified low-level code by restricting how programs are written: Low*
[
16
]
generates C without garbage collection from a first-order subset, and Bedrock2
[
6
]
verifies a low-level language end-to-end on a small RISC-V embedded system.
These approaches give stronger guarantees than ours, but either constrain the source to first-order code without garbage collection or assume a hosted runtime.

Encore!
is not a new verification methodology: it is a practical systems pipeline that runs ordinary higher-order, allocating Gallina, produced by the standard extraction mechanism, on Cortex-M hardware, with the remaining compiler/VM gap made explicit in Sect.
2.3
.

5
Evaluation

We evaluate the pipeline against four research questions.

RQ1 (memory):
which workloads fit a budget of 50 KiB of RAM (the ST33J2M0’s) and 256 KiB of flash, for each toolchain?

RQ2 (cost):
what does
Encore!
cost in executed instructions and flash, against native Rust and against CertiRocq?

RQ3 (predictability):
is the latency added by the garbage collector bounded?

RQ4 (proof effort):
what is proved, with how much proof, and how much unverified code remains?

5.1
Methodology

Variants.

E
is the pipeline of this paper (
Encore!
0.1.6, CPS optimizer on).

C
compiles the same Gallina with CertiRocq 0.9.1 to Clight and
gcc -Os
, with its generational collector running over a static arena and
nat
mapped to machine integers, as for
Encore!
.

R
is idiomatic
no_std
Rust without an allocator, written without looking at the Gallina: it is the performance ceiling and the output oracle, as every E and C run must reproduce R’s output hash.
The three variants share the Rust driver, the frozen input vectors, and the output hashing; only the logic differs.

Workloads.

Table
2
describes the eight workloads and the property proved for each.
We chose them because a bug in them is a security hole or a field failure on a hardware wallet, and because a precise property can be proved about them.
Each follows the
step
model of Sect.
2
and is parameterized by an input size
N
.
W8 is deliberately unfavorable to
Encore!
: a tight bitwise loop that allocates almost nothing, leaving no allocation to amortize interpretation.

Platform and metrics.

Linker scripts impose the ST33J2M0 budget, so a program that does not fit fails to link.
Within it, E uses a 32 KiB heap (40 KiB for W6) and C a 20 KiB arena, the rest of the RAM holding its C stack.
We run on QEMU 8.2.2, emulating a Cortex-M33 (AN505), the ARMv8-M core closest to the Cortex-M35P; instruction counts on a Cortex-M3 (LM3S6965) differ by at most 1.3%.
The metric for speed is the number of instructions executed per run, counted exactly by tracing QEMU between two markers, minus the cost of an empty region.
We also report the flash size of the linked image, the smallest E heap that completes every case (by binary search), and, in a separate build since its counters perturb the instruction counts, the number, share, and longest pause of collections.
The other tools are Rust 1.88,
arm-none-eabi-gcc
13.2.1, and Rocq 9.1.1.

RQ1: memory.

E completes all 31 cases within the budget, with minimum heaps from 0.5 to 32.25 KiB.
C completes 17 of the 27 cases of W1–W7.
Its generated code is in direct style and recurses on the C stack once per input element or event.
The larger inputs therefore exhaust the arena or the stack.
CertiRocq’s CPS mode would move this recursion to the heap, as in
Encore!
.
In version 0.9.1, however, it cannot be combined with the mapping of
nat
to machine integers.

RQ2: cost.

Interpretation is expensive.
At C’s largest
N
, E executes 4.8–10
\times
more instructions than C (2.3–10
\times
over all inputs).
E executes 155–589
\times
more instructions than R, with two exceptions: W7 (34
\times
), where tree manipulation also dominates R, and W8 (1,849
\times
), by design.
C itself executes 4–68
\times
more instructions than R.
The CPS optimizer divides E’s instruction count by 2.3–4.2 and halves its bytecode.
All images are far below the 256 KiB flash budget.
E adds a constant 21–23 KiB over R for the VM and its dependencies.
Its bytecode (1.9–6.5 KiB) is two to three times smaller than R’s native code for the policy workloads W3–W5.
The VM thus pays for itself in flash only for programs several times larger than ours.

RQ3: predictability.

The collector runs only when the heap is full, so a pause is bounded by the heap size, not by the input.
At the largest
N
, collections take 3–22% of the execution, and the longest pause is 49–309 thousand instructions.
The counts are deterministic.
Turning them into a latency bound in time requires cycle measurements on hardware, which we have not yet done.

RQ4: proof effort.

Every workload proves its property in 35–313 lines of proof, for 105–243 lines of program and specification, with no admitted lemma (Table
2
).
The unverified Rust that drives E stays at 93–104 lines across workloads.
In contrast, R’s 68–238 lines (logic and driver) carry no proof at all.

Hardware validation.

The workloads above run on QEMU.
The transaction-signing application of Sect.
2
was also validated on physical Ledger Flex hardware: the Rocq-extracted,
Encore!
-compiled firmware parses, displays, and signs data on the device.
Its verified Gallina core (
step
, parser, helpers, and proofs) has about 400 lines, and its unverified Rust layer about 575 lines.

6
Discussion

6.1
Threats to Validity

Instruction counts are not cycles.
The interpreter and native code differ in memory traffic, so the ratios of Table
3
bound the gap only roughly.
The cycle-counter path for physical boards is implemented but not yet validated.
R was written by the authors.
C’s arena is smaller than E’s heap because the C stack shares the RAM budget.
Line counts are ours and approximate.

6.2
Trace Properties

The properties of Sect.
2
constrain a single call to
step
.
Firmware also needs properties over event sequences: ordering constraints, authorization before a sensitive operation, or the absence of forbidden transitions.
The model expresses them by folding
step
over a list of events, which yields the reachable states and the emitted effects.
Safety properties then become invariants proved by induction on the event list, such as “no signing effect without a prior
ApprovedTx
”.
The FSDK typeclass of Sect.
2.2
can require such invariants from every application.
Liveness is out of scope: the device cannot force the host or the user to send an event.

6.3
Verified Optimization Passes

The nine CPS optimization passes are trusted Rust code.
Proving them semantics-preserving, step (ii) of the decomposition of Conjecture
1
, is standard for the shrinking reductions, and the growth-enabling passes (inlining, hoisting, CSE, contification) resemble optimizations verified in Pilsner
[
14
]
.

6.4
Ahead-of-Time Native Compilation

A backend compiling the CPS IR directly to ARMv8-M Thumb-2 is designed but not yet implemented: it pins the most used virtual registers to hardware registers and turns each tail call into a code-table lookup and a
BX
, removing interpreter dispatch.

6.5
Portability

Only the TCB boundary is device-specific: the
step
function, the bytecode, and
encore_vm
(
no_std
, no libc) are architecture-independent, so porting reduces to retargeting the Rust build and reimplementing the event poller, effect interpreter, and host callbacks (Sect.
2.2
).
Any Cortex-M with a Rust target and a few tens of KiB of RAM qualifies, since the runtime adds about 22 KiB of flash and our workloads need at most 32.25 KiB of heap; this includes STM32 parts and ARM-based Arduino boards, but not 8-bit AVR boards, with 2 KiB of RAM and only a tier-3 Rust target.

6.6
Verifying the VM with rocq-of-rust

encore_vm
is
no_std
Rust with minimal
unsafe
and no trait objects in the interpreter loop.
The
rocq-of-rust
tool
[
7
]
translates Rust source to Rocq definitions, enabling correctness proofs of Rust programs inside Rocq.
Applying it to
encore_vm
would close the VM’s gap in the trust chain: the same proof assistant that certifies the firmware logic certifies the runtime executing it.

The central theorem to establish is the agreement of the Rust dispatch loop with the machine of Fig.
3
, the link left outside Conjecture
1
: each step of the interpreter corresponds to a transition of the abstract machine.
Two components present the main proof obligations.
The mark-compact GC requires reasoning about pointer aliasing and preservation of the tag-byte invariant across every collection cycle, since compaction rewrites every live pointer in both the register file and the heap interior.
The ENCORE dispatch opcode must be shown to resolve the callee’s code pointer and to preserve the register-file state prescribed by the calling convention.
The
unsafe
surface is small: unchecked reads of code, whose bounds load-time validation establishes, of registers, in bounds by construction, and of the arena, which relies on the compiler emitting well-typed accesses.

7
Conclusion

We have shown that Rocq-proven firmware logic runs on a Cortex-M35P: extracted to Scheme, compiled by
Encore!
, and deployed on a Ledger Flex hardware wallet.
The verified core remains the source of truth, while the runtime, compiler, host callbacks, and device I/O are explicit trusted components.
On eight security-relevant workloads,
Encore!
fits the memory budget at every input size, whereas CertiRocq, on the seven where it was built, fails on the larger inputs;
Encore!
pays for it in speed, with up to 10
\times
more instructions than CertiRocq’s native code.

The architecture is also designed to scale.
Structuring firmware as a pure state-transition function decouples verification effort from hardware complexity: the verified
step
grows with application logic, while the unverified components grow only with the hardware interface.

Proven application logic runs on bare metal today; closing the trust chain down to the VM and scaling to larger applications remain future work.
