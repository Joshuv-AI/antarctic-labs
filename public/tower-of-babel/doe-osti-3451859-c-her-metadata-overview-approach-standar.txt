Contents C-HER Metadata Overview

The Centralized Health and Exposomic Resource (C-HER) uniﬁes environmental, demographic,
geographic, and health-related data for exposomic research. The source data differ in format,
geographic coverage, time period, resolution, terminology, and documentation. We use a common
metadata framework to describe those differences and to record how each data resource has been
processed, documented, and ingested.
This document relates only to the C-HER metadata framework. It explains the information that is
recorded for each resource, the standards used to organize that information, the conditions for
metadata completeness, and the relationship between metadata and quality review. It is intended
for those who need to understand what C-HER metadata communicates and how it supports ap-
propriate use of the data. It is not an implementation speciﬁcation or procedure. It does not doc-
ument the database schema, source code, deployment conﬁguration, transformation algorithms,
or dataset-speciﬁc QA/QC thresholds. Those materials are maintained separately.

Section 1

Background and Motivation

The external exposome—the totality of environmental inﬂuences on human health across a lifetime—
cannot be studied without large volumes of interoperable, high-quality data. Environmental, de-
mographic, and health datasets are collected by organizations of all kinds, and they often do so
for purposes unrelated to exposure research. Thus, such datasets exist in heterogeneous formats,
contain inconsistent spatial and temporal resolutions, and are accompanied by varying degrees of
documentation. Harmonizing these sources for research use is technically demanding and time-
consuming. C-HER [1] was developed to address those barriers. C-HER is a centralized repository
of curated, analysis-ready exposomic data that include criteria air pollutants, air toxics, land cover,
radiometric measurements, sociodemographic indicators, and other environmental determinants
of health. C-HER resources (see Terms Used in this Document) are organized for use across mul-
tiple projects and are not all represented at the same geographic resolution. Many resources are
prepared for analysis on the H3 [2] grid. Other resources, including some stakeholder-requested
products, are organized by administrative boundaries such as county, state, or census tract. The
relevant spatial extent and spatial resolution are recorded in each resource’s metadata.
Reliable metadata are required to transform a collection of ﬁles into a usable scientiﬁc resource.
Without it, datasets can become opaque over time: researchers cannot determine what a ﬁle
contains, how it was processed, whether it is the right version, or indeed whether they are permitted
to use it. Moreover, datasets are often archived without proper metadata and become irrelevant
as the information needed for continued use degrades or is lost. The C-HER team’s treatment of
metadata (hereinafter referred to as the C-HER metadata framework) ensures that every dataset
in the repository can be understood, discovered, trusted, and properly attributed.
For each C-HER resource entity, the metadata entry provides the context needed to determine:
 • what a resource contains
 • who published the source data
 • the data’s spatial and temporal context
 • how the C-HER resource is organized
 • what processing stage it represents
 • which rights or redistribution conditions apply
 • which ﬁelds contain measurements, identiﬁers, dates, geometry, or supporting information
 • whether the required metadata and quality checks have been completed
 • how a derived resource relates to its source resources
The C-HER metadata framework therefore serves two purposes: (1) it helps users ﬁnd and in-
terpret resources, and (2) it gives curators and users a consistent record of identity, provenance,
processing, and quality status.

1.1 Guiding Principles: FAIR Data and AI Readiness
The C-HER metadata framework supports the FAIR data principles [3]: Findable, Accessible, Inter-
operable, and Reusable. FAIR is a set of principles for making data and metadata easier for people
and machines to ﬁnd, understand, combine, and reuse. C-HER supports these principles through
structured resource identiﬁers, controlled metadata ﬁelds, documented provenance, rights infor-
mation, lineage, column-level metadata, and lookup tables that reduce inconsistent terminology.
The framework was inspired in part by the Dublin Core vocabulary [4] and can be rendered or
crosswalked into external metadata formats when needed.
 • Findable: C-HER resources are registered with structured identiﬁers generated from se-
 lected metadata ﬁelds. We use descriptive metadata and controlled terms to help users
 locate resources by source, geography, time period, subject, and other attributes.
 • Accessible: Metadata and access rights information are stored in an open, queryable
 database so that authorized users can retrieve data efﬁciently and understand usage condi-
 tions.
 • Interoperable: We use controlled vocabularies, lookup tables, and documented ﬁeld mean-
 ings so that resources can be compared and combined across source organizations, spatial
 resolutions, temporal resolutions, etc. The framework also preserves sufﬁcient structured
 information to support crosswalks into external metadata standards, including Dublin Core,
 the Federal Geographic Data Committee’s Content Standard for Digital Geospatial Metadata
     (FGDC CSDGM) [5], and ISO 19115/19139 [6], [7].
 • Reusable: Data provenance, processing history, licensing, and version information are rig-
 orously documented to ensure that datasets can be conﬁdently reused, including by re-
 searchers who were not involved in the datasets’ creation. This helps users determine
 whether a resource is suitable for a speciﬁc analysis and understand how it differs from the
 original source data or from related C-HER resources.
The C-HER metadata framework also supports AI-ready use of C-HER resources. Here, AI readi-
ness means that resources are described in a structured, consistent, and machine-readable way
so that data can be used in computational workﬂows, including AI and machine learning applica-
tions. Moreover, data have received QA/QC review, and, for some data, transformed versions of
the dataset are stored; this reduces the number of steps required of an analyst before they can
use data in computational models. C-HER resources carry the information needed for responsible
reuse in analytic and AI workﬂows.

Section 2

The C-HER Metadata Framework

2.1 Standards and Controlled Terms
2.1.1 Relation to other metadata standards
The C-HER metadata framework was developed with Dublin Core in mind, which provides a com-
pact, domain-agnostic set of elements for describing digital resources. The framework has since
evolved past those speciﬁc ﬁelds and requirements, but it incorporates the underlying principles
regarding controlled vocabularies with predictable schemas.
The framework is designed so that C-HER metadata can be rendered, crosswalked, or exported
into other metadata formats. In practice, this means that C-HER may require ﬁelds that are optional
or not directly required in a target standard. Thus, enough structured information is retained such
that C-HER metadata can be transformed to comply with other major metadata standards (e.g.,
Dublin Core, FGDC CSDGM, or ISO 19115/19139 when needed).

2.1.2 Controlled vocabularies and lookup tables
For any ﬁeld that should take a standardized value (e.g., spatial resolution, data processing level,
organization, resource type), the approved options are stored in a dedicated database lookup as
opposed to being entered as unrestricted text. All of the identifying metadata, as discussed in
depth in Resource-Level Metadata, are selected from these lookup tables.
The controlled vocabularies reduce spelling variants and duplicate concepts. They also support
precise ﬁltering and enable harmonization across data. A query for state-level resources, for in-
stance, should not depend on whether individual curators wrote state, states, statewide,
or any other variant or abbreviation. For example, in the C-HER metadata framework, the spatial
resolution code c00 means county in every dataset in the repository. A query for c00 returns the
complete set.

2.1.3 Free-text ﬁelds
Free-text ﬁelds contain resource-speciﬁc information written by the curator rather than selected
from a controlled list. They are used for details that cannot be represented adequately by stan-
dardized terms. Examples include:
 • the content and intended use of a resource
 • when data have been transformed, noted material differences from the parent ﬁle
 • known limitations or exclusions
 • the reason for creating a new version when data are versioned internally
 • when the data are a derivative of the parent ﬁle, details of the relationship not captured in the
 lineage

The metadata ﬁelds that comprise a resource identiﬁer are described further in the following sub-

Organization and dataset

We group our resources into source-level datasets. Each dataset is associated with a single pub-
lishing organization, although an organization may publish many datasets. A resource is linked to
the publishing organization through its dataset, and the organization code used in the resource
identiﬁer is taken from the dataset entry. For externally sourced data, the organization is generally
the organization that published the original data. C-HER also has its own organization identiﬁer
for datasets created by our team. A dataset can contain many resources. Resources within the
same dataset may differ in spatial or temporal coverage, resolution, or version; those differences
are recorded in the remaining segments of the resource identiﬁer.

 • Spatial extent refers to where the resource applies.

Temporal extent and temporal resolution

Temporal extent and temporal resolution also describe different properties.
 • Temporal extent is the period covered by the resource and is recorded as a start date and
 end date.
 • Temporal resolution is the frequency or granularity (e.g., annual, monthly, daily, or a single
 snapshot) of observations within that period. Examples of temporal resolution codes include
 A00 for annual data, M00 for monthly data, W00 for weekly data, IRR for irregular temporal
 intervals, SNP for a snapshot in time, and 000 when temporal resolution does not apply.
A resource can cover ten years at annual resolution or ten years at daily resolution. The extent is
similar, but the resources support different analyses.

current broad categories are as follows.

The two-digit sufﬁx distinguishes stages within a processing category. The sufﬁx is a relative indica-

Version

The version code ensures that every resource has a unique identiﬁer when its other identifying
metadata would not be sufﬁcient to distinguish it. It is generated automatically during metadata
registration, and the version entry is added to the database with version_notes at the time of
metadata insertion. When metadata are put into the database, the next available version code
for that exact combination of dataset, spatial and temporal extent, spatial and temporal resolution,
and data level is assigned, beginning with 001. Resources that differ only by version code are still
distinct resources. Most resources require only the use of 001. For an initial version, the version
notes may state that it is the ﬁrst version of the dataset for a distinct temporal, spatial, and data
level combination. See Version Code for further information.

Here, the distinction between resource descriptions and notes warrants further discussion. The
Rights ﬁeld is also discussed further below.

Resource descriptions and notes

Each C-HER resource has a structured identiﬁer and a separate description ﬁeld. The description
provides additional context needed to interpret or use the resource. The description should sum-
marize what the resource contains and, where applicable, explain how the resource was created
and why it was ingested. In practice, the description should help a user answer basic interpretation
questions: What does this resource contain? What source or process produced it? What popu-
lation, geography, or time period does it describe? What processing or transformation should a
user know about before using it? The description thus gives the reader enough context to know
what is documented in the other metadata ﬁelds.
Notes are optional, supplementary remarks that should accompany the resource but do not belong
in the primary description or another structured metadata ﬁeld. Notes can document temporary
caveats, delivery-speciﬁc context, update status, or other resource-speciﬁc details. Notes should

not replace lineage notes, version notes, rights information, or other metadata ﬁelds that have a

Rights

Rights information is recorded separately from the resource description. Whereas the description
explains what the resource contains and provides context about how it was created, rights meta-
data include the license, redistribution permissions, and usage terms associated with the data.
This ﬁeld is necessary because C-HER resources often originate from external organizations. Cu-
rators must verify the source terms of use rather than assume that data can be redistributed or
reused without restriction. At minimum, the rights metadata should identify the applicable license
or permission statement, any redistribution limits, and any attribution or credit requirements that
users must follow. For example, a resource description might state that a land cover resource
contains USGS-deﬁned land cover classes for a given year and geography. The rights ﬁeld would
separately state whether the source data are public domain, whether redistribution is permitted,
and where users can ﬁnd the authoritative rights statement.

2.3 Column-Level Metadata
Resource-level metadata describe a C-HER resource as a whole. A resource can be a ﬁle, a
database table, or another metadata-bearing data object. When the resource is tabular, we also
record metadata for the columns inside that resource. Column-level metadata answer a different
set of questions than resource-level metadata. Resource metadata explain what the resource is,
where it came from, what geography and time period it covers, what processing level it represents,
and what rights apply. Conversely, column metadata explain what each ﬁeld in the tabular resource
means and how it should be used.

Column tags classify each column’s role in a tabular C-HER resource. They identify whether a

2.4 Lineage, Inheritance, and Version Code
2.4.1 Parent–child relationships
Lineage relationships identify the C-HER resources that were utilized in the creation of a new re-
source. A resource may have one parent resource or multiple parent resources. For example, a
resource might have multiple parent resources when data are generated from a model created
at ORNL; likewise, when TIGER boundaries are used to aggregate a point-level resource to the
county level, both the boundary resource and the original point-level resource are parents. This
relationship is used to track how data evolve as they are transformed, aggregated, modeled, or
otherwise prepared for use. When a parent resource is speciﬁed, the curator records lineage
notes that explain how the new resource differs from its parent or parents. These notes are sep-
arate from the general resource description. That is, the description explains what the resource
contains, whereas the lineage notes explain the relationship between the new resource and the
resources that were used to create it.

2.4.2 Metadata inheritance
Eligible ﬁelds can be inherited from a parent resource to a child resource when the inherited values
still apply. This reduces repeated entry and helps keep related resources consistent. The only
ﬁelds that cannot be inherited are the resource-speciﬁc description and notes, as well as some
automatically generated ﬁelds (e.g., version number, metadata creation date, update date, and
uploaded by).
Inherited metadata are still subject to review. A child resource retains an inherited ﬁeld only when
that ﬁeld accurately describes the child. Fields that change during processing, aggregation, mod-
eling, or conversion are updated for the child resource.

2.4.3 Version code
Further information about the version code as distinct from inheritance is warranted here. It should
be noted again that resources that differ only by version code are still distinct resources. For ex-
ample, translating a resource’s columns into another language may require a new resource even
though no additional processing was done that would affect its other identifying metadata. Con-
versely, creating an H3 resource from a county-level parent resource or joining several parent
resources into a derived product is an example of a lineage relationship, which is documented via
parent resource links and lineage notes.

2.5 Metadata Completeness and Validation
This section provides an overview of the completeness checks performed for metadata. C-HER’s
metadata tools, CHERpy and HERMIT, support the metadata completeness checks described in
this section at the time of metadata registration. For resource-level metadata, the tools help enforce
required table_dictionary ﬁelds, contributor entries, version entries, and required links among
related metadata tables. For tabular resources, the tools also support column-level metadata entry
and can help enforce required column metadata ﬁelds before submission. However, curators are
still responsible for the technical content of the metadata, including the column description, column
tag, unit, reference column, and any notes explaining how a child resource differs from its parent
resource or resources. That is, CHERpy and HERMIT do not by themselves determine whether a
description, column tag, unit, lineage note, or QA/QC ﬁnding is correct/accurate.

2.5.1 Resource-level completeness
A C-HER resource is considered metadata complete once the following conditions are met:

 • required resource metadata ﬁelds are ﬁlled out
 • entries exist for the resource’s contributors and version

Some ﬁelds are optional at initial registration because they may not yet be available. These ﬁelds

2.5.2 Column-level completeness
A column is determined to be metadata complete when
 • its literal column name is known
 • its description is present
 • an approved column tag is assigned
 • value or meta value tagged columns have a unit assigned, where applicable
 • columns tagged as being a foreign reference identify the speciﬁc reference

 IMPORTANT

 A resource can be metadata complete and still be under quality review. Metadata
 completeness means that the required resource-level metadata have been populated,
 contributor and version records are present, and, for tabular resources, column metadata
 have been completed. Quality review is broader. The QA/QC workﬂow also includes raw
 data checks, comparison against prior processed data (where applicable), metadata val-
 idation, tabular and spatial checks, visual inspection, and ﬁnal reporting. Because meta-
 data validation is only one part of that workﬂow, a resource might satisfy completeness
 requirements while still awaiting or undergoing additional QA/QC review. The full QA/QC
 workﬂow is contained in internal documentation.

Tool-Supported Metadata Management

As documented herein, the C-HER metadata structure uses controlled values, lookup tables,
foreign key relationships, generated resource names, contributor records, version records, and
column-level metadata. As the metadata model developed, the problem became curating a con-
sistent vocabulary of values for these ﬁelds while avoiding duplication and supporting reproducibility.
Because each metadata ﬁeld may need its own table of approved values—and because resource
metadata entries reference those tables—manually specifying metadata can be difﬁcult and te-
dious.
We have developed internal tools to facilitate metadata entry and maintenance: CHERpy and
HERMIT.

Section 4

Conclusion

The C-HER metadata framework gives each resource a consistent identity and records the infor-
mation needed to understand and use it. It is intended to make metadata consistent and reliable
as well as to reduce repeated work. We use controlled vocabularies and lookup tables, gener-
ated identiﬁers, inheritance tracking, and internally developed tools that simplify data ingestion and
validate the structure and completeness of the metadata. Moreover, the framework was devel-
oped with interoperability in mind: our metadata can be transformed to comply with other major
metadata standards for broader use. Thus, it aligns with FAIR data principles and facilitates AI
readiness by making C-HER resources easier to ﬁnd, interpret, compare, combine, and reuse in
computational workﬂows. This overview document explains those practices to give users, cura-
tors, reviewers, and stakeholders insight into how the C-HER team manages metadata and what
information is available for responsible use of exposomic data.
