 ABSTRACT

The LUCID Epidemiologic Data Harmonization Pipeline was developed to make heterogeneous
occupational epidemiology and radiation exposure datasets more suitable for cross-cohort analyses,
downstream artificial intelligence workflows, and risk-modeling research. The pipeline addresses a
recurring scientific data integration challenge: although CEDR public-use epidemiologic datasets provide
rich metadata, code sets, and study-specific variables, they differ substantially in naming conventions,
coding rules, date formats, exposure units, missing-value conventions, and variable semantics. This report
describes the v18.5 implementation and provides a status update on this effort at the end of FY26. The
pipeline combines ontology-driven variable discovery with empirical validation and analytic-file quality
control. Step 1 constructs a master variable representation using metadata, code sets, exact matching, and
SBERT-based semantic similarity. It also standardizes flags, dates, and external-dose fields, generates
data profiles, and creates a row-appended analytic CSV with study provenance. Step 2 evaluates proposed
mappings using raw data, code-set overlap, semantic comparison of categorical labels, distribution
checks, and explicit validation statuses. Beginning with v18.3 and extended through v18.5, the software
adds collision-preserving analytic-file construction, column-quality auditing, dimension reconciliation,
source-by-source column contribution accounting, and optional model-based quality control. The v18.5
Model QC layer performs study-ID prediction, leave-one-study-out outcome prediction (when an
outcome is provided), missingness analysis, distribution-shift checks, redundancy detection, and Step 2
signal summarization. Together, these capabilities provide a transparent framework for determining
whether harmonized data are structurally consistent, empirically defensible, and suitable for downstream
analysis while preserving provenance and evidence for expert review rather than silently overwriting
conflicting values.

 1. Background and Related Work

1.1 CEDR as a Scientific Data Source

The DOE Comprehensive Epidemiologic Data Resource is an electronic repository containing health
studies of DOE contract workers and environmental studies near DOE facilities. DOE describes CEDR as
supporting independent access and use of data collected during studies of health impacts associated with
working at or living near DOE facilities. ORISE materials describe CEDR as providing access to de-
identified data collected since DOE early production years and note that holdings include many worker
studies and analytic data file sets [4-6]. These characteristics make CEDR a valuable resource for
research, but also create a harmonization challenge because public-use files may come from different
eras, sites, coding practices, and epidemiologic designs.

1.2 Harmonization versus Feature Engineering

Data harmonization and feature engineering both involve data transformation, but they serve different
scientific purposes. Harmonization seeks to make data from different sources comparable and
interoperable. Feature engineering seeks to improve performance of a downstream model by transforming
predictors. In this project, harmonization precedes modeling: variables must first be mapped,
standardized, and validated so that subsequent analyses do not confuse source-specific coding artifacts
with biological, epidemiologic, or exposure-related signal.

 2

1.3 Data-Science and Provenance Principles

The pipeline design follows several widely used data-science principles. Tidy data emphasizes that
variables should be represented as columns and observations as rows, creating a consistent structure for
analysis [7]. FAIR data principles emphasize machine-actionable findability, accessibility,
interoperability, and reusability [8]. W3C provenance concepts define provenance as information about
entities, activities, and people involved in producing data, supporting assessments of quality, reliability,
and trustworthiness [9]. W3C data-quality vocabulary discussions emphasize dimensions such as
accuracy, consistency, completeness, conformance, credibility, and processability [10]. Although this
project is not a clinical-trial submission dataset, CDISC ADaM provides a useful analogy because it
emphasizes analysis-ready datasets, metadata, traceability, and reviewability [11].

 2. Materials and Input Data Structure

The pipeline is designed around CEDR-style folders that include raw data files, metadata files with a
_variables.csv suffix, and CodeSet files for categorical variables. The metadata file provides variable
identifiers, names, labels, types, and CodeSet references when available. CodeSet files define allowable
values, codes, and descriptions. In historical CEDR datasets, two columns may be semantically related
even if their names differ; conversely, two similarly named columns may not represent the same concept.
Examples from the March presentation included differences in plutonium-monitoring codes, missing-
value conventions such as 0 versus 99, and temporal variables where one field records an absolute date
while another records a duration.

The v18.5 workflow assumes that the input folder includes the same file patterns used in previous
releases. It does not require that all datasets have the same columns. Instead, it builds a canonical schema
progressively and leaves analytic cells blank when a dataset does not provide a corresponding variable.
This design allows heterogeneous source files to contribute rows to a shared analytic file without forcing
artificial values into unavailable fields.

 3. Methods: v18.5 Pipeline Architecture

3.1 Workflow Overview

The v18.5 application implements a three-part operational workflow: Step 1 harmonization, Step 2
validation, and tests. A fourth optional component, Analytic Model QC, can be run after the analytic file
exists. The standard Step 1 + Step 2 + Tests workflow remains unchanged from the user perspective;
model QC is deliberately optional so that release-gate checks and diagnostic model checks remain
separate.

3.2 Step 1: Ontology Discovery and Harmonization

Step 1 constructs a master variable ontology by examining dataset variables sequentially. The largest
available variables file is used as the initial base because it supplies the widest starting schema.
Subsequent datasets are integrated by exact matching when possible and by semantic similarity when
exact matches are unavailable. The default semantic model is sentence-transformers/all-MiniLM-L6-v2,
which maps sentences and short paragraphs into a 384-dimensional vector space and supports clustering,
semantic search, and sentence similarity [12]. In the packaged application, this model is the intentionally
bundled default; other models require source-mode execution, a cached model, or a local model path.

Step 1 produces a master variable list, synonym mappings, concept relationships, concept groupings,
harmonization logs, raw/harmonized profiling reports, and detailed transformation outputs. It also
harmonizes selected flags, detects and standardizes date-like fields, standardizes external-dose variables
into derived unit fields, and records detailed reports for these transformations. The goal is to answer the
ontology question: which variables across datasets probably represent the same concept?

3.3 Step 2: Empirical Validation of Proposed Mappings

Step 2 uses the raw data and metadata evidence to determine whether Step 1 synonym suggestions behave
consistently in practice. It separates categorical and continuous checks. For categorical variables, it
evaluates CodeSet overlap and semantic similarity of code descriptions. For continuous variables, it
evaluates distributional similarity using metrics such as cosine similarity and Kolmogorov-Smirnov-style
evidence. It assigns explicit statuses, including CONFIRMED, QUESTIONABLE, REJECTED,
SKIPPED, and ERROR, and writes review files for accepted and problematic mappings. This step
answers the empirical question: do the proposed variables actually behave as comparable variables in the
observed data?

3.4 Analytic File Construction

A major addition since the March presentation is the creation of a global analysis-ready CSV. The
analytic file is row-appended across all harmonized CEDR files and begins with a generated study_id
column containing the source dataset base name. The analytic schema begins with the harmonized dataset
that has the most columns and then extends to the right as additional datasets introduce new variables.
Data are placed into canonical columns through the Step 1 master and synonym mappings where
available; when a dataset does not contain a corresponding column, the analytic cell remains blank.

v18.5 also preserves source conflicts. Earlier logic could collapse multiple source columns into one
analytic column and retain the first non-empty value when same-row non-empty values conflicted. The
current builder keeps deterministic canonical coalescing for safe cases, but when conflicting non-empty
values are detected, it preserves the conflicting source values in companion columns and writes the event
to a collision audit. This design prioritizes traceability and avoids silent data loss.

3.5 GUI and CLI Implementation

The application can be operated through a graphical user interface (GUI) or a command-line interface
(CLI). The GUI provides tabs for running the pipeline, viewing profiling reports, and running optional
Analytic Model QC. The CLI supports reproducible scripted execution from Windows PowerShell,
macOS Terminal, Linux shells, or high-performance computing environments. v18.5 separates optional
model-QC controls into their own GUI tab, maintains the standard Step 1 + Step 2 + Tests behavior, and
adds model-QC helper buttons for recommended defaults and suggestions from the analytic file.

 5. Analytic-File Quality Assurance

Analytic-file quality assurance was implemented to verify that the harmonized output is not only
generated successfully, but also internally consistent, traceable to the source datasets, and suitable for

 7

downstream analysis. Because the analytic CSV combines multiple heterogeneous CEDR datasets into a
single row-appended file, the pipeline applies several layers of checks to confirm that rows, columns,
mappings, and derived outputs are handled as expected. These checks are designed to identify structural
errors, preserve evidence when mappings are uncertain, and flag variables that may require expert review
before use in pooled analysis or modeling.

5.1 Deterministic Tests

The first level of quality assurance is deterministic. These tests verify conditions that should always be
true if the analytic file was constructed correctly. The tests confirm that the analytic CSV exists, contains
a leading study_id column, has no duplicate column names, and matches the expected final ordered
schema. Row counts are reconciled by verifying that the total number of analytic rows equals the sum of
the harmonized source-file rows and that each study_id count equals the corresponding source dataset row
count. Source-value preservation checks confirm that mapped non-empty values appear in the expected
analytic locations unless an audited transformation or collision-preserving alternate column is used.

The deterministic quality checks include the following:

 • Dimension reconciliation: Source rows, analytic study_id rows, and total analytic rows must
 match mathematically.
 • Schema validation: Analytic columns must match the expected canonical schema after variable
 mapping and collision-preserving alternate columns are applied.
 • Collision handling: Conflicting same-row non-empty values must be preserved in companion
 columns and recorded in the collision audit rather than silently overwritten.
 • Column-quality auditing: All-blank columns, source-prefixed unresolved columns, external-
 dose derivative columns, and duplicate-content columns are flagged for review rather than
 silently deleted.
 • Release-gate checks: Required outputs must be present and readable before the pipeline is
 considered complete.

Together, these deterministic tests provide the structural foundation for analytic-file validation. They
confirm that the file was assembled correctly, that no source rows were lost, that the analytic schema is
reproducible, and that uncertain or conflicting mappings are preserved for review. After these
mathematical and structural checks are completed, the pipeline applies additional empirical and model-
based diagnostics to evaluate whether the harmonized variables behave consistently across datasets.

5.2 Column Contribution Accounting

The v18.5 column contribution summary was added to make analytic-file column counts interpretable.
Source columns are counted as occurrences because the same concept may appear in multiple datasets.
The analytic file, however, contains a unique canonical schema. For each dataset, the report records how
many source columns introduced new analytic columns, how many mapped to existing analytic columns,
how many unresolved source-prefixed columns were added, and how many collision-preserving alternate
columns were created. The core accounting rule is: final analytic columns = study_id + new unique
analytic columns + collision alternate columns. This explains why the arithmetic sum of source-file
columns can be larger than the final analytic-file column count.

5.3 Profiling Reports and Fallback Behavior

The system attempts to generate full HTML profiling reports using available profiling backends. Because
packaged macOS environments may lack optional profiling dependencies, v18.5 adds runtime
compatibility support and a built-in LUCID basic profile report if the full backend is unavailable. The
diagnostic file records the backend error for transparency, but a usable profile report is still written and
the release gate does not fail solely because the optional backend was unavailable.

 6. Optional Model-Based Analytic Quality Control

Model-based quality control is intentionally implemented as a diagnostic layer, not as proof of
correctness. Deterministic tests establish structural validity. Model-based tests then ask whether the
harmonized file behaves plausibly for analysis and whether residual dataset-specific artifacts remain. The
design follows general prediction-model transparency principles, including the need to report model
validation clearly and to avoid leakage between training and test data. scikit-learn documentation
emphasizes that test data should not be used when fitting transformations or models and that splitting and
preprocessing should be handled carefully to avoid optimistic performance estimates [13]. TRIPOD+AI
likewise emphasizes transparent reporting for prediction model development and validation using
regression or machine-learning methods [14].

 7. Validation Status and Reproducibility

The v18.5 source package was validated locally with Python compile checks, import binding and
coverage guard tests, analytic builder column/row/collision logic tests, analytic column contribution
summary unit checks, analytic model-QC unit tests, and package hygiene checks. The full real-data end-
to-end run must be performed in the user environment because the original CEDR input datasets were not
included in the source package workspace. The expected validation practice is to run Step 1, Step 2,
Tests, then optional Model QC; preserve all output files; and review dimension summaries, collision
audits, column audits, column contribution summaries, Step 2 review files, and model-QC findings
together.

7.1 Reproducibility Features

Reproducibility was a central design consideration in the v18.5 implementation. Because the pipeline is
intended to support scientific review, cross-cohort analysis, and future reuse, the software was structured
so that each run can be traced to specific scripts, configuration choices, output files, and validation
artifacts. These features help ensure that results can be repeated, inspected, and compared across
operating systems and future software versions.

The v18.5 implementation includes several reproducibility features:

 • Versioned source scripts and output names use v18.5 and v18_5 naming conventions.
 • The bundled default SBERT model supports local and offline packaged execution.
 • Command-line interface commands support repeatable runs in Windows PowerShell, macOS
 Terminal, Linux, and high-performance computing environments.
 • The release capability manifest records required outputs and their pass/fail status.
 • The analytic model quality-control step writes a JSON data contract describing the configuration,
 selected features, sampling settings, and output paths used during the run.

Together, these features provide a practical audit trail for the harmonization workflow. They allow users
and reviewers to determine which version of the pipeline was used, which outputs were generated,
whether required deliverables passed the release checks, and how optional model-based quality control
was configured. This reproducibility framework supports the next section, which describes how the
pipeline validates harmonized variables and analytic outputs through deterministic checks, empirical
review, and model-based quality-control diagnostics.

7.2 Scientific Contributions

The work contributes a practical and transparent approach to harmonizing historical occupational
epidemiology datasets for modern analytic use. First, it combines semantic metadata alignment with
empirical validation, reducing reliance on name matching alone. Second, it treats analytic-file
construction as a provenance-preserving process: rows are appended, columns are mapped to a canonical
schema, missing cells remain blank, and source conflicts are preserved in companion columns. Third, it
produces quantitative reconciliation reports that explain row and column math. Fourth, it adds model-
based quality-control diagnostics to identify residual dataset-specific structure before AI or statistical
modeling. These features make the pipeline useful not only as a software tool but also as a documented
scientific workflow for preparing heterogeneous epidemiologic data for analysis.

7.3 Limitations and Risk Management

The pipeline does not eliminate the need for expert review. Semantic similarity can propose plausible
mappings, but it cannot fully determine epidemiologic equivalence. Step 2 can reject or question
mappings based on empirical evidence, but some variables may remain ambiguous because of missing
metadata, sparse values, or cohort-specific design. Model-QC warnings are diagnostic signals rather than
automatic errors. High study-ID predictability may reflect real cohort differences as well as incomplete
harmonization. Similarly, exact duplicate-content columns may represent true duplicate information,
expected unit conversions, or distinct variables with identical observed values in the current data. The
software therefore emphasizes auditability, preservation, and review queues rather than irreversible
automatic deletion or rewriting.

Additional future work could include a post-Step-2 validated analytic view that adds mapping-status flags
directly into the analytic dataset; compact analysis exports that remove all-blank columns while
preserving the full provenance file; richer metadata export for each analytic column; and configurable
positive/negative-control outcome tests defined by domain experts.

 8. Conclusions

The LUCID v18.5 harmonization pipeline advances an earlier conceptual workflow into a more mature
scientific and operational system for heterogeneous occupational epidemiologic data. It preserves the
original two-step structure of ontology discovery and empirical validation while adding a global analytic
CSV, study-level provenance, collision-preserving conflict handling, dimension reconciliation, source-by-
source column accounting, profiling reports, release-gate tests, and optional model-based analytic quality
control. These features support data-science principles of tidy analytic structure, provenance, traceability,
quality assessment, and transparent model-based diagnostics. A central conclusion of this work is that a
harmonized analytic file should not be judged by row and column counts alone. It must also be evaluated
through provenance-preserving audits, empirical validation, and diagnostic modeling approaches that help
determine whether variables behave consistently enough to support downstream artificial intelligence,
statistical modeling, and risk analysis. The v18.5 implementation provides a structured foundation for this
evaluation while preserving evidence for expert review rather than silently resolving uncertain or
conflicting mappings. This creates a clear path toward future validated analytic releases and more
defensible use of harmonized occupational epidemiology data.

A3. Pipeline data flow

The input folder contains raw dataset CSV files named <dataset>.csv and metadata files named
<dataset>_variables.csv. Optional code-set CSVs and date/external-dose override files may also be
present.

Step 1 profiles raw files, creates harmonized per-dataset copies, detects and standardizes flags, dates, and
external dose units, builds the master variable list, creates synonym and concept relationship outputs,
builds the all-study analytic CSV, writes analytic audits, and writes the release manifest.

Step 2 reads Step 1 synonym mappings and Step 1 harmonized datasets, compares mapped variables
using rule-aware empirical validation, writes validated/rejected/questionable/skipped reports, writes raw-
to-harmonized consistency audit output, and enforces an embedded release gate.

Tests run unit checks and real-output regression checks against the selected input, Step 1 output, and Step
2 output folders.

Model QC is optional and reads the analytic file after Step 1; it writes diagnostic machine-learning and
data-quality review outputs under analytic_model_quality_v18_5.

A4. Algorithms and harmonization policies

 Policy Implementation detail

 SBERT semantic matching Step 1 uses SentenceTransformers to compare variable definitions. Default model
 is all-MiniLM-L6-v2. The GUI/CLI can pass a different model name/path, but
 packaged offline builds are intentionally prepared for the bundled MiniLM model.

 Similarity threshold Default is 0.65. Higher values are stricter and lower values are more permissive.
 The GUI uses explicit up/down buttons to adjust the displayed value.

 Base dataset ordering Variables files are sorted by variable count. The largest metadata file initializes the
 master variable list.

 Exact VarID match If a new variable has the same VarID as an existing base variable and is not a
 radiation time-sliced measure, it maps as an exact synonym.

 Semantic match If semantic similarity meets the threshold and no special concept rule separates the
 variable, it maps as a synonym.

 Concept-related separate Radiation time-sliced variables and selected employment timing/job-title timeline
 measurements variables are kept as separate analytic concepts rather than collapsed as ordinary
 synonyms.

 Analytic schema order The analytic CSV starts with study_id, then begins with the harmonized dataset
 that has the most columns, and extends to the right only when later datasets
 introduce new analytic columns.

 Collision policy When multiple same-dataset source columns map to the same canonical analytic
 column, non-overlapping or identical overlaps are safely coalesced. Conflicting
 non-empty overlaps are preserved in companion columns named
 <canonical>__from__<dataset>__<source> and documented in the collision audit.

 Profiling fallback If ydata-profiling cannot load, v18.5 writes a built-in LUCID basic profile report
 and diagnostic text. A valid basic profile should not fail the release gate.

 macOS GUI workers By default, macOS runs pipeline work in-process from a Python worker thread to
 avoid a second visible .app window. Setting

 Policy Implementation detail

 LH_MAC_USE_SUBPROCESS_WORKERS=1 restores subprocess workers for
 advanced use.

A9. Maintenance notes

Keep release constants synchronized across core.py, __init__.py, pipeline scripts, output filenames, tests,
README, and build scripts.

When adding a required output, update REQUIRED_CAPABILITY_IDS, release capability manifest
logic, and harmonization_test_v18.5.py.

Avoid silently dropping mapped data. Prefer preserving conflicts in audited companion columns or
producing explicit review files.

Model QC should remain diagnostic. WARN findings are review prompts, not automatic proof of
incorrect harmonization.

The packaged offline app should resolve SBERT from the bundled model cache; source mode may use a
local path or internet/cache-backed model resolution.

 Status Meaning

 PASS The check found the expected file/condition or did not detect the issue it was designed to find.

 WARN The output is usable for review, but the pattern should be inspected before final
