- Agentic Science Toolkit for Exoplanet Research
Emilie Panek, 1 Alexander Roman, 1 Gaurav Shukla, 1 Leonardo Pagliaro, 2 Katia Matcheva 1 and \newauthor Konstantin Matchev 1 1 Department of Physics and Astronomy, University of Alabama, Tuscaloosa, AL, 35487, USA 2 Department of Physics and Astronomy ‘Galileo Galilei’, University of Padova, Vicolo dell’Osservatorio 3, I-35122 Padova, Italy

Abstract
The rapid expansion of exoplanet atmospheric observations and the proliferation of a wide range of specialized modeling tools has created a need for flexible, accessible, and user-friendly workflows. Transmission spectroscopy, in particular, has become a key technique for probing atmospheric composition of transiting exoplanets. The analyses of these data require the combination of archival queries, literature search, the use of radiative transfer models, and Bayesian retrieval frameworks, each demanding specialized expertise. Modern large language models (LLMs) enable the coordinated execution of complex, multi-step tasks by AI agents with tool integration, structured prompts, and iterative reasoning. In this study we present ASTER, an Agentic Science Toolkit for Exoplanet Research. ASTER is an orchestration framework that brings LLM capability to the exoplanetary community by enabling LLM-driven interaction with integrated domain-specific tools, workflow planning and management, and support for common data analysis tasks. Currently ASTER incorporates tools for downloading planetary parameters and observational datasets from the NASA Exoplanet Archive, as well as the generation of transit spectra from the TauREx radiative transfer model, and the completion of Bayesian retrieval of planetary parameters within the TauREx framework. Beyond tool integration, the agent assists users by proposing alternative modeling approaches, reporting potential issues and suggesting solutions, as well as higher-level interpretations. We demonstrate ASTER’s workflow through a complete case study of WASP-39b, performing multiple retrievals using observational data from different sources available on the archive. The agent efficiently transitions between datasets, generates appropriate forward model spectra and performs retrievals that recover atmospheric parameters reported in the literature. ASTER provides a unified platform for the characterization of exoplanet atmospheres. Ongoing development and community contributions will continue expanding ASTER’s capabilities toward broader applications in exoplanet research.

2.1
Orchestral overview

Orchestral AI
(
53
)
is a Python framework designed for scientific applications of AI agents. It makes agent behavior transparent, debuggable, and portable across different LLM providers. Instead of hiding execution logic behind complex concepts, Orchestral keeps control flow explicit and easy to inspect.

One feature of Orchestral is provider agnosticism, meaning that the framework provides a unified interface to multiple LLM providers, such as OpenAI, Anthropic, or Google. This allows users to switch models without rewriting code, avoiding vendor lock-in. This is desirable in an institutional setting as universities and labs may require researchers to use a particular inference provider or local computing resources. Orchestral also uses a synchronous execution model, which makes agent behavior easier to debug, lowering the barrier to entry for domain experts in astrophysics unfamiliar with asynchronous programming.

In general, an AI agent is a system including the following core elements: An LLM, the “context”, and a set of tools (see Figure
1
). AI agents may also include additional features such as longer-term memory, model selection mechanisms, security safeguards, and context management tools.

The context is a record of all messages, tool calls, and tool outputs. In the Orchestral AI framework it also tracks associated metadata including token usage and cost. The context can be saved, loaded, and even continued with a different LLM provider.
Orchestral automatically validates that tool calls and tool results match correctly. This prevents common errors that can occur when tool outputs are missing or misaligned with requests.

The LLM performs reasoning and selects actions based upon the current context. Typically it “acts” by generating tokens, which can be thought of as words (or parts of words). These may be in the form of natural language responses to the user (the typical behavior in chatbot tools such as ChatGPT) or in specially coded structures that indicate the use of tools or other special functions. If a user asks an agent equipped with a planetary data search tool the question “what is the temperature of WASP 39”, the agent might immediately respond with “
<tool> tool_name: ‘get_stellar_info’, parameters: {star_name: ’WASP-39’}</tool>
” and the system then detects and executes this pattern. Actual examples of ASTER tool calls are discussed in Section
4
.
Defining tools in this way leverages “in-context learning,” a phenomenon in which LLMs can adapt their behavior based on information provided within the prompt, even when that information was not explicitly encountered during training
15
.
We define a set of functions which carry out concrete actions, and present them to the agent along with descriptions of how and when to use them.

Tools form a bridge between the LLM and external software. In Orchestral, tools are easily defined as Python objects, the docstring and type hints are automatically processed into the “tool schema” language that the LLM expects. Orchestral also provides a Python decorator “
@define_tool
" which allows any Python function to be used as a tool.
One notable feature of tools is that they can return outputs in any format. Their outputs are inserted as strings into the conversation context alongside user messages. In the prior example, after querying the hypothetical
get_stellar_info
tool, the output might be “
WASP-39: Temperature:
5400\pm 150\,K
, Radius:
0.895\textpm 0.023\,R_{\odot}
, ...
”
In some cases the tool may return an error, for example, if the agent queried:
get_stellar_temp(‘Death Star’)
it might return: “
Star not found, please check the stellarhosts database.
”

As illustrated in Figure
1
, the agent runs in an iterative loop. At each step, it reads the current context, asks the LLM to produce a response, checks whether tool calls are requested, executes those tools if present, and then updates the context with the results. This loop continues until no further tool calls are required or a stopping condition is reached. The LLM never executes code directly. All external actions happen through tools, which are executed outside the model in a controlled environment.

Security hooks

While modern commercial LLMs generally behave in predictable and desirable ways, they can sometimes take surprising and harmful actions. This is often the result of a “misunderstanding” of the user’s intent on the part of the model, analogous to an “honest mistake” by human collaborators. However, a growing body of AI safety research has demonstrated that, under certain conditions, language models can also violate explicit instructions or engage in strategically harmful behavior, including deception or rule circumvention
36
;
49
. Since these agents are equipped with tools granting them access to external systems, in some cases executing arbitrary terminal commands, it is imperative that guardrails be put in place to detect and block unwanted behavior.

Orchestral incorporates multiple layers of execution safety through a system of hooks that intercept tool calls before and after execution, enabling structured control over agent behavior and supporting safe, human-supervised workflows.

One key mechanism is user validation, implemented through a “user-approval hook”. A simple approach is to require the user to approve all tool executions. While this guarantees safety, it is often impractical, as it interrupts the workflow and places a significant burden on the user. Heuristic rules provide a more efficient alternative by detecting and blocking clearly dangerous actions, such as destructive shell commands; however, they may miss more subtle risks and can be overly restrictive.

A more flexible approach is to employ a separate LLM to evaluate proposed actions. In practice, specialized policy models can classify actions according to their safety, capturing more nuanced behavior than heuristics while remaining lightweight and efficient. However, such models are not perfectly reliable and must be used conservatively.

In Orchestral, these approaches are combined into a hybrid system. Heuristic checks first block clearly harmful actions, after which a safeguard LLM classifies remaining actions as safe, unsafe, or uncertain. Unsafe actions are blocked, while uncertain cases are escalated to the user for explicit approval. This layered approach balances safety, usability, and flexibility without unnecessarily interrupting routine workflows.
53

These mechanisms ensure a strict separation between reasoning and execution: the language model proposes actions, while the orchestration layer enforces safety and validation.

Cost tracking

Orchestral includes built-in cost and token-usage tracking at the framework level. Every interaction with an LLM provider records token counts and associated costs, which are accumulated within the agent’s context object. This information persists across turns and tool calls, allowing users to monitor computational cost in real time. Because the context is provider-agnostic, cost tracking remains consistent even when switching between different models or providers within the same workflow.
The Orchestral UI also supports setting a cost ceiling which will interrupt execution if reached.
This enables cost-aware experimentation, such as using lower-cost or local models for exploratory reasoning, followed by higher-capability models for final execution. These features are particularly relevant for long-running or iterative scientific analyses, where uncontrolled LLM usage could otherwise become quickly expensive.

Conversations history

Orchestral manages conversation history through the context object that encapsulates and validates the complete sequence of messages exchanged between the user, the LLM, and any external tools. This history includes prompts, model responses, tool calls, and tool outputs, ensuring that each step in the reasoning process is preserved and logically consistent. The system automatically verifies that tool calls and their results match correctly, and maintains provider-agnostic encoding so conversations can be saved and resumed across different LLM providers.
This persistent conversational history is particularly valuable in science for bookkeeping and retracing a train of thoughts.

Tool implementation

We now turn to the practical question of how domain-specific functionality is implemented. As described earlier, all interactions between the agent and external software are accomplished through tools. Tools define the actions an agent is able to perform and form the building blocks from which the scientific workflow is constructed. This section describes how tools are defined and used within the Orchestral framework, with a focus on ASTER tools for exoplanet applications.

3.1
Getting started

ASTER builds on top of the Orchestral framework and requires additional dependencies specific to exoplanet atmospheric analysis. These requirements are maintained separately and are documented at
https://github.com/emipanek/aster

Users should ensure that all ASTER-specific dependencies are installed before running or developing new tools.

3.2
The role of tools

The interaction between the agent and the tools follows a loop reasoning and execution pattern:

1.

The agent receives the current context.

2.

The language model responds, possibly invoking tools.

3.

If tool calls are not present, the response is passed to the user.

4.

If tool calls are present, the arguments are validated.

5.

The tool call passes though all pre-call hooks for approval.

6.

If approved, the tool is executed.

7.

The tool’s output is passed though all post-call hooks.

8.

The processed output is added to the agent’s context.

9.

Repeat.

3.3
How to write a tool

Orchestral supports two primary ways of defining tools:

•

Function-based tools, using a decorator

•

Class-based tools, for stateful or more complex behavior

In both cases, tools are written in standard Python syntax and rely on type hinting and docstrings to define their functioning. From these comments, Orchestral generates a universal tool object that can be used with any LLM.

When using the function-based tool definition, the function signature represents the parameters the agent is allowed to control. The variable names will be visible to the agent, and it will decide based upon the context and the tool description (defined by the docstring) how to use these arguments.
Thus, clear and descriptive variable names and good documentation are strongly encouraged, as they inform the agent’s decision-making process.
When a tool is called, its code is executed once. The tool may call external libraries, run scientific models, or interact with data on disk. Tools should avoid side effects beyond what is necessary for their task and should always produce a well-defined output.
Errors should be clearly passed to the agent along with relevant suggestions of how to remedy them, allowing the agent to detect failures and respond appropriately.

The agent can then download and process the selected datasets. This process allows users to access any public dataset available on the NASA Exoplanet Archive without needing to manually reformat the data for retrieval analysis. The tool cannot be fully automated because the generated
wget
commands are not persistent over time.
Once the path to the
wget
commands is provided, the agent executes those commands to download IPAC tables and saves them as per-planet CSV files. The agent then reads the CSV files, extracts the relevant spectral information, and produces two outputs: a data file (spectrum.dat) and a metadata file (metadata.json).
The data file contains three columns: wavelength (in microns), transit depth, and the error on the transit depth. The metadata file includes the authors of the dataset’s first publication, a URL to the associated paper, the observing facility and instruments used, and the units corresponding to each column in the data file.
Direct use of the NASA Exoplanet Archive TAP system is not viable for this task because the legacy ’transitspec’ table has been retired and is no longer being updated after the summer of 2023. The archive explicitly directs users to the newer Atmospheric Spectroscopy Table instead, which is not retrievable through TAP in the same way.

3.5.4
Running a retrieval

This next tool runs a TauREx
(
65
;
4
)
retrieval starting from an observed transmission spectrum and a simple forward model. The user can either provide the path to an observation file or let the agent download a dataset using the tool described previously. TauREx supports multiple retrieval modes: reduced, full, and equilibrium. The reduced mode uses a predefined set of common molecules: H
2
O, CH
4
, CO
2
, CO and NH
3
. This is the simplest configuration and is therefore used as the default when no mode is explicitly specified by the user. The full mode allows the user to define a custom set of molecules. The user can also ask the agent to use every molecule available, in which case the agent inspects the available cross-section files in the path specified earlier and uses the complete set of molecules. The user also defines an initial mixing ratio for each molecule, as the starting point before the retrieval begins. In both the reduced and full modes the fitted parameters are the mixing ratios of each molecules. The equilibrium mode relies on ACE
(
1
;
2
)
to compute the thermochemical equilibrium abundances by minimizing the Gibbs free energy. In this case the fitted parameters are the metallicity and C/O ratio.
TauREx currently supports the following optimizers: Nestle
(
61
;
47
;
59
;
31
)
, MultiNest
(
31
;
17
)
, and UltraNest
(
20
)
. All three rely on nested sampling, a Bayesian inference method that explores the parameter space and simultaneously estimates the Bayesian evidence
(
18
;
19
)
. Nested sampling is well-suited for multi-modal posterior distributions and problems with parameter degeneracies because it explores parameter space globally rather than locally. While all three are based on nested sampling, they differ in their practical use cases. Nestle is lightweight and faster, making it more appropriate for simple, low-dimensional problems. MultiNest is well-established and commonly applied in exoplanets analysis. UltraNest is a more recent implementation that provides improved numerical stability and better performance for high-dimensional parameter spaces.

3.5.5
Plotting the results

This tool generates corner plots from the posterior of a retrieval run, using the corner library
(
32
)
. It offers an easy way to see the parameter distributions and their correlations. Corner plots are common in retrieval studies because they reveal the overall structure of the solution space.

The agent can automatically generate simple corner plots without user intervention, returning them alongside the retrieval results. A basic corner plot is also produced and stored when the retrieval tool is executed. This dedicated plotting tool extends that functionality by providing sensible defaults and configurable arguments for commonly adjusted formatting options. It is particularly useful for comparing multiple retrieval runs, as it can overlay posteriors from different results within a single corner plot, facilitating direct comparison. For more specialized visualizations, the code-based approach discussed in Section
3.7
can be used.

3.6
Sequential tool execution

These tools get used in combination to accomplish complicated tasks, sometimes without the user explicitly asking. For example, if you ask for a transmission spectrum of WASP-39b, the agent knows that entails first searching for the parameters and then running the forward model tool.
The agent decomposes the request into a sequence of subtasks, selects the appropriate tools, and executes them in the correct order. This behavior highlights the agent’s ability to perform implicit planning, allowing it to autonomously execute multi-step scientific tasks.

3.7
Tools vs. Skills

A recurring idea in recent work on coding agents is that code provides a near-universal interface to computation: given sufficient capability and access to a terminal environment, an agent can in principle implement arbitrary functionality through code generation and execution. This perspective, which became increasingly prominent in 2024–2025, has led to the view that instead of building specialized tools, one can equip agents with “skills”, typically expressed as natural language instructions or reusable code snippets provided in context.
In this paradigm, a skill may take the form of a structured prompt, markdown file, or retrieval mechanism that injects task-specific guidance into the agent’s context. In contrast, a tool is a predefined function with a fixed interface that executes a specific operation.

We argue that both approaches have complementary strengths. On one hand, if an agent has access to a sufficiently expressive environment such as a terminal, many tasks can in principle be accomplished through direct code generation. This suggests that not all functionality must be exposed as explicit tools.
On the other hand, tools are valuable when reliability, safety, or structure is required. For example, if agents consistently struggle with a recurring task, encapsulating that functionality in a tool can improve robustness.
Tools can also enforce constraints or maintain state in ways that are difficult to achieve through prompting alone. For example, in Orchestral the file read and edit system tracks which files an agent has read and blocks blind modifications to unseen files, thereby reducing the risk of unintended changes.
Other tasks exhibit a high degree of variability and open-ended structure that is difficult to capture with a fixed function interface. For instance, generating a scientific plot involves a large design space of stylistic and semantic choices, making it cumbersome to parameterize as a tool. In such cases, requiring the agent to directly write code is often more natural and efficient.
For such open-ended tasks, skills provide a flexible, user-friendly mechanism for guiding agent behavior. They also allow non-technical users to encode preferences, domain knowledge, and heuristics in natural language without needing to define rigid interfaces.

In our own experiments, we initially implemented a dedicated tool for generating corner plots of posterior distributions, but later found that we preferred the agent to use its built-in coding tools to write the code directly, guided by a skill describing best practices and stylistic preferences.
Conversely, in our testing, we observed that the agent required trial and error to correctly configure TauREx and, in some cases, hallucinated a nonexistent TauREx
run_transit()
function. We contend that this is a case where a dedicated tool such as
RunTaurexModel
greatly improves reliability and efficiency.

One can improve the quality of the fit by adding a more comprehensive molecular list in the retrieval model, consistent with previous studies.

In this work, our objective was to demonstrate the feasibility and efficiency of using an agent to perform end-to-end retrieval analyses. In that respect, the results presented here successfully validate the capabilities of ASTER: the agent is able to autonomously handle data acquisition, model generation, retrieval execution, and result interpretation within a realistic scientific workflow. This proof of concept application to WASP-39b demonstrates that agents can be effectively integrated with existing exoplanet tools.

Conclusion

In this paper, we have presented the Agentic Science Toolkit for Exoplanet Research. The goal of ASTER is not to replace existing frameworks, but to act as an assistant that can coordinate common tasks and provide suggestions. In this work, we applied ASTER to data acquisition, modeling, retrieval, and visualization in the context of transmission spectroscopy of exoplanets’ atmospheres.

We have shown that the agent can autonomously orchestrate the full pipeline, from obtaining planetary parameters and downloading datasets from public repositories to generating transmission spectra from radiative transfer models, performing Bayesian retrievals of atmospheric parameters, and visualizing the results. The successful autonomous execution of multiple retrievals using different datasets, along with their comparison, highlights the flexibility and utility of the approach. In this sense, the goal of the study is achieved: we demonstrate that an agent can reliably integrate existing exoplanet tools into a coherent, reproducible, and efficient analysis framework.

Unlike a fixed script, which encodes a predefined sequence of operations, ASTER dynamically adapts its behavior based on intermediate results, user input, and evolving context, enabling more flexible and interactive scientific workflows. Additionally, the LLM retains a broad base of knowledge from its training data, which can be useful when a query is under-specified or when a tool call implicitly relies on prior knowledge. For example, ASTER was not explicitly provided with the spectral resolution of Ariel, which was required for the rebinning experiment; nevertheless, it was able to infer this information when needed. However, practitioners should not rely solely on this implicit knowledge, providing explicit context remains best practice. In situations where the model must infer missing details, the risk of hallucination increases.

Another key strength of the agent-based approach is format compatibility. Oftentimes, data comes in different formats and units, and making different inputs/outputs compatible is tedious. By standardizing how datasets, models, and retrieval outputs are ingested and produced, ASTER simplifies comparisons between different analyses and results. ASTER is also modular by design. Individual capabilities are independent tools, allowing new functionality to be added without requiring modification of the overall system architecture. This makes ASTER adaptable to evolving scientific needs, such as new instruments, updated chemical models, or alternative retrieval techniques.

Beyond orchestration, ASTER functions as a research assistant. The agent actively checks intermediate results, validates inputs, and verifies assumptions when possible. When errors occur, the agent attempts to diagnose issues, suggest corrective actions, and retry failed steps. In addition, the agent can highlight unexpected or atypical behavior in results, prompting further inspection by the user. Routine and repetitive tasks, such as parameter explorations, resolution changes, or repeated retrievals, can be automated, allowing researchers to focus on interpretation rather than execution.

Another important aspect of ASTER is its accessibility. By lowering the technical barrier to entry, this toolkit makes advanced analyses such as atmospheric retrievals more approachable for early-career researchers and non-specialists.

Finally, ASTER represents a first step toward more capable scientific agents. The framework demonstrates how agent-based systems can support rigorous scientific analysis. As tools, models, and datasets continue to grow in complexity, agent-based systems may play an increasingly important role in managing workflows, enforcing best practices, and enabling more efficient and reproducible research. We strongly encourage the exoplanet community to extend this library of tools and implement new capabilities within the ASTER framework.
