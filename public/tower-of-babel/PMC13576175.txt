A pragmatist approach to bridging tables and ontologies through LinkML and punning
Authors: William D. Duncan, Christopher J. Mungall, Robert P. Guralnick
Published: 2026

ABSTRACT
BackgroundOntologies support data integration and knowledge discovery across multiple life science disciplines through the application of formal semantics that define hierarchical and cross-hierarchical relationships which enable automated reasoning capabilities. At the same time, tabular data is by far the most commonly produced format of data in most disciplines. This is especially true in biodiversity dataset production. Creating rich semantic data from tables can be complex because of a mismatch between flat tabular data and hierarchical ontology models. Here, we present a practical approach for closing this gap using Linked Data Modeling Language (LinkML) in combination with OWL punning. LinkML allows tabular schemas to be formally defined, validated, and automatically documented. OWL punning allows schema elements to function simultaneously as both classes and data properties. This approach has many practical advantages that we showcase using mammal trait data assembled from the Ranges Digitization Network.ResultsOur work demonstrates how using LinkML + punning simplifies alignment of trait data in tabular format with ontologies such as the FuTRES Ontology of Vertebrate Traits (FOVT). Additionally, we show multiple advantages of our practical approach, including: maintaining synchronization between schema, ontology, and documentation, reducing modeling overhead, and preserving compatibility with conventional relational data workflows. On the downside, full logical reasoning is limited relative to more verbose RDF translations. Often this is a perfectly acceptable tradeoff for many use cases focused on data discovery and integration.ConclusionThe LinkML + punning framework shown here provides a scalable and pragmatic strategy for building semantically rich, ontology-aligned data resources that lower the barrier to semantic interoperability in biodiversity and trait informatics.Supplementary informationThe online version contains supplementary material available at https://doi.org/10.1186/s13326-026-00359-4.

Background

Ontologies have significantly impacted the field of bioinformatics [1]. Their uses include, among other things, providing structured, controlled vocabularies for biological and biomedical terms1, making the implicit meanings of terms explicit [2], and through the use of automated reasoners such as HermiT [3] and ELK [4], inferring relations between terms as well as checking for logical consistency. However, effectively using ontologies to operate on data presents several challenges. We highlight many of these challenges here in the context of tabular data.

Many bioinformatics ontologies are built using the Web Ontology Language (OWL) [5]. Typically, these ontologies consist of a class hierarchy of general and more specific classes with relations (i.e., object properties) holding between classes across the hierarchy. For example, in the FuTRES Ontology of Vertebrate Traits (FOVT)2 [6], testis is hierarchically defined as a subclass of gonad and related to the male reproductive system, which is hierarchically defined as a subclass (i.e., is a) of reproductive system, via the part of relation (Fig. 1).3, 4

Tabular data, on the other hand, is neither hierarchically structured nor are relations defined between the columns of a given table. This difference in structure creates a kind of impedance mismatch between tabular data and ontologies. One strategy to overcome this impedance mismatch is to map columns to ontology terms. A drawback of this strategy is that it forces you to choose between mapping a column to either a class or property (i.e., object or data property). Mapping a column to a class enables the system to leverage logical axioms to make inferences. For example, it can infer that if a column is mapped to a length quality which inheres in a tail is a type of tail length. However, when using classes, you cannot enforce range constraints. For example, an OWL class cannot require that the mapped field use floats as values.

For OWL ontologies, another strategy for using ontologies with tables is to convert tabular data into a serialization of the Resource Description Framework (RDF) [7], such as the Terse RDF Triple Language (Turtle) [8]. This may involve writing custom programs, or scripts, or leveraging an existing tool such as YARRRML [9], ROBOT [10], Ontop [11], or Tarql5. Mapping languages, such as the RDB to RDF Mapping Language (R2RML) [12] and D2RQ [13], may be used to define customized rules that map tabular data into RDF, and some graph database vendors, such as GraphDB6 and Virtuoso7, provide functionality to query relational data using the SPARQL Protocol and RDF Query Language (SPARQL) [14].

Regardless of the strategy chosen, there is still the challenge of communicating to users of the data that a data element is defined by an ontology term. This information may be provided as part of a project’s documentation (e.g., a data dictionary or project website) or as an ontology term annotation, but these kinds of approaches require extra effort to ensure that the method of communication and data schema are kept in sync. For example, if a column is added or removed from a spreadsheet, the documentation or ontology term annotation must also be updated. Moreover, it is common practice for an ontology term to use an opaque Uniform Resource Identifier (URI). For instance, in FOVT, the URI for ear length to notch is <http://purl.obolibrary.org/obo/FOVT_0000005>. This may create an additional level of complexity for relating data fields to ontology terms, especially for non-ontologists.

To address the challenge of using ontologies with tables, we have implemented an approach in which the Linked Data Modeling Language (LinkML) [15]8 is used to define the data schema, and the schema elements are mapped or annotated to OWL terms that are punned9 as both classes and data properties. This approach enables us to execute queries that make use of an ontology’s semantics as well as easily keep schema in sync with the documentation. We tested this method using a subset of data from the Ranges Digitization Network (abbreviated Ranges from here on)10 and found the results promising. Although we focus on trait data in this manuscript, we hold that this method can be applied to a wide variety of datasets and across different domains.

Methods

Ranges is a community effort to digitize a set of specified specimen-level traits from all terrestrial mammal natural history specimens collected in western North America, append them to digital records, publish them openly in community repositories, and make them interoperable with complementary data streams [16]. In conjunction with the digitized information, community members record data about specimen traits that are stored as tables available to the Ranges research community. Analysis of trait data contained in these tables, such as limb lengths, body mass, and reproductive traits, enable researchers to investigate questions about the ecology and evolution of mammals in a regional hotspot.

An integral part of the Ranges is the standardization of the meanings of trait data. Specimen data is not always collected in the same way. For example, a body length measurement may or may not include the tail. To address this, Ranges integrates with efforts to develop key trait ontologies such as the aforementioned FOVT. This enables data to be precisely defined. For example, FOVT contains classes for representing an organism’s body length, body length with tail, and body length without tail. In addition to defining trait data, the data collected by the network needs to be shared to the rest of the community. This requires that the community - both data providers and data users - understands the structure of the data, and LinkML (discussed next) is a good fit for defining and publishing data schemas. Thus, the use of ontologies for data standardization and the need for communicability of the data schema made the Ranges dataset a good test case for our method.

Linked data modeling language (LinkML)

We use LinkML to define the Ranges’ trait data schema (i.e., the structure of the data). LinkML is a flexible modeling language that uses YAML to model (or define) schema elements. In a LinkML schema, classes model types of entities that the data represents, and slots model relations between classes or the data values associated with the class. In the context of tabular data, a class models a table and a slot models a column. Important metadata, such as a description, can be associated with tables and slots, and for slots, you can further specify the types of values (e.g., string, float) that it can hold. Being able to define slots in this way is important for ensuring data quality (i.e., that the data conforms to the specifications of the schema).

In the Ranges’ LinkML schema, the TraitValue11 class defines what kinds of data can be used as trait values, and the allowable data elements and datatypes are defined by the slots12 associated with the TraitValue class. OWL punning and LinkML

In OWL, an ontology term is “punned” when it is used in different ways, for example, both as a class and an individual. Examples of punning include defining classes as individuals for purposes of meta-modeling [17, 18] and treating an object property as a class to facilitate deprecating18. An ontology term can also be punned as both a property and an individual. However, a term cannot be punned as two different properties. For instance, a term cannot be both an object and data property.

In the Ranges’ LinkML schema, we use punning to address the impedance mismatch between the column names that relate observations to data values and the ontology classes used to define the meaning of the data. To do this, we use a special pun_as slot annotation to specify the kind of entity for which we want the slot to be punned. After the initial OWL for the schema is generated, a custom script19 is executed that looks for these pun_as annotations and then generates the corresponding OWL. Discussion

To review, in the methods section we outlined our approach for leveraging an ontology’s semantics to better define and understand tabular data. However, a more in-depth consideration of our LinkML punning approach, possible alternatives, and tradeoffs warrant discussion.

Comparison with mapping technologies

There are several semantic-web technologies (mentioned in the introduction) that can be used to transform tabular data into RDF. Many of these support punning. For example, in YARRRML, the body_mass data property can be punned as a class by adding sections to the mapping file (see Appendix D.1):

The punning approach we have implemented in LinkML, however, is not intended to compete with the aforementioned mapping technologies. Rather, we implemented the punning approach as a pragmatic means to remain within the LinkML framework and augment the LinkML data schema with the functionality provided by OWL ontologies, such as hierarchical queries, without replicating the ontology in the LinkML schema or adding another technology to the data translation pipeline.

Moreover, our LinkML punning method is not as robust in all situations as other mapping technologies. For example, YARRRML has a more straightforward approach for creating relations between entities. However, some preprocessing would be needed to convert the id values (based on the occurrenceID field) into valid IRIs and to convert the tabular data to yaml, since the LinkML converter does not work with tabular formats. Another approach is to utilize the LinkML YARRRML generator30, but in order to convert the data to RDF, YARRRML would still need to be executed on the generated mapping file.

Additionally, LinkML is not a framework for enabling SPARQL queries on tabular data. This is possible with tools such as Ontop. For instance, Calvanese et al. [11] demonstrate how to utilize Ontop for creating a cancer-research virtual knowledge graph. This virtual knowledge graph enables users to execute SPARQL queries against the data, and within the virtual knowledge graph, punning is used to ensure that terms such as “brain” and “developmental stage” are used the same way across data sources.

Despite lacking YARRRML’s ease for relating instances and not having the SPARQL functionality of Ontop, we find our punning approach useful. We start by defining the schema in LinkML. This provides several utilities for data validation and generating documentation. We then extend the functionality of the schema by annotating the slots (data properties after conversion into RDF) with punning information (i.e., pun_as). This workflow emphasizes the need for good schema design, whereas YARRRML and Ontop are primarily concerned with mapping data elements. Although we have focused on the Ranges project in this manuscript, our approach is generalizable to other projects. For instance, Wilson et al. [19] are using the LinkML punning approach on dental care-related fear and anxiety data.

A final alternative to consider is that instead of referencing an external OWL ontology class in the LinkML schema, the class could be represented as a LinkML class using the class_uri metamodel slot. For example, FOVT’s tail length class could be defined in the schema as follows:

This is indeed a possibility, and it has some advantages. First, the documentation produced for LinkML schema will include information about the classes. Thus, users do not need to use other services, such as the Ontology Lookup Service [22], to track down class definitions. Second, the classes can be used as the slot ranges, which may be quite useful for certain data validation scenarios.

However, there are some important disadvantages to consider. First, LinkML does not support automated reasoning, and thus Ranges would sacrifice many of the benefits of using OWL such as consistency checking, class subsumption inferencing, and leveraging formal semantics for querying (see testis query in section “Results”). Second, LinkML does not (as yet) have tooling for converting OWL ontologies into LinkML schemas. Thus, the classes need to be created manually or programmatically (e.g., a custom script that reads classes from the ontology and outputs the corresponding LinkML classes). While manual creation of classes may be an option for small ontologies, the ontologies used by Ranges are too large for this to be a viable option. Programmatically creating the classes would add additional effort to the project, and Ranges does not have the resources to support this.

Tradeoffs

We recognize that there are some tradeoffs to consider when implementing our method of incorporating LinkML and punning. First, many ontologies may find punning to be unappealing based on ontological commitments. For instance, top-level ontologies, such as the Basic Formal Ontology (BFO) [23] and the Descriptive Ontology for Linguistic and Cognitive Engineering (DOLCE) ontology [24], make a number of abstract mutually exclusive distinctions, such as between entities that persist (or endure) through time and entities that unfold in time. Ontologists operating under such commitments may reject the notion (on philosophical grounds) of treating a term as both a data (or object) property and a class. We recognize this, but we also point out that adopting our method of using LinkML with OWL punning does not necessarily require completely abandoning commitments to top-level ontologies. At the class (or T-box) level, an ontology may align with a top-level ontology (in fact, FOVT is a BFO-based ontology), but, at the data or instance level, these ontological commitments are relaxed. It is at this level (i.e., the data level) where data scientists need to efficiently and effectively operate, and we hold that this approach has pragmatic advantages in making the ontology more accessible to data scientists.

A second tradeoff is that our approach may limit the utility of using automated reasoning.

Since we are not creating OWL individuals (i.e., instances) to represent each data field, axioms within the ontology may not produce the desired inferences. For instance, in FOVT, tail length is defined by the equivalence axiom:

In contrast, our punning method only translates the tail_length slot into the data property and puns it as a class. We do not create instances of length and tail related by inheres in, and thus, the FOVT equivalence axiom for tail length would not generate new inferences. In practice, we have found this to be an acceptable tradeoff. Based on the needs of the Ranges’ project, the kinds of queries described in the Methods section are sufficient for data retrieval and generating insights. We recognize that the decision of whether to do a more verbose translation of data (e.g., creating multiple triples for each data field) is dependent on the needs of a specific project. However, in practice, we have found that the process of generating such verbose translations requires complex data translation pipelines that are costly to build and maintain, and the cost of developing these pipelines may outweigh the benefits. If a project determines that more reasoning power is needed, other mapping technologies can be incorporated. However, this has the disadvantage of having to maintain tools that are outside of the LinkML ecosystem.

Finally, our method of using LinkML and OWL punning does incur some technical debt. In order to generate punning statements in Turtle, the Ranges’ schema and tabular data need to be processed by a custom script and merged with the Turtle generated by the LinkML gen-owl tool.37 In order to address this technical burden, we will submit our approach to the LinkML development community so that it can be maintained as part of the LinkML tools.

Conclusion

Here we utilize a LinkML and ontology punning approach to simplify development of semantic data resources focusing on vertebrate functional traits. Domain scientists interested in trait data discovery often have relatively simple use case queries such as “search for all forearm length measurements”, or “show me all the appendicular skeleton measurements for mammals”, which would be challenging without an underlying ontology with a well developed class-level hierarchy. Given these kinds of use cases, we strongly encourage approaches that can simplify development and deployment and here showcase combining LinkML and punning as one such approach. This solution, in particular, has three positive outcomes. First, this approach simplifies keeping schema, ontology and documentation synchronized. Second, via punning, this approach narrows the gap between semantic models and traditional key-value approaches via linking data and class properties. The end result is that datastores can still support asking ontology-aware queries, while keeping a more traditional row and column based approach. The third upside is reduction in modeling overhead, both in terms of the time taken to perform reasoning and the outcome set of assertions. The only downside of this approach is more limited full reasoning, but in many cases this is a desirable tradeoff. In sum, the LinkML+punning approach we champion is particularly well suited for many applications where more expressive reasoning provides only marginal, or no value increase, while also providing a simplified means to synchronize and simplify data generation and publication.
