Skill-as-Pseudocode: Refactoring Skill Libraries to Pseudocode for LLM Agents
Xinze Li, Yuhang Zang, Yixin Cao, Aixin Sun, [3pt] Nanyang Technological University

Abstract
Markdown skill libraries for LLM agents ship as free-form prose, forcing the agent to re-derive both the input schema and the concrete invocation syntax on every retrieval. We observe that this often produces a “confused → \to re-retrieve → \to still confused” loop in which the agent issues a partially-correct action, receives uninformative environment feedback, and re-retrieves the same prose. We propose Skill-as-Pseudocode (SaP), an automatic conversion of markdown skill libraries into typed pseudocode with deterministic quality control. For each cluster of similar procedural passages drawn from one or more skills, SaP extracts a typed contract and filters it through a four-check deterministic verifier (coverage, binding, replacement, risk). Promoted contracts are inlined into a rewritten skill skeleton together with restored concrete action templates, giving the agent two complementary signals: a typed signature for what the skill does and a concrete template for how to invoke it. On the 134 134 -game ALFWorld unseen split with gpt-4o-mini , pooled across three seeds, SaP wins 82 / 402 82/402 paired games versus 47 / 402 47/402 for the Graph-of-Skills (GoS) baseline (pooled McNemar p = 8.2 × 10 − 5 p=8.2\times 10^{-5} ), at − 22.8 ± 6.4 % -22.8\pm 6.4\% input tokens and − 14.5 ± 4.1 % -14.5\pm 4.1\% LLM calls per game.

Prose is the bottleneck.

We argue, and our experiments support, that the prose
representation itself, not the absence of factoring, is the
dominant bottleneck when LLM agents consume markdown skill
libraries. A markdown skill document does not separate
what

the skill produces (its output schema) from

is invoked (the concrete primitive actions the environment

retrieval-action feedback loop

Typed pseudocode is a better representation.

Two pieces of information short-circuit the loop. (1) A typed

that exposes the skill’s trigger, input schema,
output schema, and pre/post-conditions tells the agent in one

it can do and
what arguments it must

typed-routing agents. (2) The
concrete action templates

(“

”, “

{appliance}
”) that the contract abstracts over tell the agent

how
to actually invoke the underlying environment, in the
exact tokens the environment accepts. Together these two pieces
form a structured pseudocode spec: a typed signature paired with
template-level concrete syntax. Markdown skill libraries today
contain both pieces of information but only in scattered prose
form, and existing typed-routing methods

(
36
;
27
;
26
)
assume the
contract has already been hand-written upstream.

Skill-as-Pseudocode (SaP).

We propose to
automate the prose-to-pseudocode conversion

of markdown skill libraries with deterministic quality
control.

3
Method

3.1
Problem statement

A
skill library

\mathcal{L}=\{p_{1},\dots,p_{n}\}
is a set
of
parent skills
, each a procedural document (markdown

SKILL.md
, OpenAPI specification, or MCP server
description). Each parent
p_{i}
consists of a sequence of

procedural units

u_{i,1},\dots,u_{i,k_{i}}
(markdown
sections, OpenAPI parameter groups, etc.). A

candidate cluster

c
is a set of procedural units, drawn
from one or more parents, hypothesised to describe the same
underlying procedure in different prose.

A
typed contract

\kappa
is a structured pseudocode spec
with explicit
trigger
,
input_schema
,

output_schema
,
preconditions
,

postconditions
, and
side_effects
fields (full
schema in
Appendix F
).
\kappa
is the

structured surrogate
for the prose in
c
: the same
information re-expressed in a form the agent can consume in
one read instead of re-deriving it on every retrieval.

We define the conversion
c\to\kappa
as
valid
iff
\kappa

satisfies four deterministic checks (
§ 3.3
):

Coverage
,
Binding
,
Replacement
, and

Risk
. The verifier returns either “valid, with witness

\kappa
and supporting evidence” or “invalid, with check-level
rejection reasons”. The verifier produces no soft-classifier
score; any rejection is grounded in one of four named checks.
Given a set
\mathcal{K}
of validated
contracts, the converted library
\mathcal{L}^{\prime}
rewrites each
parent’s matching units into
invoke(
\kappa_{j}
,
\vec{a}
)

placeholders and adds each
\kappa_{j}
as a child skill (reached via

invoke
, not direct retrieval;
§ 3.5
).
Cross-parent factoring (when
|\text{src}(\kappa)|>1
) is a
secondary benefit; the principal benefit is the
prose-to-pseudocode conversion itself.

3.2
Pipeline overview

Figure 1
shows the pipeline: five base stages plus
two LLM-aware post-verifier passes. Parser, candidate proposer,
and refactor (Stages 1, 2, 5) are deterministic; the contract
extractor (Stage 3) issues one
gpt-4o-mini
call per
candidate cluster; the verifier (Stage 4) is fully deterministic.
The contract IR (full schema in
Appendix F
) is a
typed record with fields
trigger
,
input_schema
,

output_schema
,
pre/postconditions
,

resources
,
side_effects
,
source_parents
,
and per-call-site
bindings
filled by BE.

Stage 1: Parser.

For
SKILL.md
the parser splits YAML frontmatter from body
and uses markdown headings to define procedural units. For OpenAPI
it groups parameter-handling operations into units. Output:

parents.json
, a list of parents each with

procedural_units
,
scripts
,
references
.

Stage 2: Candidate proposer.

For each procedural unit we extract a
frame
tuple

(\texttt{verb},\texttt{objects},\texttt{code\_langs},\texttt{linked\_scripts})
via shallow parsing, then embed the unit
text with
text-embedding-3-small
. Single-linkage clustering
joins units sharing a frame and cosine similarity
\geq 0.65
. The
stage is intentionally
high-recall
; over-clustering is
acceptable because the verifier filters downstream.

Stage 3: Contract extractor (LLM).

A single
gpt-4o-mini
call per candidate cluster produces
a strict-JSON contract draft; the model can refuse via

_extraction_failed
(structural rejection). Subsequent
rejections are deterministic.

Stage 4: Verifier (4 checks).

Outputs a profile
\phi(c,\kappa)
over

coverage
,

binding_rate
,

replacement_rate
,
and
risk
, plus a 3-tier decision (
§ 3.3
,

§ 3.4
).

Stage 5: Refactor.

For each
auto_promote
contract, we (i) detect call-sites
deterministically by walking parents and matching units that
contributed to the cluster, (ii) apply BE LLM-aware bindings
(below), (iii) rewrite each parent skeleton by replacing call-site
units with
invoke(
\kappa
,
\vec{a}
)
, then
(iv) apply RC cleanup. The output is a per-parent

*.rewritten.md
for every touched skill plus the index

refactored_library.json
.

Binding Extraction (BE).

For each deterministic call-site, BE asks
gpt-4o-mini

whether the unit is a genuine instance of
\kappa
and, for each
required input, which substring of the unit text binds it. A
deterministic post-check drops call-sites whose bindings are empty
or whose tokens do not overlap the unit. Passing bindings are
inlined into the rewrite as
invoke(
\kappa
, {object=
"laptop 1", source="bed 2", dest="desk 1"})
, grounding the
placeholder per-parent. BE dropped
630/2{,}105
(
30\%
) call-sites as spurious on

skills_500
.

Rewrite Cleanup (RC).

The deterministic rewrite leaves non-clustered sections (Workflow
lists, Examples, Bundled Resources) verbatim; if any of these
content blocks contradict the child contract (e.g., an Example
using a different action verb), the conflict misleads the agent.
RC is a single-shot verifier-guided rewrite in the spirit of
self-correction
(
23
;
9
)
: it asks

gpt-4o-mini
to detect and rewrite such conflicts as

invoke(
\kappa
,
\vec{a}
)
calls, preserving
parent-specific text and introducing no content absent from
either the original parent or the verified contract. A
deterministic post-check ensures every invoked
\kappa
remains
referenced after cleanup. RC succeeded on
320/322
(
99.4\%
)
touched parents.

3.3
The four verifier checks

Given a candidate
c
and contract draft
\kappa
, the verifier
computes four rule-based, check-level scores; unlike learned
step-level verifiers
(
19
;
37
)
,
the output is a structured rejection profile, not a soft classifier
score. The four checks:
Coverage
(token recall of

\kappa
’s trigger/I-O strings against each parent’s unit text,
catches misnamed contracts);
Binding
(for each required
input, fraction of (parent, input) pairs whose unit text overlaps
the input name, catches over-wide clusters);
Replacement

(fraction of parents whose unit admits an

invoke(
\kappa
)
-substitution preserving markdown
structure, catches control-flow entanglement);
Risk
(AST
scan of contract scripts/resources for unsafe sinks like

rm -rf
or undeclared network egress, hard-rejects at
weighted score
\geq 0.80
). Each check catches a distinct class
of would-be-promoted candidates—no single layer accounts for more
than
\sim 51\%
of first-failed rejections and the layers are
nearly disjoint
(
Appendix I
,
Table 7
). Full
threshold definitions and the per-layer rejection bucket are in

Appendix I
.

3.4
Decision policy + calibration (summary)

The four scores are combined into a scalar promotion score

s(\phi)=w_{b}\,\texttt{binding}+w_{c}\,\texttt{coverage}+w_{r}\,\texttt{replacement}-w_{s}\,\texttt{risk}
and
mapped to a three-tier decision (
auto_promote
,

review
,
reject
) by thresholds

(\tau_{\text{auto}},\tau_{\text{rev}})
. We calibrate the two
thresholds against
30
synthetic negative controls from three
single-library classes (same-domain-distinct, near-miss verb-object
permutations, swapped-contract pairings;
n=10
each), a
benchmark-free counterpart to output calibration

(
11
)
and Chow-style reject options. On

skills_500
a wide range of thresholds achieves
0\%
FP
on the negatives; for the main result we use the calibrated point

(\tau_{\text{auto}},\tau_{\text{rev}})=(0.30,0.10)
which
promotes
80
verified children. A stricter point

(0.65,0.35)
promotes only
49
at the same
0\%
FP rate and is
reported as a sensitivity variant in
Appendix H
.

Hierarchical-only retrieval pool.

At task time the agent retrieves over a pool that contains only
parent skills; promoted child contracts are kept in a separate
internal store. Children are reusable subprocedures designed to be
reached via a parent’s
invoke(
\kappa
,
\vec{a}
)

them as standalone results lets the agent read an
under-contextualised child without its wrapping parent
(
§ 5.5
).

Substituted skill bundle
(
Figure 2
).

For each retrieved parent whose

appears in the
refactored library, the retrieval module replaces the parent’s
content with a short header (clarifying that

is notation, not an executable verb) followed by three content
blocks: (i) for every

\kappa_{j}
,
\vec{a}
)
the
verbatim
original_unit_text
(the concrete env-action

,

) with extracted bindings;
(ii) the rewritten parent skeleton; and (iii) the inlined child

needs to be specialised to a new binding. The substitution adds no

re-presents it in the order the agent consumes it.

7
Conclusion

Our results raise a broader question: should skill libraries be
authored in pseudocode directly? Markdown optimises for human
authors, but LLM agents pay the prose-to-structure conversion cost

on every retrieval
. SaP shows this cost is recoverable
post hoc with deterministic quality control—paid at index time
rather than at every read. Publishers in typed catalogues (OpenAPI,
MCP) can therefore pre-substitute at index time; domain experts
who cannot write pseudocode directly keep writing prose while the
verifier-driven pipeline maintains an agent-readable pseudocode
layer on their behalf. More broadly, SaP’s
discipline—each LLM extraction is a hypothesis checked by
deterministic rules, not a black-box output—transfers to other
prose-to-structure tasks (schemas from runbooks, terms from legal
docs, API specs from wikis). The four checks vary per domain; the
rule generalises: accept with a witness, reject with a named cause.

interpretation of the numbers in

limitations (single-model sweep, single-LLM-family pipeline,
synthetic-only negative controls, no human user study, English-only,
deferred recursive split / repair loops) are detailed in

.

The fourth verifier check (

adversarial chains, or higher-level reasoning failures—but it does
prevent the most direct failure mode where library factorization
silently aggregates unsafe operations.

Dual use.

A malicious actor could in principle apply the same pipeline to
compress a library of harmful tools. The method is content-neutral:
SaP factors whatever subprocedures recur, without judging
whether the underlying skills are beneficial. We discourage such
applications and do not provide a harm-classification step.

Appendix G
Extended limitations

The main-text limitations (
Limitations
) cover
single-seed, SkillsBench subset, single library, and static
replacement. We list secondary limitations here for completeness.

Single agent / single model.

ALFWorld evaluations use
gpt-4o-mini
; SkillsBench uses

gpt-5-codex
(best-of-1, no retries). Behavior under
substantially weaker (e.g.,
7
B class) or stronger (e.g.,
reasoning-heavy) models is not tested. The
+50\%
relative gain may
be amplified or attenuated under different agent capabilities; a
sweep across model scales is needed.

Single LLM family for pipeline + ablation.

Both BE and RC use
gpt-4o-mini
. Repeating the
pipeline with a different LLM family (Claude, Gemini) would test
whether the
+5
pp /
+5
pp ablation effects reproduce or whether
they are specific to a particular model’s behaviour. Per-pass cost
is
\sim\$0.30
, so this is a feasible next experiment.

Negative controls are synthetic.

Calibration uses
30
controls of three synthetic classes
(
B_same_domain_distinct
,
C_near_miss
,

D_swapped_contract
). Real adversarial inputs—e.g., a
candidate cluster that looks coherent to the LLM but is semantically
broken—are not represented. The calibrated
0\%
FP on synthetics
is a
lower bound
on practical FP; field FP on real mis-clustered
candidates would require human gold labels we do not have.

No human user study.

We use deterministic proxies (binary task reward, token count,
verifier-call counts). We do not measure downstream user-perceived
agent quality, latency under realistic load, or developer-side
maintenance cost reduction. The latter is arguably the most direct
motivation for library factorization but is not in scope here.

English-only.

All parsed skills are in English. Cross-lingual
SKILL.md
or
non-English OpenAPI documentation is untested.

Recursive split and repair loops deferred.

The pipeline includes scripts for (a) recursive splitting of
over-wide rejected clusters into sub-clusters that may pass
verification, and (b) a
1
–
2
-round LLM repair loop on borderline
rejects. Both are implemented but disabled by default in this
paper’s results, to keep the ablation cleanly attributable to the
two LLM-aware passes we evaluate. Enabling either is expected to
further increase promotion yield.

Appendix R
Spurious BE call-site patterns

The
630
deterministic call-sites BE dropped as spurious cluster
into two dominant patterns: (i) units that share keywords with the
contract but describe a distinct procedure (a Bundled Resources
list containing the file-helper child’s name, classified as an

io-helper
call-site); (ii) units that mention the
contract’s domain abstractly without invoking it (a Risk bullet
“do not delete
output.json
” classified as a

file-delete
call-site). Both patterns survive the
deterministic per-unit binding filter because each unit

does
contain a relevant token; only a prompt-aware LLM
seeing the full contract can tell that the unit is not an
invocation.

T.4
LLM prompts

Stage 3 contract extractor (system prompt, abridged).

You are extracting a typed callable contract from a cluster of
procedural units across multiple parent skills. Return STRICT JSON:
{id, trigger, input_schema, output_schema, preconditions,
postconditions, side_effects, rationale}. If the cluster contents
are too heterogeneous to unify, return
{_extraction_failed: true, reason: ...}.

Binding Extraction pass (system prompt, abridged).

You decide whether a procedural unit is genuinely a call of the
given child skill, and if so extract per-input bindings. Output:
{should_invoke: bool, confidence: low|medium|high, bindings:
{name: source_substring}, residual_parent_text: ..., rationale:
...}. For every required input you MUST provide a binding that
overlaps with the unit text, else should_invoke=false.

Rewrite Cleanup pass (system prompt, abridged).

Some passages of this rewritten parent may still describe operations
that the listed child contract already covers, or may contradict the
child’s stated I/O. Rewrite such passages to use
invoke(child_id, args). Keep parent-specific text. Do not introduce
content absent from the original. Sanity post-check: every listed
child contract must still appear at least once.
