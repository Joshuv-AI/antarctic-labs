Causal Past Logic for Runtime Verification of Distributed LLM Agent Workflows
Benedikt Bollig

Abstract
Distributed LLM agent workflows should not be monitored as if they produced a single sequential log. In an asynchronous execution, a decision can only depend on events that are causally visible to the lifeline that makes it: an event that appears earlier in some log may still be unknown locally. We extend the ZipperGen agent-workflow framework with Causal Past Logic (CPL), a small past-time temporal logic for guards in conditionals and while loops. In addition to standard past-time modalities such as previous and since, a guard can inspect the latest causally visible event of another lifeline and selected variables stored there. The formula is a source-level guard: it is evaluated online by the owner lifeline and can influence control flow at runtime. We give a vector-clock monitor with latest-value views and prove that the locally computed monitor value coincides with the denotational semantics of the guard at the current event. Thus runtime verification becomes part of the coordination language itself, rather than a post-hoc check over an execution log.

Introduction

Large language models have led to the development of LLM agents, where language models are equipped with tools and can execute actions. Many useful applications do not rely on a single agent, but on several interacting agents that work on separate tasks and maintain separate contexts. This can improve efficiency and can also make the system easier to structure: each agent has its own role, its own local information, and its own interaction history. In practice, this separation may also reduce unnecessary context growth.

However, these agents still need to communicate. They exchange plans, findings, approvals, warnings, and intermediate results over communication channels. At this point, agent workflows become distributed systems. This is useful, but it also brings back the usual difficulties of distributed programming. Failures are not limited to wrong LLM outputs. A committer may merge a patch whose tests have since failed. An executor may rely on an approval that was given for an earlier version. A reviewer may see a message that is locally the latest one received, although it does not contain the latest information available elsewhere in the system.

Runtime verification
[
30
,
6
,
4
]
is a natural way to complement static coordination guarantees in this setting. In classical runtime verification, one specifies properties of executions, often in a temporal logic, and monitors check at runtime whether the current execution satisfies the specification. If something goes wrong, the monitor can raise an alarm. For agent workflows, however, it is often not enough to report a violation after the fact. Monitoring should also affect the execution at the point where a decision is made. If a committer has not seen a clean test result in its causal past, the right response is not to merge and report a violation later. The workflow should instead take another branch: block the merge, request a re-run, or escalate.

We develop this idea for ZipperGen
[
11
]
. ZipperGen programs
are written as global workflows and projected to local agent programs that
communicate asynchronously. It follows the general philosophy of
choreographic programming
[
14
,
35
,
43
,
24
]
:
the programmer writes the coordination from a global point of view, and the
framework derives the local behavior of the individual agents. We use the
term lifeline for the local participant, usually an agent, that executes its
part of the workflow. In ZipperGen, branch and loop decisions have an
explicit owner lifeline. The projection inserts control broadcasts so that
the lifelines that need to know a decision are informed about it.

The point of this paper is that even with such a projection discipline, which guarantees deadlock-freeness, runtime decisions may depend on causal information that is not easy to track by hand. Messages exchanged between agents create causal dependencies. As a result, the latest message received by an agent is not necessarily the latest relevant information produced by another agent. Conversely, information that appears earlier in a sequential log may not be causally visible to the agent that is about to make a decision. Thus, for distributed agent workflows, monitoring should not be interpreted over an arbitrary sequential log. It should be interpreted over causally structured executions. Since guards are evaluated by their owner lifeline, monitoring is distributed as well: a decision cannot rely on a complete sequential log maintained by a central observer.

The same issue also arises with per-lifeline parallel composition. Several
local actions of the same lifeline may be enabled at the same time, and their
actual order may be chosen at runtime rather than fixed statically by the source
workflow. Runtime guards should therefore be evaluated against the causal
information available at the event where the decision is actually made.

To address this, we extend the guard language of ZipperGen with Causal Past Logic (CPL), a small past-time logic interpreted over message sequence charts (MSCs), which depict lifelines and the messages exchanged between them. A guard is written as
\varphi\mathord{\mathtt{@}}A
and is evaluated locally by lifeline
A
, which owns the corresponding branch or loop. CPL formulas can express causal-temporal facts such as “the owner has causally seen that the tests passed, and has not seen any later visible failure”. They can also combine such facts with identity checks, for instance whether the visible test result concerns the same merge candidate as the current proposal.

Unlike external runtime specifications, CPL formulas are source-level guards.
They are not checked beside the workflow after the fact: their truth values
choose the next branch or loop step. This is why the logic is past-time:
at each decision point, the owner lifeline must determine the guard from
the information causally visible to it. An external monitor could only report verdicts
on an execution that has already happened. A guard, on the other hand, determines what the
execution becomes.

This perspective also differs from many guardrail mechanisms for LLM applications, which treat the execution as a sequential log. Such logs are useful for debugging and auditing, but workflow control needs a different notion of past: what matters is what is causally visible at the decision point.

Contributions.

We extend ZipperGen guards with Causal Past Logic formulas that are evaluated at runtime and influence the control flow at decision points. Formally, CPL formulas are interpreted at runtime events, and guard evaluation is represented by a choice event on the owner lifeline. In addition to standard past-time temporal modalities, such as previous and since along one lifeline, the logic contains causal past modalities and access to the values of variables at the latest visible event of a lifeline. This allows formulas to compare information from different lifelines. We give an online monitoring algorithm based on vector clocks and latest-value views, and prove that local runtime evaluation coincides with the denotational MSC semantics. We also report on a prototype implementation in ZipperGen (
https://zippergen.io
).

A Distributed Code Review Example

In an LLM agent workflow, agents exchange messages over dedicated channels
and have no shared memory. In the formal development, we call each
agent a
lifeline
. In this section, we use the two terms
interchangeably.

Consider a coding-agent workflow in which a patch is checked by several
specialized agents. A TestRunner executes the test suite, a Security agent
checks for vulnerabilities, and a Committer decides whether a merge
candidate may be merged. These agents run concurrently and report their
results asynchronously. They may also send updated assessments after an
initial result. For example, the required pre-merge checks may pass, while
a subsequent check detects a regression. Similarly, a
security scan may first clear a patch and later report a vulnerable
dependency.

The Committer may merge a pull request only if, in its causal past, the
required tests have passed with no later visible failure, and the security
scan has cleared the patch with no later visible critical issue. Both
results must concern the same merge candidate as the current proposal.

A monitor that uses a sequential log ordered by send time would see the

Committer can enforce locally: the failure exists in the global execution,
but it is not yet causally visible at the decision point. The policy
expressed here is therefore not “merge only after all checks have
finished”, but “merge once the required checks have passed, unless a
later visible failure has appeared”. If the intended policy is stronger,
the workflow must add synchronization before the merge proposal. CPL does not replace such synchronization. It makes explicit which
information is visible at the local decision point.

3
Message Sequence Charts

We model agent-workflow executions as
message sequence charts

(MSCs). An MSC consists of
events
distributed over lifelines. Each
event represents one observable step: sending or receiving a message,
executing a local action, or making a branching decision.
Events on the same lifeline are linearly ordered. Messages are represented
by matching send and receive events. In prefixes, some sends may not yet
have been received. The causal order combines local succession with message
delivery. Figure
2
shows a small MSC for the
merge scenario: the Orchestrator sends a merge proposal to the Committer,
the TestRunner sends a result that arrives before the proposal, and a later
update is still in transit at the choice event.

We enrich each event with a
valuation
. The valuation at an event
records the local state of the corresponding lifeline after that event. It
is a mapping from variables to values, for instance the current merge
candidate or the latest test status. The MSC semantics specifies where
formulas are evaluated and which valuations they may inspect. It does not
define the internal store semantics of the agents.

Let
\mathscr{L}
be a finite set of lifelines.

Definition 1
(Message Sequence Chart (MSC)

)

A
Message Sequence Chart (MSC)
over
\mathscr{L}
is a tuple

M=(E,\to,\lhd,\mathsf{kind},\mathsf{pid},\mathsf{val}),

where
E
is a finite set of events,
{\to}\subseteq E\times E
is the local successor
relation,
{\lhd}\subseteq E\times E
is the message relation,

\mathsf{kind}:E\to\{\mathsf{act},\mathsf{recv},\mathsf{choice}\}\uplus(\{\mathsf{send}\}\times\mathscr{L})

classifies events. A send event has kind
(\mathsf{send},B)
, where

B
is its intended receiver. The map
\mathsf{pid}:E\to\mathscr{L}

assigns each event to its lifeline, and
\mathsf{val}
assigns an event valuation to each event. For

A\in\mathscr{L}
, define

E_{A}=\{e\in E\mid\mathsf{pid}(e)=A\}

and

{\to_{A}}={\to}\cap(E_{A}\times E_{A}).

The tuple satisfies the following conditions.

(i)

The relation
\to
is local: if
e\to f
, then

\mathsf{pid}(e)=\mathsf{pid}(f)
.

(ii)

For each
A
, the relation
\to_{A}
is the immediate-successor
relation of a finite linear order on
E_{A}
. We write
\leq_{A}

for its reflexive transitive closure and
<_{A}
for the corresponding
strict order.

(iii)

The message relation
\lhd
is a partial matching between send and
receive events. If
s\lhd r
, then

\mathsf{kind}(s)=(\mathsf{send},\mathsf{pid}(r)),\qquad\mathsf{kind}(r)=\mathsf{recv},\qquad\mathsf{pid}(s)\neq\mathsf{pid}(r).

Every receive has exactly one matching send, and every send has at most
one matching receive. Unmatched sends are messages still in transit, but
their intended receiver is still given by their event kind. Note that
messages are not necessarily delivered in FIFO order.

(iv)

The graph generated by local successor edges and message edges is
acyclic.

The Lean development formalizes event kinds, message matching, and the
semantic interface used by CPL: lifelines, local order, causal order,
valuations, and the previous-local and latest-visible navigation
operations.

The causal order
\leq_{M}
is the reflexive transitive closure of local
successor edges and message edges.
By acyclicity,
\leq_{M}
is a partial order.
We write
e<_{M}f
if
e\leq_{M}f
and
e\neq f
.

For an event
e
, we write
\nu_{e}:=\mathsf{val}(e)
.
Thus
\nu_{e}(x)
is the value of variable
x
at event
e
.
One can think of
\nu_{e}
as the local store of the lifeline after event

e
. Actions and receives may update this store, while send and choice events
typically leave it unchanged. For choice events,
\nu_{e}
is the store on which the
guard is evaluated.

Causal Past Logic

This section defines the guard language used at decision events. The logic
is past-time: formulas are evaluated at an event and refer only to the
local and causally visible history of that event.

Definition 2
(CPL syntax

)

Variable terms

t

atomic conditions

\alpha

CPL formulas

\varphi

\begin{array}[]{rcl}t&::=&x\mid\mathord{\mathtt{@}}A.x\qquad\alpha::=p(t_{1},\ldots,t_{n})\\[2.15277pt]
\varphi&::=&\alpha\mid\mathord{\mathtt{@}}A(\varphi)\mid\mathsf{Y}\varphi\mid\varphi_{1}\mathbin{\mathsf{S}}\varphi_{2}\mid\varphi_{1}\wedge\varphi_{2}\mid\varphi_{1}\vee\varphi_{2}\mid\neg\varphi.\end{array}

Here,

p
ranges over
application-level predicate symbols. We use standard mathematical
notation for common predicates. Thus

abbreviates a unary
predicate on
x

abbreviates a
unary predicate on
\mathit{status}
, and

\mathord{\mathtt{@}}\mathsf{TestRunner}.\mathit{candidate}=\mathit{candidate}

abbreviates a binary equality predicate applied to the two displayed
terms.

Moreover,
\mathsf{Y}
and
\mathbin{\mathsf{S}}
are the usual previous and since operators
from past-time linear temporal logic, interpreted along the current
lifeline. The operator
\mathord{\mathtt{@}}A(\varphi)
is the causal part: it evaluates

\varphi
at the latest visible event of lifeline
A
. The term

\mathord{\mathtt{@}}A.x
is different. It reads the value of
x
at that event
and can only occur inside atomic conditions.

Let
e\in E
, and let
A=\mathsf{pid}(e)
. Define the previous local
event, if it exists, by

\mathsf{last}_{\mathsf{loc}}(e)=\max\{f\in E_{A}\mid f<_{A}e\}.

For any lifeline
B

B
from
e

\mathsf{last}_{B}(e)=\max\{f\in E_{B}\mid f\leq_{M}e\}.

Both maxima are unique when they exist, since events on a lifeline are
linearly ordered.

The value of a variable term at event
e
is partial. It is defined by

[\![x]\!]_{M}(e)=\nu_{e}(x)\qquad\text{and}\qquad[\![\mathord{\mathtt{@}}A.x]\!]_{M}(e)=\nu_{\mathsf{last}_{A}(e)}(x),

when the right-hand side is defined. Atomic conditions are evaluated only
when all variable terms occurring in them are defined. If any term in a
predicate atom or comparison is undefined, then the atom is false. In particular, if no latest visible
A
-event exists,
then any atomic condition using
\mathord{\mathtt{@}}A.x
is false. Thus

\mathord{\mathtt{@}}A.x
always reads the latest visible value of
x
on
lifeline
A
. This is the current event itself when
e
is on
A
,
and the latest causally visible
A
-event otherwise. Strict movement is
expressed separately with the local previous operator
\mathsf{Y}
. For
example,
\mathord{\mathtt{@}}A(\mathsf{Y}\varphi)
moves to the latest visible
A
-event
and then one local step back.

The application fixes how atomic conditions are evaluated. We write

\nu_{e}\models_{M}\alpha

when the atomic condition
\alpha
is true at event
e
. The judgment
may depend on
M
, because terms of the form
\mathord{\mathtt{@}}A.x
are
resolved through the causal structure of the MSC. All unqualified variables
are read from
\nu_{e}
. Atomic predicates may also inspect fixed event
metadata, such as the event kind, but the examples below use only
local-store and latest-value data. Thus, the application fixes the atomic predicates,
while the MSC semantics fixes the temporal and causal operators.

\displaystyle M,e

The lifeline-specific form is

Online Monitoring

At runtime, each guard is evaluated by its owner lifeline. The monitor must therefore track which events are causally visible at the current event. Each lifeline
A
maintains a vector clock
[
27
,
20
,
32
]
, which is of the form

\mathsf{vc}_{A}:\mathscr{L}\to\mathbb{N}.

We use vector clocks after the current event has been processed. Thus,
after processing an event
e\in E_{A}
, the value
\mathsf{vc}_{A}(B)

records how many events of
B
are in the causal past of

e
, including
e
itself when
B=A
. This matches the non-strict
semantics of
\mathord{\mathtt{@}}B(\varphi)
and
\mathord{\mathtt{@}}B.x
: both refer to
the latest visible
B
-event. We let
e^{B}_{k}
denote the
k
-th event on lifeline
B

(where indexing starts at 1).

Let
\Phi
be a finite set of CPL formulas,
\mathsf{sub}(\Phi)
the set of
all their subformulas, and
\mathsf{Vars}(\Phi)
the set of variable
names that appear in
cross-lifeline
terms
\mathord{\mathtt{@}}B.x
in

\Phi
. For the workflow under consideration,
\Phi
contains
all CPL guards that can be evaluated at runtime, where derived shorthands
such as
\mathsf{P}_{A}
are unfolded to primitive CPL syntax before taking
subformulas. The monitor state is designed to answer three kinds of local
queries: strict previous-local formulas, latest visible formulas on each
lifeline, and latest visible field values used by terms

\mathord{\mathtt{@}}B.x
. This is formalized in the following definition:

Definition 4
(Monitor state

)

At each lifeline
A
, the monitor maintains:

•

a
vector clock

\mathsf{vc}_{A}:\mathscr{L}\to\mathbb{N}
;

•

a partial
Boolean latest-value view

\mathsf{view}_{A}:\mathscr{L}\times\mathsf{sub}(\Phi)\rightharpoonup\{0,1\}
;

•

a partial
variable view

\mathsf{var}_{A}:\mathscr{L}\times\mathsf{Vars}(\Phi)\rightharpoonup\mathsf{Val}
,
where
\mathsf{Val}
is the domain of stored values;

•

a
local store

\sigma_{A}
for the current event valuation;

•

a
previous-local copy

\mathsf{old}_{A}(\psi)\in\{0,1\}
for each

\psi\in\mathsf{sub}(\Phi)
, used during formula evaluation.

In a stable state, after an event update has completed, the clock is the
presence test for the two latest-value tables: entries with first
component
B
are defined exactly when
\mathsf{vc}_{A}(B)>0
. If

\mathsf{vc}_{A}(B)=k>0
, those entries refer to the
k
-th event of
B
; if

\mathsf{vc}_{A}(B)=0
, they are absent.

The previous-local copy
\mathsf{old}_{A}
is total, not partial. At the first
event of
A
, it is set to
0
for every
\psi\in\mathsf{sub}(\Phi)
.

For a fixed workflow, the Boolean part of the monitor state has size
O(|\mathscr{L}|\cdot|\mathsf{sub}(\Phi)|)
per lifeline, plus the temporary local copy used during one update. Variable views add
O(|\mathscr{L}|\cdot|\mathsf{Vars}(\Phi)|)
selected data values. The vector-clock components are unbounded counters. This is consistent with lower bounds showing that finite-state monitors cannot in general track latest values exactly
[
9
]
. In practice, these counters are bounded by the lifetime of the run or a timeout.

We reason about a run by fixing an arbitrary linear extension of the causal order of the MSC. Each event is processed by the monitor of its own lifeline when that event occurs. The prefix processed before an event is therefore causally closed: if an event has been processed, all of its causal predecessors have been processed as well.

When lifeline
A
creates a new event, the monitor runs Algorithm
1
. For a receive, it first merges the vector clock, Boolean views, and variable views carried by the incoming message. Entries are copied from the message exactly when the message is ahead on a lifeline
B
. In that case the message clock is positive on
B
, so the corresponding message entries are defined. The monitor then increments its local clock component, updates the local store, evaluates all subformulas bottom-up (Algorithm
2
), and records the results. All messages carry vector clocks and latest-value views; the algorithm treats user messages and projection-internal control messages uniformly.

The local store update is performed only by
\mathsf{effect}
: actions and receives update the store, while sends and choice events leave it unchanged.

7
Conclusion

We presented Causal Past Logic, a past-time temporal logic for source-level
guards in distributed agent workflows. Guards are evaluated locally by the
lifeline that owns a branch or loop, and their truth values choose the next
control-flow step. The relevant past is not a prefix of a global log, but the
causal past visible at the MSC event where the decision is made.
Future work includes evaluating the implementation on
realistic LLM agent workflows, including concurrent code review with test
and security checks, retries, and handoff to a human reviewer.
