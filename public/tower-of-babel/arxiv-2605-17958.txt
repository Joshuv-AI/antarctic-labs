Enhancing the Code Reasoning Capabilities of LLMs via Consistency-based Reinforcement Learning
Zhanyue Qin, Jia Feng, Yibo Lyu, Yun Peng, Dianbo Sui, Cuiyun Gao, Qing Liao

Abstract
Code reasoning refers to the task of predicting the output of a program given its source code and specific inputs. It can measure the reasoning capability of large language models (LLMs) and also benefit downstream tasks such as code generation and mathematical reasoning. Existing work has verified the effectiveness of reinforcement learning on the task. However, these methods design rewards solely based on final outputs or coarse-grained signals, and neglect the inherent consistency of the stepwise reasoning process in the task. Therefore, these methods often result in sparse reward or reward hacking, which limits the full play of enhanced learning capabilities. To alleviate these issues, we propose CodeThinker, a consistency-driven reinforcement learning framework for code reasoning. Specifically, the CodeThinker has three key components: 1) a stepwise reasoning-aware model training module, which utilizes a consistency tracing paradigm as a template to synthesize training data that captures the stepwise reasoning process, 2) a dynamic beam sampling strategy, which aims at improving the quality of sampled samples under a fixed sampling budget, and 3) a consistency reward mechanism that can effectively alleviate the reward hacking. Experiments on three popular benchmarks show that CodeThinker achieves state-of-the-art performance across multiple LLMs. For instance, it outperforms the strongest baseline by 4.3% in accuracy when deployed on Qwen2.5-Coder-7B-Instruct. We also validate the effectiveness of CodeThinker on downstream tasks. Results show that without additional training, CodeThinker obtains average accuracy gains of 5.33 and 3.11 percentage points on mathematical reasoning and code reasoning tasks covering 17 programming languages, respectively.

Code Reasoning Training Data Construction

Existing training datasets for code reasoning suffer from insufficient logical complexity. For instance, synthetic code datasets built with Python built-in functions (e.g.,
list.append()
) in prior work
[
31
]
generally lack elaborate logical structures, providing limited training value for code reasoning models.
To address this limitation, we construct a competition-level code reasoning training dataset named LeetCodeReasoning built upon LeetCodeDataset
[
36
]
, which is sourced from the LeetCode algorithm competition platform.
The construction pipeline of our dataset consists of four steps.

Step 1: Static Filtering

We employ Abstract Syntax Trees (AST)
[
9
,
1
]
to perform static analysis on the code within the LeetCodeDataset.
We retain only function-level code, filter out samples containing fewer than five lines of code, and remove redundant information such as blank lines, comments, and function signatures.
Following this step, we obtain 1,673 distinct code snippets.

Step 2: Unit Test Generation

Leveraging Qwen3-32B
[
38
]
, we generate 15 sets of function inputs for each of the 1,673 functions obtained in the previous step. Since the model only needs to comprehend the function signature and input format, this generation task is straightforward and yields high-quality results. This step produces a total of 25,095
(code, input)
pairs.

Step 3: Execution Filtering

We execute each function with its corresponding generated input to obtain the expected output, forming
(code, input, output)
triples. We then apply rigorous filtering: discarding samples that failed to execute, samples that timed out (2s), and so on. Following this step, we retain 10,132 samples.

Step 4: Similarity Filtering

Inspired by
31
, we use the
all-mpnet-base-v2
sentence embedding model to vectorize the code from the 10,132 samples obtained in the previous step, as well as code from three benchmarks: CRUXEval
[
13
]
, LiveCodeBench
[
18
]
, and REval
[
4
]
.
Subsequently, we compute the cosine similarity between our sample code and the benchmark code, and filter out all samples with a similarity score of 0.90 or higher.

After the four steps above, we obtain 9,142 samples, covering 651 distinct functions, with an average of 14.04 unit tests per function. Compared to existing datasets, our LeetCodeReasoning exhibits higher logical complexity.

Appendix

C
view the detailed comparison of our LeetCodeReasoning with existing datasets in terms of logical complexity.

3.1
Code Reasoning Paradigm: Consistency Tracing

Existing paradigms for code reasoning primarily fall into one mainstream category, which is the vanilla tracing employed by
32
(
Figure

1
(B)).
This paradigm guides LLMs to conduct explicit thinking with the entire program as the basic granularity and directly yields final results.
Nevertheless, it lacks explicit tracking of intermediate program variables during the reasoning procedure.
As a result, valuable information cannot be effectively extracted from the thinking flow to reflect execution consistency, and the reasoning process is decoupled from the real program state, which frequently leads to errors in deducing variable values.

To address the above issues, we propose a novel code reasoning paradigm named
Con
sistency
Tra
cing (
ConTra
) on the consistency.
This paradigm requires LLMs to first divide a given program into several code blocks based on the logical coherence of the outermost code.
As shown in
Figure

1
(C), the outermost loop block will be treated as a separate block for only one reasoning.
After that, ConTra requires LLMs to reason through each block sequentially.
Within the ConTra paradigm, the LLMs’ output must begin with
[TRACE]
and conclude with
[/TRACE]
.
The content of each reasoning block must comprise: the actual code content of the current block (enclosed within
[CODE]
and
[/CODE]
).
The explicit thinking process undertaken by the LLM regarding that block (enclosed within
[THOUGHT]
and
[/THOUGHT]
), and the current values of the program variables explicitly tracked by the LLM (enclosed within
[LOCALS]
and
[/LOCALS]
).
Once the program tracing process is complete, an assertion must be output—placed between
[RETURN]
and
[/RETURN]
, which contains the final answer derived by the LLM.

3.3
Consistency Reward Mechanism

Recent studies indicate that reinforcement learning can further enhance the code reasoning capabilities of LLMs
[
34
,
31
]
.
However, CWM
[
34
]
and CodeReasoner
[
32
]
provide a pure ORM solely based on the correctness of the final answer, which leads to reward sparsity
[
21
,
39
,
24
]
and reward hacking
[
35
,
33
,
7
,
25
,
12
]
.
Even if ExecVerify
[
31
]
uses multiple white-box questions to calculate PRM, which mitigates the above issues.
However, the white-box questions in ExecVerify cannot allocate rewards to the reasoning process at a step granularity and does not take into account the consistency nature of code reasoning task.

In light of these observations, we propose a novel consistency reward mechanism specifically designed to address this consistency property of code reasoning.
Refer to
Appendix

E
for a detailed comparison of the consistency reward mechanism against existing work.

Let the ground-truth execution trajectory for a code-input pair be

\tau^{*}=\{(B_{t}^{*},z_{t}^{*})\}_{t=1}^{T},

(1)

where
B_{t}^{*}
denotes the
t
-th code block under the ConTra code reasoning paradigm, and
z_{t}^{*}
denotes the corresponding ground-truth local program state after executing that block.
Let a model-generated trace with ConTra be

y=\{(\hat{B}_{t},\hat{h}_{t},\hat{z}_{t})\}_{t=1}^{\hat{T}},\hat{r}

(2)

where
\hat{B}_{t}
,
\hat{h}_{t}
, and
\hat{z}_{t}
denote the generated code block, explicit thinking, and tracked local state at step
t
, respectively, and
\hat{r}
is the final predicted return value.
We define the overall reward as

\mathbb{R}(y)=\alpha\mathbb{R}_{\mathrm{proc}}(y)+\mathbb{I}\!\left[\mathbb{R}_{\mathrm{proc}}(y)=2\right]\cdot\mathbb{R}_{\mathrm{res}}(y)

(3)

where
\mathbb{R}_{\mathrm{proc}}(y)
is the PRM score with a maximum value of 2,
\mathbb{R}_{\mathrm{res}}(y)
is the ORM score with a maximum value of 2, and
\alpha
balances the contribution of process-level supervision.

Process Reward Model (PRM)

The PRM is designed to measure execution flow consistency. It first requires the generated trace to satisfy the ConTra format, including the correct use of
[TRACE]
,
[CODE]
,
[THOUGHT]
,
[LOCALS]
, and
[RETURN]
tags, as well as valid block boundaries and code-block alignment. Any invalid trace receives zero PRM score. For a valid trace, we further compare the generated local state with the ground-truth local state on a block-by-block basis.
Formally, let

\delta_{\mathrm{fmt}}(y)\in\{0,1\}

(4)

be an indicator of whether
y
satisfies the required ConTra format and block alignment constraints.
For each block
t
, define the block consistency indicator

\delta_{t}(y)=\mathbb{I}\!\left[\hat{B}_{t}=B_{t}^{*}\right]\cdot\mathbb{I}\!\left[\hat{z}_{t}=z_{t}^{*}\right],

(5)

which is
1
only if the generated code block and the tracked local state are both consistent with the ground-truth execution at step
t
.
To reflect the fact that different blocks contribute unequally to the program semantics, we assign each block a nonnegative weight
w_{t}
, computed from the cyclomatic complexity
[
26
]
of
B_{t}^{*}
.
We then define the PRM as

\mathbb{R}_{\mathrm{proc}}(y)=2\,\delta_{\mathrm{fmt}}(y)\cdot\frac{\sum_{t=1}^{T}w_{t}\prod_{j=1}^{t}\delta_{j}(y)}{\sum_{t=1}^{T}w_{t}}.

(6)

This formulation captures consistency: once the generated trajectory deviates from the ground-truth execution flow at any step, subsequent blocks obtain no reward.

Output Reward Model (ORM)

The ORM evaluates whether the final predicted return value matches the ground-truth program output:

\mathbb{R}_{\mathrm{res}}(y)=2\,\delta_{\mathrm{fmt}}(y)\cdot\mathbb{I}\!\left[\hat{r}=r^{*}\right],

(7)

where
r^{*}
denotes the ground-truth output of the program on the given input. The factor
\delta_{\mathrm{fmt}}(y)
ensures that, just like the PRM, the ORM is granted only to traces that conform to the required ConTra format; format-violating traces are denied any credit even when their final return value happens to match the ground truth.
Importantly, as shown in
Equation

3
, the ORM is activated only when the PRM reaches its maximum value, i.e., only when the entire generated trace is fully consistent with the ground-truth execution flow.
This gating mechanism tightly couples final-answer correctness with process consistency, and prevents the model from receiving high reward merely by guessing the correct answer while producing an inconsistent intermediate trace.

2

Conclusion

Guided by consistency in code reasoning task, we propose CodeThinker.
We design a consistency-based code reasoning paradigm named ConTra, and construct a competition-level training dataset called LeetCodeReasoning.
Leveraging consistency, we put forward a sampling strategy termed DBS, which improves the quality of sampled examples without increasing the sampling budget.

Appendix A
Related Work

A.1
Evaluating LLMs on Code Execution Reasoning Task

CRUXEval
[
13
]

CRUXEval introduces 800 short, self-contained Python functions (3–13 lines) paired with deterministic input/output, and decomposes execution reasoning into output prediction (CRUXEval-O) and input prediction (CRUXEval-I). Functions are filtered to be solvable mentally by an undergraduate-level programmer, making CRUXEval a clean lens on the foundational execution-following capability of code LLMs.

LiveCodeBench
[
18
]

LiveCodeBench addresses contamination and benchmark saturation by continuously sourcing date-tagged problems from LeetCode, AtCoder, and CodeForces, so that a model can be evaluated only on problems posted after its training cutoff. In addition to code generation, it covers self-repair, test-output prediction, and a code-execution scenario inherited from CRUXEval-O over more complex, human-written competition functions.

REval
[
4
]

REval explicitly probes the intermediate runtime behavior of a program, defining four tasks adapted from HumanEval and ClassEval—next-line prediction, executed-line judgment, variable-state tracing, and final-output prediction. It further introduces an Incremental Consistency score that penalizes models which give the right answer to a downstream task while failing an upstream one, putting consistency at the center of code reasoning evaluation.

CRUXEval-X
[
37
]

CRUXEval-X extends CRUXEval to a multilingual setting, automatically translating the original Python tasks into 19 programming languages via a test-guided “translate–execute–repair” pipeline that preserves content consistency across languages. The resulting benchmark contains roughly 19,000 test cases and reveals strong cross-language correlations as well as the often-poor cross-lingual generalization of Python-trained code LLMs.

A.2
Enhancing LLMs’ Performance on Code Execution Reasoning Task

CodeIO
[
20
]

CodeIO turns large-scale code corpora into a unified input/output prediction learning task, where the model is fine-tuned to predict function outputs (or feasible inputs) entirely in natural-language chain-of-thought, thus decoupling reasoning primitives—logic-flow planning, state-space search, decision-tree traversal—from code-specific syntax. A multi-turn variant, CodeIO++, further uses execution feedback to revise incorrect predictions.

SemCoder
[
8
]

SemCoder proposes monologue reasoning: a forward monologue narrates each line’s effect, the executed control flow, and variable changes, while a backward monologue abstractly describes possible prior states for non-invertible operations such as sorting or aggregation. Trained on the curated PyX corpus, this scheme yields strong CRUXEval-I/O performance with only 6.7B parameters but produces highly verbose traces and lacks any machine-verifiable variable-tracking signal.

CWM
[
34
]

The Code World Model is a 32B open-weights LLM trained from scratch with extensive mid-training on Python interpreter traces and agentic Docker trajectories, and post-trained with multi-task RL on verifiable coding, math, and software-engineering environments. Its execution-reasoning paradigm forces the model to emit explicit line-level program state after every executed statement, achieving strong long-horizon state tracking under teacher forcing but generating verbose traces that are prone to action hallucination on real programs.

CodeReasoner
[
32
]

CodeReasoner is a two-stage post-training framework—instruction tuning followed by GRPO reinforcement learning—that distills a teacher’s CoT during SFT and then applies pure outcome rewards (final-answer correctness only) during RL to encourage concise, accurate reasoning. Its training data is synthesized around Python built-in methods, which limits algorithmic depth, and its outcome-only reward leaves intermediate reasoning steps unsupervised.

ExecVerify
[
31
]

ExecVerify augments the outcome reward with verifiable white-box signals: from interpreter traces it deterministically constructs control-flow questions (next-statement prediction) and data-flow questions (variable value/type prediction), and uses a weighted sum of these binary white-box rewards together with the I/O-correctness reward as the GRPO reward function. Despite its “stepwise” label, however, the white-box questions are scored independently and lack any prefix-consistency constraint, so the model can still be credited for inconsistent reasoning chains.

Appendix B
Preliminaries: Group Relative Policy Optimization (GRPO)

We briefly review the GRPO algorithm
[
29
]
that underpins the RL stage of CodeThinker, and clarify how its sampling, advantage estimation, and surrogate objective interact with our consistency reward in
Equation

3
.

From PPO to GRPO

Standard PPO
[
28
]
optimizes a parameterized policy
\pi_{\theta}
via a token-level clipped surrogate objective and relies on a learned value network to estimate per-token advantages. In settings where rewards are only available at the trajectory level—as is typical for verifiable reasoning, math, and code execution tasks—training the value network is both expensive and unstable. GRPO removes the value network entirely and instead estimates advantages through a group-relative normalization of rewards over multiple rollouts that share the same prompt. This yields a critic-free, memory-efficient algorithm that has empirically proven well-suited to reasoning RL post-training.

Group sampling

For each prompt
x
drawn from the training distribution
\mathcal{D}
, GRPO uses the behavior policy
\pi_{\theta_{\mathrm{old}}}
to sample a group of
G
trajectories

\{y^{(i)}\}_{i=1}^{G}\stackrel{{\scriptstyle\mathrm{i.i.d.}}}{{\sim}}\pi_{\theta_{\mathrm{old}}}(\cdot\mid x),

(8)

each scored by an outcome-style reward function
\mathbb{R}(y^{(i)})
. In CodeThinker,
\mathbb{R}(\cdot)
is the consistency reward of
Equation

3
; in DBS (
Algorithm

1
), the same
G
samples are drawn under our budget-preserving allocation between independent sampling and active beam expansion, which leaves the GRPO objective formally unchanged.

Group-relative advantage

Given the group of trajectory-level rewards
\{r^{(i)}=\mathbb{R}(y^{(i)})\}_{i=1}^{G}
, GRPO estimates each trajectory’s advantage by standardization within the group:

\hat{A}^{(i)}\;=\;\frac{r^{(i)}-\mathrm{mean}\!\left(\{r^{(j)}\}_{j=1}^{G}\right)}{\mathrm{std}\!\left(\{r^{(j)}\}_{j=1}^{G}\right)+\epsilon},

(9)

where
\epsilon
is a small constant for numerical stability. Each token of trajectory
y^{(i)}
inherits the same group-relative advantage
\hat{A}^{(i)}_{t}\equiv\hat{A}^{(i)}
. Intuitively,
\hat{A}^{(i)}>0
when trajectory
i
is better than the average rollout for the same prompt, and
\hat{A}^{(i)}<0
otherwise; this group-internal contrast removes the need for a separate value baseline.

Surrogate objective

Let
\rho^{(i)}_{t}(\theta)=\pi_{\theta}(y^{(i)}_{t}\mid x,y^{(i)}_{<t})/\pi_{\theta_{\mathrm{old}}}(y^{(i)}_{t}\mid x,y^{(i)}_{<t})
denote the token-level importance ratio. GRPO maximizes the following PPO-style clipped objective, normalized within each trajectory and averaged across the group:

\displaystyle\mathcal{J}_{\mathrm{GRPO}}(\theta)

\displaystyle=\mathbb{E}_{x\sim\mathcal{D},\,\{y^{(i)}\}\sim\pi_{\theta_{\mathrm{old}}}}\!\bigg[\frac{1}{G}\sum_{i=1}^{G}\frac{1}{|y^{(i)}|}\sum_{t=1}^{|y^{(i)}|}\min\!\Big(\rho^{(i)}_{t}(\theta)\,\hat{A}^{(i)},

(10)

\displaystyle\mathrm{clip}\!\big(\rho^{(i)}_{t}(\theta),\,1-\varepsilon,\,1+\varepsilon\big)\,\hat{A}^{(i)}\Big)\bigg]\;-\;\beta\,\mathbb{D}_{\mathrm{KL}}\!\left[\pi_{\theta}\,\|\,\pi_{\mathrm{ref}}\right].

where
\varepsilon
is the clipping range and
\beta
controls a KL regularizer against a reference policy
\pi_{\mathrm{ref}}
(typically the SFT checkpoint). The first term encourages each token of better-than-average trajectories to be up-weighted (and conversely for below-average trajectories), while the clipping operator caps the per-step policy update, preventing destructively large ratio shifts. Compared with PPO, GRPO drops the value-function term and the GAE bootstrapping, which we empirically observe to be both unnecessary and harmful when rewards are sparse and trajectory-level.

KL regularization choices

GRPO admits two common ways of incorporating the KL term: (i) as an auxiliary loss with coefficient
\beta
as in
Equation

10
; or (ii) as a penalty subtracted from the per-token reward before computing
\hat{A}^{(i)}
. As listed in
Table

11
, we deliberately disable both variants so that the policy is shaped solely by our consistency reward; we also set the entropy coefficient to zero. This minimal configuration follows recent observations
[
24
,
39
]
that, with a sufficiently informative process reward, KL and entropy regularizers often hurt rather than help rule-based RL on code or mathematical reasoning.

Why GRPO suits code reasoning

Three properties of GRPO are particularly aligned with our setting. First, the group-relative advantage in
Equation

9
converts the consistency reward into a contrastive signal that identifies, among
G
rollouts on the same program, which ConTra trajectory is more execution-faithful—this is exactly what our prefix-consistency design is meant to expose. Second, the absence of a learned critic makes GRPO compatible with DBS, which alters the within-prompt sampling distribution in a way that would otherwise complicate value-function training. Third, the trajectory-level reward
\mathbb{R}(y)
in
Equation

3
is naturally consumed by GRPO without any reward-shaping detour, while the hard gate
\mathbb{I}[\mathbb{R}_{\mathrm{proc}}=2]
is preserved end-to-end.

Appendix D
Details of Consistency Tracing Code Reasoning Paradigm

D.1
Strict Formatting Requirements

Whenever the ConTra format is required—both during rejection sampling in the SFT phase and during reward computation in the GRPO phase—we apply a strict, deterministic format validator
\delta_{\mathrm{fmt}}(\cdot)
. A trace is accepted (
\delta_{\mathrm{fmt}}=1
) only if it satisfies
all
of the following constraints; otherwise it is treated as a format violation and assigned zero reward.

Outer wrapper.

•

The trace must begin with a single line
[TRACE]
and end with a single line
[/TRACE]
.

•

Every tag line—
[TRACE]
,
[/TRACE]
,
[CODE]
,
[/CODE]
,
[THOUGHT]
,
[/THOUGHT]
,
[LOCALS]
,
[/LOCALS]
,
[RETURN]
,
[/RETURN]
—must appear on its own line with no leading or trailing whitespace.

Block structure.

Between
[TRACE]
and
[/TRACE]
, the trace must contain one or more blocks followed by exactly one
[RETURN]
block. Each ConTra block must appear in the strict order

\texttt{[CODE]}\;\rightarrow\;\texttt{[/CODE]}\;\rightarrow\;\texttt{[THOUGHT]}\;\rightarrow\;\texttt{[/THOUGHT]}\;\rightarrow\;\texttt{[LOCALS]}\;\rightarrow\;\texttt{[/LOCALS]},

with no missing or reordered tags, and none of the three sections may be empty.

Code section.

Every line inside
[CODE]…[/CODE]
must match the pattern
[LINENO
X
]␣␣␣␣<source line>
, where
X
is a non-negative integer. Within a block the line numbers must be strictly consecutive (
X_{k+1}=X_{k}+1
); across blocks they must continue without gaps—the first block must start at
LINENO 0
, and block
i+1
must start at
X_{\text{end}}^{(i)}+1
.

Locals section.

The content of
[LOCALS]…[/LOCALS]
must parse via
ast.literal_eval
into a Python
dict
. Any unsafe expression (function calls, comprehensions over names, etc.) is rejected.

Return section.

The content of
[RETURN]…[/RETURN]
must be a single Python
assert
statement of the form
assert f(
\cdot
) == <literal>
. The right-hand side of
==
must evaluate to a Python literal via
ast.literal_eval
(or, as a fallback, a safe
eval
); otherwise the trace is rejected.

Alignment with ground truth.

When the ground-truth execution trace is available (i.e., during rejection sampling and reward computation), the validator additionally checks: (i) the number of blocks in the model output equals the number of ground-truth blocks; (ii) each block’s
LINENO
range matches the ground-truth block boundary; and (iii) the code content of each block, after stripping leading/trailing whitespace, is line-by-line identical to the ground-truth source code.

A trace satisfies
\delta_{\mathrm{fmt}}(y)=1
iff it passes every check above; any failure short-circuits the validator and yields
\delta_{\mathrm{fmt}}(y)=0
, which in turn forces both
\mathbb{R}_{\mathrm{proc}}(y)=0
(
Equation

6
) and
\mathbb{R}_{\mathrm{res}}(y)=0
(
Equation

7
).

Appendix E
Comparison of CodeThinker Against Existing Work in Reward Design

In
Figure

12
,
Figure

13
, and
Figure

14
, we respectively present a sample drawn from CodeReasoner, ExecVerify, and CodeThinker.

Reward analysis of the CodeReasoner rollout.

For the rollout shown in
Figure

12
, the CodeReasoner reward checks only two things: whether the output respects the required format (i.e., contains a
[THOUGHT]
block followed by an
[ANSWER]
block) and whether the predicted assertion equals the ground truth. Both conditions are satisfied here, so the rollout receives the maximum reward of 2. The entire intermediate reasoning chain inside
[THOUGHT]
—including any factual or logical mistakes the model may have made about variable values—is left completely unsupervised; only the final assertion contributes to the gradient. As a consequence, a rollout whose chain of thought silently drifts from the actual program state but coincidentally guesses the correct return value would be indistinguishable, in CodeReasoner’s eyes, from a rollout whose intermediate reasoning is faithful step by step.

Reward analysis of the ExecVerify rollout.

For the rollout shown in
Figure

13
, the ExecVerify reward sums two parts. The first part rewards a correct final assertion, identical in spirit to CodeReasoner. The second part is an aggregate over a fixed-size set of independent white-box questions about intermediate execution behaviour (Q2–Q6 in this example), in which each question contributes equally to the white-box term regardless of how other questions are answered. In this rollout the assertion is correct and all five white-box answers happen to be correct as well, so the rollout earns the maximum reward of 2. Crucially, however, the white-box questions are scored independently: had the model answered, say, Q3 incorrectly while still answering Q4–Q6 correctly, it would have lost only one fifth of the white-box term and still received roughly 1.8 reward. ExecVerify therefore behaves as a multi-objective process reward—there is no consistency constraint that propagates an early mistake to subsequent steps, so an inconsistent reasoning chain can still be credited with a near-maximum reward.

Reward analysis of the CodeThinker rollout.

For the rollout shown in
Figure

14
, the ground-truth execution flow—obtained by interpreting the program with the actual input—consists of four ConTra blocks
B_{1},B_{2},B_{3},B_{4}
with cyclomatic-complexity weights
w_{1}{=}w_{2}{=}w_{3}{=}1
and
w_{4}{=}2
(since
B_{4}
contains the while loop), together with the ground-truth final value
r^{*}{=}15
. The model’s output passes the strict ConTra format check (
\delta_{\mathrm{fmt}}{=}1
), and at every block the predicted code segment and the predicted local-variable state agree with the ground truth, i.e.,
\delta_{t}{=}1
for
t{=}1,\ldots,4
. Plugging these into the prefix-consistent process reward of
Equation

6
yields
\mathbb{R}_{\mathrm{proc}}(y)=2\,\delta_{\mathrm{fmt}}\cdot\frac{\sum_{t}w_{t}\prod_{j\leq t}\delta_{j}}{\sum_{t}w_{t}}=2\cdot 1\cdot\frac{5}{5}=2
, i.e., the maximum process reward is achieved. Because the gate
\mathbb{I}[\mathbb{R}_{\mathrm{proc}}{=}2]
in
Equation

3
is now open, the result reward
\mathbb{R}_{\mathrm{res}}(y)=2\,\delta_{\mathrm{fmt}}\cdot\mathbb{I}[\hat{r}{=}r^{*}]=2
is admitted, and the total reward becomes
\mathbb{R}(y)=\alpha\,\mathbb{R}_{\mathrm{proc}}+\mathbb{I}[\mathbb{R}_{\mathrm{proc}}{=}2]\cdot\mathbb{R}_{\mathrm{res}}=2+2=4
(with
\alpha{=}1
), exactly matching the score
=4
logged in our JSONL rollout file. The qualitative difference from the previous two cases lies in the prefix-consistency factor
\prod_{j\leq t}\delta_{j}
: had the model instead predicted
x{=}8
in
B_{3}
(a typical off-by-one bit-shift mistake),
\delta_{3}
would become
0
and the prefix product would zero out the contribution of every later block including
B_{4}
, dragging
\mathbb{R}_{\mathrm{proc}}
below its maximum and closing the gate on the result reward. In such a counterfactual the rollout would receive at most a partial process reward and no result reward, even if the final return value happened to coincide with
r^{*}{=}15
by a lucky cancellation; CodeReasoner and ExecVerify, by contrast, would still pay the full final-answer reward in this case.

Appendix H
Training and Inference Details of Baselines

In this section, we provide a detailed description of the training process of the baselines and the code inference paradigm used.

H.1
CodeIO

Training

We process our LeetCodeReasoning dataset using the open-source data processing pipeline from CodeIO, resulting in a final set of 17,068 samples, which we then use for SFT.
The training hyperparameters employed for the SFT training are kept consistent with those used by CodeThinker during its SFT phase.

Inference

CodeIO uses vanilla tracing for code reasoning. An example is shown in
Figure

19
.

H.2
SemCoder

Training

Since SemCoder’s dataset processing pipeline is not open source, we extract the same number of samples from SemCoder’s open source dataset as CodeIO for SFT training.
The training hyperparameters employed for the SFT training are kept consistent with those used by CodeThinker during its SFT phase.

Inference

SemCoder employs its own unique code reasoning paradigm, which is similar to vanilla tracing but requires activation via the special token
[MONOLOGUE]
. An example is shown in
Figure

20
.

H.3
CodeReasoner

Training

CodeReasoner uses SFT and GRPO for two-stage training. During the SFT stage, we use Qwen3-32B to extract the vanilla tracing of the samples in the SFT subset of LeetCodeReasoning. We perform rejection sampling on the obtained samples to filter out the bad ones. The prompt used to extract the vanilla tracing is shown in
Figure

21
. During the GRPO stage, CodeReasoner employs a pure result reward mechanism: if the model’s response is correct, it receives full marks; otherwise, it receives a score of zero. Consequently, we can directly utilize the ground truth answers from the GRPO subset of the LeetCodeReasoning dataset for scoring, without the need for any additional processing.
The training hyperparameters employed for the SFT and GRPO are kept consistent with those used by CodeThinker.

Inference

ExecVerify uses vanilla tracing for code reasoning. An example is shown in
Figure

22
.

H.4
ExecVerify

Training

ExecVerify uses SFT and GRPO for two-stage training. During the SFT phase, the fine-tuning dataset used is consistent with the dataset used by CodeReasoner during the SFT phase. During the GRPO phase, in order to calculate white-box rewards, we used their open source piplines to extract white-box questions and answers from the code in LeetCodeReasoning’s GRPO subset.
The training hyperparameters employed for the SFT and GRPO are kept consistent with those used by CodeThinker.

Inference

ExecVerify uses vanilla tracing for code reasoning. An example is shown in
Figure

23
.

H.5
CWM

Training

CWM is a decoder-only model architecture comprising 32 billion parameters. It is trained entirely from scratch—spanning the full pipeline from pre-training through intermediate training to post-training (SFT + RL). Consequently, it is extremely difficult to apply the specific training pipeline used for CWM to our QC-7B/14B/32B, DS-6.7B, and Llama3-8B. Therefore, we directly use CWM’s publicly released weights for evaluation, comparing it in our model generalization experiments against Qwen2.5-Coder-32B-Instruct, which was trained using the CodeThinker training paradigm.

Inference

For code reasoning tasks, CWM has a unique reasoning paradigm (shown in
Figure

. The reasoning paradigm is to let CWM execute code step by step.

Appendix J
Limitation and Future Work

Language and execution environment coverage

LeetCodeReasoning is built on top of LeetCodeDataset, so all training data is in Python.
Although our cross-language evaluation on CRUXEval-X (
Table

12
) shows that CodeThinker trained purely in Python still yields consistent gains across 17 other programming languages,
we have not yet retrained on languages with runtime semantics markedly different from Python (e.g., manual memory management in C/C++, or strict static typing in Java), and whether retraining further improves performance remains open.
A natural next step is to extend CodeThinker to more language runtimes, or to port it onto a unified symbolic execution engine so that block-level states can be verified in a language-agnostic way.

Problem complexity and real-world code

Constrained by LeetCodeDataset, our LeetCodeReasoning data is at the single-function level, which is still far from complex real-world, particularly repository-level code.
Mainstream code reasoning benchmarks such as CRUXEval, LiveCodeBench, and REval share the same limitation.
A promising direction is to lift code reasoning to the repository level, design evaluation protocols for repository-level code reasoning, and apply CodeThinker to such tasks.

Granularity in the ConTra code reasoning paradigm

Our ConTra paradigm operates at code-block granularity, a design choice that keeps the generated execution trajectory both human-readable and machine-verifiable while controlling its length.
However, this granularity is fixed at the extraction stage: simple blocks may be over-annotated, while loops or recursive blocks with rapidly changing states may be too coarse to be fully parsed.
An adaptive ConTra variant that dynamically chooses block boundaries based on cyclomatic complexity or local data-flow density could provide finer signals where it matters and coarser signals elsewhere.

Beyond code execution reasoning

We view code execution reasoning as a means to probe the depth of code understanding rather than the ultimate goal.
The reward mechanism we designed reflects an underlying consistency principle, whose applicability extends far beyond input-output prediction.
We are actively exploring this principle in other settings, including unit-test-guided code generation, fault localization, repository-level code edit prediction, and execution-trace generation for long-horizon code agents.
A comprehensive empirical study of these extensions is left to future work.
