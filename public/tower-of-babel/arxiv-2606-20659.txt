Skill Coverage: A Test Adequacy Metric for Agent Skills
Boyin Tan, Xiaowei Huang, Youcheng Sun

Abstract
Agent skills encode reusable procedural knowledge that guides large language model (LLM) agents across tasks and execution contexts. Existing evaluations primarily assess skills through task-level outcomes, yet task success alone does not reveal which parts of a skill have been exercised or which remain untested. We introduce skill coverage , a test adequacy metric that treats the skill artifact as the object under test. Our approach extracts observable skill behavior constraints from skill documents and measures whether an agent trajectory provides sufficient evidence to exercise and evaluate each constraint. Skill coverage uses a binary cover/not-cover judgment: it reports whether a documented behavior has been exercised with sufficient observable evidence, without assigning an additional outcome label to the behavior. Applying skill coverage to SkillsBench reveals that existing benchmark executions cover only 39.90–43.98% of skill behavior constraints, suggesting that current benchmark tasks leave large portions of documented skill guidance untested. These findings show that successful task completion does not imply adequate testing of the skill artifact, highlighting skill coverage as a measure of how thoroughly agent skills are tested. Project website: https://shuaijiumei.github.io/skillcoverage/ .

agent skills, agent systems, software testing, test adequacy, skill evaluation

Introduction

Agent skills package procedural knowledge in a structured form that can augment LLM agents at inference time
(
1
;
11
)
.
Studies of public skill ecosystems and cumulative skill creation further show that skills are emerging as reusable artifacts that can be shared across agents and tasks
(
7
;
22
)
.
Benchmark evidence also shows that such skills can improve downstream task utility across diverse domains
(
11
;
25
;
14
)
.

Although recent benchmarks
(
11
)
demonstrate that skills can improve agent performance, they primarily provide a task-level signal of whether a skill helps an agent complete a particular task. However, task success does not indicate which instructions, expectations, or action patterns encoded in the skill were actually exercised during execution. This distinction matters because a skill is intended to be reused across tasks, models, and execution contexts. To assess whether a skill has been adequately tested, users need evidence about which parts of the skill have been exercised and which expected behaviors remain unobserved under a specific model-task setting. Such evidence enables users to make informed decisions about whether to reuse a skill for a new task, how to adapt it to a new context, and where the skill should be improved.

To provide a more informative signal for skill evaluation, we introduce a testing framework centered on
skill behavior constraints
. The framework first extracts and formalizes source-grounded behavioral constraints from natural-language skill documents, making explicit the scenarios and expected agent behaviors encoded in the skill. It then defines when such a constraint is
covered
by an agent trajectory, requiring observable evidence that the trajectory instantiated the relevant scenario and made the constrained behavior judgeable. These two components support
skill coverage
, a new adequacy perspective that reports which documented behaviors of a skill have been exercised by a test suite under a binary cover/not-cover judgment.

The key design choice is to connect skill evaluation to two testing concepts: requirements normalization and oracle-based coverage. First, we use EARS-style controlled natural language
(
15
)
to normalize heterogeneous skill prose into a finite set of source-grounded behavioral constraints. This step does not assume that a skill is a complete formal specification; instead, it formalizes the testable obligations, prohibitions, workflow steps, and artifact expectations that can serve as an auditable denominator. Second, we adapt oracle-based coverage, where an exercised element is meaningfully tested only when its effect is connected to oracle-checkable evidence
(
16
)
. For skill artifacts, this means that a documented behavior is not covered merely because the skill was loaded into the agent context. It is covered only when the observable trajectory instantiates the relevant condition and exposes enough evidence to judge the constrained behavior.

Our application to SkillsBench shows why this distinction matters. We validate
the binary cover or not-cover attribution protocol against human judgments on 350
sampled constraint–trajectory pairs, obtaining 93.71% agreement and Cohen’s

\kappa=0.874
. We then apply the validated protocol to 78 SkillsBench source
tasks across seven agent–model configurations and three traces per
configuration. The observed executions cover only 39.90–43.98% of the
extracted skill behavior constraints on average. The remaining constraints are
not necessarily violated; rather, the benchmark executions do not expose enough
scenario-specific and oracle-checkable evidence to judge them. This result
shows that task-level success can coexist with substantial untested portions of
the reusable skill artifact, making skill coverage a complementary signal to
task-level outcomes.

This paper makes the following contributions:

•

We formulate skill-level test adequacy as an artifact-level evaluation problem for reusable natural-language agent skills, exposing the missing behavioral denominator in task-level benchmark results.

•

We introduce skill behavior constraints as source-grounded, observable behavioral units extracted and formalized from skill documents while filtering out background prose and incidental implementation detail.

•

We define skill coverage over observable agent trajectories, using a binary cover/not-cover judgment to report whether a skill behavior has been exercised with judgeable evidence.

•

We validate LLM-based coverage attribution against human labels and
apply the resulting protocol to SkillsBench, showing that existing
executions cover less than half of the extracted skill behavior
denominator.

2
Problem Formulation

2.1
From Skills to Skill Behavior Constraints

A reusable skill is not merely a one-off prompt fragment for completing a
single task. Rather, it is a natural-language artifact that guides how an
agent should behave across a class of future tasks. Such guidance may describe
what the agent should do, what it should avoid, which workflow steps it should
follow, how it should use a documented tool path, or what properties its
delivered artifacts should satisfy. These prescriptions create

skill-scoped behavioral constraints
on the agent.

This view is consistent with the role of requirements in requirements
engineering, where requirements capture desired system behaviors and
constraints, and are expected to be verifiable and traceable to their sources

(
23
;
6
;
8
)
. However, a skill document is
typically not written as a conventional requirements specification. It may mix
instructions, examples, tool usage guidance, workflow steps, common mistakes,
artifact expectations, and rationale in free-form natural language. Treating
the entire skill document as a testing denominator would therefore be too
coarse and ambiguous.

We instead define a conservative abstraction called a
Skill Behavior
Constraint
(
SBC
). An
SBC
is a source-grounded, observable, EARS-normalized
condition-action rule derived from a skill document. It specifies what the
agent shall do, avoid, or deliver under skill-scoped conditions. The purpose of
this abstraction is not to recover the full semantics of the skill document.
Rather, it projects the testable portion of the skill into a finite and
auditable denominator for coverage analysis.

A retained
SBC
must be (1)
source-grounded
, supported by a concrete
source span in the skill document; (2)
constraint-bearing
, imposing an
obligation, prohibition, usage pattern, workflow progression, or deliverable
property on the agent; (3)
observable
, judgeable from execution evidence
such as tool calls, generated code, command invocations, logs, final outputs,
artifact states, file diffs, or other visible records; and (4)
atomic
,
expressing one main behavioral obligation or artifact expectation that can be
judged independently.

This boundary matters because a skill document contains more than behavioral
constraints. It may include provenance, motivation, scope descriptions,
examples, implementation snippets, warnings, and deliverable requirements in
the same natural-language artifact. Table

SBC

background prose, and rationale are excluded, while behavioral rules,
deliverable constraints, workflow steps, common mistakes, and documented

SBC

2.2
Skill Behavior Constraint Coverage

A task-level oracle verdict does not by itself characterize test adequacy.
Classical coverage asks whether the relevant elements of the artifact under
test have been exercised
(
5
;
18
;
27
)
,
while oracle-aware coverage further requires that the execution expose
evidence an oracle can inspect
(
16
;
3
)
.
For skill artifacts, this distinction is essential: loading a skill into an
agent context does not mean that any particular documented behavior has been
tested. We therefore define coverage with two binary checks: whether the
constraint applies, and whether the observable trajectory contains enough
evidence to judge the constrained behavior. The coverage judgment does not
require that the agent satisfy the behavior constraint.

Let
S
be a skill document and let
\mathcal{C}(S)
be the audited set of

SBC
s extracted from it. A constraint

c=\langle C_{c},B_{c},J_{c}\rangle\in\mathcal{C}(S)
contains the applicability
condition
C_{c}
, the constrained behavior or artifact property
B_{c}
, and the
evidence criterion
J_{c}
. Let
\tau
be one agent trajectory, and let

\mathsf{Obs}(\tau)
denote the observable evidence in that trajectory, such as
visible messages, tool calls, outputs, file states, diffs, command invocations,
logs, and final responses. For a constraint–trajectory pair
(c,\tau)
, we
define:

\displaystyle\mathsf{applicable}(c,\tau)

\displaystyle=1

\displaystyle\text{iff }\mathsf{Obs}(\tau)\text{ instantiates }C_{c},

\displaystyle\mathsf{evidence}(c,\tau)

\displaystyle=1

\displaystyle\text{iff }\mathsf{Obs}(\tau)\text{ can judge }B_{c}\text{ using }J_{c}.

Each value is binary: it is 1 when the condition holds and 0 otherwise.

applicable
checks whether the constraint is relevant to the observed
scenario. For example, a formula-preservation constraint is relevant only when
the trajectory edits a spreadsheet whose formulas may be affected.

evidence
checks whether there is concrete evidence a judge can inspect
to decide whether the constrained behavior
B_{c}
was satisfied or not, such as
a file diff, command output, generated artifact, or cited final answer.

A constraint is covered in a trajectory only when both checks pass:

\mathsf{cov}(c,\tau)=\mathsf{applicable}(c,\tau)\cdot\mathsf{evidence}(c,\tau).

Because both terms are binary, the product is 1 only when the constraint is
applicable and supported by adjudicable evidence. Otherwise it is 0. This
binary label reports whether the trajectory creates an observable opportunity
to judge the documented skill behavior. If the evidence shows that the agent
satisfied
B_{c}
, the covered case could be further interpreted as a pass; if
the evidence shows that the agent violated or omitted
B_{c}
, it could be
interpreted as a fail. The skill-coverage metric used in this paper collapses
both cases into the binary covered label because both expose judgeable evidence
about the skill constraint.

For a test suite or benchmark execution set
T
, a constraint is counted as
covered if at least one trajectory in
T
covers it:

\mathsf{covered}_{T}(c)=\max_{\tau\in T}\mathsf{cov}(c,\tau).

Suite-level
SBC
coverage is then the average of this covered indicator over
the skill’s audited constraint set:

\mathsf{SBCCov}(S,T)=\frac{1}{|\mathcal{C}(S)|}\sum_{c\in\mathcal{C}(S)}\mathsf{covered}_{T}(c).

Here,
|\mathcal{C}(S)|
is the number of audited constraints extracted from
skill
S
. The numerator counts how many of those constraints are covered by at
least one trajectory in
T
. This definition is conservative. If a constraint
is merely present in the loaded skill document, it is not covered. If the
scenario does not instantiate the constraint’s applicability condition, it is
not covered. If the scenario does instantiate the condition but the trajectory
lacks sufficient observable evidence to judge whether the constrained behavior
was satisfied or violated, it is still not covered. Thus,
SBC
coverage
measures the portion of the skill’s documented constraints that has been made
judgeable by oracle-adjudicable evidence, rather than the portion that the
agent claims to have followed.

3
Method

Our method operationalizes skill coverage as an auditable procedure that maps
skill documents and observable agent trajectories to constraint-level coverage
judgments. Given a benchmark task, its task-associated skill documents, and the
trajectory produced by an agent, the procedure produces two artifacts: an
audited set of source-grounded skill behavior constraints and a set of
trajectory-grounded coverage labels. The design follows the definitions in
Section
2.1
and Section
2.2
, but shifts
from definitions to procedure: how constraints are extracted from skill text
and how each constraint is judged against observable execution evidence.

3.1
Overview

The method has two stages. First, the
constraint extraction
stage turns a
natural-language skill document into an auditable denominator of
SBC
s.
Second, the
coverage judging
stage compares each
SBC
against an
observable agent trajectory and decides whether the trajectory makes the
constraint covered under the binary cover/not-cover rubric. This decomposition
separates the two procedural questions needed for skill coverage: what
documented behavior the skill requires, and what observable trajectory
evidence exposes about that behavior.

3.2
Extracting Skill Behavior Constraints

The extraction stage implements the
SBC
boundary from
Section
2.1
through LLM-assisted candidate extraction
followed by human audit and repair. We use the LLM as a recall-oriented parser
over skill prose, and use human audit to decide which candidates enter the
final
SBC
set.

Given a skill document
S
, we provide the full skill document to the LLM and
ask it to extract candidate
SBC
s directly. The extraction prompt defines the

SBC
boundary from Section
2.1
, requires EARS-style
condition-action output, and includes a one-shot example that illustrates the
source-block categories and inclusion/exclusion decisions in
Table
1
. Thus, Table
1

serves as prompt guidance for what kinds of skill text should or should not
produce constraints, rather than as a separate preprocessing classifier over
segmented blocks.

The LLM proposes one or more candidate
SBC
s from the full skill document. Each
candidate records the supporting source span, applicability condition,
constrained behavior, and expected evidence for judging the behavior. The LLM
also proposes atomic splits when a passage contains multiple independently
judgeable obligations. At this stage, candidates are intentionally
over-inclusive: they are hypotheses about testable skill behavior, not the
final denominator.

Human auditors then review and repair the candidate set before it becomes

\mathcal{C}(S)
. The audit checks whether each candidate is source-grounded,
constraint-bearing, observable, and atomic. Auditors discard candidates derived
from background or incidental implementation detail, merge duplicate
candidates, split compound candidates, repair applicability conditions, and
make the expected observable evidence explicit. For example, a workflow
sentence that says to inspect a file before modifying it can yield a constraint
about the inspection step, while a rationale sentence explaining why the
workflow is useful is removed unless it independently imposes an observable
obligation.

The audited candidates are finally normalized into EARS-style condition-action
forms. This normalization is a control layer over natural-language skill prose,
not a claim that skills are complete formal specifications. Scope-wide
constraints are written with the skill’s task context as their condition, while
local constraints introduce additional triggers such as user requests, artifact
states, workflow states, or the agent’s choice of a documented tool path. The
output of this stage is the audited set
\mathcal{C}(S)
used as the
denominator for skill coverage.

3.3
Judging Coverage in Agent Trajectories

The coverage judging stage assigns a coverage label to each
constraint–trajectory pair. The input is a constraint

c=\langle C_{c},B_{c},J_{c}\rangle
and an observable trajectory
\tau
. We
first construct
\mathsf{Obs}(\tau)
by retaining evidence available to an
external evaluator: the user request, visible agent messages, tool calls, tool
outputs, command invocations, generated code, file diffs, artifact states,
logs, and final responses.

The judge follows a two-step decision procedure. First, it checks

applicability
: whether the observable task context and trajectory
instantiate
C_{c}
. If the condition is not instantiated, the constraint is
labeled
\mathsf{Uncovered}
for this trajectory. Second, it checks

adjudicable evidence
: whether the trace contains enough observable
evidence, according to
J_{c}
, to decide whether the constrained behavior
B_{c}

was satisfied or violated. If this evidence check is not satisfied, the
constraint remains
\mathsf{Uncovered}
for this trajectory.

When both checks succeed, the judge records the constraint as

\mathsf{Covered}
, regardless of whether the observed behavior satisfies or
violates
B_{c}
. Otherwise, the pair remains
\mathsf{Uncovered}
. In contrast,
a final response that merely claims compliance is not sufficient unless the
final response itself is the object constrained by the
SBC
. The judgment must
be grounded in concrete trace evidence such as a tool call, file state, command
output, generated artifact, or cited response content.

Because benchmark-scale coverage requires many constraint–trajectory
judgments, we use an LLM judge only under a validation-before-scale protocol.
This follows prior LLM-as-a-judge evaluations, where automatic judges are first
checked against human or expert judgments before being used for broader model
or output assessment
(
24
;
13
;
4
)
.
It is also aligned with fine-grained rubric and criterion-based evaluations,
where LLM judges apply predefined criteria at scale after calibration or
validation
(
21
;
9
;
17
;
2
)
.
Accordingly, the LLM judge is not treated as an uncalibrated source of model
opinion; it is used as a scalable implementation of a fixed coverage rubric
after its agreement with human labels has been checked.

Concretely, before applying the judge to the full SkillsBench trajectory
corpus, we sample constraint-level attribution decisions from the Claude Code +
Opus 4.6 trace corpus, preserving variation across skills, tasks, and
preliminary coverage outcomes when available. Human annotators independently
check the sampled cases with the same rubric and assign one of two labels:

\mathsf{Covered}
or
\mathsf{Uncovered}
before disagreement resolution. The
LLM judge is then run on the same sampled pairs using only the
extracted
SBC
and observable trajectory evidence. We compare the adjudicated
human labels and LLM labels using agreement metrics; after this agreement
check, we freeze the judging prompt, evidence format, and binary label space
before applying the same protocol to the full corpus.

4
Evaluation

We evaluate skill coverage in two steps. First, we validate whether the LLM
coverage judge matches human labels on a sampled subset of
constraint–trajectory pairs. Second, we apply the judge to SkillsBench
executions and report how much of the
SBC
denominator is covered by
existing benchmark tasks. The evaluation therefore separates judge reliability from the benchmark-scale coverage result.

4.1
Experimental Setup

Benchmark.

We use SkillsBench
(
11
)
as the evaluation benchmark.
SkillsBench is a suitable setting for skill-level adequacy analysis because
its skills are intended to provide reusable procedural guidance for classes of
tasks, rather than one-off solutions to individual task instances. This makes
task success and skill adequacy meaningfully separable: an agent may complete a
task while exercising only a subset of the behaviors documented by the
associated skills. We report benchmark-scale coverage on 78 source tasks for
which we collected task outcomes, observable agent trajectories, and
skill-level coverage judgments.

Agent configurations.

We evaluate seven agent–model configurations: Gemini CLI with Gemini 3 Flash
and Gemini 3 Pro, Codex with GPT-5.2, and Claude Code with Opus 4.6, Opus 4.5,
Sonnet 4.5, and Haiku 4.5. Each configuration is evaluated on the same 78
source tasks. We use the benchmark verifier to obtain task-level success
outcomes, and then apply our validated coverage judge to the resulting
observable trajectories.

Coverage judge.

We use DeepSeek V4 Flash as the LLM coverage judge. It receives only the
extracted
SBC
and the observable trajectory evidence, and applies the
two-step coverage rubric from Section
3.3
. For
benchmark-scale reporting we use its binary cover/not-cover label space. Before
applying it at scale, we validate the judge against human labels
(Section
4.2
).

Judge-validation sample.

We sample extracted
SBC
s and their associated trajectories from the Claude
Code + Opus 4.6 trace corpus. Following a statistically principled sampling
method at a 95% confidence level
(
10
)
, this process
produces 350 cases. Human auditors independently check whether each sampled
constraint–trajectory pair is covered or not covered before disagreement
resolution. We adopt the adjudicated binary coverage label and validate the
judge against human labels on this binary label space
(Section
4.2
). The validation sample is used only
to assess judge reliability; it is not used as a separate estimate of
SkillsBench coverage.

Metrics.

For judge validation, we compare human and LLM labels using exact agreement,
Cohen’s
\kappa
, and cover/not-cover agreement. For benchmark-scale coverage,
we report the fraction of the 78 source tasks’ audited skill denominator that
receives a covered judgment. We do not include every skill in a repository-level
skill pool; the denominator is limited to the task-associated skill artifacts.
For each skill
S
, the denominator is the audited set
\mathcal{C}(S)
. For a set of trajectories
T
, a
constraint is counted as covered if at least one trajectory in
T
covers it.

SBC coverage
is the fraction of extracted
SBC
s for the associated
skills that have at least one covered judgment. Each aggregate remains
traceable to the skill source span that produced the
SBC
, the trajectory
evidence used by the judge, and the resulting cover/not-cover label.

4.2
Measurement Validation

The validated judge matches human cover/not-cover labels.

Following the validation-before-scale protocol in
Section
3.3
, we compare the initial DeepSeek V4 Flash
judge against human labels on the 350-case validation sample. The judge agrees
with the human cover/not-cover audit on 328 cases, for an exact agreement of
93.71% and Cohen’s
\kappa=0.874
. We therefore use the binary
cover/not-cover label space for benchmark-scale coverage analysis.

4.4
Analysis and Discussion

Implication for benchmark interpretation.

The results suggest that task-level scores should be interpreted as related to,
but not sufficient for, skill-level test adequacy.
Figure
3
shows that successful executions tend to
cover more
SBC
s than unsuccessful executions, so the benchmark verifier is not
unrelated to skill-behavior exercise. However, the same figure also shows that
task success leaves a large part of the denominator untested, and that unsuccessful
executions can still exercise substantial portions of the skill. A successful task
establishes that the agent satisfied the benchmark verifier for that task
instance; it does not establish that the execution exercised the workflows,
tool-use conditions, prohibitions, or artifact expectations documented by the
skill. Skill coverage makes this gap explicit by reporting a denominator over
the skill text itself.

Implication for test-suite design.

The uncovered portion of the denominator is actionable rather than punitive.
Uncovered
SBC
s identify skill-scoped scenarios or constraints for which
the current benchmark executions provide no judgeable evidence. The
task-outcome-conditioned view further helps prioritize this work. Successful tasks
with low skill coverage reveal benchmark successes that still leave documented
skill behavior untested, while unsuccessful tasks with nontrivial coverage may still
provide useful evidence about which behaviors were exercised. Benchmark
designers can therefore target new tasks, stronger trace capture, or
oracle-facing checks at uncovered constraints, while skill authors can identify
which parts of a skill have not yet been validated under realistic agent
executions.

Scope of the evidence.

This evaluation is intended as a preliminary diagnostic application of skill
coverage, not as a complete reliability claim about SkillsBench or the tested
agents. The judge-validation sample estimates whether the LLM judge matches
human labels on sampled constraint–trajectory pairs, while the full
SkillsBench results estimate how much of the audited
SBC
denominator is
covered by benchmark executions. The task-outcome-conditioned analysis is
associational: it compares coverage across successful and unsuccessful
executions, but it does not identify why a particular task outcome occurred.
Within that scope, the main conclusion is that task success and skill coverage
answer different evaluation questions and should be reported separately.

5
Discussion

What skill coverage does and does not claim.

Skill coverage is an adequacy signal, not a replacement for task success. A
covered constraint means that the trajectory instantiated the relevant
condition and exposed enough evidence to judge whether the constrained behavior
was satisfied or violated. Conversely, an uncovered constraint
should not be interpreted as a violation. It means that the available
execution did not create judgeable evidence for that documented skill behavior.
The task-outcome-conditioned results reinforce this boundary: successful
benchmark executions are associated with higher coverage, but they still leave
many
SBC
s uncovered, and unsuccessful executions can still exercise judgeable
skill behavior. The observed coverage gap therefore identifies untested or
unjudgeable parts of the skill denominator, not necessarily agent problems.

Using uncovered constraints to improve benchmarks.

The practical value of skill coverage is that the uncovered denominator is
actionable. If a constraint is uncovered because no task instantiates its
condition, benchmark authors can add tasks that exercise that scenario. If the
condition is instantiated but the trajectory lacks adjudicable evidence, the
benchmark can add stronger trace capture, artifact checks, or oracle-facing
assertions. Skill coverage therefore provides an evidence map for improving
both skill artifacts and benchmark suites. This evidence map is useful even
when task outcomes are available: successful executions with low coverage
suggest missing adequacy pressure, while unsuccessful executions with
nontrivial coverage can still expose concrete skill behaviors for diagnosis.

7
Conclusion

This paper addresses the gap between task-level agent evaluation and
artifact-level skill adequacy. We introduced skill behavior constraints as
source-grounded, observable behavioral units extracted from natural-language
skill documents, and defined skill coverage as the fraction of those
constraints made judgeable with oracle-adjudicable trajectory evidence. The key
idea is to treat the reusable skill document as the artifact under test, rather
than assuming that a successful benchmark task has exercised the skill broadly.

Our SkillsBench study shows that this distinction is empirically important.
After validating binary cover/not-cover attribution against human labels, we
applied the fixed judging protocol to 78 source tasks across seven
agent–model configurations and three traces per configuration. Existing
executions cover only 39.90–43.98% of the extracted skill behavior
denominator on average. Successful task executions cover more of the
denominator than unsuccessful executions, but even successful executions leave
large portions of documented skill behavior untested. These results show that
task success and skill coverage answer different evaluation questions and
should be reported separately.

Skill coverage turns untested parts of a skill into inspectable benchmark
evidence. It can help benchmark designers identify missing scenarios, help
skill authors locate underspecified or unvalidated behaviors, and help users
interpret whether a reusable skill has been exercised under realistic agent
executions. Future work should extend the protocol to additional skill
ecosystems and connect coverage-guided task generation to automatic benchmark
improvement.
