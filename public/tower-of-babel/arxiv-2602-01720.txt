Phoenix: A Modular and Versatile Framework for C/C++ Pointer Analysis
Peisen Yao, Zinan Gu, Qingkai Shi

Abstract
We present Phoenix, a modular pointer analysis framework for C/C++ that unifies multiple state-of-the-art alias analysis algorithms behind a single, stable interface. Phoenix addresses the fragmentation of today’s C/C++ pointer analysis ecosystem by cleanly separating IR construction, constraint generation, solver backends, and client-facing queries—making analyses easy to compare, swap, and compose while exposing explicit precision–performance trade-offs. We evaluate Phoenix against SVF under two representative configurations: a flow- and context-insensitive setting and a more precise flow- and context-sensitive setting, on 28 GNU coreutils programs. Phoenix delivers robust speedups in the baseline configuration (up to 2.88 × \times ) and remains competitive—and often faster—even in the stronger precision regime (up to 2.91 × \times ), without a systematic runtime penalty. In production, Phoenix serves as the analysis substrate for static analysis and fuzzing tools that have uncovered hundreds of new bugs and enabled deployments reporting > 1,000 >1,000 bugs found in an industrial toolchain.

Data Structures
.
Efficient points-to manipulation is critical for scalability.
Phoenix decouples the abstract interface of points-to sets from their
concrete representation, and supports multiple set implementations:

BDD-based
representations for compact storage of large points-to sets, and

sparse bitvectors
for fast bulk set operations.
In addition, Phoenix provides a pluggable backend interface to support
specialized implementations; a SIMD-accelerated sparse bitvector backend is under
development to further improve throughput.

Constraint Solving
.
Phoenix provides an interchangeable solver layer with configurable optimizations
summarized in Table
2
.
The key design choice is to treat simplifications and propagation strategies as first-class, composable modules, allowing Phoenix to instantiate a large space of solver configurations without rewriting core logic.

Algorithm Portfolio
. Phoenix integrates an algorithm portfolio that spans a broad range of
precision–performance trade-offs.
To make these trade-offs explicit and configurable, we categorize algorithms by their semantic abstraction.

Inclusion-Based Analyses.

Inclusion-based analyses model assignments as directional constraints (e.g.,
p\supseteq q
), preserving fine-grained flow of information between pointers.
Phoenix includes Andersen analysis as the canonical baseline:

•

Andersen Analysis: A flow-insensitive, context-insensitive, subset-based
analysis that serves as the baseline in many pointer analysis frameworks.

•

Context-Sensitive Variants: A configurable family of variants
that refines aliasing across call sites. Phoenix supports systematic context abstractions (e.g., 1-CFA, 2-CFA, etc.) to enable controlled studies of precision and cost.

•

Flow-Sensitive Variants.: Phoenix can incorporate control-flow awareness into constraint propagation while reusing the same inclusion-constraint semantics.

Notably, to our knowledge, there is a lack of publicly available, exhaustive, flow- and context-sensitive Andersen analysis, which Phoenix addresses.

Unification-Based Analyses.

Unification-based analyses trade precision for speed by merging pointers that
are related by assignments, yielding near-linear performance in practice for many
codebases.
Phoenix supports unification-style analyses through equality constraints and
implements Dyck-style variants that provide a principled way to recover useful precision for common C/C++ idioms while retaining efficient solving.

Phoenix exposes a
unified query interface
that hides algorithm-specific
representations behind a stable set of operations. The key goal is to decouple
client analyses from (i) the choice of pointer-analysis algorithm and (ii) solver- and optimization-level engineering details.
To this end, Phoenix adopts an
adapter
design: each analysis backend provides a thin
result adapter that normalizes its output into a common set of query primitives, while the interface layer offers higher-level convenience queries built from these primitives.

Intermediate Representations
.
Beyond answering direct pointer queries, Phoenix provides access to a set of intermediate representations (IRs) that capture control, data, and memory dependencies.
These IRs serve as a shared substrate for downstream analyses:

•

Program Dependence Graph (PDG): an inter-procedural graph encoding both
data and control dependences, supporting reachability-based queries for clients such as program slicing.

•

Inter-procedural Control-Flow Graph (ICFG): extends intra-procedural CFGs with
call/return edges that connect call sites to callee entries, and callee exits back to callers, enabling
inter-procedural propagation.

•

MemorySSA: an SSA-style representation for memory operations with
implicit use–def links, enabling precise memory-dependence reasoning by identifying the most recent
memory-defining operation reaching each memory use.

•

Static Single Information (SSI): extends SSA with
\sigma
(split) and
\pi
(merge) nodes
to support bidirectional information flow, benefiting analyses that mix forward and backward propagation.

8
Conclusion

We introduced Phoenix, a modular and versatile framework for pointer analysis that unifies a broad class of state-of-the-art algorithms under a common interface. Its extensible architecture and clearly defined abstractions significantly reduce the engineering effort required to implement new analyses. By decoupling algorithmic concerns from infrastructure, Phoenix aims to accelerate both research prototyping and the development of production-grade tools for C/C++ programs.
We are actively pursuing several extensions to the framework:

•

Path-Sensitive Pointer Analysis:
We are developing a variant of Andersen-style analysis that incorporates path sensitivity, building on the authors’ recent work for path-sensitive data-dependence analysis
[
62
]
.

•

More Built-in Analysis Clients:
We are expanding the suite of built-in downstream analyses, including support for the Weighted Pushdown System (WPDS)-based interprocedural dataflow analysis framework
[
35
]
and the Newtonian program analysis framework
[
36
]
for quantitative program analysis.

•

Dynamic Alias Analysis:
We are developing a dynamic alias analysis component to complement the static analyses and improve precision in hybrid static-dynamic analysis settings.
