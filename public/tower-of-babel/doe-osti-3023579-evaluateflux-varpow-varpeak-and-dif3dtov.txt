 SUMMARY
 The DIF3D-VARIANT solver is part of the DIF3D code which was developed at ANL
for engineering level predictive analysis of nuclear reactor cores. Over the course of the last 20
years, the DIF3D-VARIANT option of DIF3D has become increasingly more used because of
improvements in computer memory capabilities and performance. This is beneficial to the users
of DIF3D as DIF3D-VARIANT is able to apply both p- and h-spatial mesh refinement
strategies in diffusion and transport theory. Given its greater use, utility programs were created
to assist in post-processing the DIF3D output. This document discusses the basic execution
process of DIF3D and the output files it creates but is primarily focused on being the manual
for the utility programs EvaluateFlux, VARPOW, VARPEAK, and DIF3DtoVTK.

 The EvaluateFlux utility program was created to assist users in obtaining flux and power
traverses through the domain. The user provides a set of points in the domain where the flux
and power are to be evaluated in the EvaluateFlux input file and EvaluateFlux provides the
various evaluations in several output files. The input for EvaluateFlux is displayed, the
methodology behind the point evaluation is discussed, and examples of the output files it
generates are displayed and discussed.

 The VARPOW utility program was created to provide input for follow-on steady state
thermal-hydraulics analysis. VARPOW takes the PMATRX cross section data file and the
neutron and gamma flux files produced by DIF3D and generates neutron and gamma power
distribution information. The spatial distribution of the fast flux is also included as part of the
VARPOW output as is the cladding damage. The VARPOW utility program produces a
NHFLUX formatted output file which can be imported by EvaluateFlux so users can produce
traverses of the neutron power, gamma power, fast flux, and clad damage distributions.

 The VARPEAK utility program was created to provide an alternative evaluation of the
power and fast flux peaking in the domain from the present special nodal procedure
implemented in DIF3D. VARPEAK can work with the regular DIF3D output to provide the
equivalent output that DIF3D reports in its output tables. VARPEAK can also work with the
GAMSOR output to produce an alternative evaluation of the peaking details accounting for
gamma heating. If the user provides the SFEDIT file produced by DIF3D, VARPEAK will
provide the identical output seen in DIF3D in the VARPEAK output to allow a direct
comparison of the two different evaluations in one file.

 The DIF3DtoVTK utility program was created to assist the user in visualizing the output
of DIF3D. The DIF3DtoVTK utility program does not do the visualization but only translates
the DIF3D geometry into an unstructured finite element mesh. This allows the user to use finite
element analysis visualization packages to display the DIF3D output. The input and output of
DIF3DtoVTK were discussed and several examples of the visualizations possible are given.

 These utility programs have proven to be quite useful when doing reactor analysis with
the DIF3D software.

1 Introduction
 The DIF3D code [1-5] has been a workhorse of fast reactor analysis work at Argonne
National Laboratory for over 50 years. There are three distinct solver capabilities in DIF3D
available today: a finite difference diffusion solver, DIF3D-FD [2], a transverse integrated
diffusion solver DIF3D-Nodal [3], and the even-parity transport solver DIF3D-VARIANT [4-
5]. All three solvers provide the functionality to obtain a numerical solution to the neutral
particle diffusion equation for a user provided multi-group cross section set and geometry
definition. All three also assume the fine-grained details of the geometry are homogenized and
thus provide semi-structured grids to work with (as opposed to detailed finite element or
combinatorial geometry representations). This approach is focused on reproducing the average
behavior of the heterogeneous geometry in the homogeneous equivalent and it should be clear
that the generation of multi-group cross sections that produce a solution consistent with a real
reactor is beyond the scope of this document.

 For fast spectrum reactor analysis, the MC2-3 software [6] is typically relied upon for
multi-group cross section generation, and there is considerable documentation in the literature
on how successful this is. DIF3D-VARIANT was added to DIF3D in 1995 [4] to improve the
flux solutions for fast reactor problems and it has been pushed to the forefront of usage in the
last decade because of improved computing resources and the focus on reactors with significant
leakage. VARIANT performs nodal neutron transport calculations using P N or SPN theory in
Cartesian and hexagonal two- and three-dimensional geometries. With increased usage of
DIF3D-VARIANT, there have been many requests for additional features and functionality
over the last 20 years by users.

 In order to assist users to post-process DIF3D outputs for evaluation, visualization, and
use in downstream codes, utility programs were developed. In this manuscript, four utility
programs are discussed: EvaluateFlux, VARPOW, VARPEAK, and DIF3DtoVTK. Most of
these utility programs do not have input files but rely upon command line inputs to control the
output or they scan for specific files in the local working directory to determine what outputs
should be generated. The purpose and intended usage of each utility program, along with details
on any input files they need and the outputs they produce are presented and discussed in this
report. Each utility program is covered in its own section.

2 DIF3D Execution and Output Summary
 Because all of the utility programs discussed in this document make use of binary files
created by DIF3D, some detail on how DIF3D operates is needed. Figure 2.1 provides a basic
diagram of how the DIF3D software operates. As seen, the user provides ASCII input via the
four major input blocks A.NIP3, A.DIF3D, A.HMG4C, and A.SUMMAR which are read by
the GNIP4C module of DIF3D and converted into the binary interface files GEODST,
NDXSRF, ZNATDN, and LABELS [1,2,7]. If set up properly, DIF3D will then solve the
problem and generate the RTFLUX, COMPXS, and PWDINT files. There are of course several
different ways to provide an input to DIF3D and more output files that it will create during its
execution that the user can make use of, but those listed in Figure 2.1 are the ones of interest
for utility programs discussed here.

 The NHFLUX file will only be produced if the DIF3D-Nodal or DIF3D-VARIANT
solver are being used. The NHFLX0 file will only be produced if DIF3D-VARIANT is being
used. The NHFLX0 file is equivalent to NHFLUX but has a smaller storage requirement as it
only stores the scalar flux moment (as opposed to all angular moments stored in NHFLUX)
along with the diffusion equivalent currents. DIF3D-VARIANT and REBUS [8] were
specifically modified to produce and export the NHFLX0 files for post processing of the output.
The angular flux and currents are only needed in a DIF3D restart calculation or for PERSENT
[9] which requires both to apply the perturbation theory equation. For the purposes of this
document, NHFLX0 and NHFLUX will both be referred to as NHFLUX as there is no
distinction in the output results from the utilities.

3 The EvaluateFlux Utility Program
 The genesis of EvaluateFlux was the need to obtain off-center mesh foil reaction rates
for experimental measurements taken in ZPR and ZPPR. As part of metal fueled fast reactor
validation work, several foil measurements from ZPPR-15 were analyzed [11,12]. In that work,
the foils were typically placed alongside the fuel plates which in some drawers were located at
the geometric center while other drawers would have an off-center location. For a homogenized
problem, the global gradient is generally smooth and thus for relative reaction rate distributions,
evaluating the homogenized, global flux solution at the correct point was found to be important
for correctly computing these reaction rate distributions.

 In past work, the DIF3D-FD solver would be used and the user would apply sufficient
spatial meshing that the global flux gradient could be efficiently evaluated at the desired
coordinate using a spline methodology or simple interpolation. When using DIF3D-VARIANT,
each drawer is handled with a single mesh and the axial dimension is typically 8-12 cm. The
foil of course is small relative to the size of the mesh for any DIF3D solver, but using a coarse
mesh methodology like that of DIF3D-VARIANT prevents the user from being able to
construct a good fitting methodology which was typical for DIF3D-FD. Of course the inherent
advantage of DIF3D-VARIANT is that it retains the spatial flux distribution such that after the
solution is obtained, the flux distribution within each mesh can be evaluated at any point within
that mesh. The EvaluateFlux utility program was not the first such program to perform these
operations [13], but its creation and distribution since 2015 allowed all users to easily define a
set of points in the domain and then obtain the flux solution and macroscopic reaction rates at
those points.

 The first version of EvaluateFlux focused on just obtaining the flux evaluation at the
user specified points. Because foil cross sections are not used by DIF3D as part of the regular
solver operations, it is simply easier to provide the user with the flux evaluation and have them
merge the flux and cross sections to get the reaction rate in each foil. In that regard, only two
binary interface files are required by EvaluateFlux to operate: GEODST and NHFLUX. The
GEODST file contains the geometry information provided by the user in their DIF3D execution.
The NHFLUX file contains the coefficients of the space-angle approximation in DIF3D-
VARIANT.

 Because some users wanted to obtain radial and axial reaction rate traverses, the
EvaluateFlux code was later modified to provide the composition-based reaction rate traverse.
An extension of that capability to perform the isotopic breakdown of the reaction rate was also
added. Finally, the code was modified to evaluate all of the isotopic cross sections in a provided
file at a given point. The intention of this feature was to have the user provide EvaluateFlux
with an ISOTXS file that only contained the foil cross sections with which it could provide the
foil reaction rate distributions at all of the user provided points. This approach avoids the user
manually combining the cross section data, but it requires some effort from the user to select
the desired output from the output file as all of the foil cross sections are evaluated at all chosen
points.

 3.1 Input Setup for EvaluateFlux

 The primary reason the EvaluateFlux utility gained acceptance is because it provides
the required input as part of its regular output. Figure 3.1 provides the output created by
EvaluateFlux when no input is provided. Lines 1-4 provide a description of what the utility
program does. Lines 5-16 describe the input setup that EvaluateFlux accepts and the output that
will result from them. Lines 18-19 indicate that the input file was not present and that the
program will die. Finally, lines 20-30 provide the input file description of EvaluateFlux.inp.

 Reviewing lines 5-16, EvaluateFlux defines three valid input setups. These setups are
dependent upon what files are present in the local directory or made available to EvaluateFlux
via the input file (EvaluateFlux.inp). For the first setup (line 06), only the NHFLUX and
GEODST files are provided as was discussed earlier which was to obtain just the flux
evaluation. The output for this case (line 10) is a file called FluxAndRegionRR.out which
contains the point-wise flux and reaction rate evaluation. As line 10 indicates, because no cross
section data is provided to EvaluateFlux, it cannot calculate reaction rate and thus all reaction
rate output in the file FluxAndRegionRR.out will be zero.

 The second input setup (line 07) has the user provide GEODST, NHFLUX, ISOTXS,
and reaction type information in EvaluateFlux.inp. This setup was intended for foil reaction rate
evaluation where the ISOTXS file only contains foil cross section data. The reaction rate setting
indicates which reaction rates (fission and capture) are to be evaluated and provided to the user
in the file IsotopeMicroRR.out (line 11). The third input setup (line 08) has the user provide
GEODST, NDXSRF, LABELS, ZNATDN, ISOTXS, NHFLUX, and a reaction rate selection.
This represents the maximal input that EvaluateFlux will take and this will lead to the maximal
output also (line 12).

 As seen in Figure 3.1, the output files are named, but their contents are not really
described well in the EvaluateFlux output. For FluxAndRegionRR.out, the output turns out to
be rather intuitive while the other output files are rather complicated and additional description
is needed. To display these aspects, the fifth verification test problem for EvaluateFlux was
selected and all three input setups will be executed and the inputs and output will be displayed
and discussed.

 One of the first aspects to deal with in EvaluateFlux is the coordinate system definition.
For Cartesian geometries, the X-Y-Z coordinate system has no additional transformation and
thus it is easy for the user to define coordinate points in the mesh of their choosing. For
hexagonal geometries, this is not straightforward as DIF3D-Nodal and DIF3D-VARIANT
impose a 30 degree rotation of the coordinate system. Figure 3.2 shows a common assembly
layout for a reactor problem in the left picture and the coordinate axis definitions on the right
picture. The DIF3D input definition defines the red coordinate system where the first row of
hexagons in each ring lies along the 30 degree line. This is primarily to allow DIF3D-FD to
define a hexagonal geometry consisting of complete equilateral triangles. The hexagonal input
can be viewed as six sectors with the first sector including the first hexagon in each ring where
more details can be found in the DIF3D-FD manual [2]. For a 120 degree periodic geometry in
DIF3D-FD, the user must provide the full input for sector 1 and partial input for sectors 2 and
6. This approach has proven somewhat painful for users over the years.

 As DIF3D-Nodal and DIF3D-VARIANT were added later and require a geometry with

 3.2 EvaluateFlux Point Evaluation Algorithm

 EvaluateFlux will identify which GEODST mesh (indexed as I, J, K) each user
evaluation point lies within in the domain. This is done as part of the GEODST module in the
source code and has been extensively tested although only for DIF3D-VARIANT. If the point
lies outside of the domain, the evaluation will yield zeros for the flux and reaction rates. No
error or warning message is issued when this occurs as producing a zero result for the flux
evaluation is sufficient information to the user that there was a problem. As detailed in reference

 3.4 Structure of the FluxAndReactionRate.out File

 As shown in Figure 3.3, EvaluateFlux has three setup approaches for input. As a
consequence, the output for each setup can be different. In the first setup, only the GEODST
and NHFLUX files are provided which means EvaluateFlux will only produce the
FluxAndRegionRR.out file, an example of which is shown in Figure 3.5. The second setup
where GEODST, NHFLUX, and an ISOTXS file containing isotopes produces an identical
FluxAndRegionRR.out file. The third setup will produce a slightly different
FluxAndRegionRR.out file, an example of which is shown in Figure 3.6.

 In Figure 3.5 the header indicates the contents in the file while the second line shows
the column indices. As only the flux can be evaluated, the first four columns provide the input
index of each evaluation point along with the X, Y, and Z position of the point (again the user
input). The remaining columns are the flux solution in each energy group from 1 to the Number
of groups. Note that it is not unusual to see negative fluxes near the vacuum boundaries in
DIF3D and thus the negative values shown are of little concern.

 A comparison of Figure 3.6 with Figure 3.5 shows that the primary reactions listed as

 3.5 Structure of the IsotopeMicroRR.out File

 The IsotopeMicroRR.out file is only produced when an ISOTXS file is provided and
thus only with setup 2 and 3. In setup 2, the intention is for the user to provide a foil reaction
rate while setup 3 assumes the ISOTXS file is consistent with the NDXSRF file being provided.
The output file typical of setup 2 is shown in Figure 3.7 while that of setup 3 is shown in Figure
3.8.

 A header line is provided to indicate which microscopic reaction rate is being evaluated
(e.g., GAMMA, FISSION, etc.). Only those reactions provided on the SELECT_REACTION
line will have blocks of output in this file. Within each block of output for a given reaction, the
row wise output is provided with respect to the user evaluation points provided in the input. In
each output block, the columns beyond the index and X, Y, Z position information for each
evaluation point provides the ISOTXS isotope names associated with the evaluated microscopic
reaction rate data.

 The number of isotopes printed per row is limited to 128 to avoid an excessively large
number of columns. Because the foil ISOTXS file in setup 2 only has 25 isotopes, the various
header lines only appear once. The ISOTXS file in setup 3 has 230 isotopes in it and thus there
will be two blocks of isotope data for each reaction type which is shown for the GAMMA
reaction in Figure 3.8. As seen in both files, the microscopic isotope reaction rate is evaluated
at each point regardless of whether the isotope actually exists at that point in the mixture. This
output file can become extremely large and difficult to view when using setup 3 and thus it is
strongly recommended to only use the output file when using setup 2.

 3.6 Structure of the IsotopeMacroRR.out File

 The IsotopeMacroRR.out file has an identical setup to the IsotopeMicroRR.out file.
This file will only appear in setup 3 as it requires the atom density information from ZNATDN.
Figure 3.9 provides the example output for setup 3. As was the case with IsotopeMicroRR.out,
only the reactions listed on SELECT_REACTION are provided in the output. A quick
comparison of Figure 3.8 and Figure 3.9 shows that a majority of the output in
IsotopeMacroRR.out consists of zeros as most of the isotopes do not actually exist (zero atom
density) in the various regions of the domain with evaluation points.

 3.7 Structure of the LabeledRegionRR.out File

 The last file that is produced by EvaluateFlux is called LabeledRegionRR.out. This file
will only appear with setup 3 and Figure 3.10 shows an example output. This file has a
completely different structure from the preceding files. The intention of the file was to provide
the region and zone that each evaluation point intersects and then give the reaction rate
evaluations for all isotopes in the zone at the evaluation point. In the Figure 3.10 example, the
result for just a few evaluation points is provided as the output can be quite extensive.

 The tabulated data at each evaluation point is organized row-wise by isotope and
column-wise by reaction type. Unlike the preceding files, the reaction rate data is evaluated for
all isotope regardless of the SELECT_REACTION input. Each evaluation point can be
identified by a header line giving the evaluation point index number and the X, Y, and Z
coordinate. The next line of output lists the GEODST index number, the region name, the
NDXSRF zone index number and the zone name. The table of output data that follows this line
is rather self-descriptive and needs no additional details.

 3.8 EvaluateFlux Utility Summary Details

 As stated, the EvaluateFlux program purpose was to provide off center foil evaluations
of the flux within the coarse mesh methodology of DIF3D-VARIANT. It has progressed to
provide some additional capabilities for spatial reaction rate distributions. Many changes have
been made to the program to improve its efficiency as the number of evaluation points requested
by users has increased substantially since the beginning of its usage.

 EvaluateFlux is still used to obtain the foil reaction rates for all modern calculations of
ZPR and ZPPR experimental assemblies at ANL today. EvaluateFlux is presently used to obtain
the fast flux evaluation in the duct wall for the input needs of NUBOW [14]. The underlying
methodology in EvaluateFlux was incorporated in the DASSH software [15] for evaluating pin,
duct, and coolant power distributions within an assembly.

4 The VARPOW Utility Program
 The VARPOW utility program was specifically built to provide input for DASSH [15].
DASSH is an alternative analysis capability to the SE2ANL software [16] which is based upon
Superenergy-2 [17]. All three of these pieces of software exist to provide a steady state
temperature distribution in a fast reactor with ducted fuel assemblies. The Superenergy-2
software was designed to take a user power distribution as input along with basic assembly
geometry details and assembly flow specifications. The SE2ANL software is effectively a
wrapper around Superenergy-2 which handles the interface with DIF3D-FD (as part of
GAMSOR) to obtain pin power details. SE2ANL also expands upon the assembly pin geometry
details such that Superenergy-2 will carry out a pin temperature calculation. This pin
temperature calculation allows the user to obtain the 3-sigma peak clad mid-wall temperature
evaluation given the user can provide base material property uncertainties and statistical
uncertainties on the problem being studied. With all of this stated, the VARPOW utility
program acts as the interface between DASSH and DIF3D-VARIANT.

 4.1 Definition of the Spatial Power Distribution

 As the preceding EvaluateFlux details displayed, the point-wise flux and reaction rate
evaluation within an assembly are non-trivial matters. The intention of VARPOW is to simplify
this aspect by providing the user with a data file that can be more easily manipulated. To
understand this, one must first understand how the power is being computed which is best
described in the GAMSOR manual [10]. Reproducing equation 2.15 from the manual [10], the
total power in a mesh can be written as

            𝑃𝑜𝑤𝑒𝑟 =    𝑑Ω    𝑑𝑉      𝑁        κ , ∙ 𝜓 (𝑟⃗, Ω) +        Κ , ∙ Ψ (𝑟⃗, Ω) .

In this equation, the power consists of a neutron heating and gamma heating component. Ni is
the atom density of each isotope in the mixture for the targeted mesh. κi,g is the neutron KERMA
factor while Ki,p is the gamma KERMA for each isotope in the mixture and the number of
energy groups (g for neutrons, p for gammas) is typically different. The variables 𝜓 and 𝛹 are
of course the angular flux for neutrons and gammas, respectively.

 For a spatially dependent power distribution within the mesh, one simply eliminates the
volume integration to define:

             𝑃𝑜𝑤𝑒𝑟(𝑟⃗) =    𝑑Ω     𝑁        κ , ∙ 𝜓 (𝑟⃗, Ω) +         Κ , ∙ Ψ (𝑟⃗, Ω) .

As shown earlier, the flux representation in DIF3D-VARIANT assumes a polynomial basis
within each mesh while the coefficients for that distribution are obtained by DIF3D-VARIANT
and provided on the NHFLUX file (or NHFLX0 file for the scalar flux). Applying the integral
over angle to define the power relationship in terms of scalar fluxes 𝜙 and Φ, the spatial
distribution of power can be written as

ANL/NSE-22/55 Rev. 1                           20

              𝑃𝑜𝑤𝑒𝑟(𝑟⃗) =         𝑁         κ,       𝑓 (𝑟⃗) 𝜙 , +      Κ,   𝑓 (𝑟⃗)Φ ,   .

 Because DIF3D is a homogeneous methodology, the preceding power calculation
should involve a de-homogenization technique to take the homogeneous flux and produce a
heterogeneous flux distribution. This is primarily as the thermal-hydraulics code needs the
heterogeneous power distribution such that it can define power for the fuel pellet, the cladding,
the coolant, and the duct wall. For fast spectrum reactors, the heterogeneous to homogeneous
flux transformation only typically impacts the lower energy groups which themselves do not
account for much of the power in the reactor. As a consequence, the typical thermal spectrum
flux reconstruction technique is not employed in fast spectrum reactors and the homogeneous
flux and subsequent homogeneous power distribution are directly used which is the approach
for SE2ANL and DASSH.

 With the displayed form and homogeneous flux solution, one can readily identify all of
the information needed by the thermal-hydraulics code to produce the power distribution: Atom
density details, isotopic cross section data, the spatial polynomial expansion details, and the
flux vector data for each mesh. Having the thermal-hydraulics code deal with this input is not
the typical practice and thus the standard path simply provides the power distribution as
Superenergy-2 was designed to do.

 Even with the homogeneous flux distribution, there is some assumption about how the
heterogeneous power distribution is defined. Take as an example, that the power is to be
exclusively distributed to Q pellets within a given mesh (no spatial dependence within the
pellet). In that form, the preceding power distribution can be evaluated at each pellet centroid
(or a spatial integral done over the pellet volume using Gaussian integration) to obtain

            𝑃𝑜𝑤𝑒𝑟 𝑟⃗      =       𝑁        κ,        𝑓 𝑟⃗ 𝜙 , +        Κ,   𝑓 𝑟⃗ Φ ,        .

 As this power definition relies upon the homogeneous flux, the remainder of the power
produced by the mesh is included in the above point (or integral) evaluation. As a consequence,
an additional normalization must be imposed to ensure that the total power is preserved which
takes the form:

 𝑃𝑜𝑤𝑒𝑟 𝑟⃗ = 𝑑𝑉 𝑃𝑜𝑤𝑒𝑟(𝑟⃗).

For DASSH, this normalization detail is done internally to DASSH using the power distribution
details provided by VARPOW. In SE2ANL, this detail is again handled as part of the SE2ANL
wrapper for Superenergy-2.

 As a final note, for a heterogeneous geometry definition, the isotopic breakdown of the
energy deposition typically gets split by material type. As an example, the fuel is composed of
actinides while the cladding is typically composed of iron and other structural materials. It is

                                                      21                           ANL/NSE-22/55 Rev. 1

rather rare that the isotopes used in the cladding also will appear in significant concentrations
in the fuel. The same can be said about the coolant and the cladding and fuel materials. Because
it is again not desirous to provide the thermal-hydraulics code with an isotopic power
distribution within each mesh, the setup of VARPOW includes a splitting of the power
distribution into fuel, structure, and coolant where the user must select which coolant and fuel
type is being used when running VARPOW. How VARPOW discriminates the isotopic power
is discussed in the following section.

 The fast flux evaluation from VARPOW is described in the DIF3D manual [2]. The
output units are n/cm2/sec and evaluation at a point with EvaluateFlux will yield the same units.
For the structural damage output, the input to VARPOW was modified so the user can provide
the displacement energy (eV) that is required to dislodge an atom from its position in the lattice.
This input is material and isotope specific and thus it is perfectly reasonable to assign different
values in the domain based upon different structural materials. In that regard, the user is
assumed to have created region specific ISOTXS cross section sets and thus VARPOW allows
the user to assign region specific isotopic displacement energy values as is shown later.

 For the damage reaction rate calculation itself, combining the atom density 𝑁 , the
damage cross section, d , , from the PMATRX file, and the isotropic neutron flux 𝑓 (𝑟⃗)𝜙 ,
will produce a spatial distribution in each mesh with units eV/s. The displacement energy E
with units eV, is multiplied by 2 and divided into the preceding reaction rate on an isotopic
basis to produce dpa/s which is thus written as:
 d,
                        𝐷𝑎𝑚𝑎𝑔𝑒(𝑟⃗) =        𝑁               𝑓 (𝑟⃗) 𝜙 , .
 2∙E

As seen VARPOW will yield a spatial distribution of dpa/sec in every mesh for the set of
isotopes that were identified as the structural materials. When passed to EvaluateFlux, the user
must account for the fraction of the structural material that the clad constitutes to the total
structural material. As an example, if the cladding is 80% of the structure where wire wrap and
duct wall makes up the rest, then the dpa rate produced by EvaluateFlux from the VARPOW
result should be multiplied by 0.8 for a cladding evaluation point in the domain. One can
account for this factor in the definition of the displacement energy such that the EvaluateFlux
output exactly produces the clad dpa/sec.

 The displacement energy, E , for all isotopes is initialized to 109 eV and can only be
changed by the user through the optional AssignIsotope.inp input file for VARPOW as detailed
later. As a consequence, every VARPOW output will contain a dpa/sec result even if the
PMATRX file does not contain damage cross section data (VARPOW will produce a zero
distribution). The source of E comes from material radiation damage experimental evaluations
and the user should consult the literature as to its meaning and for source inputs for their
structural material. For convenience, an example AssignIsotope.inp file that includes
displacement energies for a typical steel cladding is provided in the test suite of GAMSOR.

 4.2 VARPOW Input and Output Details

 With the preceding power distribution objective described in the previous section, the
input for VARPOW is more easily understood. Figure 4.1 shows the VARPOW output when
VARPOW is not executed properly. Everything in this output but line 39 is always produced
for user convenience of using VARPOW. As can be seen, unlike EvaluateFlux, there is
presently no input file for VARPOW as it just requires command line arguments. It is noted
that the user can provide a “AssignIsotope.inp” file to control the isotope assignments to fuel,
clad, and coolant material types along with the displacement energy for each isotope. This file
should just be provided in the local working directory where VARPOW is being executed.

 Lines 3 and 4 detail the command line input paths accepted by VARPOW where there
are no optional arguments. Line 3 details the input data required if the user intends on using
power derived from GAMSOR (coupled neutron-gamma) while line 4 details the input when
using regular DIF3D or REBUS. The only difference between the two lines is the use of
PMATRX for the GAMSOR route and the inclusion of the gamma NHFLUX file produce by
GAMSOR in the second step referred to as GHFLUX. In the DIF3D approach, the PMATRX
is replaced with ISOTXS and the GHFLUX is of course not available. The preferred approach
for defining the power is to use GAMSOR as its purpose was to properly distribute the gamma
heating throughout the modeled domain. However, for rapid prototyping the regular DIF3D (or
REBUS) power methodology can be used as line 4 indicates. Note that the clad damage
evaluation will not be available in this approach.

 The PMATRX, LABELS, GEODST, NDXSRF, ZNATDN, and NHFLUX files are all
standard parts of the Argonne computing system and definitions can be found for all of them in
the DIF3D, MC2-3, and REBUS. As stated, the GHFLUX refers to the NHFLUX file produced
by GAMSOR in the second step which leaves iTypeFuel, iTypeCool, and iOutput as the only
inputs that need to be explained.

 Starting with iTypeFuel, line 5 indicates that the input options are integer values from
1 to 4. These numbers refer to the type of fuel material present in the pellet where the options

 With this information, one can understand why the “Output.VARPOW” file only
contains 2 spatial distributions (iOutput=M or P) or 6 distributions (iOutput=S or T). The
original work on DASSH assumed that the 2 option output (M or P) yielding the neutron and
gamma power distributions would be sufficient. This was because much of the focus was on
the fueled region of the domain where the other parts of the core were believed to contain
smooth shapes only dependent upon one component (i.e., power in reflector is dominated by
the structural power distribution). As this is an implicit assumption forced upon the user, the 6
component output in “Output.VARPOW” was included to ensure that the spatial distribution
of each material component was preserved correctly. Keep in mind that the spatial dependence
can be different between materials because the multi-group cross sections are different leading
to different sums of the energy spatial shape functions. Not surprisingly, the 6 component output
yielded a 4th significant digit change in the temperature distribution prediction thereby
indicating that the original 2 component output was likely sufficient.

 As stated earlier, the thermal-hydraulic input requirements must know the spatial basis
functions within each mesh in order for it to carry out the interpolation. This is the purpose
behind the “VariantMonoExponents.out” output file described on line 34 in Figure 4.1. An
excerpt of this file was shown earlier during the EvaluateFlux discussion in Figure 3.4. The
output produced by VARPOW is identical to that of EvaluateFlux except for the program origin
name and thus any example here is omitted for brevity.

 With the above outputs explained, the purpose of the iOutput input value becomes more
apparent. For option M and S, the monomial basis spatial distribution of the power (neutron
and gamma heating) is provided in the “Output.VARPOW” file. For option M, only 2 spatial
distributions (neutron and gamma) are provided while option S retains the 6 component
breakdown (fuel, clad, coolant for neutron and fuel, clad, coolant for gamma). As NHFLUX
typically contains the polynomial coefficients of the flux expansion, using M or S will result in
the VARPOW file containing the monomial coefficients of the expansion. In this regard, the f̅
matrix has already been applied, which negates the need for the polynomial to monomial
coefficient matrix. Thus if option M or S is selected, the f̅ coefficient matrix will not appear in
the “VariantMonoExponents.out” file as was done in example Figure 3.4.

 From lines 7 and 9 of Figure 4.1, one can observe that the monomial distribution output,
options M and S, are referred to as “normalized.” The stated normalization imposes that the
spatial integral of the monomial distribution in a given mesh will yield 1.0 instead of the total
power of that mesh. Given the file “MaterialPower.out” can be used to define the total power
in each mesh (volume of every mesh is known), there is no need to have the monomial spatial
distribution equate to the real mesh power as one can simply multiply by the result in
MaterialPower and the point evaluation of the neutron and gamma spatial distributions to get
the power density at any point. Thus, using a normalized monomial basis can be easier as it
eliminates the need to integrate the monomial spatial distribution when imposing that the
heterogeneous total power matches the homogeneous total power.

 For options P and T of iOutput, the coefficients for the polynomial distribution of the
power distribution are given. As seen in lines 8 and 10 of Figure 4.1, when the polynomial
distribution is exported, the spatial distributions are not normalized. The basic idea was to
assume that whatever follow-on program was using the output needed it to be further

ANL/NSE-22/55 Rev. 1                            26

manipulated. In that regard, the option P approach would still require “MaterialPower.out” in
order to separate the power into the three material components of neutron and gamma heating.
For option T, the “MaterialPower.out” file is unnecessary as the “Output.VARPOW” file would
contain the spatial distribution of all components. As VARIANT uses an orthonormal basis, the
first moment in the spatial distribution is always the average value in the mesh and thus the first
moment in each mesh of the vector stored in “Output.VARPOW” is exactly what would appear
in “MaterialPower.out.”

 4.3 Structure of the Output.VARPOW file

 As stated earlier, the “Output.VARPOW” file is a NHFLUX formatted file. This means
the file format of NHFLUX used identically by DIF3D-VARIANT is used to define the
“Output.VARPOW” file. The NHFLUX format description can be found in the Documents
directory included with every DIF3D distribution and it does not need to be displayed here as
there are no changes to the file format specification. What does need to be explained here is
how the 2 or 6 components of the power distribution, the fast flux, and the clad damage spatial
distributions are stored in a file format that was intended to contain the multi-group spatial flux
distribution.

 In the NHFLUX form specification, the mesh-wise flux solution is stored in an array
named FLUX(NMOM+NMOMS,NINTXY,NINTK,NGROUP). The definition of these
variables is given in the first record of the file format description which is provided in Figure
4.3. From Figure 4.3, one can see that NMOM and NMOMS specify the number of spatial and
angular basis moments stored in each mesh, NINTXY is the number of radial meshes in the
domain, NINTK is the number of axial meshes, and NGROUP is the number of groups in the
multi-group flux approximation. Given that the power and fast flux spatial distributions still
require unique values for the number of spatial basis moments and the number of radial and
axial meshes, the only array index that can be easily manipulated is the number of groups. In
that regard, for the M and S options of iOutput, the neutron power distribution is stored in the
first group position, the gamma power distribution in group 2, the fast flux in group 3 with units
n/cm2/sec, and the clad damage in group 4 with units dpa/sec. Thus VARPOW will create a
NHFLUX file with NGROUP=4 when using the M or S options of iOutput.

 The same basic approach is taken for the P and T options except NGROUP=8 with the
fuel, clad, and coolant neutron power density stored in groups 1, 2, and 3, respectively. The
fuel, clad, and coolant gamma power density are stored in groups 4, 5, and 6, respectively. The
fast flux spatial distribution is stored in group 7 and the clad damage distribution is stored in
group 8. All of the remaining details of the NHFLUX file are simply taken from the neutron
NHFLUX file imported by VARPOW noting that some variables are intentionally set to zero
to prevent the file from actually being usable by DIF3D in a restart calculation. The variable
NMOM is set to the number of polynomial terms in the spatial distribution and NMOMS is set
to zero. The partial currents detailed in the NHFLUX file format are also not stored as IWNHFL
is set to 1. The ITRORD and ITRMAP arrays are copied from the user provided NHFLUX file.

 4.4 Using Output.VARPOW in EvaluateFlux

 With the preceding details, it should be noted that EvaluateFlux can import the
“Output.VARPOW” file as if it were a multi-group flux solution from DIF3D and carry out the
same point interpolations that were described earlier. As the multi-group neutron or gamma
cross section data sets are unlikely to contain 4 or 8 groups, it should be apparent that the
intended usage of EvaluateFlux is setup 1 where only the GEODST and NHFLUX
(Output.VARPOW) file are provided. The multi-group point interpolation results would then
need to be interpreted by the user as the neutron power, gamma power, fast flux, and clad
damage evaluation at the point rather than a multi-group flux result as was displayed in the
EvaluateFlux output. Using the output of VARPOW in EvaluateFlux can only be done correctly
when using options P and T of iOutput as those options produce a NHFLUX formatted file with
coefficients for the polynomial distribution. While the M and S options will still execute
properly in EvaluateFlux, the results will be garbage as the polynomial to monomial coefficient
matrix would be incorrectly applied in EvaluateFlux.

ANL/NSE-22/55 Rev. 1                               28

 Being able to use the VARPOW output in DASSH and EvaluateFlux was the primary
reason why VARPOW computes the fast flux and clad damage distributions. As part of the goal
to improve the interface of the various pieces of analysis software, the fast flux evaluation in
the duct wall is a required input of the NUBOW software and thus DASSH will obtain that
information in the form that NUBOW needs. Similarly, clad damage is a vital part of fuel
performance and thus the damage cross section evaluation was added to MC 2-3 and the
evaluation was added to VARPOW. With VARPOW, this input can be generated trivially
compared with past work to obtain it from the regular DIF3D output. The added ability to obtain
radial and axial traverses of the neutron power and gamma power are also beneficial to help
analysts understand the impact of GAMSOR versus regular DIF3D as shown in Figure 4.4.

 In Figure 4.4, a control rod assembly, it should be clear that the neutron and gamma
heating have very different spatial distributions and that there are significant local peaks due to
material interfaces in the domain. While the same information can be understood from the
region edits, the peaks can be rather obscured as the result is averaged over a large mesh and
the detailed spatial traverse clearly shows the importance of the material interfaces. Such plots
like this help analysts to better understand the flow rate requirements needed to cool the
assemblies below the peak allowable cladding temperature at all axial points in the assembly
along with the reason behind the peak burnup that REBUS produces.

 4.6 VARPOW Default Isotopic Separation Algorithm

 The default algorithm used by VARPOW to select which isotopes are fuel, clad, and
coolant is discussed in this section. Fundamentally it is difficult to anticipate which isotope
names will be selected by the user along with being able to guess what the new MC 2-3 names
will be for future ENDF evaluations. As a consequence, the existing algorithm is exclusively
setup to discriminate the isotopes based upon their masses. Table 4.1 shows the three steps of

Both DIF3D-Nodal and DIF3D-VARIANT use this subroutine to evaluate the peak power
density and fast fluence. The NHSREG subroutine uses the special nodal procedure
documented in [3] to obtain the peak information. The basic idea behind the procedure is to
apply a polynomial fit to the flux moments obtained in the solution algorithm on the surface of
each mesh (8 surfaces for hexagons and 6 for Cartesian geometries) and the average value in
the mesh. With this approach, the peak value is determined which are reported in the regular
DIF3D output tables. An excerpt of the affected DIF3D tables is shown in Figure 5.1 where the
highlighted text indicates the impacted output. This same peaking procedure is used when
producing the SFEDIT file from DIF3D [2] and later used by REBUS when calculating the
peak burnup and peak fast fluence.

 When the above error message is reported by NHSREG, it indicates that the fitting
procedure could not be used and the peak values were computed by finding the maximum of
the available surface and mesh average values. This happens when the flux magnitudes on the
surfaces are very disparate and it is likely that the peak occurs on one of the surfaces or at the
corner where two surfaces meet. This message does not mean the reported peak values are
incorrect, but they may be an underestimate of the true peak that occurs in the mesh. Over the
years, the existing algorithm has proven sufficiently accurate although there are many cases
where it has produced obviously invalid results and the above error message was not triggered.
For DIF3D-Nodal, there is not much that can be done with regard to obtaining a better estimate
of the peaking behavior. For DIF3D-VARIANT the flux basis can be evaluated after the flux
solution has been iterative solved and thus one can obtain the peak value of power density or
flux more consistently than the DIF3D-Nodal algorithm.

 5.1 Evaluation of the Peak in VARPEAK

 For DIF3D-VARIANT, there are two approaches that can be taken to obtain the peaking
within a mesh. The most rigorous approach is to take the derivative of the spatial basis and use
a root finding technique to identify the peak values. For low order polynomial functions this
can be very efficient, but for a high order, three-dimensional basis typical of DIF3D-
VARIANT, this can be rather expensive and there is significant potential for a local peak to be
obtained rather than the true peak. The second approach is to pick a set of points in the domain
and evaluate the solution at those points and take the maximum value of the individual points.
Because of past experiences with the root finding technique applied to the VARIANT basis, a
point evaluation technique was chosen for VARPEAK.

 The default set of radial sample points used by VARPEAK is plotted in Figure 5.2 and
it should be quite apparent that the hexagonal evaluation (73) has more points than the Cartesian
(25). This is because the testing done on Cartesian geometries is rather non-existent at this point
and there was no need to refine it further. Testing on various hexagonal geometry reactor
problems lead to the displayed set of points. It should be clear that the points on the outer edge
of Figure 5.2 lie on the surface of the hexagon and box in the reference space. This ensures that
if the peak lies on the surface (or corner) that it is properly evaluated by VARPEAK. Axially,
these points are repeated at 11 equally spaced points including the upper and lower surfaces.

 Cartesian Hexagonal
 Figure 5.2. VARPEAK Default Radial Sample Points for Cartesian and Hexagonal

What should be clear from either sample point distribution is that there is no guarantee that the
obtained peak is the true peak in the mesh. From experience with DIF3D, other than control
rods, the peak almost always lies at the center of the mesh or on the surface, typically at the
corner point. For those cases where it does not lie at these locations, the above point distribution
for hexagonal geometries does a very good job getting a peak value very close to the true peak
in the mesh. Both distributions shown are hard-wired in VARPEAK, but the number of points
can be modified as is desired as the point determination is formulaic.

 Because the same spatial basis is used in all meshes, the polynomial evaluation of these
sample points yields an identical result for all meshes. That means the evaluation of the point
fluxes collapses to a matrix-vector product in each mesh with matrix dimensions

                                                      37                          ANL/NSE-22/55 Rev. 1

(NumSamplePoints,NumBasisMoments). The vector of course is the polynomial flux
coefficients for each mesh obtained from NHFLUX and the matrix itself is the evaluated
polynomial basis for all sample points. After the point-wise value of power density and fast flux
is obtained, a simple maximum can be applied to find the maximum in the mesh. For the
maximum over a given region and area, one just determines the maximum of all meshes that
are contained with the region or area. The underlying point evaluation is identical to that used
in EvaluateFlux and no further description of how it is done is required here. Unlike
EvaluateFlux, in VARPEAK, the same matrix is applied to all meshes which makes the sample
point evaluation comparably very efficient.

 5.2 VARPEAK Input Details

 The goal for VARPEAK is to provide the user with an updated evaluation of the peak
power density and the peak fast flux results shown in Figure 5.1. Figure 5.3 shows the header
output that is produced by VARPEAK for every execution which was setup similarly to other
utility programs such that it describes how to use it. As can be seen in lines 3 and 4 of Figure

methodology and the other on the GAMSOR power methodology via VARPOW. Figure 5.4
shows output excerpts when VARPEAK is provided the DIF3D power methodology while
Figure 5.5 shows the same output excerpts when VARPEAK is given the GAMSOR power
methodology. The evaluation of the power density and fast flux can be found in the DIF3D
manual and the GAMSOR manual and there is no difference in the approach implemented in
VARPEAK.

 The VARPEAK input described by Figure 5.3 primarily consists of binary interface
files generated by DIF3D or GAMSOR. The definitions of these binary files can be found in
the reference documentation [1,2,3,7] and are not discussed here. The only exception of course
is the GAMSOR (VARPOW) power methodology indicated on line 9 where VARPEAK can
handle both the 4 group (iOutput option P) and 8 group (iOutput option T) in VARPOW without
user intervention. Line 11 indicates that the user can provide a different power normalization
than what VARPOW is set for. This detail comes primarily because GAMSOR does not
normalize the power distribution to the original input value given to DIF3D. As a consequence,
the GAMSOR final power has been observed to be in error up to 5%. Thus if one were to
directly compare the peak power density results of VARPEAK without the proper power
normalization, the results could easily be misleading.

 Both the DIF3D and VARPOW execution pathways of VARPEAK allow for use of the
SFEDIT file. As stated earlier, the SFEDIT file is used by DIF3D (and REBUS) to produce the
peaking values shown in Figure 5.1. When provided to VARPEAK, they are used identically
to the way they are used in DIF3D to produce the comparison results. This allows the user to
easily compare the peaking results seen in the DIF3D output tables to the results obtained in
VARPEAK. Lines 15 through 19 in Figure 5.3 only appear when invalid input is provided to
VARPEAK. In this example, it occurred as no command line input was provided and the stated
files were not present in the working directory. The default names of the files are expressed in
the error outputs and thus one can execute VARPEAK without command line inputs although
it is not advised.

 5.3 VARPEAK Output Details

 When the DIF3D power methodology input is provided to VARPEAK, it constructs
spatial distributions in a similar form as the power and fast flux spatial distribution details that
VARPOW generates. Using the collapsed results eliminates a considerable portion of the point
evaluation done in NHSREG subroutine of DIF3D as only two spatial functions need to be
evaluated (instead of all groups of the multi-group flux).

 In both Figure 5.4 and Figure 5.5, the first section of output is identical. The first line
indicates how many sample points are used per mesh (803). The VARIANT monomial basis
and polynomial coefficient matrix are exported to the “VariantMonoExponents.out” file which
has an identical structure to that used by EvaluateFlux and VARPOW and thus Figure 3.4. The
next few lines of output detail the evaluation points given in the reference space for the X-Y
space. As seen, there are 73 radial sample points and 803/73 = 11 axial mesh points per radial
sample point. This output is provided so the user can plot the points and determine if they are
sufficient for their needs. The reference geometry space is detailed in the DIF3D-VARIANT
manual [4,5].

 Continuing with the next section of output in Figure 5.4 and Figure 5.5, the first line of
output after the radial sample points are given indicates the power normalization methodology
being used by VARPEAK. In Figure 5.4, the DIF3D power methodology is indicated and the
total power of the provided solution is displayed (1 megawatt). In Figure 5.5, the VARPOW
methodology is used where the GAMSOR related power of ~1.01 MW is reported followed by
the user desired power via the command line input (Power was set to 1 MW) and the scaling
factor that will be applied to all of the GAMSOR (VARPOW) results. As stated earlier, if this
scaling is not applied, then the power peaking results from VARPEAK will not be consistent
with those provided in the DIF3D output tables or the SFEDIT results repeated in VARPEAK.

 The output in Figure 5.4 and Figure 5.5 continues with the region-wise table of peak
power density and fast flux. The area-wise table is provided after the region-wise table. For the
region-wise table, the first four columns give the GEODST numbered region index, the region
name, the associated zone number and zone name. The next two columns give the volume from
the GEODST file and the one computed in VARPEAK. These two columns should always
match, and any inconsistencies indicate a basic problem with consistency of the GEODST and
NHFLUX file.

 The next three columns in the outputs are the power density, the peak power density
evaluated by VARPEAK (reported as NHFLUX) and the peak power density from the SFEDIT
data file. As can be seen, there are relatively trivial differences between most of the regions in
Figure 5.4 for the peak power density when using the DIF3D power methodology and the
SFEDIT file. For the GAMSOR power methodology in Figure 5.5, one finds considerably
larger differences indicating that the GAMSOR methodology can significantly impact the peak
power density result in both the driver regions (as seen in regions I20105 to I20109) and other
parts of the domain.

 After the SFEDIT column for peak power density are columns for total fast flux, the
peak fast flux calculated by VARPEAK (cited as NHFLUX in the table), and that taken from

 The area-wise table follows the region-wise table in Figure 5.4 and Figure 5.5 and has

as there is nothing to display. With the preceding stated, there is no additional details that need
to be expressed with regards to the VARPEAK output as it is rather straightforward for those

6 The DIF3DtoVTK Utility Program
 The DIF3DtoVTK utility program (dif3d_to_vtk.x) was created to assist in the
visualization of the DIF3D output. In the 1980s and 1990s, DIF3D was connected to a
visualization package called DISPLA. This software would generate postscript files directly
and allow the user to display one-dimensional lines of evaluated solution data (power, fast flux,
flux, etc.) and two-dimensional plots on a hexagonal, triangular, or Cartesian grid. The software
was developed external to ANL and was thus provided as a precompiled library to link to. As
the software development company has long since gone out of business, the DISPLA software
is no longer available. With the transition from SunOS to Linux in the 2004-2008 range at ANL,
the ability to link to the last provided compiled package was lost and the functionality was thus
lost.

 Since that time period, individual user efforts have allowed MATLAB [18], Excel [19],
and Python [20] to be viable pathways for replacing the older visualization post-processing
capability. More recent efforts in PyARC, built on Python, have made the process transparent
to the user. None of these capabilities allow the 3D aspect of the power, flux, etc. to be viewed
easily and for certain not customizable. Thus the purpose of the DIF3DtoVTK utility program
was to allow the user to make use of the existing visualization software for finite element
analysis. Unlike the pathways discussed above, this approach requires the user to learn how to
use a finite element visualization package such that they can create the plot of interest. Figure
6.1 shows some visualizations created in VisIt [21] with the geometry translation of
DIF3DtoVTK. As can be seen, the visualization capability allows for color pictures of not only
2-D plots, but also 3D distributions.

 6.1 Casting the DIF3D Geometry as a Finite Element Geometry

 As mentioned, the DIF3DtoVTK utility program was built to construct a finite element
geometry from the DIF3D structured grid geometry. The DIF3D code can handle 1D, 2D, and
3D structured geometries. Many of the DIF3D-FD specific geometries were included in
DIF3DtoVTK as were the DIF3D-Nodal and DIF3D-VARIANT geometries. At present, the
following geometries are handled by DIF3DtoVTK: Cartesian x, x-y & x-y-z, hexagonal and
hexagonal-z, r-z and r-z-θ, and triangular-z. This leaves relatively few geometries definable by
GEODST that are not handled by DIF3DtoVTK. In order to convert the GEODST geometry

                                                      45                       ANL/NSE-22/55 Rev. 1

into a finite element one, one must first identify a finite element file format. The VTK file
format [22,23] was chosen as it 1) was ASCII based and could be transferred to any machine,
2) required no external libraries to generate it, and 3) was very simple to understand and
implement. The VTK file format is not the fastest loading or lowest memory format which are
the primary weaknesses of choosing it.

 Figure 6.2 shows the finite elements supported by the VTK format, the picture of which
was retrieved from [23]. As can be seen, there are specific finite elements that are exact
reproductions of the geometries DIF3D supports. The problem of course is that the visualization
tool must also support all of these finite elements. Two finite element visualization packages
that were available at the creation of DIF3DtoVTK were Paraview [24] and VisIt [21]. These
packages only supported some of the finite elements available in the VTK file format: triangle,
quadrilateral, tetrahedron, hexahedron, and prism. It is not a surprise that hexagonal elements
were not supported as most finite element analysis packages and mesh generators did not
support that element type either.

 Figure 6.2. Finite Elements Supported by the VTK Format (taken from [23]).

 In the geometry translation, the DIF3D structured geometry is cast as an unstructured
finite element mesh. While the VTK file format does support a structured grid Cartesian
geometry, the hexagonal and triangular-z geometry options are not available and thus all
geometries are translated to unstructured finite element meshes. The mesh-wise data such as
flux, power density, region number, etc., are all considered to be vector data stored on the VTK
file after the unstructured mesh is defined.

 Focusing on the needs of DIF3D, the vector data can be plotted by element or by vertex
in most visualization packages. Because all of the binary output data produced by DIF3D,
except for NHFLUX, is focused on mesh averaged values, storing the vector data by element

ANL/NSE-22/55 Rev. 1                           46

is the best translation of the DIF3D output. The consequence of this approach means that each
energy group of the flux is stored as a separate vector in the VTK output file.

 For Cartesian geometries, the (linear) quadrilateral and hexahedron finite elements were
used leading to the minimal VTK file sizes for the geometry translation. For hexagonal and
hexagonal-z geometries, two (linear) quadrilateral and two hexahedral finite elements are used.
This causes a doubling of the vector data as the same value (e.g., power density or flux) must
be assigned for the two elements. For r-z and r-z- θ, the (linear) wedge element is used to define
the central circle of meshes and (linear) hexahedrons are used to define the remaining meshes
again leading to the minimal VTK file size. It is important to note that the r-z geometry is
represented as a 2D Cartesian geometry in the visualization package. Finally, for triangular-z
geometries, each mesh is represented as a single (linear) wedge element which leads to the
minimal VTK file size. It is not clear today whether the visualization packages listed can
support the other finite elements defined in the VTK file formats today and there is little
motivation to update the DIF3DtoVTK software as the existing approach works.

 All of the binary interface files listed in lines 3 through 6 are assumed to be present in

DIF3DtoVTK to build a finite element equivalent geometry of the DIF3D geometry, it must

it is the minimal input required.

 Except for GWDINT, the remaining binary files are all defined in the DIF3D
documentation [1,2,7], but the purpose of all of the files is summarized here. The ISOTXS,
LABELS, NDXSRF, and ZNATDN files are used by DIF3DtoVTK to create vector data of
isotopic reaction rates. The LABELS file is additionally used to evaluate the area edits for a

                                                      47                               ANL/NSE-22/55 Rev. 1

summary file of PWDINT. The FIXSRC binary file was added to DIF3D to allow the
visualization of a fixed source. This option was primarily added to allow users to inspect the
gamma source being generated by GAMSOR, but it also proved quite useful for the software
verification work of DIF3D [25].

 The RTFLUX file stores the average flux solution for every mesh for the forward
diffusion or transport equation and thus allows the multi-group flux solution to be visualized.
The ATFLUX file stores the average flux solution for every mesh for the adjoint diffusion or
transport equation. To be consistent with the DIF3D definition, the ATFLUX group-wise
solutions are re-ordered to be consistent with the RTFLUX file being displayed. The GTFLUX
file is produced when using GAMSOR and it allows the gamma flux solution to be displayed.

 The PWDINT file contains the average mesh power density data which when using
GAMSOR will split into GPDINT and NPDINT files for gamma and neutron power density,
respectively. All three files can be plotted by DIF3DtoVTK. As mentioned, GWDINT is not a
recognized binary file of DIF3D and was included in DIF3DtoVTK to allow a generic file to
be imported that has the same file format as PWDINT. As the visualization software typically
allows a means to manipulate vector data (calculate error or ratio between two vectors, etc.),
having an additional input pathway for power was needed to allow the user to directly compare
the power density file generated by a regular DIF3D solution against one created by GAMSOR.
With this in mind, it is not uncommon for users to overload the GTFLUX input to DIF3DtoVTK
with a different RTFLUX file to do said comparisons (e.g., compare differences in diffusion
and transport solution of a given problem).

 The command line input listed on lines 8 through 12 only consists of five words:
FISSION, CAPTURE, PRODUCTION, DENSITY, ACTINIDE. The first four of these will
cause the isotopic reaction rates to be stored on the VTK file. Internal to DIF3DtoVTK, all
isotopes are identified using the MC2-3 name on ISOTXS and thus only a few unique isotope
outputs will appear as opposed to region-wise cross sections. The ACTINIDE command line
flag will limit the isotopic reaction rate data to only consist of actinide isotopes (those ISOTXS
isotopes with fission). Using any of the command line options can lead to extremely large VTK
files and this approach is relatively unused today as the capability is rarely of strong interest.
Past uses were to display specific actinide reaction rate distribution in the core, such as U-238
capture or U-235 fission. EvaluateFlux replaced the need for this capability as it better exposes
the actual gradient.

7 Conclusions
 This document serves as the manual for the DIF3D utility programs EvaluateFlux,
VARPOW, VARPEAK, and DIF3DtoVTK. In the preceding sections the execution of DIF3D
and the binary files it produces was discussed. With the exception of the SFEDIT and PWDINT
files that require special DIF3D inputs, all of the files needed for the utility program are
generated as part of the regular DIF3D usage. The same files are generated at each time point
by REBUS within which DIF3D is embedded.

 The primary purpose of the EvaluateFlux utility program was to allow users to obtain
flux traverses through the domain and evaluate foil reaction rates. The input file for
EvaluateFlux was discussed and the mathematics behind how the point evaluation is done were
displayed. The output files produced by EvaluateFlux were listed and detailed.

 The purpose of the VARPOW utility program was to assist in creating input for DASSH.
In this regard, VARPOW will take the files generated during GAMSOR and merge the
PMATRX cross section data with the NHFLUX and GHFLUX files to produce spatial
distributions of the neutron and gamma heating. It also provides spatial distributions of the fast
flux in n/cm2/sec and the clad damage in dpa/sec. VARPOW allows the user to override the
default isotopic separation routine (split the power into fuel, clad, and coolant components)
with an input file called AssignIsotope.inp. This file is not required for VARPOW to function.
The primary input to VARPOW is on the command line where the user must list the connected
input files with an optional normalization power level. The NHFLUX formatted output file
from VARPOW can be read by EvaluateFlux and used to get traverses of the neutron and
gamma heating distributions, the fast flux, and the clad damage distribution.

 The purpose of the VARPEAK utility program was to provide an alternative evaluation
to the power and fast flux peaking in the domain to the special nodal procedure presently used
by DIF3D. The VARPEAK program does not have an input file and takes all of its inputs via
the command line. The output from VARPEAK is just a reproduction of the DIF3D output
tables for power and fast flux. If the SFEDIT file is provided, VARPEAK will provide a direct
comparison of the special nodal procedure result and that obtained by VARPEAK. VARPEAK
can also take the GAMSOR output in and provide an alternative evaluation that considers the
impact of gamma heat generation.

 The purpose of the DIF3DtoVTK utility program is to provide a pathway for the user to
visualize the DIF3D flux and power data. In DIF3DtoVTK, an unstructured finite element mesh
is constructed from the structured grid DIF3D data to produce a VTK file. Given a finite element
visualization package such as VisIt or Paraview, the user can take the translated data and
construct complex two- and three-dimensional plots of the flux and power distribution details
that DIF3D produces as output. As DIF3DtoVTK is called as a subroutine in PERSENT, the
spatial aspects of any perturbation problem can be visualized.

 The EvaluateFlux, VARPOW, VARPEAK, and DIF3DtoVTK utility programs are
distributed with every DIF3D release. With the preceding input and output details, the user
should have a good starting point for making use of them as they see fit. For any support on the
cited utility programs, feel free to consult nera-software@anl.gov as necessary.
