1 FleCSI Overview
1.1 What is FleCSI
FleCSI is a C++ framework for writing multi-physics simulations. FleCSI ab-
stracts away complicated backends, enabling high performance while eliminating
the need for users to directly manage memory and execution. This is done via
FleCSI’s data and execution model.

1.2 Execution Model
FleCSI uses a task based execution model. This means that the user defines
what they want FleCSI to execute inside of a task (a C++ function). The task
is then passed to FleCSI to be executed later. Passing tasks to FleCSI is done
via a scheduler. Schedulers have a member function called execute which ac-
cepts a task as a template argument, and accepts the task arguments as regular
arguments. This syntax places emphasis on the separation of task parameters
and task argument. The difference between parameters and arguments here is
important, as they are not only conceptually different, but can in fact be entirely
different types in FleCSI as will be discussed.

1.3 Data Model
FleCSI’s data model provides various types including index spaces, topologies,
and fields. Index spaces are an enumeration of every entity of a particular type
used for solving a problem (such as vertices or edges of cells). A topology is
how FleCSI groups index spaces and encodes information about how the data
is formatted in memory. Fields are the way in which the data itself is managed.
Fields may be defined, accessed, or “referenced”. Fields are defined by providing
the type of data (int, double, etc.), and a topology type. Field accessors provide
access to the data itself and can be thought of as a pointer pointing to the

data inside the index spaces associated with the topology the field is defined
on. Field accessors are instantiated with a field definition and a permission
which may be read, write, read and write, or no access. Field accessors are
one of the types that can be used as task parameters. Field accessors cannot be
constructed by the user, but are constructed by FleCSI directly. This is because
only FleCSI can know where the data is stored in memory (data is allocated
by FleCSI at runtime). Instead, users use field references, which act as opaque
handles, to interact with data. If a field accessor is used as a task parameter,
its corresponding task argument is a field reference.

2 User-Defined Types in Tasks
Currently in FleCSI there is no way to have a custom type with field accessor
members be a parameter for a task. It is also not possible to pass a custom type
with field reference members to execute (the argument side of task execution).
Such a feature would give users an ergonomic way of arranging their data and
defining associated behavior. In addition, topologies are currently being re-
examined. If the current topology format is dissolved, user-defined types could
provide a way of organizing data that was previously organized by topologies.
 Since FleCSI separates task execution into two sides, the receiver (parame-
ter) side and the caller (argument) side, to add support for custom types it is
necessary to extend both the parameter and argument sides. We do this by pro-
viding interfaces flecsi params and flecsi args, the first adding task parameter
support and the second adding execute argument support.

3 Implementation
The implementation of the new feature required modification of three primary
files. These files are launch.hh, prolog.hh, and bind parameters.hh, and are
located in the directory flecsi/exec/. The unit tests for the feature were imple-
mented in task.cc, and is located in the directory flecsi/exec/test/.

3.1 Parameter Side
We begin with the parameter side.

3.1.1    Launch
launch.hh handles task launch logic, detailing how task parameters and argu-
ments should be processed. The tag params tag was implemented as a default
initialized struct with no members, inheriting from bind tag. Its purpose is to
label custom types via inheritance, allowing FleCSI to use the appropriate proce-
dures to handle the custom type. In the case of params tag, it tells FleCSI that
the inherited type has the interface flecsi params, which is a member function

 2

that returns a tie (tuple of references) of the accessor members of the inherited
type.
 task param is a struct that handles the construction of task parameters
from execute arguments. A task param struct specialization was implemented
to handle task parameters which inherited from params tag. The specializa-
tion accounts for the accessor members by calling the parameter’s flecsi params
member function, exposing the accessors to FleCSI. It then uses the existing
FleCSI machinery to replace the task arguments given the accessors.
 The launch struct infers the launch-size of a given parameter-argument pair.
A launch struct specialization was implemented to similarly handle task pa-
rameters inheriting from params tag. The specialization calls flecsi params and
decays the elements (removes references, const, etc.). It then uses existing
FleCSI machinery to combine the launch sizes of the elements.

3.1.2   Prolog
prolog.hh handles the collection of backend-specific information for each parameter-
argument pair. The visit function is often used to recursively break down
parameters into types FleCSI can understand. A visit function overload was
implemented to handle params tag inherited types. The visit overload calls
flecsi params and then immediately passes it to visit along with a corresponding
argument passed by the caller, which will then proceed to call visit recursively.

3.1.3 Bind Parameters
bind parameters.hh handles parameter binding to arguments, and is thus spe-
cific to the parameter side. In bind parameters.hh, a function overload for visit
is needed that serves a very similar function as the visit function overload in
prolog.hh. The visit function overload in prolog.hh handles the caller-side, while
the visit function overload in bind parameters.hh handles the receiver-side. The
implementations are quite similar, only containing subtle differences. Just as in
prolog.hh, the visit in bind parameters.hh calls flecsi params, and it is passed
immediately to visit. However, as apposed to the visit in prolog.hh, no addi-
tional arguments are passed to visit in bind parameters.hh.

3.1.4 Task
task.cc handled unit testing and debugging for the feature. To test the feature,
a custom type was created to serve as a task parameter. Two fields, one of type
int and one of type double, were defined on a simple array topology. The custom
type was given two field accessors to these global fields as members. A simple
constructor was implemented which accepted field accessors used to initialize the
members (in fact, it is a requirement that the constructor have a signature that
corresponds to the type returned by flecsi params). A flecsi params member
function was implemented to return a tie of the accessor members. An additional
member function, update members, was implemented which updated the fields

 3

with test values using the accessor members. This was done to demonstrate the
ability to call additional member functions of custom types inside a task.
 Two tasks were implemented, both using the custom type as a parameter.
The first task was set field values which simply called the passed instance’s
update members member function. This would in turn update the fields with
the test values mentioned prior. The second task was get field values which was
used to ensure the fields were updated correctly.
 The tasks were executed with the scheduler, passing a tuple of field refer-
ences as execution arguments. These references are then later converted to field
accessors by FleCSI for compatibility with the parameter (this is the separation
of declaration and allocation in FleCSI). The get field values task was checked
with an assert.

3.2 Argument Side
The implementation of the argument side is similar to the implementation of the
parameter side. As stated before, bind parameters.hh is a concern for the pa-
rameter side only. Thus, launch.hh, prolog.hh, and task.cc are the only modified
files on the argument side.

3.2.1   Launch
In launch.hh, args tag (inheriting from convert tag) is implemented, analogous
to params tag. A replace function overload is implemented for args tag inherited
types. It calls flecsi args, passing its return value to replace arguments and then
returns the result. The launch specialization for args tag inherited types uses
flecsi args to determine launch size.

3.2.2   Prolog
In prolog.hh, a visit function overload is implemented which uses flecsi args and
passes it back to visit similar to the parameter side.

3.2.3 Task
In task.cc, a similar unit test is created to test the argument side. A custom
type is implemented which inherits from args tag. The implementation for the
custom type on the argument side has notable differences. One such difference
is an asymmetry in the members used.
 Field references may not be simply constructed. Rather, they are created
by passing a topology to a field that is defined on it (FleCSI defines the field
definition’s operator() to return a corresponding field reference). Thus, it is
more natural to store (C++) references to the topologies as members. Thus,
the constructor takes references to the topologies and with them initializes the
topology members. flecsi args returns the field references by returning a tuple
of the references produced by calling the relevant fields on the corresponding
topology members.

 Similar to the parameter side, two tasks were created, both having a tuple of
field accessors as their parameter. The first task was set values, which sets the
field values to test values. The second task is print values, and simply displays
the field values to confirm they were modified correctly. An instance of the
custom type is instantiated, and passed as an argument to execute for both
tasks.

4 Future Work
In the future we seek to merge the two features. To do this will require an
extension in logic, as FleCSI will need to be given a detailed order of operations
to successfully handle simultaneous use of both interfaces. Once complete, user-
defined types will be supported for both the parameter and argument sides
simultaneously.
