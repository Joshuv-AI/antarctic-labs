Foundations of the GraphAlg Language
Daan de Graaf, Robert Brijder, Nikolay Yakovets

Abstract
The GraphAlg domain-specific language for graph algorithms enables user-defined algorithms in graph databases. In this work we show how GraphAlg is built on top of the formal 𝖬𝖠𝖳𝖫𝖠𝖭𝖦 \mathsf{MATLANG} language for matrix manipulation. Starting from 𝖬𝖠𝖳𝖫𝖠𝖭𝖦 \mathsf{MATLANG} , we describe the extensions to 𝖬𝖠𝖳𝖫𝖠𝖭𝖦 \mathsf{MATLANG} needed to derive GraphAlg Core, a simplified version of GraphAlg that is used as the internal representation in the GraphAlg compiler. Furthermore, we prove that any GraphAlg Core expression can be simulated in an extension of for- 𝖬𝖠𝖳𝖫𝖠𝖭𝖦 \mathsf{MATLANG} that supports simultaneous induction.



1
Introduction

Graph algorithms are key components in many analytical workloads over graph data.
Despite graph databases being the natural home for such data, typical graph query languages such as Cypher
[
6
]
or GQL
[
10
]
are unable to express algorithms such as PageRank or Weakly Connected Components, forcing users to export their graph data and process it in external tools.
To bring user-defined algorithm support to graph databases, the
GraphAlg
language has been proposed
[
9
]
.

GraphAlg
is a domain-specific language for writing graph algorithms in the language of linear algebra.
It is specifically designed to be embedded in databases: the
GraphAlg
compiler transforms programs into an extended relational algebra that can be executed by an existing relational query processing engine with minimal changes.

The design of
GraphAlg
is based on
\mathsf{MATLANG}

[
1
]
, a formal language for matrix manipulation.
The
\mathsf{MATLANG}
language follows a principled and minimal design suitable for high-level optimization, with an established connection to relational algebra
[
2
]
, making it an ideal starting point for
GraphAlg
.
In this work we describe and motivate a number of extensions to
\mathsf{MATLANG}
for expressing a diverse set of graph algorithms, each adding a small feature to the previous extension, to eventually arrive at the
GraphAlg
Core language, a simplified version of the ‘full’
GraphAlg
language.
The
GraphAlg
compiler uses
GraphAlg
Core as its internal representation for
GraphAlg
programs, performing various analyses and optimizations such as constant propagation and sparsity analysis
[
4
]
.

By formalizing the connection between
GraphAlg
Core and
\mathsf{MATLANG}
, results from existing studies of
\mathsf{MATLANG}
can be leveraged for
GraphAlg
.
For example,
\mathsf{MATLANG}
has been shown to correspond to a natural fragment of relational algebra
[
2
]
.
We establish in this work that
GraphAlg
Core expressions can be simulated in an extension of for-
\mathsf{MATLANG}
that supports simultaneous induction (
Corollary

1
), suggesting that loop-free
GraphAlg
Core expressions translate to relational algebra.
Indeed, we implement this exact translation in the
GraphAlg
compiler.

Simultaneous Induction.

Many graph algorithms require iteration, which is the primary reason that Cypher and GQL (language without loops or recursion) are insufficient.
While iteration support in
\mathsf{MATLANG}
has been previously studied
[
7
,
8
]
, the proposed extensions only allow a single matrix value to be carried over between loop iterations.
Various graph algorithms, however, are naturally expressed using multiple state variables carried over between loop iterations, also called
simultaneous induction
.
Our proposed extension sifor-
\mathsf{MATLANG}
, based on for-
\mathsf{MATLANG}

[
8
]
, adds support for simultaneous induction to
\mathsf{MATLANG}
.

Leader Election and Loop Decomposition.

Another important problem in graph analytics is the selection of a representative vertex from a set, also called
leader election
.
We observe that while
\mathsf{MATLANG}
has no specific leader election operation, it can be simulated in sifor-
\mathsf{MATLANG}
using the powerful loop construct.
Conversely, if we do add a leader election primitive to the language, then the loop construct is unnecessarily powerful.
We propose an extension that decomposes the expressive power of the sifor-
\mathsf{MATLANG}
loop construct into two orthogonal constructs.
The resulting dec-
\mathsf{MATLANG}
language has simpler individual operations and can naturally express leader election, yet it has the same expressive power as sifor-
\mathsf{MATLANG}
.

Multiple Semirings.

The next issue we face is that
\mathsf{MATLANG}
expressions operate over a fixed semiring, while the natural semiring to use depends on the specific algorithm.
Complex algorithms can even use multiple semirings at different stages, requiring casting of values between different semirings.
We propose muse-
\mathsf{MATLANG}
, an extension of dec-
\mathsf{MATLANG}
that allows using multiple semirings within an expression.
We find that, perhaps counterintuitively, this extension does not increase the expressive power of the language: muse-
\mathsf{MATLANG}
and dec-
\mathsf{MATLANG}
(and therefore also sifor-
\mathsf{MATLANG}
) have equal expressive power.

Executable Specification.

The
\mathsf{MATLANG}
language and its extensions mentioned above are all formal languages:
some details of the languages are irrelevant to theoretical analysis, and are therefore only loosely defined.
In particular,
\mathsf{MATLANG}
does not specify the set
\Omega
of allowed pointwise functions, or which semirings may be used.
To create an executable specification of muse-
\mathsf{MATLANG}
, we fix a particular
\Omega
through a grammar, and define a set of semirings that is broad enough to support many graph algorithms.
The resulting language is
GraphAlg
Core, the small subset of
GraphAlg
that is used in the
GraphAlg
compiler for optimization.

The remainder of this paper is organized as follows.
In
Section

2
we recall the definition of
\mathsf{MATLANG}
, as well as the extension for-
\mathsf{MATLANG}
that adds iteration in the form of a loop construct.

Section

3
defines sifor-
\mathsf{MATLANG}
, which adds simultaneous induction.
In
Section

4
we decompose this loop construct to obtain dec-
\mathsf{MATLANG}
.
Next,
Section

5
proposes muse-
\mathsf{MATLANG}
, allowing multiple semirings to be used within a single expression.
We also show that muse-
\mathsf{MATLANG}
and dec-
\mathsf{MATLANG}
have equal expressive power.
Finally, in
Section

6
we introduce
GraphAlg
Core, fixing
\Omega
and the set of supported semirings.

2.1
MATLANG

\mathsf{MATLANG}
is a formal language for matrix manipulation using common matrix operations and linear algebra.
Previous work on
\mathsf{MATLANG}
has studied its expressive power
[
1
]
and connection to relational algebra
[
2
]
.

We assume a countably infinite set of matrix variables
\mathcal{V}
that serve as the inputs to
\mathsf{MATLANG}
expressions.
We also assume a repertoire
\Omega
of functions
f:R^{k}\to R
, where
R
is a semiring.
While we make no assumptions about
R
, previous works have used the complex numbers
[
1
]
or the real numbers
[
8
]
for
R
.
The syntax of
\mathsf{MATLANG}
expressions is defined by the following grammar:

\displaystyle e

\displaystyle::=M\in\mathcal{V}

(matrix variable)

\displaystyle\mid\quad e^{T}

(transpose)

\displaystyle\mid\quad\mathbf{1}(e)

(one-vector)

\displaystyle\mid\quad\diag(e)

(diagonalization of a vector)

\displaystyle\mid\quad e_{1}\cdot e_{2}

(matrix multiplication)

\displaystyle\mid\quad\Apply[f](e_{1},\ldots,e_{k})

(pointwise
application,
f\in\Omega
)

The definition of
\mathsf{MATLANG}
in
[
1
]
also includes a let binding expression
\mathsf{let}\ M=e_{1}\ \mathsf{in}\ e_{2}
for convenience.
As noted in
[
1
]
, this operation can be omitted without affecting the expressive power of the language, so we omit it from our definition.

Type System

We now recall the type system for
\mathsf{MATLANG}
from
[
1
]
.
We assume a sufficient supply of
size symbols
, denoted
\alpha,\beta,\gamma
, that represent the number of rows or columns of a matrix (e.g.,
\alpha\times\beta
).
Together with an explicit
1
, we can express column vectors (
\alpha\times 1
), row vectors (
1\times\beta
) and scalars (
1\times 1
).
A
size term
is either a size symbol or an explicit
1
.
Formally, a
type
is an ordered pair of size terms
s_{1}
and
s_{2}
, denoted
s_{1}\times s_{2}
.
A
schema

\mathcal{S}
is a function defined over a finite set of matrix variables
\mathcal{M}\subset\mathcal{V}
that assigns a type to each element of
\mathcal{M}
.
By
\mathcal{S}[M:=\alpha\times\beta]
we denote the schema obtained from
\mathcal{S}
by mapping
M
to
\alpha\times\beta
.
The type of an expression
e
with respect to a schema
\mathcal{S}
, if it exists, is denoted by
\texttt{type}_{\mathcal{S}}(e)
.
It is inductively defined as follows:

•

\texttt{type}_{\mathcal{S}}(M):=\mathcal{S}(M)
, for a matrix variable
M\in\mathcal{M}
;

•

\texttt{type}_{\mathcal{S}}(e^{T}):=\beta\times\alpha
if
\texttt{type}_{\mathcal{S}}(e)=\alpha\times\beta
;

•

\texttt{type}_{\mathcal{S}}(\mathbf{1}(e)):=\alpha\times 1
if
\texttt{type}_{\mathcal{S}}(e)=\alpha\times\beta
;

•

\texttt{type}_{\mathcal{S}}(\diag(e)):=\alpha\times\alpha
, if
\texttt{type}_{\mathcal{S}}(e)=\alpha\times 1
;

•

\texttt{type}_{\mathcal{S}}(e_{1}\cdot e_{2}):=\alpha\times\gamma
if
\texttt{type}_{\mathcal{S}}(e_{1})=\alpha\times\beta
, and
\texttt{type}_{\mathcal{S}}(e_{2})=\beta\times\gamma
;

•

\texttt{type}_{\mathcal{S}}(\Apply[f](e_{1},\ldots,e_{k})):=\alpha\times\beta
, if
\texttt{type}_{\mathcal{S}}(e_{i})=\alpha\times\beta
for all
i\in\{1,\ldots,k\}
and
f\in\Omega
.

We call an expression
e

well-typed
according to the schema
\mathcal{S}
if
\texttt{type}_{\mathcal{S}}(e)
exists.

Semantics

We denote the dimensions of a matrix
A
by
\dim(A)=m\times n
.
An
instance

\mathcal{I}
over a schema
\mathcal{S}
is a pair of functions
\mathcal{I}=(\mathcal{D},\mathsf{mat})
,
where
\mathcal{D}
maps size terms to matrix dimensions, and
\mathsf{mat}
assigns a concrete matrix to each matrix variable
M\in\mathcal{M}
,
such that
\dim(\mathsf{mat}(M))=\mathcal{D}(\alpha)\times\mathcal{D}(\beta)
if
\texttt{type}_{\mathcal{S}}(M)=\alpha\times\beta
.
We use the notation
\mathcal{I}(M)
as a shorthand for
\mathsf{mat}(M)
.
By
\mathcal{I}[M:=A]
we denote the instance obtained from
\mathcal{I}
by mapping matrix variable
M
to value
A
.
We write
(\mathcal{I}[M_{1}:=A])[M_{2}:=B]
as
\mathcal{I}[M_{1}:=A,M_{2}:=B]
.
The
evaluation
of an expression
e
with respect to an instance
\mathcal{I}
, denoted by
\llbracket e\rrbracket(\mathcal{I})
, is inductively defined as:

•

\llbracket M\rrbracket(\mathcal{I}):=\mathcal{I}(M)
, for
M\in\mathcal{M}
;

•

\llbracket e^{T}\rrbracket(\mathcal{I}):=\llbracket e\rrbracket(\mathcal{I})^{T}
, which is the transpose of
\llbracket e\rrbracket(\mathcal{I})
;

•

\llbracket\mathbf{1}(e)\rrbracket(\mathcal{I})
is an
m\times 1
vector with value
1
at all positions, where
\llbracket e\rrbracket(\mathcal{I})
is an
m\times n
matrix;

•

\llbracket\diag(e)\rrbracket(\mathcal{I})
is a matrix with the vector
\llbracket e\rrbracket(\mathcal{I})
on its main diagonal, and zero in every other position;

•

\llbracket e_{1}\cdot e_{2}\rrbracket(\mathcal{I}):=\llbracket e_{1}\rrbracket(\mathcal{I})\cdot\llbracket e_{2}\rrbracket(\mathcal{I})
;

•

\llbracket\Apply[f](e_{1},\ldots,e_{k})\rrbracket(\mathcal{I})
is a matrix
A
of the same dimensions as
\llbracket e_{1}\rrbracket(\mathcal{I})
, and where
A_{ij}
has the value
f(\llbracket e_{1}\rrbracket(\mathcal{I})_{ij},\ldots,\llbracket e_{k}\rrbracket(\mathcal{I})_{ij})

2.2
For-MATLANG

The language for-
\mathsf{MATLANG}

[
8
]
extends
\mathsf{MATLANG}
by a construct that we call the
canonical for loop
.
Its syntax is as follows:

\texttt{for}\,v,X\texttt{.}\,e

(canonical for loop, with
v,X\in\mathcal{V}
)

The associated typing rule is defined as:

\texttt{type}_{\mathcal{S}}(\texttt{for}\,v,X\texttt{.}\,e):=\texttt{type}_{\mathcal{S}}(e)
, if
\texttt{type}_{\mathcal{S}}(e)=\texttt{type}_{\mathcal{S}}(X)
and

\texttt{type}_{\mathcal{S}}(v)=\gamma\times 1

Let
b_{i}^{n}
be the vector of dimension
n
with value
1
at position
i
and zero at all other positions.
Such a vector is called
canonical
.
Assuming
\mathcal{I}(v)
is an
n\times 1
vector,
\llbracket\texttt{for}\,v,X\texttt{.}\,e\rrbracket(\mathcal{I})
is defined iteratively as follows:

•

Let
A_{0}
be the zero matrix of the same size as
\mathcal{I}(X)
.

•

For
i\in\{1,\ldots,n\}
,
A_{i}:=\llbracket e\rrbracket(\mathcal{I}[v:=b_{i}^{n},X:=A_{i-1}])
.

•

Finally,
\llbracket\texttt{for}\,v,X\texttt{.}\,e\rrbracket(\mathcal{I}):=A_{n}
.

Intuitively, this loop construct repeatedly updates state variable
X
by evaluating
e
, where
e
is allowed to refer to the previous state of the loop as
X
.
Additionally,
e
may refer to the
canonical vector

v
.
In the first iteration,
v
takes on value
b_{1}^{n}
, in the second iteration
b_{2}^{n}
, etc.

We can define a variant of the above loop construct that initializes
X
to an arbitrary expression
e_{0}
rather than
A_{0}
.
This variant, denoted
\texttt{for}\,v,X:=e_{0}\texttt{.}\,e
, has the same expressive power as the zero-initialized loop construct
[
8
]
.

3
Adding Simultaneous Induction

Many algorithms are naturally expressed using loops that update multiple state variables, also known as
simultaneous induction
.
Simultaneous induction is usually supported in programming languages and in certain query languages
[
3
]
.
For example, consider that a typical breadth first search algorithm requires keeping three pieces of state:

1.

A queue of vertices to be visited;

2.

The vertices that have been visited so far; and

3.

The depth at which each vertex was first visited (or alternatively, a pointer to the parent vertex).

The language for-
\mathsf{MATLANG}
, however, only allows a single matrix to be carried from one iteration of a loop to the next.
The lack of simultaneous induction makes it difficult, if not impossible, to express various commonly used algorithms in for-
\mathsf{MATLANG}
.
We discuss the implications for the expressive power of for-
\mathsf{MATLANG}
in detail in
Section

3.1
.

We propose an extension of for-
\mathsf{MATLANG}
, named ‘sifor-
\mathsf{MATLANG}
’, that supports simultaneous induction.
The sifor-
\mathsf{MATLANG}
language is obtained from for-
\mathsf{MATLANG}
, by modifying the loop definition to allow multiple loop variables:

\texttt{for}\,v,\{M_{1}:=e_{1}^{\prime},\ldots,M_{m}:=e_{m}^{\prime}\}(e_{1},\ldots,e_{m})

The typing rule is modified accordingly:

\texttt{type}_{\mathcal{S}}(\texttt{for}\,v,\{M_{1}:=e_{1}^{\prime},\ldots,M_{m}:=e_{m}^{\prime}\}(e_{d},e_{1},\ldots,e_{m})):=\tau_{1}
,

if
\tau_{i}:=\texttt{type}_{\mathcal{S}}(e_{i})=\texttt{type}_{\mathcal{S}^{\prime}}(e_{i}^{\prime})
for all
i\in\{1,\ldots,m\}
,

where
\mathcal{S}^{\prime}:=\mathcal{S}[M_{1}:=\tau_{1},\ldots,M_{m}:=\tau_{m}]

and
\texttt{type}_{\mathcal{S}}(v)=\gamma\times 1
.

Assuming that
\mathcal{I}(v)
is an
n\times 1
vector, the semantics of the loop are defined iteratively as follows:

•

Let
\mathcal{I}_{0}:=\mathcal{I}[v:=b^{n}_{1},M_{1}:=\llbracket e_{1}\rrbracket(\mathcal{I}),\ldots,M_{m}:=\llbracket e_{m}\rrbracket(\mathcal{I})]

•

For
i\in\{1,\ldots,n\}
, let
\mathcal{I}_{i}:=\mathcal{I}_{i-1}[v:=b^{n}_{i+1},M_{1}:=\llbracket e_{1}^{\prime}\rrbracket(\mathcal{I}_{i-1}),\ldots,M_{m}:=\llbracket e_{m}^{\prime}\rrbracket(\mathcal{I}_{i-1})]
.

•

Finally,
\llbracket\texttt{for}\,v,\{M_{1}:=e_{1}^{\prime},\ldots,M_{m}:=e_{m}^{\prime}\}(e_{1},\ldots,e_{m})\rrbracket(\mathcal{I}):=\mathcal{I}_{n}(M_{1})
.

The loop body defines a number of loop variables
m\geq 1
that each consist of a
binding variable

M_{i}
and a
body expression

e_{i}^{\prime}
.
Intuitively, before entering the loop, the binding variables are initialized as
M_{i}:=e_{i}
.
Evaluation of the loop is similar to for-
\mathsf{MATLANG}
, each time updating the binding variables with the results of the body expressions.
The loop produces a single result matrix, which is the final value of
M_{1}
.

The sifor-
\mathsf{MATLANG}
language subsumes for-
\mathsf{MATLANG}
.

Lemma 1
.

The loop construct of for-
\mathsf{MATLANG}
can be simulated using the loop construct of sifor-
\mathsf{MATLANG}
.

The above lemma follows directly from the following rewrite rule:

\texttt{for}\,v,X:=e_{0}\texttt{.}\,e\Rightarrow\texttt{for}\,v,\{X:=e\}(e_{0})

3.1
Does sifor-
\mathsf{MATLANG}
Strictly Subsume for-
\mathsf{MATLANG}
?

Adding simultaneous induction to a language does not always increase its expressive power.
In first-order logic, for example, simultaneous induction can be simulated with induction on a single predicate
[
5
, Chapter 8.2]
.
In this subsection we provide evidence to support the hypothesis that sifor-
\mathsf{MATLANG}
indeed has greater expressive power than for-
\mathsf{MATLANG}
.
We consider possible strategies for simulating simultaneous induction with a single loop variable, and show that none of them are applicable to for-
\mathsf{MATLANG}
.
We use the following simple recurrence as an example, which assumes two arbitrary input matrices
A
and
B
:

\displaystyle C_{0}

\displaystyle=A

\displaystyle C_{1}

\displaystyle=B

\displaystyle C_{i}

\displaystyle=C_{i-2}\cdot C_{i-1}

Encoding this recurrence in for-
\mathsf{MATLANG}
would require the simulation of simultaneous induction, because the value of
C_{i}
relies on the value of
two
previous loop states
C_{i-2}
and
C_{i-1}
.
For such a simulation to work,
C_{i-2}
and
C_{i-1}
must be encoded into a single matrix without loss of information.
Below we consider different strategies for combining two matrices
A
and
B
into one, and show that none of them can be applied to for-
\mathsf{MATLANG}
.

Additional Attributes.

In relational algebra, relations can have arbitrary arity.
For the recurrence above, matrices
A
and
B
can be stored in relations with attributes
(r,c,a)
and
(r,c,b)
, respectively.
To combine the two, we can simply create a table with four attributes
(r,c,a,b)
.
In relational algebra, simultaneous induction therefore does not increase expressivity.
Given that for-
\mathsf{MATLANG}
has the same expressivity as a particular fragment of relational algebra
[
2
]
, one might assume that the same holds in for-
\mathsf{MATLANG}
.
Crucially, however, in for-
\mathsf{MATLANG}
the matrix type limits us to arity 3
[
2
]
, so the strategy of using additional attributes does not carry over to for-
\mathsf{MATLANG}
.

Matrix Concatenation.

One might wonder whether in for-
\mathsf{MATLANG}
two
m\times n
matrices can be concatenated to form a single
2m\times n
(or
m\times 2n
) matrix.
However, given the type rules of for-
\mathsf{MATLANG}
it is apparent that such a matrix cannot be constructed.
Consider a schema
\mathcal{S}
with a mapping for two matrix variables
\mathcal{S}[A:=\alpha\times\beta]
and
\mathcal{S}[B:=\gamma\times\delta]
.
Then the only possible values of
\texttt{type}_{\mathcal{S}}(e)
for arbitrary
e
are combinations of
\alpha,\beta,\gamma,\delta
and 1.
Matrices must be constructed in terms of the dimensions of the inputs, and therefore concatenation of arbitrary matrices is impossible.

Pairing.

Two matrices
A
and
B
can be encoded in a single matrix using a pairing function
\pi:R\times R\to R
that maps each pair of elements
(A_{ij},B_{ij})
into a distinct value.
If
\pi
is an injective mapping, then applying
\pi
to matrices
A
and
B
gives a single matrix
C
from which both
A
and
B
can be recovered using the retraction of
\pi
.
For finite semirings, however, it is easy to show that
\pi
cannot be injective.
Let
R
be a finite semiring with cardinality
|R|
.
Then there are
|R|^{2}
distinct values in the domain of
\pi
, but only
|R|
in the co-domain, which is insufficient to map each pair
(A_{ij},B_{ij})
to a distinct value.
The implications of this are especially damning for a software implementation of for-
\mathsf{MATLANG}
, which would need to operate over fixed-size data types for performance.

None of the strategies described above succeed in simulating simultaneous induction in for-
\mathsf{MATLANG}
.
This supports the hypothesis that because of its support for simultaneous induction, the expressive power of sifor-
\mathsf{MATLANG}
is indeed greater than for-
\mathsf{MATLANG}
.

4
Decomposing the Loop Construct

The loop construct in sifor-
\mathsf{MATLANG}
can be replaced by two natural constructs:
A simpler loop definition without canonical vectors, as has been previously proposed in the context of
\mathsf{MATLANG}

[
7
]
and query languages in general
[
3
]
,
and an additional operation
\pickAny
, a type of aggregation in relational algebra, that is independently useful for tasks such as leader election.
This decomposition also has further advantages, which we discuss at length in
Section

4.1
.

Before giving the loop definition, we first define the typing rule and semantics of the
\pickAny
construct:

\texttt{type}_{\mathcal{S}}(\pickAny(e)):=\texttt{type}_{\mathcal{S}}(e)

The expression
\pickAny(e)
keeps the non-zero element with minimal column index of each row in
e
, setting all other entries to zero:

\llbracket\pickAny(e)\rrbracket(\mathcal{I})
is a matrix
A
of the same size as
\llbracket e\rrbracket(\mathcal{I})
, and where
A_{ij}

is
\llbracket e\rrbracket(\mathcal{I})_{ij}
if
\llbracket e\rrbracket(\mathcal{I})_{ik}=0
for all
k<j
, and
0
otherwise.

For the updated loop construct, we drop the canonical vector
v
, and instead use an input expression
e_{d}
to determine the number of iterations that the loop should run:

\texttt{for}\,\{M_{1}:=e_{1}^{\prime},\ldots,M_{m}:=e_{m}^{\prime}\}(e_{d},e_{1},\ldots,e_{m})

The updated typing rule is as follows:

\texttt{type}_{\mathcal{S}}(\texttt{for}\,\{M_{1}:=e_{1}^{\prime},\ldots,M_{m}:=e_{m}^{\prime}\}(e_{d},e_{1},\ldots,e_{m})):=\tau_{1}
,

if
\tau_{i}:=\texttt{type}_{\mathcal{S}}(e_{i})=\texttt{type}_{\mathcal{S}^{\prime}}(e_{i}^{\prime})
for all
i\in\{1,\ldots,m\}
,

where
\mathcal{S}^{\prime}:=\mathcal{S}[M_{1}:=\tau_{1},\ldots,M_{m}:=\tau_{m}]

and
\texttt{type}_{\mathcal{S}}(e_{d})=\gamma\times 1
.

Assume that
\llbracket e_{d}\rrbracket(\mathcal{I})
is an
n\times 1
vector.
The semantics are almost identical, except that
\mathcal{I}_{i}
does not include a matrix variable mapping to a canonical vector:

•

Let
\mathcal{I}_{0}:=\mathcal{I}[M_{1}:=\llbracket e_{1}\rrbracket(\mathcal{I}),\ldots,M_{m}:=\llbracket e_{m}\rrbracket(\mathcal{I})]

•

For
i=\{1,\ldots n\}
, let
\mathcal{I}_{i}:=\mathcal{I}_{i-1}[M_{1}:=\llbracket e_{1}^{\prime}\rrbracket(\mathcal{I}_{i-1}),\ldots,M_{m}:=\llbracket e_{m}^{\prime}\rrbracket(\mathcal{I}_{i-1})]
.

•

Finally,
\llbracket\texttt{for}\,\{M_{1}:=e_{1}^{\prime},\ldots,M_{m}:=e_{m}^{\prime}\}(e_{d},e_{1},\ldots,e_{m})\rrbracket(\mathcal{I}):=\mathcal{I}_{n}(M_{1})
.

We denote the language obtained from sifor-
\mathsf{MATLANG}
by simplifying the loop construct and adding
\pickAny
as dec-
\mathsf{MATLANG}
.
It turns out that these changes do not affect the expressive power of the language.

Theorem 1
.

Languages sifor-
\mathsf{MATLANG}
and dec-
\mathsf{MATLANG}
have equal expressive power.

The

Consider the problem of finding weakly connected components in an undirected graph

\mathsf{let}\ v=\mathbf{1}(e_{2}^{T})\ \mathsf{in}

\texttt{for}\,v\ \{

X:=\mathsf{let}\ B_{c}=e_{2}\cdot v\ \mathsf{in}

X+\mathsf{cellmul}[\underline{0},\oplus,\otimes](e_{1},B_{c})\cdot v^{T}

\}(\Apply[0](e_{1}\cdot e_{2}))

\mathsf{matmul}[\underline{0},\oplus,\otimes](e_{1},e_{2})=

\mathsf{let}\ v=\mathbf{1}(e_{1})\ \mathsf{in}

\texttt{for}\,v\ \{

X:=\mathsf{let}\ A_{r}=v^{T}\cdot e_{1}\ \mathsf{in}

X+v\cdot\mathsf{rowmul}[\underline{0},\oplus,\otimes](A_{r},e_{2})

\}(\Apply[0](e_{1}\cdot e_{2}))

The rewrite rule for matrix multiplication
e_{1}\cdot e_{2}
over semiring
R
is now simply:

e_{1}\cdot e_{2}\Rightarrow\mathsf{matmul}[\mathsf{enc}_{R}(0_{R}),\langle\oplus_{R}\rangle,\langle\otimes_{R}\rangle](\langle e_{1}\rangle,\langle e_{2}\rangle)

The above rewrite rules cover all language constructs in muse-
\mathsf{MATLANG}
, and therefore we conclude that for any muse-
\mathsf{MATLANG}
expression there exists an equivalent dec-
\mathsf{MATLANG}
expression.
∎

6
GraphAlg Core

We are now ready to define an
instantiation
of the muse-
\mathsf{MATLANG}
language (defined in
Section

5
), called
GraphAlg
Core.

GraphAlg
Core is the simplified, or
desugared
, version of the
GraphAlg
language.

GraphAlg
Core not only serves as a vehicle for theoretical analysis:
it is also used as an intermediate representation inside the
GraphAlg
compiler
[
4
]
.

GraphAlg
Core makes precise the following properties of the language that are irrelevant for theoretical analysis, but are necessary for an executable specification:

•

The repertoire
\Omega
is defined by extending the grammar to include syntax for defining pointwise functions.
An expression in this syntax is called a
scalar expression
.
While
\Omega
is not finite, execution platforms only need to support the fixed set of operations included in the syntax to execute arbitrary scalar expressions.

•

We fix the set of allowed semirings
SRing
to a number of semirings that are both highly relevant to the implementation of graph algorithms and practical to support across different execution platforms.

6.1
Syntax

The
GraphAlg
Core language syntax is obtained from muse-
\mathsf{MATLANG}
, with the following additional syntax:

\displaystyle f::=

\displaystyle(C_{1},\ldots,C_{n})\ e

(pointwise function)

\displaystyle e::=

\displaystyle\ C

(scalar variable)

\displaystyle|

\displaystyle\ r(l)

(scalar literal)

\displaystyle|

\displaystyle\ e_{1}\ \{+,\cdot,-,/,=\}\ e_{2}

(scalar arithmetic)

\displaystyle|

\displaystyle\ \cast(r,e)

(scalar cast)

We use the following notation:

•

e
represents a scalar expression

•

C
names a scalar value defined in a pointwise function.

•

l
is a literal value such as
42
,
3.14
or ‘true’.

•

r
is a semiring from the set:

\texttt{SRing}=\{\mathbb{B}_{\lor,\land},\mathbb{Z}_{+,\times},\mathbb{R}_{+,\times},\mathbb{Z}_{\min,+},\mathbb{R}_{\min,+},\mathbb{Z}_{\max,+},\mathbb{R}_{\max,+}\}

This includes the boolean, integer and real semirings
\mathbb{B}_{\lor,\land}
,
\mathbb{Z}_{+,\times}
and
\mathbb{R}_{+,\times}
, respectively.
For the integers and real numbers, their tropical min-plus and max-plus semirings are included as well.
The min-plus semirings define the addition operator as
\min
and multiplication as
+
, while the max-plus semirings use
\max
and
+
.

6.2

The typing rules match those of muse-
\mathsf{MATLANG}
except for

\texttt{type}_{\mathcal{S}}(\Apply[(C_{1},\ldots,C_{k})\ e](E_{1},\ldots,E_{k})):=\alpha\times\beta\times R_{o}

\texttt{type}_{\mathcal{S}}(E_{i})=

Typing rules for scalar expressions are presented below.
Because scalar expressions always produce a

•

\texttt{type}_{\mathcal{S}}(C):=\texttt{type}_{\mathcal{S}}(C)

6.3
Semantics

Like the typing rules above,
GraphAlg
Core largely follows the semantics of muse-
\mathsf{MATLANG}
.
The semantics of
\Apply[f]
and scalar expressions are defined as follows:

•

\llbracket\Apply[(C_{1},\ldots,C_{k})\ e](E_{1},\ldots,E_{k})\rrbracket(\mathcal{I})
is a matrix
A
of the same size as
\llbracket e_{1}\rrbracket(\mathcal{I})
,
and where
A_{ij}
has the value
\llbracket e\rrbracket(\mathcal{I}_{ij})
, with

\mathcal{I}_{ij}=\{C_{1}:=\llbracket E_{1}\rrbracket(\mathcal{I})_{ij},\ldots,C_{k}:=\llbracket E_{k}\rrbracket(\mathcal{I})_{ij}\}
;

•

\llbracket r(l)\rrbracket(\mathcal{I}):=l

•

\llbracket e_{1}+e_{2}\rrbracket(\mathcal{I}):=\llbracket e_{1}\rrbracket(\mathcal{I})\oplus_{R}\llbracket e_{2}\rrbracket(\mathcal{I})
, with

the semiring of
\llbracket e_{1}\rrbracket(\mathcal{I})
.

•

\llbracket e_{1}\cdot e_{2}\rrbracket(\mathcal{I}):=\llbracket e_{1}\rrbracket(\mathcal{I})\otimes_{R}\llbracket e_{2}\rrbracket(\mathcal{I})
, with
R
the semiring of
\llbracket e_{1}\rrbracket(\mathcal{I})

•

\llbracket e_{1}-e_{2}\rrbracket(\mathcal{I}):=\llbracket e_{1}\rrbracket(\mathcal{I})-\llbracket e_{2}\rrbracket(\mathcal{I})

•

\llbracket e_{1}/e_{2}\rrbracket(\mathcal{I}):=\llbracket e_{1}\rrbracket(\mathcal{I})/\llbracket e_{2}\rrbracket(\mathcal{I})

•

\llbracket e_{1}=e_{2}\rrbracket(\mathcal{I}):=\llbracket e_{1}\rrbracket(\mathcal{I})=\llbracket e_{2}\rrbracket(\mathcal{I})

•

\llbracket\cast(r,e)\rrbracket(\mathcal{I}):=\cast(R,r,\llbracket e\rrbracket(\mathcal{I}))
, whose definition is given below.

Casting

Function
\cast(R,T,v)
casts a value from semiring
R
to semiring
T
.
A key rule in casting is
additive identity preservation
: If
v=0_{R}
, the value after casting is
0_{T}
(see the second rule below).
This rule takes precedence over all rules that follow it.
For the remaining casting rules, only the domain of the semiring is significant.
To simplify the rule set, we write for example
\mathbb{Z}
where any semiring over integers is accepted.

\displaystyle\cast(R,R,v)

\displaystyle=v

\displaystyle\cast(R,r,0_{R})

\displaystyle=0_{r}

\displaystyle\cast(R,\mathbb{B},v)

\displaystyle=1\text{ if }v\neq 0_{R}

\displaystyle\cast(\mathbb{B},r,1)

\displaystyle=1_{r}

\displaystyle\cast(\mathbb{Z},\mathbb{R},v)

\displaystyle=v

\displaystyle\cast(\mathbb{R},\mathbb{Z},v)

\displaystyle=\lfloor v\rfloor

Preserving additive identities across casts is an important property for program optimization of matrices with sparse representations.

GraphAlg
is designed to support efficient execution over sparse matrix representations that store only non-zero elements (values that are not the additive identity).
Because of additive identity preservation, casting a sparse matrix to a different semiring only requires updating non-zero elements, because implicit zeros in the input remain zero in the output.
