Ascend-RaBitQ: Heterogeneous NPU-CPU Acceleration of Billion-Scale Similarity Search with 1-bit Quantization
Fujun He † , Chuyue Ye † , Huaxiang Cai † , Zetao Lv † , Baolong Cui † , Wenru Yan § , Chao Zhan § , Zigang Zhang § , Hao Yi † , Jie Xiang † , Xiabing Li † , Yuhang Gai † , Ziyang Zhang † , Pengfei Zheng † , Yunfei Du †

Abstract
. Vector similarity search is a critical component of modern AI systems, but traditional CPU-based implementations face fundamental scalability bottlenecks for billion-scale corpora due to prohibitive computational overhead and memory bandwidth limitations. While Neural Processing Units (NPUs) offer orders-of-magnitude higher compute density, existing CPU/GPU-optimized 1-bit RaBitQ quantization implementations cannot be directly ported to NPU architectures due to fundamental hardware mismatches, and homogeneous design paradigms struggle to simultaneously balance accuracy, memory footprint, and performance. This paper presents Ascend-RaBitQ, the first heterogeneous NPU-CPU optimized IVF-RaBitQ system for billion-scale vector search, built on the core insight that decoupling coarse ranking (NPU) from fine ranking (CPU) allows each stage to leverage its optimal hardware, breaking the long-standing accuracy-memory-performance trade-off. We propose a three-stage heterogeneous pipeline comprising AI Core-accelerated coarse ranking on 1-bit quantized vectors, on-device AI CPU Top- k k processing, and host CPU fine re-ranking on full-precision vectors. We introduce four NPU architecture-native optimizations: fused AIC-AIV operators for parallel distance computation, computation flow restructuring to exploit rotation orthogonality, fine-grained index block-level load balancing that breaks query boundaries, and intra-NPU pipeline parallelism between AI Core and AI CPU to mask Top- k k latency. Evaluation on standard datasets shows that Ascend-RaBitQ achieves 3.0 × \times to 62.8 × \times faster index construction than the CPU baseline, up to 4.6 × \times throughput improvement over the fastest CPU IVF-RaBitQ implementation, and over 100 × \times over the mathematically equivalent CPU baseline, while demonstrating encouraging scalability on distributed multi-NPU systems.

Preliminary

2.1.
Approximate Nearest Neighbor Search and IVF Index

High-dimensional vector similarity search is a core primitive for modern AI systems
including Agentic AI with industrial deployments now routinely supporting billion- to
trillion-scale vector corpora
(
23
;
27
)
.

2.1.1.
ANN Problem Definition

Given a vector corpus
\mathcal{X}=\{\mathbf{x}_{1},\mathbf{x}_{2},\ldots,\mathbf{x}_{N}\}
where each
\mathbf{x}_{i}\in\mathbb{R}^{D}
, and a query vector
\mathbf{q}\in\mathbb{R}^{D}
, the exact nearest neighbor search problem aims to find the vector
\mathbf{x}^{*}\in\mathcal{X}
that minimizes a distance metric
d(\mathbf{q},\mathbf{x}^{*})
(typically Euclidean distance or inner product).
Exact search has
\mathcal{O}(ND)
complexity per query, which is prohibitively expensive for billion-scale workloads.
Approximate Nearest Neighbor (ANN) search trades minor accuracy loss for orders-of-magnitude performance improvements, and is the standard approach in production deployments.

2.1.2.
IVF Index Structure

The Inverted File (IVF) index
(
20
)
is the de facto standard for billion-scale ANN production deployments.
It reduces the search space via vector clustering and consists of two phases:

Index Construction.

Run
K
-Means clustering on a training subset of the corpus to generate
nList
cluster centroids,
each defining an inverted list.
For each base vector
\mathbf{x}_{i}\in\mathcal{X}
, assign it to the inverted list of its nearest centroid.

Query Processing.

For an input query
\mathbf{q}
, compute its distance to all
nList
centroids, select the top
nProbe
nearest clusters as the search scope, and evaluate only the vectors in these selected inverted lists.
The search space is reduced by 2–3 orders of magnitude compared to a full corpus scan (
nProbe\ll nList
).

IVF is widely adopted in open-source ANN systems including FAISS
(
8
)
and ScaNN
(
15
)
due to its excellent scalability, low memory overhead, and flexible recall-performance trade-off.

2.1.3.
IVF Variants

Based on the storage format of vectors in inverted lists, three main IVF variants exist:

IVF-Flat
stores full-precision raw vectors directly in inverted lists.
It achieves the highest possible recall but requires
N\times D\times 4
bytes for FP32 vectors, limiting its applicability to small- to medium-scale datasets (up to
\sim
100 million vectors).

IVF-PQ
combines IVF indexing with PQ
(
20
)
, compressing high-dimensional vectors into compact PQ codes (typically 8–32 bytes per vector) and storing the codes in inverted lists.
It reduces memory footprint by 16–32
\times
compared to IVF-Flat, enabling billion-scale indices to fit in memory,
but suffers from non-negligible accuracy loss
due to quantization errors.

IVF-RaBitQ.

The IVF-RaBitQ algorithm adopted in this work retains the memory efficiency advantage of IVF-PQ while significantly reducing
quantization accuracy loss to address the fundamental trade-off limitation of prior IVF variants.
The RaBitQ quantization method and its integration into the IVF pipeline are detailed in Section
2.2
.

2.1.4.
Alternative Index Structures

For completeness, we note two alternative index structures:

Graph-based indexes
(e.g., HNSW
(
32
)
) deliver superior recall-latency trade-offs for moderate-scale datasets, but suffer from 2–3
\times
higher memory overhead and poor scalability for billion-scale corpora.

Disk-based indexes
(e.g., DiskANN
(
19
)
) support trillion-scale datasets by offloading indices to SSD, but incur 10–100
\times
higher latency than in-memory IVF solutions.

2.2.
IVF-RaBitQ Algorithm and Pipeline

IVF-RaBitQ combines IVF indexing with RaBitQ 1-bit quantization to enable high-throughput, low-memory vector search.
RaBitQ
(
12
)
compresses each high-dimensional vector into a compact binary code with formal error guarantees.
We describe the core quantization method, distance approximation scheme, and end-to-end retrieval pipeline.

2.2.1.
RaBitQ Quantization

Given a vector
\mathbf{x}\in\mathbb{R}^{D}
, RaBitQ first applies a random orthogonal rotation
\mathbf{P}\in\mathbb{R}^{D\times D}
to distribute information evenly across dimensions, yielding
\hat{\mathbf{x}}=\mathbf{P}\mathbf{x}
.
It then computes the residual between the rotated vector and a reference point
\mathbf{c}
(typically the cluster centroid to which
\mathbf{x}
is assigned), and extracts the sign of each dimension to produce a
D
-bit binary code:

(1)

\mathcal{Q}(\mathbf{x})_{i}=\operatorname{sign}(\hat{\mathbf{x}}_{i}-\mathbf{c}_{i})\in\{-1,+1\},\quad i=1,\ldots,D.

The quantized vector is stored as
\mathcal{Q}(\mathbf{x})
using 1 bit per dimension (
32\times
compression over FP32).
Two precomputed constants derived from the residual are stored alongside the binary code to enable distance reconstruction during query processing:

•

C_{\mathbf{x}}=\|\hat{\mathbf{x}}\|_{2}^{2}-\mathbf{c}\cdot\hat{\mathbf{x}}
, which depends only on the base vector
\mathbf{x}
and its assigned centroid
\mathbf{c}
;

•

The L1 norm of the residual
\|\hat{\mathbf{x}}-\mathbf{c}\|_{1}
, which is used together with the query-side L1 norm to reconstruct the full distance during the fine ranking step.

2.2.2.
Distance Approximation

During query processing, the query vector
\mathbf{q}
is similarly rotated to
\hat{\mathbf{q}}=\mathbf{P}\mathbf{q}
and quantized relative to the centroid
\mathbf{c}
of each probed cluster, yielding
\mathcal{Q}(\mathbf{q})
.
The asymmetric approximate distance between the full-precision query and a quantized base vector
\mathbf{x}
is computed as a scaled Hamming distance plus the precomputed constant
C_{\mathbf{x}}
:

(2)

d_{\text{approx}}(\mathbf{q},\mathbf{x})=\frac{\|\hat{\mathbf{q}}-\mathbf{c}\|_{1}}{D}\cdot\sum_{i=1}^{D}\mathbf{1}\bigl[\mathcal{Q}(\mathbf{q})_{i}\neq\mathcal{Q}(\mathbf{x})_{i}\bigr]\;+\;C_{\mathbf{x}}.

The scale factor
\|\hat{\mathbf{q}}-\mathbf{c}\|_{1}
can be computed once per query-cluster pair and reused across all vectors within that cluster.
Query-dependent terms that are common to all candidates (e.g.,
\mathbf{c}\cdot\hat{\mathbf{q}}
and
\|\hat{\mathbf{q}}\|_{2}^{2}
) are omitted from Eq. (
2
) because they do not affect the relative ranking of candidates.

Crucially, since both codes use
\pm 1
representation, the Hamming distance can be converted to an inner product:

(3)

\sum_{i=1}^{D}\mathbf{1}\bigl[\mathcal{Q}(\mathbf{q})_{i}\neq\mathcal{Q}(\mathbf{x})_{i}\bigr]=\frac{D-\mathcal{Q}(\mathbf{q})\cdot\mathcal{Q}(\mathbf{x})^{\top}}{2}.

Substituting Eq. (
3
) into Eq. (
2
) expresses the distance computation as a linear
combination of a matrix multiplication and per-vector constants.
This transformation is the foundation of our NPU acceleration: by batching multiple quantized base vectors into a
matrix
\mathbf{X}
, the distances from a batch of queries to all candidates can be computed via a single matrix
multiplication
\mathcal{Q}(\mathbf{q})\cdot\mathcal{Q}(\mathbf{X})^{\top}
, which maps directly onto the
Cube Unit’s high-throughput matrix multiply (Section
2.3.1
details the Da Vinci
architecture’s Cube Unit design).

2.2.3.
Online Query Retrieval Pipeline

IVF-RaBitQ query processing proceeds in three stages:

(1)

Cluster Probing:
The query vector is compared against all
nList
IVF cluster centroids, and the top
nProbe
nearest clusters are selected as the search scope.

(2)

Coarse Ranking:
Within the selected inverted lists, approximate distances are computed using Eqs. (
2
)–(
3
), and the top
M
candidates are retained.

(3)

Fine Ranking:
The full-precision vectors of the
M
candidates are fetched, exact distances are computed against the original query, and the final top
K
results are returned.

The coarse ranking stage dominates computational cost for billion-scale corpora and is the primary target of our
NPU acceleration.

Ascend NPU Architecture

The Ascend NPU family adopts the Da Vinci heterogeneous architecture, designed for high-throughput AI training and inference
workloads
(
30
;
17
)
.
Unlike CPUs and GPUs that employ hardware-managed cache hierarchies and uniform compute arrays, the Da Vinci architecture has three defining characteristics that directly shape our system design. An architectural overview is shown in Figure
1
.

.

2.3.1.
Heterogeneous Compute Units at Two Levels

The NPU organizes compute resources into two tiers of heterogeneity.
At the device level, the throughput-oriented AI Core array
is complemented by on-device AI CPUs—general-purpose scalar processors optimized for latency-sensitive,
control-heavy tasks such as sorting and scheduling.
Within each AI Core, two physically distinct execution units operate concurrently: the Cube Unit (AIC) for dense matrix
multiplication and the Vector Unit (AIV) for element-wise operations.
This two-level heterogeneity directly motivates our AIC-AIV fusion operator (Section
3
.2.1),
our computation flow restructuring (Section
3
.2.2),
and our decision to offload Top-
k
selection to the AI CPU with intra-NPU pipeline parallelism (Section
3
.3.3).

2.3.2.
Explicitly Managed On-Chip Buffers

Unlike GPUs where L1 data caches are hardware-managed, the Ascend NPU’s per-core Unified Buffer (UB) and L1 Buffer are entirely software-managed. Every byte of data reaching the compute units must be explicitly loaded by the developer via Memory Transfer Engine (MTE) instructions; there is no automatic caching or prefetching at this level. Total on-chip buffer capacity per AI Core is approximately 1 MB. The L2 Cache, by contrast, is hardware-managed and transparent to the programmer, operating analogously to GPU L2 caches. This hybrid memory model is the primary reason existing CPU/GPU RaBitQ implementations cannot be directly ported—they rely on hardware-managed L1 caches to absorb irregular index access patterns—yet it also enables our index block-level load balancing and explicit on-chip staging of quantized vectors (Section
3
.3.1), as well as our 1-bit vector computation adaptation (Section
3
.3.2), which together eliminate HBM bandwidth from the inner loop.

2.3.3.
Dedicated Asynchronous Data Movement Engines

The MTE handles all data movement between HBM and on-chip buffers, operating fully asynchronously with respect to the AI Cores and AI CPUs. Combined with the Huawei Cache Coherence System (HCCS)—a shared-memory interconnect between NPU HBM and host CPU memory—this enables overlapped pipelines spanning both intra-NPU and NPU-CPU boundaries. We exploit this asynchrony to build the intra-NPU pipeline between AI Core and AI CPU (Section
3
.3.3) and the cross-device pipeline between NPU and host CPU for fine re-ranking (Section
3
.3.4).

In summary, the Da Vinci architecture replaces the uniform compute and automatic caching paradigm of CPUs/GPUs with deliberate heterogeneity and explicit data orchestration. Section
3
describes how we translate each of these architectural properties into concrete system optimizations.

3.1.
Overall Design of Ascend-RaBitQ

3.1.1.
Index Construction

The index construction pipeline consists of three phases: the first two phases iteratively train IVF cluster centers using K-Means, and the third phase performs core RaBitQ quantization. Details are as follows:

•

Phase 1
: The CPU randomly generates
nList
initial cluster centers, and iteratively updates these centers based on the bucketing results returned from Phase 2.

•

Phase 2
: The vector dataset is partitioned into multiple batches according to HBM capacity, sequentially offloaded to the NPU for bucketing computation using the latest cluster centers, and results are transferred back to the CPU. Phases 1 and 2 iterate repeatedly until the K-Means termination condition (convergence or maximum iteration limit) is met. The core computation during bucketing is batch calculation of L2 distances between dataset vectors and cluster center vectors. We design an AIC-AIV fusion operator to improve computational efficiency, which is discussed in detail in Section 3.2.1.

•

Phase 3
: After bucketing information is finalized, RaBitQ quantization and constant precomputation are performed on all dataset vectors, including random orthogonal rotation, L1 distance calculation, and L2 norm calculation. To fully exploit the parallelism between AI Cube and AI Vector, we reorganize the traditional sequential computation flow, which is discussed in detail in Section 3.2.2.

3.1.2.
Search Pipeline

Ascend-RaBitQ processes queries at batch granularity. The first four phases perform coarse search on the NPU based on quantized indexes, and the final phase performs re-ranking on the CPU using raw vectors. Details are as follows:

•

Phase 1
: Batch computation obtains
nProbe
nearest cluster centers for each query vector. This process reuses the bucketing computation flow from index construction Phase 2, fully utilizing both AIC and AIV computing power.

•

Phase 2
: After the CPU obtains the cluster centers for each query, it performs load balancing scheduling according to batch size, number of
nProbe
, and number of AIV cores to maximize AIV utilization, which is discussed in detail in Section 3.3.1.

•

Phase 3
: Distance calculation is performed, with the core computation being the dot product between query vectors and 1-bit quantized indexes. Based on the INT8 format, we adopt the high-order
select
operator capability provided by the CANN software stack to achieve efficient 1-bit computing, with details discussed in Section 3.3.2.

•

Phase 4
: Top-
k
selection, where we leverage AI CPU computing power for this scalar-dominant computation. Two optimizations are adopted: first, IVF-aware pruning is performed to accelerate sorting; second, pipeline parallelism between AI Core and AI CPU (i.e., Phase 3 and Phase 4) is implemented within the batch to mask Top-
k
latency, which is discussed in detail in Section 3.3.3.

•

Phase 5
: The CPU performs re-ranking based on raw vectors to select the final Top-
k
results. We discuss different re-ranking schemes and our optimized NPU-CPU pipeline latency masking implementation in Section 3.3.4.

3.2.
Index Construction Acceleration

3.2.1.
AIC and AIV Fusion Operator

When calculating L2 distances between a batch of dataset vectors (or query vectors) and a batch of cluster center vectors, we decompose the computation into two parallel parts: dot product between dataset vectors and cluster centers, and norm calculation of each individual vector. The vector dot product is converted into matrix multiplication, where the left and right matrices are dataset vectors and cluster centers respectively, and we invoke CANN’s optimized
matmul
operator to run on AIC. The norm of each vector is calculated on AIV in parallel, and final L2 distance results are aggregated on AIV. We have developed a fused AIC-AIV operator that eliminates synchronization overhead between the two computing units, achieving parallel execution of dot product and norm calculation.

3.2.2.
Computation Flow Restructuring

In the standard RaBitQ pipeline, all vectors are first rotated by a random orthogonal matrix, then difference between dataset vectors and cluster center vectors (for sign extraction to obtain 1-bit quantized values), L1 distance, and L2 distance (precomputed constants) are calculated based on rotated vectors. Traditional implementations execute these computations sequentially since they share the same computing unit. Ascend-RaBitQ leverages the NPU’s heterogeneous computing capability to offload rotation computation to AIC, while decomposing subsequent computations to run in parallel with rotation. Normally, subsequent computations require rotated vectors as input, but we exploit the key property of orthogonal matrices that rotation does not change vector norms. We therefore advance the norm calculation in L2 distance computation to run in parallel with rotation as the first stage computation. In the subsequent second stage, similar to Section 3.2.1, dot product computation and remaining computations are executed in parallel on AIC and AIV respectively. This restructured flow fully unleashes the parallel computing potential of both AIC and AIV.

3.3.
Retrieval Acceleration

3.3.1.
Load Balancing

Similar to industry IVF solutions such as FAISS
(
23
)
, Ascend-RaBitQ divides each inverted list into
segNum
index blocks. Each index block is stored in contiguous physical addresses internally to improve memory access efficiency, while no contiguity requirement exists between blocks to improve memory utilization. When processing a batch of query vectors, a total of
b\times nProbe\times segNum
index blocks need to be processed for distance calculation, where
b
is the query batch size. Existing solutions generally launch distance calculation kernels at query vector granularity: they allocate
nProbe\times segNum
computation tasks to
coreNum
AIV cores for parallel execution, and launch
\lceil\frac{nProbe\times segNum}{coreNum}\rceil
kernels sequentially for each query. When
nProbe\times segNum
is not an integer multiple of
coreNum
, AIV cores will be idle during the last kernel launch for each query, wasting computing power, as illustrated in Figure
3
(a).

Ascend-RaBitQ breaks the query vector boundary and performs load balancing scheduling at index block granularity. Each kernel launch schedules
coreNum
index blocks and evenly allocates them to AIV cores for computation, as shown in Figure
3

3.3.2.
1-bit Vector Computation Adaptation

There are two main categories of distance calculation schemes for RaBitQ: 1) utilizing hardware native 1-bit operation
capabilities (such as the POPCNT instruction on CPUs) to directly calculate the dot product between query vectors
and 1-bit index vectors (CPU implementations require additional scalar quantization of query vectors into multiple 1-bit vectors);
2) the FastScan scheme, which precomputes Look-Up Tables (LUTs) and obtains dot product results through table
lookup
(
2
;
3
)
. On the Ascend NPU platform, CANN provides both the
select
operator and the
gather
operator, corresponding to these two approaches respectively.
select
takes two sets of vectors as input and uses each dimension of the first vector as a binary mask to select elements from the second vector, realizing the 1-bit direct operation approach. The
gather
operator implements the FastScan scheme: it first precomputes LUTs and then uses the quantized codes as indices to look up and gather the corresponding distance values from the LUTs.

Although
select
natively supports INT8 format while
gather
requires INT8-to-FP32 conversion, our empirical evaluation shows that
gather
-based FastScan achieves approximately 2
\times
higher throughput than
select
(Figure
9
). This is because FastScan offloads most computation to the LUT precomputation phase, which is executed once per query and reused across all index blocks. Therefore, Ascend-RaBitQ adopts the
gather
-based FastScan scheme. We leave a native INT8
gather
operator as a future work.

3.3.3.
Top-
k
Optimization

The Ascend NPU integrates a dedicated AI CPU, which is more suitable for processing scalar-dominant computations compared to the AI Core optimized for parallel vector operations. To fully utilize all NPU computing resources, Ascend-RaBitQ offloads Top-
k
selection to AI CPU and introduces two targeted optimization techniques. First, when traversing all distance calculation results for sorting, we maintain an upper bound in real time, which is the maximum distance in the current Top-
k
candidate set. Remaining distances larger than this upper bound are pruned and excluded from further sorting. We exploit the key IVF property that vectors in inverted lists of cluster centers closer to the query vector are significantly more likely to enter the final Top-
k
set. Therefore, we traverse inverted lists in the order of the distance between the query vector and their corresponding cluster centers, prioritizing lists of closer clusters to maximize pruning efficiency.

The second optimization is inter-unit pipeline parallelism between AI Core and AI CPU,
as illustrated in Figure
5
(a) and (b).
Specifically, within a batch, when a query vector completes distance calculation on AI Core, a dedicated flag in HBM is atomically set. The AI CPU continuously scans these flags and immediately starts Top-
k
computation for a query as soon as its corresponding flag is set. Our evaluation shows that this pipeline parallelism effectively masks nearly all Top-
k
latency, shortening end-to-end retrieval latency significantly.

3.3.4.
NPU-CPU Pipeline Parallelism

Ascend-RaBitQ adopts extreme 1-bit quantization to fully utilize limited HBM capacity, requiring a final re-ranking step on raw vectors to achieve acceptable recall rate. One candidate re-ranking approach is to send required raw vectors from CPU to NPU, and perform re-ranking on NPU to leverage its high vector computing throughput. The alternative is to perform re-ranking on CPU directly, avoiding cross-device data transfer. Figure
4
compares the end-to-end latency of these two re-ranking strategies across different scale factors of Top-
k
. It shows that CPU re-ranking maintains stable latency as the scale factor increases, while NPU re-ranking latency grows sharply and far exceeds the CPU approach. The primary bottleneck lies in the CPU data preparation step: to send the data, the CPU first needs to gather raw vectors from discontinuous memory space into contiguous buffers according to the returned Top-
k
coarse results, which becomes a significant performance bottleneck, especially when the Top-
k
value increases, as shown in Figure
4
. Therefore, Ascend-RaBitQ performs re-ranking on CPU to eliminate unnecessary data movement.

Although the computation amount of re-ranking is reduced by several orders of magnitude compared to coarse ranking,

This capability requires shared memory between NPU and CPU, which is natively supported in Ascend and Kunpeng

3.4.
Distributed Scaling

As vector dataset sizes continue to grow or throughput requirements increase further, single NPU devices will
eventually encounter bottlenecks in memory capacity or computing resources.
To address this challenge, Ascend-RaBitQ is designed with native distributed scaling capability.
We adopt a cluster-aware load balancing strategy to evenly partition quantized vector datasets across
multiple NPU devices, ensuring that the number of vectors in each inverted list is balanced across all nodes.
During the index construction phase, each NPU independently performs quantization operations on its responsible vector
shard in parallel, achieving near-linear speedup with increasing number of devices. During retrieval,
multiple NPU devices simultaneously process the same query batch, independently performing their local coarse
search computation tasks. Finally, the CPU aggregates results from all NPU nodes and performs global re-ranking to output
the final accurate Top-
k
retrieval results.

4.5.
Multi-NPU Large-scale Scalability Test

Finally, we evaluate the scalability of Ascend-RaBitQ on the billion-scale SIFT1B dataset using up to 8 Ascend NPUs to demonstrate its suitability for large-scale industrial deployment. Figure
10
presents the speedup of end-to-end throughput and raw distance computation throughput as the number of NPUs increases. As shown in the figure, the end-to-end throughput achieves only approximately 3
\times
speedup on 8 NPUs compared to a single NPU, falling short of linear scaling. This is because NPU acceleration primarily benefits the coarse ranking stage, while the overall throughput remains constrained by CPU re-ranking. As more NPUs are added, the system bottleneck progressively shifts from NPU computation to CPU post-processing. This finding suggests that introducing CPU pipeline parallelism to overlap re-ranking with NPU computation could further improve end-to-end throughput. In contrast, the distance computation stage scales more linearly, achieving approximately 4
\times
speedup on 8 NPUs. However, this still reaches only about half of the theoretical optimal value of 8
\times
.

Our in-depth analysis of the experimental data reveals two primary causes for the sub-linear scaling of distance computation. First, we manage vectors at the granularity of index blocks, where the total number of blocks determines the number of kernel launches. Even when inverted lists are distributed across different NPUs, the total number of blocks may not decrease linearly, leading to sub-optimal kernel launch efficiency at scale. Second, the vector counts across inverted lists are inherently uneven due to the data distribution. Although we employ block-level load balancing, when blocks from different lists are computed concurrently, inter-core load imbalance can still occur, further reducing linearity.

Two potential directions can address these issues. First, introducing list-level load balancing during clustering training could ensure a more balanced vector distribution across lists. Second, using a smaller block size would improve the granularity of block-level load balancing. However, smaller blocks lead to more fragmented memory storage, degrading memory access efficiency, and the increased number of blocks adds management complexity. Determining the optimal block size for different workload scenarios is an interesting research problem and remains as our future work.

k
selection, and host CPU fine re-ranking—our approach maps each stage to its optimal hardware, resolving the accuracy-memory-performance trilemma. Extensive experiments demonstrate that Ascend-RaBitQ achieves 3.0
\times
to 62.8
\times
faster index construction, up to 4.6
\times
throughput improvement over the fastest CPU implementation, and over 100
\times
over the mathematically equivalent CPU baseline. Controlled ablation studies confirm a cumulative 23.1
\times
speedup, and multi-NPU tests demonstrate scalable throughput on distributed configurations.

We are actively extending Ascend-RaBitQ to trillion-scale cross-NPU-node deployments, deepening integration with production vector databases such as Milvus

and Faiss
(
8
)
, and optimizing for low-latency single-query scenarios.
