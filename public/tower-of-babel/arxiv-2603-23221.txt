PRETTINESS - Privacy pResErving aTTrIbute maNagEment SyStem
Jelizaveta Vakarjuk, Alisa Pankova

Abstract
Recent advancements in the European regulatory frameworks (eIDAS2, GDPR) as well as increasing awareness of user privacy needs, have fostered a growing demand for identity management solutions that prioritise privacy. Attribute-based credential systems offer a solution, allowing users to prove ownership of their attributes to relying parties while selectively sharing specific attributes. While many systems have been proposed, and some systems have practical implementations, these solutions often store attributes locally on user devices. In this work, we propose an attribute management system, where the user attributes are stored in encrypted form by the attribute management service (AMS). AMS helps to offload the storage from the user’s mobile device and manage all the operations with credentials, including revocation. Our system is built by carefully balancing between the centralised and decentralised identity system approaches. The system relies on AMS, at the same time offering privacy against AMS, and ensuring integrity even if the AMS is corrupted. We prove security of the proposed system in the universal composability model.



1
Introduction

With the changes in the regulatory framework of eIDAS2, there is an increasing demand in the research of identity management solutions with privacy guarantees. eIDAS2 defines the new European Digital Identity (EUDI) Wallet concept that aims to provide a user with the way to manage and present their credentials to the relying parties (RP), while trying to ensure interoperability of solutions between the EU member states. The regulation
[
23
]
lists security and privacy requirements for wallets, mentioning
selective disclosure of data
,
generating pseudonyms and storing them encrypted
,
accessing a log of all transactions
(Article 5a, §4)
as well as
not allowing any party, after the issuance of the attestation of attributes, to obtain data that allows transactions or user behaviour to be tracked, linked or correlated unless explicitly authorised by the user
and
enabling privacy preserving techniques which ensure unlinkability
(Article 5a, §16). The currently proposed solution is defined in The Architecture and Reference Framework (ARF, version 2.7.3)
[
28
]
. Additionally, the ARF defines wallet functionalities, including ability of creating backup of a list of user’s attributes, attestations, and configurations as well as revocation by the issuer. In our view, the currently proposed solution defined in The Architecture and Reference Framework (ARF), is lacking some of the functionality and security properties. Similar concerns were raised in the Cryptographers’ Feedback on the EU Digital Identity’s ARF (version 1.4.0)
[
3
]
. However, we look at it from the different angle, trying to balance between the practical usability of the system and providing reasonable security and privacy guarantees.

According to the system description, the user is responsible for managing and storing the attributes themselves on their (mobile) device. However, to ensure a safe backup of credential data,
it is beneficial to have an Attribute Management Service (AMS) that would be responsible for storing user’s credentials. Such a service would also help with the process of issuing new credentials and revoking old ones. In this work, we introduce PRETTINESS – Privacy pResErving aTTrIbute maNagEment
SyStem. In design of Prettiness, we are trying to find the balance between the centralised and decentralised identity management systems. We ensure that the user is in charge of their credentials, allowing selective disclosure and revocation by the user. At the same time, a centralised AMS server helps user with the storage and management of those credentials. Additionally, while details of logging user transactions are omitted from the description of our protocol, this functionality can be added to the system by saving user’s signatures that are created to authorise each transaction with their credential. One more detail that we omit from the current definition of the protocol is the use of pseudonyms. However, we note that this functionality can be added to the system through the user identifiers
\mathsf{uID}
being used as pseudonyms.

In this work, we use revocation functionality that works through AMS and allows RP to verify the validity of presented credential without the need to request any additional information from the issuer, which is important to ensure that presentations cannot be tracked by the issuer. On the other hand, the AMS does not learn which credential is being revoked or presented. We allow two types of credential revocation: by the user and by the issuer, where revocation by the user does not require communicating with the credential issuer.

In our system, the user should be able to decrypt stored credentials and generate signatures. We ensure the protection of the cryptographic keys that need to be stored on the user’s mobile device by using server-supported threshold cryptography for signing and decryption, sharing the secret key between the user device and a supporting server. The same AMS can take the role of supporting server, storing the second key share and assisting in blind server-supported decryption and signing.

We describe the resulting system in terms of an ideal functionality, construct a protocol that implements that functionality, and provide a security proof in the universal composability
[
10
]
model.

3
. The system itself is presented in Sec.
4
. The efficiency of the system is evaluated in Sec.

Background

2.1
Related work

There are several well-known attribute-based credential (ABC) schemes that maintain privacy of users, allowing users to prove possession of credentials without disclosing any additional information. Among these schemes are Idemix
[
7
]
and U-Prove
[
21
]
. Idemix is provably unlinkable and unforgeable, and its security relies on the strong RSA problem. There are several real-world implementations of Idemix as PrimeLife
1
1

1

http://primelife.ercim.eu/about/factsheet
, last visited December 2025
, and Yivi app with IRMA backend system
2
2

2

https://docs.yivi.app/what-is-yivi/
, last visited December 2025
. U-Prove is more efficient compared to Idemix, as it can be implemented using elliptic curves, but it does not provide unlinkability. There is a number of other attribute-based systems that utilise bilinear pairings
[
8
,
25
,
2
]
, where performing operations with pairings is more expensive than performing exponentiations on an elliptic curve.

Additionally, there is a line of works focusing on the cloud-based ABC systems, where a dedicated cloud service helps to present the users’ credentials to the relying party. This approach is useful when there are efficiency constraints on the user’s device. In
[
18
]
authors have proposed a scheme, where the computations have been outsourced to a semi-trusted cloud, and the main underlying cryptographic construction is proxy re-encryption. Subsequent work
[
14
]
focus on improvements of the proposed scheme and mitigating possible attacks.

The Request For Comments (RFC)
[
12
]
defines a mechanism that allows the user to selectively disclose attributes from the JSON Web Token (SD-JWT) for the presentation. The idea behind the solution is to create hash commitments to the attribute values that can be later opened by the user by providing the attribute value itself with the salt used to create commitments.
Additionally, the RFC defines Key Binding JWT, where the user’s signature over SD-JWT is included.
This signature servers as proof of possession of the user’s private key to the verifier of the credential presentation. More precisely, the user is required to sign an issuer-signed JWT and corresponding disclosures selected for the presentation to the verifier. The verifier uses the user’s public key contained in SD-JWT to verify this signature.
This format is referenced in the EUDI Wallet ARF
[
28
]
as one of a few suitable standardised formats for releasing electronic attestations of attributes. In this work, we follow this approach as it describes an option of selectively disclosing attributes.

Another approach referenced in the EUDI Wallet ARF is mobile driver’s license (mDL)
[
16
,
26
]
. It is a digital representation of physical driving license, stored in the user’s mobile device. The format of mobile credential allows to use it for various types of user attributes, not only as a driving license. Similarly to JWT, it uses hash commitments with random salt to allow selective disclosure of attributes. A particular attribute management system CACS (Centralized Attribute Collection Service)
[
17
]
supports interaction of users, issuers, and relying parties, following mDL standards.

In this work, we follow the main idea of
[
17
]
, letting a centralized system help to manage user’s credentials. However, while
[
17
]
assumes a trusted server that is allowed to learn the user’s data, in this work we are protecting the user’s data from the server, improving the way credentials are stored and handled by the server. We also provide an integration of revocation mechanism, which has been missing in
[
17
]
. The usage of centralised server is motivated by the following reasons:

•

EUDIW ARF defines the need in backup of a list of the user’s attributes, attestations, and configurations. Thus, the attributes should be stored in a backup server by default.

•

The server can assist in managing revocations.

•

We need a centralised server for server-supported decryption and signing. This approach ensures that:

–

The adversary cannot decrypt attributes even if the adversary copies the mobile device’s memory in between decryption sessions;

–

If the memory of the mobile device gets leaked during the decryption session, a special mechanism of the server-supported signature schemes (clone detection) allows to decrypt attributes for at most one presentation before the server stops to communicate.

2.2
System requirements

The requirements that we pose on our system are mainly motivated by
[
24
]
and
[
3
]
. In
[
3
]
(2024), Carsten Baum et al. have given a feedback to the European Digital Identity ARF regulation, pointing out important properties that a system should achieve by law. The survey by Maximilian Richter et al.
[
24
]
(2023) is more technical, and it lists some properties of a system that are classified as "Essential" and "Important", and references to possible solutions that allow to achieve these properties.

Let us first go through the
essential
properties of
[
24
]
. We mark with
+
properties that we address in
Prettiness
system, and with
-
that we do not.

+

Completeness.
A valid credential will be accepted.

+

Soundness.
An invalid credential will be rejected.

+

Unforgeability.
A valid credential can only be created by the corresponding issuer. This can be achieved by letting the issuer sign a credential.

+

Freshness of the presentation.
Every presentation has to be created anew for every verification. This can be achieved by letting the verifier produce a challenge that the user should respond to (e.g. in the proof of key ownership).

+

Impossibility to duplicate credentials.
No one (except the issuer) may create a valid copy of a credential. This includes the ability of one user to present the same credential from multiple devices.
In this work, we propose to use a threshold key signature scheme with a clone detection mechanism
[
4
]
which gives a designated semi-trusted server the ability to detect that the signing protocol was initiated from different devices.

We note that the problem of
non-transferability
of the credentials is deeper, as we eventually cannot prevent a user from sharing their device with a friend. Using all-or-nothing approach
[
7
]
or one-time credentials that are not easy to obtain
[
6
]
would be possible, but we do not discuss such possibilities in this work, and leave these as optional additional mechanisms.

+

Revocation
is an essential feature that is difficult to implement efficiently while preserving privacy. An alternative approach to a separate revocation functionality is to set short validity time for the credentials, requiring credentials to be frequently re-generated. However, we believe that introducing separate revocation functionality is essential for the usability of the attribute management system in practice. While the user should be responsible for managing and storing their
attributes, ARF also requires that the issuer should be able to revoke their issued credential at any time. Assume that the user has a driver licence issued and stored in the system. After an event requiring the police to revoke driver’s licence occurs, police should be able to revoke the user’s driver’s licence by contacting the issuer.

Let us now go through non-essential, but
important
properties of
[
24
]
.

+

Selective disclosure
. The user should be able to present only certain attributes of a credential. In the survey of
[
22
]
, the methods for this are classified to hash-based, signature-based, and zero-knowledge based. In this work, we use a kind of hash-based disclosure.

-

Unlinkability of presentations
. The verifier should not be able to correlate several presentations of the same credential.
In this work, we are considering the setting where the relying party
should
learn the user’s identity, so we are not aiming for this property. This is in accordance with (Article 5a, §16), as in this case the user
explicitly
authorises linkability. We see our system in the context of legal transactions by officially recognised issuers, like presenting driving/fishing licence, or getting access to a building. We do not aim to use it in anonymous transactions (like shop purchases).

-

Repudiation
. RP should not be able to prove the authenticity of verified statements to a third party. In this work, we are not aiming for this property. In contrary, we believe that we may need non-repudiation for later accountability of transactions (although we leave it out of scope of this paper).

2.3
Participants and Threat model

In this section, we discuss the participants and the threat model for our system, including constraints on what a corrupted party should be allowed to see or do, motivated by the list of requirements on credential management systems
[
24
]
.

User
is the party to whom the attributes (and, hence, credentials) belong. A user can use their mobile device to get credentials from an issuer, present them to a relying party (RP), and revoke credentials previously issued to them. User can be
dynamically
corrupted, and
corruption level

c_{\mathsf{U}}
may increase. There are the following corruption models for the user:

•

c_{\mathsf{U}}=0
(no corruption)

•

Starting from
c_{\mathsf{U}}=0
(no corruption), the corruption level may rise to
c_{\mathsf{U}}=1
(partial corruption, after the key generation). This can advance further, moving to
c_{\mathsf{U}}=2
(partial corruption
and
learning user’s
\mathsf{PIN}
)

•

c_{\mathsf{U}}=3
(full corruption, before key generation)

The motivation behind introducing
c_{\mathsf{U}}=1
is that we want to ensure privacy of the user data even if its mobile device memory gets leaked (e.g. the device gets malware), but the secret key
stored encrypted under the user’s
\mathsf{PIN}
is not leaked. For
c_{\mathsf{U}}=2
, the attacker learns all the device memory, including the the secret key. This can happen if adversary guessed correct user’s
\mathsf{PIN}
. The final case,
c_{\mathsf{U}}=3
means that adversary has fully corrupted the user’s device, including access to memory and ability to issue requests. In this case, the attacker learns everything, and there are no privacy guarantees for the user.

The adversary can corrupt the user before key generation, reaching level
c_{\mathsf{U}}=3
. Otherwise,
c_{\mathsf{U}}=0
is assumed during the setup phase, and the adversary may increase the corruption levels later. The adversary can clone device memory, reaching level
c_{\mathsf{U}}=1
(the main focus of security analysis). If the adversary guesses
\mathsf{PIN}
, it proceeds to
c_{\mathsf{U}}=2
, and there are no privacy guarantees for the user anymore.

The reason for analysing our system in such corruption model is that static corruption of the user (from the beginning of the protocol) does not allow us to rely on specific properties introduced by server-supported signing protocol. To make use of the user’s key protection mechanisms, we need to assume that the user has not been corrupted during the key generation and adversary can copy device’s memory.

Attribute management service (AMS)
is responsible for helping the user to manage storage and interactions with their credentials. AMS server can be
statically
corrupted. In particular, we assume a
covertly

[
1
]
(explained in more details in Sec.
2.4
) corrupted server, which may deviate from the prescribed routines, but will not do it if the probability of being caught is sufficiently large. Such an assumption is reasonable for AMS established by an institution which cares for its reputation.

AMS server is allowed to see credential issuance requests submitted by the user, including the issuer identifier (as AMS is responsible for establishing connection). It is also allowed to see the
identifiers
of requested attribute, as these likely depend on the issuer identity anyway. However, AMS server should not learn the
values
of attributes that are a part of issued credential.

If AMS has not seen the credential yet (e.g. from an issuer or a RP), it should not be able to learn when that credential has been revoked. Also, it should not be able to track which credentials have been presented, and to which RP (unless RP is also corrupted).

Issuer
is responsible for issuing credentials to the user, signed with the issuer’s private key. Additionally, the issuer has authority to submit credential revocation requests to the AMS for the law enforcement purposes. Issuer can be
statically
corrupted. The issuer should not be able to track presentations (unless colluded with RP) and revocations by the user (unless colluded with AMS) of its credentials.

Relying Party (RP)
is a party requesting to see certain user’s attributes to authenticate user or to give access to certain services. RP can be
statically
corrupted. From presentation, RP should not be able to learn anything except the attributes than the user has explicitly shown to it. However, we do not aim for unlinkability of presentations, as this can be tracked through the issuer’s signature. Differently from the anonymous credentials of Idemix
[
7
]
, we are assuming standard signatures like RSA and ECDSA (for compatibility with current standards), which cannot be updated for every presentation without the issuer. Nevertheless, we see the possibility of unlinkability using proofs of ECDSA signatures in zero-knowledge as in
[
13
]
. This addition is out of scope of this paper. Similarly to the EUDIW defined in ARF
[
28
]
, our solutions supports methods proposed in ARF (section 7.4.3.5.2) for dealing with RP linkability. For the
once-only attestations
, user would need to run issuing protocol several times to obtain batch of the credentials (for the same attributes). Then each credential is used only once. For the
limited-time attestations
, issuer will need to include additional entry to the credential, defining the validity period of credential. However, even with this method we still allow to use long-term attestations with revocation. For the
rotating-batch attestations
, user would need to run issuing protocol several times to obtain batch of the credentials. During the presentation, user would randomly choose which credential from the batch to present. This method does not restrict credential to be used only once. In this case, random selection of credential for presentation and resetting the batch happens in the environment. Finally,
Per-Relying Party attestations
method can be achieved through parametrising
\mathcal{F}_{\textsf{ideal}}
with RP. Meaning that the user will use different instance of
\mathcal{F}_{\textsf{ideal}}
for each RP.

2.4
Covert Adversary

In this work, we will make some assumption on the corruption of the AMS server. Since AMS is assumed to be a reputable entity, one option would be to assume a honest-but-curious server, which will not deviate from prescribed protocols. However, in practice it could be a too strong assumption, as even a reputable entity could be capable of silent cheating, which would not be detected, but could potentially harm user privacy. To ensure that such silent attacks are not possible, we make use of the notion of a
covert
adversary, proposed by Aumann and Lindell
[
1
]
. Intuitively, a covertly corrupted party will not cheat if it will be caught with a certain non-negligible probability.

In this work, we strengthen this assumption. We assume that the AMS will not cheat if it will be
possible
to prove the fact of cheating to a third party. In particular, while AMS will be technically able to conceal the fact of revocation from the verifier, the revoker and the verifier together will be able to detect the problem and prove to a third party (e.g. external judge) that AMS has cheated.

2.5
Universal Composability

Universal composability (UC) model
[
10
]
follows the real-ideal world paradigm. In the real protocol execution, honest parties run the protocol
\pi
over a network controlled by an adversary
\mathcal{A}
, who can also corrupt some parties by sending a special corruption message directly to the party. In the ideal world, honest parties are viewed as
dummy parties
who forward their inputs directly to the ideal functionality
\mathcal{F}
that internally executes the main task of the protocol, allowing the adversary to send certain corruption messages to a special interface of
\mathcal{F}
, whose effect on the outcome of
\mathcal{F}
is specified explicitly. In hybrid model, ideal functionalities can in turn be used by parties of the real protocol, and the adversary may communicate with them directly via adversary interface.

There is an environment
\mathcal{Z}
, representing the whole world outside of the protocol, which provides inputs to the parties and receives corresponding outputs. The protocol
\pi
securely realises ideal functionality
\mathcal{F}
if for every real adversary
\mathcal{A}
attacking the protocol there exists an ideal adversary (simulator)
\mathcal{S}
, such that no environment
\mathcal{Z}
can distinguish whether it is interacting with the protocol
\pi
and real adversary
\mathcal{A}
or with ideal functionality
\mathcal{F}
and simulator
\mathcal{S}
. Intuitively, any attack on the environment that is possible in the real world, is also possible in the ideal world.

Signing functionality

For the digital signatures that are needed to sign issued attributes, we propose to use any of the standardised signature schemes like ECDSA, RSA. For the security analysis, we use digital signature ideal functionality

we propose to use privacy-preserving server-supported decryption from

that was created using the key
\mathsf{\vphantom{p}pk}
. This functionality is initiated by both parties, client and server with the client being the one who provides the ciphertext
c
as input. A corrupted client cannot decrypt more ciphertexts than the number of decryptions approved by the server.

Additionally, we introduce
a new interface to the functionality
\mathcal{F}_{\textsf{tdecrypt}}
– verification of decryption. After receiving signed encrypted credential and corresponding disclosure, RP can use it to verify that the disclosure indeed corresponds to the ciphertext from signed credential.

Verify decryption
requires inputs from the user and some other verifier party (in our case, the RP). Given user consent,
\mathcal{F}_{\textsf{tdecrypt}}
tells to the verifier whether the pair
(m,c)
provided as input has been saved in table
\mathsf{T}
of previously encrypted ciphertexts.

We propose to extend threshold decryption protocol from
[
19
]
with this interface as follows. In the protocol of
[
19
]
that UC-realises
\mathcal{F}_{\textsf{tdecrypt}}
, the ciphertext is of the form
c=(\mathsf{SE}({k},{m}),H^{\prime}(k,m))
for some hash function (random oracle)
H^{\prime}
where
\mathsf{SE}({k},{m})
is symmetric encryption of the message
m
with the key
k
, the second component
H^{\prime}(k,m)
makes the decryption unique, and the single-use key
k
is derived through KEM (key exchange mechanism) between the client and the server.

1.

Together with the ciphertext
c
, the user reveals the message
m
and the single-use KEM key
k
to decrypt
c
.

2.

The verifier parses
c
as
(c_{1},c_{2})
and performs the following checks:

•

check that
m=\mathsf{SD}({k},{c_{1}})
(symmetric decryption of
c_{1}
with
k
).

•

check that
H^{\prime\prime}(k,m^{\prime})=c_{2}
(note that this check does not allow the user to reveal a different
k
and make
c
open to a different message).

3.3
Revocation mechanism

For revocation of credentials, we use functionality of
[
20
]
. This functionality allows to extend the credential with a special
revocation token
in such a way that only a designated revoking party will be able to revoke that token. A credential that is linked to a revoked token is also considered revoked. We will assign the revoker role to
both
the user and the issuer, creating
two
distinct revocation tokens for one credential. This ensures that the issuer will not learn that the user has revoked the credential issued by that issuer. We use functionality
\mathcal{F}_{\textsf{rev}}
defined in
[
20
]
(presented in Figures
13
and
14
in App.
0.A
).

In this functionality, we have the server
S
(in practice, the AMS server) who maintains the set
X^{-}
of revoked tokens, the revoker
R
(the issuer or the user) who gets the issued token and may revoke it later, the user
U
who has the right to query token revocation status, and the verifier
V
(in practice the RP) who learns
x
and whether
x\in X^{-}
.

Initialisation.
The adversary chooses the universal set
\mathcal{X}
of tokens. The size of
\mathcal{X}
is given as a parameter to
\mathcal{F}_{\textsf{rev}}
, so it is not allowed to be too small.

Issuing.

\mathcal{F}_{\textsf{rev}}
samples a fresh token
x\leftarrow\mathrel{\mkern-2.0mu}\mathrel{\mathchoice{\vbox{\hbox{$\displaystyle\textnormal{\$\hskip-0.52502pt}$}}}{\vbox{\hbox{$\textstyle\textnormal{\$\hskip-0.52502pt}$}}}{\vbox{\hbox{$\scriptstyle\textnormal{\$\hskip-0.36751pt}$}}}{\vbox{\hbox{$\scriptscriptstyle\textnormal{\$\hskip-0.26251pt}$}}}}\mathcal{X}
that it outputs to the user and to the revoker. In our case, the revoker party can be the user or the issuer. The issuer may then include
x
into a credential as a special attribute (this will happen in the embedding protocol, outside of
\mathcal{F}_{\textsf{rev}}
).

Revocation.
A party
R
may revoke
x
if
\mathcal{F}_{\textsf{rev}}
has previously declared
R
as revoker of
x
. A revoked token is added to the set
X^{-}
of revoked tokens.

User notification.
The user
U
may ask from
\mathcal{F}_{\textsf{rev}}
whether a token, that belongs to the user
U
, has already been revoked. Such a notification would be called just before verification, to ensure freshness of revocation status.

Verifier notification.

\mathcal{F}_{\textsf{rev}}
remembers the current state of revocation database for future reference, without leaking anything to
V
. Such a notification could be triggered just before verification, but having it as a separate routine can be more practical.

Verification.
The user presents a token
x
. The verifier learns
x
and whether
x
has been revoked at the moment when
V
made its last
verifier notification
request.

Cheating detection.
The functionality
\mathcal{F}_{\textsf{rev}}
proposes interfaces for cheating detection, which allow the revoker and the verifier together to figure out whether any revocation by that revoker has been silenced from the verifier. This interface is important, assuming that the covertly corrupted server will not cheat if it will be accountable for cheating. We formalise this assumption in Definition
1
.

Definition 1
(covertly corrupted AMS)

We say that AMS is
covertly
corrupted if the adversary will not interact with the protocol in a way that allows an honest revoker
R
and a honest verifier
V
to make cheating detection interface of
\mathcal{F}_{\textsf{rev}}
report AMS as cheater.

4.1
Ideal functionality

We start with defining system functional and security requirements in the form of ideal functionality. The ideal functionality
\mathcal{F}_{\textsf{ideal}}
is inspired by the previous works
[
5
,
15
]
with some adjustments to fit design principles and requirements,
following the model defined in Section
2.3
. We can view
\mathcal{F}_{\textsf{ideal}}
as an ideal credential storage, which stores issued credentials, and also allows to revoke them, and present to third parties. Let us use
\mathsf{ST}
to denote the storage, which in practice will be realised by a single AMS server. Ideal functionality provides the following interfaces –
Initialisation
,
Issue
,
Present
,
Revoke
,
Verify
,
Corrupt
. Every call to such an interface includes a session identifier
\mathsf{sid}
, which is needed to separate calls from each other. It does not contain any private data by itself, but leaking
\mathsf{sid}
to
\mathcal{A}
allows it to match the session against a certain call from the environment.

Initialisation
is used to initialise tables
\textsf{T}_{a},\textsf{T}_{r},\textsf{T}_{p},\textsf{T}_{v}
, for storing issued attributes, revocation information, credential presentations and verification information correspondingly. Additionally,
\mathrm{c}_{\mathsf{U}}=0
gets initialised, storing information about the corruption level of user
\mathsf{U}
, as in Section
2.3
. Next, we let adversary define
\mathsf{Present}
and
\mathsf{Ver}
functions.
\mathsf{Present}
generates credential presentation for the presentation phase, and
\mathsf{Ver}
is the corresponding verification function. We need these functions to be able to output a particular presentation to
\mathcal{Z}
to be shown later to a verifier, who can verify it using
\mathcal{F}_{\textsf{ideal}}
.

Silent request
is initiated by adversary at any point of time trying to query
Issue
,
Revoke
or
Present
interfaces on behalf of corrupted initiator (user or issuer). For a user,
\mathcal{F}_{\textsf{ideal}}
firstly calls the authentication sub-routine which verifies user corruption level. If
user is not fully corrupted (
\mathrm{c}_{\mathsf{U}}<2
), adversary is not allowed to make those requests
to the
\mathcal{F}_{\textsf{ideal}}
. If the user is fully corrupted (
\mathrm{c}_{\mathsf{U}}\geq 2
),
\mathcal{F}_{\textsf{ideal}}
proceeds with the requested interface using input provided by the adversary. Finally,
\mathcal{F}_{\textsf{ideal}}
gives the user’s output to the adversary. This way, even though the adversary will see all the inputs and outputs of partially corrupted users, it cannot initiate any routines on their behalf.

Issue
is initiated by the user query containing information about the requested attribute(s). If nobody is corrupted, adversary just gets notification that the communication is happening, and is able to interrupt the communication. We are not hiding issuer’s identity and the issued
\overrightarrow{\mathsf{aID}}

\mathsf{ST}
). This is a functional requirement: to make querying by credential identifier
\mathsf{cID}
usable in practice, we need that it would be self-explanatory, and we also need these values for the transaction log. Actually, since in our model,
\mathsf{ST}
knows the issuer identifier, it will likely anyway be able to guess which kinds of attributes have been requested by the user.

The attribute request is sent to the issuer and, if not interrupted by the adversary, the issued credential consisting of attributes
\overrightarrow{\mathsf{atr}}
is recorded to the table
\textsf{T}_{a}
. Every record in table
\textsf{T}_{a}
serves as an issued credential. While credential identifier
\mathsf{cID}
is chosen by the adversary,
\mathcal{F}_{\textsf{ideal}}
checks that it is unique for an honest user and an honest storage. After attributes are received from the issuer,
corrupted storage learns only
\mathsf{cID}
, but not the values of attributes
.

Revoke
is initialised either by the user or issuer query containing identifier
\mathsf{cID}
of the credential to be revoked.
\mathcal{F}_{\textsf{ideal}}
verifies that a credential with
\mathsf{cID}
exists. The adversary learns
\mathsf{cID}
provided by an honest
P
if either (1) the user of
\mathsf{cID}
is corrupted and hence is able to trace revocation, or (2)
\mathsf{ST}
and some RP to which
\mathsf{cID}
has been presented before, are both corrupted (in that case, adversary already learned the link between the credential and corresponding revocation token). Otherwise,
\mathcal{F}_{\textsf{ideal}}
just notifies adversary that the revocation process has been initiated. If the revoking party is an issuer,
\mathcal{F}_{\textsf{ideal}}
also leaks to corrupted storage the identity of the user, owner of the revoked credential. In practice, this is needed purely for logging purposes, so that AMS could show to the user only those revocation logs which concern that user.

After receiving approval from the adversary,
\mathcal{F}_{\textsf{ideal}}
records that
\mathsf{cID}
has been revoked by user or issuer in table
\textsf{T}_{r}
and confirms successful revocation to the revoker.

Present
is initiated by the user query containing information about the credential
\mathsf{cID}
and attribute(s)
\overrightarrow{\mathsf{aID}}_{\textsf{dscl}}
that need to be presented. First of all,
\mathcal{F}_{\textsf{ideal}}
verifies whether the requested credential is in the table
\textsf{T}_{a}
.
\mathcal{F}_{\textsf{ideal}}
sends only the user identifier and the number of attributes to the adversary, even if AMS and the issuer are corrupted. If presentation is approved by the adversary,
\mathcal{F}_{\textsf{ideal}}
verifies that credential has not been revoked, by consulting table
\textsf{T}_{r}
. If the check passes,
\mathcal{F}_{\textsf{ideal}}
generates presentation for the requested credential using
\mathsf{Present}
function.
The obtained credential presentation is output to the user.

Verify
is initiated by the user and RP. If the AMS server (with or without the issuer of presented credential) is corrupted, adversary does not learn neither RP identifier nor credential identifier. It helps to capture the fact that
AMS server does not learn RP identifier or which credential is being presented by the user or which attributes are being disclosed during the presentation
.
\mathcal{F}_{\textsf{ideal}}
verifies that presented credential has not been revoked, and has been recorded by the issuer. Note that, as far as no revocations took place between a presentation and a revocation, both checks always verify for the presentations generated through the
\mathcal{F}_{\textsf{ideal}}

User authentication.

After the initialisation, each query to the AMS server by the user starts from authentication.
For this, user creates a threshold signature
\sigma_{\mathsf{req}}
, using
\mathcal{F}_{\textsf{tsign}}^{\mathsf{uID}}
.
Threshold signature generation using
\mathcal{F}_{\textsf{tsign}}^{\mathsf{uID}}
already includes user authentication to the server. Technically, going into details of the protocol implementing
\mathcal{F}_{\textsf{tsign}}
, the user proves ownership of their secret key share, as well as a special randomness, which serves as a challenge for the next authentication. Obtained signature serves as a consent from the user to perform certain actions with their data. The usage of threshold signatures instead of regular signatures is important to ensure user’s key protection. Since the user’s private key is stored on the mobile device, usage of threshold signatures adds level of protection to the private keys. Since the signature also servers as a consent to perform certain actions with the user’s credentials, this signature should be verifiable for audit purposes, hence the security of the corresponding private key is crucial.

The protocol is presented in Figure

id_{\mathsf{cID}}
for the credential. To avoid repetition attacks by a corrupted AMS, the issuer keeps all received signatures and tracks their repetitions.

AMS provides to the user a link that they can use to directly communicate with the issuer
\mathsf{IID}
(i.e. links
\mathsf{IID}
to a communication channel of

\mathsf{rev}_{U}
whose revoker will be the user. Then, the user and the issuer jointly generate a token
\mathsf{rev}_{I}

For each requested attribute
\mathsf{aID}_{i}

\mathsf{atr}_{i}

\mathsf{atr}_{i}
under the user’s public key of

and

and forwards it to the AMS server. AMS server verifies the issuer signature and forwards issued credential to the user for approval. User decrypts attributes from the credential, verifies that the attributes are not malformed (i.e. that the value
\mathsf{atr}_{i}
belongs to the set of valid attribute values
\mathcal{V}_{{\mathsf{aID}_{i}}}

, where

ensures uniqueness of
\mathsf{cID}
, and function

generates an intuitive short description of the credential. The user includes credential data into a small checksum digest that it maintains locally.

Get all

The protocol of Figure

\overrightarrow{\mathsf{cID}}
, as well as all the stored credentials
\overrightarrow{\mathsf{cred}}
. While user has already received all this data during the issuing phase, the server storage can be used as a backup. Verification of the received data against the previously stored checksum ensures integrity against corrupted AMS. While issuer’s signature already protects integrity of a credential, the checksum prevents AMS from being silent about the existence of some credential. At this step, the user only downloads
encrypted
credentials, and will need access to the decryption functionality to get their contents.

Since we want the server to serve as a backup, we need to be sure that user has all relevant data to further
use
the credentials. Besides raw credential data, the user also needs the following protocol-specific data:

•

The ciphertexts of
\mathcal{F}_{\textsf{tdecrypt}}^{\mathsf{uID}}
should be decryptable, and the signatures of
\mathcal{F}_{\textsf{tsign}}^{\mathsf{uID}}
generatable. We assume that the user has not lost their secret keys corresponding to these functionalities.

•

To keep integrity against the corrupted server, the user needs to keep the small checksum digest. As this digest is not sensitive (it it is computed from encrypted credentials), it can be copied to any other device.

•

The revocation protocol of
[
20
]
that realises functionality
\mathcal{F}_{\textsf{rev}}
assumes that the user knows a small secret
r
that corresponds to the token
x
, which is needed for both revocation and presentation. Technically,
r
can also be stored on the server in form of a ciphertext
c_{r}
, which can (but does not have to) be included into the credential. This additional overhead has been included into the benchmarks of Sec.
5
.

•

The user, acting as a revoker, should be able to prove that AMS has ignored their revocation. In the revocation protocol of
[
20
]
, the user should be able to present a confirmation signature of AMS. Such signatures cannot be stored by AMS. Here we assume that the number of such emergency-revoked credentials is not large for a single user, so they can afford to store them elsewhere.

Revocation

Revocation can be initiated either by the user (Figure
8
) who wants to revoke their credential, or by the issuer (Figure
9
). Issuer revocation is initiated by the issuer’s signed revocation request, which confirms that it is an authorised revocation. Both parties revoke
\mathsf{cID}
by revoking the corresponding revocation token (
\mathsf{rev}_{U}
or
\mathsf{rev}_{I}
) using
\mathcal{F}_{\textsf{rev}}
.

Revocation procedure may result in a double revocation of the same credential, by the user and by the issuer. During verification, as RP does the check for
\mathsf{rev}_{I}
and
\mathsf{rev}_{U}
separately, this could leak to RP the fact that some credential has been rejected twice. Moreover, if the token has been revoked once, RP could learn whether it has been revoked by the user or by the issuer. As far as the AMS is honest, since the user will call revocation notification just before the final verification, this leakage is only possible if the server collaborates with a corrupted RP.

Verification by relying party

The protocol is presented on Figure
12
. Before verification, RP receives updated state of the revocation functionality using notification interface of
\mathcal{F}_{\textsf{rev}}
. If it is done immediately before the presentation, we cannot guarantee the unlinkability of presentation to the RP by AMS server, so it should be run independently. RP generates fresh challenge and sends it to the user for signature. This step is required to guarantee freshness of the presentation. User generates signature using
\mathcal{F}_{\textsf{tsign}}
, and blindness property ensures that the AMS server does not learn anything about credential presentation, except the fact that the user has presented some credential to some party. We include
\mathsf{cred}
and
\sigma_{\mathsf{cred}}
to the message that gets signed, to achieve structure more similar to SD-JWT presentation protocol. RP receives credential presentation from the user and verifies the user and the issuer signatures. It uses verification interface of
\mathcal{F}_{\textsf{rev}}
to ensure that the credential is not revoked. Then it verifies whether the selectively disclosed attributes are indeed contained in the signed credential.

Using threshold signing for the challenge means that the supporting server should be online upon verification. If we want to make verification possible offline, we will need to use ordinary signature like
\mathcal{F}_{\textsf{sign}}
, which means weaker guarantees for the RP if the user device gets stolen together with the secret key, or cloned. If server-supported signature is used, then the actual user may contact the server to stop generating signatures in case of stealth, and clone detection protects against silent cloning of the user device.

Selective disclosure is achieved by decrypting only the values of selected
\overrightarrow{\mathsf{aID}}_{\textsf{dscl}}
. For each such
\mathsf{aID}
, user calls verification interface of
\mathcal{F}_{\textsf{tdecrypt}}
to prove to RP that the presented plaintext value indeed corresponds to the ciphertext from the signed credential
\mathsf{cred}
. Figure
11
presents comparison of the proposed solution with the selective disclosure for JWT specification with the trivial solution of protecting credentials in the storage. The main difference is that in the case of SD-JWT for the presentation, the user needs to decrypt all the attributes. Therefore, if the device memory leaks to the adversary at this point, all the attribute plaintext values will be disclosed. In our solution, only the attributes that are disclosed for the specific presentation are decrypted and can potentially leak.

Cheating detection.

Revocation functionality
\mathcal{F}_{\textsf{rev}}
allows AMS to conceal the fact of revocation from a party
P
(a user or a verifier). In this case,
P
and
R
together can detect cheating and prove it to the third party. However, some event needs to trigger such a cheating detection in practice. This depends on the impact that cheating may impose.

Cheating to a user.

If AMS silences some revocation from the user, it may result in a rejected legitimate verification. The user may consult the issuer to ask whether the issuer has revoked the credential. If it is indeed so, the user and the issuer together may prove the fact of cheating to a third party. If the credential has not been revoked, then the verifier has chosen not to accept the credential, but it is a legitimate decision of the verifier (in the scope of
\mathcal{F}_{\textsf{ideal}}
).

Cheating to a verifier.

If AMS silences some revocation from the verifier, it may result in an accepted illegitimate verification. The verifier and the issuer may resolve this problem, but the problem must be detected in first place. In practice, the verifier and the issuer could periodically run verification (with issuer acting as a presenter) on randomly selected tokens held by the issuers whom the verifier accepts, to detect cheating with some non-negligible probability.

Expiration.

Expired records need to be periodically removed (or archived). Let
\Delta
be an overestimated time after which any attribute will "definitely expire". For both the credential and the revocation tables, the server removes an entry as soon as the time
\Delta
passes after it has been added to the corresponding table.

4.3
Security of the proposed protocol

Theorem 4.3

Assuming a
covertly
corrupted AMS (Definition
1
), the protocol set
\pi_{\textsf{PRETTINESS}}
of Sec.
4
UC-realizes
\mathcal{F}_{\textsf{ideal}}
in
\mathcal{F}_{\textsf{sign}}^{\mathsf{IID}},\mathcal{F}_{\textsf{tsign}}^{\mathsf{uID}},\mathcal{F}_{\textsf{tdecrypt}}^{\mathsf{uID}},\mathcal{F}_{\textsf{rev}}
- hybrid model.

The full security proof is presented in supplementary material. In this section, we present the intuition behind the simulation, considering the most interesting corruptions.

For the proof, we define a simulator
\mathcal{S}
mediating communication between the real adversary
\mathcal{A}
and the ideal functionality
\mathcal{F}_{\textsf{ideal}}
, trying to generate messages for
\mathcal{A}
and
\mathcal{F}_{\textsf{ideal}}
in such a way that
\mathcal{Z}
gets convinced that it is communicating with the real protocol
\pi_{\textsf{PRETTINESS}}
. The simulator plays roles of honest parties in
\pi_{\textsf{PRETTINESS}}
, generating messages for corrupted parties, which are controlled by
\mathcal{A}
. In addition,
\mathcal{S}
interacts with
\mathcal{F}_{\textsf{ideal}}
to synchronise with its inputs and outputs. This shows that any attack of
\mathcal{A}
on
\pi_{\textsf{PRETTINESS}}
can be converted (by the simulator) to an analogous attack on
\mathcal{F}_{\textsf{ideal}}
. In particular, all leakages of
\pi_{\textsf{PRETTINESS}}
to the adversary are computable from the "intensional" leakage of
\mathcal{F}_{\textsf{ideal}}
and the data that
\mathcal{A}
has provided for corrupted parties. We describe how
\mathcal{S}
behaves in each routine of
\mathcal{F}_{\textsf{ideal}}
.

Initialisation:

\mathcal{S}
defines the function
\mathsf{Present}
for
\mathcal{F}_{\textsf{ideal}}
, used to generate credential presentation. This function takes the attribute values
\overrightarrow{\mathsf{atr}}
that correspond to
\mathsf{cID}
and
\overrightarrow{\mathsf{aID}}
from the table
\mathsf{T}_{a}
of issued attributes, as is done in the real protocol.
\mathcal{S}
defines
\mathsf{Ver}
that is used to verify credential presentation by checking that
\overrightarrow{\mathsf{atr}}
have indeed been stored in
\mathsf{T}_{a}
for given
\mathsf{cID}
and
\overrightarrow{\mathsf{aID}}
.
\mathcal{S}
also initializes all functionalities
\mathcal{F}_{\textsf{tsign}}^{\mathsf{uID}}
,
\mathcal{F}_{\textsf{tdecrypt}}^{\mathsf{uID}}
(a separate instance for each user of the system),
\mathcal{F}_{\textsf{rev}}
(one instance for the entire system) and
\mathcal{F}_{\textsf{sign}}^{\mathsf{IID}}
(a separate instance for each issuer in the system).

Issuing:

\mathcal{S}
ensures that the credential contents are only added to
\mathsf{T}_{a}
if it has indeed been requested by the (honest) user and issued by the (honest) issuer. On behalf of an honest issuer, the simulator treats credential request from a malicious user as successful only if it could indeed come up with some valid attribute values
\overrightarrow{\mathsf{atr}}
for that user, and if generation of revocation token for that user has succeeded, so a credential will only be sent to the user if the issuer has possibility to revoke it later. On behalf of an honest user, before accepting credential from a malicious issuer, simulator verifies that (1) it contains attribute from the valid set of the attributes, (2) that issued credential contains revocation token
\mathsf{rev}
generated by the
\mathcal{S}
and (3) that credential contains valid signature. This ensures that successful issuing will be followed by successful presentation and revocation. Finally, all credential data except the party identities and the attribute identifiers
\overrightarrow{\mathsf{aID}}
(which are explicitly leaked by
\mathcal{F}_{\textsf{ideal}}
) is encrypted, and can be simulated to a corrupted AMS.

Whenever
\mathcal{F}_{\textsf{ideal}}
adds a credential record
\mathsf{cID}
to
\mathsf{T}_{a}
, the simulator adds a corresponding entry (with additional protocol-specific data, like signatures and revocation tokens) to its local table
\mathsf{T}_{\textsf{issue}}
.

Get all CID-s:
On behalf of honest AMS,
\mathcal{S}
simulates to a corrupted user all the
\mathsf{cID}
-s and credentials that have been issued to the corrupted user so far. All such credentials have already been simulated to
\mathcal{A}
in the issuing phase, and recorded to
\mathsf{T}_{\textsf{issue}}
. On behalf of honest user,
\mathcal{S}
verifies the data provided by corrupted AMS against the digest representing the data that the AMS should have shown, which ensures consistency with the output of
\mathcal{F}_{\textsf{ideal}}
.

Revocation:
On behalf of honest AMS,
\mathcal{S}
collaborates with the corrupted revoker, letting
\mathcal{A}
choose the token to revoke. It is not possible to illegitimately revoke a credential
\mathsf{cID}
of an honest user without having rights on its revocation, which have previously been given by
\mathcal{F}_{\textsf{rev}}
only to the user and the issuer of
\mathsf{cID}
. On behalf of an honest revoker, unless the user of the revoked credential or the RP is corrupted (in these cases,
\mathcal{S}
gets
\mathsf{cID}
from
\mathcal{F}_{\textsf{ideal}}
and can use the same token
\mathsf{rev}
that was issued for
\mathsf{cID}
),
\mathcal{S}
takes a random revocation token
\mathsf{rev}\leftarrow\mathcal{X}
(which will not coincide with any other token with probability
1/|\mathcal{X}|
), and simulates calls of
\mathcal{F}_{\textsf{rev}}
with that token. Adversary will not notice the difference until the details of revocation gets leaked, which happens either upon reaching user corruption level
c_{\mathsf{U}}=2
, or during presentation to a corrupted RP. In both cases,
\mathcal{F}_{\textsf{ideal}}
will provide all relevant revocation data to
\mathcal{S}
, so that it can add all relevant tokens
\mathsf{rev}
to
X^{-}
of
\mathcal{F}_{\textsf{rev}}
.

Whenever
\mathcal{F}_{\textsf{ideal}}
adds a credential record
\mathsf{cID}
to
\mathsf{T}_{r}
, the simulator has added a corresponding revocation token
\mathsf{rev}
to its local set
X^{-}
of revoked tokens, unless
\mathsf{cID}
has not been leaked to
\mathcal{S}
yet. In the latter case, the user of
\mathsf{cID}
is an honest party, and it will anyway not call verification of
\mathcal{F}_{\textsf{rev}}
with a revoked token.

Presentation:
On behalf of honest AMS,
\mathcal{S}
collaborates with the corrupted user, letting
\mathcal{A}
choose the ciphertexts of their choice for decryption. On behalf of honest user,
\mathcal{S}
simulates presentation for a randomly chosen credential
\mathsf{cID}^{\prime}
from
\mathsf{T}_{\textsf{issue}}
, which is consistent with
\mathsf{T}_{a}
of
\mathcal{F}_{\textsf{ideal}}
. If there is no such
\mathsf{cID}^{\prime}
, presentation trivially fails, as there have been no credentials issued to that user. At this point,
\mathcal{A}
only learns
|\overrightarrow{\mathsf{aID}}_{\textsf{dscl}}|
, i.e. the number of threshold decryptions.
\mathcal{F}_{\textsf{tdecrypt}}^{\mathsf{uID}}
does not leak which ciphertexts exactly have been decrypted. The simulator does not learn whether presentation of an honest user has eventually succeeded, but this fact does not need to be simulated to
\mathcal{A}
.

Verification:
If the user is honest and RP is corrupted,
\mathcal{S}
gets disclosed presentation data from
\mathcal{F}_{\textsf{ideal}}
, which is enough to construct all messages for RP, using additional data from
\mathsf{T}_{\textsf{issue}}
. Obtained
\mathsf{cID}
may be different from
\mathsf{cID}^{\prime}
previously chosen for the presentation phase, but the simulation has not depended on
\mathsf{cID}^{\prime}
anyway.

If the user is corrupted with level
c_{\mathsf{U}}\geq 2
(with
c_{\mathsf{U}}=1
, corruptions are passive), it may show a revoked or invalid credential to an honest RP.
\mathcal{S}
detects it using its internal tables for revocation, signing and decryption for that user. If
c_{\mathsf{U}}=3
, all these tables are valid for that user from the beginning. Upon
c_{\mathsf{U}}=2
corruption,
\mathcal{F}_{\textsf{ideal}}
leaks internal records of that user to
\mathcal{S}
, allowing it to update its tables accordingly. Hence, these tables are filled with data consistent with the internal tables of
\mathcal{F}_{\textsf{ideal}}
.

If both RP and
\mathsf{ST}
are corrupted, then the adversary expects to learn the sessions on which the presented credential
\mathsf{cID}
has been revoked (if such a session exists). In this case,
\mathcal{F}_{\textsf{ideal}}
sends a corresponding index of the revocation table to
\mathcal{S}
, from which it can refer to the session id of that revocation.

5
Efficiency

We have estimated how well Prettiness would perform in practice. First of all, we collected benchmarks for implementations of certain protocols UC-realising
\mathcal{F}_{\textsf{rev}}
,
\mathcal{F}_{\textsf{tdecrypt}}
,
\mathcal{F}_{\textsf{tsign}}
, and
\mathcal{F}_{\textsf{sign}}
. We run the benchmarks on Intel(R) Core(TM) i5-10210U CPU @ 1.60GHz, 4 cores, 2 threads per core, and 15GB RAM.

5.1
Benchmarks for digest function.

We assume that the local database digest is computed using SHA256 hash function. We measured its computation times using
openssl speed sha256
, getting values below
7\cdot 10^{-9}
seconds per byte. While this small number is very small, the total time to compute the digest of the entire database grows with the number of user credenitals.

5.2
Benchmarks for
\mathcal{F}_{\textsf{sign}}
and
\mathcal{F}_{\textsf{tsign}}
.

We assume that
\mathcal{F}_{\textsf{sign}}
is realised with an ordinary 2048-bit RSA signature. We measured the signature generation and verification times using
openssl speed rsa
, getting values below
0.001
seconds. This small number has very little impact on the overall efficiency.

The efficiency of a protocol UC-realizing
\mathcal{F}_{\textsf{tsign}}
has been taken from
[
4
]
, where it is based on RSA signature. Since protocol presented in
[
27
]
just adds blinding to the protocol presented in
[
4
]
, the benchmarks will be similar. Signing operation itself takes tens of milliseconds, which we for safety round up to
0.1
seconds. According to
[
4
]
, the most time overhead comes from the network delay to transmit the signature share from the client to the server, which we do not include into the timing benchmark, instead giving a separate benchmark for communication. The signature itself is an ordinary RSA signature, verified in a usual manner.

The communication has been estimated instantiating
[
4
]
with 2048-bit RSA and 128-bit randomness. The communication consists of a message
\langle y,m,r,r^{\prime}\rangle
that the client sends to the server, and
\langle s,m\rangle
that the server sends back. Here
y
and

r,r^{\prime}\in\left\{0,1\right\}^{\eta}

2\cdot(2048+128+|m|_{b})=4352+2\cdot|m|_{b}

544+2\cdot|m|_{B}

Benchmarks for

Benchmarks of the building block protocols can be found in Table
5
and Table
6
. The times are measured for local computations only, without the network overhead, which is measured separately. Based on benchmarks of the building blocks, we estimated theoretical efficiency of the full system. In this estimate, we do
not
include the overhead of establishing communication channel (TLS) between parties, as well as the actual sizes of network packets moving inside TLS connection.

Since efficiency depends a lot on the actual number of credentials and their sizes, we considered a particular use case with
N=100
credentials per user, and
n=10
attributes per credential, and
m=1,000,000
total revocations. In practice, such an
m
can be an overestimate if there would be not too many urgent revocations of active credentials (for which expiration time has not passed).

The summary of results is given in Table
7
. As the user and verifier notification requires a large download of the revocation database, which can be done in advance, we treat is as a separate routine
DB update
in our estimate, which has more or less the same efficiency for the user and the verifier. More detailed benchmarks, explaining how exactly the times have been estimated based on the protocol descriptions, can be found in the supplementary material.

Let us discuss the bottlenecks of the full protocol efficiency.

Issuing.

The main overhead of issuing comes from letting the user decrypt the attributes to check their contents. Formally, we need this step to avoid selective failure attacks, where a further presentation of a malformed credential to RP surprisingly fails.

Get all Credentials.

The communication overhead is caused by downloading the full backup from the server. Although the user could download only
some
of the credentials, this would violate user privacy, giving to the server a hint of
which
credential is going to be presented. We find this communication feasible if the number of credentials that have not been expired yet is not too large, as in the benchmarked
N=100
case.

DB Update.

In this case, communication overhead comes from the necessity to download the data for
m
revoked tokens. Assuming that RP updates the status of the revocation database periodically (e.g. once per hour), and it is not urgent, then a download of 32MB of data per update would not be an issue. It is more complicated for the user who may be located in a place with bad network connection. We propose that, as our protocol anyway does not hide from AMS the identity of the user of a revoked credential (to make logging easier), the user only needs to download
m_{U}
of the
m
entries of the revocation database, where
m_{U}
is the number of revocations that concern the user
U
, which makes download size much smaller.

Authenticating the revoker party allows to protect against denial-of-service attacks, where a revoker maliciously attempts to add to the revocation database too many (potentially non-existent) credentials. AMS could limit the number of allowed revocations for same user/issuer. E.g. a user is not allowed to revoke more credentials that have been issued
to
it, and an issuer is not allowed to revoke more credentials that have been issued
by
it.

6
Conclusion

This work proposes attribute management system, where the user is in control over their credentials. Credentials are stored on the supporting server side. To ensure secure storage of cryptographic material on the user’s device, system relies on threshold cryptography (used for user’s signatures and attribute decryption functionalities). Credentials can be revoked by both user and the issuer. We construct an ideal functionality that captures security guarantees provided by the system and prove that proposed protocol set securely realises this functionality. Finally, we provide an efficiency estimate of our system. Future work includes post-quantum version of the proposed system as well as possible optimisations.

Appendix 0.C
UC proof for the full Prettiness system

To prove security of the proposed system, we define a simulator
\mathcal{S}
mediating communication between the
\mathcal{A}
and the ideal functionality
\mathcal{F}_{\textsf{ideal}}
, trying to convince
\mathcal{A}
that it is communicating with the real protocol
\pi_{\textsf{PRETTINESS}}
. Description of the simulator is split into different phases where each phase has separate sub-description for the different corruption models. The involved party that is not listed among the "malicious" parties is treated as honest, and is being simulated by
\mathcal{S}
. We only consider "interesting" corruptions, e.g. we do not describe simulation of a corrupted issuer alone if cheating is only possible in collaboration with a corrupted storage. We do not describe the case where all involved parties are corrupted, as there is nothing to be simulated in the real protocol, and their interactions with the sub-functionalities affect only corrupted parties. We also do not describe the case where all involved parties are honest, as the simulator would only need to simulate the notifications of different steps to
\mathcal{A}
, and simulations of these are already covered by the cases where that party is honest.

The protocol
\pi_{\textsf{PRETTINESS}}
is using functionality
\mathcal{F}_{\textsf{rev}}
which is parametrized by leakage functions
\mathcal{L}^{{\mathcal{C}}}_{{f}}
for a subroutine
f
and the set of corrupted parties
\mathcal{C}
. We write
L=\mathcal{L}^{{\mathcal{C}}}_{{f}}(x)
to denote leakage
L
that will be shown to the adversary, computed based on the internal state and the inputs
x
of simulated
\mathcal{F}_{\textsf{rev}}
. Throughout the proof, we write
\mathcal{F}(cmd,\mathsf{sid},x)
to denote running the subroutine
cmd
of
\mathcal{F}
with
\mathsf{sid}
and input
x
.

For the purpose of this paper, we allow adversary to corrupt user either before key generation, reaching level
c_{\mathsf{U}}=3
or after the key generation phase, reaching level
c_{\mathsf{U}}=1
(and subsequently
c_{\mathsf{U}}=2
). In the latter case, we prove that RP is protected from malicious user. Adversary can increase its level of corruption while making silent requests to the functionality. Processing of each silent request begins with the call to authentication sub-routine and if it results in successful authentication, corruption level can increase.

0.C.10
Corruption

In the real protocol, the adversary is corrupting
parties
. Whenever a party receives a special corruption message, it is considered corrupted in every subfunctionality (
\mathcal{F}_{\textsf{tdecrypt}}^{\mathsf{uID}}
,
\mathcal{F}_{\textsf{sign}}^{\mathsf{IID}}
,
\mathcal{F}_{\textsf{rev}}

\mathcal{F}_{\textsf{ideal}}
.On input
(\textsf{corrupt})
from
\mathcal{A}
to a party

\mathcal{F}_{\textsf{ideal}}

For the functionality

and
(\textsf{corrupt-user},\ell)
to
\mathcal{F}_{\textsf{tsign}}
. For all
\mathsf{uID}
, the simulator constantly observers the internal state of
\mathcal{F}_{\textsf{tsign}}^{\mathsf{uID}}

•

Whenever

is set in
\mathcal{F}_{\textsf{tsign}}
, send
(\textsf{corrupt-party},\mathsf{ST})
to
\mathcal{F}_{\textsf{ideal}}
.

•

If setup has not been performed, only

can be set in
\mathcal{F}_{\textsf{tsign}}
(full corruption). This implies that adversary has full control over the user’s device and there are no privacy guarantees for user any more. Send
(\textsf{corrupt-party},\mathsf{uID})
to
\mathcal{F}_{\textsf{ideal}}

0.C.11
Indistinguishability of the real and the simulated protocol.

Issuing

In the case of honest issuer, simulator indistinguishably simulates issuance of credential

\mathsf{cred}=\langle(\mathsf{aID}_{0},c_{0}),(\mathsf{aID}_{1},c_{1}),\dots,(\mathsf{aID}_{n},c_{n}),(\mathsf{aID}_{\mathsf{rev}},c_{\mathsf{rev}})\rangle

by including the public key
\mathsf{\vphantom{p}pk}_{\mathsf{uID}}
of the user
{\mathsf{uID}}
into
c_{0}
, taking attribute values
\mathsf{atr}_{i}
from the pre-defined set
\mathcal{M}_{\mathsf{aID}_{i}}
(that is the same as in the real protocol) for
i=1..n
, sampling revocation token from
\mathcal{X}
, assembling information together and creating signature. Indistinguishability of the signing and encryption processes is inherited from the underlying used constructions. Number of required attributes
n
and the attribute identifiers
\overrightarrow{\mathsf{aID}}
are received from the
\mathcal{F}_{\textsf{ideal}}
. The values
\mathsf{rev}
are allowed to repeat for a corrupted user.

In the case of malicious issuer, adversary itself generates credential for the user. Before saving issued credential to the internal tables, simulator verifies that credential contains correct revocation token
\mathsf{rev}\in\mathcal{X}
and correct attribute values
\mathsf{atr}_{i}\in\mathcal{M}_{\mathsf{aID}_{i}}
. Since
\mathsf{rev}
is freshly sampled, we have that
\mathsf{rev}\notin X^{-}
and
\mathsf{cID}
is unique with overwhelming probability.

In the case of malicious user, the issuer generates the credential for the user identity
\mathsf{uID}
that is eligible to receive the credential, even if the request is sent on behalf of a malicious party. If
\mathsf{uID}
is honest, the issuer will only generate a credential if
\mathsf{uID}
has indeed requested it, which is proven by the fresh signature of
\mathsf{uID}
. If AMS is corrupted, it is possible that the user
\mathsf{uID}
will not receive the credential, but the adversary does not learn the attribute values, since they are encrypted by the public key of
\mathsf{uID}
.

The simulator saves the credential that passes all checks to the internal table
\mathsf{T}_{\textsf{issue}}
. A credential with
\mathsf{cID}
containing
\mathsf{uID}
and
\mathsf{IID}
is only added to
\mathsf{T}_{\textsf{issue}}
if the following conditions are satisfied:

•

The credential has indeed been requested by the user
\mathsf{uID}
(if
\mathsf{uID}
is honest).

•

The credential has indeed been issued by the issuer
\mathsf{IID}
(if
\mathsf{IID}
is honest).

Here unfairness w.r.t. user is allowed, i.e. the user will not necessarily receive the credenital due to network delay.

Presentation

If the user is honest, presentation process is all simulated and adversary does not get to see credential presentation
\mathsf{pres}
. This allows simulator to simulate sub-protocols of the presentation phase with randomly selected credential. Usage of the blind threshold decryption ensures that the adversary does not learn which attribute is being decrypted. Thus, in this case simulated protocol is indistinguishable from the real protocol.

In the case of malicious user, adversary is able to initiate presentation process only if it has guessed
\mathsf{PIN}
from the underlying threshold signature scheme. If the
\mathsf{PIN}
check is successful, simulator simulates all the answers to the sub-protocol queries using its internal tables for the decryption and revocation using ciphertexts
c_{\mathsf{atr}_{i}}
and
c_{\mathsf{rev}}
supplied by adversary (note that adversary may decrypt
any
ciphertexts of
\mathsf{uID}
at this point, and this is why there are no privacy guarantees for the user when achieving
c_{\mathsf{U}}=2
). The adversary expects to see the correct notification from
\mathcal{F}_{\textsf{rev}}
. This is indeed so, as the simulated
X^{-}
in this case is consistent with the actually revoked tokens (either by the user or some issuer), both honest and corrupted. In the end of presentation, the output is produced by the simulator, and there is no effect on
\mathcal{F}_{\textsf{ideal}}
.

Verification

If the RP is malicious, it sees the presentation that is output of the ideal functionality, correctly constructed from the attributes requested by the user. We need to additionally ensure that the simulated revocation token is consistent with the previous revocations. During the previous protocol phases, whenever credential
\mathsf{cID}
of an honest user has been revoked, the following has happened:

•

In the cases when
\mathcal{F}_{\textsf{ideal}}
leaked
\mathsf{cID}
to the simulator, the corresponding
\mathsf{rev}
was added to
X^{-}

•

Otherwise, adding
\mathsf{rev}
to
X^{-}
was postponed (a random
\mathsf{rev}
has been revoked, which coincides with at least one real token with probability
\frac{n}{N}
for
n
issued credentials). During the verification, the simulator has added all relevant tokens
\mathsf{rev}
to
X^{-}
as soon as it received the corresponding information from
\mathcal{F}_{\textsf{ideal}}
, before simulating verification using
\mathcal{F}_{\textsf{rev}}
.

If user is malicious and RP is honest, the simulated challenge
\mathsf{ch}
is unique with probability
m/|\mathcal{CH}|
for
m
verification sessions. The simulator performs checks of credential presentation as an honest verifier. The simulated protocol accepts the credential only if

•

credential signature
\sigma_{\mathsf{cred}}
verifies,

•

revocation token is not among the revoked tokens:
\mathsf{rev}\notin X^{-}
,

•

disclosed attributes
\mathsf{atr}_{i}
correspond to ciphertexts from credential
\mathsf{cred}
.

•

the user could respond to the fresh challenge, proving ownership of
\mathsf{\vphantom{p}pk}_{\mathsf{uID}}

As malicious verifications are only allowed in the case
c_{\mathsf{U}}=2
and
c_{\mathsf{U}}=3
, it holds that either (1) the user has been fully corrupted from the beginning or (2) the attacker guessed PIN of the user. In the case (1), the simulator has all the data of this user included into internal tables, so all previous checks can be done against them. In the case (2), some data of this user stored in the simulator tables (up to the first corruption) is garbage. However, the true data is provided by
\mathcal{F}_{\textsf{ideal}}
upon corruption, and the simulator fills its local tables accordingly, ensuring consistency of simulated tables with the tables of
\mathcal{F}_{\textsf{ideal}}
.

Revocation by issuer

In case of malicious issuer, adversary knows the connection between the credential identifier and the revocation token and expects correct credential to be revoked. Simulator uses its internal table
\mathsf{T}_{\textsf{issue}}
to ensure that correct credential is marked as being revoked.

If AMS is corrupted, and
\mathsf{cID}
has already been presented to a corrupted RP, or it belongs to a corrupted user, then
\mathsf{rev}_{I}
should be leaked to the adversary by
\mathcal{F}_{\textsf{rev}}
. In both cases,
\mathsf{cID}
is leaked by
\mathcal{F}_{\textsf{ideal}}
, and the simulator takes the corresponding
\mathsf{rev}_{I}
from
\mathsf{T}_{\textsf{issue}}
.

If AMS is corrupted, but the credential has not been presented to a corrupted RP yet, and it belongs to an honest user, then the simulator does not receive
\mathsf{cID}
from
\mathcal{F}_{\textsf{ideal}}
. However, as
\mathcal{F}_{\textsf{rev}}
does not leak
\mathsf{rev}_{I}
neither, using random
\mathsf{rev}_{I}
is indistinguishable from using the actual revocation token
\mathsf{rev}_{I}
from
\mathsf{T}_{\textsf{issue}}
(unless
\mathsf{rev}_{I}
coincides by chance with some legitimate token, which is
\frac{n}{N}
for
n
issued credentials).

User revocation

If the user is corrupted, adversary is able to initiate revocation process only if it has guessed
\mathsf{PIN}
from the underlying threshold signature scheme. If the
\mathsf{PIN}
check is successful, then either the user has been corrupted from the beginning
(c_{\mathsf{U}}=3)
, or we have
c_{\mathsf{U}}=2
, and in both cases the simulator has filled its internal tables according to
\mathsf{T}_{a}
and
\mathsf{T}_{r}
of
\mathcal{F}_{\textsf{ideal}}
, so it has all necessary data for the simulation. The simulator simulates all the answers to the sub-protocol queries using its internal tables for the decryption and revocation.

If AMS is corrupted, and
\mathsf{cID}
has already been presented to a corrupted RP, then
\mathsf{rev}_{U}
should be leaked to the adversary by
\mathcal{F}_{\textsf{rev}}
. In this case,
\mathsf{cID}
is leaked by
\mathcal{F}_{\textsf{ideal}}
, and the simulator takes the corresponding
\mathsf{rev}_{U}
from
\mathsf{T}_{\textsf{issue}}
.

If AMS is corrupted, but the credential has not been presented to a corrupted RP yet, then the simulator does not receive
\mathsf{cID}
from
\mathcal{F}_{\textsf{ideal}}
. However, as
\mathcal{F}_{\textsf{rev}}
does not leak
\mathsf{rev}_{U}
neither, and decryption by means of
\mathcal{F}_{\textsf{tdecrypt}}^{\mathsf{uID}}
is blind, using a random
\mathsf{rev}_{U}
is indistinguishable from using the actual revocation token
\mathsf{rev}_{U}
from
\mathsf{T}_{\textsf{issue}}
(unless
\mathsf{rev}_{U}
coincides by chance with some legitimate token, which is
\frac{n}{N}
for
n
issued credentials).
