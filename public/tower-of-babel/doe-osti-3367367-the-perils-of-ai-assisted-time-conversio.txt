1.0 Executive Summary
This memo addresses a critical issue encountered when using AI assistants for time system
conversions, specifically converting data tagged with J2000 seconds through UNIX time to UTC.
Initial AI responses to this common conversion task were fundamentally incorrect, with
errors exceeding 37 seconds - enough to cause significant issues in many applications. This
document demonstrates the problem, quantifies the error, and provides best practices for using
AI tools safely in technical work. Both Claude 4.5 Sonnet [1, 2] and ChatGPT GPT-5.5 Thinking
[3, 4] gave the same answer 1.

2.0 Problem Statement

2.1 The Scenario
We have telemetry or scientific data tagged with J2000 timestamps. You need to convert this to
UNIX seconds (common in astronomy and spacecraft operations) and ultimately to UTC for
display or analysis.
This is a routine conversion performed in aerospace, astronomy, and scientific computing. It
seems straightforward - just subtract a constant offset, right? Wrong.

2.2 The Hidden Complexity
This conversion involves three different time standards:
 • Unix Time: Wall clock time ignoring leap seconds (discontinuous)
 • J2000/TT: Continuous physical time since January 1, 2000 12:00:00 TT
 • UTC: Wall clock time with leap seconds inserted
The interaction between these standards is non-trivial and requires domain knowledge that may
not be obvious from a simple query. See [5-11] for details of the time definitions.

3.0 Case Study: What Went Wrong

3.1 Initial Query to AI
"I want the formula to convert J2000 seconds to UNIX time to a UTC time."

3.2 AI's Initial Response (INCORRECT)
The AI provided this conversion:
     Unix_time = J2000_seconds + 946727935.816
 UTC_time = datetime.utcfromtimestamp(Unix_time)
This looks plausible. The constant is reasonable, the code is clean, and it runs without errors.

3.3 The Problem
This formula completely ignores leap seconds. Unix time doesn't count leap seconds (it
repeats or freezes during them), but TT/J2000 and UTC do. The AI gave a quick answer without
considering this crucial detail and the user had no idea.

4.0 Quantifying the Error

4.1 Error Magnitude
J2000 time 753192064 (November 14, 2023):
 Method Result
 Incorrect Formula                    UNIX = 1699919999.816 s
 Correct Formula (with leap seconds) UNIX = 1699919962.816 s
 Error 37 seconds

Why 37 Seconds?
  • 37 leap seconds have been added since the J2000 epoch
  • Unix time doesn't count these, but J2000/TT does
  • The naive conversion treats them as equivalent, creating a systematic error

4.2 Impact Examples
Where 37 seconds matters:
 Application Impact
 Spacecraft commanding Maneuver executed at wrong time; potential collision or mission
 failure
 Astronomical Missing transient events; incorrect target acquisition
 observations
 GPS/GNSS timing Position errors of ~144km (37s × 3,900 m/s satellite motion)
 Data correlation Events appear to occur at different times across systems
 Regulatory compliance Timestamps fail audit requirements for accuracy

5.0 Getting the Right Answer

5.1 Follow-Up Query with Context
“I want the formula to convert J2000 seconds to Unix time to a UTC time with sub-second
accuracy” – also gives wrong answer but makes mention of leap seconds being important.

Asking, "What about leap seconds? This will not be correct as Unix time does not take them into
account." – gives the correct answer.

5.2 AI's Corrected Response
The AI then provided the proper conversion accounting for:
 • TT-TAI offset (32.184 seconds, fixed)
 • TAI-UTC offset (leap seconds, time-varying)
 • Proper handling of the discontinuity
Key lesson: You must understand the tools you are using.

6.0 Why This Happened: Understanding AI Limitations

6.1 AI Behavior Patterns
AI assistants optimize for:
 • Quick, confident-sounding answers
 • Code that runs without errors
 • Responses that match common patterns in training data
 • Satisfying the literal query
AI assistants don't automatically:
 • Question unstated assumptions
 • Consider edge cases without prompting
 • Flag when a "simple" problem is actually complex
 • Validate their math against first principles
 • Know what you don't know

6.2 The Training Data Bias
Many online code examples for time conversion ignore leap seconds because:
 • They're demonstration code, not production-ready
 • The author didn't know about the issue
 • The application didn't require that precision
 • It's easier to write incorrect code
AI models learn from this corpus, inheriting these shortcuts.

7.0 Best Practices for Using AI in Technical Work
DO: Effective Prompting Strategies
 1. State Your Constraints Explicitly
 Not "Convert J2000 seconds to Unix time"
 Yes " Convert J2000 seconds to Unix time, accounting for leap seconds and
 ensuring sub-second accuracy for spacecraft applications"
 2. Mention Known Gotchas
 "I need to convert between time systems. I'm concerned about
 leap seconds, time scale differences (TT vs TAI vs UTC),
 and numerical precision."
 3. Request Validation
 "Provide the conversion formula and explain what happens
 during a leap second insertion."
 4. Ask for Caveats
 "What assumptions does this formula make? Under what conditions
 would it give incorrect results?"
 5. Demand References
 "Cite the standard or authoritative reference for this conversion."
DO: Verification Steps
Before trusting AI-generated code:
 1. Sanity check outputs against known examples
 2. Test edge cases (leap second dates, epoch boundaries)
 3. Compare with established libraries (astropy, SPICE, SOFA, spacepy)

 4. Verify against standards (IAU SOFA, IERS conventions)
 5. Check units and dimensions throughout the calculation
DON'T: Anti-Patterns
 Copying AI code directly into production systems
 Assuming "it compiles" means "it's correct"
 Trusting confident tone over technical accuracy
 Skipping peer review because "AI generated it"
 Using AI as a replacement for domain expertise – this is really common.

8.0 The Role of Peer Review

8.1 Why Peer Review is Critical
The AI couldn't self-correct, but a domain expert spotted the issue. This costed delay, expense,
and institutional credibility.

8.2 Implementing Effective Review
For AI-assisted code:
 1. Flag AI-generated sections in pull requests
 2. Require domain expert review for critical calculations
 3. Demand test cases covering known edge cases
 4. Check against authoritative references, not just "it runs"
 5. Document assumptions explicitly in comments

8.3 Cultural Considerations
Create a team culture where:
 It's expected and normal to challenge AI outputs
 Asking "did you verify this?" is standard practice
 Using AI tools is disclosed, not hidden
 Manual verification is valued, not seen as "wasting time"

9.0 Key Takeaways
Core Messages
 1. AI is a tool, not a truth oracle - It can be wrong, especially confidently wrong
 2. Domain knowledge is irreplaceable - You must know enough to spot errors
 3. Context is everything - Better prompts get better answers
 4. Verification is mandatory - Test, compare, validate
 5. Peer review is essential - Two sets of eyes catch what one misses

10.0 Conclusion
This incident demonstrates both the power and peril of AI assistants in technical work. The AI
had the knowledge to solve the problem correctly - but only when prompted with the right
context.
More fundamentally, this reinforces that AI augments human expertise but cannot replace it.
You need to know enough to:
 • Ask better questions
