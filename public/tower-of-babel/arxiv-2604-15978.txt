jMT : Testing Correctness of Java Memory Models
Lukas Panneke (✉), Heike Wehrheim

Abstract
According to common belief, the Java memory model is broken. In the past, several approaches have proposed repairs, often only to find new programs exhibiting unexpected, unintuitive behavior or the model forbidding standard compiler optimizations. The complexity of defining a memory model for concurrent Java lies in the fact that it requires a multi-execution model . Multi-execution models need to inspect many potential executions of a program in order to find the valid ones. Tools automatically validating novel proposals of Java memory models are, however, largely lacking. To alleviate this problem, we introduce jMT , a novel tool for constructing multi-execution semantics for concurrent Java programs. jMT relies on single-execution models defining well-formed execution graphs, based on which it builds valid multi-execution semantics via causality checking. Thereby, jMT supports evaluating new proposals of Java memory models (JMMs) on a per-program basis. jMT can furthermore be employed for testing the conformance of JMMs to existing compilation schemes and compilers. Our evaluation of jMT on 169 litmus tests reveals a number of interesting insights into existing JMMs.

Introduction

In the past,
there have been numerous efforts for correctly defining the Java Memory Model (JMM)
[
23
,
4
,
17
]
,
i.e., defining the semantics of concurrent Java programs on multiprocessor machines.
The official 1996 specification
[
8
]

has been shown to be flawed by Pugh
[
29
]
.
The next 2004 proposal of a JMM (Manson et al.
[
23
]
,
in the sequel called
\text{{JLS}}_{04}
)
has also been criticized
for being incompatible with some desired compiler optimizations
[
5
,
31
]
.
Moreover, it is outdated as far as modern synchronization primitives are concerned,
in particular the features of the
VarHandle
API.
The
VarHandle
API adds
new access modes for variables (opaque and release/acquire),
read-modify-write operations,
memory fences
and the mixing of volatile and non-volatile accesses to the same location.
The intended semantics of this API has been extensively described
by its designer Doug Lea
[
16
]
.
The most recent JMM proposal
of Bender, Liu and Palsberg
[
4
,
17
]

(in the following
\text{{JAM}}_{21}
)
incorporates most of these new features,
the proposed model – however –
also forbids certain expected, observable behavior,
and allows undesirable behavior,
as we show below.

The core reason for this difficulty in defining a correct JMM
lies in the fact that Java
requires a
multi-execution model
:
the validity of executions
(i.e., whether some particular execution and its outcome should be allowed or not)
cannot be determined by looking at one execution in isolation.
Instead, given a set of candidate executions,
a subset of valid executions is to be constructed.
Java memory models therefore often consist of two parts:
a single-execution model (SEM)
defining a set of candidates
and on top of that a multi-execution model (MEM)
used for validating the executions in the candidate set.
As Batty et al.
[
3
]

have discussed within the context of C++,
single-execution models alone can never suffice
without restricting compiler optimizations.
Basically, the reason for this is the so called “thin-air-problem”
in which values (of shared locations) circularly depend on their own computation.

Given the past experiences in constructing new JMMs,
every new proposal first has to undergo several healthiness checks:
(1) evaluating the novel semantics on numerous
litmus tests

(small programs with interesting behavior),
(2) checking agreement with standard compilation schemes and hardware memory models, and
(3) validating the conformance of compilers with the semantics.
Currently, in particular check (2) is ultimately carried out via formal proving
[
27
,
18
,
15
]
.
Proofs are, however, too labour-intensive
to be performed on every change of the model.
A tool allowing to first of all
test
such properties
would enable fast iteration of model changes
so that expensive proving can be deferred to later stages of the model development,
once testing finds no further inconsistencies.

Currently, the most prominent tool supporting the development of new memory models is
herd
:

herd
allows for the definition of single-execution models,
independent of any specific programming language or hardware.

herd
does, however, not support multi-execution models.
A second potentially usable tool is
JavaSim

[
21
]

which is however known to contain bugs.

In this paper,
we therefore introduce the novel tool
jMT
for multi-execution models.

jMT
allows for
testing
the above-mentioned healthiness checks
for novel Java memory models.
To this end,
a user of the tool has to develop a new single-execution model for Java
and specify it in the
.cat
language of
herd
.

jMT
then automatically calculates the semantics of concurrent programs,
thereby employing
jMT
’s multi-execution model which builds on
\text{{JLS}}_{04}
’s MEM (as this still remains the official JMM).
We provide an operational formulation of the
\text{{JLS}}_{04}
-style causality semantics,
turning its declarative definition into an executable construction of justification sequences.
Contrary to
\text{{JLS}}_{04}
, our multi-execution model is based on the concept of
symbolic execution graphs
.
Such graphs allow us to efficiently represent infinitely many candidate executions within a single graph,
and to solve parts of the justification search using an SMT solver.
Symbolic execution graphs have also in parallel been developed in
[
30
]
,
however, are therein employed for different forms of justifications.

jMT
can be used in three different scenarios:

1
to generate the semantics of litmus tests and compare
the outcomes against expected outcomes,

2
to compile programs using standard compilations schemes to hardware
and contrast the outcomes of litmus tests on the new JMM
with outcomes of the compiled program, and

3
to compile programs using standard Java compilers and then once more compare outcomes.
To support these three application scenarios,
we provide – along with
jMT
– a collection of 169 litmus tests,
assembled from
[
28
,
20
,
33
,
31
,
15
,

,
16
,
9
,
19
,
14
,
4
,
32
,
13
,
22
]
.
We have furthermore implemented a tiny compiler to Intel’s x86 processor
to support scenario
2
.
This compiler does not perform any optimizations,
so that a new JMM can be checked with respect to a compilation scheme alone.
Finally, to support scenario
3

our tool includes a toolchain
in which programs can be compiled using standard Java compilers.
For this purpose we employ a Java concurrency stress testing tool (
jcstress

[
33
]
)
to enable finding mismatches in behaviors at runtime.

We have implemented and experimentally evaluated
jMT
.
Our evaluation shows that
jMT
is able to find surprising novel issues with existing JMMs
and that
jMT
is
– according to our testing and given the right SEM –
an accurate simulator for
\text{{JLS}}_{04}

Several tools have been proposed

Many other multi-execution models have tool support as well

Many more tools target single-execution models.

[

]

are prominent tools for evaluating litmus tests for

.

We are, to our knowledge,

detects weak memory bugs in optimizing production compilers

Limitations.

Our tool supports all features of the
VarHandle
API,
but lacks support for other aspects of the Java programming language
relevant to visibility and ordering:
monitors, external events (such as I/O), final fields, and
observations of thread lifetime (first and last event, start and termination detection).
We furthermore do not support
.cat

Contributions.

Beyond tool implementation,
this paper makes the following contributions:
(1) We introduce symbolic execution graphs.
(2)
We are (to our knowledge) the first to formalize the cross-execution event equivalence,
a key but underspecified part of
\text{{JLS}}_{04}
’s MEM.
(3) We show that
\text{{JAM}}_{21}
is flawed via counterexamples,
including mismatches between intended and actual behavior,
and a counterexample to its claimed compilation correctness to x86.
(4) We identify a contradiction in Lea’s VarHandle documentation
[
16
]
,
the de facto source for volatile semantics
in presence of access mode mixing on the same variable.

A

•

•

•

•

is a set (or conjunction) of constraints over symbolic expressions such that
({\mathtt{sxp}_{\mathsf{R}}}(e^{\prime})={\mathtt{sxp}_{\mathsf{W}}}(e))\in\Gamma

.

A concrete execution graph is a symbolic execution graph

Building execution graphs.

Similar to
herd
, we build execution graphs in multiple stages.
However, while
herd
attempts to build execution graphs with concrete values,
and fails to properly evaluate assertions
for graphs where no unique value can be found by forward substitution,
we use symbolic execution graphs to handle these cases,
as they are highly relevant to MEMs, specifically JMMs.

1. Control-flow semantics.

First, we construct graphs per thread by following
the thread’s program according to a sequential semantics.
Initially, the thread graph is empty, i.e.,
G_{0}=(\emptyset,\emptyset,\emptyset,\emptyset)
.
Given a graph
G=(E,{\color[rgb]{0.2,0.2,0.2}\mathsf{po}},{\color[rgb]{0,0.6,0}\mathsf{rf}},\Gamma)
representing the execution so far, we
extend it depending on the type of the next instruction of thread
\tau
.
All newly added events are appended
{\color[rgb]{0.2,0.2,0.2}\mathsf{po}}
-after the previous events. Relation
{\color[rgb]{0,0.6,0}\mathsf{rf}}
remains empty in this stage.

Assignment

For an assignment of the form
{a}\;{:=}\;exp
,
we extend
\Gamma
by the constraint
({a}=exp)
. No additional events are added.

Store

For a store
\textbf{{{STORE}}}^{\textsf{wm}}({x},sxp)
,
we add an event labeled
{{\mathsf{W}}}^{\mathsf{wm}}({{x}},{sxp})

with thread id
\tau

and a fresh identifier,
without adding constraints.

Load

For a load
{a}\;{:=}\;\textbf{{{LOAD}}}^{\textsf{rm}}({{x}})
,
we add an event labeled
{{\mathsf{R}}}^{\mathsf{rm}}({{x}},{{a}})
,
with thread id
\tau

and – as for all events – a fresh identifier,
without adding constraints.

RMW

For a compare-and-exchange instruction
{a}\;{:=}\;\textbf{{{CAX}}}^{\textsf{rm,wm}}({{x}},{sxp_{1}},{sxp_{2}})
,
we have to construct two possible extensions, one where the CAX succeeds and the other
where it fails. In the first case, we add an event labelled
{{\mathsf{RMW}}}^{\mathsf{rm},\mathsf{wm}}({{x}},{sxp_{1}},{sxp_{2}})

and a constraint of the form
(sxp_{1}=sxp_{2})
,
in the second case an event labelled
{{\mathsf{R}}}^{\mathsf{rm}}({{x}},{sxp_{1}})

and a constraint
(sxp_{1}\neq sxp_{2})
.

Fence

For a fence
\textbf{{{fence}}}^{\textsf{fm}}
, we add an event labelled
{{\mathsf{F}}^{\mathsf{fm}}}
and no constraints.

If-then-else

Like for RMW, we build two successor graphs, one with additional constraint
\mathit{cond}
(being the condition of the if) and one with
\neg\mathit{cond}
.

The procedure ends once no instructions remain.
Since the focus of weak memory models is on values read from and written to shared locations,
termination of the procedure requires the absence of loops whose behavior depends on memory accesses.
Consequently, our tool,
like most other weak-memory tools,
supports only loop-free programs.
At that point, we have all conceivable executions of a thread, i.e., for every thread
\tau
we have a set of graphs
\mathcal{G}_{\tau}
.
The program executions of the parallel composition of the threads then correspond
to the Cartesian product of the graphs of all threads.
More precisely, for each family of graphs
{\langle{G_{\tau}=(E_{\tau},{\color[rgb]{0.2,0.2,0.2}\mathsf{po}}_{\tau},\emptyset,\Gamma_{\tau})}\rangle}_{\tau\in\mathsf{TID}}
, one per thread, we
construct a new product graph
G=(\bigcup_{\tau\in\mathsf{TID}}E_{\tau},\bigcup_{\tau\in\mathsf{TID}}{\color[rgb]{0.2,0.2,0.2}\mathsf{po}}_{\tau},\emptyset,\bigcup_{\tau\in\mathsf{TID}}\Gamma_{\tau})
. To this graph,
we finally add initializing events
{\mathsf{W}}_{\mathsf{ini}}({x},0)
for every
{x}\in\mathsf{Loc}
.

Next, we build the multi-execution model out of the set of graphs

4. Generating Justifications.

Stage 4 in the construction of valid execution graphs out of programs is now
the actual generation of justification sequences.
Formally, a justification sequence is a sequence of
justification stages

which are pairs

s={\langle{G,\mathit{C}}\rangle}

where
G
is an execution graph
and
\mathit{C}\subseteq\mathsf{Events}
is a set of committed events.
A
justification
for a target execution graph
T
is a pair

J={\langle{T,(s_{1},\dots,s_{n})}\rangle}

where
(s_{1},\dots,s_{n})
is a justification sequence.

For a given target graph
T
,
a current justification stage
{\langle{G,\mathit{C}}\rangle}

and a collection of well-formed execution graphs
\mathcal{G}
,
we compute the successor justification stages with

\mathrm{GenSuccessors}(T,{\langle{G,\mathit{C}}\rangle},\mathcal{G})=

\bigcup_{G^{\prime}\in\mathcal{G}}\bigcup_{\emptyset\neq X\subseteq G^{\prime}.E\setminus\mathit{C}}\{{\langle{G^{\prime},\mathit{C}^{\prime}}\rangle}\mid\mathit{C}^{\prime}=(\mathit{C}\cap G^{\prime}.E)\cup X\land\mathsf{ok}(T,{\langle{G^{\prime},\mathit{C}^{\prime}}\rangle},\mathit{C})\}.

We always start a justification sequence with a
well-behaved
execution
G_{1}\in\mathcal{G}
.
We set
C_{0}
(which never gets constructed) to
\emptyset
.
For graph
G_{1}
,
the initial stage is

s_{1}={\langle{G_{1},G_{1}.E|_{\mathsf{ini}}}\rangle}
, the stage with just the initial writes committed.
We then generate the justification sequences by exploring all finite sequences
(s_{1},\dots,s_{n})

such that for all
1<i<n
,

s_{i+1}\in\mathrm{GenSuccessors}(T,s_{i},\mathcal{G})
.
A justification sequence
(s_{1},\dots,{\langle{G_{k},\mathit{C}_{k}}\rangle})

generated in this way is
valid
(and the target
T
is valid) iff

\lvert\mathit{C}_{k}\rvert=\lvert T.E\rvert
and

\mathsf{ok}(T,{\langle{T,T.E}\rangle},\mathit{C}_{k})
and condition 8 is fulfilled:

8.

if

(x,y)\in G.{\color[rgb]{0.5,0,0.5}\mathsf{sw}}\cap(G_{i}.{\color[rgb]{0,0,1}\mathsf{hb}}^{-}\setminus G_{i}.{\color[rgb]{0.2,0.2,0.2}\mathsf{po}})\land(y,z)\in G_{i}.{\color[rgb]{0,0,1}\mathsf{hb}}\land z\in\mathit{C}_{i}
,
then
(x,y)\in G_{j}.{\color[rgb]{0.5,0,0.5}\mathsf{sw}}
for all
j\geq i
.

Condition 8 enforces the following constraint:
once an action
z
is committed,
removing the release-acquire synchronization
that was necessary to justify why
z
is allowed to see what it sees is not possible anymore.

5. Validating Symbolic Justifications.

Next, we need to take condition 4 into account which
we carry out together with checking for specific behaviors.
Our check has to guarantee that (1) there is some instantiation of the
registers occurring in symbolic expressions with values such
that values of committed events do not change anymore over a justification sequence,
(2) the target
T
allows for the behavior assertion, and (3) the constraints of
T
,
T.\Gamma
, are satisfied.
The check proceeds by encoding these three properties into a large first-order logic formula and
asking an SMT solver for a model of the formula.
We encode each read and write of the graphs into a variable of the form

\mathit{graph\_name}{:}\mathit{thread}{:}\mathit{type}\,\mathit{location}@\mathit{index}
,
for example,
G_{2}{:}T_{3}{:}{\mathsf{R}}\mathtt{y}@2

is the variable representing the 2nd read of location
\mathtt{y}

performed by thread
T_{3}
in execution graph
G_{2}
.
We encode the entire justification sequence and target
T

in such a way that the SMT solver finds a satisfying assignment to these variables,
whenever an instantiation of symbolic register names in the justification sequence with the values of the corresponding variables yields a concrete justification
demonstrating that the behavior as specified in the assertion is possible.

The encoding works as follows. For a register
a
occurring as symbolic value in a graph
G
, we define a local variable

\mathrm{ELV}_{G}(a)\triangleq G{:}a
.
We denote by
\phi[\mathrm{ELV}_{G}]
the replacement of each register in formula
\phi

by
\mathrm{ELV}_{G}
.
We encode a non-initializing
8
8

8

Initializing writes write a constant
that is the same for all executions of a program,
so condition 4 cannot be violated.

write

to location
\mathtt{x}

in justification stage
s_{i}={\langle{G_{i},\mathit{C}_{i}}\rangle}

by thread
\tau

to location
\mathtt{x}

with write expression
\mathit{wexpr}

and
\mathrm{idx}(w,G_{i})=p

as

\mathrm{EncWr}(w,s_{i})\triangleq\begin{cases}G_{i}{:}\tau{:}{\mathsf{W}}\mathtt{x}@p=\mathit{wexpr}[\mathrm{ELV}_{G_{i}}]=T{:}\tau{:}{\mathsf{W}}\mathtt{x}@p&\text{if }w\in\mathit{C}_{i}\\
G_{i}{:}\tau{:}{\mathsf{W}}\mathtt{x}@p=\mathit{wexpr}[\mathrm{ELV}_{G_{i}}]&\text{otherwise.}\end{cases}

We encode a read
r\in G_{i}.\mathit{R}

in justification stage
s_{i}={\langle{G_{i},\mathit{C}_{i}}\rangle}

by thread
\tau

from location
\mathtt{x}

with read expression
\mathit{rexpr}

and
\mathrm{idx}(r)=p

as
\mathrm{EncRd}(r,s_{i})\triangleq G_{i}{:}\tau{:}{\mathsf{R}}\mathtt{x}@p=\mathit{rexpr}[\mathrm{ELV}_{G_{i}}]
.

We take the conjunction
of the encoding of all reads and non-initializing writes
in a justification stage,
and the graphs constraints
\Gamma

to encode the stage

\mathrm{EncStage}({\langle{G_{i},\mathit{C}_{i}}\rangle})\triangleq

We take the conjunction of this encoding for all justification stages of the justification

We also take the conjunction with the behavior assertion
\phi

\mathrm{ELV}_{T}
,
to ensure that the justification works for a concrete target execution

This encodes the entire justification

\mathrm{EncJust}({\langle{T,(s_{1},\dots,s_{n})}\rangle},\phi)\triangleq

\phi[\mathrm{ELV}_{T}]\land\mathrm{EncStage}({\langle{T,T.E}\rangle})\land\bigwedge_{1\leq i\leq n}\mathrm{EncStage}(s_{i}).

This formula might have a satisfying assignment
mapping each read and write expression to a value.
If so, substituting these values into the justification gives a concrete justification
satisfying all conditions, including condition 4,
showing that a concrete execution satisfying the assertion is acceptable.

5
Compilation Scheme Correctness

The second key objective of our work
is to validate that a candidate Java memory model
is compatible with a realistic compilation scheme
and associated hardware memory model.
Intuitively, soundness requires no compiled program to exhibit behavior forbidden by its source.
Formally, a compilation scheme
\mathit{Comp}

from a source Java memory model
\mathit{SEM}
(and its multi-execution version
\mathit{MEM(SEM)}
)
to a target hardware model
H
is sound if,
for every source program
P
,

\displaystyle\mathrm{Beh}_{H}(\mathit{Comp}(P))\subseteq\mathrm{Beh}_{\mathit{MEM(SEM)}}(P),

(1)

where
\mathrm{Beh}_{M}(P)

denotes the set of behaviors of
P
under model
M
.
Our notion of compilation correctness coincides with the intent of
[
18
]
:
“A correct compilation, intuitively, should not introduce any new program behavior,”
although their formalization is different from ours.

Proving
this inclusion is expensive and error-prone
(as seen in
Section

7
).
To support fast, iterative development of models,

jMT
offers an automated
testing-based
approximation.
It can expose unsoundness by finding a counterexample,
i.e., a behavior of
\mathit{Comp}(P)
not permitted by
\mathit{MEM(SEM)}
,
but cannot prove soundness.

jMT
takes as input a source
\mathit{SEM}
in
herd
’s
.cat
format
and a program
P
written in
herd
’s litmus test format for Java.

9

Although the behavior assertion is not of interest in scenario

we keep this format
because that way we can use the same input file for all use-cases of

The tool outputs either a

(no counterexamples)
or a

We currently target the x86 architecture due to its simplicity,
appearance in
[

Instead of using an existing compiler,

and source registers are systematically mapped to x86 registers.
We track which thread each register belongs to,

The soundness check of behavior inclusion as stated in (

) proceeds as follows:

1.

2.

3.

4.

5.

Verdict and witness

If any behavior

Otherwise, the test

8
Conclusion

In this paper, we have introduced
jMT
,
a tool for testing Java memory models
against expected semantics
and their compatibility with compilation schemes and compiler implementations.
For its multi-execution model support,

jMT
builds on the concept of
symbolic execution graphs

which allows for an efficient representation
of infinitely many potential candidates of execution graphs.
The experimental evaluation shows that
jMT
can be a valuable aid
in evaluating how JMMs match the mentioned desiderata.
In the future, we intend to extend
jMT
with support for additional features,
e.g., final fields
and compilation to RISC-V.
Additionally
– as an alternative to the sampling approach of
jcstress
–
we could also statically analyze the machine code generated by the JIT compiler.
Finally, we believe that
jMT
could play an important role
in supporting the development of an updated JMM
compatible with
\text{{JLS}}_{04}
and the full
VarHandle
API.

Thus, either

must be irreflexive, or in the property
w
and
w^{\prime}
must be different.
We decided to go with the second option, because
w
is called an “interleaving” write,
and it does not make sense to us for a write to interleave with itself.
