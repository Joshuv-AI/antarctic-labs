A Fast Locality Simulator for GEMM Design-Space Exploration on Multi-Chiplet GPUs
Euijun Chung, Hyesoon Kim

Abstract
Multi-chiplet GPUs split memory into local and remote HBM regions across a silicon interposer, and reducing the remote HBM traffic is crucial for the performance and energy efficiency of multi-chiplet GPUs. For general matrix multiplication (GEMM), the dominant operator in large language models (LLMs), the resulting inter-chiplet traffic depends strongly on kernel choices such as operand layout, CTA traversal order, and data placement, and the optimal strategy to minimize remote accesses is nontrivial. We present a fast, functional, tile-level locality simulator that models CTA scheduling, per-chiplet L2 caches, and local/remote HBM accesses to evaluate a full-size LLM GEMM configuration. Across representative LLM GEMMs, the simulator shows that remote traffic varies by up to 58 × \times across the design space for the same GEMM dimensions. Moreover, using the simulator as feedback, an agentic AI discovers that a 2D block-swizzle CTA traversal reduces remote traffic over the best 1D traversal by up to 5.1 × \times under round-robin placement, identifying CTA traversal order as a first-order, GEMM-dependent design knob for inter-chiplet traffic.

Finding the optimal configuration for these knobs is challenging on today’s hardware and software. High-performance GEMM kernels are proprietary and difficult to reproduce, and hardware profilers expose aggregate cache and memory counters but do not attribute traffic to local versus remote chiplet HBM at the granularity needed to compare placements and traversals. II
Locality Simulator

Fig. 2:
(a) Tiled matrix-multiply. (b) Co-locating each operand region with the CTAs that consume it lets the remaining HBM accesses be served locally.

We model one MI300X-like package as four locality domains (chiplets), each with 76 compute units and a private 8 MB, 16-way L2 (128 B lines). The simulator is
functional and trace-driven
: each CTA computes one output tile with configurable size and issues strided operand accesses determined by the GEMM shape and traversal order; accesses filter through the per-chiplet L2, and every L2 miss and output write is classified as local or remote based on the data-placement policy. Each CTA computes a output tile with A/B operand tiles held in shared memory, so per-CU occupancy is set by the shared-memory budget.
CTAs within a wave advance through the K dimension in lockstep, issuing their strided A/B reads through the chiplet’s L2 at each K-step before any CTA proceeds.

The tunable knobs are (i) per-operand row/column layout; (ii) CTA traversal order in the kernel implementation, either 1D row- or column-major or a 2D block-swizzle; and (iii) data placement for the input and output matrices, either address round-robin at 4 KB/64 KB/2 MB granularity or contiguous per-chiplet. CTA scheduling then follows naturally from the placement of the output matrix. The outputs are L2 hit rate, HBM locality
=
local
/
(local
+
remote), and absolute inter-chiplet (remote) traffic. The simulator models
data movement
, a first-order proxy for the latency and energy of remote access, rather than absolute timing. We do not model the memory-side last-level cache (e.g., AMD Infinity Cache), since it resides beyond the interposer crossing and therefore does not affect the local/remote classification of traffic, only the fraction that ultimately reaches DRAM.

More broadly, because the simulator exposes both hardware and software knobs in one fast model, it makes joint hardware/software optimization easier to explore.

IV
Impact and Limitations

The simulator is a fast, AI-analyzable methodology for chiplet-GPU locality that isolates software knobs from the hardware model, enabling rapid and AI-driven design-space exploration. Its main limitation is that it is
functional
: it reports data movement, not absolute performance or power, and it assumes wave-synchronous (lockstep) CTA progress, which can slightly perturb the modeled L2 hit rate. Because the data footprint of one wave is smaller than the L2, we expect this effect on locality to be small. In short, the simulator turns chiplet-GPU GEMM locality into a fast, transparent design space that engineers and AI agents alike can explore in seconds.
