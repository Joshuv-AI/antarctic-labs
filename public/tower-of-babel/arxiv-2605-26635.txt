Pacing Types for Asynchronous Stream Equations
Florian Kohn, Arthur Correnson, Jan Baumeister, Bernd Finkbeiner

Abstract
Stream-based monitoring is a runtime verification approach where a monitor aggregates streams of input data from sensors and other sources to give real-time statistics and assessments of a system’s health. One of the central challenges in designing reliable stream-based monitors is to deal with the asynchronous nature of data streams: in concrete applications, the different sensors being monitored produce values at different speeds, and it is the monitor’s responsibility to correctly react to the asynchronous arrival of different streams of values. To ease this process, modern frameworks for stream-based monitoring such as RTLola enable users to finely specify data synchronization policies via a system of pacing annotations . While this feature simplifies the design of monitors, it can also lead users to write inconsistent policies, where synchronization between two streams is explicitly requested via annotations, but cannot always be achieved. To mitigate this issue, this paper presents pacing types , a novel type system implemented in RTLola to ensure that monitors for asynchronous streams are free of timing inconsistencies. We give a formal semantics to pacing annotations for a core fragment of RTLola , and present a soundness proof of the pacing type system. For an additional level of guarantees, we machine-checked the soundness proof using the Rocq proof assistant.

Introduction

Runtime verification is a safety assurance mechanism in which systems are monitored during their execution.
Runtime verification is particularly useful for increasing the reliability of complex cyber-physical systems (CPS) for which obtaining a model for static verification is difficult or impossible.
Stream-based monitoring is an approach to runtime verification in which a monitor
collects data through input streams, which are then combined and aggregated in output streams to give real-time assessments of a system’s health.

While, there exist many formalisms and programming languages to describe stream-based monitors
[

, we focus on the stream-based specification language
RTLola
.
In
RTLola
, a monitor is specified by listing equations relating input and output streams.
Certain boolean output streams, called triggers, indicate whether the system being monitored is behaving as expected.

From a system perspective, monitors are passive components.
They react to inputs from the system as they arrive.
If different system sensors generate inputs at varying rates, the monitor must handle the asynchronous arrival of data.
To simplify this process,
RTLola
features a system of
pacing annotations
where
each output stream is labeled with additional information indicating when a stream must
produce a fresh value in reaction to the asynchronous arrival of new input values.
While the pacing annotation system of
RTLola
has proven to be
useful in practical applications
[
12
,
5
,
3

, it also introduces a critical challenge: ensuring the
consistency
of pacing annotations.
Indeed, it is easy to write annotations that are incompatible with one another
or that over-constrain a stream by requiring it to produce values at times when its dependencies are not guaranteed to be available.
Ensuring consistency of pacing annotations is all the more difficult because the semantics of
RTLola
’s pacing annotations have, thus far, never been rigorously formalized.
In this paper, we address this issue in two ways.
We propose the first formal semantics of
RTLola
’s pacing annotations, and
we present a type system to check the consistency of pacing annotations.

2.2
A Type-driven Solution

To prevent timing inconsistencies,
RTLola
uses a type system.
First, we observe that the asynchronous
hold
stream access never causes timing inconsistencies, as it inherently provides a default value when the accessed value is absent.
Consequently, the type system focuses on synchronous stream accesses, such as direct or
prev
accesses.
More precisely, the type system ensures that a synchronously accessed value is always available when needed at runtime.
To enforce this property, it requires that a stream accessed synchronously evaluates at least at the same time points as the stream containing the access.

Pacing Types

To formalize pacing annotations and their properties,
we focus on a core language modeling the key features of
RTLola
, here dubbed
\mu
RTLola
(for micro
RTLola

In essence,
\mu

and
\mathbb{V}_{\mathit{out}}

For a fixed set of (named) input streams, these

Because of this declarative view, we refer to
\mu
RTLola

.
For clarity, we only formalize constraints over integer-valued streams, but
\mu
RTLola
can be extended to arbitrary data types in a straightforward manner

1

1

In fact, in our Rocq formalization,
\mu
RTLola
is parameterized by an arbitrary type of values equipped with arbitrary (total) operators.

3.2
Semantics of
\mu
RTLola

We equip
\mu
RTLola
with a denotational semantics assigning to lists of equations
S
a relation
\llbracket S\rrbracket
between input and output streams. Importantly, to account for the asynchronous arrival of inputs (and the asynchronous production of outputs), streams are defined as sequences of
optional
values: at each point in time, a stream can either have a value
v\in\mathbb{Z}
, or be undefined denoted by
\bot

\mathit{Stream}\triangleq(\mathbb{Z}\uplus\{\bot\})^{\mathbb{N}}

When working with streams of optional values, it is often useful to equate streams that are not exactly equal, but only equal at non-
\bot

w_{1},w_{2}\in\mathit{Stream}

w_{1}\preccurlyeq w_{2}
(read “
w_{1}

is less defined than

w_{1}\preccurlyeq w_{2}\iff\forall n.\ w_{1}(n)=\bot\vee w_{1}(n)=w_{2}(n)

Intuitively,
w_{1}\preccurlyeq w_{2}

guarantees that
w_{1}
and
w_{2}
are equal at positions where
w_{1}
is defined, but
w_{2}
is unconstrained at positions where
w_{1}
contains
\bot
.

\mu

associating each input and output variable to a stream.
We note
\mathit{InMap}
and

for input and output stream maps.

\mathit{InMap}\triangleq\mathit{Stream}^{\mathbb{V}_{\mathit{in}}}\qquad\mathit{OutMap}\triangleq\mathit{Stream}^{\mathbb{V}_{\mathit{out}}}

When proving the soundness of the type system, it will also be useful to consider

\mathit{ParMap}\triangleq(\mathit{Stream}\cup\{\ \bot\ \})^{\mathbb{V}_{\mathit{out}}}

Given a partial map

\mathit{dom}(\rho)\subseteq\mathbb{V}_{\mathit{out}}

(i.e. variables

\bot

x

.
Finally, given a partial map
\rho_{\mathit{par}}\in\mathit{ParMap}
and a total map

\rho_{\mathit{tot}}\in\mathit{OutMap}
, we define the

of
\rho_{\mathit{par}}
with respect to

as follows

\rho_{\mathit{par}}\cdot\rho_{\mathit{tot}}\triangleq\lambda x.\ \begin{cases}\begin{tabular}[]{ll}$\rho_{\mathit{par}}(x)$&if $x\in\mathit{dom}(\rho_{\mathit{par}})$\\
$\rho_{\mathit{tot}}(x)$&otherwise\end{tabular}\end{cases}

$\bot$&otherwise\end{tabular}\end{cases}

Given an input map
{\rho_{\textit{in}}}
, a pacing annotation
\tau
is
interpreted as a set of time points
\llbracket\tau\rrbracket_{\rho_{\textit{in}}}\subseteq\mathbb{N}
.
Concretely
\llbracket\tau\rrbracket_{\rho_{\textit{in}}}
represents all of the time points where the inputs described by the boolean formula
\tau
are defined in
{\rho_{\textit{in}}}
.

Definition 3
(Denotation of pacing annotations)

\displaystyle\llbracket x\rrbracket_{\rho_{\textit{in}}}

\displaystyle\triangleq\{\ n\mid{\rho_{\textit{in}}}(x)(n)\neq\bot\ \}

\displaystyle\llbracket{\color[rgb]{0.75,0.5,0.25}\textbf{{$\top$}}}\rrbracket^{n}_{\rho_{\textit{in}}}

\displaystyle\triangleq\mathbb{N}

\displaystyle\llbracket\tau_{1}\ {\color[rgb]{0.75,0.5,0.25}\textbf{{$\vee$}}}\ \tau_{2}\rrbracket_{\rho_{\textit{in}}}

\displaystyle\triangleq\llbracket\tau_{1}\rrbracket_{\rho_{\textit{in}}}\cup\llbracket\tau_{2}\rrbracket_{\rho_{\textit{in}}}

\displaystyle\llbracket\tau_{1}\ {\color[rgb]{0.75,0.5,0.25}\textbf{{$\wedge$}}}\ \tau_{2}\rrbracket_{\rho_{\textit{in}}}

\displaystyle\triangleq\llbracket\tau_{1}\rrbracket_{\rho_{\textit{in}}}\cap\llbracket\tau_{2}\rrbracket_{\rho_{\textit{in}}}

Pacing annotation
\tau
can also be understood as describing the set of streams which have defined values exactly at time points
\llbracket\tau\rrbracket_{\rho_{\textit{in}}}
.
We write
\llbracket\tau\rrbracket^{\omega}_{\rho_{\textit{in}}}\subseteq\mathit{Stream}
for the set of such “
\tau
-paced” streams.

Definition 4
(Well-paced streams)

\displaystyle\llbracket\tau\rrbracket^{\omega}_{\rho_{\textit{in}}}\triangleq\{\ w\mid\forall n.\ n\in\llbracket\tau\rrbracket_{\rho_{\textit{in}}}\iff w(n)\neq\bot\ \}

Having defined the semantics of expressions and pacing annotations, we can define the semantics of equations and specifications. An equation
x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e
denotes a binary relation between input and output maps.
A specification (i.e., a list of equations) is interpreted as the intersection of the solutions of its equations.

Definition 5
(Denotation of equations)

\displaystyle\llbracket x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e\rrbracket

\displaystyle\triangleq\{\ ({\rho_{\textit{in}}},{\rho_{\textit{out}}})\mid{\rho_{\textit{out}}}(x)\in\llbracket\tau\rrbracket^{\omega}_{\rho_{\textit{in}}}\wedge{\rho_{\textit{out}}}(x)\preccurlyeq\llbracket e\rrbracket_{({\rho_{\textit{in}}},{\rho_{\textit{out}}})}\ \}

\displaystyle\llbracket\mathit{eq}_{1}\cdot\ldots\cdot\mathit{eq}_{n}\rrbracket

\displaystyle\triangleq\llbracket\mathit{eq}_{1}\rrbracket\cap\ldots\cap\llbracket\mathit{eq}_{n}\rrbracket

A pair of stream maps
({\rho_{\textit{in}}},{\rho_{\textit{out}}})
satisfies a single equation
x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e

under two conditions. First, the stream
x

should be well-paced w.r.t.
\tau
(i.e.,
{\rho_{\textit{out}}}(x)\in\llbracket\tau\rrbracket^{\omega}_{\rho_{\textit{in}}}
).
Second,
x
should be equal to its definition
e
.
We note that the pacing annotation can force
x
to evaluate to
\bot
at certain time point, even though
e
would have had a defined value. Therefore, we only ask
x
to be less defined than
e
rather than strictly equal (i.e.,
{\rho_{\textit{out}}}(x)\preccurlyeq\llbracket e\rrbracket_{({\rho_{\textit{in}}},{\rho_{\textit{out}}})}
).

Equations might have no solutions, or only admit solutions for specific combination of inputs.
As discussed in the overview, this issue is worsened by the addition of pacing annotations.
Indeed, in the semantics of equations, the additional pacing constraint (
{\rho_{\textit{out}}}(x)\in\llbracket\tau\rrbracket^{\omega}_{\rho_{\textit{in}}}
) can turn solvable equations into unsolvable ones.
For example, assuming
a
and
b
are two input variables, the equations

\displaystyle x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ a\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ a

\displaystyle y\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ b\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ x

are unsolvable for
{\rho_{\textit{in}}}
’s where
a
and
b
are not perfectly synchronized,
but would always have a trivial solution if pacing annotations were ignored (just set
{\rho_{\textit{out}}}(y)={\rho_{\textit{out}}}(x)={\rho_{\textit{in}}}(a)
).
We wish to ensure that annotated equations have solutions for
all
possible inputs.
Equations that satisfy this property are called
consistent
.

Definition 6
(Consistency)

A specification
S
is called
consistent
if, for any input map
{\rho_{\textit{in}}}
, there exists at
least one compatible output map
{\rho_{\textit{out}}}
. Formally

\mathit{Consistent}(S)\triangleq\forall{\rho_{\textit{in}}}.\ \exists{\rho_{\textit{out}}}.\ ({\rho_{\textit{in}}},{\rho_{\textit{out}}})\in\llbracket S\rrbracket

3.3
Type System for Pacing Annotations

To determine whether a given specification is consistent, we use a type system.
Our type system uses typing judgements of the following two forms

\Gamma\vdash e:\tau\quad\textrm{and}\quad\Gamma\vdash S

\Gamma
is a

\tau

The first kind of judgement,
\Gamma\vdash e:\tau
, is used to check the pacing of stream expressions

.
Judgements
\Gamma\vdash S
are used to check the consistency of sets of equations.
In both judgements, the typing context
\Gamma
is a partial map from output variables
x\in\mathbb{V}_{\mathit{out}}
to annotations
\tau
, representing assumptions made on the pacing of some output streams.
In the following, we use the notation convention
\Gamma,x:\tau

to denote a context where

\tau
, and we note

when
\Gamma(x)=\tau\neq\bot
.

The typing rules for equations are processing the stream equations in a specification
S
in order of their appearance, extending the typing context after each processed equation.
The
Empty
rule states that an empty list of equations is consistent in any context.
The
Equation
rule processes the first equation of
x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e
of a list.
For such an equation to be well-typed, the
x
should be unbound in
\Gamma
(i.e.,
x\notin\mathit{dom}(\Gamma)
), making sure that there is at most one stream equation
per output variables in the specifications.
Further, we require the stream expression
e
to be well-typed in
\Gamma
for the annotated pacing (i.e.,
\Gamma\vdash e:\tau
).
Finally, the remaining equations should be well-typed in a context where
x
is assumed to be
\tau
-paced.

The more interesting typing rules arise from stream accesses.
Each kind of stream access comes associated with two typing rules depending on whether the accessed variable is an input or an output.
The rules for synchronous accesses (i.e.,
DirectOut
,
DirectIn
,
PrevOut
, and
PrevIn
) check that the time points at which the expression
must
be evaluated according to user annotations (
\tau_{\mathit{must}}
) are subsumed by the time points at which the accessed stream
can
be evaluated according to the current typing context (
\tau_{\mathit{can}}
).
This is made explicit by side conditions
\tau_{\mathit{must}}\models\tau_{\mathit{can}}
, formally defined as follows:

\tau_{\mathit{must}}\models\tau_{\mathit{can}}\triangleq\forall{\rho_{\textit{in}}}.\ \llbracket\tau_{\mathit{must}}\rrbracket_{\rho_{\textit{in}}}\subseteq\llbracket\tau_{\mathit{can}}\rrbracket_{\rho_{\textit{in}}}

In all rules,
\tau_{\mathit{must}}
corresponds to the pacing type that the target expression is expected to have.
If the accessed stream is an output stream,
\tau_{\mathit{can}}
is determined from the typing context.
For accesses to input streams,
\tau_{\mathit{can}}
is the stream name itself.
An important remark is that checking
\tau_{\mathit{must}}\models\tau_{\mathit{can}}
can be done using a SAT-solver.
Indeed, since pacing annotations are positive boolean formulas, it suffices to check the validity of the boolean implication
\tau_{\mathit{must}}\to\tau_{\mathit{can}}
.

Since
hold
and
prev
accesses can depend on the value of a default expression
e
, their associated typing rules require the default expression to be well-paced. For example, for
x{\color[rgb]{0.75,0.5,0.25}\textbf{{.prev}}}(e)
to be
\tau_{\mathit{must}}
paced,

e
should also be
\tau_{\mathit{must}}
paced.
We note that, contrary to synchronous accesses,
hold
accesses do not impose pacing restrictions on their accessed variables:
hold accesses
x{\color[rgb]{0.75,0.5,0.25}\textbf{{.hold}}}(e)
are
\tau
-paced for any
\tau
(provided the default expression
e
is also
\tau
-paced).
This coincides with the semantics of
hold
, which is guaranteed to produce a defined value by either returning the last defined value of the accessed stream, or a default value.

5
Soundness Proof

Having defined our type system, we still need to formally prove
its soundness.
Namely, if a specification is well-typed according to the rules presented in the previous section, is should be
consistent
.
We prove soundness by constructing an adequate
semantic model
of our typing judgements.

5.1
Semantic Model

To construct a semantic interpretation of typing judgements
\Gamma\vdash e:\tau
and
\Gamma\vdash S
, the first thing we need is to interpret the context
\Gamma
.
Given an input map
{\rho_{\textit{in}}}
, a typing context
\Gamma
can be understood as describing partial stream maps whose streams are paced as described by the bindings
(x:\tau)\in\Gamma
.
We denote this interpretation by
\llbracket\Gamma\rrbracket_{\rho_{\textit{in}}}\subseteq\mathit{Pmap}
.

Definition 7
(Interpretation of typing contexts)

\displaystyle\llbracket\Gamma\rrbracket_{{\rho_{\textit{in}}}}

\displaystyle\triangleq\{\ {\rho_{\textit{out}}}\mid\mathit{dom}(\Gamma)=\mathit{dom}({\rho_{\textit{out}}})\wedge\forall(x:\tau)\in\Gamma.\ {\rho_{\textit{out}}}(x)\in\llbracket\tau\rrbracket^{\omega}_{\rho_{\texttt{in}}}\ \}

Intuitively, if
\Gamma\vdash e:\tau
, then for any input map
{\rho_{\textit{in}}}
, and for any output map that is compatible with
\Gamma
,
e
should have a defined value at least at all time points that are described by
\tau
. This semantic interpretation of typing judgements for expressions is denoted by
\Gamma\vDash e:\tau
.

Definition 8
(Semantic typing of expressions)

\displaystyle\Gamma\vDash e:\tau\triangleq\forall{\rho_{\textit{in}}}.\forall{\rho_{\textit{out}}}\in\llbracket\Gamma\rrbracket_{{\rho_{\textit{in}}}}.\forall n\in\llbracket\tau\rrbracket_{\rho_{\textit{in}}}.\ \overline{\llbracket e\rrbracket}_{({\rho_{\textit{in}}},{\rho_{\textit{out}}})}(n)\neq\bot

We note that in this definition, output maps
{\rho_{\textit{out}}}
are only
partial maps
, so we cannot use the standard denotation of expressions
\llbracket e\rrbracket
to evaluate
e
in
{\rho_{\textit{out}}}
.
Instead, we use a slightly different
partial semantics

\overline{\llbracket e\rrbracket}
, returning
\bot
whenever
e
contains an access to an output variable
x\notin\mathit{dom}({\rho_{\textit{out}}})
.
We omit the full formal definition of
\overline{\llbracket e\rrbracket}
here, but we note that this partial semantics
agrees
with the reference semantics in the sense of the following lemma.

Lemma 1

For any
{\rho_{\textit{in}}}\in\mathit{InMap}
, any
\rho^{1}_{\mathit{out}}\in\mathit{Pmap}
, and any
\rho^{2}_{\mathit{out}}\in\mathit{OutMap}
,

\overline{\llbracket e\rrbracket}_{({\rho_{\textit{in}}},\rho^{1}_{\mathit{out}})}\preccurlyeq\llbracket e\rrbracket_{({\rho_{\textit{in}}},\rho^{1}_{\mathit{out}}\cdot\rho^{2}_{\mathit{out}})}

In other words, if
e
has defined values under the partial output map
\rho^{1}_{\mathit{out}}
, then it has the same defined values under any totalization
\rho^{1}_{\mathit{out}}\cdot\rho^{2}_{\mathit{out}}
.

As for expressions, we construct a semantic interpretation of typing judgements
\Gamma\vdash S
for equations.

Definition 9
(Semantic typing of equations)

\displaystyle\Gamma\vDash S\triangleq\forall{\rho_{\textit{in}}}.\forall\rho^{1}_{\mathit{out}}\in\llbracket\Gamma\rrbracket_{\rho_{\textit{in}}}.\exists\rho^{2}_{\mathit{out}}\in\mathit{OutMap}.\ \llbracket S\rrbracket_{({\rho_{\textit{in}}},\rho^{1}_{\mathit{out}}\cdot\rho^{2}_{\mathit{out}})}

Intuitively, for any partial output map
\rho^{1}_{\mathit{out}}
well-paced according to
\Gamma
, the equations in
S
are expected to have a well-paced solution
\rho^{2}_{\mathit{out}}
.
As a direct consequence of this definition, if a set of equations
S
is
semantically
well-paced in an empty context, then it is consistent (adequacy of the semantic model).

Theorem 5.1
(Adequacy)

\emptyset\vDash S\implies\mathit{Consistent}(S)

Proof

Suppose
\emptyset\vDash S
and let
{\rho_{\textit{in}}}\in\mathit{InMap}
.
Pick
\rho^{1}_{\mathit{out}}=(\lambda\_.\ \bot)\in\llbracket\emptyset\rrbracket_{\rho_{\textit{in}}}
, and by definition of
\emptyset\vDash S
there must exists a solution
\rho^{2}_{\mathit{out}}
to the equations
S
. ∎

5.2
Soundness of Typing Rules

Now that we have established the
adequacy
of our semantic model, we can prove that our typing rules are correct with respect to semantic typing.

Theorem 5.2
(Sound typing of expressions)

\Gamma\vdash e:\tau\implies\Gamma\vDash e:\tau

Proof

The proof proceeds by a straightforward induction on the derivation
\Gamma\vdash e:\tau
.
We refer the curious readers to our Rocq development for details.
∎

Theorem 5.3
(Sound typing of equations)

\Gamma\vdash S\implies\Gamma\vDash S

Proof

The proof proceeds by induction on the derivation
\Gamma\vdash S
.
The case
S=\epsilon
is straightforward.
Now suppose
S=x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e\cdot S^{\prime}
,
suppose
\Gamma\vdash e:\tau
, and by induction assume
\Gamma,x:\tau\vDash S^{\prime}
.
For a fixed
{\rho_{\textit{in}}}
and a fixed
\rho^{1}_{\mathit{out}}\in\llbracket\Gamma\rrbracket_{\rho_{\textit{in}}}
, we have to show the existence of a solution
\rho^{2}_{\mathit{out}}
to
x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e\cdot S
.
By Theorem
5.2
, since
\Gamma\vdash e:\tau
, this implies

\Gamma\vDash e:\tau
.
We can then construct a stream
w_{e}
as follows:

\displaystyle w_{e}(n)\triangleq\begin{cases}\begin{tabular}[]{ll}$\overline{\llbracket e\rrbracket}_{({\rho_{\textit{in}}},\rho^{1}_{\mathit{out}})}$&if $n\in\llbracket\tau\rrbracket_{\rho_{\textit{in}}}$\\
$\bot$&otherwise\end{tabular}\end{cases}

By definition of
\Gamma\vDash e:\tau
, we have

w_{e}\in\llbracket\tau\rrbracket_{\rho_{\textit{in}}}
.
Since
\rho^{1}_{\mathit{out}}\in\llbracket\Gamma\rrbracket
, we can deduce that
\rho^{1}_{\mathit{out}}[x\leftarrow w_{e}]\in\llbracket\Gamma,x:\tau\rrbracket
.
Applying
\Gamma,x:\tau\vDash S^{\prime}
to
\rho^{1}_{\mathit{out}}[x\leftarrow w_{e}]
, we obtain a solution
\rho^{\prime}_{\mathit{out}}
to
S^{\prime}
.
I.e.,
({\rho_{\textit{in}}},\rho^{1}_{\mathit{out}}[x\leftarrow w_{e}]\cdot\rho^{\prime}_{\mathit{out}})\in\llbracket S^{\prime}\rrbracket
.
By definition of
w_{e}
and Lemma
1
,

\rho^{1}_{\mathit{out}}[x\leftarrow w_{e}]\cdot\rho^{\prime}_{\mathit{out}}
is also a solution to the equation
x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e
.
Overall, we have
({\rho_{\textit{in}}},\rho^{1}[x\leftarrow w_{e}]\cdot\rho^{\prime}_{\mathit{out}})\in\llbracket x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ \tau\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ e\cdot S\rrbracket
, which concludes the proof.
∎

As an immediate consequence of Theorem
5.1
and Theorem
5.3
, we obtain the soundness of our type system for consistency.

Corollary 1
(Type Soundness)

\emptyset\vdash S\implies\mathit{Consistent}(S)

6
Sound Extensions of the Type System

While the type system presented in Figure
4
is
sound, it is also incomplete: it may reject equations that are consistent.
This section describes two simple extensions of the type system to mitigate incompleteness.

A first source of incompleteness originates from the order-sensitive nature of our type system.
As an example, the following two (consistent) equations do not type-check in this order, because
y
is defined after
x
and
x
uses
y
. However, they are well-typed if we swap
x
and
y
.

\displaystyle x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ i\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ y

\displaystyle y\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ i\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ i

Another source of incompleteness stems from the presence of self-references in stream equations.
Equations such as
x\ {\color[rgb]{0.75,0.5,0.25}\textbf{{@}}}\ {\color[rgb]{0.75,0.5,0.25}\textbf{{$\top$}}}\ {\color[rgb]{0.75,0.5,0.25}\textbf{{:=}}}\ x{\color[rgb]{0.75,0.5,0.25}\textbf{{.{prev}(}}}0{\color[rgb]{0.75,0.5,0.25}\textbf{{)}}}+1

\Gamma\vdash^{x}e:\tau

x\in\mathbb{V}_{\mathit{out}}
indicates the name of the stream containing

With this change, the rule for equations is updated to track self-references, and an additional rule

All other rules are kept unchanged, and simply ignore the extra annotation. This extension preserves soundness, but the formal proof is significantly more complicated.
In particular, the extra annotation
x

We note that beyond self
prev
-accesses, other types of self-references (like self
hold
-access, or equations of the form
x=x
) are considered to be anti-patterns even when they have models, and therefore do not need to be covered.

7
Conclusion

In this paper, we formalized the core of
RTLola
’s pacing annotations, a mechanism for data synchronization in stream-based monitoring.
We provided a formal semantics interpreting annotated stream equations as relations between input and output streams.
We showed that pacing annotations can introduce inconsistencies and addressed this by treating pacing annotations as types.
The resulting type system rejects contradictory annotations, and we proved its soundness with respect to the formal semantics.

While the presented fragment of
RTLola
is already practical, extending it to the whole language remains future work.
Another interesting research direction would be to relate the type system to an operational semantics, establishing not only the existence of models but also their computability.
