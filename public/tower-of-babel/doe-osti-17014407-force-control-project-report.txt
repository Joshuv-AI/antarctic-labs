 Introduction
 Purpose

The purpose of this project was to develop a custom force controller for the ABB IRB 140, giving PT-3
greater control over the robot's behavior. The existing ABB proprietary controller presented two key
limitations. First, its internal control structure operated largely as a black box, making tuning difficult.
Second, its performance was inconsistent across varying contact conditions, resulting in unpredictable
behavior.

By developing a custom controller, PT-3 gains the ability to directly modify the control logic, tune key
parameters, and better understand how the robot responds during contact.

 Hardware Limitations

When robotic manipulators interact with their environment, they often need to regulate not only their
motion but also the forces they exert. For this reason, robots with direct joint-torque control are generally
preferred as they allow for simpler and more intuitive force control schemes. However, these direct
methods can’t be used when working with position-controlled manipulators, like the ABB IRB 140.

 Admittance Control

Instead, the primary option is admittance control, often referred to interchangeably as position-based
impedance control. Rather than commanding joint torques directly, this method updates a trajectory based
on a virtual model of a mass-spring-damper. In some cases, like ours, the mass term is set to zero to
eliminate the inertia contributed by the virtual mass, resulting in a faster response.

While this scheme is effective and stable, it has a notable drawback. The virtual spring will reach a point

 Adaptive Admittance Control
 Methods

Adaptive admittance controllers are designed to improve force-tracking performance by modifying the
behavior of the admittance model during contact. In general, the approaches considered fall into two main
categories. The first category dynamically adjusts controller parameters, such as stiffness, damping, or
force-error gain. The second category estimates the environmental stiffness, ke, and uses it to shift the
effective spring equilibrium point. During development, one of each controller category was evaluated: a
PID admittance control and an adaptive reference admittance control.

On the other hand, the adaptive reference admittance controller estimates the environmental stiffness from
the measured force and the displacement from the initial contact point. This estimate is used to calculate
the effective stiffness, which represents the combined compliance of the environment and the virtual
controller spring. The controller then uses the effective stiffness to adjust the reference position so that the
new equilibrium point is approximately located where 𝐹𝑐𝑢𝑟𝑟 = 𝐹𝑑𝑒𝑠 .

 Software Implementation
 Program Structure

The force controller is organized into two main components: the outer loop, r_moveFC, and the inner
loop, r_adjustWaypointFC. The outer loop handles waypoint generation and sends motion commands to
the robot, while the inner loop applies the admittance law to adjust each waypoint before it is executed.

 Figure 4. Software Block Diagram

The current default control frequency is set to 100 Hz. While force controllers commonly operate
anywhere from 100 Hz to 1 kHz, testing showed that update rates above 100 Hz caused motion planning
errors. This was due to the excessive use of moveL commands, the default method for sending position
goals in RAPID. Additionally, the controller features an optional input parameter, disable_axes, which
allows force control to be disabled along selected axes. This was particularly useful during testing, since
most validation was performed along a single axis.

 Trajectory Interpolation & Motion Execution

The input to r_moveFC is a trajectory, provided as two arrays: one containing the desired target poses and
one containing the corresponding velocities. However, these input waypoints are not necessarily spaced
so that the controller can apply one adjustment per timestep. To resolve this, the controller interpolates
between the previous waypoint and the current target waypoint, generating the appropriate number of
intermediate points.

For each trajectory segment, the controller computes the maximum step size for both the robot end-
effector’s linear motion and the external table axis’s angular motion by multiplying their corresponding
speeds by the timestep. The total end-effector distance and table rotation are then divided by these step
sizes and rounded up to produce a whole number of waypoints. Because the robot end-effector and
external table axis must remain synchronized, the larger of the two counts is used as the final number of
interpolated waypoints:

 𝑛𝑤𝑎𝑦𝑝𝑜𝑖𝑛𝑡𝑠 = max(𝑛𝑙𝑖𝑛 , 𝑛𝑟𝑜𝑡 )

Los Alamos National Laboratory Page 8

This ensures that both the robot and the external axis reach their respective target positions at the same
time. However, it also introduces a small but important limitation. Since the number of waypoints must be
rounded up to a whole number, and since the end-effector and external axis motion must be synchronized,
the controller must reduce the effective speed from the original commanded velocity profile. As a result,
the robot will run slower than commanded, but this is necessary to preserve synchronization and ensure
that each interpolated step can be adjusted by the force controller.

Once the number of waypoints has been determined, the controller interpolates the position, orientation,
and external axis position. Two custom helper functions are primarily used for this process: f_vectorOffset
and f_slerp. The f_vectorOffset function handles linear translation by adding a displacement to the current
point in the direction of the target point. Orientation interpolation is handled using f_slerp, which is a
trigonometric implementation of spherical linear interpolation. Spherical linear interpolation is the
standard interpolation method for quaternions. The external axis interpolation is handled locally, where
the total table displacement is divided across the number of interpolated waypoints.

After interpolation, each generated waypoint is passed to the inner force control loop,
r_adjustWaypointFC. This routine applies the admittance control law discussed previously and returns an
adjusted waypoint, which is then sent to the robot using a MoveL command. Several optional parameters
are used to make the standard MoveL command better suited for our purposes.

First, the zone data is set to z1 instead of a fine point, allowing for fly-by behavior. While this slightly
reduces precision because force control generally operates at a sub-1mm scale, we found it was necessary
to reduce stuttering behavior. Second, the optional time parameter is used so that each MoveL command
takes one controller timestep. This is important because by commanding the motion duration directly, the
robot follows the adjusted timestep-based waypoint spacing rather than attempting to execute at the
original commanded speed. Third, concurrent motion planning is used at each original target waypoint.
This allows the ABB controller to begin planning upcoming motion commands before the current point
has fully completed, which also reduces stuttering. However, ABB controllers only allow a maximum of
5 points to be planned concurrently, meaning that this setting had to be used sparingly rather than for
every MoveL command.

Overall, r_moveFC converts the input trajectory into timestep-level interpolated waypoints, synchronizes
the robot end-effector with the external axis, and sends each adjusted point to the robot for execution.

 Waypoint Adjustment

The function r_adjustWaypointFC implements the admittance control law discussed in the previous
section. Rather than re-deriving the controller here, this section focuses on the main implementation
details needed to make the control law work reliably on the robot.

Firstly, the controller coordinate frame and the brush coordinate frame are rotated 180° about the x-axis
relative to one another. As a result, the motion corrections for the translational and rotational y and z-axis
corrections require a sign change to align with the tool coordinate frame. Similarly, the coordinate frame
used by the controller defines positive z as into the brush for both force and position. Therefore, if you
want to apply a downward force, like in Surface Prep, Fdes must be negative.

Los Alamos National Laboratory Page 9

Secondly, several bounds are included to prevent erratic motion. The adaptive stiffness scaling term:

 𝑘𝑠𝑐𝑎𝑙𝑒 = (1 − 𝐹𝑑𝑒𝑠 /𝐹𝑐𝑢𝑟𝑟 )

is bounded by [-1, 1]. This prevents the scaling factor from becoming excessively large when the
measured force is near zero. The admittance velocity correction, vadm, is bounded before being applied to
the waypoint, currently set to [-5, 5] mm/s. This prevents sudden large waypoint changes caused by force
spikes. After these bounds are applied, vadm is integrated over the controller timestep and used to update
the waypoint before it is sent to the robot.

Overall, r_adjustWaypointFC serves as the practical implementation layer that converts the theoretical
admittance law into safe, bounded waypoint corrections.

 Accessory Functions

Several accessory functions are used alongside the main admittance controller to improve reliability,
safety, and testing capability. The two primary helper routines used directly within the force controller are
r_initialContactFC and r_checkForceRetreat.

The r_initialContactFC routine is run at the very first waypoint of the trajectory. Its primary purpose is to
slowly move the robot into contact with the part and determine an estimate of the contact point, xe. This
contact point estimate is important for proper functionality of the admittance controller, as it is used
directly in the controller formulation and was discussed extensively in the controller stability analysis.
Additionally, this routine also moves the robot until its Fcurr is within a set threshold of Fdes, allowing for
better initial controller performance.

It is important to note that currently this routine is hardcoded for force control in the translational z-axis
only. Therefore, it would need to be modified for future applications that require initial contact detection
in other translational or rotational directions.

The r_checkForceRetreat routine is used throughout the main loop and checks whether the measured
force exceeds a specified maximum force threshold. If the measured force becomes too large, the function
commands the robot to retreat away from the part. This function acts as an important safety and stability
feature.

 Filtering & Simulation

Outside of the main ForceControlDevel module, the MonitorFT module is used to handle force-torque
measurement, filtering, and simulation. This module provides the filtered force values used by the
controller and includes tools for simulating contact forces. One important routine inside this module is
r_lowPass, which implements a standard discrete first-order IIR low-pass filter:

                                  𝐹𝑓𝑖𝑙𝑡 [𝑖] = 𝛼𝐹𝑟𝑎𝑤 [𝑖] + (1 − 𝛼)𝐹𝑓𝑖𝑙𝑡 [𝑖 − 1]

The filter is used to reduce high-frequency noise from the force-torque sensor before the force
measurement is passed into the controller. The current filter parameters use a cutoff frequency of f c = 5
Hz and a sampling frequency of fs = 250 Hz.

Los Alamos National Laboratory Page 10

Some common filtering guidelines are to set your sampling frequency at or below the update frequency of
the force-torque sensor and your cutoff frequency 𝑓𝑐 ≤ 𝑓𝑠 /10 in order to provide effective noise
attenuation while avoiding delay. Additionally, typical cutoff frequencies for force-control applications
are often in the range of 3 - 20 Hz, depending on the required balance between response speed and noise
reduction for your application.

Experimental testing showed little difference in controller response between 3 Hz and 5 Hz cutoff
frequencies. However, increasing it to 10 Hz introduced noticeably more noise into the force-control loop.
Therefore, a 5 Hz cutoff frequency was selected because it provided a good balance between control
bandwidth and noise attenuation.

 Controller Tuning

As previously discussed, the nominal trajectory did not perfectly match the actual shape of the test part.
This trajectory error directly affects controller stability because the contact point, 𝑥𝑒 , is estimated once at
the start of the controller relative to the trajectory. Therefore, any geometric mismatch between the
nominal trajectory and the real workpiece appears to the controller as contact point error, 𝛿𝑥𝑒 .

 Future Work
Although the controller performed well during Surface Prep testing, several improvements are
recommended before broader use. The highest priority issue is that the force controller added
approximately four minutes to the Surface Prep job. This slowdown is likely caused by the waypoint
synchronization logic, where the number of waypoints are rounded up to keep the robot and external table
axis synchronized. Future work should first check whether this slowdown is due to a logic error. If not,
alternative methods should be explored, such as handling table motion outside the force-control loop or
modifying the synchronization strategy.

Another possible cause is excessive motion planning from repeatedly sending MoveL commands at the
controller frequency. Future testing should evaluate whether the controller frequency can be reduced
while still maintaining acceptable force response. Additional MoveL optional argument tuning may also
improve performance. A larger change would be switching to ABB's Externally Guided Motion (EGM),
an interface that allows external, high-frequency updates to the robot's motion, which may be better suited
for high-frequency motion correction than repeated MoveL commands.

The controller should also be tested across more geometries, surface materials, and trajectory errors.
Current tuning was mainly focused on the Surface Prep job, and since the real part surface varied
noticeably from the input trajectory, the controller was tuned quite conservatively. This is what likely
caused testing on a flat plate to produce poor results, as the robot moved at a higher true speed than
during Surface Prep with the same controller parameters. Future testing should examine how controller
parameters need to change with speed, surface stiffness, and trajectory accuracy.

Additionally, the controller has only been validated for translational force control along the z-axis. Future
work should test multi-axis force control and evaluate whether coupling between axes affects stability.
Because testing has been limited to the z-axis, the initial contact routine is currently hardcoded for z-axis
force control and would need to be generalized for future applications. Torque control also remains
unvalidated. It should be noted that the current implementation uses a 1000x scaling factor to convert
torque readings in N*m into position corrections in mm, so this functionality should be tested cautiously
before use.

Another software limitation is that the force-control loop iterates through n_targets. Since RAPID does
not support dynamic arrays, this value is fixed at 1000, matching the initialized size of p_targets. To
handle trajectories with fewer than 1000 points, the controller exits the loop when it encounters a
commanded velocity of zero. However, this approach would be problematic for applications that require
force control at a stationary point, since a zero-velocity command is currently interpreted as the end of the
trajectory.

Finally, during testing Surface Prep the part profile files had avoid angles removed. If issues arise when
testing with them, the interpolation logic should be reviewed.
