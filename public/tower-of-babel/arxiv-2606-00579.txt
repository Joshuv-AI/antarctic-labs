Sandboxed Coding Agents are Competitive Omni-modal Task Solvers
Dongping Chen 1* , Xuanao Huang * , Zhihan Hu, Qingyuan Shi, Dianqi Li, Tianyi Zhou 2 ‡ \ddagger 1 University of Maryland, 2 MBZUAI

Abstract
As multimodal LLMs increasingly target video and audio, it is often assumed that such tasks require native omnimodal models. We show that this is not always the case: coding agents with only text+image access and a sandboxed tool-use interface can match, and in several settings outperform, SOTA native omnimodal models and predefined multimodal agent scaffolds across multiple audio-video benchmarks. Our trajectory analysis suggests that their strength comes from writing code and orchestrating tools to extract relevant evidence from transcripts, frames, and other modality signals, thereby converting omnimodal tasks into retrieval and information-processing problems rather than ingesting entire media streams. We further characterize their limitations through a failure taxonomy and process-level trace analysis, and show that simple skill injection, including human-written and self-distilled skills, substantially improves performance. To explore open-source elicitation, we introduce Code-X , a training recipe with the OmniCoding trajectory dataset and verifiable reward, and provide baselines on Qwen-3.5-9B and Qwen-3.6-27B. Finally, we argue that the next frontier is many-modality processing, and introduce TerminalBench-O , a process-level benchmark for real-world omnimodal processing tasks. Code will be available at https://github.com/Dongping-Chen/OmniCoding .

Introduction

As AI agents move from screen-bound workflows toward the broader world around users, they are expected to spend increasing amounts of time participating in everyday life as general-purpose assistants. To do so, they must handle multi-modal information from the embodied environments, especially video and audio. This immediately raises a question: Is native video and audio understanding necessary to an agent that is expected to process video or audio in real-world tasks?

In practice, however, many commonly-adopted agents nowadays, such as OpenClaw
(
56
)
and Hermes
(
53
)
, are still text-only or text+image systems, while extending them to handle video and audio natively requires substantial additional modeling and engineering effort. This creates a large gap between real-world agent deployment and the dominant paradigm for video-audio processing, namely native omni-modal models that directly ingest audio and video
(
61
,
googleGemini31Pro
)
. At the same time, modern coding agents already make highly effective use of terminal environments for search, editing, execution, and long-horizon task solving
(
88
,
1
,
7
)
. This raises a straightforward question:

Can coding agents, which are not designed for native multimodal perception, solve video and audio tasks by exploiting existing tools like
ffmpeg
, ASR, or new tools they write in a sandbox?

We investigate this problem using the most native Codex and Claude Code harnesses, without any human-provided tools or skills. Text+image coding agents, namely GPT-5.4
high
/
xhigh
and Claude Opus 4.6
(
55
,
2
,
1
)
, achieve strong performance on video-audio benchmarks such as OmniGAIA, SocialOmni, and LVOmniBench
(
39
,
83
,
70
)
. Codex with GPT-5.4
xhigh
reaches 75.0% on OmniGAIA without directly perceiving raw video or audio, outperforming the strongest native omni-modal model in our study, Gemini 3.1 Pro
(
googleGemini31Pro
)
, by more than 8%, while Claude Opus 4.6 exceeds it by 2.5%. Trajectory analysis shows that this advantage does not come from end-to-end perception. Instead, coding agents selectively decompose video and audio into transcripts, sampled frames, and metadata through staged tool use, which also consumes substantially fewer tokens than packing raw streams into model context.

To push coding agents on omni content further, we ask where they still fail and whether such failures can be repaired without retraining the base model. We sample 200 trajectories across models and benchmarks and propose an
Omni Terminal Failure Taxonomy
together with a process-level evaluation, which reveals six recurring failure modes ranging from premature exploration of multimodal content to brittle tool and environment infrastructure
(
27
,
92
,
42
)
. Guided by this taxonomy, we then study three skill-injection settings inspired by recent work on reusable agent skills and harness optimization
(
38
,
33
)
: human-in-the-loop skills that encode expert workflows, calibration-set self-iteration where the agent revises its skills using only binary correctness feedback, and log-driven self-distillation where a separate agent mines reusable skills from raw execution traces. All three improve over the no-skill baseline, raising average OmniGAIA accuracy from 61.4% to 76.7% in the best setting, with execution-trace distillation outperforming both binary self-iteration and human-written skills.

The above results are obtained with closed-source frontier models, which raises a natural follow-up question: can the same capability be elicited on open-source models through targeted post-training? As an exploratory baseline, we propose
Code-X
, a complete recipe for many-modality terminal agents. We construct
OmniCoding
, a 6,035-example trajectory dataset spanning video, audio, image, and cross-modal tasks, and train Qwen-3.5-9B and Qwen-3.6-27B with a supervised warm-start followed by GSPO-based reinforcement learning under a process-aware verifiable reward that jointly penalizes modality-skipping, malformed tool calls, and answer mismatches. Evaluating on four challenging benchmarks,
Code-X
yields substantial gains over direct MLLM baselines and achieves state-of-the-art results among open-source models, with the 27B model reaching 43.3% on OmniGAIA, 60.0% on LVOmniBench, where it surpasses all existing coding agents, and more than doubling performance on VideoZeroBench.

Given the maturity of many-modality understanding, we believe the meaningful frontier lies in many-modality processing: editing videos, auditing image databases, producing spec-compliant multimodal outputs, where coding agents enjoy a structural advantage over end-to-end omni models. To draw attention to this second half of many-modality, we introduce
TerminalBench-O
, the first process-level benchmark for coding agents on omni-modal processing, with 50 real-world tasks across video, audio, image, document, and cross-modal categories, each evaluated along weighted dimensions over intermediate artifacts and final output compliance. Despite strong omni-understanding results, these tasks remain hard for current agents as they demand long-horizon planning, reliable tool chaining, cross-modal grounding, artifact verification, and strict output adherence; even the strongest GPT-5.5 Codex reaches only 24% on
TerminalBench-O
. We hope our analysis, training recipe, and benchmark open new directions for many-modality processing.

Analysis of Sandboxed Agent Performance on Omni-Modal Tasks

Preliminary: Adapting Sandboxed Agents for Omni-Modal Tasks.

We represent each omni-modal task as
x=(q,\mathcal{F},\mathcal{Y})
, where
q
is a natural-language instruction,
\mathcal{F}
is a set of input files, and
\mathcal{Y}
is the set of acceptable final answers (formal definitions and the full rollout formulation are deferred to Appendix
C
). A native omni-modal model and a sandboxed agent differ mainly in
where
omni-modal processing happens:

\displaystyle\textbf{native omni:}

\displaystyle(q,\mathcal{F})\xrightarrow{\mathrm{pack}}\text{model context}\xrightarrow{M_{\theta}}\hat{y},

\displaystyle\textbf{sandboxed agent:}

\displaystyle(q,\mathcal{F})\xrightarrow{\mathrm{stage}}\text{workspace}\xrightarrow{\text{terminal interactions}}\tau\xrightarrow{\mathrm{Ans}}\hat{y}.

A native omni-modal model
M_{\theta}
packs all files into model context via media-specific encoding and sampling, treating video and audio as first-class model inputs to generate answers
\hat{y}
. A sandboxed agent, by contrast, stages
\mathcal{F}
into an isolated workspace and is given only the instruction and file paths; it then inspects files, invokes tools such as
ffmpeg
,
ffprobe
, OCR, and ASR, writes and executes scripts, produces intermediate artifacts (transcripts, sampled frames, OCR text, timestamps, tables, crops), which compose a trajectory
\tau
, and submits a final answer
\hat{y}
parsed from
\tau
. This view treats raw video, audio, images, and documents as environment state rather than mandatory model context, so the agent can solve omni-modal tasks by adaptively reducing raw media into compact evidence that fits the native reasoning interface of a general-purpose coding model.

Evaluation Protocol.

We use four benchmarks with complementary emphases: OmniGAIA for open-ended, tool-mediated factual and multi-hop omni-modal reasoning
(
39
)

(

(
70

(
49

Given their scale, we evaluate the first 100 examples per level on SocialOmni and LVOmniBench, and on SocialOmni we report only Level-1 and Level-2 Q1 accuracy, omitting the aggregate Level-2 score since it is computed only over Level-2-eligible examples and introduces substantial selection bias. For VideoZeroBench, questions on the same video are asked in a grouped manner. Unless otherwise noted, all models are evaluated with pass@1, and the agent receives only the task instruction and filesystem path(s) to the input files, with no pre-built Skills.

Environments.

ffmpeg

ffprobe

Token Usage Analysis.
Given the concern of using more tokens for better performance, we calculate the avg. token input and accuracy across four benchmarks. As shown in Figure
3

Based on our analysis of model trajectories and tool use patterns, we found that the image and audio content actually consumed by the coding agent is far smaller than what would otherwise be fed in its entirety to an omnimodal model. Through proactive tool use, the model selectively retrieves only the content it needs, substantially reducing the multimedia footprint in its context and thereby eliminating a significant amount of redundant tokens.

Failure Analysis: Taxonomy and Process-level Trajectory.

Given the strong performance of coding agents, we investigate the challenges they face in omni content processing. We propose a new failure mode taxonomy based on task type, and sample 200 trajectories (6,268 steps in total) across different models and benchmarks, along with their primary failure reasons. For each trajectory, we construct a DAG to identify its main trunk and branches, enabling process-level annotation. The resulting taxonomy comprises six failure modes: (i)
Audio Perception and Extraction
, (ii)
Video Perception and Extraction
, (iii)
Insufficient Exploration of Modal Content
, (iv)
Knowledge Retrieval and Factual
, (v)
Logical Reasoning and Calculation
, and (vi)
Tool and Environment Infrastructure
. Detailed definitions and representative examples are deferred to Appendix
G
. To scale the analysis beyond the 200 hand-annotated trajectories, we use GPT-5.5 as the process-level judge, which we validate against human labels on this small benchmark (see Appendix
8
for the validation protocol and results).

Figure
5
reports the empirical distribution of the six failure modes across four coding agents on
OmniGAIA
. Knowledge-Retrieval dominates the residual errors for three of four agents (Kimi 40%, Sonnet 43%, MiniMax 35%), while Codex-GPT5.4-Low is distinctive in that Tool/Environment Failure (21%) and Insufficient Exploration (20%) each rival its knowledge errors (27%). MiniMax further stands out for heavy Video-Perception errors (28%), indicating that different agents break down along different axes of the taxonomy. Beyond aggregate rates, Figure
4
dissects a single
OmniGAIA
trajectory as a DAG of annotated steps, showing how multiple modes from our taxonomy—audio-perception errors, rule violations, and scraping failures—co-occur with exploration-with-recovery behavior inside the same run, and how the agent ultimately recovers the correct answer.

Case Study

Question.

2.3
Skills and Self-Evolution for Strong Many-modality Content Processing

Experiment Setups.

Following recent work, we treat Skills as structured, inference-time packages of procedural knowledge that supply reusable workflows, instructions, and optionally executable resources to an agent
(
38
,
87
)
. Unless explicitly stated otherwise, the main results in this paper are reported without Skills.
We study three settings as follows:

•

Calibration-set self-iteration.
The agent is given a small calibration set and iteratively revises its Skills using only binary correctness feedback; we reveal whether an attempt is correct or incorrect, but do not provide any human-written diagnosis of the intermediate process.

•

Log-driven self-distillation.
A separate agent reviews raw execution logs, extracts recurring success and failure patterns, and writes Skills from these traces. This setting is inspired by recent log- and trace-driven harness optimization work such as Meta-Harness
(
33
)
.

•

Human-in-the-loop Skills.
We provide manually written Skills that encode a strong human route or best-known workflow. This setting serves as an approximate upper bound on the value of explicit procedural knowledge, while also introducing human prior and route bias.

Results and Analysis.

Figure

Skills
consistently improve

No Skills
baseline across all difficulty levels. All skill-enhanced variants raise average accuracy, with gains remaining visible on the

provides a representative example, where Skills help the agent avoid an incorrect application of regional rules and reach the correct answer.

Given that closed-source coding models outperform native omni-modal models in both performance and efficiency, we ask whether such capability can be elicited through post-training and reproduced on open-source models. To this end, we propose a strong baseline on Qwen-3.5-9B and Qwen-3.6-27B, with a complete SFT-then-RL training recipe, aiming to explore this direction on open-source coding agents on omnimodal content.

3.1
OmniCoding
: Synthesized Omnimodal Coding Agent Trajectory Dataset

We construct
OmniCoding
, a dataset of 6,035 verifiable question–answer examples paired with video, audio, or image files for multimodal terminal-tool-use agents. Each example follows a unified schema with a question, a list of acceptable ground-truth answers, media paths, and source/modality/task metadata. We draw from four complementary sources, OmniGAIA-SFT-2K
(
39
)
, OmniVideoBench
(
34
)
, AVUTBenchmark
(
92
)
, and Video-MME-v2
(
20
)
, keeping only the Video-MME-v2 subset requiring audio-visual or temporal reasoning. Table
3
and Figure
8
report the per-source composition and media-duration distribution. Construction proceeds in three steps:
(i) Normalization
, unifying all sources into the same schema with deduplicated questions and media consolidated into a flat directory;
(ii) Verifiability
, regenerating open-ended questions with ground-truth lists covering common surface variants (units, abbreviations, capitalization, number formats) and converting multiple-choice into option-letter answer sets; and
(iii) Cross-review
, verifying answer lists and task coverage. We stratified-split the data into 4,042 SFT and 1,993 RL examples by source-task key, and use exact match against the ground-truth list (extracted from an
<answer>
tag) as the binary RL reward.

3.2
Method and Training Infrastructure

We train the terminal agent with supervised warm-start followed by reinforcement learning from verifiable rewards. All training examples follow the schema
x=(q,\mathcal{F},\mathcal{Y})
, where multiple-choice tasks use option-letter answer sets and open-ended tasks are assigned curated answer sets covering common aliases, units, abbreviations, capitalization, and number formats. The agent submits its final answer inside
<answer>
.

Supervised warm start.

For examples with demonstration trajectories, we fine-tune on assistant-generated tokens only, masking terminal outputs, tool responses, and environment observations from the loss. This stage teaches the basic interaction protocol: inspect files, run commands, create intermediate artifacts, recover from tool failures, and submit answers in the required format.

Reward design.

We design a process-aware verifiable reward that goes beyond binary answer matching, addressing three failure patterns: (1) the agent guesses without engaging the workspace, (2) it ignores the relevant modality (e.g., answering a video question from text alone), and (3) it emits malformed, escape-attempting, or otherwise broken tool calls. For each rollout
\tau
we compute

R(x,\tau)=\begin{cases}0,&\text{if }\tau\text{ is removed (timeout / step-limit / context overflow)},\\[2.0pt]
\text{base}(\tau)+r_{\mathrm{mod}}(\tau)+r_{\mathrm{tool}}(\tau),&\text{otherwise},\end{cases}

with the following components:

•

Three-tier base reward.

\text{base}(\tau)=w_{\text{correct}}
if gated-correct (normalized exact match against
\mathcal{Y}
, modality engaged,
\geq 1
tool call, no escape attempt); else
w_{\text{fmt}+}
if the agent terminated cleanly via
task_complete
with a non-empty
<answer>
; else
w_{\text{fmt}-}
. The format bonus does
not
stack with correctness; it exists solely to keep gradient signal on tried-correctly-but-answered-wrong trajectories that would otherwise collapse the group to zero variance.

•

Modality penalty
r_{\mathrm{mod}}
.
A fixed negative weight
w_{\mathrm{mod}}
is charged when the task contains video or audio but the agent invokes no tool from the corresponding universe (
ffmpeg
,
whisper
, etc.), detected by substring matching on bash commands.

•

Bad-tool penalty
r_{\mathrm{tool}}
.
A weighted ratio
-w_{\mathrm{tool}}\cdot P_{\text{bad}}
with
P_{\text{bad}}=(n_{\text{unparseable}}+n_{\text{disallowed}}+n_{\text{escape}}+n_{\text{syntax-fail}})/(1+n_{\text{tool}})
aggregates malformed calls, disallowed tools, gold-answer leakage attempts, and persistent shell errors.

Weight values are listed in Appendix
H.1
. We further apply group-level mechanisms:
(i) group advantage normalization
centers rewards within each group of
G
sibling rollouts;
(ii) zero-variance masking
drops groups where all rollouts succeed or fail;
(iii) active-only baseline
excludes removed samples from group statistics; and
(iv) dynamic filter
drops groups with
\leq 1
active sample or near-zero variance originated from DAPO
(
96
)
.

GSPO update.

For each task we sample
G
rollouts
\tau_{i}\sim\pi_{\theta_{\mathrm{old}}}(\cdot\mid x)
and compute group-normalized advantages
A_{i}=(R_{i}-\bar{R})/(\sigma_{R}+\epsilon_{A})
. Let
z_{i}=(z_{i,1},\ldots,z_{i,L_{i}})
be the model-generated tokens in
\tau_{i}
(tool outputs masked from the loss) and
c_{i,\ell}
the transcript prefix before
z_{i,\ell}
. Following GSPO
(
105
)
, we use a length-normalized sequence-level importance ratio and optimize the clipped objective:

\displaystyle\rho_{i}(\theta)=\exp\!\left(\frac{1}{L_{i}}\sum_{\ell=1}^{L_{i}}\big[\log\pi_{\theta}(z_{i,\ell}\mid c_{i,\ell})-\log\pi_{\theta_{\mathrm{old}}}(z_{i,\ell}\mid c_{i,\ell})\big]\right),\qquad\mathcal{J}_{\mathrm{GSPO}}(\theta)=\mathbb{E}_{x}\!\left[\frac{1}{G}\sum_{i=1}^{G}\min\!\Big(\rho_{i}(\theta)A_{i},\,\mathrm{clip}\!\big(\rho_{i}(\theta),1-\epsilon_{-},1+\epsilon_{+}\big)A_{i}\Big)\right].

Since reward is assigned to whole trajectories, sequence-level clipping is a natural fit: one importance ratio weights all generated tokens while tool outputs stay masked.

Training infrastructure.

Our RL system decouples sandboxed rollout generation from policy optimization. Rollout workers run the current policy in isolated workspaces, execute terminal commands, collect trajectories, parse answers, compute reward components, and return old log-probabilities and masks; the trainer consumes these logs and applies GSPO without executing tools or touching raw media. This separation is useful because omni-modal rollouts involve non-differentiable operations, while the optimizer only needs token sequences, masks, old log-probabilities, and scalar rewards. Sandboxes are hosted on a Slurm cluster with CPU/GPU nodes and storage, the trainer runs on cloud servers, and the two are connected via a
Cloudflare
tunnel for trajectory collection.

3.3
Experiment Setups and Results

Agent Harness.

To train
OmniCoding
, we build a local terminal-agent harness adapted from Terminus-KIRA
(
29
)
for converting raw multimodal files into small, checkable agent operations. At each episode, the environment creates an isolated workspace with the question and staged media files. The media remains in the filesystem rather than being packed into the model context, so the agent must decide how to inspect it through audio extraction, frame sampling, OCR/ASR, metadata reading, scripting, and intermediate verification. The visible action space is deliberately compact:
execute_commands
runs one command in a persistent shell,
image_read
inspects an image as a native multimodal observation, and
task_complete
ends the episode. Higher-level media processing is expressed through code and command-line tools rather than benchmark-specific APIs, keeping the harness lightweight but expressive. Unlike general software-engineering harnesses
(
74
,
67
)
, our scaffold focuses on offline multimedia processing and trajectory collection: tool calls, terminal/image observations, final answers, exit reasons, and rewards are serialized for SFT filtering, RL replay, and failure analysis. Full details are in Appendix
I.1
.

Baselines and Evaluation Protocol.
We train Qwen3.5-9B and Qwen3.6-27B and compare against three baselines:
(i)
training-free direct MLLM inference, where the model is fed visual frames sampled at fps=1 (capped at 512) together with Whisper-large ASR transcripts;
(ii)
the same MLLM evaluated under our harness with direct image reading; and
(iii)
SFT warm-up baseline. We additionally include Codex GPT-5.4 (low) under our harness as a reference. The thinking budget is set to 4K tokens; if the model fails to produce a correctly formatted answer, we issue a multi-turn reminder to re-answer in the required format, and if reasoning is truncated, the model is allowed to continue thinking. We evaluate on the same benchmark suite as before, reporting pass@1 throughout.

TerminalBench-O
: From Many-modality Understanding to Processing

Figure 9
:
Overview of our benchmark, illustrated with Task T01. The coding agent is required to generate a highlight clip and caption from a soccer video and a player query, and its outputs are evaluated by an LLM-based judge in terms of event accuracy, video quality, and task correctness.

As many-modality understanding capabilities mature, the frontier is shifting from passive
understanding
to active
processing
: editing videos, auditing image databases, and producing spec-compliant multimodal outputs. This shift reveals a gap between native omni-models, which excel at end-to-end perception but cannot directly operate on files, and coding agents, which can decompose tasks into tool-use pipelines. Yet existing benchmarks do not evaluate this capability: omnimodal benchmarks such as OmniGAIA
(
39
)
and LVOmniBench
(
70
)
focus on QA-based perception, while coding-agent benchmarks such as Terminal-Bench
(
50
)
and Claw-Eval
(
95
)
mainly target text or text+image tasks. As shown in Table
6
, none jointly cover many-modality understanding (MMU) and many-modality processing (MMP) on real-world cases. To close this gap, we introduce
TerminalBench-O
, the first process-level benchmark for coding agents on omnimodal tasks, requiring agents to process realistic inputs such as long videos, multilingual documents, and noisy audio through multi-stage pipelines, and evaluating both multimodal understanding and operation capability.

Design Principles.

TerminalBench-O
comprises 50 challenging tasks across video (38%), audio (26%), image (14%), document (4%), and cross-modal (18%) categories. Four core principles guide the design:
(i) Real-world cases
, where all tasks are drawn from authentic sources (Internet Archive, HuggingFace datasets, public videos) rather than synthetic constructions;
(ii) Multi-dimensional grading
, where each task is scored along 4–8 weighted dimensions covering accuracy, cross-document consistency, and output quality;
(iii) Shortcut-resistant design
, which combines closed vocabularies, cross-file ID consistency checks, decoy injection, and word limits to prevent gaming; and
(iv) Process-level evaluation
, which validates intermediate artifacts and reasoning chains rather than only final answers.

Task Categories.

Representative tasks include:
Video Understanding & Processing
(T01a: extract 60-90s highlights from 90-min soccer broadcast by jersey number; T03a: auto-edit 5-min final cut from 3-camera meeting footage);
Audio Forensics
(T107a: segment 22-min concert recording into songs with tempo/defect detection; T108a: extract rhetorical devices and thematic structure from political speech);
Image Database Analysis
(T13a: detect wood defects with pixel-level masks; T50a: audit mislabeled images in CIFAR-10 subset). Unlike QA benchmarks,
TerminalBench-O
requires agents to
create
multimodal outputs (edited videos, text+video interleaved reports) that satisfy strict format and consistency constraints.

Evaluation Protocol.

Each task defines a weighted scoring formula
\text{score}=\sum_{i}w_{i}\cdot m_{i}
where

6
Conclusion

We study offline omnimodal understanding through the lens of sandboxed coding agents in both training-free and fine-tune settings. Across multiple benchmarks, these agents solve a surprisingly large fraction of video-audio tasks by selectively retrieving and processing evidence from raw inputs, often rivaling or surpassing native omnimodal systems. We hope this work motivates a deeper study of multimodal intelligence at the model–tool–environment interface.

Appendix A
Limitations

Our study has several limitations. First, due to computing-resource constraints, the
Code-X
training recipe is only validated at the 9B and 27B scales (Qwen-3.5-9B and Qwen-3.6-27B), and we have not yet characterized how the recipe scales to frontier-size open-source models. Second, due to API credit constraints, several closed-source coding agents could not be evaluated on the full benchmark suite. In particular, Claude Opus 4.6 results on VideoZeroBench and Claude Opus 4.7 results across all four benchmarks are incomplete in the current draft, which means the comparison between coding agents and native omni-modal models is somewhat uneven on the closed-source side. Third, our scope is restricted to
offline
omni-modal tasks, where files are staged into a workspace ahead of time; conclusions do not transfer directly to streaming or interactive settings.

Appendix B
Broader Impacts

Our findings establish a more compute- and token-efficient pathway for offline omni-modal understanding, showing that text+image coding agents with sandboxed tool use can match or surpass native omni-modal models on many video- and audio-centric tasks while consuming fewer tokens. This lowers the resource barrier for omni-modal applications and broadens access for researchers and users who lack dedicated omni-model APIs, while our open-sourced
Code-X
recipe,
OmniCoding
dataset, and
TerminalBench-O
benchmark further support reproducible research at the model–tool–environment interface. As with any tool-using agent that processes video and audio, downstream deployments should incorporate standard safeguards such as content provenance, access controls, and user consent; we note that our agents operate only on user-staged files within an isolated workspace and do not autonomously take real-world actions.

Appendix C
Adapting Sandboxed Agents for Omni-Modal Tasks

We represent each omni-modal task as

x=(q,\mathcal{F},\mathcal{Y}),

where
q
is a natural-language instruction,
\mathcal{F}
is a set of input files, and

\mathcal{Y}
is the set of acceptable final answers. We use an answer set rather than a
single reference string so that aliases, option letters, numerical formats, and unit variants can
be handled uniformly in both evaluation and reinforcement learning.

A native omni-modal model solves the task by packing the files into model context:

\hat{y}_{\mathrm{omni}}=M_{\theta}\!\left(\mathrm{Pack}(q,\mathcal{F})\right),

where
\mathrm{Pack}(\cdot)
denotes model-specific media encoding, sampling, and serialization.
In this formulation, video and audio are first-class model inputs.

In contrast, our sandboxed agent does not need to ingest all raw media as context. The files

\mathcal{F}
are staged into an isolated workspace, and the agent is given the instruction and
the corresponding file paths. It then interacts with the workspace through a terminal interface:
it can inspect files, invoke tools such as
ffmpeg
,
ffprobe
, OCR, or ASR systems,
write and execute scripts, create intermediate artifacts, and finally submit an answer.

A sandbox rollout is written as

\tau=(o_{0},a_{0},o_{1},a_{1},\ldots,o_{T},a_{T}),

where
o_{t}
is the current observation, including command outputs and workspace feedback, and

a_{t}
is the agent’s next message or terminal action. During a rollout, raw omni-modal files may
be converted into task-relevant artifacts such as transcripts, sampled frames, OCR text, timestamps,
tables, crops, or executable analysis scripts. The final prediction is parsed from the trajectory:

\hat{y}=\mathrm{Ans}(\tau),

where
\mathrm{Ans}(\cdot)
extracts the submitted answer, e.g., the content inside an

<answer>
tag when this format is required.

Thus the two settings differ mainly in where omni-modal processing happens:

\displaystyle\textbf{native omni:}

\displaystyle(q,\mathcal{F})\xrightarrow{\mathrm{Pack}}\text{model context}\xrightarrow{M_{\theta}}\hat{y},

\displaystyle\textbf{sandboxed agent:}

\displaystyle(q,\mathcal{F})\xrightarrow{\mathrm{stage}}\text{workspace}\xrightarrow{\text{terminal interaction}}\tau\xrightarrow{\mathrm{Ans}}\hat{y}.

This view treats raw video, audio, images, and documents as environment state rather than mandatory
model context. The agent can therefore solve omni-modal tasks by adaptively reducing raw media
into compact evidence that fits the native reasoning interface of a general-purpose coding model.

Appendix D
Discussion and Future Works

Do non-native modalities really require native end-to-end perception?
Our results suggest that non-native modalities do not always require native end-to-end perception. Even in the simplest Codex and Claude Code settings, coding agents solve a surprisingly large fraction of video-audio tasks, and on OmniGAIA they can even outperform strong native omnimodal baselines. The key is not that the base model suddenly becomes an audio-video perceiver, but that the sandbox lets it decompose raw multimedia into artifacts that match its native reasoning interface, such as transcripts, key frames, timestamps, OCR, metadata, and compact summaries. In this sense, multimodal processing becomes analogous to protocol-based software access in text-domain agents: the model delegates non-native operations to the environment and then reasons over the returned evidence. This perspective is consistent with the broader shift from static function calling to environment-mediated problem solving in tool-use and terminal-agent evaluation
(
75
,
51
,
8
)
. It also resonates with recent tool-augmented perception work, where explicit visual-tool policies and tool-derived perceptual signals both improve fine-grained multimodal reasoning
(
107
,
76
)
. A natural next question is therefore not only whether a model is natively omni, but which capabilities should remain externalized, which can be compiled into reusable skills, and how agents should detect and recover from imperfect tool outputs. Our failure taxonomy and process-level benchmark point in this direction, suggesting that the central bottleneck is often tool selection, verification, and repair rather than the mere absence of raw multimodal encoders.

Shortcuts in current video-audio benchmarks.
Are current video-audio benchmarks measuring what they claim to measure? Our findings suggest only partially. When a text+image coding agent can answer many ostensibly omnimodal tasks by selectively extracting transcripts, sparse frames, or metadata, benchmark accuracy no longer cleanly measures native end-to-end audio-video understanding. This does not make such benchmarks uninformative, but it does mean that they frequently conflate at least three capabilities: native perception, external evidence acquisition, and general knowledge-based reasoning. Our results are aligned with recent audits and diagnostic studies showing that many video or audio-visual benchmarks admit strong visual, textual, or temporal shortcuts
(
26
,
43
)
. They are also consistent with benchmark-design efforts that explicitly enforce stronger audio dependence or reduce text-based shortcut channels
(
76
)
. Going forward, we believe benchmark design should standardize at least three controls: reporting text-only, text+image, and agentic baselines; auditing modality dependence with masking or filtering tests; and minimizing leakage from subtitles, transcripts, metadata, and external retrieval whenever the target claim is native multimodal understanding. Conversely, when the target is multimodal agentic competence, retrieval, tool orchestration, and evidence processing should be treated as first-class evaluation targets rather than accidental shortcuts. Making this distinction explicit would help separate backbone perception from system-level problem solving, which are both important but not interchangeable.

Can the same sandbox move from understanding to generation?
We believe this is the most promising next step. Once an agent can inspect raw video, audio, and documents, compress them into structured evidence, and maintain task-relevant state over long horizons, it can in principle also plan edits, retrieve assets, invoke generative models, and validate outputs in a closed loop. Early multimedia-generation and agentic video-editing systems already point in this direction, showing that multimodal agents can coordinate text, images, video, music, and external tools under explicit planning and feedback loops
(
97
,
103
)
. The next frontier is to connect that generative loop with persistent multimodal memory, so that an assistant can build private memos, recap videos, highlight reels, or even broadcast-ready drafts grounded not only in a single uploaded file but in a user’s longer-term audiovisual history
(
45
)
. Doing so will require stronger memory management, preference modeling, provenance tracking, and process-level verification, since generated content must remain faithful both to source media and to user intent. More broadly, this points to a different picture of future omni assistants: not a single monolithic model that passively consumes everything in one shot, but a sandboxed system that can inspect, remember, transform, and generate across modalities with the right mix of reusable skills and external tools. Under this view, offline omnimodal understanding is not the endpoint of this line of work, but the substrate for practical multimedia copilots.

Raw data.

We ground the suite in real-source data: public research
datasets, public archives, public-domain scans, and direct-download media. The
sources cover broadcast/web video, AMI and legal speech, action and egocentric
video, industrial and scientific imagery, geospatial data, music stems,
bioacoustics, score-audio pairs, FITS files, and historical comics. Synthetic
content is reserved for controlled corruptions, decoys, overlays, and auxiliary
labels needed to make evaluation precise.

Preprocessing.

Each source is normalized into a stable workspace representation before task
packaging. We also prepare
closed vocabularies, masks, catalogs, WCS headers, timestamp maps, and
source-to-fixture mappings for downstream grading.

Construction.

Step 1: Candidate mining.

We first select source segments whose native structure supports a realistic
operation task, such as eventful video intervals, speaker turns, action clips,
score-aligned music excerpts. Candidate
segments are filtered for duration, visibility, signal quality, annotation
availability, and non-triviality before fixture generation.

Step 2: Task-specific transformation.

We then impose an operation or creation objective on the selected source. Some
tasks add controlled corruptions, hidden mappings, decoys, overlays, splice
events, synchronization errors, or multi-source audio compositions. Others keep
the media unchanged but require structured deliverables such as ledgers,
catalogs, action datasets, OMR alignments, reading-order tables, or redaction
reports.

Step 3: Hidden reference synthesis.

For each instance, we write hidden references that specify the answer geometry
used by the grader. These references include event windows, speaker maps,
transcripts, quote spans, crop paths, clean media, masks, stem targets,
timestamp curves, object tracks and
closed-vocabulary labels. They are withheld from the agent but used to score
both final outputs and intermediate artifacts.

Step 4: Output-surface packaging.

Finally, we expose each task as a small working directory rather than a
question-only prompt. The visible files may include media, manifests, closed
vocabularies, policy snippets, PDFs, CSVs, point clouds, FITS files, or
auxiliary metadata, and the expected outputs are ordinary files such as
MP4/WAV/PNG artifacts, CSV/JSON ledgers, subtitles,plots, and
reports. This format keeps the benchmark native to terminal tools,

ffmpeg
, OCR/ASR, numerical Python, and file-system coordination.

Filtering.

We apply filtering before and after packaging. Source candidates are removed if
they are too short, ambiguous, silent, weakly annotated, or trivially solvable. Packaged tasks are then checked for
complete schemas, aligned hidden references, active closed vocabularies, decoy
coverage, and resistance to shortcuts such as pass-through media, empty
manifests, constant labels, or copied templates.

Evaluation.

Each task uses a dedicated grader with weighted dimensions and gating
conditions. Deterministic checks cover temporal IoU, event recall,
closed-vocabulary accuracy, WER/CER, speaker attribution, ASR preservation,
signal metrics, SSIM/PSNR, mask IoU, timestamp error, catalog matching,
photometric error, geospatial overlap, table consistency, and schema validity.
For naturally open-form artifacts such as memos, overlays, or semantic
summaries, some graders add constrained LLM/MLLM checklist axes. The final score
therefore measures process-level completion: media quality, structured
intermediate artifacts, format compliance, and cross-document consistency.

Here we provide detailed definitions of the six failure modes introduced in the main text.

•

Audio Perception and Extraction Error.
The agent mis-transcribes, mis-segments, or mis-attributes the audio signal itself (
e.g.
, ASR errors under noise or speaker confusion), so all downstream reasoning is conditioned on content that diverges from the true recording.

•

Video Perception and Extraction Error.
The visual stream is misread at the source via blank or off-key frame sampling, OCR mistakes, or inverted event ordering, leaving later stages with incorrect evidence.

•

Insufficient Exploration of Modal Content.
With multimodal inputs available, the agent answers from textual cues or priors, or terminates exploration before critical evidence is verified. The failure lies in the decision to stop probing rather than in perception quality.

•

Knowledge Retrieval and Factual Error.
Given correct perception, the agent links it to wrong external knowledge through poorly specified queries, unreliable sources, conflated entities, or fabricated facts when retrieval fails.

•

Logical Reasoning and Calculation Error.
Evidence is largely correct, but the derivation breaks down via wrong formulas (
e.g.
, planar vs. spherical distance), arithmetic mistakes, or dropped conditions in multi-step deductions.

•

Tool and Environment Infrastructure Failure.
The agent picks the right tool but is blocked by missing dependencies, sandbox permissions, or resource limits, forcing later steps to build on corrupted intermediates.

I.1
Omni-terminal Harness

This appendix details our terminal-agent harness, adapted from Terminus-KIRA
(
29
)
and designed around a single operation: turning raw multimodal files into small, checkable evidence. Each episode begins with an isolated workspace containing the question and the staged media files. Rather than packing media into the model context, files remain on disk, and the agent must decide how to inspect them: extracting audio, sampling frames, running OCR or ASR, reading metadata, writing scripts, and verifying intermediate results before answering. The agent operates through a small action space (
execute_commands
,
image_read
,
task_complete
) and expresses higher-level media operations through code and command-line tools (
ffmpeg
/
ffprobe
, ASR, OCR, Python, OpenCV, NumPy, and self-authored scripts) rather than benchmark-specific APIs. Beyond execution, the harness is centered on trajectory collection: every tool call, terminal observation, image observation, final answer, exit reason, and reward field is serialized so the same rollout can be reused for SFT filtering, RL replay, and failure analysis.

Concretely, the harness has four properties that are important for training:

•

Filesystem-grounded media processing.
Raw video, audio, images, and documents are workspace state. The agent learns to transform them into transcripts, key frames, OCR text, timestamps, tables, and other compact evidence.

•

Persistent terminal interaction.
Commands run in a stateful bash session with marker-based completion, bounded observations, timeout recovery, and support for scripts written during the episode.

•

Replay-faithful multimodal observations.

image_read
inserts the actual image into the main conversation, rather than replacing it with a caption from a separate model. The saved rollout therefore matches the observation distribution used for multimodal SFT/RL.

•

Qwen-compatible rollout collection.
The tool schema is flat, malformed tool-call blocks are conservatively recovered, and requests are routed through sticky SGLang endpoints to preserve prefix-cache locality during large parallel rollouts.

Episode state.

Each task starts from an isolated workspace

s_{0}=(q,W_{0},U_{0}),

where
q
is the task instruction,
W_{0}
contains the staged input files, and
U_{0}
contains the available command-line tools and Python libraries.
The model does not receive the raw video or audio stream as context.
Instead, it interacts with files through the terminal.
During a rollout, the workspace may accumulate derived artifacts such as extracted frames, audio clips, ASR transcripts, OCR outputs, metadata files, temporary scripts, and numerical tables.
The final prediction is accepted only from the benchmark-normalized
<answer>...</answer>
wrapper.

Tool interface.

The model sees three tools.
The small tool set is deliberate: the terminal is the compositional interface, and the agent decides how to combine existing utilities with code it writes during the episode.

Tool

Function

execute_commands

Runs one shell command in a persistent bash session.
The schema is flat: the call contains
analysis
,
plan
, and
keystrokes
.
Multi-step work is expressed with shell syntax, scripts, or heredocs.

image_read

Loads an image file as a native multimodal observation for the main agent.
This is used for frames, crops, figures, screenshots, OCR targets, and visual verification.

task_complete

Ends the rollout after the model has emitted the final answer wrapper.
If the wrapper is missing, the harness issues one format reminder before scoring the run as empty.

Agent loop.

At each step, the harness sends the current conversation and tool schema to the model.
If the model calls
execute_commands
, the command is executed in the persistent shell and the bounded output is returned as a tool observation.
If it calls
image_read
, the harness first records a short tool acknowledgement and then appends the image itself as a multimodal observation in the main conversation.
If it calls
task_complete
, the harness checks whether a wrapped answer already appears in the trajectory.
The loop stops on successful completion, step limit, no-tool-call exhaustion, or runtime error.

Shell runtime.

The shell is a persistent bash subprocess.
This preserves state across turns, including the current directory, environment variables, installed packages, and files created by the agent.
Command completion is detected by appending a hidden marker after each command and polling until the marker appears.
Terminal observations are capped with head–tail truncation, which keeps both the beginning of long outputs and the end where errors or final answers often appear.
When a command times out, the harness terminates the direct child processes while keeping the shell alive.
If the shell itself dies, it is restarted and the next observation warns the model that shell-local state has been lost.

Native multimodal replay.

The main change from a standard terminal harness is the native
image_read
path.
A caption-only image reader is acceptable for evaluation, but it is not acceptable for multimodal policy training: the saved trajectory would contain text produced by a separate model rather than the pixels observed during rollout.
Our harness instead stores image observations as multimodal content blocks in the main conversation.
For Qwen-style chat templates, these messages are folded into the provider-specific tool-response format only at send time.
The saved artifact remains provider-neutral and can be replayed for SFT or RL without changing the observation sequence.

Qwen serving and tool-call robustness.

Open-weight models served through SGLang can emit partially malformed tool-call blocks, especially when shell commands contain quotes, heredocs, or escape characters.
We therefore use a flat
execute_commands
schema and a conservative recovery layer.
If the backend returns no structured tool call but the assistant text contains a recognizable
<tool_call>
block, the harness reconstructs the call only when the function name is in the declared tool list and the arguments can be parsed without inventing content.
Recovered calls are marked in the trajectory, so downstream data filtering can keep or drop them explicitly.

Trajectory artifacts.

Each rollout stores the full message sequence, parsed tool calls, shell outputs, image-observation references, final extracted answer, exit reason, and evaluation metadata.
The same artifact supports three downstream uses.
First, successful trajectories can be filtered into SFT examples.
Second, RL training can replay the same observation distribution seen during rollout.
Third, failures can be inspected at the process level: whether the agent sampled the wrong frames, trusted a bad ASR transcript, stopped too early, chose the wrong external fact, or made a calculation error.
