Hera: Learning Long-Horizon Coordination for Device–Cloud Collaborative LLM Agents
Yuxin Zhang, Mengxue Hu, Zheng Lin, Xiaoyi Fan, Fan Xie, Zihan Fang, Jing Yang, Wenjun Zhu, Zhiwen Chen, Chengfei Lv, Zhe Chen

Abstract
Large language model (LLM) agents excel at solving complex long-horizon tasks through autonomous interaction with environments. However, their real-world deployment faces a fundamental device–cloud dilemma : on-device models are efficient but often brittle, while cloud models are stronger but costly in computation. State-of-the-art LLM device–cloud routers usually make coarse task-level decisions, which cannot adapt to the changing difficulty of multi-step agent interactions. To address this issue, we present Hera, a step-level device–cloud LLM agent coordinator for long-horizon tasks achieving a strong performance–cost Pareto frontier. Hera adopts a novel two-stage training paradigm: (1) imitation learning for cold-start, followed by (2) reinforcement learning that jointly optimizes task success and cloud usage efficiency. The first stage casts step-level routing as a supervised classification problem: the device agent is replayed on cloud trajectories, with each state labeled by the agreement between device and cloud actions. In the second stage, we perform cost-aware reinforcement learning by grouping identical states across trajectories and updating Hera with labels favoring higher expected return and fewer future cloud calls. We evaluate Hera on ALFWorld, WebShop, and AppWorld, where it consistently outperforms prior methods, achieving 92.5% of the cloud-only success rate with cloud use in only 46.3% of steps.

On one hand, deploying advanced agents directly on user-end is infeasible due to stringent resource constraints.
Small models (e.g.,

To balance local efficiency and global performance, recent work dynamically allocates inference between device- and cloud-side LLMs

Importantly, we find that offloading only a small fraction of critical steps along the trajectory to the cloud is sufficient to match the task success of cloud-only execution (§

Building on this insight, we propose Hera, a lightweight yet powerful device–cloud coordinator that identifies when cloud assistance is necessary, reducing cloud usage while maintaining strong task completion.
Hera follows a two-stage training paradigm, as shown in Figure

We initialize Hera via imitation learning by replaying the device agent on cloud trajectories and labeling each step by device–cloud action consistency.
We then refine Hera with cost-aware reinforcement learning: across multiple rollouts, we group identical states and assign step-level preference labels that prioritize higher estimated return and lower expected future cloud usage.
Across various challenging agent benchmarks including ALFWorld

Our contributions are threefold:

•

To the best of out knowledge, Hera is the first step-level device–cloud agent coordinator, addressing the performance–cost trade-off of deploying LLM agents in long-horizon tasks.

•

We develop a two-stage training framework for Hera: an imitation-learning stage that initializes routing from device–cloud action agreement, followed by a state-grouped reinforcement learning stage that jointly optimizes trajectory return and cloud cost.

•

Experiments on various agent benchmarks show that Hera outperforms state-of-the-art methods, achieving a stronger trade-off between task success and cloud usage.

Preliminaries

Problem setup.

We consider a finite-horizon, multi-step agentic task setting in which an LLM-parameterized policy
\pi_{\theta}
governs an agent interacting with an environment to accomplish a task specified by a description
x\in\mathcal{X}
.
At each step
t\in\{1,\dots,T\}
, the agent observes
\mathbf{s}_{t}\in\mathcal{S}
and samples a textual action
\mathbf{a}_{t}\in\mathcal{V}^{n}
according to the conditional distribution
\pi_{\theta}(\mathbf{a}_{t}\mid\mathbf{s}_{t},x)
, where
\mathcal{V}
is the LLM vocabulary and
n
is the maximum output length.
The environment subsequently returns a scalar reward
r_{t}\in\mathbb{R}
and the next state
\mathbf{s}_{t+1}
.
An episode produces a trajectory
\tau=\{(\mathbf{s}_{1},\mathbf{a}_{1},r_{1}),(\mathbf{s}_{2},\mathbf{a}_{2},r_{2}),\dots,(\mathbf{s}_{T},\mathbf{a}_{T},r_{T})\}
with an associated return
R(\tau)
(e.g., verifiable, outcome-level task feedback), which is often used to optimize the LLM policy to maximize the expected return of the agent’s trajectories
(
27
;
28
)
.

Device–cloud collaboration.

Extending the single-agent paradigm, we formalize the device–cloud collaborative system: the device policy
\pi_{\theta_{\mathrm{d}}}
performs low-latency inference using a lightweight LLM (typically
<
3B parameters) under strict memory and compute constraints, while the cloud policy
\pi_{\theta_{\mathrm{c}}}
exploits massive scale (hundreds of billions of parameters) to deliver superior reasoning capabilities at the cost of non-negligible latency and high resource overhead.
Let
r_{\phi}:\mathcal{S}\times\mathcal{X}\rightarrow\{0,1\}
denote a device–cloud router parameterized by
\phi
, where for a task–state pair
(\mathbf{s},x)
,
r_{\phi}(\mathbf{s},x)=0
selects local processing by
\pi_{\theta_{\mathrm{d}}}
, and
r_{\phi}(\mathbf{s},x)=1
escalates the request to
\pi_{\theta_{\mathrm{c}}}
.
Thus, the final action of device–cloud collaborative agents under
(\mathbf{s},x)
is given by:

\hat{\mathbf{a}}(\mathbf{s},x)=\big(1-r_{\phi}(\mathbf{s},x)\big)\,\pi_{\theta_{\mathrm{d}}}(\mathbf{s},x)+r_{\phi}(\mathbf{s},x)\,\pi_{\theta_{\mathrm{c}}}(\mathbf{s},x).

(1)

Optimization objective.

The objective of Hera is to maximize operational efficiency by minimizing cloud offloading, while maintaining task performance competitive with a cloud-only baseline.
We formulate the optimization of device–cloud router
\phi
as follows:

\displaystyle\min_{\phi}

\displaystyle\mathbb{E}_{x\sim p(X),\,\tau\sim\pi_{\theta_{\mathrm{mix}}}}\Bigg[\sum_{t=1}^{T}r_{\phi}(\mathbf{s}_{t},x)\Bigg]

(2)

\displaystyle\text{s.t.}

\displaystyle\mathbb{E}_{x\sim p(X),\,\tau\sim\pi_{\theta_{\mathrm{mix}}}}\big[R(\tau)\big]\geq\mathbb{E}_{x\sim p(X),\,\tau\sim\pi_{\theta_{\mathrm{c}}}}\big[R(\tau)\big].

where
\pi_{\theta_{\mathrm{mix}}}=\big(1-r_{\phi}(\mathbf{s},x)\big)\,\pi_{\theta_{\mathrm{d}}}+r_{\phi}(\mathbf{s},x)\,\pi_{\theta_{\mathrm{c}}}
is the collaborative policy controlled by
\phi
.

4
Do We Need the Cloud LLM for Every Step?

This section presents an in-depth investigation of the performance gap between device and cloud LLM agents on long-horizon tasks.
We use Qwen2.5-7B-Instruct
(
44
)
as the device model and its closed-source counterpart Qwen-Max
(
23
)
as the cloud model, representing a resource-efficient model for local deployment and a compute-intensive, state-of-the-art oracle, respectively.
We evaluate them on two demanding long-horizon agent benchmarks: ALFWorld
(
30
)
, which focuses on embodied household task completion, and WebShop
(
46
)
, which requires multi-step e-commerce navigation and decision-making.
More experimental details are shown in §
6.1
and Appendix
C
.

Individually, device and cloud LLMs achieve success rates of 48.6% (3.8%) and 90.9% (35.6%) on ALFWorld (WebShop), respectively, revealing a substantial
task-level
performance gap.
However, not all steps in device-failed trajectories require cloud intervention.
As shown in Figure
2(a)
, for tasks where the device fails but the cloud succeeds, we replay the cloud trajectory on the device by providing the same state at each step, and find that 34.9% (39.3%) of steps produce identical outputs on ALFWorld (WebShop).

This suggests that an ideal step-level device–cloud agent router would need to invoke the cloud on
<
25% of steps to match cloud-only task success.

We further analyze device–cloud step-level agreement across multiple dimensions, including trajectory position, reasoning length, and predictive entropy.
Figure
2(b)
shows the step match rate across trajectory positions (up to 50 steps for ALFWorld and 20 for WebShop).
Notably, the match rate varies with step index rather than remaining stable, reflecting heterogeneous task structure and stage-dependent reasoning difficulty.
For instance, in ALFWorld, early steps primarily involve environment exploration, while intermediate stages require more complex planning and long-horizon reasoning, leading to increased device–cloud divergence. Case studies are provided later to further illustrate these patterns.

Figures

and

quantify the relationship between device–cloud step-level agreement and action difficulty from the perspectives of reasoning length and predictive entropy, respectively.
Reasoning length reflects the depth of deliberation required at each step, while sequence-level predictive entropy captures model uncertainty and is computed as the average token-level entropy:

H(\mathbf{a}_{t})=-\frac{1}{n}\sum_{i=1}^{n}\sum_{v\in\mathcal{V}}p_{\theta}(v\mid y_{<i},\mathbf{s}_{t},x)\log p_{\theta}(v\mid y_{<i},\mathbf{s}_{t},x),

(3)

where
\mathbf{a}_{t}=(y_{1},\dots,y_{n})\in\mathcal{V}^{n}
is the generated action sequence at step
t
, and
y_{<i}=(y_{1},\dots,y_{i-1})
denotes the token prefix.
The results show that steps with consistent device–cloud outputs are, on average, 13.8 tokens shorter than mismatched ones, indicating a lower required reasoning depth (i.e., more direct and simpler).
Interestingly, the device–cloud reasoning-length gap differs markedly across the two benchmarks.
On ALFWorld, the structured environment and limited action space allow the device model to act more directly, though often without capturing deeper dependencies handled by the cloud. In contrast, WebShop presents a large, unstructured action space—e.g., free-form queries and diverse attribute parsing—causing the weaker device model to produce more verbose deliberation, while the stronger cloud model remains more concise and efficient.
Beyond reasoning length, entropy also exhibits a clear separation: the device model is more uncertain on mismatched steps and more confident on those aligned with the cloud, suggesting that the need for cloud intervention is structured by step difficulty rather than random chance.
Moreover, entropy exhibits a similar benchmark-dependent pattern: cloud interventions reduce device entropy on ALFWorld, indicating stronger alignment with device reasoning, but increase it on WebShop, where cloud decisions more often fall outside the device model’s familiar decision regime.

Figure
2(e)
shows examples of device–cloud step-level agreement, with more cases and analysis provided in Appendix
D
.
While the device agent can handle many routine follow-up actions, its gap from the cloud agent is concentrated in decisions requiring deeper context tracking, precise grounding, or complex constraint composition. Accurately identifying these steps could substantially reduce cloud calls while preserving task success, highlighting the promise of step-level coordination.

5
Hera: A Long-Horizon Device–Cloud LLM Agent Coordinator

This section presents Hera, a step-level device–cloud agent coordinator that optimizes Eq.
2
to maximize task performance while minimizing cloud reliance.
Hera consists of a 500M-parameter decoder-only Transformer with a binary classification head to route between device agent
\pi_{\theta_{\mathrm{d}}}
and cloud agent
\pi_{\theta_{\mathrm{c}}}
. The training of Hera follows a two-stage pipeline (pseudocode in Appendix
B
):
a cold-start phase with imitation learning
, followed by
a refinement phase with reinforcement learning
, ultimately enabling effective performance–cost co-optimization in device–cloud LLM agent systems.

5.1
Cold Start with Imitation Learning

To equip Hera (the coordinator
r_{\phi}
in §
3
) with initial routing capability, we first employ a cold-start imitation learning (IL) phase. The objective in this stage is to transform the discrete routing decision into a supervised classification problem by identifying the capability gap between device and cloud models across long-horizon trajectories.
For each task
x
, we begin by rolling out both device-side
\pi_{\theta_{\mathrm{d}}}
and cloud-side
\pi_{\theta_{\mathrm{c}}}
to collect trajectories
\tau_{\mathrm{d}}(x)
and
\tau_{\mathrm{c}}(x)
, respectively.
Tasks exhibiting the pronounced device–cloud performance gaps are then selected as:

X_{\text{diff}}=\left\{x\;\middle|\;R(\tau_{\mathrm{c}}(x))-R(\tau_{\mathrm{d}}(x))>\delta\right\},

(4)

where
\delta
serves as a prescribed margin of sub-optimality. This set delineates a regime where cloud assistance is fundamentally necessary.

Using
X_{\text{diff}}
, we construct step-level supervision signals for
r_{\phi}
by using cloud trajectories as an oracle reference, which provide guidance on states where
\pi_{\theta_{\mathrm{d}}}
and
\pi_{\theta_{\mathrm{c}}}
exhibit discrepancies.
Specifically, for each
x\in X_{\text{diff}}
, we take cloud rollout

\tau_{\mathrm{c}}(x)=\{({\mathbf{s}}^{\mathrm{c}}_{t},{\mathbf{a}}_{t}^{\mathrm{c}})\}_{t=1}^{T}
, and feed each
({\mathbf{s}}^{\mathrm{c}}_{t},x)
into
\pi_{\theta_{\mathrm{d}}}
to get the corresponding action

{\mathbf{a}}_{t}^{\mathrm{e}}\sim\pi_{\theta_{\mathrm{d}}}(\cdot\mid{\mathbf{s}}^{\mathrm{c}}_{t},x)
.
We define a step-level consistency indicator as
y_{t}=1-\mathbb{I}\big[{\mathbf{a}}_{t}^{\mathrm{e}}={\mathbf{a}}_{t}^{\mathrm{c}}\big]
, where
y_{t}=1
indicates that
\pi_{\theta_{\mathrm{d}}}
output disagrees with the cloud oracle and current state should be routed to
\pi_{\theta_{\mathrm{c}}}
, while
y_{t}=0
means
\pi_{\theta_{\mathrm{d}}}
is sufficient for local execution.

Based on this, we construct a cold-start IL dataset for the
r_{\phi}
:

\mathcal{D}_{\mathrm{IL}}=\left\{({\mathbf{s}}_{t},x,y_{t})\;\middle|\;x\in X_{\text{diff}},\ ({\mathbf{s}}_{t},{\mathbf{a}}_{t}^{\mathrm{c}})\in\tau_{\mathrm{c}}(x)\right\}.

(5)

The coordinator
r_{\phi}
is then trained as a binary classifier on
\mathcal{D}_{\mathrm{IL}}
with input
({\mathbf{s}}_{t},x)
and label
y_{t}
(as defined in §
3
) using a binary cross-entropy (BCE) loss:

\mathcal{L}_{\text{IL}}(\phi)=-\frac{1}{|\mathcal{D}_{\text{IL}}|}\sum_{(\mathbf{s}_{t},x,y_{t})\in\mathcal{D}_{\text{IL}}}\left[y_{t}\log p_{\phi}(\mathbf{s}_{t},x)+(1-y_{t})\log\big(1-p_{\phi}(\mathbf{s}_{t},x)\big)\right],

(6)

where
p_{\phi}(\mathbf{s},x)\in(0,1)
denotes the Bernoulli parameter of routing policy
r_{\phi}(\mathbf{s},x)
.
This cold-start IL phase aligns the coordinator’s latent space with the agents’ performance differential, providing a stable policy initialization that significantly accelerates the subsequent RL phase.

5.2
Cost-Aware Reinforcement Learning with State Grouping

The IL phase provides a strong initialization but relies on a proxy objective and does not directly optimize Eq.
2
. We then refine Hera with reinforcement learning (RL)
1
1

1

We use trajectory return and cost as reinforcement signals, but optimize the router through induced step-level classification targets rather than direct policy gradients.
, jointly maximizing end-to-end task success while minimizing step-level cloud invocations.
We deploy device agent
\pi_{\theta_{\mathrm{d}}}
and cloud agent
\pi_{\theta_{\mathrm{c}}}
, together with router
r_{\phi}
trained in the preceding IL stage, into the environment and collect
N
trajectories for each task
x
from the same initial state.
To induce sufficient exploration, we sample routing decisions from a temperature-scaled Bernoulli distribution parameterized by the router’s binary head.
Concretely, at step
t
the router
r_{\phi}
outputs a logit
\ell_{\phi}(\mathbf{s}_{t},x)
, and we form:

p_{t}^{(\gamma)}\;=\;\sigma\!\left(\ell_{\phi}(\mathbf{s}_{t},x)/\gamma\right),\qquad r_{\phi}(\mathbf{s}_{t},x)\sim\mathrm{Bernoulli}\!\left(p_{t}^{(\gamma)}\right),

(7)

where temperature
\gamma>0
(larger
\gamma
increases stochasticity).
This yields
N
trajectories
\{\tau_{i}\}_{i=1}^{N}
, where each is defined as

\tau_{i}=\{(\mathbf{s}_{1}^{(i)},\hat{\mathbf{a}}_{1}^{(i)},r_{1}^{(i)}),(\mathbf{s}_{2}^{(i)},\hat{\mathbf{a}}_{2}^{(i)},r_{2}^{(i)}),\dots,(\mathbf{s}_{T}^{(i)},\hat{\mathbf{a}}_{T}^{(i)},r_{T}^{(i)})\}
. All trajectories share the same initial state, i.e.,
\mathbf{s}_{1}^{(1)}=\mathbf{s}_{1}^{(2)}=,\cdots,=\mathbf{s}_{1}^{(N)}
.

We then group identical states to derive step-level learning signals.
Let
\mathcal{G}(x)
denote the set of distinct states encountered across the
N
trajectories.
For each grouped state
\mathbf{s}\in\mathcal{G}(x)
, we collect all its occurrences

\mathcal{J}(\mathbf{s})\coloneqq\{\,(i,t)\mid\mathbf{s}^{(i)}_{t}=\mathbf{s}\,\},

which enumerates every visit to
\mathbf{s}
.
For each
\mathbf{s}\in\mathcal{G}(x)
, we estimate two quantities conditioned on the routing decision:
(1) the expected trajectory return, and
(2) the expected future cloud reliance.
Specifically, we compute decision-conditioned averages by restricting
r_{\phi}({\mathbf{s}}_{t}^{(i)},x)=d
:

\displaystyle\widehat{R}(d;\mathbf{s})

\displaystyle:=\frac{1}{\sum_{(i,t)\in\mathcal{J}(\mathbf{s})}\mathbb{I}[r_{\phi}({\mathbf{s}}_{t}^{(i)},x)=d]}\sum_{(i,t)\in\mathcal{J}(\mathbf{s})}\mathbb{I}[r_{\phi}({\mathbf{s}}_{t}^{(i)},x)=d]\;R(\tau_{i}),

(8)

\displaystyle\widehat{C}(d;\mathbf{s})

\displaystyle:=\frac{1}{\sum_{(i,t)\in\mathcal{J}(\mathbf{s})}\mathbb{I}[r_{\phi}({\mathbf{s}}_{t}^{(i)},x)=d]}\sum_{(i,t)\in\mathcal{J}(\mathbf{s})}\mathbb{I}[r_{\phi}({\mathbf{s}}_{t}^{(i)},x)=d]\;C_{i,t},

(9)

for
d\in\{0,1\}
, where
d=0
routes to
\pi_{\theta_{\mathrm{d}}}
and
d=1
routes to
\pi_{\theta_{\mathrm{c}}}
.
Here,
\widehat{R}(d;\mathbf{s})
estimates the expected trajectory return, and
\widehat{C}(d;\mathbf{s})
estimates the expected remaining cloud calls (including the current step), where

C_{i,t}:=\sum_{t^{\prime}=t}^{T}\mathbb{I}\!\left[r_{\phi}({\mathbf{s}}_{t^{\prime}}^{(i)},x)=1\right]
.

We use above estimates to derive a cost-aware routing rule for step-level supervision.
For each
\mathbf{s}\in\mathcal{G}(x)
, we define a preference label
y(\mathbf{s})\in\{0,1\}
by selecting the decision with higher estimated return, and breaking near-ties by lower expected cloud usage.
Formally, with a margin
\epsilon>0
:

y(\mathbf{s}):=\begin{cases}1,&\widehat{R}(1;\mathbf{s})-\widehat{R}(0;\mathbf{s})>\epsilon,\\
0,&\widehat{R}(0;\mathbf{s})-\widehat{R}(1;\mathbf{s})>\epsilon,\\
\arg\min\limits_{d\in\{0,1\}}\widehat{C}(d;\mathbf{s}),&\text{otherwise}.\end{cases}

(10)

Here,
\epsilon
controls the performance–cost trade-off:
\epsilon\!\to\!0
favors higher
\widehat{R}
, while
\epsilon\!\to\!+\infty
favors lower
\widehat{C}
.
In each RL iteration, we roll out
N
trajectories and construct training set
\mathcal{D}_{\mathrm{RL}}=\{(\mathbf{s},x,y(\mathbf{s}))\mid\mathbf{s}\in\mathcal{G}(x)\}
, and update
r_{\phi}
by minimizing the BCE loss over
\mathcal{D}_{\mathrm{RL}}
:

\mathcal{L}_{\mathrm{RL}}(\phi)=-\frac{1}{|\mathcal{D}_{\mathrm{RL}}|}\sum_{(\mathbf{s},x,y)\in\mathcal{D}_{\mathrm{RL}}}\left[y\log p_{\phi}(\mathbf{s},x)+(1-y)\log\big(1-p_{\phi}(\mathbf{s},x)\big)\right]+\beta\,\|\phi-\phi_{\mathrm{IL}}\|_{2}^{2},

(11)

where
\phi_{\mathrm{IL}}
is the frozen router parameters obtained at the end of the imitation learning stage, and
\beta
controls the regularization strength. This regularization stabilizes RL refinement by preventing Hera from drifting excessively far from the well-initialized IL stage.

In general, the IL stage provides Hera with a strong device–cloud coordination prior, and RL refines it into a cost-aware routing policy that directly optimizes task success under limited cloud usage. Together, Hera achieves effective success–cost co-optimization in device–cloud LLM agent systems.

Experiment

We conduct comprehensive evaluations of Hera across diverse agentic tasks to show:
(1) the strong device–cloud coordination capability of Hera for an optimal performance–cost trade-off;
(2) the contribution of each training stage through ablation studies;
(3) microbenchmarks, including cloud offloading rate, compute overhead, and analyses of routing patterns.

Benchmarks.

WebShop is a web-based benchmark for LLM agents on realistic shopping tasks, featuring over 1.1M products and 12k user instructions in a large, diverse action space.
AppWorld is a high-fidelity multi-app environment with 9 daily apps and 457 APIs, offering 750 interactive coding-centric agent tasks with robust programmatic evaluation via state- and execution-based unit tests.

Baselines.

We compare Hera with a range of competitive baselines:

The device-side agent yields the smallest latency but the lowest success rates.

This gain is mainly attributed to the RL stage, whose end-to-end trajectory-level success–cost optimization enables Hera to learn not only state-wise routing decisions but also their interdependence across consecutive steps, ultimately yielding more precise and cost-effective device–cloud coordination.

7
Conclusions

This paper proposes Hera, a step-level device–cloud LLM agent coordinator for long-horizon tasks. Specifically, Hera accurately identifies whether cloud assistance is needed at each interaction state, thus enabling effective task execution with minimal cloud invocations. Hera adopts a two-stage training paradigm. First, we perform cold-start imitation learning by replaying the device agent on cloud trajectories and using step-level action consistency as supervision, providing Hera with an initial device–cloud routing capability.
Next, we refine Hera via cost-aware reinforcement learning: across multiple rollouts, we group identical states and generate step-level preferences that favor higher return and, when comparable, fewer future cloud calls, thereby explicitly co-optimizing success and cost.
Extensive experiments on ALFWorld, WebShop, and AppWorld demonstrate that Hera consistently outperforms state-of-the-art baselines while invoking the cloud agent in only 46.3% of steps and achieving 92.5% of cloud-only success.
We present the broader impact of Hera in Appendix
A
, and discuss the limitations of Hera and directions for future research in Appendix
E
.

Appendix A
Broader Impacts

This work introduces Hera as the first step-level device–cloud coordinator for LLM agents, marking a pivotal shift from coarse, task-level routing to fine-grained, dynamic collaboration. By demonstrating that only a small fraction of critical steps require cloud intervention, Hera significantly lowers the computational and financial barriers to deploying sophisticated agents on user devices. This efficiency democratizes access to advanced agentic capabilities, enabling real-time, latency-sensitive applications—such as autonomous robotic control and interactive assistants—to operate reliably on device hardware without prohibitive costs.

Amid the explosive growth of LLM agents, artificial intelligence is undergoing a fundamental paradigm shift from static, single-turn queries to long-horizon autonomous interaction, where agents must sustain coherent reasoning over extended, dynamic trajectories. We believe Hera is essential for realizing scalable, sustainable, and ubiquitous autonomous agents in real-world applications by establishing a strong performance–cost Pareto frontier for this complex mode of operation.

C.2
Details of Experimental Settings

For ALFWorld benchamrks ,we use a maximum prompt length of 2048 tokens and a maximum response length of 512 tokens.
Each episode is capped at 50 environment interaction steps, counting both device- and cloud-executed actions.
In WebShop, the prompt length is capped at 4096 tokens and the response length at 1024 tokens. Each episode terminates after 20 interaction steps.
In AppWorld, we set the maximum prompt length to 4096 tokens, the maximum response length to 1024 tokens, and the maximum number of steps to 50.
At each execution step, the agent is given access to a bounded history window. The number of visible historical steps is set to 50, 15, and 5 for the three datasets, respectively.
To evaluate request-level baselines in long-horizon agent settings, we apply them independently at each interaction step. Specifically, at step
t
, each baseline receives the same per-step context as Hera —task instruction, current observation, and truncated history—and outputs a binary decision for routing the current step to either the device or the cloud model.

The definition of an identical state in the RL training stage depends on the benchmark-specific environment representation. In ALFWorld, two states are considered identical if they correspond to the same textual environment observation and admissible action set. In WebShop, two states are considered identical if they have the same webpage observation, including the current page content and available actions. In AppWorld, two states are considered identical if they produce the same execution observation returned by the Python environment under the same task context.

For device-side model deployment, we run the open-source MNN engine
(
10
)
on a single NVIDIA RTX 4090 GPU using BF16 precision. Cloud-side closed-source models are invoked exclusively through their official APIs. All training experiments are performed on 2 NVIDIA H100 GPUs. Unless otherwise specified, the imitation learning and reinforcement learning phases are run for 30 and 50 iterations, respectively. C.4
Effect of Hyperparameters

We investigate the sensitivity of Hera to the hyperparameter
\epsilon
and
\beta
.
\epsilon
governs the trade-off between task success and cloud cost in the RL stage: a small
\epsilon
(e.g., 0) prioritizes success but incurs excessive cloud usage, while a large
\epsilon
(e.g., 0.3) overly restricts offloading, leading to performance degradation. Similarly,
\beta
stabilizes RL updates against the IL initialization; removing regularization (
\beta=0
) causes policy drift, whereas excessive regularization (
\beta
=0.3) hinders adaptation to RL objectives.
Empirical results in Table
4
indicate that the optimal configuration (
\epsilon=0.05
,
\beta=0.1
) effectively balances these dynamics, allowing Hera to refine the IL prior into a robust, cost-efficient routing policy. This demonstrates that our design successfully leverages moderate regularization to prevent catastrophic forgetting while utilizing a fine-grained preference margin to identify critical states for cloud intervention, ensuring superior co-optimization of accuracy and efficiency.

AppWorld

In AppWorld tasks, Hera exploits the cloud mainly when stronger code synthesis is needed. While the device can handle API inspection, Step 8 requires composing state checks, branching, API calls, and task termination into an executable loop. The cloud produces this complete control logic, whereas the device only extracts an intermediate variable. This highlights Hera ’s ability to reserve cloud usage for execution-critical programming steps.

Appendix E
Limitations and Future Work

Limitations

By studying fine-grained, step-level device–cloud coordination for long-horizon agents, Hera improves efficiency and establishes a favorable performance–cost Pareto frontier. However, several limitations remain. First, Hera assumes a synchronous, always-connected setting with reliable low-latency communication between device and cloud, and does not account for asynchronous execution or intermittent connectivity, which may limit robustness in mobile or remote environments. Second, Hera does not incorporate built-in privacy-preserving mechanisms for offloaded data. Although it reduces the frequency of cloud calls, it does not sanitize transmitted context, which may restrict deployment in privacy-sensitive domains such as healthcare or finance. Third, our study focuses on a binary single-device–single-cloud topology. As a result, Hera does not address routing and coordination in more complex multi-agent settings, such as systems with multiple edge devices, specialized services, or hierarchical cloud infrastructure, where coordination overhead can scale non-linearly.

Future Directions.

To address these limitations, we outline several directions for future research in device–cloud collaboration for LLM agents. Building on Hera, we hope to further broaden the applicability, robustness, and scalability of step-level coordination, ultimately enabling more reliable and efficient autonomous systems in real-world environments. Future systems should move beyond the assumption of stable synchronous interaction and explicitly reason about latency, communication uncertainty, and temporary disconnection, allowing adaptive execution under weaker connectivity. It is also important to improve the safety of offloading itself. Incorporating privacy-aware representations, controllable context abstraction, or secure transmission and computation mechanisms would make such frameworks more suitable for domains where sensitive information cannot be directly shared with external providers. More broadly, the current setting opens up opportunities to study coordination at larger system scales. Extending beyond single-device–single-cloud topology toward heterogeneous networks of edge devices, specialized services, and hierarchical cloud resources will require new methods for routing, scheduling, and distributed planning, particularly when workflow dependencies and coordination costs grow rapidly with system size.
