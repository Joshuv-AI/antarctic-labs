 ABSTRACT
 This report summarizes FY26 work to develop Maggie, an artificial intelligence-based
assistant designed to support software model generation and validation activities for fast reactor
analysis codes. The project established a modular, code-agnostic software architecture that
separates reusable agent capabilities from code-specific knowledge and tools, with initial
implementation focused on the FRP-supported fast reactor safety analysis code SAS4A/SASSYS-
1 (SAS). A curated SAS-specific knowledge base was assembled from the code manual, training
materials, historical analysis reports, and representative input files, and was integrated through
retrieval-augmented generation to ground Maggie’s responses in authoritative sources. Maggie
was deployed on the internal Argonne network, where it demonstrated practical user-facing
capability as a chatbot for answering natural language questions about SAS and retrieving relevant
technical information. Demonstration cases also showed that Maggie can generate useful snippets
of SAS input for selected modeling tasks, while highlighting current limitations in reliability and
consistency for more complex input generation tasks. Overall, the FY26 effort established the
technical foundation for an AI-assisted capability intended to improve the efficiency, consistency,
and accessibility of fast reactor software model development at Argonne and, with further
improvements, to support eventual use by the broader fast reactor community, including industry
users of FRP-supported analysis tools.

1 Introduction
 The objective of this project is to develop an AI-based assistant that helps users create software
input files for fast reactor modeling and simulation, with a focus on code validation activities.
High-quality validation work requires building many simulation cases by translating
specifications, experimental data, and analyst expertise into detailed code input files. This process
is time consuming, repetitive, and prone to human error, particularly for complex analysis tools.
By automating part of this work, the goal is to reduce the time and effort required to prepare
validation cases, improve consistency across inputs, and enable analysts to focus more on technical
interpretation and less on manual file construction.
 The AI-based assistant developed under this project is named Maggie, inspired by the Latin
word magister, meaning “teacher.” Maggie’s name reflects that it is being designed to support
users step by step, helping them understand what information is needed, how inputs are organized,
and how modeling choices are translated into structured software inputs. This guidance-oriented
approach is important because fast reactor analysis codes require substantial expertise to use
effectively, and users must understand and evaluate the basis for their models. The modeling
process cannot be treated as a black box; analysts need visibility into how inputs were developed
and what choices and assumptions were made. Much of the expertise needed to construct these
files resides in documentation, examples, and the experience of code developers and expert
analysts. By capturing and organizing this knowledge within an AI-based assistant, the project
aims to create a practical knowledge transfer tool that improves accessibility for a broader user
community while preserving the benefit of expert practices.
 This project builds on experience gained from a previous effort, Dr. Metal, a chatbot developed
to allow users to query the Metallic Fuels Irradiation and Physics Database (FIPD) using natural
language. Dr. Metal demonstrated the value of combining large language model (LLM)
capabilities with a structured software framework to make specialized technical information more
accessible to users. From a software development perspective, that project provided a useful
starting point for this effort, including the approach to use the open-source Python packages
LangChain and LangGraph [1, 2], together with internal Argonne-hosted Application
Programming Interface (API) gateways for LLMs. At the same time, Maggie’s objectives are
broader and more technically demanding than the previous effort. In addition to retrieving and
summarizing information, Maggie must help generate technically correct software inputs, guide
users through input development, and support multiple nuclear analysis codes with different
structures, conventions, and requirements. This has required development of a more general agent
framework tailored to engineering input creation.

 1

 This report summarizes FY26 work that has involved the development of a modular, code-
agnostic software architecture that can support the addition of multiple reactor analysis tools over
time. This architecture separates general agent capabilities from code-specific knowledge and
utilities. Under this approach, the core framework is reusable, while individual modules can be
added to support the syntax, workflows, and domain requirements of specific codes. As an initial
demonstration of this framework, the project has focused on implementing and testing code-
specific tools for SAS4A/SASSYS-1 (SAS) [3]. Starting with one code allows the project to
establish the overall architecture, identify the technical challenges associated with generating
structured input, and lay the groundwork for future extension to additional codes. In this way, the
FY26 effort establishes both the technical foundation for Maggie and the path toward a broader,
user-facing capability for AI-assisted input development.

2 Knowledge Base
 General-purpose LLMs, such as ChatGPT or Claude, are useful for language understanding
and interaction, but they do not inherently contain the detailed, code-specific knowledge needed
for reactor modeling and simulation. Maggie must draw on authoritative sources such as code
documentation, prior modeling and validation studies, and historical input files to provide
responses that are technically grounded and traceable. For this reason, the project uses an approach
commonly referred to as retrieval-augmented generation in which Maggie can search a curated
collection of reference material to use when responding to the user.
 FY26 work focused on demonstrating Maggie’s capability to support validation for the FRP-
supported SAS code. SAS is a systems-level safety analysis code developed at Argonne for
simulating the behavior of liquid metal cooled fast reactors during normal operation, transients,
and accident scenarios. The code couples reactor kinetics, thermal-hydraulics, heat transfer, and
plant control and protection system models to predict the transient response of the reactor core and
heat transport systems. SAS has been used for licensing support, safety evaluation, and design
studies of fast reactor systems of several historical sodium-cooled fast reactor (SFR) designs and
is currently being used by multiple US industry organizations to support their licensing activities
for new SFR designs.
 A SAS-specific knowledge base was created consisting of the SAS code manual, a large set of
historical modeling and validation reports, and SAS input files corresponding to those reports.
Together, these materials provide documentation and examples of how the code has been applied
in practice. The knowledge base is stored on Box so it can be maintained and expanded as
additional materials become available. To support access control, documents are organized by
folder naming convention into Public and Private collections.

 2.1 Content of the Knowledge Base
 A wide variety of materials covering several decades of modeling and simulation activities was
compiled for the SAS-specific knowledge base. Descriptive text files are included throughout the
file structure of the knowledge base summarizing the contents of each directory to better enable
Maggie to quickly identify files related to a given inquiry. There are two main categories of
materials in the knowledge base: informational files related to code usage and examples from
actual applications of the code for analysis of reactors. Files in the knowledge base related to code
usage include the SAS code manual, SAS training materials, and materials related to the code’s
software quality assurance (SQA) program.
 The SAS code manual documents all aspects of the code. It includes a general overview of the
code, a user’s guide with documentation of every input parameter, and detailed descriptions of all
models available in the code. The model descriptions cover the detailed formulations from which
the models in the code were built, the various options for each model, and general usage
considerations. While the SAS code manual is approximately 2000 pages long in document format,
it is well organized with a logical structure and includes plentiful references throughout to relevant
sections elsewhere in the manual. It is easily navigable and digestible to both users and Maggie,
and is the single most important resource included in Maggie’s knowledge base.

 3

 Materials from the annual SAS training program that are included in the SAS knowledge base
include presentations from each session, input examples, and hands-on training materials from the
three-day training session. The annual SAS training program includes content for both new and
experienced users. The training materials are thus extremely valuable for developing functional
knowledge for broad swaths of the code’s capabilities.
 Materials in the knowledge base from the SQA program include the SAS Acceptance Testing
Report (ATR) [4]. This report documents the suite of functionality tests created by the
development team to assess the specific capabilities and algorithms of the code and the ranges of
validity for critical input parameters. The test suite includes nearly 300 cases. For each case, the
ATR documents the problem definition, analytical solution(s), computational solution(s),
acceptance criteria, comparisons of the analytical and computational solutions, and determination
of acceptance of the computational solution(s). The SAS input files for each test and other files
used to determine pass and fail statuses are also included in the knowledge base. Inclusion of these
materials provides context to Maggie as to what inputs and modeling considerations affect which
simulation outcomes.
 The second category of materials in the SAS-specific knowledge base is example models and
accompanying documents that were developed during Argonne’s application of SAS for safety
analyses, benchmarking and validation efforts, and various design support activities for both real-
world and conceptual reactor designs. The files in this category were compiled from analyses
carried out over the past two-plus decades for 12 different reactor designs.
 Directories for each reactor design include the SAS models with input files for the postulated
transients it was used to simulate. In some cases, inputs for more than a dozen different transients
are included in the model directory for a design, for example protected and unprotected versions
of station blackouts, transient overpowers, loss of heat sinks, pump overspeeds, pump coastdown
failure events, and more. There are SAS input files representing more than one hundred different
transient cases in this part of the knowledge base. Twenty-two major reports for the associated
projects are also included in the knowledge base. These reports summarize how the models were
built and give extensive analysis of simulation results. For several models, reports were written to
fully document the calculation of every parameter in the model. These are also included in the
knowledge base when available and are a tremendous resource for Maggie.
 The directories for each reactor design also include supplemental Excel spreadsheets, Mathcad
files, and other files that were used to build the models and Excel spreadsheets containing
measured data from experiments performed at the real-world facility. Maggie currently does not
read the contents of spreadsheets and Mathcad files in the knowledge base, but they have been
assembled to support future work.
 Materials in the SAS model section of the knowledge base are separated into Private and Public
collections. Private materials are restricted if they contain data that is proprietary, export
controlled, or controlled unclassified information, or if they are being used for ongoing
collaborations that necessitate withholding their release until a project’s completion. The
remaining materials in this section are labeled Public.

 4

 Materials in the SAS model section of the knowledge base are further categorized based on
whether they were developed for modeling and analysis of reactors that were designed, built, and
operated or reactors that were designed but never built. The former includes reactors like EBR-II
and FFTF while the latter includes conceptual designs such as ABTR and VTR [5-8]. The key
distinction is the availability of measured data against which SAS simulation results can be
evaluated. For the models of real-world reactors, there is a massive amount of experimentally
measured data from testing programs performed at those reactors that has been used to validate
SAS’s capability to accurately predict transient system responses during accident scenarios.
Modeling of these reactors has tended to focus on simulation of the tests that were performed at
those facilities. Conversely, much of the modeling for the conceptual reactor designs was
performed to support the design process. The modeling for these reactors often covered a wider
range of postulated scenarios and many of the models include prototypic features and components
utilized in current designs.

 2.2 Conversion to Vector Database
 To make the knowledge base useful to Maggie, the document collection is converted into a
vector database. A vector database helps the system find information that is similar in meaning,
even if it does not use the exact same words. This is important for this type of technical material,
where the same idea may be described in different ways across manuals, reports, and input files.
 To support continued growth of the knowledge base and the creation of additional code-
specific knowledge bases in the future, a script was developed that performs this conversion
process. Text is extracted from the documents, divided into smaller sections, and converted into
numerical representations that capture meaning. These representations are then stored in the vector
database. When Maggie receives a user question or request, the system compares the meaning of
the request to the stored document sections and returns the most relevant results. For example, a
search for “pump coastdown” would also find passages discussing “loss-of-flow timing,” even if
the exact words are different. The vector database helps Maggie retrieve relevant information from
the knowledge base and use it to provide guidance to the user.

3 Software Design
 Maggie was designed from the start to have knowledge of more than a single nuclear analysis
code. Although the software currently only supports SAS, its internal structure cleanly separates
the general-purpose machinery (which works for any code) from the code-specific content (the
manuals, examples, rules, and reference files that apply only to SAS). Adding support for a new
code in the future is largely a matter of supplying that code’s content in a few well-defined places.
This “framework plus plug-in” philosophy is visible throughout the design. The implementation
uses the open-source Python software packages LangChain and LangGraph, which provide
building blocks for connecting LLMs to external information sources, tools, and step-by-step
workflows.
 The software is kept in a remote, Argonne-hosted Git version-control repository, which allows
the development team to collaborate, track every change over time, and access the latest version
from anywhere on the lab network. The repository also includes written documentation describing
how to install and run the tool.
 Once installed, the software can be started up from the command line using:
 $ ai-builder

 Maggie will then prompt the user asking which code they want support for; currently the only
option is SAS. Alternately, the user can provide the name of the code as a command line argument
to skip the interactive question:
 $ ai-builder –-code SAS

 By default, Maggie starts up with only a subset of its tools (see Section 3.3) that give it access
to the public knowledge base. This configuration is appropriate for deployed versions of Maggie
that are made available to internal Argonne users. In these versions, there is currently no
differentiation of access level. Developers (who are each individually given access to the Git
repository) can load tools which give Maggie access to the private knowledge base by starting up
the software using the following command:
 $ ai-builder –-private

 In future work, user authentication with different access levels can be added to determine
whether access to the private knowledge base is appropriate for each specific user.
 The following sections describe key pieces of the software architecture.

 3.1 System Prompt
 The system prompt is the set of instructions Maggie reads before it does any work and serves
as a job description and rulebook. In keeping with the modular design philosophy, the system
prompt is split into two parts that are combined automatically each time the software runs:
 • Generic content applies to every code the agent might support. It establishes good general
 behavior; for example, instructing the agent to plan before it writes, to rely on the provided
 knowledge base rather than its own general knowledge, to avoid inventing information it
 cannot confirm, and to validate its work before presenting it.
 • Code-specific content applies only to the selected code. For SAS, this part supplies “few-
 shot” examples – a handful of examples that show an AI agent how it should respond before
 it tries a new, similar task. These are complete, real SAS input files the agent can pattern
 itself after. The code-specific content also describes SAS-specific guidance and formatting
 rules through a series of individual prompts.
 SAS-specific prompts were drafted in parallel with testing performed as the agent was
developed. Maggie was presented with a range of modeling questions and requests, many
repeatedly over the course of the development process and often several times in a row, to gauge
the accuracy and consistency of its responses. Prompts were engineered to correct errors or
mistakes regularly observed in Maggie’s responses and to improve consistency of its responses.
 Maggie is currently provided with 18 sets of code-specific prompts. Some prompt sets are very
simple, while others include a few dozen simple rules and/or examples to clearly define how a
given modeling aspect should be performed. While many prompts fit into more than one category,
the SAS-specific prompts can roughly be categorized as 5 sets on general information, 3 sets on
establishing guidelines for Maggie’s responses, 5 sets on error checking and auditing of written
SAS input, 2 sets on input formatting, and 3 sets on modeling best practices. The modeling best
practices prompts were necessary either because Maggie occasionally made assumptions about
information not explicitly stated in the manual or other sources in the knowledge base, or in cases
where older examples in the knowledge base were written before inline and intra-block comments
were added to SAS, making them poorly formatted examples compared to recently developed
models. Such models remain in the knowledge base because they demonstrate modeling features
or components that are not included in the more recent examples.
 The following are examples of general information prompts given to the agent to guide what
resources it consults before responding to user inquiries:
 [Topic: The code manual]
 - Always consult the SAS4A/SASSYS-1 code manual when users ask questions about
 the code.

 [Topic: Repository of models]
 - You have a large repository of models available to reference. For simple
 modeling questions, always refer to the VTR SAS4A/SASSYS-1 model, the ABTR
 SAS4A/SASSYS-1 model, and the models in the Test_Suite/5.8/TestSuite directory.

 7

Guiding Maggie to consult the most complete source of SAS information available (the code
manual), the SAS model used for training new code users (ABTR), a recent heavily reviewed
model used for published safety analyses (VTR), and a broad suite of models where new features
and components are implemented incrementally (the SQA Test Suite) predisposes the agent
towards reviewing what are often the best sources of information available to it.
 The SAS-specific prompt file includes rules geared towards ensuring Maggie always follows
the requirements for writing SAS input with accompanying examples to demonstrate correct and
incorrect application of those rules. The following is an excerpt from one prompt set designed to
prevent Maggie from skipping input locations in any fixed-formatted input it writes:

 [Rules and examples: Writing SAS4A/SASSYS-1 Input]
 - Always follow these rules when writing SAS4A/SASSYS-1 input:
 ...
 - Rule: When writing a fixed-format array data line, write only a contiguous
 block of known values beginning at `LOC`.
 - Rule: Each fixed-format array line must contain one uninterrupted sequence
 of known values only.
 - Begin at `LOC`.
 - Write consecutive known values only.
 - Stop before the first unknown.
 - Set `NUM` to the count of values actually written.
 - Never leave blanks or skip positions within a line.
 - If a value is unknown, end the line; resume later on a new line with the
 correct `LOC`.
 ...

`LOC` and `NUM` in the above excerpt are parameters specified on each fixed-formatted line of
input that inform the code which inputs are defined on the rest of the line and are related to the
rule that users may not skip input locations in a line of fixed-formatted input. While the rules
defining their usage are clearly written in the manual and training materials for a human user to
understand that skipping inputs is not allowed with fixed-formatted input, the agent could interpret
the rules in ways that a human user might not. This combined with input skipping being allowed
in free-formatted lines of input led to Maggie often assuming it was acceptable to skip inputs in
fixed-formatted input lines prior to these clarifying rules being added to the SAS-specific prompt
file. Many of the other prompts added to the SAS-specific file are similar to this in restating rules
that are sufficiently clear for a human user but in a clear and concise manner that are much harder
for the agent to misinterpret.

 8

 Beyond the guidance available in Maggie’s knowledge base and prompts guiding or
specifically prohibiting certain behaviors, Maggie was observed to continue occasionally making
certain mistakes. The final set of prompts in the SAS-specific prompt file are a third line of defense
to correct against repeatedly observed mistakes that establish rules for Maggie to perform specific
audits of any written input before presenting it to a user. In most instances, these self-checks catch
errors before they are presented to the user, and the agent then revises the input accordingly. Some
mistakes, however, could not be completely eliminated with this approach. Section 4.2.4 discusses
one such example and Section 4.3 discusses future effort that aims to eliminate these more
frequently observed mistakes.

 3.2 LLMs Used
 The intelligence behind Maggie comes from LLMs. A key requirement for this project is that
Argonne data stays internal. The agent does not send anything to public, external AI services.
Instead, it connects only to Argonne’s internal AI gateway (Argo API), so all prompts, reference
materials, and generated files remain within the internal lab environment. Maggie uses two models,
each chosen to fit its task:
 • A high capability model (GPT 5.4) does the main reasoning. This includes understanding
 the user’s request, planning, and drafting the input file.
 • A smaller, faster, lower-cost model (GPT 4.1 mini) handles the narrower, high-volume task
 of answering focused lookup questions against the code manual.
 Matching the model to the task keeps Maggie both capable and economical. The models can
be swapped or upgraded as better options become available on Argonne’s gateway, without
changes to the rest of the software.

 3.3 Tools
 On its own, an LLM can only write words. To do useful engineering work it needs “tools” –
specific capabilities it can call on, much like a person reaching for a reference book or a calculator.
Generally, the agent decides when each tool is needed, unless the workflow specifically requires
use of a tool at a certain step (see Section 3.4). Maggie currently has four tools:
 • A manual-expert helper. The complete SAS manual is loaded into the context of a
 dedicated helper LLM. The main agent can ask this helper plain-language questions and
 get answers grounded in the actual manual.
 • Manual variable look-up tools. Quick, exact lookups that translate between a variable’s
 name and its location in the input file, in either direction. This is useful for getting exact
 name and numerical memory locations correct.
 • Knowledge base search tools. The agent can search the knowledge base described in
 Section 2. The knowledge base is split into public and private sections. The private section
 (containing sensitive or proprietary information) is only made available when the tool is
 explicitly run in private mode, providing a clear boundary for protected material.
 • An input-file format validation tool. This tool checks a drafted input file for structural and
 formatting problems and reports any errors back in plain language.

 9

 3.4 Workflow
 Rather than letting the agent decide entirely on its own when it is “finished,” the agent follows
a simple, fixed workflow that guarantees every drafted input file is checked by the format
validation tool before it is shown to the user. The workflow is shown in Figure 1. Maggie reads
the user request and calls on its tools as needed to fulfill it. If in that process, it drafts SAS input,
it calls the format validation tool to inspect the draft. If the validation tool finds no errors, the file
is presented to the user. If it finds errors, the file and the list of problems are sent back to the agent
to correct, and the corrected draft is checked again. This correct-and-recheck loop repeats until the
file passes or a small retry limit (3 tries) is reached, at which point the best draft is returned along
with any remaining notes.

4 Demonstration Cases
 Throughout the FY26 effort, Maggie’s practical utility was demonstrated iteratively with
development of the software architecture described in Section 3. The demonstrations are intended
to evaluate whether the software can support technically meaningful interactions for SAS users
and to identify strengths and limitations of the current implementation. Two capability areas were
prioritized. The first was a chatbot-style interface for question answering and knowledge retrieval,
which represents the most immediately useful application of the system. The second was
generation of SAS input, which is more technically demanding and central to the long-term
objective of supporting software model development and validation activities.

 4.1 Chatbot
 A chatbot interface was the first user-facing capability implemented for Maggie and served as
the initial demonstration for the project. The chatbot was deployed on the internal Argonne
network for use by the SAS development team who provided feedback that led to improvements.
The primary improvements from this effort were system prompts generally directing the agent to
simply state that it cannot find an answer if applicable, and the code manual variable/location look-
up tools described in Section 3.3. An example of user interaction with the chatbot is shown in
Figure 2.

 Figure 2 Example User Chat with Maggie

 In the Figure 2 conversation, Maggie correctly identifies the SAS variable name for
entrainment length (XLENTR) even though the user has not provided it in the question. Maggie
locates the relevant section of the code manual and truthfully states that it does not include a
recommended value but explains what the parameter is used for by SAS. After the part of the
conversation visible in Figure 2, Maggie goes on to search example SAS input files and identifies
representative values used in ABTR models, including a larger value of 100 m and smaller value
of 7 m. Maggie provides sources for this information, and concludes that selection of the

where possible, experimental data and sensitivity studies.
 At this stage, the agent was generally useful and accurate when answering conversational
natural language questions about SAS and historical SAS modeling and validation work. The agent
would try to generate input if asked, but the input produced was not consistently correct and had
formatting issues.

 4.2 Input Generation
 In order to advance the agent past the conversational chatbot functionality, the agent’s
capability for generating input was evaluated based on several test prompts. During this stage,
much of the code-specific system prompt described in Section 3.1 was iteratively developed, as
well as the format validation tool described in Section 3.3 and the entire workflow configuration
described in Section 3.4.
 Three of the test prompts regularly provided to the software and its corresponding written input
are presented and discussed below. Each test was written to request a snippet of SAS input
parameters that could be incorporated into or appended to the end of an existing SAS model.
Arbitrary values, quantities, and times were used in each case to differentiate from any potentially
matching examples in the knowledge base. The prompt supplied to the software and the input
generated to fulfill the request are presented first for each case, followed by an evaluation of the
generated input.

 4.2.1 Test Case 1: Number of Pins and Assemblies

 channel 4 represents 1 assembly with just 1 pin and channel 10 represents 2

 This test prompt requests an input file snippet to specify how many assemblies are represented
by specific channels and how many pins there are in each assembly. Different numbers of pins and
assemblies per channel were requested to verify that the software assigns the correct values for
each to each channel. With 217 pins and 271 pins, respectively, Channels 1 and 2 may represent
different types of fueled assemblies, while the single pin Channel 4 could represent a block type
reflector assembly and the 19-pin Channel 10 could represent control rods.
 All aspects of the software’s response to this test prompt are correct. The block headers, e.g.
the “INPCHN 51 10 10” line, govern for which block and channel the following inputs
are specified. The input headers correctly specify the input block that contains NPIN and NSUBAS via
the INPCHN keyword and the 51 block ID that follows. Inputs are written in the INPCHN block
corresponding to the correct channels, as defined by the pairs of integers at the end of the block
header lines matching the channel numbers in the test prompt.
 The lines beginning with a ‘#’ symbol are comment lines. Although comments indicating
which input parameters are being written are not strictly necessary, they are considered good
modeling practice. The comments preceding the actual lines of input parameters correctly identify
which parameters are being defined, and in a format matching the comments used in the knowledge
base examples that Maggie was specifically requested to reference via the code-specific prompts.
Additionally, the software was not confused by the use of “assembly” in the test prompt and the
use of “subassembly” in the NSUBAS input description. The discrepancy of Maggie using both
“assembly” and “subassemblies” in the response is likely caused by the two words appearing in
different knowledge base examples that Maggie referenced. However, this is a minor inconsistency
and not considered a mistake because the two labels are interchangeable for SFRs.
 The lines of four integers after the comment lines define the NPIN and NSUBAS input parameters.
The locations within the INPCHN block are correctly specified as locations 25 and 26, as defined by
LOC being set to 25 and NUM being set to 2 in each of those lines. Most importantly, for each channel,
the number of pins per assembly (NPIN) and the number of assemblies represented by the channels
(NSUBAS) are both correctly specified.
 Via the SAS-specific prompts, Maggie has been instructed to write SAS inputs using fixed-

 Finally, the software correctly wrote a `-1` to close the INPCHN block for the channel before

 This test prompt is one of a set of tests that were written to evaluate the capability of the

relying on users to know if data is extrapolated beyond the final data point or if the final data point

 4.2.4 Identified Improvement Areas
 During regular evaluation of the software with the full suite of test prompts, one of the mistakes
the software occasionally made with the test case described in Section 4.2.3 was writing the
incorrect value for the ILRPMP input for Pump #1. Sometimes the software would input a value for
a different pump operation option, likely because it copied an ILRPMP value from one of the
knowledge base examples without recognizing that doing so would change the meaning of the data
input on the AMOTTK array. That is an error and steps to correct such behavior can be implemented
in future work. A similar mistake made in another test case was a regular failure to write a specific
integer input in the correct input location. The ITABVV input defines the table number where orifice
coefficients are input for a valve component. For one of the examples not included in this report,
the software was just as likely to write the value for ITABVV in the correct location as it was to write
it in a different location. The reason for this type of mistake has not yet been determined, as it does
not appear to originate from any of the knowledge base examples. Improvements to the software
in future work will also be implemented to address mistakes like this one.

 4.3 Future Software Architecture Improvements
 Based on evaluation of the demonstrations described in the previous sections, several strategies
for improving Maggie’s software architecture have been identified that will be needed to advance
its capability from generating useful snippets of input toward producing full standalone nuclear
analysis models for any code. Testing showed that reliability becomes more challenging for
requests that span multiple related inputs or input blocks, particularly when the agent must
maintain consistency between selected modeling options and downstream parameter definitions.
Future architectural improvements will focus on increasing control over the generation process,
making intermediate reasoning steps more explicit, and reducing opportunities for the agent to
introduce inconsistencies.
 One important improvement area is to expand the existing simple workflow into a more
granular sequence of required steps. Currently, Maggie can decide which tools to use while
working toward a response, with the only enforced control being that any drafted input must pass
through the format validation tool. More complex model-building requests will benefit from a
workflow that has explicit steps such as identifying the objective, determining what portions of
the model are affected, retrieving references, selecting examples, drafting values, and performing
consistency checks. Requiring the agent to proceed through steps like these would make its
behavior more predictable and reduce the likelihood that it skips an important step or relies too
heavily on a single retrieved example.
 A second important improvement is the introduction of structured output together with explicit
state tracking. Currently, Maggie primarily works through unstructured text, even though the task
involves highly structured engineering information. This makes it harder to examine intermediate
results, reliably connect them to tools, or keep all parts of a larger task consistent. For example,
the system could maintain an internal record of what has already been defined in the model and
what still remains to be specified. This would help ensure that later steps remain consistent with
earlier ones and would give the agent a clearer representation of the evolving model than reliance
on conversational context alone.
 A structured state representation would also enable eventual transition to a multi-agent
architecture. Full model generation is likely to require narrower, more specialized capabilities than
one general agent can reliably provide. Future versions of Maggie may benefit from dividing
responsibilities among multiple agents that each operate on the shared model state. For example,
one agent could focus on individual core channels, another on assembling those channels into a
core model, another on creating the heat transport system, and another on troubleshooting failed
SAS runs. The shared state would support coordination by giving each agent access to the same
evolving representation of the model. Under this approach, each agent would perform a more
constrained class of tasks and could be given prompts and tools tailored specifically to that task.
This would improve control and reduce the kinds of errors that arise when a single agent must
simultaneously manage many different modeling concerns.
 Another area for improvement is expansion of validation beyond format checking alone. The
current format validation tool detects structural and formatting problems, but not technical
consistency between model inputs. Addressing issues seen in the demonstration cases will require
a broader set of validation tools that can examine whether selected inputs are compatible with
chosen model options, whether required supporting inputs have been provided, and whether input
locations are internally consistent.

 19

 Together, these improvements will lead to a more controlled and modular architecture in which
Maggie does not simply generate text in response to a prompt but instead progresses through a
defined engineering workflow supported by structured representations, persistent state, target
validation, and specialized reasoning components.

5 Conclusions and Future Work
 The FY26 work established the initial foundation for Maggie, an AI-based assistant intended
to support software model generation and validation activities for fast reactor analysis codes. A
modular, code-agnostic software architecture was developed that separates reusable agent
capabilities from code-specific knowledge and tools. This architecture allows the same general
framework to be extended over time to additional nuclear analysis codes by adding new knowledge
bases, code-specific prompts, and tools. A SAS-specific knowledge base was created, combining
the SAS code manual, training materials, historical analysis reports, and representative input files
into a curated resource Maggie can search and use when responding to user requests. This
grounding is essential for such a specific technical domain, where general background of an LLM
alone is not sufficient.
 The FY26 effort demonstrated practical user-facing capability through deployment of a chatbot
interface on the internal Argonne network. Maggie was generally effective at answering natural
language questions about SAS, locating relevant information in the code manual and historical
reports, and identifying useful example cases from prior modeling work. Beyond simple question
answering, the project made meaningful progress toward AI-assisted input generation. Maggie can
draft useful snippets of SAS input. This demonstration shows that the system has progressed
beyond a simple chatbot, yet there is room for improvement as larger and more complex input-
generation tasks remain challenging. Maggie’s output varies from run to run and may still contain
technical or logical errors, particularly for larger and more complex input generation tasks that
require consistent coordination across multiple modeling decisions and input blocks. Future work
is needed to better control the agent’s behavior for more complex tasks such as creating a full
standalone SAS model, and strategies for improvements have been identified.
 Future work should focus on improving reliability while expanding capabilities. Key priorities
are identified as follows:
 • Advance the software architecture for complex engineering workflows. Refine the current
 agent design into a more structured architecture with a more granular workflow, explicit
 state tracking, structured outputs, and specialized agents for narrower subtasks.
 • Extend the framework to an additional FRP analysis code.
 • Plan for future deployment to external users. Although Maggie is not yet sufficiently
 reliable for external deployment, important implementation issues such as user
 authentication, data access control, and management of LLM token usage – including
 whether external users would provide their own LLM API access – will need to be
 addressed. Because these considerations may influence architectural and deployment
 decisions, strategies for supporting external users should be considered early in
 development. Solutions adopted by other FRP-supported AI-based projects will likely
 provide useful guidance.
