 Executive Summary of CRADA Work:

 The aim is to create a prototype open-source long-term load forecasting tool suitable for quickly

 assembling country-level load forecasts for power sector planning models accounting for major
 drivers like population, Gross Domestic Product (GDP), Vehicle Miles Traveled (VMT),
 technology adoption, and a changing climate.

 CRADA benefit to DOE, Participant, and US Taxpayer:

 • Enhances the laboratory’s core competencies
 • Uses the laboratory’s core competencies

 Summary of Research Results:

 Task 1 – Prototype Design

 This task will start with a series of meetings between NLR and Equinor to be sure that the design
 team understands Equinor’s current decision-making process and desired improvements.
 Following those meetings, the design team will further develop the initial design concept, which
 is partially described above and in Figure 1. The expected outcome of this process is an MVP
 design comprising a light wireframe design for the user interface, a high-level description of user
 interactions, and a list of initial data sources, as well as a description of the technology stack and
 a “hello world” installation package Equinor’s IT team can check for compatibility with their
 systems.

 NLR Deliverable: MVP light wireframe design, description of user workflows, and list of key
 data sources and provide to Equinor.

 NLR Deliverable: Provide description of the technology stack and a “hello world” installation
 package for evaluation by Equinor’s IT department.

 Equinor Deliverable: Decision Point - A decision will be made at this time to determine if Tasks
 2 and 3 will be required. Equinor will provide its decision in writing to NREL notice contacts
 herein. NREL will be considered authorized to proceed to next task until deemed not-approved
 by Equinor in written notice.

 Results:

 The project started with a thorough design phase, the bulk of which took place November 2024 –
 January 2025. Design started with a series of interviews that clarified technical requirements and
 desired user workflows. Lab staff interviewed Equinor energy modelers, energy project analysts,
 and software developers and this led to a common understanding of the prototype tool consisting
 of two components. First, a Python command line interface for data assembly and second, a
 Plotly Dash web application for data inspection. Furthermore, the tool was required to quickly
 create country-level long-term load forecasts (multiple decades) at hourly resolution, but should
 then allow for inspection and refinement, to make use of the project-specific data commonly
 collected by Equinor modelers and analysts.

 3

 Figure 2. Excerpt from the prototype tool’s light wireframe design.

 With this high-level description in hand, design progressed to identifying input data sources,
 designing the data inspection user interface, and validating backend technology selection via
 delivery to and testing by Equinor of a “hello world” installation package. The lab team
 identified data source options and recommended a leading candidate for nine different categories
 of data: gross domestic product (GDP), population, weather, country load shapes, load
 components and forecasts, load shape forecasts, current electric vehicle stock and sales, electric
 vehicle stock and sales projections, and vehicle miles traveled. An experienced graphic designer
 worked with us to develop a light wireframe of the data inspection user interface, see Figure 2
 for an excerpt. Finally, in mid-January 2025 we iterated with Equinor staff on an initial
 installation package, ultimately verifying that our selected software technologies were
 compatible with Equinor IT policies and practice.

 4

 Task 2 – Build and Demonstrate Prototype

 This task will build a functional prototype based on the MVP design articulated in Task 1. The
 prototype will be able to assemble hourly, country-level load profiles decomposed into (a)
 electric vehicle load, and (b) all other load for future years out to 2050 (or other end point as
 determined by input data and user options) using a combination of default datasets, user-supplied
 datasets, and user options. At this point in time, we expect major subtasks to include:

 • Implement demand-Side grid toolkit (dsgrid) features required to support this workflow,
 e.g., enable simpler backend data engine, support multiple metric types (e.g., population,
 GDP, VMT, in addition to energy), and enable fully flexible dimension types.
 • Ingest data sources and implement application logic to apply appropriate transformations.
 • Build simple web application (e.g., Plotly Dash) to wireframe specification of relevant
 pieces.

 However, this list is subject to change based on Task 1 and agile development processes.

 NLR Deliverable: Check-in meetings with Equinor at a mutually agreed upon frequency (e.g.,
 monthly or weekly)

 NLR Deliverable: Tagged, private GitHub.com repository with installation instructions. Live
 demonstration of the prototype capability in an interactive webinar.

 Results:

 In the next phase of the project, we built and demonstrated the prototype tool. This involved
 accessing and processing data, finalizing and implementing the backend approach, and building
 the Plotly Dash UI. Initial implementation focused on annual energy projections via energy
 intensity regressions, prototyping data calculations using dbt, and developing the initial UI, the
 latter two subtasks primarily done with a test dataset designed to match the full dataset’s
 structure, but very small and with fictitious numbers. This culminated in a live demonstration
 with test data on August 6, 2025, after which Equinor tested the draft tool and provided
 additional feedback.

 5

 Figure 3. Screenshot from STRIDE v1.0.0

 A second implementation push completed the prototype tool by adding weather and load profile
 data, implementing an optional light-duty passenger electric vehicle projection module, mapping
 datasets into a common set of dimensions with dsgrid (primarily to support datasets with
 different geographic coverage than the annual energy projection datasets), enabling dataset
 download from the command line, supporting color customization in the visualization UI, and
 numerous other improvements. This culminated in a demonstration to diverse Equinor staff on
 December 18, 2025, and another round of testing and feedback that was completed by early
 February 2026. Figure 3 shows the final implementation of the visualization UI (compare to
 Figure 2).

 Task 3 – Iterate and Decide on Next Steps

 After Task 2 is complete, we expect Equinor staff to try out and comment on the capability.
 During this period of time, we will respond to questions, fix bugs, and make minor
 improvements that are in scope. Should the prototype be meeting or exceeding expectations, and
 if there is sufficient time and scope remaining, the project team might consider designing and/or
 adding new data and features related to high priorities for Equinor like EV charging flexibility
 and electrolysers. We also expect to have exploratory conversations across NLR, Equinor, and
 with other organizations to collaborate on further development opportunities with stakeholders
 who could stand to benefit from this capability and/or are motivated to enable access to broader
 stakeholder base. This effort is likely to lead to a description of a follow-on, Phase 2 project.
 Phase 2 could be a straightforward extension of the MVP prototype or could include major
 rework, depending on what’s learned in this interactive and iterative process.

 NLR Deliverable: Provide repository updates and final long-term load forecasting tool prototype

 Equinor Deliverable: Provide feedback to NLR on prototype capability to troubleshoot bugs and
 make improvements to prototype

 Equinor Deliverable: Decision Point - Equinor will provide to NREL written affirmation that
 the prototype meets or exceeds expectations and that Equinor wishes to proceed, collaboratively
 with NREL, with developing a user base and future funding to support maintenance and further
 development.

 NREL Deliverable: Upon the end of the period of performance, if NREL does not receive a
 written notice from Equinor that the prototype is explicitly not-approved, NREL will proceed to
 make the tool repository publicly available via Tagged, open-source (BSD-3 license)
 GitHub.com repository with installation instructions.

 Results:

 At the end of the project, Equinor and NLR staff both expressed satisfaction with the end
 product, which resulted in the public release of the tool on GitHub1 and PyPI.2 Documentation is
 also available.3

 Although Equinor cannot commit additional resources for further tool development at this time,
 they are “now deploying the tool within [their] system and will begin gathering more feedback as
 [their] analysts start using it.” Both parties agreed to socialize the tool within their own
 organizations and with other organizations.
