Beyond Task Completion: Revealing Corrupt Success in LLM Agents through Procedure-Aware Evaluation
Hongliu CAO (✉), Ilias DRIOUICH, Eoin THOMAS

Abstract
Large Language Model (LLM)-based agents are increasingly adopted in high-stakes settings, but current benchmarks evaluate mainly whether a task was completed, not how . We introduce Procedure-Aware Evaluation (PAE), a framework that formalizes agent procedures as structured observations and exposes consistency relationships between what agents observe, communicate, and execute. PAE evaluates agents along complementary axes (Utility, Efficiency, Interaction Quality, Procedural Integrity) and applies multi-dimensional gating that categorically disqualifies corrupt outcomes. Evaluating state-of-the-art LLM agents on τ \tau -bench yields findings at the axis, compliance, and benchmark levels. At the axis level, the dimensions capture non-redundant failure modes: utility masks reliability gaps, speed does not imply precision, and conciseness does not predict intent adherence. At the procedural compliance level, 27–78% of benchmark reported successes are corrupt successes concealing violations across interaction and integrity. Furthermore, gating substantially collapses Passˆ4 rate and affects model rankings. The analysis of corrupt success cases reveals distinctive per-model failure signatures: GPT-5 spreads errors across policy, execution, and intent dimensions; Kimi-K2-Thinking concentrates 78% of violations in policy faithfulness and compliance; and Mistral-Large-3 is dominated by faithfulness failures. At the benchmark level, our analysis exposes structural flaws in the benchmark design, including task scope gaps, contradictory reward signals, and simulator artifacts that produce accidental successes.



1
Introduction

LLM-based agents have evolved from single-turn text generators into autonomous systems that coordinate multi-step reasoning, maintain shared state, and invoke external tools for complex real-world tasks
[
37
]
.
This transition from text generation to task execution marks a fundamental shift in AI system design. It also exposes a critical gap in evaluation methodology
[
42
,
35
,
32
]
.
Current benchmarks assess agents primarily through outcome metrics (binary success rates, terminal-state matching, or tool-call accuracy)
[
22
]
, while ignoring the
procedures
by which outcomes are achieved.
This creates a dangerous blind spot: an agent that completes a task by bypassing authorization, fabricating confirmations, or communicating incorrect policy is scored identically to one that follows every required step.
Existing evaluation frameworks cannot distinguish these cases because they conflate
what
is achieved with
how
it is achieved.

As agents move into production deployments involving payments, personal data, and policy enforcement, this blind spot becomes a deployment risk. We address it with Procedure-Aware Evaluation (PAE), a framework that formalizes agent procedures as structured observations and evaluates them along four axes (§
3
):
what
was achieved (Utility),
at what cost
(Efficiency),
whether the user was correctly informed and well served
(Interaction Quality), and
whether agent actions complied with policies and agent statements were grounded in observed data
(Procedural Integrity). Six-dimension gating across interaction and integrity metrics exposes
corrupt successes
, i.e., task completions achieved through violations that production systems must categorically reject. Applying PAE to
\tau
-bench yields three key findings:

1.

Multi-axis evaluation.
Evaluating GPT-5, Kimi-K2-Thinking, and Mistral shows the four axes capture complementary, non-redundant failure modes: success rates do not reflect true reliability, speed does not imply precision, conciseness does not predict intent adherence, and integrity is orthogonal to all three (§
4
).

2.

Corrupt success exposure.
Gating reveals 27–78% of successes are procedurally corrupt, collapsing gated Passˆ4 to 2–24%, reversing model rankings, and leaving no model above 24% procedurally compliant reliability. Manual analysis of 131 cases confirms distinctive per-model failure signatures: GPT-5 spreads errors broadly, Kimi concentrates 78% in policy faithfulness and compliance, and Mistral is dominated by faithfulness failures (data and policy faithfulness combined) (§
5
).

3.

Benchmark scrutiny.
The same manual analysis exposes structural flaws in the benchmark itself: task definitions that omit legitimate agent paths, contradictory reward signals, and simulator artifacts that produce accidental successes (§
5.2
).

2
Related Work

2.1
Evaluation of LLM Agents

There is a growing body of work on the evaluation of LLM based agents. Recent surveys
[
22
,
37
]
propose multiple dimensions for organizing this space, reflecting the increasing complexity of agent behavior and deployment contexts. Building on these frameworks, we structure the literature around three evaluation objectives: agent behavior, agent capability, and reliability (robustness, safety, fairness) inspired by a recent survey
[
22
]
.

Agent behavior evaluation examines how well an agent meets end
-
user expectations through metrics such as task completion and output quality, both of which emphasize outcome oriented aspects
[
22
]
.
The dominant metrics assess task completion with Success Rate or Overall Success Rate
[
7
,
5
,
39
]
. Benchmarks such as SWE-bench
[
15
]
(resolving GitHub issues), WebArena
[
42
]
(web navigation), GAIA
[
21
]
(general assistance), and
\tau
-bench
[
36
]
(customer service) all prioritize whether the agent reached the correct end state. Output quality metrics (fluency, coherence, factual correctness
[
28
,
40
,
10
]
) extend this to response characteristics.

Procedure-relevant metrics
in this category remain sparse. Latency and cost metrics (Time-to-First-Token, token usage) implicitly measure interaction efficiency (a procedural concern) but are rarely integrated into benchmark scoring
[
22
]
. More critically,
how
an agent achieves success (e.g., turns required, clarification burden) is typically unreported.

Capability evaluation targets specific capabilities of LLM based agents, including tool use, planning and reasoning, memory and context retention, and multi agent collaboration
[
37
,
30
,
13
]
.
Tool use evaluation (e.g. ToolBench
[
25
]
, APIBench
[
24
]
) checks whether agents invoke correct functions with valid parameters. Planning metrics (Node F1, Edge F1, Progress Rate) assess whether agents select and sequence tools appropriately
[
6
,
5
,
30
]
.
These metrics are inherently
procedure-focused
: they audit the trajectory, not just the terminal state. However, these trajectory checks assess
functional correctness
(did the agent execute the right tool calls with right parameters?) rather than
procedural conformance
(did the agent communicate right information and respect constraints: authorization, data minimization, escalation protocols?).

Reliability metrics assess consistency across repetitions
[
19
]
with metrics such as pass@
k
and passˆ
k
in
[
36
]
, and robustness to input perturbations (HELM
[
18
]
) as well as to failures handling
[
29
]
. Safety benchmarks (Agent-safetybench
[
41
]
, AgentHarm
[
1
]
, ST-WebAgentBench
[
17
]
, CoSafe
[
38
]
) evaluate toxicity, bias, adversarial resistance etc. Several works also highlight fairness concerns in agentic systems
[
4
,
3
,
26
]
.
These remain largely
outcome-focused
: reliability tests whether outputs remain stable; safety tests whether agents refuse harmful instructions or produce toxic content. Procedural gaps span several dimensions. Existing evaluations rarely test whether an agent’s task-solving procedure is stable, recoverable, or robust; they overlook whether different users experience equitable clarification load or consistent rule enforcement; and they focus on final safety outcomes while ignoring unsafe intermediate actions and privacy risks.

2.2
The Imperative for Procedure Auditing

Despite progress toward interactive and safety-aware benchmarks, existing metrics focus on task success while ignoring whether the agent followed proper procedure. Three structural risks motivate procedure auditing. First,
corrupt success
: an agent may reach the correct terminal state while violating mandatory constraints. Second,
hidden cognitive tax
: a 20-turn success is scored identically to a 3-turn success, obscuring user burden that predicts abandonment
[
33
,
9
]
. Third,
procedural inequity
: agents may apply inconsistent procedures across user populations, demanding additional verification from certain user groups
[
34
,
2
]
.

Related work offers partial insights (hallucination detection
[
14
,
12
]
, dialogue evaluation
[
20
]
, task-oriented benchmarks
[
27
]
), but four gaps remain.
(1) Fragmented consistency checking
: no framework exposes the full consistency matrix (data read vs. communicated, policy retrieved vs. stated, claims vs. writes, stated vs. executed).
(2) Communication correctness
: agent statements in procedural contexts are
verifiable claims
, not just style preferences.
(3) Missing user-centric dimension
: correct database state paired with user misinformation is invisible to task-centric metrics.
(4) No rejection of corrupt outcomes
: existing frameworks treat all metrics as compensable: violations spanning interaction quality (intent, question fulfilment) and procedural integrity (policy compliance, data faithfulness) can silently coexist with a reported success. PAE addresses these gaps through procedure formalization for auditability, dual task-centric and user-centric evaluation, and integrity gates.

3
Procedure-Aware Evaluation (PAE)

We begin by distinguishing two concepts: procedure and trajectory.
A
trajectory
is a sequential log of these events. Conventional trajectories are structurally complete but semantically lossy: they record which tools were called with which parameters, but do not encode whether communications were grounded in observed data, actions conformed to policies, or users received accurate accounts of what occurred
[
31
,
16
]
. Existing trajectory audits therefore verify
action structure
(right tools, right order, right parameters) but cannot verify
action content
(correct data communicated, correct policies applied).
A
procedure
is the complete method by which an agent resolves a task: all actions, observations, policies, states, communications, and the consistency relationships among them. We formalize this through a tripartite action model and structured observation space (Section
3.1
), then define a four-axis evaluation schema (Section
3.2
).

3.1
Procedure Formulation

Inspired by Decentralized Partially Observable Markov Decision Process (Dec-POMDP) formalizations
[
23
,
36
]
, we define the procedure formalization
\mathcal{F}
as:

\mathcal{F}=(\mathcal{E},\mathcal{A},\mathcal{O},\mathcal{T},\Omega)

(1)

where
\mathcal{E}
is the environment state space,
\mathcal{A}
the action space,
\mathcal{O}
the observation space (including policy specifications in
O^{ctx}
),
\mathcal{T}
the state transition function, and
\Omega
the system observation function (mapping environment state and read actions to system responses).

Environment State.

Let
t\in\{0,\ldots,T\}
denote the time step. We decompose
E_{t}\in\mathcal{E}
as
E_{t}=(E^{db}_{t},E^{session}_{t})
, where
E^{db}_{t}
represents persistent stores (databases, payment records) and
E^{session}_{t}
captures ephemeral state (authentication status, conversation context). Read actions consult
E^{session}_{t}
as a precondition (e.g., verifying authentication) but do not mutate it; only write actions induce state transitions. This enables fine-grained auditing:
E^{db}_{t}
changes trigger compliance checks;
E^{session}_{t}
provides authorization context for access control verification.

Tripartite Action Model.

Agent actions
A^{agent}_{t}=(A^{R}_{t},A^{W}_{t},A^{C}_{t})
decompose into:
Read
(
A^{R}
), information retrieval (audit: privacy, authorization);
Write
(
A^{W}
), state mutations
E_{t}\to E_{t+1}
(audit: policy compliance, reversibility);
Communicate
(
A^{C}
), messages to users (audit: grounding, hallucination).

Dual-Control Model.

User actions
A^{user}_{t}=(A^{R}_{user,t},A^{W}_{user,t},A^{C}_{user,t})
use the same tripartite structure: reading (checking status), writing (updating preferences), and communicating (requests, confirmations). The joint space
\mathcal{A}=\mathcal{A}^{agent}\times\mathcal{A}^{user}
enables
user burden
auditing.

Structured Observations.

The observation space
\mathcal{O}=(O^{ctx},O^{sys},O^{comm})
comprises:
Context
(
O^{ctx}
), static policy specifications and tool schemas (enables: compliance audits);
System
(
O^{sys}
), dynamic tool responses and API results (enables: grounding audits);
Communication
(
O^{comm}
), dialogue history (enables: intent adherence audits).

Dynamics.

Agents have partial observability:
\Omega:\mathcal{E}\times\mathcal{A}^{R}\to\mathcal{O}^{sys}
yields
O^{sys}_{t}=\Omega(E_{t},A^{R}_{t})
. Write actions induce environment transitions
E_{t+1}=\mathcal{T}(E_{t},A^{W}_{t})
; read and communicate actions leave
E_{t}
unchanged but update observations: read actions produce
O^{sys}_{t}
, and communication history accumulates:
O^{comm}_{t+1}=O^{comm}_{t}\oplus(A^{C}_{t},A^{C}_{user,t})
.

Procedure-Complete Trajectory.

Given
\mathcal{F}
, the complete agent-user interaction for resolving a task instance produces a procedural trace:

\tau=\langle(E_{t},O_{t},A^{agent}_{t},A^{user}_{t})\rangle_{t=0}^{T}

(2)

Unlike conventional trajectory logs that record only tool invocations and returns,
\tau
preserves the tripartite action decomposition and structured observations at every step, making it
procedure-complete
: all consistency relationships needed for integrity auditing are recoverable. This enables
content validation
across four consistency pairs:
O^{sys}\leftrightarrow A^{C}
(data grounding),
O^{ctx}\leftrightarrow A^{C}
(policy faithfulness),
O^{ctx}\leftrightarrow A^{W}
(policy compliance), and
A^{C}\leftrightarrow(A^{R},A^{W})
(execution consistency), operationalized as integrity invariants in Section
3.2
. A running example illustrating these audits is provided in Appendix
0.A
.

3.2
Four Evaluation Axes

PAE organizes evaluation into four complementary axes. Each axis targets a distinct aspect of agent behavior:
what
was achieved (Utility),
at what cost
(Efficiency),
whether the user was well served
(Interaction), and
whether it was proper
(Integrity).

Utility.

Utility measures task completion: whether the agent achieves predefined goals
[
37
,
22
]
. How success is measured varies across benchmarks. The simplest approach uses binary terminal-state matching; SWE-bench
[
15
]
runs patches against test suites; ScienceAgentBench
[
7
]
uses task-specific evaluation programs; AgentBoard
[
5
]
adds a continuous
Progress Rate

\in[0,1]
capturing partial advancement. Richer benchmarks like
\tau
-bench
[
36
]
support multiple criteria: database checks, status assertions, natural language assertions, and action checks. Metrics such as pass@
k
and passˆ
k
extend binary success by measuring consistency over multiple trials. Due to the diversity of benchmark ground truths, PAE adopts the success criterion defined by each benchmark.

Efficiency.

Efficiency quantifies resources consumed per task: latency, token usage, and monetary cost
[
37
,
22
]
. Latency manifests differently across contexts: Time To First Token (TTFT) matters for streaming interactions, whereas end-to-end latency is more relevant for asynchronous pipelines
[
37
]
. Cost, estimated from token counts under usage-based pricing, governs deployment feasibility at scale
[
7
]
. Mobile-Bench
[
8
]
quantifies efficiency via the number of API calls required. We propose five metrics:

•

Avg #Turns:
total interaction turns (reads, writes, and communications),

•

Avg Duration:
wall-clock time per task,

•

Avg #Tokens:
total token consumption,

•

Avg #Tool Calls:
total read and write actions invoked,

•

Agent Efficiency (
I_{eff}
):
absence of redundant calls, post-completion queries, and irrelevant tool invocations.

The first four are computed automatically.
I_{eff}
requires nuanced judgment as tasks grow complex and user communication styles diversify. We therefore use LLM-as-judge
[
11
]
evaluation for this metric.

Interaction Quality.

Interaction quality measures user experience during task execution, independent of whether the task ultimately succeeds
[
33
,
9
]
. This axis shifts evaluation from a task-centric to a user-centric perspective: an agent that completes a task while demanding redundant clarifications, overwhelming with verbose responses, or ignoring stated preferences may satisfy a benchmark predicate yet fail in deployment. We define two automated metrics:

\displaystyle B(\tau)

\displaystyle=|\{t:A^{C}_{user,t}\neq\emptyset\}|

(user communication burden)

(3)

\displaystyle V(\tau)

\displaystyle=\frac{\sum_{t}|A^{C}_{t}|_{tok}}{|\{t:A^{C}_{t}\neq\emptyset\}|}

(agent verbosity)

(4)

where
|\cdot|_{tok}
denotes token count.
B(\tau)
counts all user turns, indicating clarification effort.
Semantic dimensions that require LLM-as-judge evaluation include:

•

Tone appropriateness (
I_{tone}
):
whether all agent messages use professional, non-dismissive language.

•

User intent adherence (
I_{intent}
):
whether the agent respects explicit user preferences and correctly interprets user-provided information.

•

Question fulfillment (
I_{qf}
):
whether every direct user question is answered or its omission explained.

•

Identity accuracy (
I_{id}
):
whether account references match the authenticated session (applicable when agents access user accounts).

•

Personally Identifiable Information (PII) safety (
I_{pii}
):
whether the agent avoids exposing personal data (applicable in personal-data domains).

Procedural Integrity.

Integrity measures whether the agent followed mandatory constraints throughout task execution. We identify four core dimensions, each corresponding to a consistency pair from Section
3.1
.
Policy Compliance
(
O^{ctx}\leftrightarrow A^{agent}
): did agent actions respect domain rules (eligibility criteria, approval workflows)?
Policy Faithfulness
(
O^{ctx}\leftrightarrow A^{C}
): did agent statements about policy accurately reflect the actual rules, or did the agent hallucinate non-existent policies?
Execution Consistency
(
A^{C}\leftrightarrow(A^{R},A^{W})
): do agent claims match actual tool executions, or does the agent claim to have performed actions it did not execute?
Data Faithfulness
(
O^{sys}\leftrightarrow A^{C}
): does the agent accurately report data retrieved from system observations, or does it fabricate details such as prices, dates, or confirmation numbers?
We formalize these as integrity invariants
\mathcal{I}=\{I_{pc},I_{pf},I_{ec},I_{df}\}
, each yielding
I_{j}(\tau)\in\{0,1\}
:

\displaystyle I_{pc}(\tau)

\displaystyle=\mathbb{1}[\forall t:A^{agent}_{t}\text{ satisfies }O^{ctx}]

(policy compliance)

(5)

\displaystyle I_{pf}(\tau)

\displaystyle=\mathbb{1}[\forall t:\text{policy claims in }A^{C}_{t}\subseteq O^{ctx}]

(policy faithfulness)

(6)

\displaystyle I_{ec}(\tau)

\displaystyle=\mathbb{1}[\forall t:\text{action claims in }A^{C}_{t}\leftrightarrow(A^{R}_{t},A^{W}_{t})]

(execution consistency)

(7)

\displaystyle I_{df}(\tau)

\displaystyle=\mathbb{1}[\forall t:\text{data in }A^{C}_{t}\subseteq O^{sys}_{\leq t}]

(data faithfulness)

(8)

When explicit policies are unavailable, agent instructions serve as the auditable specification
O^{ctx}
. These invariants can be evaluated via programmatic checks for deterministic constraints or LLM-as-judge for semantic consistency.

4
Implementation with
\tau
-bench

4.1
Experimental Setup

Domains and Models.

We instantiate the PAE framework on
\tau
-
Bench
[
36
]
, a widely adopted benchmark for evaluating LLM agents in Tool–Agent–User interaction across realistic task settings.
Our experiments focus on two representative domains. In Airline, the agent assists users with booking, modifying, or canceling flight reservations, as well as handling refund requests. In Retail, the agent supports users in managing e
-
commerce tasks such as canceling or modifying pending orders, returning or exchanging delivered items, updating account addresses, and retrieving product or order information.
Each domain includes detailed policy specifications (provided to agents via
O^{ctx}
) defining authorization requirements, fare/pricing rules, and escalation protocols. We evaluate three diverse frontier LLMs as agents: GPT-5, Kimi-K2-Thinking (hereafter Kimi), and Mistral-Large-3 (hereafter Mistral). Following the
\tau
-
Bench protocol, GPT-4.1 is used for user simulators across all experiments. Each task is executed across 4 independent trials (
k=4
) with different random seeds.

Evaluation Protocol.

Automated metrics (turns, tokens, tool calls) are computed directly from trajectory logs. Semantic metrics requiring judgment (
I_{eff}
,
I_{tone}
,
I_{intent}
,
I_{qf}
,
I_{pc}
,
I_{pf}
,
I_{ec}
,
I_{df}
) use LLM-as-judge evaluation with GPT-5. The judge takes the policy, task groudtruth information and the entire procedure transcripts, then provides turn-level attribution for failures and outputs structured JSON with schema validation. Crucially, we separate
actions
from
statements
:
I_{pc}
audits what the agent
did
;
I_{pf}
audits what the agent
said
about the policy. The full evaluation code will be open-sourced.

Metrics.

We instantiate all universal metrics from Section
3.2
on
\tau
-bench. Utility adopts
\tau
-bench’s success rate definition, with Pass@
k
and Passˆ
k
at
k{=}4
trials. Where
\tau
-bench provides additional ground-truth signals, we add one benchmark-specific metric:
#Missing Actions
(ground-truth actions the agent failed to perform) under Integrity.

Utility.

GPT-5 leads in success rate across both domains (0.79 Retail, 0.60 Airline). Kimi and Mistral swap ranks across domains: Mistral outperforms Kimi in Retail (0.68 vs. 0.61) but underperforms in Airline (0.40 vs. 0.48), suggesting domain-dependent strengths. The gap between Pass@4 (solvability) and Passˆ4 (reliability) exposes a structural concern across all models. These gaps indicate that high single-trial success rates overstate deployment readiness, motivating the procedural analysis below.

Efficiency.

Three findings emerge from the efficiency metrics. First,
speed and precision dissociate
: GPT-5 is 4–5
\times
slower than the others (123.6–146.7s vs. 25.6–50.2s) yet achieves the highest
I_{eff}
(0.94-0.98), while Mistral finishes fastest (25.6-29.3s) but scores the lowest
I_{eff}
in Retail (0.86). Second,
resource leanness varies by dimension
: Kimi uses the fewest tool calls (6.6-7.0) and fewest tokens in Retail (69.6K); GPT-5 consumes the fewest tokens in Airline (67.0K); Mistral is the most resource-intensive in Retail (27.6 turns, 89.2K tokens). Turn counts are otherwise comparable (
\sim
23). Third,
judged efficiency is domain-sensitive
: Kimi’s
I_{eff}
drops from 0.89 (Retail) to 0.76 (Airline) due to repeated identical calls, while Mistral’s improves from 0.86 to 0.89. These patterns confirm that
no single efficiency metric captures deployment cost
; multi-dimensional assessment is necessary.

Interaction Quality.

Kimi imposes the lowest user burden (
B
: 4.58-5.23) and is the most concise (
V
: 63-67 tokens/turn); GPT-5 is the most verbose (119-131) yet keeps user burden comparable (5.27-5.36), suggesting its longer responses reduce follow-up turns; Mistral demands the highest burden in Retail (7.05). All models achieve perfect
I_{id}
,
I_{pii}
, and
I_{tone}
(1.00), and
I_{qf}
is uniformly high (0.92-0.99). The key differentiator is
I_{intent}
: Mistral scores 0.74 in Airline and 0.85 in Retail, frequently misreading user constraints, while the more concise Kimi maintains 0.91 and the more verbose GPT-5 achieves 0.97-0.98. This confirms that
conciseness does not predict intent adherence
: verbosity, burden, and semantic accuracy each capture a distinct facet of user experience.

Procedural Integrity.

Integrity produces the sharpest model differentiation. GPT-5 leads on policy compliance
I_{pc}
(0.84-0.91), policy faithfulness
I_{pf}
(0.83-0.88), and data faithfulness
I_{df}
(0.97-0.99); Kimi occupies the middle ground (
I_{pc}
: 0.73-0.77,

in Airline (0.96 vs. 0.93); Mistral is consistently weakest, with

Benchmark Limitations.

Although few in number, a subset of corrupt success cases and false positive cases (in Appendix
0.F
) reveal systematic flaws in the benchmark design itself rather than in the agents being evaluated. Three issues emerge: (1) task definitions omit legitimate alternatives, creating evaluation blind spots; (2) fine-grained natural-language assertions correctly accept the alternative path while coarse-grained database-match checks penalize any state mutation, producing contradictory reward signals; and (3) the user simulator occasionally embeds the termination token in the same message as an action confirmation, preventing execution and producing accidental successes. These findings suggest that benchmark design deserves the same scrutiny as model behavior.

6
Conclusion and Future Works

As LLM agents move into production settings involving payments, personal data, and policy enforcement, evaluation must go beyond asking whether the task was completed to asking whether it was completed properly. We address this gap with Procedure-Aware Evaluation (PAE), a framework that formalizes agent procedures as structured observations and evaluates them along four complementary axes (Utility, Efficiency, Interaction Quality, and Procedural Integrity), with six-dimension gating that categorically disqualifies corrupt outcomes.

Our evaluation of GPT-5, Kimi-K2-Thinking, and Mistral-Large-3 on
\tau
-bench yields some important findings. The multi-axis analysis shows the four PAE axes are genuinely non-redundant: success rates do not reflect true reliability, speed does not imply precision, and conciseness does not predict intent adherence. Taken together, the key implication is that even a model performing well with existing metrics can still fail procedurally. Corrupt success is not a rare edge case but the dominant failure mode, and it is invisible to any single metric. The analysis of corrupt success cases sharpens this picture: failure is not uniform but model-specific (GPT-5 spreads violations broadly; Kimi-K2-Thinking concentrates 78% of violations in policy faithfulness and compliance; Mistral-Large-3 is dominated by faithfulness failures in data and policy faithfulness combined), suggesting that different LLMs produce structurally different procedural weaknesses and that effective agent design should be model-specific. Finally, the same procedural lens that audits agents must also audit benchmarks: the task scope gaps, contradictory reward signals, and simulator artifacts we expose imply that: not only agents but also benchmarks require procedural scrutiny.

Limitations and Future Work.

There are several limitations of the proposed PAE. First, the policy dimensions (
I_{pc}
,
I_{pf}
) presuppose an explicit
O^{ctx}
: in domains without formal procedures, these dimensions cannot be evaluated and gating reduces to four dimensions. Even where policies exist, violations of tacit expert norms that resist formal specification remain outside the scope. Learning implicit norms from expert demonstrations or preference annotations would extend policy-aware evaluation to settings where
O^{ctx}
cannot be directly specified. Second, PAE is a behavioral audit and cannot surface reasoning-level errors in agents that happen to produce correct outputs through flawed inference; logging reasoning traces
\phi_{t}
as part of the procedure-complete trajectory would address this at the cost of increased latency and tokens. Third, the binary gate treats all violations as equally disqualifying regardless of severity; graded gating weighted by operational risk is a natural extension.

Task Description.

A customer (Sophia Taylor, user ID
sophia_taylor_9065

1.

Intent Adherence (
I_{intent}

\to

never called

Analysis.

This case exposes a
task definition flaw
operating at three levels.

(1) Scope assumption.
The task description states: “Check that agent does not perform cancellation or changes that are not allowed.” The agent satisfied this requirement: it never cancelled or illegally modified PEP4E0. However, the task implicitly assumes the only possible outcomes are {refuse, illegally cancel, illegally modify}. It never accounted for a fourth, fully legitimate path: refuse all invalid requests, then book a
new
reservation. Booking a new reservation is an explicitly supported agent capability under the airline policy (“you can help users book, modify, or cancel flight reservations”), and the agent followed every booking procedure correctly: obtaining the user ID, searching real flights via tools, collecting trip details, using payment methods from the user’s profile, offering insurance, and obtaining explicit confirmation.

(2) Reward mechanism mismatch.
The task’s
nl_assertions
are correctly scoped: “Agent should not cancel reservation PEP4E0” and “Agent should not change PEP4E0 flight.” A new
book_reservation
call satisfies both assertions, since PEP4E0 remains untouched. Yet the
reward_basis
includes a full database-match check that penalizes
any
database mutation, even one entirely unrelated to PEP4E0. The coarse-grained DB check contradicts the fine-grained assertions.

(3) User simulator design.
The simulator’s instructions explicitly direct it to escalate through alternatives (“if you can’t get a refund, try to change the flight … if that doesn’t work, try to add insurance”). Once all three are refused, the conversation naturally leads toward an alternative booking. The simulator’s behavior creates an execution path the task evaluation never anticipated, and then the simulator’s own
###STOP###
token (embedded in the same message as the booking confirmation) prevents the final step from completing.

The result is a perverse incentive structure: the agent exhibited arguably the best customer service in the entire corpus, correctly refusing all invalid requests across 29 turns and proactively offering a policy-compliant alternative with accurate pricing and insurance for a customer in a family emergency, yet the benchmark rewards it
only because
the conversation terminated before the correct action could be executed. Case 24 exhibits the identical pattern with a grieving widower whose $771 booking was confirmed but never executed.
