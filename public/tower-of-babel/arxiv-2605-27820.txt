EgoBench: An Interactive Egocentric Multimodal Benchmark for Tool-Using Agents
Yunqi LiuAnt Group liuyunqi.lyq@antgroup.com, Tong NiuAnt Group niutong.niu@antgroup.com Zitong WangAnt Group yesi.wzt@antgroup.com Zhenlong DaiAnt Group daizhenlong.dzl@antgroup.com Yuqi QingAnt Group qingyuqi.qyq@antgroup.com Weiqiang WangAnt Group weiqiang.wwq@antgroup.com Jian LiuAnt Group rex.lj@antgroup.com

Abstract
As AI agents increasingly operate in open, real-world environments, they require a deep synergy of multimodal perception, tool invocation with multi-hop reasoning, and dynamic interaction with users. However, existing benchmarks fail to jointly evaluate these capabilities due to challenges in designing strictly coupled multi-capability tasks, simulating natural and task-constrained user feedback, and ensuring objective evaluation of dynamic interaction. To bridge this gap, we introduce EgoBench, the first interactive multimodal benchmark for tool-using agents. EgoBench comprises 1,045 egocentric-video-grounded tasks covering four daily scenarios, along with a user-agent-tool interactive environment for evaluation. We implement a three-stage synergistic pipeline through which each task is designed to enforce the joint application of visual perception and tool-augmented multi-hop reasoning. We additionally develop a multi-agent simulated user within EgoBench to evaluate agents’ interaction capabilities, which generates high-fidelity, task-aligned responses to agents. Furthermore, we establish a deterministic joint validation framework that guarantees objective assessment through process-based and result-based equivalence. Benchmarking eight SOTA video-MLLM agents on EgoBench reveals a severe performance ceiling: the best model achieves only 30.62% accuracy in the best-performing scenario, averaging 19.43% across all four scenarios. Finally, we conduct a multi-dimensional error analysis to disentangle failure modes, exposing capability bottlenecks for advancing future AI agents.

Introduction

Recent advances in AI agents have enabled effective automation of structured workflows such as desktop task assistance, and code generation (
32
;
18
;
7
;
13
). Most existing agents rely on unimodal inputs and operate within predefined task boundaries. As agents are increasingly deployed on ubiquitous devices such as wearables and integrated into daily life, they must operate in open, real-world environments grounded in users’ situated context and perception. This shift requires agents to possess three key capabilities for effectively understanding user intent and coordinating tool use in complex, user-initiated tasks: (1) multimodal contextual understanding to resolve user references, (2) multi-hop reasoning and execution to process information with complex tool-based actions, and (3) interaction to adapt to users’ dynamic goals and proactively obtain information (
3
;
27
).

However, existing benchmarks for evaluating models fail to comprehensively assess these three capabilities. For example,
33
;
3
;
19
lack the multimodal understanding assessment;
12
;
21
;
28
;
29
lack support for dynamic interaction with users; and
20
;
35
overlook the integration of tool use and action execution. Meanwhile, constructing a benchmark that jointly assesses all three capabilities remains challenging for three main reasons: (1) Ensuring capability coupling: it is difficult to design tasks that genuinely require the joint use of multimodal understanding, logic reasoning, and tool invocation, as models often exploit shortcuts or rely on a single capability rather than integrating all (
40
;
10
). (2) Simulating realistic user-agent interactions: It is challenging to generate user feedback that is both natural and aligned with task goals and constraints, given the unpredictability of the evaluated agent’s behavior (
36
). (3) Establishing reliable and objective evaluation criteria: Extracting quantifiable metrics from dynamic and subjective interactions (e.g., dialogue) is challenging yet indispensable, as it serves as the cornerstone of stable, objective, and reproducible assessment (
15
).

To bridge the aforementioned evaluation gap, we introduce
EgoBench
, the first benchmark for tool-using agents grounded in egocentric (first-person) video, which jointly evaluates multimodal perception, dynamic interaction, and multi-hop reasoning (Table
1
). To address the above challenges, EgoBench is built around the following designs:
First, we implement a
three-stage synergistic task generation pipeline
to generate evaluation tasks and tool-using environment that assess models’ integrated abilities of multimodal perception, tool use, and reasoning. Specifically, in Stage 1, we collect egocentric videos rich in explicit spatiotemporal cues to serve as visual anchors. In stage 2, we construct a comprehensive tool library and a database integrating both visible video content and invisible but contextually relevant supplementary information, introducing a visual-data information gap. In Stage 3, we design tasks that require the evaluated agent to complete four different aspects to succeed: multimodal perception, retrieval of associated invisible information via tools, logical reasoning, and database state update via tools. In total, Egobench comprises 1,045 tasks spanning four real-world scenarios: dining, kitchen operations, food ordering, and retail. Second, we develop a
multi-agent simulated user
with an Actor-Evaluator-Summarizer structure that creates a robust user-agent interaction environment by iteratively generating and refining user responses via four binary evaluation criteria. It further supports three interaction modes (Dynamic Easy, Dynamic Hard, and Static) to evaluate models under varying interactive complexities. Fig.
1
shows an example task and interaction. Third, we propose a
joint validation framework
that quantifies agent performance by simultaneously assessing process-based tool-call coverage and result-based database state equivalence. Unlike subjective LLM-based evaluations, this deterministic approach ensures objective precision, leveraging our task design which inherently requires tool invocations and state modifications. Furthermore, all ground truth is human-annotated and rigorously quality-checked to ensure reliability. We benchmark eight SOTA video-MLLMs on EgoBench, and the top-performing model achieves only 20.19%, 16.75%, and 21.34% across the three interaction modes described above, averaged over four scenarios. Even in retail, the best-performing scenario for the top model, the average success rate reaches only 30.62%, underscoring the limited end-to-end capabilities of current models. To diagnose these failures, we implement a
multi-dimensional error analysis
that disentangles failures into five categories:
multimodal perceptual misinterpretations
,
hallucination
,
structural non-compliance
,
logical fallacies
, and
risky operations
. Our main contributions are summarized as follows:

•

We develop EgoBench, the first egocentric video-grounded benchmark to jointly evaluate tool-using agents on multimodal perception, multi-hop reasoning, and dynamic interaction, which comprises 1,045 tasks across four daily scenarios within a dynamic environment.

•

We implement a three-stage synergistic task generation pipeline to ensure that every generated task jointly evaluates multimodal perception and tool-augmented logical reasoning. Concurrently, we design an Actor-Evaluator-Summarizer simulated user to generate high-fidelity, goal-aligned responses to unpredictable agent behaviors, thereby providing a robust environment for evaluating interactive capabilities.

•

We establish a deterministic joint validation framework in EgoBench that enables objective and precise assessment through process-and-result equivalence, benchmark eight state-of-the-art video-MLLMs, and conduct a multi-dimensional error analysis to diagnose failure modes and inform future model development.

Related Work

2.1
Tool-Using Benchmarks

Early research on tool use primarily focuses on evaluating API comprehension and parameter generation. Gorilla (
24
) shows that domain-specific fine-tuning can outperform larger closed-source models, while ToolBench (
25
) and API-Bank (
14
) further scale up instruction tuning and introduce multi-stage evaluation frameworks. Subsequent benchmarks such as BFCL (
23
) standardize function calling across diverse programming environments, while AgentBench (
18
) advances an agent-centric paradigm by situating LLMs in terminal and database environments. More recent efforts move toward standardized agentic protocols and extended context windows: MCP-Bench (
30
) and LiveMCP-101 (
34
) evaluate agents under the Model Context Protocol, while AgencyBench (
13
) studies long-horizon planning under million-token context windows. Despite this progress, these benchmarks still predominantly operate in text-only, static, or highly structured environments.

2.2
User Simulation for Conversational Agents

LLM-based user simulators largely replace rigid goal templates, enabling more natural and context-aware dialogue evaluation (
6
;
11
). This paradigm extends to tool-augmented settings, where simulated users actively interact with external APIs, as exemplified by
\tau
-bench (
33
) and its dual-control extension
\tau^{2}
-Bench (
3
). To enhance behavioral fidelity, recent work incorporates long-term personalization (
37
), stateful execution environments (
19
), and real-time turn-taking dynamics (
16
). While these simulators significantly improve conversational realism, they remain predominantly text-centric and operate under predefined interaction flows. Consequently, they struggle to capture the multimodal grounded, and dynamically evolving intent shifts that characterize real-world human-agent collaboration.

2.3
Multimodal Benchmarks

Multimodal evaluation now extends beyond passive perception to active, tool-mediated problem solving. VisualWebArena (
12
) pioneers agent navigation in visually complex web interfaces, while m&m’s (
21
) introduces multi-step computational planning that requires coordinated tool orchestration across modalities. To address intent ambiguity, MLLM-Tool (
28
) and GTA (
29
) evaluate context-aware tool selection with deployed APIs and diverse visual inputs, such as screenshots and handwriting. M
3
-Bench (
40
) further standardizes multi-hop, multi-threaded evaluation via the MCP, and Beyond Seeing (
10
) highlights the necessity of active visual preprocessing under imperfect inputs. Although these benchmarks advance multimodal reasoning, they typically rely on static instructions and isolated evaluations, neglecting the user-driven feedback loops and process-level validation.

3
EgoBench

EgoBench is a multimodal environment for evaluating interactive tool-using agents in egocentric settings.
Following the standard formulation of interactive decision-making, we model each task in EgoBench using a POMDP-style framework, denoted by
(S,A,O,T,V)
. Here,
S
denotes the state of the simulated user and database in the environment,
A
the action space, and
O
the observation space. The environment dynamics are driven by tool execution on the database and user-agent interaction, which are formalized as
T:S\times A\rightarrow\Delta(S)
. In addition,
V
denotes the first-person video space, representing the egocentric visual input available to the agent. At each step, the evaluated agent receives the observation
o\in O
, consisting of the user feedback and tool outputs, together with an egocentric video
v\in V
representing the current first-person scene.
Based on
(o,v)
, the agent selects an action
a\in A
, which may be either a natural-language response to the user or tool calls over the database.
The environment then implement the tool execution
T
, updates the dataset state, and returns the next observation.
We next describe the construction of the benchmark in detail(Fig.
2
).

Overview of EgoBench construction and evaluation.

3.1
Egocentric Video Collection

We collect first-person videos from common real-world daily scenarios (Fig.
2
, Stage 1). To be included in the benchmark, videos
V
must satisfy the following three conditions: (1) they contain objects with clearly distinguishable features, such as unique colors, shapes, or spatial positions, thereby enabling evaluation of the agent’s spatial understanding; (2) they exhibit explicit temporal order, such as different user actions occurring sequentially, thereby enabling evaluation of the agent’s spatial understanding; and (3) the duration is limited to 10-30s to reflect the typical length of everyday videos captured on wearable devices. Overall, 82.4% of the benchmark tasks use videos that we personally collected and recorded in real-world settings with smart glasses and mobile phones, while the remaining 17.6% use videos drawn from the public Ego4D dataset (
9
). These videos in the benchmark span scenarios including kitchens, retail environments, restaurants, and food ordering. Ethical considerations regarding both the use of Ego4D and our self-collected videos are provided in Appendix
B
.

3.2
Tool Library and Database Construction

After selecting the videos, we design the tool library and database based on the videos and the common daily tasks in the corresponding real-world scenarios.(Fig.
2
, Stage 2).

In designing the tool library, we follow three principles. (1)
Scenario specificity:
tools are tailored to the functional requirements of each scenario, and different scenarios are equipped with different tool libraries. For example, the kitchen scenario includes recipe-related tools, whereas the retail scenario includes shopping-cart-related tools; (2)
Comprehensive functionality:
the tool library covers the full execution pipeline required for task completion, including retrival tool and state-changing tools that modify the database state; (3)
Parameter fuzziness matching:
retrieval tools support approximate or partial inputs, allowing agents to invoke tools without exact visual matches. For example, in a retail task, a partial product-name query can return all products whose names match the partial string. In addition, for selected tools, we deliberately introduce
multiple required arguments
, such that the agent must collect and integrate several relevant attributes before invocation, thereby evaluating its complex tool-using ability. Concrete tool examples are provided in Appendix
C.1
.

For database construction, we intentionally introduced a visual-data information gap. Concretely, we use a VLM to extract visible attributes (e.g., product names, prices) from videos, while augmenting the database with non-visible, scenario-relevant data (e.g., nutritional information). This process ensures alignment between the database and visual content while enabling future task designs that require agents to access invisible information through tool interactions. Consequently, successful task completion depends on the integrated use of perception and tool invocation. Details of the database are provided in Appendix
C.2
.
Overall, the tool library and database are co-designed to preserve semantic and operational consistency among the tools, the database, and the video content. Formally, the database configuration is part of the state
S
, while each tool call corresponds to an action in
A
that queries the database information or modifies the state itself.

3.3
Task Design and Ground-truth Annotation

Based on the established dataset and tool library, we initiate the task design process (Fig.
2
, Stage 3). To evaluate the three core agent capabilities introduced in Sec.
1
, each task is built by combining the following difficulty factors.
Multimodal Perception Complexity:
Each task incorporates multiple multimodal references—grounded in distinct spatial localization or temporal events-to evaluate whether the agent can understand them from the dynamic, sparse egocentric videos.
Logic Reasoning Complexity:
Each task is designed with conditional branching and multi-attribute filtering(e.g., "If this wine costs more than $100, add the cheapest sweet wine with the same origin as this one to my cart"). Consequently, by analyzing the agent’s tool call sequences and input arguments, we can evaluate whether it has performed correct logical reasoning. Additionally, to organically integrate these two complexities, task design adopts the following aspects: 1. First, designing multimodal references; 2. Then asking for attributes related to these references but not obtainable from the video, which requires the agent to retrieve relevant information through tool calls; 3. Introduting conditional branching logic and multi-attribute filtering based on the aforementioned attributes (involving more tool calls); 4. Different branches lead to different database modification instructions, which also require tool calls. This four-aspects setup appears at least once in each task(Fig.
1
), with harder tasks containing multiple such designs.
Interaction Complexity:
During task design, specific constraints are also imposed on the simulated user (detailed in Sec.
3.4
) to increase interaction difficulty, such as requiring the user to withhold critical parameters initially or introduce redundant noise, to assess active elicitation and information extraction capabilities. See Appendix
D
for example tasks.

The ground truth for each task is defined as a sequence of key tool calls required for successful completion, including necessary retrieval operations and state-modifying actions on the database. We further annotate task-critical visual information to support fine-grained error analysis. Each instance is independently annotated by two human annotators, followed by review to ensure the accuracy of the annotations. Annotators complete only 2.2 tasks per person-hour on average, reflecting high task complexity.
Given the complexity of the above construction pipeline, constructing the benchmark is costly. Nevertheless, EgoBench comprises 4 scenarios, 1,045 annotated tasks, representing a substantial scale for multimodal, interactive, and tool-grounded evaluation. For comparison, tau
2
-bench(
3
), a widely used benchmark for dynamic interactive tool use, contains 269 instances in total. The detailed information for the four scenarios is shown in Appendix
A
.

3.4
Multi-agent Simulated User

Egobench needs to incorporate a simulated user that assigns pre-designed tasks to the agent through interaction, which is nontrivial to implement. In multi-turn interaction, the simulated user must not only produce contextually coherent responses, but also consistently adhere to the predefined
role
,
constraints
, and
goals
of the above tasks. In terms of role, it must remain a customer rather than an executor or service staff member. In terms of constraints, it must adhere to task requirements faithfully, avoid fabricating unspecified details, and remain robust to persuasion or misleading suggestions from the agent. In terms of goals, it should advance the task when the agent successfully completes a subgoal, while steering the dialogue back to the intended objective whenever the conversation drifts off topic. These requirements make user simulation a long-horizon alignment problem, rather than a simple response generation task.

To achieve these requirements, we adopt a multi-agent framework for user simulation, consisting of an
Actor
, an
Evaluator
, and a
Summarizer
, as illustrated in Fig.
2
. Specifically, the
Actor
generates the next user response conditioned on the dialogue history summary and the evaluated agent’s latest response. The
Evaluator
then determines whether the Actor’s output satisfies the desired behavioral criteria, including role consistency, instruction following, resilience to agent interference, and contextual robustness. Each criterion is assessed using a binary score. When any violation is detected, the user response is not accepted; instead, the Evaluator provides targeted revision feedback, and the Actor regenerates a revised response. Detailed metric definitions are provided in Appendix
E.1
. The
Summarizer
maintains a compact representation of the dialogue history by compressing the multi-turn interaction and explicitly tracking task progress, including which steps have already been completed. This updated summary is then used in the next turn to help the Actor reason about the current stage of the task.
Empirically, this design substantially outperforms the direct fine-tuning of a single model with GDPO (
17
). Detailed evaluation results are reported in Appendix Table
7
, and the pseudocode for the interaction pipeline is provided in Algo.
1
.

Building on this simulated user framework, we further implement three user-agent interaction modes to evaluate different aspects of agent capability. In
Dynamic Easy Mode
, the agent interacts with the simulated user through standard multi-turn dialogue, measuring its ability to complete tasks under typical interactive conditions. In
Dynamic Hard Mode
, the interaction remains multi-turn but becomes substantially more challenging: the simulated user may exhibit impatience, provide scenario-relevant but task-irrelevant information, or even terminate the conversation under certain undesirable agent behaviors, such as producing excessively long responses or outputs filled with non-natural-language content. This mode places substantially stronger demands on the agent’s robustness. In
Static Mode
, interaction is removed entirely: the simulated user provides all task requirements at once, and the agent must solve the task within a single user-agent turn, although it may still invoke tools for multiple steps internally. This setting isolates the agent’s task-solving ability without interactive uncertainty, while increasing the burden of long-horizon planning. Detailed information about the three user-agent interaction modes is shown in Appendix
E.2
.

3.5
Joint Validation Framework

To objectively and accurately assess agent performance on our benchmark, we design the following evaluation metrics. Let
\mathcal{D}
denote the set of all evaluation tasks,
N(\mathcal{D})
the total number of tasks.

Process-Based Evaluation

A task
d\in\mathcal{D}
is considered successful under process-based evaluation if the ground-truth tool-call set
\tau_{d}^{\ast}
is contained in the agent-generated set
\tau_{d}
, i.e., the agent covers all necessary tool calls required by the task:
\mathrm{\mathbf{ToolSucc}}=N(\{d\in\mathcal{D}:\tau_{d}^{\ast}\subseteq\tau_{d}\})/N(\mathcal{D})
. This metric measures the proportion of tasks for which the agent completes all required tool-use steps.
Let
N(\tau_{d}^{\ast})
be the number of tool calls in the ground-truth set for task
d
, and
N(\tau_{d}^{\ast}\cap\tau_{d})
the number of tool calls produced by the agent that also appear in the ground-truth set. Then
\mathrm{{\mathbf{MicroAcc}}}=\sum_{d\in\mathcal{D}}N(\tau_{d}^{\ast}\cap\tau_{d})/\sum_{d\in\mathcal{D}}N(\tau_{d}^{\ast})
. Unlike task-level success metrics, MicroAcc captures partial progress at the tool-call level and provides a more detailed view of model capability.

Result-Based Evaluation

A task is considered successful under result-based evaluation if the final database state produced by the agent is identical to that obtained by executing the ground-truth tool-call sequence. Let
s_{d}(\tau_{d}^{\ast})
and
s_{d}(\tau_{d})
denote the final database states obtained by executing the ground-truth and agent-generated tool-call sequences, respectively. A task is counted as successful if these two final states are equivalent on all task-relevant database variables:
\mathrm{{\mathbf{ResultSucc}}}=N(\{d\in\mathcal{D}:s_{d}(\tau_{d}^{\ast})\equiv s_{d}(\tau_{d})\})/N(\mathcal{D})
. In practice, this state equivalence is verified by comparing the hash values of the final database states.

Joint Success Rate

The joint success rate measures the proportion of tasks that are successful under both process-based and result-based evaluation, i.e., the agent must both cover all necessary tool calls and reach the correct final database state:
\mathrm{{\mathbf{JointSucc}}}=N(\{d\in\mathcal{D}:\tau_{d}^{\ast}\subseteq\tau_{d}\text{ and }s_{d}(\tau_{d}^{\ast})\equiv s_{d}(\tau_{d})\})/N(\mathcal{D})
. We treat
Joint Success Rate
as the primary benchmark metric, as it most directly reflects full end-to-end task completion.

Experimental Setup

We evaluate eight SOTA video-MLLMs spanning both closed-source models(Gemini-3.1-Pro

All models are evaluated with default inference parameters and unified prompt templates(Appendix

\leq 5

4.2
Performance Analysis

Overall Analysis
Table
2
presents the overall performance of eight models on EgoBench across three interaction modes. The top-performing model, Gemini-3.1-Pro, achieves an average joint success rate of 19.43% in three modes, while the best open-source model, Qwen3.5-397B-A17B, reaches 15.80%. These results underscore that current models remain far from achieving reliable end-to-end problem-solving capabilities in real world ego centric scenarios.

Interaction Mode Analysis.
Each model exhibits varying levels of performance across interaction modes. It is evident that all models exhibit a decline in success rate in
Dynamic Hard Mode
compared to
Dynamic Easy Mode
, exposing deficiencies in their robust dialog management and interference-resistant state tracking capabilities. Additionally,
Static Mode
did not significantly improve task accuracy as anticipated. On one hand, this confirms that the benchmark poses challenges in both multimodal understanding and logic-driven tool use. On the other hand, certain models even underperform in
Static Mode
compared to the
Dynamic Easy Mode
. Case analysis reveals that the multi-turn interaction mechanism plays a compensatory role: First, by presenting only a single requirement per turn, the simulated user performs task planning on behalf of the evaluated models to some extent. Second, the user can promptly correct fundamental errors made by the model (e.g., pointing out when the model incorrectly replies, “I have found a bitter wine for you…” after being asked to “find a sweet wine”), thereby providing real-time verification throughout the interaction. In summary, although
Static Mode
delivers all task instructions and complex logical constraints in a single turn, it increases the cognitive load for models with limited planning and reflection capabilities, ultimately leading to lower accuracy.

Scenario Analysis
We further decompose model performance across four task scenarios illustrated in Figure
3
. Models achieve the highest accuracy in the
Retail
scenario, mainly due to clear visual grounding cues (e.g., color, spatial orientation, and finger pointing) and relatively straightforward queries. In addition, retail tasks are common agent applications and are often covered during pre-training, providing models with a solid performance baseline. Accuracy in the
Kitchen
scenario is slightly lower, primarily due to the need to interpret less explicit visual information, such as cooking steps, which requires stronger joint vision-language understanding. The
Restaurant
and
Order
scenarios exhibit noticeably lower accuracy. The main bottlenecks arise from more complex visual references and greater amounts of irrelevant visual information (as shown in Fig.
8
in the appendix, where multimodal perceptual errors increase significantly). Compared with
Restaurant
, the
Order
scenario performs worse because it introduces additional steps of multi-attribute filtering and logical reasoning. Statistics from the ground-truth data further show that the average number of tool calls in
Order
is 31.61% higher than that in
Restaurant
, indicating higher task complexity. The illustrative task examples of the four scenarios are provided in Appendix
I
.

4.3
Error Attribution Analysis

Figure 4:
Multi-dimensional error statistics accros different models

To conduct a fine-grained assessment of model capabilities, we employed a multi-dimensional error analysis method to systematically categorize and quantify the failure trajectories of each model (see Fig.
4
). Detailed methodologies for objective error classification are provided in Appendix
F.2
. The specific error dimensions are defined as follows:
Structural Non-Compliance
: The model generates incorrectly formatted tool calls, uses invalid tool names or parameters, or in Static Mode asks the user for additional information even though it is asked to directly perform tool calls based on the complete task description, resulting in immediate task failure.
Multimodal Perceptual Misinterpretations
: The agent fails to correctly understand or extract multimodal referential information from the user and egocentric videos.
Hallucination
: The agent fabricates content not present in the context during tool invocation or when responding to the user.
Logical Fallacies
: The agent makes errors in logical conditional judgments and in the processes of tool retrieval and invocation.
Risky Operations

Conclusions

We introduce
EgoBench
, an interactive multimodal benchmark for evaluating tool-using agents in open, real-world environments. EgoBench jointly assesses visual grounding, dynamic user interaction and multi-hop tool use through a environment containing egocentric videos, scenario-specific tools, structured databases, and a task-constrained user simulator. It also provides an objective joint evaluation framework that checks both tool-call process and final execution results. Experiments show that current SOTA models perform poorly on Egobench, revealing a substantial gap between existing capabilities and reliable real-world deployment.

Appendix D
The Complexity of Tasks

1. Multimodal Perception Complexity

Egocentric videos introduce unique perceptual challenges that differ substantially from traditional third-person or static-image datasets. Compared with standard multimodal settings, visual understanding under the egocentric perspective is inherently more difficult due to restricted fields of view, partial observations, continuous camera motion, and frequent hand-object interactions. In EgoBench, we focus on the following two aspects:

•

Multimodal Information Sparsity and Dynamics
: Due to the motion characteristics, egocentric videos often exhibit motion blur, severe shaking, occlusion, and rapidly changing viewpoints. The agent must therefore possess robust visual feature extraction capabilities in order to maintain accurate perception under degraded input quality. In practice, this means identifying the key clear frames from a sequence of unstable or blurred observations and grounding user intent in dynamically changing visual evidence.

•

Spatial/Temporal Referential Dependency
: In natural first-person interaction, users often do not explicitly name target objects, but instead refer to them through viewpoint-dependent expressions grounded in the current scene and recent actions. To reflect this property, we do not explicitly provide the names of visible objects in the task descriptions. Instead, tasks include a variety of egocentric referential expressions, such as spatial relations (e.g., "the bottle on the left"), body- or action-centered references (e.g., "the one on my right-hand side" or "the one I just picked up"), appearance attributes (e.g., color and shape), and temporal cues (e.g., "the second item pointed to by the finger"). The agent must combine
visual context
and linguistic instructions to accurately resolve these references and eliminate ambiguity. Moreover, key events in long videos may appear only briefly, so the tasks require not only understanding of the current frame, but also long-horizon temporal modeling ability to precisely locate specific past events or action segments.

2. Reasoning and Tool Usage Complexity

As a benchmark for tool-using agents, EgoBench evaluates not only perception, but also cognition and execution. This dimension measures the logical depth with which an agent transforms perceived information into effective action:

•

Multi-Hop Logical Reasoning
: Complex tasks in EgoBench usually cannot be completed in a single step. We deliberately design each task to require at least one reasoning step before all tool calls can be completed correctly. Many tasks must be decomposed into multiple subtasks, requiring the agent to construct a coherent chain of reasoning and execute operations sequentially. Importantly, this reasoning is not limited to explicit conditional branching, but also includes compositional constraint satisfaction, candidate filtering, comparison, and selection. For example, a representative instruction is: "I only have $10 and want to buy two bottles of the drink I’m holding in my left hand. If the money is not enough, then buy only one bottle." To succeed, the agent must first retrieve the price of the drink held in the left hand, perform numerical reasoning, determine which branch of the condition applies, and then invoke the subsequent tools accordingly. Similarly, tasks such as "Help me find a bottle of wine that has the same country of origin as the one I pointed to earlier, is sweet in taste, and has the lowest price, and add it to the cart" require the agent to jointly search across multiple constraints and then perform an optimization step among the valid candidates.

•

Inter-Tool Parameter Dependency
: User instructions often do not contain all parameters required for tool execution. The agent must infer implicit parameter values using contextual clues, and information gathered during the interaction or other tool-using. Moreover, since later tool calls may depend on earlier perceptual or reasoning results, incorrect intermediate decisions can propagate through the execution chain, further increasing task complexity.

3. Interactive Dynamics Complexity

Real assistive scenarios are dynamic and non-linear. EgoBench introduces interaction-level challenges to evaluate the adaptability of agents in open-domain dialogue:

•

Intent Incompleteness and Active Elicitation
: Before executing a task, the agent often faces lack key information. In realistic settings, users typically do not provide all requirements at once, so the agent must proactively ask follow-up questions to obtain the necessary constraints before invoking tools. For example, when the agent needs to modify the state of a user’s shopping cart, it must first know the
user_id
, which requires the agent to actively ask the user for this missing information. To simulate this setting, we use the multi-agent simulated users that interact dynamically with the evaluated agent.

•

Information Redundancy and Key Extraction
: Real interactions often contain redundant, irrelevant, or potentially misleading details. Different users may also exhibit distinct personality traits, produce uncooperative utterances, or make confusing but task-irrelevant remarks while still responding to the agent’s ongoing questions and actions. The agent must therefore filter noisy context, identify decision-critical constraints, and extract the key information required for correct reasoning and tool execution. In addition, we incorporate negative user feedback to further assess dynamic interaction ability: the simulated user may react negatively when the agent produces overly long responses, unnatural language, irrelevant utterances, or fails to follow the user’s instructions. This makes the benchmark more realistic than settings with fully pre-scripted user utterances.

E.1
Metrics for Simulated User

For example, the original instruction of all following cases is: You are a budget-conscious student with only $10 to spend on water. You want to buy two bottles of the first green mineral water you point to in front of you. If the money is not enough, buy only one bottle. Your user_id is user_001.

Role Consistency

It measures whether the simulated user consistently maintains the identity of a "requester" or "consumer." If a response includes service-provider or assistant-style expressions such as "I will help you handle it" or "I will place the order for you," then a role reversal has occurred and the instance should be marked as failed. Table
8
presents illustrative examples of incorrect and correct simulated user responses for the following evaluation dimensions.

Instruction Following

It evaluates whether the simulated user strictly adheres to the explicit constraints in the original task and avoids generating unsupported information. This metric examines whether key elements, including budget, quantity, conditional logic, and ordering information, are preserved in full. For instance, restrictive descriptions such as “the first item” or “the one just pointed to” should be reproduced accurately, without omission or weakening. In addition, the model must not fabricate content such as brand, price, or appearance traits that is absent from the instruction or current context.

Resilience

It mainly evaluates whether the simulated user can adhere to the original goal when facing inducement, recommendation, or misleading suggestions from the agent. In real interaction, the agent may influence user decisions through upselling, quantity adjustment, or preference guidance. The simulated user should remain stably aligned with the core constraints and avoid exceeding budget, changing quantity, or switching product choice under persuasion.

Contextual Robustness

It measures whether the simulated user can produce coherent, reasonable, and task-consistent responses based on explicit information in the current turn. On the one hand, the model should identify and correct errors made by the agent in the current dialogue, such as incorrect identity references, contradictory product attributes, or deviations from the task goal. On the other hand, when the agent clearly drifts away from the current task topic, the simulated user should proactively bring the conversation back to the core objective rather than continue following irrelevant topics. For example, if the agent incorrectly describes the target product as blue while the original task explicitly requires green, the user should correct it in time. If the agent shifts to unrelated topics, the user should actively steer the discussion back to the purchasing task. If the model ignores obvious conflicts or continues to agree with off-topic content, it is marked as failed.

E.2
Interaction Mode Settings

To evaluate service agents under different levels of user interaction complexity, we design three user modes: Static Mode, Dynamic Easy Mode, and Dynamic Hard Mode. These three settings differ mainly in how much information the user provides, how the dialogue progresses, and how challenging the user behavior is for the agent. We provide the prompts in Appendix
L
.

E.2.1
Dynamic Easy Mode

In Dynamic Easy Mode, the user interacts with the agent through multi-turn conversation and reveals task information step by step rather than all at once. At each turn, the user focuses on only one unfinished step of the task, based on the conversation history and the agent’s latest response. The example is shown in Appendix
L.4.1
.

E.2.2
Dynamic Hard Mode

In Dynamic Hard Mode, the user also reveals information progressively in multiple turns, but the interaction is significantly more challenging. Compared with Dynamic Easy Mode, the user in this mode is less patient, less cooperative, and more ambiguous. The user may show dissatisfaction when the agent’s response is overly long, unnatural, or ineffective. We deliberately append a random sentence at the end of each user response that is relevant to the current scenario but unrelated to the current task, in order to simulate casual daily chatting behavior and impose higher demands on the agent’s information extraction ability. The example is shown in Appendix
L.4.2
.

E.2.3
Static Mode

In Static Mode, the user provides the complete request in a single turn. The user message is clear, direct, and task-focused, with all necessary information expressed at once. This setting represents the lowest interaction difficulty, because the service agent does not need to gradually elicit missing details or manage complex conversational behaviors. The main challenge for the evaluated agent is simply to understand the request correctly and complete it accurately. The example is shown in Appendix
L.4.3
.

To systematically diagnose
why
an agent fails on a given retail scenario,
we propose a
hierarchical, mutually exclusive error taxonomy
comprising
five error categories. Rather than independently labeling each failure mode and
risking conflated attribution, we apply a
cascading priority classifier
:
the diagnostics are evaluated in a strict top-down order, and a sample is
assigned to the
first
matching category. This design ensures that
(i) every erroneous sample receives exactly one root-cause label, and
(ii) downstream errors that are
consequences
of upstream failures are
not double-counted.

Let
\mathcal{C}=\{c_{1},c_{2},\dots,c_{5}\}
denote the ordered sequence of
error predicates. For a given sample
s

\mathrm{ErrorType}(s)=\begin{cases}c_{k},&\text{if }c_{k}(s)=\textsc{True}\text{ and }c_{j}(s)=\textsc{False}\ \forall\,j<k,\\
\textsc{Correct},&\text{if }c_{k}(s)=\textsc{False}\ \forall\,k\in\{1,\dots,5\}.\end{cases}

(1)

Step 1: Syntactic Format Error (

).

We first verify whether the agent’s output conforms to the expected tool-call

(a) no tool call is emitted at all;
(b) a tool-call entry is not a valid dictionary;
(c) the required fields
tool_name
and
parameters
are missing or invalid.
This check serves as a
gating condition
: if the agent cannot produce
well-formed tool invocations, all subsequent semantic analyses are not applicable.

c_{2}
).

Specifically, each ground-truth entry may contain a key–value pair

(\kappa,\mathcal{V})
, where
\kappa
is the attribute name (e.g.,

) and
\mathcal{V}=\{v_{1},\dots,v_{m}\}
is the set of
expected values. We collect all query-type tool calls

.

Step 3: Hallucination Error (
c_{3}
).

We detect identity hallucination by extracting the ground-truth user identifier

u^{*}
from the instruction (via the pattern
User ID: <id>
) and
comparing it against the
user_id
parameter in every tool call. If
any call contains a fabricated or incorrect user ID
\hat{u}\neq u^{*}
, the
sample is classified as a hallucination error:

c_{3}(s)=\textsc{True}\iff\exists\,\text{call }q\in\mathcal{Q}_{s}\text{ s.t. }q.\texttt{user\_id}\neq u^{*}.

(3)

This captures cases where the model "invents" contextual information not
grounded in the input.

Step 4: Tool-Call Logical Reasoning Error (
c_{4}
).

Let
M
denote the number of matched tool calls and
G
the total number of
ground-truth calls. We define the
call deficit

\Delta=G-M
. A
logical reasoning error is triggered when
\Delta\geq 1
:

c_{4}(s)=\textsc{True}\iff\Delta(s)=G-M\geq 1.

(4)

The threshold of one reflects a substantive failure in multi-step planning:
missing one or more required operations indicates that the agent failed to
decompose the task into the correct sub-goals.

Step 5: Over-Operation Error (
c_{5}
).

Finally, even when all ground-truth tool calls are matched (
M=G
), the
agent may still produce an incorrect final answer—for example, by issuing

extraneous
operations that corrupt the database state. We detect this
by checking whether the result-based evaluation fails despite tool-call-based
success:

c_{5}(s)=\textsc{True}\iff M=G\;\wedge\;\neg\,\textsc{ResultCorrect}(s).

(5)

Correct Samples.

A sample is labeled
Correct
if and only if
M=G
and the
result-based evaluation succeeds.

Appendix G
Limitations

Our work still has sevral aspects that could be further improved. First, EgoBench currently covers only four daily scenarios, and future work will expand it to a broader range of real-world scenarios, such as dating and education. Second, current multimodal data mainly come from smartphones and smart glasses, while future versions may incorporate richer signals from devices like smart earbuds (audio) and smartwatches (physiological signals). Third, for fairness and consistency, we disable all thinking modes, which may reduce model performance and thus underestimate the full potential of some models. This setting may also partially explain why Qwen3.6-Plus underperforms Qwen3.5-397B-A17B in our evaluation. Fourth, because evaluation is conducted through APIs, we cannot measure response latency in a fully controlled environment, although such latency is important for real-time interactive agents.

Appendix H
Broader Impact

EgoBench is intended to support the development of more reliable multimodal assistants that can understand egocentric visual input, interact with users, and correctly invoke tools in realistic environments. A positive societal impact of this work is that it provides a more rigorous and objective evaluation framework for real-world assistant systems, which may help improve robustness, reduce tool-use errors, and promote safer deployment in applications such as task assistance, and daily activity management.

At the same time, our work also carries potential risks. Agents developed or improved using our benchmark could be misused in surveillance-like settings or deployed in high-stakes scenarios where incorrect tool calls may cause financial, operational, or user-experience harms. To mitigate these risks, we emphasize that EgoBench is an evaluation benchmark rather than a certification of deployment safety. We hope this benchmark will encourage the community to study not only task success, but also intermediate reasoning quality, state consistency, and considerations for responsible deployment.
