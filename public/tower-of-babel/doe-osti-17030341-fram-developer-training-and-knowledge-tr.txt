 1. Executive Summary
The FY26 FRAM Developer Training and Knowledge Transfer project focused on improving the
accessibility, maintainability, and transferability of technical knowledge associated with FRAM
software development. The project work plan identified three primary documentation
objectives: documenting development-environment setup and known issues, documenting use
of the software testing suite and identifying testing gaps, and documenting the FRAM code
architecture, including the purpose of individual modules and their interfaces. The project also
called for reporting the impact of the Human Capital Development (HCD) investment through
metrics such as individuals trained, technical resources created, knowledge gained, and future
work.

 During FY26, these objectives were addressed primarily through the implementation of
Doxygen-based software documentation for the FRAM code base. Doxygen provides a
structured method for generating

 The resulting documentation provides a centralized technical resource for current and
future FRAM developers. In addition to preserving developer knowledge, the Doxygen site
provides an expandable foundation that can be maintained as the FRAM software evolves. This
reduces dependence on informal knowledge transfer and improves the ability of new developers
to understand the development environment, testing practices, code organization, and
relationships among major software components.

 2. Project Objectives
The FY26 Project Work Plan defined the following documentation and knowledge-transfer
activities:

 1. Development environment documentation — Create guidance for setting up the
 development environment and document known issues.
 2. Testing documentation — Create a manual describing how to use the testing suite,
 identify modules tested and applicable use cases, and report gaps in testing.
 3. Code architecture documentation — Describe each module, how it is used, and how
 modules interface with one another.
 4. HCD impact reporting — Record the impact of the investment, including individuals
 trained, technical resources produced, knowledge gained, and future work.
 5. Final project reporting and closeout.

 These activities and their associated documentation deliverables were established in the
FY26 project execution plan. The use of Doxygen supported these objectives by consolidating
developer-oriented information into a consistent and maintainable documentation framework
rather than maintaining disconnected documents that can become outdated as the software
changes.

 3. Doxygen Documentation Approach
Doxygen is a software documentation-generation system commonly used for source-code
projects. It processes specially formatted comments and source-code structure to generate
documentation in formats such as HTML. For the FRAM project, the HTML output provides a
website-like interface through which developers can navigate the software and associated
technical information.

 A major advantage of this approach is that documentation can reside close to the
software it describes. As developers update classes, functions, interfaces, or modules, the
corresponding documentation can be updated within the same development workflow. The
Doxygen output can then be regenerated to provide an updated technical reference.

For FRAM, this approach supports knowledge transfer in several important ways:

 • It provides a single, searchable technical reference for developers.
 • It organizes documentation according to the actual structure of the source code.
 • It allows developers to move from high-level descriptions to detailed implementation
 information.

 • It documents relationships between software components rather than presenting
 individual files in isolation.
 • It encourages documentation to remain synchronized with future code changes.
 • It gives incoming developers a starting point for understanding unfamiliar portions of the
 code base without relying exclusively on direct instruction from experienced developers.

The Doxygen site therefore serves both as a reference for experienced FRAM developers and as
a training resource for personnel to become familiar with the software.

 4. Development Environment Setup and Known Issues
One objective of the FY26 effort was to create guidance for development-environment setup and
document known issues. Development environment information was incorporated into the
documentation framework so that developers have a defined location for information needed to
begin development work. Centralizing this information is particularly important for knowledge
transfer because environment configuration is often knowledge that is learned informally and
can otherwise be lost when personnel transition to other work.

The documentation provides a framework for capturing items such as:

 • required development tools and dependencies;
 • configuration and setup steps;
 • expected directory or repository structure;
 • build-related considerations;
 • recurring setup problems or known issues; and
 • solutions or workarounds identified during development.

This material reduces the amount of trial-and-error required for a new developer to establish a
working FRAM development environment and provides a repeatable onboarding resource.
Where environment-specific issues continue to be identified, the Doxygen documentation can
be updated as those issues are resolved or new configurations are introduced.

 5. Code Architecture Documentation
The largest documentation activity identified in the FY26 work plan was development of code
architecture documentation describing each module, its use, and the interfaces among modules.
Doxygen is particularly well suited to this objective because it derives much of its organization
from the source-code structure itself. Rather than documenting architecture only as a static
narrative, the generated documentation allows developers to navigate between related software
elements and examine component details at multiple levels.

The FRAM Doxygen documentation was used to capture and organize information concerning:

 • major software modules;
 • the purpose and responsibilities of individual modules;
 • important classes, functions, or related software elements;
 • interfaces and dependencies between components;
 • relationships within the code base; and
 • developer-facing information needed to understand or modify the software.

 This documentation improves the ability of developers to form a high-level mental model of
the FRAM code base before examining implementation details. It also supports targeted learning
because developers can navigate directly to the component relevant to the task they are
performing. The architecture documentation is expected to be particularly valuable for future
developer onboarding. It reduces reliance on knowledge held by individual developers and
creates a repeatable mechanism for communicating how the software is organized.

 6. Testing Documentation
The FY26 work plan also required documentation describing how to use the FRAM testing suite,
including the modules tested, relevant use cases, and gaps in testing. For the purposes of this
report, define the following:

 • Testing: Verify the software runs as expected. Check for bugs, performance issues etc.
 Can be at the application level or unit level. Can be manual or automated.
 • Validation: Verify that FRAM’s analysis results are correct and gives correct uncertainty
 values on the results.

At this time there is no testing framework in place for FRAM at either the application or unit level.
Validation is performed via batch analysis and Excel calculations. An automated validation suite
is under development. The Doxygen documentation described above will provide a suitable
location to document the validation suite when completed.

 7. HCD Impact
The project work plan identified the need to report HCD impact through measures such as the
number of individuals trained, technical resources created, knowledge learned, and future work.

The primary technical resource created during this effort is the FRAM Doxygen documentation
set. Unlike a one-time training presentation, the Doxygen site remains available after completion
of the FY26 effort and can continue to support both independent learning and instructor-led
developer training.

Technical Resources Created

 • FRAM Doxygen-generated developer documentation website.

 o Development-environment setup and troubleshooting information.

 o Testing-suite documentation and associated testing information.

 o Code/module architecture documentation.

 o Detailed source-level reference material generated from the documented code.

 o A maintainable framework for adding future FRAM developer documentation.

Personnel / Training Impact

 • Individuals directly trained or supported: 2
 • Individuals contributing to or reviewing documentation: 2
 • Training or knowledge-transfer sessions conducted: Numerous

The principal HCD benefit of the work is the conversion of developer knowledge into a persistent
technical resource. Knowledge that previously may have required direct communication with an
experienced developer can increasingly be obtained through the documentation. This improves
continuity when personnel change and provides new developers with a more structured path for
learning FRAM.

Improved Developer Onboarding

A new developer can use the Doxygen site as an initial reference for understanding the software,
locating modules, reviewing component responsibilities, and becoming familiar with
development and testing practices.

Reduced Knowledge Loss

Technical knowledge is captured in a form that can remain available even when individual
developers are unavailable or transition to other projects.

Improved Maintainability

Because Doxygen documentation can be maintained alongside source code, developers can
update technical descriptions as implementations change. This makes the documentation
framework more sustainable than a stand-alone architecture document that is rarely revisited.

Improved Code Navigation

Generated links among documented software entities allow developers to move through related
components and understand software relationships more efficiently.

Support for Future Training

The documentation provides a common technical reference that can be used during future FRAM
developer training activities. Trainers can point new developers to specific modules or pages
while trainees retain access to the same material afterward.

Foundation for Continued Documentation

The FY26 effort establishes a documentation structure that can be expanded as the code base
and developer community evolve.
