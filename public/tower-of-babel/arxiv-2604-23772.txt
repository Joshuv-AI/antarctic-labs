Abstract
. Users browsing the web daily struggle to quickly locate relevant information in cluttered pages, complete unfamiliar multi-step tasks, and stay focused amid distracting content. State-of-the-art AI assistants ( e.g., ChatGPT, Gemini, Claude) and browser agents ( e.g., OpenAI Operator, Browser Use) can answer questions and automate actions, yet they return answers without showing where the information comes from on the page, forcing users to manually verify results and blindly trust every automated steps. We present PageGuide , a browser extension that grounds LLM answers directly in the HTML DOM via visual overlays, addressing three core user needs: (a) Find —locating and highlighting relevant evidence in-situ so users can instantly verify answers on the page; (b) Guide —showing step-by-step instructions (e.g. how to change password) one at a time so users can follow and perform actions by themselves; and (c) Hide —hiding distracting content—giving users a chance to decide to hide an element or not. In a user study ( N = 94 N{=}94 ), PageGuide outperform unaided browsing across all modes: Hide accuracy improve by 26 percentage points (86.7% relative gain) and task completion time drops by 70%; Guide completion rate increases by 30 percentage points; and Find reduces manual search effort, with Ctrl+F usage falling by 80% and task time decreasing by 19%. Code and demo is at: PageGuide.github.io .

2.
Related Work

Web agents are built to serve a purpose:
helping users accomplish goals on the web more efficiently and accurately than they could alone
. Yet the dominant design paradigm (
i.e.,
fully autonomous agents that plan, click, and return a final result) conflates
completing a task
with
serving the user
. When a user needs to verify a claim on a cluttered page, follow a multi-step task, or stay focused amid irrelevant content, end-to-end automation offers little help. Prior work can be understood through two orthogonal design choices that determine how well a system actually serves users in these situations:
(i) autonomy level
, whether the system acts on behalf of the user or alongside them; and
(ii) output grounding
, whether the answer is returned without showing where it comes from on the page or linked to specific, visible elements. Systems that score high on autonomy and low on grounding (most existing agents) maximize speed at the cost of verifiability.
PageGuide
inverts this trade-off: it acts as a copilot that grounds every output (
e.g.,
answers, guidance steps, and hiding decisions) directly in the HTML DOM, keeping the user in control at every stage.

Web Agents and Browser Automation.

LLM-based web agents have made rapid progress on benchmarks that measure end-to-end task success
(
47
;
20
;
16
;
11
)
. Early systems such as Auto-GPT
(
32
)
and BabyAGI
(
28
)
decompose high-level goals into sub-tasks, execute them via code or tool calls, and iterate until done. More recently, browser-integrated systems—OpenAI Operator
(
31
)
, Claude in Chrome
(
3
)
, Gemini in Chrome
(
12
)
, Browser Use
(
7
)
, Dia Browser
(
36
)
, and ChatGPT Atlas
(
30
)
—embed LLM planners directly in the browser, enabling click, type, scroll, and navigate actions on pages. All of these systems sit at the
high-autonomy, low-grounding
end of the design space: they handle the task for the user and return a final result, but their intermediate decisions are opaque and they do not show where the output comes from on the page.

This opacity carries real costs. Recent benchmarks show that autonomous web agents often make incorrect decisions in high-stakes situations—such as deleting data, making unintended purchases, or following deceptive “Download” buttons that expose personal information
(
21
;
44
;
24
;
37
;
8
)
. A partial remedy is the copilot model named Cowpilot
(
41
)
, where the agent proposes actions and the user is able to pause, reject, or take alternative action when needed.
PageGuide
extends this idea further by not only requesting confirmation but grounding each proposed action in the specific HTML DOM element it will affect, hinting what will happen next, so users can verify intent before execution rather than trusting an opaque plan.

Chain-of-Thought and Grounded Reasoning.
Chain-of-Thought (CoT) prompting improves LLM accuracy by externalizing intermediate reasoning steps
(
39
;
1
;
35
;
26
)
. Highlighted Chain-of-Thought (HoT)
(
29
)
takes this further by embedding XML-style evidence tags in each reasoning step, linking conclusions to specific input spans so users can trace
why
an answer is produced. Vision-language work on web interfaces reinforces this direction: ScreenAI
(
5
)
and WebQuest
(
38
)
show that reliable web interaction requires aligning model outputs with screen elements and multimodal page evidence, not just fluent text.

These approaches share a common limitation: evidence is surfaced in the model’s output—a sidebar answer, a tagged span, a cited region—while the webpage in the browser stays exactly as it is. The user sees the model point to evidence but must scroll back to the page and locate it themselves.
PageGuide
closes this gap by moving evidence directly onto the page: instead of returning “the answer is supported by element 42,” it places a highlight
on
element 42 in the HTML DOM, making the evidence visible exactly where the user is already looking. This shifts grounding from a feature of the model’s text output into a live, interactive layer on the webpage itself—one that users can inspect, override, and act on without switching context.

Content Moderation and Selective Filtering.
Existing filtering tools operate at the
rule
level: Ad blockers
(
15
)
match URLs and CSS selectors, Purpose-Mode
(
23
)
simplifiers hide predefined element classes, and task-focused readers strip non-content regions
(
15
;
23
;
13
)
. These rules are static, require manual updates as page layouts change, and cannot respond to a user’s natural-language intent (
e.g.,

“hide posts that feel politically divisive”
). Research on personalized moderation confirms that users want more agency over what gets filtered and clearer explanations for why
(
18
)
, yet current tools offer neither: they hide content silently, with no per-element justification and no way for the user to review or override individual decisions.

PageGuide
’s
Hide
mode approaches this problem through the
output grounding
len: rather than applying a fixed rule, it interprets the user’s intent at query time, scores each HTML DOM element against that intent using an LLM, and surfaces a one-sentence hiding reason for every hidden element directly on the page. The user can inspect each decision, restore individual elements, and re-run filtering as new content loads in infinite-scroll feeds. This turns content hiding from an opaque background process into a transparent, user-steered interaction.

Taken together, our work extends these insights by combining HTML DOM-grounded answers, mixed-initiative control, and intent-driven filtering into a single browser extension, treating the browser not as a surface for automation, but as a shared workspace where agent and user can work together.

Workflow of the PageGuide system. A user query enters the Router, which classifies intent into FIND, GUIDE, or HIDE. FIND produces an in-page answer with highlighted inline evidence. GUIDE generates a step-by-step action plan, delivered one step at a time with highlighted buttons and user confirmation at each step. HIDE detects target elements and removes them from the page.

PageGuide
is a Manifest v3 Chrome extension that injects content scripts into webpages, giving it both read and write access to the HTML DOM in real time. As shown in Figure
4
, the system follows a three-step pipeline: the
Router
classifies the user’s query and dispatches it to the appropriate handler; each handler
reads the HTML DOM
to ground its answers in the current page state; and the handler produces a
final state
by mutating the HTML DOM directly, highlighting evidence, surfacing step-by-step instructions, or hiding distracting elements. The three handlers differ in how they interact with the user after the initial HTML DOM read:

•

Find
is single-pass: the agent identifies supporting evidence spans and renders inline highlights on the page in one shot.

•

Guide
is iterative: the agent proposes one action at a time, the user confirms or skips it (the
Feedback
loop in
Figure

4
, and the agent re-reads the HTML DOM on the new page before generating the next step.

•

Hide
is single-pass: the agent scores all HTML DOM elements against the user’s hiding intent and applies

display:none
to matched elements, attaching a one-sentence reason to each.

Across all three features, every text output is coupled to a HTML DOM mutation:
Find
returns a text answer with clickable inline citations that scroll to and highlight the source element on the page;
Guide
outputs predicted actions alongside a visual highlight on the target element; and
Hide
hides matched elements in place with an attached reason. The page itself is always the primary output surface. To ensure that these cross-component interactions function correctly in a browser (e.g., MS Edge, Chrome), we maintain a comprehensive
end-to-end testing framework
built on Playwright, and integrate it with automated continuous integration (CI) via GitHub Actions. (see Appendix
I
).

3.2.
Reading the HTML DOM

Before the Router or any handler can reason about the page,
PageGuide
must convert the HTML DOM into a form the LLM can work with. Using a Set-of-Marks (SoM)
(
20
)
style approach, every visible, text-bearing, or interactive node is assigned a unique integer index, producing a structured element index
\mathcal{D}=\{(id_{j},\,\text{text}_{j},\,\text{tag}_{j},\,\text{bbox}_{j})\}_{j=1}^{m}
that records each element’s content, tag type, and on-screen bounding box. This index is passed to the Router for intent classification and to whichever handler is invoked, enabling the LLM to refer to specific page elements by index rather than parsing raw HTML. For
Guide
, the HTML DOM is re-read after each user-confirmed action so that the next step reflects the current page state.

3.3.
Intent Router

Once the HTML DOM index
\mathcal{D}
is ready, the Router is the first component the query reaches
Figure

4
. Its sole job is to decide which of the three handlers should run before any page-level interaction begins. Given query
q
and a compact page context
\mathcal{C}
(
e.g.,
page title, content type), the router selects:

(1)

\text{mode}=f_{\text{router}}(q,C),\text{where~~~mode}\in\{\text{{Find}, {Guide}, {Hide} }\}.

The router is a single LLM call with a structured prompt that describes each mode with canonical examples and asks for a mode label plus a one-sentence justification (see full prompt in
Figure

13
in Appendix). Routing by mode allows each pathway to be optimized for its specific task, rather than relying on a single monolithic prompt to handle all cases.

System:

Find
Mode: Grounded Information Retrieval

Find
addresses a core limitation of existing LLM-based web agents: answers that are fluent but unverifiable because there is no pointer on the screen for users to follow or locate information. Given query
q

\mathcal{D}

Figure

14

[N:"exact phrase"]

“The movie was directed by

[45:"Nolan"]

PageGuide

The final state visible to the user has two coupled components (see

•

In-page highlights:

•

This keeps evidence
in situ

Hide
Mode: Transparent Content Hiding

Hide

“hide all sponsored posts”

Figure

3

Hide

Given query
q

\mathcal{D}

Figure

15

H\subseteq\mathcal{D}

\uparrow

3.7.
Data Collection

To evaluate how well PageGuide assists users in finding correct
information, guiding them through realistic web tasks, and hiding
specific webpage content, we construct the
PageGuide
dataset, which consists of three subsets:
Find
,

Guide
, and
Hide
. For details on how each dataset is constructed, please refer to Appendix
F
.

Find
Subset.

For
Find
subset, we randomly sample 5 questions from Google Natural Questions
(
22
)
, which provides questions and answers grounded in webpage content. However, this source alone is not sufficient for the user study, as many examples are centered on Wikipedia-style pages with relatively short content, making the answers easy to find. To better evaluate the efficiency of the
Find
feature in diverse, long, and content-heavy webpage settings, we augment the task set with 5 additional
FIND
tasks from other websites.

Guide
Subset.
The goal of the
Guide
dataset is to examine how well
PageGuide
assists users in completing web-based tasks through step-by-step guidance. This requires tasks that reflect real user needs and require a certain degree of human supervision (refer to
Figure

2
). Existing datasets, such as Mind2Web
(
11
)
, Online-Mind2Web
(
42
)
, and WebArena
(
47
)
,
are primarily designed to evaluate autonomous web agents rather than to examine how an agent assists a human user in completing a task
. As a result, some tasks are less appropriate for a user study since they are not well aligned with assistive guidance. We therefore construct a
Guide
subset consisting of 138 tasks spanning 37 websites. From this larger task pool, we select 7 representative tasks for the user study.

Hide
Subset.
The objective of the
Hide
dataset is to study whether
PageGuide
can hide specific webpage elements in response to a user’s request. This requires tasks that pair a hide request with the exact webpage elements that should be concealed. To the best of our knowledge, existing benchmarks do not capture this specific problem. We therefore introduce a dedicated

4.
User Study

4.1.
Study Design

We conducted a controlled user study (N=94) to evaluate whether
PageGuide
improves users’ ability to retrieve information, complete procedure tasks an reduce distraction from web-interactions. Participants complete tasks under two conditions: (1) a control condition, where they used standard browsing tools (
e.g.,
scrolling, Ctrl+F) and (2) an extension condition, where
PageGuide
is enabled. The study followed a within-subject design with counterbalanced ordering to mitigate the learning effects.

Participants and Setup.
We recruited participants through departmental mailing lists and laboratory networks. All participants were students, ranging from undergraduate to graduate level, and participated voluntarily without compensation. The study (see
Figure

11
in Appendix) was conducted in person in a controlled lab setting and lasted approximately 30 minutes per session. Each participant completed six tasks in total—two per interaction mode (
Find
,
Guide
,
Hide
)—with a maximum of three minutes allowed per task. For each mode, one task was completed under the control condition and one under the extension condition. All procedures were reviewed and approved by the Institutional Review Board (IRB).

For each task, we record the completion time, accuracy, task outcome (completed/partial completed/ failed), and some more fine-grained behavioral signals such as number of time user hit Ctrl+F, number of mouse clicks and page navigation patterns. Participants also completed post-task surveys collecting the subjective feedback from the users. The survey questions are designed in a Likert-scale and is shown in
Figure

9
.

5.
Limitations and Future Work

Single-mode dispatch limits composite tasks.

The current intent router maps each query to exactly one mode, which works well for clearly scoped requests but fails on composite queries that span multiple features,
e.g.,

“find the settings page and guide me through changing my password”
requires both a
Find
and a
Guide
step. Future work will replace the single-mode router with a
multi-step planner
that decomposes composite queries into an ordered sequence of mode invocations (
e.g.,

Find

\to

Guide
), handling tasks that currently require users to issue multiple separate queries.

Evidence highlights lack cross-page persistence.

Find
’s in-page highlights occasionally overwhelmed participants on dense pages with many matching spans. Additionally, the current implementation highlights only within a single page; users who navigate across multiple pages to gather information must re-issue the query each time. Future work will introduce a re-ranking step that surfaces the most relevant evidence first, and explore
multi-page context
: persisting and aggregating highlights across page visits so users can build up a cross-page evidence trail within a single session.

Per-step confirmation in GUIDE may introduce overhead

When task time is measured only over correctly completed tasks,
PageGuide
is consistently faster than the control condition in the GUIDE tasks (
Figure

6
). The remaining limitation is that the per-step confirmation model adds overhead for users who already know the procedure. Future work will explore adaptive step granularity that compresses self-evident actions into a single confirmation, and multi-turn correction (
e.g.,

“skip this step”
,
“undo the last action”
) so experienced users can move at their own pace.

Content hiding has no memory across sessions.

Hide
’s confirmation dialog added review overhead that some participants found cumbersome for long lists of matched elements. More broadly, users currently have no memory across sessions: content they routinely hide must be re-specified each time. Future work will introduce a
user preference history
that persists hiding decisions across sessions—learning what a user dislikes over time and applying those preferences automatically on revisited pages, with the ability to review and edit the saved profile.

6.
Conclusion

We presented
PageGuide
, a browser extension that grounds LLM answers directly in the HTML DOM across three interaction features:
Find
locates and highlights supporting evidence in-place so users can instantly verify answers;
Guide
delivers step-by-step instructions one action at a time with user confirmation at each step; and
Hide
hides distracting content with a per-element justification shown in a pre-action review dialog. In all three features, the agent’s output is embedded in the page itself rather than returned as plain text in a sidebar.

A controlled user study (
N{=}94
) against unaided browsing showed consistent gains across all features.
Find
reduced task time by 15.2% and Ctrl+F usage from 24.1% to 4.4% of tasks, with page visits dropping by 44.3%.
Guide
improved navigation completion by 7.7% while keeping users in full control of every action.
Hide
reduced task time by 50.8% and improved content hiding accuracy by 25.7%, enabling users to identify targeted elements they would otherwise overlook.

These results support the core thesis of this work: grounded, in-situ interaction—where every answer, step, and hiding decision is anchored to a specific HTML DOM element—is more effective than opaque autonomy for tasks where users need to understand
why
an answer is correct,
how
a procedure should unfold, or
what
has been changed on a page. We hope
PageGuide
serves as a step toward web agents that augment rather than replace human judgment—tools that earn trust by showing their work.

We construct the dataset through three separate pipelines for
Find
,
Guide
and
Hide
subsets. (refer to
Figure

17
).

Find
Subset

To construct the
Find
subset, we collect webpages on the internet and examples from existing resources, such as Google Natural Questions Dataset
(
22
)
. We then filter for long, content-dense pages in which the answer is present but not immediately obvious, requiring users to locate specific information within substantial page content. From these pages, we extract requests and manually validate the resulting examples before exporting the final dataset. In total, the
Find
subset contains 10 questions (see
Figure

17
A).

Guide
Subset

The construction of Guide subset follows a four stage pipeline: collect webpages, select official documentations, extract guide requests and export dataset. (refer to
Figure

17
b). Firstly, we select popular websites based on global web traffic rankings, using the list of most-visited websites compiled from Similarweb and Semrush
(
40
)
. We then collect official documentation, help-center articles, and tutorial pages associated with these websites on different common user-facing tasks (
e.g.,
changing a setting, applying a filter, or navigating to a feature.) Next, we extract requests from the help pages and, in some cases, rewrite these procedures into an actual user requests. Finally, we perform manual quality control to remove outdated, ambiguous, or duplicate tasks. The resulting
Guide
examples each contain a natural-language request, the reference length and the corresponding website link.

Hide
Subset

For Hide subset, we first collect a diverse set of commonly used webpages across different domains, such as social media, forums, shopping sites, and content platforms. For each page, we save a rendered HTML snapshot so that the page structure and visible elements can be inspected during annotation. (refer to
Figure

17
c)

We then build an annotation tool that allows annotators to examine each webpage and hide requests based on the specific content shown on that page. For each request, annotators identify the set of page elements that should be hidden and ground the task to the corresponding page content.

After annotation, we manually review the tasks to remove trivial, unclear, or duplicate examples and to ensure that each request is feasible and supported by the visible page. The final Hide examples therefore each include a webpage, its crawled HTML, a hide request, and the grounded target elements to be removed.

PageGuide
extends beyond the core
Find
,
Hide
, and

These features are motivated by an important limitation of conventional web extensions: user needs are often not confined to the visible content of the current webpage. In practice, users frequently interact with documents such as PDFs, compare webpage content with uploaded images, or ask questions that go beyond the active tab. Supporting these settings allows

to provide a more complete and flexible browsing experience, rather than restricting assistance to page-bound interactions alone.

Many webpages contain or link to information in PDF form, such as papers, reports, manuals, and forms. However, this content is often difficult to browse efficiently using standard web tools. The PDF reading feature allows users to upload a PDF and ask questions about its content, enabling the agent to support document-centered information seeking within the same interaction framework as webpage assistance (

Appendix I
End-to-End Testing Framework

PageGuide employs
Playwright
as its end-to-end (E2E) testing framework, integrated into an automated continuous integration (CI) pipeline using GitHub Actions. This pipeline is triggered on each push and pull request to the main branch, invoking
npm run ci
to execute manifest validation, unit tests, and the full Playwright browser suite in sequence. The rationale for E2E testing stems from the inherent limitations of unit testing in the context of browser extension development: numerous failure modes appear only when code executes within a real Chromium environment, where it must interact with native browser APIs, extension-specific permissions, and live page contexts. Accordingly, E2E tests are designed to detect integration-level defects that unit tests cannot surface, including extension initialization failures, content-script injection errors, UI regressions, and cross-component interactions among the side panel, options page, and background service worker.

The Playwright configuration instantiates Chromium with a persistent browser context, enabling the unpacked extension to be loaded via the
--load-extension
and
--disable-extensions-except
launch flags. Test coverage encompasses extension loading and initialization, service worker and background script startup, side panel rendering and user interaction, options page functionality, and PDF viewer integration. Additional edge cases are also tested, including pages with minimal content, extended scrollable layouts, and image-dense documents. Collectively, this framework provides empirical validation that PageGuide operates correctly as a fully integrated browser extension, rather than relying solely on the correctness of individual, isolated modules.
