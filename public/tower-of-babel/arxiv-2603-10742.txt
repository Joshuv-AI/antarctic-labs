A Grammar of Machine Learning Workflows
Simon Roth

Abstract
Data leakage affected 294 published papers across 17 scientific fields ( [ ref-kapoor2023leakage ] ); a living survey has since grown that count to 648 papers across 30 fields ( [ ref-kapoor2025living ] ). The dominant response has been documentation: checklists, linters, best-practice guides. Documentation reduces errors but does not close structural failures. A structural approach exists: a grammar that decomposes the supervised learning lifecycle into 8 kernel primitives connected by a typed directed acyclic graph (DAG), with four hard constraints that reject the two most damaging leakage classes at call time. Invalid compositions are rejected by call-time guards; for the leakage classes the grammar covers, structural prevention reduces reliance on post-hoc detection. The grammar’s core contribution is the terminal assess constraint: a call-time-enforced evaluate/assess boundary where repeated test-set assessment is rejected by a guard on a nominally distinct Evidence type. Preliminary evidence from a companion study across 2,047 experimental instances ( [ ref-roth2026landscape ] , in preparation) motivates the constraint design: selection leakage inflates performance by d z = 0.93 d_{z}=0.93 ( n n -invariant) and memorization leakage by d z = 0.53 d_{z}=0.53 – 1.11 1.11 , scaling with model capacity, while estimation leakage is negligible ( | d z | < 0.1 |d_{z}|<0.1 ). The grammar’s structural claims (the type DAG, four constraints, and formal specification) are independently verifiable without that evidence. The grammar generated three falsifiable predictions before observing experimental results; two confirmed, one falsified. Two implementations (Python and R) demonstrate the claims; a third (Julia) served as an internal portability proof. The appendix specification (the paper’s core artifact) lets anyone build a conforming version. The grammar’s most significant limitation is optimization leakage: repeated evaluation on validation data is grammatically valid but methodologically suspect (Section 8.6). Multi-model comparison is addressed architecturally: model selection belongs in the evaluate zone, and the test holdout gets one assessment (Section 8.3).

is the closest existing work to a type-theoretic treatment of pipeline
correctness: partition labels are types, propagation rules are typing
rules, and leakage is a type error. But their system requires a separate
analysis pass over completed code; the grammar presented here embeds
analogous partition-tracking semantics directly into the API, rejecting
invalid workflows at call time rather than detecting them after the
fact. The question the literature has not fully answered is whether
leakage can be rejected at the structural level, made inexpressible by
the composition rules of the workflow itself. This paper addresses that
question with a
grammar
in the Wilkinson–Wickham sense: a
compositional system with typed primitives and a rejection criterion for
a domain, not a generative rule system in Chomsky’s sense (the
distinction is elaborated in Section 4). Specifically, it addresses that
question for tabular supervised learning (binary classification,
multiclass classification, and regression) on the three leakage classes
for which effect sizes have been empirically quantified. Temporal
leakage, target leakage, and distribution mismatch are real problems
that occur outside the grammar’s API boundary (data collection,
labeling, deployment) and are therefore outside its jurisdiction.
Extending the type DAG to cover them would require empirical baselines
analogous to those established for Classes I–III.

practitioners composed complex artifacts from simpler parts, a grammar

All five entries share a common move: enumerating the primitives of a
domain. But they differ on composition. Bertin catalogued visual
channels by perceptual capacity: a taxonomy that identified primitives
without defining rules for combining them or criteria for rejecting
invalid combinations. Bertin is included for its pioneering primitive
enumeration, not as a grammar in the compositional sense. Chomsky, Codd,
Wilkinson, and Wickham went further: each defined composition rules and
a rejection criterion that makes “this is wrong” a formal statement
rather than an opinion. The grammars that survived had executable
implementations: SQL for Codd, ggplot2 for Wickham, parsers for Chomsky.
Without one, a grammar stays academic.

The Wickham gap.
Wickham
(
[
ref-wickham2010layered
]
)’s contribution was not the
API; it was the selection. ggplot2 is not a complete implementation of
Wilkinson’s full system; it exposes a curated subset of it. By choosing
which primitives to make primary and which to omit, Wickham shifted
which errors were easy to make: incomplete specifications fail at
construction, and correct compositions become the default path. The
analogous selection has not been made for the ML lifecycle. Kuhn and
Silge (
[
ref-kuhn2022tidy
]
) made leakage less likely
through good design: recipes inside workflows enforce per-fold
preprocessing. But a user can still fit a recipe outside a workflow,
evaluate on training data, or reuse the test set. The structure
discourages mistakes but does not eliminate them. There is no type that
distinguishes “this data has been split correctly” from “this data
has not.” The primitives are typed at the implementation level (recipe,
parsnip model, workflow), not at the correctness level (Partition,
PreparedData, Model).

This paper makes that selection for supervised learning. The formal
specification (Appendix) is the paper’s core artifact: it defines the
type system, primitive operations, guards, and validity conditions
precisely enough for independent reimplementation.

3.5
The terminal boundary

The evaluate/assess distinction is the grammar’s central structural
claim. Evaluation theory has a name for this: Scriven
(
[
ref-scriven1967methodology
]
) separated
formative

evaluation (iterative feedback that improves the thing being developed)
from
summative
evaluation (terminal judgment of the finished
product). Practitioner terminology has not preserved this distinction.
In sklearn,
cross_val_score
reports
test_score
for
CV folds that are formative feedback, not terminal tests. In tidymodels,
“assessment set” denotes the same held-out CV folds. Both use
terminal-sounding names for iterative evaluation. When the same word
covers both iterative feedback and terminal judgment, nothing in the
vocabulary marks the boundary the grammar enforces. The grammar recovers
the distinction structurally:
evaluate
is formative,

assess
is summative, and the type boundary between them is
enforced at call time.

•

Evaluate
operates on validation data. It is repeatable,
cheap, and safe for decisions. It informs the iterate cycle: the
practitioner reads the Metrics output, adjusts, and fits again.
Metrics is terminal in the type system (no primitive accepts it as
input), but it drives iteration at the practitioner level.

•

Assess
operates on test data. It is terminal, once per
holdout, and irreversible. It is the commit: the model’s performance
on data it has never been influenced by or seen.

The sample-splitting logic is textbook
(
[
ref-hastie2009elements
]
): hold out a test set for generalization estimation
(§7.2), use cross-validation for model selection (§7.10), and never
preprocess before splitting (§7.10.2, “the wrong way”). The grammar
does not add new statistical insight; it types the boundaries that the
textbook explains and that hundreds of papers violated. Cross-validation
becomes
cv(s, folds=k)
feeding the Evaluation family. The two
textbook failure modes (preprocessing before splitting; reusing the test
set, §7.7) map to Constraints 4, 2, and 1. The evaluate/assess
distinction, implicit in every textbook’s sample-splitting advice, is
enforced by the types, not by the student’s memory.

4
Design Properties

The three properties below are design constraints, not theorems. Codd’s
data independence and Wickham’s layer independence play the same role in
their grammars. Any proposed extension can be validated against them; so
can any third-party implementation.

The grammar uses two kinds of rejection. Structural rejection (type
mismatch) is static: a function that accepts Model cannot receive a
Partition. Guard rejection is dynamic: it requires runtime state (e.g.,

model.assessed = false
and test partition not previously
assessed) and fires before the call completes. The four hard constraints
are four policies enforced by one mechanism (type checking + guard
checking), each targeting a distinct leakage vector (three address Class
II through different mechanisms; one addresses Class I). Assess-once is
a guard; the type DAG prevents nonsensical type chains structurally. The
policies are independent (each addresses a specific leakage vector); the
enforcement mechanism is shared. A full algebraic formalization of the
guard system (characterizing the grammar as a formal specification with
preconditions) is left for future work.

4.1
Connectivity (not algebraic
closure)

Every type in the DAG is reachable from DataFrame through the
primitives. The non-terminal types form two paths from DataFrame: the
linear chain (DataFrame
\to
Partition
\to
PreparedData
\to

Model) and a branch (Partition
\to
CVResult
\to
Model, via
fold-aware
fit
). The terminal types (Predictions, Metrics,
Evidence, Explanation) are all reachable from Model. No type is
orphaned; any conforming extension must preserve this connectivity.

The grammar is not closed in Codd’s sense. In the relational algebra,
every operator returns a relation, so operators compose freely. Here,

predict
returns Predictions, not a DataFrame — you cannot
call
split
on a prediction. That is the point: the types that
prevent leakage are the same types that prevent free composition. A
fully composable grammar would let you pipe anything into anything,
including leaky workflows. Free composition is not the design goal;
correctness is.

4.2
Generativity

It does not cap iteration: split
\to
(fit
\to
evaluate)
n

\to
assess is valid for any
n
. Each fit and evaluate call draws
from the same Partition produced by split, not from the Metrics output
of the previous evaluate (which is terminal). The cycle exists in the
workflow pattern, not in the linear type chain. A weak form of
generativity; any system with a loop generates an infinite language. The
claim is not about expressiveness class (the grammar’s formal
language-theoretic classification is an open question) but about
practical scope: the grammar does not artificially restrict how many
models a practitioner trains before committing to assessment.

Scope.
The grammar covers batch supervised learning on a
complete dataset available at split time. Multi-task learning (multiple
simultaneous targets), self-supervised learning (no explicit labels),
few-shot learning (
N
too small to partition meaningfully), federated
learning (data never centralized), and online learning (incremental data
arrival) each violate at least one foundational assumption and fall
outside the grammar’s scope. It permits all valid workflows within its
scope (no valid workflow is rejected) and makes no claim about valid ML
workflows in general.

that any conforming implementation must enforce them. The Appendix (§

A grammar is a rejection function, not a generation function: its value
lies not in the workflows it enables but in the workflows it rejects at
call time.

The rejection here is
positional

Chomsky’s grammar makes certain strings underivable: the invalid form
cannot be generated at all. Codd’s constraints make certain states
unstorable: the invalid row cannot exist in the relation. The ML grammar
is weaker on both counts:

is a valid
Python expression and a valid R call. The invalid workflow is
representable in the host language. What the grammar rejects is the

transition
: test-tagged data entering

is blocked at
the verb boundary by a guard, not prevented from existing. A necessary
consequence of embedding a grammar in a general-purpose host language
that has no native partition type. The grammar operates at verb entry
points, not at the level of the host language’s type system.

The grammar’s
partition_tag
is formally an information flow
label (
[
ref-myers1999jflow
]
): train, valid, and
test are security levels, and the guards enforce non-interference
(test-labeled data cannot flow into training operations). Leakage
prevention is information flow control applied to the train/test
boundary rather than the public/private boundary.

All four rules are purely negative: they define the boundary of valid
workflows without ranking or recommending within it. It does not specify
which algorithm to choose, how many folds to use, or when to stop
iterating; those are semantics-layer decisions. The Codd pattern: the
relational model rejects invalid queries without suggesting good ones.
The positive structure of a good ML workflow is the diagnostics and
strategy layer’s job, not the grammar’s.

No existing ML framework enforces a terminal assess-once constraint at
call time (by guard failure or type mismatch, not detected after the
fact). It does not lint completed workflows; it rejects invalid ones as
they are constructed. This claim is bounded to the grammar’s own type
system: operations outside the grammar’s eight primitives can always
produce leakage that the grammar cannot see.

The workflow’s structural guarantees are a minimum over its constituent
primitives: a violation at
split()
propagates through all
downstream operations, and no downstream primitive recovers correctness
from an upstream violation. Hence the four hard constraints are placed
at
split
and
prepare
rather than at
assess
:
the terminal boundary is too late to undo upstream contamination.

6.2
tidymodels

Kuhn and Silge (
[

inside workflows, preventing Class I leakage structurally. It deserves
explicit credit as the most important prior work.

The grammar inherits tidymodels’ insight that preprocessing must be
per-fold, and extends it in one direction: terminal assessment.
tidymodels types are implementation-level — recipe, parsnip model,
workflow — and ensure that preprocessing steps are applied
consistently.

the grammar’s assess-once guard: it encourages a one-shot terminal
evaluation on the test set after model selection is complete. But

is a recommended workflow function, not a guard;
the user can bypass it and call

on test data
repeatedly without raising an error. No type marks a model as assessed.
It closes that gap with a terminal type distinction that makes repeated
test-set assessment unrepresentable. tidymodels and the grammar agree on
what the correct workflow is; the grammar rejects the incorrect one at
call time.

6.3
D3M and AutoML grammars

DARPA’s D3M programme (2018–2022) developed a typed primitive taxonomy
with ~280 annotated components, input/output type
annotations, and automated pipeline search. Smith et al.
(
[
ref-smith2020mlbazaar
]
) unified these as composable ML
primitives with a common API for cross-domain search. Drori et al.
(
[
ref-drori2019alphad3m
]
) extends D3M with formal
context-free grammars over pipeline components.

D3M’s types serve AutoML search pruning: they narrow the candidate space
for pipeline generation, not define which workflows are methodologically
valid. A D3M-generated pipeline can still evaluate on training data,
reuse the test set, or cherry-pick seeds. AlphaD3M’s grammar generates
pipeline
candidates

lifecycle constraints
that reject leakage at call time. Their
grammars answer “what pipelines can I build?”; mine answers “what
workflows are valid?”

6.4
NBLyzer and abstract
interpretation

Drobnjaković, Subotić, and Urban
(
[
ref-drobnjakovic2024abstract
]
) applied abstract
interpretation, a principled framework from programming language
semantics, to ML leakage detection in Jupyter notebooks. Their system
propagates partition-membership labels (Train, Test, Full, Unknown)
through data-flow operations and flags any Test-labeled value flowing
into a fit-class operation as a leakage error. Evaluated on 2,111 Kaggle
notebooks, the approach achieved 93% precision. This is the closest
existing work to a type-theoretic treatment of pipeline correctness.

NBLyzer’s 93% precision on completed notebooks is strong; the grammar
trades that coverage for a different guarantee. NBLyzer is a static
analysis tool: it examines completed code and reports violations. The
grammar is an API: it blocks invalid operations at call time, before
they execute. NBLyzer can analyze arbitrary Python code including
operations outside the grammar’s eight primitives; it can only enforce
its own API boundary. NBLyzer produces false positives (sound but
imprecise); it produces no false positives within its scope (the guards
never reject a valid workflow) and addresses multi-model comparison
architecturally: model selection belongs in the evaluate zone, and the
test holdout gets one assessment (Section 8.3). It has no jurisdiction
outside its primitives. The two approaches are complementary: NBLyzer
can audit code that mixes grammar primitives with raw sklearn calls; it
prevents leakage within its own type system without requiring a separate
analysis tool.

6.5
sklearn API design

Buitinck et al. (
[
ref-buitinck2013sklearn
]
) formalized
the fit/predict/transform protocol that sklearn standardized. The
protocol is duck-typed typestate: calling

before

raises a

grammar makes this typestate explicit and extends it:
fit

requires partition-tagged data (not just any array),
evaluate

rejects test-tagged data, and
assess
fires once per holdout.
The sklearn protocol enforces one state transition (unfitted → fitted);
the grammar enforces a multi-state chain (untagged → partitioned →
[prepared | rotated] → fitted → evaluated → assessed). The
contribution is not replacing sklearn’s protocol but extending the
typestate chain to cover the full assessment lifecycle that sklearn
currently leaves ungoverned.

6.6
mlr3

Binder et al. (
[
ref-bischl2021mlr3pipelines
]
) is the most
formally specified competitor. Its PipeOp system defines typed inputs
and outputs for each pipeline step using graph-based composition.
However, mlr3’s type system is a composition model (how to build
pipelines from components) rather than a grammar (what workflows are
valid and what workflows are not). It does not define a rejection
criterion; it does not identify specific workflow patterns as
structurally invalid. The grammar presented here is complementary:
mlr3’s engineering could serve as an implementation substrate for the
grammar’s constraints.

6.7
The novelty claim

The contribution is the terminal assess constraint: the first
guard-enforced evaluate/assess boundary in any ML framework, making
repeated test-set assessment unrepresentable in a conforming
implementation. The enforcement hierarchy is: documentation <
linting (
[
ref-yang2022leakage
]
)
< static analysis
(
[
ref-drobnjakovic2024abstract
]
) < call-time guards (this grammar) <
dependent types. The grammar occupies the runtime-guard position, the
strongest enforcement available in dynamically typed languages without
external tooling.

invalid in isolation; it becomes invalid when passed to

specification; they appear secondary in the prose because the actionable
grammar lives on the verbs, not the values flowing between them.

8.4

External validation is the missing piece and the paper’s most important

the same distinction applies here. A user who serializes a model and

registry mapping fingerprints to partition roles and split lineage.
Guards query the registry by content fingerprint, not metadata
attribute, so provenance survives host-language operations that preserve
content (column selection, reindexing, dtype coercion). Operations that
change content produce a new fingerprint absent from the registry; the
guard rejects the data as unregistered. The registry additionally stores
split lineage, enabling a cross-verb check at

time: test
data from a different split than the training data is rejected.

Early SQL implementations violated Codd’s relational model routinely:
allowing duplicate rows, failing to enforce referential integrity,
permitting NULL semantics that contradicted the specification. The
specification remained correct, and implementations improved over
decades. Hopefully, the grammar’s enforcement gaps are smaller than
early SQL’s. The most significant gap, tag erasure, was closed by
content-addressed partition identity in both implementations. The
remaining gaps (runtime circumvention, optimization leakage, stopping
criterion) are well understood, and the path to closing them is
established.

Three open flanks define the grammar’s current ceiling.
Runtime
circumvention
: the assess-once guard resets on serialization or

copy.deepcopy
.
Optimization leakage
: indefinite
iteration in the evaluate zone is grammatically valid even when
methodologically suspect.
No stopping criterion
: the transition
from iteration to commitment is ungoverned. Together, they mark the
boundary between what the grammar guarantees and what a rigorous
methodology requires.

Multi-model comparison is architectural: model selection belongs in the
evaluate zone (validation data, repeatable), not at the assess boundary
(test data, terminal). The assess-once constraint is per holdout: the
test set gets one assessment, period. Assessing multiple models on the
same test set is model selection on test data — the evaluate/assess
distinction exists precisely to prevent this. The provenance registry
that already tracks partition identity enforces this: once any model is
assessed on a test partition, that partition’s fingerprint is marked as
spent. The architecture channels comparison through
evaluate

and reserves
assess
for the committed model or ensemble.
Practitioners who need independent assessments can re-split (a new

split
call produces a new holdout with its own identity and its
own single-use budget) or bypass the guard explicitly via

config(guards="off")
, making the circumvention visible and
deliberate rather than silent.

8.7
Feature engineering and the closed-world
boundary

Feature engineering is absent from the eight primitives: no verb for
encoding categoricals, computing lag features, or selecting variables. A
natural objection is that it therefore cannot prevent the most common
form of preprocessing leakage: computing features on the full dataset
before splitting.

Two cases need distinguishing. Domain-driven feature engineering
(creating new columns from domain knowledge: lag features, ratios,
aggregations) happens on the raw DataFrame before the grammar’s
jurisdiction begins, or after
split
on the training partition.
This is outside the grammar’s scope: the grammar begins at the DataFrame
boundary and has no opinion on how that DataFrame was constructed.
Data-dependent transformations (scaling, imputation, target encoding,
one-hot encoding) are model-dependent preparation that must run per fold
to prevent leakage. These belong inside
prepare
, which runs
inside
fit
, per fold (Constraint 2).
prepare
is not
feature engineering; it is model-dependent data preparation. The
distinction matters: computing a rolling average from domain knowledge
before
split
is safe (the feature definition does not depend on
the train/test partition); computing a target encoding before

split
uses test labels to construct training features, a
leakage that
prepare
’s per-fold constraint prevents.

This position is specified structurally:
fit
requires data that
has passed through
split
.
cv
makes the per-fold
constraint concrete:
split
fixes the three partitions (train,
valid, test);
cv
rotates train and valid within the dev set
(
k
fold assignments), while test remains outside as holdout until

assess
.
prepare
runs inside each fold of that
rotation. The implementation enforces this by rejecting data without
split provenance: not just data with a known-wrong tag, but any data
that has not been registered by
split
. Data-dependent
transformations are forced through
prepare
per fold via

cv
; domain-driven feature engineering happens upstream, on the
DataFrame, before it takes jurisdiction.

Detection is unnecessary; it makes the pre-split path structurally
inaccessible. Decomposing
prepare
into typed sub-operations
(encode, scale, impute, derive, select) is a natural extension left for
future work; the current guarantee is that
prepare
runs per
fold, and no unregistered data can bypass it.

8.8
Implementation variance

Two conforming implementations of the same algorithm can produce
different predictive surfaces. In cross-engine experiments,
implementations of SVM using different solvers produced
R^{2}
values
of 0.964 and 0.917 on identical data with identical hyperparameters. It
guarantees type-correctness but not behavioral equivalence across
engines. I acknowledge this as an expressiveness limitation.

8.9
Data flow and operational
flow

Data flow is what the type DAG models: which types are produced and
consumed by each primitive. Strategy verbs (
tune
,

screen
,
stack
) have implicit operational semantics
that the type DAG does not capture.
tune
calls
fit
and

evaluate
internally; its type signature

tune :: Model × HyperparameterSpace → TuningResult
hides
this orchestration. It specifies what types flow between operations but
not which operations trigger which. For correctness checking this is
sufficient: the type guard at each primitive boundary is what prevents
leakage, not the order in which strategies invoke primitives internally.

evaluate
is a hub (
screen
,
shelf
, and

tune
all call it during the iterate zone), while

assess
and
evaluate
are fully independent primitives
with no call relationship. A complete account of ML workflow structure
would distinguish the data flow graph from the control flow graph; the
current grammar covers the former.

8.10
Optimization leakage

A gate, not a schedule: it controls which data flows to which primitive
but does not govern how many times the iterate zone runs or when the
transition to
assess
is triggered.

The grammar enforces data isolation:
assess
uses held-out data
that has not participated in any prior training or evaluation call. This
closes data leakage. It does not close optimization leakage: a
practitioner who runs
screen()
with 11 algorithms,

tune()
with 500 hyperparameter configurations, and then calls

assess()
has made hundreds of model selection decisions on the
validation set. The grammar considers this valid. Statistically, the
final
assess
result is biased upward because the model was
selected to look good on validation data. The grammar prevents test-set
leakage but does not prevent validation-set overfitting through repeated
evaluation. This is the dominant failure mode in modern ML practice and
the grammar’s most significant
scope limitation
, a pattern the
grammar does not attempt to govern, distinct from the enforcement gaps
within its scope (Section 8.3).

Mayo (
[
ref-mayo1996
]
) requires that a hypothesis passes a
severe test only if it would probably have failed the test were it
false. The grammar satisfies the structural condition: the assessor is
held-out data independent of training. It does not enforce the epistemic
condition: the model could have been tuned until evaluation looked good,
in which case a weak model may still pass
assess
on a favorable
split. Goodhart’s law applied inside the type boundary: the evaluation
metric was optimized rather than simply measured.

Nested cross-validation partially addresses this
(
[
ref-varma2006bias
]
): the outer loop
provides an unbiased estimate of generalization performance while the
inner loop handles model selection. The grammar is compatible with
nested CV (a valid workflow within its scope) but does not require it.
For high-stakes applications, nested CV or a pre-registered stopping
criterion (how many evaluation iterations are permitted, or what
convergence condition triggers
assess
) would close the
optimization leakage gap. The grammar specifies the type boundary; it
does not specify the transition condition. That specification is left to
the practitioner.

Pre-registration of the stopping criterion is the natural complement to
the grammar’s type enforcement; that pairing is not yet standard
practice.

9
Conclusion

The grammar does not slow down discovery; it redirects effort. Time
currently spent on unsafe exploration — fitting on test data, leaking
preprocessing across folds, re-assessing holdouts until results look
favorable — is forced into the evaluate zone, where iteration is
“unlimited” and honest. The evaluate/assess boundary is, to my
knowledge, the first guard-enforced implementation of this distinction
in any ML library.

Eight primitives, four constraints, two maintained implementations
(Python, R), and a companion study across 2,047 experimental instances
(
[
ref-roth2026landscape
]
): the grammar is internally
consistent and the implementations satisfy the conformance conditions.
The leakage classes it rejects produce large effects
(
d_{z}=0.93
–
1.11
); the class it tolerates does not
(
|d_{z}|<0.1
). Three testable predictions before the V2 experiments:
two confirmed, one falsified. The grammar is falsifiable and has
survived its initial tests.

The type DAG and four constraints are frozen: they define what a
conforming implementation must satisfy. The verb names, function
signatures, and language binding are the changeable surface. The open
empirical question is whether the grammar reduces leakage errors in
practice. The test is straightforward: a randomized study comparing
leakage rates in student or researcher code written with the grammar
versus without it. That test would require a reference implementation
whose conformance to the type DAG and eight conformance conditions is
certified, so that “written with the grammar” means the same thing
across conditions. Two fully conforming implementations now exist. The
grammar makes the hypothesis precise enough to run that test. Better
features, better data, better research — but only if the exploration
that produces them is structurally sound.

9.3
When is a workflow valid?

A workflow (a sequence of primitive calls) is
valid
if:

1.

Types connect:
each primitive’s output type matches the next
primitive’s expected input type.

2.

Guards pass:
each primitive’s precondition holds at call
time, given all prior effects.

3.

Effects apply in order:
state mutations (e.g.,

model.assessed ← true
) accumulate sequentially.

A workflow is
invalid
if any step fails a type check or a
guard. The four hard constraints are guards in this sense: not rules a
user must remember, but checks that reject invalid workflows at call
time.

Note on evaluate guard.
The guard on
evaluate
rejects
test-tagged data; it accepts train and valid partitions. Evaluating on
training data is legitimate (train-vs-valid score comparison for
overfitting diagnosis). The guard prevents test data from entering the
iterate cycle: if
evaluate
accepted test data, the practitioner
could iterate on test-set feedback, which is structurally equivalent to
training on the test set. The
assess
primitive is the only path
for test data. This is a design decision:
evaluate
is the
practice exam (repeatable, on validation data);
assess
is the
final exam (terminal, on test data).

Note on implementation separation.

assess
and

evaluate
are independent primitives with no call relationship.
Both delegate to a shared private scoring function for prediction and
metrics computation, but neither calls the other.
assess

enforces the test-tag requirement and the once-per-holdout constraint;

evaluate
enforces the test-data rejection guard. Strategy verbs
(
compare
,
validate
,
screen
,
shelf
,

tune
) that need metrics on arbitrary partitions call the same
shared scoring function directly, bypassing both
evaluate
’s and

assess
’s guards and enforcing their own partition constraints.
The type DAG correctly shows
assess
and
evaluate
as
independent primitives.

Note on branching strategies.
This definition covers linear
workflows. Branching strategies (screen, tune, stack) involve parallel
or iterated applications of the same primitives; their validity follows
from applying the same type signatures and guards to each branch
independently.

Note on domain specializations.

split
admits domain
specializations (
split_temporal
,
split_group
) that
share its type signature but carry additional guards specific to a
scientific domain. This is a representational mechanism, not a primitive
extension: the guard set
G(\text{split})
is parameterized by domain,
but the type signature and position in the DAG are invariant. Time
series forecasting, for example, would add temporal guards to

split
without requiring new primitives.

Scope.
The guarantees apply to programs that compose the
grammar’s 8 primitives. Operations outside these eight (arbitrary
DataFrame transformations, external feature selection, direct attribute
mutation) are outside the grammar’s scope. The grammar enforces its own
API boundary; it cannot enforce what happens in surrounding code.
