ToolWeave: Structured Synthesis of Complex Multi-Turn Tool-Calling Dialogues
Dinesh Khandelwal, Gnana Prakash Punnavajhala, GPS Bhargav, Gaurav Pandey, Sachin Joshi, Hima Karanam, Dinesh Raghu

Abstract
Multi-turn tool calling is essential for LLMs to function as autonomous agents, yet synthesizing the training data required for these capabilities remains a fundamental challenge. Existing synthetic data generation pipelines often produce unrealistic dialogues for two reasons: they chain tools that are only superficially compatible rather than aligned with meaningful user tasks, and they generate dialogues in one shot, which often introduces arguments that were neither provided by the user nor produced by prior tool calls. These issues also lead to a severe underrepresentation of multi-step tool interactions. We introduce ToolWeave , a structured framework for synthesizing realistic multi-turn tool-calling dialogues. ToolWeave support realistic multi-step workflows (or tool sequences) by constructing tools with built-in dependencies and filters the workflows based on alignment with user goals. It reduces parameter hallucination by using a fine-grained planning stage that explicitly tracks parameter provenance. As a result, ToolWeave-generated synthetic dialogues contain more multi-step tool interactions (45%) and fewer hallucinations in parameters and tool names. Consequently, LLMs fine-tuned on ToolWeave consistently outperform those fine-tuned on prior datasets across three public benchmarks. Notably, Llama-3.1-70B fine-tuned on ToolWeave achieves 39.75% on BFCL-V3 multi-turn, compared to 23.50% when fine-tuned on SOTA ToolFlow data.



1
Introduction

The evolution of large language models (LLMs) into autonomous agents relies on
multi-turn tool-calling
: the ability to chain tools, elicit user information, and maintain state across complex workflows
(
Yao et al. 2023
;
Schick et al. 2023
)
. Fine-tuning on synthetic data has become a standard approach for improving these capabilities
(
Qin et al. 2024
)
. However, generating realistic multi-turn tool-calling dialogues is not simply generating fluent conversations with tool calls. Existing synthesis pipelines, such as ToolFlow
Shim et al. 2025
, Magnet
Yin et al. 2025
, and ToolDial
Shim et al. 2025
, suffer from two major limitations: semantically incoherent workflows and parameter hallucinations.

Semantically incoherent workflows:
Given a set of tools, existing approaches construct a tool graph and sample sequences of connected tools (i.e., workflows) for dialogue synthesis. However, the coherence of these workflows is fundamentally limited by the quality of the underlying tool graph. In most pipelines, edges in the tool graph are inferred by matching parameter names and descriptions across tools. For instance, a pipeline may connect
create_support_ticket(issue)

\rightarrow

ticket_id
with
cancel_movie_ticket(ticket_id)
solely because both expose a parameter named
ticket_id
. While this enforces schema-level compatibility, it does not guarantee semantic coherence.

This issue has an important downstream consequence. Because workflows are constructed based on superficial similarity rather than true data dependencies, they rarely require the output of one tool to meaningfully drive another.
As a result, the synthesized dialogues seldom contain genuine
multi-step
tool interactions within a turn. This is a crucial limitation, as real world tool use tasks require composing multiple dependent operations, where intermediate results must be propagated across tools to achieve a single user objective. In our analysis (Table
2
), fewer than 7% of dialogues from prior pipelines contain multi-step dialogues.

Parameter hallucinations:
Given a candidate workflow, existing approaches typically prompt an LLM to generate the entire dialogue or plan in a single pass. This leaves the execution structure implicit. The model must infer how tool calls align with user intent, where each argument originates from, and how intermediate results are propagated. In practice, this often leads to hallucinated arguments, where parameters are neither provided by the user nor produced by preceding tool calls. As shown in Table
3
, more than 50% of dialogues generated by prior approaches contain such parameter hallucinations, and models trained on this data risk inheriting the same behaviour.

These limitations stem from a common root cause: the absence of structured, verifiable intermediate representations that explicitly capture workflow dependencies and parameter provenance.

Our Approach:
To address these challenges, we introduce
ToolWeave
, a modular framework that decomposes synthesis into structured, verifiable stages. ToolWeave is designed to generate dialogues with realistic multi-step tool interactions while minimizing hallucinations.

First, instead of starting with a fixed set of tools and inferring edges in the tool graph post hoc via semantic similarity, we propose an iterative curriculum that synthesizes tools with built-in information flow between them. This yields tool graphs with meaningful data dependencies and coherent workflows by construction. We further improve workflow quality through an explicit verification step. We sample workflows, synthesize user goals for each workflow, score the compatibility between workflows and goals, and retain only high-quality pairs, thereby filtering out incoherent compositions. This increases the prevalence of multi-step tool interactions from
\sim
7% in prior approaches to
\sim
45%.

Second, we introduce a fine-grained planning stage that explicitly models
parameter provenance
.
For each dialogue, the plan specifies parameters at each step and their sources (user, context, or prior tools).
This explicit structure eliminates ambiguity in execution and significantly reduces hallucinated arguments, lowering hallucination rates from
\sim
53% in prior approaches to nearly 20%.

ToolWeave consistently outperforms existing approaches across three publicly available tool-calling benchmarks.

ToolWeave Architecture

Figure 1:
The modular architecture of ToolWeave. Starting with a domain name, the
Tool Graph Synthesizer
creates synthetic APIs and organizes them into an interconnected graph; the
Structured Tool Graph Sampler
extracts coherent subgraphs as goals; the
Structured Plan Generator
expands these goals into detailed dialogue plans; and the
Multi-Agent Dialogue Synthesizer
instantiates the plans into natural multi-turn dialogues.

ToolWeave is a modular pipeline for synthesizing realistic multi-turn, multi-step tool-calling dialogues from automatically generated tools. It decomposes dialogue generation into four stages that progressively transform structured intermediate representations into natural conversations. As shown in Figure
1
, ToolWeave first constructs a synthetic tool graph, then samples goal-directed workflows, converts them into fine-grained executable plans, realizes these plans as multi-agent dialogues with grounded tool calls, and finally applies post-processing to introduce linguistic variation and controlled noise. By externalizing complex reasoning into these structured stages, ToolWeave enables reliable generation of high-quality tool-calling trajectories. A full ToolWeave example (goal, plan, tools, and dialogue) is shown in Appendix
J
.

3.1
Tool Graph Synthesizer

Figure 2:
Input schema comparison for
generate_maintenance_schedule()
. One-shot generation yields a flat parameter list, while ToolWeave produces a richer schema with nested objects.

Prior tool graph construction typically relies on either real-world APIs from marketplaces like RapidAPI
(
RapidAPI 2025
)
or one-shot synthetic tool generation via LLMs. The RapidAPI-based approaches provide realistic tools but have two limitations. First, existing frameworks typically infer connections between tools using semantic similarity over parameter names and descriptions
(
Shim et al. 2025
;
Wang et al. 2025
)
. Such heuristics often create incorrect edges; e.g., unrelated parameters like
get_hotel_id(.)
\to
id
and
reserve_restaurant(id)
may be falsely linked as compatible, leading to invalid tool compositions. Second, many tools lack clear redistribution rights, raising potential licensing concerns.

Synthetic generation approaches
(
Liu et al. 2025
;
Chen et al. 2025a
)
avoid licensing issues but generate all tools in a single step. As a result, the generated tools tend to cover only superficial functionality, rarely capturing deeper schema relationships, real-world business logic, or workflows across tools.

In contrast, ToolWeave’s multi-stage curriculum produces highly structured and realistic definitions. Figure
2
illustrates this contrast by comparing the input parameter schemas for a
generate_maintenance_schedule()
tool. While the one-shot baseline generates a flat, simplistic list of parameters, ToolWeave generates complex structures such as nested objects, conditional parameter dependencies, and explicit identifiers that link to other tools. This is made possible by a curriculum-driven, multi-stage tool generation process that ToolWeave follows, described next.

1.

Seed generation:
Create a minimal set of core tools covering fundamental operations.

2.

Entity expansion:
Expand coverage using structured knowledge from Wikipedia and Wikidata. E.g., ToolWeave captures the business rule that
interval_days
is mandatory when
recurring
is true. This is inferred from Wikipedia’s maintenance page (see Figure
2
).

3.

Schema enrichment:
Add depth via nested objects, enums, defaults, and optional parameters.

4.

Connection discovery:
Introduce explicit linking parameters that enable workflows across tools (e.g.,
technician_id
and
equipment_id
), rather than inferring edges post-hoc via semantic similarity.

By decomposing tool synthesis into staged steps, ToolWeave constructs a domain-specific tool graph
\mathcal{G}
, where nodes represent tools and directed edges indicate that outputs of one tool may serve as inputs to another. This graph captures explicit data dependencies between tools and serves as the foundation for workflow sampling in the next stage. More details on the Tool Graph Synthesizer are provided in Appendix
B
.

3.2
Structured Tool Graph Sampler

Given the synthesized tool graph, the next step is to sample coherent tool workflows aligned with meaningful user goals. Prior work
(
Wang et al. 2025
)
generates tool sequences using random walks over tool graphs. While this ensures syntactic compatibility between tools, it often produces sequences that do not correspond to meaningful user tasks. ToolWeave instead enforces
tool–goal alignment
by sampling workflows that follow common structural motifs:
linear
,
fan-in/fan-out
, and
conditional
. These motifs mimic real-world tool interactions and enable the generation of goal-directed tool sequences. By constraining sampling to such motifs, ToolWeave transforms tool-sequence generation from an unconstrained graph traversal into a controlled workflow synthesis process.

Workflow motifs:

ToolWeave samples workflows using common structural motifs:
linear
,
fan-in/fan-out
, and
conditional
. Linear chains form the backbone of the sampler, reflecting typical interactions where each step builds on previous results (e.g., search tickets
\to
retrieve details
\to
update status
\to
notify user). These chains are obtained through a random walk over the tool graph. Higher-order motifs capture more complex patterns.
Fan-in/fan-out
workflows aggregate multiple pieces of information before a final action (e.g., retrieving ticket details and checking user history before updating the ticket).
Conditional
workflows model branches where the next step depends on an API result (e.g., retrieve ticket details if creation succeeds, otherwise list existing tickets).

Validation and Selection:

For each sampled workflow,
ToolWeave
synthesizes a natural-language goal and scores the pair
(\text{tools in workflow},\text{goal})
using an LLM judge. After discarding pairs below a minimum quality threshold, we apply Maximum Marginal Relevance (MMR)
(
Carbonell and Stewart 1999
)
to the linear workflows to prune similar goals and maximize task diversity. For
fan-in/fan-out
and
conditional
motifs, all valid pairs are retained to preserve complex interaction patterns. Detailed scoring rubrics and algorithms are provided in Appendix
C
.

3.3
Structured Plan Generator

Given a goal and its tool sequence, the next step is to generate a plan that guides dialogue synthesis. Broadly, plan generation strategies fall into two categories: high-level planning and turn-level planning. High-level plans
Wang et al. 2025
specify only abstract steps, leaving most work to the dialogue synthesizer. While flexible, this places a heavy burden on synthesizer and often leads to errors such as repeated interaction loops (e.g., repeated goodbyes), incorrect tool ordering (e.g., shipping an order before it is created), or hallucinated outputs produced without corresponding tool calls. In contrast, turn-level plans explicitly specify the structure of each dialogue turn. However, existing turn-level approaches
Shim et al. 2025
rely on predefined action-sequence templates that do not explicitly model parameter dependencies across tools, and rarely generate dialogues containing multi-step tool interactions within the same turn, producing such patterns in only 7% of dialogues.

To address these limitations, ToolWeave shifts much of the reasoning burden from the dialogue synthesizer to an explicit planning stage, so that the synthesizer mainly realizes the dialogue from the plan rather than performing complex reasoning. Unlike prior methods that infer dialogue structure during generation, ToolWeave computes tool grouping, parameter dataflow, and clarification requirements during planning. As a result, the planner enables richer interaction patterns, increasing the proportion of dialogues containing multi-step tool interactions within a single turn to nearly 50%. The planner operates in three stages.

Tool Path Partitioning:

Given a goal and its corresponding tool sequence (e.g., [A, B, C, D]), the planner partitions the sequence into contiguous groups (e.g., [[A], [B, C], [D]]). Each group represents a coherent sub-goal realized as a dialogue segment. Linear paths are partitioned by an LLM conditioned on the goal to identify natural subgoal boundaries. Higher-order motifs use deterministic rules to preserve dependencies between tools.

Subgoal Synthesis and Segmentation:

Next, each tool group is assigned a concise natural-language subgoal, and the corresponding dialogue segment is constructed. Each segment is realized as a sequence of interaction acts including
user_request
,
assistant_clarification
,
user_clarification_response
,
tool_invocation
, and
assistant_response
. A segment begins with a user request expressing the subgoal. If required parameters are missing, the assistant issues clarification requests, followed by user responses that provide the requested inputs, before executing the corresponding tool calls and summarizing the results of the tool executions.

Parameter Planning:

Within each segment, the planner resolves tool parameters by tracing the Tool Graph. Parameters are categorized as (i) user-provided (from user utterances) and (ii) derivable (populated from prior tool outputs or dialogue history). This explicitly plans dataflow instead of relying on the dialogue synthesizer to infer dependencies during generation.

Overall, the Structured Plan Generator introduces three key design elements. Tool grouping partitions the tool path into tool groups, enabling multi-step tool interactions within a dialogue segment. Fine-grained interaction acts improve conversational coherence. Explicit parameter binding ensures consistent data flow across turns. Together, these choices transform dialogue generation from a loosely guided language generation problem into a structured execution process, enabling reliable synthesis of complex multi-turn tool-calling dialogues. Planner algorithms are described in Appendix
D
.

3.4
Multi-Agent Dialogue Synthesizer and Post-Processing

Using the structured plan, ToolWeave synthesizes the dialogue using a plan-driven multi-agent framework. Each interaction act is handled by a dedicated agent, along with a tool agent and a memory agent. The memory agent maintains a persistent state containing resolved parameters, tool outputs, and other dialogue facts, ensuring consistency across turns. The tool agent generates schema-consistent responses for tool calls without requiring access to live API endpoints. The agent responsible for the current interaction act receives the dialogue history, the parameter plan, and the memory state, and produces the next utterance accordingly. The memory is then updated before executing the next step. This stateful execution ensures that dialogues faithfully follow the plan while maintaining coherent multi-turn interactions. Details are in Appendix
E
.

To ensure robustness, we further refine the synthesized dialogues through three post-processing steps: (i)
Linguistic Variation:
rephrasing user utterances to prevent overfitting; (ii)
Failure Injection:
introducing erroneous tool calls and recovery behaviors to simulate real-world API faults; and (iii)
Schema Masking:
replacing function names with generic identifiers (e.g.,
func_01
) to force reasoning over rich schemas rather than surface labels. This refinement process transforms raw synthetic traces into a natural, error-robust dataset suited for generalizable tool-calling. (Detailed algorithms are in Appendix
F
).

Conclusion

We introduced ToolWeave, a modular framework for synthesizing realistic multi-turn tool-calling datasets through structured generation stages that enforce multi-step interactions and consistent parameter provenance. Across multiple LLM families and benchmarks, models fine-tuned on ToolWeave data significantly outperform existing pipelines. Our results reveal that structured synthesis enables open-weight models to produce higher-quality training data than frontier-model-driven pipelines. We further show that ToolWeave’s synthetic APIs can rival or surpass real-world APIs such as those from RapidAPI. Overall, our findings suggest that the structure of the synthesis pipeline, rather than the scale of the synthesis LLM, is the key driver of realistic multi-turn tool-calling data.

B.6
API Quality Metric Definitions

This section provides the formal definitions for the metrics used to evaluate the quality of the synthetic APIs in Section
4.1
. In all definitions,
A=\{a_{1},a_{2},\dots,a_{n}\}
represents the set of
n
APIs in a given domain.

1. Interconnectivity
(IC)

The average number of input parameters per API that can be filled by an output from another API in the graph. This measures the data-flow potential.

IC=\frac{\sum_{i=1}^{n}\left|I_{a_{i}}\cap O\right|}{n}

Where:

•

O=\bigcup_{i=1}^{n}O_{a_{i}}
: The set of all unique output parameters from all APIs.

•

I_{a_{i}}
: The set of input parameters for API
a_{i}
.

•

|I_{a_{i}}\cap O|
: The count of input parameters for
a_{i}
that match any output from the entire API set
A
.

2. Complex API Use
(CAU)

The proportion of APIs that use at least one complex parameter type (i.e., “object” or “array”), measuring schema depth.

CAU=\frac{\sum_{i=1}^{n}C(a_{i})}{n}

Where the indicator function
C(a_{i})
is defined as:

C(a_{i})=\begin{cases}1,&\parbox[t]{207.0021pt}{if $a_{i}$ has an {object} or {array} parameter},\\
0,&\text{otherwise}\end{cases}

3. Required Parameter Ratio (RPR)

The average proportion of an API’s input parameters that are marked as “required”, measuring schema strictness.

RPR=\frac{1}{n}\sum_{i=1}^{n}\frac{|I_{\text{req}}(a_{i})|}{|I_{\text{total}}(a_{i})|}

Where
I_{\text{req}}(a_{i})
is the set of required input parameters for API
a_{i}
, and
I_{\text{total}}(a_{i})
is the set of all input parameters for
a_{i}
.

4. Longest Chain Length

The length of the longest simple path (a path with no repeated nodes) in the
Tool Graph
. This metric quantifies the maximum number of sequential, multi-step operations possible in a single dialogue.

This section provides the low-level implementation details for the

3.2
), including the algorithms and heuristics used to extract, score, and synthesize goals.

C.1
Pattern Extraction Algorithms

The main paper outlines three pattern classes. Here is how they are discovered:

1.

Linear Paths:
These are found using a bounded
beam search

(
Norvig and Russel 2002
)
. The search explores paths from a start node, expanding a “beam” of the top-
k
candidates at each depth.

2.

Fan-in / Fan-out:
These patterns are found by analyzing node connectivity. For a given
start_node
, we find its successors. We then find the “common children” of combinations of these successors using set intersection. This allows us to identify points where parallel data flows (fan-out) later merge (fan-in).

3.

Conditional Branches:
These are identified by scanning an API’s output schema. We scan for output fields that can act as a logical predicate, specifically those typed as
boolean
,
enum
, or other simple types, while filtering out non-conditional fields like IDs.

C.2
Path Scoring and Ranking

To rank the paths found by our algorithms, we use a combination of a hybrid score and a diversification algorithm.

Hybrid Heuristic Score:

The
final_score
for any given path is a weighted sum of three components, and is calculated as:

\displaystyle S_{\text{final}}={}

\displaystyle w_{l}\cdot(S_{\text{coherence}}+S_{\text{relevance}})

\displaystyle+w_{d}\cdot S_{\text{dataflow}}+w_{b}\cdot S_{\text{length}}

Where:

•

S_{\text{coherence}}
and
S_{\text{relevance}}
are
LLM-based ratings
(from
-2
to
+2
) where the LLM judges the quality of a synthesized goal for the provided tool path.

•

S_{\text{dataflow}}
is the
semantic dataflow score
, calculated by checking cosine similarity between embeddings of output and input parameters of sequential tools.

•

S_{\text{length}}
is a
length bonus
to reward longer, more complex paths.

•

w_{l}
,
w_{d}
, and
w_{b}
are the respective weights for LLM rating, dataflow, and length, set as hyperparameters (we use
w_{l}=0.5,w_{d}=0.8,w_{b}=0.3
in our experiments).

Ranking and Embedding Model:

To ensure a diverse set of goals, we rank the top-scoring linear paths using
Maximal Marginal Relevance (MMR)

(
Carbonell and Stewart 1999
)
. This balances the
final_score
(relevance) with the cosine dissimilarity from already-selected goals (diversity). In our experiments, we use a value of
0.7
for
\lambda
. All embeddings for MMR and semantic dataflow are computed using the
all-MiniLM-L6-v2
model from the
SentenceTransformers

(
Reimers and Gurevych 2019
)
library.

Dialogue Planning

D.2
Tool Path Partitioning

The
PartitionToolPath
function uses different strategies based on the pattern type:

•

Linear:
We use an LLM-based approach. The prompt provides the full tool path and their schemas, and asks the LLM to split them into coherent segments, based on logical groupings and dataflow, while also ensuring meaningful multi-step tool sequences.

•

Fan-in / Fan-out:
We use a deterministic graph-based approach. We identify the branching point (fan-out) and the merging point (fan-in) in the path, and create partitions accordingly. The intermediate tools between these points are grouped into either segment, and all possible valid partitions are generated to allow for diverse dialogue structures.

•

Conditional:
Based on the value of the decision variable (from goal metadata
M
), the second tool is chosen from the available branches. The first tool and this chosen branch form a single partition to ensure the conditional logic is preserved in the dialogue, while also generating high-quality multi-step dialogues.

D.3
Subgoal Synthesis

The
SynthesizeSubgoal
function uses an LLM prompt that provides the tool schemas in the partition and the overall goal text
G
. The LLM is instructed to generate a concise, user-friendly subgoal that accurately reflects the purpose of the tools in the partition, while ensuring it is distinct from other subgoals in the dialogue.

D.4
Parameter Planning and Clarification Insertion

The parameter planning and clarification insertion process involves several steps to ensure that the dialogue captures realistic user-assistant interactions.

D.4.1
Parameter Preparation

The
ExtractToolParams
function retrieves all input parameters for the tools in the current partition. The
UpstreamToolOutputs
function identifies any parameters that can be automatically filled from outputs of tools in previous partitions, and these are removed from the required parameters.

D.4.2
Clarification Insertion

The
SplitParams
function randomly selects a subset of the remaining parameters to be clarified, based on the clarification probability
p_{clar}
. This introduces variability and simulates real-world scenarios where users may not provide all necessary information upfront.

D.4.3
Speaker Sequencing and Turn Creation

The turn creation functions add well-formatted JSON objects to the dialogue plan, specifying the role and the associated content (subgoal, tool calls, parameter requests, clarifications, summaries). Following is the structure of these turns:

•

CreateUserTurn
: User turn with subgoal and parameters to provide upfront.

•

CreateAssistantClarificationTurn
: Assistant turn asking for clarification on missing parameters required for the tool calls in the current partition.

•

CreateUserClarificationTurn
: User turn providing values for the requested parameters.

•

CreateAssistantToolCallTurn
: Assistant turn invoking a tool with the provided parameters and source hints for each parameter, either from the user or from upstream tool outputs.

•

CreateAssistantSummaryTurn
: Assistant turn summarizing the results of the tools in the current partition.

Additional Error Injection Modules:

Beyond the cascading failures detailed in Algorithm
9
, our pipeline includes:

•

Out-of-Order Execution:
We simulate scenarios where the model attempts to execute a tool call before its dependencies are met. Specifically, we identify dependent tool pairs and inject a premature call to the downstream tool (missing the dependent parameter) prior to the prerequisite tool. The model receives a missing dependency error and must recover by executing the sequence in the correct order.

•

Semantic Confusion (Wrong Tool):
We utilize a hybrid similarity matcher (SentenceBERT
(
Reimers and Gurevych 2019
)
+ Levenshtein distance
(
Lcvenshtcin 1966
)
) to identify semantically similar but incorrect tools (e.g.,
search_ticket
vs.
get_ticket_details
). We inject a turn where the model mistakenly calls the confusable tool, receives an unhelpful response, and must self-correct.

•

Schema Violations:
We deterministically mutate valid tool calls to violate JSON schema constraints. This includes removing required parameters (
MISSING_PARAM
), violating type constraints (e.g., passing an integer for a string field), or using invalid enum values. The model is trained to read the resulting standardized error message and retry with the correct schema.

•

Missing Function Recovery:
We simulate scenarios where a necessary tool is initially absent from the provided context. The algorithm identifies a scheduled tool call in the plan and temporarily “hides” it. We inject an Assistant turn refusing the request due to the missing tool, followed by a User turn that explicitly provides the missing tool’s schema JSON. The model is trained to recognize the new tool definition in the context window and immediately proceed with the correct tool call.

I.3
LLM-as-Judge Evaluation Details

This appendix provides full details of the LLM-as-judge protocol used in Section
4.4
to assess the semantic quality of synthetic dialogues.

Judge Model and Decoding Setup

Following
(
Wang et al. 2025
)
, we use
Llama-3-405B-Instruct

(
Grattafiori et al. 2024
)
as the judge model. To ensure deterministic and reproducible scoring, the model is run with temperature
0.0
, greedy decoding, and a fixed maximum token budget. Each dialogue is evaluated in a single forward pass; no score aggregation or self-consistency sampling is applied.

Evaluation Dimensions

Each dialogue is independently rated along four dimensions on a 1–5 Likert scale:

•

Naturalness
: Fluency and human-likeness of the conversation.

•

Coherence
: Logical consistency and relevance across turns.

•

Helpfulness
: Degree to which the dialogue successfully addresses the user’s goal.

•

Accuracy
: Correctness of tool usage, arguments, and factual content.

Sampling Protocol

For each dataset, we randomly sample 200 dialogues, stratified uniformly across the available domains (20 domains for ToolWeave and ToolFlow). ToolDial dialogues are sampled from the publicly released dataset and may not cover all domains. Each sampled dialogue is evaluated exactly once.

Evaluation Prompt

The judge is provided with a full dialogue transcript and instructed to score it independently along the four dimensions above. Dataset and model identities are not disclosed to the judge. We adopt the full evaluation prompt from
Wang et al. 2025
, which is shown below:

LLM-as-judge Evaluation Prompt

You are asked to evaluate some synthetic dialogue data. These synthetic dialogue occur between the user, the AI assistant, and the tool. Please evaluate the data based on the following criteria, assigning a score from 1 to 5 for each category. Use the detailed descriptions below to guide your assessment:

- Naturalness (1-5 points): Only evaluate whether the user’s request and response is natural and realistic. Focus more on the natural flow of the conversation and less on the choice of words. For example, pay attention to whether users will ask similar questions in real scenarios. And assess whether user behavior is natural. For example, real users rarely ask similar questions consecutively or ask longer questions.

- Coherence (1-5 points): Evaluate the overall flow and logical connection between the turns in the conversation. Focus on checking whether the user’s previous and subsequent rounds of requests are relevant. Also, ensure that meaningful order of agent interactions is maintained. For example, the agent should not provide information before the user requests it. Similarly, the relevant tools must be invoked only after the assistant calls the tool with the relevant parameters. Such discrepancies should be heavily penalized.

- Helpfulness (1-5 points): Determine the effectiveness and value of the AI assistant’s responses in addressing the user’s needs.

- Accuracy (1-5 points): Check for the accuracy and consistency of the information provided. Everything returned by the tool is assumed to be accurate. However, at the same time, if the assistant hallucinates or makes up information, it should be heavily penalized.

Below are some examples that are rated poorly in each category:

1. Naturalness:

- User: "Can you tell me about the weather?"

- Assistant: "The weather is nice."

- User: "What about tomorrow?"

- Assistant: "Tomorrow will be nice too."

2. Coherence:

- User: "What’s the capital of France?"

- Assistant: "The capital of France is Paris."

- User: "And the capital of Germany?"

- Assistant: "The capital of Germany is Berlin."

3. Helpfulness:

- User: "I need help with my homework."

- Assistant: "What subject is it?"

- User: "Math."

- Assistant: "Okay."

4. Accuracy:

- User: "What’s the capital of Italy?"

- Assistant: "The capital of Italy is Rome."

- User: "What’s the capital of Spain?"

- Assistant: "The capital of Spain is Barcelona."

Some more examples specifically catered to tool usage:

1. Coherence: (Tool simulated before assistant provides tool to be called along with its input parameters)

- User: "Can you raise a ticket for my internet issue?"

- Tool: {"ticket_id": "12345"}

2. Coherence: (Assistant goes on rambling trying to correct erroneous tool output but never calls the tool)

- User: "Please book a flight for me."

- Assistant: "Sure, I can help you with that. Can you please provide me with the details of your flight?"

- User: "I need a flight from New York to San Francisco on March 10th."

- Assistant: book_flight({"from": "New York", "to": "San Francisco", "date": "March 10th"})

- Tool: "Flight ID not found."

- Assistant: "I apologize for the inconvenience. It seems that there was an error with the flight ID. Let me try again."

- Tool: "Flight ID not found."

3. Coherence: (Assistant talks about calling tool but does not use the required tool-calling format)

- User: "Can you check the weather for me?"

- Assistant: "Sure, I can help you with that. Let me check the weather for you."

- Tool: {"temperature": "72°F", "condition": "Sunny"}

- Assistant: "The weather is 72°F and sunny."

4. Accuracy: (Assistant hallucinates information)

- User: "Can you reserve a table for two at an Italian restaurant in New York City for tomorrow night?"

- Assistant: "Sure, I have reserved a table for two at ’Luigi’s Italian Bistro’ in New York City for tomorrow night at 7 PM."

All such examples must be heavily penalized, and the scores they receive should be 1 or 2.
