ABSTRACT
During a product’s full life cycle—from conceptual design to qualification, deployment, and
surveillance—ownership of testing responsibilities changes hands numerous times. Each team may
have preferred testing strategies executed in domain-specific programming languages or
environments. Translating testing intent and details between different languages and environments
can introduce errors that adversely affect product quality, cause delays in the design cycle, and
increase overall costs. IEEE standards can serve as an industry-recognized format to store all
testing-relevant information. Leveraging well-established, universally-accepted standards and
definitions eliminates ambiguity and facilitates the reuse of scripts authored by engineers. This report
describes the progress of a prototype GUI, nicknamed LightStar, that enables engineers to convert
existing test scripts into IEEE-compliant, XML-based documents, as well use these documents to
automatically generate executable scripts.
The initial version of the software takes as-written Python scripts and converts them into Automatic
Test Markup Language (ATML) descriptions. Although ATML is fundamentally not designed to
store code artifacts, we demonstrate how the flexible nature of the standard allows it to encapsulate
and preserve executable logic alongside test metadata in a structured, interoperable form. The
LightStar program can then translate these ATML files into either Python or MATLAB code. Code
generation relies on Large Language Models (LLM) converting the ATML descriptions into error-
free code. To improve the reliability of the output, LightStar relies on skills files to define the scope
and provide examples for how the LLM should answer questions. Tailoring the skills file and using a
statistics-based approach improves the LLM accuracy to greater than 95%.
To provide evidence that any AI-generated script behaves as intended, an AI-generated unit test
accompanies the executable code. Should the unit test fail, or should the operator have doubts about
any of the AI-generated content, LightStar provides the user complete control to manually override
the scripts and unit tests. The tool never produces an authoritative artifact. An engineer reviews and
signs off on the generated script; and ATML makes that review tractable by giving the engineer a
structured statement of intent rather than unfamiliar code.

1. INTRODUCTION
Ineffective communication is often the biggest barrier that must be overcome to reduce
development time and decrease costs. At Sandia National Laboratories (SNL), where a myriad of
organizations must collaboratively work together to develop complex systems, effectively conveying
technical information between groups with different backgrounds is essential for delivering high-
quality products on schedule. As but one of a plethora of examples of the effects of poor-
communication, an issue recently arose as a result of difficulty translating testing details between a
product development team and the team tasked with developing the qualification test system. The
development team had written all of the initial test scripts in Python—a language that was not used,
nor well known, by the test organization. Attempts were made to incorporate the initial scripts into
the qualification tester, but this approach resulted in a software architecture that was overly complex
and unmaintainable. As a result, all of the initial scripts were manually rewritten in a different
language, delaying the release of the product by approximately six months at a cost of roughly $1
million. As an organization, we need to improve how we communicate.
Developing new products generates an abundance of interrelated documents from requirements to
compatibility definitions to interface documents, etc. When building test systems to qualify new
designs, the test team must pull information from this multitude of sources to create a system capable
of verifying requirements. These testers must place a unit in a desired state, provide appropriate stimuli
(source, level, commands, timing, etc.) and accurately measure the unit’s response. At present, this
process is very manual: engineers read and interpret each of the documents; understand how the unit
operates, develop a plan for testing, select appropriate instrumentation, build the test system, write
code to interrogate the unit, and write additional code to analyze the results against the requirements.
It is no wonder that building test systems takes multiple years and costs millions of dollars. With the
advent of ever more sophisticated AI systems, it’s natural to consider options for automating some of
these processes. Even an 80% solution could reduce overall development time by 1-2 years and save
on order $1-3 million.
One challenge in automating the design workflow is that the underlying documents that drive the
decision-making process do not conform to an agreed-upon standard. Locally accepted formats—i.e.
within groups, centers, or a single institution—fail to meet SNL’s needs as Sandia has a diverse internal
portfolio and works with a variety of external partners (KCNSC, DoD, SPP, contractors, etc.). A
universally accepted standard would enable better communication within SNL and between SNL and
its external partners. This report endorses the use of the IEEE standards for signal and test definitions
(IEEE 1641 [1] and IEEE 1671 [2, 3, 4, 5, 6, 7]) as the medium for storing the “ground truth” for all
testing related information, the latter of which is the focus of the work presented in this paper. The
1671 standard defines the Automatic Test Markup Language (ATML) and the complete 1671 family
of standards specify how to store information regarding the test description (1671.1 [2]), measurement
equipment (1671.2 [3]), the unit under test (1671.3 [4]), the test configuration (1671.4 [5]), the test
adapter (1671.5 [6]), and the test station (1671.6 [8]). These are sufficient to fully describe the test
system from the hardware setup to the software execution and requirements verification and
validation. (See also reference [9] for a more in-depth discussion of the 1671 family). Table 1 provides
a brief description of what each member of the family contains.

It is therefore possible to start from a set of requirements and derive all of the necessary
documentation to define, build, and execute tests on a test system. Figure 2 presents a hypothetical
flow diagram illustrating how the process could work. From the requirements one can directly generate
full descriptions of the physical properties of the unit under test (power requirements, interface
definitions, etc.) as well as the details of signals and waveforms relevant to the UUTs operation.
Fundamentally, this process can be completed by modern Large Language Models (LLMs), provided
that the requirements are written in a format that can be ingested by a language model.
With the signals defined, the instrument selection process can be automated—selecting an instrument
with the requisite capabilities corresponds to a classification problem, where the search space can be
limited based on a library of trusted or preferred vendors, cost considerations, existence of software
drivers, etc. The details of the instruments are then stored in 1671.2 for use with downstream
extraction processes. Next, designing the test adapter requires knowledge of the UUT description, the
test equipment (instruments), and the signals. The flow diagram allows for additional information
from the requirements to feed 1671.5, though the majority of the test adapter’s design will follow from
elements in 1641, 1671.2, and 1671.3. At its core, the test adapter defines mappings from the test
system to the UUT—i.e. it simply routes signals. Signal routing is another task that can be automated,
as has been done in the field of auto-routing traces on printed circuit board.
With the test adapter defined, the test description (which includes the test scripts) can be developed.
The test description will require the signal definitions, knowledge of the instruments and their
associated drivers, the UUT commands and expected responses, and how the signals propagate
through the test adapter to the UUT. Automation of test scripts constitutes perhaps the lowest-
hanging fruit in the overall structure. Generative AI’s ability to write code is widely used across
industry. The code generation process can be made more reliable if the test scripts are based on a

 11

predefined code base such that the LLM need not write low-level code modules, rather it can simply
construct the higher-level action sequences. Such an approach has been demonstrated in developing
robotic control routines; by leveraging a database of high-level functions that wrap the underlying
drivers, the LLM can string together the correct sequence of concepts necessary for a robot to achieve
a goal, without having to keep in its memory all of the low-level details required to execute any single
action [12]. By analogy, test sequences can be viewed as control problems, where a test system must
follow a logic series of actions to provide the UUT the appropriate stimulus so that a requirement can
be adequately verified.
The ATML descriptions above contain most of the details necessary to fully describe the test system.
The remaining 1671 elements, the test configuration and test station, summarize the interdependencies
between the constituent components. LLM agents that leverage Retrieval Augmented Generation
(RAG) [13] should be capable of pulling all this information together and generating the ATML
documents.

In total, each step in the process can leverage some form of automation, though the auto-generated
documentation will likely be only an 80% solution that still requires human oversight and some level
of input. Even so, automation will relieve engineers of much of the burden of searching through
instrument manuals, datasheets, connection diagrams, manually optimizing signal paths through
interface cards, and writing the initial code to test the unit.
Another potential benefit comes from the ability to use these documents as training aids for future
projects. When the full set is completed (i.e., when a system is qualified), the ATML documents define
how a given set of requirements was tested. These can be stored in a database so that, if a future team
needs to measure similar requirements, they have a reference for how comparable problems have been

 12

solved in the past1. An engineer could then have a conversation with a RAG LLM agent regarding
approaches to test certain classes of requirements. The agent would use its native reasoning capabilities
to understand the scope of the query and then supplement its answer with content provided by the
documents. While document repositories such as PRIME do exist, the more structured format of the
IEEE standards makes it easier for the agents to search for specific content.
Combining all these factors could potentially result in an 80% reduction in time and cost to build a
tester; decreasing the development time from years to months. This report focuses on one aspect of
the larger vision: understanding the extent to which test code can be stored within 1671.1. While
seemingly only a small piece of the full vision, it is motivated by the aforementioned real-world
experience at SNL. Having a means to store test intent and code details in a common language could
prevent such a scenario from happening in the future. The IEEE standards provide this structure.
The report is organized as follows: Sections 2 and 3 provide motivation for the use of ATML to store
test code and provide implementation details. Section 4 describes the approaches taken to improve
the reliability of the AI output. Section 5 details operation of an interactive GUI, named LightStar.
Section 5 includes an example conversion that demonstrates the ability to use ATML for translating
scripts that control hardware and analyze results to determine pass/fail. Section 5 concludes with a
discussion of future work.

2. ON THE USE OF ATML FOR STORING TEST CODE
Thorough testing ensures components and systems behave as intended when deployed in the field.
However, engineers at different stages of the development and deployment process use different
software and hardware to execute tests within their domain, making it difficult to effectively share
information. These communication problems lead to inefficiencies, as tests are often rewritten in
multiple formats as a project progresses from conceptual design to prototyping, through qualification,
and ultimately to surveillance. Miscommunication between groups may lead to errors due to changes
in test methodology, and these issues are amplified on long, multiphase programs, where test
ownership often changes hands and institutional knowledge is lost. This not only slows development
and qualification efforts but also hinders our ability to upgrade legacy test systems and overcome
obsolescence issues in both software and hardware.
Currently, there is no agreed-upon methodology or readily accessible tool to accurately communicate
test intent and details between different scripting environments. While each programming language
tends to have its own coding standard (see e.g. [14] for Python and [15] for MATLAB, respectively),
those standards do not provide a common, language-agnostic representation of a test. However,
redefining test sequences in terms of universally accepted standards, such as ATML, would streamline
the process and eliminate ambiguity. Leveraging ATML descriptions of test sequences requires the
development of a tool capable of translating between executable scripting languages such as
MATLAB, Python, C#, Visual Basic, etc., and ATML. With the development of RAG-based LLMs
[13], AI agents are powerful enough to meaningfully assist in the conversion process between text-
based languages and the standard.
Sandia’s ATLAS/Shirty services [16] provide an internal means to build RAG agents utilizing a variety
of pretrained language models (e.g. the Llama family of models from Meta [17]). Figure 3 depicts the
updated workflow. Rather than relying on a fully manual process whereby engineers re-author test
sequences each time ownership changes hands, AI agents help convert the tests to and from the IEEE
standards. Recognizing that LLM outputs are stochastic in nature, the translations are, therefore, prone
to errors and require human oversight; however, the bulk of the work can still be offloaded to a
machine.

The most significant challenge to this process arises from the flexible nature of how engineers write
tests. Programmers employ a variety of design patterns and syntaxes to accomplish similar tasks, and
any conversion routine must be capable of handling the most common approaches. Reliably
managing this complexity requires a coordinated collection of AI agents—each with a clear, focused
role—rather than a single monolithic agent.
Not every step in the conversion process will rely on LLMs—there are aspects of any given program
that can readily be extracted using deterministic methods. Consider the process of converting an as-
written program into ATML; in the case of Python files, the Abstract Syntax Tree (AST) module can
parse the file and provide detailed information regarding each line and/or segment of code [18]. For
example, if a Python file contains two or more different functions; they can be separated by parsing
with AST. This is more efficient than asking an LLM to extract all of the text from all functions in a
file—it’s both faster and fully deterministic2. Many other examples exist, however, AST is incapable
of interpreting intent—and this is where AI can contribute. Take for instance, the following
declaration of a variable, vMeasured, as an empty list of length equal to the number of test points
(numTestPoints):
 vMeasured = [0.0 for i in range(numberTestPoints)]
This statement is non-trivial to parse via AST into a set of ATML-compliant details that can be used
to recreate at a later date. But note that, simply asking ChatGPT 5.2 (through SandiaAI3) to interpret
the above line, it provides a response of “That line creates a Python list named vMeasured [with]

3. ATML DESCRIPTION
To successfully convert between any programming language and the IEEE standards, one must first
decide how to store code within ATML. This is a non-trivial task, as ATML inherently defines what
a test must do, but code defines how it is done. The standard has a strict set of rules regarding how
the XML must be structured and there is no perfect 1:1 mapping between programming languages
and the ATML schema. But ATML provides a degree of flexibility in where any given piece of
information can be stored. Examples such as the NI TestStand ATML [19], store only the high-level
sequence step details in the standard. The executable VIs called by the sequence are presumed to
already exist and contain all of the lower-level implementation details. Here, we wish to include all
information necessary to recreate a test: the sequence steps and the underlying code called in each
step.

3.1. ATML Structure
This report focuses on storing Python scripts in ATML compliant files. As such, the organization of
code details within ATML is, admittedly, currently optimized for Python. As more languages are
incorporated, the approach will need to be fine-tuned; but it is hoped that the subtle differences
between programming syntaxes won’t cause significant issues.
Given the nature of a Python file, and the allowed ATML entries, the structure defined in Table 2
was adopted. The last entry, the Python specific “if __name__ == '__main__':” block is treated as the entry
point to the script. For MATLAB, we use the file function definition to store the same content, with
the return variable carrying any output from the function, including a Boolean that indicates whether
the test passed.

3.2. Language Agnostic Entities

3.2.1.     Comments
ATML does not contain a universal XML tag for storing comments. As a result, comments are
stored using different definitions, depending upon where they occur. For example, a docstring
comment describing a function is stored in a <Description> element within the <Test> declaration.

 17

<td:Test ID="genericfunction:MyFunction" name="MyFunction">
  <td:Description>Description of MyFunction</td:Description>
</td:Test>

Comments made within the global or local variable sections are treated as string variables with the
value being the comment.

<td:Variables>
  <td:Variable name="comment">
 <td:Value>
 <c:Datum xsi:type="c:string" value="Local Variables"/>
 </td:Value>
  </td:Variable>
</td:Variables>

By contrast, comments in main body of function are treated as a signal set by “Operation Other”.

<td:Operation ID="14" name="OperationOther">
  <td:Description>comment</td:Description>
  <td:Signal>
 <td:InValues>
 <td:InValue>
 <td:ValueFrom>
 <c:Datum xsi:type="c:string" value="Main"/>
 </td:ValueFrom>
 </td:InValue>
 </td:InValues>
  </td:Signal>
</td:Operation>

(Note: the ID for this operation corresponds to the line number for which the comment appears in
the original script.)
End-of-line comments must be associated with the preceding code and stored in the generic catch-
all <Other> field within the parent element that defines the commented object. For example,
suppose the original Python code includes an end of line comment following a variable declaration:
 answer = "N/A" # default value. Overwritten for valid input.
The corresponding ATML section has the following form:
<td:Variable ID="LocalVariable_answer" name="answer">
  <td:Value>
 <c:Datum xsi:type="c:string" value="N/A"/>
  </td:Value>
  <td:Other>default value. Overwritten for valid input.</td:Other>
</td:Variable>

 18

The <Other> field sits within <Variable> as a sibling to <Value> and stores only the text of the
comment. The appropriate comment delimiter (e.g., # for Python and % for MATLAB, etc.) is
determined by the conversion tool.

3.3. Python Specific Code

3.3.1. Import Statements
Most Python scripts begin with a block of import statements that load all the requisite packages.
These import statements can take a variety of different forms; for example, the following are all valid
expressions:
import os
import numpy as np
from InstDrivers import pxie6363 as pxi
ATML does not readily contain objects capable of differentiating among these forms. Consequently,
the entire set of imports is stored in a single global variable as an array of strings.

<td:GlobalVariable ID="GlobalVariable_importedPackages"
 name="importedPackages">
  <td:Value>
 <c:IndexedArray xsi:type="c:string" dimension="[2]">
 <c:Element position="[0]" value="import os"/>
 <c:Element position="[1]" value="import numpy as np"/>
 <c:Element position="[2]"
 value="from InstrDrivers import pxie6363 as pxi"/>
 </c:IndexedArray>
  </td:Value>
</td:GlobalVariable>

It is left to the ATML-to-code generator to properly handle these statements. In the case of
generating Python code, it is straightforward to treat these strings as literal expressions that must be
inserted into the code. For MATLAB we envision using an LLM to determine any non-native
packages that must be included and to provide the user with informative comments on to how to
import these packages. For example, MATLAB has no need to import a mathematical package

conversion process. Anytime an LLM is needed to interpret text or generate code, a new instance of

4.2. Document Segments
The IEEE standards for signal and test definitions encompass more than a thousand pages of
information. As such, it is currently impossible to provide the full text to a RAG agent for queries
regarding proper formatting of the ATML file. The MATLAB Text Analytics Toolbox provides
functions that can search through the standards for pertinent sections and extract the most relevant
text for a given query [20]. In order to reduce computation resources and token usage, the UI
combines custom functions and the Text Analytics Toolbox to parse the document into “chunks”
that can more easily be accessed by the LLM for context retrieval. These chunks may contain
information such as section numbers, section names, labels, indices, word counts, and more; all of
which the LLM can use to provide answers and citations related specifically to the document of
interest. Processing larger documents or file folders understandably takes more processing time–the
chunking characteristics can be modified as needed–but once the content has been parsed it can be
saved and loaded more easily in subsequent sessions.

4.3. Improving Reproducibility
The stochastic nature of an LLM’s response means that, for any given query, the answer provided
may differ from one run to the next. This is true even for simple questions that a human might
expect the LLM to behave deterministically. While on average, the LLM might give a “correct”
answer, the finite probability that the LLM generates, e.g., non-functioning code, creates reliability
issues for any conversion routine. To reduce errors, several approaches have been implemented.
First, for simple queries that involve returning definite answers, the LLM is queried three to five
times, and the most common response is taken as the accepted answer. For example, if an LLM is
asked for the dimensionality of a matrix, the values of n from five separate queries are recorded, and
the most common value accepted as the correct response. The three-to-five instances is a hyper-
parameter selected to minimize the run time while providing enough statistics to improve
confidence in the answer. Table 4 shows the probability that the most common response is correct
after 𝑁 queries, assuming the LLM answers each individual query correctly with probability 𝑝. Table

queries are described by the same probability, 𝑝.

Second, some queries specifically ask the LLM to return an answer in the form of a Python
dictionary. Unfortunately, LLMs occasionally return malformed dictionaries that throw errors when
parsing. These, and similar errors associated with un-executable code snippets, were dealt with in the
following manner: if attempts to “execute” the initial response of the LLM failed, the response and
the error message were added to the question context as “Your previous answer of
{previous_response} failed to execute and returned an error of {error}.” The LLM was then re-
queried with this additional context. If errors persist through three consecutive cycles, the operator
is notified that the process failed at this step due to an inability to correctly answer the specified
question.
Third, for large segments of generated code, the entire code section can be passed to an LLM to
correct minor syntax errors. This is, admittedly, a dangerous step. The LLM is being asked,
wholesale, to read the script, find what it determines are syntax errors, and correct them. To keep
humans in the loop, this step will include a “gate” whereby the operator must authorize the program
to proceed along these lines. As a further safeguard, the “corrected” output will be visible to the
operator—who can always make additional changes before saving the generated code. In terms of
how the LLM performs the operation, the skills file includes definitions for in-scope and out-of-
scope activities. These statements instruct the LLM not to alter any of the intent of the original
code, and to make only the minimum changes necessary to allow the code to parse and execute.
While the code editing agents had specially designed skills files to assist them in eliminating syntax
errors, it should be noted that there are limitations to the effectiveness of a skills file for this task.
An example was discovered when developing code for a simple loop-back test using NI hardware
(see section 5.4 for complete details). Briefly, the goal of the script was to use an NI PXIe-6363 card
to source a signal on an analog output channel and measure the value on an analog input channel.
The aim was to demonstrate control of physical hardware through a script that was translated into

 23

and out of ATML. To control the hardware, a wrapper class named “NIDAQSession” was created
to house all of the low-level NI DAQ code. This mimics real-world scenarios where instrument
control will rely on sets of external drivers. When generating MATLAB scripts that call this class, the
LLM fails to recognize that NIDAQSession is a user-defined class that is separate from the
MATLAB Data Acquisition Toolbox drivers for controlling NI DAQ cards. As a result, the LLM
mistakenly classifies all calls to the NIDAQSession class as errors and attempts to remove these
“syntax” errors from the script by overwriting every line of code that includes a call to
NIDAQSession. Soley modifying the skills file did not improve the success rate of the LLM
correctly recognizing the user-defined class as valid code. And, because repeated sampling reduces
variance, not bias; systematic misunderstandings are invisible to majority voting and must be
addressed by supplying more relevant context. Therefore, it was necessary to add the
NIDAQSession class definition as additional context for the LLM so that the LLM recognizes calls
to the class as being syntactically valid.
Finally, the scripts can be evaluated using unit tests. These unit tests can either be known-good tests
previously validated by an engineer or generated by the LLM [21]. Pre-existing unit tests represent a
gold-standard: the AI generated scripts must pass these tests as they have (presumably) test all
possible inputs to the functions within the script and have been fully vetted by engineers. Failures
indicate the script is flawed and must be updated. By contrast, if an AI generated unit test fails, it is
not immediately obvious whether the issue is with the unit test or the script. The only way to discern
between the two options is to use a test oracle that defines what the function output must be, given
a set of inputs. This oracle traces back to requirements and ultimately, we envision building tools
capable of reading the requirements documents and storing the information within ATML files. But
for the sake of this report, it is assumed the oracle is included in the description of the function
within the original script (i.e. for Python files it resides within the docstring). ATML can store
prescribed unit test cases within <Test>/<Outcomes>/<Outcome> tags. Populating these unit
test descriptions still relies on AI to interpret the docstring and generate the test cases. However, the
risks associated with interpreting the requirements can be greatly reduced if the oracle contained
within the docstring is clear, concise, and well written. This theme permeates throughout this
report—improving the consistency and accuracy of LLM code conversion requires programmers to
comment their code.

5.3.1. Which is flawed – the script or the unit test?
Section 5.3 shows how the GUI provides the user with the option to have the LLM rewrite a failing
unit test. Choosing to rewrite the unit test assumes that the test fails due to some error in the test
code. But as was mentioned in section 4.3, it is also possible that the script contains the bug; or in
the worst-case scenario, both might contain errors. Can an LLM determine the underlying cause for
the unit test failures and therefore automatically update the correct file? To do so, the LLM must be
provided a complete set of expected outputs for a given input (i.e. a requirements oracle), as well as
a copy of the script in question, a copy of the failing test, and a detailed test report stating what
failed. The test report should clearly identify which test failed, what the input values were, what the
expected output values were, and what the function returned.
The approach under development stores the requirements oracle within the ATML file and requires
the test results be stored in an XML file (ultimately within IEEE 1636.1). The expected outcomes of
a function are located in <Test>/<Outcomes>/<Outcome> tags. For example, suppose a function
converts a numerical score into a letter grade, the <Outcomes> section of the xml file then might
take the form:

  <td:Outcome ID="case_001"
                       qualifier="{'grade': '90 &lt;= grade &lt;= 100'}"
                       value="{'return': 'A'}"/>
 <td:Outcome ID="case_002"
                       qualifier="{'grade': '80 &lt;= grade &lt; 90'}"
                       value="{'return': 'B'}"/>
 <td:Outcome ID="case_003"
                       qualifier="{'grade': '70 &lt;= grade &lt; 80'}"
                       value="{'return': 'C'}"/>
 <td:Outcome ID="case_004"
                       qualifier="{'grade': '60 &lt;= grade &lt; 70'}"

Through trial and error, it was found that simply passing the LLM all of the relevant information at
once (script, unit test, oracle, and full report) and asking it to determine whether the script or unit
test contained the error, was highly ineffective. With too many steps to complete within a single
query, the LLM seemed to base decisions on only a subset of the relevant information. For example,
if two test cases failed, then, in some instances, the first was either used exclusively, or the model
seemed to weigh it more heavily. By not considering the full set of failed test cases, the LLM often
misclassified the cause of the test failure.
The quality of the responses can be improved by breaking up the task into several smaller objectives.
Thus, one agent is tasked with determining whether an individual unit test case follows the correct
logic (if the input/expected values pairs adhere to the oracle), while another performs the same
analysis on the function under test using its input/output pairs. In both cases, the agents are not
informed of whether the test passed, nor are they given report details from any other test case.
Including these additional pieces of information seems to bias the model—occasionally resulting in
flawed reasoning along the lines of “if the unit test failed, the unit test must be flawed”; or the LLM
concluding the exact opposite “if the unit test expects an answer of ‘A’, that must be the correct
answer so the function is flawed”. Adjusting the skills file and prompting seemed less effective at
steering the LLMs away from these lines of argument than simply limiting the scope of information
provided.

It is worth mentioning that the oracle checking agent only looks at failed test cases because this
simplifies its role. When provided the full set of results and asked to find and eliminate any
inconsistencies, the LLM made too many mistakes. It would often make changes to sections of code
that contained no errors or introduce additional logic checks that were unnecessary. By limiting what
the LLM has access to and limiting the scope of its assignment, the efficiency with which it properly
identified and corrected errors increased (we do not have formal statistics on this, but when the
LLM had permission to edit the full file, the failure rates were on the order of 50%, and this line of
work was quickly abandoned in favor of more efficient approaches).
Finally, the 97.6% success rate for the full routine represents a procedure that is not yet fully
optimized. The process does not include an independent check of the updated script/unit-test to
ensure the LLM has written executable code. One observed failure was due to the LLM improperly
indenting a section of code. This could be double checked and corrected before the updated code
modules are returned. However, the 3% failure rate was deemed sufficiently successful at this point
to warrant its use without adding additional verification steps that would slow the process down. At
a minimum, to correct the error and validate the updated code, a flawed script/unit test combination
requires at least seven LLM queries and a rerunning of the unit test. This minimum occurs if there is
a single failure amongst all the test cases. With multiple failures or if there is a need to rerun the
algorithm on the interim files, this number can easily increase by a factor of two to three. As a result,
fixing the errors introduced to the assignLetterGrade routine took an average of 477 seconds (over 30
successful trials). This number should not be taken too seriously—it was obtained through tests run
on a Windows laptop connecting to ATLAS/Shirt remotely (albeit on a Sunday when traffic was at a
minimum). But it does indicate that even with optimization, each failure will likely add minutes to
the overall ATML to code conversion routine. Determining how to balance speed/performance is
left as a future exercise, when more representative code bases can be processed by the ATML code
converter.
The key result here is that, given a properly defined oracle, LLM agents can accurately determine the
cause of failed unit tests and correct the code. To do so, one must treat the LLM query as a type of
pseudo hidden Markov model6, where the hidden state is the true answer, and the observable is the
LLM response.

the appropriate code modules for analysis. The argument details for Python native and imported

5.5. Future Work
The project assumes that a thorough set of validated test sequences already exists and addresses the
need to store test intent and execution details in a language agnostic form that can be reused in the
future. But this assumption does not generally hold. When test ownership changes hands during the
product’s 30+ year life, the new owning organization will often reuse only a portion of the existing
tests, while expanding or modifying what’s tested to meet ever-changing goals. For example, the
qualification team has different goals and needs than the development team; and the surveillance
team’s focus differs from both of these. In total, test ownership can change hands upwards of five
or six times (more if one considers potential turnover in surveillance teams during, e.g. preventive
maintenance activities that can span decades). It therefore becomes necessary to consider the tester
code base not as a static entity, but as a living body of work that evolves with the changing needs of
the project. The various elements within IEEE 1641 and the IEEE 1671 family (see Figure 1) can be
leveraged to help streamline the process of editing or modifying the test scripts to meet new goals.
Developing a tool that takes the written requirements and assists in test creation represents the next
step in automating the tester design process.
The first step in converting from requirements to tests involves casting as-written requirements into
mathematically rigorous statements consistent with the IEEE 1641 standard. Converting text-based
requirements into mathematically rigorous statements provides multiple benefits. First, all of the
down-stream components that rely on the signals and waveforms (instruments, test adapter, test
sequences) need the requirements cast in mathematical terms. For example, matching instrument
specifications to signal requirements becomes easier if the requirements are expressed
mathematically and adhere to the format typically provided in the instrument datasheet. Second,
once requirements are defined mathematically, it is possible to use formal methods to analyze the
requirements and ensure they are verifiable, consistent, and add value. Far too often, requirements
are written that cannot be directly tested (because they define limits on hidden variables that are
internal to a system and not exposed externally), are incompatible with other requirements (e.g.
interacting subsystems specify different limits for a shared variable), or overly constrain the system
(such as defining limits on hidden variables which do not impact that values of external, observable
variables). With mathematically defined requirements that can be cast into a state-space
representation, poorly written requirements can be more easily identified and eliminated.

6. CONCLUSIONS
This report demonstrated a practical path toward representing test intent and structure using the
IEEE standards 1641 and 1671—which defines the XML-like language, ATML. By leveraging
universal standards, test information can be shared across organizations and execution
environments, while reducing translation errors. A central outcome of the work is an initial,
implementable mapping between common Python script constructs and ATML elements—
including import statements, global and local variables, function definitions, function calls, and
pass/fail evaluations. The adopted structure intentionally combines deterministic parsing (e.g., via
Python’s AST module for segmentation and syntactic extraction) with LLM-assisted interpretation
for portions of code where intent must be inferred. This hybrid strategy leverages determinism for
repeatability and speed while reserving LLMs for the problems they solve best: translating between
representations when rigid schema-based rules become brittle.
Because LLM outputs are stochastic, the report also outlined multiple safeguards required for
operational use: repeated querying for simple, definite outputs; automated detection and repair loops
when responses are malformed or non-executable; optional gated code editing; and validation
through unit tests. Collectively, these measures shift the LLM from being a single point of failure to
a set of productive assistant agents operating inside a controlled workflow with human oversight and
objective checks.
Finally, the MATLAB-based GUI provides a usable interface to these capabilities, enabling
engineers to execute conversions, inspect intermediate artifacts, and manually intervene when
necessary. While the present implementation focuses on Python-to-ATML and ATML-to-
Python/MATLAB translation, the overall architecture—standards-based intermediate
representation, modular “skills” agents, deterministic parsing where possible, and validation-driven
iteration—generalizes well to additional languages and test environments. Continued work will focus
on expanding language coverage, strengthening outcome representations, improving automated
handling of external dependencies (e.g., instrument drivers), and tightening the linkage between
requirements, oracles, and unit tests to further increase confidence in automated conversions.
