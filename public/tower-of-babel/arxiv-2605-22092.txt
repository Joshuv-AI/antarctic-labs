Abstract
. Network configurations are prone to errors, which can lead to catastrophic service outages. A tool that can achieve automatic configuration repair (ACR) is highly desired by operators. Existing tools for ACR follow a semantic-driven approach : they model network semantics as a set of SMT constraints, and solve them for a location or fix of the error. Due to the complex semantics of networks, constructing and solving these constraints can be prohibitively expensive, making these tools neither general nor scalable. Inspired by automatic program repair (APR), we explore another direction, i.e., a syntax-driven approach , which tries to repair program bugs by “grafting” some existing code in the same repository, without modeling program semantics. Following this direction, we propose Astragalus, a syntax-driven method for ACR. It uses multiple iterations of a “localize-fix-validate” pipeline to search for repairs, and proves quite effective on configurations of our production network. Specifically, we show that Astragalus can repair every incident in multiple sizes of a synthesized network, and 97.5% of the incidents on a real network, both with 15 types of errors injected, within an average time of 7.36 seconds. It has also provided valid repair suggestions in under 6 minutes for 4 recent network incidents or undesired changes, in a real production network with O(1,000) ∼ \sim O(10,000) devices.

2.
Motivation

In this section, we discuss the hurdle of current configuration repair approaches to motivate the need for a syntax-driven approach to ACR. Then, we contrast network configurations with software code to introduce the challenges of a syntax-driven approach.

2.1.
Semantics-driven repair

Existing work has explored synthesis-based methods for root-cause diagnosis and automated repair.

Synthesis methods
build a formal model of the network control plane, and repair the configuration with solvers.

AED
(
2
)
encodes the intent like (e.g., blackhole-freedom) and the semantics of routing protocols as a set of SMT constraints, and introduces free variables for each line to represent candidate modifications.
An assignment of these free variables that make the constraints satisfied is a repair.
While this SMT-based approach guaranties correct updates, it is hard to scale to large networks, due to the vast search space generated by SMT constraints and free variables. Meanwhile, the repairs tend to focus on "the most straightforward modifications" that make the constraints satisfiable, which does not necessarily correspond to a true root-cause repair. For example, on our dataset with injected misconfigurations, AED produced a repair that restores reachability by adding a static route. Although this kind of “workaround” is functionally effective, it neither resolves the underlying configuration error nor provides a clear explanation of the root cause.

CEL
(
15
)
extends Minesweeper by decoupling configuration from the control logic and encoding the network model and intent using SMT constraints. It localizes misconfigurations by solving for a Minimum Correction Set (MCS) of constraints, which maps back to the root-cause configuration statements. However, since it is designed for fault localization, it can only identify the statements that are most likely responsible (in most cases), but cannot output an actionable repair.
In addition, its scalability is similarly constrained by the size of the candidate space, the complexity of the constraints, and the performance of the solver. When these factors are combined in a large-scale data center network, the methods often struggle to maintain stable time/space consumption.

2.2.
Preliminary of APR

In the following, we discuss approaches for automatic program repair (APR), which inspires our method in the next section. APR has been extensively studied, and methods for APR are broadly classified into two categories:
semantics-driven
methods and
syntax-driven
methods.

Semantics-driven approaches
, also known as correct-by-construction approaches, formally encode the program repair problem as a satisfiability problem, i.e., a set of SMT constraints, and solve the problem using off-the-shelf SMT solvers (e.g., Z3, CVC5)
(
23
;
21
)
. The advantage of such approaches is that they can guarantee the repair does not introduce side effects. However, scalability is quite limited due to the fact that the entire problem can have many constraints.

Syntax-driven approaches
, also known as generate-and-validate (G&V) approaches,
is another important category of approaches for APR.
Many of G&V approaches are based on the

“plastic surgery hypothesis”
(
6
)
, that is,
the code ingredients that can repair the software already exist somewhere in the codebase,
so we can graft existing configuration lines to construct the repair.

Automated Program Repair (APR) systems mainly follow generate-and-validate approaches: they enumerate patch candidates via syntactic modifications, such as template-based changes, and use the test suite as the primary correctness evaluation, rather than relying on a full semantic specification.

At a high level, these systems (i) generate a set of candidate updates and (ii) validate each candidate to identify a patch that fixes the failing behavior while avoiding regressions
(
18
;
19
;
26
)
. In practice, this approach is often preferred over semantics-driven repair because it is
more scalable
: it sidesteps expensive global semantic reasoning (e.g., solving large SMT constraints), and
more general
: it does not require a precise, program-specific semantic model, but instead leverages readily available tests for validation.

2.3.
From APR to ACR

Automated Configuration Repair (ACR) and Automated Program Repair (APR) share a highly similar problem structure
: both aim to apply smaller, safer changes, starting from current erroneous behavior and using consistent input intention without introducing side effects as the criteria to filter and validate candidate fixes, thereby driving the system from an incorrect state to one that satisfies the expected behavior. In practice, this intent is often expressed as a set of checkable specifications, such as test cases, configuration item checks.

Network configuration repair presents unique challenges compared with general program repair
. Network configurations are typically declarative, with their effective behavior resulting from the composition and overlay of multiple rules. Consequently, configuration repair needs to take into account the system’s global behavior, which emerges from the combination of multiple configuration rules through mechanisms such as priority or override, and configuration items are interconnected through network topology, protocol states, and other information. Modification of a single rule may affect routing, access control, or service availability across the entire network. Therefore, network configuration repair cannot be accomplished solely through local syntax checking or single-rule validation.

To the best of our knowledge, all existing methods
(
14
;
2
;
15
)

for network configuration repair fall within the category of
“semantics-driven” approaches
.
For example, CPR
(
14
)
and AED
(
2
)
encode network control plane semantics and operator intents as a set of SMT constraints, and incrementally synthesizing configurations by solving the satisfiability problem.
CEL
(
15
)
localizes the root cause by solving the minimal correction set (MCS),
a minimal subset of SMT constraints whose removal makes the remaining constraints satisfied.

In contrast, we explore the other direction, that is, the “syntax-based” approach for automatic configuration repair.

3.
Overview

3.1.
Key Ideas

The key idea of this paper is:
instead of following the semantic-driven approach,
we explore the syntax-driven approach to achieve ACR for better scalability and generality.
This feasibility of applying syntax-driven approaches is due to the following two observations.

The “plastic surgery hypothesis” holds true for network configurations.

As observed in Provider A’s network,
the devices are organized into availability zones, planes and pods;
each of the zones also has multiple devices with the same role (i.e. core, aggregation, edge, etc.) to serve the purpose of redundancy.
The devices serving as each other’s backup are often configured similarly;
and even the devices with the same role in different zones share similar configurations to achieve the same functionality
(
25
;
10
)
.

Therefore, we can repair a device’s configuration by copying the configuration of other devices.

Validation is efficient for network configurations.

Network verification is well-developed
(
34
;
33
)
and can quickly check configuration correctness for large networks within seconds.
Provider A has an in-house control plane simulator, which can finish the computation of the data plane for a production network with 2000 nodes, within 5 seconds, enabling us to efficiently try a lot of candidate fixes.
Note that in APR, the validation process dominates runtime due to the time required for recompiling and rerunning parts or the entire program
(
27
)
.
Thus, the efficiency of validation implies the efficiency of repair for network configurations.

3.2.
Workflow

Figure
1
shows a simplified workflow of Astragalus.
First, Astragalus does a full validation of the network to identify the incident and its impact range. After that, Astragalus tries to fix the network through multiple iterations of three steps: localization, fix generation, and validation.

Step 1: Localization (§
4.2
).

The localizer aims to identify the suspicious configurations that would cause the incident.
It tries to localize the fault based on the output from the validator.
With no extra information attached, it does the localization by best effort:
the identified configurations by the localizer are usually
suspicious configurations
rather than the
root causes
.
After the localization, the fix generator receives the suspiciousness of each part of the configuration.

Step 2: Fix generation (§
4.3
).

Based on the suspiciousness provided by the localizer, the fix generator generates
candidate updates
heuristically, aiming to fix the suspicious config to resolve the incident.
Like the G&V approach in APR, the fix generator selects one of the suspicious configuration and applies
change operators
to produce a new configuration, i.e. the candidate update.

The change operators are purely syntactic, such as removing nodes in the abstract syntax tree (AST) of the configuration
(
7
)
, modifying a node or inserting a new node with values from other ASTs.

Step 3: Validation (§
4.4
).

After applying the change operator, the validator checks if the update satisfies the specification.
Since network verifiers
(
33
;
12
)
can simulate the control plane from configurations, we can use off-the-shelf tools to validate candidate updates.

If the validator shows the network is fully fixed, it returns success. Otherwise, if it shows the network has fewer errors than before, it localizes again based on the new configuration (i.e., with the candidate update) to find new suspicious configurations;
if it shows the network is not improved, it tells the fix generator to try again by generating a new candidate update and validate it.

The above process iterates for several rounds until a repair is found,
or a maximum number of iterations is reached.

3.3.
Merits of Astragalus

The localize-fix-validate framework has three merits, compared with semantic-based approaches.

•

Scalability.
The search space for fix is relatively small,
as it only involves a small subset of configurations related to the suspicious one.

•

Generality.
The framework generalizes to different protocols and vendors, since it operates upon configuration syntax, rather than semantic.

•

Flexibility.
the framework allows a flexible choice of various techniques for each stage. For example, many SBFL methods can be applied for localization.

4.
Design

This section presents the design of Astragalus, which consists of three steps, i.e., localization, fix generation, and validation.

4.1.
Modeling the configuration

As a syntax-driven approach to ACR, the prerequisite for Astragalus to generate a valid fix is to keep the fix syntactically correct. This section focuses on the modeling of the configuration used by Astragalus.

Figure 2
.
A sample configuration snippet (a), the corresponding AST (b).

Most routing software and network simulators model the configuration as an abstract syntax tree
(
12
)
.
Similarly, Astragalus also internally represents the configuration files as an AST.
Figure
2
(b) is an example of the AST of Figure
2
(a).
It organizes the configuration into three nodes: BGP process, route policies, and prefix lists;
and each node is a well-formed structure containing child nodes, e.g. BGP peers and prefix list rules.
The leaves of the AST are singular parameters: A string like the import policy, a boolean for permit, and an IP address for the peer address.
To make the AST syntactically correct, its nodes are well typed; e.g., a route policy node cannot be a child of a prefix list.
We can only remove or add children to some of the AST nodes, e.g. adding a new rule to a prefix list is valid, but we cannot create a route policy with two permit / deny actions.

Astragalus generates syntactically valid candidate updates on the AST.
To meet the restrictions, we hereby define two terms:

(1)

A
configuration unit
is a node in the AST. The term
configuration unit
and AST node are used interchangeably throughout the rest of this paper.

(2)

A
container configuration unit
is a node in the AST that supports deleting or adding nodes of the same type as its children.

Here, the peers of a BGP process, the route policies, the nodes of a route policy, the prefix lists, and the rules of a prefix list are all container configuration units.

4.2.
Localization

In APR, spectrum-based faults localization (SBFL) is a widely-used technique which generates suspiciousness scores for each line of a given program.
Specifically, it uses a test suite
(
3
)
, and generates an
execution profile
, which contains:

(1)

A
coverage report
: what test cases are executed by each line of code.

(2)

An
error vector
: the pass / fail result for each test case.

Astragalus uses SBFL in the localization step.
The following section introduces how to construct the test suite,
how to execute the test suite to form the execution profile,
and how to compute suspiciousness of each configuration unit.

Prefixes as the test suite.

For APR, the test suite is a set of inputs to the program.
Since the input space of the program can be huge, and even unlimited, one has to sample some inputs to form a test suite.
By viewing the network control plane as a program, the inputs are a set of prefixes
announced by some devices inside the network or advertised into the network by some neighbors.
For example, BGP uses commands like
bgp network
and
bgp aggregate

1
1

1

bgp aggregate
networks are not included in the test suite because it is only announced if a detailed route in the range of aggregated prefix exist; we trace the detailed route instead.
to announce a prefix.
Compared to the huge input space of APR, the space of prefixes for a network’s control plane is often quite limited, and even fixed in prior.
For example, all prefixed announced inside the network can be easily determined based on the device configurations.
Therefore, Astragalus constructs the test suite as the set of all prefixes specified by all
bgp network
.
In case which external routes are also relevant, their prefixes are included in the test suite as well.

Computing the configuration coverage report.

Compared with APR, computing how each configuration unit is covered by a prefix seems to be tricky, since
the routing and forwarding behaviors are jointly determined by the configurations, the control plane semantics, and the routing software / simulator implementation.

However, we can still see the configurations as executable “code”:
When the routing software / simulator references one configuration unit while it is dealing with some route, we say the configuration unit is “executed”, and the unit is considered covered by the prefix of the route.

For example, in Figure
3
, the propagation of aggregate route 20.7.0.0/23 covers the following configuration units in sequence:

(1)

Line 14, as
S_{3}
is processing the BGP route aggregation;

(2)

Line 13, as the aggregate route is being exported by the BGP process to neighbor
S_{2}
;

(3)

Line 6, as the route is being received by the BGP process of
S_{2}
;

(4)

Line 8, as the BGP process of
S_{2}
is finding the neighbor configuration for the incoming routes;

(5)

Line 9, as the BGP process of
S_{2}
is processing import policy
RP_S3
for the route;

(6)

Line 10, as the route is processed by the route policy’s first node;

(7)

Line 11 and Line 12, as the route is being tested for the match condition
LE23
.

For Astragalus, we implement the coverage test functionality as an interface of the in-house simulator.
We start an iteration of data plane computation. The simulator records the coverage during its simulation process, and outputs the report to Astragalus.

The execution is initialized by simulating a single iteration of route advertisement from a converged data plane: each router sends all of its routes in the main RIB to neighbors.
The insight of starting from a converged data plane is as follows:
(1) the test cases (i.e. the
bgp network
s’ and external routes’ prefixes) are propagated to every destination as the control plane program suggests, so every logic that should be covered by the test cases is covered;
(2) because of the convergence, route withdrawal in transient states will not affect the coverage.
The converged data plane can be derived from the validation step of the previous ACR iteration to avoid duplicate calculation.
By aligning Astragalus’s AST with that of the simulator’s, the coverage report can be used seamlessly by Astragalus.

Generating the error vector.

In Astragalus, we use
specifications
, which are specified by the operators, to check whether a test case passes or not.
We use per-prefix forwarding graph as the default specification of Astragalus, as it implies many invariants in a network, such as reachability, blackhole freedom, loop freedom, route-hijacking freedom, and ECMP multipath. The forwarding graph can also be automatically generated in a well-formed hierarchical network like fat-trees.
For each prefix in the test suite, Astragalus generates the forwarding graph of that prefix from the data plane computed by the simulator, and checks if the forwarding graph is different from the one in the specification.
If the path violates the specification, Astragalus adds the prefix to the set of
failing tests
;
otherwise, Astragalus adds it to the set of
passing tests
.

Astragalus enables a wide range of specifications choices, as long as a specification can test whether a prefix meets its requirement.
For example, all-pair reachability is a parameter-free specification which can be adapted by Astragalus; the specification reports failure if and only if any of the nodes cannot reach the owner of the prefix.

In the example of Figure
3
, we mark two prefixes (10.0.0.0/26, 50.1.0.0/24) as passed, as they can be reached from all other devices;
we mark the other two prefixes (20.7.0.0/23, 30.5.0.0/23) which are denied by line 9 and 10 are marked as failed.

Calculating suspiciousness scores.

Astragalus can use any SBFL technique to calculate suspiciousness scores. Among the well-known methods like Tarantula
(
17
)
, Ochiai
(
3
)
, Jaccard
(
9
)
, and D-Star
(
29
)
, Astragalus uses Ochiai by default,
to calculate the suspiciousness scores for configuration units.
According to Ochiai, the suspiciousness of a statement
s
is calculated as:

(1)

\mathrm{susp}(s)=\frac{\mathrm{failed}(s)}{\sqrt{(\mathrm{failed}(s)+\mathrm{passed}(s))\cdot\mathrm{totalfailed}}}

where
\mathrm{failed}(s)
and
\mathrm{passed}(s)
represent the number of failed and passed test cases executed by the statement
s
, respectively;
Meanwhile,
\mathrm{totalpassed}
and
\mathrm{totalfailed}
represent the total number of failed and passed test cases.
The decision of using Ochiai SBFL technique as default is based on the evaluations in §
5.6
.

4.3.
Generating the Fixes

The fix generation step generates candidate repairs for the suspicious configuration units computed by the localization step.

How to fix.

For each suspicious configuration unit, Astragalus can use three
change operators
to fix the suspicious configuration unit.

•

Remove
deletes the node (and its subtree) of the suspicious configuration unit from the AST.

•

Insert
inserts a node into the suspicious configuration unit in the AST.

•

Modify
changes the value of the suspicious configuration unit to other values different from the current one.

Where to apply
Remove
/
Insert
/
Modify
.

As discussed in §
4.1
, to maintain the syntactic validity of the AST, only
container configuration units
support
Insert
and
Modify
operators.
As a result, we restrict
Remove
/
Insert
to be applicable to only container configuration units;
Modify
can be applied to any configuration unit.

What to
Insert
/
Modify
.
As the plastic surgery hypothesis suggests, Astragalus inserts into / modifies the suspicious configuration unit with nodes that exists elsewhere.
At first glance, it seems there are a large number choices for configuration lines to copy and parameters values to modify.
However, we find that the number of all feasible choices is quite limited for network configurations, due to device roles and configuration syntax.
More specifically, Astragalus selects a device of the
same role
(including the device itself) as the template device,
and chooses a configuration unit of the
same type
as the suspicious unit.

Figure
3
(a) shows the fixes that can be generated from the suspicious configurations, only part of the
Modify
and
Insert
options are shown. For example, line 8 shows the possible repair options for configuration unit
route-map RP_S3 in
. As the import policy is optional (i.e. a container configuration unit with capacity of 1), the
Remove
option can be applied; it may also paste the route policy name
RP_S1
from line 7.

Deciding the order of fixes.

Astragalus generates all possible fixes for configuration units with a suspiciousness score
>0
.
Then, Astragalus sorts the possible fixes from high to low based on the suspiciousness of the configuration unit from which each fix is generated.
If multiple configuration units have the same score, then
Remove
updates are placed higher in the list and searched earlier, since there are at most one removing option per configuration unit, and it is more likely to yield a successful repair based on our tests;

Insert
updates are placed after
Remove
, and finally
Modify
, If the comparison is a tie, their order in the list is determined randomly.

The order is decided based on the heuristics of the data center studied.

The list then forms all candidate updates of the network, as shown in Figure
3
(b).

4.4.
Validating the Fixes

For each fix, Astragalus first apply the fix to the configurations, thus forming a new control plane consisting of the new configurations.
Then Astragalus computes the data plane, and validate the fix by testing if all test cases are passed, using the specification described by §
4.2
.

The above process of generate-and-validate is repeated for multiple iterations until a repair is found.
In each iteration,
we apply the topmost repair option in the candidate update list (as shown in Figure
3
) to our network,
and a new set of configurations with the repair applied (e.g. the removal of line 6 in
S_{2}
) is produced.
By viewing the old and new set of configurations as two states,
each iteration can be seen as transition from the old state to the new one.
Therefore, Astragalus needs a search strategy to efficiently explore the state space of configurations.

Currently, Astragalus adopts a depth-first strategy as follows.
After each iteration,
if the new configuration state produces less errors,
then we fork a new iteration base on the new state,
and start searching on the state immediately.
To avoid duplicates, we will check whether the state has been visited before executing the iteration.
We also backtrack to the previous state if the repair option is exhausted.

If we find the state that produce no error, we report a successful repair, with the path to the final state as the final repair suggestion.

5.
Evaluation

In this section, we evaluate Astragalus to answer the following research questions:

(RQ1)
Can Astragalus accelerate the repair / fault localization of network configurations?

(RQ2)
Can Astragalus improve the scalability of ACR to larger production networks?

(RQ3)
Can Astragalus provide higher quality repair suggestions than existing tools?

(RQ4)
Is localization (SBFL) effective for repairing network configurations?

We implemented Astragalus with

To reflect the characteristics of the CSP’s real data center networks (DCNs), we have modified the configurations as follows.

•

In DCNs, the devices at the same layer reuse the ASNs.
As a result, the AS-path of a BGP route sent across a layer twice may contain two identical ASNs.

In the route policies created above, we mimic this characteristic by introducing some redundant route policies, e.g.,

Misconfigurations.

We consider 15 types of configuration errors, as shown in Table
1

The first 7 are real historical bugs, while the remaining 8 are bugs that we hypothesized to be at risk of occurring.
For each type of error, we generate 100 instances for the above two configuration datasets.

wrong

These errors may lead to two types of incidents:
(1) reachability incidents, where one or more devices cannot reach a prefix;
and (2) path change incidents, where the forwarding paths in the misconfigured network are different from the original ones.

For the real configuration dataset, 100 errors cause path change incidents for each error type.

5.5.
(RQ3) Repair Quality

To quantify the repair quality of Astragalus, we evaluate how many repair suggestions are given by directly removing the root cause of the problem,
i.e. removing the misconfiguration being injected.
we define
hit ratio
as the frequency of a tool giving a repair suggestion with the location
exactly the same
as the location where the misconfiguration is injected.
That is, if a repair is “add a static route”, it does not count as a hit since it does not localize the root cause.
This metric roughly estimates the probability that the repair solutions provided by Astragalus are
directly adopted
by operators.

For each network to be repaired, CEL gives multiple
candidate predicates
, which can be seen as the possible locations of misconfigurations.
To apply a fix, network engineers also need to investigate all of the candidate predicates.
We calculate the frequency of the root cause as the frequency of the root cause in all candidate predicates.

5.6.
(RQ4) Localization quality

Astragalus searches candidate updates guided by the suspiciousness given by SBFL.
Without an efficient localization strategy, Astragalus may end up with randomly searching and validating in space of all configuration units,
which is extremely time consuming.
As a result, the localization quality directly determines the efficiency and quality of Astragalus.

We define
relative root cause location

L_{r}
as the ratio of position of the root cause configuration in the list to the number of all suspicious configuration units.
For example, if the suspiciousness of the root cause is 0.5, and there are 5 configuration units with suspiciousness higher than 0.5 out of a total of 100 configuration units, the relative root cause position is
5/100=0.05
.

The distribution of
L_{r}
indicates how effective the localization is.
If we choose the fix randomly from all suspicious configuration units,
L_{r}
should satisfy uniform distribution, where the root cause should be found anywhere with equal possibility density;
if the localization method is effective, we should expect more root causes to be found in prior positions.

but all of the three methods can find the root causes faster than Tarantula.

We choose Ochiai as the default because it is one of the three faster SBFL techniques, but using Jaccard and D-Star

will not make localization observably less accurate.
Choosing Tarantula, however, would make the localization, and the repair slower.
In fact, in fat-tree with
k
as small as 6, Tarantula cannot find a valid repair within 6000 iterations for 9 cases of path change incidents, making the repairing time more than 5 minutes;
while using Ochiai, all faults in the synthesized dataset can be repaired within 2607 iterations.

6.1.
Incident A: Blackhole due to VSBs

Network and configurations.

The network comprises
\sim
1000 devices, and each device has
\sim
20,000 lines of configuration on average.
As shown in Figure
8
(a),
The network includes multiple data centers (only two of them are shown, with ASN 12 and ASN 13), and they are connected by a transit AS (AS11).
In AS11, each data center has two peering switches (
S_{3}
,
S_{4}
for AS12, and
S_{7}
,
S_{8}
for AS13) which are connected to the neighbor AS, and a BGP route-reflector (RR).
The RRs of the two datacenters establish IBGP peer to exchange routes from two data centers;
and the peering switches only establish IBGP peer with the corresponding RR (
S_{3},S_{4}\leftrightarrow RR_{1}
,
S_{7},S_{8}\leftrightarrow RR_{2}
).

Many data centers in the network reuses ASN in some layer of the network.
As a result, the AS-path of a BGP route sent from from one data center to another may contain two identical ASNs.
To prevent routes from being dropped because of EBGP loop prevention mechanism,
the peering switches in AS11 configures
as-path rewrite
(as the import policy from the AS12 / AS13) to override the AS path of the routes sending to another data center.
Any routes with the AS-path containing ASNs from the original data center will be replaced with ASN 11 repeated several times.

The incident.

The operators found that the routes originated from ASN 12 could not be received by the devices in ASN 13.
The root cause is that the operators overlooked the vendor-specific behavior (VSB) of the RRs – it not only have EBGP loop prevention mechanism in BGP standard, it also have IBGP loop prevention:
it would discard a route if it contains the ASN it belongs to.
As
S_{3}
and
S_{4}
rewrited the AS-path of the route from AS12 to several 11s,
RR_{1}
thought it contains an IBGP loop.
As a result,
RR_{1}
could not learn the routes from AS12, and all of
RR_{2}
,
S_{7}
,
S_{8}
,
S_{5}
and
S_{6}
could not receive it.

The repair suggestion given by Astragalus.

Astragalus gave 2026 candidate updates for the network fault.
Among these updates, the 23
{}^{\textrm{rd}}
most suspicious update is to
Modify

set as-path
replace
to
set as-path
exclude
in the import policy from
S_{1}
in
S_{3}

Effectively, instead of overriding the AS-path by its own ASN, it empties the AS-path attribute directly.
Thus, it prevents the IBGP loop prevention mechanism of
RR_{1}
from acting unintentionally, while also serves the purpose of preventing routes drop by EBGP loop prevention in other data centers.

Astragalus adopted it as the fix successfully restores the reachability requirement from AS13 (via
S_{3}

Nonetheless, AS12 is still unreachable via
S_{4}

S_{4}

The network is now fixed with correct ECMP paths to AS12.

Lessons learned.
(1) Astragalus is scalable. It can be applied on on real, hyper-scale data center networks, providing repair suggestions in minutes.
(2) SBFL in network configuration is effective, as the root cause is found in top 1.1% of the candidate updates.

7.
Discussion

Using LLMs for fix generation.

In this paper, we leveraged the “plastic surgery hypothesis” for repair network configurations.
When generating fixes, we used heuristics to generate fixes from candidates.
Recent studies (e.g.,
(
30
)
) suggests that LLMs can be used to find better fixes.
We will try to apply similar approaches to improve the quality of fixes in the future.

Repairing data plane misconfigurations.

Astragalus currently repairs only misconfigurations for routing protocols (e.g., BGP).
There are other configurations used for data plane forwarding (e.g., policy-based routing and NATs),
and can also cause network incidents if there are errors.
For data-plane configuration, the same SBFL approach also works.
By viewing packets as test cases, and test packet forwarding properties (reachibility, blackhole-freedom, etc.),
the localization approach can be also applied on data plane configurations.
As the simulator only supports simulation of control plane. Astragalus currently is unable to fix these configurations.
In the future, we will try to implement the ACR principle on data plane or general network simulators to enable the repair of data plane configurations.

Repairing wide-area network configurations.

In this paper, we design and evaluate Astragalus based on data center network configurations.
For other kinds of networks such as WANs, we tentatively think the plastic surgery hypothesis also holds, as there are also some level of redundancy (e.g. multiple border routers peering with the same ASes).
Therefore, we hypothesize Astragalus can be a general tool for repairing these networks.
We leave the evaluation of Astragalus on WANs as a future work.

Limitations.

For those incidents caused by missing the origin of the route – advertisement statement, route redistribution, static route, etc.,
Astragalus cannot generate the coverage report based on current test suite, since the faulty prefixes are not generated, and configuration units cannot.
We leave it to manual troubleshooting because they are relatively obvious.

8.
Conclusion

In this paper, we motivate the need of automatic configuration repair (ACR) with

Inspired by APR, we propose to achieve ACR with a syntax-driven approach, which is general and scalable.
Specifically, we design and implement Astragalus, and evaluate it based on configurations of real production networks.
We show Astragalus can repair over 97.5% of the injected errors within 5 seconds.

This work does not raise any ethical issues.
