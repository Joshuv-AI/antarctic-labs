 Overview
 Purpose

The LMX file format is designed to store neutron detection events in a list-mode scheme for use by
neutron multiplicity counting analysis hardware and software. It supports the accurate and ordered
recording and storage of neutron detection events and the context of the recording providing
comprehensive information about the counter as well as the assayed material (Geist et al., 2024, p. 445).
LMX is associated with List Mode Control (LMC) software.

 Scope

This specification defines:
 • File structure
 • Header layout
 • Data sections
 • Metadata encoding
 • Versioning rules
This specification does not define:
 • Application-level behavior outside file parsing
 • User interface behavior
 • Storage transport protocols
 • Licensing or commercial terms

 Intended Audience

This document is intended for:
 • Engineers implementing readers
 • Engineers implementing writers
 • QA and test engineers
 • Tooling and interoperability teams

 File Type

LMX is a hybrid file format consisting of a variable-length header section containing key-value pairs
providing metadata about the file and list-mode recording context, followed by a binary container format
where each “row” is defined as a sequence of a specified number of bytes (typically 8) which can be (a) a
flag, which are defined explicitly in the header section or (b) a recording of a neutron detection event,
where the first half of the bytes in the row record the channel on the neutron coincidence counter where
the event occurred and the second half of the bytes in the row record the timestamp of the event.

 Design Goals

 • Preserving the full neutron pulse train.
 • Preserve event channel information when available.
 • Provide partially human-readable header in file and measurement condition metadata.
 • Use compact event storage without discarding timing or channel information.
 • Support fast sequential reading for offline analysis.
 • Keep the format simple to implement.

 Non-Goals

 • The format does not support in-place modification after acquisition/finalization.
 • The format does not support error correction.
 • The format does not require byte-for-byte identical files from different writers for semantically
 equivalent data.
 • The format does not provide transport-level security, encryption, or authentication.
 • This format does not provide or verify file integrity.
 • The format is not intended for direct human editing.
 • The format was not designed to work with more than 32 channels.

Encoding Rules

 Encoding Rules
 Header Data Encoding

Data in the header MUST be stored as strings (i.e., text-based). This includes integers, floating points,
text, date and time values, and anything else.

A string value is the sequence of Unicode scalar values represented by the ASCII bytes before and after
the separator “:” and before the line terminator.

Strings MUST be encoded as ASCII text.

String values SHOULD be terminated by the Carriage Return Line Feed (CRLF, 0x0D 0x0A) bytes but
may be terminated with just a Line Feed byte.

Leading and trailing whitespace in string values is significant unless otherwise specified.

Header data (ASCII) MUST be written and sent in buffers of an odd size. Readers MUST assume buffers
received with an odd size contain ASCII data.

Table 2: Header String Encoding Properties
 Property Rule
 Encoding ASCII
 Length unit Bytes
  Null termination Not used
 Empty string Length 0
  Maximum length 2575 bytes
 Invalid ASCII MUST be rejected

 Binary Data Encoding

Each row in the binary data container MUST be the exact number of bytes specified by the
BinaryDataEventSizeInBytes value in the header.

Each row of binary data MUST contain two sets of data. The first set of bytes in the row MUST be the
channel information (i.e., the channel mask). The second set of bytes MUST be the clock information
(i.e., the timestamp).

The number of bytes required by the channel mask, hereinafter referred to as the channel mask bytes,
MUST be determined by the data type specified by the BinaryDataChannelFormat value in the header.
The number of bytes required by the clock information set, hereinafter referred to as the timestamp bytes,
MUST be determined by the data type specified by the BinaryDataClockFormat value in the header.

There MUST NOT be any padding or alignment between each row.

Control events (16 bytes) MUST consist of exactly two consecutive records.

The final two lines of the binary data container MUST be the End Flag control event (0x00000000
followed by 0xFFFFFFFF in the channel mask bytes).

Encoding Rules

LMX has already been implemented in functional readers/writers in real-world applications, with a tacit
standard that has been adopted by existing implementations. This standard assumes that the header fields
below are read, written and adhered to as follows:
 • The BinaryDataEventSizeInBytes value SHOULD be 8.
 • The BinaryDataChannelFormat value SHOULD be unsigned int32. In other words, the channel
 mask SHOULD be represented by an unsigned int32 requiring 4 bytes.
 • The BinaryDataClockFormat value SHOULD be unsigned int32. In other words, the timestamp
 SHOULD be represented by an unsigned int32 requiring 4 bytes.
While the above values MAY change, the vast majority of existing LMX readers/writers utilize and
assume the standard of those header values defined above. Therefore, it is highly recommended that
future readers/writers continue to follow this standard.

Binary Container data (Binary) MUST be written and sent in buffers of an even size. Readers MUST
assume buffers received with an even size contain Binary data.

 Channel Mask Encoding

The channel mask bytes in each row MUST indicate physical detector channels associated with the event.
Each “high” bit (bit set to 1) indicates a channel associated with the event. When multiple channels are
associated with the same event, multiple bits will be high.

The channel mask bytes MUST be in little-endian order.

The channel mask uses a direct bit-to-channel mapping where bit position N corresponds to Channel
(N+1). Devices with fewer than 32 channels SHOULD allocate channels to consecutive bit positions
beginning at bit 0. However, implementations MAY use non-zero starting bit positions if required by
hardware architecture. For instance, an 11-channel device SHOULD map its channels to bits 0-10, but
MAY alternatively map to bits 4-14.

 Timestamp Encoding

The timestamp bytes in each row MUST represent the elapsed time relative from the start of the data
acquisition. The timestamp represents the nearest hardware clock tick, as defined by
BinaryDataClockTickLength in the header, associated with an event.

The timestamp MUST start at 0 when data acquisition begins. The first timestamp reported on a recorded
event MAY (and will typically) be greater than 0.

Encoding Rules

The timestamp MUST NOT be tied to any absolute time.

The timestamp MUST be monotonically increasing until each clock rollover control sequence/event,
where it resets to the minimum value. The final timestamp value recorded before a clock rollover
sequence/event MUST be the maximum value (typically 0xFFFFFFFF).

The timestamp bytes MUST be in little-endian order.

 Standardized Header Comments

The Header Section of an LMX file MAY contain 0 to many ‘Comment’ fields.

Each comment field SHOULD be less than 51 characters in length for readability. Comments requiring
additional characters SHOULD utilize multiple comment fields to continue the full comment.

Each LMX file SHOULD contain at least the following standardized comments within the header section:

Comment : If all channels are zero, this indicates channels
Comment : in next event is a flag (not a real event)
Comment : Flag = 0x00000001 (Clock rollover occurred)
Comment : Flag = 0x00000002 (Gate input started)
Comment : Flag = 0x00000003 (Gate input ended)
Comment : Flag = 0x00000004 (User pause started)
Comment : Flag = 0x00000005 (User pause ended)
Comment : Flag = 0x00000008 (Timing sync occurred)
Comment : Flag = 0xFFFFFFFF (End of binary data)

 Purpose

The Binary Data Container section of an LMX file contains the sequential, list-mode recording taken by a
neutron coincidence counting instrument. Each row (i.e., a Detection Event or DetectionEvent) is a
section of bytes (whose size is dictated by the BinaryDataEventSizeInBytes header field value in the
header, typically 8) represents (a) a neutron detection event, where the binary data stores both the
channel(s) where the event was detected and the timestamp at which the event occurred or (b) a flag
representing a control/status event.

A binary data container MAY contain no neutron detection events but MUST contain at least one or more
flags.

For the sake of simplicity and understanding, the rest of this section will assume the following
standardized configuration:
 • The BinaryDataEventSizeInBytes value is 8, meaning each row of binary data is 8 bytes.
 • The BinaryDataChannelFormat value is an unsigned int32. In other words, the channel mask is
 represented by an unsigned int32 requiring 4 bytes.
 • The BinaryDataClockFormat value is an unsigned int32. In other words, the timestamp is
 represented by an unsigned int32 requiring 4 bytes.

 Binary Data Container Definition

struct BinaryDataContainer {
 struct DetectionEvent listOfEvents;
}

struct DetectionEvent {
 byte[4] channelMask;
 byte[4] timestamp;
 struct DetectionEvent* next;
}

Here, the ‘next’ in DetectionEvent is conceptual only and signifies the next 8 bytes in the stream. It is not
a stored field.

 Binary Data Container Grammar

The general grammar for each Detection Event in the Binary Data is as follows:
<binary_data> ::= { <binary_record> }
<detection_event> ::= <neutron_event> | <control_event>
<neutron_event> ::= <non_zero_channel_mask> <timestamp>
<control_event> ::= <marker_record> <flag_record>
<marker_record> ::= <zero_channel_mask> <timestamp>
<flag_record> ::= <flag_value> <timestamp>

 Binary Data Channel Mask Writing and Reading Examples

The Channel Mask portion of each DetectedEvent can support reporting neutron detection events across a
minimum of 1 channel and a maximum of 32 channels. A neutron detection event MUST NOT ever be
recorded with none of the bits set to high (all 0’s), as this is reserved for control sequences.

Multiple channels MAY be associated and recorded with single neutron detection events. The bytes are

01 00 00 00 <timestamp>

An event recorded on channels 1, 2, 3, 4, 6, 7, 8, 25, 26, 27, and 28 will look as follows:

// Corresponds to 0000 0000 0000 1111 0000 0000 1110 1111

And so on.

 Binary Data Timestamp Writing

Timestamp values MUST begin and, at a minimum, start at 0. The first value output after starting
acquisition or a clock rollover event MAY (and typically is) greater than 0.

The value written for the timestamp MUST be equal to the number of ticks which have passed since the
beginning of acquisition relative to the DetectionEvent’s occurrence. The length of a tick is defined in the
header field BinaryDataClockTickLength, typically 100 nanoseconds.

The timestamp counter MUST reach its maximum value (0xFFFFFFFF for 4-byte counters) before
wrapping to zero. The last timestamp value before wraparound MUST be 0xFFFFFFFF, which may
appear in either a neutron detection event or the rollover flag marker record. This ensures the integrity of
multiplexing algorithms when multiple neutron detectors are producing LMX files that are merged by
time-sensitive hardware for efficiency.
