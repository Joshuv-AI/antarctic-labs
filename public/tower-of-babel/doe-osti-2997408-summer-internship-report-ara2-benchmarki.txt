1 Introduction
Over the past decade, the RISC-V Instruction Set Architecture (ISA) has emerged
as a significant player in both academic and industrial processor design due to its
open-source nature, modular extension system, and versatility across domains
ranging from microcontrollers to high-performance computing (HPC). One of
its most important recent advancements is the RISC-V Vector Extension
(RVV), which enables explicit data-level parallelism through vector registers and
vectorized instructions. Unlike traditional SIMD (Single Instruction, Multiple
Data) architectures that fix vector lengths at design time, RVV uses the con-
cept of VLEN (vector register length) as a hardware-independent parameter and
allows software to adapt dynamically to the available vector width. This flexi-
ble approach ensures portability across implementations while enabling scalable
performance.
 The ARA2 core is a parameterizable RISC-V vector processor developed
at the Integrated Systems Lab at ETH Zürich and the University of Bologna.
Designed as a tightly-coupled accelerator to a scalar RISC-V core, ARA2 im-
plements the RVV 1.0 specification and offers tunable architectural parameters
such as the number of vector lanes, VLEN, and cache sizes.

2 Methodology
During the internship, we evaluated the performance of the ARA2 vector core
using a suite of benchmarks adapted from the Barcelona Supercomputing Cen-
ter’s repository (GitHub user: RALC88). Benchmarks from the ARA2 repository
were also adapted to run on OpenXiangShen and evaluated on ARA2 as addi-
tional correctness and sanity checks. Modifications were made to allow bench-
marks to accept external .bin data files instead of relying solely on built-in
script generation or runtime computation. This adaptation was designed to fa-
cilitate portability to other cores, such as the OpenXiangShan core, enabling
cross-platform performance comparisons.

 The primary performance metric recorded was the total cycle count required
for benchmark completion. Configurations with VLEN = 128 and four or more
lanes did not execute successfully on most benchmarks tested. The ARA2 core
is optimized for long vector length and the source code includes a comment that
VLEN must be greater than 128.

3 Benchmarks
This section details the benchmarks used to evaluate the ARA2 vector unit and
the modifications made to them.

3.1 MatMul
MatMul is a matrix-matrix multiplication benchmark from the BSC benchmark
suite. This was the first benchmark adapted as detailed in Section 2. The data
generation script was modified to save the data in external .bin files that could
be used by other cores.

3.2 axpy
The axpy benchmark implements the operation r = a · x + y.

 2

3.3 dotproduct
The dotproduct benchmark was adapted nearly as is from the ARA2 benchmark
suite, with minimal changes other than providing the data in external .bin
files. Due to the use of the dotproduct benchmark in the original paper that
discusses the ARA2 core, our most intensive evaluation was performed using this
benchmark. We used a version of this benchmark that performs a few initial
iterations to warm the cache.

3.4 SpMV
The SpMV benchmark, taken from the BSC benchmark suite, implements a
sparse matrix-vector multiplication. The sparse matrix is represented in COO
form. It is important to note that vector intrinsics based benchmarks from both
the ARA2 team and BSC reported incorrect results for some array elements. As
such, we used the serial version of the benchmark and used this as an opportunity
to investigate the auto-vectorization capabilities of clang for the ARA2 stack.
Two matrices we tested were the football benchmark (M=115, N=115, 613
non-zeros) and the larger lhr07 benchmark (M=7337, N=7337, 156,508 non-
zeros).

4 Results
Data was collected for a diverse set of benchmarks, as discussed above, including
matrix multiplication (MatMul), AXPY, dot products of various precisions, and
sparse matrix-vector multiplication (SpMV). Representative configurations were
plotted as charts for visual comparison. Configurations are represented in the
form (lanes, VLEN, L2 size exponent). For example, a configuration represented
as 8, 8192, 21 is a configuration with 8 vector lanes at a VLEN of 8192, and
an L2 cache with 221 words.

Example Observations:
 • MatMul 64x64 and 128x128: Showed clear scaling with both lane
 count and VLEN. Performance gains were substantial up to moderate
 vector widths, after which the improvements became incremental.

 • AXPY 1024: Improvements from increased lanes and VLEN were mod-
 est, indicating a bandwidth-bound kernel.
 • Dot Product (64b, len 4096): Performance scaled with lanes until
 memory throughput became the bottleneck.
 • SpMV (football, lhr07): Vectorization via clang had only marginal
 effect, reducing cycle counts by less than 0.1% compared to the serial
 version. This is consistent with the irregular access pattern of SpMV and
 the limited ability of clang compiler vectorization on the SpMV memory
 access pattern. L2 cache size showed no effect across both datasets.

6 Analysis
Our results show that increasing hardware parallelism through additional vector
lanes and larger vector lengths (VLEN) generally improves performance, though
the benefits are workload-dependent. Compute-bound kernels such as matrix
multiplication scale strongly with both parameters, while bandwidth-sensitive
benchmarks like AXPY saturate earlier and show only modest improvements.
Dot products scale until memory throughput becomes the limiting factor, and
sparse matrix-vector multiplication benefits from added parallelism despite its
irregular access pattern.
 Cache analysis highlights key differences between ARA2 and OpenXiang-
Shan. Increasing the L1 cache size from ARA2’s 4KB baseline to 128KB, as
in OpenXiangShan, had no measurable impact on performance. Reducing it to
2KB did degrade performance (not shown in charts). L2 cache size similarly
had minimal effect unless the data set was small enough to fit entirely in L2.
Benchmarks on OpenXiangShan showed performance benefits of having L3, but
ARA2 lacks a third level cache.

7 Conclusion
Overall, these findings show that for the benchmarks studied, ARA2’s perfor-
mance is dominated by compute resources (lanes, VLEN) rather than cache
sizing. The benchmark modifications and dataset developed here provide a
foundation for systematic vector unit analysis and cross-platform comparison
going forward.
