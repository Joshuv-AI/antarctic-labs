RepoLaunch: Automating Build&Test Pipeline of Code Repositories on ANY Language and ANY Platform
Kenan Li, Rongzhi Li, Linghao Zhang, Qirui Jin, Liao Zhu, Xiaosong Huang, Geng Zhang Yikai Zhang, Shilin He, Chengxing Xie, Xin Zhang, Zijian Jin, Bowen Li, Chaoyun Zhang Yu Kang, Yufan Huang, Elsie Nallipogu, Saravan Rajmohan, Qingwei Lin, Dongmei Zhang Microsoft

Abstract
Building software repositories typically requires significant manual effort. Recent advances in large language model (LLM) agents have accelerated automation in software engineering (SWE). We introduce RepoLaunch, the first agent capable of automatically resolving dependencies, compiling source code, and extracting test results for repositories across arbitrary programming languages and operating systems. To demonstrate its utility, we further propose a fully automated pipeline for SWE dataset creation, where task design is the only human intervention. RepoLaunch automates the remaining steps, enabling scalable benchmarking and training of coding agents and LLMs. Notably, several works on agentic benchmarking and training have recently adopted RepoLaunch for automated task generation.

Introduction

Building software repositories (repos) often requires substantial human effort. Repository configurations vary widely, documentation is frequently incomplete, and different platforms have specific dependency and compilation errors, necessitating multiple rounds of trial and error.

Recently, there has been growing interest in evaluating large language model (LLM)-driven agents on real-world coding tasks within executable environments, as well as training LLMs using execution feedback. Notable benchmarks include the SWE-bench family: SWE-bench
(
9
)
, SWE-bench-Multimodal
(
14
)
and SWE-bench-Multilingual
(
15
)
. Recent training works on these SWE benchmarks include rejection supervised fine-tuning and reinforcement learning
(
17
)

(
6
)

(
4
)
. These advances underscore the need for scalable methods to build massive number of executable sandboxes and extract test results for evaluating agent performance—far exceed manual capacity, motivating the need for agentic automation.

GitTaskBench
(
11
)
tests LLM agents to solve GitHub issues on raw repos without a pre-built executable environment. It reports that in
65%
of cases, agents fail to build executable environments before resolving issues. The experiment reveals two key insights: (1) building repositories is itself a challenging problem that warrants dedicated study; and (2) combining repository setup and issue resolution into a single task can obscure the distinct challenges and failure modes of each stage. These observations further emphasize the importance of producing and managing pre-built executable repo sandboxes at scale.

Based on such demands, we propose RepoLaunch, an agent for fully automated repository build and test status management. To the best of our knowledge, RepoLaunch is the
first
agent capable of handling any programming language and any platform, given only the language’s basic build/test prompts and a base OS image. RepoLaunch autonomously explores a repository to install dependencies, compile the code and execute regression tests. Beyond initial builds, it also supports repository maintenance by generating minimal rebuild commands after code modifications and extracting test statuses —capabilities that are essential for long-term repository management.

Our experiments demonstrate that RepoLaunch can build and test repositories across nine programming languages on both Windows and Linux platforms, achieving a build success rate of approximately 70%. RepoLaunch enables the automatic creation of large-scale, diverse SWE task instances for evaluating and training coding agents. We further benchmark recent LLMs and agent systems on the multi-language, multi-OS tasks generated by RepoLaunch, offering insights into their current capabilities and limitations.

The contributions of this work are threefold:

1.

An agentic method that automates repository build and test status management
generalized to any language and any platform, eliminating the tedium of human effort.

2.

A fully automated pipeline to create SWE tasks
to evaluate and train LLM agents, with task design as the only human effort. We release SWE-bench-Live/MultiLang and Windows together as demonstration.

3.

A comprehensive failure pattern analysis of agentic repo build & test task
is further provided to guide future research on this topic.

Related Works

Rule-based automatic repo-build tools.
Some works have used rule-based methods to build repos. Oss-Fuzz-Gen relies on predefined build instructions (such as “./bootstrap.sh”, “./configure”, “make”) in specified files to build repos. Starter

These rule-based methods cannot cover the huge variants of project settings and structures, especially for noisy GitHub public repos, illustrating the necessity of LLM agents to inspect repos case by case.

Initial efforts to build repos with agents.
Several works have made some initial efforts to use agents for the setup of Python repos in Linux environments. Repo2Run
(
8
)
designed an agent for Python repos to install dependencies, change base images, execute tests and organize agents’ commands into a Dockerfile as the result. SWE-bench-Live
(
19

and SWE-rebench
(
2

designed agents to generate installation and test commands for Python repos at the commit before a pull request was merged, and created code-fix tasks for benchmarking and training of coding agents with the requirements of this pull request. They leverage simple pytest–format parser to manage the test statuses. While Repo2Run and SWE-rebench prompt LLMs to generate a Dockerfile directly from repo content, SWE-bench-Live adopts our initial version of RepoLaunch Agent designed for Python only, exploring the repos and make trial commands freely in docker containers. However, setting up Python repos on Linux is very trivial, mostly with one simple command like "pip install ."; the test framework of Python is also unified and simple, with pytest covering most cases. Generalizing the automated build and test task to all languages and operating systems requires complex exploration process which direct Dockerfile generation cannot cover, and we address as follows.

3
RepoLaunch

We address two core challenges in automating software repository management. The
first
is how to build a repository and make it executable using an agentic method. The
second
is how to manage the repository after the initial build—specifically, how to support repeated rebuilds, re-tests, and test status monitoring over time. We formally define our problems in
Section 3.1
. To address them, we propose RepoLaunch – a multi-agent workflow comprising three stages:
Preparation
(Section 3.2),
Build
(Section 3.3) and
Release
(Section 3.4). We then demonstrate one application of RepoLaunch with an
automated pipeline for SWE benchmark creation
(Section 3.5).

3.1
Problem Formulation

Let
R\in\mathcal{R}
be a target repository.
Let
\mathcal{S}
be the set of environment states and
\mathcal{C}
the set of command sequences.
Define

\delta:\mathcal{S}\times\mathcal{C}\to\mathcal{S}

as the state–transition function, and

\varepsilon:\mathcal{R}\times\mathcal{S}\to\{0,1\}

as the verification function, where exit code
0
denotes a successful build.
Let
\mathcal{B}\subseteq\mathcal{S}
be the set of admissible base images, and let
S_{\emptyset}\in\mathcal{S}
be the bare operating system.

In the first stage of
Preparation
, a base image
B
is decided by executing a discovery sequence
C_{B}\subseteq\mathcal{C}
:

B=\delta(S_{\emptyset},C_{B}),\qquad B\in\mathcal{B}.

In the second
Build
stage, given
B
, a build command sequence
\mathcal{P}\subseteq\mathcal{C}
is selected such that

S_{f}=\delta(B,\mathcal{P})

satisfies

\varepsilon(R,S_{f})=0.

In the third stage of
Release
, we fix the solution
(B^{*},\mathcal{P}^{*})
from Build stage. A minimal rebuild subsequence needs to be extracted
\mathcal{P}_{R}\subseteq\mathcal{P}^{*}
such that for any updated repository
R^{\prime}
yielding an updated base state
B^{\prime}
,

S_{f}^{\prime}=\delta(B^{\prime},\mathcal{P}_{R})

still satisfies

\varepsilon(R^{\prime},S_{f}^{\prime})=0.

Let
C_{\mathrm{test}}\in\mathcal{C}
be commands to print logs of per–test status.
Let
\mathcal{L}
be the set of logs produced by

\lambda:\mathcal{S}\times C_{\mathrm{test}}\to\mathcal{L}.

Let
\mathcal{T}
be the set of test cases with status space

\mathcal{O}=\{\mathrm{pass},\mathrm{fail},\mathrm{skip}\}.

We also need to determine a parser

\Pi:\mathcal{L}\to\mathcal{O}^{\mathcal{T}}

mapping logs to outcome assignments.

However, leveraging LLM agents to achieve each of the above stage is non-trivial, which we address with a multi-agent workflow as follows.

3.2
Preparation Stage

Utilities
. RepoLaunch begins with two key utilities: (1) a
base image
, which provides a minimal operating system environment with basic dependencies for a given programming language, and (2)
language-specific instructions
, which offer build and test guidance for common frameworks in that language. See Appendix
A
for base image list and the instructions. These utilities are central to RepoLaunch’s generalization capability. From experiments we found that the pre-built base images do not affect success rate of the agent, but only reduce trial steps and image size; however, the instructions do affect the success rate, as current LLMs lack sufficient knowledge of the diverse frameworks used across programming languages.

Preparation Agent.
The Preparation Agent scans the repository’s file tree to identify relevant configuration and instruction files. It reads their contents to determine what to retain for downstream stages. Based on this analysis, the agent selects an appropriate base image, launches a
container
from the image, and copies the repository into it. The base image name, relevant file contents, and language-specific instructions are then passed as prompts to the next stages.

3.3
Build Stage

Setup Agent
. The Setup Agent uses the context from the Preparation stage to install dependencies and compile the repository. It is equipped with a
Bash
tool for executing shell commands within the container and a
WebSearch
tool for retrieving external knowledge to resolve errors. After attempting to build the repository, the agent searches for the repository’s regression test commands. If a majority of test cases pass, the container is handed off to the
Verify Agent
.

Verify Agent
. The Verify Agent validates the build outcome to mitigate potential hallucinations by the Setup Agent. It inspects the command history to identify test commands that report the status of
individual
test cases. If the majority of tests pass, the container is committed as a new image. Otherwise, the agent reports the failure back to the Setup Agent for retry. This loop continues until a maximum number of retries is reached, after which the build is marked as failed.

3.4
Release Stage

In the final stage, the
Organize Agent
extracts reusable artifacts from the previous records.

Rebuild commands.
The Setup Agent’s command history may contain redundant or failed steps. The Organize Agent filters and optimizes this sequence to produce a minimal set of
rebuild commands
that can re-install the modified dependencies and recompile the project after code edits. These commands are then executed in the container to verify correctness. If issues are detected, the agent iteratively refines the commands until they execute successfully.

Test commands and parser.
Similarly, the Organize Agent distills the Verify Agent’s command history into a minimal set of
test commands
that output the status of each test case. It also generates a
test log parser
—a Python function that parses the test output and returns a structured mapping from test case names to their statuses. When possible, the agent prefers test commands that produce structured output (e.g., JSON or XML) to reduce the difficulty of log parsing. If the test framework automatically dumps the structured test statuses to a default path, the agent generates commands to print the file contents for parsing. Although RepoLaunch supports delegating failures in this stage back to the Setup Agent, we disabled this feedback loop in our experiments for efficiency.

Per-test command (Optional).
In scenarios where fine-grained test control is needed downstream, the agent attempts to generate commands for executing individual test cases. It produces a Python script that returns a list of per-test commands from the test case list. The system samples and executes a subset of these commands, prompting the agent to verify and refine the script.

Dockerfile (Optional).
If required, a Dockerfile can be reconstructed from the committed image’s layers. This step is deterministic and implemented via hard-coded logic.

3.5
RepoLaunch-Automated SWE Dataset Creation

This subsection highlights RepoLaunch’s broader application beyond repository setup. As discussed earlier, coding LLMs require large-scale, diverse datasets of software engineering (SWE) tasks for benchmarking and training. Traditionally, creating such datasets—particularly those involving repository builds and test status extraction—has required extensive manual engineering effort. RepoLaunch automates this process end-to-end.

As illustrated in Figure
2
, for new SWE task creation, researchers only need to consider task design. Specifically, they must: (1) select repositories to clone, (2) identify relevant commits, (3) design new tasks by modifying the repository (e.g., introducing bugs or incomplete features), and (4) introduce new tests to validate whether a coding agent has successfully completed the task. RepoLaunch builds the repository, generates a Docker image, and extracts rebuild/test commands and a parser for structured test results.

To evaluate a task instance, RepoLaunch applies the test patch and the ground-truth solution patch separately. It executes the rebuild and test commands and parses the resulting logs to obtain the test statuses before and after the ground-truth solution patch. This yields the status of both existing regression tests and newly added task-specific tests. After a coding agent attempts the task, its predicted patch is applied and evaluated using the same process. RepoLaunch then compares the agent’s test outcomes with those of the ground-truth solution to determine whether the agent has successfully solved the task.

In addition to enabling automated benchmarking, the agent’s full execution trajectory can be saved for further analysis or agent training. This pipeline allows human effort to focus only on the creative task design, while the repetitive and time-consuming steps of repository setup, build, and test management are all automated by RepoLaunch.

Experiment

4.1
Evaluation of RepoLauch

The evaluation of RepoLaunch includes two experiments:

Exp 1. RepoLauch-automated SWE dataset creation.
To demonstrate the application of RepoLauch-automated SWE dataset creation, RepoLaunch is used to generate SWE task instances for SWE-bench-Live
(
19
)
from real GitHub issues and pull requests. We measure success rates in the Build and Release stages and analyze failure patterns from the real distribution of GitHub repositories and commits.

Exp 2. Comparison with related works.
RepoLaunch is applied to build sandbox images and extract test statuses for existing human-curated SWE benchmarks with ground-truth labels. We use task instances from SWE-bench-Verified
(
9
)
and SWE-bench-Multilingual
(
15
)
. For each repository, we select three task instances with commits farthest apart in time to evaluate reproducibility and robustness to dependency drift (see Appendix
B.1
for full task list).

We then compare Repolaunch against two baselines: SWE-agent
(
13
)
, a general-purpose SWE agent with only bash and file-editing tools, and repo2run
(
8
)
, the first repo-build agent prior to our work, limited to Python base images and hard-coded commands (e.g., pip install, pytest). Although rule-based build tools exist as described in
Related Works
, they are excluded due to their limited ability to handle only one specific language and previously benchmarked inferior performance compared to agentic methods
(
8
)
.

Hyper Parameters.
The Setup Agent is allowed up to 60 steps on Linux and 90 on Windows due to increased complexity. The Verify Agent is capped at 20 steps. Rebuild, test, and parser generation stages are each limited to 20 steps. Each bash command has a 30-minute timeout. For comparison, the maximum step of SWE-agent and repo2run is set to 120 due to context and rate limits.

4.2
SWE Task Creation from GitHub

SWE-bench-Live previously used RepoLaunch to generate Python tasks on Linux. In this work RepoLaunch is finally extended to support multiple programming languages and both Linux and Windows platforms. The pipeline is as follows:

1.

Crawl:
Collect GitHub issues with associated pull requests.

2.

Split:
Use an LLM to classify issues as general or Windows-specific.

3.

Launch:
Run RepoLaunch to build and test the repository at the commit preceding the pull request.

4.

Validation:
Retain instances with test cases that fail (or skip / do not run) before the PR and pass after.

5.

Verification:
Use an LLM to filter out unreliable task descriptions.

Refer to Appendix
D
for details of the pipeline.

SWE-bench-Live on Multiple Languages
. This subset is hereafter referred to as SWE-bench-Live/MultiLang. It includes tasks in C/C++, C#, Java, Golang, JavaScript/TypeScript (JS/TS) and Rust. Due to resource and time limitations, we focus on pull requests from July and August 2025, yielding 413 task instances from 234 repositories—surpassing the original SWE-bench-Multilingual benchmark (300 instances from 41 repos). Building multilingual tasks is significantly more challenging than single-language (e.g., Python) tasks, which RepoLaunch now automates at scale.

SWE-bench-Live for Windows-Specific Tasks.
This subset is hereafter referred to as SWE-bench-Live/Windows. It includestasks in Python, C/C++, C#, Java, Go, JS/TS, and Rust. Prior benchmarks focused only on Linux environments, limiting their ability to capture Windows-specific issues. We crawled issues from January to December 2025 and, after LLM filtering, retained 507 Windows-specific problems. We randomly sampled 400 for evaluation. This subset tests agents’ ability to operate in Windows environments and handle platform-specific code.

Evaluation of SWE agents on SWE-bench-Live / MultiLang & Windows
. To assess the utility our of RepoLaunch datasets, we also evaluate some popular SWE agents and latest LLMs on the tasks created, delivering new insights to the community on the latest progress of SWE agents and LLMs. For agent and LLM choices, refer to Appendix
C
. Since SWE-agent, OpenHands and ClaudeCode do not support Windows containers, we implemented a minimal Windows-compatible agent equipped with the same toolset as SWE-agent and OpenHands, named as Win-agent for Windows benchmarking. The max step of rollout for these agents is set at 100.

Failure pattern analysis of RepoLaunch.
To guide future improvement on SWE agents for automatic repo build&test, we conduct comprehensive failure pattern analysis of RepoLaunch on the Build and Release stages. We manually labeled the execution trajectories of RepoLaunch for 100 failed instances in the Build stage and 50 in the Release stage to get the failure categories. The failure categories for the Build and Release stages are described as follows.

The Build stage.

1.

Repository not at production
. The repository at the current commit is not ready for production. The source code has some problems so it is impossible to build the project if we don’t modify the source code.

2.

Incomplete test framework.
The repository does not contain regression tests, or does not have a complete test framework that can run regression tests, or cannot output the test status of each test case one by one, so the LLM agent cannot verify whether the build is successful or not.

3.

Require API key.
The repository requires an API key to run tests.

4.

Require database backend.
The repository requires a database installed in the system to run.

5.

Build / test timeout.
TThe build or test of the repository timed out, so we cannot verify whether the repository can be built and tested. This is probably due to the repository being too big.

6.

Wrong base image.
The LLM coding agent selected the wrong base image.

7.

Failed denpendency resolution.
The LLM coding agent does not know how to install some of the dependencies.

8.

Failed build / compilation.
The LLM coding agent does not know how to build / compile the repository.

9.

Failed regression test execution.
The repository has complete test framework that can print the status of each test case, but the LLM coding agent failed to figure out how to run regression tests in the repository.

The Release stage.

1.

Hallucination in Build stage.
Previously, the Setup agent exhibited a hallucination, falsely reporting that the build result is successful. In reality, the repository did not build successfully, or the agent failed to verify whether the repo has complete test framework, or the agent failed to verify whether the majority of test cases passed (including build/test timeouts), making it impossible to rebuild or execute tests.

2.

Failure to figure out rebuild cmd.
The agent fails to figure out how to re-build the repository in the limited 30 steps.

3.

Failure to print test status separately.
The repository has complete test framework that can print the status of each test case, but the agent fails to figure out how to run tests and print the status of EACH test case one by one in the limited 30 steps.

4.

Failure to parse test log.
The agent fails to write the correct test log parser to extract the status of each test case in the limited 30 steps.

Then we use a Reasoning LLM (GPT-5.2-Thinking-Medium) to label the left instances with the categories we got. Final proportions of each failure pattern on the 6 languages evaluated on Linux are shown in Figure

Comparison with repo2run & SWE-agent

The evaluation of repo2run only includes the build stage, as it does not have solution for rebuild and test status extraction. repo2run’s original criterion to judge the build as successful is that all the test functions can be
imported
, which is too lax. For fair comparison, here we consider the build of repo2run as successful when
more than half of the tests pass
.

For evaluation of SWE-agent, its initial prompt is set as "build a repo in a container, and write a bash script that rebuilds the repo and extracts test statuses". The evaluation of SWE-agent includes two criteria –
Build
and
Release&Validation
. Successful
Build
requires regression tests can run, while successful
Release&Validation
requires successful extraction of "FAIL_TO_PASS" test cases from a SWE-bench instance, which requires 1) the repo is fully not partially built; 2) successful rebuild and 3) accurate test status extraction.

6
Conclusion

This work introduces RepoLaunch, the first agent that automatically builds and tests code repositories generalized to any programming languages and any operating systems. We use RepoLaunch to create SWE-bench-Live / MultiLang and Windows datasets to demontrate its application in automating SWE dataset creation to benchmark and train coding LLMs and agents. RepoLaunch significantly surpasses baselines in build and test success rate. RepoLaunch has been made open-source as a SWE tool for the community. It is gratifying to note that, as of this writing, the GLM-5 base model
(
18
)
has already employed RepoLaunch for agentic training.

Limitations

RepoLaunch is a multi-turn free agent, which costs a lot of tokens. Future works might focus on reducing LLM calls such as using hard-coded test log parser to cover the common test frameworks first. Building these large repositories requires intensive CPU computing and disk I/O. Due to limited time and computing resources, only 431 + 50 instances have been created for SWE-bench-Live so far. But this is not the end. We will continue expanding the task set over time, incorporating the latest SWE problems to support and benefit the community in benchmarking and training.

Currently we select Linux images and Windows images as examples to demonstrate the cross-platform ability of RepoLaunch. We haven’t provided examples on macOS or other platforms because they are mostly Unix-based and similar to Linux. Future work will include examples of other systems.

Appendix C
Model and Agent Choices for SWE-bench-Live Benchmarking

We find that Deepseek-V3.2 and Kimi-K2-Thinking cannot use tool call correctly.
This may be because they have not been tuned for tool calling.
Deepseek-V3.1-Terminus is a tuned version of Deepseek-V3.1 specifically designed for tool calling.
It is the latest Deepseek model that supports tool calling, so we evaluated this model.
We find that OpenAI Codex does not support windows system and Gemini CLI does not support customized models (GPT, Claude, even our Gemini API from Openrouter source), that’s why we choose Claude Code as the close-source agent for evaluation.
As Claude Code does not support the thinking_signature block required by Gemini-3, we did not evaluate Gemini-3 with Claude Code.
Though Agentless
(
12
)
is also a popular method for SWE benchmarks, it hard-codes Python syntax tree so it cannot run on other programming languages.
While promising, observations suggest that the integration between LLMs and agentic frameworks is still ongoing and has not yet achieved full compatibility.

Appendix D
SWE-bench-Live / MultiLang & Windows Task Creation Pipeline

1.

Crawl.
Filter GitHub public repos with stars > 1k. Then, filter these repos with the proportion of any of the six languages > 60%. Crawl merged pull requests (PRs) that are related to some issues during a specific time period.

2.

Split.
Use a Reasoning LLM (GPT-5-Thinking-Medium here) to categorize issue descriptions as either general/Linux or Windows-specific. Windows-specific problems should be built sandbox images on Windows images instead of the Linux images adopted by previous SWE benchmarks.

3.

Launch.
Use RepoLaunch to build the sandbox images, extract the rebuild and test commands, and run the test log parser for each task instance before the PR was merged.

4.

Validation.
Apply the test patch of the PR and run rebuild commands, test commands and test log parser. Get the test status
before
the solution patch. Apply the test
and
solution patch of the PR and run again to get the test status
after
the solution patch. Compare the test status before and after the solution patch. Extract
PASS_TO_PASS
test cases that pass both before and after the solution patch. Extract
FAIL_TO_PASS
test cases that fail OR are missing before but pass after.
For languages that require compilation to execute, if code snippets are not implemented correctly or contain errors, related tests will fail to build, or the entire repository may become uncompilable due to failing static code checks.
Such test cases will only run and pass after the related code snippet is implemented correctly.
As such test cases can still test whether a code snippet is implemented correctly, we still take them as "FAIL_TO_PASS".
For evaluation of coding agents, their submitted prediction patch must pass both
PASS_TO_PASS
and
FAIL_TO_PASS
to be considered correct.

5.

Verification.
An additional step is to verify whether the test patch contains requirements that are not specified in the issue description, or the issue descritpion directly contains ground truths either in natural language or code. In our experiment we filter out these 2 cases out with a reasoning LLM (GPT-5-Thinking-Medium).

Appendix F
Failure Pattern Analysis of Coding Agents’ Trajectories on SWE-bench-Live/MultiLang & Windows

The SWE-agent paper
(
13
)
classify the failure pattern of SWE-agent on SWE-bench into (1) Incorrect Implementation (2) Overly Specific Implementation (3) Failed to Recover from Edit
(4) Failed to Find Edit Location (5) Failed to Find Relevant File (6) Gave Up Prematurely (7) Can’t Reproduce
(8) Ran Out of Time. Following their work and through further case study of 50 failed trajectories of the coding agents evaluated on SWE-bench-Live/MultiLang and Windows, we propose the following failure patterns when solving SWE-bench-Live:

1.

Reproduction Failure.
The reproduction test file written by agent runs successfully but cannot reproduce the issue.

2.

Execution Failure.
The agent even does not know how to run the code repository, so it fails to run the written reproduction test file.

3.

File Localization Failure.
The agent did not view all the files that need to be edited in ground truth patch.

4.

Line Localization Failure.
The agent failed to edit correct locations that the ground truth patch edits.

5.

Overly Specific Implementation
.

6.

Normal Functionality Corrupted.
The agent’s edits corrupted originally normal functionalities.

7.

Incorrect Solution
to the problem statement.

8.

Failed to Recover from Edit.
The agent fell into edit-error-edit-error loop.

9.

Submit Prematurely
.

10.

Key commands Timeout.
Running important shell commands like testing or modifying dependencies went timeout so verification of edits is not possible.

11.

Max Step Reached
, before completing the task.

We then use GPT-5.2-Thinking-Medium to classify all the failed trajectories on SWE-bench-Live/MultiLang and Windows. Result is shown in Figure
4
. Failure pattern on Linux illustrates that:

(1)

The reproduction of the problem and the validation of the fix mostly fails to work because the agents do not know how to run the code repo.

(2)

Failure of localization is a major failure reason.

(3)

Normal functionality corrupted by agents’ fix also accounts for 5.90%, showing it is also important to instruct agents to find the correct way to run regression tests in the repo.

(4)

Only 5.41% percent of the instances are tagged as max step reached, showing max step of 100 is mostly enough.

(5)

The known problem of LLM agents falling into edit-failure loop seems to be mitigated by latest stronger LLMs, with the proportion dropped from 23.4% in the original SWE-agent paper
(

Failure pattern on Windows illustrates that:

(1)

The pattern mostly aligns with that on Linux, with localization the major problem and very few instances of max step reached.

(2)

The proportion of failures to reproduce the issue and execute code both increased significantly, showing that Windows tasks are more difficult in terms of configuring the settings, managing the executable environment and running code successfully.

(3)

However, the proportion of implementation problems (such as being overly specific, corrupted, or incorrectly implemented) drops significantly.
From our initial observation, these Windows tasks are relatively easy in code implementation – mostly writing / fixing the corresponding Windows-specific code given the existing sound implementation in Linux, such as modifying file path from Unix format to Windows format and modifying commands from bash commands to powershell commands.
The trivial nature of this aspect makes the observed drop in success rate relatively modest
