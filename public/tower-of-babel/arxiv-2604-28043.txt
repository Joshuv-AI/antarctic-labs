Collaborative Agent Reasoning Engineering (CARE): A Three-Party Design Methodology for Systematically Engineering AI Agents with Subject Matter Experts, Developers, and Helper Agents
Rahul Ramachandran, Nidhi Jha, Muthukumaran Ramasubramanian

Abstract
Large Language Models (LLMs) are increasingly used in scientific and technical knowledge work, but their performance remains uneven across task regimes, and outcomes depend strongly on user expertise and verification discipline. This paper proposes CARE (Collaborative Agent Reasoning Engineering), a disciplined, stage-gated methodology for engineering LLM agents in which subject-matter experts (SMEs), developers, and required LLM-based helper agents collaboratively translate tacit domain intent into explicit, reviewable artifacts specifying interaction policy, grounding, tool orchestration, and verification. CARE frames helper agents as facilitation infrastructure (influenced by accelerated knowledge discovery) that increases specification throughput by asking phase-aligned questions, drafting and normalizing artifacts in concise Markdown, and proposing concrete revisions for human approval at stage gates. We evaluate CARE in a NASA Earth Science data discovery case study where a tool-using agent retrieves datasets via the NASA CMR API. Using a two-gate evaluation (synthetic benchmark for rapid iteration followed by an SME-created gold benchmark for higher-confidence validation) and Recall@K as the metric, the CARE-designed agent outperforms a baseline under identical model and tool access, achieving higher Recall@1 on the synthetic gate (n=621; 71.7% vs 69.1%) and higher Recall@5 on the gold gate (n=43; 27.2% vs 20.2%). Overall, CARE provides a practical, repeatable process for building maintainable LLM agents by making design intent explicit, reviewable, and verifiable over time.

Introduction

LLMs now produce high-quality text and code across many tasks, creating an opportunity to accelerate scientific and technical workflows where analysts interpret requirements, retrieve information, and synthesize evidence into decisions.
However, LLM performance remains uneven across tasks and contexts, often described as a “jagged technological frontier”, where outputs can be highly useful within certain regimes but unreliable outside them, and where user skill determines whether productivity increases or decreases

This unevenness creates a practical gap between novice and expert analysts: experts more consistently apply domain constraints, verify intermediate outputs, and structure multi-step workflows, while novices are more likely to accept fluent but incorrect results or to under-specify intent and constraints.

Custom LLM agents can reduce this gap by embedding expert analytic practices into reusable system behavior, including disciplined decomposition, verification habits, domain grounding, and (when relevant) tool-using workflows that make retrieval and computation authoritative rather than speculative.
Yet building reliable agents is non-trivial because behavior emerges from interactions among prompts, grounding content, tools, orchestration logic, and evaluation criteria; trial-and-error prompt iteration can yield systems that fail silently, regress after small changes, or overfit to narrow test cases.
Traditional software processes support iteration, but they do not directly solve agent-engineering problems such as specifying intended reasoning behavior, translating SME knowledge into stable grounding artifacts, and constructing verification benchmarks that detect regressions over time.

II
Design Targets for LLM Agents

An LLM “agent” is best understood as a system that repeatedly transforms an input goal into intermediate decisions and actions rather than a single prompt producing a single response.
In CARE, we treat agent quality as dependent on four interacting design targets:

Interaction policy and reasoning strategy
specifies how the agent interprets intent, decomposes tasks, manages uncertainty, decides when to ask clarifying questions, and performs critique/verification behaviors.

Domain grounding
specifies what domain knowledge and context the agent should treat as authoritative (terminology, assumptions, schemas, decision criteria) and how it constrains interpretation to reduce plausible-but-wrong outputs.

Tool orchestration
specifies what tools the agent may use, what each tool is for, how inputs/outputs are represented, how tool choice is made, and how errors, ambiguity, retries, and provenance are handled.

Evaluation and verification
specifies what success means, how performance is measured on realistic tasks (including complex or ambiguous queries), and how regressions are detected as prompts, tools, or models evolve.

Because failures often arise at the boundaries between these targets, ad hoc prompt tweaking rarely yields robust behavior.
CARE operationalizes these targets as explicit artifacts with review gates so intent is testable and maintainable. This decomposition is illustrated in Fig.

III
CARE Methodology

CARE is a collaborative methodology for engineering LLM agents in which SMEs, developers, and LLM-based helper agents jointly translate domain expertise and workflow requirements into explicit, reviewable artifacts rather than relying on iterative prompt tinkering that is difficult to reproduce and verify.
CARE is organized into phases with stage gates, where each phase produces artifacts specifying interaction policy, domain grounding, tool orchestration, and evaluation/verification so agent behavior can be tested and maintained as tools, prompts, and models evolve. The complete methodology and its artifact flow are outlined in Fig.

.

Figure 2:
CARE Methodology Overview.

Phase 1: Scope and decompose the agent.

The team defines the target workflow, intended users, and constraints, and uses the agent deconstruction to define what must be specified before implementation begins.
Helper agents draft an initial scoped artifact set (constraints, decomposition targets, intended users) to seed SME and developer review.

Phase 2: Key information elicitation (Tools, Context, Output format).

Helper agents run structured elicitation by generating targeted, phase-aligned questions and drafting the Tools/Context/Output artifacts in consistent Markdown for human validation.
This phase makes the operational environment and expected deliverables explicit before detailed behavior design.

Phase 3: Reasoning policy and guardrails.

Helper agents draft candidate reasoning policies and guardrail behaviors to address uncertainty, missing evidence, tool errors, and ambiguous queries, and iteratively revise them based on SME and developer feedback.
Phase 3 enforces that safety boundaries and the intended thinking logic determine what the prompt must implement.

Phase 4: Prompt architecture and tool-orchestration implementation.

This phase translates the approved artifacts into an implementable agent prompt designed using patterns from a prompt catalog
[
6
]
, including grounding injection strategy, tool schemas, routing logic, and retry policies.
A helper agent generates a prompt aligned with the input artifacts; implementation is treated as structured translation of artifacts into a working prompt rather than ad hoc iteration.

Phase 5: Benchmarking and verification.

This phase defines requirements for constructing a benchmark of realistic queries, defines scoring rubrics and pass/fail thresholds, and integrates evaluation into iteration.
Helper agents elicit responses from SMEs to identify sources, query types, and target answer formats that support automated or semi-automated benchmark construction; a separate auxiliary agent workflow can then generate candidate benchmark items grounded in those sources, followed by SME validation.

Stage gates.

CARE’s stage gates are defined by review and approval by both developers and SMEs of phase artifacts, ensuring intended behavior, constraints, and verification criteria remain aligned with domain requirements and implementation feasibility.

Helper agents are the mechanism that makes CARE repeatable at scale because they continuously convert informal intent into structured Markdown artifacts and propose candidate revisions, while SMEs and developers retain authority through stage-gate approval.

Minimum helper-agent capabilities.

At minimum, helper agents must (i) accurately summarize SME intent without introducing new requirements,
(ii) ask structured, phase-aligned clarification questions when information is missing or inconsistent,
(iii) draft and edit concise Markdown artifacts using consistent templates and terminology,
and (iv) propose concrete revision candidates that SMEs and developers can accept, modify, or reject at review gates.

IV

We evaluate CARE in a case study where we developed a data discovery agent for NASA Earth Science that retrieves datasets by invoking the NASA CMR API.
We compare a CARE-designed agent against a baseline under identical model and tool access to isolate the effect of CARE-driven design.

The evaluation uses a
two-gate benchmarking approach

Gate 1 (synthetic)
uses a large synthetic benchmark that can be produced quickly for rapid feedback and as a practical check that CARE does not underperform a minimal “LLM + tool” approach.

uses an SME-created gold benchmark as a smaller but higher-effort evaluation set for higher-confidence validation.

V
Discussion and Limitations

The case study suggests CARE is most valuable when workflows require nuanced domain interpretation and constrained retrieval, because CARE’s staged artifacts translate tacit SME practice into explicit reasoning policies, context/grounding requirements, tool-use constraints, and verification criteria that are otherwise difficult to keep consistent across iterations.

Threats to validity include benchmark sensitivity and benchmark leakage or overfitting that can occur through multiple pathways, including iterative refinement of artifacts and prompts to the benchmark distribution, helper-agent elicitation that implicitly “teaches to the test,” and auxiliary benchmark-generation workflows that may encode latent regularities not representative of real user queries.
This risk is compounded if helper-agent elicitation fails to cover important dimensions (e.g., edge-case query types, tool constraints) or if stage-gate reviews become superficial, because teams may optimize benchmark-visible behaviors while leaving real-world failure modes unspecified and therefore untested.

CARE also depends on the
quality of helper agents
(especially whether they ask the right questions across relevant dimensions and faithfully draft artifacts) and on the
expertise levels of SMEs and developers
(SMEs must surface nuanced constraints; developers must ensure tool realism and feasibility).
Finally, model/provider drift can affect both the deployed agent and the helper-agent facilitation layer, motivating periodic re-verification through CARE’s stage gates and controlled versioning of artifacts and helper-agent prompt modules.

VI
Conclusion

This paper introduced CARE (Collaborative Agent Reasoning Engineering), a disciplined, stage-gated methodology for engineering LLM agents that translates domain expertise and workflow requirements into reusable artifacts specifying interaction policy, grounding, tool orchestration, and verification rather than relying on trial-and-error prompt iteration.
CARE is explicitly defined as a three-party workflow among SMEs, developers, and required helper agents, with helper agents providing facilitation infrastructure that increases specification throughput while humans retain authority at review gates.
In a NASA Earth Science data discovery case study using the NASA CMR API, a CARE-designed agent outperformed a baseline under identical model and tool access in a two-gate evaluation, demonstrating consistent retrieval gains on both synthetic and SME-grounded benchmarks.
Future work should prioritize multi-domain replication and further detailed evaluation to test whether CARE’s gains persist across domains, query distributions, and tool ecosystems.
