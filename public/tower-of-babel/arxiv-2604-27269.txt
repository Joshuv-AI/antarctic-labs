Abstract
Abstract Biomedical knowledge graphs (KGs) are widely used in the life sciences, yet many are derived from unstructured documents and therefore lack schema-level constraints, whereas graphs assembled from structured resources are difficult to harmonize into a unified representation. We present OptimusKG , a multimodal biomedical labeled property graph (LPG) built from structured and semi-structured resources to preserve factual, type-specific metadata across molecular, anatomical, clinical, and environmental domains. OptimusKG contains 190,939 nodes across 10 entity types, 21,818,752 edges across 27 edge types, and 67,070,490 property instances encoding 109,665,797 values across 145 distinct property keys, derived from 18 ontologies and controlled vocabularies. The graph enforces a top-level schema for nodes and edges and retains granular, type-specific properties, cross-references, and provenance. We assessed the validity of OptimusKG by evaluating whether graph relationships are supported by evidence from the scientific literature using a multimodal agent, PaperQA3. PaperQA3 identified supporting evidence for 70.0% of sampled edges, whereas 83.4% of sampled false edges received no supporting evidence. Edges without literature support were concentrated in associations derived from experimental and functional genomics resources, suggesting that OptimusKG captures biomedical knowledge that may precede synthesis in the scientific literature. OptimusKG is distributed as Apache Parquet files, providing a standardized resource for graph-based machine learning, knowledge-grounded retrieval with large language models, and biomedical discovery use cases such as hypothesis generation.

Methods

Development of
OptimusKG

We constructed
OptimusKG
with a reproducible, ontology-grounded data pipeline designed to integrate heterogeneous biomedical resources spanning molecular, anatomical, and clinical scales into a unified labeled property graph.
The pipeline was fully version-controlled and designed to enable reproducible reconstruction of the knowledge graph from raw data sources.
Data sources were selected based on relevance, curation quality, update frequency, and compatibility with standardized ontologies. Table

OptimusKG

The pipeline followed a medallion data lake architecture
[
67
]
, comprising four layers (
Landing
,
Bronze
,
Silver
,
Gold

The pipeline was orchestrated using the Kedro workflow manager
[
68
]
(Figure
). All transformations were defined as modular, deterministic steps within the pipeline, ensuring consistent outputs across executions. At ingestion, the pipeline interfaced with heterogeneous data sources, including APIs (
e.g.
, NCBI), FTP servers (
e.g.
, Open Targets), external databases, static files, and ontology repositories such as BioPortal
[
69

). Raw data were replicated into the
Landing

e.g.
, ZIP, SQL, CSV, JSON, OWL). This design preserved full traceability to original data sources and enabled auditability of all downstream transformations.

The
Bronze

i.e.
, Apache Parquet) complemented by semi-structured formats (
i.e.
, JSON). In the
Silver

), schema alignment, entity harmonization, and cross-source integration to construct a consistent intermediate graph representation. Edges were first constructed from normalized datasets, after which nodes were materialized from edge endpoints to ensure that all nodes participated in at least one relationship.

The
Silver
layer constrained all nodes and edges to a shared top-level schema, augmented with type-specific properties. The node and edge schemas were defined in Tables
and
, respectively, and all labels were restricted to a predefined set of enumerated values (Table
). Schema constraints were enforced at this stage to ensure consistency across entity types and compatibility with the underlying ontology.

The
Gold
layer produced
OptimusKG
in Apache Parquet format. Nodes and edges were stored as separate Parquet files, with properties encoded using native columnar types, including nested structures that capture rich scientific metadata (Figure
). This representation enabled efficient storage, vectorized processing, and schema-level validation across entity types. The resulting files can be materialized into graph databases (
e.g.
, Neo4j), relational systems (
e.g.
, PostgreSQL), or vector indexes for embedding-based retrieval. These outputs constituted the released dataset and can be directly used or ingested into downstream systems. Apache Parquet was selected as the supported release format because it embeds a typed schema within each file, and supports the nested, strongly typed columns required by
OptimusKG
.

OptimusKG
follows semantic versioning, with new releases produced when significant changes in the upstream resources occur. Breaking changes to the released graph format or schema are released as major versions (
e.g.
, x.0.0). Non-breaking changes, such as pipeline features, are released as minor versions (
e.g.
, 0.x.0). Documentation changes or fixes that do not affect the data are released as patch versions (
e.g.
, 0.0.x).

Graph construction

OptimusKG was the result of a deterministic dataflow rather than a single script. The graph was constructed using a directed acyclic graph (DAG) of 63 deterministic processing nodes that produced 108 materialized, independently inspectable datasets across the
Landing
,
Bronze
,
Silver
, and
Gold
layers. Each processing node declared its input and output datasets in a central data catalog (Table
), could be executed independently, and wrote its output to disk. Retaining every intermediate dataset was a deliberate design choice to facilitate the diagnosis and audit of the final graph.

Therefore, instead of enumerating 108 different dataset schemas, which are auditable from the pipeline itself, we describe the construction process in terms of its invariants. Two invariants were enforced. First, at most one edge existed between any pair of entities, so that every pair carried a single canonical relationship. Second, every node identifier contained a CURIE whose prefix belonged to the set of namespaces enumerated by the Biolink Model. When a prefix was not available in the primary sources, the pipeline used cross-references as a backup. Entities that could not satisfy the second invariant were excluded from the graph.

Identifier prefixes (
e.g.
,
HP:
) were standardized during source-specific normalization, where entities were canonicalized to controlled vocabularies (
e.g.
, using the Human Phenotype Ontology). Records describing the same relation were de-duplicated and consolidated into a single edge with the union of their properties. For cases where the upstream sources disagreed on the relation type, we used a priority map to deterministically select the canonical edge relation (
i.e.
, the
RELATION_PRIORITY
defined in the
code
), while perserving all source-specific relation assertions in
properties.relation_assertions
as
{source, relation}
records. We additionally included a
properties.relation_conflict
boolean flag indicating whether the retained assertions contain relations belonging to curated sets of potentially conflicting relation types. Nodes were then constructed from the edge endpoints, so every node participated in at least one relationship. This harmonization process was performed in the
Silver
layer, with specific sub-packages for the materialization of nodes and edges. Finally, the
Gold
layer exported the final graph and checked for identifier uniqueness and integrity between edge endpoints.

Ontology harmonization

While some existing biomedical KGs emphasize scale or breadth,
OptimusKG
prioritizes ontology-based validation. To ensure consistency between biomedical data sources, the pipeline used the BioCypher framework
[
65
]
. We defined the Biolink Model (v3.2.1)
[
63
]
as the upper schema, which provides high-level semantic categories and standardized CURIE namespace conventions. Ontologies were incorporated through explicit mapping pairs of the form
(head node, tail node)
, allowing the attachment of additional ontology trees to the base structure and extending semantic granularity. We extended Biolink with the Gene Ontology (GO)
[
70
]
and Uber Anatomy Ontology (UBERON)
[
71
]
to increase vocabulary resolution across molecular functions (MFN), biological processes (BPO), cellular components (CCO), and anatomical entities (ANA).

Beyond these ontologies,
OptimusKG
includes entities derived from ontology trees referenced through CURIE namespaces encoded as prefixes of node identifiers. These prefixes correspond to established ontologies (
e.g.
, HPO, DOID, ChEMBL, Orphanet), and therefore the effective ontological coverage of
OptimusKG
reflects the union of all ontology trees present in the underlying primary data sources. Although entities may originate from external ontologies, BioCypher enforces that all identifiers map to the merged ontology tree. In particular, CURIE prefixes are validated against the set of allowed namespaces specified by Biolink, ensuring that only compliant prefixes are incorporated into the graph.

This constraint enabled dynamic expansion of ontology coverage in
OptimusKG
while preserving a consistent semantic representation. Table
summarizes the resulting ontological coverage of
OptimusKG
.
OptimusKG
focuses on human biomedical entities and associations. Although some ontologies used for harmonization, such as the Gene Ontology and Uberon, are cross-species resources,
OptimusKG
retains records derived in a human biomedical context.

Technical Validation

To assess the biological and clinical validity of edges in
OptimusKG
as a data resource, we evaluated whether graph relationships are supported by evidence from the scientific literature.
We used PaperQA3, a multimodal AI agent for deep research
[
93
,
66
]
that synthesizes evidence from scientific literature. PaperQA3 retrieves information from over 150 million research papers and patents and aggregates supporting evidence for scientific queries. It has been shown to match human expert performance on literature review and search
[
94
]
and we use it here to assess whether edges in
OptimusKG
are supported by evidence from the scientific literature
[
7
]
.

We first performed stratified sampling of seed nodes across all node types represented in
OptimusKG
. The top and bottom 10% of nodes by within-type undirected degree centrality were excluded from sampling to avoid concepts that are extremely generic hubs or peripheral nodes with insufficient connectivity for evaluation, respectively (Figure
). From the remaining pool, we uniformly sampled 100 seed nodes per type, for a total of 1,000 seed nodes. For each seed, we constructed a validation set of true edges by sampling up to 10 distinct neighbors in
OptimusKG
with non-empty descriptions. 743 seed nodes had degree
<10
; for these nodes, the full neighborhood was sampled for evaluation. As a negative control, we also sampled one false neighbor per seed not connected to the seed in
OptimusKG
. The final evaluation set consisted of 459 edges incident on exposure nodes (EXP,
\bar{d}=5.20
, where
\bar{d}
represents the mean degree across sampled seeds, Figure
a), 343 edges incident on cellular component nodes (CCO,
\bar{d}=3.85
, Figure
b), 164 edges incident on anatomy nodes (ANA,
\bar{d}=1.64
, Figure
c), 274 edges incident on molecular function nodes (MFN,
\bar{d}=2.74
, Figure
d), 690 edges incident on pathway nodes (PWY,
\bar{d}=12.37
, Figure
e), 367 edges incident on phenotype nodes (PHE,
\bar{d}=4.03
, Figure
f), 444 edges incident on biological process nodes (BPO,
\bar{d}=4.70
, Figure
g), 439 edges incident on drug nodes (DRG,
\bar{d}=58.68
, Figure
h), 528 edges incident on disease nodes (DIS,
\bar{d}=37.25
, Figure
i), and 1,000 edges incident on gene nodes (GEN,
\bar{d}=229.27
, Figure
j), for a total of 4,708 true edges, along with 1,000 false edges.

For each edge, PaperQA3 was prompted to retrieve relevant literature and assign an integer evidence score on a scale from
1
to
5
, where
1
indicates no supporting evidence found,
2
indicates weak evidence, with 1-2 papers in support;
3
indicates moderate evidence, with 3-4 papers in support;
4
indicates strong evidence, with 5-6 papers in support; and
5
indicates very strong evidence, with over 6 supporting papers or substantial experimental evidence. PaperQA3 also produced a rationale for each evaluation along with references to supporting peer-reviewed scientific or clinical evidence. The agent generated a successful response for 5,706 of the 5,708 queries. This procedure provides a quantitative measure of literature support for graph edges and enables assessment of
OptimusKG
dataset validity.

Literature evidence was identified for 70.0% of sampled edges in
OptimusKG
(
n=3,293
); of those, 12.2% were weakly supported (
i.e.
, 1-2 papers,
n=575
), 17.6% were moderately supported (
i.e.
, 3-4 papers,
n=826
), 10.9% were strongly supported (
i.e.
, 5-6 papers,
n=511
), and 29.3% were very strongly supported (
i.e.
, greater than 6 papers,
n=1,381
) (Figure
). PaperQA3 could not find evidence to support 30% of edges (
n=1,413
); of these, the most prevalent edge type was ANA-GEN (
n=661
, 46.8% of rating
=1
, Figure
j), followed by DIS-GEN (
n=204
, 14.4% of rating
=1
, Figure
j) and DRG-DRG (
n=118
, 8.4% of rating
=1
, Figure
h). This pattern likely reflects a lag between primary experimental data deposition and its synthesis in the scientific literature. Many gene expression, disease target, and drug-drug interaction edges in
OptimusKG
were derived from primary experimental data or functional genomics screens available via Open Targets
[
79
]
or similar platforms. Associations are often deposited in these platforms as raw data before they are synthesized into narrative text, and as such, would not be accessible to literature search agents like PaperQA3. By contrast, 83.4% (
n=834
) of false edges were not supported by any evidence, and only 1.4% (
n=14
) of false edges were very strongly supported, indicating that the graph has high specificity with respect to literature-supported relationships.
Together, these results indicate that
OptimusKG
is broadly consistent with the scientific literature and also includes experimental data that is not yet widely represented in published studies. These analyses demonstrate a scalable agentic approach for assessing the validity of large knowledge graphs using literature evidence.

Usage Notes

OptimusKG
is intended for biomedical research and scientific AI, providing a standardized resource for graph-based machine learning, knowledge-grounded retrieval with large language models, and biomedical discovery use cases such as hypothesis generation.

The supported release format is Apache Parquet, which can be loaded through the
optimuskg
Python client.
OptimusKG
can be used as a columnar DataFrame or NetworkX MultiDiGraph, with the option to point to specific node and edge types and the largest connected component of the graph. Additional community-developed integrations are listed in the project website.

For use with AI agents,
OptimusKG
provides an agent skill that describes how to load, query, filter, and analyze the graph.
OptimusKG
can also be used via the Model Context Protocol Bundle (MCPB) file, which provides natural-language access through graph-specific tools backed by a locally indexed database.

is versioned and available through Harvard Dataverse at

]

Table 7:

Overview of Kedro hooks and dataset-level validation mechanisms across pipeline layers in
OptimusKG
.
The table summarizes hooks that operate at different stages of the
OptimusKG
pipeline and their corresponding behaviors. Hooks are executed in a last-in, first-out order:
Origin
and
Checksum
are applied prior to pipeline execution during dataset loading, whereas
QualityChecks
are applied after node execution.
The
Origin
hook ensures that input data are available by validating the declared data provider and triggering downloads when needed, or by creating schema-compliant placeholder files for missing private or manually curated datasets. The
Checksum
hook verifies data integrity by comparing file checksums against expected values stored in metadata. The
QualityChecks
hook performs post-processing validation, enforcing naming conventions, checking identifier completeness, and validating relation types against controlled vocabularies.
Hard failures (for example, invalid relation values or missing required files) halt pipeline execution, whereas soft warnings (for example, checksum mismatches, naming violations, or null identifiers) are logged but do not interrupt execution. In addition, schema enforcement is applied at dataset load time within the dataset abstraction, ensuring type consistency at ingestion.
