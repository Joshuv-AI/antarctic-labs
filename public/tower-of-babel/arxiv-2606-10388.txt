SkillResolve-Bench: Measuring and Resolving Same-Capability Ambiguity in Agent Skill Retrieval
Jiandong Ding

Abstract
Agent skill libraries are becoming routable software assets: a retrieved skill can contribute instructions, scripts, resource bindings, and execution assumptions to an agent. This makes skill retrieval more than broad relevance matching. A retriever can find the right capability family yet expose the wrong same-capability representative. We study this failure as same-capability execution-risk retrieval. Each query pairs a helpful skill with a query-specific risky sibling that shares the capability family but can lead execution toward a stale resource, missing precondition, or wrong procedure. We introduce SkillResolve-Bench 1.0, an auditable benchmark for this setting with 661 helpful/risky pairs, source-role and admission evidence, cue/leakage checks, query-disjoint splits, and a 7,982-candidate pool that includes 6,660 public SkillRet candidates. The benchmark reports helpful ranking together with harmful sibling rate (HSR@K), the top-K exposure of the risky sibling. We also provide SkillResolve, a reference method that resolves active candidate families, scores query-conditioned utility from confusable library negatives and contract-profile cues, and selects one representative from each family before the final top-K list. Under the released family relation, SkillResolve reaches Recall@3 0.766 and NDCG@3 0.699 while keeping HSR@3=0. It improves over SkillRouter by 0.112 Recall@3 and 0.165 NDCG@3 while reducing HSR@3 from 0.693 to 0. Without representative selection, HSR@3 rises to 0.236 under the same scorer, identifying within-family representative choice as the mechanism that turns capability retrieval into safer procedural exposure.

The failure studied here appears when a library contains multiple skills from
the same capability family. One skill may contain the current resource,
precondition, or procedure needed by the task; a sibling may use the same
domain vocabulary and procedure shape but point to a stale resource, skip a
precondition, or apply the wrong check. A generic retriever can solve broad
capability matching and still surface the wrong representative. The risky skill
is not an irrelevant distractor; it is a close semantic neighbor with a

This representative ambiguity is visible in public skill libraries. In a
SkillRet audit using only public metadata, 4,716 of 4,997 queries have at least
one non-gold skill in the gold skill’s domain/action/object family; across
seven standard retrievers, a top-three list surfaces such a sibling for 47.3%
of queries, and 36.6% contain both a gold skill and a strict same-family
sibling. These siblings are not harmful labels. They show that, after a router
finds the right capability family, it may still need to form the right
representative competition. SkillResolve-Bench adds the execution-risk labels
needed to evaluate that choice.

We formalize this setting as same-capability execution-risk skill retrieval.
For each query, the benchmark identifies a helpful skill and a query-specific
execution-risk sibling, then evaluates retrieval under a larger public skill
pool. The central metric is harmful sibling rate (HSR@K): whether the risky
sibling appears in the final top-K. A good skill retriever should have high
Recall@K and NDCG@K for the helpful skill while keeping HSR@K low. This
evaluation differs from positive skill retrieval benchmarks such as SkillRet
and SRA-Bench, whose native labels identify useful or gold skills but do not
assign query-specific execution-risk siblings. It also differs from malicious
skill detection and permission enforcement: SkillResolve measures the upstream
retrieval-time decision of which same-capability representative is admitted to
the context.

We propose SkillResolve, a utility-aware retrieval method for this setting.
Figure
1
summarizes the core decision made before
execution.
SkillResolve first resolves which candidates should compete as alternative
representatives of an active capability, then scores each candidate with a
query-conditioned utility model trained from admitted helpful skills and
confusable library negatives. The utility model keeps ordinary retrieval
signals and contract-profile cues for resource bindings,
preconditions, API or temporal scope, output schema, and procedure indicators.
The final selector keeps the highest-utility representative from each resolved
family and ranks these representatives for the top-K list. The retrieval
objective becomes a family-resolved utility competition before global top-K
ranking.

SkillResolve-Bench 1.0 makes this failure measurable as a reusable fixed-library
retrieval task. It contains 661 helpful/risky sibling pairs, records source role
and admission evidence, separates harmful-sibling labels from SkillRet library
pressure, and releases hashes, query-disjoint splits, a fixed
7,982-candidate pool, and held-out outputs. Generic lexical, SkillRouter, and
BGE reranking baselines retrieve relevant skills but expose risky siblings;
Attribution-listwise suppresses them but loses helpful retrieval quality.
SkillResolve reaches Recall@3 0.766, HSR@3=0, and NDCG@3 0.699, improving
helpful retrieval over Attribution-listwise while both have HSR@3=0, and
improving both retrieval and HSR over SkillRouter and BGE reranking.

This paper makes three contributions:

•

We construct SkillResolve-Bench 1.0, an auditable benchmark for
same-capability execution-risk skill retrieval. It pairs helpful skills
with query-specific risky siblings, records source roles, admission
evidence, risk taxonomy, cue checks, hashes, splits, and release files, and
evaluates top-K exposure under public library pressure.

•

We introduce SkillResolve, a utility-aware retrieval method with a
Capability Resolver, a query-conditioned Utility Scorer over retrieval and
contract-profile cues, and a Representative Selector that exposes one
selected skill per active family.

•

We show that SkillResolve improves helpful retrieval while suppressing
risky siblings. Across 661 benchmark pairs and 7,982 candidate skills,
SkillResolve reaches Recall@3 0.766, NDCG@3 0.699, and HSR@3=0;
component and family-source analyses identify representative selection,
confusable-negative utility learning, and capability resolution as the main
sources of the recall–exposure tradeoff.

3
Problem and Method

3.1
Task Setup

The failure mode in this paper is not that a retriever misses the right broad
capability. It is that the retriever finds a relevant capability family and
then exposes the wrong member of that family. We model each query as a choice
among skills in a larger library, where two skills can share task vocabulary
and procedure shape but differ in their execution consequence.

Formally, a benchmark collection is

\mathcal{D}=\{(q_{i},\mathcal{C}(q_{i}),s^{+}_{i},s^{-}_{i},g^{\star})\}_{i=1}^{n}
, where

q_{i}
is a user query,
\mathcal{C}(q_{i})
is its candidate pool,
s^{+}_{i}
is
the admitted helpful skill,
s^{-}_{i}
is the query-specific execution-risk
sibling, and
g^{\star}:\mathcal{S}\rightarrow\mathcal{G}
is the released benchmark family
relation. The helpful skill guides execution toward a
verifier-consistent solution for the current query. The risk sibling belongs to
the same capability family but encodes a stale resource, missing precondition,
wrong check, or otherwise query-inappropriate procedure. The labels are
therefore query-specific: a skill can be useful in one context and a risky
sibling in another.

The benchmark construction keeps this distinction close to the decision a
retriever must make. Starting from a task-facing skill that is admitted for a
query, the paired sibling changes the condition that makes a procedure usable:
the referenced resource, temporal scope, input precondition, formula-preserving
operation, unit convention, or output schema. The sibling remains plausible
under ordinary semantic retrieval, but following it would move the agent away
from the query’s verifier-facing target. The risk label is therefore an
execution relation between a query and a skill, not an intrinsic safety label
attached to the skill text.

Candidate pools add library pressure around each pair. The helpful and risky
siblings are ranked together with unrelated and partially related public
skills, so the retrieval system must solve two coupled decisions: recover the
active capability families from a larger library and choose the right
representative within each active family.

3.2
Evaluation Objective

A retrieval system outputs a ranked list
R_{K}(q_{i})
of at most
K
skills.
Recall@K and NDCG@K measure whether the helpful skill is present and ranked
highly. Harmful sibling rate (HSR@K) measures whether the query-specific risky
sibling is exposed in the final top-
K
list:

\mathrm{HSR@K}=\frac{1}{n}\sum_{i=1}^{n}\mathbb{I}[s^{-}_{i}\in R_{K}(q_{i})]

A relevance-only scorer can improve Recall@K and still increase HSR@K if it
ranks both siblings highly. The target is therefore a utility-aware top-
K

ranking: keep
s^{+}_{i}
high while preventing
s^{-}_{i}
from being exposed to
the agent.

3.3
SkillResolve Overview

SkillResolve factors same-capability skill selection into three components. A

Capability Resolver
determines which candidates should compete as
alternative representatives. A
Utility Scorer
estimates how useful each
candidate is for the current query. A
Representative Selector
keeps one
highest-utility member from each resolved group before the final top-
K

ranking.

This factorization separates the benchmark relation from the deployable
method interface. The released benchmark relation
g^{\star}
gives a controlled
family source for measuring the within-family decision. Other family sources
can be derived from public metadata, titles, or skill text. SkillResolve uses
the same scoring and selection interface once a family source has produced
candidate groups.

3.4
Capability Resolution

Let
\rho
denote a capability resolver. Given a query and candidate pool, it
returns a set of active candidate groups

\Pi_{q}=\rho(q,\mathcal{C}(q))=\{G_{1}(q),\ldots,G_{m}(q)\}

where each
G_{j}(q)\subseteq\mathcal{C}(q)
contains candidates that should
be treated as alternative representatives for the same resolved capability.
The groups cover the candidate pool, with singleton groups allowed. A
singleton resolver recovers ordinary individual ranking; the released benchmark
family relation gives a controlled grouping; public metadata and text-derived
resolvers give public family sources.

Capability resolution does not decide which skill is helpful. It defines the
local competitions that the scorer must settle. If a helpful skill and a risky
sibling are placed in the same resolved group, the representative selector can
expose only the one assigned higher query-conditioned utility. If they are
split into different groups, both can survive into the final ranking. The
quality of
\rho
therefore affects the recall–exposure tradeoff, while the
utility scorer still decides which representative wins inside each group.

3.5
Utility Learning from Confusable Skills

SkillResolve learns a query-conditioned utility scorer

F_{\theta}(q,s)
. For each training query
q_{i}
, the positive
example is the admitted helpful skill
s^{+}_{i}
. The negative set
\mathcal{H}_{i}

contains confusable library alternatives mined under the same query and
candidate-pool protocol, with

\mathcal{H}_{i}\subset\mathcal{C}(q_{i})\setminus\{s^{+}_{i},s^{-}_{i}\}
. These negatives are
not random nonmatches and are not treated as universally unsafe skills. They are
query-conditioned competitors: skills that appear plausible in the library but
were not admitted as the helpful skill for
q_{i}
.

The mining rule is fold-local. For each training query, SkillResolve ranks the
fixed candidate pool with a base attribution-vote library signal, removes the
admitted helpful skill and its paired risky sibling from the top 50, and keeps
up to five highest-ranked remaining candidates as
\mathcal{H}_{i}
. Dev and test queries
never contribute training edges. The released benchmark relation is not used to
mine negatives; it only defines representative competitions for controlled
evaluation. Appendix
B.2
replaces this mining source with
lexical alternatives under the same folds, scorer, resolver, and selector.

The utility scorer is built from cached query–candidate signals, not from a
separately fine-tuned neural reranker. For each query–skill pair we form

\phi(q,s)=[\phi_{\mathrm{base}}(q,s),\,\phi_{\mathrm{contract}}(\kappa(q),\kappa(s))]

The learned utility is
h_{\theta}(q,s)=\theta^{\top}\phi(q,s)
.
The final score used at inference interpolates this learned utility with the
attribution-vote library score
a(q,s)
:

F_{\theta}(q,s)=\alpha\,a(q,s)+(1-\alpha)\,h_{\theta}(q,s)

where
\alpha
is selected on the dev fold. The base features in
\phi
are
normalized word TF-IDF, character TF-IDF, reciprocal-rank fusion, a
routing-view score, the attribution-vote score, and fold-local attr/risk
text-classifier scores fitted on cue-sanitized training text. Held-out labels
are never used to fit these coordinates.

The contract profile
\kappa(x)
is a deterministic text profile over six
execution-facing fields: resource binding, precondition, API or temporal scope,
output schema, procedure, and identifiers. Keyword and literal detectors extract
file-like resources, quoted identifiers, versions, schema terms, applicability
terms, and procedural verbs from query or skill text. For each field, the
contract block compares query and skill profiles with overlap, query-side
coverage, and contrast features, plus flags for missing resource or
precondition terms. This gives the linear scorer explicit dimensions for
execution-contract differences without adding a neural judge.

All score coordinates are min–max normalized within the evaluated candidate
pool. The pairwise learner is L2-regularized logistic regression with a fixed
seed, and
\alpha
is selected on the dev fold before held-out evaluation.

The scorer is trained by minimizing a pairwise logistic loss over training
queries:

\mathcal{L}(\theta)=\sum_{i}\sum_{s\in\mathcal{H}_{i}}\log\left(1+\exp(-\Delta_{i}(s))\right)+\lambda\|\theta\|_{2}^{2}

The margin inside the loss compares the admitted helpful skill against one
confusable candidate under the same query:

\Delta_{i}(s)=F_{\theta}(q_{i},s^{+}_{i})-F_{\theta}(q_{i},s)

Here
\lambda\geq 0
is the L2 regularization weight.
Larger positive margins reduce the loss, so the objective teaches the scorer to
prefer the admitted helpful skill over nearby library alternatives that compete
under the same retrieval setting. Appendix
B.2
tests this
mining design. The paired risky sibling is reserved for evaluation and
sibling-edge ablations, rather than used as a direct edge in the final
utility-learning loss; training-fold risk labels enter only through the cached
risk coordinate described above.

3.6
Representative Selection

Utility scoring alone still ranks individual skills. A top-
K
list may contain
both a helpful skill and its risky same-family sibling if both receive high
semantic scores. SkillResolve changes the candidate set before the global top-
K

ranking. It first resolves candidate groups with
\rho
, then runs a
within-group utility competition.

For each active group
G\in\Pi_{q}
, SkillResolve computes

u_{s}=F_{\theta}(q,s)
for every candidate in the group. The
selected representative is

\mathrm{rep}(G,q)=\argmax_{s\in G}u_{s}

The final list ranks only these representatives by their stored utility scores:

R_{K}(q)=\TopK_{s\in\{\mathrm{rep}(G,q):\,G\in\Pi_{q}\}}u_{s}

Here
\TopK
returns the
K
highest-scoring representatives in descending
order. The global top-
K
decision is therefore made after the
capability-resolved utility competition. If the helpful and risky skills share
a resolved group and the scorer assigns higher utility to the helpful skill,
representative selection keeps
s^{+}_{i}
and removes
s^{-}_{i}
from the final
candidate set.

The resolver defines the candidate groups, the utility scorer profiles query

4
Experiments

4.1
Benchmark and Protocol

SkillResolve-Bench 1.0 turns the task in Section 3 into a fixed-library
retrieval problem. Each labeled instance provides a public query, a helpful
skill, and a same-capability risky sibling whose resource binding,
precondition, procedure, API scope, or example would steer execution away from
the query’s verifier-facing target. The 661 labeled pairs contain 630
answer-backed SRA-Bench pairs and 31 SkillsBench pairs with executable-test or
oracle/verifier evidence. SkillRet plays a different role: its 6,660 public
skills enlarge the fixed candidate pool, but its positive-retrieval qrels are
not converted into harmful-sibling labels. The final evaluation pool has 7,982
candidates.

The benchmark records source identifiers, admission class, risk type, split,
and text hashes. It fixes a query-disjoint 446/68/147 release split with no
cross-split query leakage, no helpful/risky split mismatch, and no detected
label cues after cue-cleaning and manual inspection. Main results use grouped
five-fold held-out aggregation over all 661 pairs: each fold holds out one
query-group partition for testing, uses the next for model selection, and
trains learned scorers on the remaining partitions.
Appendix
A
documents the construction pipeline,
release schema, hash/split checks, candidate-pool manifests, rank outputs, and
reproduction script.

SkillResolve-Bench 1.0 also releases a benchmark family relation over the
final candidate pool. This relation contains 7,321 groups: 661 helpful/risk
sibling groups of size two and 6,660 singleton SkillRet groups. It identifies
which candidates are alternative representatives of a family; it does not
identify which sibling is helpful. The main table uses this benchmark relation
as a controlled source for the within-family representative decision.
The public capability-resolution analysis below replaces it with public
metadata/title and text-derived family sources under the same held-out protocol.

We report Recall, harmful sibling rate (HSR), and NDCG at final context
cutoffs. Recall and NDCG measure helpful retrieval; HSR measures whether the
query-specific risky sibling appears after any representative-selection step.
Because the held-out pipeline is deterministic after dev selection, uncertainty
is reported with 5,000-replicate paired bootstrap intervals over the 661
held-out predictions.

4.2
Baselines

We compare against baselines that target different parts of the retrieval
problem. Attribution-listwise is the closest same-protocol comparison: it uses
the same fixed candidate pool and label space, and applies a listwise
attribution selector inspired by SkillsVote’s evidence-governed skill
selection
(
16
)
. SkillRouter and BGE reranking provide
zero-shot relevance references without SkillResolve utility training

(
35
;
3
)
. SkillRouter uses the official 0.6B
embedding and reranker checkpoints in a zero-shot fixed-pool adaptation. BGE
reranking applies a strong general reranker to the same retrieved pool. Hybrid
lexical RRF uses reciprocal-rank fusion
(
5

. The component

Together, the baselines and ablations test three parts of the retrieval

SkillResolve changes the recall–exposure tradeoff, and which components
produce the final behavior.

5
Analysis and Execution Scope

Behavior across risk types.

The main-table HSR@3 result is not concentrated in a single risk category.
SkillRouter exposes risky siblings across wrong-resource, wrong-precondition,
and procedure/API/example strata, while removing representative selection from
the same SkillResolve scorer exposes risk in each stratum as well. In this
fixed-pool evaluation, SkillResolve keeps HSR@3 at zero across the measured
strata while preserving helpful recall, consistent with the mechanism in
Table
3
: relevance scoring can place both siblings near
the top, but representative selection decides which member of the active family
reaches the final context. Appendix
B.3
gives the
stratified values, and Appendix
A.1
illustrates resource,
precondition, and procedure cases.

Label and construction validity.

The benchmark labels are tied to task consequences rather than topical
difference alone. In a 14-task verifier-consequence slice, every
helpful/repaired condition passes the public verifier twice, while every
matched risky/corrupted condition is rejected; a broader SkillsBench sweep adds
31 risk-side verifier-failure logs. Construction checks also reduce the chance
that HSR@3=0 is driven by a visible template: on a 50-pair rewrite stress test,
detected template phrases fall from 0.47 to 0.03, SkillResolve remains at
HSR@3=0, and removing representative selection raises HSR@3 to 0.860. A
120-row external preference check further aligns with the annotation direction,
preferring the helpful skill in 101 cases and marking the annotated risky
sibling as riskier in 104. These checks support label semantics and construction
robustness, not additional main retrieval metrics; the rewrite slice uses a
cached top-300 competition scope, so its high recall is not a full-pool recall
estimate.

Scope.

HSR measures pre-execution exposure: whether a query-inappropriate sibling is
placed into the context before the agent acts. Executor-specific outcomes
depend on downstream policies and runtime checks, and open capability
ontologies require a separate construction protocol. Public metadata/title and
text-derived resolvers keep HSR@3 at zero in the fixed-pool analysis with
Recall@3 about 0.755, but they also introduce broader active groups than the
released benchmark relation. The metadata row is therefore a coarse
public-resolver check rather than a precise ontology claim. The method lowers
exposure to incorrect procedural context; executor robustness, skill-library
maintenance, and fully open ontology construction remain separate problems.

6
Conclusion

This paper studies same-capability execution-risk skill retrieval, where a
retriever reaches the right capability family yet exposes a query-inappropriate
representative. We introduce SkillResolve-Bench 1.0, a benchmark with
query-conditioned pairs of helpful skills and risky siblings, source-role and
admission evidence, cue and split audits, and public-library pressure.
SkillResolve is a reference method for this benchmark: it combines capability
resolution, confusable-library utility scoring, and representative selection.
On 661 pairs and 7,982 candidates, SkillResolve
improves helpful ranking while keeping HSR@3=0, including against an official
SkillRouter embedding-reranker baseline that retrieves helpful skills but
exposes risky siblings frequently.

Scalable skill libraries need evaluation protocols and retrieval objectives
that choose a query-appropriate representative within each capability family.
SkillResolve-Bench 1.0 makes this requirement measurable and auditable, while
SkillResolve shows one effective way to act on it through a resolver interface
followed by utility-conditioned representative selection. The no-selection
ablation shows what positive retrieval metrics can hide: high helpful recall
can still leave a risky sibling in the top-K context.

A.1
Label Examples

The following examples illustrate the label distinction used in
SkillResolve-Bench 1.0. In each case, the helpful and risky siblings belong to
the same capability family and are therefore plausible retrieval targets under
topical relevance. The difference is the execution-controlling clause: which
resource to bind, which precondition to preserve, or which procedural contract
to follow. These cases are documentation examples, not additional evaluation
rows beyond the fixed 661-pair benchmark.

Radar vital-sign analysis.

One task asks an agent to estimate heart rate and breathing rate from 24 GHz
continuous-wave radar recordings. Both siblings are radar-signal-processing
skills: they describe I/Q parsing, clutter removal, range-bin or phase-signal
extraction, and downstream vital-sign analysis. The helpful sibling ties these
steps to the task-specific recording metadata and sidecar format. The risky
sibling keeps the same radar pipeline but allows default artifact selection when
several files or references are visible. The resulting failure is not an
off-topic method; it is a plausible radar analysis run on the wrong capture or
under the wrong I/Q convention, producing rates that can look numeric while no
longer answer the requested instance.

Offer-letter template filling.

Another task asks the agent to fill a Word offer-letter template from employee
data. Both siblings are document-generation skills for Word documents: they
cover split template fields, headers and footers, nested tables, and
template-preserving edits. The helpful sibling binds those operations to the
requested template and the intended employee record. The risky sibling remains
a relevant document skill, but weakens the binding to the task-specific file
and data source. The execution consequence is a valid-looking document that may
be generated from the wrong template, row, or field convention. A
relevance ranker can see the right document-manipulation vocabulary in both
siblings, while the executor would experience different document semantics.

Geodesic map construction.

A code-generation task asks for a self-contained function that builds a
folium map, computes pairwise geodesic distances, and raises ValueError when the
input dictionary is empty. Both siblings are geopy skills and describe the same
core operation: extract latitude and longitude fields, pass coordinate tuples to
geodesic, and return a map with distance results. The helpful sibling treats
the input contract as part of
the procedure. The risky sibling keeps the same library guidance but relaxes the
applicability condition when it conflicts with the query. The generated code can
therefore import the right packages and follow the right distance formula while
failing the oracle by skipping the required empty-input exception or by handling
the dictionary schema incorrectly.
