 1. INTRODUCTION
The HFIR Activity WorkbooK generator (HAWK) is a Python code that automates and streamlines the ac-
tivity calculation of samples after irradiation in the High Flux Isotope Reactor (HFIR). HAWK’s results
provide estimates of the activity and nuclide inventory of irradiated specimens before they are moved to
hot cell facilities, where they undergo post-irradiation examination. The samples’ activity results guide the
packing of shipping containers and inform the accountable inventories for the hot cell facilities. The toolkit
was originally developed by Charles Daily, a former R&D staff member at Oak Ridge National Labora-
tory (ORNL). As of May 2025, HAWK is developed by the Radiation Transport & HPC Methods Group
(Nuclear Energy and Fuel Cycle Division) at ORNL.
Figure 1 presents HAWK’s workflow. To use HAWK, users need to:
 1. Develop an Excel input workbook (i.e., XLSX extension) containing data from the experiment’s
 materials, irradiation history (cycles), and irradiation positions.
 2. Make minor edits to an existing template JSON file (i.e., auxiliary_data.JSON) and to the Python
 driver. The driver sets the necessary environment variables, defines the material compositions, and
 ultimately calls HAWK.
Once configured, HAWK runs the Oak Ridge Isotope Generation code (ORIGEN) to calculate the masses,
activities, and heat load at the end of irradiation for each isotope in the specimen. ORIGEN is part of SCALE,
ORNL’s in-house computational tool for performing nuclear safety and design calculations [1]. Following
this step, HAWK postprocesses the results and generates three output workbooks summarizing the activity
calculations.

 2. INPUTS
This section discusses HAWK’s three input files: input workbook, auxiliary_data.JSON, and the Python
driver.
2.1 WORKBOOK
HAWK’s input workbook has two worksheets. The first one is named Detail and the second Cycles. These
worksheets are constructed with the fabrication sheets, which are provided by the requester. In general, a
requester is an ORNL staff who oversees the experiment or is directly involved in its design and fabrica-
tion. Fabrication sheets have multiple worksheets but, to build their input workbook, users should look for
the worksheets that are named after the experiments that they are analyzing. Table 1 shows an example of
an experiment’s worksheet inside the fabrication sheet. In this case, the experiment is named MUN310.
The Detail and Cycles worksheets in the HAWK input workbook are discussed in the following subsec-
tions.
2.1.1 Detail Sheet
In the Detail worksheet, users define six columns: (1) Rabbit ID, (2) Part Name, (3) Specimen, (4) Speci-
men Name, (5) Material Name, and (6) Mass (g).
Table 2 shows which corresponding columns from the experiments’ worksheet (inside the fabrication
sheets) should be used to populate the columns in the Detail worksheet. There are only two exceptions.
The first one is the Rabbit ID column, which is usually the experiment’s name but users have the flexibil-
ity to pick any name they desire. The second exception is the Specimen column. This column designates
the experiment parts that are of main interest for the activity calculation with “Yes” entries. The remaining
ones will be classified with a “No.”
Table 3 shows an example of the Detail sheet for two rabbits (experiments): MUN310 and MUN204. Note
that since a single input workbook can represent the data of multiple rabbits, each unique Rabbit ID is sim-
ply repeated for as many entries as necessary.
2.1.2 Cycles Sheet
Table 4 shows an example of the Cycles worksheet. This sheet only has three columns: (A) Rabbit ID, (B)
Cycle, and (C) Position. These columns are populated with the experiment’s cycle information, which can
be extracted from HFIR’s EXSITE database [2]. The Cycle and Position information need to be entered for
every Rabbit ID entry that was defined in the Detail worksheet.
It is important to note that, although it is possible for a target to be irradiated at different locations dur-
ing different irradiation cycles, Charles Daily recommended that only one of the positions be used. More
specifically, HAWK uses the position in the last cycle because it is assumed that the experiment was moved
around from positions with similar flux profiles. This is also a valid simplification because the resulting
discrepancies are minor.
The irradiation position string in column C has the following format: radial_position-axial_position.
Specifying both the radial and axial positions of each irradiation location (or zone) allows HAWK to adjust
the flux level accordingly for said location. This is achieved by multiplying the zone-dependent flux at core
mid-plane with the axial factors; these factors range from 0.25 to 1.00 and are defined in the
auxiliary_data.JSON file. Currently, the axial factor for any experiment that is irradiated in either the
vertical experiment facilities (VXFs) or the removable beryllium (RB) is 1.0 because the mid-
plane flux is the highest and this is used for all axial locations in these locations for a conservative esti-
mate.

2.1.3 Python Executable/Driver
Users need a Python driver to run HAWK. An example of a working template is provided in Listing 1.

Special attention should be given to the following variables: (1) curie_cutoff, (2) spread_sheet, and (3)
assay_date (see Section 4 for a definition of each one). The following are set variables relevant to SCALE
modules: (1) scale, (2) decay_lib, (3) reaction_lib, and (4) yield_lib. Additionally, the user should
ensure that the composition of each material in the specimen has the weight composition (in percentage)
that was specified in the fabrication sheets’ Materials worksheet. The weight composition is also found
in the Inspection Request (IR) files. Each of these files has a unique ID, which is located under the FAB
IR and MAT IR columns in the experiment’s worksheet (inside the fabrication sheets). Users can ask the
requester to provide the IR files.
It is important to note that, under sufficient irradiation, the cobalt content (in the form of 59 Co) in stain-
less steel (SS) materials can lead to nonnegligible amounts of 60 Co, which is considered a nuclear hazard.
Therefore, the 59 Co content should be properly accounted for in the activity calculation.
The housing parts of the MiniFuel experiments as well as the end caps are sometimes fabricated with SS.
In rabbits, SS is occasionally used to fabricate the spring pins and wave springs. As mentioned previ-
ously, the chemical composition of each material/specimen in the experiment can be found in the Mate-
rials worksheet inside the fabrication sheets or in the IR files. If the cobalt content for a given SS material
is not specified, users should rebalance the material composition slightly to add a conservative 0.21 wt %

2.1.4 File auxiliary_data.JSON
The auxiliary_data.JSON file contains important definitions, such as the beginning-of-cycle (BOC) and
end-of-cycle (EOC) fluxes, the spectra, the zones, the radial and axial positions, and the axial peaking fac-
tors, as well as other information.
However, users should only be concerned with the following Python dictionaries: (1) synonyms and (2)
cycle_dates. An example of these dictionaries inside the auxiliary_data.JSON is shown in Listing 2.

The first is a dictionary with all the potential synonyms that are used to identify a given material. For ex-
ample, stainless steel 316 has a Python dictionary key of SS316 and a corresponding synonym value list of
["SS-316", "316SS", "316 SS", "SS 316", "SS316"]. Users should verify that the Part Name string is
in the list; otherwise, HAWK execution will exit abnormally (crash). The value list can also be expanded,
if desired, by manually editing the JSON file.

 6

As for cycle_dates, all the irradiation cycles listed in the Cycles sheet need to have a key–value pair in
this dictionary. For example, for cycle 511, the key is simply a string of the cycle number (e.g., "511") and
the corresponding value will look like ["02/18/25 12:00", "03/14/25 18:00"]. Again, this information
is readily available in EXSITE.

 3. HOW TO RUN HAWK
This section discusses how to execute HAWK on either ORNL’s Helios [3] cluster or on any local ma-
chine. Helios is a three-file system with nodes for storage, compute processing, and login. ORNL employ-
ees can request access to Helios after completing the Export Controlled Training in SuccessFactors. This
is done through the Universal Computer Access Management System (or UCAMS) by the user.
3.1 RUNNING HAWK ON HELIOS
To run HAWK on Helios, users first need to request access to the HAWK source code directory

 /projects/helios/hawk/src

through UCAMS (HAWK falls under HPC-Projects). This path also contains templates for auxiliary_data.JSON
and the Python driver files. The HAWK environment should be sourced with the following command:

 source /projects/helios/hawk/env.sh

Users should then create a directory (commonly referred to as working directory) in which they will place
all the inputs to run HAWK.

 mkdir working_dir
 cd working_dir

Once in the working directory, the following command ln -s should be used to soft-link the read_f71.JSON
and make_origen_input.py

 ln -s make_origen_input.py
 ln -s read_f71.JSON

Both files are part of the inputs that HAWK needs to run SCALE. Alternatively, the users can copy the
files from /projects/helios/hawk/src to their working directory. However, if they decide to copy, they
have to routinely ensure that their copies are up to date. Soft-linking the files will always guarantee that the
latest HAWK version is being used.
Along with both read_f71.JSON and make_origen_input.py (either soft-linked or copied), users should
also add all the aforementioned inputs (i.e., input workbook, Python driver, auxiliary_data.JSON) to their
working directory.
Whether running an interactive session or a job, users should ensure that scale, decay_lib, reaction_lib,
and yield_lib are set to the following paths (note: paths are valid as of April 2025) in the driver file:

scale="/projects/helios/SCALE/SCALE_6.3.1/bin/scale-6.3.1.sif"

decay_lib="/projects/helios/SCALE/SCALE_6.3.1/data/origen_data/origen.rev03.decay.data"

reaction_lib="/projects/helios/SCALE/SCALE_6.3.1/data/origen.rev01.jeff56g"

yield_lib="/projects/helios/SCALE/SCALE_6.3.1/data/origen_data/origen.rev05.yields.data"

At this point, HAWK can be run either through an interactive session or through a Slurm job submission.
Each approach is briefly discussed in the following subsections.

 8

3.1.1 Interactive Session
HAWK runs usually do not take long, so there are instances where an interactive session is reasonable. For
example, users might want to test their inputs. There are also instances where the computing nodes on the
cluster are down for maintenance. Running HAWK with an interactive session can be achieved with the
following steps:
First, request an interactive session with the following command:

 srun -time=TIME --pty /bin/bash

where TIME is whatever time the user desires to allocate for said session. In this example, the default num-
ber of compute nodes and processors are 1.
Important to note that HAWK only runs in serial, so it is not necessary to run with parallel compute nodes
or processors.
Next, source the HAWK environment (unless this is already being done from the .bash_profile or .bashrc
files):

 source /projects/helios/hawk/env.sh

Third, execute the Python driver:

 python ./gen_RABBIT.py

The last step is to finalize the interactive session by typing exit.
3.1.2 Slurm Job Submission
Listing 3 shows an example of a generic Slurm batch submission script to run a HAWK job on Helios.
Users should update the required cards (e.g., --job-name, --output, --mail-user) along with the Python
driver’s filename. As mentioned previously, HAWK runs do not usually take long, so --time can be set to
less than 4 hours.

To submit the script, use the sbatch command:

 sbatch RABBIT_job.sh

3.3 EXPECTED RESULTS
Upon successful completion, HAWK postprocesses the ORIGEN outputs and writes two output work-
books for each unique Rabbit ID in the main input workbook along with a third workbook that summarizes
the entire activity calculation. The main output workbook is titled after Rabbit ID. Here, users can expect a
complete history and summary of all the specimens that were analyzed in each rabbit. Recall that relevant
parts in the experiments were labeled with a “Yes” under the Specimen column. Each of these specimens
has a detailed results worksheet. To name the worksheet, HAWK combines the Part Name of the said spec-
imen along with the Specimen Name (i.e., the ID) to create a unique string.
For example, specimen in entry number 5 in Table 3, has a Part Name of D6T12 AG Specimen and a Spec-
imen Name of 3B45. Therefore, the specimen’s worksheet in the output workbook will be titled D6T12 AG

 4. MISCELLANEOUS
4.1 KEY DEFINITIONS
This section defines key concepts related to shipping calculations. Most of these are variables in the
auxiliary_data.JSON data file.

 1. zones: rings in the flux trap.
 2. fluxes: BOC and EOC fluxes for each zone.
 3. spectra: 56-group flux spectra for each zone.
 4. axial_factors: fractional factor used to correct for the axial profile of the BOC/EOC fluxes. Value
      ranges from 0.25 to 1.00
 5. synonyms: Python dictionary of potential synonyms for each material.
 6. cycle_date: Python dictionary of irradiation cycles and their start/end dates.
 7. curie_cutoff: threshold for the lowest activity value that will be tabulated in the results workbook
      (e.g., 5e−011 ).
 8. spread_sheet: string for the name of the input workbook (e.g., ‘‘MUN.xlsx’’).
 9. assay_date: string for the date the experiment is expected to be assayed (e.g., ‘‘04/04/25 08:00’’).
