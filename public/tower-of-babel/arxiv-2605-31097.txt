SpecDB : LLM-Generated Customized Databases via Feature-Oriented Decomposition
Yunkai Lou, Longbin Lai, Shunyang Li, Zhengping Qian, Ying Zhang

Abstract
Mainstream relational databases ship a uniform feature set across deployments, although individual workloads exercise only a fraction of the available subsystems. We investigate whether a database can instead be generated on demand with a feature set matched to the target workload. We present SpecDB , a system that uses large language models (LLMs) to synthesize customized relational databases. We survey 9 production systems and decompose them into 10 functional modules, each further divided into implementation variants. To capture dependencies among variants, including cases where implementations in disjoint subtrees must be co-designed, we adopt the FODA feature model and extend it with a cooperate edge, yielding a dependency graph DBModuleGraph . SpecDB operationalizes DBModuleGraph through a layered module-construction pipeline in which each module is generated, validated, and integrated by a dedicated subagent (driven internally by three inner agents: Main, Tester, Architect), and a specdb-refining that iteratively repairs and tunes the assembled database against a user-supplied refining harness with read-only access to existing database source code. A companion selection component translates a natural-language workload description into a set of implementation variants, providing an end-to-end pipeline from workload description to deployable database. We evaluate SpecDB on TPC-C with BenchmarkSQL. The generated database (23,779 lines of Rust) completes 60-minute TPC-C at 1 and 10 warehouses with zero errors. At 10 warehouses it reaches tpmC = 130, compared to 128 for PostgreSQL 14.23 and 127 for MySQL 8.0.45, with per-transaction latency comparable to PostgreSQL and at ∼ \sim 2.9% of PostgreSQL’s and ∼ \sim 2.8% of MySQL’s server-side code size. Because the agent operates at the level of module specifications rather than product source, the pipeline has no product-specific scaffolding to defend and can in principle combine techniques across system boundaries; the TPC-C instance here exercises a PG-dominated subset of that capacity, and a workload-mix demonstration is left to future work. Paired with falling LLM costs, we see this capacity as a step toward a future in which generating a purpose-built database for a target workload becomes straightforward.

Feature-Oriented Domain Analysis

Introduction

Relational database management systems (RDBMSs) are deployed across
workloads with widely varying feature requirements. Representative
examples fall into roughly four categories.

Embedded and small-scale
applications—a bibliography
manager, a mobile app’s local store, a one-off CSV cleanup
script—need simple CRUD over a small table; MVCC, crash
recovery, and a network server are all unnecessary.

Transactional OLTP
applications—e-commerce checkout, a
banking ledger, multi-player game state—require MVCC,
multi-version isolation, crash recovery, and high-throughput
indexing under many concurrent connections, with tail latency as
the dominant cost.

Analytical OLAP
applications—BI dashboards, ad-hoc data
exploration, nightly ETL—scan gigabytes-to-terabytes and
aggregate them; columnar storage, vectorized execution, and bulk
ingest matter, whereas concurrent fine-grained updates and full
ACID over single rows do not.

Latency-bound or specialized
applications—real-time
trading engines, online feature stores—demand aggressive space-for-time optimizations (in-memory
indexes, no-disk-on-read paths, no eviction) that would be
prohibitive for a multi-terabyte dataset.
For any one workload, the required feature set is a strict subset
of the full RDBMS design space.

Mainstream systems such as PostgreSQL
[
13
]
and
MySQL
[
11
]
instead adopt a monolithic architecture in which a
single product covers the entire design space. Every installation
ships the same full stack of subsystems (e.g., query optimizer,
storage engine) regardless of which of these the workload
actually exercises. Workload-specific tuning may then be
applied on top of such monolithic systems to improve performance
on the given tasks
[
3
,
20
,
12
]
. This produces three
costs: unused subsystems consume code and runtime resources,
system complexity raises the barrier to use, extension, and
correct configuration, and the system’s functional boundary is
fixed at release time—new scenarios that require a different
feature subset cannot be accommodated without forking the
codebase or accepting the overhead of features the scenario
never exercises.

These costs share a common cause: the system is designed once and then
adapted to each workload through configuration. An alternative is to
fix the feature set at generation time, designing the system per
workload rather than at run time
[
18
]
. Recent advances in code-generation
LLMs make this approach feasible: SpecFS
[
10
]
demonstrated
that a complete file system can be synthesized on demand from modular
specifications. The analogous move for databases is to generate, from
a workload description, a database whose feature set matches the
workload, exposing only the configuration surface that the chosen
feature set requires.

Realizing this in practice, however, is harder than it appears.
Asking an LLM to implement each database subsystem purely from a
workload description and the model’s own priors faces two
compounding problems. The first is algorithmic: left to its
priors, an LLM tends to select algorithms with worse time complexity when
more efficient alternatives
exist
[
1
,
15
]
; in the
database context it is particularly costly because hot paths
execute millions of times per second. A heap allocator that scans
pages linearly for free space instead of maintaining a free-space
map, an MVCC layer that omits a vacuum horizon and leaks dead
versions, a B
+
-tree that takes an exclusive latch on every
internal node instead of using a shared-exclusive intent latch for
descent—each of these is a natural “obvious” implementation
that is nonetheless far from production quality.

The second problem is the repair cascade that follows. An LLM can
produce a compilable, unit-test-passing implementation in minutes,
but the first realistic workload run exposes failures. Fixing one
defect shifts the bottleneck to the next; the model patches
locally without restructuring, and each patch introduces new
regressions. The loop rarely converges: after enough point fixes
the subsystem’s internal invariants are too entangled to repair
incrementally, and the only path forward is a full rewrite of the
component.

We address the problems by changing what the LLM is asked to produce.
Rather than synthesize each subsystem from a workload description and
the model’s priors, we ask it to borrow: for every architectural slot,
to select a design that an existing production system has shipped, and
to re-implement it in the generated database. Production RDBMSs have
explored which storage models, concurrency-control strategies,
recovery protocols, and access paths perform well on real hardware;
borrowing from these designs reduces the search space the LLM must
cover. Drawing on the DB-Engines
ranking

https://db-engines.com/en/ranking
, we select
9 open-source relational databases (PostgreSQL, MySQL, MariaDB,
SQLite, DuckDB, TiDB, ClickHouse, YugabyteDB, CockroachDB).
These 9 systems are chosen so that the seven classification
dimensions of the relational design space (workload, deployment,
scale, transactional guarantees, data model, SQL surface,
distribution topology) are jointly covered (Table
1
): each principal
alternative along each dimension is realized by at least one of
the surveyed systems. Taking the data model dimension as an example, the 9 systems
collectively span the major data-model alternatives a relational
engine can expose: pure relational tables of scalar columns
(MySQL, MariaDB, SQLite, TiDB), object-relational extensions
with composite, array, and range types (PostgreSQL, CockroachDB,
YugabyteDB, DuckDB), multi-model engines that ship JSON, spatial,
and vector types as first-class (PostgreSQL, DuckDB, ClickHouse),
and schema-flexible JSON-column storage (supported by eight of the
nine). The other six dimensions are covered with the same logic. Sec.
3

dimensions and the selection in detail, and reports the full
per-system coverage in Table
1
. We then analyze the
module structure and implementation techniques of each surveyed
system.
The result is consolidated into a module tree that records, per
module (storage, indexing, concurrency, etc.), the design each
surveyed database adopts. PostgreSQL’s append-only
heap
and
MySQL InnoDB’s clustered B
+
-tree, for example, both appear under
storage as alternative designs. Different modules can be filled from
different databases: an analytical workload, for instance, may pair
ClickHouse-style columnar storage with PostgreSQL-style query
optimization.

We operationalize the borrowing recipe by handing the module tree to
a coding agent and asking it to assemble the chosen designs into a
working database. This raises two challenges.

Challenge 1: Cross-module dependencies.

Borrowing a known-good design for each module does not by itself
ensure that the resulting subsystems fit together. The implementation
of one module often depends on choices made in another module in a
disjoint part of the tree. The buffer pool (under storage) must not
flush a dirty page until the corresponding WAL record (under
recovery) has reached stable storage; the optimizer’s access-path
enumeration must match the indexing module’s leaf inventory. If each
module is generated in isolation, integration requires substantial
rewrites.

Challenge 2: Harness engineering.

A coding agent producing one-shot code rarely yields a database that
compiles, passes its tests, and meets the workload’s performance
target in a single pass. Under the borrowing recipe, each module’s
implementation must also be reconciled with the borrowed behaviour
of its cooperating modules. A single-agent loop provides no
separation between code generation, testing, integration, and
post-deployment performance tuning, and no mechanism to consult the
production codebases the designs were borrowed from when problems
arise.

We address Challenge 1 by adopting the FODA feature
model
[
9
]
on top of the module tree and extending
it with cross-module edges. Two are inherited from classical FODA
(requires, mutex-with) and two are new: reference, for soft
directional consistency, and cooperate, for the symmetric case where
two modules share an invariant that neither owns alone. The result
is the dependency graph
DBModuleGraph
. For Challenge 2, we extend
SpecFS’s generation approach into a layered module-construction
pipeline in which each selected module is handled by a dedicated
subagent, and the subagents in the same dependency layer run in
parallel. Each subagent drives three specialized inner agents in
sequence: a Main Agent that generates Rust code for the module, a
Tester Agent that writes and runs unit and integration tests and
reports structured results, and an Architect Agent that performs
cross-module integration and fixes correctness or performance
regressions. A subsequent

specdb-refining
takes a user-supplied refining harness and target metrics
(e.g., mean latency
\leq
50 ms) and iteratively repairs and tunes
the database until the targets are met. The
specdb-refining
has
read-only access to the source repositories of the 9 surveyed
databases, allowing it to consult how PostgreSQL, MySQL, or other
systems handle a given situation and adapt their solution. This
extends the borrowing loop into the post-generation debugging phase.
Fig.
1
illustrates the process of using

specdb-refining
to refine the generated database against
the TPC-C benchmark: per-transaction latency decreases and
throughput increases across successive commits as the agent
iteratively diagnoses and resolves performance defects.

This paper makes the following contributions:

1.

We introduce per-workload customized databases generated
via a borrowing recipe. Rather than ship a single monolithic
system, we generate per workload a database containing only the
features the workload needs, and we restrict each module’s
implementation to designs already shipped by production RDBMSs.
This avoids the performance inefficiencies that LLM-generated
code exhibits when written purely from a workload description.

2.

We survey 9 production RDBMSs and consolidate their
module structures into a unified module tree whose leaves are
implementation variants drawn from the surveyed systems. To
capture cross-module dependencies among these variants, we
adopt the FODA feature model and extend it with two edge types,
reference (soft directional) and cooperate (symmetric joint
contract), yielding the dependency graph
DBModuleGraph
.

3.

We implement
SpecDB
as a pipeline that operationalizes

DBModuleGraph
. The pipeline includes a workload-driven selection
component that maps a natural-language description to nodes in

DBModuleGraph
, a layered module-construction stage in which each
module is generated, validated, and integrated by a dedicated
subagent (driven internally by Main, Tester, and Architect
inner agents), and a
specdb-refining
that closes the loop
against a user-supplied refining harness with read-only access to
the surveyed databases’ source code.

4.

We evaluate
SpecDB
on TPC-C with BenchmarkSQL. The
generated database, 23,779 lines of Rust, completes 60-minute
TPC-C at 1 and 10 warehouses with zero errors. At 10
warehouses it reaches tpmC = 130, compared to 128 for
PostgreSQL 14.23 and 127 for MySQL 8.0.45, with
per-transaction latency comparable to PostgreSQL and at

\sim
2.9% of PostgreSQL’s and
\sim
2.8% of MySQL’s
server-side LOC.

Related Work

2.1
Workload-Driven DBMS Tuning

A substantial body of prior work adapts a DBMS to a target
workload at deployment or runtime through configuration choices,
physical-design advisors, or autonomous in-engine planners,
without modifying the engine’s source code.

AutoAdmin

[
3
]
, initiated at Microsoft
Research in 1996 and incorporated into SQL Server as the Index
Tuning Wizard and the Database Engine Tuning Advisor, automates
the selection of indexes, materialized views, and partitioning
through cost-based search over the optimizer’s “what-if”
interface.
OtterTune

[
20
]
applies factor
analysis, Lasso regression, and Gaussian-process recommendation
to tune the configuration knobs exposed by modern DBMSs; it
operates as an external service that connects to the target
system via JDBC, recommends knob settings, and iterates over an
observation loop.
Peloton

[
12
]
integrates
the tuning loop within the engine: its self-driving architecture
monitors workload behaviour, forecasts demand, and autonomously
applies actions drawn from a fixed action set (e.g., adding
indexes, adjusting knobs).

All three approaches share a common assumption: the engine code
is implemented in advance, and the automated component, whether
a cost model, a machine-learning recommender, or a forecasting
planner, only
selects
among pre-implemented options. The
achievable optimization space is therefore bounded by the
mechanisms the engine already supports, so both the optimization
capability and the scalability to new mechanisms are limited.
SpecDB
pursues the same objective of
producing a workload-specific DBMS, but moves the synthesis
target from
configuration
to
code
: rather than
select among pre-built knobs, indexes, or actions, the pipeline
synthesizes the corresponding subsystems from a cross-database
specification library. The optimization space is therefore
bounded by what the specification library and the LLM can
jointly express, not by what an existing engine already provides.

2.2
LLM-Driven System Synthesis

Beyond editor-level completion provided by tools such as GitHub
Copilot
[
6
]
and Claude Code
[
5
]
, two recent
lines of work demonstrate that an LLM agent can produce an
end-to-end system. SpecFS
[
10
]
synthesizes a complete
FUSE-based concurrent file system by replacing free-form
natural-language prompts with a structured specification written
in Hoare-style pre/post-conditions and invariants, from which an
LLM toolchain emits the corresponding C code.
Bespoke OLAP
[
21
]
synthesizes a “one-size-fits-one”
OLAP engine from a workload contract consisting of parameterised
SQL query templates plus a Parquet dataset, and reports

11.78\times
/
9.76\times
TPC-H/CEB total-runtime speedups over
DuckDB by hard-coding workload-specific columnar layouts and
per-template C++ execution kernels. This “one workload, one
engine” thesis is consistent with the earlier empirical argument
of Stonebraker et al.
[
18
]
that purpose-built
engines can outperform general-purpose RDBMSs by orders of
magnitude when freed from features the workload never exercises.
Stonebraker’s argument, however, operates at the granularity of
major
markets
(e.g., OLTP, OLAP, stream processing)
and treats per-market specialization as worthwhile only when the
market is, in their phrasing, “of significant enough size to
warrant the investment” in a hand-built engine. With LLM-driven
generation, that investment threshold collapses to the cost of a
generation run, so the unit of specialization can shrink
further—per workload, per team, per benchmark, or per class of
queries.

SpecDB
is related to SpecFS and Bespoke-OLAP. From SpecFS we adopt the specification
style: each leaf in
DBModuleGraph
(Sec.
3.2
) carries
Hoare-style pre/post-conditions and invariants describing an
implementation technique (e.g., PostgreSQL’s append-only heap or
MySQL/InnoDB’s clustered B
+
-tree). The generated artefacts,
however, differ in scope.
SpecFS generates a file system, whose external surface is the POSIX
vfs interface and whose internal modules form a layered stack.
Bespoke generates a workload-specific fast path that does not parse
SQL, omits a conventional query optimizer, and excludes indexes,
statistics, materialized views, concurrency control, crash recovery,
replication, and a wire protocol; out-of-contract queries are routed
to a fallback general-purpose SQL processor.
SpecDB
generates a standalone relational DBMS that exposes SQL, provides
ACID under concurrent access, and spans parser, optimizer, storage
model, indexing, concurrency control, recovery, and replication. The
resulting module set carries cross-module invariants (e.g.,
WAL-before-page ordering, snapshot-visibility consistency) that no
module owns alone.

2.3
LLM Agent Harnesses for Code Generation

Beyond single-prompt code completion, a body of work studies how to

orchestrate
an LLM into a reliable code-producing agent. We
group prior work into three threads.
Multi-agent role
decomposition
assigns distinct roles—designer, coder,
tester—to separate LLM instances that communicate via structured
messages: ChatDev
[
14
]
casts software development as a
chat between specialized agents, MetaGPT
[
7
]
encodes
standard-operating-procedure templates so that each role’s output
matches a fixed schema, and AutoGen
[
22
]
provides a
general framework for conversable agents that can also call tools
and humans.
Iterative self-repair
closes a feedback loop
between generated code and execution signals: Reflexion
[
17
]

turns runtime failures into verbal critiques that are appended to
the next prompt, and Self-Debug
[
4
]
teaches the model
to inspect intermediate state and rewrite faulty code without
external supervision.
Test-driven flow engineering and
agent-computer interfaces
structure the entire generation
pipeline around verifiable artefacts: AlphaCodium
[
16
]

splits competition-style code generation into a spec-then-test-then-code
flow that markedly improves correctness over single-prompt
prompting, while SWE-agent
[
23
]
engineers the interface
between an LLM and a real software-engineering environment (file
editing, command execution, search) to make autonomous bug fixing
feasible.

SpecDB
’s harness specializes these threads for full-system database
synthesis rather than function- or repository-level edits. Role
decomposition is instantiated per module: each selected module is
handled by a dedicated subagent driven by three specialized inner
agents (Main, Tester, Architect) that mirror the
generate-validate-integrate loop required by
DBModuleGraph
’s cross-module
edges. The Architect Agent addresses cross-module integration over
symmetric joint contracts, which prior chat-style frameworks do not
surface as a first-class construct.
Iterative repair is extended beyond unit-test failures to performance
regressions: the
specdb-refining
runs a user-supplied workload harness
with explicit target metrics and turns latency or throughput
shortfalls into repair tasks. Where AlphaCodium and SWE-agent rely on
the model’s priors when a fix is non-obvious, the
specdb-refining
has
read-only access to the source repositories of the 9 surveyed
databases, so that borrowing also drives post-generation debugging
and tuning.

Constructing
DBModuleGraph
from Production Codebases

We extract modules and implementation techniques from 9 production
relational systems (SQLite, DuckDB, TiDB, PostgreSQL, MariaDB,
ClickHouse, MySQL, YugabyteDB, CockroachDB) into a unified module
tree, and turn this tree into the dependency graph
DBModuleGraph
by adding
cross-module edges.

3.1
Background: the FODA Feature Model

FODA (Feature-Oriented Domain Analysis)
[
9
]
models
a software family as a
feature tree
. Each non-root node is
annotated with its relationship to its parent:
mandatory

(
\bullet
, present whenever the parent is present),
optional

(
\circ
, may or may not be present),
alternative
/XOR (a
sibling group of which exactly one is selected), or
or
(a
sibling group of which one or more are selected). The tree
therefore captures both the common backbone of the family and the
variability points at which family members differ. FODA also
admits
cross-tree constraints
between non-sibling features
to restrict valid selections; we defer the discussion of edges
to Sec.
3.3
.

Why FODA fits the database design space.

Three properties make FODA a fit for this setting. First, production
relational databases form a product family: they share a common
backbone (parser, query processor, storage engine, recovery, etc.)
but differ in which implementation each module ships
(B
+
-tree-clustered storage vs. append-only heap, MVCC vs. 2PL,
WAL vs. rollback journal). FODA’s mandatory markers capture the
backbone, and alternative/or groups capture the variability. Second,
customising a database for a workload is an instance of FODA’s
configuration problem: choose, for every variability point, which
sub-feature to include. This makes the user-facing operation in

SpecDB
(picking an implementation per module) a projection of FODA
semantics onto the database design space. Third, FODA admits
cross-tree constraints between non-sibling features, which database
modules require (storage talks to recovery, the optimizer talks to
indexing), and provides a vocabulary that we extend
in Sec.
3.3
.

3.2
Bottom-Up Extraction from 9 Codebases

Selection of the 9 systems.

Before describing the extraction procedure, we explain why these
particular 9 databases were surveyed. The selection targets

coverage of the relational design space
rather than market
size. We characterize that design space along seven user-facing
dimensions, each split into its principal alternatives, and select
systems so that every alternative is realized by at least one
production implementation. The seven dimensions are workload
positioning (OLTP / OLAP / HTAP), deployment shape (embedded /
single-server / distributed cluster), scale envelope (vertical /
read-replica / sharded / native horizontal / geo-distributed),
transactional guarantees (single-node ACID / distributed ACID /
strict serializable / tunable or BASE), data model (pure relational
/ object-relational / multi-model / schema-flexible), SQL surface
(broad ANSI / stored procedures / advanced features such as CTE and
window functions / limited or specialized dialect), and distribution
topology (single instance / single-leader / multi-leader /
per-shard consensus / geo-replicated). The taxonomy intentionally
covers the major mainstream categories; several less mainstream
ones, such as workload-specialized engines, cloud-native architectures with separated compute
and storage, and federated query engines, are left outside the
scope of this paper to keep the design space tractable.
Table
1
reports the resulting coverage: every one
of the 28 alternatives is realized by at least one of the 9
systems. This is the precondition for the borrowing recipe: if any
alternative had no production exemplar, the corresponding XOR slot
in the merged tree would have to be filled by LLM priors rather
than by re-implementing a proven design.

Extraction overview.

With the 9 systems, the remaining task is to extract their
module structures into a unified tree. We do this bottom-up from
the source trees rather than top-down, since a top-down authoring
would require us to anticipate the design space ahead of time. Two
automation skills, run over each of the 9 repositories in turn,
fold the heterogeneous codebases into a single unified feature
tree; Fig.
2
shows two representative branches.

Per-database extraction (
DB-Feature-Extract
).

For each of the 9 databases, the
DB-Feature-Extract
skill runs three
phases over their source codebases.

(i) Module extraction.
The agent reads the top-level
directory structure, build files (
CMakeLists.txt
,

Makefile
,
go.mod
), and any

ARCHITECTURE.md
/
README
files, and identifies the
architectural modules the codebase contains rather than projecting a
fixed template onto it. PostgreSQL’s source tree, for instance,
surfaces
src/backend/storage
,
src/backend/access
,

src/backend/optimizer
, and
src/backend/replication
,
which align onto the storage/indexing/query-processing/replication
axes; MySQL’s
storage/innobase
reveals InnoDB as a pluggable
engine, recorded as a separate dimension under storage.

(ii) Hierarchical decomposition.
Each module is decomposed
by following the source code into its implementation choices: storage
model (row/column/KV), data organisation (heap, sorted file, LSM,
B
+
-tree-clustered), buffer-pool replacement (clock-sweep, LRU,
ARC), and so on, until each leaf is a concrete implementation. The
skill applies a split-vs-don’t-split rule set: configuration values
(page size, buffer-pool size) stay as leaf annotations, while
behaviourally distinct choices (WAL vs. rollback journal, hash join
vs. merge join, MVCC vs. 2PL vs. OCC) become subtree splits. This
keeps parameter knobs and architectural decisions on separate axes.

(iii) FODA relationship annotation.
Each parent-child edge
is labelled mandatory, optional, alternative (XOR), or or based on
whether the source code unconditionally initialises the child, gates
it behind a compile flag or plugin selector, or selects one of
several mutually exclusive variants.

Cross-database merge (
DB-Feature-Merge
).

The 9 module trees describe 9 parallel design spaces in different
vocabularies. To produce a single design space, the

DB-Feature-Merge
skill folds them into the unified module tree.

The merge is necessary because the per-database trees, while
faithful to their source codebases, are not directly comparable. The
same design choice appears under different names (e.g., PostgreSQL’s
“shared buffer pool” and MySQL’s “InnoDB buffer pool”), at
different levels of the tree (PostgreSQL files its row-storage
variant under
storage_model/row/heap
, while MySQL files
the same slot under
innodb/storage_model/row_format
), and
as different mandatory children of the same parent (PostgreSQL’s
heap is mandatory under row storage; MySQL’s clustered B
+
-tree is
mandatory under the same slot). The merge identifies these
relationships: which mechanisms are different names for the same
concept, which co-exist as independent capabilities, and which are
alternative solutions to the same design problem and therefore
become selection knobs in the unified tree.

The merge realises this in two phases that run together over
each pair of trees. The first phase performs
module
alignment
: it matches concepts that play the same role across the
two trees, regardless of name, granularity, or parent, and records
the matches in an alignment table that the second phase consults.
Alignment is not constrained to nodes at the same depth: when one
source documents a single leaf where the other expands the same
concept into a multi-level subtree of internal sub-mechanisms,
alignment matches the leaf to the subtree’s root and the merge
keeps the deeper source’s subtree in place beneath the aligned
node, treating the shallower source’s leaf as one contribution to
that subtree. Refinements therefore accumulate across passes
rather than collapsing down to the coarsest common denominator.
The second phase performs
relationship reconciliation
: when
the two sources mandate different children of an aligned parent,
the merge does not pick one over the other, nor does it silently
drop either; it demotes both to
alternative
siblings of the
merged parent, turning the disagreement into an explicit XOR
variability point. Identical mandatories remain mandatory, and
optional children carry over unchanged.

3.3
From the Module Tree to
DBModuleGraph
: Cross-Module Edges

The module tree captures, for each module independently, what the
module is built from. Database modules do not stand alone: storage
talks to recovery, the optimizer talks to indexing, and the parser
talks to the lock manager. The mandatory/optional/XOR/or annotations
on parent-child edges do not express these cross-module
relationships. To turn the module tree into a dependency graph that

SpecDB
’s code generator can walk, we use four cross-module edge
types. Two are inherited from classical FODA’s cross-tree
constraints (requires, mutex-with), and two are new: reference, for
soft directional consistency, and cooperate, for symmetric co-design.

Requires and mutex-with.

Classical FODA’s two cross-tree constraints carry over directly.
Requires (
A\to B
) is a hard dependency:
A
cannot be implemented
without
B
, so the generation pipeline must finish
B
first. For
example,
value_types/compound/array

\to

parser/syntax/expression/subscript
: the array value type
is unreachable from SQL unless the parser accepts the subscript
grammar
arr[i]
that reads array elements, so the array
type cannot be exercised end-to-end until the subscript productions
are in place. Mutex-with
(
A\otimes B
) prohibits coexistence in the same configuration
(e.g.,
storage_model/row

\otimes

storage_model/col
). These two cover the must-have and the
cannot-coexist cases.

Reference: soft directional dependency.

Between hard requires and outright mutex-with, we observe a third
pattern in production codebases:
A
does not need
B
to exist, but
if
B
is selected,
A
must stay consistent with
B
’s interface.
Encoding this as a requires edge overstates the dependency and
forces unnecessary co-selection; dropping it loses an integration
constraint that production code enforces. We therefore add reference
(
A\dashrightarrow B
), a soft directional consistency edge.
Examples include:

•

join-order search
\dashrightarrow

statistics module: join-order search can
fall back to default selectivities and still produce a plan,
but if a statistics module is selected, the search must consume
the statistics’ distribution summaries and cardinality estimates. The
dependency is soft (search runs without statistics) but
enforced when both are present.

•

parser productions for DDL
CREATE DATABASE

\dashrightarrow
catalog
implementation, (with three
XOR variants: heap-relation, versioned-descriptor,
engine-dictionary): the namespace depth that

CREATE DATABASE
parses (hierarchical

db.schema.table
for the first two variants vs flat

schema.table
for the engine-dictionary variant)
depends on the catalog variant in use. The parser productions
can be written without a catalog, but once a catalog variant
is selected, its hierarchy constrains which name forms the
parser must accept.

Together with requires and mutex-with, the three directional edges
express “
A
must / may / must-not depend on
B
”, a caller-callee
relationship in which one side defines the contract and the other
consumes it.

Cooperate: a symmetric joint contract.

A directional edge cannot express the case where two leaves share an
invariant that neither owns alone, so that neither side is caller
nor callee. Forcing such a case into a directional edge picks an
arbitrary side, hides the joint contract, and creates a generation
order that the other side later has to revise. We add cooperate
(
A\;\Longleftrightarrow\;B
), a symmetric joint contract on a shared
invariant (a binary layout, an ordering rule, or a conflict policy)
that neither side can specify in isolation. The two leaves must be
generated as a single unit; otherwise they are written independently
and only meet at integration time, producing the integration costs
that motivate this section. Our design contains 61 cooperate edges;
representative cases include:

•

MVCC strategy
\;\Longleftrightarrow\;
recovery strategy: the on-disk
version-record format (xmin/xmax fields, undo-pointer encoding,
redo/undo split) is split between MVCC’s visibility logic and
the recovery log’s redo path; the layout is owned by neither
side and any change requires both to agree.

•

checkpoint
\;\Longleftrightarrow\;
buffer pool: redo correctness
rests on two halves of one invariant—the buffer pool flushes
a dirty page only after its WAL record is durable, and the
checkpoint records exactly the WAL prefix consistent with what
is on disk—neither module enforces both halves alone.

•

optimizer
\;\Longleftrightarrow\;
indexing: the access-path
contract—which predicates each index answers, what bounds and
statistics it exposes—is split between the optimizer’s
enumeration and the indexing module’s implementation; the
optimizer cannot enumerate paths the indexing module does not
implement, and the indexing module cannot expose capabilities
the optimizer does not consume.

•

MVCC inplace
\;\Longleftrightarrow\;
isolation level: the conflict
policy (abort vs. wait, visibility cut-off, in-place version
overwrite rule) lives in neither module on its own.

Edges from production-database evidence.

Like the tree, the four edge types are grounded in the 9 surveyed
codebases rather than designed top-down. For each edge, at least
one production system documents or implements the corresponding
constraint, which we identify by reading source code and
architecture documentation with LLM assistance.

These cross-module edges admit more rigorous, programmatic
recovery, which we leave as future work. In principle, requires
edges can be recovered from cross-module function calls and
imports in the source tree; mutex-with edges from compile-time or
build-time exclusivity (e.g., a build configuration that admits
exactly one storage model); reference edges from
interface-coupling points where one module’s API is consumed by
another only when both are selected (e.g., cost-model dependence
on statistics histograms, catalog-to-wire type identity); and
cooperate edges from architectural invariants documented in
production-DB READMEs that the corresponding source files
transitively enforce, with READMEs serving as the entry points
and source as the verification target. Compared with the LLM-assisted reading we currently use, such a
pipeline would yield edges more rigorously and verifiably grounded
in the source itself, and would let
DBModuleGraph
track upstream changes
in the surveyed codebases automatically.

The module tree augmented with these cross-module edges is the
dependency graph
DBModuleGraph
. Each leaf carries a Hoare-style
specification following SpecFS
[
10
]
. The downstream
pipeline (Sec.
4
) consumes
DBModuleGraph
for workload-driven
node selection, cooperate-cycle decomposition, and code generation.

4.1
Workload-Driven Selection

A user typically arrives with workload requirements rather than
database expertise: they know what data they have, what queries
they intend to run, and what latency or throughput they need, but
not which storage model, concurrency-control strategy, or recovery
protocol matches those needs. Mainstream databases expose a
configuration surface large enough that even users with some
database background struggle to map requirements onto settings,
and
DBModuleGraph
(Sec.
3
), with several hundred leaves and
four edge types, is correspondingly hard to navigate by hand. We
therefore design the
specdb-select
skill to translate
user requirements directly into the corresponding modules and
implementation variants in
DBModuleGraph
, without exposing the FODA
structure to the user.

The skill takes four classes of input from the user: dataset
characteristics (e.g., table count, row counts, column types, key
distributions); query patterns (point lookup vs. range, join
frequency, read/write ratio); performance goals (p50/p99 latency,
throughput, memory budget); and workload type, which takes one of
three forms: a free-text description of the intended use case, the
path to a representative dataset (SQL dump, CSV/Parquet directory,
or an existing database), or the name of a standard benchmark
(e.g., TPC-C, TPC-H, YCSB).

A coding agent then invokes
specdb-select
with these
inputs and walks
DBModuleGraph
one variability point at a time, picking
the appropriate variant for each XOR or Or group (e.g., choosing the storage model and value types supported by the database). The picks cannot be made in isolation, because
the cross-module edges of Sec.
3.3
constrain
neighboring choices.
For instance, when a node is selected, every node it
requires must also be selected, and every node it conflicts with via a
mutex-with edge must be excluded. The
skill therefore closes the selection under these edges before
returning.

The output of
specdb-select
is a JSON file containing the
picked nodes and the requires, reference, cooperate, and mutex-with
edges among them. This file is the input to the cycle-resolution
stage of Sec.
4.2
.

4.2
Resolving Cooperate Cycles

Once
specdb-select
returns the chosen nodes and the edges
among them, the next stage prepares the graph for code generation.
Code generation requires a topological order over the selected
nodes: when
A
requires
B
, the pipeline must finish
B
first so
that
A
’s implementation can build on
B
’s interface. Requires,
reference, and mutex-with edges are all directional and, by
construction, do not form cycles, so they admit such an order via
topological sort. Cooperate edges, however, are
symmetric (Sec.
3.3
). We call a maximal connected
subgraph of nodes linked by cooperate edges a

cooperate component
; any cooperate component forms a cycle
that the scheduler cannot break, because implementing any member
requires referencing the others’ implementation. Breaking the cycle by picking a side would discard the
co-design constraint that cooperate encodes. We design the

specdb-decycle
skill to resolve this: each cooperate
component is merged into a single contract node that the generation
pipeline treats as one unit.

Neither module specifies the visibility predicate alone—MVCC alone

4.3

With the input now a DAG, code generation can in principle proceed
in topological order: each node is generated only after all its
requires/reference predecessors are done. To parallelise independent
work—unrelated modules whose implementations do not depend on
each other—we further group the topologically sorted nodes into

predecessor in the DAG lies in an earlier layer, so nodes within

When a contract has many members (e.g.,

limited benefit: the larger the joint scope, the more
specifications, source files, and test artefacts share one

own layer.

handled by its own subagent, so the subagents in a layer run in
parallel. Each subagent drives its assigned module end-to-end
through three specialized inner agents that take turns: the Main
Agent first reads the sub-skill spec for the node, the specifications of
upstream ancestors, and any contract-node members the node depends
on, and writes Rust source under the target directory; when the node is
a contract, the Main Agent additionally writes the wiring code
that ties its members together behind a unified API and any
joint-protocol code that no single member owns.
The Tester Agent then writes unit and integration tests, runs them
via
cargo test
and
cargo bench
, and reports
pass/fail counts, latency histograms, and error messages; for
contract nodes the tests include the cross-module test points. The Architect Agent finally reviews
code quality and wires the module into the engine’s main
query-processing flow, so that incoming SQL actually reaches the
new code; without this wiring the module compiles in isolation but
is dead code at run time. If correctness or performance fails, the
Architect Agent patches locally or sends the module back to the
Main Agent for regeneration.

All three inner agents run for every module: dropping the Tester
Agent leaves races and visibility bugs undetected at module
boundaries, and dropping the Architect Agent produces modules that
compile in isolation but are unreachable when the engine accepts a
query.
Please note that to accelerate generation, the Tester and Architect agents may be merged into a single Reviewer subagent, trading off strict verification rigor for reduced latency.
Each module cycles through a test-integrate-retest loop (up to three
rounds), and if it still fails, the Main Agent regenerates from
scratch (up to three regeneration attempts) before the

specdb-refining
(Sec.
4.4
) takes over.

4.4
Test-Harness-Driven Refinement

The construction pipeline produces an end-to-end database, but the
resulting artefact is rarely ready to deploy, for a variety of
reasons: cross-module integration bugs may hide on interaction
surfaces that unit tests fail to cover, the measured performance
may miss the user’s target,
specdb-select
may have omitted
a capability the workload turns out to need (e.g., group commit,
plan cache, HOT updates), and so on.

To close this loop, we design the
specdb-refining
. The skill takes
three inputs: the problem to fix, the optimization target, and a
test script. The problem can be either a correctness bug or a
performance shortfall—we treat the latter as a first-class
problem on equal footing with crashes and wrong answers. The
optimization target makes the success criterion measurable: a
specific bug fixed, a latency below a threshold, zero error lines
over a 60-minute run, and so on; each repair attempt is checked
against this criterion. The test script is what the skill runs
after every fix to decide whether the criterion now holds. The
problem and the optimization target can either be carried over
from the context of earlier stages (for instance, a regression
flagged by the Tester Agent) or be supplied directly by the user;
the test script can likewise be synthesized from the workload
description and earlier test artefacts, or be supplied by the
user.

For each diagnosed problem, the skill commits to one of two repair
routes, decided by cross-checking the sub-skill catalog before any
code change:

•

Route A (existing-code issue). The relevant module
already exists in our codebase, and the issue—a correctness
bug or a performance shortfall—lives inside it. The skill
first attempts a direct edit. If a direct edit does not yield
a reproducible fix (which is common for concurrency races,
MVCC visibility glitches, or any bug whose trigger is
intermittent on the production code), the skill constructs a
minimal standalone Rust test that exercises only the
misbehaving code path, locates the root cause and a candidate
fix on this minimal reproducer, and then ports the fix back to
the production code and data. Throughout, the skill consults
the source of the 9 surveyed relational databases, examines how they avoid or solve the same issue,
and adapts the fix accordingly. This is a second form of
borrowing, complementary to the design borrowing of
Sec.
1
—there we borrow module
designs
at
generation time, here we consult their source code directly
to guide bug fixes and performance tuning at repair time.

•

Route B (missing-module issue). The diagnosis is that a
module the workload turns out to need was not selected by

specdb-select
and was therefore never generated. The skill locates the corresponding
module in
DBModuleGraph
, computes the closure of its requires and
reference dependencies, and routes the resulting subgraph
through the layered module construction stage
(Sec.
4.3
) so that the missing module and its
dependencies are generated and integrated through the same
quality gate as the original modules.

Each cycle reproduces the problem, identifies the subsystem,
selects a route, applies the route’s repair procedure, rebuilds, and
re-runs the test script. Once the criterion holds, the skill
performs a performance audit: every measured path that still
misses the stated target becomes a new task on the queue and is
routed in the same way. The loop has no upper iteration bound, and
new error classes can be pushed onto the queue and processed in
the same session. The only graceful exit other than success is a
stuck rule: if the same error class appears at the same magnitude
for three consecutive iterations after non-trivial code edits, the
skill surfaces the diagnosis to the user, since this typically
signals that a deeper architectural or specification change is
required (only edits that touch the diagnosed subsystem’s code
path reset the counter).

5.5
Discussion

SpecDB
’s most significant practical limitation is that each new
target workload triggers a fresh generation run—module selection,
cycle resolution, layered construction, and refinement—which
takes hours of LLM compute and requires a user-supplied refining harness
before the refining loop can converge. This one-time cost is
non-negligible, yet it should be weighed against what the
alternative actually costs. Stonebraker et al.
[
18
]

demonstrated that general-purpose relational systems impose the
full overhead of a design tuned for the broadest possible workload
on every application, including the vast majority that use only a
narrow, fixed slice of the available features, and that stripping
the portions a given workload does not need—as
H-Store
[
8
]
did for OLTP—recovers more than an order
of magnitude in throughput. Our own
code-size analysis (Sec.
5.4
) reaches the same conclusion from
a different angle: well over 95% of PostgreSQL’s and MySQL’s server
code does not contribute to a single-node TPC-C run. For the
overwhelming majority of deployed services—which drive a database
server with a fixed set of parameterised transaction
templates—there is no reason to install, operate, or license a
general-purpose engine (let alone an enterprise product such as
Oracle) when the application will never exercise most of what it
ships. Against that baseline,
SpecDB
’s generation step is expensive
precisely once; the resulting artefact is a small (23,779-line),
self-contained binary whose maintenance and operational complexity
remain proportional to what the workload actually needs, with no
ongoing feature tax.

Looking forward, as LLM capability grows and inference costs fall,
the one-time generation overhead will shrink to the point where
producing a bespoke database engine becomes straightforward. At
that point the natural model
becomes
generate-once-deploy-forever
: describe the workload,
let the pipeline converge, and ship a purpose-built artefact rather
than configuring a general-purpose system from the outside. The
Bespoke-OLAP work
[
21
]
pursues a similar philosophy for
analytical engines;
SpecDB
extends the idea to full OLTP stacks
generated from a cross-database feature model
(Sec.
2.2
). We believe this mode of database
provisioning will become the default as LLM-driven development
matures.

This is not a claim that prior database systems research has become
redundant. Quite the opposite: during generation we found that
asking an LLM to implement a subsystem from a blank slate reliably
produces code that is correct in isolation but fails under concurrent
load—heap pages without a free-space map fill up silently, MVCC
without a proper vacuum horizon leaks dead versions, B-tree descent
without an intent latch serialises concurrent readers. Grounding
each module in at least one production implementation consistently
closes those gaps. Decades of engineering decisions encoded in
production codebases are not an obstacle to
SpecDB
but its primary
raw material: a high-quality specification library the LLM
recombines rather than reinvents. What the approach changes is the way that knowledge is reused.
The deeper consequence is principled: a coding agent operating
at the level of module specifications has no product-specific
scaffolding—wire protocol handlers, catalogs, planner state,
crash-recovery bookkeeping—to defend, so techniques can in
principle be combined across system boundaries. The TPC-C
instance presented here lands predominantly on PG-derived
variants (Sec.
5.2
) and does not by itself exhibit
cross-system recombination; demonstrating that capacity on a
workload mix that draws from multiple archetypes is left to
future work.

6
Limitations and Future Work

SpecDB
demonstrates that an LLM-driven pipeline can generate a
TPC-C-competitive relational database from modular specifications.
Several limitations remain.

Refining-harness supervision.

The
specdb-refining
(Sec.
4.4
) requires
the user to provide a refining harness and target metrics.
Supervision gives the loop its strength: the harness defines what
“good” means, and convergence is unambiguous. Without such a
harness, the skill cannot guide tuning, and automatically
synthesizing refining harnesses from a workload description or
trace data is an open direction. Even when the harness is in place,
we observed that bug fixing under the loop frequently requires many
iterations: with one of the strongest available coding models in our
session (Claude Opus 4.7), the agent can still lock onto an
incorrect hypothesis, fail to identify the true root cause of the
problem, and not converge within reasonable wall time (the stuck
rule
(Sec.
4.4
) fired on STOCK_LEVEL after three such
no-progress iterations in our TPC-C run). Designing harness-level
mechanisms that detect such reasoning lock-in and steer the agent
toward alternative hypotheses is a complementary future
direction.

Correctness scoped to the target workload.

Because the generated database is customized for a specific workload,
many features and code paths in mainstream systems are omitted or
simplified. Correctness for queries outside the refining harness is not
guaranteed. For example,
SpecDB
’s TPC-C-targeted instance does not
implement TEXT/VARCHAR faithfully, omits some constraint forms, and
supports only the SQL features TPC-C exercises. Extending coverage
incrementally, driven by additional harness queries, is
straightforward; offering general SQL guarantees would require
richer specifications and broader testing.

Synthesis of existing techniques rather than novel design.

The modules and their variants in
DBModuleGraph
are distilled from 9
production databases (Sec.
3.2
). Code generation
proceeds by recombining and tailoring existing techniques rather than
inventing new ones, which fits the customisation goal but limits

SpecDB
to integrating known techniques rather than producing novel
database research. Closing that gap (e.g., generating new operator
algorithms or storage formats) would require the LLM to drive both
specification evolution and implementation.

7
Conclusion

We presented
SpecDB
, a system that uses LLMs to generate customized
relational databases from a feature graph (
DBModuleGraph
) distilled from
9 production systems.
DBModuleGraph
extends the FODA
model
[
9
]
with a cooperate edge that captures
cross-subtree implementation dependencies. A cycle-resolution stage
collapses cooperate components into contract nodes, a layered
module-construction stage generates Rust code one topological
layer at a time using per-module subagents (each driven by Main,
Tester, and Architect inner agents), and the
specdb-refining
closes
the loop against a user-supplied refining harness with read-only access
to the surveyed databases’ source code.

The evaluation validates the borrowing recipe. On a 60-minute TPC-C
workload at wh=10, the generated database (23,779 lines of Rust)
reaches tpmC=130, slightly ahead of PostgreSQL 14.23 (128) and
MySQL 8.0.45 (127), at
\sim
2.9% of
PostgreSQL’s and
\sim
2.8% of MySQL’s server-side LOC. All
three systems achieve comparable throughput. These results
confirm that an LLM-generated database can match hand-engineered
production systems on a target workload while shipping only the
code that workload actually requires.

Two observations from the generation process point toward a broader
implication. First, grounding modules in production references
proved critical in our experience: modules written from a blank
slate were often correct in isolation but underperformed or broke
under concurrent load, while borrowing from production designs
(predominantly PostgreSQL in this TPC-C case) consistently closed
the gap. Decades of database engineering are
not made obsolete by LLM-driven generation—they become its primary
raw material. Second, because the agent operates at the level of
module specifications rather than product source, the pipeline
has no product-specific scaffolding to defend and can in
principle combine techniques across system boundaries. The
TPC-C case presented here exercises a PG-dominated subset of
that capacity; demonstrating recombination across multiple
production systems on a workload mix is left to future work.
Paired with falling LLM inference costs and growing model
capability, this capacity points toward a future in which
generating a purpose-built database for a target workload
becomes straightforward.

Storage Engine

Storage Model / Row Store / Row Organization / Heap / Heap Page Management

Each heap relation is paired with a Free Space Map that tracks remaining room per page in a tree structure, letting inserts pick a non-full page in near O(1), and a Visibility Map that uses 2 bits per page to mark all-visible and all-frozen pages so MVCC visibility checks and vacuum work can be skipped.

Storage Engine

Storage Model / Row Store / Row Organization / Heap / TOAST

Oversized attributes are sliced into chunks stored in a per-relation TOAST table and compressed inline; the default codec is the historical pglz, while LZ4 is offered from PG 14+ as a faster optional alternative selectable per column.

Storage Engine

Table Access Method

PostgreSQL ships exactly one built-in Table AM, the heap, which all base relations use unless a third-party Table AM is registered through the pluggable API.

Storage Engine

Storage Manager

Block-level I/O goes through a thin storage manager indirection layer (smgr) that dispatches to one built-in backend, the magnetic-disk backend, which simply maps relation forks onto regular operating-system files.

Storage Engine

Async I/O

Asynchronous I/O can be performed by the legacy synchronous read path (method_sync), by a pool of dedicated I/O worker processes (method_worker), or, on Linux from PG 18+, by submitting requests through io_uring (method_io_uring) for kernel-side batching.

Indexing

Index Access Methods / BRIN (Block Range Index)

Block Range Indexes summarise ranges of heap pages; the supplied operator classes are minmax for monotonic columns, minmax_multi for multi-modal data, inclusion for containment of geometric or range types, and bloom for low-cardinality equality filtering.

Indexing

Index Features

On top of every access method PostgreSQL supports partial indexes filtered by a WHERE predicate, expression indexes keyed on arbitrary functions, covering indexes that attach non-key INCLUDE columns (PG 11+), and composite multicolumn indexes.

Parser

DDL Syntax

The grammar accepts the full DDL surface: CREATE/DROP TABLE for relations, CREATE VIEW that the rewriter later expands, CREATE INDEX for any registered AM, CREATE TRIGGER for row and statement triggers, ALTER TABLE for online schema change, CREATE FUNCTION/PROCEDURE for user-defined routines, and CREATE EXTENSION for packaged modules.

Parser

DML Syntax

All standard mutations are parsed: SELECT, INSERT, UPDATE, DELETE, and from PG 15+ the SQL-standard MERGE statement that combines insert/update/delete in a single source-driven pass.

Parser

Query Syntax Features

The query language covers scalar and table Subqueries, recursive and non-recursive CTEs, Window Functions, Compound SELECT via UNION/INTERSECT/EXCEPT, UPSERT through INSERT … ON CONFLICT, Generated Columns, native JSON Path operators on the built-in jsonb type, EXPLAIN/EXPLAIN ANALYZE for plan inspection, LATERAL joins for correlated derived tables, and GROUPING SETS/CUBE/ROLLUP for multi-grouping aggregation.

Parser

Constraint Syntax

Declared constraints include Foreign Keys with referential actions, CHECK predicates, UNIQUE and PRIMARY KEY enforced via B-Tree indexes, and EXCLUDE constraints that use a GiST index to forbid overlapping values for arbitrary operators.

Parser

Built-in Functions

A large standard library of Date/Time, Math, and String functions is built in, alongside the canonical Aggregate Functions SUM, AVG, COUNT, MIN, MAX, and friends.

Query Processing

–

The raw parse tree is run through an Analyzer/Rewriter that does name resolution, type checking, rule application, view expansion, and row-level security to produce the canonical Query Tree; an optional LLVM-based JIT Compilation can compile expressions and tuple deforming at runtime when costs exceed thresholds; an extended Statistics subsystem captures multi-column dependencies and MCV lists gathered by the ANALYZE command.

Query Processing

Optimizer

The Standard Planner enumerates access paths, performs preprocessing, and generates plans using cost-based dynamic programming over join orders; when the number of relations exceeds the geqo_threshold (default 12), GEQO replaces exhaustive search with a semi-random evolutionary search over join orderings.

Query Processing

Executor / Join Operators

Three physical join operators are available: Nested Loop (with optional inner index), Hash Join with a build-and-probe in-memory or partitioned hash table, and Merge Join over presorted inputs.

Query Processing

Executor / Scan Operators

The executor offers Sequential Scan over heap pages, Index Scan that pipelines tuples through the heap, Index Only Scan that uses the Visibility Map to skip the heap entirely, Bitmap Scan that ORs index results into a TID bitmap before a heap fetch, and TID Scan for direct ctid lookups.

Query Processing

Executor / Other Operators

The remaining stream operators include external-merge Sort, hash and grouped Aggregate, a Hash node that builds the table feeding Hash Join, Materialize for caching a subplan, Memoize for parameterised result caching, WindowAgg for window functions, and Limit.

Concurrency Control

Isolation Mechanism

MVCC is realized by storing row versions in-place inside the heap with xmin/xmax fields in each tuple header; readers pick visible versions via snapshot comparison, so old versions linger in the table itself (rather than in an undo log as in Oracle/MySQL) until VACUUM reclaims dead tuples.

Concurrency Control

Transaction Management

Per-transaction state is tracked across several SLRU stores: the CLOG (Commit Log) records committed/aborted/in-progress status keyed by xid, a Subtransactions directory maps savepoints back to their parents, Two-Phase Commit persists PREPARE TRANSACTION state for distributed coordinators, and an optional Commit Timestamp store records the wall-clock commit time.

Concurrency Control

Lock Management

Four lock layers cooperate: Spinlocks for ultra-short critical sections backed by hardware atomics, LWLocks (lightweight read/write locks) protecting shared-memory data structures, the Regular heavyweight lock manager exposing eight lock modes with deadlock detection, and Predicate Locks used exclusively by Serializable Snapshot Isolation.

Concurrency Control

Deadlock Handling

Deadlock Detection runs periodically against a wait-for graph built from blocked processes; when a cycle is found one transaction is chosen as the victim and aborted with a deadlock error.

Concurrency Control

Isolation Levels

Three isolation levels are supported: Read Committed, the default, takes a fresh snapshot per command; Repeatable Read uses a single transaction-long snapshot for true snapshot isolation; Serializable layers SSI on top with predicate locks and read-write conflict tracking.

Recovery and Logging

–

Durability rests on a WAL (Write-Ahead Log) subsystem that inserts, reads, and replays records during crash and archive recovery; a Checkpointer periodically flushes dirty pages to bound recovery work; a Background Writer pre-cleans dirty buffers ahead of replacement; WAL Archiving hands completed segments off for long-term retention; PITR (Point-In-Time Recovery) replays archived WAL on top of a base backup to any chosen time; from PG 17+ a WAL Summarizer maintains incremental-backup metadata.

Replication

Physical Replication

Streaming Replication has the WAL sender on the primary stream freshly written WAL bytes to a WAL receiver on each standby, giving block-level physical replication; Synchronous Replication can optionally hold COMMIT until designated standbys acknowledge, with the mode configurable per transaction or globally.

Replication

Logical Replication

Logical Decoding parses WAL into a stream of row-level changes that downstream output plugins consume; built-in Publication/Subscription DDL ships changes selectively; pgoutput is the default plugin used by native subscribers; from PG 17+ a Conflict Resolution layer detects and reports apply-time conflicts on the subscriber.

Replication

–

Replication Slots are persistent registrations on the primary that pin the oldest required WAL position (and, for logical slots, the catalog xmin) so that needed segments are not recycled before downstream consumers have read them.

Memory Management

Buffer Pool / Buffer Replacement

The shared buffer pool uses a Clock Sweep replacement policy that decrements a usage counter on each pass over the buffer ring and evicts the first buffer reaching zero, approximating LRU without per-access bookkeeping.

Memory Management

Memory Context / Allocator Implementations

Four memory-context allocator strategies plug into the hierarchical palloc API: AllocSet, the default general-purpose allocator using power-of-two size classes; Generation, optimised for cohort allocations freed together; Slab, for fixed-size objects; and Bump, an append-only arena that does not support per-chunk free.

Memory Management

Shared Memory

In addition to the static main shared-memory segment, a DSM (Dynamic Shared Memory) subsystem lets backends create and attach to named segments at runtime, which is what parallel query and extensions use to share state.

Catalog and Metadata

–

All metadata lives in regular heap relations such as pg_class, pg_attribute, pg_type, and pg_proc; because the System Catalogs are themselves tables, any metadata can be inspected with ordinary SQL.

Catalog and Metadata

Cache Layer

Four cooperating caches keep catalog access cheap: a per-row Catalog Cache for syscache lookups, a Relation Cache holding parsed table and index descriptors, a Plan Cache memoising prepared-statement plans, and a Cache Invalidation bus that broadcasts changes across backends so stale entries are evicted.

Process Architecture

Process Model

PostgreSQL is Process-per-connection: a postmaster supervisor accepts incoming connections and forks a dedicated backend process per client, isolating memory and crashes at OS-process granularity.

Process Architecture

Background Processes

A fixed cast of background processes runs alongside backends: Autovacuum launcher and workers reclaim dead tuples, the Checkpointer flushes dirty buffers, the Background Writer pre-cleans them, the WAL Writer flushes WAL, the Stats Collector / Activity subsystem tracks cumulative counters, and the Syslogger captures stderr into rotated log files.

Process Architecture

–

A general Background Workers framework lets extensions register custom long-running processes, and the Parallel Query infrastructure spawns leader-and-worker groups that share state through DSM to parallelise scans, joins, and aggregates.

Networking and Protocol

–

Clients speak the proprietary PostgreSQL Frontend/Backend Protocol (not HTTP) implemented over a binary message-formatting layer; connections may be wrapped in SSL/TLS via OpenSSL; before authentication, the Host-Based Access Control (HBA) engine matches the client against pg_hba.conf rules to decide which auth method to require.

Networking and Protocol

Authentication

Many authentication methods are bundled: Trust (no challenge), Password in md5 or plaintext, SCRAM-SHA-256 (the recommended default since PG 10+), GSSAPI/Kerberos for enterprise SSO, Certificate (SSL) via TLS client certs, LDAP, RADIUS, PAM, and from PG 18+ OAuth bearer tokens.

Procedural Languages

–

SQL Functions are built in and need no installation; PL/Perl, PL/Python (PL/Python3u), and PL/Tcl ship as in-tree modules that embed the Perl, Python, and Tcl interpreters respectively as procedural-language handlers.

Procedural Languages

PL/pgSQL

PL/pgSQL has its own pipeline independent of the SQL engine: a dedicated Parser tokenises and parses block-structured source, a Compiler lowers it to an internal execution tree, an Executor interprets statements including loops, conditionals, and exception handling, and a Function Manager dispatches function and trigger invocations into that interpreter.

Extensibility

–

Packaged functionality is delivered through the Extension Framework managed by CREATE/ALTER/DROP EXTENSION, with the pg_extension catalog tracking installed versions and a control file plus SQL script defining each extension; orthogonally, function-pointer Hooks at strategic points (planner_hook, ExecutorStart_hook, ExecutorRun_hook, ProcessUtility_hook, emit_log_hook) let loaded modules intercept or wrap core behaviour.

Extensibility

Custom Access Methods

Two pluggable AM APIs are exposed: the Index AM API (used by contrib modules such as bloom) for new index types, and from PG 12+ the Table AM API for alternative table storage formats.

Extensibility

Foreign Data Wrapper

Two reference Foreign Data Wrappers are bundled: postgres_fdw connects to remote PostgreSQL servers with predicate and join pushdown, and file_fdw exposes local CSV or text files as foreign tables.

Extensibility

Official Extensions – contrib /

The contrib directory ships dozens of officially maintained extensions: monitoring and introspection (pg_stat_statements, pg_buffercache, pg_freespacemap, pg_visibility, pg_walinspect, pgstattuple, pg_prewarm, pageinspect, auto_explain, amcheck, pg_surgery, vacuumlo, sslinfo); index and operator-class support (bloom, btree_gin, btree_gist, pg_trgm); data types (hstore, ltree, cube, seg, citext, isn, uuid-ossp); text-search dictionaries (dict_int, dict_xsyn, unaccent, fuzzystrmatch); security and crypto (pgcrypto, passwordcheck, sepgsql, auth_delay); cross-database and tabular tools (dblink, tablefunc, earthdistance, xml2, tcn); and the test_decoding logical-decoding output plugin.

Storage Engine Selection / InnoDB / InnoDB Tablespace

InnoDB stores data across the shared system tablespace ibdata1, file-per-table .ibd files, user-defined general tablespaces shared by multiple tables, dedicated undo tablespaces for rollback segments, and a temporary tablespace for intrinsic and user temporary tables.

Storage Engine

Storage Engine Selection / MyISAM

MyISAM is a classic non-transactional row store that keeps data in MYD files and indexes in MYI files, optimised for read-mostly workloads without MVCC or crash recovery.

Indexing

Index Types

The default access method is a B+Tree used by both InnoDB and MyISAM. Hash indexes back the Memory engine and InnoDB’s adaptive hash, full-text indexes provide MATCH…AGAINST search in InnoDB and MyISAM, and R-Tree indexes serve spatial GIS queries in both engines.

Indexing

Index Organization (InnoDB)

The clustered primary-key index physically stores the row, secondary indexes carry the primary-key value as their tuple identifier and require a back-lookup, and the adaptive hash index is automatically promoted by InnoDB over hot B+Tree pages to short-circuit equality probes.

Indexing

Index Features

Beyond covering indexes, MySQL offers prefix indexes that index only the first N characters of a column, descending indexes (8.0+) for true reverse-order traversal, invisible indexes (8.0+) hidden from the optimizer for safe drop trials, and functional indexes (8.0.13+) over expressions.

Query Processing

–

Query Processing

Optimizer

The 8.0+ Hypergraph optimizer represents join relationships as a hypergraph and unifies plans under an Access Path abstraction, complementing the legacy heuristic-plus-cost optimizer. The range optimizer drives index range scans, Index Merge, Skip Scan and Group Skip Scan, and partition pruning, while equi-height histograms, index cardinality, and ANALYZE TABLE feed cost estimation.

Query Processing

Execution Engine / Join Operators

Joins are executed by nested loop as the universal fallback, Hash Join for equi-joins since 8.0.18, and Batch Key Access which buffers join keys and feeds them to the storage engine in batches to amortise random I/O.

Query Processing

Execution Engine / Scan Operators

The executor exposes full table scan, full index scan, index range scan, ref lookups for unique key equality, and Index Merge which intersects or unions row-id sets from several single-column indexes when no composite index covers the predicate.

Concurrency Control

Isolation Mechanism

InnoDB implements MVCC by chaining old row versions through the undo log rather than retaining old tuples in the heap as PostgreSQL does. MyISAM falls back to coarse table-level locking, and Memory and Archive run effectively without locking for their respective access patterns.

Concurrency Control

Lock Management

InnoDB’s lock manager exposes record, gap, next-key (record plus gap, the REPEATABLE READ default), insert-intention (a gap variant allowing concurrent inserts in different positions of the same gap), predicate (for R-Tree spatial indexes), and auto-increment lock modes.

Concurrency Control

–

Metadata locking guards DDL/DML interaction at the SQL layer with a richer mode lattice including SHARED, EXCLUSIVE, and INTENT_EXCLUSIVE so schema changes do not race with running statements that depend on the same objects.

Concurrency Control

Synchronization Primitives

Internal critical sections are protected by mutexes for short exclusive sections and read-write latches offering S-Latch and X-Latch modes for buffer-pool pages and other shared structures.

Concurrency Control

Deadlock Handling

InnoDB builds a wait-for graph among transactions to detect cycles and aborts a victim, and as a coarse fallback the innodb_lock_wait_timeout setting bounds how long any lock acquisition may block before erroring out.

Concurrency Control

Transaction Management

Transactions support nested SAVEPOINTs for partial rollback and XA two-phase-commit transactions that allow MySQL to act as a resource manager in distributed transactions coordinated by an external TM.

Concurrency Control

Isolation Levels (InnoDB)

InnoDB offers all four SQL standard levels: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ (which uses next-key locks to prevent phantoms while still using MVCC for reads), and SERIALIZABLE which promotes plain SELECTs to locking reads.

Recovery & Logging

InnoDB Redo Log

The redo log uses group commit to batch many transactions into a single fsync for higher throughput, and supports log encryption so on-disk redo records are protected at rest.

Recovery & Logging

InnoDB Undo Log

Undo records are managed in rollback segments living in dedicated undo tablespaces, providing both transaction rollback and the version chain that MVCC reads follow.

Recovery & Logging

–

InnoDB performs fuzzy checkpoints that advance the redo low-water mark without freezing writes, replays redo from the last checkpoint during crash recovery, and uses the doublewrite buffer to repair partial-page writes detected at recovery.

Recovery & Logging

Binary Log (Binlog) / Binlog Format

The binary log records changes for replication and point-in-time recovery in three formats: statement-based logs the SQL text, row-based logs before/after row images, and mixed switches per-statement based on safety.

Replication

Binary Log Replication

Replicas tail the primary’s binlog asynchronously by default for maximum throughput, while the semi-synchronous plugin makes the primary wait for at least one replica’s acknowledgement before returning success to the client.

Replication

–

GTIDs assign a globally unique identifier to each transaction so failover can resume from the correct position without binlog-coordinate bookkeeping. Replication channels let one replica consume from multiple sources, and the Clone plugin produces a physical snapshot to bootstrap new nodes quickly.

Replication

Group Replication

Group Replication runs a Paxos-based atomic broadcast (XCom) and resolves write conflicts through certification of write-sets, applies flow control to keep replicas from falling behind, and operates in either single-primary mode for a fixed writer or multi-primary mode where any node accepts writes.

Memory Management

InnoDB Buffer Pool

The buffer pool implements a two-segment young/old LRU to resist scan pollution, can be sharded into multiple instances to reduce mutex contention, performs linear and random read-ahead prefetching, and supports dump/restore so a restarted server can repopulate hot pages quickly.

Memory Management

–

MyISAM owns a separate key cache for index blocks, the TempTable engine provides modern in-memory storage for query temporaries, the sort buffer feeds Filesort, and a dedicated join buffer backs Hash Join and Batch Key Access.

Catalog & Metadata

–

The 8.0+ atomic data dictionary stores catalog metadata in transactional InnoDB tables instead of legacy .frm files, enabling DDL that is fully atomic across catalog and storage. A dictionary cache layer speeds repeated lookups, INFORMATION_SCHEMA exposes the dictionary as views, and Performance Schema offers deep instrumentation through hundreds of virtual tables.

Process Architecture

Threading Model

The default model assigns one OS thread per client connection, a single-threaded mode exists for debugging, and the Enterprise edition ships a thread-pool plugin that multiplexes connections onto a bounded worker set for high connection counts.

Process Architecture

Connection Transports

Clients connect over TCP sockets and Unix domain sockets on Unix-like systems, plus named pipes and shared-memory transports on Windows for local low-latency access.

Process Architecture

Background Threads (InnoDB)

InnoDB runs a master thread coordinating periodic maintenance, multiple I/O threads for asynchronous reads and writes, purge threads that retire undo records, page-cleaner threads that flush dirty buffer-pool pages, and a dedicated log writer thread driving redo durability.

Networking & Protocol

Protocol

The classic MySQL wire protocol carries SQL statements and result sets for legacy and standard clients, while the X Protocol underpins MySQL Document Store with CRUD operations over JSON documents and a more modern message framing.

Networking & Protocol

Authentication

Authentication plugins span legacy mysql_native_password, the 8.0+ default caching_sha2_password, and enterprise integrations with LDAP, PAM, and Kerberos, with multi-factor authentication chaining several methods per account.

Networking & Protocol

–

Client/server traffic can be wrapped in SSL/TLS for transport encryption and certificate-based mutual authentication.

Networking & Protocol

Authorization

Authorization in 8.0+ adds true role-based access control with grantable roles, dynamic privileges that finely scope administrative actions, and partial revokes that deny access to specific schemas even when a broader privilege is granted.

Extensibility

–

MySQL is heavily plugin-driven: storage engines, authentication, audit, and replication ship as plugins; the 8.0+ component system layers a service-oriented replacement for the older plugin API; user-defined functions extend SQL; the rewriter plugin transforms incoming queries; the audit plugin emits compliance logs; the keyring plugin manages keys for transparent data encryption; and full-text parser plugins such as ngram add tokenizers.

Indexing

Index Types

Provides B+Tree as the default for InnoDB and MyISAM, hash indexes in the Memory engine and InnoDB’s automatically built Adaptive Hash Index, full-text indexes across InnoDB, MyISAM and Mroonga, R-Tree spatial indexes in InnoDB and MyISAM, and LSM-tree indexing through MyRocks.

Indexing

Index Organization (InnoDB)

The clustered index is the table’s physical layout keyed by primary key, secondary indexes hold primary-key bookmarks at their leaves so non-covering lookups must traverse back to the cluster, and the Adaptive Hash Index opportunistically maps frequently accessed B+Tree pages to a hash structure.

Indexing

Index Features

Supports covering indexes that satisfy queries from secondary structures alone, prefix indexes that key only the leading N characters, descending index ordering, invisible indexes hidden from the optimizer for safe rollouts, and functional indexes computed from expressions.

Query Processing

–

Semantic analysis resolves names against the catalogue and performs type checking and coercion before the optimizer plans the statement.

Query Processing

Optimizer / MariaDB Unique Optimizations

MariaDB-only transforms include table elimination that drops unreferenced JOIN inputs, group-by cardinality optimization, virtual-column substitution that rewrites expressions to use indexed virtual columns, an enhanced Index Condition Pushdown, and condition pushdown into IN-subqueries.

Query Processing

Execution Engine / Join Operators

Supports nested-loop joins, hash join, Batched Key Access for amortising index probes, and Block Nested Loop for joining without an applicable index.

Query Processing

Execution Engine / Scan Operators

Provides full table scans, ordered index scans, index range scans, multi-index merge scans, and ref-style unique key lookups for equality probes on primary or unique indexes.

Concurrency Control

Isolation Mechanism

InnoDB implements MVCC by chaining old row versions through the undo log (rather than keeping prior versions in the heap as PostgreSQL does), MyISAM and Aria fall back to table-level locking, Memory and Archive run lock-free or with engine-internal serialisation, and MyRocks offers both pessimistic and optimistic transactional modes.

Concurrency Control

Lock Management

InnoDB acquires record locks on individual rows, gap locks on the empty ranges between index entries to block phantoms, next-key locks combining record and gap (the REPEATABLE READ default), insert-intention locks as a lightweight gap-lock variant, predicate locks for R-Tree spatial queries, and table-level auto-increment locks for AUTO_INCREMENT columns.

Concurrency Control

–

Metadata locking arbitrates between DDL and concurrent DML using SHARED, EXCLUSIVE, INTENT_EXCLUSIVE and other modes so that schema changes wait for in-flight statements without corruption.

Concurrency Control

Synchronization Primitives

Internal synchronisation uses mutexes for short critical sections and read/write latches with shared (S) and exclusive (X) modes for buffer-pool pages and other shared structures.

Concurrency Control

Deadlock Handling

InnoDB maintains a wait-for graph and aborts the cheapest victim when a cycle appears, while a configurable lock-wait timeout (innodb_lock_wait_timeout) bounds how long any waiter blocks before being rolled back.

Concurrency Control

Transaction Management

Transactions support nested SAVEPOINT markers for partial rollback and XA two-phase commit so external transaction managers can coordinate atomic commits across resources.

Concurrency Control

Isolation Levels (InnoDB)

InnoDB implements all four standard isolation levels: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ which uses next-key locking to prevent phantoms, and SERIALIZABLE which promotes plain SELECTs to shared locks.

Recovery & Logging

InnoDB Redo Log

The redo log uses group commit to coalesce many transactions into a single fsync, amortising flush latency, and supports redo log encryption to protect on-disk log contents.

Recovery & Logging

InnoDB Undo Log

Undo records are managed in rollback segments that drive both transaction rollback and MVCC version-chain reconstruction, with a configurable number of segments to reduce contention.

Recovery & Logging

–

Aria has its own write-ahead log so it can perform crash recovery (unlike MyISAM which has none), fuzzy checkpoints flush dirty pages incrementally, crash recovery replays the redo log to restore committed but unflushed transactions, and the doublewrite buffer protects against partial page writes.

Recovery & Logging

Binary Log (Binlog) / Binlog Format

The binlog can be written in statement-based, row-based, or mixed format; MariaDB defaults to mixed and switches to row-based whenever a statement is unsafe to replay deterministically (whereas MySQL defaults to row-based).

Replication

Binary Log Replication

Replication is asynchronous by default with a semi-synchronous mode that delays commit acknowledgement until at least one replica has received the events, trading throughput for stronger durability guarantees.

Replication

–

MariaDB GTID identifies events by a domain-server-sequence triple distinct from MySQL’s source_id:transaction_id, multi-source replication lets a replica consume binlogs from several primaries simultaneously, and mariabackup (a Percona XtraBackup fork) performs hot physical backups of running instances.

Replication

Galera Cluster

Galera provides certification-based replication that detects write-set conflicts using a Paxos-style protocol so all nodes accept writes, flow control throttles fast nodes when slow members lag, and node bootstrap uses incremental state transfer when possible or full state snapshot transfer (via rsync, mariabackup or mysqldump) for fresh joiners.

Replication

Parallel Replication

Replicas can apply events in parallel under a conservative scheduler that respects original commit order, an optimistic mode unique to MariaDB that speculatively applies non-conflicting transactions out of order, and an aggressive mode that maximises parallelism.

Memory Management

InnoDB Buffer Pool

The buffer pool uses a young/old LRU split to protect hot pages from full-table-scan eviction, supports multiple instances to reduce mutex contention, performs linear and random read-ahead, and can dump and restore its page contents for fast warm-up after restart.

Memory Management

–

Aria has a dedicated page cache that supersedes the legacy MyISAM key cache for index blocks, and per-statement memory comes from sort buffers for filesort and join buffers backing hash join, BKA and BNL; the built-in thread pool greatly reduces per-connection memory compared with thread-per-connection.

Catalog & Metadata

–

Table definitions are still kept in .frm files combined with InnoDB’s internal data dictionary (rather than the transactional data dictionary in MySQL 8.0), while INFORMATION_SCHEMA exposes standard catalog views, PERFORMANCE_SCHEMA provides deep instrumentation, and the mysql system database stores users, privileges, time zones and help tables.

Process Architecture

Threading Model

MariaDB supports the traditional thread-per-connection model and ships a built-in thread pool in the community edition (MySQL restricts this to Enterprise) that organizes workers into thread groups, auto-tunes the number of active threads, and scales much better under high connection counts.

Process Architecture

Connection Transports

Clients can connect over TCP sockets, Unix domain sockets on POSIX hosts, and on Windows additionally via named pipes and shared memory.

Process Architecture

Background Threads (InnoDB)

InnoDB runs dedicated background threads: I/O threads driving asynchronous reads and writes, purge threads recycling old undo records, page cleaner threads flushing dirty pages from the buffer pool, and a log writer thread emitting redo records.

Networking & Protocol

Protocol

Speaks the classic MySQL wire protocol so existing MySQL client libraries and connectors interoperate without modification.

Networking & Protocol

Authentication

Supports mysql_native_password and SHA-256 password schemes, Unix-socket peer authentication based on the OS user, and several plugins shipped in the community build only by MariaDB: Ed25519 elliptic-curve signatures, GSSAPI/Kerberos, and PAM.

Networking & Protocol

–

SSL/TLS encrypts client/server traffic and supports certificate verification, cipher selection and modern protocol versions for in-transit confidentiality.

Networking & Protocol

Authorization

Role-based access control has been available since 10.0 (predating MySQL 8.0), built on top of the traditional grant tables that store privileges per user, database, table, column and routine.

Encryption

Data-at-Rest Encryption / Encryption Key Management Plugin

Master keys for at-rest encryption can be served by pluggable key managers including a file-based provider, AWS KMS, HashiCorp Vault, and any KMIP-compliant key server.

Encryption

Data-at-Rest Encryption / Encrypted Components

Encryption can be applied to InnoDB tablespaces at the tablespace level, the InnoDB redo log and undo log, Aria tablespaces (a MariaDB-only capability), the binary log, and on-disk temporary files used by sorts and large joins.

NoSQL Interface

–

The MariaDB-only HandlerSocket plugin exposes the storage-engine handler interface directly over a network protocol, bypassing SQL parsing and optimization to deliver very high-throughput key-value style index lookups.

Extensibility

–

A pluggable architecture covers storage engines, authentication, audit, encryption and more (with a broader plugin taxonomy than MySQL), users can register UDFs in C/C++, the bundled MariaDB Audit Plugin is community-edition (versus MySQL Enterprise-only), the MariaDB-exclusive Query Response Time plugin captures latency distributions, and full-text parser plugins let users supply custom tokenisers.

Storage Engine

Storage Model / Row Store / Row Organization

Each B-Tree leaf node holds an entire row (rowid plus all column values). Column values are serialised compactly in declaration order using the SQLite Record Format.

Storage Engine

B-Tree / B-Tree Page Management / Autovacuum / Autovacuum Mode

Full Autovacuum compacts and reclaims free pages automatically at the end of every commit. Incremental Autovacuum only marks pages reclaimable, deferring the actual shrink until the application invokes PRAGMA incremental_vacuum(N).

Storage Engine

Pager / Journal Mode

Rollback Journal is the default and copies original pages to a side journal before mutation, with DELETE, TRUNCATE, PERSIST, and MEMORY sub-modes. WAL mode writes changes to a log first, allowing readers and a writer to proceed concurrently, and can be omitted at compile time via SQLITE_OMIT_WAL.

Storage Engine

–

The Pager fronts a pluggable Page Cache whose default implementation uses LRU replacement. The Database File Format is a single cross-platform big-endian file with a backward-compatible layout. VACUUM rebuilds the file to reclaim space (omittable via SQLITE_OMIT_VACUUM), In-Memory Databases are addressable via :memory:, and Incremental BLOB I/O streams large values without loading them whole.

Storage Engine

VFS – Virtual File System / VFS Implementations

Built-in VFS backends ship for Unix (POSIX file syscalls), Windows (Win32 file APIs), and an optional KV-store VFS gated by SQLITE_OS_KV_OPTIONAL for embedded key-value targets.

Virtual Machine

–

The VDBE Core is a bytecode interpreter executing roughly 190 opcodes that SQL is compiled into. The VDBE API surface exposes sqlite3_step and sqlite3_finalize to drivers, auxiliary helpers manage Mem value cells, and a dedicated VDBE Sorter implements ORDER BY with in-memory plus external merge passes.

Parser

DDL Syntax

The parser handles CREATE TABLE and DROP TABLE through the schema builder, plus CREATE VIEW, CREATE INDEX, CREATE TRIGGER, ALTER TABLE, and ATTACH DATABASE. Most are gated by SQLITE_OMIT_* compile flags so embedded builds can drop unused DDL.

Parser

DML Syntax

DML covers SELECT, INSERT, UPDATE, and DELETE through dedicated compilation paths, plus UPSERT via INSERT … ON CONFLICT. UPSERT can be excluded with SQLITE_OMIT_UPSERT.

Parser

Query Syntax Features

Query features include Subqueries, CTE, Window Functions, Compound SELECT (UNION/INTERSECT/EXCEPT), Generated Columns, EXPLAIN, and CAST, each with its own SQLITE_OMIT_* trim switch. PRAGMA is SQLite’s signature configuration mechanism for runtime tuning and introspection.

Parser

Constraint Syntax

Foreign Keys are parsed unconditionally but only enforced when PRAGMA foreign_keys is ON, and can be compiled out via SQLITE_OMIT_FOREIGN_KEY. CHECK constraints are similarly trimmable, while UNIQUE and PRIMARY KEY are always available and backed by index B-Trees.

Parser

Built-in Functions

Built-ins include the JSON1 function set for JSON manipulation, Date/Time functions for ISO and Julian-day conversions, and the standard Aggregate Functions SUM, AVG, COUNT, MIN, and MAX. JSON and date families are individually trimmable via SQLITE_OMIT_* flags.

Query Processing

–

Semantic Analysis and Code Generation are split across the schema builder for DDL, the SELECT/INSERT/UPDATE/DELETE compilers for DML, an expression compiler for scalar evaluation, and a name resolver that binds column and table references before VDBE bytecode is emitted.

Query Processing

Query Optimizer / Optimization Strategies

The optimizer chooses among Index Scan, Full Table Scan, Covering Index, and Automatic Index (transient indexes built on the fly). It also applies OR, BETWEEN, and LIKE rewrites to convert predicates into index-friendly range scans, each toggleable via SQLITE_OMIT_*_OPTIMIZATION.

Query Processing

Executor Operators / Join

SQLite implements only Nested Loop Join: the planner picks an outer table and probes inner tables (often via an Index Scan) for each outer row, with no hash or sort-merge alternatives.

Concurrency Control

Threading Model

Single-Thread mode disables all mutexes for the smallest and fastest build but forbids cross-thread use. Multi-Thread mode protects each connection with its own mutex so different connections can run on different threads. Serialized mode (default) wraps everything in a global mutex so any thread may use any connection.

Concurrency Control

Mutex Implementation

The mutex layer is pluggable: a No-op Mutex for single-threaded builds, a pthread-based Unix Mutex, and a Win32 critical-section Windows Mutex.

Concurrency Control

File Locking / Locking Protocol

The Unix VFS supports POSIX fcntl byte-range locks (default), whole-file flock for filesystems lacking byte-range support, and a dotfile lock-file scheme for NFS and other environments where kernel locks are unreliable.

Concurrency Control

–

Shared Cache Mode lets multiple connections in the same process share one page cache, adding table-level read/write locks for finer-grained intra-process concurrency. The feature can be removed via SQLITE_OMIT_SHARED_CACHE.

Concurrency Control

Transaction

Savepoints provide nested transaction semantics: each SAVEPOINT establishes a named rollback point that can be released or rolled back independently of the enclosing transaction.

Concurrency Control

Isolation Level

Outside WAL mode, transactions are Serializable because the writer holds an exclusive lock for the duration of the write. In WAL mode, read transactions see a stable Snapshot Isolation view of the database as of their start while a single writer proceeds in parallel.

Memory Management

Memory Allocator

The allocator is selectable at build time: the default System malloc wrapper (mem1), mem2 with guard bytes and leak detection, mem3 carving from a pre-allocated buffer with no system malloc, and mem5 which uses a power-of-two Buddy system over a fixed arena.

Memory Management

Lookaside Allocator

Each connection owns a Two-Size Lookaside arena that satisfies small allocations (such as parse trees and statement structures) from a pre-allocated slab to bypass the general allocator. SQLITE_OMIT_TWOSIZE_LOOKASIDE disables it.

Memory Management

–

The Memory Journal stores rollback data for temporary tables and transient databases entirely in RAM to avoid disk I/O. The Soft Heap Limit, set via sqlite3_soft_heap_limit64, asks the engine to release cached pages when usage crosses a threshold, and SQLITE_ENABLE_MEMORY_MANAGEMENT enables proactive memory release.

Extensions

R-Tree

The R-Tree extension supports spatial indexing of bounding boxes, and the GeoPoly add-on extends it with arbitrary 2D polygon containment and intersection queries on top of the same R-Tree index.

Extensions

–

Dynamic Extension Loading allows runtime loading of shared libraries (.so or .dll) when SQLITE_ENABLE_LOAD_EXTENSION is set. The Virtual Table mechanism lets external data sources appear as ordinary SQL tables, and FTS5, R-Tree, and dbstat are all built on this framework; SQLITE_OMIT_VIRTUALTABLE removes it.

API & Callbacks

–

The Core API exposes sqlite3_open/close, sqlite3_prepare_v2, and sqlite3_step/sqlite3_column_* for connection, compilation, and result retrieval. The Authorization Callback lets applications intercept and forbid specific SQL operations, the Backup API performs online hot copies, and Trace/Profile and Progress callbacks let applications observe engine behaviour, each individually trimmable via SQLITE_OMIT_* flags.

Build & Deployment

Build Mode

The recommended Amalgamation build concatenates every source file into a single sqlite3.c of 200k+ lines, which compiles faster and runs about 5% faster thanks to whole-program optimization. Separate Compilation builds each translation unit individually and is mainly used by SQLite developers.

Build & Deployment

Platform Targets

SQLite ships as a Native C Library and is also packaged as a WASM build for browsers, a JNI binding for Java and Android, and a long-standing Tcl binding (the language in which SQLite’s test suite is written).

Build & Deployment

–

The Shell is the sqlite3 command-line tool that provides interactive SQL execution, dot-commands for import, export, and schema inspection, and is itself an example application built on the public C API.

Storage Engine

Storage Model

Stores user data in a pure column-store layout where each column lives independently on disk. The columnar layout naturally enables vectorized execution and high-ratio compression.

Storage Engine

Data Organization

Tables are partitioned into Row Groups of roughly 122880 rows that act as the unit of parallelism and I/O. Within a Row Group each column is held as an independently compressed and encoded Column Segment, and each Column Segment carries min, max, count, and null_count statistics used for segment-level pruning.

Storage Engine

Compression Algorithms

Selects per-segment among RLE, Dictionary plus FSST, Bit-packing, ZSTD, Chimp for time-series floats, Roaring Bitmaps, ALP and ALPRD for floating-point data, PATAS, Constant for uniform columns, and Uncompressed as a fallback. The choice is made by a sampling-based analyzer that picks the smallest representation per Column Segment.

Storage Engine

Index / ART (Adaptive Radix Tree) / ART Node Types

Implements an Adaptive Radix Tree whose internal nodes adapt their fan-out using Node4, Node16, Node48, and Node256 layouts depending on the number of children. The ART backs PRIMARY KEY and UNIQUE constraint enforcement and accelerates point and range lookups.

Storage Engine

Buffer Manager

Performs all disk traffic in fixed-size blocks, treating block-level I/O as the unit of read, write, and eviction between memory and storage.

Storage Engine

–

Persists the entire database in a single file similar to SQLite, with explicit forward and backward compatibility management across file format versions. A checkpoint mechanism flushes in-memory state and merges WAL changes into the main database file.

Query Processing

–

A dedicated Binder spread across many files performs name resolution, type inference, and expression binding to turn the AST into bound logical expressions. The Planner then converts the bound AST into a logical plan tree composed of Scan, Filter, Projection, Join, Aggregate, Sort, and Limit operators.

Query Processing

Optimizer / Optimization Strategies

Applies filter pushdown and pullup, projection pullup, column pruning, and join order optimization driven by a cost model, cardinality estimator, and plan enumerator. Further passes include join elimination, CTE inlining and CTE filter pushing, common subexpression elimination, late materialization, Top-N rewrites for ORDER BY plus LIMIT, Row Group pruning via column statistics, compressed materialization of intermediates, build/probe side selection for Hash Join, and outer join simplification.

Query Processing

Execution Engine

Executes plans as vectorized column batches rather than tuple-at-a-time iterators, in the spirit of ClickHouse and unlike the SQLite VDBE or PostgreSQL Volcano model. Queries are decomposed into Pipelines connected at materialization points, and a Task Scheduler dispatches Pipeline tasks across multiple worker threads for intra-Pipeline parallelism.

Query Processing

Join Algorithms

Defaults to Hash Join and additionally provides Nested Loop Join, Sort-Merge Join, Cross Product, ASOF Join for time-series nearest matches, Range Join, IEJoin for inequalities, Blockwise Nested Loop, Positional Join, Delim Join for delimiter-driven correlation, and Perfect Hash Join when key domains permit.

Query Processing

Aggregation

Builds aggregations on a radix-partitioned hash table that splits keys by hash radix into independent partitions, enabling parallel aggregation across worker threads with low contention.

Type System

Scalar Types

Offers TINYINT, SMALLINT, INTEGER, BIGINT, and 128-bit HUGEINT integers, FLOAT and DOUBLE floats, arbitrary-precision DECIMAL, and BOOLEAN.

Type System

String Types

Provides VARCHAR for variable-length text and BLOB for arbitrary binary payloads.

Type System

Temporal Types

Supports DATE, TIME, TIMESTAMP with TIMESTAMP_S, TIMESTAMP_MS, and TIMESTAMP_NS precision variants, and INTERVAL for durations.

Type System

Complex Types

Implements nested STRUCT records, variable-length LIST, fixed-length ARRAY, key-value MAP, and tagged UNION types, allowing arbitrary composition for semi-structured workloads.

Type System

Special Types

Adds VARIANT for JSON-like semi-structured data, geospatial types delivered through the spatial extension, and custom user-defined types registered through the Catalog.

Concurrency & Transaction

MVCC

Uses optimistic concurrency control where writers do not acquire row locks eagerly but check for conflicts at commit time. An Undo Buffer retains prior row versions so concurrent readers see a consistent snapshot without blocking writers.

Concurrency & Transaction

Writer Model

Adopts a single-writer multiple-reader model in which only one write transaction is active at a time while any number of read transactions proceed concurrently against MVCC snapshots.

Concurrency & Transaction

Transaction States

Transactions move through Commit and Rollback terminal states, followed by a Cleanup phase that releases the Undo Buffer entries once no snapshot still needs them.

Concurrency & Transaction

–

A Write-Ahead Log records changes before the corresponding data pages are mutated, providing the foundation for crash recovery. Checkpoint operations periodically or manually fold WAL contents into the main database file and truncate the log.

Catalog

Catalog Manager / Catalog Entry Types

Maintains catalog entries for Schema, Table, Index, View, Function, Sequence, Macro, and Type objects. Each entry kind is versioned alongside the transaction system so DDL respects MVCC visibility.

Catalog

–

A Dependency Manager tracks references between catalog objects, for example views depending on tables, to prevent unsafe drops. The Attached Databases mechanism allows mounting multiple database files at once and issuing cross-database queries.

Data Formats

Built-in Formats

Reads and writes Parquet with support for geometry and variant types, CSV with an automatic sniffer for delimiters and types, and JSON in both directions. These formats are first-class table sources usable directly in SELECT statements.

Data Formats

Extension-based Formats

Adds Arrow, Delta Lake, and Excel support through dedicated extensions that register additional table functions and writers, keeping the core engine slim.

Extension System

–

An Extension Manager dynamically loads and unloads compiled extensions and can auto-install them from a remote extension repository.

Extension System

Built-in Extensions

Bundles core_functions, parquet, json, icu for ICU collations, autocomplete for SQL completion, jemalloc for the Jemalloc allocator integration, and tpch and tpcds for benchmark data generation.

Extension System

External Extensions

Offers httpfs for S3 and HTTP file access, spatial for GIS functions, postgres_scanner, mysql_scanner, and sqlite_scanner for federated reads, arrow for Apache Arrow interoperability, excel for spreadsheet I/O, fts for full-text search, and aws and azure for cloud credentials and Azure Blob Storage access, plus delta for Delta Lake reads.

Memory Management

–

A Buffer Manager governs block-level data exchange between memory and disk and can spill blocks to a temporary directory when memory is exhausted. An Arena Allocator handles bulk allocation and release during query execution, all data is managed in fixed-size blocks, and the optional jemalloc extension supplies a more efficient system allocator.

Process Architecture

–

Runs as an embedded library linked directly into the host application, executing in-process with no server and no client-server protocol, mirroring the SQLite model. Inside that process a Task Scheduler drives multi-threaded Pipeline execution for intra-query parallelism, and although there is no native network protocol, community wrappers expose HTTP and PostgreSQL-compatible interfaces.

Column Types & Encoding

Compression Codecs

Per-column codecs include LZ4 as the speed-first default and ZSTD for higher ratio, time-series specialists Delta, DoubleDelta and Gorilla, integer encodings T64, GCD and Bitpacking, floating-point compressors FPC and ALP, an Encrypted codec for at-rest encryption, and an explicit None option.

Query Processing

–

Query processing is split into an Analyzer for name resolution, type inference and expression analysis, a Planner that builds a logical query plan, and a large family of Interpreters that translate AST and plans into executable operations with one interpreter class per statement type.

Query Processing

Processor-Based Execution Engine / Execution Mode

The processor graph supports both pull-based execution where downstream stages request chunks and push-based execution where producers actively forward chunks, allowing each pipeline edge to choose the most efficient mode.

Query Processing

Processor-Based Execution Engine / Source Processors

Source processors feed the pipeline from MergeTree parts, remote nodes, Kafka topics, and local files or S3 objects.

Query Processing

Processor-Based Execution Engine / Transform Processors

Transform processors implement WHERE and PREWHERE filtering, expression evaluation, sorting and merge sorting, aggregation, joins, window functions, LIMIT truncation, HAVING with TOTALS, and ROLLUP or CUBE expansion.

Query Processing

Processor-Based Execution Engine / Sink Processors

Sink processors persist pipeline output to MergeTree parts, forward chunks to remote nodes, or discard rows via a null sink.

Query Processing

Join Algorithms

Join execution chooses among hash join as the default, parallel hash join, sort-merge join and full sorting merge join, direct lookup joins through a Dictionary or Join engine, grace hash join for spill-to-disk operation on large inputs, cross join, and ASOF join for nearest-time matching unique to ClickHouse.

Data Formats

Input/Output Formats

Pluggable input and output formats include text forms TabSeparated, CSV, several JSON dialects, Values, Pretty and Vertical for terminals, and Markdown plus XML, alongside binary forms Parquet, ORC, Avro, Arrow, the Native ClickHouse encoding, RowBinary, Protobuf, MsgPack and Cap’n Proto.

Distributed Architecture

Sharding / Sharding Strategy

Sharding strategies include hash-based routing on a column, random distribution, and arbitrary custom expressions evaluated per row.

Distributed Architecture

Replication / Coordination / ClickHouse Keeper

ClickHouse Keeper is a built-in Raft-based replacement for ZooKeeper that speaks the same client protocol so existing replicated tables can switch coordinators without code changes.

Distributed Architecture

–

Remote query execution ships intermediate columnar chunks between nodes over TCP using the Native binary format for low-overhead transfer.

Memory Management

–

Per-query memory is bounded by tracking allocations and aborting queries that exceed the configured maximum, columnar buffers are sourced from arena allocators and POD-style array structures so memory is allocated and released per column, and a global overcommit mechanism arbitrates memory across concurrent queries.

Memory Management

Caches

Multiple caches accelerate reads: a mark cache holds granule offset metadata, an uncompressed block cache retains decoded blocks, a compiled expression cache retains JIT-generated code, a query result cache memoises full results, and the engine otherwise relies on the operating system page cache instead of maintaining its own buffer pool.

Concurrency & Consistency

–

Concurrency is part-centric: each INSERT writes one immutable data part atomically with no row-level transactions, ALTER TABLE mutations are asynchronous rewrites with eventual consistency and no undo log, readers and writers never block each other thanks to immutable parts swapped via atomic pointers, DDL takes coarse table locks with no row or gap locks, and inserted blocks are deduplicated by content hash so retries are idempotent and ReplicatedMergeTree drops duplicate replicated blocks automatically.

Recovery & Data Integrity

–

Each data part carries a checksum manifest to detect corruption, small inserts can be protected by a write-ahead log to survive in-memory buffer loss, ReplicatedMergeTree recovers missing parts by syncing from healthy replicas through ZooKeeper or Keeper, immutable parts and merge-to-new-part semantics avoid partial writes without needing a double-write buffer, and BACKUP and RESTORE statements introduced in 22.x support incremental backups.

Materialized Views

Materialized View Types

Materialized views come in two flavours: incremental views are triggered on INSERT so new rows flow continuously into a backing MergeTree-family table for real-time pre-aggregation, while refreshable views perform full periodic recomputation under a REFRESH schedule.

Materialized Views

–

Materialized views may be chained so the output of one view feeds another, building multi-stage pre-aggregation pipelines.

Process Architecture

Threading Model / Background Thread Pools

Dedicated background pools handle merging of data parts, executing mutations, fetching parts from replicas, and moving parts between storage volumes.

Process Architecture

Connection Handling

Clients connect over the high-performance native TCP protocol, a RESTful HTTP interface, gRPC, and wire-protocol shims that emulate MySQL and PostgreSQL clients.

Access Control & Security

Authentication

Authentication accepts password hashes such as SHA256, double SHA1 and bcrypt, integrates with LDAP and Kerberos, and supports SSL client certificates.

Access Control & Security

Authorization

Authorization layers role-based access control, per-row policies for row-level security, quotas that cap query frequency and resource usage, and reusable settings profiles.

Access Control & Security

Encryption

Encryption covers SSL and TLS for transport and an Encrypted column codec for at-rest protection of selected columns.

External Integrations

Streaming Sources

Streaming integrations consume from Kafka, RabbitMQ and NATS through dedicated table engines that materialise messages into ClickHouse tables.

External Integrations

Object Storage

Object storage integrations read and write S3 with a queue-based variant for continuous ingestion, Azure Blob Storage, and HDFS.

External Integrations

Database Engines

Database-level engines mount entire remote schemas, mapping a remote MySQL, PostgreSQL or SQLite database as a local ClickHouse database.

External Integrations

Table Functions

Ad-hoc table functions query remote ClickHouse clusters via remote and remoteSecure, hit external systems through mysql, postgresql, jdbc and odbc, and read files directly from S3, URLs or the local filesystem.

Administrative Syntax

Administrative grammar includes TiDB-specific ADMIN statements, SET and SHOW for variables, ANALYZE TABLE to refresh statistics, SPLIT REGION for manual Region pre-splitting, RESOURCE GROUP management, and CALIBRATE RESOURCE for capacity calibration.

Query Processing

–

Semantic analysis resolves names against the InfoSchema, infers types, and pre-processes expressions before logical planning, ensuring identifiers, columns and function signatures are bound prior to optimization.

Query Processing

Optimizer / Logical Optimization

Logical rewrites include column pruning, predicate push-down, aggregation push-down, join reorder, subquery decorrelation, partition pruning, outer-join elimination, and projection elimination, each applied as a transformation on the logical plan tree.

Query Processing

Optimizer / Physical Optimization

Physical optimization estimates cost from collected statistics, picks Root, Coprocessor or MPP task placement, prunes index candidates by Skyline comparison across multiple dimensions, and finally chooses an access path balancing scan cost and index utility.

Query Processing

Optimizer / Statistics

Statistics combine equi-depth histograms for range estimation, Count-Min Sketch for point-query frequency, FM-Sketch for distinct value counts (NDV), and Top-N tracking of high-frequency values, with a background Auto Analyze loop refreshing them as data shifts.

Query Processing

Execution Engine / Join Operators

Joins are realized as Hash Join as the default in-memory algorithm, Index Join (index nested loop) when an inner index can be probed per outer row, and Merge Join when both inputs arrive sorted on the join key.

Query Processing

Execution Engine / Scan Operators

Scans include full table scan, secondary index scan, index range scan bounded by computed ranges, and a Point Get fast path that bypasses the iterator stack for single-row lookups by primary key or unique index.

Query Processing

Execution Engine / Aggregate

Aggregation is performed either by Hash Aggregate, which builds a hash table keyed on the grouping columns, or Stream Aggregate, which exploits sorted input to emit groups incrementally with constant memory.

Query Processing

Distributed Execution / MPP Execution

For TiFlash-backed analytical workloads TiDB runs an MPP engine using shuffle exchanges to repartition data, broadcast joins for small build sides, and shuffle hash joins when both sides need hash repartitioning across compute nodes.

Storage Interface

KV Interface

TiDB talks to TiKV through a transactional KV API exposing Get, BatchGet and Scan for reads and Set and Delete for mutations, with all higher-level table and index operations expressed as compositions of these primitives.

Storage Interface

–

A key-encoding layer maps tables and indexes onto KV pairs: row data is encoded as a tablePrefix/tableID/recordPrefixSep/rowID key bound to the row payload, and each secondary index becomes its own tablePrefix/tableID/indexPrefixSep/indexID/indexValues key pointing back to the rowID. A Region cache on the SQL layer remembers which TiKV node currently serves each Region so requests can be routed without consulting PD on every call.

Indexing

Index Types

Indexes include the primary key (clustered or non-clustered), secondary indexes encoded as separate KV pairs in TiKV, unique indexes that constrain the indexed values, expression indexes over computed expressions, invisible indexes hidden from the optimizer for safe rollout, and multi-valued indexes that index elements of JSON arrays.

Indexing

Index Organization

A clustered index, default since 5.0, stores row data directly under the primary key so the row is co-located with its PK; a non-clustered table instead allocates an internal _tidb_rowid as the heap address and the primary key becomes an ordinary unique index pointing to it.

Indexing

Index Selection & Range Analysis

Index selection uses Skyline Pruning to discard candidate indexes dominated on every dimension (covering, equal-prefix length, scan order), and a range builder converts WHERE predicates into the disjoint key intervals that the chosen index must scan.

Transaction Coordination

Transaction Model

Distributed transactions follow the Google Percolator design: a Prewrite phase places primary and secondary locks on participating keys and a Commit phase marks them committed once the primary succeeds, with the protocol implemented client-side via the TiKV client library.

Transaction Coordination

Locking Mode / Pessimistic Locking

Pessimistic transactions take row locks during execution like MySQL InnoDB; Fair Locking arranges waiters in a queue so the longest-waiting request is granted next, reducing starvation under contention.

Transaction Coordination

Isolation Levels

Read Committed reads the latest committed value per statement, Repeatable Read takes a single MVCC snapshot at transaction start which behaves as Snapshot Isolation, and Serializable is accepted as a syntax-compatible alias rather than a separate enforcement mechanism.

Transaction Coordination

–

Every transaction obtains start and commit timestamps from the Timestamp Oracle hosted by PD, which hands out globally monotonic TSOs that order all reads and writes across the cluster.

Transaction Coordination

Transaction Features

Optional features include Savepoint for partial rollback, Lazy Uniqueness Check that batches uniqueness verification to commit, Async Commit which returns success once Prewrite completes to cut latency, and 1PC which collapses Prewrite and Commit when all keys live in a single Region.

DDL

Online DDL Framework

Online DDL implements the F1 multi-state schema-change protocol, advancing the cluster through compatible intermediate schema versions; pending changes go through a job queue scheduled by a single elected DDL Owner so that exactly one node drives state transitions at a time.

DDL

DDL Operations

Supported operations include adding and dropping columns, building indexes via distributed parallel backfill, modifying column types, renaming and truncating tables, and DDL over partitioned tables such as adding, dropping and reorganising partitions.

DDL

Fast DDL

Fast DDL accelerates index creation by ingesting pre-sorted SST files directly into TiKV instead of issuing per-row writes, and by running the backfill phase using a Lightning-style parallel worker pool.

DDL

–

Multi-Schema Change lets a single ALTER TABLE statement bundle several column or index modifications, executing them under one schema version transition rather than as separate DDL jobs.

Session & Connection

–

The frontend speaks the MySQL wire protocol so unmodified MySQL clients connect directly, with optional SSL/TLS encryption negotiated during the handshake.

Session & Connection

Session Management

Sessions expose MySQL-compatible system variables augmented with TiDB-specific ones, support Prepared Statements with parameter binding and plan caching, and accept multi-statement requests in a single round-trip.

Session & Connection

Authentication

Authentication plugins include the legacy mysql_native_password challenge-response, caching_sha2_password, an auth_token mechanism for token-based logins, and LDAP-backed verification against an external directory.

Session & Connection

Authorization

Authorization is role-based: privileges are granted to roles that users assume, and a set of dynamic privileges names cluster-level capabilities (such as backup or system management) that can be delegated independently of the static MySQL grant table.

Catalog & Metadata

InfoSchema

Two InfoSchema implementations coexist: V1 loads the entire schema snapshot into memory at startup and on each version bump, while V2 fetches and caches schema objects on demand to bound memory use on clusters with very many tables.

Catalog & Metadata

–

Table, column and index metadata is encoded as KV pairs and stored inside TiKV itself rather than in a separate catalog store, with read/write helpers managing the encoding; INFORMATION_SCHEMA exposes MySQL-compatible introspection views and the mysql.* system tables hold users, privileges and persisted statistics.

Resource Management

Resource Control / Resource Group

Resource Groups meter consumption in a unified Request Unit (RU) that combines CPU, IO and network costs, prioritise traffic as HIGH, MEDIUM or LOW, allow burstable groups to exceed quota when capacity is idle, and apply Runaway Query Management to tag, throttle or kill queries that overrun their budget.

Resource Management

Memory Management

A per-query Memory Tracker accumulates allocations across operators; when the limit is exceeded a configurable OOM Action either cancels the query or triggers Disk Spill, allowing Sort and Hash Join operators to spill intermediate state to local files and continue executing.

Resource Management

–

A temporary file manager owns the on-disk scratch space used by sort, aggregation and other spillable operators, handling allocation, cleanup on query end and bounding aggregate disk usage across concurrent queries.

TTL

TTL Framework

TTL is implemented as a background framework with a job scheduler that periodically launches expiry jobs per TTL-enabled table, scan-and-delete workers that locate expired rows and remove them in batches, and integration with partitioned tables so whole expired partitions can be dropped instead of row-by-row deletion.

CDC & Data Replication

–

TiDB itself only exposes the change-event interface; the actual change-data-capture pipeline runs as the separately deployed TiCDC component, while legacy MySQL Binlog compatibility was provided by the Pump/Drainer pair, which is now largely superseded by TiCDC.

Extensibility

Plugin System

A plugin interface allows loadable Audit plugins that observe statements and connections, and Authentication plugins that introduce custom credential validation alongside the built-in handshake methods.

Extensibility

–

A lightweight Extension Framework lets operators register custom scalar functions and session hooks without forking the server, and a Coprocessor Cache memoises Coprocessor request results so repeated pushed-down sub-queries can be served from cache rather than re-executed in TiKV.

Query Processing

Execution Engines / Row-Oriented Engine / Join Operators

DistSQL

KV Layer

–

KV Layer

Range Management / Allocator

KV Layer

Lease Management

Epoch-based Leases bind validity to a node liveness epoch so leases stay cheap to renew while the holder is alive, Expiration-based Leases use a wall-clock expiration for the meta and system Ranges, and Lease Transfers hand the leaseholder role to peers when the allocator needs to balance load.

Consensus & Replication

Raft Consensus

Each Range runs a Raft group with Leader Election, Log Replication that durably commits writes once a majority acknowledges, Snapshot transfer to bootstrap new or far-behind followers, Joint Consensus for safe membership changes, and Pre-Vote to suppress disruptive elections during transient partitions.

Consensus & Replication

Replica Management

Maintains a default Replication Factor of three voting replicas per Range, uses Learner Replicas as non-voting catch-up targets during rebalancing, and supports Non-Voting Replicas placed in remote regions to serve follower reads without contributing to quorum.

Distributed Transactions

Transaction Protocol

Writes deposit Intent markers visible alongside committed MVCC versions, a Transaction Record stored on the coordinator’s Range tracks pending/committed/aborted state, Parallel Commits acknowledge the client once intents and the staging record reach consensus, and Transaction Pipelining lets later writes proceed without waiting for prior writes to fully replicate.

Distributed Transactions

Timestamp Management

An HLC combines physical wall-clock time with a logical counter to produce monotonic causally consistent timestamps, the Timestamp Cache records the highest read time per key span to detect write-after-read conflicts, and Closed Timestamps publish a horizon below which no new writes will appear so follower reads are safe.

Distributed Transactions

Isolation Levels

Defaults to Serializable isolation enforced through timestamp ordering and conflict detection, with Read Committed added in later versions for workloads that prefer fewer retries at the cost of weaker guarantees.

Concurrency Control

–

A Concurrency Manager coordinates incoming requests, the Latch Manager grants short-lived span latches that serialise overlapping requests during execution, distributed Deadlock Detection inspects waits-for graphs across nodes, and a Transaction Wait Queue parks conflicting transactions until the blocking transaction commits or aborts.

Concurrency Control

Lock Table

The lock table tracks Exclusive Locks acquired by writers, Shared Locks for SELECT FOR SHARE, and Intent Locks materialized from MVCC intents so distributed lock state is reconstructed from the same versioned data the storage engine already holds.

Recovery & WAL

–

Durability comes primarily from the Raft Log acting as a replicated write-ahead log so a write is recoverable once a quorum has persisted it, supplemented by Pebble’s local WAL that protects MemTable contents between flushes, and Snapshot Recovery brings far-behind or fresh replicas up to date by streaming a Raft snapshot of the Range.

Backup & Restore

BACKUP / RESTORE

The BACKUP statement produces a Full Backup of all targeted spans and Incremental Backups derived from MVCC timestamp ranges since the prior backup, writing artefacts into Cloud Storage destinations such as S3, GCS, or Azure Blob.

Backup & Restore

–

Change Data Capture

Changefeeds / Sink Types

–

Distributed Transactions

Transaction Management

Distributed writes follow an intent-based protocol that first stages provisional records as intents in each Tablet’s dedicated Intent RocksDB instance, while a Transaction Status Tablet authoritatively tracks each transaction as pending, committed, or aborted.

Distributed Transactions

MVCC

Multi-version concurrency uses HybridTime, a globally ordered hybrid logical clock timestamp combining physical and logical components, together with a Safe Time barrier that fixes a consistent read point across replicas.

Distributed Transactions

Isolation Levels

YSQL offers Snapshot Isolation as the default, Serializable isolation enforced through conflict detection on read and write sets, and Read Committed semantics matching PostgreSQL behaviour.

Distributed Transactions

–

A distributed deadlock detector builds the wait-for graph across TServers to break cycles among contending transactions, and Savepoint statements are supported so YSQL clients can roll back to intermediate transaction points.

Cluster Architecture

Master Server

The Master process hosts the Catalog Manager for table, index, and namespace metadata, a Placement Policy engine for multi-region and multi-AZ replica rules, a Tablet Split Manager that triggers automatic splits, a Load Balancer that migrates Tablet replicas across TServers, and Master HA via its own Raft group.

Cluster Architecture

TServer

Each TServer serves local Tablet read and write requests, embeds a PostgreSQL backend process for YSQL clients, exposes a Backup Service for snapshot operations, and performs Remote Bootstrap to copy Tablet data when new replicas join.

Memory Management

–

Memory is partitioned among the RocksDB Block Cache for SSTable data with LRU eviction, the RocksDB MemTable as a flushable write buffer, PostgreSQL Shared Buffers playing a limited role under YSQL since most caching lives in DocDB, and Per-Tablet memory accounting that bounds resource usage per shard.

Recovery & Durability

–

Durability layers a per-Raft-group WAL that guarantees committed entries survive crashes, the underlying RocksDB WAL for storage-level recovery, Crash Recovery that replays Raft logs and reopens RocksDB to restore Tablet consistency, Snapshot and Restore at cluster or table granularity with Point-in-Time Recovery, and a Backup pipeline for distributed backup and restore.

Networking & RPC

–

Inter-node and Master-TServer communication runs over a custom Protobuf-based RPC framework with asynchronous I/O, and SSL or TLS can be enabled for both peer traffic and client connections.

Networking & RPC

Connection Pooler

Odyssey is bundled as a built-in connection pooler in front of the YSQL endpoint to multiplex many short-lived client sessions onto a smaller backend pool.

Networking & RPC

Client Protocols

Clients connect via the PostgreSQL wire protocol for YSQL, the Cassandra CQL binary protocol for YCQL, and the Redis protocol for the legacy key-value API, allowing reuse of existing ecosystem drivers.

Networking & RPC

Authentication

Authentication methods include Password credentials, LDAP integration with directory services, Kerberos for enterprise SSO, and Certificate-based mutual TLS for service-to-service trust.

Networking & RPC

Authorization

Authorization is enforced through YSQL RBAC, which inherits the PostgreSQL role and privilege model, and YCQL RBAC, which implements Cassandra-style permission grants on keyspaces and tables.

Security

–

Security features include Encryption at Rest using AES-256 over data files, Encryption in Transit via TLS for both node-to-node and client-to-node channels, and Row-Level Security in YSQL inherited from PostgreSQL row policies.

Observability & Administration

–

Operators interact through Admin UIs hosted on the Master and TServer web ports, scrape Prometheus-formatted Metrics for monitoring, and inspect System Catalog Tables surfaced as PostgreSQL system catalogs under YSQL and Cassandra-style System tables under YCQL.
