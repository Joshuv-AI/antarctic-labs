 ABSTRACT
Kokkos, a C++ library focused on performance portability, requires a build system that can work with a
variety of compilers and hardware. Ideally, users need only select the compiler and architecture and should
not have to know or specify how programs using Kokkos are built. CMake can be used to create a flexible,
robust build system and automatically configures compilers and settings based on the user’s inputs. Nev-
ertheless, Kokkos’ requirements as a performance portability library for the build system exceed CMake’s
current capabilities. This report describes the requirements, solutions, and testing of various implementa-
tions to create a CMake-based build system suitable for Kokkos. It compares the strengths and shortcom-
ings of the approaches and evaluates the implementations with respect to the requirements. Because no
solution was found to meet all of the requirements, the Kokkos team engaged with the CMake develop-
ment team to discuss and plan a path toward support for performance-portable build systems in CMake in
the future.

 1. PROBLEMS WITH THE CURRENT BUILD SYSTEM
Kokkos is a C++ library that leverages a machine model to allow downstream users to map their code onto
different parallel accelerators like Central Processing Units, Graphics Processing Units, etc. In this con-
text, the machine model defines the set of memory operations and parallel patterns (e.g. parallel_for ,
parallel_reduce) and Kokkos implements these abstract operations in different programming models
that the vendors of the hardware supply. By doing this, Kokkos allows users to target different hardware
efficiently without having to change their source code. To do this, Kokkos requires users to select a "back-
end" (e.g. CUDA, HIP, SYCL, etc.) and the architecture of the targeted hardware. Additionally, Kokkos
supplies users with a CMake-based build system that facilitates compiling code on different backends tar-
geting different hardware. Therefore, Kokkos supplies users with a complete package for creating perfor-
mance portable applications.
Unfortunately, the current state of the build system still requires users to have some detailed knowledge
about compiler compatibility in order to compile their applications.
Problem 1: The (user selected) compiler needs to fulfill non-trivial requirements
in order to compile a valid Kokkos application.
Problem 2: CMake’s notion of programming languages (partially) conflicts with
having a single source (as Kokkos is using) for multiple languages.
This report describes different ways of redesigning Kokkos’ build system in order to remove this burden
from the users and streamline the building process. The root cause for the formulated abstract problem
statements will be translated into requirements in Section 2. These requirements have to be fulfilled while
adhering to the user interface specified in Section 3. Section 4 describes various approaches to solve the
problem, which are evaluated in Section 5 with respect to the requirements. At last, Appendix A describes
how the chosen approach is tested.

 2. TECHNICAL REQUIREMENTS TO A PORTABLE BUILD SYSTEM
In general, Kokkos is compiled and linked into a downstream application. While building the downstream
application, there are several mechanisms that impose requirements on the build system. This Section de-
scribes the resulting problems and implied requirements on the build system.

2.1 TEMPLATE INSTANTIATION
Kokkos allows users to write their custom workload in form of a functor or C++ lambda and pass it to
Kokkos’ parallel patterns. The parallel patterns in Kokkos are C++ templates that create a template instan-
tiation of the workload for the target hardware. This allows the compiler to introspect and subsequently
optimize the workload for the hardware architecture and allows the user to write reusable, modern C++
code. Nevertheless, the design choice to use templates down to the kernel that gets executed on the tar-
geted hardware introduces implicit requirements on the build system.

To the user, Kokkos looks and behaves like a conventional C++ library independent of which hardware is
targeted by the machine model. Nevertheless, the Application Programming Interface of Kokkos consists
to a large part of C++ templates with a few conventional functions and objects. For performance reasons,
the C++ templates are specific to every backend. This allows the use of backend-specific performance en-
hancements (e.g. SIMD types, loop orders, use of shared resources, etc.). Thus the templates in Kokkos’
public Application Programming Interface depend on the backend and architecture targeted. When detect-
ing a call to a Kokkos template in user code, the compiler instantiates the corresponding function or ob-
ject from the template. Since templates are instantiated by the translation unit that compiles the source in
which the template is used, the compiler that translates this source file needs to be able to create the tem-
plate instantiation for the respective backend and architecture.
Technical requirement 1: The compiler needs to be able to instantiate the used
templates for the targeted architecture.

2.2 LINKING OF LIBRARY AND RUNTIME
Parts of Kokkos’ API are conventional functions and objects that are precompiled into a library and linked
into the final application. Therefore, the used linker has to be able to link the precompiled library and the
downstream application code, which requires that the library and the instantiated templates are compatible.
Furthermore, the appropriate runtime for the selected backend has to be linked into the application. One

 2

compiler that fulfills these requirements is the compiler that was used to compile the Kokkos library. It will
be called Kokkos-compiler in this text.
Large software libraries that use Kokkos can have parts that do not compile with the Kokkos-compiler.
This is fine as long as the resulting binary objects produced by the used compilers are Application Binary
Interface compatible and the correct runtime libraries for the Kokkos backend are included.
Technical requirement 2: The library and the instantiated templates have to be
compatible.
Technical requirement 3: The runtime needs to be included in the final application
binary.

2.3 IN-TREE VS. INSTALLED BUILDS
There are various ways to integrate Kokkos into a downstream project. This document will only reference
two categories, ”in-tree” and ”installed” builds.
”in-tree” builds refer to having Kokkos’ source code saved inside the CMake file tree of the project and
Kokkos gets built as part of the application. There are various ways to establish an ”in-tree” situation:
Users can download and put Kokkos inside their project and add the directory to their main CMake file
via CMake’s add_subdirectory. Another way to build Kokkos ”in-tree” is via CMake’s FetchContent,
which takes care of the download and including it as subdirectory in the project.
The advantage of ”in-tree” builds is that all parts of Kokkos that are needed are compiled as part of the
project. As CMake only uses one toolchain (compiler and linker) per language, Kokkos and the down-
stream project are guaranteed to be compatible. Given this, ”in-tree” builds use the Kokkos-compiler.
Kokkos’ build system needs to support this build type.
Technical requirement 4: The build system has to support Kokkos being a subproject.
In contrast to ”in-tree”, downstream projects can be built against an ”installed” Kokkos. In this case, Kokkos
gets compiled as a standalone project and the resulting library, headers, and CMake files are copied to an
install location. A downstream application using this installation imports the installed CMake files into
its own project via CMake’s find_package(Kokkos). In this case Kokkos and the downstream applica-
tion can use two different CMake toolchains. Therefore, it cannot be guaranteed per se that the previously
compiled library and the template instantiations are compatible. Even if the used toolchains produce code
with compatible Application Binary Interface, differences might exists because Kokkos’ souce code con-
tains preprocessor #ifdef conditionals on the compiler, backend, and architecture. In contrast to backend
and architecture, which get checked when find_package(Kokkos) is called, there is no warning about
the current toolchain (especially the used compiler) differing from the one used for compiling the installed
Kokkos.
Technical requirement 5: If a Kokkos library is used with a different toolchain than
the one it was built with, the selected paths (#ifdef) have to form valid code.

2.4 USAGE IN MULTIPLE CMAKE LANGUAGES
CMake has the notion of languages. Apart from CXX, the languages CUDA and HIP are available and can
be mapped to backends in Kokkos. As of version 4.7 Kokkos allows to be used only in one language. This
avoids having to define settings for multiple languages, but also unnecessarily restricts a Kokkos installa-
tion.

 3

For the HIP and CUDA backend, Kokkos should be usable in both CXX and HIP or CUDA respectively. This
allows larger downstream projects to use a mix of libraries in multiple languages in different subprojects
with one installed version of Kokkos. Furthermore, it facilitates interoperability of raw HIP and CUDA code
with Kokkos functions within single files.
As CMake allows one toolchain per language, making Kokkos multi-language capable introduces more
requirements. For a single Kokkos installation to support multiple languages it has to be ensured that all
previously stated requirements are met by all toolchains that Kokkos is used with.
Technical requirement 6: In multi-language builds all previous requirements have
to be met by all used toolchains.

 3. USER INTERFACE OF A PORTABLE BUILD SYSTEM FOR KOKKOS
Kokkos tries to abstract intricacies of hardware and the corresponding software stack into generalized pat-
terns to make it easy for users. The same abstraction level should also hold for the build system. This leads
to the following requirements from a user’s perspective:
 • Kokkos should look like any conventional C++ library
 • Users should not have to set or know backend-specific information when using a Kokkos library
 • Users should not need to set different compilers themselves
 • Using Kokkos should not require users to change the file endings of their code
 • Users should not have to call a CMake function for source files that use Kokkos
 • Users should be able to mix Kokkos and raw code (given the backend is compatible, e.g. mixing
 CUDA code with Kokkos’ CUDA backend)
 • Only files that need to be compiled with a Kokkos-compatible compiler should be forced to use it.
These requirements were gathered by a survey of the Kokkos developers, asking about what the users they
interact with are asking for in an informal setting. Although not perfect, this survey is considered sufficient
for the scope of the report.

 4. APPROACHES FOR CREATING A ROBUST, PORTABLE BUILD SYSTEM
Creating a build system that fulfills the technical and user requirements and works in a portable way is dif-
ficult. Furthermore, CMake’s interpretation of file endings as language specification is problematic. Since
the source and header files in Kokkos are named .cpp and .hpp, CMake automatically associates them
with the CXX language and wants to use the user provided toolchain for that language. In an ”in-tree” build
that toolchain is checked when building the Kokkos subdirectory. But when using an ”installed” Kokkos,
the toolchain given for CXX might not fulfill the requirements. Nevertheless, the toolchain for another lan-
guage like CUDA or HIP might, but due to the file endings CMake does not use it.
Therefore, the build system needs a way to redirect what toolchain to use for source files that use Kokkos
code. Unfortunately, CMake does currently not provide an intrinsic way to do that, except either setting
the toolchain for CXX to a Kokkos compatible one (e.g. the one that was used to compile Kokkos itself if
an ”installed” Kokkos is used), renaming the source files to have the appropriate ending, or specifying for
each individual target and source file what language and architecture should be used.
Since none of these solutions are feasible in large software projects or require unreasonable amounts of
user interaction, Kokkos should provide an automated way to ensure the technical requirements are met
while fulfilling as many of the user requirements as possible. This Section describes different approaches
to achieve this.

4.1 USING A LAUNCHER SCRIPT
One approach to solving both problems listed in Section 1 consists of Kokkos providing a script that gets
used with CMake’s RULE_LAUNCH_COMPILE and RULE_LAUNCH_LINK. It acts like a compiler and linker
launcher and gets invoked with the CMake generated compiler and linker call. The script can redirect the
call to whatever it was configured to (both for ”in-tree” and ”installed”) by the Kokkos library. This is sim-
ilar to hipcc provided by Advanced Micro Devices.
Kokkos already includes such a script named kokkos_launch_compiler that takes 3 arguments. The
first argument is the Kokkos-compiler. The second argument is the compiler that should be redirected to
the Kokkos-compiler. The third argument is the compile command generated by CMake. For the launcher
script to swap the compiler with the Kokkos-compiler, two conditions have to be met. First, the third ar-
gument to the script needs to contain the second argument. Second, the compile command contains the
option KOKKOS_DEPENDENCE. If both are met, the launcher script swaps the compiler and executes the
resulting command. If the conditions are not met, the original compile command will be executed. The
KOKKOS_DEPENDENCE option is defined for all applications linking to Kokkos.

4.2 IMPLEMENTING KOKKOS AS A CMAKE LANGUAGE
Another approach consists of defining a new language in CMake. This can be done via creating the appro-
priate CMake files that set the toolchain, associate certain file endings with the language, and define values
for compiler and linker precedence over competing languages. As soon as a language is active, CMake
will automatically use the toolchain associated with that language on all files with the language associated
file endings.
Nevertheless, in the case of Kokkos, the newly implemented CMake language does not represent a distinct
language but forwards to the native CMake languages CXX, CUDA, or HIP depending on the backend. This
approach allows Kokkos to implement the non-trivial requirements on the toolchain in the files defining
Kokkos as a CMake language, allowing to solve both problems listed in Section 1.

 6

4.3 DEFERRED TRAVERSAL OF THE TARGET TREE
The third solution discussed in this report is a deferred traversal of the tree of targets in a project. This
traversal function is called after all subdirectories in the project have been scanned by CMake (thus ”de-
ferred”). At the time of execution, all targets that are part of the project have been defined and all settings
are available for modification.
During the traversal the target and file properties are modified or set to allow compiling the project in a
Kokkos-conforming way. As the traversal function is supplied by Kokkos, this approach allows Kokkos
to set the toolchain and add properties to files and targets as required. Thereby, this approach solves both
problems defined in Section 1.

5.1 RATIONALE FOR REJECTING
Both implementing Kokkos as a CMake language and the deferred traversal were rejected as solutions.
The following Section gives detailed reasoning for this decision and highlights particular roadblocks that
were encountered.

IMPLEMENTING KOKKOS AS CMAKE LANGUAGE
Implementing Kokkos as a CMake language was rejected for several reasons. First and foremost, this
approach was found to be especially invasive in CMake’s internal handling of languages. When CMake
parses a project, it expects languages to be enabled at the project’s top level. As the Kokkos CMake lan-
guage is only available after find_package(Kokkos) is executed, this implies that Kokkos has to be in-
cluded at the project’s top level. For larger software packages this might be a very restrictive requirement.
Furthermore, as the Kokkos CMake language mimics another CMake language depending on the backend,
this language needs to be enabled previously. This would implicitly rely on a project enabling all the lan-
guages Kokkos needs before being found as a package. Although this might not be a problem in practice, it
nevertheless is in violation of CMake’s notion of languages.
CMake uses generator expressions to express different options a library adds to the compile command.
These expressions allow to setting options depending on the language a library is compiled in. With Kokkos

 8

as a CMake language, these generator expressions would need to be adapted to work. While this is simple
for Kokkos itself, this also applies to third party libraries that users want to combine with Kokkos in their
application. Therefore, a modification of the generator expressions is required which currently is not sup-
ported in CMake and would need to be implemented.
Another argument against using this approach is, that it requires users to rename all their files once to use
the file ending that is associated with Kokkos. Although, this can be seen as a one time change, it also is
likely to break a lot of syntax highlighting and convenience functionality in editors and development envi-
ronments.
Due to the various drawbacks, this approach was not developed past than an early concept phase and was
not verified using the test in Section A.

DEFERRED TRAVERSAL OF THE TARGET TREE
Although the deferred traversal approach is the only one fulfilling all requirements at least partially, it was
rejected. The main reason for that is the amount of implementation and testing necessary to support this
approach. This adds significant workload to the development team.
While traversing the target tree, the approach sets the language and architecture on targets and source files
that link to Kokkos. Unfortunately, this creates problems for multi-language builds. As targets can only
be associated with one language, the target traversal has to decide which CMake language to assign to a
target. This can give rise to special cases that would need to be correctly processed to allow a project to be
built. Since Kokkos controls the traversal, the handling of the special cases needs to be done in functions
written and maintained by the Kokkos development team. This adds more workload to the development
team.
Furthermore, CMake evaluates the generator expressions to generate the build instructions after the con-
figuration stage is finished. This implies, that within the CMake configure stage, the generator expressions
cannot be evaluated or modified as information is missing (which gets added at the end when the actual
build commands are executed). Therefore, if another library in an application uses generator expressions
to set e.g. compiler flags for CXX, these will be disregarded when Kokkos sets the compile language for
a target to CUDA or HIP. This can potentially limit the libraries that can be used together with Kokkos in
downstream applications. Nevertheless, this would only apply to builds in languages other than CXX.
This approach was fully implemented in PR #7582 and verified using the testing in Appendix A.

5.2 RATIONALE FOR ACCEPTING THE LAUNCHER SCRIPT
Using a launcher script to conditionally forward the CXX calls CMake generates to the compiler Kokkos
was compiled with solves both problems described in 1. If the compiler used by CMake does not fulfill the
Kokkos requirements and a source file uses Kokkos, the command can be redirected. If a file does not use
Kokkos, the script executes the compile command given to it without modification.
Furthermore, all files that use Kokkos can identify as CXX files to CMake. Since the launcher script can
modify the compile command it is given, it can change how the file is compiled after all CMake logic
is run. Furthermore, information from the configure stage of CMake can be injected into the script and
used for decision of what to execute. Since a language in CMake consists of a toolchain and flags, both
of which the script can change, it can circumvent CMake’s notion of languages. This allows to solve the
second problem mentioned in Section 1.
The script mentioned in Section 4 is used as a starting point. As it redirects to the Kokkos-compiler, it ful-
fills all technical requirements apart from multi-language builds. In order to extend the functionality to

 9

include this requirement, Kokkos itself needs to use generator expressions to set the flags it requires for all
languages it supports. This is implemented in PR #8167. After the change the same Kokkos can be used in
CXX and CUDA or HIP (if the appropriate backend is enabled). In order to ease transition and give libraries a
workaround this feature needs to be enabled with Kokkos_ENABLE_MULTIPLE_CMAKE_LANGUAGES.
The launcher script was historically used to automatically forward CXX compile commands to NVCC via
nvcc_wrapper for the CUDA backend. nvcc_wrapper was used by Kokkos to sort the compiler flags into
ones that are known by NVCC and ones that would need special treatment to be forwarded to the host com-
piler. Although this highlights that using a launcher script is already something familiar to Kokkos users,
the proposed approach automates using the launcher if and only if it is needed. This automation is imple-
mented in PR #8168. The full approach was verified with the tests in Section A.
Nevertheless, the approach creates three problems. The first is, that Kokkos uses the CMake-internal func-
tions RULE_LAUNCH_COMPILE and RULE_LAUNCH_LINK to set the launcher script as global compiler and
linker launcher. This could be changed to only setting the launcher script for targets that link to Kokkos via
a deferred traversal. Unfortunately, this puts considerable maintenance load onto the Kokkos develoment
team. Furthermore, setting the launcher globally can be prevented by requiring the separable_compilation
component of Kokkos and setting the launcher for the targets/directories/projects that link to Kokkos via
the kokkos_compilation function in CMake manually.
The second problem is, that the supplied launcher script does not work on Windows. To make the launcher
independent of the operating system, it needs to be implemented in a portable language (e.g. python). The
third problem is, that using a launcher script is not composable. If another library uses the same approach
to set a different launcher, there is no clear precedence of launchers.
The discussion and resulting changes to resolve these problems in CMake are described in the next Sec-
tion.

5.3 FUTURE CHANGES IN CMAKE
The two implemented solutions (Deferred traversal of the target tree, Launcher script) were discussed with
Kokkos users in the Trilinos project. In order to resolve the build problems the Kokkos team discussed
funding the implementation of a transient way to set target and file properties in CMake with represen-
tatives from the Trilabs. In a following meeting with CMake developers, the Kokkos team presented the
faced problems and the implemented solutions. The meeting concluded with CMake promising ot imple-
ment a operating-system-independent launcher following the model of Kokkos’ kokkos_launch_compiler.
Furthermore, using a compiler and linker launcher will be made a transient property of CMake targets.
This allows Kokkos to not rely on the CMake-internal functions RULE_LAUNCH_COMPILE and
RULE_LAUNCH_LINK. The correspondence of the meeting is archived in NNSA Tri-lab CMake and CMake
gitlab.
With the required changes implemented in CMake, the tests developed in this report can be used to ensure
the transient setting of a launcher script is working correctly.

 6. SUMMARY AND CONCLUSION
This report describes the updates to Kokkos’ build system with the goal of reducing the build complex-
ity of performance portable software. Two central problems were identified and three different solutions
to these problem were discussed. The approaches were evaluated with respect to technical and user re-
quirements and two were implemented. The implementations were verified by extensive testing and finally
discussed with Trilinos and CMake developers.
This resulted in the decision to use a launcher script to redirect compile commands issued by CMake to a
compiler that fulfills Kokkos’ requirements. This approach allows to work around CMake’s limitations in
performance portable code like Kokkos and downstream applications. Furthermore, it requires minimal
knowledge from the user and allows Kokkos to be used in software projects with multiple languages and
compiler restrictions.
By implementing a transitive way of passing this launcher script to libraries and applications that link
to Kokkos in CMake, the developed solution is available for other performance portable software like
NVIDIA Thrust.
Apart from this reduction in build system complexity for users, the investigation highlighted two areas
where Kokkos could reduce its restrictions imposed on the compiler and linker.
First, Kokkos’ source code uses #ifdef on the used compiler version. If this is used in non-header source
files, the produced library is compiler specific. Kokkos should avoid to be compiler specific by removing
#ifdef on compilers in non-header source files.
Second, Kokkos source code uses #ifdef on the architecture e.g. in atomics. Just like for the compiler,
this produces architecure specific libraries. Kokkos should avoid to be architecture specific in non-header
source files, or use code that works on all specified architectures.

 APPENDIX A. TESTING THE NEW BUILD SYSTEM
To verify a new build strategy, it needs to be able to accurately set the compiler and linker and respec-
tive flags independent of how deep Kokkos is inside the library dependency tree of a software project.
Therefore, an induction based verification was chosen. If a build strategy is able to correctly handle an
executable with a direct dependency on Kokkos (n = 0), an executable with a dependency on a library
with a direct dependency on Kokkos (n = 1), and an executable with a dependency on a library with a de-
pendency on a library with a direct dependency on Kokkos (n = 3), and does not include a limit on the
dependency depth it can handle, induction indicates the build strategy works for any depth of depdendency.
Therefore, a hierarchy of interdependent libraries mixing Kokkos and non-Kokkos code was developed.
Each library has either a t=PRIVATE, t=PUBLIC, or t=INTERFACE dependency on Kokkos or a library with
a respective dependency on Kokkos. This hierarchy spans all combinations of depdendency depth n and
dependency type t.
The tests are contained in PR #8140. But have not been merged as Kokkos currently still sets the launcher
script globally until CMake merges the implementation described in Section 5.3. The reasoning behind
this decision is, that a global setting does not need to be tested by us but by CMake and we can reduce the
maintenance burden of the Kokkos developers.
