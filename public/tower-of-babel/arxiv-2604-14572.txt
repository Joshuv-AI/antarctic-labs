Don’t Retrieve, Navigate: Distilling Enterprise Knowledge into Navigable Agent Skills for QA and RAG


Abstract
Retrieval-Augmented Generation (RAG) grounds LLM responses in external evidence but treats the model as a passive consumer of search results: it never sees how the corpus is organized or what it has not yet retrieved, limiting its ability to backtrack or combine scattered evidence. We present Corpus2Skill , which distills a document corpus into a hierarchical skill directory offline and lets an LLM agent navigate it at serve time. The compilation pipeline iteratively clusters documents, generates LLM-written summaries at each level, and materializes the result as a tree of navigable skill files. At serve time, the agent receives a bird’s-eye view of the corpus, drills into topic branches via progressively finer summaries, and retrieves full documents by ID. Because the hierarchy is explicitly visible, the agent can reason about where to look, backtrack from unproductive paths, and combine evidence across branches. On WixQA, an enterprise customer-support benchmark for RAG, Corpus2Skill outperforms dense retrieval, RAPTOR, and agentic RAG baselines across all quality metrics. We further evaluate generalization on nine RAGBench subsets reformulated as retrieval-stress benchmarks: Corpus2Skill attains the highest macro-average F1 across the full 10-dataset suite and characterizes a clear regime — single-domain, atomic-document corpora — where corpus navigation is the right primitive, while flat retrieval remains preferable for open-domain or extractive pools.

Introduction

Figure 1

Enterprise knowledge bases contain thousands of heterogeneous documents: support articles, product guides, policy documents, and FAQs
(
14
)
.
Large language models alone cannot answer questions about these corpora reliably: they lack access to private, frequently updated content and are prone to hallucinating plausible but incorrect details
(
21
;
14
)
.
Retrieval-Augmented Generation
(
21
, RAG;)
was introduced to solve these problems by grounding LLM responses in retrieved evidence.
By embedding the query, fetching similar passages from a vector index, and conditioning the model’s answer on the retrieved context, RAG enables LLMs to leverage enterprise-specific knowledge they were never trained on, providing factual, up-to-date answers while reducing hallucination.
This pipeline has become the dominant paradigm for enterprise QA, customer support, and compliance workflows
(
14
;
40
)
.
Yet it presents a structural limitation for more complex queries:
the LLM never sees the forest for the trees.

Consider a support agent faced with the query “How do I switch my business from sole proprietorship to LLC on Wix?”
This query spans multiple topics: account types, payment provider configuration, and legal entity management, each covered in different sections of the knowledge base.
A flat retrieval system returns the top-
k
passages closest to the query embedding, which are likely to match on surface-level terms (“sole proprietorship,” “LLC”) but miss the operationally critical article explaining that account types cannot be changed directly and require contacting support.
The LLM receives these fragments but has no understanding of how the corpus is organized, what topic areas exist beyond the retrieved set, or whether the best-matching documents were even in the retrieval window.
It cannot reason about where else to look, whether its evidence is complete, or how the retrieved passages relate to the broader knowledge structure.
In short, conventional RAG treats the LLM as a passive consumer of search results, leaving the model’s planning and reasoning capabilities largely unused.

Agentic RAG systems
(
47
;
37
)
partially address this by allowing the LLM to issue multiple search queries iteratively.
But even with tool access, the agent operates without a map: it must guess productive search terms, has no way to survey the corpus structure, and cannot systematically narrow its focus from broad topics to specific documents.
Each search query is a shot in the dark, guided only by the agent’s prior knowledge and whatever fragments previous queries returned.
For the business-type query above, an agentic retrieval system would need to independently discover that the answer involves both the payments ecosystem
and
account verification policies — topics whose connection is not apparent from keyword similarity alone.

Hierarchical approaches such as RAPTOR
(
36
)
and GraphRAG
(
11
)
organize documents into trees or graphs with LLM-generated summaries at internal nodes.
These summaries capture thematic structure that flat embeddings miss.
However, these systems still rely on embedding-based similarity search at query time: RAPTOR indexes all tree nodes in a flat vector store, while GraphRAG requires a graph database and entity extraction pipeline.
The hierarchy enriches the retrieval candidates but remains invisible to the LLM at query time; the model still receives search results without understanding the organizational structure that produced them.
More recent work pushes further: StructRAG
(
22
)
restructures retrieved information into tables or graphs at inference time, and BookRAG
(
45
)
builds hierarchical indices with agent-based planners.
Yet these systems still invoke embedding-based search at query time and do not give the agent direct access to the organizational structure itself.

Meanwhile, a parallel line of work on LLM agent skills
(
44
;
17
)
has shown that agents perform complex tasks more effectively when given structured, reusable knowledge modules that they can selectively load and follow.
Agent platforms now support filesystem-based skill packages
1
1

1

https://docs.anthropic.com/en/docs/agents-and-tools/agent-skills
that the agent discovers via metadata and reads on demand, a mechanism known as progressive disclosure (
Section

2.3
).
This suggests an alternative to retrieval: rather than searching for passages,
distill
the corpus into a navigable skill hierarchy and let the agent explore it.

We propose exactly this: make the hierarchy itself the primary interface for the LLM.
Rather than searching
over
a hierarchy, the agent navigates
through
it.
This is the core idea behind
Corpus2Skill
(
Figure

1
): a one-time offline compilation phase transforms a document corpus into a navigable skill tree, and at serve time, the LLM agent browses this tree to find information, much like a human navigating a well-organized file system or table of contents.

We evaluate
Corpus2Skill
on WixQA
(
6
)
, an enterprise customer-support benchmark designed for evaluating RAG systems over real-world knowledge bases.

Corpus2Skill
achieves the highest quality across all metrics, outperforming flat retrieval, RAPTOR, and a multi-turn agentic RAG system, while requiring no embedding index or vector database at serve time.
We complement this anchor result with a generalization study on nine RAGBench
(
13
)
subsets reformulated as retrieval benchmarks:
Corpus2Skill
attains the highest macro-average F1 over the full ten-dataset benchmark, and the per-dataset dispersion isolates the regime where navigation is the right primitive (single-domain, atomic-document corpora) versus the regime where flat retrieval remains preferable (open-domain abstracts, very long extractive documents).
These results suggest a complementary design point for knowledge-grounded systems: invest computation at compile time to make the corpus
navigable
, rather than solely at query time to make it searchable.

We summarize our contributions as follows.

1.

We identify corpus navigability as an underexplored dimension in current RAG systems: LLMs lack a structured overview of the knowledge base, which limits their ability to systematically locate the best evidence.

2.

We propose
Corpus2Skill
, a compile-then-navigate framework: an offline pipeline transforms a raw corpus into a hierarchical skill directory via iterative clustering and LLM-based summarization, and at serve time an LLM agent navigates this hierarchy through file browsing and document lookup tools, requiring no embedding index or vector database at serve time.

3.

We evaluate on WixQA
(
6
)
against five baselines, conduct ablation studies on hierarchy structure, exploration budget, and serving model choice, and run a 9-subset generalization study on RAGBench
(
13
)
that characterizes which corpus shapes
Corpus2Skill
helps and which it does not.

2
Background: Skills in LLM Agents

2.1
From Tools to Skills

Modern LLM agents interact with external systems through
tools
: atomic, stateless functions such as web search or database queries
(
37
;
47
)
.
Tools give an agent the ability to
act
but do not tell it
how
to approach a complex task.

Agent skills
fill this gap: reusable modules that package procedural knowledge or multi-step workflows into a form the agent can load and follow
(
17
)
.
Unlike a tool, a skill shapes reasoning over multiple steps, persisting across tool calls to guide the agent’s decisions throughout a task.
This distinction is increasingly important as agents tackle longer-horizon tasks where choosing the right sequence of tool calls requires domain-specific strategy, not just tool availability.

Formally,
17
define a skill as a tuple
S=(C,\pi,T,R)
: an applicability condition
C
, an execution policy
\pi
, a termination condition
T
, and a reusable interface
R
.
This distinguishes skills from one-off plans (no reusable interface), episodic memories (no execution policy), and atomic tools (no multi-step structure).

2.2
Skill Representations

Skills take several forms in practice:

•

Code-as-skill.
Voyager
(
44
)
stores successful action sequences as executable functions in a growing library.

•

Natural-language playbooks.
SkillX
(
43
)
and EvoSkill
(
2
)
distill agent experience into structured textual instructions.

•

Filesystem-based packages.
A directory containing a structured instruction file (
SKILL.md
) alongside optional scripts and data assets. This is the pattern adopted by recent agent platforms and the one
Corpus2Skill
builds on.

Code-based skills offer precision but require execution environments; natural-language skills are portable and interpretable at the cost of ambiguity.
Filesystem-based packages balance the two by combining structured text with auxiliary resources that the agent can access on demand.

2.3
Progressive Disclosure

Loading all skill content at startup would overwhelm the context window; loading nothing would leave the agent unable to choose.
The filesystem pattern resolves this via
progressive disclosure

(
39
)
:

1.

Metadata
(at startup): skill name and one-line description (
<
100 tokens each).

2.

Instructions
(on demand): the full
SKILL.md
is read when the agent selects a skill.

3.

Resources
(as needed): supporting files remain on disk, consuming zero tokens until accessed.

The agent thus maintains awareness of many skills while paying the token cost only for those actually used.

2.4
From Procedural Skills to Informational Skills

In prior work, skills encode
how to perform a task
: workflows, decision trees, or code patterns.

Corpus2Skill
repurposes the same mechanism to encode
what a corpus contains
.
Each skill directory represents a topical partition, with
SKILL.md
and
INDEX.md
files that summarize its contents at increasing levels of detail.
The agent follows the same progressive disclosure workflow (description
\to

SKILL.md

\to

INDEX.md

\to
document) but navigates an information hierarchy rather than executing procedural instructions.
This reinterpretation—from procedural to informational skills—is the central design insight of
Corpus2Skill
.

3
Corpus2Skill
Framework

Corpus2Skill
operates in two phases: a one-time offline
compile phase
that transforms a raw document corpus into a browsable skill tree, and a per-query online
serve phase
where an LLM agent navigates this tree with full visibility into the corpus structure.

Figure

2
illustrates the full architecture.

3.1
Problem Setup

Let
\mathcal{D}=\{d_{1},\dots,d_{N}\}
be a corpus of
N
documents.
Given a natural-language query
q
, the task is to produce an answer
a
grounded in a subset
\mathcal{D}_{q}\subseteq\mathcal{D}
of relevant documents.
Standard RAG systems select
\mathcal{D}_{q}
via a retrieval function
f(q,\mathcal{D})\to\mathcal{D}_{q}
that operates as a black box from the LLM’s perspective: the model receives
\mathcal{D}_{q}
but has no visibility into what
\mathcal{D}
contains or why
\mathcal{D}_{q}
was chosen.

Corpus2Skill
replaces this opaque retrieval step with
agent-driven navigation
.
The compile phase constructs a hierarchical skill forest
\mathcal{S}=\{s_{1},\dots,s_{K}\}
where each skill
s_{k}
is a navigable directory tree of summaries covering a topical partition of
\mathcal{D}
.
Following the agentic skills formalism of
17
, each skill can be viewed as a tuple
(C,\pi,T,R)
:
the
applicability condition

C
is the skill’s summary (the agent reads it to decide relevance);
the
execution policy

\pi
is the navigation workflow (descend through summaries, then retrieve documents);
the
termination condition

T
is the agent’s judgment that sufficient evidence has been gathered;
and the
reusable interface

R
is the standardized file structure (
SKILL.md
,
INDEX.md
) and the
get_document
tool.
At serve time, the agent selects and navigates skills autonomously, making the document selection process transparent and steerable.

) and document lookup (
get_document
).

3.2
Compile Phase

The compilation pipeline consists of four stages (implementation details and full prompts in
Appendices

A
and
C
).

Document loading and embedding.

The compiler accepts directories containing standard document formats (
.md
,
.txt
,
.json
,
.jsonl
).
Each document is assigned a content-hash-based unique identifier, ensuring deterministic, collision-free IDs that are independent of the source system’s naming scheme.
Documents are truncated to a maximum character length and embedded using a sentence embedding model
(
32
)
, producing a dense vector for each document.
These embeddings capture semantic similarity between documents and serve as the foundation for the subsequent clustering step.

Iterative hierarchical clustering.

We build a multi-level hierarchy through an iterative bottom-up process controlled by two parameters: the branching ratio
p
(target number of children per cluster) and the maximum number of top-level clusters
K
.
At each level, the current set of
n
embeddings is partitioned into
\lceil n/p\rceil
groups via K-Means
(
25
)
on L2-normalized vectors.
Each resulting cluster is then summarized by an LLM that reads representative member texts and produces a concise description of the cluster’s topical coverage, the types of questions the documents answer, and key terms or features mentioned.
These summaries are re-embedded using the same sentence embedding model, and the resulting embeddings become the input to the next round of K-Means.
This process repeats until the number of remaining clusters falls below
K
, yielding a set of root clusters that form the top level of the hierarchy.

This iterative embed-cluster-summarize loop is inspired by the recursive tree construction in RAPTOR
(
36
)
, but adapted for our navigability goal.
We use K-Means with hard assignments so that each document maps to exactly one path in the directory tree, and we materialize the hierarchy as browsable files rather than indexing it in a flat vector store.
These two choices, deterministic partitioning and filesystem materialization, are what enable agent-driven navigation at serve time.
Small clusters below a minimum size are merged into the nearest centroid to avoid orphan groups.

Labeling.

After the clustering hierarchy stabilizes, the LLM generates a short (2 to 5 word) filesystem-safe label for each non-leaf node.
These labels serve a dual purpose: they provide human-readable directory names for inspection (e.g.,
wix-commerce-monetization
) and, more importantly, they give the agent semantically meaningful entry points for topic routing.
When the agent reads a
SKILL.md
listing subgroups such as “wix-payments-ecosystem” or “domain-dns-management,” the labels alone often suffice to identify the relevant branch without reading full summaries.

Skill tree construction.

The hierarchy is materialized into a filesystem structure designed for agent navigation:

•

Root clusters
become top-level skill directories, each containing a
SKILL.md
with the cluster summary and a listing of child groups.

•

Sub-clusters
become subdirectories with
INDEX.md
files that list either further subgroups or leaf document identifiers alongside brief summaries of each document.

•

Full document text
is stored externally in a
documents.json
file, referenced by document ID from within the navigation files.

This separation between navigation metadata and document content is a deliberate architectural choice.
Navigation files (
SKILL.md
,
INDEX.md
) remain small (typically under 2 KB each), containing only summaries and document identifiers.
This keeps the agent’s per-step token cost low: reading an
INDEX.md
to survey 20 documents costs far fewer tokens than reading the documents themselves.
Full document content is accessed only when the agent has narrowed its search, via a dedicated
get_document
tool call.
The result is a forest of
K
independent skill trees, each representing a topical domain within the corpus.
The forest structure allows the agent to reason about topic relevance at the coarsest level before committing to a branch.

Skill file design.

Each
SKILL.md
and

follows a uniform template with YAML frontmatter (

) that the Skills API reads for progressive disclosure.
Compilation prompts produce
routing-oriented
summaries: the LLM identifies the topic area, question types, and key terms, so that each file functions as a decision point for the navigating agent.
Each file also embeds actionable next-step instructions (e.g., “Use
get_document
with the doc_id”), so the agent always knows which tool to invoke next.

Navigation complexity.

The hierarchy depth grows as
O(\log_{p}N)
: with branching ratio
p
and
N
documents, the agent traverses at most
L=\lceil\log_{p}N\rceil
levels to reach a leaf.
At each level
\ell
, the agent reads one navigation file summarizing
O(p)
children.
A single decision at level
\ell
reduces the candidate set from
N/p^{\ell-1}
to
N/p^{\ell}
, yielding a multiplicative information funnel:

N\;\xrightarrow{\div\,p}\;\frac{N}{p}\;\xrightarrow{\div\,p}\;\frac{N}{p^{2}}\;\cdots\;\xrightarrow{\div\,p}\;\frac{N}{p^{L}}\approx 1

(1)

The total summaries inspected scale as
O(p\cdot\log_{p}N)
rather than
O(N)
.
For WixQA (
N{=}6{,}221
,
p{=}10
), this gives
L{=}3
levels and approximately 30 summaries to locate a single document among thousands.
Note that this bound counts summaries inspected under an idealized single-path traversal; in practice, the actual token cost is higher because the Skills API includes previously loaded navigation files in each subsequent call, and the agent may explore multiple branches.
The per-query costs reported in
Section

4
reflect these real-world overheads.
A 100,000-document corpus with
p{=}10
would require only one additional level (
L{=}5
).

3.3
Serve Phase

At serve time, the pre-compiled skill directories are uploaded to Anthropic’s Skills API.
The API implements progressive disclosure: skill names and one-line descriptions are pre-loaded into the agent’s context, but full file content is loaded only when the agent explicitly reads a file.
This design is critical for token efficiency.
Pre-loading all navigation files would flood the context with thousands of tokens of irrelevant summaries; loading nothing would leave the agent blind to the corpus.
Progressive disclosure strikes a balance: the agent sees just enough (skill names and descriptions, approximately 200 tokens total) to make an informed first decision, then incrementally loads detail as it descends.

Tools.

The agent receives two tools:
(1)
code_execution
, which allows browsing
SKILL.md
and
INDEX.md
files through
view
commands, providing the agent with full visibility into the hierarchy; and
(2)
get_document(doc_id)
, a custom tool that retrieves the full text of a document from the document store given its identifier.
The two-tool design reflects the two types of information the agent needs:
navigational
(where to look) and
evidential
(what to cite).
Keeping them separate means the agent can survey many document summaries cheaply before committing to the token cost of reading full documents.

Navigation workflow.

Because skill descriptions are pre-loaded, the agent begins each query with a bird’s-eye view of the corpus, knowing what topics exist and roughly how many documents each topic covers.
A typical query proceeds in 2 to 3 turns:

1.

The agent identifies the most relevant skill from pre-loaded descriptions and reads its
SKILL.md
to understand the subgroup structure.

2.

The agent navigates into the relevant subgroup’s
INDEX.md
, which lists document identifiers with brief titles and summaries.

3.

The agent calls
get_document
to retrieve the full text of one or more promising documents and synthesizes a grounded answer.

At each step, the agent makes an informed decision guided by summaries describing each branch.
If a
SKILL.md
lists ten subgroups and the agent has only explored one, it knows nine remain—an awareness that flat retrieval cannot provide.
This structural visibility enables two behaviors:
targeted backtracking
(abandoning an unpromising branch for a more relevant one) and
cross-branch synthesis
(combining evidence from multiple subgroups within or across skills).
The system prompt enforces a
grounding rule
(every claim must trace to a retrieved document, not a summary file) and a
concise-answer format
(word limits, no preamble); see
Appendix

D
.

4
Experiments

4.1
Setup

Dataset.

We evaluate on WixQA
(
6
)
, a customer support QA benchmark built from the Wix knowledge base.
The corpus contains 6,221 support articles covering website building, e-commerce, SEO, marketing, and platform features.
The evaluation set consists of 200 expert-written questions with gold-standard answers and gold article IDs.

Compilation.

We compile the WixQA corpus with branching ratio
p{=}10
and maximum top-level clusters
K{=}7
.
This produces a 3-level hierarchy with 6 top-level skills, 665 navigation files, and a 13 MB document store.
Compilation takes 6.5 minutes on a 32-CPU server.

Baselines.

All methods use the same LLM for answer generation and the same evaluation protocol.
We compare five baselines spanning three retrieval paradigms:

BM25
(sparse keyword retrieval
(
33
)
),

Dense
(Qwen3-Embedding-0.6B
(
48
)
with a FAISS index
(
18
)
),

Hybrid
(Reciprocal Rank Fusion
(
7
)
of BM25 and Dense),

RAPTOR
(hierarchical tree retrieval
(
36
)
with UMAP+GMM+BIC clustering),
and
Agentic
(an LLM agent with iterative access to BM25, Dense, and Hybrid tools).
The first three are single-shot (top-5 passages, one LLM call); RAPTOR uses collapsed tree retrieval; Agentic is allowed up to 10 interaction rounds.
Full implementation details are in
Appendix

H
.

Metrics.

We report four lexical overlap metrics:

Token F1
(harmonic mean of token-level precision and recall against the gold answer),

BLEU

(
31
)
(n-gram precision with brevity penalty),

ROUGE-1
and
ROUGE-2

(
23
)
(unigram and bigram recall).
We additionally report two LLM-judged metrics following the LLM-as-judge paradigm
(
49
)
, inspired by RAGAS
(
12
)
:

Factuality
measures how factually correct the generated answer is relative to the gold answer (1–5 scale, normalized to 0–1),
and
Context Recall
measures how well the retrieved context covers the essential claims in the gold answer (same scale).
We also report input token usage and per-query cost.
Details on metric computation and fairness standardization across methods are in
Appendix

I
.

RAPTOR’s collapsed tree retrieval achieves Factuality of 0.675 and Context Recall of 0.616, substantially above flat methods (Dense: 0.536/0.450, BM25: 0.470/0.386), and
Corpus2Skill
exceeds RAPTOR by a further 10% on Factuality (0.739) and 9% on Context Recall (0.673).
Cluster summaries surface thematic connections that flat embeddings miss, allowing the retrieval system to match queries to relevant document groups rather than individual passages.

Cost analysis.

With Anthropic ephemeral prompt caching enabled on the navigation context,
Corpus2Skill
costs
$0.089 per query
, essentially matching Agentic ($0.088) while delivering substantially higher quality on every metric (
Table

1
).
Caching is particularly effective for
Corpus2Skill
: across the 200-query run we observed 6.07M cache-read input tokens versus 2.52M freshly-billed input tokens, so roughly 70% of the prompt content is served from cache at one-tenth the base rate.
This reflects the fact that
SKILL.md
and
INDEX.md
summaries are reused across many consecutive turns and queries, whereas Agentic’s per-query retrieval snippets are largely query-specific and thus less cacheable.
Relative to single-shot retrieval baselines ($0.007–$0.012 per query),
Corpus2Skill
is 7–13
\times
more expensive; it is therefore best positioned for high-value queries where the quality gap matters (complex multi-hop support questions, compliance-critical lookups), while single-shot retrieval or RAPTOR remain the right default for high-volume, low-stakes traffic.

Corpus2Skill
also produces only 837 output tokens per query—40% fewer than Agentic (1,409)—suggesting that navigating to the right documents yields more targeted answers.

Headline result.

Corpus2Skill
attains the highest macro-average F1 (0.350) across the 10-dataset benchmark (

Agentic continues to win Factuality (0.660), and Dense wins Context Recall (0.540) because the LLM-judged CtxR rewards span overlap that embedding retrieval is explicitly optimized for. The picture is therefore not a uniform sweep —
Corpus2Skill
wins on 4 of 10 datasets by a margin of 0.02–0.10 F1, ties on 2, and loses on 4 (
Table

2
) — but the per-dataset dispersion lets us characterize
which corpora navigation actually helps
.

When does corpus navigation help?

Three structural properties consistently separate wins from losses:

(i) Atomic, topically-coherent documents.
On WixQA, Emanual, DelucionQA, and HAGRID — corpora where each document covers a single feature, entity, or how-to —
Corpus2Skill
beats every retrieval baseline by 0.02–0.09 F1. HAGRID is particularly informative: even though its corpus is open-domain Wikipedia, every article is by construction a coherent unit about one entity, and the cluster summarizer recovers a clean per-topic taxonomy. The hierarchy gives the agent useful disambiguation that flat retrievers cannot exploit.

(ii) Document granularity in the 0.5–3k character range.
The wins cluster around documents long enough to contain a complete answer (
\geq 500
characters) but short enough that an LLM-written summary captures the article (
\leq 3000
characters). On CUAD (legal contracts averaging
\approx
7,500 characters of mixed clauses) and TechQA (IBM technotes averaging 3,740 characters), single documents straddle multiple clause types or symptom categories, so any single skill placement is provably suboptimal and
Corpus2Skill
loses to flat retrieval.

(iii) A recoverable implicit taxonomy.
On TatQA, which is essentially homogeneous SEC-style financial-statement tables, the level-1 cluster summaries collapse onto near-identical labels (“corporate financial reporting”) and the agent can no longer distinguish branches at the top level.
Corpus2Skill
hits
max_turns
on a third of queries and the cost balloons to $0.97/query, the worst case in our evaluation. ExpertQA exhibits a milder version of the same failure mode: queries span dozens of unrelated scientific fields, summaries become generic, and the navigator cannot exploit them. Agentic search wins both subsets, presumably because the lack of a useful hierarchy makes the search-then-read pattern strictly more efficient.

Where flat retrieval is the right default.

On CovidQA, the corpus is short, near-duplicate research abstracts whose information density is already saturated by top-5 retrieval; on TechQA, lexical / dense baselines are within a few percent of each other and
Corpus2Skill
pays a
30\times
cost premium for no quality gain. The pattern is consistent: when the bottleneck for a corpus is
retrieval recall
rather than
topic disambiguation
, hierarchical navigation adds turns and tokens without helping. We therefore position
Corpus2Skill
as a complementary primitive — strongly preferred for curated, single-domain enterprise knowledge bases (the deployment target this paper is motivated by), with flat retrieval or RAPTOR retained as the right default for open-domain or homogeneous pools.

Competitive cases.

CovidQA and FinQA sit between the wins and the failures. On CovidQA the lexical metrics agree to within 0.02 F1 across all five methods. On FinQA,
Corpus2Skill
matches the best baseline on lexical n-gram quality (BLEU 0.132 and R-2 0.217 are both highest, F1 within 0.02 of Dense), confirming that financial reports still admit a useful by-firm and by-statement-section hierarchy; the cost premium (
\sim 80\times
over Dense) rather than the quality is what makes it a poor fit. We treat FinQA and CovidQA as ties rather than losses in our headline count.

Failure modes exposed by the generalization sweep.

The CUAD and TatQA results are the two cleanest cases in our evaluation where the design hypothesis behind
Corpus2Skill
— that an LLM-written hierarchy provides useful navigation signal — does not hold. CUAD answers are long verbatim quotes from a single contract clause, which token-F1 penalizes for any paraphrase; TatQA is structurally so flat that the cluster summarizer has nothing discriminative to surface. Both motivate concrete follow-on work — span-level extraction tools at the leaf level for the former, table-aware schema-based clustering for the latter — discussed alongside other limitations in
Section

5
.

5
Limitations

Cost.

The per-query cost of
Corpus2Skill
is dominated by input tokens: the Skills API includes navigation file content in every call, so even relatively small
SKILL.md
and
INDEX.md
files accumulate significant token counts across turns.
Enabling Anthropic ephemeral prompt caching on the navigation context reduces $/query from $0.172 to $0.089—close to the Agentic baseline—since roughly 70% of the prompt content is reused across consecutive turns and queries; we use this cached configuration throughout our main results.

Corpus2Skill
is nonetheless best suited for high-value queries where answer quality justifies the cost premium, such as complex multi-hop support questions or compliance-critical lookups.
For high-volume, low-stakes queries, single-shot retrieval or RAPTOR remain cost-effective.

API constraints.

The framework relies on Anthropic’s Skills API, which imposes limits of 8 skills per request, 200 files per skill, and 30 MB per skill.
These constraints shape the hierarchy design: the 8-skill limit caps top-level clusters, and the 200-file budget constrains tree depth before requiring compact merging (
Section

4.5
).
The WixQA corpus fits comfortably (6 skills,
\leq
133 files each), but larger corpora would require compact merging or multi-level partitioning.
As Skills APIs evolve and constraints relax, even narrower hierarchies could improve navigation precision.

Hard single-path clustering.

Each document is assigned to exactly one cluster path, a deliberate choice that enables filesystem materialization and deterministic navigation.
However, documents that span multiple topics (e.g., billing
and
subscriptions) can only appear under one branch, creating a routing bottleneck when queries target the other topic.
Our failure analysis (
Appendix

G
) confirms that top-level routing errors account for the majority of failures.
Soft or multi-parent assignment could mitigate this at the cost of duplicated content and more complex navigation; we leave this exploration to future work.

Compilation.

The one-time compilation costs $5–$10 in LLM calls plus 6.5 minutes of wall-clock time, negligible for enterprise deployments handling thousands of daily queries.
The pipeline is fully automated and deterministic given fixed random seeds, but does not yet support incremental updates—adding documents requires recompilation.

Corpora where corpus navigation does not help.

Our RAGBench generalization study (
Section

4.4
) makes the failure modes explicit.
Corpus2Skill
loses to flat retrieval on three structurally distinct corpus shapes. (1)
Long extractive documents
: CUAD legal contracts (
\approx
7,500 characters per doc, with answers being verbatim quotes from a single clause) and TechQA technotes (3,740 characters covering multiple symptom categories) violate the assumption that one document fits cleanly under one branch. (2)
Homogeneous tabular corpora
: TatQA is essentially identical SEC-style financial-statement tables, so the level-1 cluster summaries collapse onto near-duplicate labels and the navigator cannot disambiguate top-level branches; this case yields the worst quality and cost in our evaluation. (3)
Open-domain pools where retrieval recall is the bottleneck
: on CovidQA short research abstracts and ExpertQA cross-disciplinary scientific QA, hierarchical navigation adds turns and tokens without improving over what dense retrieval already surfaces in a single shot. We see these as honest scope limits of the design hypothesis behind
Corpus2Skill
rather than implementation issues. Three natural follow-on directions are clear from this analysis: a
span-level retrieval head
attached at the leaf level so the agent can quote verbatim from long documents (addressing CUAD),
table-aware schema clustering
that groups financial-statement rows by line-item / period / segment rather than embedding similarity (addressing TatQA), and
hybrid routing
that lets a lightweight classifier decide per-query whether to enter the skill tree or fall back to dense retrieval. We are exploring this last design under the working name CorpusForge in subsequent work.

Related Work

Cluster-based document organization.

Scatter/Gather
(
8
)
introduced the paradigm of navigating a pre-computed cluster organization rather than matching by similarity, grounded in the cluster hypothesis
(
42
;
24
)
.
Where Scatter/Gather required users to manually select and refine clusters in an interactive loop,
Corpus2Skill
delegates this navigation entirely to an LLM agent that reasons about cluster summaries at each level.

Hierarchical summarization for retrieval.

Positioning.

Corpus2Skill
combines offline hierarchical clustering, materialization as navigable skill files, and LLM-driven top-down navigation into a system that replaces embedding-based retrieval with agent-driven file browsing at serve time.

Conclusion

Corpus2Skill
demonstrates that giving an LLM agent a structured, browsable overview of a document corpus leads to higher-quality answers than providing it with retrieved passages alone.

The key insight is that modern LLM agents are capable navigators when given the right map:
a pre-compiled hierarchy of summaries and topic clusters enables informed, top-down exploration that exploits the agent’s reasoning abilities rather than treating it as a passive consumer of search results.
Because the agent reads summaries describing each branch, it can make informed routing decisions and combine evidence across branches when queries span multiple topics—an advantage that flat retrieval, which offers no corpus overview, cannot match.
With Anthropic ephemeral prompt caching enabled on the navigation context,
Corpus2Skill
matches the Agentic baseline on per-query cost ($0.089 vs. $0.088) while still delivering the highest quality on every metric, and it suggests a complementary design point for knowledge-grounded systems: invest computation at compile time to make the corpus navigable, rather than at query time to make it searchable.
Hierarchy depth grows logarithmically (
O(\log_{p}N)
), so the framework scales to larger corpora.

Future work includes evaluation on more domains, incremental compilation, and multi-parent soft clustering to handle queries that span multiple topics.

Impact Statement

Corpus2Skill
is designed for enterprise knowledge-grounded QA, a setting where incorrect answers can lead to real-world harm (e.g., wrong compliance guidance or billing instructions).
Like all LLM-based systems, it can produce confidently wrong answers when the agent navigates to irrelevant documents or misinterprets retrieved content.
Hierarchical summaries produced during compilation may also expose corpus structure that organizations consider sensitive.
Hard clustering means that documents spanning multiple topics are routed to a single branch, creating blind spots that may disproportionately affect certain query types.
Finally, because compilation is a batch process, the system cannot reflect real-time corpus updates, risking stale or outdated answers until recompilation occurs.
We recommend human-in-the-loop verification for high-stakes deployments.

Appendix D
Serving System Prompt

The serving agent receives the following system prompt:

# Corpus-Grounded Support Agent
# (Hierarchical Navigation)

You are a knowledge agent that answers
questions by navigating a hierarchical
skill directory. You explore a structured
file tree where documents are organized
into topic clusters.

## Hard Rules

- Every factual claim must trace to a
document you retrieved via get_document.
- SKILL.md files are NAVIGATION AIDS --
they tell you where to look, not what
to say.
- Never fabricate steps, URLs, prices, or
specifics not found in documents.
- Never guess. If you cannot find relevant
content after thorough exploration,
say so.

## Navigation Strategy

Your skills directory has this structure:

skill-XX-topic/
SKILL.md <- top-level summary
+ index of contents
group-YY-subtopic/
INDEX.md <- summary + index of
sub-contents
group-ZZ/
INDEX.md <- summary + document
ID listings

Skill names and descriptions are already
available to you. Follow this workflow:

1. Read the SKILL.md of the 1-2 most
relevant skills for your query.
2. Drill into the most relevant sub-group:
Read its INDEX.md.
3. At the leaf level, INDEX.md lists
document IDs with brief titles. Pick
the most relevant document IDs.
4. Call get_document with each relevant
doc_id to retrieve the full text.
5. Read at least one full document before
answering.

## Tools

- Code execution: Use ‘ls‘ and ‘cat‘ to
navigate the skills hierarchy.
- get_document(doc_id): Retrieve the full
text of a document by its ID. The doc_id
values are listed in leaf-level INDEX.md
files.

## Answer Format

- First sentence = direct answer.
No preamble.
- Factual questions: 1-3 sentences
(~80 words max).
- Procedural questions: numbered steps
only (~150 words max).
- Plain text. No bold, headers, or
dividers.
- One approach only. Do not present
alternatives.
- Never add "contact support" or closing
remarks.

Navigation mechanism.

Scatter/Gather relies on human users to iteratively select clusters; RAPTOR and GraphRAG delegate navigation to fixed algorithms (vector similarity or graph traversal).

Corpus2Skill
is unique in delegating navigation to an LLM agent that can reason about which branch to explore, backtrack when a path is unproductive, and combine evidence across branches.
This agent-driven navigation is what enables the trial-and-error behavior illustrated in
Figures

4
and
5
.

Serve-time infrastructure.

All prior systems require dedicated infrastructure at query time: a cluster index, a vector database, or a graph database.

Corpus2Skill
eliminates this dependency entirely—the only runtime component is the LLM itself, which receives pre-compiled skill files via the API.
This “LLM only” property simplifies deployment but shifts the cost burden to input tokens, as discussed in
Section

5
.

Appendix G
Failure Analysis

We examine the 62 queries (31%) on which
Corpus2Skill
scores Factuality
\leq
0.4 or Context Recall
\leq
0.2.
By comparing each query’s retrieved documents against the gold article IDs (using prefix matching, since
Corpus2Skill
uses truncated content hashes), we identify three failure modes:

Navigation miss (38 queries).

The agent retrieves documents but none match the gold article, indicating it descended into the wrong branch of the hierarchy.
For example, a query about reordering CMS collection items is routed to a general site-editing skill instead of the CMS-specific one; a query about blocking time slots in a staff schedule navigates to a generic booking group rather than the staff-management leaf.
These misroutes occur at the
top level
of the hierarchy, where broad skill summaries fail to distinguish closely related topics.

Partial navigation (19 queries).

The agent’s retrieved set includes the gold document, yet scores remain low.
In these cases the gold article is retrieved alongside several non-relevant documents, diluting the context provided to the answer synthesis step.
The agent correctly identified the general topic area but over-retrieved from neighboring leaf groups.

Synthesis error (3 queries).

The agent retrieves contextually relevant documents (Context Recall
\geq
0.6) but produces a factually incorrect answer, typically by over-generalizing across multiple articles or misinterpreting conditional instructions as universal.

No documents retrieved (2 queries).

Two queries (“How do I clear my browser cache?” and a Gmail password reset question) resulted in zero retrieved documents.
Both have gold articles in the corpus (Wix publishes help articles for these topics), but the agent could not locate a matching skill branch and correctly declined to answer rather than hallucinating.

Takeaway.

The dominant bottleneck is initial topic routing: 38 of 62 failures stem from the agent choosing the wrong top-level branch.
The compact-mode ablation (
Section

4.5
), which produces narrower top-level clusters, partially mitigates this by providing finer-grained topic separation at the first navigation step.

Appendix H
Baseline Implementation Details

All baselines use the same LLM (Claude Sonnet) for answer generation and the same evaluation prompts for fair comparison.

BM25.

We implement BM25 sparse keyword retrieval using the
rank_bm25
library
(
33
)
.
Documents are tokenized and indexed at the full-article level.
At query time, we retrieve the top-5 articles by BM25 score and pass them as context to a single LLM call.

Dense.

We encode all documents using Qwen3-Embedding-0.6B
(
48
)
, producing 1024-dimensional embeddings stored in a FAISS flat index
(
18
)
.
We use the document prompt template for encoding articles and the query prompt template for encoding questions.
At query time, we retrieve the top-5 nearest neighbors by cosine similarity and pass them as context to a single LLM call.

Hybrid.

We combine BM25 and Dense scores using Reciprocal Rank Fusion
(
7
)
with
k{=}60
and equal weighting (
\alpha{=}0.5
).
The fused ranking selects the top-5 passages, which are passed to a single LLM call.

RAPTOR.

We faithfully implement the RAPTOR algorithm
(
36
)
: UMAP
(
27
)
for dimensionality reduction, Gaussian Mixture Model (GMM) soft clustering
(
28
)
with BIC-based cluster count selection
(
38
)
, and recursive summarization of clusters.
We use the same embedding model (Qwen3-Embedding-0.6B) as the Dense baseline for consistency.
At query time, collapsed tree retrieval searches across all hierarchy levels simultaneously, returning the top-5 passages from any level.

Agentic.

An LLM agent is given access to three search tools (
search_bm25
,
search_dense
,
search_hybrid
), each returning top-
k
results.
The system prompt instructs the agent to search first, then answer based on accumulated evidence, choosing BM25 for exact terms and product names, dense for conceptual queries, and hybrid as a default strategy.
The agent can issue up to 10 rounds of iterative retrieval, reformulating sub-queries based on intermediate results.
Evidence is accumulated across all turns; when the agent stops, it produces a structured JSON response containing the answer and curated top-5 references selected from the full evidence pool.
For evaluation fairness, context recall is computed over the last 5 retrieved documents (matching the context window of single-shot baselines).
This baseline tests whether agentic multi-turn retrieval over traditional search infrastructure can match navigation-based exploration.

Appendix I
Evaluation Metrics

Lexical metrics.

Token F1
tokenizes both the predicted and gold answers into word tokens and computes the harmonic mean of token-level precision and recall.

BLEU

(
31
)
measures modified n-gram precision (up to 4-grams) with a brevity penalty to penalize overly short outputs.

ROUGE-1
and
ROUGE-2

(
23
)
measure unigram and bigram recall respectively, capturing how much of the gold answer’s content appears in the prediction.

LLM-judged metrics.

Both
Factuality
and
Context Recall
use an LLM judge
(
49
)
following the RAGAS framework
(
12
)
, scoring on a 1–5 scale normalized to 0–1.
Factuality evaluates whether the claims in the generated answer are factually consistent with the gold answer, independent of the retrieved context.
Context Recall evaluates whether the retrieved context contains sufficient information to answer the question, by checking how many essential claims in the gold answer can be attributed to the provided context.

Context Recall standardization.

A critical design decision is the standardization of Context Recall measurement across different retrieval paradigms (single-shot, multi-turn, and navigation-based).
For fair comparison, all methods follow the same protocol:
(1) collect the last 5 documents or passages retrieved by the method;
(2) join them with separator tokens;
(3) truncate to a uniform 8,000-character window.
The LLM judge receives this standardized context.
This ensures that single-shot baselines contribute their top-5 retrieved passages, Agentic contributes the last 5 documents from its multi-turn retrieval, and
Corpus2Skill
contributes the last 5 documents retrieved via
get_document
tool calls.

Cost metrics.

Input token count is the total number of tokens sent to the LLM across all turns.
Per-query cost is computed using the model’s published per-token pricing (input and output tokens combined).
For single-shot methods, cost reflects one LLM call; for multi-turn methods (Agentic,
Corpus2Skill
), it reflects all turns including tool-call reasoning.
