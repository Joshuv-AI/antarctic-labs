Finite Functional Programming
Michael Arntzenius, Max Willsey

Abstract
We unify functional and logic programming by treating predicates as functions equipped with their support: the set of inputs whose output is nonzero. Datalog, for instance, is a language of finitely supported boolean functions. Finite support allows representing functions as input-output tables. Generalizing from boolean functions to other pointed sets neatly handles aggregation and weighted logic programming. We refer to the combination of finitely supported functions, represented as data, with higher order functions, represented as code, as finite functional programming. We give a simple type system to check finite support, using graded effects to check variable grounding and relevance types to model pointed sets.

Support, pointedly

The support of a boolean function
f
is the set
\{x\in A:f(x)\neq\mathit{false}\}
.
It will be useful to generalize beyond booleans,
firstly to expose compositional structure, for instance, to define the support of a curried function
f:A\to B\to\textit{bool}
;
and secondly to generalize from boolean logic and existential quantification (or relational algebra and projection, respectively) to weighted logic programming and aggregation (or tensor algebra and contraction).

To this end we write
P,Q,R
for sets with a designated element (‘pointed sets’) and
\mathit{nil}_{P}\in P
for the designated element (the ‘point’).
(We use
A,B,C
for ordinary sets.)
For instance, we regard
bool
as pointed with
\mathit{nil}_{\textit{bool}}=\mathit{false}
.
We define the support of a function
f:A\to P
into a pointed set to be
\support f=\{x\in A:f(x)\neq\mathit{nil}_{P}\}
.
If one regards
\mathit{nil}_{P}
as an uninteresting, default value, a function’s support contains those inputs with interesting, nondefault outputs.

We write
A\Rightarrow P=\{f\in A\to P:\support f~\text{is finite}\}
for the finitely supported functions from
A
to
P
.
This is a pointed set with
\mathit{nil}_{A\Rightarrow P}=\lambda{x}.\>\mathit{nil}_{P}
;
the boring, default finite map is the one with empty support.
What can we do with finite maps?
We can of course apply them—this is lookup in a key-value table.
We can also curry and uncurry them:
A\times B\Rightarrow P\cong A\Rightarrow(B\Rightarrow P)
.
This converts between a single flat table
A\times B\Rightarrow P
and a trie-like nesting of tables
A\Rightarrow B\Rightarrow P
.

But how can we manipulate the output
P
of a finite map
A\Rightarrow P
?
Can we, for instance, compose finite maps?
Unfortunately, the composition of two finite maps may not have finite support:
e.g. take
\lambda{x}.\>x<3:\mathbb{N}\Rightarrow\textit{bool}
followed by
\mathit{not}:\textit{bool}\Rightarrow\textit{bool}
.
The set of naturals less than three is finite; its complement is not.
For the same reason, we cannot compose a finite map
g:A\Rightarrow P
with an arbitrary function
f:P\to Q
and expect the result to be finitely supported.

However, we
can
compose a finite map with a function
f
if
f(\mathit{nil}_{P})=\mathit{nil}_{Q}
; this preserves finiteness because it can only contract our support.
These are the
point preserving maps
, which we notate
P\multimap Q=\{f\in P\to Q:f(\mathit{nil}_{P})=\mathit{nil}_{Q}\}
.
These are pointed with
\mathit{nil}_{P\multimap Q}=\lambda{x}.\>\mathit{nil}_{Q}
.
The category
\mathrm{Set}_{*}
has pointed sets
P,Q
as objects and point preserving maps as morphisms; what we have just observed is that, for any set
A
, there is a functor
F_{A}:\mathrm{Set}_{*}\to\mathrm{Set}_{*}
given by
F_{A}(P)=A\Rightarrow P
.
If finitely supported maps are this work’s
raison d’être,
point preserving maps are how we will manipulate and combine them.

One can verify these examples mechanically using the definitions of

and

To use an

we must use both

\mathit{nil}
we will propagate it.
By contrast, if a

then both of its components are, so we are free to use only one.
This is why

is invalid but
\mathit{fst}_{\mathbin{\&}}
is correct—and also why we use destructuring to eliminate
\otimes
, but projection for
\mathbin{\&}
.
Conversely, constructing an

uses anything used by either

or

or

is
\mathit{nil}
the whole pair is,
but constructing a
\mathbin{\&}

uses only what both

and

use, since only these will force both

and

\mathit{nil}

This is why

\mathit{and3}_{\otimes}
are correct but
\mathit{pair}_{\mathbin{\&}}
and
\mathit{and3}_{\mathbin{\&}}
are invalid.

Since we need to mix a cartesian, structural type system for sets

for point preserving maps.
A few example rules:

\frac{{\Gamma}\mathbin{/}{\Delta}\,\vdash\,{t}:{P}\quad{\Gamma}\mathbin{/}{\Delta}\,\vdash\,{u}:{Q}}{{\Gamma}\mathbin{/}{\Delta}\,\vdash\,{\langle{t,u}\rangle}:{P\mathbin{\&}Q}}\par\frac{{\Gamma}\mathbin{/}{\Delta_{1}}\,\vdash\,{t}:{P}\quad{\Gamma}\mathbin{/}{\Delta_{2}}\,\vdash\,{u}:{Q}}{{\Gamma}\mathbin{/}{\Delta_{1}\cup\Delta_{2}}\,\vdash\,{(t,u)}:{P\otimes Q}}\par\frac{~}{{\Gamma}\mathbin{/}{{x}\mathbin{:}{P}}\,\vdash\,{x}:{P}}\par\frac{{\Gamma}\mathbin{/}{\Delta,{x}\mathbin{:}{P}}\,\vdash\,{t}:{Q}}{{\Gamma}\mathbin{/}{\Delta}\,\vdash\,{\lambda{x}.\>t}:{P\multimap Q}}

which must

This union is a key difference from standard linear logic, which would split the contexts disjointly; it allows a variable to be used in both branches—but, unlike the

The other side of the tracks

Alas, these are not yet the typing rules we are looking for.
A scant two contexts will not suffice; we have

Oh no!
What went wrong?
Well, constant functions like

are not finite because their support is their entire possibly infinite domain (

is the only exception).
Similarly, the support of

,
\mathit{dup}_{\otimes}
, and

is the entire domain minus
\mathit{nil}
; we cannot generally use a finite map’s input directly in its output.

4

4

We could in principle make a carve-out for maps with finite domains.
As we intend to represent finite maps by tables, however, this poses a usability hazard: enumerating all 64-bit integers just because a programmer wrote
\lambda{x}.\>x
is not desirable.

If
\lambda{x}.\>x
is not well typed, what does our variable rule look like?
How do we use variables in our finitely supported context
\Omega
?
Let’s return to our source of inspiration.
In bottom-up logic programming, we generate nonempty, finite relations by either (1) combining other nonempty relations or (2) using rules that refer to constants.
We saw in
section

3
that in
\lambda_{\mathrm{FS}}
, (1) means using point preserving maps to transform finite maps, and (2) means using equality

to generate singleton finite maps.
Let’s consider a prototypical example of each kind:

\displaystyle\mathit{actorOrDirector}

\displaystyle=\lambda{x}.\>\mathit{actor}\>x\mathrel{\textrm{or}}\mathit{director}\>x:\mathit{person}\Rightarrow\textit{bool}

✓

\displaystyle\mathit{hitchcockAlone}

\displaystyle=\lambda{x}.\>\mathit{hitchcock}=x\phantom{\lambda{x}.\>\mathit{actor}\>x\mathrel{\textrm{or}}\mathit{director}\>x}\mathchoice{\hskip-71.91907pt}{\hskip-71.91907pt}{\hskip-59.66548pt}{\hskip-43.82074pt}:\mathit{person}\Rightarrow\textit{bool}

In each case, we use the finitely supported variable

This, then, will serve both as our elimination rule for finite maps and our usage rule for finitely supported variables:

\frac{{\Gamma}\mathbin{/}{\Delta}\mathbin{/}{\Omega,{x}\mathbin{:}{A}}\,\vdash\,{t}:{P}}{{\Gamma}\mathbin{/}{\Delta}\mathbin{/}{\Omega}\,\vdash\,{\lambda{x}.\>t}:{A\Rightarrow P}}\quad\textsc{right=$\Rightarrow$\,i}\par\frac{{\Gamma}\mathbin{/}{\Delta}\mathbin{/}{\Omega}\,\vdash\,{t}:{A\Rightarrow P}}{{\Gamma}\mathbin{/}{\Delta}\mathbin{/}{\Omega,{x}\mathbin{:}{A}}\,\vdash\,{t\>x}:{P}}\quad\textsc{right=$\Rightarrow$\,e}

These rules structuralize the isomorphism

(which is more obvious after renaming:

Along with the isomorphism

, this shows that finitely supported maps form not just a functor but a

on

.

A (non-graded) monad is an endofunctor

with natural transformations
\mathit{pure}_{\alpha}:\alpha\to F\alpha
and
\mathit{join}_{\alpha}:FF\alpha\to F\alpha
, satisfying laws which we omit for brevity.
For our purposes, a graded monad

is a family of functors

where

, with analogues of
\mathit{pure}
and
\mathit{join}
that interact with the grading monoid:
\mathit{pure}_{\alpha}:\alpha\to F_{1}\alpha
and
\mathit{join}_{\alpha}:F_{m}F_{n}\alpha\to F_{mn}\alpha
, again satisfying certain omitted laws.

In our case, the graded monad is
F_{A}P=A\Rightarrow P
, and the monoid of grades is sets under cross product.
5
5

5

Technically this is not a monoid, since

and

are only isomorphic, not equal.
This technicality is not worth getting hung up on; it can be defeated, for instance, by taking grades to be contexts

This makes
\mathit{pure}_{P}:P\multimap(1\Rightarrow P)
and
\mathit{join}_{P}:(A\Rightarrow B\Rightarrow P)\multimap(A\times B\Rightarrow P)
merely the forward legs of our two isomorphisms.
The laws we omitted hold trivially because these maps are isomorphisms—indeed, the isomorphisms’ reverse legs also make

a graded comonad

.
Although almost trivial, this graded (co)monad is of practical interest because type systems for graded monads (effect systems) have been extensively studied

.

Unfortunately, our typing rules do not all follow neatly from this connection to grading.
Let’s examine the rules for

The support of

So what typing rule does this example need?
We have used each variable

\frac{{\Gamma}\mathbin{/}{\Delta_{1}}\mathbin{/}{\Omega_{1}}\,\vdash\,{t}:{P}\quad{\Gamma}\mathbin{/}{\Delta_{2}}\mathbin{/}{\Omega_{2}}\,\vdash\,{u}:{Q}}{{\Gamma}\mathbin{/}{\Delta_{1}\cup\Delta_{2}}\mathbin{/}{\Omega_{1},\Omega_{2}}\,\vdash\,{(t,u)}:{P\otimes Q}}

\frac{{\Gamma}\mathbin{/}{\Delta_{1}}\mathbin{/}{\Omega_{1}}\,\vdash\,{t}:{P}\quad{\Gamma}\mathbin{/}{\Delta_{2}}\mathbin{/}{\Omega_{2}}\,\vdash\,{u}:{Q}}{{\Gamma}\mathbin{/}{\Delta_{1}\cup\Delta_{2}}\mathbin{/}{\Omega_{1}\cup\Omega_{2}}\,\vdash\,{(t,u)}:{P\otimes Q}}

This is unproblematic semantically: we can filter a finite set by any predicate we like and the result remains finite!

We give the typing rules of
\lambda_{\mathrm{FS}}

The attentive reader will find few surprises.
As mentioned in

[

to handle the interaction between ordinary functions and point preserving functions.
This corresponds semantically to an adjunction between the cartesian closed category
\mathrm{Set}
(LNL’s
\mathcal{C}
) and the symmetric monoidal closed category
\mathrm{Set}_{*}
(LNL’s
\mathcal{L}

Additionally,
\mathrm{Set}_{*}
possesses a natural family of diagonal maps

[

18

The adjunction in question consists of the free functor
\textit{maybe}:\mathrm{Set}\to\mathrm{Set}_{*}
and the forgetful functor
U:\mathrm{Set}_{*}\to\mathrm{Set}
.
Our main difference from a standard adjoint calculus is our additional context
\Omega
of finitely supported variables, which in most typing rules follows the context-hopping pattern of
\otimes
introduction that we explored in
section

Unsurprisingly, we interpret ‘set’ types as sets
\llbracket{A}\rrbracket\in\mathrm{Set}
, and ‘pointed set’ types as pointed sets
\llbracket{P}\rrbracket\in\mathrm{Set}_{*}
.
We have deliberately used almost identical notation for the syntax of types and for the mathematical objects they denote.
See
figure

5
for the semantics of types and contexts.
The
n

\bigotimes_{i}P_{i}
deserves some explanation: this denotes the pointed set
\{(x_{1},\dots,x_{n}):x_{1}\in P_{1},\dots,x_{n}\in P_{n}\}\uplus\{\mathit{nil}\}
quotiented by
\forall{i}.\>x_{i}=\mathit{nil}\implies(x_{1},...,x_{n})=\mathit{nil}
.
The explicit addition of
\mathit{nil}
means that the nullary smash product,
\bigotimes\{\}
, has two elements:
\mathit{nil}
and the empty tuple
()
, which is important for interpreting the case
\Delta={\cdot}
of an empty pointed set context.

7
Looking back and forward

There are many ways to combine logic and functional programming.
Mercury
[
29
]
integrates
functional programming into top-down logic programming.
Functional IncA
[
22
]
embeds functional programming into Datalog via a demand transform.
Flix
[
20
]
has two sublanguages, logical and functional, which can each invoke the other.

\lambda_{\mathrm{FS}}
, however, belongs to the subfamily of languages that integrate logical features into a functional substrate.
Perhaps its best known exemplars are ‘functional logic programming’ languages like Curry
[
1
]
and Verse
[
4
]
, where relations
A\times B\to\textit{bool}
become ‘functions’
A\to B
that may yield many
B
s for a given
A
.
We find this undesirable because it (a) makes multiple returns and unification into pervasive ambient effects and (b) hides the boolean-ness, losing the opportunity to generalize from
bool
to other types.

\lambda_{\mathrm{FS}}
is closer to Datafun
[
3
]
and
\lambda_{\vee}

[
26
]
, which avoid ambient effects by representing relations as finite sets, a separate type from normal functions.
However, they express logical operations via loops or set comprehensions.
In contrast
\lambda_{\mathrm{FS}}
is inspired by Rel
[
2
]
,
where relations are defined pointwise like functions,
using ‘and’, ‘or’, and ‘exists’.
Rel also supports arithmetic operators and aggregations, as if relations had return values.
However, Rel implements this by desugaring to a Datalog-like core where the ‘value’ of a Rel expression is just the relation’s final column.

\lambda_{\mathrm{FS}}
reimagines this syntactic sugar semantically.

By generalizing beyond booleans,
\lambda_{\mathrm{FS}}
moves closer to weighted logic programming languages like Dyna
[
10
,
11
]
, ProbLog
[
25
]
, or Datalog°
[
17
]
.
Indeed,
\lambda_{\mathrm{FS}}
is inspired by and indebted to databases research on
K
-relations
[
14
]
, generalizing Datalog semantics from booleans to semirings, which has in turn inspired functional query languages
[
15
,
27
]
.
Other Datalog-inspired languages like Datafun, Flix, and
\lambda_{\vee}
generalize to semilattices.
However, so far as we know only
\lambda_{\mathrm{FS}}
uses pointed sets—the minimal, most general structure required to define a function’s support.
Semirings then emerge as a natural structure over pointed sets:
we can generalize
\mathit{or}
and
\mathit{exists}
to an ‘additive’ commutative monoid
(P,{\oplus}:P\mathbin{\&}P\multimap P,\mathit{nil}_{P})
and its aggregation operator
\bigoplus:(A\Rightarrow P)\multimap P
, and similarly
\mathit{and}
generalizes to a ‘multiplicative’ monoid
(P,{\oast}:P\otimes P\multimap P,\boldsymbol{1})
distributing over
\oplus
.

\lambda_{\mathrm{FS}}
has many limitations which we would like to lift in future work:

Recursion

There are two kinds of recursion we might want in
\lambda_{\mathrm{FS}}
:
lazy functional recursion (as in recursively defined functions or codata) and bottom-up iteration until reaching a fixed point (as in Datalog’s recursively defined relations).
It’s not obvious how these should interact semantically.
\lambda_{\vee}

[
26
]
shows how to unify them, but requires a lot of structure (semilattices, dcpos, and continuity); moreover, it seemingly cannot do stratified computation, where we compute a fixed point and then use its results in a non-monotone way.

Implementation

We did not show how to implement either our type system or our semantics, although
we have built
a prototype
(
https://github.com/rntz/fslang/blob/main/fslang.rkt
) which we lack space to discuss here.
As our finite map operations are a form of tensor algebra, perhaps indexed streams
[
19
]
could provide an efficient implementation technique.

Interleaving
\boldsymbol{\Delta}/\boldsymbol{\Omega}
contexts

We use three contexts,
\Gamma\mathbin{/}\Delta\mathbin{/}\Omega\,\vdash\,P
, glossed as
\Gamma\to\Delta\multimap\Omega\Rightarrow P
.
This is not enough: since
P\multimap(A\Rightarrow Q)\ncong A\Rightarrow(P\multimap Q)
, writing programs of the latter type naturally requires another context,
\Gamma\mathbin{/}\Delta_{1}\mathbin{/}\Omega\mathbin{/}\Delta_{2}\,\vdash\,P
.
In general we may need any number of interleavings of
\Delta
and
\Omega
contexts.
Since our contexts handle the interaction of a graded effect (
\Omega
for finite maps) and a coeffect (
\Gamma
for the
maybe
comonad) on the category
\mathrm{Set}_{*}
(
\Delta
),
we hope to apply or extend prior work on combining graded effects and coeffects
[
12
]
.

Free grounding order

Following the pattern of
\otimes
i
, our rules ground finitely supported variables left to right.
This choice is arbitrary: there need only be some order which grounds all variables without circularity.
This ordering can discovered automatically for Datalog programs
[
7
]
.
Extending this to
\lambda_{\mathrm{FS}}
would free the programmer from thinking about grounding order.

Destructuring
\boldsymbol{\mathbin{\&}}
pairs

Outer joins like
\mathit{union}
are most naturally expressed as destructuring their
\mathbin{\&}
pair argument,
but standard linear/relevance typing rules do not allow this.
We suspect it may be possible by stealing rules from the logic of bunched implications
[
21
]
.

Patterns and finite maps

We would like to extend finite map
\lambda
and application to patterns, such as tuples
\lambda{(x,y)}.\>t
and
t\>(x,y)
.
Otherwise, for example,
currying/uncurrying of finite maps is quite tricky.

However, the unusual behavior of finite support contexts

Metatheory

\lambda_{\mathrm{FS}}
lacks metatheory.
Our semantics is a sketch; we have not proven semantic finite support or point preservation, nor syntactic weakening or substitution.
The need for
{\Rightarrow}\,\textsc{e}_{2}
should show this is surprisingly subtle.
Moreover, because of left-to-right grounding, substitution fails for finitely supported variables:

(\lambda{x}.\>t)\>u
may have a typing derivation when
t\{x\mapsto u\}
does not (see previous footnote’s solution for an example).
