Subjective Code Preferences in Experts and Large Language Models
Anna Mokhova, Subhabrata Dutta, Iryna Gurevych, Simone Balloccu

Abstract
Large Language Models (LLMs) have become increasingly popular for coding tasks, with subjective coding preferences being an essential element to adapt to programmers’ personal needs. Existing work overlooks such characteristics and mainly focuses on code correctness. In this study, we propose a typification of four subjective coding preference axes — complexity, commenting, modularity, and readability — motivated by common engineering habits and validated by 25 software engineers. We collect a dataset of ≈ 3,000 \approx 3,000 paired Python code snippets reflecting these axes, annotated by 73 experts who rate their preferences on a Likert scale. Using our dataset, we study how LLMs handle subjective coding preferences. We present 13 LLMs with pairs of solutions to the same programming task, first as textual descriptions and then as concrete code snippets. We find that models often prefer one option in natural language but the opposite when evaluating code. More consistent models (i.e., those that are coherent in their choices between deeds and words) frequently reveal positional bias: swapping the order of options changes the preferred alternative. We then use the five most consistent models to re-annotate the dataset. Compared to humans, models show polarized Likert distributions and notable divergence in ratings. A case study on GPT-5 reveals reliance on external assumptions and brittle reasoning. 1 1 1 Data available at https://CodePref-B07D

1
Introduction

In recent years, LLMs have become broadly used as coding tools
13
. To measure their coding capabilities, there is a need to assess the models’ prior knowledge and skills. This is required to differentiate between the system’s fundamental understanding of the task and its generalization power
9
, which might be specious at its logical core.

LLM evaluation in the coding domain typically involves benchmarks that target objective aspects such as code correctness and security
58
;
32
. This, however, limits the estimation to a "correct vs incorrect" paradigm and does not explain how LLMs behave when subjective coding preferences come into play. This is especially critical since LLMs can be inconsistent in opinion-based or value-related domains
62
. Focusing only on objective criteria also contradicts the fundamental definition of a
preference

6
, which is a set of
alternative
choices, where a more desirable choice precedes a less desirable one. Finally, evaluating code quality does not directly validate the model’s core understanding of the task that it is performing
36
.

In this work, we provide an extensive investigation of LLMs’ behavior across subjective coding preferences (Figure
1
). First, we introduce a set of coding preferences axes that are subjective (i.e., both preference values produce a working code) but can still be measured and shown from the previous work to be important for software development
52
;
10
: commenting, modularity, readability, and complexity.
We then generate a novel dataset of
\approx 3000
programming problems with paired solution snippets, where each snippet of a pair represents a different value on our preference axes (e.g., more vs less commented code to solve the same problem). This dataset is then fully annotated by 73 coding experts, using a Likert-6 scale to express their subjective preferences for each pair. Borderline annotations (slight preferences) are enriched by experts with textual rationale.

We use our generated dataset to analyze the behavior and alignment of 13 LLMs in two setups. First, we test if LLMs are consistent in expressing a utility at a textual level (e.g., "a more/less commented code") and code level (coding snippet solving the problem with more/less comments). All tested LLMs show severe inconsistency, choosing a specific textual preference, but then picking the opposite coding snippet, and most of the evaluated models exhibit positional bias.

Second, we let LLMs replicate our dataset annotation, and compare their preference distribution with that of experts: most models
predominantly choose the extremes of our selection scale), compared to the more balanced one of our experts. GPT-5, the only exception, more closely models the overall human distribution, but still shows severe divergence on a per-item basis. We also run a case study where we qualitatively inspect cases of disagreement between experts and GPT-5, showing reliance on external assumptions
and brittle reasoning, culminating in ignoring core knowledge necessary for a correct assessment.

To summarize, this paper provides the following three contributions (Figure
1
):

1.

A novel dataset of Python coding snippets showcasing subjective preferences, validated and annotated by expert software engineers (SE) (§
3
).

2.

First assessment of LLM consistency over subjective coding preferences, across natural language and code modality (§
4
).

3.

Analysis of the alignment and behavior between LLMs and humans with respect to subjective coding preferences (§
5
).

Related Work

Coding Preferences

Previous works related to LLMs’ coding preferences
58
;
32
inspect objective criteria, such as security or correctness

32
;
58
. These studies do not reflect the complexity of decisions and tradeoffs that a developer experiences
12
.
This tendency is also mirrored in existing datasets like CodeUltraFeedback
58
, CodePrefBench
32
, and OpenCodeInstruct
2
, which focus on tuning LLMs for software development problems, but not on preference alignment. It results in LLMs developing towards code generation correctness and ignoring humans’ priority for a more nuanced and complex approach to software development
4
. Some examples of the importance of this multi-criteria analysis include readability’s enhancement of software maintainability
7
;
52
, or development optimization across multiple objectives
30
. While some previous research integrates benchmarking to assess coding criteria beyond correctness
65
; it does not provide validation from the side of the end users, as opposed to our study.

Human-LLM preferences comparison

Being trained on vast amounts of natural language data, LLMs show similar decision heuristics to humans in text generation
50
, including preexisting biases and conceptual behavior tendencies. However, this human-like pattern is not exhibited in controlled binary-choice experiments, where the decision-making requires broader narrative support
21
and is systematically distinguished by positional bias
45
. This leads to LLMs being more prone to hesitating and admitting their limits in the presence of a clear dislike
29
. Additionally, AI systems are argued to better maximize the satisfaction of preferences and uncover hidden contexts by integrating normative reasoning with machine learning
66
. In this experiment, we enrich borderline preferences with textual rationale to gain a better, first-of-its-kind understanding of how humans and LLMs ground their choices with regard to decision-making in the coding domain.

LLM Alignment on Code and Natural Language

Prompt-based inference
49
;
57
has been shown to enhance LLMs’ performance across a variety of coding tasks, mostly generation
20
;
59
and testing
25
;
28
. LLMs also systematically fail in correctly performing “description-to-code” evaluations due to inherent biases and hallucinations within LLMs
22
. There is no up-to-date proof of the positive contributions of these methodologies to LLMs’ alignment between words and coding deeds. We address this in our study by exploring different prompting setups.

3.1
Coding Preferences

We define four coding preference axes, designed to be subjective but measurable. This means that choosing one value of the axis does not affect the code correctness; instead, the choice for each preference should be motivated by the individual professional experience, project requirements, or specific industry protocols. For our axes, we model:

Commenting

Appropriate code commenting benefits code maintenance, and speeds up debugging. However, excessive or redundant comments can be detrimental.
’Commenting’
utility represents the extent to which a code snippet contains commented lines, including the code documentation
41
;
40
.

Consider a code snippet
\mathcal{S}

\mathcal{L}_{\mathrm{total}}(\mathcal{S})
total lines,
and
\mathcal{L}_{\mathrm{comment}}(\mathcal{S})\subseteq\mathcal{L}_{\mathrm{total}}(\mathcal{S})

commented lines. The commenting score
CS(\mathcal{S})

\mathrm{CS}(\mathcal{S})=\frac{\left|\mathcal{L}_{\mathrm{comment}}(\mathcal{S})\right|}{\left|\mathcal{L}_{\mathrm{total}}(\mathcal{S})\right|}.

Modularity

Code modularity refers to the practice of breaking down a large program into smaller, independent, and reusable units called modules. Making a correct and balanced use of this coding feature can improve code organization, re-usability, and maintainability. Modularity is typically measured by the number of separate modules and functions, divided by the total number of code lines
60
;
54

\mathcal{S}
, with

\mathcal{M}(\mathcal{S})
distinct modules and functions, and

\mathcal{L}_{\mathrm{total}}(\mathcal{S})

\mathrm{MS}(\mathcal{S})

\mathrm{MS}(\mathcal{S})=\frac{\left|\mathcal{M}(\mathcal{S})\right|}{\left|\mathcal{L}_{\mathrm{total}}(\mathcal{S})\right|}.

Complexity

The degree of complexity of a code can have a profound effect on maintainability

Readability

Code readability is a fundamental coding characteristic
5
;
61

Human Preference Annotation

To compare humans and LLMs, we collect human preferences annotations for our dataset. We hire experts from Prolific

3

We verify their ability to differentiate preferences via a qualification task: given 8 coding pairs, experts are asked to mark those with a higher/lower degree of commenting/modularity or are more/less computationally complex. Only annotators with 100% passing rate are accepted.

Preference annotation

In the main task (example of the annotation UI in Appendix
G
,
Figure

11

Experts choose their preference among the two snippets, based on their working experience, via a Likert-6 scale (0 = Strongly prefer snippet A; 5 = Strongly prefer snippet B). The median option was deliberately omitted to obtain distinguishable preferences between A and B, since, otherwise, humans lean towards the neutral option

4
Evaluating LLMs’ consistency over subjective preferences

As a first experiment, we assess if LLMs can effectively understand subjective preferences when explicitly expressing them. Given a Python problem
z
from our dataset, we ask the LLM to choose between two preference options
x
or
y
(e.g. extensive or minimal commenting), to solve it. We do this with
x,y
represented as both text and code. Ideally, we expect the model to be consistent (e.g., "extensive commenting", and the snippet with more comments). This tells us to what extent LLMs recognize the code realization of a textual preference.

We note that our annotators are expected to have this ability, given their work experience. Regardless of this, they also demonstrate it in our qualification task with an acceptance rate of 100% accuracy to proceed with the main annotation task. We also note that human coders, during their job, do not explicitly state a preference: they apply it implicitly. An expert AI assistant, on the other hand, should motivate its choices, and a developer may even state their own preference before, to condition them (e.g. “keep in mind I prefer more densely commented code”).

Exploring Preference Behavior among LLMs and Humans

Next, we compare the distribution of preference values between humans and LLMs. To manage the computational and inference cost of our experiments, we select 3 open-weight and 2 vendor LLMs based on combined

Disagreement

We first compute the distribution of human Likert rankings from
Section

3.3
. For each coding pair
i

a_{i}

\binom{n_{i}}{2}

(j,k)

h_{ij}
and
h_{ik}
are their respective Likert ratings; for an LLM, it is the absolute deviation of its response
\ell_{i}
from the human mean
m_{i}

D

a_{i}
over all
N

\displaystyle a_{i}

\displaystyle=\begin{cases}\dfrac{1}{\binom{n_{i}}{2}}\displaystyle\sum_{1\leq j<k\leq n_{i}}\left|h_{ij}-h_{ik}\right|&\text{for human annotation}\\[10.0pt]
\left|\ell_{i}-m_{i}\right|&\text{for LLM annotation}\end{cases}

D=\frac{1}{N}\sum_{i=1}^{N}a_{i}

: despite producing realistic aggregate statistics, GPT-5 still frequently deviates from human judgement on individual examples. This indicates that a model can learn the "shape" of human opinions without learning what drives human decisions on specific cases. Llama3-70B shows the opposite failure mode: systematic distribution biases (
JSD
), but low
D
. This shows how a consistent directional bias can accidentally align with human medians. Generally, all open LLMs show extremely skewed distribution; DS-GRM-16B consistently shows the worst results for each metric, which could be attributed to it being the smallest model. Additional statistical analysis of these results is in Appendix
J
.

Qualitative analysis

Subjectivity can be trivial for judgments on Commenting and Modularity. Computational complexity, however, includes more intricate factors like worst-case complexity, expected input distribution, amortized complexity, or computational limitations. To understand the sources of disagreement along this axis, we perform a qualitative analysis of the experts’ judgments compared to GPT-5, as it shows the strongest
JSD
(
Table

4
). We inspect 20 randomly selected code pairs with at least one human annotator disagreeing with GPT-5. First, we observe
reliance on external assumptions
: GPT-5 (alongside some experts) occasionally presumes additional contexts beyond the problem statement; for example, it favours code with better average case complexity, while experts may consider worst-case complexity (Appendix
K
, ID 1).
Such hidden contexts of preferences can misdirect preference-learning
48
, and are of utmost importance in case of expert preferences. Similarly, GPT-5 sometimes relies on auxiliary metrics beyond complexity, like commenting, readability, pure-pythonic vs mixed-implementations, and usage of certain libraries such as Numpy (
K
, ID 2-4).
This sometimes leads to choosing an inefficient implementation due to surface-level simplicity. Finally, we observe consistent
brittle reasoning
in GPT-5: its rationale (
K
, ID 5) relies on superficial characteristics of the code, or even blatantly ignores known algorithmic complexity bounds, echoing prior findings
43
.

6
Conclusions

In this work, we inspected the behaviour of LLMs over subjective coding preferences, which are critical in expert coding, and often overlooked by traditional benchmarking. We introduced a novel dataset of coding snippets, that are expert-annotated with subjective preferences. We then used our dataset to identify patterns of behavior and consistency in LLMs. We find that LLMs cannot consistently identify the realization of subjective preferences, and struggle in identifying the same preference value when it’s presented as text or code. We also find severe positional bias, showing that even seemingly robust models just learned fixed selection patterns. Vendor models are less affected by positional bias, but still fall far from desirable consistency. Compared to experts, most tested models show extremely polarized distribution, opting almost exclusively for the extreme of the proposed scale. GPT-5 closely resembles the human distribution, but still suffers from consistent per-item divergence. Our qualitative study further reveals problematic patterns in how the model reasons.

We release our dataset to foster research in preference learning and expert coder models. Our dataset can be used to integrate coding preferences into human reinforcement strategies for further development of coding assistants that follow users’ personal choices. Additionally, acquired annotations and rationales can serve as a source for extended linguistic and statistical analysis for deeper insights into how LLMs understand code.

7
Limitations

Preference Matching and Preference Aggregation

We focus on four coding preference axes. We do understand, however, that subjective preferences may widen into many other axes we did not consider. Some examples of those from the related literature and results of our survey include code
maintainability
and
security
. We also acknowledge that preference axes could aggregate in complex ways, entangling and co-influencing each other. Our current framework represents the single-principal alignment for an AI system to match one unique preference. We reserve the analysis of complex aggregation of multiple axes within single coding snippets for future work.

Programming Languages

We limit our study to Python, excluding other programming languages. This choice was motivated by the extensive set of Python resources available online; however, other programming languages should be considered in future developments of our research line.

Model choices

The choice of our 13 LLMs is certainly limited, especially when it comes to the rapid development of new models, scales, and training approaches. In this work, we restricted ourselves to those baseline, coding, judge, and vendor models that showed the strongest performance in popular coding benchmarks. This is a conscious choice that lets us analyze the models that are more likely to be used by software engineers, when it comes to both open and vendor LLMs. This was also a necessity to keep a manageable computational requirement and experimental runtime: testing each model on
\approx 3000
paired snippets, in three prompting setups, including the swapped case, imposed us to take this choice. The same logic made us narrow our selection in our second experiment, where we picked the 5 most consistent models. Additionally, this was motivated by the necessity of keeping the inference cost of vendor model within our budget (accounting also for the budge spent in human annotation).

Assumption of expert competence

We consider our coding experts as the gold standard when it comes to real-world subjective preferences. However, we do not assume that our experts are always correct. We acknowledge that our qualification task, annotation setup, and sanity checks may be limited and not fully sufficient against all the challenges that come into the implicitly complex domain of subjective data annotation. We assume the trustworthiness of our expert based on our protocol, but also acknowledge that the convoluted nature of expert preference may need deeper analysis.

Application of the chosen binary scenario in coding assistants

This work investigates the preliminary task and fundamental premise of the successful implementation of modern coding assistants. More specifically, contemporary agentic practices implicitly or explicitly rely on the agent’s ability to understand what is preferred and or dispreferred. In the proposed setup, we directly evaluate if the LLM can understand the human’s input. However, we acknowledge the possible limitation of this proxy and do not state that it is a logically sufficient guarantee of the downstream competence of coding agentic systems.

Appendix A
Additional information on coding metrics

Although there is no single objective criteria for readability, discussions on this topic agree on the following characteristics that are usually associated with how easy code is to understand:
(1) Following coding standards, linters, pep8, etc.;
(2) Cyclomatic complexity, which is a way of evaluating the code based on a built graph and number of nodes, edges and connected components;
(3) Code maintainability, including above-mentioned cyclomatic complexity as well as relations between operators and operands;
(4) Subjective human perception of how code looks which is based on local factors. These are the surface features that aim to capture human notions of readability and include such traits as number of comments, average line length, and loop count.
We propose creating a combined readability model (Figure
10
) that, on one hand, contains overt code features, and, on the other hand, represents the established concepts of readability. For this purpose, a multiple linear regression is used with code local factors as independent variables and scores acquired by three methods that to some extent reflect readability as dependent variables on this data
35
. We then obtain weights for each of the local features, which allow us to reproduce the readability metric on any code snippet of any programming language. To filter code pairs from the dataset for the readability samples, we selected instances that were either more readable and less complex or less readable and more complex, using the above-described metric.

Appendix H
Sanity checks

Rationale annotation sanity check

Before acquiring rationale from experts, we conduct a short probing rationale annotation study to understand the potential risks and limits for this kind of experimental setup. We contacted 4 experts who had already done the numeric annotation task, and asked them to ground their previous choices in the written form (2 coding pairs per each annotator). We compare the obtained answers with the responses from ChatGPT and Gemini by BertScore
64
, as well as review them manually, to eliminate the use of LLMs for this round of annotation. This verification showed that both open-ended questions and a template can serve as a reliable source for collecting human rationales. In addition, we apply a combination of metrics on the sequences of numeric annotations for each participant to exclude lazy workers or participants whose previous annotations have been done mechanically. Those metrics include: entropy, switch rate (how often an annotator changes their label), switch symmetry (whether the annotator switches symmetrically and does random left-right clicking), percentage of using two midpoint labels together and separately, and frequency of the most repeated annotation sequence. We use the following thresholds for each metric: entropy
<1.43
; switch rate
<80\%
; switch symmetry
<0.375
; usage of each midpoint label separately
<23\%
; usage of midpoint labels together
<41\%
.

Appendix I
Experimental Setup

The experimental setup for pairwise and 6-scale preference setting uses a fixed random seed across Python, NumPy, and PyTorch, and enables deterministic CUDA behavior to ensure reproducibility. For some models of larger size (e.g., Llama3-70B, Qwen3-32B, and DS-Coder-33B), inference is run with 8-bit quantization. We use greedy decoding (
do_sample=False
) for deterministic token selection. The remaining settings, such as left padding and a maximum of new generated tokens, are standard implementation choices motivated by enforcing either binary-choice or N-token generation output. In some cases, the
max_new_tokens
hyperparameter was heuristically increased to avoid truncated outputs and ensure the model produced a complete decision.
