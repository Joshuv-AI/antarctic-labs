CodeTaste : Can LLMs Generate Human-Level Code Refactorings?
Alex Thillen, Niels Mündler, Veselin Raychev, Martin Vechev

Abstract
Large language model (LLM) coding agents can generate working code, but their solutions often accumulate complexity, duplication, and architectural debt. Human developers address such issues through refactoring: behavior-preserving program transformations that improve structure and maintainability. In this paper, we investigate if LLM agents (i) can execute refactorings reliably and (ii) identify the refactorings that human developers actually chose in real codebases. We present CodeTaste , a benchmark of refactoring tasks mined from large-scale multi-file changes in open-source repositories. To score solutions, we combine repository test suites with custom static checks that verify removal of undesired patterns and introduction of desired patterns using dataflow reasoning. Our experimental results indicate a clear gap across frontier models: agents perform well when refactorings are specified in detail, but often fail to discover the human refactoring choices when only presented with a focus area for improvement. A propose-then-implement decomposition improves alignment, and selecting the best-aligned proposal before implementation can yield further gains. CodeTaste provides an evaluation target and a potential preference signal for aligning coding agents with human refactoring decisions in realistic codebases.

However, success on issue resolution does not imply that agents can sustain code quality across iterations. SlopCodeBench

These observations suggest that while current methods excel at producing functional patches, they struggle to produce code that remains comprehensible and extensible over time.

Lack of challenging refactoring benchmarks

Refactoring is the software engineering practice of applying behavior-preserving transformations that improve structure and maintainability. OpenAI reports that they train and evaluate their models on large-scale code refactoring tasks, without disclosing their internal evaluation frameworks
(
22

. The academic community has also contributed benchmarks for refactoring: RefactorBench provides few-file tasks with syntactic tests
(
11

, and SWE-Refactor collects 1,099 refactoring of a fixed set of method-level refactorings from 18 Java repositories
(
33

These benchmarks have a key limitation: they only cover refactorings of small and limited scope, which results in them quickly becoming obsolete. For example,
GPT-5 Codex
already achieves
75\%
accuracy on SWE-Refactor.
Beyond this size limitation, these benchmarks do not measure whether the model can determine autonomously which refactoring should be performed. This distinction matters: to bootstrap a code base out of accumulated technical debt, agents must recognize when code has become unmaintainable and determine what transformations are necessary to restore clarity
(
25
)

A recent related study found that LLMs rarely identify refactoring opportunities on their own: given Java files as input, ChatGPT identified only 28 out of 180 refactoring opportunities that human experts had selected
(
19

Our work

In this work, we investigate this challenge extensively and use precise code-level measurements to assess whether state-of-the-art coding agents can autonomously discover and implement relevant refactorings in real-world code bases.
We introduce an alignment score that measures how many occurrences of undesired coding patterns are converted to desired versions, counting only functionally correct implementations.
Our results indicate a clear gap: while frontier models score highly on implementing complex refactorings that are specified in detail, achieving up to
70\%
alignment in our evaluation, they fail to mitigate undesired coding patterns correctly when no concrete refactoring is specified, achieving overall less than
8\%
alignment.
We introduce
CodeTaste
, a benchmark designed to measure this gap. We publicly release its leaderboard, our code and the dataset

A scalable pipeline for discovering refactoring instances.

We mine popular GitHub repositories for 100 large multi-file refactorings performed by human developers. For each task, we generate an executable environment and static analysis rules that match the changed code patterns. The latter support semantic dataflow reasoning within files, which provides more flexibility than syntactic matching, and is automatically verifiable. After the model applies a refactoring, we measure performance, ensuring that (i) the repository test suite passes and (ii) the static analysis rules confirm code pattern transformation.

Two complementary tracks for evaluating agent performance.

Our benchmark features two tracks: In the

evaluates whether agents can propose refactorings that align with human developer choices. In this track, the agent is only tasked to improve a general focus area. We discover that agents struggle significantly here, achieving only single-digit scores, even with oracle support.

We observe that frontier models consistently outperform lower capability models on our benchmark, with for example

Qwen3

2
Methodology

In
Figure

1
, we provide a summary of the
CodeTaste
pipeline. Based on a dataset of historic code changes, we (i) mine large, multi-file refactorings performed by human developers, (ii) translate each refactoring into task descriptions for our two tracks, (iii) build a reproducible execution environment that can run each repository’s unit tests, and (iv) generate static analysis rules that capture desired and undesired patterns of the transformation. We then run agents to produce a candidate patch and evaluate it using both the repository test suite and our static rules.

During evaluation, we task coding agents to reimplement the original human refactoring. These agents can interact with the task description, the codebase, and the test suite, and the execution environment, producing a final predicted patch.
Finally, we evaluate this patch using (i) the test suite to validate whether the functionality has been preserved and (ii) the static analysis rules to validate how consistently the refactoring was implemented.

3
Benchmark Construction

In this section, we outline our benchmark construction process, sketched in
Figure

2
.

3.1
Data curation

Each task instance in our benchmark corresponds to a commit in a codebase.
We obtain a list of commits for further processing using a three-stage pipeline.
We first query and keyword-filter candidate repositories and commits to prioritize 5000 commits that perform large refactorings.
Second, we prefilter to around 1000 commits by removing inaccessible repositories, documentation-only changes, and outlier diffs.
Third, we score commit messages and diffs with a small LLM and keep the highest-ranked 160 candidates.
We run these three steps four times, once for each of the years 2023, 2024, and 2025 from the GitHub Archive
(
13
)
, and once for the GitHub Activity Data dataset
(
12
)
.
The full details on the pipeline can be found in
Section

A.1
.

Our current pipelines and filters are designed to generate a benchmark of relatively small size, due in large part to the high cost of performing a refactoring, often exceeding 10 USD per task.
Our collection using can be scaled up trivially by leveraging additional base databases and modifying its filter criteria.

3.2
Task generation

For each task instance, we generate a structured, highly detailed task description modeled after a human-written GitHub issue using an LLM. The description is synthesized from the commit message, associated Pull Requests, including titles, bodies, and linked issues, and the code of the golden patch
X^{*}
.

The LLM is instructed to structure the task description as three components: 1)
Title:
A brief heading for the refactoring task. 2)
Summary:
A concise overview of the technical changes, and 3)
Why:
The rationale and relevance of the refactoring, with the goal of providing a highly detailed task description structured similarly to the instructions a human could write for a coding agent. The prompt used for this generation can be found in
Figure

13
.

3.3
Build Environment

To provide a stable and reproducible execution environment, our method utilizes a multi-phase bootstrap process that pairs each benchmark instance with a specialized containerized environment.

Base Container

The foundation is an Ubuntu-based container image with pre-configured toolchains across language ecosystems (details in
Section

A.2
).

Phase 1: Agentic Environment Setup

For each instance, our method spins up a base container and performs a shallow clone of
R
and
R\circ X^{*}
.
A coding agent is initialized inside the container with administrative privileges, time, and expense limit.
The agent is tasked with installing any additionally required system dependencies and creating scripts that allow reproducing a standardized execution environment for the repository. We provide the prompt in the Appendix in
Figure

11
and an example excerpt of the generated scripts in
Figure

12
.

Validation and Quality Gates

Upon completion of the environment setup phase, the framework validates the reproducibility of the environment by executing
\mathrm{exec}_{R}(T)
and
\mathrm{exec}_{R\circ X^{*}}(T)
using the standardized execution scripts. A bootstrapping process is deemed successful only if the following conditions are met:

\forall R^{\prime}\in\{R,R\circ X^{*}\}.\quad|T_{R^{\prime}}|\geq 10\quad\text{and}\quad\frac{P_{R^{\prime}}}{|T_{R^{\prime}}|}\geq\frac{3}{10}

Phase 2: Runtime Creation

After validation, the resulting image is transformed into a hardened runtime to prevent leaking golden solutions and standardize the interface for model evaluation. First, by removing history and network accesses, we ensure that the golden state
R\circ X^{*}
is inaccessible from the base state
R
during inference.
Second, we add a unified entrypoint script that serves as the primary orchestration layer.
This script is executed upon container start and enables execution of agents under restricted network access, extracting the generated patch
\hat{X}
for later evaluation.

Rule Formalization

A rule
\gamma
produces a multiset of witnesses on a codebase
R
, denoted
\Omega(\gamma,R)=\{\omega_{1},\dots,\omega_{k}\}

From these, we derive two metrics: (i) match count

and (ii) line coverage
\mathcal{C}(\gamma,R)=\bigcup_{\omega\in\Omega(\gamma,R)}\omega\subseteq L_{R}

\gamma

We categorize rules into additive (

\forall\gamma\in\Gamma^{+}:M(\gamma,R\circ X^{*})>0\wedge M(\gamma,R)=0

\forall\gamma\in\Gamma^{-}:M(\gamma,R)>0\wedge M(\gamma,R\circ X^{*})=0

The agent runs in two distinct passes to discover

We derive the open track description via a secondary LLM pass over the instructed track full description. In the end, we manually investigated all open track descriptions to confirm that they indeed do not reveal the actual refactoring.

Functional Correctness

To evaluate functional correctness of a predicted patch
\hat{X}
, we require no major regression of the test suite. Concretely, we require a minimum number
p_{R}
of test cases to pass on the patched code base
R\circ\hat{X}
, and a maximum number
f_{R}
of test cases to fail.
To determine
p_{R}
and
f_{R}
, we execute
k
times the test suites of both
R
and
R\circ X^{*}
. We then set
p_{R}=\min_{i\in\{1,\dots,k\}}(P_{R}^{i},P_{R\circ X^{*}}^{i})
and
f_{R}=\max_{i\in\{1,\dots,k\}}(F_{R}^{i},F_{R\circ X^{*}}^{i})
, where
P_{R}^{i}
denotes the number of passing tests of the
i
-th run on codebase
R
, and
F_{R}^{i}
failing tests respectively. Finally, we define the functional correctness score
\textsc{Pass}(\hat{X})=\mathbb{1}\left[F_{R\circ{}\hat{X}}\leq f_{R}\land P_{R\circ{}\hat{X}}\geq p_{R}\right]
.
We set
k=5
to account for nondeterministic tests
(
20
)
.

Instruction Following Rate

We assess adherence to the refactoring intent using the discovered static analysis rules
\Gamma
. Let
\mathbb{1}_{M}(\gamma,R)=\mathbb{1}[M(\gamma,R)>0]
indicate that rule
\gamma
matches in state
R
.
The instruction following rate (
Ifr
) measures the recall of additive and reductive rules in the resulting state
R\circ X
:
The additive rules (
\Gamma^{+}
) represent desired patterns, i.e., patterns that should match, while the reductive rules (
\Gamma^{-}
) represent undesired patterns that should not match. The additive instruction following scores
\textsc{Ifr}^{+}
is then the percentage of rules
\gamma\in\Gamma^{+}
that match on the predicted state of the repository
R\circ\hat{X}
. The reductive instruction following score
\textsc{Ifr}^{-}
is respectively defined as the percentage of non-matching rules. The total instruction following score
Ifr
is a weighted combination of the scores.
By construction,
\textsc{Ifr}{(X^{*})}=1
.

\displaystyle\textsc{Ifr}^{+}{(\hat{X})}

\displaystyle=\frac{1}{|\Gamma^{+}|}\sum_{\gamma\in\Gamma^{+}}\mathbb{1}_{M}(\gamma,R\circ\hat{X})

\displaystyle\textsc{Ifr}^{-}{(\hat{X})}

\displaystyle=\frac{1}{|\Gamma^{-}|}\sum_{\gamma\in\Gamma^{-}}\left(1-\mathbb{1}_{M}(\gamma,R\circ\hat{X})\right)

\displaystyle\textsc{Ifr}{(\hat{X})}=\frac{|\Gamma^{-}|}{|\Gamma|}

\displaystyle\textsc{Ifr}^{-}{(\hat{X})}+\frac{|\Gamma^{+}|}{|\Gamma|}\textsc{Ifr}^{+}{(\hat{X})}

Alignment Score

We combine the instruction following rate and the functional correctness into an
alignment score

\mathcal{A}
. Concretely, the alignment score
\mathcal{A}(\hat{X})=\textsc{Pass}(\hat{X})\times\textsc{Ifr}{(\hat{X})}
. The multiplication ensures that adherence to refactoring intent is only rewarded if the generated patch is also functionally correct.

Precision

Precision
Prec
(
\hat{X}
) measures the extent to which a patch
\hat{X}
avoids unrelated changes.
As defined in
Section

2.1
, a patch
\hat{X}
defines two sets of lines,
L_{\hat{X}}^{-}
and
L_{\hat{X}}^{+}
corresponding to additions and removals respectively.
For a given codebase
R
,
\mathcal{C}_{\Gamma}(R)=\cup_{\gamma\in\Gamma}\mathcal{C}(\gamma,R)
defines the set of all lines matched by the rule set
\Gamma
.
We then define additive precision
\textsc{Prec}^{+}
as the percentage of added lines
L_{\hat{X}}^{+}
that also match the additive rules
\Gamma^{+}
. Negative precision
\textsc{Prec}^{-}
is the percentage of removed lines
L_{\hat{X}}^{-}
that matched the reductive rules
\Gamma^{-}
. Precision

is the weighted average of these terms.

\displaystyle\textsc{Prec}^{+}(\hat{X})

\displaystyle=\frac{|L_{\hat{X}}^{+}\,\cap\,\mathcal{C}_{\Gamma^{+}}(R\circ\hat{X})|}{|L_{\hat{X}}^{+}|}

\displaystyle\textsc{Prec}^{-}(\hat{X})

\displaystyle=\frac{|L_{\hat{X}}^{-}\,\cap\,\mathcal{C}_{\Gamma^{-}}(R\circ\hat{X})|}{|L_{\hat{X}}^{-}|}

\displaystyle\textsc{Prec}(\hat{X})=\frac{|L_{\hat{X}}^{+}|}{|L_{\hat{X}}|}\,

\displaystyle\textsc{Prec}^{+}(\hat{X})+\frac{|L_{\hat{X}}^{-}|}{|L_{\hat{X}}|}\,\textsc{Prec}^{-}(\hat{X})

monetary budget per task; runs exceeding this limit are terminated and evaluated with available output.
GPT-5.2
hit this limit in 14 instances, compared to only 3 instances for
Sonnet 4.5
. The mean cost for
GPT-5.2
in instructed mode is
\$5.17
, compared to
\$3.46
for
Sonnet 4.5
and
\$0.59
for
GPT-5.1 M
. This is due to the aforementioned targeted patches by
GPT-5.2
, while
Sonnet 4.5
relies on cheaper search and replace commands (e.g.
sed -i
).

4.3
Results on the Open Track

Achieving high
Ifr
on the open track is significantly harder.
This is because agents are only provided with a high-level focus area and need to recover human architectural choices. The maximal achieved alignment score
\mathcal{A}
over all models is
7.7\%
in Direct Inference mode, as can be seen in
Figure

7(b)
.

Models need planning for large refactorings

When the models first propose a plan before implementing it (Plan Mode), there is a significant increase in
\mathcal{A}
. For
GPT-5.2
, the
\mathcal{A}
nearly doubles from
7.7\%
to
14.1\%
. On average, the scores increase by a total of almost
3\%
, corresponding to a more than
50\%
relative increase. This suggests that explicit reasoning before editing helps in recovering large-scale human refactoring intents. Case studies (
Section

C.1
) reveal that planning tends to yield repository-wide transformations that reflect high-level architectural thinking. The corresponding patches are approximately 2 to 3 times larger (measured by
|L_{\hat{X}}|
) and achieve up to a
72\%
relative increase in
Ifr
. The broader scope can come at the cost of up to
24\%
lower
Pass
rates (Direct vs. Plan).
Qwen3
exhibits the most significant decline, whereas
GPT-5.2
sees no decline. Details across all models and modes are presented in Appendix
Table

4
.

Suggestions generally include human choices

Among all generated proposals, the models more frequently suggest at least one human suggestion. This is visible in Oracle Multiplan, where they generate several proposals, and the closest plan to the desired refactoring is chosen by an LLM with oracle knowledge. In this setting
GPT-5.2
reaches an alignment score
\mathcal{A}
of
19.4\%
.
Interestingly,
Sonnet 4.5
does not improve in this setting, with its score dropping slightly from
10.2\%
in Plan mode to
9.7\%
. This might indicate that, when tasked to generate several possible refactorings, the model shifts into a different, less aligned distribution of refactoring plans.

4.4
Failure Modes in Open Track

To answer what the open track actually tests, we investigated a sample of solutions predicted by
GPT-5.2
and
Sonnet 4.5
and compared the golden solution with their solutions.
Some observed issues concern (a) fixating on salient, obvious subjects, e.g., a typo in the name of a class, and completely ignoring the broader focus area, (b) resorting to lazy, hacky workarounds, e.g., creating a compatibility shim to bypass updating hundreds of import statements, (c) relying on destructive, repository-wide replace-all string commands, leaving the codebase in a broken and inconsistent state, and (d) working on entirely different aspects of the system than required. While we cannot predict what a realistic upper bound for human alignment is on a refactoring, we observe that even the best current models have major issues choosing appropriate refactorings.
We include examples of LLM-assisted manual analysis on such cases in
Appendix

C
.

How much guessing is needed?

When generating the static analysis rules, we did not show the agent the modified code. This was done so that the agent would not overfit rules to the actual code edit. However, some of the rules assert that elements with certain names should appear in the codebase. We believe this could lead to harder rules in the open track. To quantify how much of a concern this is, we compared the
\textsc{Ifr}^{+}
and
\textsc{Ifr}^{-}
across modes. In Direct mode,
GPT-5.2
has
\textsc{Ifr}^{+}
of
8.9\%
and
\textsc{Ifr}^{-}
of
10.3\%
. In Plan mode,
\textsc{Ifr}^{+}
is
9.9\%
and
\textsc{Ifr}^{-}
is
17.2\%
, while in Multiplan mode
\textsc{Ifr}^{+}
and
\textsc{Ifr}^{-}
rise to
15.7\%
and
26.7\%
, respectively. This indicates that while some rules may involve guessing elements such as names, such problems likely affect approximately half of the additive rules. We provide detailed results in the Appendix in
Table

3
.

Related Work

Prior benchmarks have measured more basic refactorings conducted by LLMs or coding agents, which we detail in this section.

Single-File Refactoring Benchmarks

A number of benchmarks measure changes only on single-file edits.
RefactorMirror
(
19
)
is a Java-only benchmark that checks whether LLM refactoring suggestions align with human preferences. They observe generally low alignment with human preferences, but do not verify the proposal by having the LLM implement the refactoring.

8
evaluate the ability of Starcoder to decrease generic code complexity metrics on 30 Java tasks.

28
measure code complexity metrics when tasking LLMs to refactor C++ and C code.
The aider team introduced a benchmark for Python code that evaluates function-level refactorings
(
1
)
.
Finally,
5
present instructions of varying degree of detail to LLMs to refactor Python code on a function-level and measure whether generated code matches manually specified syntactic properties.

Multi-File Refactoring Benchmarks

RefactorBench
(
11
)
analyses GPT-4o refactoring suggestions and implementations on a 100-instance Python dataset. On average, they edit 4.3 files and test instruction following with syntactic validation against expected structures.
SWE-refactor
(
33
)
is a Java-only benchmark for simple, few-file, and line refactorings
MiniCode
(
16
)
measure whether LLMs can successfully discover shared code and extract it into a library function, thus limit themselves to a fairly simple task.
In our benchmark, the average number of edited files
91.52
, significantly higher than prior works. Further, our work covers
6
distinct languages. Thus,
CodeTaste
is a significantly more challenging benchmark, even in the instruct track.

Repository-level Code Benchmarks

Spearheaded by
15
, evaluating coding agents on the autonomous resolution of real-word repository-level tasks quickly became the gold standard for assessing their capabilities. While initial work focuses on issue resolution
(
15
)
, follow up work proposed benchmarks on feature addition
(
17
;
10
)
,
unit test generation
(
20
)
, function generation
(
18
)
, code performance
(
14
)
, and security
(
6
)
.

Methods to improve refactoring

26
evaluate whether models can decide when to extract code into external methods.

35
evaluate the function-level capability of models at rewriting Python code into idiomatic expressions.

30
similarly prompt GPT-3.5 with few-shot prompts to evaluate its refactoring capabilities.
All of these methods are limited to very specific refactorings, while our benchmark covers a wide range of potential refactorings.

6
Conclusion

We introduced
CodeTaste
, a benchmark for evaluating refactoring agents on real, multi-file changes mined from open-source repositories. Our pipeline pairs each refactoring with executable environments and OpenGrep-based static rules that verify the intended transformation beyond test passing. Our benchmark features two complementary tracks: an instructed track that measures diligence in the execution of detailed refactorings, and an open track that measures alignment with human refactoring choices under underspecification.

Our results demonstrate that when provided with explicit refactoring instructions, current agents achieve relatively strong, yet unsaturated, performance. GPT-5.2 stands out as the most capable model, achieving a compound alignment score
\mathcal{A}
of 69.6%, leaving room for improvement across the board.
Alignment collapses when only a focus area is provided. Propose-then-implement strategies and oracle selection over multiple plans increase alignment by up to
2.44
-fold, yet remain far from human choices. These findings highlight that autonomous judgment about
what
to refactor remains a key bottleneck. We hope
CodeTaste
serves as both a rigorous evaluation target and a preference signal for training agents that can preserve long-term code quality, and we see expanding the dataset, strengthening rule and test coverage, and learning better proposal mechanisms as promising directions for future work.

Appendix A
Experimental Details, Ablations and Case Study

In this section, we provide additional details about the implementation, hyperparameters, datasets, and so on.

A.1
Data curation pipeline details

We obtain a list of commits for further processing using a three-stage pipeline.

Stage 1: Querying and Keyword Filtering

We filter out all repositories with less than 90 stars.
Among those, we search for commits that edit at least 45 files and feature specific keywords.
Concretely, let
K^{+}
and
K^{-}
denote the sets of keywords indicative of refactoring and non-refactoring commits, respectively. We further distinguish between strong (
K^{\pm}_{\text{strong}}
) and weak (
K^{\pm}_{\text{weak}}
) keywords, which form subsets of
K^{+}
and
K^{-}
.
For instance,
deduplicate

\in K_{\text{strong}}^{+}
,
reorganize

\in K_{\text{weak}}^{+}
,
fix

\in K_{\text{strong}}^{-}
, and
lint

\in K_{\text{strong}}^{-}
.

Commit messages
M
of candidate commits must satisfy:

\text{Count}(M,K^{-}_{\text{strong}})=0\quad\text{and}\quad\frac{\text{Count}(M,K^{+})}{\text{Count}(M,K^{-}_{\text{weak}})}\geq 2

We then obtain the top 5000 commits sorted lexicographically descending by (
\text{Count}(M,K^{+}_{\text{strong}})
,
\text{Count}(M,K^{+}_{\text{weak}})
, #stars, #files changed).

Stage 2: Prefiltering

We remove all repositories and commits that are not accessible anymore, i.e., have been deleted or made private.
To exclude pure documentation changes, we require a minimum of 25 edits in files that have a file extension of typical programming languages, such as
.py
or
.cpp
.
Via manual inspection, we determine that we need to remove extreme outliers, which include, for example, entire virtual environments.
We retain only those commits that satisfy:

0.5p_{10}\leq\text{changes}\leq 2p_{90}

where changes refers to the number of added or removed lines, and the number of created, deleted, modified, or moved files.
Finally, to exclude highly repetitive and simple search-and-replace refactorings, we sort the results by the ratio of
\frac{|\text{diff}_{c}|}{|\text{diff}|}
, where
|\text{diff}_{c}|
is the size of the Gzip level 6 compressed diff (excluding file context) in bytes.

Stage 3: LLM Scoring

In the final step we use a small LLM (
Claude 4.5 Haiku
) to analyze the commit messages and code diffs. The prompts for this step can be found in
Figures

9
and
10
.

First, the LLM is prompted to score the commit message across several dimensions: a score for being a project-wide change
S_{\text{large}}
, a score for behavior-preserving refactoring
S_{\text{refactor}}
, and a message cohesion score
S_{\text{cohesion}}
.
The model also estimates a length penalty
P_{\text{length}}
for multi-topic messages, a triviality penalty
P_{\text{trivial}}
for simple edits, and a penalty for general uncertainty
P_{\text{unc}}
.
We retain the top 1,120 candidates based on the overall message score
S_{\text{msg}}
calculated as:

\displaystyle S_{\text{msg}}

\displaystyle=(0.35S_{\text{large}}+0.45S_{\text{refactor}}+0.2S_{\text{cohesion}})

\displaystyle-(0.2P_{\text{length}}+0.2P_{\text{trivial}}+0.2P_{\text{unc}})

Next, the LLM is prompted to analyse the code diff, focusing on the refactoring likelihood
S_{\text{refactor}}
and the estimated complexity
S_{\text{complexity}}
of the change. It also identifies penalties for mixed content
P_{\text{mixed}}
, evidence of behavior-altering logic
P_{\text{risky}}
, signs of automation
P_{\text{auto}}
, uncertainty
P_{\text{unc}}
, and the presence of trivial changes
P_{\text{trivial}}
. The diff-specific score
S_{\text{diff}}
is defined by:

\displaystyle S_{\text{diff}}

\displaystyle=(0.8S_{\text{refactor}}+0.2S_{\text{complexity}})-1.5(0.4P_{\text{mixed}}

\displaystyle+0.2P_{\text{risky}}+0.1P_{\text{unc}}+0.15P_{\text{trivial}}+0.15P_{\text{auto}})

We retain the top 160 candidates based on a combined score
S_{\text{total}}
that prioritizes the diff analysis over the commit message:

S_{\text{total}}=\frac{S_{\text{msg}}+3S_{\text{diff}}}{4}

Running the pipeline

This pipeline is run four times, once each on the main table of the GitHub Activity Data dataset
(
12
)
and the three main tables for 2023, 2024 and 2025 respectively in the GitHub Archive
(
13
)
, filtered to
PullRequestEvent
for merged pull requests. We obtain the count of "stars", an indication of popularity, for each repository from
9
.
The final result are
4\times 160=640
candidates.

A.2
Details of the execution environment agent

We use a polyglot container based on Ubuntu 24.04 with pre-configured toolchains and version managers for common language ecosystems. The base image includes: (i) Python 3.8–3.11 managed via
uv
, (ii) Node.js 22.12.0 (default) managed via Node Version Manager (NVM), (iii) Go v1.23.4 and a Rust toolchain (
cargo
), (iv)
OpenJDK
, and (v)
C/C++
via GCC/Clang.

The build environment agent,
Sonnet 4.5
in the
Claude Code
harness, is restricted to
\$5
cost and
90
minutes time.
To ensure portability of the benchmark, we limit the size of the writable storage layer, after all setup is completed, to 5GB. Further, we enforce a 15-minute time limit on running the test suite.
This container is then committed.

In the runtime setup, we concretely remove the git commit history and remote origins to prevent leakage of golden commits.

A.3
Details of the rule agent

In this section, we detail the specific commands that the rule discovery agent can use.

•

BashExplore
R
(cmd)
: Executes a set of read-only shell commands in the base codebase
R
to identify relevant code patterns (e.g.,
ls
,
rg
).

•

Register(
\Gamma_{\text{candidates}}
)
: Submits candidate rules in
yaml
syntax.
Without loss of generality, we show the registration of additive rules only.

Registration:
Every valid additive rule is registered:

\displaystyle\Gamma^{+}=\Gamma^{+}\cup\{\gamma\in\Gamma_{\text{candidates}}

\displaystyle\mid M(\gamma,R\circ X^{*})>0

\displaystyle\land M(\gamma,R)=0

\displaystyle\}

To prevent redundant rules, candidates must be sufficiently distinct from previously registered rules; we require pairwise Jaccard overlap of matched lines to be at most
0.95
.

Feedback:
For each
\gamma\in\Gamma_{\text{candidates}}
, the agent receives the match counts
M(\gamma,R)
and
M(\gamma,R\circ X^{*})
, as well as rejection reasons (if applicable).
In the case of execution failures (e.g.,
SyntaxError
or
OpengrepError
), the agent is forwarded parts of error message for refining the rules in the next iteration.
For highly discriminative but invalid rules where
M(\gamma,R\circ X^{*})>10\times M(\gamma,R)
, the agent is provided with a witness
\omega\in\Omega(\gamma,R)
to facilitate adding exemptions.
2
2

2

In many real-world refactorings there are edge cases such as unadjusted examples that can prevent a rule from reaching
M(\gamma,R)=0
.
Providing witnesses for these matches allows the agent to construct more general patterns by exempting specific outliers.

•

Finish()
: Signals completion and returns the valid registered rule set.
