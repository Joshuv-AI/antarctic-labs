ABSTRACT
Because surveillance and tracking are common in next generation wireless protocols, a user may
want to have extra information about a cellular network before connecting to it.
The thrust of this research answers the question: how much information can a user device get about
a 5G cellular core network as a function of the amount of information the user device provides to
the network? In answering this fundamental question, the project creates:
 • The prototype of a tool for fuzzing 5G cellular cores
 • An analysis of broadcast system information for determining network architecture
 • A model for analyzing error handling during the attach process to identify the type of 5G
 core with 100% precision
 • A proposal for a proof of concept for spoofing RF signals to maintain location privacy of a
 device

EXECUTIVE SUMMARY
We want to be able to use a user device to gather enough information to characterize a 5G core so
that we can determine whether the 5G core is Ericsson, Nokia, Samsung, Huawei, etc. We do not
want to provide the 5G core information about the device (identity or location). How much
information does the device have to give away to have 100% accuracy on the core classification?
Without providing any information (passive monitoring), we analyzed that if we have system
information (SI), we can determine the type of non-public network and the type of connected
devices. We can also map relationships between public and private networks. Modeling the public
and private networks may provide a method for determining the resiliency of public networks in the
face of cascading private network failures.
We modified open-source network stacks and used commodity Software Defined Radios (SDRs). By
sending a single message to the 5G core, we can trigger an error condition for which each tested
core responds differently. Our data analysis models accurately predicted the correct 5G core 100%
of the time with the transmission of a single message.
Our tests zeroed all identifying information during the attach process to the 5G base station and for
the single message to the 5G core. Zeroing out information is a proxy for randomizing identifying
information like subscriber information or authentication keys.
As part of an in-depth analysis of location privacy, we researched a proof-of-concept plan for
mitigating 5G positioning. We believe we can significantly reduce the accuracy of 5G positioning by
obscuring information sent to other base stations.
So, we proved that we can classify multiple open source 5G cores and one commercial 5G core with
a single message to the 5G core. We do not have to send identifying information to the base station
or 5G core and we have outlined a method by which we can obfuscate our device location.

2. NEXT GENERATION WIRELESS OPPORTUNITIES
TOMCAT5G expected that we could use software defined radios (SDRs) with open source 5G
protocol stacks to gather information on 5G cores. We hypothesized that we could take advantage
of differences in 5G protocol implementation or 5G core deployment to characterize a 5G core.
Our research focused on getting enough information from the 5G core without providing any
information (about identity or location) to the 5G infrastructure.

2.1. Microservice architecture
The 3rd Generation Partnership Project (3GPP) 5G protocol standard outlines a microservice
architecture for next generation cellular communications. This microservice architecture, generally
called service-based architecture (SBA) fundamentally changes the deployments and business plans
of the telecom industry. Instead of large servers containing monolithic cellular packet core, 5G
allows telecoms to distribute microservices to devices at the edge.
Figure 2 (3GPP, 2025) shows the 3GPP SBA as defined by the standard. The TOMCAT5G team
hypothesizes that this extensive SBA affects the complexity and flexibility of the standards. This
complexity and flexibility can be leveraged to identify specific implementation mechanisms, and
therefore specific vendors (like Nokia, Ericsson, Samsung, Huawei, ZTE, etc.).

2.3. Software Defined Radio
There are multiple mature SDRs that can be used to implement base stations (gNBs) or user
endpoints (UEs). Two notable SDR companies are Ettus and Lime.
The 5G software stack associated with UEs is more challenging. There are two open source 5G
stacks for UEs, OpenAirInterface (OAI) (OpenAirInterface Software Alliance, 2025) and Software
Radio Systems (SRS) (Software Radio Systems, 2025). The SRS is not continuing development or
maintenance of the srsUE code base. It is missing critical features and does not connect to most
commercial base stations. OAI, on the other hand has invested significantly in their user endpoint
software stack (OAIUE). At the time of the start of the TOMCAT5G project, OAIUE and the
OAI gNB were not as mature as srsUE and the SRS gNB.

3. PROVIDING 5G CORE INFORMATION WHILE PROTECTING USER
 PRIVACY

3.1. Fully Passive Survey
Passive surveys are ideal because no user privacy is compromised. They are often the first line in
understanding a network. Passive surveys provide Master Information Block (MIB) and System
Information Block 1 (SIB1) messages broadcast from the base stations. Survey tools provide MIBs
and SIBs (Minimum System Information or SI) as part of existing tools like tools from Keysight and
Rohde and Schwarz. Because a fully passive survey provides the least risk, we studied whether
broadcast SI could provide enough information to identify the type of 5G core.
SI provides the public land mobile network number (PLMN). These are publicly identifiable and
regulated names. The first 3 digits of a PLMN are the mobile country code (MCC). The remaining
digits are the mobile network code (MNC). Private 5G and LTE networks are called non-public
networks (NPN). Their PLMN is static at 9999999.
Often, the PLMN number and lookup table provide sufficient information for users. This is
generally known. The motivation for TOMCAT5G was an exploration of the relationship between
information and privacy in next generation wireless protocols. The tools and models designed by
TOMCAT5G can be used in the following situations:
 1) Determining the type of private 5G network
 2) Mapping the relationship between a telecom operator (e.g. Verizon) and a core provider (e.g.
 Ericsson)
 3) Verifying the relationship between a telecom operator and a core provider
Besides the most obvious information provided in a fully passive survey, we studied other
information that can be gleaned, especially for non-public networks (NPNs). Appendix A shows
this study.
The two main conclusions of the study are:
 1) We believe that fully passive surveys of NPNs can provide significant information about the
 type of NPN and the type of devices attached to the NPN. For defensive purposes, it’s
 crucial to understand what information can be gleaned from a deployed network.
 2) Public networks are often used to deploy NPNs via slicing or as a backup network in case
 the NPN fails. We propose mapping the public and NPNs to understand how failures in
 NPNs cause congestion in public networks and to evaluate the probability of cascading
 failures on the public or private networks.

3.2. Configuration Analysis Tool for 5G
CAT5G, the configuration analysis tool leverages initial work on an audit tool for the Zea project
(PI: Andrew Hoffman). CAT5G modifies 5G open-source software stacks. In addition to
modifying the state machine, the CAT5G team modified the configuration files and log files.
Appendix B shows an example of a configuration file. The CAT5G source code is archived on the
Sandia network. CAT5G has multiple features:
 • Multiple effects possible – No recompile.
 • Modify messages by bit, byte or protocol-specific enumerator

 15

 • Delay/discard messages
 • CAT5G Controller
 • Allows remote control of multiple runs of different effects (with or without
 network restart)
 • Stops test when requested criteria are met
 • Generalized for different test suites

The TOMCAT5G team implemented CAT5G on both OAIUE and srsUE. Because the srsUE and
SRS gNB were more mature at the time of development, and because we could attach the SRS gNB
to various 5G cores, we chose to use the SRS software stack for gathering data. The advantage is
that we can remove the base station as a variable. The disadvantage is that we must connect an SRS
gNB into the 5G core being tested.
SRS has partnered with a group RANTester-UE (RAN Tester UE, 2025) to continue some
development of the srsUE (now RANTester). At least some of the CAT5G (fuzzing) work has
been duplicated by the RANTester. The code and corresponding paper were released in May 2025.
The core characterization and RF spoofing work of TOMCAT5G has not been duplicated. The
team recommends that any follow-on core characterization use RANTester-UE or 5G-Pentest-UE
(discussed below).
Barkhausen-Institut has adopted OAIUE to implement the same functionality as CAT5G. 5G-
Pentest-UE (Riedel, 2025) is open source and can be used as CAT5G is used. The code and
corresponding paper were published in August 2025. The core characterization and RF spoofing
work of TOMCAT5G has not been duplicated. The team recommends that any follow-on core
characterization work use 5G-Pentest-UE or RANTester-UE (discussed above).

4.3. Preprocessing
To get the data ready for training and testing by a machine learning model, we first perform
preprocessing on the raw data, using the protocol_parse.py script. The original data has lines that look
like
<timestamp> [<protocol>] message
Sometimes there are multiline messages, but the parser should handle it. Timestamps are stripped
and ignored, unless --timestamp is specified, in which case relative timestamps are produced. The flag -
-duplicates will remove any duplicate messages, which can occur occasionally and potentially distort
frequencies of tokens.
The script, src/preprocess/protocol_parse.py, formats the data and organizes it by protocol, namely
 • ETC: Bucket for everything but NAS, PDCP, and RRC.
 • NAS: Non-access stratum, a protocol managing communication between UE and gNB.
 • PDCP: Packet Data Convergence Protocol manages data transmission and security.
 • RRC: Radio Resource Control includes connection establishment and other configuration.
 • TOTAL: Includes all the above
For the most part, utilizing TOTAL was the most advantageous for machine learning classifier
performance.

directory and replicate it in the output directory. Each log file will have five different versions as
output, with the original filename appended with ETC, NAS, PDCP, RRC, and TOTAL.

4.4. Tokenizing
After preprocessing, the next step is to train a tokenizer. Below is an example invocation
cd src/tokens
python train_bpe.py --inputdir <data dir>/CuratedData/Cleaned\
 --save <output>\
 --normalizers filters/UEFilters.txt
The normalizers remove parts of the file that are not helpful for classification, too specific, or
provide identifying information specific to the experimental setup that will not be found in a real-
world environment. The normalizers we found useful over the course of the project are found in the
src/tokens/filters directory. The UEFilters.txt file contains the normalizers used for UE logs. Each in a
filter file should be of the form:
<regex>-<replacement>

 24

<regex> is a regular expression, specifically to fulfill the first parameter of a python tokenizer.Regex
(Hugging Face, 2025). Whitespace before the regex and after the regex is ignored.
<replacement> is the text that should replace the regex. Every character after the -> is used, even
whitespace, but not the final newline. Doesn't support a replacement that is multiple lines.
Training the tokenizer can take some time. Training the tokenizer on all of Curated/Original/normal
and Curated/zeroed_IMSI_and_zeroed_IMEI_and_zeroed_PEI took 85 minutes.

4.5. Training Models
We focused on logistic regression as the machine learning model for classifying cores based upon
logs. Logistic regression is a simple model, but appeared sufficient for identifying cores, and
additionally, is inherently interpretable. Below is an example invocation to train and test a logistic
regression model:
cd src/run
python logistic_regression.py --dir <data dir>/CuratedData/Cleaned/normal/\
 --tokenizer <tokenizer location>\
 --ngram_range 1 1\
 --vectorizer count\
 --test NO_SEC_MODE_COMPLETE\
 --protocol TOTAL\
 --rrcr 6\
 --weight_threshold 0.001\
 --output_prefix output/<identifying info>\
 --n_splits 5

4.5.1. Explanation
 • --dir The input directory. This should point to a subdirectory under CuratedData/Cleaned.
 • --tokenizer This should point to the tokenizer defined in the previous step.
 • --ngram_range This is two integers, indicating the range of n-grams to use. For example, 1 1
 indicates to use only single grams, i.e. the original tokens, while 1 3 will use 1-grams, 2-
 grams, and 3-grams.
 • --vectorizer Either count or tfidf. Experimentally, we found count to work better.
 • --test What test stage will be utilized, see Table 2.
 • --protocol Which protocol will be used, see Table 3
 • --rrcr Which rrcr value to use, see Figure 7
 • --weight_threshold A float, which determines which features are considered important. If set to
 too large of a value, the script will throw an exception, and you should try setting it smaller.

 25

 • --output_prefix This will be prepended to the output files, so should include identifying
 information.
 • --n_splits The number of folds to use in stratified k-fold cross validation.
The command will generate a json file, _experiment.json. It will contain all the experimental results
for a common set of hyperparameters and experimental settings. Many of the common experimental
settings are encoded in the directory name under the Cleaned directory. Other hyperparameters are
included in the json file under the hyperparameter section, which right now only includes the ngram
range.
To make it easier to run across all data, there is a script: src/run/runall.sh Some of the parameters are
currently hard-coded, but you must specify the directory location of the cleaned UE logs and the

Results are scored according to multiclass and binary settings. With multiclass, each core and its

Important weights will be discussed later under Explainability. Metrics are included, namely
accuracy, average precision, precision, true positive rate, false positive rate, true negative rate, and
false negative rate, and a confusion matrix, and are used to evaluate the performance of a classifier.

4.6. Explainability
Logistic regression is inherently explainable, as the model consists of weights per input parameter.
Large positive weights indicate a positive correlation between the target class and the associated
input parameter. Negative weights indicate the opposite. In each experiment json file, important
weights are listed, ordered in decreasing order of absolute magnitude. Each entry has the token that
was deemed important and the associated weight. The important weights section is vital to
understanding how the classifier works and what parts of the log files are valuable to determining
the core. It is also aids in identifying features that are too specific or cases of overfitting.

4.8. Zero-shot to Few-shot
When used in the field to identify a core, it is likely that we will need to

 30

 • recognize when a core has not been seen before, and
 • build an updated classifier based on a single or few log samples from this new core. While
 logistic regression worked well so far in our experiments with a relatively small number of
 examples, it will likely encounter problems as it is deployed in the wild. We may need a
 model with greater representational power. However, more complex models need more
 examples to train them. A relatively new subfield of machine learning, known as zero-, one-,
 or few-shot learning, aim to train powerful models with very few examples.

4.8.1. Siamese neural networks
Siamese neural networks (Neculoiu, 2016) is a few-shot learning that may fulfill both the need to
recognize when a class has not been encountered and train the model from just one example of the
new core. Figure 8 shows the architecture of Siamese neural networks (SNN).

 Figure 8: Siamese neural networks
One challenge of applying SNN to text is the representation of the input, which is variable and long
for our problem of representing 5G/UE connection logs. The typical approach is to create an
embedding space, eventually creating a fixed-sized vector that represents the semantic information
of the provided text. This step will require plenty of general 5G/UE connection logs to train but will
not need to be retrained when used in the field and can remain static.

4.8.2. Approaches to dealing with long sequences
 • The log files can be long, so approaches that account for long sequences are needed.
 Transformers don't scale well with long sequences, as the attention mechanisms grows
 quadratically with sequence length. The LongTransformer (Beltagy, 2020) has an attention
 mechanism that grows linearly, allowing it to process sequences > 32,000.

5. ADVANCED PRIVACY TECHNIQUES – RF SIGNAL SPOOFING
CAT5G provides privacy by:
 • Zeroing IMSI and authentication key material to show randomization of USIM identifiers
 • Not sending a sounding reference signal (SRS)
 • Delaying messages (because of logging)
However, CAT5G cannot connect to commercial base stations. Once of many reasons why the
srsUE code base does not connect to commercial base stations may be the lack of a sounding
reference signal.
TOMCAT5G researched advanced positioning methods for 5G and created a proposal for
maintaining position privacy while connecting to base stations. The proposed solution for
mitigating the need for an SRS supposes that all current techniques used by CAT5G, and randomly
modifying RSSI continue to be implemented.

5.1. 5G location measurements
Device location is critical to fast handover in 5G. Release 16 of the 3GPP specification provides
using the uplink sounding reference signal (SRS) for localization as well as its original intent,
characterizing and optimizing uplink traffic (ShareTechnote, 2025).

The SRS is configured and controlled by the home base station (the gNB to which the device is
attached) within the boundaries of a device capability. The gNBs also send a reference signal
used for location, the positioning reference signal (PRS).

Location using GNSS is used considerably at the device level and location requests from the 5G
core to the device request GNSS location. GNSS spoofing is outside the scope of this project.
However, generally, GNSS location can be spoofed by the device at the protocol level.

5.1.1.      UL-TDoA
The Uplink Time Difference of Arrival is a method for location using the SRS. Time synchronized
gNBs receive and record the time of arrival of an SRS from a device. The gNBs share the times of
arrivals and the differences of these arrival times can be used to determine the device location
relative to the gNBs.

5.1.2.      UL- AoA
The Uplink Angle of Arrival is a method for location using the SRS usually with gNBs with large
antenna arrays. Time synchronized gNBs receive and record the angle of arrival of an SRS from a
device. The gNBs share the angles of arrival for a particular SRS and the differences of these arrival
angles can be used to determine the device location relative to the gNBs.

 33

5.1.3.    Multi-RTT
The multi-round trip time method uses the SRS and the PRS to measure time differences across
multiple (at least 3 gNBs and the UE). Multi-RTT does not require synchronized gNBs.

5.1.4.    DL-TDoA
The Downlink Time Difference of Arrival is a method for location using the PRS. A device receives
and records the times of arrivals of the PRS for at least 3 gNBs. The device can use these to
determine position but is more likely to send the information to its home base station for calculating
the position.

5.1.5.    DL-AoA
The Downlink Angle of Arrival is a method for location using the PRS. A device receives and
records the angle of arrivals of the PRS for at least 3 gNBs. The device can use these to determine
position but is more likely to send the information to its home base station for calculating the
position.

5.1.6.    Cell-ID
The gNB can provide the cell-id of the connected UE. When gNBs have massive phased arrays of
antennas, or in networks that are very dense, the cell-id can provide sufficient location.

6. CONCLUSIONS AND NEXT STEPS

 1. (Passive Monitoring) - Using System Information and PCAPs to passively characterize some
 5G core features

  A.1.1. What is a non-public (private) network?

  public telecom use. Private networks often use a subset of the unlicensed spectrum specifically
  for their use. Private networks are not prescribed to use specific frequencies, however.
  Frequency information is not sufficient for determination that a 5G base station is servicing a 5G
  non-public network.
  The choice of frequency bands can be used to characterize a network known to be a private
  network, though. For example, 2.4GHz, 5GHz, and millimeter wave bands are used for in-house
  automation and sub 900MHz bands for long-distance sensor applications.

A.2. System broadcast information and 5G identification
5G base stations broadcast system information required for connection to a network in two
messages. The master information broadcast (MIB) contains enough information to allow a
device to synchronize to a network and decode its messages. The system information block 1
(SIB1) contains enough information to attach to the network. The MIB and SIB1 are often called
the Minimum System Information for a network (MSI). They are always broadcast.
 We propose to identify 5G network characteristics by analyzing minimum system information
broadcast by base stations.

 49

A.2.1. MIB
Figure A 5 (5g nr master information block (MIB), 2025) shows the MIB. From the MIB, the
device determines how to find and decode the SIB1.

 Figure A 5: Master Information Block (MIB)
We can analyze the MIB for some information.
If the cellBarred bit is set, the base station is performing congestion control, or the network is
fully joined. This provides some evidence that the base station is servicing a private network as
congestion control in a public network is performed proactively by moving connections between
base stations to avoid the situation. This data is correlative and rare.
 The MIB does provide enough information to determine whether the network is a stand-alone
network or a non-standalone network (with LTE control plane and 5G data plane). The device
(UE) uses the subCarrierOffset and the pdcch-ConfigSIB1 to determine the presence of a SIB1.
If there is a SIB1, the MIB is for a base station servicing a 5G standalone network.

A.2.2.    SIB1
The SIB1 can provide significant information about the type of 5G network as well as features
supported by the network. The amount of information provided by the SIB1 increases with each
release of 5G. Using release 15, we can use correlation to provide some confidence level
regarding whether the serving network is a private network. By release 18, we can identify the
type of private network, whether reduced capability devices can be connected, and whether they
can be connected by a VSAT gateway.

APPENDIX C. CORE IDENTIFICATION USING PCAPS

The Tomcat project largely focused on identifying 5G cores through UE logs, but some effort was
expended to see if pcap files could be used instead.

C.1. The Data
A small set of files were captured for Aether, OAI, and Open5gs cores, a total of 10 files for Aether
and OAI and 5 for Open5gs.
The data for the packet experiments is currently stored within a shared windows network drive:
\\snl\Collaborative\tomcat5G\TOMCAT\CuratedData\PacketCaptures.
To packet capture files are named to follow the pattern defined for UE logs.
<core>-<stage>-rrcr_<rrcr_num>-run_<run_num>-<protocol>.log
These files represent full connections between the UE and gNB. In the nomenclature used in the
UE log analysis, we leave out the actual full connection, so <stage> was set to None. Defaults
parameters were used, so the rrcr value for all experiments is 7. As we don't do any filtering based
on protocol, TOTAL is listed as the protocol.

C.2. Preprocessing
Again, to make the problem similar enough to utilize the approach developed for UE logs, we
convert the pcap files into json. The command to convert the files to json:
for file in *.pcap; do tshark -r "$file" -T json > "${file%.pcap}.json"; done
The preprocessing script, protocol_parse.py, was designed for UE logs and is not used for
preprocessing the packets.

C.3. Tokenizing
We use the same tokenization script developed for the UE logs for the packet examples. There are
two files with normalizers specified. The file, src/tokens/filters/PacketFilters.txt, contain all the filters
that remove text that are highly specific and hurt the generalizability of the models. The file,
src/tokens/filters/PacketFilters_optional.txt, contain normalizers that filter out features that were deemed
most important to classification. This was used to iteratively layer back what is most important in
identifying cores based on the network traffic.
Three features were found to useful in distinguishing between 5G cores that may point to
differences in how the cores operate within the network.
 • Time to live parameter of ip packets: There did appear to be differences between servers
 with regards to the TTL values.
 • SCTP checksum and value: The SCTP protocol specifies a checksum; however, to save
 computational resources, this checksum can be skipped and set to zero (there are other
 checksums that can be utilized). Some 5G cores calculated a checksum and others did not.
 • IP checksum and status: Again, there were differences between cores with regard to the IP
 checksum and status.

 60

After these transport-layer differences were identified, more UE-gNB communication-specific
differences arose, like UE log analysis.
Below are commands to create byte-pair encodings utilizing the PacketFilters.
cd src/tokens
python train_bpe.py --inputdir <Path to curated data>/CuratedData/PacketCaptures/Original/\
             --regex ".*\.json"\
 --save output/packet_tokenizer_base.txt\
 --normalizers filters/PacketFilters.txt
python train_bpe.py --inputdir <Path to curated data>/CuratedData/PacketCaptures/Original/\
             --regex ".*\.json"\
 --save output/packet_tokenizer_filtered.txt\
 --normalizers filters/PacketFilters_optional.txt

C.4. Training Models
Training the models remains consistent with UE log analysis.
python logistic_regression.py --dir ~/data/Tomcat/CuratedData/PacketCaptures/Original/\
 --tokenizer ../tokens/output/packet_tokenizer_base.txt\
 --ngram_range 1 2 --vectorizer count --test None\
 --protocol TOTAL --rrcr 7 --weight_threshold 0.001\
 --output_prefix output/packet_results_base --n_splits 2
python logistic_regression.py --dir ~/data/Tomcat/CuratedData/PacketCaptures/Original/\
 --tokenizer ../tokens/output/packet_tokenizer_filtered.txt\
 --ngram_range 1 2 --vectorizer count --test None\
 --protocol TOTAL --rrcr 7 --weight_threshold 0.001\
 --output_prefix output/packet_results_filtered --n_splits 2

C.5. Results
We performed a limited experiment using establishment cause 7 over Aether, OAI, and Open5gs
cores. A full connection was established, thus negating some of the privacy benefits outlined in
section 3.3. The effort was a proof-of-concept, with much room for further exploration. Overall, we
obtained 100% accuracy in identifying the cores based upon the network logs, with the important
features a combination between IP and SCTP protocol differences and the same UE-gNB
communication differences noted in Section 4.7. These preliminary results indicate that the network
logs associated with UE and gNB communication may offer additional information that is not
present in UE logs and will be helpful for core identification.
