 Abstract
 This white paper outlines potential approaches to supporting special values in the zfp nu-
 merical compressor without breaking backwards compatibility. Other than infinities and NaNs,
 special values are often used to indicate the absence of data, where no value is defined, for
 example by designating finite but extreme “fill values” as special. Such fill values are commonly
 used in earth system science, among other applications, but if left as is during compression lead
 to artifacts and loss of precision in nearby true values. Multiple candidate solutions that would
 allow zfp to recognize special values are here proposed. Until such support is available, we also
 sketch available workarounds.

1 Introduction
The zfp numerical compression library [9, 10] has been designed to handle finite integer and real
numerical values that exhibit strong spatial correlation in one or more dimensions. We will refer to
such values here as “normal” values. Some applications, however, also require support for special
values (also known as exceptional values), some of which may be nonnumerical. Examples from the
IEEE 754 floating-point (FP) standard [1] include ±∞ and NaN (“not a number”). Other examples
include indeterminate values, such as the result of ill-defined expressions 0/0, ∞ − ∞, and 0 × ∞,
as well as undefined values, where data is simply missing. This latter category occurs frequently
in earth system science, where for example ocean temperature is not defined over land [3]. Using
IEEE FP, conventions are often used to indicate undefined values, e.g., using NaN or a predefined
fill value that is well out of range (e.g., 1e+30) of common normal values.
 zfp does not support special values of any kind in its default “lossy” modes, though both
NaN and ±∞ are supported in “reversible” (or lossless) mode, which guarantees that values are
reproduced exactly bit-for-bit. The primary downside of reversible mode is that it severely limits
the compression ratios achievable, usually to 2:1 or less. As suggested in one of the zfp FAQs [11],
one can use reversible mode with loss by specifying that less than full precision is to be retained.
However, as we shall see, this approach also compromises compression ratio.
 Whereas zfp was originally designed as an in-memory compressed-array representation for
numerical computations [9], it has since been widely adopted for reducing offline storage, and it is
primarily this latter use case that we seek to address here, with storage size and accuracy rather
than (de)compression speed as primary considerations.

2 Special Values
Past efforts to support special values in zfp were based on the assumption that one can easily
enumerate a set of values that would be sufficient for all applications. For example, ±∞ and a
single NaN. However, as seen from Table 1, it often makes sense to further distinguish additional
categories of special values, e.g., depending on the context within which a nonvalue was generated.
Anticipating and enumerating all possible types of special values an application may want to support
is impractical. Moreover, a given application is unlikely to make use of all possible special values
within a single data set, and allowing for special values known not to occur increases coding cost.
 Thus, we advocate for having the user specify a list of distinct special values in their native-
format binary representation (e.g., IEEE FP or two’s complement integers) that may be referenced
in a data set. Hence, each special value is identified by an index into this list that is stored with
the compressed data. This allows, for instance, each application to represent whatever fill value is
used by that application, and zfp would ensure that such fill values are reconstructed exactly bit
for bit (i.e., even in lossy mode).

3 Current Practice for Supporting Fill Values
As zfp does not yet recognize special values, current solutions are limited and generally ineffective
or cumbersome. We discuss three approaches here and illustrate our points using example 2D data
from the Energy Exascale Earth System Model [2], which contains fill values primarily over land.

 1. Use large, “out-of-range” fill values and compress them as is (see Figure 1(b)). Both normal
 and fill values are perturbed by lossy compression, and therefore decompressed fill values may
 not exactly match those being compressed. Thus, the application may need to be modified
 to check if a value is out of range and to correct such values for downstream processing
 dependent on exact fill values.
 The main downside of this approach is that such large fill values dwarf the normal values that
 actually matter, often resulting in a complete loss of precision in normal values when fill values
 within the same block are present due to zfp’s block-floating-point representation. Such
 “pollution” by nearby fill values, exemplified in Figure 1(b), leads to large errors (NRMSE is
 root-mean-square error over standard deviation computed only over normal values).

  2. As proposed in zfp FAQ #20 [11], use zfp’s reversible mode with reduced precision (see
 Figure 1(c)). As this approach generally does not employ a block-floating-point representa-
 tion, it preserves both precision in normal values and exponents associated with both large
 fill values and NaN (when NaN is used to indicate missing data; see Figure 2(c)).
 One drawback of this approach is the reduction in compression ratio associated with reversible
 mode as well as the discontinuities in values that degrade the effectiveness of decorrelation.
 As exponents of individual values are explicitly represented in this mode, far higher precision
 is needed to attain comparable levels of accuracy to zfp’s lossy modes.

  3. Compute and store a separate bit mask that indicates which values are normal and which are
 fill values (Figure 3). In this approach, the fill values are subsequently replaced with normal
 values (e.g., block-local averages) before compression to reduce discontinuities and promote
 compression. The bit mask can, for instance, be compressed losslessly by zfp in reversible
 mode with 1-bit precision, as was done here when reporting compression ratios.

 While this approach can be effective at reducing artifacts and loss in accuracy associated with
 the previous two approaches, the chief downside to using a separate bit mask is the need for
 the data producer to compute and store an additional field and a reliance on data consumers
 to interpret this field to restore the original fill values. This extra work and need to process
 multiple fields together precludes the clean and transparent approach to (de)compression
 provided by compression plugins in formats like HDF5 [4, 13], where the consumer need not
 even know that the data is stored in compressed form.

4 Proposals for Supporting Special Values in zfp
We here give a brief outline of possible approaches to supporting special values directly in zfp,
each with its pros and cons. With enormous amounts of data already stored in the zfp format, the
notion of “backwards compatibility” is of great importance and will be discussed first to provide
context for the motivation of some candidate approaches.

4.1 Backwards Compatibility
Backwards compatibility is always a serious consideration when extending file formats with new
features. We will refer to zfp streams (and analogously blocks) with support for special values as
special streams, distinguishing such streams from normal streams written by the current version of
zfp. In the present context, “backwards compatibility” implies the following:
 • When data sets contain no special values, there should be no impact on zfp streams written
 by an implementation that supports special values. Therefore, zfp streams are decoded to
 exactly the same values before and after special-value support is added.

 • Conversely, existing normal streams can be decoded correctly by an implementation that
 supports special values.
Note that special streams will inevitably encode information that current versions of zfp will not
be able to interpret correctly. Ideally, current versions would still be able to reconstruct normal
values correctly or do something sensible when presented with a special stream, possibly including
reporting an error so that the user is alerted that an older version of the zfp library is not able to
decompress such streams.
 Our proposals do not consider forwards compatibility, which ensures that future revisions to
the format are possible, e.g., by reserving zero-initialized bit fields that may be used to encode
(optional) information supported by a future version.

4.2 Technical Approaches
With backwards compatibility an important design goal, we here outline four proposals to accom-
modate support for special values directly in zfp, i.e., with minimal additional effort on the user’s
part (unlike, for example, the user-managed bit mask approach discussed above). Note that we
will defer the actual details of how to encode the special values themselves to later sections.
 1. Use special exponent to signal special blocks. A floating-point zfp block of all-zeros
 (an “empty block”) is currently detected and coded using a single bit, while nonzero blocks
 are preceded by a common exponent. The IEEE FP exponent associated with zero is, thus,
 never used for non-empty blocks and can be repurposed as a special code to indicate the
 presence of special values.

 6

  Pros:

 • The solution is straightforward and can be implemented using a single conditional outside
 the inner loop.

  Cons:

 • Unfortunately, the storage overhead of the reserved exponent is quite high: 8 or 11
 bits per special block depending on IEEE precision. All-special blocks must absorb this
 overhead, while blocks with at least one normal value would need separate encoding of
 the actual exponent.
 • The current version of zfp would not know the special meaning of this exponent and
 would interpret subsequent bits incorrectly. It would, thus, silently decode data as
 garbage and lose synchronization with the remainder of the stream.
 • It is unclear how this approach would interact with reversible mode, which does not
 necessarily use a common block exponent.

2. Use special leading bit plane to signal special blocks. It can be shown that the
 most significant bit plane of a zfp block cannot contain more than two one-bits. Hence,
 five consecutive one-bits in zfp’s variable-length code (implying three or more decompressed
 one-bits) would suffice to indicate that the block is special.
  Pros:

 • Reduces the overhead of signaling special blocks from 8 or 11 bits to 5.

  Cons:

 • Whereas the overhead relative to the previous proposal is reduced, the performance cost
 is larger as bit plane encoding/decoding occurs in the innermost loop of zfp. Having to
 unconditionally check for this escape code could therefore be costly performance-wise.
 • As with the above special-exponent approach, one pays the overhead of encoding a full
 (unused) exponent even if all values in a block are special.
 • Also like the special-exponent approach, current versions of zfp would simply be obliv-
 ious to the leading bit plane constraint and would happily continue decoding such bit
 planes, leading to desynchronization.

3. Enter special encoding/decoding mode through the zfp stream state. Like how zfp’s
 reversible mode currently is invoked by a special setting of zfp compression parameters to
 take a completely different code path, one could use combinations of compression parameters
 to put the zfp codec in a special-value mode. When in this mode, the stream would be
 produced and interpreted differently, much like in reversible mode. Note that this requires
 a new interpretation of the four expert-mode compression parameters, which not only are
 stored in the zfp stream object but also are encoded in zfp’s optional header.
  One possible approach is to repurpose one bit of zfp’s maxprec parameter, which allows up
  to 128-bit precision, yet current (and likely future) versions of zfp limit precision to 64 bits.
  Thus, the most significant bit of the maxprec field that currently is zero could be used to put
  the codec in special-value mode.

 7

 Pros:

 • No per-block storage overhead to enter special-value mode.
 • Similar mechanism to already-supported reversible mode.

 Cons:

 • Foregoes any future support for 128-bit precision.
 • Current zfp versions might get confused when being asked to process more than 64 bits
 of precision, as implied by setting the most significant bit of maxprec.
 • The decoder would need to know to initialize the codec in this mode to process the
 stream correctly. If headers are not used, it falls on the user to initialize zfp stream
 correctly. This, however, is no different from reversible mode.

  4. Bump codec version and use it only for special streams. The codec version is encoded
 in the optional zfp header, which must match the current codec version of the zfp library
 or an error is returned. Through a new version of the zfp codec, one is free to mark special
 blocks in whichever way is most efficient with no concern about backwards compatibility or
 need to work within the constraints of the current codec.
 Pros:

 • Provides the most flexibility and best tradeoff between storage and performance.
 • Special streams can be detected by the current codec, which would simply fail and return
 an error.

 Cons:

 • We do not take the significance of codec updates lightly. The current codec 5 has seen
 no revisions since 2016, and the prospect of introducing a new codec a decade later only
 to support a single new feature is not attractive given the many other features we would
 hope to introduce in the next revision of the zfp format.
 • This approach requires code to support two codecs. Although we expect reuse of exist-
 ing code for normal streams, having to switch between and handle the logistics of two
 different codecs within one library adds new and possibly unforeseen challenges.
 • When writing the header, one would have to a priori know that special values will follow.
 Using a newer codec conservatively even if streams are found to be normal would break
 backwards compatibility.

 As should be evident, the tradeoffs laid out above call for difficult decisions that require sub-
stantial consideration before a path forward can be chosen. Moreover, we suspect that these are not
the only reasonable approaches, and more work is needed to investigate other potential solutions.

4.3 Future Work
Assuming a solution to marking which blocks contain special values is identified, additional work is
needed to then efficiently encode both special and normal values. In this section, we discuss future
work needed to solve challenging technical issues.

4.3.1 Encoding Which Values in a Block are Special
We here turn our attention to encoding which values in a special block are special and, when there
are multiple special value types in a block, how to encode indices into the user-defined table of
special values.
 When only one special value is possible, as in the case of data with fill values, a bit mask may
be encoded that distinguishes normal from special values (Figure 4). To losslessly compress such

 9

a mask, one may employ zfp’s variable-length bit plane code,1 which assigns shorter codes to bit
planes with many zeros, and preferably many “leading zeros” for a given ordering of bits within
a bit plane. Such bit planes are losslessly encoded as unsigned 4d -bit integers for d-dimensional
arrays, with shorter codes for small integers with few one-bits.
 As Figure 4 and intuition suggest, we expect bit masks within blocks to exhibit spatial cor-
relation, i.e., bits at adjacent grid points are likely to have the same value. An analysis of 2D
E3SM lat/lon data with fill values confirms this expectation: the vast majority of 2D blocks have
either all-normal values (54.9%) or all-fill values (37.2%). The next most common of 24×4 = 65, 536
possible bit patterns is present in only 0.25% of blocks.
 Thus, a reasonable strategy would be to map all-normal blocks to the integer x = 0 and all-
special blocks to the integer x = 1; the mapping m(x) of remaining bit patterns (x ≥ 2) is likely
of marginal importance. However, as we expect spatial locality of one-bits, we may exploit this by
ordering grid points within a block along a space-filling curve (e.g., Hilbert or Moore curve), which
is likely to produce sequences of consecutive one-bits. Such runs of one-bits can then be zeroed
using a variant of Gray code:
                                      m(x) = (x ⊕ 2x) mod 4d ,                                    (1)
where ⊕ denotes bitwise exclusive or. Then m(00 . . . 02 ) = 0 and m(11 . . . 12 ) = 1, as desired for
all-normal and all-special blocks. Furthermore, m(x) = m(¬x) ⊕ 1, and thus a bit pattern x and
its complement ¬x are mapped to consecutive integers that differ only in the least significant bit.
Hence, x and ¬x, which we expect to be roughly equally likely, have similar coding costs.
 When more than one special value is possible, a different strategy is needed. One approach
would be to first signal using one bit per normal and special value whether such a value is present
in a block, which often reduces to only a single value type or two types; cases already handled
above.
 When three or more values are present, we propose computing one bit mask per special value
and encoding special values in order of expected likelihood (as estimated by the user). For each
value type present, we encode a bit mask and then for subsequent value types “remove” bits where
prior value types are known to be present, thus avoiding bits in the bit mask already known to be
zero. We acknowledge that we have little data to base such a strategy on, and additional work is
needed to determine its effectiveness.

4.3.2 Interpolation
Once we know which values in a block are special, we would like to substitute such (possibly
nonnumerical) values with suitable numerical values that promote compression. Toward this end,
we suggest possible candidate solutions for “interpolating” normal values to fill voids between them
left by special values:

 • Local average interpolation. As explored above in combination with bit masks, one may
 replace special values with the block-local mean of normal values. (All-special blocks would
 be replaced with zero.) Although not optimal in terms of compression ratio, this pragmatic
 approach is both straightforward to implement and efficient.

 • Nearby neighbor interpolation. As already utilized by zfp to handle partial blocks
 near domain boundaries when array dimensions are not multiples of four, one may use a
 pre-defined neighbor (or sequence of neighbor candidates) as interpolant. Such an approach
 could be extended to arbitrary configurations of missing values.

 • Spectral interpolation. The idea behind spectral interpolation [8] is to produce an as-
 smooth-as-possible interpolant from irregular configurations of known values on a grid. Spec-
 tral interpolation uses the discrete cosine basis for regular grids (and otherwise the Laplacian
 eigenbasis), with the assumption that high-frequency modes are to be minimized. Given the
 configuration of known values, one can find the lowest-frequency interpolant of those values
 and express all missing values as affine (weighted) combinations of known values. This same
 principle is well-suited to zfp—albeit using the zfp rather than DCT basis—as zfp maxi-
 mizes compression when the high-sequency response is minimal. One downside is that this
 solution requires large, pre-computed tables of 42d weights.

 • Polynomial/low-rank interpolation. zfp uses as basis a slight modification of the orthog-
 onal discrete Gram polynomial basis. When a value is missing in one dimension, one could
 fit the lowest-degree polynomial that interpolates the known values and use it as interpolant.
 Or, using zfp’s basis instead of polynomials, one can fit the first few basis functions to known
 data. This approach is closely related to spectral interpolation, but solves the problem in
 only one dimension at a time, which allows the interpolation to be implemented directly in
 code rather than using a lookup table of weights.

 • Full minimization of coding cost. A more sophisticated approach is to optimize the
 interpolant that has the lowest coding cost. This is a nonlinear and likely nonconvex problem
 that may require an approximate objective that models the true coding cost. The true coding
 cost, as discussed in part in [12, §3.3], involves the negabinary representation of a coefficient
 and its magnitude in relation to preceding coefficients in the “zig-zag” ordering [5]. We expect
 this to be a nontrivial optimization problem to solve that will likely prove impractical as inline
 solution, but which may be used as a baseline for evaluating alternatives.

5 Conclusion
We have discussed four possible solutions to directly supporting special values in a future version
of the zfp library. In addition to analyzing their pros and cons, we have presented three potential
workarounds for compressing data containing fill values using the current version of the library.
Although the most onerous on the user’s part, we find that the storage of an auxiliary, losslessly
compressed bit mask coupled with simple local-mean replacement of fill values is the most effective
solution currently available, both in terms of compression ratio and numerical accuracy. Finally,
we have outlined remaining challenges to be addressed in terms of locating and replacing special
values so as to promote compression. We expect this document to serve as a starting point for
future work to implement full special-value support within zfp.
