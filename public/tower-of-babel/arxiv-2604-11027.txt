Abstract
. Binary size reduction is an increasingly important optimization objective for compilers, especially in the context of mobile applications and resource-constrained embedded devices. In such domains, binary size often takes precedence over compilation time. One emerging technique that has been shown effective is function merging , where multiple similar functions are merged into one, thereby eliminating redundancy. The state-of-the-art approach to perform the merging, due to Rocha et al. [CGO 2019, PLDI 2020], is based on sequence alignment , where functions are viewed as linear sequences of instructions that are then matched in a way maximizing their alignment. In this paper, we consider a significantly generalized formulation of the problem by allowing reordering of branches within each function, subsequently allowing for more flexible matching and better merging. We show that this makes the problem NP -hard, and thus we study it through the lens of parameterized algorithms and complexity , where we identify certain parameters of the input that govern its complexity. We look at two natural parameters: the branching factor and nesting depth of input functions. Concretely, our input consists of two functions F 1 , F 2 , \texttt{F}_{1},\texttt{F}_{2}, where each F i \texttt{F}_{i} has size n i , n_{i}, branching factor b i , b_{i}, and nesting depth d i . d_{i}. Our task is to reorder the branches of F 1 \texttt{F}_{1} and F 2 \texttt{F}_{2} in a way that yields linearizations achieving the maximum sequence alignment. Let n = max ⁡ ( n 1 , n 2 ) , n=\max(n_{1},n_{2}), and define b , d b,d similarly. Our results are as follows: • A simple algorithm running in time 2 𝒪 ⁡ ( b ​ d ) ​ n 2 , 2^{\mathcal{O}(bd)}n^{2}, establishing that the problem is fixed-parameter tractable ( FPT ) with respect to all four parameters b 1 , d 1 , b 2 , d 2 . b_{1},d_{1},b_{2},d_{2}. • An algorithm running in time 2 𝒪 ⁡ ( b ​ d 2 ) ​ n 7 , 2^{\mathcal{O}(bd_{2})}n^{7}, showing that even when one of the functions has an unbounded nesting depth, the problem remains in FPT . • A hardness result showing that the problem is NP -hard even when constrained to constant d 1 , b 2 , d 2 . d_{1},b_{2},d_{2}. To the best of our knowledge, this is the first systematic study of function merging with branch reordering from an algorithmic or complexity-theoretic perspective.

Function Merging

One emerging technique that has been shown effective for binary size reduction is
function merging

(
28
;
22
;
23
;
21
;
27
;
25
;
16
)
. The high-level idea is to repeatedly run the following process: Identify a pair of functions
\texttt{F}_{1},\texttt{F}_{2}
that are highly similar, under some notion of similarity, and introduce a new function
\texttt{F}_{\star}
that captures their combined behaviour. The parts common to both
\texttt{F}_{1}
and
\texttt{F}_{2}
will be included only once in
\texttt{F}_{\star},
while the differing parts will be captured through an additional parameter given to
\texttt{F}_{\star},
which determines which
\texttt{F}_{i}
to simulate. Finally, the body of each
\texttt{F}_{i}
is replaced with a single call to
\texttt{F}_{\star}
with the appropriate argument. The more similar
\texttt{F}_{1}
and
\texttt{F}_{2}
are, the more success merging can have in reducing code size. Thus, the usefulness of this optimization relies on the presence of redundancy in the code. Such redundancy can arise, for instance, due to using templates in a high-level language, which is projected into multiple highly-similar copies in the low-level code, to which the optimization is applied. Moreover, interprocedural compiler optimizations can create more redundancy in code which can then be eliminated through merging. See
(
28
, Section 1)
for further discussion.

Pair Selection vs. Merging

We distinguish between the following two tasks in function merging:

Pair Selection:

From
n
functions
\texttt{F}_{1},\dots,\texttt{F}_{n},
optimally
select then merge
a pair of functions
\texttt{F}_{i_{1}},\texttt{F}_{i_{2}}.

Merging
:

Optimally merge a
given
pair of functions
\texttt{F}_{1},\texttt{F}_{2}.

As the pair selection problem involves not only merging a pair of functions optimally, but also finding the best pair to merge, it clearly subsumes the merging problem. At the same time, pair selection is too difficult, as it seems to require
\Theta(n^{2})
invocations of the merging routine. For this reason, all related works
(
22
;
23
;
27
;
28
)
take a heuristic approach to pair selection by first identifying a
seemingly promising
pair of functions, and then delegating the extraction of as much profit from that pair to the merging routine. In this work, we only focus on the merging task, and whenever we speak of function merging, we are referring to optimally merging two functions that are readily given as part of the input.

Sequence Alignment

Sequence alignment (SA)
is a classical problem that has its roots in bioinformatics, and it generalizes other standard problems such as
edit distance
and
longest common subsequence

(
14
)
. Informally, the input consists of two strings/sequences
S_{1},S_{2}
of
n_{1},n_{2}
characters, respectively, and our goal is to insert or delete characters from them in order to maximize their character-wise alignment. This optimal alignment has a value denoted by
\texttt{SA}(S_{1},S_{2}).
Formal definitions are delegated to Section
2
, but we note that
\texttt{SA}(S_{1},S_{2})
and its corresponding alignment can be computed in time
\mathcal{O}\left(n_{1}n_{2}\right)
via a standard dynamic programming algorithm
(
14
;
5
)
.

Function Merging via Sequence Alignment
(
22
;
23
)

The state-of-the-art approach to perform function merging is based on sequence alignment
(
22
;
23
)
. Their insight is to view each instruction as a character, and each function
\texttt{F}_{i}
(
i\in\{1,2\}
) as a string
S_{i}
of such characters. Then, they run an SA algorithm to compute
\texttt{SA}(S_{1},S_{2})
and find the best alignment, which then guides the merging of the two functions. This is precisely the approach used to perform the merging in Figures
1
and
2
: The SA algorithm identifies the aligned regions in
\texttt{F}_{1}
and
\texttt{F}_{2}
highlighted in green, and moreover guarantees that this is the best possible alignment that, say, maximizes the number of aligned instructions. Given this alignment, a merging procedure merges the aligned instructions (green) together, while the unaligned instructions (red and blue) are kept separate, as explained above.

Reordering Branches

In this sense, the SA-based approach only works on a single linearization of the input functions, which may be suboptimal. A natural question is whether we can do better by considering
multiple
linearizations of the input functions, and selecting the best one for merging. In particular, we consider
reordering the branches
appearing in each function to obtain equivalent but syntactically different functions, and then performing the SA-based merging on the resulting strings. Slightly more formally, our problem is as follows: Given two functions
\texttt{F}_{1},\texttt{F}_{2},
we want to reorder the branches of their branching constructs (e.g.,
\texttt{if}/\texttt{switch}
) to obtain equivalent functions
\texttt{F}_{1}^{\prime},\texttt{F}_{2}^{\prime}
such that
\texttt{SA}(\texttt{F}^{\prime}_{1},\texttt{F}^{\prime}_{2})
is maximized. The benefit of doing so can be readily seen in our example: The function
\texttt{F}_{1}^{\prime}
obtained by swapping the two branches in
\texttt{F}_{1}
has a better alignment with
\texttt{F}_{2}
than
\texttt{F}_{1}
itself. In particular, the entirety of the
if-elif
block of
\texttt{F}_{1}^{\prime}
and
\texttt{F}_{2}
can now be aligned, resulting in the merged function
\texttt{F}_{\star}^{\prime}
shown in Figure
4
, which is 3 lines smaller than the first merging in
\texttt{F}_{\star}.

Parameterized Algorithms and Complexity
(
8
)

In classical complexity theory, we analyze the complexity of a computational problem
\mathcal{A}
based on its behavior with respect to the
size
of its inputs. That is, given an input
x
of size
|x|,

\mathcal{A}
is considered efficiently solvable if it has an algorithm with a low dependence (e.g., polynomial) on the input size
|x|.

Parameterized complexity theory
generalizes this idea by allowing additional parameters to be associated with an input
x.
It then explores whether problems that are hard on general inputs can be solved by an algorithm that depends polynomially on
|x|,
but might have a higher dependence on these extra parameters. We call such an algorithm
fixed-parameter tractable
(
FPT
). Formal definitions are given in Section
2
. In addition to its theoretical elegance and depth, parameterized complexity offers a practical workaround for problems that are hard in the classical sense: Suppose that
\mathcal{A}
is
NP
-hard, and thus not in
P
unless
P
=
NP
. If we can identify certain parameters that are typically small on instances of interest in practice, and if we further design an
FPT
algorithm for
\mathcal{A}
under these parameters, then we get an efficient practical algorithm for
\mathcal{A}.
This is despite its
NP
-hardness on general inputs, and while still providing guarantees on the optimality and running time of the algorithm. Indeed, various
NP
-hard problems admit an
FPT
algorithm under many natural parameters
(
8
;
7
)
.

Contributions

We consider the problem of function merging with branch reordering defined above. Though the state-of-the-art on function merging
(
22
;
23
)
mentions this problem as an open question, it has remained unstudied so far. We formulate the problem rigorously in Section
2
, and then we study it through the lens of parameterized algorithms and complexity. We look at two natural parameters: the
branching factor
and
nesting depth
of input functions. Given two functions
\texttt{F}_{1},\texttt{F}_{2}
to merge, let
n_{i},b_{i},d_{i}
denote the size, branching factor, and nesting depth of
\texttt{F}_{i}
for
i\in\{1,2\}.
Let
n=\max(n_{1},n_{2}),
and define
b,d
similarly. Our results are as follows:

•

A simple algorithm running in time
\mathcal{O}\left(2^{b_{1}d_{1}+b_{2}d_{2}}(b_{1}+b_{2})^{2}(d_{1}+d_{2})\cdot n_{1}n_{2}\right)
(Theorem
3.4
). This shows that the problem is in
FPT
when parameterized by
b_{1},d_{1},b_{2},d_{2}.
The algorithm is based on a dynamic programming approach and generalizes the classical SA algorithm.

•

An algorithm running in time
2^{\mathcal{O}(b_{2}d_{2}+b_{1})}(n_{1}n_{2})^{3}(n_{1}+n_{2})
(Theorem
3.6
). That is, the problem remains in
FPT
even when one of the functions is of unbounded nesting depth. This algorithm relies on reducing the problem to reachability on a weighted pushdown system
(
19
)
.

•

A compelling hardness result, showing that the problem is
NP
-hard even when restricted to
d_{1}=1,b_{2}=d_{2}=0
(Theorem
4.2
). This implies that the parameterization by
d_{1},b_{2},d_{2}
is not in
FPT
, unless
P
=
NP
.

To the best of our knowledge, this is the first systematic study of function merging with branch reordering from an algorithmic or complexity-theoretic perspective.

Related Works on Function Merging

There have been a handful of recent works on function merging
(
28
;
22
;
23
;
21
;
27
;
25
;
16
)
. They usually look at the problem more broadly by additionally considering heuristics to pick which functions to merge. Existing compilers, e.g., LLVM, were limited to only merging identical functions, and the first work to go beyond that is
(
28
)
. They merge two functions if their CFGs satisfy a strong notion of isomorphism and the total difference of basic-block code in isomorphic nodes is below a certain threshold. This is a much simpler problem than the general graph isomorphism, and can be solved in polynomial time. The sequence alignment-based approach
(
22
)
looks at one linearization of each of the two functions and computes an alignment between them to profitably guide the merging. A major drawback of
(
22
)
is that it is not able to handle phi-nodes in SSA-form programs. This technical challenge, which is orthogonal to the theory of merging, was addressed in
(
23
)
, obtaining better size reductions in practice. The work
(
21
)
proposes further optimizations that achieve a faster memory-efficient compilation without significantly compromising the size reduction.
(
27
)
proposes a hash-based technique to more effectively identify promising function pairs before merging them. All of these works focused on merging two functions at a time. Merging multiple functions
(\geq 3)
has been explored in
(
25
)
, which builds on top of
(
27
)
. Finally, the work
(
16
)
proposed a scalable approach to function merging that composes it with function outlining, and works well within a distributed build environment.

Formulation and Preliminaries

In this section, we formally define the problem of function merging with branch reordering (Section
2.1
). Then, we provide some background from parameterized complexity (Section
2.2
) and pushdown systems (Section
2.3
) that will be used in subsequent sections.

2.1.
Function Merging with Branch Reordering

Abstract Syntax

Let
\Sigma
be an alphabet containing all instructions of interest, e.g., arithmetic operations, memory accesses, etc. We consider programs written in an abstract syntax over the extended alphabet
\hat{\Sigma}:=\Sigma\cup\left\{~\textbf{|}~,[,],\cdot\right\}
defined by the following grammar:

\begin{split}P\rightarrow\sigma\in\Sigma\;\;\Big|\;\;[P~\textbf{|}~\dots~\textbf{|}~P]\;\;\Big|\;\;P\cdot P.\end{split}

That is, a program
P
can either be a single instruction from
\Sigma,
a
branching construct

[P_{1}~\textbf{|}~\dots~\textbf{|}~P_{k}]
with
branches

P_{1},\dots,P_{k},
each of which is a program, or a
sequential composition
of two programs
P_{1}\cdot P_{2}.
We note that the number of branches can be arbitrary, but must be finite. Let
\text{Prog}(\Sigma)
denote the set of all programs derived from this grammar. To illustrate, consider the function
\texttt{F}_{1}
from Figure
1
. We denote the instruction on line
i
by
\texttt{i}.
Then, its representation in our abstract syntax is:

(1)

Remark

Though minimal, this syntax is expressive enough to capture the features relevant to our task of reordering branches for optimal merging. Constructs omitted from the syntax are either unaffected by reordering (e.g., the function’s name and parameters) or reordering has a negligible effect on them (e.g., conditions of branching), so they can be left as an implementation detail.

Problem Statement

We are now ready to formally define the problem of function merging with branch reordering. Given two functions with abstract programs
P_{1},P_{2}\in\text{Prog}(\Sigma),
and a scoring function
\delta,
the goal is to compute:

\texttt{FMBR}(P_{1},P_{2},\delta):=\max_{\pi_{1},\pi_{2}}\;\texttt{SA}(\text{Linear}({P_{1}},{\pi_{1}}),\text{Linear}({P_{2}},{\pi_{2}}),\delta),

where
\pi_{1},\pi_{2}
range over all possible reorderings of
P_{1}
and
P_{2},
respectively. For consistency with the complexity-theoretic notions given in Section
2.2
and used in later sections, we also consider the decision variant of
FMBR
. There, the input includes an additional integer threshold
\tau,
and the goal is to decide whether the optimal value
\texttt{FMBR}(P_{1},P_{2},\delta)
is at least
\tau.
Throughout the remainder of the paper, we let
n_{i}:=|P_{i}|,

b_{i}:=\text{BrFactor}(P_{i}),
and
d_{i}:=\text{Dep}(P_{i})
for
i\in\{1,2\}.

2.2.
Background from Parameterized Complexity

Parameterized Problems

Our definitions follow the standard reference
(
7
)
. We fix
\Phi
as our finite alphabet. In classical complexity theory, a problem is defined as a
language

L\subseteq\Phi^{*}.
Then, an algorithm for this problem decides, on a given input
x\in\Phi^{*},
whether
x\in L.
In parameterized complexity theory, inputs are augmented with one or more
parameters
that capture certain aspects of the input. More formally, a
parameterized problem with
k
parameters
is a language
L\subseteq\Phi^{*}\times\mathbb{N}^{k}.
An input instance of
L
is a tuple
\langle x,\eta_{1},\dots,\eta_{k}\rangle
where
x\in\Phi^{*}
is the main part of the input and
\langle\eta_{1},\dots,\eta_{k}\rangle\in\mathbb{N}^{k}
are the
parameters
associated with
x.

The standard notion of efficiency in classical complexity is taken to be the class
P
, which encompasses all problems with an algorithm running in polynomial time, i.e.,
\mathcal{O}\left(|x|^{c}\right)
for some constant
c.
In the parameterized world, two other complexity classes fulfill this role:
XP
and
FPT
.

XP
and
FPT

Let
L
be a parameterized problem with
k
parameters. We say that
L\in\textit{{XP}}
if there is an algorithm that, given an input
\langle x,\eta_{1},\dots,\eta_{k}\rangle,
decides whether
\langle x,\eta_{1},\dots,\eta_{k}\rangle\in L
in time
\mathcal{O}\left(|x|^{f(\eta_{1},\dots,\eta_{k})}\right)
for some computable function
f:\mathbb{N}^{k}\rightarrow\mathbb{N}.
We also call such an algorithm an
XP
algorithm. This algorithm is polynomial-time for every fixed value of the parameters, but the degree of the polynomial may depend on the parameters’ value.
FPT
, short for
fixed-parameter tractable,
is a stricter class than
XP
which requires polynomial input-size dependence regardless of the parameter. We say that
L\in\textit{{FPT}}
if there is an algorithm that decides whether
\langle x,\eta_{1},\dots,\eta_{k}\rangle\in L
in time
\mathcal{O}\left(f(\eta_{1},\dots,\eta_{k})\cdot|x|^{c}\right)
for some constant
c
and a computable function
f:\mathbb{N}^{k}\rightarrow\mathbb{N}.
Such an algorithm is also called an
FPT
algorithm. It is immediate that
\textit{{FPT}}\subseteq\textit{{XP}}.

Parameters of Interest

In our problem
\texttt{FMBR},
the corresponding (unparameterized) language is simply the set
L_{\texttt{FMBR}}:=\{(P_{1},P_{2},\delta,\tau)\;|\;\texttt{FMBR}(P_{1},P_{2},\delta)\geq\tau\}.
Here, we assume standard binary encoding of the input where programs are represented as a sequence of characters and the scoring function is given as a constant-sized Turing machine. Given an input
x=(P_{1},P_{2},\delta,\tau),
we are interested in parameterized variants of
L_{\texttt{FMBR}}
obtained by associating with
x
a non-empty subset of the four parameters
b_{1},b_{2},d_{1},d_{2}.
For each parameterization, we can ask whether it is in
FPT
or
XP
. For instance, if we choose
b_{1},d_{2},
we get the parameterized problem:

L_{\texttt{FMBR}}^{b_{1},d_{2}}:=\left\{\big\langle(P_{1},P_{2},\delta,\tau),b_{1},d_{2}\big\rangle\;\big|\;\texttt{FMBR}(P_{1},P_{2},\delta)\geq\tau\land b_{1}=\text{BrFactor}(P_{1})\land d_{2}=\text{Dep}(P_{2})\right\},

which we simply refer to as
FMBR

parameterized by

b_{1}
and
d_{2}.
Finally, note that if a parameterized problem with
k
parameters
\eta_{1},\dots,\eta_{k}
is in
FPT
(
XP
), then the same problem parameterized by any superset of these parameters is also in
FPT
(
XP
).

Background from Pushdown Systems

In this subsection, we provide some relevant background on weighted pushdown systems and reachability over them. Our presentation mostly follows the seminal work of
(
19
)
.

Idempotent Semirings

An
idempotent semiring

\mathcal{D}
is a tuple
\mathcal{D}=(D,\oplus,\otimes,\overline{0},\overline{1})
where
D
is a set,
\overline{0}
and
\overline{1}
are elements of
D,
and
\oplus,\otimes:D^{2}\rightarrow D
are binary operations over
D
satisfying:

(1)

\oplus
is commutative, associative, and idempotent, i.e.,
a\oplus a=a
for all
a\in D;

(2)

\otimes
is associative and distributes over
\oplus;

(3)

\overline{0}
is the neutral element for
\oplus
and an annihilator for
\otimes,
i.e.,
a\otimes\overline{0}=\overline{0}\otimes a=\overline{0}
for all
a\in D;

(4)

\overline{1}
is the neutral element for
\otimes.

Weighted Pushdown Systems

A
weighted pushdown system (WPDS)
\mathcal{S}
over semiring
\mathcal{D}
is a tuple
\mathcal{S}=(S,\Gamma,\Delta,\text{wt})
where:

(1)

S
is a finite set of
control locations
;

(2)

\Gamma
is a finite set called the
stack alphabet
;

(3)

\Delta\subseteq(S\times\Gamma)\times(S\times\Gamma^{*})
is a finite set of
transitions
, each of which is denoted by
(s,\gamma)\hookrightarrow(s^{\prime},w)
where
s,s^{\prime}\in S,\gamma\in\Gamma,w\in\Gamma^{*}
; and

(4)

\text{wt}:\Delta\rightarrow D
is a
weight function
that assigns a weight from
D
to each transition.

A
configuration
is a pair
\langle s,w\rangle
where
s\in S,w\in\Gamma^{*}.
We call
w
the
stack
of the configuration, whose first element refers to the top of the stack. The WPDS
\mathcal{S}
induces a
configuration graph

G_{\mathcal{S}}
where:

•

The set of nodes is the (infinite) set of all configurations of
\mathcal{S};
and

•

For every transition
t:(s,\gamma)\hookrightarrow(s^{\prime},w)\in\Delta
in
\mathcal{S}
and every
w^{\prime}\in\Gamma^{*},
we add to
G_{\mathcal{S}}
the edge
e:\left(\langle s,\gamma w^{\prime}\rangle,\langle s^{\prime},ww^{\prime}\rangle\right)
and we further assign to
e
a weight
\text{wt}(e):=\text{wt}(t).

Reachability on WPDSs

Given a WPDS
\mathcal{S}
over
\mathcal{D},
we can now ask reachability questions over its configuration graph
G_{\mathcal{S}}.
Given a (possibly infinite) path of configurations
\rho=c_{0},c_{1},c_{2}\dots
in
G_{\mathcal{S}},
we define its weight as
\text{wt}(\rho)=\text{wt}(c_{0},c_{1})\otimes\text{wt}(c_{1},c_{2})\otimes\dots,
where
\text{wt}(\rho)=\overline{1}
if
\rho
is empty. Given a source configuration
c
and a target configuration
c^{\prime},
we define
\text{Paths}(c,c^{\prime})
as the set of all paths in
G_{\mathcal{S}}
starting from
c
and ending at
c^{\prime}.
Given
c,c^{\prime},
we are interested in computing:

\text{Reach}(c,c^{\prime}):=\bigoplus_{\rho\in\text{Paths}(c,c^{\prime})}\text{wt}(\rho),

where
\oplus(\emptyset)=\overline{0}.
The work
(
19
)
gives an algorithm for computing
\text{Reach}(c,c^{\prime}),
which we will use in Section
3.2
to solve
\texttt{FMBR}.

3.
Algorithms

In this section, we present two
FPT
algorithms for
FMBR
. The first one, presented in Section
3.1
, is for the parameterization by all four parameters
b_{1},d_{1},b_{2},d_{2}.
It is based on dynamic programming, and when instantiated with straight-line programs, it coincides with the classical algorithm for
SA
/
LCS
. Next, in Section
3.2
, we give an algorithm that allows one of the programs to have unbounded depth, showing that the parameterization by
b_{1},b_{2},d_{i},
for
i\in\{1,2\},
is in

. The main insight behind it is that we can reduce
FMBR
to reachability on a compact WPDS. Combining this with the algorithm of
(

)
, we obtain an

Remark

Throughout this section, we use three pseudocodes (Algorithms
1
-
3
). We present them modularly to simplify development and avoid repetition, which may make an algorithm seem more complicated than necessary when viewed in isolation.

3.1.
Dynamic Programming Algorithm

Source of Hardness

We give an algorithm for
FMBR
parameterized by
b_{1},d_{1},b_{2},d_{2}.
First, we give an intuition for the source of hardness in this parameterization. Observe that if our input programs only have sequential composition, then the problem reduces to
SA
, which is solvable in
\mathcal{O}(n^{2})
time
(
14
;
5
)
. On the other hand, if we only have branching, then we readily have an
FPT
algorithm: Each of the programs
P_{i}
is a branching construct with at most
b_{i}
branches, each of which is also a branching-only program, and this recursion continues until depth at most
d_{i}.
Thus, we have
\mathcal{O}(b_{i}^{d_{i}})
branching constructs in
P_{i},
and we can enumerate all
b_{i}!^{\mathcal{O}(b_{i}^{d_{i}})}
reorderings of each program, and then apply
SA
on each pair of resulting linearizations. This gives us a running time of
b!^{\mathcal{O}(b^{d})}n^{2},
which is
FPT
with respect to
b_{1},d_{1},b_{2},d_{2}.
The hardness comes from the simultaneous presence of both sequencing and branching: If we have
n
sequential compositions of a program with branching factor
b
and depth
d,
then we have
b!^{\mathcal{O}(b^{d}\cdot n)}
linearizations, which is not in
FPT
. We tackle this combinatorial explosion of linearizations through dynamic programming, as described next.

Overview

For ease of understanding, we present our solution in four steps as follows:

(1)

We first define a convenient graph representation for a program
P
in
\text{Prog}(\Sigma),
which we call the
branching graph

\text{BrGraph}(P).
For a reordering
\pi
of
P,
its linearization
\text{Linear}(P,\pi)
corresponds to an
Eulerian path
in
\text{BrGraph}(P),
i.e., a path visiting each edge exactly once.

(2)

We give a recursive exponential-time algorithm to enumerate all Eulerian paths in
\text{BrGraph}(P),
thereby capturing all possible linearizations of
P
induced by reordering its branches.

(3)

We show how two simultaneous runs of the above algorithm on branching graphs
\text{BrGraph}(P_{1})
and
\text{BrGraph}(P_{2})
can be combined with the ideas from the classical
SA
/
LCS
algorithm to give us an exponential-time algorithm for
FMBR
.

(4)

Finally, and this is the crux of the algorithm, we carefully analyze the state space and compactly represent it using only
f(b_{1},d_{1},b_{2},d_{2})\cdot n_{1}n_{2}
states, yielding an
FPT
algorithm.

Branching Graphs

As noted above, we define a convenient graph representation for programs, which will make it easier to illustrate our algorithmic ideas. An actual implementation can skip this representation and work directly at the program level, avoiding any overhead associated with generating the graph. Given a program
P\in\text{Prog}(\Sigma),
its
branching graph

\text{BrGraph}(P)
is a directed graph which (i) has three types of edges: sequential edges, branch-entry edges, and branch-exit edges, (ii) has two designated nodes which we call the
left
and
right
nodes, and (iii) each node in
\text{BrGraph}(P)
has three attributes: a label holding the instruction associated with it, if any, a value denoting its nesting depth, and a
branch ID
which is an identifier for the branch containing the node. Formally,
\text{BrGraph}(P)
is a tuple
\text{BrGraph}(P)=(V,E^{\text{seq}},E^{\text{en}},E^{\text{ex}},l,r,\text{Lab},\text{Dep},\text{BrID})
where:

(1)

V
is the set of nodes, which roughly correspond to nodes of the parse tree of
P.

(2)

E^{\text{seq}},E^{\text{en}},E^{\text{ex}}\subseteq V\times V
are the set of sequential, branch-entry, and branch-exit edges, respectively.
E^{\text{seq}}
encodes moving from one node to the next using sequential composition,
E^{\text{en}}
encodes moving from a branching construct to the left node of one of its branches, and
E^{\text{ex}}
encodes moving from the right node of a branch back to the enclosing branching construct.

(3)

l,r\in V
are respectively the left and right nodes, denoting the start and end of
P.

(4)

\text{Lab}:V\rightarrow\Sigma\cup\{\textbf{br}\}
is the labeling function, which either tells us the instruction associated with a node, or indicates that it corresponds to a branching construct.

(5)

\text{Dep}:V\rightarrow\mathbb{N}
is the nesting depth for nodes.

(6)

\text{BrID}:V\rightarrow V
gives the ID of the branch that a node belongs to, where a branch is identified by its unique leftmost node.

We construct the branching graph
\text{BrGraph}(P)
inductively as follows:

(1)
If
P=\sigma\in\Sigma
:
Let
u
be a fresh node. We set
V=\{u\},E^{\text{seq}}=E^{\text{en}}=E^{\text{ex}}=\emptyset,l=r=u,
and
\text{Lab}(u)=\sigma,\text{Dep}(u)=0,\text{BrID}(u)=u.

(2)
If
P=[P_{1}~\textbf{|}~\dots~\textbf{|}~P_{k}]
:
Let
\text{BrGraph}(P_{i})=(V_{i},E^{\text{seq}}_{i},E^{\text{en}}_{i},E^{\text{ex}}_{i},l_{i},r_{i},\text{Lab}_{i},\text{Dep}_{i},\text{BrID}_{i})
for
1\leq i\leq k.
Let
u
be a fresh node and define:

•

V=\bigcup_{i=1}^{k}V_{i}\cup\{u\},

•

E^{\text{seq}}=\bigcup_{i=1}^{k}E^{\text{seq}}_{i},E^{\text{en}}=\bigcup_{i=1}^{k}E^{\text{en}}_{i}\cup\{(u,l_{i})~|~1\leq i\leq k\},E^{\text{ex}}=\bigcup_{i=1}^{k}E^{\text{ex}}_{i}\cup\{(r_{i},u)~|~1\leq i\leq k\},

•

l=r=u,

•

\text{Lab}(u)=\textbf{br}
and
\text{Lab}(v)=\text{Lab}_{i}(v)
for
i\in\{1,\dots,k\}
and
v\in V_{i},

•

\text{Dep}(u)=0
and
\text{Dep}(v)=\text{Dep}_{i}(v)+1
for
i\in\{1,\dots,k\}
and
v\in V_{i},

•

\text{BrID}(u)=u
and
\text{BrID}(v)=\text{BrID}_{i}(v)
for
i\in\{1,\dots,k\}
and
v\in V_{i}.

(3)
If
P=P_{1}\cdot P_{2}
:
Let
\text{BrGraph}(P_{i})=(V_{i},E^{\text{seq}}_{i},E^{\text{en}}_{i},E^{\text{ex}}_{i},l_{i},r_{i},\text{Lab}_{i},\text{Dep}_{i},\text{BrID}_{i})
for
i\in\{1,2\}.
Define:

•

V=V_{1}\cup V_{2},E^{\text{seq}}=E^{\text{seq}}_{1}\cup E^{\text{seq}}_{2}\cup\{(r_{1},l_{2})\},E^{\text{en}}=E^{\text{en}}_{1}\cup E^{\text{en}}_{2},E^{\text{ex}}=E^{\text{ex}}_{1}\cup E^{\text{ex}}_{2},l=l_{1},r=r_{2},
and

•

\text{Lab}=\text{Lab}_{1}\cup\text{Lab}_{2},\text{Dep}=\text{Dep}_{1}\cup\text{Dep}_{2},\text{BrID}(v)=\begin{cases}\text{BrID}_{1}(v)&\quad\text{if }v\in V_{1},\\
l_{1}&\quad\text{if }v\in V_{2}\land\text{BrID}_{2}(v)=l_{2},\\
\text{BrID}_{2}(v)&\quad\text{otherwise.}\end{cases}

Linearizations as Eulerian Paths

The intuition behind branching graphs is that, for a linearization
\text{Linear}(P,\pi)
of
P
under a reordering
\pi,
it has a corresponding
Eulerian path
in
\text{BrGraph}(P),
meaning that it visits every edge of
\text{BrGraph}(P)
exactly once. Moreover, an Eulerian path in
\text{BrGraph}(P)
can be uniquely mapped back to a linearization, creating a one-to-one correspondence between linearizations of
P
and Eulerian paths in
\text{BrGraph}(P).

Given
\text{Linear}(P,\pi),
we construct the corresponding Eulerian path in
\text{BrGraph}(P)
as follows. The path starts from the left node
l
and is extended incrementally. If we are at a node
u
with label
\sigma\in\Sigma,
we follow the unique edge outgoing from
u,
which must be either a sequential or a branch-exit edge. Otherwise, we are at a node
u
with label
br
and we have multiple ways of extending the path. Here, we observe that since
\pi
is a function over branching constructs in
P,
we can equivalently view it as a function over the
br
-labelled nodes of
\text{BrGraph}(P).
Given that, we extend the path by visiting the branches of
u
in the order given by
\pi(u),
where we initiate the traversal of a branch
P_{i}
of
u
by taking the branch-entry edge
(u,l_{i})
to the left node
l_{i}
of
P_{i}.
After visiting all branches, we follow the unique edge in
E^{\text{seq}}\cup E^{\text{ex}}
emitting from
u.
It is easy to see that this traversal will visit every edge in
\text{BrGraph}(P)
exactly once and will eventually end at the right node
r,
which makes it indeed an Eulerian path. It is also easy to see that given an Eulerian path, we can uniquely identify a corresponding linearization of
P
by simply reading the labels of the
\Sigma
-labelled nodes in the order they are visited along the path. Note that any Eulerian path necessarily starts at
l
and ends at
r.

We can apply dynamic programming on Algorithm

WPDS-based Algorithm

We further modify the algorithm of Theorem

to avoid the high dependence on one of the depth parameters

resulting in an

b_{1},b_{2},d_{3-i}

Then, we exploit the stack-like structure of signatures to encode one of the two signatures on the stack of the WPDS, subsequently allowing for arbitrary depth over that signature. In this subsection, when we refer to Algorithm

Bounded SA/LCS Values

Our algorithm assumes that the scoring function
\delta
either returns small integer values, or a very large negative value to forbid certain pairs in
(\Sigma\cup\{-\})^{2}
from being aligned. This does not impose a restriction in practice as alignment scores for realistic programs are based on a simple scoring scheme where equivalent pairs of instructions get a small non-negative score, and other cases are either forbidden or incur a small penalty
(
22

23

for all

where

are integers in
\mathcal{O}(1).
Without loss of generality, we further suppose that

Note that
\delta_{\texttt{LCS}}
has

Intuition

The main insight behind our WPDS formulation is to look at the graph of the recursive calls induced by Algorithm
2
. Every node corresponds to a dynamic programming state
(u_{1},X_{1},u_{2},X_{2})
and has an associated optimal value, i.e., the value
FuncMerg
(u_{1},X_{1},u_{2},X_{2}).
The crucial observation is that a (possibly suboptimal) solution for this state corresponds to a path from this state to the terminal state
(\bot,[],\bot,[])
in the graph of recursive calls, and the value of that solution is the
sum
of the scores accumulated along the edges (choices) in that path. Thus, finding the optimal
FMBR

(l_{1},[\emptyset],l_{2},[\emptyset])
to
(\bot,[],\bot,[])

Formally, we use the semiring
\mathcal{D}=(D,\oplus,\otimes,\overline{0},\overline{1})
where

6

It is easy to verify that

5.
Discussion

In this section, we discuss some high-level aspects of our formulation and results, possible extensions, and limitations.

Scoring Functions

The scoring function can be exploited to capture various notions of similarity between instructions. Namely, it can be more involved than simple equality checking of its arguments
(
22
;
23
)
, and the returned score can be proportional to the similarity of the two instructions. More generally, we can define the scoring function to consider a pair of (sequences of) instructions equivalent if they induce the same transfer function over the program state. In this sense, we can let
\delta
consider, say, the instructions
x++;y++
and
y++;x++
as equivalent and thus candidates for alignment as they both induce the same update to the program’s state. However, in general, for longer sequences, this will require costly SMT calls to check equivalence.

Balancing Depth and Branching

We remark that any function can be rewritten so that its branching factor is at most
2.
However, this transformation restricts the set of possible linearizations and moreover increases nesting depth. For instance, the program
[A~\textbf{|}~B~\textbf{|}~C]
(with
b=3,d=1
) can be rewritten as
[[A~\textbf{|}~B]~\textbf{|}~C]
(with
b=2,d=2
). The former can be linearized as
BCA
whereas the latter cannot. This loss of information applies for any other way of rewriting. Nevertheless, such transformation provides a good approximation when we aim to reduce the branching factor. We can also do the reverse transformation to reduce nesting depth and increase the branching factor whilst gaining more linearizations. A well-engineered implementation should employ these two transformations in pre-processing to find a balance where both
b
and
d
are small, without sacrificing too much precision.

Fine-tuning Pair Selection

Our algorithm’s runtime is inherently dependent on
b
and
d.
One can use this as a heuristic to only try pairs of functions that have smaller
b,d,
thus reducing the optimization runtime. We note, however, that there is no direct tradeoff between the estimated similarity of selected pairs and our runtime. The algorithm runs fast on two non-similar functions if
b,d
are small and will be slow if
b,d
are large, even if the two functions are highly similar.

Variable Renaming

Another aspect that can increase the effectiveness of function merging is variable renaming, where we can rename variables in the two functions to increase their similarity and thus the potential for merging. This can be integrated into our algorithms as follows: Given a pair of functions, the merging algorithm can be run on that pair multiple times under different variable renamings, and we then choose the best merging over all renaming choices. Alternatively, we can interleave renaming with merging by augmenting the dynamic programming state with extra information to indicate which variables have been renamed to which. We note, however, that there are exponentially many variable renamings and thus such extension would require heuristics to approximate which renamings are profitable with respect to merging.

Encoding Conditionals

Conditionals were not encoded in our formulation, and incorporating them depends on the exact representation of conditionals as well as the procedure that merges two already-aligned functions. Nevertheless, the most likely scenario is that function merging is applied to a low-level intermediate representation language. There, compilers like GCC or LLVM split a condition into an instruction computing the predicate followed by a conditional jump statement, and append an unconditional jump to the end of the condition’s body. For instance, a statement
if(X1){Y1} elif(X2){Y2}; Z
can be transformed into
b1=..; cond-jmp b1 L1; Y1; jmp L1’; b2=..; cond-jmp b2 L2; Y2; jmp L2’; Z
. This can be abstracted as:

[b1=..
\cdot
cond-jmp b1 L1
\cdot
Y1
\cdot
jmp L1’
|
b2 =..
\cdot
cond-jmp b2 L2
\cdot
Y2
\cdot
jmp L2’]
\cdot
Z
,

which soundly accounts for conditionals. Merging this with another function will allow us to match the computation of
b1
,
b2
with a corresponding instruction in the other function.

Branch Fusion

Our techniques can be adapted to merge any two programs that use standard sequential and branching constructs, and not just functions. In particular, our results carry over to the closely related problem of
branch fusion
, where the goal is to merge two similar branches of an
if-else
statement into a single branch in order to reduce code size
(
6
;
24
)
.

The Need for Well-nesting

Our approach heavily relies on the well-nesting of branches and only considers reorderings local to each branching construct. We note that our results can be stated more generally in terms of reordering the successors of nodes at the CFG-level, even when the CFG is not well-nested. However, this would crucially depend on the procedure used to identify meaningful points of reordering so as to balance the branching factor and the depth of the reordering.

Handling Code Motion and Data Dependencies

An interesting direction for future work is to extend our approach so that it supports code motion based on an arbitrary set of data dependence rules between the program statements, which do not necessarily follow the well-nested structure of the program. For example, an optimizing compiler might choose to move out a statement from the body of a loop, while keeping the program equivalent to its original version. This would enable new reorderings, which might open up the possibility of better alignments.

6.
Conclusion

In this work, we considered an expressive formulation for function merging that incorporates branch reordering. We then provided a thorough algorithmic and complexity-theoretic analysis of the problem. We showed that the problem is
NP
-hard even under severe restrictions on the input programs, and we identified natural parameters that make the problem fixed-parameter tractable.

Proof of Theorem

See

Proof.

For correctness, by Lemma
3.2
, we only need to show correctness of the updated
Upd-
\ast
and
Contains
functions in Algorithm
3
. It is not hard to see that with these definitions, invoking
Contains
(u_{i},v,X_{i})
in the modified Algorithm
2
, where
X_{i}
is a signature, returns the same boolean value as invoking
\text{Contains}(u_{i},v,X_{i})
in the original Algorithm
2
, where
X_{i}
is a set of visited nodes. This implies that the modified Algorithm
2
explores the state space in the same way as the original Algorithm
2
, and thus computes the same value.

Namely, we start with a signature
X_{i}
containing one empty record, corresponding to the empty set initially passed in the original algorithm. At
Upd-en
, we increase the depth and go to a previously unvisited node, so we push a new empty record on the stack. At
Upd-seq
, we move to the neighbouring same-depth node, which cannot have been visited before, so we get rid of the current top record and replace it with a new empty record. At
Upd-ex
, we decrease the depth and pop the current record from the stack. Moreover, we need to update the record of the (immediate) enclosing branching construct to inform it that
u_{i}
’s branch has been fully visited, which we do by inserting the index of that branch. At
Upd-done
, we have
u_{i}=r_{i}
and the signature has exactly one record, so we pop it to get the empty signature
[],
which will persist until
P_{i}
is fully processed, because
u_{i}
will be set to
\bot.
Finally,
Contains
(u_{i},v,X_{i})
checks whether the branch of
u_{i}
identified by
v
is not yet processed, which is a simple membership check on the top record of the stack.

For the time complexity, note a signature for
P_{i}
can be directly represented as a stack, with each of its elements being a subset of
\{1,\dots,b_{i}\}.
Clearly, operations on a given stack element, e.g., inserting an index or checking membership, can be done in
\mathcal{O}(b_{i})
time. Manipulating the stack itself, e.g., copying, pushing, popping, can be naively done in
\mathcal{O}(b_{i}h)
time, where
h
is the height of the stack, which can be as large as
\mathcal{O}(d_{i}).
Thus, each call to
Upd
-
\ast
and
Contains
takes
\mathcal{O}(b_{i}d_{i})
time.

As argued in Lemma
3.3
, we have
\mathcal{O}(2^{b_{i}\cdot d_{i}})
possible signatures for
P_{i}.
Since we remember an index and a signature for each program
P_{i},
we get
\mathcal{O}(2^{b_{1}d_{1}+b_{2}d_{2}}\cdot n_{1}n_{2})
dynamic programming states. In each state, for
i\in\{1,2\},
we make
\mathcal{O}(b_{i})
calls to
Contains
and
\mathcal{O}(1)
calls to
Upd
-
\ast,
each taking
\mathcal{O}(b_{i}d_{i})
time, which is clearly upper bounded by
\mathcal{O}((b_{1}+b_{2})^{2}(d_{1}+d_{2})).
Other routine operations, such as checking and fetching values from the memoization table, can also be done within the same time bound. This gives the claimed time complexity.
