ContextCov : Deriving and Enforcing Executable Constraints from Agent Instruction Files
Reshabh K Sharma

Abstract
. As Large Language Model (LLM) agents increasingly execute complex, autonomous software engineering tasks, developers rely on natural language Agent Instructions (e.g., AGENTS.md ) to enforce project-specific coding conventions, tooling, and architectural boundaries. However, these instructions are passive text. Agents frequently deviate from them due to context limitations or conflicting legacy code, a phenomenon we term Context Drift . Because agents operate without real-time human supervision, these silent violations rapidly compound into technical debt. To bridge this gap, we introduce ContextCov , a framework that transforms passive Agent Instructions into active, executable guardrails. ContextCov extracts natural language constraints and synthesizes enforcement checks across three domains: static AST analysis for code patterns, runtime shell shims that intercept prohibited commands, and architectural validators for structural and semantic constraints. Evaluations on 723 open-source repositories demonstrate that ContextCov successfully extracts over 46,000 executable checks with 99.997% syntax validity, providing a necessary automated compliance layer for safe, agent-driven development. Source code and evaluation results are available at https://anonymous.4open.science/r/ContextCov-4510/ .



1.
Introduction

Large language model agents are fundamentally changing how software is developed. Early tools like GitHub Copilot operated as autocomplete engines with instantaneous human verification. Chat-based interfaces such as Cursor
(
18
)
allowed developers to delegate larger tasks, but the developer remained an active supervisor. We are now entering the era of autonomous agents. Tools like GitHub Copilot Workspace
(
28
)
, Devin
(
16
)
, SWE-Agent
(
61
)
, and OpenHands
(
59
)
operate asynchronously to complete high-level objectives, with benchmarks like SWE-bench
(
36
)
driving rapid capability improvements. These agents often run for hours in cloud environments without human oversight. As agent autonomy increases, certain classes of constraints become increasingly difficult to monitor manually. Style violations blend into large diffs, architectural boundary crossings require mental tracking of module dependencies, and build workflow deviations may not surface until much later.

This shift motivates a fundamental change in how we communicate constraints to agents. The specification can no longer reside solely in the developer’s mind or in transient chat history. It must be externalized and persistent.

The Rise of Agent Instructions.

To bridge this supervision gap, the developer community has organically adopted
Agent Instruction files
. Stored in files such as
AGENTS.md
,
CLAUDE.md
, or
copilot-instructions.md
, these documents define the rules of engagement for autonomous agents. The agents.md website
(
2
)
reports that over 60,000 GitHub repositories now include such files. Recent taxonomic studies have identified over 16 categories of instructions
(
14
)
, which we organize into three broad categories based on enforcement mechanism.
Process constraints
govern build commands, package managers, and environment setup (e.g., “Always use
pnpm
, never
npm
”).
Source constraints
specify style guides, naming conventions, and API preferences (e.g., “Use arrow functions over anonymous function expressions”).
Architectural constraints
define module dependencies and layer restrictions (e.g., “The UI layer must not import from the database layer”).

The Problem.

Agent Instructions suffer from a critical flaw. They are passive text files, not executable specifications. This introduces the challenge of
Context Drift
, where an agent produces changes that violate the constraints specified in its instructions. Many constraints are inherently difficult to verify through manual review. Without automated enforcement, violations accumulate silently.

Two distinct challenges contribute to Context Drift. The first is
underspecified instructions
, which we do not address since agents cannot follow unspecified constraints. The second, which we focus on, is
agent non-compliance
. Even when instructions are adequately specified, agents may fail to follow them due to conflicting input, capability limitations, context overload, or codebase patterns that conflict with stated instructions
(
41
;
23
)
. We term this gap between what agents
should
do and what they
actually
do the Reality Gap.

The Reality Gap has severe implications. An agent instructed to “use
pnpm
” but encountering legacy
package-lock.json
files faces an instruction-environment conflict. LLMs often prioritize immediate context over system-level directives
(
53
;
25
;
34
)
, leading to non-compliant changes. Similarly, agents optimizing for local task completion may cause architectural erosion
(
6
)
by introducing circular dependencies or layer breaches. Perhaps most concerning, these violations compound over time
(
43
)
. When an agent mimics existing patterns that violate instructions, subsequent agent runs continue and amplify the drift.

Our Approach.

ContextCov
addresses this challenge by transforming passive Agent Instructions into active, verifiable invariants. We argue that as agent autonomy increases, Agent Instructions must be treated as executable specifications, not passive documentation but verifiable code that compiles into runtime checks.
ContextCov
operationalizes this principle through (1)
Hierarchical Constraint Extraction
, a path-aware parsing algorithm that preserves semantic scope imposed by heading hierarchies, (2)
Domain-Routed Policy Synthesis
, an intent classification system that routes each constraint to specialized code generators for
Process
,
Source
, or
Architectural
enforcement, and (3)
Multi-Layer Runtime Enforcement
, comprising a Process Interceptor via PATH injection, a Universal Static Linter built on Tree-sitter, and an Architectural Validator using graph algorithms and LLM-based judgment.

3.
ContextCov
Design

ContextCov
consists of two main phases.
Check generation
extracts and synthesizes constraints into executable checks, and
runtime enforcement
executes these checks during agent operation. Given an Agent Instruction file,
ContextCov
generates code-based checks that can be incrementally updated as the instruction file evolves. At runtime, source and architectural checks can be enforced over an entire repository, a git diff, or just unstaged changes, while process checks are enforced during agent execution.
ContextCov
is implemented in Python and uses
gpt-5.2-chat
for all LLM-based operations including constraint refinement, intent routing, code generation, and semantic evaluation.

3.1.
System Overview

Figure
2
presents the high-level architecture. During extraction, Agent Instruction documents are parsed into a Markdown Abstract Syntax Tree, and a path-aware algorithm traverses the tree extracting constraints as slices with their hierarchical context preserved. An LLM refines each constraint into a standalone, unambiguous statement. During synthesis, each refined constraint is classified by an intent router into one of four enforcement domains and passed to specialized code generators that produce executable Python checks. These checks are stored in a JSON file.

Figure 2
.
Architecture of
ContextCov
. The check generation phase comprises Extraction (parsing Agent Instructions into a Markdown AST and refining constraints via LLM) and Synthesis (routing constraints to domain-specialized code generators). The Enforcement phase executes checks through a Process Interceptor, Universal Static Linter, and Architectural Validator.

The
Enforcement
phase executes these checks through specialized modules. A Process Interceptor uses PATH shims to intercept shell commands before execution. A Universal Static Linter uses Tree-sitter to analyze source code across multiple languages. An Architectural Validator constructs and queries dependency graphs to detect structural violations. Finally, an LLM-as-judge evaluates semantic architectural constraints that cannot be verified through static analysis alone.

This architecture provides several benefits. When Agent Instructions change, only affected constraints are re-extracted and re-synthesized, enabling efficient incremental updates. Using separate code synthesis modules improves generation quality, as each expert generator is prompted with domain-appropriate patterns and examples. The multiple enforcement modules address the heterogeneity of agent actions. Process constraints require runtime interception, source constraints require AST analysis, deterministic architectural constraints require graph reasoning, and semantic architectural constraints require LLM-based judgment.

3.2.
Constraint Extraction

The extraction phase transforms unstructured Markdown into a set of refined, standalone constraints. This is challenging because Agent Instructions are written for human readers who naturally understand context and scope from document structure.

The Challenge of Lexical Scope.

Simple approaches to Agent Instruction segmentation fail to preserve
lexical scope
. Consider the following excerpt:

⬇

#

Backend

##

Testing

-

Use

pytest

##

Database

-

Use

SQLAlchemy

The instruction “Use pytest” appears as a standalone bullet, but its meaning depends on its hierarchical context and applies to
Backend Testing
, not to the entire project or to Database operations. If we extract this constraint without its context, we might incorrectly enforce pytest usage for frontend code or database migrations.

Markdown Abstract Syntax Tree.

To preserve this hierarchical context, we parse each Agent Instruction file into a tree structure. Internal nodes represent headers at various levels (H1 through H6), leaf nodes represent content blocks (paragraphs, list items, code blocks), and edges represent containment relationships. This tree structure mirrors how humans mentally organize the document when reading it.

Path-Aware Slicing.

For each leaf node representing a potential constraint, we compute its
header path
, the ordered sequence of ancestor headers from the document root to the leaf. In the example above, “Use pytest” has the header path
[Backend, Testing]
. We then use an LLM to rewrite the raw instruction into a standalone, unambiguous statement that incorporates this context, producing a refined constraint like “For backend testing, use the pytest framework for all unit and integration tests.” This refinement step disambiguates scope and normalizes diverse phrasings into consistent constraint statements that can be enforced without additional context.

Stable Identifiers for Incrementality.

To support incremental updates, we assign each constraint a stable identifier by hashing its header path and content. When a developer modifies one section of an Agent Instruction file, only constraints from that section need to be re-extracted and re-synthesized. Constraints from unmodified sections retain their identifiers and their previously generated checks remain valid. This is important for large instruction files where full re-extraction would be expensive.

3.3.
Constraint to Check

This phase transforms refined constraints into executable Python code. Rather than using a single monolithic code generator, we route each constraint to a specialized generator based on its enforcement domain. This domain-specific approach improves code quality because each generator is optimized for its particular verification pattern.

The Intent Router.

The Router classifies each constraint into one of four enforcement domains. For the
Process Domain
, the router extracts target binary names (e.g.,
npm
,
yarn
), the enforcement level, and the applicable scope. For the
Source Domain
, it identifies target programming languages, the pattern type to detect, and the severity level. For the
Architectural Deterministic Domain
, it determines the constraint type (dependency direction, cycle detection, or boundary enforcement) and selects an appropriate graph algorithm. For the
Architectural Semantic Domain
, it preserves the natural language description of the design principle for later LLM evaluation.

The router’s classification is performed by the LLM, prompted with examples of each domain to improve accuracy.

Specialized Code Generators.

Each domain has a specialized Expert Generator that produces Python code tailored to that domain’s verification needs. The
Process Expert
generates code that inspects command-line arguments and environment variables, returning a verdict that determines whether the command should proceed. The
Source Expert
generates code using Tree-sitter bindings that constructs AST queries and traverses parse trees, returning violations with precise file and line information. The
Architectural Expert
generates code using NetworkX that applies graph algorithms to dependency structures, detecting cycles, layer violations, or boundary crossings.

Tree-sitter grammars are bundled for Python, TypeScript, JavaScript, Go, and Rust. This coverage addresses the most common languages in repositories with Agent Instructions, though additional languages can be added by installing the corresponding Tree-sitter packages.

3.4.
Runtime Check Enforcement

The enforcement phase executes synthesized checks through four specialized modules, each designed for a particular type of constraint.

Process Interceptor.

Enforcing process constraints requires intercepting shell commands before execution. We use
$PATH
manipulation for its simplicity and portability.
ContextCov
creates a shim directory containing wrapper scripts for monitored binaries and prepends this directory to
$PATH
. Each monitored binary (e.g.,

⬇

When a command is executed, the shell resolves the binary via
$PATH
and finds our shim first. The shim loads relevant checks from the JSON file and executes each check with the command arguments and environment. If any check fails, the shim prints an error message to stderr explaining which constraint was violated and exits with code 1, preventing the command from running. If all checks pass, the shim uses
which -a
to find the real binary and executes it with the original arguments, making the interception transparent to the agent.

Universal Static Linter.

ContextCov
uses Tree-sitter as a universal parser for source code analysis. Tree-sitter provides incremental parsing, graceful error recovery, and a uniform API across languages, making it ideal for analyzing code in diverse repositories. The linter scans source files matching configured patterns, parses each file with the appropriate grammar based on file extension, and runs all applicable checks. Each check receives the parse tree, the raw source bytes, and the file path, allowing it to construct queries, traverse the AST, and report violations with precise locations. Semantic Architectural Validator.

Some architectural constraints cannot be verified through static analysis alone because they require understanding the intent behind code. For example, the constraint “Do not use another component’s storage keys, define a proper API instead” cannot be checked by examining import graphs or file paths. It requires understanding what constitutes a “storage key,” which code belongs to which “component,” and whether an access pattern constitutes a violation.

For these semantic constraints, we use an LLM-as-judge approach
(
17
)
. When evaluating code changes, the LLM receives the constraint text, the relevant code snippet, and surrounding context such as file path and neighboring code. The LLM then judges whether the code respects the design principle, providing a verdict and explanation. Semantic checks produce
WARNING
verdicts rather than hard blocks, flagging potential violations for human review while avoiding false positives from overly strict interpretation.

3.5.
Handling Ambiguity

A key design decision is how to handle ambiguous constraints. Agent Instructions are often written informally, and the same intent can be expressed in many ways. When a constraint like “Use
pnpm
” is encountered, should it block only explicit
npm
invocations, or also
yarn
and
bun
? Should it apply globally or only in certain directories?

We adopt a fail-closed philosophy where ambiguous constraints are interpreted strictly. “Use
pnpm
” triggers blocking of
npm
,
yarn
, and
bun
globally, even though a human reader might interpret this more narrowly. This approach may cause false positives, but we argue this is the correct trade-off. False positives can be overridden by developers who understand the context, either by refining the Agent Instructions to be more precise or by marking specific checks as exceptions. False negatives, on the other hand, allow violations to slip through undetected, accumulating as technical debt. This philosophy aligns with security principles where, when uncertain, the system denies the action and requires explicit authorization.

5.
Discussion

The shift from human-supervised to autonomous agents fundamentally changes the role of project documentation. Context Drift, where agents produce changes that violate their instructions, is not merely a technical bug but a symptom of a deeper mismatch between how we document intent and how agents consume it. We discuss the theoretical and practical implications of treating Agent Instructions as executable specifications to bridge this Reality Gap.

5.1.
Documentation as Code

Historically, software documentation was
descriptive
, written for humans who use common sense to bridge the gap between outdated docs and current code. In the era of autonomous agents, documentation like
AGENTS.md
is
prescriptive
, serving as literal execution context.
ContextCov
forces a paradigm shift where documentation must co-evolve with the codebase. By aggressively blocking commands or flagging code that violates Agent Instructions, the tool treats ambiguity and staleness not as minor annoyances but as build-breaking defects. This effectively turns passive Markdown into a living contract between the human developer and the AI agent.

This shift has several implications. When
ContextCov
blocks an agent action, developers face a choice. Either the agent’s action was wrong and the instructions are correct, or the instructions need updating. Both outcomes improve the repository. This creates an instruction quality feedback loop that does not exist with passive Agent Instructions. Just as code changes undergo testing, Agent Instruction changes should be tested.
ContextCov
enables “instruction tests” that verify the codebase complies with Agent Instructions before merging instruction changes.

5.2.
The Agentic Feedback Loop

Because natural language is inherently ambiguous, compiling it into strict checks will yield “false positives,” such as globally blocking
npm
when the developer only meant to block it in
/backend
. Instead of seeing this as a failure of the tool, we view it as a critical communication mechanism.

When an agent hits a
ContextCov
enforcement block, the error is fed back into its context window. This empowers the agent to reason about the failure. If the agent determines the rule was poorly scoped, it can autonomously propose a fix to the Agent Instructions.
ContextCov
transforms the agent from a passive consumer of documentation into an active maintainer of project specifications. Our design adopts a strict, fail-closed interpretation of documented constraints (Section
3.5
). We argue that ambiguity in Agent Instructions is itself a defect. If a rule has valid exceptions, those exceptions should be specified explicitly. By blocking ambiguous cases,
ContextCov
forces Agent Instructions to become more precise over time, progressively narrowing the Reality Gap.

5.3.
Executable Interpretability

A major challenge in prompt engineering is interpretability. A developer writes “Ensure a clean architecture” but has no idea how the LLM interprets “clean.”
ContextCov
addresses this by materializing the agent’s understanding into readable, deterministic Python code through Tree-sitter queries and NetworkX graphs. Developers can audit the generated checks to see exactly what the agent thinks the prompt means. If the generated check is too narrow, the developer instantly knows their natural language prompt was too vague. In this sense,
ContextCov
acts as a prompt debugger, providing visibility into how natural language constraints are operationalized.

This interpretability enables iterative refinement. When a check produces unexpected results, developers can trace the issue to the original constraint and refine it.

5.4.
Guardrails vs. Sandboxes

It is important to distinguish
ContextCov
from security sandboxes. Security mechanisms like SELinux
(
52
)
, AppArmor
(
8
)
, and seccomp
(
40
)
enforce mandatory access controls at the kernel level, while container runtimes like gVisor
(
29
)
and Firecracker
(
4
)
provide process isolation. Runtime verification frameworks
(
32
;
15
;
51
)
monitor program execution against formal specifications.
ContextCov
is not designed to prevent a malicious actor from compromising a system. Rather, it is designed to prevent a well-intentioned but hallucinating agent
(
39
)
from degrading the repository. By restricting the execution environment through mechanisms like the Process Interceptor,
ContextCov
bounds the agent’s action space, ensuring that its exploratory problem-solving stays within approved architectural and operational limits.

ContextCov
assumes three trust boundaries. Agent Instructions are written by authorized maintainers, the repository is not adversarial, and generated checks run without write permissions. Process checks can only block or allow commands, and static checks are read-only AST queries. Organizations should treat
AGENTS.md
with the same rigor as
.github/workflows/
.

7.
Limitations

ContextCov
may flag code that does not actually violate the intended constraint. This can occur when the LLM misinterprets the natural language constraint during extraction, when the synthesized check is overly strict, or when the constraint has implicit exceptions not captured in the Agent Instructions. When false positives occur, they serve as signals for developers to refine their Agent Instruction files, enabling the generation of more appropriate checks over time.

We did not run controlled experiments with LLM agents because diffs generated by agents for specific repositories are not publicly available. While our detection results on existing codebases suggest
ContextCov
would prevent agent-introduced violations, a study comparing agent task success with and without
ContextCov
enforcement would directly demonstrate its value. Such an evaluation would require either access to proprietary agent execution logs or a large-scale study where agents are deployed on real repositories with
ContextCov
integration.

8.
Conclusion

As agents take on more complex, multi-file tasks, certain classes of constraints become impractical to enforce through manual review. Style conventions, architectural boundary rules, and process workflow requirements are inherently difficult to verify by inspection. The specification that once resided in the developer’s mind must be externalized to Agent Instruction files, yet these files are passive text, and without automated enforcement, Context Drift accumulates silently.

ContextCov
addresses this challenge by treating Agent Instructions as executable specifications, providing automated enforcement for constraints that are difficult to monitor manually. Through hierarchical constraint extraction, domain-specialized code synthesis, and multi-layer runtime enforcement,
ContextCov
transforms passive instructions into active invariants that prevent agent violations. Our evaluation on 723 open-source repositories demonstrates that
ContextCov
successfully extracts over 46,000 executable checks with 99.997% syntax validity and detects over 500,000 violations, with 81% of repositories containing at least one violation.

Future work could explore self-healing instructions where
ContextCov
suggests edits to Agent Instructions or code changes to restore compliance. Agent Instruction files could also adopt structured language features that enable deterministic check extraction without LLM involvement, improving reliability and reducing cost.

As autonomous agents become standard contributors to software repositories, frameworks like
ContextCov
will be essential for maintaining repository integrity, bridging the Reality Gap between what agents are told to do and what they actually do.
