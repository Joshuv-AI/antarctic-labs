 ABSTRACT
The Natural Resources Management Team (NRM) at Oak Ridge National Laboratory (ORNL) maintains
an extensive archive of ecological data accumulated over decades of field work — wildlife surveys, GIS
mapping files, environmental assessments, photographs, and acoustic recordings. This data was previously
stored on a shared network drive, making it difficult to search, slow to access remotely, and vulnerable to
data loss.
This report documents a two-phase initiative to digitize and modernize access to this archive. In Phase
1, 1,452,590 files — approximately 4 terabytes of data — were migrated to secure cloud storage and
made searchable through a web-based interface. Staff can now find files by keyword, file type, date, or
geographic location on an interactive map, from any browser, without navigating complex folder structures.
Original file creation dates were recovered from the old server for 99.6% of the archive, preserving the
historical record.
In Phase 2, an AI-powered chat interface was added, allowing staff to ask questions in plain English and
receive answers synthesized directly from document content. Rather than finding a file and opening it, a
user can now ask "What bat species have been recorded on the reservation?" and receive a structured, cited
answer drawn from across the document library in seconds.
The result is a modern, searchable data library that makes decades of institutional knowledge accessible
and actionable — reducing the time staff spend locating information and preserving the value of the team’s
historical data for current and future research.

 1. PROJECT BACKGROUND & OBJECTIVES
The Natural Resources Management Team at ORNL has conducted systematic ecological monitoring of
the Oak Ridge Reservation (ORR) for decades. This work has produced an extensive and irreplaceable
archive of biological surveys, geographic information system (GIS) data, field photographs, environmental
assessments, acoustic recordings, and technical reports — representing the most comprehensive longitudinal
record of wildlife and habitat conditions on the reservation.
Until recently, this archive resided on a shared network drive (SMB server). While functional as a file
storage system, this approach presented several operational challenges:
 • Discoverability: Staff had to know where a file was stored, or remember its name, to find it. There
 was no way to search across the entire archive by topic, date, or location.
 • Preservation risk: A single server hosted the team’s entire decades-long data record, with limited
 redundancy.
 • Institutional knowledge loss: As staff turned over, knowledge of where specific data resided — and
 what it contained — left with them.

1.1 OBJECTIVES
This initiative was undertaken with four primary objectives:
 • Preserve the archive. Migrate the full contents of the shared drive to a resilient, redundant cloud
 storage platform, ensuring the data is protected against hardware failure and accessible long-term.

 1

 • Make the data searchable. Build a web-based search tool that allows any authorized team member to
 find files by keyword, file type, date of creation, or geographic location — without needing to know
 the folder structure.
 • Recover historical metadata. The migration process stripped original file creation dates from most
 files. A key objective was to recover these dates from the source server and restore them to the
 archive, preserving the chronological integrity of the data record.
 • Enable intelligent access through AI. As a Phase 2 objective, add the ability for staff to ask
 natural-language questions and receive answers synthesized directly from document content —
 reducing the time between a question and an answer from hours to seconds.
This initiative aligns with ORNL’s broader commitment to open science, data stewardship, and the
long-term preservation of environmental monitoring records. The Oak Ridge Reservation’s ecological
archive represents a unique scientific asset — one that grows more valuable over time as long-term trends
emerge and historical baselines become harder to reconstruct. Making this data accessible and searchable
ensures it can contribute to future research, regulatory reporting, and conservation planning for years to
come. The project was executed incrementally, with each phase delivering immediately usable capabilities
before the next was begun, allowing the team to validate results with real data and adjust priorities based
on operational feedback before committing to further investment.

 2. PHASE 1: DATA MIGRATION & CORE SEARCH
Phase 1 established the foundation of the data library — moving the team’s entire archive from the shared
network drive to cloud storage and building the search interface that makes it accessible. This phase was
the largest in scope, requiring both significant data engineering work and the development of a custom web
application suited to the team’s needs.

2.1 DATA MIGRATION FROM SHARED DRIVE TO CLOUD
The first step was a full migration of the NRM shared drive (SMB server) to Amazon S3, a cloud
storage platform operated by Amazon Web Services (AWS). S3 was selected for its durability (files are
automatically replicated across multiple physical locations), its cost-effectiveness at large scale, and its
compatibility with the search and AI tools planned for later phases.
The migration transferred 1,452,590 files totaling approximately 4 terabytes of data. Every file type
present on the shared drive was preserved, including:
 • GIS data (shapefiles, KML/KMZ, MapInfo files, raster imagery)
 • Documents (PDFs, Word files, PowerPoint presentations, spreadsheets)
 • Field photographs and scanned documents
 • Acoustic monitoring recordings (bat and wildlife surveys)
 • CAD drawings and technical files
 • Miscellaneous data files (R statistical data, databases, log files)
The original folder structure was preserved in its entirety, so staff who are familiar with the drive’s
organization can still navigate by path if preferred. At the same time, the indexing pipeline created a
searchable database of every file’s name, location, type, and size — making it possible to find files without
knowing where they are stored.

2.1.1 Creation Date Recovery
One consequence of the migration was the loss of original file creation dates. When files are copied
between storage systems, the operating system records the copy date rather than the original creation date
— in this case, the February 2026 migration date. Since date filtering is a critical capability for a historical
ecological archive, a dedicated effort was undertaken to recover the original dates.
A custom script was developed to read the original creation timestamps directly from the SMB server and
write them back to the database record for each file. After several processing runs, original creation dates
were successfully recovered for 1,446,135 of 1,452,590 files — a recovery rate of 99.6%. The remaining
0.4% of files could not be matched, most likely because they had been deleted or moved on the source
server since the migration. These files display their upload date with a clear label indicating the date
source, so users are never misled about what the date represents.

2.2 BASIC FILE SEARCH & DISCOVERY
With the data in cloud storage and indexed, the next step was building the search interface. A web
application was developed that allows staff to search the entire archive from any browser or knowledge of
the folder structure.

2.2.1 Keyword Search
The core search capability matches keywords against filenames and folder paths across all 1.45 million
files. Results are returned in under three seconds for most queries. The search engine uses a token-based
index — each filename is broken into individual words and those words are indexed separately — allowing
partial matches and multi-word queries to work naturally.
To reduce frustration from typos and variant spellings, a fuzzy matching system was implemented. When
a search returns no exact results, the system automatically tries near-matches at an edit distance of one
character — meaning it considers words that differ from the original by a single addition, deletion, or
substitution. For example, searching "bever" returns results for "beaver," and "frogg" returns results for
"frog." The system searches these alternatives in parallel and ranks results by how closely they match the
original term, ensuring the most relevant files appear first. A notice is displayed in the results header when
fuzzy matching has been applied, so staff are always aware when they are viewing approximate rather than
exact matches. This feature is particularly useful for species names and technical terms that staff may not
remember how to spell precisely.
As staff type in the search box, an autocomplete system suggests the closest matching filename drawn from
files already returned during the session. Suggestions appear instantly as a light gray hint below the input
field and can be selected with a single click to auto-fill and search. Because suggestions are built from
filenames the user has already encountered in their search session rather than from a separate database
lookup, the feature adds no delay and becomes progressively more useful as staff explore the archive.
Together, fuzzy matching and autocomplete reduce the effort required to find a specific file — particularly
for staff who are less familiar with the archive’s contents or the exact names of datasets they are looking
for.

2.2.2 Filtering & Sorting
Search results can be filtered and sorted using a set of controls displayed alongside the search box:
 • File type — results can be filtered to specific categories such as GIS Data, PDF, Word, Excel, Image,
 or Audio. Multiple types can be selected simultaneously.

 4

 • Date range — results can be filtered by creation date, using preset options (last 30 days, last year)
 or a custom date range. Because 99.6% of files have their original creation dates restored, this filter
 reflects when data was actually collected, not when it was migrated.
 • Sort order — results can be sorted by relevance (default), newest first, or oldest first. Date sorting
 operates across the full result set, not just the current page, ensuring the most recent or oldest files
 are always surfaced regardless of how many results exist.

2.2.3 Download
Every search result includes a secure, time-limited download link that allows staff to retrieve the file
directly from cloud storage. Links expire after one hour for security and are regenerated on demand with
each search.

2.3 MAP-BASED GEOGRAPHIC SEARCH
A significant portion of the NRM archive consists of geographically referenced data — files associated
with specific locations on the Oak Ridge Reservation. To support location-based discovery, an interactive
map interface was integrated into the search tool.
Staff can click any point on the map to search for files associated with that location. A configurable search
radius (1 km, 5 km, or 10 km) determines how broadly the search extends from the selected point. This is
useful for finding all GIS layers, survey reports, and photographs associated with a specific site, pond, or
habitat area without knowing the names of those files.
For users who need to search an irregular area rather than a fixed radius, a freehand drawing tool allows
them to outline any shape on the map. The search then returns files whose geographic coordinates fall
within the drawn boundary. This is particularly useful for searching along a survey transect, within a
specific management unit, or across a habitat patch that does not correspond neatly to a radius circle.
The map interface can also be used in combination with keyword and file type filters. For example, a user
could draw an area around a specific pond, filter for GIS Data files, and search for "survey" — returning
only GIS files tagged to that location that have "survey" in their name or path.

2.3.1 Map Enhancements: Result Pins & Sidecar File Groups
Following the initial map implementation, several enhancements were made based on operational
feedback.

2.3.2 Result Pins
Geo-referenced files returned by a map search are now displayed as orange pins on the map itself, in
addition to appearing in the results list on the left. Clicking a pin opens a popup that shows the filename
and a direct download link. This allows staff to visually confirm which files are associated with which
locations before downloading, which is particularly useful when searching a large area with many results.

2.3.3 Sidecar File Grouping
GIS data formats such as shapefiles consist of multiple companion files that must be used together — for
example, a shapefile named roads.shp is accompanied by roads.dbf, roads.shx, roads.prj, and other files.
Previously, these appeared as separate search results, which could be confusing.
The system now recognizes these file groupings automatically. When a parent file (such as a .shp or .MAP)
is returned in search results, its companion files are displayed as a grouped set beneath it. The map pin
popup for a parent file lists all companion files with individual download links, making it easy to download
a complete GIS dataset in one interaction.

 3. PHASE 2: AI-POWERED SEARCH
Phase 2 extended the data library beyond file discovery into active knowledge retrieval. While Phase
1 allows staff to find files by name, type, date, and location, it does not address a deeper challenge —
the knowledge contained inside those files. A staff member who wants to know what bat species have
been recorded on the reservation, or how water quality at a specific pond has changed over time, would
previously need to find the relevant reports, open them one by one, and read through them manually.
Phase 2 addresses this by adding an AI-powered chat interface that allows staff to ask questions in plain
English and receive answers synthesized directly from the content of documents in the library. Rather
than returning a list of files, the system reads relevant passages from across the archive and constructs
a structured, cited response — reducing the time between a question and a useful answer from hours to
seconds.

 Figure 3. AI-Powered Search

3.1 PHASE 2 OVERVIEW — WHY AI SEARCH
The Basic Search capability delivered in Phase 1 solved the discoverability problem — staff can now find
any file in the archive in seconds, regardless of where it is stored or what it is named. However, finding a
file and extracting useful information from it are two different tasks, and Phase 1 addresses only the first.
In practice, many of the questions staff bring to the data library are not about files — they are about
findings. A wildlife biologist preparing a management report does not need to know that a survey
document exists; they need to know what it says. A team member responding to a regulatory inquiry does
not need a list of water quality spreadsheets; they need the data those spreadsheets contain. Under the
Phase 1 system, answering these questions still required a staff member to locate the relevant files, open

 7

each one, read through the content, and manually extract the information they needed — a process that
could take hours when the answer was spread across multiple documents.
This gap becomes more significant as the archive grows and staff turnover occurs. Institutional knowledge
— the awareness of which reports contain which findings, and where in a document the relevant information
sits — is difficult to transfer and easy to lose. The AI search capability addresses this directly by making
the content of the archive queryable, not just its filenames.
The decision to implement AI search was also shaped by practical considerations of cost and complexity.
Rather than building a custom natural language processing pipeline from scratch, the implementation
leverages AWS Bedrock — a managed AI service that handles document parsing, content indexing, and
language model access through a single platform. This approach significantly reduced development time
and ongoing maintenance burden while providing access to state-of-the-art language models that would be
impractical to develop or host independently.
The choice of Claude Sonnet 4.6 as the language model was based on its demonstrated ability to synthesize
information from multiple source documents, produce well-structured scientific summaries, and adhere
reliably to instructions about citation and factual grounding — qualities that are essential for a system
intended to support ecological research and regulatory reporting, where accuracy and traceability are
non-negotiable.

3.2 DOCUMENT CONTENT INDEXING (KNOWLEDGE BASE)
Before the AI chat interface could answer questions about the content of the library’s documents, those
documents needed to be read, processed, and stored in a form that supports rapid semantic retrieval. This
process — known as indexing — is the technical foundation on which all AI search capabilities rest.

3.2.1 What Indexing Does
Unlike a traditional keyword search, which matches exact words against filenames, content indexing
extracts the actual text from inside each document and converts it into a mathematical representation called
a vector embedding. A vector embedding captures the meaning of a passage of text, not just the words it
contains — allowing the system to retrieve documents that are semantically relevant to a question even
when they do not contain the exact words used in the query. For example, a question about "amphibian
population monitoring" can retrieve documents that discuss "frog and salamander surveys" without any of
those words appearing in the question itself.
Each document is divided into overlapping passages of approximately 300 words before embedding.
This chunking approach ensures that long documents — a 50-page survey report, for example — can be
searched at the passage level, so the system retrieves the specific section of a document that answers a
question rather than returning the entire document as a single undifferentiated result.

3.2.2 Implementation
The indexing infrastructure was implemented using AWS Bedrock Managed Knowledge Base, a fully
managed service that automates the entire pipeline from document ingestion to vector storage. This
eliminated the need to build and maintain custom parsing, chunking, and embedding code, and ensured
that the indexing process could be re-run as new documents are added to the archive in the future.
The Knowledge Base was configured to connect directly to the library’s cloud storage (Amazon S3) and
process all supported document formats found there. The embedding model used was Amazon Titan Text
Embeddings V2, which converts each text passage into a 1,024-dimensional vector stored in a dedicated S3
vector store. Vector storage was selected over traditional database approaches because it supports semantic
similarity search — the capability that allows meaning-based retrieval rather than keyword matching.

 8

3.2.3 Document Coverage
The indexing process targeted files with human-readable text content. Approximately 12,400 files were
identified as candidates, representing roughly 1% of the archive by file count but the majority of its written
scientific record. These included:
 • PDF reports and assessments
 • Word documents (field notes, survey reports, management plans)
 • PowerPoint presentations
 • Excel and CSV spreadsheets
 • Plain text files and markdown documents
A significant portion of the NRM archive consists of scanned paper documents saved as image files —
older field reports, handwritten notes, and forms that were digitized from physical records. Standard text
extraction methods cannot read these files because they contain no embedded text. To address this, visual
content processing was enabled for the Knowledge Base, using computer vision to recognize and extract
text from scanned images. This ensures that the team’s older documentary record — which may contain
some of the most historically significant ecological observations — is included in the searchable index.

3.2.4 Indexing Results
Upon completion of the indexing process, 254,396 searchable passages were stored in the Knowledge
Base, drawn from across the document collection. Each passage retains a reference to its source file, its
location within that file, and a relevance score that is calculated at query time based on how closely the
passage matches the user’s question. This metadata enables the system to cite specific source documents in
every answer and to provide direct download links so staff can retrieve and review the originals.
The indexing process is repeatable. As new documents are added to the library, the Knowledge Base
can be re-synchronized to incorporate them into the searchable index, ensuring the AI search capability
remains current as the archive grows.

3.3 AI CHAT INTERFACE
The AI chat interface is the user-facing component of Phase 2 — the point at which staff interact with the
indexed document content through natural language. It is accessible from the data library’s main web page
via a mode toggle that allows users to switch between Basic Search and AI Search without leaving the
application. When AI Search is selected, the search interface is replaced by a conversational panel with
a text input, a set of example questions to guide first-time users, and a running history of questions and
answers from the current session.

3.3.1 How a Question is Answered
When a staff member submits a question, the system processes it through a structured pipeline designed to
produce accurate, grounded answers as efficiently as possible.
Step 1 — Query routing. The system first determines what kind of information the question requires.
Questions that ask what documents say — such as "what species were observed at the P1 pond?" or
"summarize the findings of the 2021 wildlife surveys" — are routed to the document content index.
Questions that ask where files are — such as "find GIS files near Melton Hill" or "list PDF reports from
2022" — are routed to the file metadata search. Questions that require both are handled in parallel, with

 9

both searches running simultaneously to minimize response time. This routing step happens automatically
using keyword analysis, with no additional delay or input required from the user.
Step 2 — Content retrieval. The system queries the Knowledge Base with the user’s question and retrieves
the most semantically relevant passages from across the indexed document collection. Up to eight
passages are retrieved per query, ranked by relevance score. Passages from Word documents and PDFs
are prioritized over image-derived descriptions to ensure answers draw primarily from the team’s written
scientific record.
Step 3 — Answer synthesis. The retrieved passages, along with the original question, are passed to Claude
Sonnet 4.6 — a large language model developed by Anthropic and accessed through AWS Bedrock. The
model reads the passages and constructs a structured, coherent answer. It is explicitly instructed to base
its response only on the information present in the retrieved passages, to cite the source document for
every claim, and to focus on ecological and scientific content — species observations, survey methods,
population counts, habitat conditions, dates, and locations — rather than incidental details.
Step 4 — Response delivery. The answer is returned to the user in the chat panel, formatted with a brief
summary followed by bullet-pointed findings. Where file search results are included, direct download
links to the source documents are embedded in the response, allowing staff to retrieve the originals without
navigating away from the chat interface.

3.3.2 What the System Can and Cannot Do
The AI chat interface is designed to answer questions about the content of documents in the NRM archive.
It performs well on questions that require synthesizing information from one or more written reports
— species lists, survey findings, habitat observations, methodological descriptions, and chronological
comparisons across survey years.
It is not designed to answer general scientific questions about ecology or wildlife that are not grounded
in the team’s own data. The system is explicitly configured to decline such questions and redirect users
to the archive, ensuring that every answer it provides reflects the team’s actual field record rather than
external knowledge. This is an intentional design choice: the purpose of the tool is to make the team’s own
institutional knowledge accessible, not to serve as a general-purpose encyclopedia.
The system also cannot currently search the content of audio files — the archive’s 807,000 acoustic
monitoring recordings represent a specialized data type that requires purpose-built audio analysis tools
beyond the scope of this phase.

3.3.3 Example Interaction
To illustrate the system’s capabilities, the following is a representative example of an exchange with the AI
chat interface:
Question: "What bat species have been detected on the Oak Ridge Reservation, and what survey methods
were used?"
Answer: The system retrieved relevant passages from multiple bat survey reports and returned a structured
response identifying detected species by name, the survey sites where each was recorded, the methods
used — acoustic monitoring with automated recorders and mist netting — the years surveys were
conducted, and citations with download links to each source report. The complete response was returned
in approximately 12 seconds.
This type of answer — synthesized from multiple documents, structured for readability, and traceable to
primary sources — would previously have required a staff member to locate, open, and manually read
through several reports before assembling a response.

3.4 ANSWER QUALITY & SOURCE CITATIONS
The usefulness of an AI-powered search system depends not only on its ability to find relevant information,
but on the reliability and transparency of the answers it produces. A system that returns confident but
inaccurate responses — or that provides answers with no indication of where the information came
from — would undermine rather than support the team’s scientific work. Answer quality and source
transparency were therefore treated as design requirements, not secondary considerations.

3.4.1 Grounding in Source Documents
The most significant risk associated with large language models is their tendency to generate plausible-sounding
information that is not grounded in any actual source — a phenomenon commonly referred to as hallucination.
In a general-purpose context this is an inconvenience; in a scientific and regulatory context it is unacceptable.
An answer about species presence, population trends, or environmental conditions that is fabricated rather
than sourced could inform management decisions, regulatory submissions, or research conclusions in ways
that cause real harm.
To address this, the system is explicitly configured to base every answer exclusively on the passages
retrieved from the Knowledge Base. The language model is instructed that it may not introduce information
from its general training knowledge, may not speculate beyond what the documents say, and must clearly
indicate when the retrieved passages do not contain sufficient information to answer a question. When
the archive does not contain relevant content, the system says so directly and suggests how the user might
refine their query — rather than filling the gap with unverifiable information.

3.4.2 Source Citations
Every answer includes citations to the source documents from which the information was drawn. Citations
are formatted as direct download links to the original files, allowing staff to open and review the source
material with a single click. This serves two purposes: it allows users to verify the accuracy of the answer
against the primary document, and it provides a clear audit trail for any information that is used in a report,
regulatory submission, or management decision.
Citations appear naturally within the body of the answer rather than as a separate reference list, making
it easy to trace specific claims back to specific documents. For example, an answer about frog species
observed at a particular pond will identify the specific survey report that recorded each species, linked
directly to the file.

3.4.3 Structured Answer Format
Answers are formatted consistently to support readability and rapid information extraction. Each response
begins with a brief summary — one to two sentences that directly answer the question — followed by
bullet-pointed findings that present species names, dates, locations, counts, and other specific data in a
scannable format. Source citations and download links appear alongside the findings they support.
This structure was chosen deliberately. Staff using the tool are typically looking for specific facts to
inform a decision or populate a report, not reading for general interest. A structured format allows them
to extract what they need quickly, while the citations and download links ensure they can go deeper when
the situation requires it.

3.4.4 Continuous Improvement
Answer quality is influenced by the completeness and quality of the indexed documents. As the Knowledge
Base is re-synchronized to incorporate new documents added to the archive, the range and accuracy of

 11

answers will improve correspondingly. Questions that currently return limited results — because the
relevant documents have not yet been indexed, or because the information exists only in formats the system
cannot yet read — will become answerable as the index matures.
Staff feedback on answer quality is encouraged. Cases where the system returns an incorrect, incomplete,
or misleading answer are valuable signals for refining the system’s configuration and expanding its
document coverage over time.

 4. SYSTEM ARCHITECTURE & TECHNOLOGY STACK
4.1 OVERVIEW
The Natural Resources Management Team Data Library is a cloud-native system built entirely on Amazon
Web Services (AWS). It consists of three layers: a storage and indexing layer that holds the data and
makes it searchable, a compute layer that processes queries and generates AI-powered answers, and a web
application layer that staff interact with through their browser. All three layers are managed services —
meaning AWS handles the underlying infrastructure, security patching, and scaling automatically — which
minimizes the operational burden on the ORNL team and eliminates the need to maintain physical servers.
Figure 4 provides a high-level overview of the system’s components and how data flows between them.

4.2 CLOUD STORAGE (AMAZON S3)
Amazon Simple Storage Service (S3) is the foundation of the data library. S3 is an object storage platform
that stores files — referred to as objects — in a container called a bucket. The NRM archive is stored in
a single bucket named natural-resources, which holds all 1,452,590 files totaling approximately 4
terabytes of data.
S3 was chosen for several reasons. Files stored in S3 are automatically replicated across multiple physical
data centers, providing a level of redundancy that the original SMB server could not match. Storage
costs are low — approximately $0.023 per gigabyte per month — making it practical to retain the full
archive indefinitely. S3 also integrates natively with the other AWS services used in this project, including
DynamoDB, Lambda, and Bedrock, eliminating the need for custom data transfer infrastructure.
Files in S3 are not directly accessible to the public. Access is controlled through time-limited presigned
URLs, which are generated on demand by the search Lambda and embedded in search results as download
links. These URLs expire after one hour, ensuring that access to files remains controlled even when links
are shared.

4.3 SEARCH DATABASE (AMAZON DYNAMODB)
Amazon DynamoDB is a fully managed NoSQL database that stores the metadata and search indexes that
power the library’s search capabilities. Three DynamoDB tables were created for this project:
DynamoDB was chosen over a traditional relational database because it scales horizontally without
configuration changes, charges only for the storage and queries actually used, and integrates directly with
AWS Lambda without requiring a persistent database connection. At the scale of 1.45 million records, a
traditional database would require provisioning and maintaining a database server; DynamoDB handles
this transparently.

4.4 SEARCH API (AWS LAMBDA — EPS-SEARCH)
The search Lambda is the computational engine of the data library. It is a Python 3.12 function deployed
on AWS Lambda — a serverless compute platform that runs code on demand in response to requests,
with no server to provision or maintain. The function is exposed to the web application through a public
Function URL and processes every search request made by staff.
The Lambda implements the following search capabilities:

4.5 GEOGRAPHIC INDEXING AND MAP SEARCH
Files that contain geographic coordinates — including KML, KMZ, and shapefile formats — are indexed
in a separate DynamoDB table (eps-geo-index) using a grid cell system. Each file’s coordinates
are mapped to a ∼1 km2 grid cell identified by a rounded latitude/longitude pair. When a map search
is performed, the Lambda queries all grid cells that overlap the selected area and filters the results
geometrically before returning them.
Two map search modes are supported:
 • Radius search — the user clicks a point on the map and selects a search radius (1 km, 5 km, or
 10 km). The Lambda identifies all grid cells within that radius and applies a haversine distance
 calculation to confirm that each candidate file’s coordinates fall within the exact radius boundary.
 • Polygon search — the user draws a freehand shape on the map. The Lambda identifies all grid cells
 that overlap the bounding box of the drawn shape and applies a ray-casting point-in-polygon test to
 confirm that each candidate file’s coordinates fall within the exact drawn boundary.
Safety caps of 400 grid cells and 3,000 matched files are applied to prevent queries over very large areas
from exceeding the Lambda’s execution timeout.

4.6 DOCUMENT CONTENT INDEX (AWS BEDROCK KNOWLEDGE BASE)
The document content index is what enables the AI chat interface to answer questions about what
documents say, rather than just where they are stored. It is implemented using AWS Bedrock Managed
Knowledge Base — a fully managed service that automates the process of extracting text from documents,
converting it into a searchable mathematical representation, and storing it in a vector database.

 16

The indexing process works as follows. When the Knowledge Base is synchronized, it crawls the S3
bucket, reads each supported document, and divides the text into overlapping passages of approximately
300 words. Each passage is then converted into a vector embedding (a list of 1,024 numbers that represents
the meaning of the passage) using the Amazon Titan Text Embeddings V2 model. These embeddings are
stored in an S3-based vector store.
When a user asks a question, the question is converted into a vector embedding using the same model, and
the vector store is searched for passages whose embeddings are mathematically similar to the question’s
embedding. This is called semantic search: it finds passages that are relevant in meaning, not just in
keywords, allowing the system to match a question about “amphibian population monitoring” to a
document that discusses “frog and salamander surveys” even though none of those words appear in the
question.
Visual content processing was enabled to handle scanned documents saved as image files. These files
contain no embedded text and cannot be processed by standard text extraction methods. With visual
content processing enabled, Bedrock uses computer vision to recognize and extract text from the images
before embedding, ensuring that older scanned field reports are included in the searchable index.
The Knowledge Base for this project indexed 254,396 passages from approximately 12,400 documents. It
is re-syncable as new documents are added to the archive.

4.7 AI CHAT (AWS LAMBDA — EPS-CHAT AND CLAUDE SONNET 4.6)
The AI chat Lambda (eps-chat) is a separate Python 3.12 function that handles all conversational AI
requests. It is deployed with a 3-minute execution timeout and 1,024 MB of memory to accommodate the
additional processing time required for AI inference.
When a question is submitted, the Lambda processes it through the following pipeline:
 1. Query routing — the Lambda analyzes the question using keyword matching to determine whether
 it requires document content retrieval, file metadata search, or both. This step is instantaneous and
 requires no model call.
 2. Parallel tool execution — the relevant searches are executed simultaneously. Document content
 retrieval queries the Bedrock Knowledge Base and returns the most semantically relevant passages.
 File metadata search invokes the eps-search Lambda and returns matching file records with
 presigned download URLs.
 3. Answer synthesis — the retrieved passages and file results are passed to Claude Sonnet 4.6, which
 synthesizes a structured, cited answer. The model is explicitly instructed to base its response only on
 the retrieved content, to cite source documents, and to include download links.
 4. Response delivery — the final answer, along with file results and document passages, is returned to
 the web application and displayed in the chat interface.
Claude Sonnet 4.6 is a large language model developed by Anthropic and accessed through AWS Bedrock.
It was selected for its demonstrated ability to synthesize information from multiple source documents,
produce well-structured scientific summaries, and adhere reliably to instructions about factual grounding
and citation — qualities essential for a system supporting ecological research and regulatory reporting.
The model is accessed through an AWS inference profile (us.anthropic.claude-sonnet-4-6), which
routes requests across AWS regions for improved availability.

4.8 WEB APPLICATION (ANGULAR)
The user-facing web application was built using Angular 17, a TypeScript-based web application
framework developed by Google. The application runs entirely in the user’s browser and communicates
with the backend Lambda functions through their public Function URLs using standard HTTP requests.
The application provides the following interface components:
 • Mode toggle — switches between Basic Search and AI Search modes.
 • Search input — keyword entry with autocomplete suggestions and fuzzy match notice.
 • Filter bar — file type selector, date range controls, radius buttons, and map filter toggle.
 • Results list — paginated file results with filename, path, file type, creation date, and download link.
 • Interactive map — Leaflet.js map with click-to-search, radius control, freehand draw-to-search, and
 geo result pins.
 • AI chat panel — conversational interface with example question chips, question history, structured
 answers, and source download links.
The application is version-controlled in a GitLab repository (https://code.ornl.gov/ai/arboretum_digitization)
and deployed by pushing updates to the repository, which triggers a build and deployment pipeline.

 5. PROPOSED FUTURE ENHANCEMENTS
The following improvements could be considered as next steps for the data library. They are presented in
approximate order of priority and potential impact. Each builds on the existing infrastructure and expands
the library’s capabilities without requiring major changes to the current system architecture.

5.1 AUTOMATED FILE SYNCHRONIZATION FROM THE SHARED DRIVE
The current data library reflects the contents of the shared drive at the time of the initial migration in
February 2026. Files added or modified on the SMB server since then are not automatically added to the
library and currently require a manual update. As new field data continues to be collected, keeping the
library synchronized with the shared drive will become increasingly important.
An automated synchronization pipeline could be developed to periodically identify and process changes
on the shared drive. The pipeline would detect files that have been added, modified, or deleted since the
previous synchronization, transfer new or updated files to Amazon S3 while preserving their original
metadata and timestamps, and update the DynamoDB search indexes. The Bedrock Knowledge Base could
also be synchronized as part of the same process so that new content becomes available through both the
standard search and AI chat interfaces.
The synchronization schedule could be configured based on the team’s needs, such as nightly during active
field survey periods and weekly during periods with less activity. An optional summary could also be
generated after each synchronization to report the files that were added, updated, or removed. A direct
upload option could also be added to the data library web application, allowing staff to upload files through
the browser without first placing them on the shared drive. This could be useful for field data collected on
laptops or tablets.

5.2 PHOTO AND VISUAL SEARCH
The library contains approximately 191,000 image files, including field photographs, camera trap images,
scanned field forms, and aerial imagery. Currently, these files can only be searched using their filenames
and folder paths. This makes many images difficult to find, especially when filenames consist of camera
identifiers, dates, or sequential numbers that provide little information about the image itself.
A visual search capability could be added using multimodal vector embeddings. Each image would be
represented based on its visual content, allowing users to search with natural language descriptions such
as ‘beaver dam”, ‘white-tailed deer trail camera”, or “aerial view of wetland”. Relevant images could then
be returned regardless of their filenames or folder locations. Text extraction could also be incorporated for
scanned field forms and handwritten notes, making these files searchable based on the information they
contain.
The estimated one-time cost to generate embeddings for approximately 191,000 images is $11.50, with
minimal ongoing costs at the expected search volume.

5.3 AUTOMATED BIOACOUSTIC ANALYSIS OF AUDIO RECORDINGS
The library contains approximately 807,000 audio recordings collected through automated wildlife
monitoring across the reservation, including bat echolocation surveys, frog call monitoring, and other
acoustic wildlife data. While the recordings can currently be searched by information such as date and
deployment location, their audio content is not searchable. As a result, users cannot search the library
based on the species detected within a recording.

 19

Automated species classification could be used to analyze these recordings and generate searchable
species tags using bioacoustic tools trained to recognize regional species. These tags could be stored in the
DynamoDB index and added as search filters, allowing users to search for records such as bat recordings
containing Perimyotis subflavus or frog surveys with wood frog detections. This would make the existing
collection much easier to explore and could provide a searchable long-term record of species observations
across the reservation.
This enhancement would require more development and evaluation than the other proposed improvements.
Work would include evaluating available classification models, developing a processing pipeline capable
of handling approximately 807,000 recordings, and establishing a process for evaluating classification
accuracy. Because of the size and complexity of the effort, this is better suited as a medium-term objective,
with the scope and technical approach discussed with the team before development begins.

5.4 BATCH DOWNLOAD
Staff often need to download groups of related files, such as shapefiles from the same survey, photographs
from a field session, or reports from a specific year. Currently, these files must be downloaded individually,
which can be inefficient when working with larger datasets.
A batch download option could be added to allow users to select multiple files from the search results and
download them together as a single compressed archive. This enhancement is estimated to require 10–15
hours of development effort and would make it easier for staff to work with collections of related files.

5.5 IN-BROWSER FILE PREVIEW
Currently, users must download a file and open it locally to view its contents. Adding an in-browser
preview for common file types, such as PDF reports and images, would allow users to quickly review a
file and confirm that it contains the information they need before downloading it.
A preview panel could be added directly to the search results interface to display PDFs and images in
the browser. PDFs can be displayed using standard browser functionality without requiring additional
infrastructure, while image thumbnails could be generated as needed and cached in S3.

5.6 AUTOMATED KNOWLEDGE BASE RE-SYNCHRONIZATION
The Bedrock Knowledge Base that supports the AI chat interface currently requires manual synchronization
whenever new documents are added. This process could be automated as part of the file synchronization
pipeline described above, allowing new documents to become available through the AI interface during the
same cycle in which they are added to the basic search results. This would be a relatively small addition,
and would fit naturally within the automated synchronization work.
