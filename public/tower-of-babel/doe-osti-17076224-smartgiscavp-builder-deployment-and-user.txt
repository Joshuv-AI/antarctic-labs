 ABSTRACT

This deployment and user guide provides technical information on the user interface SMARTGISCAVP, a
self-contained prototype developed at Oak Ridge National Laboratory for generating multi-page React
dashboards from plain-language requirements. It describes the builder interface, page types, requirements,
AI model selection, multi-page usage, generation and deployment behavior. The deployment guide covers
the following: prerequisites, quick-start commands, checks, configuration, image rebuilding, and general
troubleshooting. The builder is distributed as a Docker Hub image that bundles the React interface, Express
API, a Python retrieval-augmented generation engine, Vite/React project template, reference codebases, an
embedding model, and a prebuilt FAISS index. A live SMARTGISCAVP interface example demonstrates
an interactive GIS map, summary statistics, chart, and synchronized data table generated automatically. The
prototype runs offline except for calls to an external Ollama large-language-model endpoint used for code
generation.

 SMARTGISCAVP BUILDER: DEPLOYMENT AND USER GUIDE

This report provides the deployment and user documentation for the SMARTGISCAVP Builder, the
containerized realization of the Context-Aware Visual Prompting framework developed in the NSRD
project “ML-Assisted Atmospheric Hazard Modeling for Effective Geospatial Risk Analysis”. The
prototype is a self-contained, multi-page React application generator built at Oak Ridge National
Laboratory and published to Docker Hub as the image jtupayac/smartgiscavp. Part A.1 covers
deployment and operations, and Part A.2 covers day-to-day use of the interface.

1.1 Deployment Guide

1.1.1 Published Image and Contents

The published image is fully self-contained, so a single docker run boots the entire prototype with no bind
mounts and no build step. The image is available at https://hub.docker.com/r/jtupayac/smartgiscavp as
docker.io/jtupayac/smartgiscavp:latest, exposes container port 80 over HTTP, and is approximately 3.2 GB.
The following components are embedded into the image:

 • Express API and generation pipeline (server.js, pipeline.js).
 • Python RAG engine (rag_server.py, rag_embeddings.py).
 • Production React build of the builder UI (/app/build).
 • Vite and React project template with Tailwind and PostCSS pre-installed.
 • Reference codebases used by retrieval (/reference-codebases).
 • Sentence-transformers embedding model (all-MiniLM-L6-v2).
 • Pre-built FAISS index of 270 code snippets for a warm start.
The only external dependency is the Ollama LLM endpoint used for code generation (e.g.
https://ollama.viridian.ise.utk.edu). Everything else runs offline inside the container.

1.1.2 Prerequisites

 • Docker Engine 20.10 or newer, or Docker Desktop.
 • Outbound HTTPS access to the Ollama endpoint for actual app generation (secured with username
 and password).
 • Approximately 7 GB of free disk for the image.

1.1.3 Quick Start (Pull and Run)
 docker pull jtupayac/smartgiscavp:latest
 docker run -d \
 --name smartgiscavp \
        -p 8432:80 \
 --restart unless-stopped \
 jtupayac/smartgiscavp:latest

Open the app at http://localhost:8432. First boot takes about 6 to 10 seconds while the RAG server loads
the FAISS index, follow docker logs -f smartgiscavp and wait for the RAG server ready message.

1.1.4 Health Checks
 curl http://localhost:8432/health
 docker exec smartgiscavp wget -qO- http://127.0.0.1:5001/health

 2

The builder API returns a JSON status object of the form {"status":"ok","message":"Backend proxy server
is running"}, and the internal RAG embedding server prints ok.

1.1.5 Persisting Generated Projects

Generated projects live at /app/projects inside the container. To keep them across container recreation,
mount a named volume:
 docker run -d \
 --name smartgiscavp \
       -p 8432:80 \
 -v nsrd_projects:/app/projects \
 --restart unless-stopped \
 jtupayac/smartgiscavp:latest

1.1.6 Production Deployment behind a Reverse Proxy

For production the repository ships a docker-compose configuration wired for an nginx-proxy and Let's
Encrypt reverse proxy. The self-contained image is deployed with a minimal override that sets the
VIRTUAL_HOST, VIRTUAL_PORT, LETSENCRYPT_HOST, and LETSENCRYPT_EMAIL
environment variables, maps port 8432 to container port 80, mounts the nsrd_projects volume, and joins
the external nginx-proxy network, after which the stack is started with docker compose up -d. The bind-
mount docker-compose file in the repository root is intended for local development with live source editing.

1.1.7 Configuration Reference

 • PORT (default 80): Express listen port inside the container.
 • RAG_PORT (default 5001): internal RAG embedding server port.
 • NODE_ENV (default production): Node runtime mode.
 • VIRTUAL_HOST and VIRTUAL_PORT: optional nginx-proxy routing.
 • LETSENCRYPT_HOST and LETSENCRYPT_EMAIL: optional TLS via acme-companion.
The Ollama endpoint and credentials are configured through OLLAMA_HOST in server.js. To point at a
different LLM gateway, rebuild the image with an edited server.js or fork the configuration.

1.1.8 Rebuilding the Self-Contained Image

From the smartgiscavp directory, the build stages the reference codebases and builds the React bundle and
FAISS index into the image:
 cp -r ../reference-codebases ./reference-codebases
 docker build -f Dockerfile.hub -t jtupayac/smartgiscavp:latest
 docker login
 docker push jtupayac/smartgiscavp:latest

Dockerfile.hub differs from the development Dockerfile by baking in the source, the React build, the
reference codebases, the embedding model, and a pre-built FAISS index, so the image needs no bind
mounts.

1.1.9 Operations and Troubleshooting

Common operational commands include docker logs -f smartgiscavp to follow startup and request logs,
docker exec -it smartgiscavp sh to open a shell, and docker restart, docker stop, or docker rm -f smartgiscavp

 3

to manage the container. To update, pull the latest image, remove the running container, and re-run it.
Frequently encountered issues include:

 • Generate fails while the UI loads: the Ollama endpoint is unreachable, verify outbound HTTPS to
 e.g., ollama.viridian.ise.utk.edu.
 • Empty Thinker or Coder dropdowns: the Ollama /api/tags call failed, check docker logs
 smartgiscavp for the fetch error.
 • RAG falls back to keyword search: the FAISS index is missing, confirm that
 /app/.cache/faiss_index.bin exists in the container.
 • Port already in use: host port 8432 is taken. Map a different host port, for example -p 9000:80.

1.2 User Guide

The SMARTGISCAVP Builder lets a user describe the pages they want in plain English, pick an AI model
pair, and generate and deploy a live, multi-page React application complete with maps, charts, tables, and
dashboards. After the container is running, the interface is available at http://localhost:8432.

1.2.1 The Interface at a Glance

The interface has three main regions: the Pages sidebar on the left, the page editor in the center, and the
model and generate control bar along the bottom. The Pages sidebar lists every page in the app and provides
an Add Page button. The page editor sets the page name, type, requirements, and an optional SVG mockup.
The control bar selects the AI engine and the Thinker and Coder models and triggers Generate and Deploy,
while the footer shows how many pages are currently configured.

Figure 1. The SMARTGISCAVP Builder main interface: the Pages sidebar (left), the page editor with name,
type, requirements, and SVG mockup (center), and the Ollama model and Generate and Deploy control bar
 (bottom).

1.2.2 Choosing a Page Type

Each page has a type that tells the generator what kind of UI to build. The Home type is used for landing
pages with hero banners, summaries, metric cards, and navigation. The Base type is used for general
content pages with tables, forms, text, and generic dashboards. The Geo or Map type is used for
interactive Leaflet maps with markers, layers, heatmaps, GeoJSON, and CSV-driven points. When the
Geo or Map type is selected, an area to attach a CSV of coordinates appears so the map can be driven by
real latitude and longitude data.

 Figure 2. The three page types (e.g., Home, Base, and Geo or Map) that determine the kind of UI the
 generator produces for each page.

1.2.3 Writing Requirements

The Requirements box is where the user describes, in plain English, what the page should contain and do,
being specific about layout, data, and interactions. For example, a Home page might request a landing page
for an environmental monitoring dashboard with a hero banner, a short project summary, and three metric
cards showing active sites, species tracked, and data points collected. An SVG mockup can optionally be
attached, by uploading a file or drawing one, to guide the visual layout, which the generator uses as a design
reference.

 5

  Figure 3. The page editor with a filled-in requirements description and an optional SVG mockup used to
 guide the generated layout.

1.2.4 Selecting AI Models

Generation uses a two-model pipeline shown in the control bar. Ollama is the inference engine, served by
the self-hosted Ollama gateway. The Thinker is the reasoning model that plans the app structure and page
logic, and the Coder is the code model that writes the actual React and JSX components. Any available
model can be chosen in each dropdown, with sizes shown, for example qwen3-coder-next at 51.7 GB. A
capable Thinker paired with a strong Coder generally gives the best results, and the model lists are fetched
live from the Ollama server.

 Figure 4. The control bar: the Ollama engine indicator, the Thinker and Coder model dropdowns, and the
 Generate and Deploy button.

1.2.5 Building a Multi-Page App

Dashboards need several pages. The Add Page button in the sidebar adds another page whose type and
requirements are set independently. For example, a Geo or Map page can be added alongside a Home page
to request an interactive Leaflet map of monitoring towers across the managed area, colored by status, with
a CSV-driven marker layer and a side panel listing each site. The generator wires up navigation between
all configured pages automatically, so the output is a single cohesive multi-page React app.

Figure 5. The multi-page workflow: multiple pages of different types are configured in the sidebar and
 combined into a single cohesive React application.

1.2.6 A.2.6 Generating and Deploying

To generate an application, the user confirms that each page has a name, type, and requirements, chooses
the Thinker and Coder models, and clicks Generate and Deploy. The pipeline then retrieves relevant
patterns from the RAG index of reference codebases, plans the app with the Thinker model, generates each
page's components with the Coder model, builds the Vite and React project, deploys it, and serves the live
app at a preview URL of the form /preview/<projectId>/, which is shown in the UI when generation
completes. Progress streams live in the UI, and the user can disconnect and reconnect without losing
progress because the run continues server-side.

1.2.7 Tips and Frequently Asked Questions

For best results, be concrete about the desired content, name the data columns for map and chart pages (for
example latitude, longitude, and status) so the generator binds them correctly, keep one responsibility per
page, attach a mockup when a specific layout is required, and match larger coder models to complex, data-
heavy pages. If the dropdowns are empty or Generate does nothing, the app could not reach the Ollama
gateway, so outbound HTTPS access should be verified and docker logs smartgiscavp reviewed. Generated
apps are written to /app/projects/<projectId> inside the container and served under /preview/<projectId>/,
mounting a volume on /app/projects persists them. The retrieval step needs no internet because the
embedding model and FAISS index are baked into the image, only the LLM generation step calls the
external Ollama endpoint.

The deployed dashboard contains an interactive Leaflet and OpenStreetMap map centered on Oak Ridge,
Tennessee, with ten monitoring station markers placed from the source data and full pan, zoom, and marker

interaction. A Sensor Readings panel presents live summary stat cards, including Total Stations (10),
Average Temperature (21.3 degrees C), and Maximum Temperature (22.7 degrees C), all computed from
the dataset. A scatter chart renders the temperature and humidity distribution from the same readings, and
a per-station data table (station, temperature, humidity, and date) stays in sync with the map. A top
navigation header labeled NSRD exposes one tab per page, so that multi-page applications can switch
between generated pages.

The dashboard was produced by describing the page in the builder's Requirements box, after which the
RAG engine retrieved matching patterns from the baked-in reference codebases (Leaflet maps, stat cards,
Recharts, and data tables), the Thinker and Coder model pipeline planned the layout and generated the
React and JSX components, and the project was built with Vite and deployed inside the container. With the
container running, deployed projects can be listed with docker exec smartgiscavp sh -c 'ls -d
/app/projects/*/dist/index.html' and opened in a browser at http://localhost:8432/preview/<projectId>/.
