AdaMem: Learning What to Remember for Personalized Long-Horizon LLM Agents
Xingyu Chen, Rui Wang, Zhaopeng Tu, Liefeng Bo

Abstract
Long-term memory systems for Large Language Model (LLM) agents typically try to remember everything , extracting memories uniformly to retain as many facts as possible. In production, however, inference cost and finite context budgets make this untenable: beyond consolidating raw dialogue into memory, an agent must exert write control , efficiently keeping only the information each user actually cares about. Otherwise, long-horizon personalized interactions suffer memory bloat , where irrelevant trivia crowds out useful information and steadily erodes question-answering (QA) accuracy. We argue that what is worth remembering is role-dependent, and propose AdaMem (Adaptive Memory), a method that learns what to remember for each user from feedback. AdaMem maintains a structured, role-specific Memory Policy and refines it from weekly QA feedback through a lightweight, patch-style self-reflection step with failure rollback. To study this setting, we build AdaMem-Bench , a benchmark that simulates weeks of interaction with week-by-week QA. Across two extraction models and two feedback modes, AdaMem improves QA accuracy by up to +9.0% over the uniform Mem0 baseline while shrinking memory volume by 9% .

Introduction

Large Language Model (LLM) agents are increasingly deployed in long-horizon personalized scenarios, where consistent long-term memory underpins trust and personalization
15
;
19
. To overcome context-window limits, existing memory systems (e.g., Mem0, MemoryBank) adopt a Retrieval-Augmented Generation (RAG) architecture
5
;
14
;
24
and operate under a
uniform extraction rule
: they try to remember everything, saving every factual statement on the assumption that more is better. In real-world deployment, this collides with two hard constraints—inference cost and a finite context budget—since every memory that is later retrieved consumes tokens and latency. Consolidating raw dialogue into memory is therefore not enough: an agent must also
control what it writes
, retaining only the information each user cares about.

As interactions span weeks or months, this uniformity backfires, producing
memory bloat
: the memory bank accumulates irrelevant trivia (e.g., casual greetings, minor scheduling details) that crowds out the memories that matter at retrieval time, steadily degrading QA accuracy (Figure
1
).

Our key insight is that an agent should not remember everything, but instead
learn what to remember
, because what counts as important is subjective and role-dependent: an agent talking to a manager should track business decisions, whereas one chatting with a fitness buddy should track workout schedules. Memory extraction should therefore be guided by a
Memory Policy
aligned with each user’s preferences and continually corrected from feedback.

We realize this idea in
AdaMem
, a preference-guided extraction framework that runs a closed-loop weekly cycle: (1)
Daily Extraction
stores memories under a structured Memory Policy; (2)
Weekly Evaluation
probes the agent via QA; (3)
Policy Reflection
diagnoses the resulting errors and emits a “patch” that updates the policy, guarded by a failure-rollback check; and (4)
Policy Rendering
compiles the policy into the next week’s extraction instructions, including a
Time Anchoring
step that resolves relative dates.

Contributions

(1) We reframe long-horizon memory for industrial deployment as a
write-control
problem: under real-world inference-cost and context budgets, an agent should keep only user-relevant information rather than consolidate dialogue wholesale, turning extraction into an actively managed, preference-aligned process. (2) We propose
AdaMem
, which learns a role-specific Memory Policy from feedback and applies patch-style reflection with failure rollback to decide what to write—a lightweight recipe that drops into existing RAG memory stacks. (3) We build
AdaMem-Bench
, a personalized long-horizon benchmark with golden-memory annotations, and show that across two extraction LLMs and two feedback modes AdaMem improves QA accuracy by up to
+9.0%
while shrinking memory volume by
9%
; our analysis localizes the gains to ‘‘soft preference’’ categories (emotions, promises, schedules) and identifies policy inference from weak feedback as the primary remaining bottleneck.

Related Work

Long-Term Memory and Hierarchical Storage

Long-term memory is essential for LLM agents in long-horizon interactions
19
. Early works retrieve raw chat history
15
or extract atomic facts
13
;
24
. To handle context limitations, MemGPT
14
and MemoryOS
1
use hierarchical storage paging. Graph-based architectures like MemInsight
2
and All-Mem
9
build topological relations to prevent structure drift, while systems like Temporal Semantic Memory (TSM)
17
organize events along semantic timelines to resolve temporal reasoning.

Personalization, Preference Alignment, and Alleviating Bloat

To personalize agent behavior
3
, systems like PersonaAgent
22
, PersonaMem
23
, and Dynamic Affective Memory
8
align agent actions or emotions using retrieved long-term memory. Yet they still remember everything at extraction time, so the underlying store suffers from memory bloat. SimpleMem
6
applies semantic compression and Nemori
10
uses predictive-coding theory to trigger storage on prediction gaps, but both compress
after
the fact. AdaMem instead decides
what to remember
upfront, via a structured, role-specific Memory Policy that guides extraction.

Active Memory Policies and Self-Reflective Loops

Memory management has shifted from static heuristics to active policies. AgeMem
21
, for instance, frames CRUD operations as an action space trained via GRPO. For self-correction, dialogue systems adopt reflective memory management (RMM)
18
for prospection and retrospection, while EvolveMem
7
learns retrieval configurations from failure logs. Unlike task- or code-level reflection
16
;
11
, AdaMem applies patch-style reflection to the
extraction policy
itself, iteratively refining the natural-language rules that decide what to remember for each role—and, in doing so, exposes policy inference as the key bottleneck.

3.1
Memory Policy Structure

The
Memory Policy

\mathcal{P}=\{C_{1}:\mathcal{T}_{1},\dots,C_{n}:\mathcal{T}_{n}\}
is a JSON object mapping characters
C_{i}
to their natural language extraction preferences
\mathcal{T}_{i}
(e.g., “Only extract final business decisions and deadlines; ignore daily chit-chat”).

3.2
Patch-Style Reflection and Update

At the end of each week, the agent reflects on incorrect QA pairs
\mathcal{W}_{t}
and diagnoses failures as: (1)
Recall Failure (Missing Memory)
where the dialogue had the info but the extractor missed it (policy too restrictive); or (2)
Precision Failure (Noisy Memory)
where irrelevant retrieved memories misled the answering model (policy too permissive).

Based on this, the agent generates a
policy patch

\Delta\mathcal{P}_{t}
to adjust
\mathcal{T}_{i}
. To ensure stability and prevent policy drift, AdaMem employs a
failure rollback
mechanism: if the updated policy degrades validation performance on historical QA pairs, the update is rejected and the policy rolls back.

3.3
Rendering and Time Anchoring

During daily extraction, the active policy
\mathcal{P}
is rendered as custom instructions (e.g., “
Extract memories strictly according to the following character preferences…
”) in the extractor’s prompt.

Time Anchoring

Relative temporal references (e.g., “tomorrow”) become misleading if saved verbatim. AdaMem injects the session’s absolute date into the extraction prompt and instructs the LLM to resolve all relative expressions into absolute dates before saving (e.g., “Meeting scheduled for June 18, 2026”).

4
AdaMem-Bench and Setup

We construct
AdaMem-Bench
, a personalized long-horizon benchmark with session-level golden-memory annotations, to evaluate the AdaMem method.

4.1
Dataset and Data Synthesis

To evaluate preference-guided memory systems under realistic settings, we build AdaMem-Bench around three design principles:

•

Realistic conversational dynamics.
We simulate natural, multi-session dialogues that embed casual chit-chat, temporal references, and subjective nuances, rather than single-turn or template-based text.

•

Multi-persona memory tracking.
Each environment involves concurrent interactions with several characters, each with distinct roles and information preferences, so the agent must track persona-specific memory and retrieve accordingly.

•

Homogeneous concept interference.
Dialogues are designed with high semantic overlap across characters (e.g., several people discussing fitness schedules), and these same-category distractors stress whether the system confuses similar but irrelevant content from other personas.

Our data synthesis pipeline consists of four main stages:

Scenario and Persona Initialization

We initialize
N
long-term interactive stories, each involving an assistant interacting with
C
characters. Each character is assigned a distinct preference profile (e.g., schedules, emotional states, deadlines) representing their ground-truth preferences.

Multi-Session Dialogue Generation

We simulate daily dialogues across
T
weeks using a multi-agent pipeline, naturally embedding key events, factual information, and casual chit-chat.

Golden Memory Annotation

Each dialogue is annotated with session-level “golden memories” (atomic facts matching characters’ preferences), treating other details as noise.

Preference-Aligned QA Generation

At each week’s end, we generate QA pairs targeting only preference-aligned information to test the agent’s long-term recall.

4.2
Baselines and Temporal Alignment

We compare AdaMem against three baseline methods processed in the same chronological order:
(1)
Full Context
: A theoretical upper bound where the entire raw history is fed directly into the LLM context.
(2)
Ideal Memory
: A bound where only human-annotated “golden memories” are stored.
(3)
Mem0
: A widely used uniform extraction baseline
13
that remembers everything, extracting all factual information without preference guidance.

QA answers are always produced by
deepseek-v4-flash
; the two models we vary (DeepSeek-V4-Flash and Gemini-3.5-Flash) are the
extraction
models used by Mem0 and AdaMem. Because Full Context and Ideal Memory involve no memory extraction or policy update, they are extractor-independent and reported once rather than per model.

4.3
Feedback Modes

We evaluate two feedback modes after incorrect QA answers:
(1)
Explicit Feedback
: The user provides the correct answer and explains their preference (e.g., “
Incorrect. You should remember this because I only care about schedules
”).
(2)
Implicit Feedback
: The user only provides the correct answer, and the agent must implicitly infer the underlying preference.

4.4
Evaluation Metrics

We employ a decoupled evaluation methodology:

QA Accuracy

The percentage of weekly QA questions answered correctly, evaluated by a decoupled
deepseek-v4-flash
judge.

Extraction F1

The harmonic mean of Precision (the proportion of extracted memories matching user preferences) and Recall (the proportion of successfully extracted golden memories). Note that precision here is preference-based, not factual.

Memory Efficiency Ratio (MER)

Measures the trade-off between QA accuracy and memory volume, defined as:

\mathrm{MER}=\frac{\mathrm{Acc}/\mathrm{MemVol}}{\mathrm{Acc}_{\mathrm{Ideal}}/\mathrm{MemVol}_{\mathrm{Ideal}}}

We evaluate AdaMem to answer four research questions:

•

RQ1 (Overall Performance)
: Does AdaMem outperform the uniform memory baseline in terms of QA accuracy and memory compactness across different models and feedback modes?

•

RQ2 (Information Categories)
: Where do the performance gains of AdaMem come from when analyzed across different categories of user preferences?

•

RQ3 (Retrieval Dynamics)
: How does AdaMem affect retrieval quality and mitigate memory bloat over extended multi-week interaction horizons?

•

RQ4 (Policy Learning)
: What is the primary bottleneck in preference-guided memory: policy adherence (following instructions) or policy inference (learning preferences from feedback)?

6
Conclusion

We introduced AdaMem, a preference-guided framework that shifts personalized long-horizon LLM agents from remembering everything to
learning what to remember
. By refining a role-specific Memory Policy from weekly QA feedback, AdaMem exercises
write control
over memory, mitigating bloat and retrieval noise over long timelines. This carries direct industrial value: under production inference-cost and context budgets, keeping memory compact and user-aligned lowers retrieval and inference overhead while improving accuracy, and the policy patches drop into existing RAG memory stacks without retraining. On our AdaMem-Bench benchmark, AdaMem consistently beats uniform baselines in both QA accuracy and memory efficiency across two models and two feedback modes. Finally, our analysis shows that while instruction adherence is reliable in modern LLMs, inferring preferences from implicit feedback remains a key bottleneck and an important future direction.

7
Limitations

We acknowledge several limitations:

1.

Synthetic data dependency.
Our evaluation is conducted on a synthesized long-horizon dataset. Although it is highly controlled and annotated with precise golden memories, synthetic dialogues may not fully capture the linguistic diversity, conversational noise, and erratic preference shifts of real-world human interactions.

2.

Reliance on LLM-as-a-judge.
Our evaluation of QA correctness, extraction quality, policy following, and policy alignment relies on LLM-as-a-judge methods. Although we decoupled the judge model (
deepseek-v4-flash
) from the answering models and used strict schemas, LLM judges can still exhibit subtle biases.

3.

Evaluation scale.
Due to API cost constraints, our evaluation is limited to 5 stories and 10 weeks of interaction. A larger cohort of stories and longer horizons (e.g., full-year interactions) would provide stronger statistical guarantees.

4.

Policy drift and over-fitting.
Under implicit feedback, the patch-style reflection mechanism can occasionally over-fit to a single QA failure, producing an overly restrictive patch that degrades other categories. Our rollback mechanism mitigates this, but stronger policy regularization is needed.
