SciTaRC: Benchmarking QA on Scientific Tabular Data that Requires Language Reasoning and Complex Computation
Hexuan Wang Yaxuan Ren Srikar Bommireddypalli Shuxian Chen

Abstract
We introduce SciTaRC, an expert-authored benchmark of questions about tabular data in scientific papers requiring both deep language reasoning and complex computation. We show that current state-of-the-art AI models fail on at least 23% of these questions, a gap that remains significant even for highly capable open-weight models like Llama-3.3-70B-Instruct, which fails on 65.5% of the tasks. Our analysis reveals a universal ‘‘execution bottleneck’’: both code and language models struggle to faithfully execute plans, even when provided with correct strategies. Specifically, code-based methods prove brittle on raw scientific tables, while natural language reasoning primarily fails due to initial comprehension issues and calculation errors. 1 1 1 Dataset and evaluation protocol: https://huggingface.co/datasets/JHU-CLSP/SciTaRC and https://github.com/JHU-CLSP/SciTaRC

To benchmark current AI system performance on such challenges, we manually created a set of scientific tabular reasoning questions. While designed to be self-contained, these tasks demand deep language understanding, strategic planning, and complex calculation. Each instance consists of a question, one or more tables, a pseudo-code execution plan, a gold response, and an automatic evaluation protocol. In contrast to other recently proposed table QA benchmarks, our questions are authored by domain experts and
not automatically generated
by an LLM. Figure
1
illustrates a representative example. Despite recent advances, current state-of-the-art models like GPT-5 only achieve an accuracy score of 76.8% on this benchmark, highlighting the need to develop better methods.

In this paper, we detail the construction of the
SciTaRC
benchmark, evaluate a wide range of proprietary and open-weight models, and analyze the factors that drive model success and failure. Our analysis reveals several key findings: (1) reasoning-optimized models outperform larger baselines but still fail on a non-trivial subset of problems; (2) failures arise primarily from question comprehension, but also during computations; (3) program-based reasoning underperforms natural language reasoning in zero-shot settings due to brittleness in handling heterogeneous scientific tables; and (4) separating planning from execution shows that execution compliance, rather than strategy formation, is the dominant failure mode. These results suggest that improving faithful execution over structured data remains a central challenge for future agentic and neuro-symbolic systems.

3
Dataset

Our dataset is based on scientific papers sourced from recent arXiv preprints, mainly in the domain of artificial intelligence. We downloaded the LaTeX sources for these papers, and consolidated them into a single file.

3.1
Question Creation

For each paper, a question author selected 1 to 3 tables, wrote out a question and the corresponding answer. The tables were then automatically extracted from the LaTeX file and added to the dataset.

The dataset consists of the following fields:

•

arXiv paper ID

•

question (text)

•

answer (text)

•

LaTeX source of each relevant table

•

LaTeX sources of all tables in the paper

•

LaTeX source of the full paper

The question creators (all authors of this paper) comprise undergraduate, Masters, and PhD students as well as a professor working in the area of natural language processing. The questions were designed to be answerable unambiguously just given the tables (with captions) and general domain knowledge about the subject matter. Each question was checked by two reviewers (different from the creator).

Some of the questions were too complex to come up manually with the correct gold answer. In those cases, a short script was written to compute correct results. These scripts were very ad-hoc and written in a mix of programming languages, so we do not include them as part of the released dataset.

3.2
Evaluation Protocol

Since the answers are free-form, with a mix of text and numbers, sometimes consisting of multiple items, matching answers generated by a model with the gold answer is non-trivial.

3.4
Quantifying Complexity

To get a better understanding of the challenges of SciTaRC, we define metrics characterizing difficulty along two dimensions:

Input Complexity.

We measure the amount of information to be processed:

•

Context Load (
S_{tok}
):
Total token count of serialized tables, measuring context length.

•

Structural Size (
S_{cell}
):
Total grid cells (including empty) parsed from LaTex, representing amount of data items.

•

Input Scope (
S_{tab}
):
Number of distinct tables required, measuring cross-table linking needs.

Reasoning Complexity.

We quantify algorithmic hardness via ground-truth plans:

•

Calculation Intensity (
I_{calc}
):
Count of
COMPUTE
operations, measuring arithmetic burden.

•

Retrieval Demand (
I_{retr}
):
Count of
SELECT
operations, measuring retrieval frequency.

•

Plan Horizon (
L_{plan}
):
Total instruction count, serving as a proxy for reasoning depth.

•

Control Flow (
C_{flow}
):
Composite score
C_{flow}=N_{loop}+N_{if}+D_{max}
, where
N_{loop}
and
N_{if}
count iterative and conditional blocks, and
D_{max}
represents maximum nesting depth.

Main Results

Table

We observe frequent instances where smaller models successfully solve “hard” questions that frontier models miss, indicating that difficulty is often determined by specific architectural fits rather than scale alone.

We observe three primary trends that characterize scientific table reasoning:

Reasoning Strategies Amplify Capabilities.

Models trained with reinforcement learning
(
7
)
for reasoning significantly boost performance, enabling models to outperform larger standard baselines. For instance, Kimi-K2-Thinking (73.3%) exceeds its base model Kimi-K2 (49.1%) by over 24 percentage points. This capability allows efficient scaling: the 32B DeepSeek-R1-Distill reasoning model (41.5%) scores higher than the 71B Llama-3.3 model (34.5%).

Model Scale Matters, but Capabilities Vary.

While larger models generally perform better, the improvement is not strictly linear. As shown in Figure
3
, smaller or weaker models occasionally solve "hard" questions that frontier models miss.
This stochasticity suggests that reasoning is not a single monotonic skill; different architectures may find different types of logic easier, even if they lack overall capacity.

Zero-Shot Code Execution Struggles.

Contrary to the expectation that tables are best handled by code, Program-of-Thought (PoT) performs substantially worse than natural language reasoning. Strong generalist models suffer massive degradation when forced to write code—DeepSeek-V3.2 drops from 69.3% (CoT) to 36.1% (PoT)—and dedicated code specialists like Qwen-2.5-Coder achieve only 21.3%. Code appears brittle when applied to the ad-hoc, heterogeneous structures of scientific tables, whereas natural language is more robust to interpret the noise.

5.2
Methodology: The Gain Curve

To analyze planning efficacy, we define the
Gain Curve
. We rank questions
q_{1},\dots,q_{N}
by baseline difficulty under
S_{\text{direct}}
. Let
y_{i}\in\{0,1\}
denote correctness for a given model on
q_{i}
. We define the Local Success Probability as a centered sliding-window average

P_{\text{success}}(i)=\frac{1}{|W_{i}|}\sum_{j\in W_{i}}y_{j}
,
where
W_{i}=\{j:\max(1,i-\lfloor w/2\rfloor)\leq j\leq\min(N,i+\lfloor w/2\rfloor)\}
and
w=50
.
This filters stochastic noise to visualize robust trends across the difficulty spectrum.

The Cost of Compliance.

Figure

and Table

illustrate a distinct capability trade-off.

Explicit planning significantly aids the code-specialized Qwen-Coder, yielding accuracy gains of +1.9% with autonomous planning and +6.2% when provided with an oracle plan, confirming that structured blueprints reduce error in programmatic generation. Conversely, generalist language models consistently regress (-5.4% to -10.0%). This divergence highlights a

Moreover, providing an Oracle plan does not guarantee improved accuracy over an autonomously generated plan for larger model, suggesting that an external strategy must
fit
the model’s intrinsic reasoning mode to be effective. However, for smaller architectures, the Oracle Plan remains a definitive upper bound on the Gain Curve, revealing a significant latent execution capability that autonomous planning fails to realize.

Error Analysis

To better understand the “Hard Reasoning Ceiling” identified in Section
4.2
, we conduct a qualitative error analysis on 98 failure cases from the outputs of the top-performing open-weight model, DeepSeek-V3.2.
We categorize model failures using a four-class error taxonomy designed to isolate where table reasoning breaks.

•

Comprehension
: misunderstanding of the question intent, constraints, or the meaning of the table attributes, leading to the wrong objective.

•

Localization
: selecting incorrect rows, columns, or values from tables despite a correct objective.

•

Calculation
: producing an incorrect numeric result given the correct evidence and operation.

•

Memory
: failing to retain or consistently apply intermediate results or constraints across steps.

Each incorrect prediction is assigned exactly one primary error type based on the
earliest
point in the reasoning chain at which the output becomes unrecoverable.

7
Conclusion

We presented SciTaRC, a novel expert-authored table QA dataset that stresses language understanding, planning, and numerical execution. Despite recent advances, state-of-the-art models fail on over 30% of the benchmark, revealing systematic weaknesses across model families and reasoning paradigms. Our analyses show that these failures arise primarily from errors in comprehension and faithful execution rather than strategy formation. SciTaRC thus highlights execution fidelity as a central bottleneck for agentic and neuro-symbolic systems, and provides a diagnostic testbed for future methods that aim to bridge this gap.

Limitations

Dataset Scale and Scope.

SciTaRC consists of 370 questions, all of which were human-annotated and double-checked by domain experts. While small compared to automated training corpora, this scale was necessitated by the requirement for rigorous verification. Consequently, the benchmark is intended as a high-fidelity diagnostic tool rather than a training resource. Additionally, as tables are sourced exclusively from AI-domain arXiv papers, results may not fully generalize to domains with different tabular conventions, such as finance or medicine.

Evaluation Protocol.

We rely on an LLM-as-a-Judge metric (Llama-3.3-70B). Although validation on a subset of 245 questions showed
>
95% agreement with human annotators, automated judges lack the rigor of deterministic execution checks and may harbor latent biases, such as inconsistencies in numerical precision or leniency toward semantic equivalence.

Reproducibility.

Our evaluation includes closed-weight frontier models accessed via opaque APIs. Despite our use of strict generation parameters (e.g., model temperature), these systems are subject to unannounced updates and hidden version changes. This introduces a layer of irreproducibility that does not affect the open-weight models in our leaderboard, where weights are static and inspectable.

Planning Constraints.

The pseudo-code ablation enforces a rigid format in a zero-shot setting. Observed failures may partially stem from the cognitive overhead of adhering to this unfamiliar syntax (the “Compliance Cost”) rather than a fundamental inability to reason.

Code Execution Robustness.

Our Program-of-Thought (PoT) setting operates directly on raw LaTeX without pre-parsed structures. This design choice ensures a strict zero-shot evaluation of the model’s raw capability to handle authentic scientific documents, maintaining fairness across paradigms. However, this approach likely penalizes code-based strategies, as reasoning failures may be conflated with the brittleness of parsing complex tables from scratch.

Appendix A
Evaluation Prompt

We designed the evaluation prompt to address three specific scoring challenges in scientific table reasoning:

•

Stylistic Invariance:
Surface-level variations (e.g., typos, phrasing) are ignored provided the core factual content is accurate.

•

Numerical Tolerance:
To account for rounding differences, the protocol permits a deviation of
\pm 1
in the final significant digit.

Strictness on Extra Information:
To avoid rewarding recall bias, the inclusion of unrequested components not present in the ground truth is penalized.

Note on Binarization:
While the prompt utilizes a ternary scale (0.0, 0.5, 1.0) to allow the judge to explicitly categorize partial matches, we strictly binarize these scores for the final leaderboard. The ternary structure serves to isolate partially correct answers from the fully correct class; for our reported metrics, only a score of 1.0 is treated as a success (1), while 0.5 and 0.0 are treated as failures (0).

System Prompt

You are evaluating a table QA system. Compare the predicted answer against the ground truth answer.

SCORING RULES (follow exactly):

- 1.0: CORRECT - Prediction contains the same core factual information as ground truth

- 0.5: PARTIALLY CORRECT - Prediction has some correct information but missing key parts

- 0.0: INCORRECT - Prediction is factually wrong or completely unrelated

CRITICAL REQUIREMENTS:

- ALL components in ground truth MUST be mentioned in prediction

- If ground truth has multiple parts, prediction must include ALL parts

- Missing ANY component = maximum score 0.5

- Adding extra components not in ground truth = maximum score 0.5

- Numbers must be nearly identical - only final digit can differ by ±1

EXAMPLES:

- Ground: "Japanese" | Prediction: "None. HTML2Text performs best in Japanese" -> 1.0

- Ground: "Adam" | Prediction: "Adam optimizer with 0.001 learning rate" -> 1.0

- Ground: "ResNet-50" | Prediction: "ResNet-50 and DenseNet-121" -> 0.5

- Ground: "4.2" | Prediction: "approximately 3.8" -> 0.0

You are a helpful assistant that creates step-by-step plans for answering questions about tables.

- SELECT: Extract specific values or subsets from the table

- LOOP: Iterate over items (e.g., LOOP for each model)

- RETURN: State what to return for the final answer

Rules:

- Use exact syntax: "LOOP for each", "SELECT", "COMPUTE", "IF", "RETURN"

- Indent after LOOP and IF

- Use actual entity names, not generic "row" or "column"
