Query-Specific Pruning of RML Mappings
Sitt Min Oo, Olaf Hartig

Abstract
Current approaches for knowledge graph construction with RML focus on full RDF graph materialization without considering user queries. As a result, mapping engines are inefficient in dynamic query environments, materializing large graphs even when only a small subset is needed to answer user queries. In this paper, we formally define satisfiability for SPARQL queries with respect to RDF data obtained via RML mappings and use this property to prune RML mappings for partial RDF graph materialization. Evaluation on the GTFS-Madrid benchmark shows that pruning significantly reduces materialization time, and RDF graph size while also noticeably improving querying time. Thus, enabling existing materialization engines to efficiently support generating RDF graphs in dynamic federated querying environment where user queries change frequently.



1
Introduction

State-of-the-art knowledge graph generation approaches generate RDF graphs from structured data like relational databases, or even semi-structured data such as JSON and XML.
These approaches either rely on a mapping language (materialization),
such as
RML
[
7
,
10
]

and SPARQL-Generate
[
12
]
,
granting them access to more diverse types of data sources, including those without a query language for partial retrieval of data,
or they rely on translating SPARQL queries to equivalent queries (virtualization) supported by the underlying data sources, such as SQL, to generate a subset of the RDF graph necessary to answer the user’s query.
To date, materialization approaches ignore user queries when generating RDF graphs, while virtualization approaches are limited by the types of data sources that they support.

An approach that supports mapping heterogeneous types of data to RDF while considering user
queries would unlock significant opportunities, especially for federated querying.
Federation engines would be able to provide access to diverse types of data
without being constrained by the fact that the aforementioned virtualization approaches support only data sources with query languages,
nor by the materialization approach of always materializing the full RDF graph, of which a significant portion may be irrelevant for the given query.

In this work, we combine the support of heterogeneous types of data sources (with or without query languages) from materialization with
the query-aware efficiency of virtualization to generate an RDF graph.
Specifically, we use RML mappings and prune away mapping definitions that generate portions of the RDF graph that are irrelevant for answering a given SPARQL query.
This approach advances federated querying by enabling query endpoints that support heterogeneous types of data sources while being efficient and query-aware as the virtualization-based endpoints.

Our main contribution is an algorithm for pruning an RML mapping for a given SPARQL query (Section
6
).
In order to define the algorithm, we first define the syntax and the semantics of mapping expressions that can be derived from an RML mapping document (Section
3.3
and
3.4
).
Using these mapping expressions, we define the notion of satisfiability of SPARQL triple patterns over mapping expressions,
and formally show that determining the satisfiability of a triple pattern over a mapping expression is undecidable,
which constitutes our second contribution (Section
4
).
Although the decision problem of satisfiability is undecidable, we show that there are cases where a given triple pattern is confirmed to be not satisfiable over a mapping expression (Section
5
).
These formal results together provide the foundation for the pruning algorithm.
As our final contribution, we show using a benchmark that an existing mapping engine can benefit from our pruning technique without modification, for faster materialization and query time while generating a smaller RDF graph (Section
7
).

Preliminaries

We formalize our pruning approach in terms of the
RML-related mapping algebra of Min Oo and Hartig
[
13
]
.
This section provides the relevant background for this work by introducing the concepts of that algebra, and of RDF and SPARQL.

3.1
Relevant Concepts of RDF and SPARQL

Let
\mathcal{S}
be the countably infinite set of all possible strings, and
\mathcal{I}

be the subset of
\mathcal{S}
that consists of all valid IRIs.

\mathcal{L}
is the countably infinite set of all RDF literals where every such literal is a pair
(\mathit{lex},\mathit{dt})\in\mathcal{S}\times\mathcal{I}
in which
\mathit{lex}
is the lexical form and
\mathit{dt}
is the datatype IRI of the literal.
Moreover,
\mathcal{B}
is the countably infinite set of blank nodes (and is disjoint from
\mathcal{S}
and
\mathcal{L}
).
IRIs, literals, and blank nodes are jointly referred to as
RDF terms
.
An
RDF triple
is a tuple
(s,p,o)\in(\mathcal{I}\cup\mathcal{B})\times\mathcal{I}\times(\mathcal{I}\cup\mathcal{B}\cup\mathcal{L})
, and an
RDF graph
is a set of RDF triples.

For our definitions related to SPARQL we adopt the algebraic syntax of Pérez et al.
[
14
]
. Queries
are formed using
graph patterns
, of which the most basic type is a
triple pattern
, that is, a tuple
(s,p,o)\in(\mathcal{I}\cup\mathcal{V})\times(\mathcal{I}\cup\mathcal{V})\times(\mathcal{I}\cup\mathcal{L}\cup\mathcal{V})
, where
\mathcal{V}
is a countably infinite set of variables (disjoint from
\mathcal{S}
,
\mathcal{L}
, and
\mathcal{B}
). Other graph patterns can then be constructed recursively, using operators such as
AND
and
OPT

[
14
]
.
The result of evaluating any such graph pattern
P
over an RDF graph
G
is a set, denoted by
[\![P]\!]_{G}
, that consists of so-called
solution mappings
, which are partial functions of the form
\mu\!:\mathcal{V}\rightarrow\mathcal{I}\cup\mathcal{B}\cup\mathcal{L}
. If
P
is a triple pattern
tp=(s,p,o)
, then
[\![tp]\!]_{G}
consists of every solution mapping
\mu
for which
\mathrm{dom}(\mu)=\{s,p,o\}\cap\mathcal{V}
and
\mu[tp]\in G
, where
\mu[tp]
denotes the triple obtained by replacing the variables in
tp
according to
\mu
. For other forms of graph patterns, we refer to Pérez et al.’s work for the definition of
[\![P]\!]_{G}

[
14
]
.

3.2
Data Model of the Mapping Algebra

The mapping algebra by Min Oo and Hartig is defined over so-called
mapping relations

[
13
]
in which the possible values are RDF terms, plus a special value,
\epsilon
, that
captures
processing errors (and is not an RDF term). For the
following
formal definition of these relations,
let
\mathcal{A}
be a countably infinite set of
attributes
.

Definition 1

[
13
]

A
mapping tuple
is a partial function
t\!:\mathcal{A}\rightarrow\mathcal{I}\cup\mathcal{B}\cup\mathcal{L}\cup\{\epsilon\}

Definition 2

[
13
]

A
mapping relation

r
is a tuple
(A,I)
, where

A\subset\mathcal{A}
is a finite, non-empty set of attributes
and

I
is a set of mapping tuples such
that, for every such tuple
t\in I
, it holds that
\mathrm{dom}(t)=A
.

While the mapping algebra operates over such mapping relations, the final mapping relation
that results from a relevant sequence of such operations
is meant to capture an RDF dataset.
At this point we diverge slightly from the original formalism
[
13
]
, which considers the creation of whole RDF datasets (i.e., including named graphs);
in this paper we limit ourselves to single RDF graphs.
For this purpose, we assume three special attributes,
a_{\textrm{s}},a_{\textrm{p}},a_{\textrm{o}}\in\mathcal{A}
, and adapt the definition of an RDF representation of mapping relations as follows.

Definition 3

Let
r=(A,I)
be a mapping relation with
a_{\textrm{s}},a_{\textrm{p}},a_{\textrm{o}}\in A
.
The
RDF graph resulting from
r
is the RDF graph

G=\bigl\{\bigl(t(a_{\textrm{s}}),t(a_{\textrm{p}}),t(a_{\textrm{o}})\bigr)\,\big|\,t\in I\text{ such that }\bigl(t(a_{\textrm{s}}),t(a_{\textrm{p}}),t(a_{\textrm{o}})\bigr)\text{ is an RDF triple}\bigr\}.

For examples of
these concepts,
refer to
Min Oo and Hartig’s
work
[
13
]
.

Satisfiability

Our pruning approach is based on a notion of satisfiability of triple patterns with respect to RDF data obtained via mappings. This section provides the relevant formal results, for which we begin by defining this notion of satisfiability.

Definition 10

Benchmark

We use the GTFS-Madrid benchmark

It enables the generation of a synthetic dataset based on real-world data about the Madrid subway network, scaled by a factor, along with 15 SPARQL queries based on actual user queries.
The benchmark task is to answer these queries over the RDF representation of the generated dataset, referred to as the
full RDF graph
for the rest of the section.
The benchmark includes an RML mapping document containing 86 TrMap-expressions to generate the full RDF graph.
The provided SPARQL queries are diverse, using SPARQL features such as

While GTFS-Madrid benchmark is mainly used to evaluate virtualization engines

we prune the benchmark RML mapping by considering a given SPARQL query to generate an RDF graph that is a subset of the full RDF graph.
We configure the GTFS-Madrid benchmark to generate the synthetic dataset at scale factor 10.
This small scale factor fits our aim, which is to evaluate the performance impact of our pruning technique
rather than the scalability of an end-to-end data-mapping pipeline.
Furthermore, to limit the impact of a potential implementation error in the underlying mapping engine when parsing complex input data,
the benchmark is configured to generate data in CSV.

7.3
Results

Pruning Time.

As shown in the Table
1
, the time taken to prune the 86 TrMap-expressions
is negligible, less than
\sim 5
ms even in the worst case, compared to the baseline translation time of 218.22 ms and
the fastest materialization time at 1,717.52 ms, both of which are several orders of magnitude slower.
Furthermore, the pruning time correlates with the number of TrMap-expressions retained after prunning:
the fewer the number of TrMap-expressions retained, the lower the pruning time.

Materialization Time.

Table
1
show that, for two-third of the cases, our approach reduces the materialization time after pruning
to at most 8 % of the time taken (7 s) for the baseline materialization time (82 s)!
The significant decrease in the materialization time is due to the small number of TrMap-expressions that remain after the pruning step.
Specifically, the original 86 TrMap-expressions are pruned down to at most 20, thus, significantly lowering the computation load in the materialization step.
Moreover, our approach ensures a lower materialization time for five of the remaining cases (Q2, Q3, Q7, and Q9).

For Q1 and Q9, even though both queries retain fewer TrMap-expressions than Q7 (the query with the most TrMap-expressions retained), their materialization times are higher than that of Q7.
Queries Q1 and Q9 contain the triple pattern
"?shape gtfs:shapePoint ?shapePoint"
.
The corresponding TrMap-expression
M
in the retained set of TrMap-expressions for generating triples that satisfy such pattern is of the second form (Definition
5
).
Moreover, all the source references in
M
are the same:
they refer to the same largest input file of the dataset,
SHAPES.csv
which contains around 585K records.
This results in two compounding negative effects on the materialization time.
First, because both source references point to the same input file, evaluating
M
results in a self-join operation that
are known to cause higher materialization time
[
6
]
.
Second, evaluating self-join on the largest file of the dataset results in the materialization time being significantly
higher compared to the others.

Materializing RDF graph for Q15 took 125.63 % longer than the baseline in terms of materialization time,
even though no TrMap-expressions are pruned.
Q15 contains the triple pattern
?stop ?p ?str
such that all the TrMap-expressions are retained during the pruning step.
The generated RML mapping, using the retained TrMap-expressions, contains more
RML triples map definitions than the original RML mapping but they are semantically the
same (i.e., evaluating them independently produces the same RDF graph).
A mapping engine that is not aware of such semantic equivalence of two
differently written RML mappings, may take longer to evaluate one over the other.
We can infer from this result that CARML is not aware of such semantic equivalence.

Querying Time.

From the results (Table
1
), we can conclude that querying the RDF graph generated from the pruned RML mappings
is much faster than querying the full RDF graph.
The speed-up is especially noticeable for Q10, Q12, and Q14,
where the querying time is lower by around 35 ms, 53 ms, and 66 ms respectively.
The exceptions are Q7 and Q8, where the execution timed out at 3600 s.
Q7 and Q8 contain the most triple patterns, 15 and 14 respectively,
while also using SPARQL’s
OPTIONAL
feature
[
4
]
.
On top of having 15 triple patterns, Q7 also uses the
DISTINCT
feature leading to a higher querying time.
Although Q10 also uses
DISTINCT
, the querying time is substantially lower because
the corresponding generated RDF graph is much smaller (around 80,000 triples) compared to Q7’s 1.3 million triples.
For Q8, the timeout occurred due to the combination of having the second most triple patterns (14) having the
largest chained star-shape group, increasing the querying complexity.
Lastly, Q7 is also a
DISTINCT
query
which removes duplicate solution mappings from the result set, and thus, leading to a higher querying time.

On the other hand, virtualization approaches like Ontop

use R2RML
[

mappings as a guide
to translate a given SPARQL query to an equivalent query supported by the underlying data source.
The translated query is then applied on that source, and the resulting data is returned directly as SPARQL query results.
At first glance, this appears more efficient than materialization, as only query-relevant data is retrieved.
However, virtualization is limited to using data sources that provide a query language into which a user’s SPARQL query can be translated.
Consequently, sources without a query language cannot be used by virtualization systems.

While virtualization is query-aware, it is less flexible than materialization
in supported data sources, whereas materialization can handle diverse sources
but generates unnecessary triples.
Our approach bridges this gap by pruning
mappings, before materialization, to retain only those that are relevant to answering the user’s query.

9
Concluding Remarks and Future Work

The approach presented in this work opens up new possibilities for research on using non-RDF data sources when evaluating SPARQL queries over a federation of data sources.
More concretely, there are two scenarios in which our pruning approach is beneficial.
First, a non-RDF data source can be wrapped as a SPARQL endpoint to provide access to an RDF view of the underlying data efficiently by pruning the irrelevant mappings.
Second, a federation engine may access non-RDF data sources and convert the retrieved non-RDF data locally at query time.
As an example of the latter case, consider a JSON-based REST API as such a data source: if a part of the SPARQL query over the whole federation is
meant to be matched in the RDF views of the data from requests to that API, the
pruning approach will speed up the process of both materializing the data
retrieved from the API and evaluating the relevant sub-pattern of the SPARQL
query over this materialized RDF view.

Since our pruning approach works at the triple pattern level, a natural next step is to
extend it to consider star-shaped and chained queries, allowing satisfiability checks across related triple patterns
and pruning even more TrMap-expressions.
Such an extension will enable materialization engines to generate even smaller RDF graph in less materialization time.
