Agentic Vulnerability Reasoning on Windows COM Binaries
Hwiwon Lee ∗ Jongseong Kim ∗ Lingming Zhang University of Illinois at Urbana-Champaign

Abstract
. Windows Component Object Model (COM) services run with elevated privileges and are widely accessible to authenticated users, making race conditions in these binaries a critical surface for local privilege escalation. We present Slyp , an end-to-end agentic pipeline that discovers race condition vulnerabilities in COM binaries and generates debugger-verified proof-of-concept (PoC) code. Slyp exposes binary exploration, COM inspection, and dynamic debugging as reusable tool interfaces, giving agents the static context, COM activation metadata, and debugger feedback needed to move from vulnerability discovery to verified PoC generation. On a benchmark of 20 COM objects covering 40 vulnerability cases, Slyp achieves 0.973 F1, outperforming production coding agents by up to 0.208 F1 and the state-of-the-art static analyzer by 3.3 × \times in bug discovery. For PoC generation, production coding agents in their default setup (without our COM inspection and dynamic debugging tools) verify essentially no cases on either frontier model, whereas Slyp ’s interactive toolsets enable it to autonomously synthesize working PoCs for 67.5% of cases on the strongest configuration. Deployed on production Windows services, Slyp discovers 28 previously unknown vulnerabilities across nine COM services, all confirmed by the Microsoft Security Response Center (MSRC) with 16 CVEs assigned and $140,000 in bounties. Furthermore, Slyp is designed with generalizable binary analysis and debugging interfaces, making it readily applicable to other commercial off-the-shelf (COTS) binaries beyond Windows COM services.

Introduction

Windows Component Object Model (COM) services constitute a vast attack surface for local privilege escalation.
Hundreds of privileged COM classes run in Windows service processes with elevated privileges, and many are accessible to authenticated users through Remote Procedure Call (RPC)
(
30
;
14
)
.
Race conditions in these services arise when concurrent RPC threads access shared object state without synchronization, producing use-after-free and double-free vulnerabilities that yield arbitrary code execution at the privilege level of the hosting service
(
14
;
58
)
.
These vulnerabilities are prevalent across Windows installations yet remain difficult to detect.
Analysis requires reasoning about thread interleavings, object lifetimes, and locking protocols simultaneously across functions that optimizing compilers strip of all type and symbol information.

Existing approaches to detecting race conditions in COM binaries face fundamental limitations.
Coverage-guided fuzzers lack control over thread scheduling to trigger specific interleavings

Structural assumptions about register usage and vtable layouts further miss vulnerabilities across diverse binary patterns.
Manual reverse engineering requires decompiling each entry function, tracing shared-state accesses, and checking locking discipline across many functions, which does not scale to production COM services.

In recent years, Large language models (LLMs) offer a complementary capability.
LLMs demonstrate strong semantic reasoning over decompiled code, recovering variable names, data structures, and types from binaries

2.
Background

COM as a Privilege Escalation Surface.

Windows Component Object Model (COM) is a binary interface standard for inter-process software composition
(
30
)
.
Hundreds of COM classes are hosted in Windows service processes that run with elevated privileges.
A low-privileged client activates a COM object by calling an activation function such as
CoCreateInstance
with the target class identifier (CLSID).
The COM runtime routes the request across a process boundary via RPC over Advanced Local Procedure Call (ALPC) into the privileged service.
Two permission layers gate access.
Launch permission
controls whether the client can start the server process, and
access permission
controls whether the client can invoke methods on a running object
(
14
)
.
Many system services grant both permissions to all authenticated users, and some grant access to AppContainer-sandboxed processes with specific capabilities.
A memory corruption vulnerability in any reachable interface method gives the attacker code execution at the privilege level of the hosting service, making cross-process COM a dense, high-value attack surface for local privilege escalation.

Interfaces, Vtables, and the Binary Reality.

Each COM class implements one or more typed interfaces, all ultimately deriving from
IUnknown
(
QueryInterface
,
AddRef
,
Release
).
Interface methods are dispatched through virtual function tables (vtables) stored in the binary, where each vtable entry holds a pointer to a concrete function
(
14
;
70
)
.
Cross-process calls use a proxy/stub pair that marshals arguments via RPC between client and server
(
30
)
.
The Windows registry maps each CLSID to its binary path, threading model, AppID, service name, and hosting account.
In production binaries, interface methods appear as indirect call sequences through vtable pointers at fixed offsets, obscuring the interface hierarchy and concrete targets
(
56
;
36
)
.
Recovering virtual call targets is a prerequisite for tracing data flows (
§4.3
).

Threading Model and Root Cause of Races.

COM uses
apartments
to govern concurrency
(
14
)
.
A single-threaded apartment (STA) serializes all incoming calls through a Windows message queue, making objects thread-safe by construction.
A multi-threaded apartment (MTA) allows concurrent method calls from multiple RPC threads, requiring objects to synchronize shared state themselves.
Most cross-process system services register as MTA for performance, so concurrent client requests execute on separate RPC threads with no framework-provided locking.
If an interface method reads or writes a member field (
this+offset
) without holding a lock, the field is a data race candidate.
Conflicting accesses on the same field (read/free, write/free, free/free, read/write) produce use-after-free, double-free, and type confusion vulnerabilities
(
14
;
58
)

Running Example.

Figure 1
shows the
SetPrintTicket
method of the
CWorkflowSession
COM class, hosted in PrintWorkflowUserSvc, a per-user service that manages the Windows Print Workflow.
The method first reads the heap pointer stored at the shared field
*((_QWORD *)this + 10)
into a local variable (line 8) and, if non-null, frees the old buffer via
operator delete[]
(line 11).
It then allocates a fresh buffer with
operator new[]
(line 12), stores the returned pointer back into
*((_QWORD *)this + 10)
(line 15), and copies print-ticket data into the buffer via
memcpy
(line 18).
Because
CWorkflowSession
is registered under the MTA threading model, the COM runtime dispatches concurrent RPC requests to
SetPrintTicket
on the same object from separate threads with no framework-provided serialization.
The entire read–free–allocate–write sequence on
*((_QWORD *)this + 10)
therefore executes without mutual exclusion, and two distinct vulnerability classes arise depending on the thread interleaving.

Figure 2
illustrates both dangerous interleavings.
In the
use-after-free
scenario (
Figure 2
(a)), Thread 1 allocates a new buffer (line 12) and stores the returned pointer into the shared field
*((_QWORD *)this + 10)
(line 15), exposing the new allocation to other threads.
Before Thread 1 reaches the
memcpy
(line 18), Thread 2 enters the method, reads the pointer that Thread 1 just stored (line 8), and frees it (line 11).
Thread 1 then proceeds to write data into the now-freed buffer, producing a use-after-free.
In the
double-free
scenario (
Figure 2
(b)), both threads check the allocation at
*((_QWORD *)this + 10)
and find it non-null (line 9) before either performs the free.
Each thread independently invokes
operator delete[]
on that pointer (line 11), causing a double-free.
Both vulnerabilities are security-relevant because a low-privileged client can trigger concurrent RPC invocations on the shared object from separate threads.
This unsynchronized read–free–write pattern on shared fields recurs across Windows system services and constitutes the primary vulnerability class
Slyp
targets.
Detecting these patterns requires understanding COM threading semantics, tracing shared-state access across decompiled functions, and verifying that no synchronization primitive protects each access path.

3.
Motivation and Problem Statement

Why an Agentic System for COM Binaries.

We adopt an agentic architecture where an LLM plans, invokes tools, and iterates with verification, rather than relying on monolithic static analyses or unguided prompting.
This design choice rests on four empirical observations.
First, LLMs exhibit strong semantic reasoning over binaries, recovering variable names, types, and data structures from executables without requiring bespoke analyzers
(
65
;
66
)
.
Second, agentic orchestration generalizes across targets through prompt and tool adjustments, avoiding the multi-year engineering effort required to extend traditional analyzers to new platforms
(
26
;
68
;
59
)
.
Third, iterative think-act loops grounded in concrete tool outputs mitigate hallucination and sustain progress over long-horizon analyses, as demonstrated by systems coupling LLM planning with execution and constraint solving
(
69
;
18
)
.
Fourth, agentic workflows enable validation through decompilation-based data flow analysis, targeted execution, and call-graph tracing, corroborating bug hypotheses with evidence before reporting and improving precision over pattern-only detectors
(
26
)
.

Target: Windows COM Services.

We target Windows COM services (
§2
), which constitute ideal subjects for evaluating scalable vulnerability discovery in closed-source binaries.
COM services present four properties that make them compelling targets: ❶ they are ubiquitous across Windows installations, ❷ they frequently run with elevated system privileges, ❸ they expose complex attack surfaces through multiple interfaces with well-defined entry points, and ❹ they exhibit significant detection challenges due to intricate reference counting, locking protocols, and virtual dispatch semantics that optimizing compilers obscure or eliminate in resulting binaries.
As discussed in
§2
, memory corruption in any reachable interface method of a cross-process COM service yields code execution at the privilege level of the hosting service.
COM interfaces provide well-defined entry points for systematic analysis while presenting the full complexity of production binaries.

Problem Scope: Race Condition Vulnerabilities.

Given a target COM binary and entry function addresses, the task is to determine whether race condition vulnerabilities are reachable through these entry points, localize the root cause, and generate a proof-of-concept program that triggers the vulnerability.
While
Slyp
targets race conditions as its primary vulnerability class, the architecture supports other classes by modifying task prompts and tool configurations.
Race conditions occur when concurrent threads access or modify shared objects without appropriate synchronization, leading to use-after-free or double-free bugs that manifest only under specific thread interleavings
(
14
;
20
;
58
)
.
We focus on memory corruption arising from unsynchronized accesses to shared objects across concurrent COM interface invocations, including setter/getter interactions, cross-thread object lifetimes, and improper reference counting.
Successful analysis demands tracking object lifetimes and argument flows across function boundaries, reasoning about locking protocols and synchronization primitives, and synthesizing evidence across multiple execution paths to confirm vulnerabilities.

Limitations of Existing Approaches.

Static analysis tools for binary vulnerability detection each target a narrow bug class with bespoke engines:
COMRace
models COM locking protocols
(
14
)
,
COMFusion
recovers types to find union type confusions
(
70
)
, and
QueryX
enables symbolic queries over decompiled binaries
(
15
)
.
Each requires predefined vulnerability signatures, substantial per-target engineering, and handcrafted queries from domain experts, limiting adaptability to unfamiliar locking idioms or new platforms
(
58
;
20
)
.
Fuzzers, including traditional pipelines
(
5
;
20
)
and recent LLM-driven approaches
(
9
;
62
)
, achieve broad code coverage but struggle with the narrow timing windows of race conditions, while general-purpose binary analysis frameworks lack COM-specific threading and activation models
(
53
)
.

Why End-to-End Matters.

Discovery alone yields candidate vulnerabilities that can include hallucinations, forcing domain experts to separate true positives from false reports.
An end-to-end pipeline that continues through PoC generation and debugger verification filters discovery outputs that fail to produce crashes and reduces manual effort by generating actionable crash evidence such as stack traces, register dumps, and faulting call stacks.

COMRace
generates template-based PoCs but cannot iteratively debug them against a live service
(
14
)
.

Slyp
closes this gap through an iterative compile-execute-debug loop that refines PoC programs until a debugger-attached crash is captured (
§4.5
).
The resulting crash artifacts directly support triage and patch prioritization, converting agent output into actionable security reports.
Since the MCP tools are target-agnostic and domain knowledge resides in prompts,
Slyp
generalizes to other binary targets with minimal engineering effort such as prompt revisions and tool interface adjustments.

4.2.
Agent Architecture

Slyp
implements a standard
ReAct
agent
(
69
)
, the same think-act-observe paradigm used by production coding agents such as
Codex

(
33
)
and
Cc

(
4
)
.
Algorithm
1
formalizes the shared loop: at each step, the reasoning model
\mathcal{M}
generates an action
\omega_{a}
(a tool call or final response), the tool interface dispatches the call to the appropriate MCP server or the built-in tool and returns an observation
\omega_{o}
, and the model reasons about the result before selecting the next action.
The loop terminates when the agent produces a structured vulnerability report or exhausts the step budget.
A middleware pipeline runs before each turn and before the agent stops, enabling the context management and verification behaviors described below.
The differences between agents lie in specific engineering choices within this shared framework, not in a fundamentally different architecture.

Context Management.

Long-horizon binary analysis generates large trajectories.
A single decompilation produces 2,000+ tokens, and examining dozens of entry functions with their callees generates 100K+ tokens.

Slyp
addresses context growth through auto-compaction with structured checkpointing.
A middleware monitor tracks the running token count and triggers compaction when usage approaches the context window limit.

The compaction process proceeds in four phases.
First, the system preserves recent messages by walking backward from the most recent turn, keeping tool-call/response pairs intact.
Second, it extracts all substantive assistant messages and saves them to an external checkpoint file, creating a lossless side-channel that bypasses the lossy summary.
Third, a compaction model generates a structured summary following a seven-section template (task, methodology, per-item findings with evidence, cross-item analysis, coverage, external state, current work state) that preserves cross-function relationships and analytical state.
Fourth, a post-compaction directive instructs the agent to read the saved checkpoint, re-verify tentative conclusions, and continue analysis.
If a single tool output exceeds the context window before compaction triggers, the system applies progressive truncation at three levels until the context fits.

Memory.

Slyp
provides a file-based memory system organized as a compact index plus topic files.
The index file is loaded into the agent’s context at each turn and serves as a quick reference with section headers, inline findings, and links to detailed topic files.
Each topic file stores one durable analytical finding and begins with YAML frontmatter containing a name, description, and type.
During long analyses, the agent incrementally saves function summaries, vulnerability patterns, and cross-function relationships into these topic files so they survive compaction.
The index remains size-bounded so it stays cheap to reload, while the detailed evidence stays in topic files until the agent needs it.

Retrieval uses BM25 search
(
52
)
augmented with frontmatter text.
For each topic file, the searcher prepends the name and description fields before tokenization, which boosts files whose declared purpose matches the query without extra model calls or hand-tuned field weights.
Because the search is deterministic and local, the agent can recover specific evidence after compaction with low latency.
This indexed design lets
Slyp
revisit prior findings without re-reading the full interaction history.
In this way, investigation depth can grow on disk while the active context stays bounded.

Task Verification.

We use verifier-style middleware to keep the agent aligned with the task throughout long analysis sessions.
Instead of trusting the agent’s self-assessment, the middleware inspects observable execution state and injects corrective feedback when the trajectory shows that the task has not yet been carried out or no usable answer has been produced.
This improves reliability by grounding control decisions in concrete execution properties rather than the model’s stated intent.
Furthermore, it can prevent the premature termination on weaker models.

A stop-time verifier intervenes when the agent attempts to terminate without demonstrating meaningful progress toward the task.
In task-oriented sessions, it prevents plan-only exits by requiring actual tool use and it also catches empty final turns after tool execution, forcing the agent to continue until it emits a usable artifact.
During long trajectories, a token-budget-driven memory nudge asks the agent to consolidate durable findings into external memory and re-check that the current line of work still matches the original objective.
As this nudge is triggered by context growth rather than fixed turn counts, it preserves analytical state during tool-heavy phases without disrupting shorter reasoning phases.

4.3.
Binary Exploration

Analyzing compiled binaries requires specialized tools that differ fundamentally from source code analysis.
Even with debug symbols, binaries lack the full semantic context available in source code: object layouts, type hierarchies, and inter-procedural data flows must be recovered through decompilation and cross-reference analysis.
COM binaries present an additional challenge through virtual dispatch via vtable pointers, making indirect calls opaque to standard decompilation
(
56
;
35
)
.
We implement a suite of binary exploration tools through MCP
(
3
)
, providing a unified interface for vulnerability analysis over compiled code.

Table 1
lists the agent-facing tools exposed during evaluation.
Code reconstruction tools (
decompile_function_addr/name
,
disassemble_function
) transform binary code into high-level pseudocode with integrated virtual function call resolution or instruction-level assembly.

get_function_by_name
and
get_function_by_address
retrieve function metadata including bounds and argument arity.
Navigation tools enable tracing how data and control flow propagate through call chains.

get_xrefs_to
identifies all code locations referencing a given address, enabling agents to locate all uses of shared state or calls to critical functions.

get_callees
and
get_callers
enumerate direct call relationships, and
search_functions
finds matched functions by name patterns.

Virtual function calls in COM binaries appear as indirect calls through vtable pointers, obscuring the actual target function
(
36
;
54
)
.
We integrate virtual function call resolution directly into the decompilation process, automatically resolving virtual calls and annotating them in the pseudocode output.
For each indirect call, the system identifies whether it represents a virtual call by analyzing the instruction pattern.
An object tracer then follows the object backward through its definition chain, collecting candidate vtables by analyzing cross-references and constructor invocations.
The system parses the method offset, looks up the concrete function in each candidate vtable, and annotates the pseudocode with resolved function names and addresses.
This eliminates the need for agents to arduously reason about COM virtual dispatch and ensures that resolved targets appear as concrete callees in navigation results.
Vtables loaded dynamically from external binaries and polymorphic initialization from multiple classes remain unresolved by this static technique.
The detailed recovery procedure is provided in Appendix
C
(Algorithm
2
).

4.4.
COM Inspection

Writing a PoC for a COM race condition requires knowing how to activate the target COM object such as which CLSID to use, which interfaces to query, what method signatures look like, and what privilege level the service runs at.
This information resides in the Windows registry and in proxy/stub DLLs, not in the target binary itself.
We expose COM registry inspection as a dynamic MCP interface, giving the LLM agent on-demand access to the live COM metadata of the target Windows system.

The tool interface provides 14 tools organized by workflow stage (
Table 1
).

Service discovery
locates target COM services and their hosting model.

Class and interface enumeration
retrieves classes, interfaces, and metadata (threading model, privilege level, AppContainer accessibility) with separate paths for WinRT and classic COM CLSIDs.

Security analysis
retrieves launch and access permissions in SDDL format to determine whether an unprivileged client can activate the target.

Interface inspection
retrieves full method signatures in Interface Definition Language (IDL) or C++ format from proxy/stub DLLs.

Code generation
produces compilable C++ skeletons with the correct activation pattern (
CoCreateInstance
for classic COM,
RoActivateInstance
or
RoGetActivationFactory
for WinRT) working as a placeholder for crafting a PoC.

These tools enable hierarchical COM registry traversal.
The agent locates the target service, enumerates its classes and interfaces, retrieves method signatures via proxy definitions, and generates a skeleton PoC.
This skeleton becomes the starting point for the iterative PoC refinement loop in Stage 2.

4.5.
Dynamic Debugging

As discussed in
§3
, Stage 1 still produces candidate vulnerabilities that require crash evidence to reject hallucinated reports and confirm true positives.
Race condition PoCs are especially challenging because they require correct COM activation, a workable thread interleaving, and iterative debugging against a live service.
Stage 2 addresses this with automated PoC generation paired with debugger-based crash verification.

The PoC pipeline receives Stage 1’s vulnerability report as input.
The agent extracts the vulnerable COM class, affected entry functions, race condition type, and suggested interleaving from the structured report.
It then uses COM inspection tools (
§4.4
) to retrieve interface definitions and generate a skeleton C++ template, and writes the concurrent invocation logic to trigger the identified race window.
The agent enters an iterative compile-execute-debug loop
(
63
)
, submitting PoC source code, receiving compilation errors or execution results (crash dump, timeout, or clean exit), and refining the source based on the feedback.
We enable page heap on the target VM so that race-induced heap corruptions are caught deterministically at the faulting instruction.
A PoC is verified when the crash dump shows an access violation or heap corruption and the faulting call stack still reaches the target function from Stage 1.

The tool interface provides 10 debugging tools in four categories.

PoC submission
compiles C++ source on the target VM and captures output and crash evidence in a single tool call.

Command execution
tools run arbitrary debugger commands and command sequences for targeted analysis.

Process and service management
tools enumerate running processes, start services, and attach or detach the debugger.

VM control
tools break into the debugger and resume VM execution when the target service requires recovery.

The agent typically requires 3 to 10 compile-debug iterations per successful PoC, with common refinement patterns including COM activation errors, thread count and timing adjustments, service crash recovery, and heap diagnostics.
Each verified case produces four artifacts (C++ source, crash dump, call stack, register state) constituting the evidence package submitted to MSRC.

5.
Implementation

We implement
Slyp
as a 19.9K-line Python agent framework plus 8.7K lines of Python code across three MCP servers:

Binary Exploration Server.

The binary exploration server implements diverse tools on top of IDA Pro
(
16
)
, and the evaluation exposes the 9 agent-facing tools listed in
Table 1
.
A Python FastMCP server communicates with an IDA Pro plugin via HTTP JSON-RPC.
The plugin runs inside IDA’s Python interpreter and exposes analysis functions as JSON-RPC endpoints.
The MCP server auto-generates tool wrappers from plugin decorators via abstract syntax tree (AST) manipulation, eliminating boilerplate for each new tool.
Vtable resolution logic and callee/caller enumeration are implemented from scratch atop IDA Hex-Rays.
Core decompilation uses IDA Hex-Rays together with official Microsoft debug symbols from the public symbol server.

COM Inspection Server.

The COM inspection server exposes 14 tools built on OleViewDotNet
(
12
)
.
A Python FastMCP server on the host communicates with a C# .NET 4.8.1 application inside the target Windows VM via a TCP JSON-line protocol.
The .NET application queries the live Windows COM registry and WinRT APIs.
This is the same underlying tool used by
COMRace

(
14
)
for COM registry inspection, exposed as a dynamic MCP interface that the LLM agent queries on demand.

Dynamic Debugging Server.

The debugging server exposes the 10 agent-facing tools used in evaluation and relies on a larger backend built on WinDbg and Microsoft Visual C++ (MSVC).
A Python FastMCP server communicates with a C++ WinDbg extension DLL via a Windows named pipe.
The extension uses the WinDbg debugger engine API for kernel and user-mode debugging.
PoC compilation and execution on the target VM are handled via Windows Remote Management (WinRM) and MSVC compiler.
The exposed tool set covers PoC submission, debugger command execution, process and service management, and VM control.

Agent and Infrastructure.

The agent framework uses an async generator-based streaming architecture.
A middleware pipeline with before-turn and before-stop hooks enables composable policies for compaction, memory nudging, and task verification (
§4.2
).
MCP integration uses a shared registry that caches tool discovery across sessions and supports multiple transports.
The same MCP servers work with
Codex
,
Cc
, and
Slyp
without modification.
All evaluation runs execute against a QEMU-hosted Windows 11 VM with a userland debugger (
cdb.exe
) attached, using per-case snapshots from a base image for isolation.

6.1.
Experimental Setup

6.1.1.
Dataset

We curate a dataset of 20 Windows COM objects covering 40 vulnerability cases from production systems across ten COM services.
The dataset is constructed from two independent sources:
① 12 COM classes containing zero-day vulnerabilities across the 6 services from
Table 2

② 8 COM classes containing 1-day vulnerabilities across 7 services (3 overlapping with the zero-day set and 4 additional:
McpManagementService

We confine the vulnerability scope to use-after-free (
UAF
) and double-free (
DF
) conditions arising from race conditions, which lead to memory corruption and local privilege escalation.
The 20 COM objects contain 379 entry functions in total, of which 64 are vulnerable, with per-object complexity ranging from 3 to 69 entry functions.
We define vulnerable entry functions according to three criteria:
❶ if a race condition occurs in the entry function itself or its nested functions, we regard it as vulnerable.
❷ if the vulnerability results from interactions between setter and getter functions, we consider both as vulnerable.
❸ the vulnerable location must be reachable by a working proof-of-concept that crashes the service.

A
vulnerability case
is a minimal, unique race condition pattern that demonstrates memory corruption in a COM service.
A single case may involve one entry function (self-race) or a set of functions whose concurrent invocations complete the interleaving scenario (
e
.
g

The 20 COM objects yield 40 vulnerability cases spanning the 64 vulnerable entry functions.

6.1.2.
Experimental Protocol

We evaluate all agents on the full 20 COM objects under identical experimental conditions:
❶ binary exploration, COM inspection, and dynamic debugging tools exposed through standardized MCP interfaces, evaluated under complete and reduced toolset configurations as detailed in each RQ.
❷ identical task prompts describing the objective to discover race-condition-induced memory corruption vulnerabilities, with prompt templates in
Appendix A
.

For discovery (RQ2, RQ4), we execute three independent runs per agent configuration and report best-of-3 per-case F1 by selecting the highest F1 across the three runs for each COM object, then macro-averaging across all 20 objects.
Discovery requires the agent to analyze many entry functions per COM object without any validation mechanism, making both analysis coverage and output correctness sensitive to non-deterministic reasoning.
For PoC generation (RQ3), we execute a single run per case because the task is inherently self-correcting: each case receives a scoped input (one or two vulnerable functions), and the dynamic debugging toolset provides interactive feedback through compilation, execution, and crash reporting, enabling the agent to iteratively correct errors.

7.
Discussion

Domain-Specific Knowledge Requirements.

LLMs lack comprehensive knowledge of platform-specific APIs and synchronization primitives, impacting analysis accuracy for race conditions involving critical sections, locks, and reference counting semantics.
We address this through in-context learning
(
7
;
60
)
by incorporating detailed explanations of synchronization APIs, locking patterns, and COM lifecycle management into task prompts.
This proves effective, as evidenced by 28 confirmed vulnerabilities discovered in production Windows services.
A natural next step is domain-specific fine-tuning or knowledge augmentation to reduce prompt-engineering overhead
(
27
;
28
)
.

Decompilation and Symbols.

Slyp
leverages official Microsoft debug symbols to produce high-quality pseudocode via IDA Pro’s Hex-Rays decompiler.
Like other systems
(
15
)
, mis-inferred types or control flow can hide or fabricate bug patterns even with symbols.

Slyp
mitigates this through multiple decompilation views, LLM reasoning that tolerates artifacts, and vtable resolution that provides ground-truth virtual dispatch targets
(
65
;
55
;
21
)
.

Context Window Scaling.

Stage 1 discovery completes within current 400K–1M+ token context windows, but Stage 2 PoC generation involves iterative compile-execute-debug cycles that consume 7.7–11.4M tokens per case on the strongest configurations (
Appendix D
).

Slyp
’s pre-compaction checkpointing (
§4.2
) manages this overhead, contributing to 22–61% token reductions on Claude backbones relative to the production agent.
Larger or more complex targets, such as analyzing hundreds of COM objects or tracing cross-binary dependencies, would exceed current limits.
Recent work confirms that increasing context length degrades LLM performance even with sufficient retrieval capacity
(
10
;
17
)
, motivating structured management approaches that decouple reasoning depth from the raw token budget available to the model.

Model Scaling and Task Decomposition.

The RQ2 results reveal an inverse relationship between model capability and scaffold benefit, with the largest gap on Haiku 4.5 (+0.208 F1) and smallest on GPT-5.3-codex (+0.003).
Task verification compensates for weaker reasoning by preventing premature termination, while stronger models partially self-organize without explicit scaffolding.
This matters for cost-sensitive deployment, as
Slyp
makes smaller models viable for vulnerability reasoning that would otherwise require frontier-class capabilities, and the complementarity analysis (
§6.4
) suggests that ensembling across cost tiers can increase coverage beyond any single configuration.

Generalization and Limitations.

Adapting
Slyp
to a different vulnerability class or platform requires modifying the task prompt and potentially adding new MCP tools, though the binary exploration server and agent architecture (pre-compaction checkpointing, task verification) are fully reusable.
Limitations include dependence on decompiler quality, non-determinism in LLM reasoning (addressed via the best-of-3 protocol), and the inherent difficulty of triggering race conditions due to timing-sensitive crash behavior.
The six unsolved PoC cases involve complicated threading object acquisitions where agents must coordinate multiple concurrent operations to trigger the race condition.

Appendix B
Details of
COMRace
Reproduction

Reproduction methodology.

We reproduce
COMRace
using IDA Python and Angr
(
2
)
, implementing virtual function recovery, taint propagation, and field usage detection for
read
/
write
/
free
operations.
The original vtable recovery algorithm assumes vtable addresses are loaded exclusively via the
rcx
register.
Our dataset contains diverse vtable loading patterns across multiple registers, rendering the original assumptions inapplicable.
Since vulnerability detection depends entirely on successful virtual function recovery, the vanilla implementation fails completely on our dataset.
We extend the recovery logic to handle diverse register usage patterns and additional edge cases in production binaries, yielding
COMRace++
.

Validation.

We validate
COMRace++
against the original
COMRace
datasets, confirming that it produces field usage patterns consistent with the original paper and detects the vulnerabilities reported in that work.

B.1.
Engineering Enhancements

COMRace++
extends the original
COMRace
with two core fixes (M1–M2) and five engineering enhancements (E1–E5) across three categories.

Table 8
summarizes each item, its category, and its effect on detection accuracy.
These changes address limitations L1 (field granularity) and L3 (indirect call resolution, branch handling) from the original paper.
Limitations L2 (alias analysis) and L4 (state-aware PoC synthesis) remain unresolved.

Table 8.
Core fixes (M1–M2) and enhancements (E1–E5) in
COMRace++
. M1–M2 are prerequisites for the tool to function on real-world binaries. E1–E5 improve detection accuracy across three categories: architectural (E1–E2), false negative reduction (E3, E5), and false positive reduction (E4).

Core fixes (M1–M2).

In real-world COTS binaries, MSVC frequently moves the
this
pointer to a callee-saved register (
rdi
,
rbx
,
rsi
, etc.) in the constructor prologue, and vtable initialization and field accesses occur via that register rather than
rcx
.
M1 extends vtable store detection to track all general-purpose registers, capturing vtable assignments through patterns such as
lea rax, [rip+vtable]; mov [rdi], rax
that the original
[rcx]
-only check misses entirely.
M2 propagates the
this
pointer through all registers using
(base, offset)
tuples in the field usage analysis engine, supporting multi-hop register chains (
mov rbx, rcx; mov rsi, rbx
) and stack spills (
mov [rsp+0x20], rbx
followed by
mov r12, [rsp+0x20]
).
Without these core fixes, the majority of vtable start addresses and field accesses in optimized binaries are missed, rendering the entire downstream pipeline inoperative.

Architectural improvements (E1–E2).

The original
COMRace
performs a linear scan of instructions, which cannot model branch-dependent synchronization states.
We replace the linear scan with BFS over the function’s CFG, maintaining independent analysis state per basic block with conservative merge at join points (E1).
The minimum lock count at each join ensures a field is considered guarded only if guarded on all reaching paths.
The original single
sync
counter conflates distinct lock objects into one integer.
We track lock state as a dictionary keyed by the lock object’s field offset, enabling precise lock-set inconsistency detection where two methods accessing the same field with disjoint lock sets are flagged as racing (E2).

False negative reduction (E3, E5).

In COM MTA threading models, the same method can be invoked concurrently by multiple threads on the same object instance.
Following
COMRace
’s original design, we implement self-race detection (E3). If a single method performs an unguarded write to a shared field, two concurrent self-invocations produce a data race.
COM objects frequently contain sub-objects accessed via pointer fields (
v4 = *(this+0x20); put_CallingUser(v4, v7)
).
Without recursive analysis, only the pointer load
this+0x20
is detected, but field writes inside the callee (
e
.
g
.to
v4+0x68
) are missed.
E5 enables recursive analysis through dereferenced field pointers, remapping callee field accesses to the caller’s namespace (
e
.
g
.callee’s
this+0x68
becomes
[this+0x20]+0x68
).
This exposes getter/setter conflicts on sub-object fields that flat analysis cannot detect.

False positive reduction (E4).

We implement R/R pair filtering that excludes fields with read-only access from race candidates (E4), since read-read pairs generally do not produce the memory corruption primitives (use-after-free, double-free) targeted by the analysis.
This removes a substantial number of false positives from fields that are only read across all entry functions.
However, R/R filtering also eliminates a small number of true positives.
These are genuinely vulnerable functions that
COMRace++
detects only through R/R pairs rather than through the expected R/W or W/W conflict patterns, because the taint engine fails to classify the actual write access correctly.
Removing R/R pairs therefore suppresses these cases, making them appear as lost true positives even though the original detection was based on an incomplete access classification.

B.2.
Limitations of Static Taint Propagation

COMRace++
’s limited base-configuration performance (0.225 F1, 0.500 recall, and 32 missed vulnerable functions out of 64) stems from four structural limitations that persist despite our engineering enhancements.

Field-scoped taint origin.

COMRace++
tracks shared state exclusively through
this
-relative field offsets, as taint propagation originates from the
this
pointer passed via
rcx
.
Race conditions arising from global variables or other non-instance shared memory fall outside this taint scope entirely.

C14
exemplifies this gap. All eight vulnerable functions involve unsynchronized access to global variables, and
COMRace++
achieves F1 = 0 across all three configurations (
Table 7
).

Slyp
detects all eight with every backbone model except Haiku 4.5, as LLM-based reasoning naturally considers all forms of shared mutable state regardless of provenance.

WinRT
produce<T,I>
wrapper.

WinRT’s
produce<T,I>
template wraps every interface method with a branchless null-safe
this
-pointer adjustment:
lea rax,[rcx-8]; neg rcx; sbb rcx,rcx; and rcx,rax
.
The expression
(a1 - 8) & -(int64)(a1 != 0)
adjusts the interface pointer back to the implementation object when non-null.
The taint engine’s binary operation handler for
And
can partially recover the
(’this’, -8)
value from the
lea
operand, but recursive member analysis expects
rcx == (’this’, 0)
.
A value of
(’this’, -8)
does not satisfy this check, so the callee’s field accesses are unattributed.
Different
produce<>
instantiations use different offsets (
this-8
,
this-0x10
,
this-0x18
) depending on the interface’s position in the inheritance hierarchy.
Allowing arbitrary offsets and arithmetic operations on pointer values as valid
this
aliases without type information would create false field-offset mappings across unrelated interfaces and sharply raise the false-positive rate.

Indirect field access through struct construction.

A further class of false negatives occurs when a method embeds the
this
pointer into a locally constructed struct and passes that struct to a transaction or callback mechanism.
When
this
is stored into a stack-allocated struct (
v12[1] = this
) and the struct’s address is passed to a callee via
rcx
, the taint tracker sees
rcx = (’rsp’, 0x40)
, a stack pointer rather than a
this
-derived value.
Recovering the relationship requires points-to analysis: tracking which memory locations contain pointers to which objects.
The current engine tracks
(’base’, offset)
tuples through registers and direct stack slots but does not model struct-embedded pointer indirection.

Statically-linked internal helpers.

Statically-linked internal helper functions (
e
.
g
.
std::wstring
constructors compiled into the binary) may be recovered only partially by lightweight static analysis.
When the callee’s internal CFG or IR is incomplete, field accesses performed inside the helper can be missed during callee analysis.
This primarily affects Write detection in our implementation, because confirming a write requires recoverable internal basic blocks that the fast CFG recovery does not produce, whereas Read accesses can still be conservatively approximated.

Appendix C
Virtual Function Call Recovery

Algorithm
2
presents the virtual function call recovery procedure, which resolves indirect calls through vtable pointers to their concrete target functions.
This recovery is partial because backward object-provenance tracing may fail to resolve a vtable when the definition chain is broken by indirect assignments, cross-module calls, or compiler-driven register reuse.

Algorithm Overview.

The algorithm processes all call instructions in a function (Lines
3
–
17
), filtering for virtual calls and resolving each to concrete function targets.
The core workflow consists of five key operations implemented through specialized helper functions.

Virtual Call Detection.

CollectCalls
extracts all call instructions from the function (Line
1
), then
IsVirtualCall
identifies virtual calls by analyzing instruction patterns (Line
5
).
Virtual calls exhibit the characteristic pattern of indirect calls through vtable pointers with fixed offsets, distinguishing them from other indirect calls such as function pointer invocations.

Object Provenance Tracing.

For each confirmed virtual call,
TraceObject
identifies the object used at the call site by analyzing register usage and stack variables (Line
6
).

FollowObjectChain
then traces this object backward through its definition chain, analyzing cross-references to identify constructor invocations and vtable assignments (Line
9
).
This backward analysis collects candidate vtables that the object might reference at runtime, handling polymorphic scenarios where multiple derived classes are possible.

Method Resolution.

ParseMethodOffset
extracts the method offset from the call instruction by analyzing the vtable dereference pattern (Line
10
).

LookupVtable
then reads the vtable structure at each candidate address, retrieving the function pointer at the computed offset (Lines
12
–
15
).
When multiple candidate vtables exist, all possible targets are collected, providing agents with complete information about potential polymorphic dispatch targets.

Integration with Decompilation.

The resolved mappings
\mathcal{R}
integrate into the decompilation pipeline, where resolved calls appear as comments in the pseudocode output formatted as
// Resolved virtual call: function_name at 0xaddress
.
This annotation enables agents to understand complete call chains without manual vtable analysis.

We present a detailed analysis of CVE-2025-53802 (

), a use-after-free vulnerability discovered by
Slyp
.
The vulnerability arises from the interaction between
put_ScanResponsePayload
and
get_ScanResponsePayload
that operate on the same COM reference pointer at offset 192, shown in

.

put_ScanResponsePayload
updates this pointer via
operator=

Concurrently,
get_ScanResponsePayload
reads the same pointer and calls
InternalAddRef
using a virtual
AddRef_Proxy
.
When two setter threads run while a third executes the getter, both setters decrement the same old object’s reference count to zero and free it.
The getter then dereferences a freed pointer during
InternalAddRef
, causing a use-after-free that enables local privilege escalation from
Low
to
System
integrity.

Slyp
performance.

Slyp
successfully identifies this vulnerability with precise localization through LLM-based semantic reasoning.
Although
Slyp
cannot recover the complete virtual function table due to cross-module dependencies, the LLM agent infers the functionality of
InternalAddRef
and
InternalRelease
based on their names and calling context.
By recognizing these as standard COM reference counting operations,
Slyp
correctly determines that they manipulate shared object state without synchronization and pinpoints the vulnerable access within
InternalAddRef
where the freed object is dereferenced.
The agent then synthesizes the precise interleaving scenario (two
put_ScanResponsePayload
calls followed by one
get_ScanResponsePayload
call) that triggers the race window, providing detailed thread interaction patterns that enable efficient verification.

Comparison with
COMRace
.

COMRace
fails to recover two main methods due to incomplete vtable resolution, resulting in zero detection.

COMRace++
, our improved reproduction with extended vtable recovery (
Appendix B
), successfully recovers both methods and flags them as vulnerable to race conditions, achieving perfect recall on this case.
However,
COMRace++
fails to resolve the virtual calls within
InternalRelease
and
InternalAddRef
, which breaks propagation to reference-count functions and contributes to missed localization of the true unsafe site.
As a result, it reports line 7 of
get_ScanResponsePayload
(a benign copy operation for
this+192
) as the vulnerable point, missing the actual vulnerability within
InternalAddRef
where freed objects are accessed.
Given the granularity at which VEX IR represents memory effects, precisely trimming benign expressions/statements without suppressing security-relevant accesses is challenging, as discussed in
§6.5
.
Mitigating this requires extensive engineering to tune filters and heuristics that separate benign patterns from genuine vulnerabilities, underscoring the specialization burden.
In contrast,
Slyp
’s semantic reasoning distinguishes the benign field copy from the critical freed-object access, demonstrating superior precision in vulnerability localization.
