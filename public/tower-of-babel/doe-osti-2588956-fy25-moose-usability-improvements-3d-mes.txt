 Executive Abstract
 Usability improvements have been made to MOOSE and Workbench in FY25 to enhance usability and
user workflows. Assorted enhancement have been made to MOOSE’s intrinsic meshing capabilities in order
to enable more flexible and complex meshing of nuclear reactor systems, in particular for 3D applications.
Mesh generators have been added to perform operations such as batch mesh generation, surface mesh gen-
eration, and creation of 3D transition layers. These mesh generation capabilities make it much easier to
generate high quality non-extruded 3D meshes. Additionally, work to integrate Monte Carlo reactor physics
simulations into MOOSE-based multiphysics workflows has reached another milestone with the implemen-
tation of the Constructive Solid Geometry (CSG) base framework. This framework lays the foundation for
mesh generators to offer the user a generic CSG output option (as opposed to a finite element mesh). To
support users, workshop on the MOOSE Reactor Module was delivered which featured hands-on examples
using the NEAMS Workbench on INL’s High Performance Computing system.
 Recent updates to the NEAMS Workbench, WASP, and the MOOSE language server have introduced
several improvements aimed at making MOOSE-based simulation setup and input management faster, more
accurate, and easier to use. Key capabilities that have been added include multi-tab-stop autocomple-
tion, visual input diagnostics, developer-directed data visualizations, upgraded ParaView integration, and
Workspace-level file tracking. Together, these changes make it easier for users to build, validate, and man-
age complex MOOSE-based simulation models — especially those involving reusable components, included
files, and datasets. The improvements are designed to save time, reduce input errors, and help users get to a
successful simulation run faster, with more confidence in the results.

 1. Introduction

 The Office of Nuclear Energy Advanced Modeling and Simulation (NEAMS) program [3], under the

U.S. Department of Energy, develops an integrated suite of advanced reactor physics tools built upon the

Multiphysics Object-Oriented Simulation Environment (MOOSE) framework [4]. This report documents

user-oriented improvements delivered in FY25 to the MOOSE framework focusing on mesh generation

capabilities and enhancement of MOOSE - Workbench user interactions.

 High fidelity, finite element mesh (FEM)-based modeling tools like the MOOSE-based physics appli-

cations require the construction of a mesh to spatially discretize complex nuclear geometry for use with

numerical algorithms. FEM construction can be tedious for both new and experienced users, and available

meshing tools have historically required software licenses and steep learning curves due to their generality.

The MOOSE Reactor Module [5] was first developed in FY21 to make free, quality, easy-to-use meshing

tools accessible to NEAMS users, providing functionality specifically for nuclear reactor geometries. The

Reactor Module achieved nearly immediate adoption by NEAMS users both within and outside the pro-

gram. The Reactor module has been expanded this year to include new features requested by stakeholders,

including implementation of more advanced 2D and 3D meshing algorithms. Additionally, the base frame-

work for enabling Monte Carlo constructive solid geometry definitions from existing mesh generators was

been developed in the main MOOSE framework, which will help integrate Monte Carlo workflows into

MOOSE-based multiphysics simulations.

 As MOOSE-based simulation workflows grow in complexity, users are working with input configu-

rations that span multiple files, including application blocks, external datasets, mesh files, and included

subfiles. While this modular structure improves reuse and organization, it can also introduce challenges in

navigating, editing, and validating these inputs. To reduce setup errors and make simulation preparation

more efficient, recent updates to the NEAMS Workbench, the Workbench Analysis Sequence Processor

(WASP), and the MOOSE language server have introduced new features that improve input editing, visual-

ization, and workspace awareness. These include smarter autocompletions with multiple tab stops to guide

users through required fields, interactive plotting of functions and CSV-based inputs for early error detec-

tion, and developer-controlled visualizations using the new waspplot backend. The Workbench has also

been upgraded to ParaView 5.13 to improve mesh visualization performance and compatibility with newer

user operating systems. Additionally, support for workspace-level file tracking enables real-time revalida-

 1

tion of inputs when any related file is changed, helping users stay on top of inter-file dependencies. Together,

these updates provide a more responsive, accurate, and user-friendly environment for building and managing

MOOSE simulation models.

 This work builds upon and continues user-oriented improvements in the MOOSE framework in support

of multiphysics simulation accomplished in FY22 [6], FY23 [7], and FY24 [2].

 2

 2. 2D and 3D Meshing Improvements

 The ability to do 3D tetrahedral meshing in MOOSE has been a user request since the inception of the

Reactor Module. Relevant 3D meshing use cases include (1) pebble-bed reactor cores where each node

indicates a pebble center in reactor physics, (2) transition regions between detailed test assemblies and more

homogenized neighboring assemblies, (3) non-extruded 3D axi-symmetric geometries like cones or domes,

and (4) non-extruded 3D detailed geometries like TRISO particles, additively manufactured fuel, structural

components, and heat exchangers. Last year, we introduced capabilities to handle several non-extruded

3D geometries with an axis of symmetry such as cones and domes, and we also integrated the Netgen

tetrahedral meshing capability in MOOSE. We also determined that Netgen is not suitable for pebble bed

reactor meshing schemes and commenced exploration of possible alternatives. This year we have improved

the usability of the Netgen tetrahedral mesher for well-suited applications like (2), (3), and (4). Finally,

assorted 2D meshing enhancements have also been delivered, and a hands-on user workshop for the MOOSE

Reactor Module was offered in spring 2025.

 This chapter contains the following key improvements:

 • Netgen integration maintenance: Bugs have been fixed, feature compatibility expanded, and ad-

 ditional performance logging and correctness verification added to the tetrahedral mesh generation

 capability in MOOSE.

 • Netgen alternatives investigation: Other tetrahedral meshing packages were investigated, in the

 hopes of finding a backend option for the XYZDelaunayGenerator that could handle tetrahedral mesh

 generation from scratch without adding Steiner points; unfortunately the alternatives investigated were

 unsuitable for this.

 • 3D mesh cutting by level set: Analytically generates the complex meshed surfaces which are needed

 as input to XYZDelaunayGenerator.

 • 3D transition layers: Applies a strategic transition layer to allow compatibility with XYZDelaunayGenerator

 while avoiding excessively high mesh density.

 • Multi-dimensional extruded mesh junctions: Enables the smooth joining of meshes together such

 as in pipe junctions.

 3

 • Mesh generation for repeated objects: Streamlines input for repeated objects by invoking batch

 mesh generation with variable parameters.

 • Simplex conversion: Generation of pure simplex (tetrahedron and triangle) meshes from meshes of

 non-simplex elements is now better supported, making other mesh generator outputs easier to integrate

 with tetrahedral meshes.

 2.1 Status of 3D Tetrahedral Meshing Based on Netgen

 In FY24 fiscal year, NEAMS development extended the MOOSE unstructured simplicial mesh gen-

eration capabilities from 2D (where the “simplicial” elements or “simplices” are triangles) to 3D (where

simplices are tetrahedra). We employ the Netgen mesh generation and optimization library to perform do-

main tetrahedralization, via a new implementation class based on a libMesh abstract base class that has

been used in the past for Tetgen tetrahedralization. Like the XYDelaunayGenerator developed in previous

years, the MOOSE XYZDelaunayGenerator takes a domain from the user, defined by a triangulated sur-

face mesh or a volume mesh for the domain exterior and for any holes in the mesh, and triangulates the

interior of the domain with a conforming simplicial mesh; in the 3D context “triangulation” here refers to

tetrahedralization.

 Even for two-dimensional meshes, triangulation of arbitrary domains via simplicial meshes has been

invaluable to MOOSE users and to developers of advanced compound mesh generators like those in the

MOOSE Reactor Module, and it was natural to hope to see equal or greater value in 3D. Hexahedral meshing

is not a solved problem, and the ability to generate 3D meshes in domains too difficult for hex generators

and extrusion-based methods essentially requires the use of tetrahedral elements.

 The pre-existing Tetgen-based tetrahedralization capability in libMesh, as well as many of the alter-

natives we investigated last year, were unsuitable for integration with MOOSE. Tetgen and many other

tetrahedralization libraries do not have an LGPL-compatible software license; other libraries we investi-

gated had incompatible software architectures and/or other technical flaws. We settled on and integrated

Netgen, the most advanced meshing library we could find with the tetrahedral capabilities we needed under

an LGPL-compatible open-source license.

 4

2.1.1 Netgen Interface Testing and Maintenance

 The previous year’s work on Netgen integration and the XYZDelaunayGenerator interface (the user-

facing mesh generator for tetrahedral meshing using Netgen) has been stress tested by various users and

developers this year, and assorted bug fixes and improvements have been made to the system.

 The libMesh configure help text for the options controlling Netgen (and Poly2Tri, used for XYDelaunayGenerator

support, and QHull) have been made clearer. Netgen is now distributed along with tarball distributions

of libMesh. Performance logging for the Netgen interface using the libMesh PerfLog has been added;

This and other profiling tools were used to investigate performance issues encountered during valgrind test-

ing of XYZDelaunayGenerator regression tests. A necessary valgrind suppression file entry was made to

avoid false positives on other valgrind tests. Bugs in the interaction of mesh cloning (used by some mesh

generation workflows and complex generators to stitch together copies of the same submesh in various

patterns) were identified and fixed after they triggered errors in tetrahedralization code. Additional sup-

port for mesh self-consistency testing in debug runs was added, and this was used to identify cases where

meshes were not being adequately prepared before stitching into holes in new tetrahedralizations. A new

ElementsToSimplicesGenerator has been added to MOOSE, useful for converting input meshes with hex,

prism, and/or pyramid elements into entirely-tetrahedral meshes that can define the domain of and can be

directly stitched to a new tetrahedral mesh. The generator also converts 2D quads to triangles, including

when the quads are embedded in 3D space. The ElementsToSimplicesGenerator was subsequently made

compatible with and is now tested with distributed meshes in parallel as well as with replicated meshes.

Finally, a default boundary condition id assignment has been added to Netgen-generated meshes.

2.1.2 Investigation of Alternate Tetrahedral Mesh Generation Algorithm for Pebble
 Bed Applications

 Netgen, unfortunately, does not perfectly meet all our users’ needs. Although it produces locally-

Delaunay output, it does not use a 3D Delaunay algorithm to triangulate the interior with a fixed set of

vertex points, but rather an advancing front algorithm that inserts new vertices itself as deemed necessary.

This is acceptable to most Finite Element Method users, but for users of the Pebble-Tracking Transport

(PTT) method relevant for pebble bed reactor analysis, which requires precise placement of tetrahedral

vertices at fuel pebble locations, arbitrary point insertion and mesh refinement is not allowable.

 5

 Accordingly, we investigated additional tetrahedral meshing utilities this year, in an attempt to find an

additional alternative for these users. Unfortunately, we were unsuccessful.

 We investigated the Omega h [8] library maintained at Sandia National Laboratory, the university-

developed MeshGenC++ [9] library, the LaGriT [10] library from Los Alamos National Laboratory, and

the MMG [11] and ParMMG [12] codes developed in a collaboration of French universities and research

institutions. Each of these met our requirements for software license compatibility and our standards for

software quality, however we were unable to harness them to perform constrained Delaunay tetrahedraliza-

tion of a triangulated surface manifold without nodal insertion. OmegaH, MMG, and ParMMG appear to be

excellent options for adaptivity on existing tetrahedral meshes, but we were unable to get a priori mesh gen-

eration of triangulated surfaces from them. MeshGenC++ does mesh generation, but of domains defined by

implicit level-set descriptions rather than triangulated surfaces; it also has not been under development since

2021, and has at least minor software quality and compiler compatibility issues that needed to be addressed

for our tests. LaGriT also supports mesh generation, but for workflows typically beginning with hex mesh

generation, octree refinement, and boundary capture via node insertion. We were not able to find a way to

directly generate a tet mesh without node insertion.

 Although we do hope that the open source tet meshing ecosystem expands in the future to include all

the capabilities we would desire, for the foreseeable future we expect that all 3D tetrahedral meshing work

in MOOSE will continue using the Netgen backend alone. There may be room in the future to employ other

libraries for mesh refinement, but Netgen remains our best option for initial generation.

2.1.3 User Interface Improvements

 Several user interface enhancements have been introduced for the XYZDelaunayGenerator. Hole meshes

are now automatically verified for compatibility, and their external boundaries can either be consistently

and automatically generated to prevent conflicts, or explicitly defined by the user. When a hole mesh is

designated to be stitched with the generated tetrahedral mesh, it is automatically converted to a TET4 mesh

if its surface contains non-TRI3 side elements, ensuring seamless integration and compatibility. The mesh

generator also provides more informative error messages to help users debug their input files. However, this

conversion to all TET4 elements can result in higher-than-necessary element counts, which is addressed by

the next feature improvement.

 2.2 3D Mesh Cutting By a Level Set

 The integration of NetGen-based tetrahedral mesh generation in libMesh and its implementation in

MOOSE via the XYZDelaunayGenerator provides powerful tools in MOOSE for meshing arbitrary 3D ge-

ometries. However, the preparation of complex 2D surface geometries suitable as input for the XYZDelaunayGenerator

was identified as a major challenge in practical use. A mesh generator capable of cutting existing 3D

meshes based on level set definitions to create the 2D surfaces was developed to enhance the usability of the

XYZDelaunayGenerator.

 CutMeshByLevelSetGenerator is an natural extension of CutMeshByPlaneGenerator. It trims a 3D

input mesh using a specified level set function ( f (x, y, z) = 0), retaining the portion of the mesh where

f (x, y, z) ≤ 0, and discarding regions where f (x, y, z) > 0, effectively sculpting the mesh according to the

level set.

 The input mesh must be a 3D mesh that is composed exclusively of first-order elements. The level set

function ( f (x, y, z)) is provided as a parsed function that can be interpreted by FParser. To ensure a smooth

and accurate cut, elements intersecting the level set are trimmed based on their precise intersection points,

avoiding jagged or ”zigzag”-type boundaries. This generator enables the transformation of a structured

3D mesh (such as one created by GeneratedMeshGenerator within a bounding box) into a mesh whose

geometry conforms to a user-defined level set. The surface of the cut mesh can then be used as the input of

XYZDelaunayGenerator so that the 3D elements can be further refined.

 With the CutMeshByLevelSetGenerator, complex geometries such as triply periodic minimal surfaces

 7

(TPMS) can be meshed using MOOSE, as shown in 2.1.

 2.3 3D Transition Layers

 As noted in the previous section, to fully harness the advanced tetrahedral 3D meshing capabilities

offered by the NetGen implementation via XYZDelaunayGenerator, it may be necessary to modify the

element type of meshes generated by other intrinsic MOOSE mesh generators to ensure compatibility with

tetrahedral 3D meshes. Specifically, any surface intended to interface with the tetrahedral mesh must consist

exclusively of TRI3 elements.

 The most straightforward element type conversion strategy is to transform all 3D elements into TET4.

However, in many applications, retaining non-TET4 elements is preferable due to their structural or compu-

tational advantages. A complete conversion to TET4 can also lead to a significant increase in element count,

thereby raising computational costs.

 To avoid full mesh conversion to TET4 while also maintaining TRI3 elements on the surface, a transi-

tion layer approach is employed. This method allows the majority of non-TET4 elements in the original

mesh to be preserved. The transition layer is constructed by converting the original non-tetrahedral ele-

ments into a combination of TET4 and PYRAMID5 elements. This hybrid layer provides one surface com-

posed entirely of TRI3 elements—ensuring seamless integration with the tetrahedral mesh generated by

XYZDelaunayGenerator—and another surface containing the necessary QUAD4 elements to maintain com-

patibility with the remaining original mesh.

 The 3D transition layer meshing capability has been integrated into MOOSE as a utility, enabling devel-

opers to easily incorporate tetrahedral meshes into their projects. To make this feature broadly accessible,

a dedicated mesh generator, BoundaryElementConversionGenerator, was developed based on the util-

ity, allowing all users to leverage the new meshing functionality. BoundaryElementConversionGenerator

converts the elements of a linear mesh that are involved in a set of given boundaries in a mesh to ensure that

the side elements on these boundaries are all TRI3. As shown in Figure 2.2, HEX8 and PRISM6 are converted

into a combination of TET4 (based on the sides included in the given boundaries) and PYRAMID5 (based on

the sides not included in the given boundaries) elements, whereas PYRAMID5 elements are converted into two

TET4 elements if needed.

2.3.1 Application of 3D Transition Layers in Other Mesh Generators

 The 3D transition layer generation utility has also been adopted by several existing mesh genera-

tors to improve performance and broaden their applicability. Previously, mesh cutting generators such as

CutMeshByLevelSetGenerator and CutMeshByPlaneGenerator required converting the entire input mesh

into a TET4-only format to enable cutting operations. With the introduction of the transition layer capability,

only the elements intersected by the specified level set or cutting plane need to be converted into TET4. The

remaining portions of the original mesh can now be seamlessly connected to the converted region using a

transition layer. After these mesh generators were enhanced with a transition layer capability, the majority

of the original elements remain intact during the cutting process (see Figures 2.3 and 2.4 for examples).

  2.4 Generalized Triangulation with Application to Curved Surfaces

 The Boundary2DDelaunayGenerator builds upon the 2D triangulation capabilities in the XY-plane,

originally employed by the XYDelaunayGenerator, and extends them to handle more generalized 2D sur-

face scenarios. Unlike its predecessor, this generator is not restricted to flat meshes confined to the XY-plane.

Instead, it can accept 2D curved boundaries embedded in 3D space.

 The input for Boundary2DDelaunayGenerator consists of a 3D mesh (input) and a list of bound-

ary names (boundary names) contained within it. The mesh generator extracts the specified 2D bound-

aries from the input 3D mesh and performs Delaunay triangulation to produce a 2D mesh. This out-

put mesh could then be further processed or used as input for 3D Delaunay mesh generation via the

XYZDelaunayGenerator. Additionally, Boundary2DDelaunayGenerator supports hole meshes, defined

by boundary names (hole boundary names), as well as automatic area control based on node spacing on

the boundary of the 2D mesh.

 This mesh generator adopts the same core methods in libMesh used by XYDelaunayGenerator, but

extends them to support generalized 2D surfaces (see 2.5a). The following steps are implemented:

 • An average normal vector of the given 2D surface is computed based on the normal vectors of the

 elements weighted by their areas.

 • The 2D surface is then rotated and translated so that its centroid is on the XY-plane and the average

 normal vector is aligned with the Z-axis (see 2.5b).

 • The 2D surface is projected onto the XY-plane so that the triangulation method can be applied (see

 2.5c).

 • The new 2D mesh in the XY-plane is generated through Delaunay triangulation (see 2.5d).

 • The new 2D mesh is reversely projected back to the original 3D space based on the original 2D

 surface.

 • The new 2D mesh is translated and rotated back to the original position of the 2D surface (see 2.5e).

 • Optionally, the nodes in the new 2D mesh can be corrected using a provided level set function of the

 surface (see 2.5f).

 A common application of this mesh generator is the preparation of 2D surface meshes for use as input

in XYZDelaunayGenerator. When working with a raw 3D mesh that contains a closed 2D surface, the sur-

face can be subdivided into multiple regions to ensure compatibility with the projection-based triangulation

method. The Boundary2DDelaunayGenerator enables the generation of high-quality 2D surface meshes

with enhanced control over mesh density and refinement. This is particularly beneficial for surfaces pro-

duced through mesh cutting operations (e.g., CutMeshByPlaneGenerator and CutMeshByLevelSetGenerator),

which can be significantly improved using this approach. The resulting 2D surface meshes can then be

stitched together to reconstruct a closed surface mesh suitable for 3D Delaunay mesh generation. An exam-

ple is provided as shown in 2.6.

 2.5 Multi-dimensional extruded mesh junctions

 To create the mesh shown in Section 2.8.2, we needed the ability to join parts together. Since these parts

have the same radial discretization, the junctions only need to extrude from one surface onto the other. To

form a smooth mesh, the width of the extrusion curve should also be varied. The following capabilities were

added to accomplish this:

 12

 • The ability to generate 1D splines passing through a start and end point with the desired direction

 • The ability to extruded a surface following an arbitrary 1D curve, here the 1D splines

 • The ability to expand linearly or cubically the radius of the extruded surface

2.5.1 1D Spline mesh generation

 As part of a simplified workflow for both mesh generation and simulation, further introduced in subsec-

tion 2.8.2, we needed to be able to join two arbitrary points in space using a smooth line. We also needed to

follow the orientation of the connected components, hence the line also had prescribed derivatives at both

ends. We considered using the following general curves:

 • a circle. A circle only has 4 degrees of freedom (radius, center coordinates) in 3D. Thus it is insuffi-

 cient to impose two points it has to pass through and two tangents at these points.

 • a general cubic polynomial. We observed that the interpolation was mostly linear and thus the shape

 was undesirably non-smooth.

 • a generalized ellipse. The Newton solve we derived to obtain the ellipse parameters struggled to

 converge due to periodicity.

 • a B-Spline. This curve is simpler to define, does not require complex solves to obtain the coefficients,

 and can honor both points and tangents.

 A BSplineCurveGenerator mesh generator was thus added to MOOSE, which can create a 1D mesh,

with edge elements, in 3D space.

2.5.2 Extrusion along curves

 As part of a simplified workflow for both mesh generation and simulation, further introduced in subsec-

tion 2.8.2, we needed to be able to join two cylinders (pipes) in 3D space using a 3D cylindrical mesh. The

shape of the junction should preserve the starting and ending surface shapes. The junction should respect the

 15

 orientation of the pipes, to prevent a jump in the curvature of the mesh on its radial boundary. The junction

 should also be able to map the meshes between the end surfaces of two cylinders of different radii. The

 cylinders are currently assumed to be meshed using the same discretization, though this could be relaxed in

 the future if using a different algorithm than extrusion.

 There were already advanced extrusion capabilities available in MOOSE. These were notably leveraged

 2.7 Miscellaneous items

 Additional developments supporting 2D and 3D meshing capabilities of MOOSE are reported in this

section for completeness. The following capabilities were added:

 • The ability to convert mesh elements to simplex elements (triangle, tetrahedron)

 • The ability to mark elements on boundaries as part of different subdomain to facilitating using differ-

 ent equations on elements near the mesh boundary

 • The ability to create nodesets with the same expansive logic available for sidesets

2.7.1 Mesh element conversion

 An additional mesh generator, ElementToSimplicesGenerator, was added to MOOSE to convert the

entire mesh to simplices. It can convert all non-simplex element types supported by libMesh to the cor-

responding simplex elements, triangles and tetrahedra, in 2D and 3D respectively, including hexahedra,

prisms, pyramids and polyhedra. The conversion to a tetrahedral mesh is notably useful for performing

operations such as trimming the mesh with an arbitrary lower-dimensional curve, for example a plane, and

reconstructing the boundary to prevent a jagged outer surface. This reconstruction is difficult to perform ex-

cept with tetrahedra. Note that a ElementsToTetrahedronsConverter is available in MOOSE. Note that

with the novel support for polyhedra, we should be able to cut a hexahedral mesh arbitrarily and reconstruct

the boundary using polyhedras. This has not been investigated at this time.

 19

2.7.2 Boundary layer mesh generation

 We added the BoundaryLayerSubdomainGenerator to MOOSE to enable setting a different subdo-

mains for elements that share a side or a node with a named boundary of the mesh.

 In computational fluid dynamics simulations, it is often the case that the equations differ on the boundary

elements, beyond the usual boundary condition on the face of these elements. For example, in the k − ε

turbulence model, wall functions are applied in those elements, setting specific production and destruction

terms for the turbulent kinetic energy, and turning off advection and diffusion contributions for all or part of

these elements. The k − ε and k − τ models were implemented in Pronghorn for molten salt reactor analysis

studies [13].

 In MOOSE, the detection of the proximity to a boundary of an element requires the examination of

all sides of the element, and checking whether these sides are part of a boundary. This is currently done

once and cached inside a map due to the computational cost. An alternative solution enabled by this

BoundaryLayerMeshGenerator is to simply place these elements in a specific subdomain.

2.7.3 Versatile nodeset generation

 MOOSE initially attempted to blur the distinction between sidesets and nodesets and simply refer to

the more commonly understood concept of a boundary. This was enabled by automatically or manually

converting sidesets to nodesets, or the opposite, to provide the right type of boundary to the objects that

need them. For example, a Dirichlet boundary condition on a variable with degrees of freedom defined at

nodes, naturally requires a nodeset rather than a sideset for its definition. If the nodeset did not exist, the

user was told to attempt to convert their sidesets to nodesets.

 However, specific needs sometimes require the distinction to be made. While considerable capability

was built for sideset generation in MOOSE, notably using combinatorial parsed (written directly in the input

file) expressions, combinations of neighbor subdomains, with fixed/rolling side normals or included points,

the same was not the case for nodesets. In FY25, we introduced the ParsedGenerateNodeset, a mesh

generator that can create nodesets based on the combinations of the following criteria:

 • the evaluation of a parsed expression at the node. If positive, include the node in the nodeset

 • whether it is part of, or not, of a combination of existing boundaries

 20

 • whether it is part of elements of specific subdomains, with both a subdomain include and exclude list

 (this capability was added later by Dr. Wang)

 • whether it is an external boundary of the mesh

 These criteria provide the same flexibility as found with sideset generation.

2.8.2 Automated mesh generation workflow for the Molten Chloride Reactor Ex-

 Using the new mesh generation capabilities, namely spline curve generation, extrusion along a spline,

and extrusion with a radial expansion, we can generate the mesh for the fluid domain in the Molten Chloride

 The authors of this report would like to acknowledge contributions in this section by K.R.B. Nantes,

R.T. Sweet, and J.A. Hirschhorn, who provided a very useful assessment of recently developed capabilities.

 The NEAMS Fuels Technical Area has been developing compact-scale thermomechanics analysis ca-

activities. This effort was divided into three discrete activities in order to develop a modular tool which

could be tailored to support stakeholder needs. These activities focused on optimizing particle packing

in compacts, generating finite-element meshes of the compacts from these particle locations, and finally

performing thermomechanical analyses on the compacts using the BISON fuel performance code [17].

 3. Constructive Solid Geometry Support

 The ultimate goal of this work in MOOSE is to create a generalized and automated process for creating

Monte Carlo (MC) Constructive Solid Geometry (CSG) definitions from MOOSE geometry input to sup-

port the reactor analysis needs in the reactor physics community. In FY24, work was done to investigate the

feasibility of adding generalized support for CSG model generation in MOOSE and subsequently create a

multi-year implementation plan [2]. The first phase of that implementation plan was carried out in FY26,

which was to develop a comprehensive CSG base framework in MOOSE that can be used by any mesh gen-

erator to implement the method(s) required to create a generic CSG representation for that mesh generator.

It is important to note that this work does not produce a CSG representation that is specific to any one MC

code, but rather a generic definition. The resulting generic definition can later be converted to code-specific

syntax through development of code-specific conversion methods, as noted in Section 3.7.

 3.1 Motivation

 Having tools and support for easily creating accurate MC models is a common request among the reactor

physics analysis community due to the complex nature of constructing CSG representations. For users of

MOOSE-based nuclear reactor analysis software, MC CSG models must be manually developed in order

to generate group cross sections (such as for deterministic neutronics analysis), create reference neutron-

ics results, perform multiphysics analysis with multiple analysis tools, and do code-to-code comparisons.

Manually creating these MC CSG models is a complex and tedious task that requires users to be familiar

with the syntax and complexities of a specific MC code and to understand how the CSG models are created.

Additionally, creating multiple geometry input representations (i.e., MOOSE and MC) for the same model

manually, especially for large complex models, is unnecessarily time consuming and can lead to inconsisten-

cies in the geometry definitions due to human-introduced errors that are difficult to identify. For users who

already use MOOSE-based workflows, the information required to generate any geometry representation of

a model is generally already available in the MOOSE input and can therefore be used to create any other

type of geometry representation given the right workflows and tools in place. For example, MOOSE uses

reporting IDs to represent collections of finite elements that define different regions, such as material zones,

pin type, axial zones, etc.. These IDs that are already available in MOOSE can be leveraged automatically

in the CSG model generation to assign CSG materials or other domain types (such as tally regions or deple-

 33

tion zones) to the different CSG spatial domains (also known as cells). Implementing an automated process

 3.2 Finite Element Mesh vs. Constructive Solid Geometry

 MC calculations are often used for reference solutions for finite element mesh codes because of their

”zero-space discretization errors.” In many MOOSE-based physics applications, the geometry representation

for the model at hand is a finite element mesh representation, meaning the surfaces or boundaries between

different spatial regions are discretized and represented as a collection of discretized mesh elements. For

example a circle or cylinder, such as is the geometry of a fuel pin, is not represented as a singular curved

surface but rather a collection of surface elements. Therefore, the accuracy of the finite element mesh

geometry representation can depend on the order, size, and form of these surface elements and granularity

of the discretization. On the other hand, CSG is a geometry representation in which models are created

through boolean combinations of surfaces, cells, and universes. Because the surfaces in CSG models are

analytically defined and combined using standard boolean operations, the boundaries of the spatial domains

in a CSG model are exact representations of those boundaries, requiring no discretization or approximations.

A comparison of the differences in these geometric representations is shown in Fig. 3.1 where a pincell is

defined as two concentric cylinders surrounded by a hexagonal region. The curved surfaces of the cylinders

must be discretized to use a collection of surface elements and the spatial region is discretized into the

discrete mesh elements. Conversely, the CSG representation of this same pincell geometry would be exactly

as is shown on the left in Fig. 3.1, with the cylindrical surfaces intact and the spatial regions whole.

Figure 3.1: An example of a pincell using a CSG representation on the left and an exaggerated coarse finite element
mesh representation on the right.

 34

 In order to maintain geometrical accuracy, the CSG models are generated using the mesh generator

input (i.e., the user input parameters), and not the finite element mesh that is generated by MOOSE by

default. In other words, the CSG model is both accurate and consistent in its geometric representation

compared to the user geometry input parameters, regardless of the mesh size used for the finite element

mesh representation. By creating the CSG representation directly from user geometry input rather than

from a discretized geometry representation, the MC simulations that will eventually use these models will

be efficient and reliable. Although it is theoretically possible to create a CSG representation directly from

a finite element mesh, it would require that each individual surface element on the boundary of a region

be represented as its own unique CSG surface, which would be extremely computationally inefficient and

prone to higher statistical uncertainty due to the sheer number of surfaces and resulting logic that would be

required to create and process such a model at run time.

 3.3 CSG Theory

 CSG models are most commonly used for MC neutronics simulations. While each MC code has its own

syntax for defining the CSG model, the underlying theory for creating CSG representations is common to

all MC codes. A CSG representation is defined minimally as a series of surfaces, cells, and universes, the

theory of which is presented in the following paragraphs.

 Surfaces are defined explicitly through surface equations (such as equations of a plane, sphere, etc.).

Each surface inherently separates two half-space regions: positive and negative half-spaces. For example,

for a plane with the equation ax + by + cz = d the positive half-space represents the region ax + by + cz > d,

while the negative half-space represents the region ax + by + cz < d. Similarly, for a spherical surface

defined by the equation x2 + y2 + z2 = r2 , the negative half-space represents the region x2 + y2 + z2 < r2

within the sphere, while the positive half-space represents the region x2 + y2 + z2 > r2 outside the sphere.

Example half-spaces are shown in Fig. 3.2.

 These half-space regions defined by the surfaces can be combined further as series of boolean operators

for unions, intersections, and complements to further define more complex regions. For example, if we

wanted to use the surfaces from Fig. 3.2 to define just the left hemisphere, we would define the cell region

as the intersection of the negative half-space of the plane and the negative half-space of the sphere as seen

in Fig. 3.3.

 Cells are defined by two main characteristics: a region and a fill. The region defines the spatial domain

 35

 Figure 3.2: Example depiction of the positive and negative half-spaces defined by a plane (left) and sphere (right).

 Figure 3.3: Example depiction of a closed region (yellow) defined by an intersection (&) of two half-spaces.

of the cell as shown above. The fill can typically be set as void (i.e., nothing), a material, a universe, or a

lattice (note: support for lattices in MOOSE is planned for future work).

 Universes can be defined as a collection of cells, which can then be used to either fill other cells, or

used repeatedly throughout a geometry (such as in a repeated lattice). By default, every model will have a

root universe that represents the entire domain. This universe is a single overarching universe that all other

universes can be traced back to through the tree defined by universes containing cells and cells filled with

universes.

 3.4 Framework Implementation

 This FY, a new base framework in MOOSE, CSGBase class, has been created and made available for

developers to implement CSG-generation methods in any MOOSE mesh generator. This class provides

developer tools to create generic CSG representations of mesh generators that can then be used by MC codes.

The CSG framework is located in the MOOSE framework (moose/framework/[src/include]/csg/) and

integrated into the MeshGenerator framework in order to leverage data and workflow management already

available for mesh generators. This section describes how this framework is to be used by future developers

and how it is invoked at the command line by users.

 36

3.4.1 Command Line Option to Invoke CSG-based Geometry Generation

 CSG geometry generation is invoked through the command line when calling MOOSE by specifying

the --csg-only flag as:

 /path/to/moose-opt -i mesh input file.i --csg-only [OUTPUT FILE.SON]

 This is analogous to the command for generating a MOOSE finite element mesh for the problem:

 /path/to/moose-opt -i mesh input file.i --mesh-only [OUTPUT FILE.e]

 The latter command generates an Exodus file that represents the finite element mesh without solving

the physics problem. The --csg-only command line argument instead generates an output JSON file

(explained in Section 3.4.2) that represents the CSG geometry without solving the physics problem. The

optional argument [OUTPUT FILE.son] specifies the name of the output JSON file. If this optional argument

is not provided, the default name [mesh input file] out csg.json is assigned to the output JSON file

name. This mirrors the behavior of --mesh-only mode, where a default Exodus output file name is assumed

if not provided by the user.

3.4.2 Integration with MOOSE Mesh Generator System

 This section discusses some of the lower-level implementation details when the --csg-only command

line argument is called. Under the hood, a new action CSGOnlyAction is called when this command line

argument is provided. CSGOnlyAction iterates through the list of mesh generator dependencies (already con-

structed by the MOOSE mesh generator system) based on the user input file, and calls the generateCSG()

function for each mesh generator provided in the input file. Once again, this generateCSG() function mir-

rors the analogous generate() function call that would typically happen in --mesh-only mode to generate

the finite element mesh for the particular mesh generator. More specifically, generateCSG() constructs the

surfaces, regions, cells, and universes from the available input parameters available for the particular mesh

generator. More details about these CSG components can be found in Section 3.4.3. In order for --csg-only

to work properly, every mesh generator that is within the input file needs to have a generateCSG() imple-

mentation defined.

 As was hinted in the previous paragraph, this newly added CSG functionality is built on top of the

existing mesh generator system defined within MOOSE. In this manner, much of the logic for finite element

mesh generation was able to be reused in order to support CSG-based geometry definitions. One other key

 37

pre-existing capability that was leveraged in the MOOSE mesh generator system is the concept of data driven

mesh generation, introduced to MOOSE in FY24 [2]. Originally, this feature was added as an optimization

to speed up creation of homogenized neutronics meshes defined from a heterogeneous mesh representation

in Reactor Geometry Mesh Builder (RGMB) [21] by bypassing mesh generation of the input heterogeneous

mesh altogether in favor of populating metadata to represent the input heterogeneous mesh instead. This

logic for bypassing the finite element mesh generation could be used for the CSG generation as well since

invoking --csg-only implies that a finite element mesh does not need to be generated. In this way, CSG-

based geometry definitions are constructed by completely bypassing any code routines that are responsible

for the construction of finite element meshes, saving a lot of runtime in the process. Instead, any data that

needs to be retrieved by the generateCSG() method is saved to metadata for future mesh generators in the

dependency tree to access.

3.4.3 CSGBase Components

 The framework for CSG-based geometry definition is implemented through the new CSGBase class,

which is the main class developers will interact with when implementing the generateCSG() method for

any mesh generator. This class acts as a container and driver for all methods necessary for creating a CSG

representation such as generating surfaces, cells, and universes of the mesh generator under consideration.

The generateCSG() method returns a unique pointer to the CSGBase object that was created or modified for

a particular mesh generator using the CSGBase class methods. This section describes the various components

of the CSGBase class framework that can be used when implementing the generateCSG() method for any

given mesh generator. In all examples in the following paragraphs, csg obj refers to the CSGBase object

that has already been initialized.

Surfaces Surfaces are used to define the spatial extent of the region of a CSGCell (see section “Cells”

below). This CSG framework provides the support to create any type of surface that can be explicitly defined

in some way. This new framework includes direct support for some basic surface types: planes, spheres,

and axis aligned cylinders. However, there are many different kinds of surfaces that could be necessary for

different types of mesh generators, and therefore the framework has been developed in a way to allow for

any custom surface definition to be defined in modules, other MOOSE apps, etc.. This flexibility allows

developers to define custom surfaces (e.g. a torus for fusion applications) that may be required for specific

 38

 physics applications, without modifying MOOSE’s main framework.

 To create a CSGSurface object, the surface constructor must be called directly to create a unique pointer.

 This pointer then has to be passed to the current CSGBase instance with addSurface which will then return

 a reference to that generated surface. The syntax to do this is shown in Listing 3-5, where SurfaceType is

 replaced with they specific type of surface being created (e.g., CSG::CSGPlane) and arguments refers to the

 surface-specific input required to define this surface (e.g., coefficients, points, etc.):

 All universes in a model should be able to be traced back, through the hierarchical tree of cells and uni-

 verses, to a singular overarching universe known as the root universe. Because universes are a collection of

 cells and cells can be filled with a universe, a tree of universes can be constructed such that the root universe

 is the collection of all cells in the model. When a CSGBase object is first initialized, a root CSGUniverse

 universe unless otherwise specified. The root universe exists by default, and which universe is set as the

 root cannot be changed, except when joining CSGBase objects, as described below in “Updating and Joining

 Existing Bases”. However, the name of the root universe can be updated and cells can be manually added or

 removed using the same methods noted above. Methods in CSGBase for managing the root universe include

 getRootUniverse() and renameRootUniverse().

 3.5 JSON Output

 Calling --csg-only at the command line (see Section 3.4.1) will produce a JSON file containing the

 complete generic CSG-based geometric description of the mesh generator input. There are three main

 sections in the file: SURFACES, CELLS, and UNIVERSES. Each item within these sections is keyed by its

 unique name identifier, and the value is the corresponding definition for that item.

 The SURFACES section contains the following information for each surface in the model:

 43

 • TYPE: the type of surface as defined by the class name that was used to create the surface

 • COEFFICIENTS: the values for each coefficient in the equation defining the surface type

For example, for a plane, the TYPE would be CSG::CSGPlane, and the COEFFICIENTS would be the values

of a, b, c, and d of the equation that defines the plane in the form ax + by + cz = d.

 The CELLS section contains the following information for each cell defined in the model:

 • REGION: the string representation of the equation of boolean operators and unique surface names that

 defines the cell region

 • FILLTYPE: type of fill in the cell ("VOID", "CSG MATERIAL", or "UNIVERSE")

 • FILL: for material or universe FILLTYPE, this is the unique name of the fill

 Examples of the JSON output can be seen in Listing 3-14 in Section 3.6.

 3.7 Future Work and Stakeholder Engagement

 The full implementation of CSG support in MOOSE will require additional effort and an expanded

 group of developers. The implementation plan originally developed in FY24 is repeated here in Table 3.2

 for convenience [2]. The work presented in this document largely completes Task 1, with some outstanding

 features, which are elaborated on below. Task 2 has been started with the preliminary implementation of

 generateCSG() for RGMB’s PinMeshGenerator (see Section 3.6), which as of date of publication of this

 report is not yet in the main MOOSE repository.

 49

Figure 3.5: Representation of PinMeshGenerator demonstration example as a CSG geometry from the output JSON
file shown in Listing 3-14, plotted as an XY slice (left) and YZ slice (right).

 Regarding the outstanding parts of Task 1, some key components in the CSGBase framework still need to

be implemented including support for lattices, macros or convenience functions, and arbitrary engineering

units. The framework for defining repeated lattices is crucial for RGMB mesh generators and other patterned

mesh generators that create regular reactor lattices. Lattices are a pattern of repeated cells and universes and

is considered a key component in MC codes that allow for efficient particle tracking at runtime on regular

or patterned reactor geometries.

 Additionally, there is the desire to support some common macros or convenience methods (e.g., a single

method to define a rectangular prism rather than four distinct planes). Providing some basic macros and

generalized geometric convenience functions will be low effort and greatly ease future developers’ burden

by not having to implement common logic manually in various generateCSG() implementations.

 Finally, the support for arbitrary engineering units will be crucial for downstream code-specific con-

versions. Arbitrary engineering units refers to being able to define a “unit” or “component” in familiar

human-readable domain-specific language which can then be processed by an MC code into the necessary

low-level CSG definition. An example of this is defining a “pincell” by the user providing a list of radii and

list of material IDs, which is then automatically processed by a code into the necessary cylindrical surfaces,

regions, and cells to create that pincell universe in CSG form. Engineering units, such as a pincell, will be a

key component to be able to support the connection between Shift’s Titan interface [22], which is a front-end

to the Shift MC code that is based on users defining engineering units for reactor definitions, and other MC

codes. The RGMB mesh generators, which are the MOOSE-equivalent of reactor-specific engineering units,

 50

would benefit from these as well and simplify the connection to specific MC codes in the future (Task 4 in

Table 3.2). Because engineering units are domain-specific, it does not make sense to implement support for

any domain-specific engineering units in the CSGBase framework, but rather create the common framework

such that specific engineering units can be defined in modules or other MOOSE-based applications, much

like has been done for CSGSurfaces to allow for any arbitrary surface type (see Section 3.4.3).

 The support for lattices will be implemented in early FY26, followed by added support for macros,

and engineering units, which will complete Task 1 in Table 3.2. Following the completion of the lattice

implementation, the generateCSG() methods for each of the remaining mesh generators in RGMB will be

implemented, thus completing Task 2.

 With the completion of at least the PinMeshGenerator implementation from Task 2, we will be able to

engage with the Shift and Titan MC development teams to advise on the code-specific conversions methods

that they will implement as a part of Task 4. As a reminder, the generateCSG() methods produce generic

CSG definitions and are not code-specific, meaning that additional development will be required to convert

the generic definition into code-specific syntax. The intention is that these code-specific conversion methods

be implemented once per MC code or input syntax as the final step in this automated connection between

MOOSE and specific MC codes.

 Additionally, engagement with relevant stakeholders will determine how to best support material defi-

nitions or other spatial domain characteristics (such as tally regions, depletion zones, etc.), as well as which

stakeholder will be responsible for implementing such support (Task 5 in Table 3.2). Currently, basic sup-

port for material-filled cells is implemented in the framework (see “Cells” in Section 3.4.3) but is only a

placeholder using a string for a material name (this can be a region ID in MOOSE), with no actual material

definition attached. Defining the scope of material definition support for MC codes within this framework

is yet to be determined.

 4. NEAMS Workbench

 Recent updates to the NEAMS Workbench, WASP, and the MOOSE language server have introduced

several improvements aimed at making MOOSE-based simulation setup and input management faster, more

accurate, and easier to use. Key capabilities that have been added include the following:

 • Multi-tab-stop autocompletion: As an extension of prior snippets support [23], input autocomple-

 tion now guides users through required fields using tab-based navigation, reducing input entry time

 and errors.

 • Visual input diagnostics: Users can now plot input functions and tabular data (e.g., Piecewise

 functions, CSV files) before execution from within the NEAMS Workbench, helping to catch issues

 like discontinuities or unexpected values early.

 • Developer-directed data visualizations: A new plotting backend (waspplot) gives developers con-

 trol over how data inputs are best communicated to users through plots.

 • Upgraded ParaView integration: The NEAMS Workbench includes ParaView 5.13, improving

 mesh interaction performance and enabling future compatibility with deeper integration.

 • Workspace-level file tracking: Support for dynamic file watchers and relative pattern matching al-

 lows real-time detection of file changes across multi-file inputs. This helps users stay informed when

 one file affects another and improves input validation accuracy.

 Together, these changes make it easier for users to build, validate, and manage complex MOOSE-based

simulation models — especially those involving reusable components, included files, and datasets. The

improvements are designed to save time, reduce input errors, and help users get to a successful simulation

run faster, with more confidence in the results. In FY26, plans include integration of the MOOSE stochastic

tools module and further extending visual input diagnostics.

 4.1 Support for Multiple Tab Stop Snippets

 In the Language Server Protocol (LSP), snippets allow application developers to specify their applica-

tion’s input autocompletion to have sequential tab cursor movement. By annotating the input component

 53

 with tab stops ($1, $2, $0, etc.), the user’s text editor knows how to manage the tabbing through the entry

 fields. This enables a user to TAB and SHIFT+TAB to quickly move through fields for which the application

 developer needs data to be entered. The MooseServer was updated to provide a snippet tab stop for each

 required field included in the input completion request.

 For example, the TransfiniteMeshGenerator block has required parameters bottom type, corners,

 left type, nx, ny, right type, and top type. When a user requests that TransfiniteMeshGenerator be

 completed in their input, the MooseServer constructs the input snippet with tab stops at the value position

 of each required field, as illustrated in Listing 4-15.

 Note, the user’s text editor does not display the tab stop syntax. The $0 on line 12 is a special tab stop

 In summary, support for multiple tab stops allows users to streamline their data entry by navigating

 through key fields quickly without manually moving the text cursor. This, combined with subsequent

 autocompletion requests, reduces cognitive load by helping users know exactly where to enter context-

 specific values. This results in fewer errors and accelerates the input editing workflow for all parts of the

 MooseServer input where multiple required fields exist.

 4.2 Visual Verification of Input Functions

 Recent enhancements to the MOOSE framework provide support for a new plotting protocol extension

within the MooseServer. This extension enables the NEAMS Workbench to issue requests for the genera-

tion of plots representing user-defined input data, particularly Piecewise functions and externally supplied

datasets (e.g., CSV files), prior to simulation execution.

 The MooseServer utilizes a LSP extension to facilitate communication between the Workbench client

and the MooseServer, returning instances of waspplot::CustomPlot objects. These objects support the

rendering of bar charts, color maps, and line graphs, with optional support for error bars.

 This capability directly supports visual verification of the input data for the simulation. By allowing

users to visually inspect input functions, this enhancement provides an intuitive mechanism for identifying

specification errors, unexpected discontinuities, or incorrect value ranges. These kinds of issues are often

difficult to identify through textual inspection alone, but can lead to significant problems at run-time.

 Incorrect or malformed input data is a frequent cause of downstream simulation failures. For exam-

ple, discontinuities or nonphysical gradients in a Piecewise function representing a material property may

introduce localized numerical instabilities that lead to non-convergent nonlinear solves. By supporting pre-

simulation visual diagnostics, the new protocol extension mitigates these risks by allowing users to identify

and correct such issues early in the workflow.

 Notably, this enhancement does not affect the behavior of the MooseServer in environments like VS

Code, as such clients currently do not implement the LSP extension required to activate this functionality.

This design choice ensures backward compatibility while selectively enhancing the capabilities available

within the NEAMS Workbench.

 Visualization of an input function is performed in the NEAMS Workbench by right-clicking within the

function block and selecting Plot data in the presented context menu, as illustrated in Figure 4.1.

4.2.1 Graphical Capabilities in waspplot for Developer-Directed Data Presentation

 The waspplot module provides a structured and extensible framework for defining 2D graphical visu-

alizations of scientific data. Through a rich set of graphical primitives and style enumerations, waspplot

enables developers to construct visual representations that are both semantically meaningful and visually

tailored to the data being conveyed.

4.2.2 Graphical Primitives

 The core building blocks of waspplot are a set of graphical primitives designed to define how plots are

rendered. These include:

 • Color: Supports full RGBA (red, green, blue, alpha) specification, enabling both precise color control

 56

 and transparency effects.

 • Font: Allows customization of font family, point size, and typographic styling. Supported styles

 include bold, italic, underline, and strikeout, offering flexibility for axis labels, legends, and annota-

 tions.

 • Brush: Used to define fill properties for graphical elements (e.g., bars, areas, background). A Brush

 object combines a fill color with a pattern style governed by the BrushStyle enumeration.

 • Pen: Specifies the appearance of lines and outlines, including stroke color, line width, dash pattern,

 cap shape, and segment joins. Pen behavior is configured using associated enumerations such as

 PenStyle, PenCapStyle, and PenJoinStyle.

4.2.3 Style Enumerations

 The waspplot package defines several enumerated types that govern the appearance and interpretation

of plotted elements:

 • BrushStyle: Specifies fill patterns, such as solid, dense, or various hatchings (e.g., crosshatch).

 • PenStyle: Controls the visual pattern of stroke lines — solid, dashed, dotted, etc.

 • PenCapStyle and PenJoinStyle: Determine the rendering of line ends and junctions.

 • LineStyle: Defines how data curves are rendered — continuous lines, stepped plots, or impulse

 graphs.

 • ScatterShape: Specifies the geometric shape used to represent discrete data points, such as circles,

 squares, or custom symbols.

 • ScaleType: Indicates axis scaling behavior, supporting linear and logarithmic modes.

 • LabelType: Dictates the formatting of axis tick labels, including numeric and date/time options for

 temporal data visualization.

 • ErrorType: Configures the style and direction of error bars, enabling visualization of uncertainty or

 statistical variability.

 57

 • GradientPreset: Provides named color map presets for use in color-mapped data such as heatmaps

 or colormaps.

4.2.4 Implications for Developer Workflow

 By leveraging these constructs, developers can design plot outputs that are accurately aligned with the

semantics of the underlying simulation data. These capabilities position waspplot as a core tool for building

interactive, data-driven visualization experiences within the NEAMS Workbench modeling workflows.

4.2.5 Summary of Visual Verification Improvements

 The addition of this plotting extension improves the robustness, transparency, and efficiency of the

MOOSE-based simulation workflow. It empowers developers to definitively present input data. It facilitates

the rapid visual verification of user-defined input data, promotes early error detection, and contributes to

overall model correctness and stability.

 4.4 Workspaces

 MOOSE-based simulations commonly span multiple interdependent files: a primary application input

file, data sources such as meshes and CSV files, and — in increasingly common cases — modular sub-

files included via include directives as introduced in 2022 [26]. This structure enables powerful reuse

and separation of concerns, especially in advanced workflows involving MultiApps, parameter libraries, or

postprocessors. However, this modularity introduces a key challenge: it can be difficult for users to know

the state of their simulation files, and to detect when changes in one file affect the validity or behavior of

others.

 For instance, modifying an included file that defines material properties or boundary conditions may

silently affect application behavior unless users remember to recheck the input hierarchy. Similarly, remov-

ing or renaming a referenced file can result in broken dependencies that may only be caught during exe-

cution. As simulation configurations grow more complex and collaborative, such inter-file issues become

more frequent and harder to trace. In a GUI (e.g., NEAMS Workbench or VS Code) an edit of the top-most

application was required before comprehensive diagnostics were presented for a user’s understanding.

 To address these challenges, recent updates to the NEAMS Workbench, WASP, and the MOOSE lan-

guage server have integrated support for workspace-level capabilities defined by the LSP. This includes

 59

dynamic registration of file watchers as well as real-time propagation of file change notifications via the

workspace/didChangeWatchedFiles mechanism.

4.4.1 Dynamic File Watchers

 Support for dynamicRegistration allows the MooseServer to request that the client (e.g., NEAMS

Workbench or VS Code) observe specific files — such as included MOOSE input files, meshes, or referenced

data files. This enables the client to watch the files the user may interact with and notify the MooseServer

when a reprocessing of relevant file is needed and subsequently publish any noteworthy diagnostics back to

the client for presentation to the user.

 For example, when a user edits a CSV file that defines temperature-dependent material properties, any

input files that reference those properties are automatically revalidated. This ensures that errors resulting

from format issues, value mismatches, or missing data are caught immediately, mitigating, if not preventing,

the user from wasting time attempting to execute a MOOSE-based simulation that would ultimately end in

failure.

4.4.2 Relative Pattern Support

 The addition of relativePatternSupport further enables the language server to specify scoped file-

watching rules. Rather than watching the entire workspace indiscriminately, the server can monitor specific

files. This improves performance and ensures that diagnostics focus only on relevant files.

4.4.3 Real-Time Inter-File Awareness

 With the combination of these capabilities, the NEAMS Workbench and VS Code can now track how

changes in one file affect others in real time. Key improvements include:

 • Automatic revalidation of parent input files when included sub-files are modified.

 • Automatic propagation of mesh or data file changes into relevant diagnostics for expedited resolution.

 • Automatic refresh of input assistance features like autocomplete, goto-definition, and find references.

 This inter-file awareness is particularly valuable in configurations that use MOOSE’sinclude directive

to modularize complex input files. Users can now make updates to shared components with confidence that

all downstream dependencies will be rechecked automatically.

 60

 In summary, the enhanced workspace features in NEAMS Workbench, WASP, and the MOOSE lan-

guage server provide robust support for complex simulation environments. By adopting advanced LSP

mechanisms for file monitoring and inter-file coordination, the system empowers users to work more effec-

tively and confidently with modular, multi-file MOOSE inputs.

 5. Conclusion

 The updates to MOOSE’s intrinsic meshing capabilities assist with complex mesh generation, partic-

ularly for non-extruded 3D geometries. The capabilities this year assist with generation of the meshed

surfaces required as input for tetrahedral meshing, applying transition layers in 3D to reduce total element

count, generalized triangulation with application to curved surfaces, and 1D spline generation and subse-

quent extrusion along the curve. These improvements collectively aid the user in meshing complex geome-

tries such as molten salt reactor primary loops, TRISO fuel compacts, and other uniquely shaped fuel or

component regions. Batch mesh generation has also been added to streamline the input structure of repeated

mesh generator objects, useful in repeated lattice calculations. Additionally, a hands-on user workshop was

held in spring 2025 which demonstrated the latest tool capability and utilized the NEAMS Workbench for

hands-on examples.

 Additionally, a major capability was delivered this year on the path to delivering a CSG model option in

MOOSE to better CSG-based Monte Carlo workflows into MOOSE multiphysics calculations. At the time

of this report, the base framework that supports defining CSG representations is under final review as a pull

request in MOOSE and will be available after it is merged for developers to begin adding CSG generation

options in various mesh generators, which is the next stage of this work. The final stage of this workflow

support will see reactor physics application developers take these CSG representations and modify them for

suitability to specific codes like Shift or OpenMC.

 The updates to NEAMS Workbench, WASP, and the MOOSE language server make working with com-

plex MOOSE-based input files more efficient and less error-prone. With support for features like multi-tab-

stop autocompletion and visual previews of function data, users get better feedback during setup to help

avoid common input errors before running a simulation.

 The waspplot system gives developers tools to present input data using plots while removing error-

prone variability of user postprocessing and interpretation. The ParaView upgrade brings mesh visualization

in line with newer systems and adds flexibility for future meshing workflows. File tracking improvements

allow users to catch issues across included files and data sources without needing to manually instigate a

revalidation in a controlling input.

 Together, these changes make the NEAMS Workbench and MOOSE simulation environment more re-

sponsive and helpful, especially for users working with modular, multi-file inputs. The result is a more robust

modeling workflow with fewer surprises and a smoother path from input creation to successful simulation.
