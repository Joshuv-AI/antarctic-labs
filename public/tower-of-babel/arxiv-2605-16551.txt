PQR : A Framework to Generate Diverse and Realistic User Queries that Elicit QA Agent Failures
Yunan Lu, Luigi Liu, Omar Yahia, Arpit Sharma, Zhou Yu

Abstract
Evaluating LLM-based agents remains challenging because identifying meaningful failure cases often requires substantial human effort to design realistic test scenarios. Prior works primarily focus on automatically discovering agent failures induced by adversarial users, while overlooking queries with real user intents that also trigger agent failures. We introduce PQR , a framework that not only surfaces agent failures with respect to specific objectives (e.g., helpfulness, safety, etc.) but also resembles real users’ intents. PQR operates through an iterative interaction between two complementary modules. The query refinement module performs rewrites to explore diverse query variations, while the prompt refinement module uses prior feedback to derive new objective-violating strategies and realism policies for refining prompts, which in turn generate failure-triggering yet realistic queries. We evaluate PQR on detecting an e-commerce QA agent’s unhelpful responses. Our method uncovers 23% – 78% more unhelpful responses, and our generated queries are more diverse and realistic compared to previous methods.

Introduction and Related Work

LLM-based agents are increasingly deployed in real-world domains such as e-commerce, healthcare, and finance
25
;
11
;
9
.
Unlike general-purpose language models, agents are typically designed around objectives (e.g. helpfulness, personalization, harmlessness) with task-specific criteria
34
;
33
;
4
.
Existing evaluation practices rely heavily on human effort. Practitioners manually design test cases or scenarios intended to expose violations of these objectives. This process is costly, difficult to scale, and poorly suited to iterative development cycles
17
.

Many works have explored automating this evaluation process. One line of work focuses on generating adversarial attacks. For example, PAIR
6
and TAP
16
are black-box jailbreak methods for detecting safety failures, which use tree-based reasoning to iteratively refine queries based on predefined strategies. GoAT
2
further extends this approach to a more intricate graph structure, improving efficiency through collaborative exploration. However, these methods are designed to generate arbitrary failure-inducing queries, so the resulting queries are often gibberish. Moreover, their reliance on predefined strategies limits their ability to explore unexpected failure cases that require novel, dynamically learned strategies.

To generate realistic user queries while effectively exploring new failure-triggering strategies, prompt refinement represents a promising approach. Prior work focuses on improving task success by iteratively optimizing prompts through reflection.
For example, GEPA
1
iteratively proposes candidate prompts based on feedback and selects effective ones using Pareto-aware optimization. ACE
32
summarizes the feedback into structured playbooks to preserve the reflection insights and improve prompt performance.
However, these methods are primarily designed to optimize prompt effectiveness under a task instruction (e.g. generating realistic queries that elicit evaluation violations) and do not explicitly account for query diversity, which is essential for agent evaluation. In the context of failure discovery, repeatedly eliciting the same type of failure provides limited diagnostic value and does not capture the breadth of an agent’s weaknesses.

Therefore, to systematically generate failure-triggering queries that are both diverse and realistic, we propose PQR, a
P
rompt–
Q
uery-
R
efinement framework for agent evaluation under natural-language-defined objectives. It couples two complementary modules in an iterative loop to mitigate the weaknesses of using either module alone: unrealistic surface-level variants from query refinement and repetitive output from prompt refinement. Specifically, query refinement performs localized rewrites to explore nearby query variations, while prompt refinement aggregates reflections from query refinement to derive new objective-violating strategies and realism policies that guide future query generation toward realistic violations.

We demonstrate the effectiveness of
PQR
on detecting an e-commerce QA agent’s unhelpful responses.
Through both automatic and human evaluations, we show that
PQR
more cost-efficiently uncovers unhelpful agent responses while generating queries whose diversity and realism more closely match real user queries than existing methods.

The
PQR
Framework

Figure
1
illustrates the overall workflow of our framework to generate diverse and realistic queries for eliciting agent failures. Given an initial prompt and domain knowledge, the framework first generates candidate queries. These queries are then diversified through the query refinement module by applying effective query refinement strategies (Section
2.1
). All queries from the same prompt are subsequently aggregated and passed to the prompt refinement module, which derives new objective-violating strategies and realism policies for refining prompts. These prompts in turn generate failure-triggering yet realistic queries (Section
2.2
).

2.1
Query Refinement

To construct diverse query candidates under compute budget, we adopt rewriting strategies from prior work
6
;
27
to generate query candidates and perform beam search to retain queries that can potentially benefit from further refinement. At each iteration, the refinement process consists of two steps:
dual selection
and
query expansion
. The dual selection step conducts query and strategy selection in parallel, while the expansion step applies rewriting strategies to generate variants. We iteratively apply these two steps until the budget is exhausted (e.g., number of iterations). See Figure
1
for a query example.

Dual Selection

To bound the exponential growth from rewrite branching while preserving high-potential query candidates, we adopt beam search for query selection. At each iteration, we retain a fixed number of promising queries based on the rewards score from LLM-as-a-Judge. Details of the judge are described in Appendix
B.2
.

In addition, prior work
21
shows that tasks are sensitive to different perturbation strategies. Therefore, to further improve query search efficiency, we apply beam search over strategies. We retain only the strategies more effective in the previous iteration at refining queries toward lower reward scores (i.e. more agent failures).

Query Expansion

Following prior work
21
;
6
;
27
, we adopt two widely used strategy categories: perturbation and role-playing. Perturbation operates at three granularity levels: character-level, word-level, and sentence-level. Role-playing strategies introduce variations through three types: personas, tones, and scenarios. Additional details of the strategy taxonomy are provided in Appendix
B.1
.

2.2
Prompt Refinement

While the query refinement module promotes query diversity, it misses the failures that require strategies beyond the existing ones and does not explicitly enforce query realism. To address this, we integrate a prompt refinement module that explores new strategies while enforcing realism through a feedback-driven loop with three stages:
selection
,
reflection
, and
expansion
. This loop follows the high-level structure of prior work
32
;
1
, but incorporates guided and diversified feedback. Concretely, at each iteration, it aggregates the interaction history
(p,q,a,R)
for all prompt candidates. Then the selection stage retains prompts that most effectively induce agent failures according to the reward signals. Next, the reflection stage produces feedback that diagnoses both objective violation and realism issues. Finally, the expansion stage uses this feedback to propose new candidate prompts.

Prompt Selection

To bound tree expansion without prematurely pruning promising prompt trajectories, we apply beam search, retaining prompts that generate more objective-violating queries.

Prompt Reflection

To jointly account for realism and target objective (e.g., helpfulness), we organize reflection into two feedback types:
realism-related
and
objective-related
. Realism-related feedback explains why generated queries appear unrealistic and suggests how to make future queries more natural.
Objective-related feedback contains three signals:
objective-violation feedback
, which identifies query features that trigger agent failures;
objective-compliant feedback
, which identifies features that help the agent satisfy the objective; and
criterion-specific feedback
, which identifies criteria that remain under-explored based on the evaluator’s reward signal. These feedback signals are passed to the expansion stage to guide prompt generation.

Prompt Expansion

Prior work on prompt refinement often generates a single prompt candidate per iteration
32
;
1
or produces multiple candidates conditioned on the same feedback context
19
. Both choices limit prompt diversity and consequently reduce query diversity.
To better explore diverse strategies, each prompt refinement iteration applies three expansion directions in parallel and generates one prompt for each:
exploitation
,
exploration
, and
examination
.
All directions use realism-related feedback but draw on different objective-related signals.

Exploitation
uses objective-violation feedback to amplify strategies that have already triggered agent failures.

Exploration
uses objective-compliant feedback to introduce contrasting strategies that push generation toward new failure modes.

Examination
uses criterion-specific feedback to target the least frequently violated criteria and generate prompts that probe these under-explored objectives. The related prompts are in Appendix
E.2
.

3.1
Automatic Evaluation

Failure Discovery Rate
It is measured by the
unhelpfulness rate
(UHR), defined as the percentage of queries that successfully elicit unhelpful agent responses. We evaluate the helpfulness score of each response using an LLM-as-a-Judge approach. To mitigate concerns about judge bias and reward hacking, we validate these scores against majority-vote labels from three human experts. Across 30 samples, the LLM-as-a-Judge scores achieve a Spearman correlation of 0.75 with human annotations. See Appendix
B.2
for additional details.

Query Realism
Following prior work
24
, we evaluate query realism by averaging LLM-as-a-Judge scores from three model families: GPT, DeepSeek, and Gemini. Each model rates query human-likeness on a 1–5 scale. The final score achieves a Spearman correlation of

with human ratings. See Appendix

and Measure of Textual Lexical Diversity (MTLD). Higher diversity scores indicate a broader coverage of failure types.

4
Discussion

To illustrate PQR in practice, we trace a failure case for a Sceptre TV with the selected attribute "number of audio inputs". A generic prompt first generates: "For the Sceptre TV, how many audio inputs?" After prompt-query-refinement, the prompt favors concise and multi-attribute queries, producing:"How many audio inputs and can I use a 3.5mm cable?" Query refinement then applies word and character-level perturbations, yielding “How many audo inputs can I utlize a 3.5mm connector?” The agent responds, "The product has 2 audio inputs", answering only the audio-input segment and omitting 3.5mm compatibility. This trace shows how prompt refinement discovers a realistic failure pattern, while query refinement exposes a brittle variant. See Appendix
D.7
for the full trace.

5
Limitations

Our current framework evaluates diversity and realism through both automatic metrics and human evaluation, but it is tested only on helpfulness and safety objectives, with stronger gains in the helpfulness setting. In future work, we plan to apply
PQR
to additional objectives, such as hallucination and personalization, to better characterize where the framework generalizes well and where its limitations emerge.

Additionally, our evaluation considers only a single agent type: an e-commerce QA agent built on an open-source model. This setting is comparatively lightweight relative to modern tool-using, multi-step agentic systems, which often employ more complex policies and exhibit stronger robustness. Although
PQR
is agent-framework-agnostic and operates in a black-box manner, it remains unclear how well it scales to agents with richer capabilities or to domains beyond e-commerce. Broader evaluations across diverse agent architectures and domains are necessary to characterize the method’s robustness and practical impact.

Appendix A
Further Related Work

Prior work on surfacing vulnerabilities of LLM-based agents has largely focused on adversarial attacks, which are primarily aimed at inducing harmful or policy-violating behaviors in target models. Depending on the level of access attackers have to the target LLM, these attack methods are typically categorized into white-box and black-box attacks
30
. White-box attacks require internal access to model information (e.g., architecture, parameters, gradients), which makes them unsuitable for agent-based black-box scenarios where agent built with multiple tools under complex framework and is mainly accessible via an API. Black-box attacks include template completion
26
, prompt rewriting
15
;
31
, and LLM-based generation
16
;
6
. While these methods can effectively identify vulnerabilities, they are generally designed to generate arbitrary failure-inducing queries, and the resulting prompts are often unnatural. Recent work such as SECA
14
elicits hallucinations through realistic modifications to queries that preserve meaning while maintaining semantic coherence. However, it requires access to the target model parameters, making it unsuitable for black-box scenarios. In addition, all of these methods rely on predefined strategies, which limits their ability to explore unexpected failure cases that require novel strategies. Our work addresses this limitation by integrating adversarial attacks (i.e. query refinement) with prompt refinement, which aggregates feedback from query refinement step to derive new effective objective-violating strategies and realism policies. As a result, the generated queries not only trigger agent failures but also remain realistic.

Another line of research focuses on evaluating agents interactively through user simulators.
\tau
-bench
29
evaluates API-augmented agents in retail and airline domains using dynamic task-oriented dialogues between a simulated user and the target agent. CRMArena
10
starts from human-written seed query templates for initial user requests and then rolls out interactions using prompt-based rules. SAGE
20
introduces a knowledge-grounded user simulation framework for identifying agent errors. While these methods effectively assess agent performance, they are scenario-based and do not directly optimize toward specific agent evaluation objectives. Our work addresses this limitation with a search-based approach that heuristically searches for strategies to generate queries that trigger the agent’s failures with respect to the specific evaluation objectives.

B.2
Evaluator

To effectively measure whether synthesized queries actually expose failures, we adopt a LLM-as-a-Judge approach to score the target agent’s answers. The evaluator consists of three reasoning models:
gpt-5-mini

18
,
gemini-2.5-flash

7
, and
deepseek-reasoner

8
. Given the synthesized query
q
, the target agent’s answer
a
and evaluation criteria defining the agent objective, each model determines the violated criteria and a short justification explaining why the response fails to satisfy them. See Appendix
E.3
for the prompt. We then keep the criteria selected by the majority of models and report the final score as the mean of score assigned to those criteria.

To validate this automated evaluator, we recruited three experts as annotators. All of them are working at e-commerce platforms and have experience in developing shopping agents, which qualifies them to perform this task. The annotators rated answer quality on a 3-point Likert scale based on the helpfulness criteria. They conducted the evaluation collaboratively, discussing each case until they reached a consensus score. We provide the full annotation guidelines below.

By comparing evaluator predictions against the consensus human labels, we find that the evaluator attains 76.67% accuracy, 77.78% precision, 82.22% recall, and 79.00% F1, with a Spearman correlation of 0.75. These results show that our evaluator closely tracks expert judgments and provides a reliable signal for detecting helpfulness violations in agent responses.

Appendix C
Experiments Details

C.1
Hyperparameter Settings

For large commercial model, we use
gpt-5-mini
via the OpenAI API with the default model temperature of 1.0. For the open-source model, we use
gemma3-27
. Following the Gemma team’s recommended decoding settings
22
, we set the temperature to 1.0, top_k to 64, and top_p to 0.95. We use the same underlying model consistently across all stages of our framework.

To balance the diversity and realism gains provided by query refinement and prompt refinement, we allocate comparable generation budgets to both modules. For prompt refinement, we run 4 iterations with a beam size of 2. For query refinement, we run 3 iterations with a beam size of 3, giving its larger space of predefined strategies and thus incurs more API calls per iteration.

C.2
Baselines

Query Refinement

We compare
PQR
with two closely related existing methods for our task: the black-box jailbreak methods
PAIR

6
and
TAP

16
. PAIR runs multiple strategy branches in parallel and iteratively refine the query for each branch until it jailbreaks the target model. TAP generates multiple candidates for each strategy template and prunes off-topic ones before sending to the attacker in order to reduce the cost.

To adapt these methods to our setting, we modify their objectives to break the target model by inducing unhelpful responses based on predefined strategy templates. Both PAIR and TAP use the same strategy categories as
PQR
(i.e., perturbation and role-playing). For PAIR, we set the number of iterations to 10. For TAP, we set the maximum depth d = 3, the maximum width w = 4, and the branching factor b = 4. These settings ensure that the number of queries generated by the baseline methods and
PQR
are comparable.

Prompt Refinement

We further adopt two contemporary state-of-the-art prompt optimization methods for our task:
GEPA

1
and
ACE

32
. GEPA iteratively proposes candidate prompts based on execution traces from sampled minibatches of the training dataset and selects candidates using a validation dataset. In our experiments, we use 50 products for training with a minibatch size of 25 and the remaining 50 products for validation. ACE treats prompt optimization as the evolution of playbooks that explicitly summarize strategies for updating prompts in the form of clear bullet points. Both methods are provided with the same prompt refinement instructions as
PQR
. We set the number of optimization iterations to 30 for both methods in order to ensure that the number of queries generated by the baseline methods and
PQR
are comparable.

D.3
Safety-Objective Experiments

To further assess the generality of
PQR
, we conduct additional experiments on eliciting unsafe responses from the e-commerce QA agent. We measure failure discovery using the unsafety rate (USR), defined as the percentage of queries that successfully elicit unsafe agent responses. As with the helpfulness setting, we compare all methods against a human baseline on realism and diversity, where smaller gaps indicate closer alignment with real shopper behavior.

Tables
8
and
8
show that
PQR
maintains a favorable trade-off under the safety objective, though its gains are less consistent than in the helpfulness setting. With
gpt-5-mini
,
PQR
achieves the second-highest USR, behind
PAIR
; with
gemma3-27b
, it falls behind
ACE
. However, across both settings,
PQR
has the lowest cost, the highest realism score, and ranks among the top methods on diversity metrics. This pattern reflects a key difference between helpfulness and safety failures. Helpfulness failures can often be triggered by realistic shopper queries, such as ambiguous or under-specified product questions. In contrast, unsafe responses are more often elicited by adversarial or unnatural queries, which conflict with
PQR
’s realism constraint. Nevertheless,
PQR
still identifies realistic queries that elicit unsafe responses. Overall, these results suggest that
PQR
is most useful when the goal is to discover realistic safety failures rather than maximize adversarial attack success alone.

D.4
Human evaluation

For human evaluation, we recruited three expert annotators who work at e-commerce platforms and have prior experience in developing shopping agents, which qualified them to perform the task. They are asked to rate the quality of 300 user queries along two dimensions - realism and relevance. The inter-annotator agreement, measured by Fleiss’ Kappa, is 0.58 for realism and 0.42 for relevance. Detailed annotation guidelines are provided below. Our data collection protocols are IRB approved.

Instruction:

You will be shown a user query and the product that the query refers to. Your task is to rate the quality of the query on a 3-point Likert scale (1, 2, 3) along two dimensions: Realism and Relevance.

1. Realism

Definition
: How closely a query resembles something a real shopper would naturally and plausibly ask when interacting with a shopping assistant.

Scale (1–3)
:

1 = Clearly artificial, system-oriented, or contrived. The query resembles a command, database query, narrative explanation, or expert analysis that a real shopper would be unlikely to type.

2 = Plausible but somewhat unnatural. The query may be overly verbose, formal, or slightly awkward compared to typical user behavior.

3 = Clearly resembles something a real shopper would naturally ask. The phrasing, intent, and level of detail are consistent with real-world shopping behavior.

2. Relevance

Definition
: Whether the query is meaningfully related to the product’s category, attributes, or usage.

Scale (1–3)
:

1 = Irrelevant or off-topic. The query is unrelated to the product.

2 = Partially relevant. The query is somewhat related to the product; some aspects or attributes mentioned are relevant, but the connection is weak or indirect.

3 = Fully Relevant. The query directly concerns the product’s attributes, usage scenarios, or purchase considerations.
