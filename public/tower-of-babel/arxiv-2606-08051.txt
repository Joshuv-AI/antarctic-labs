How Small Can You Go? LoRA Fine-Tuning 270M–8B Models for Merchant Information Extraction in Financial Transactions *Corresponding author: zxwang@smu.edu.sg
Donghao Huang 1,3 , Tomáš Drietomský 2 , Benjamin Barrett 1 , Zhaoxia Wang 3,*

Abstract
Financial transaction processing requires extracting structured merchant information from noisy, abbreviated bank transaction strings at scale. Our current production system, a LoRA-fine-tuned LLaMA 3.1-8B, achieves 96.95% F1 on this task, but deploying 8-billion-parameter models imposes prohibitive memory, latency, and cost constraints. To identify more efficient alternatives, we conduct a deployment-focused study of 24 model variants spanning four model families: Gemma 3 (270M, 1B, 4B), Qwen 3.5 (0.8B, 2B, 4B), Aya (3.35B), and LLaMA 3.1-8B— systematically evaluating accuracy, inference throughput, training cost, and hardware behavior to assess production suitability. Our findings show that: (1) reproducing the LLaMA 3.1-8B fine-tune with a LoRA rank of 8 achieves 96.75% F1, only 0.20 points below the rank-32 baseline; (2) Qwen 3.5 4B with JSON-only prompting reaches 96.60% F1, within 0.35 points of the 8B baseline while using roughly half the parameters; (3) the 0.8B Qwen 3.5 model achieves 94.75% F1, matching models 2.5–4× larger and offering an attractive latency–accuracy trade-off; (4) chain-of-thought fine-tuning generally improves F1 by 0.3-1.8 points across most models, although Qwen 3.5 4B performs best with direct JSON-only prompting; and (5) Qwen 3.5 Think and Nothink training templates produce nearly identical results (F1 differences <0.004), indicating that explicit reasoning supervision is unnecessary for structured extraction tasks. We further deploy all 14 fine-tuned sub-8B models as Databricks Model Serving endpoints and observe that benchmark performance transfers reliably to production, with an average F1 change of only 0.8 points. Aya 3.35B, based on the Cohere2 architecture, is the sole exception, exhibiting a 3-5 point decline under serving conditions. Based on these results, we provide deployment recommendations across accuracy and latency requirements, demonstrating that compact models can support production financial NLP workloads with approximately half the parameters and up to 4 × 4\times lower per-sample inference latency.



I
Introduction

Financial transaction processing generates billions of text strings daily, each encoding merchant identity, location, and transaction metadata in compressed, noisy formats. A representative transaction string such as
‘‘VIATOR IT-1558003355 360 3RD ST, STE 400, SAN FRANCISCO 7027495744’’
must be decomposed into ten distinct entity fields, which include merchant name, location, intermediary, and contact fields (Table
I
). Accurate extraction is critical for fraud detection, merchant categorization, and consumer analytics
[
23
]
.

This study positions merchant information extraction as an upstream analytical component for Mastercard products and algorithms that operate on Mastercard-derived transaction descriptor data. The proposed approach is not designed to authorize, route, clear, settle, or otherwise process Mastercard payment transactions; rather, it operates on textual descriptors from existing transactions to improve merchant understanding, data enrichment and analytics, downstream product quality, and the overall reliability of merchant intelligence systems.

Our current production system uses a LoRA-fine-tuned LLaMA 3.1-8B
[
5
]
that achieves approximately 97% F1 on this task. However, deploying an 8B-parameter model raises practical concerns: high GPU memory requirements (16+ GB in half-precision), limited inference throughput, and substantial energy costs
[
18
]
. As the system must process millions of transactions daily, even small improvements in efficiency translate to significant operational savings.

The proliferation of capable small language models (SLMs)—Gemma 3
[
6
]
, Qwen 3.5
[
15
]
, Aya
[
16
]
—motivates a systematic investigation:
what is the minimum model size that maintains production-grade accuracy for structured entity extraction?

This paper addresses this question from a deployment perspective. Rather than focusing on methodological novelty, we provide a comprehensive empirical study spanning 24 model variants across four model families, two prompting strategies, and two training templates. Our contributions include:

1.

A
LoRA rank ablation on LLaMA 3.1-8B
showing that rank 8 achieves 96.75% F1—within 0.20 points of the rank-32 baseline—demonstrating that smaller adapters are production-ready.

2.

A
scaling analysis
from 0.27B to 8B parameters, revealing that Qwen 3.5 4B closes the accuracy gap to within 0.35 points of the 8B baseline.

3.

Evidence that
chain-of-thought prompting during fine-tuning
generally improves performance, with gains of 0.3–1.8 F1 points across most models—though Qwen 3.5 4B is a notable exception where JSON-Only prompting achieves the best result.

4.

A finding that
Qwen 3.5’s hybrid Mamba-attention architecture
achieves anomalously strong performance at 0.8B, matching 2B–4B conventional transformers.

5.

A
Think vs. Nothink training comparison
showing that Qwen 3.5 models trained with and without reasoning tokens achieve near-identical accuracy (F1 deltas
<
0.004), with Nothink variants offering faster inference.

6.

A

that deploys all 14 sub-8B fine-tuned variants as Databricks Model Serving endpoints, showing benchmark F1 transfers to production with a mean drop of just 0.8 points—with the Cohere2-based Aya the sole outlier.

7.

Deployment recommendations
covering accuracy–latency–cost trade-offs across hardware tiers.

II
Related Work

II-A

Parameter-Efficient Fine-Tuning

LoRA
[
8
]
introduced low-rank adaptation as a parameter-efficient alternative to full fine-tuning, and has since been extended by QLoRA
[
4
]
for quantized training and AdaLoRA
[
22
]
for adaptive rank. In practice these methods are most readily applied through open-source toolkits, and LLaMA-Factory
[
25
]
(ACL 2024) is among the most widely adopted: it provides a unified pipeline for parameter-efficient fine-tuning of 100+ open-source LLMs and VLMs, supports a range of training objectives (SFT, DPO, KTO, ORPO, PPO), and typically adds support for new model releases on a day-zero basis. Its widespread adoption has produced a growing body of follow-on research—for example, LoRA fine-tuning of 3.5B–72B open-source LLMs for Chinese-to-English translation
[
11
]
and few-shot prompting combined with LoRA fine-tuning of LLMs for logical reasoning on Turtle Soup puzzles
[
10
]
—and we adopt it as the fine-tuning backbone of this study.

II-B

Small Language Models

Models such as Phi-3
[
1
]
, Gemma 3
[
6
]
, and Qwen 3.5
[
15
]
have demonstrated strong performance at 1–4B parameters. Qwen 3.5 introduces a hybrid architecture combining Mamba state-space layers
[
7
]
with transformer attention
[
2
]
. Concrete production-oriented evaluations are starting to show that small open-source LMs can match much larger proprietary models on demanding tasks: in LLM-based agentic payment systems, for example, Gemma 4 E4B has been shown to match GPT-5.2’s perfect workflow-fidelity score (ASR) despite being orders of magnitude smaller
[
9
]
.

II-C

Merchant Information Extraction in Financial Transactions

Traditional Named Entity Recognition (NER) approaches rely on CRF-based sequence labeling methods
[
12
,
14
]
. Recent work has reframed information extraction as a generation task
[
19
,
13
]
. Financial NER tasks, such as merchant information extraction from noisy bank transaction strings, present unique challenges due to abbreviated text, limited context, and non-standard formatting
[
23
,
17
]
. Chain-of-thought prompting
[
20
]
has also been shown to improve performance on structured prediction tasks
[
24
]
.

III-D

Fine-Tuning Pipeline

All eight models (including our LLaMA 3.1-8B rank-8 fine-tunes) are trained with LLaMA-Factory
[
25
]
on an NVIDIA DGX Spark—a compact desktop workstation powered by the GB10 Blackwell Superchip with 128 GB unified LPDDR5x memory. Both training and inference use this single device.

This choice deliberately separates experimentation from production. Our Databricks production environment (Section
V
) is, by security policy, highly restrictive about which base models may be pulled into the workspace, and its built-in MLflow fine-tuning support lags the open-source ecosystem in covering newly released LLM architectures. LLaMA-Factory, by contrast, is an actively maintained project whose model coverage tracks new releases closely. Running it on a self-contained DGX Spark workstation outside the production perimeter lets us train, evaluate, and select among arbitrary candidate base models without policy or tooling friction. This is also materially cheaper. The 23 retained training runs reported here totaled 462 GPU-hours of training plus 195 hours of checkpoint evaluation (12 checkpoints per run) on the DGX Spark—657 GPU-hours of retained compute in all. At the workstation’s manufacturer’s suggested retail price (MSRP), this fixed-cost hardware breaks even against managed cloud GPU compute within a few hundred to a few thousand billable hours depending on instance class and rate; the retained sweep alone approaches that range, and the trial-and-error exploration preceding each retained entry multiplies it further. Only the best-of-family adapters identified through this sweep are subsequently promoted as managed serving endpoints—a two-stage
experiment-then-deploy
workflow whose viability we confirm via the endpoint validation in Section
V
.

III-E

Prompt Strategies

We compare two prompting strategies with identical output labels (full templates in Appendix
A
):

Free-Thinking (FT):
A two-step chain-of-thought instruction—first analyze freely, then apply entity rules and output JSON. The reasoning is internal only (not in output labels). Prompt: 3,700 chars.

JSON-Only (JO):
Direct extraction with the same rules but no CoT instruction. Prompt: 2,870 chars.

III-F

Evaluation Protocol

We evaluate each model at all 12 saved checkpoints and report the best. Per-field precision, recall, and F1 are computed via exact string match; the overall F1 is micro-averaged across all entity fields. Inference throughput is reported as median samples per second, measured on an NVIDIA DGX Spark with batch size 4 and deterministic decoding (
\texttt{do\_sample}{=}\texttt{false}
,
T{=}0
).

The Qwen 3.5 0.8B model (F1=94.75% with FT Nothink) nearly matches the 2B variant (95.18%) and exceeds Gemma 3 1B (93.93%), a model

At the 4B scale, the best Qwen 3.5 variant (JO, F1=96.60%) surpasses Gemma 3 4B (FT, 96.24%), demonstrating that the hybrid architecture’s advantage persists at larger scales.

IV-D

Prompt Strategy Analysis

Fig.
3
compares Free-Thinking and JSON-Only across model sizes. FT outperforms JO for most models, with gains from
+0.18
points (LLaMA 8B) and
+0.46
(Qwen 2B) up to
+1.82

This demonstrates that chain-of-thought framing during fine-tuning guides models toward better internal representations, even without explicit reasoning in the output—consistent with findings on implicit CoT
[
3
]
. The benefit is larger for smaller models, suggesting CoT instructions partially compensate for limited capacity. Notably, even at 8B parameters LLaMA still shows a small positive FT-over-JO gain, indicating that CoT framing remains marginally beneficial at the upper end of the size range we study.

The Qwen 3.5 4B model reverses this trend—JO (F1=96.60%) outperforms FT (96.15%) by 0.45 points, making it the best sub-8B model overall. We hypothesize that at sufficient capacity Qwen 3.5’s hybrid architecture can internalize the extraction logic without explicit CoT scaffolding, and the shorter JO prompt allows the model to allocate more of its context window to the extraction task itself.

IV-F

LoRA Rank Ablation

We compare LoRA rank 8 against rank 32 on two models. On Aya 3.35B, rank 32 (60.5M trainable params, 1.8%) achieves F1=95.29% vs. rank 8’s 95.22%—a difference within noise despite 4
\times
more parameters. On LLaMA 3.1-8B, our rank-8 FT fine-tune reaches 96.75% F1 compared to the rank-32 production baseline’s 96.95%, a gap of only 0.20 points. The findings are directionally consistent across both models: rank 32 provides marginally more adaptation capacity, but rank 8 captures the vast majority of the benefit. For practical deployment, rank 8 provides sufficient adaptation capacity while reducing adapter storage by 4
\times
and simplifying model versioning.

IV-H

Accuracy–Latency Pareto Analysis

Fig.
5
plots best F1 against average inference time per sample for all retained variants, revealing the Pareto-optimal configurations. The frontier spans from Gemma 3 270M FT (0.24 s, F1=87.35%) through Gemma 1B FT, Qwen 2B Nothink variants, Qwen 3.5 4B JO NT, Qwen 3.5 4B JO (1.97 s, F1=96.60%) to LLaMA 8B FT (7.46 s, F1=96.75%). V

)—far larger than any Gemma or Qwen variant, whose worst case is a 1.1-point drop. We attribute this to Aya’s non-standard Cohere2 architecture, which has less mature support in common serving runtimes than the transformer-based Gemma and hybrid Qwen stacks. Aya is thus a weak production choice despite competitive benchmark accuracy, reinforcing that model selection must weigh serving-stack compatibility, not accuracy alone.

VI
Deployment Recommendations

Based on our results, we propose tiered deployment strategies:

Tier 1 — Maximum accuracy
(
>
96% F1): for sites willing to keep the 8B footprint, the LLaMA 3.1-8B rank-8 FT fine-tune (96.75% F1) is a production-validated alternative to the rank-32 baseline at 4
\times
smaller adapter size; endpoint validation of this variant is deferred to future work. For a smaller alternative, Qwen 3.5 4B JO at 96.60% F1 closes to within 0.35 points of the baseline at half the parameter count. Gemma 3 4B FT or Qwen 3.5 4B Nothink variants achieve 96.24% and offer further deployment flexibility.

Tier 2 — Balanced
(
>
95% F1): Qwen 3.5 2B FT Nothink (95.18% F1, 0.98 s/s) is the recommended choice—strong accuracy with high throughput and endpoint accuracy that matches benchmark (
\Delta
F1
=-0.0025
in Table
IV
). Aya 3.35B (95.72% F1, 14.5 h training, 0.33 s/s) edges it on benchmark but loses 3–5 F1 points on the Databricks endpoint due to its Cohere2 architecture (Section
V
); we therefore advise against Aya for production serving despite its benchmark score.

Tier 3 — Latency-critical
(
>
94% F1): Qwen 3.5 0.8B FT Nothink achieves 94.75% F1 at 1.32 s/s on DGX Spark—remarkable for a sub-1B model. Its hybrid architecture makes it the clear choice for edge or high-throughput deployments.

Prompt strategy.
Use Free-Thinking for Gemma and Aya models, which provides +0.3–1.8 F1 points with no inference cost increase. For Qwen 3.5 4B, JSON-Only prompting yields the best result (96.60%); for smaller Qwen models, FT and JO perform comparably.

Training template.
For Qwen 3.5, Nothink training is preferred: it matches Think accuracy while offering faster inference (up to 2.9
\times
for FT prompts) and simpler output parsing (no thinking tags).

LoRA configuration.
Rank 8 is sufficient across model sizes: rank 32 yields only +0.07 points on Aya 3.35B and +0.20 points on LLaMA 3.1-8B at 4
\times
the adapter size, reducing adapter footprint and simplifying model versioning.

Production serving.
Endpoint validation (Section
V
) confirms that benchmark accuracy transfers to Databricks Model Serving for the Gemma and Qwen families (mean
\Delta
F1
=-0.0081
). Aya 3.35B is the exception, losing 3–5 F1 points once deployed; we therefore favor the Gemma 3 and Qwen 3.5 families over Aya for production serving, and advise validating any candidate directly on its target endpoint.

Experiment-then-deploy workflow.
Our results support a deliberate two-stage workflow:
experiment and select
with LLaMA-Factory on flexible compute (DGX Spark in our case), then
deploy and serve
only the selected adapters via MLflow on a security-constrained production cluster. This separation lets teams evaluate any newly released open-source LLM as soon as its weights become available, while keeping the production attack surface limited to a small set of vetted models. It also keeps experimentation cost predictable—fixed-hardware amortization rather than per-experiment cloud GPU spend—which matters disproportionately for the hyperparameter trial-and-error inherent in such sweeps. We expect this pattern to generalize to other enterprise settings with similar tooling and policy constraints.

VII
Conclusion

We presented a deployment-oriented study of LoRA-fine-tuned small language models for financial entity extraction, evaluating 24 model variants from 0.27B to 8B parameters across two prompting strategies and two training templates. Reproducing the LLaMA 3.1-8B fine-tune with LoRA rank 8 achieves 96.75% F1—within 0.20 points of the rank-32 baseline—confirming that smaller adapters are production-ready even for the 8B model. The best sub-8B model—Qwen 3.5 4B with JSON-Only prompting—achieves 96.60% F1, closing to within 0.35 points of the 8B baseline. Qwen 3.5’s hybrid Mamba-attention architecture enables competitive accuracy even at 0.8B parameters (94.75% F1). Chain-of-thought fine-tuning generally helps across model sizes, though Qwen 3.5 4B demonstrates that sufficiently capable hybrid architectures can match or exceed CoT-trained variants with direct prompting. Think and Nothink training templates produce near-identical accuracy for Qwen 3.5, with Nothink offering faster inference. Deploying the fine-tuned variants as Databricks Model Serving endpoints confirms that these benchmark results transfer to production serving (mean
\Delta
F1
=-0.0081
), with the Cohere2-based Aya the sole exception. Together, these findings validate a two-stage
experiment-then-deploy
workflow—broad experimentation with LLaMA-Factory on flexible compute, followed by production deployment of only the selected adapters via MLflow—that is well suited to enterprise environments where production model availability is constrained by security policy. Overall, the results demonstrate that production financial NLP systems can achieve near-state-of-the-art accuracy with dramatically reduced computational requirements, enabling deployment on consumer-grade hardware.

Appendix A
Prompt Templates

We provide the text of both prompt templates used for fine-tuning. The two prompts share the same entity classification rules but differ in two places: (i) the preamble instruction, and (ii) the output specification—the FT prompt includes an explicit JSON schema, whereas the JO prompt omits it and relies on the entity keys enumerated in the rules to elicit correct JSON. The transaction string is appended after the
TRANSACTION:
token.

A-A

Free-Thinking (FT) Prompt

### Instructions
Please follow the two-step approach below.
#### Step 1 (Free-Form Analysis)
1. Analyze the bank transaction on your own
without applying any rules or guidelines.
2. Provide a free-form interpretation of the
transaction, focusing on any entities you
naturally identify.
3. Perform this internally, do not return this
as an output.
#### Step 2 (Rule-Based Classification)
1. Re-analyze the same transaction strictly
using the Entity Identification and
Classification Rules below.
2. Return a JSON object containing exactly the
keys listed under JSON Output Format.
3. Leave any key as an empty string if you do
not find a corresponding value.
4. Include no explanations or additional text
beyond the JSON object.

Followed by the shared entity classification rules (Section
A-C
) and the JSON output format with explicit schema (Section
A-D
).

A-B

JSON-Only (JO) Prompt

Extract entities from the following bank
transaction string and return a JSON object.

Followed by the same shared entity classification rules (Section
A-C
) and an output instruction for the JSON schema (Section
A-D
).

A-C

Shared Entity Classification Rules

Both prompts include identical classification rules:

1. General Approach:
- Extract entities without assumptions
or constraints.
- Identify all possible segments and
interpret them contextually.
- Consider multiple interpretations for
ambiguous segments.
2. Entity Classification Rules:
- INTERMEDIARY: Payment facilitators or
intermediaries (e.g., PayPal, Square,
Toast, Klarna, DoorDash, CashApp).
Often appears before MERCHANT_NAME.
Example: "SQ* WAL-MART #1234"
-> {"INTERMEDIARY": "SQ*",
"MERCHANT_NAME": "WAL-MART #1234"}
- MERCHANT_NAME: Primary business where
the transaction occurred. May include
store numbers (e.g., "WAL-MART#6732",
"STARBUCKS 27057", "TARGET 0001332904",
"SHELL OIL 12679923008"). If a brand
name is immediately followed by
product/service text, include the
entire portion (e.g., "MICROSOFT
* ONE DRIVE").
- DYNAMIC_DESCRIPTOR: Transaction-
specific identifiers (order numbers,
reference codes, invoice details).
Examples: "*INV-5384", "-X99S90S43",
"* O #03901", "KG9RCW",
"* HM3W5MY95J", "*RV8KK6372"
- STREET: Street address; starts with a
number or building identifier plus
street name and known suffixes
(e.g., ST, AVE, BLVD). Example:
"2323 West 5th AvenueSte 230"
- ZIP: 5- or 9-digit postal codes.
- CITY: Recognizable US city or town
names.
- STATE: Two-letter US state code
(e.g., "VA").
- COUNTRY: Two- or three-letter code
(e.g., "USA", "US").
- PHONE: Phone numbers in any format
(e.g., "800-365-6868", "4029357733",
"+14086348696", "(800)262-3246").
- WEBSITE: URL associated with the
merchant (e.g., "AMZN.COM/BILL",
"G.CO/HELPPAY#",
"HTTPSWWW.DOORDASH.COM").
3. Handling Special Cases:
- If a token might fit multiple
categories, use position/formatting
to determine the correct entity type.
- If unsure, use your best guess.
- If duplicate or partially duplicate
information (e.g., website, street,
city, state, country) appears at the
end of MERCHANT_NAME, remove it and
assign it to the appropriate key.
- Omit complete and partial duplicate
strings.

A-D

JSON Output

The two prompts diverge in how they describe the output. The FT prompt includes an explicit JSON schema:

### JSON Output Format
Return your Step 2 classification with
exactly these keys and nothing else:
{
"INTERMEDIARY": "",
"MERCHANT_NAME": "",
"DYNAMIC_DESCRIPTOR": "",
"STREET": "",
"ZIP": "",
"CITY": "",
"STATE": "",
"COUNTRY": "",
"PHONE": "",
"WEBSITE": ""
}

The JO prompt omits the schema and ends with an instruction only:

### Output Format
Return a JSON object with exactly these
keys. Leave any key as an empty string
if no value is found. Return only the
JSON object with no additional text.

Models fine-tuned on the JO prompt still produce well-formed JSON: the ten entity keys are enumerated as bullet items in the Entity Classification Rules above (Section
A-C
), so the model has the full key set even without an explicit schema.
