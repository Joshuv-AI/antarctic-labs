Executive Summary
This report examines the software supply chain security posture of mobile applications developed for consumer
whole-house battery and energy-management products. While these applications are not currently integrated
with critical infrastructure, their growing role in connected energy domain spaces underscores the importance of
understanding the external dependencies, permission structures, and runtime behaviors that could introduce
systemic risk; particularly, if adoption expands into more critical environments.

The assessment combined static and dynamic analysis to capture a comprehensive view of the applications’ digital
supply chain landscape. Applications were reverse-engineered, installed on test devices, and observed under
network capture to document both static and dynamic behavior.

Static analysis revealed broad use of third-party libraires and overlapping Android permissions across applications,
with many relying on the same sets of analytics frameworks, messaging systems, and Google-provided services.
These overlaps highlight baseline, and in some cases high-impact, permissions associated with Bluetooth device
discovery, geolocation access, persistent background execution, and media handling. This raises concerns that a
single compromised third-party dependency could affect the operational integrity of several battery-management
applications due to their reliance on identical underlying software. Because these shared components appear
across numerous vendors, a single exploit could be adapted and weaponized across multiple products, creating
common attack surfaces within the domain.

Permissions describe what an application is allowed to access, but its libraries reveal where its code originates,
which third parties participate in the domain, and how trust relationships form throughout the supply chain. While
the presence of broad permissions does not inherently signal exploitation, their use expands the potential attack
surface.

Library analysis showed no dependency shared across all eight applications: however, seven of the eight shared
seventeen libraries. This suggests the application domain depends on a common set of external providers for
critical functionality such as analytics, networking, telemetry, and installation attribution. Because many of these
dependencies and external connections may be functionally necessary, they also concentrate risk within shared
components and services. A vulnerability or supply chain compromise affecting a single widely used provider, such
as Firebase or Google Play Store, could simultaneously impact a majority of the domain space.

Dynamic testing collected outbound network connections generated during installation and first-run activities
using tcpdump, with endpoints analyzed in Wireshark. The resulting IP address and domains revealed connections
to hosting regions spanning the United States, Europe, and several Asia-Pacific jurisdictions, including Hong Kong,
Singapore, and mainland China.

Overall, the findings indicate that while many observed dependences, permissions, and network endpoints support
legitimate functionality, they also create intertwined risk pathways across multiple applications. Without rigorous
dependency governance, permission minimization, careful vetting of external service endpoints, and continuous
monitoring of runtime behavior, this domain space remains vulnerable to inherited vulnerabilities that could
propagate across vendors. As these applications continue to evolve and their integration with broader energy
systems deepens, a proactive supply chain strategy will be essential to establish trust and mitigate long-term
operational risk.

Background
This report examines a set of Android mobile applications that can be downloaded from public application stores
and run directly on users’ personal smartphones. Each application is designed to operate and monitor a portable
energy storage system built around rechargeable battery technology. These systems are commonly used to power
small household applications, support off-grid electricity requirements, and provide remote or outdoor power for a
variety of recreational activities. The physical battery systems were not available during testing, so the applications
were the sole focus of our assessment; it included examining their internal architecture, library dependencies,
connectivity requirements, and other software supply-chain characteristics.

Each application was packaged as an Android Package Kit (APK) file, which is the standard file format used to
distribute and install Android applications. An APK file is similarly to a ZIP archive. The file aggregates all the
components required for the application to run: compiled bytecode, interpreted scripts, native shared libraries,
configuration files, resources, assets, certificates, and metadata. Our analysis focused on these individual artifacts.

The applications in this study were written using Kotlin, Java and JavaScript, reflecting both traditional Android
development practices and cross-platform frameworks such as React Native. The APKs include a mix of compiled
and interpreted components. Kotlin and Java source code is compiled into Dalvik Executable (DEX) bytecode, which
must can be decompiled using tools such as JADX to obtain readable code prior to analysis. While the decompiled
output is not identical to the original source code, symbols, strings, classes, and methods often remain
understandable unless stronger protections are used during compilation.

R8 is a default code shrinker and optimizer used in modern Android build pipelines. It removes unused code,
performs basic optimizations, and can optionally obfuscate class, method, and field names to reduce APK size and
make reverse engineering more difficult. In practice, most Android applications, especially those built with
frameworks like React Native, are compiled with R8 as part of the standard release build process, meaning its
presence typically reflects routine build configuration rather than deliberate security hardening.

React Native applications include a substantial amount of interpreted JavaScript, packaged inside the APK as a
single bundle, i.e., the code necessary for a single application. This JavaScript is heavily minified during the build
process. Minification strips whitespaces and formatting, shortens function and variable names, collapses code into
dense blocks, and removes unnecessary structure. This is similar to the effects of optimizing and stripping
compiled binary code. The purpose of these “pre-deployment” operations on an application’s code is primarily to
reduce their size and enhance load and execution time; a secondary purpose is obfuscation. As a result, the
minified JavaScript must be “beautified” before analysis to restore readable indentation and spacing. Although
different technically, beautification is conceptually the same as the decompilation that JADX performs. Even after
beautification, developers’ chosen identifiers cannot be regained, so short placeholders like “a, b, c” and several
logical structures remain flattened in the beautified code. Understanding the behavior of beautified code requires
manually reversing complex function call graphs and other code structures, making JavaScript-based mobile
applications more labor-intensive to reverse engineer that compiled Kotlin or Java components.

Smart phone applications target a specific operating system and hardware platform; this common base allows the
applications to make use of commonly available software components that perform common operations. The
modern Android applications we analyzed rely on numerous commonly available dependencies, which in this
context refers to external libraries, SDKs, and shared components included within the APK. These dependencies
provide common functionality such as networking, file handling, Bluetooth Low Energy (BLE) device control, cloud
messaging, and analytics. Developers use dependencies to avoid implementing complex features from scratch to
ensure compatibility across a wide range of devices. Because many Energy Storage System (ESS) vendors rely on
the same mobile ecosystem, i.e., Google Play Services, Firebase, open-source libraries, and OEM SDKs, it is an
appropriate application domain to examine to better understand potential supply chain security challenges.

 10

A large portion of these dependencies are third-party libraries, maintained by external vendors or open-source
communities. Use of these libraires speeds application development. They can also improve application
performance, facilitate cloud service integration, and provide specialized capabilities such as push notifications or
device discovery. From a business and design perspective, use of third-party and open-source code provides
significant value. On the other hand, it also expands the number of people, processes, and opaque artifacts
involved in the construction of an application. Application development and testing is costly. Furthermore, some of
the “obfuscation” practices described previously may make visibility into application code difficult. These factors
all affect an application’s trust boundary: security, privacy, and update hygiene depend not only on the vendor’s
code, but also on how safely and consistently third-party components are maintained.

Almost all mobile devices can be hardwired to other internet connected devices using some form or Universal
Serial Bus (USB) connection. Despite this being a security concern, their numerous wireless capabilities present a
more significant risk. Almost all modern mobile devices have Wi-Fi capability, and many pair that with cellular
connectivity as well. These provide long-range connectivity. Bluetooth, and its newest variant Bluetooth Low
Energy (BLE), is also available in most mobile devices and its range can vary depending on the device’s
environment but is typically between ten and 100 meters. Mobile devices also integrate Near-Field
Communications (NFC) for close-range (4 cm) wireless communication. Since mobile devices are almost always
connected to the Internet (Wi-Fi or data over cellular), this report focuses on Internet connections. All the
applications in our test set use Internet endpoints to communicate with remotely hosted services.

The set of applications analyzed in this report also expose interesting data supply chains. Although not the primary
focus of this work, these supply chains may be essential to the application’s operation while also meeting vender-
specific or third-party requirements that do not benefit the user. Since the invention of third-party mobile device
applications, user data has been a commodity for a broad business community; this data can be a significant
breach of user privacy and a security concern. As third-party and open-source libraries are integrated into
applications, data supply chains can become less transparent, not only for the user but for the application
provider. In short, software and data supply chains for mobile device applications are related, and it may be very
difficult for a user, and potentially the application developer, to know exactly what data is being transmitted from
their device and where it is being stored and analyzed.

The safety concerns related to the mobile applications analyzed in this report remain limited to individual users.
These applications do not do control safety critical systems that affect large populations; however, mobile
applications are emerging in the energy sector that do interface with systems that could affect large populations.
The purpose of this report is to better understand digital supply chain security issues that affect energy-related
control systems; the collection of applications reviewed in this report meet this requirement in several ways as the
sections that follow outline.

Overview and Combined Analysis

All Android Package Kit (APK) files analyzed in this research were obtained from publicly accessible and verifiable
sources to ensure authenticity and minimize the risk of tampering. Where available, applications were downloaded
directly from the Google Play Store [1] or the official websites of the respective vendors, using legitimate
extraction methods. This approach prioritized traceability, enabling us to evaluate each application in the context
of its official software supply chain.

Across the eight analyzed applications, the degree and sophistication of obfuscation varied widely. Goal Zero [2]
showed minimal obfuscation; although R8 was present, as expected in modern React Native builds, the underlying

 11

Android code remained readable. Base Power [3] showed clearer signs of deliberate code shrinking and structural
fragmentation consistent with standard R8 or ProGuard obfuscation. Tesla stood out as the most aggressively
protected application, displaying hundreds of short class names and large volumes of non-ASCII content, both
indicative of intentional barriers to static analysis and reverse engineering.

The Dakota Lithium PG [4] application is minified, which effectively obfuscates some logic due to React Native’s
automated production build pipeline. Several class files matched YARA rules [5] typically associated with emulator
or environment detection, suggesting basic checks for device authenticity rather than structured anti-analysis
controls. Anker [6] employed one of the strongest commercial protections in the cohort: APKiD [7] attributed the
APK to Ijiami [8] packing. Bluetti’s [9] app combined common emulator-detection patterns with code expansion
consistent with R8 or ProGuard [10], resulting in a moderately obfuscated structure that slows analysis but does
not fully conceal logic.

Jackery [11] showed obfuscation, combining emulator and debugger checks with extensive fragmentation of code
across numerous small classes. EcoFlow [12], contained several shortened class names and several class files were
flagged by YARA rules associated with anti-Virtual Machine (VM) and debugger detection.

This section examines eight mobile applications within the energy-management ecosystem: EcoFlow, Goal Zero
Yeti, Base Power, Tesla Powerwall, Dakota Lithium, Anker, Bluetti (PowerOak), and Jackery. Each application was
reviewed to identify its declared permissions, the third-party software components it incorporates, and the
broader implications these elements have for software supply-chain security. The assessment considers the
technical requirements behind Bluetooth [13], network-based device control and the additional privileges
introduced indirectly through analytics tools, cloud-messaging services, advertising libraries, and OEM-specific
integrations.

Android permissions are declared, or requested, by an application, so it can gain access to data or actions that the
application would normally be restricted from using. Permissions are normally granted by the device’s user
through the operating system. Permissions are install-time or runtime depending on when they are approved by
the device’s owner. Special permissions offer a third category of permissions [14]. Install-time permissions are
considered safer than runtime permissions. Providing location information is an example of a runtime permission.

Across the eight applications, a consistent architectural pattern becomes evident. Necessary operational
permissions are closely tied to a range of inherited dependencies required by external frameworks, analytics
platforms, and vendor-specific Software Development Kits (SDKs).

Six permissions appear universally across all applications reviewed:

  android.permission.WAKE_LOCK,
  android.permission.INTERNET,
  android.permission.POST_NOTIFICATIONS,
  com.google.android.c2dm.permission.RECEIVE,
  com.google.android.finsky.permission.BIND_GET_INSTALL_REFERRER_SERVICE,
 and
  android.permission.ACCESS_NETWORK_STATE.

Their widespread inclusion suggests a common technical foundation within this app ecosystem. INTERNET and
ACCESS_NETWORK_STATE are essential for cloud-based communication, device telemetry, firmware delivery,
account synchronization, and energy-usage reporting. WAKE_LOCK supports continuous background activity by
preventing device sleep during Bluetooth or network operations.

 12

POST_NOTIFICATIONS allows each application to alert users about device events, charging status, firmware-update
availability, and connectivity changes. The Firebase Cloud Messaging permission,
com.google.android.c2dm.permission.RECEIVE, supports push notifications and cloud-to-device messaging, and its
universal presence highlights the widespread reliance on Google’s notification infrastructure. The install-referrer
permission, com.google.android.finsky.permission.BIND_GET_INSTALL_REFERRER_SERVICE, is introduced
automatically by Google Play Services and enables install-source tracking and analytics initialization.

Figure 1 presents a sorted list of commonly used, or shared, permissions in our application test set. Permissions
are listed on the graph’s y-axis; the x-axis denotes the number of applications that use that permission.

Beyond the shared permissions, a broader set of non-shared permissions appear, revealing differences in vendor
functionality and inherited SDK behavior. The Bluetooth-related permissions vary depending on the libraries used.
Applications that communicate with hardware over Bluetooth Low Energy (BLE) include BLUETOOTH,
BLUETOOTH_CONNECT, BLUETOOTH_SCAN, or BLUETOOTH_ADMIN, though the exact combinations differ.
Variations often arise from the choice of BLE implementation, some developers rely on native Android Application
Programming Interfaces (APIs), while others use cross-platform libraries such as React Native BLE modules or
RxAndroidBLE2.

Storage and media-related permissions emerge more sporadically. READ_EXTERNAL_STORAGE,
WRITE_EXTERNAL_STORAGE, READ_MEDIA_IMAGES, CAMERA, and RECORD_AUDIO often originate from
embedded frameworks rather than the core functionality of energy-management features. Applications such as
Tesla Powerwall, Base Power, and Jackery include these permissions through SDKs like Expo [15], Intercom [16], or
Zendesk [17], which support file uploads, media attachments, or customer-support interactions. Their absence in
applications such as Goal Zero or Dakota Lithium suggests more targeted development approaches or deliberate
exclusion of optional features that require access to sensitive hardware.

Regional and Original Equipment Manufacturer (OEM) specific permissions create another layer of divergence.
Permissions associated with JPush [18], Baidu Push [19], or manufacturer launchers, such as
com.hihonor.android.launcher.permission.CHANGE_BADGE or
com.vivo.notification.permission.BADGE_ICON, appear primarily in apps intended for Chinese or
multi-regional markets. These are especially common in EcoFlow and Anker and are not found in applications like
Goal Zero or Tesla Powerwall.

Although a permission used by only one application does not propagate its vulnerability to the other apps, it still
contributes to a broader supply chain risk profile. Unique permissions can create localized, app-specific
vulnerabilities, meaning the impact is limited to that vendor’s product rather than spreading across all eight
applications. However, from a supply chain perspective, every unique or vendor-specific permission expands the
overall attack surface because it introduces behaviors and system interactions that are not visible in the other
applications and therefore cannot be assessed or monitored in a uniform way. The more varied the permission set
becomes across applications, the harder it is to ensure the security of each one, especially when these uncommon
permissions interact with sensitive system components, or manufacturer-specific launchers. Isolated permissions
do not create shared vulnerabilities, but they introduce uncertainty and added complexity into maintaining
security across energy storage systems applications.

To build on the insights gained from permission analysis, the next section shifts focus to the software libraries and
embedded components found within each APK. Permissions describe what an application is allowed to access, but

Uniform Resource Locators (URLs)
Apps use remotely hosted compute and data infrastructure (the Cloud) to provide critical capabilities, namely data

you can query for data based on your interaction with a battery application on your smart phone. Behind each URL
is an IP address for a specific computer host physically located somewhere on Earth.

The analysis summarized in this section combines results from both static and dynamic examination of eight
portable battery-generator mobile applications. Static review involved decompiling each APK to identify embedded
URLs, configuration values, and hardcoded endpoints. Dynamic testing involved running the apps in a controlled
Android environment and capturing each application’s network activity using Wireshark [27]. In combination, our
static and dynamic testing provides a view of how each application operates, revealing the network connections it
is configured to establish, as well as the connections it establishes at runtime.

Across the dataset, three broad clusters emerge based on cloud-service usage:

 Western Cloud Providers: Goal Zero, Tesla Powerwall, Dakota Lithium PG, and Base Power rely mainly on
 Western cloud providers, built almost entirely on AWS and Google Cloud.

 22

 Hybrid Cloud Providers: Bluetti and Jackery follow a hybrid model that mixes Western hyperscalers with
 Chinese and Hong Kong–based infrastructure.
 Chinese Cloud Providers: EcoFlow and Anker form a third cluster that operates largely within Chinese domestic
 cloud platforms, including Alibaba Cloud, Huawei Cloud, and dbankcloud.

In the first cluster, most traffic from the apps resolve to AWS and Google infrastructure, with additional activity
flowing through Content Delivery Networks (CDNs) such as Cloudflare [28], Akamai [29], and Fastly [30]. Analysis of
the Tesla and Goal Zero apps revealed they use the largest number of IP addresses. Dakota Lithium PG follows a
similar pattern; however, it also connects to remote advertising and telemetry services. The Base Power app
utilizes fewer endpoints, suggesting a smaller backend. Apps in this cluster use Google Firebase and Play Services
libraries. Static analysis confirmed this, and dynamic captures showed that they route analytics and messaging
through endpoints associated with the services these libraries support. A service disruption or security issue
affecting these shared components would likely impact every app in the cluster.

Bluetti and Jackery make up the second cluster which we characterize as “hybrid” based on their use of network
endpoints that are geographically distributed across several countries. Bluetti uses a mix of PowerOak and Alibaba
Cloud servers, spanning China, Hong Kong, Germany, and U.S. hyperscalers. Jackery connections are similar: most
of its traffic goes to AWS and Google, but some requests route through Alibaba Cloud [31] nodes. Both apps also
use CDNs and customer-support platforms such as Akamai, Fastly, and Zendesk [32]. The hybrid connection model
employed by these applications provides both global reach and increased susceptibility to security issues.

The third cluster relies on Chinese-regulated infrastructure. EcoFlow uses region-specific endpoints hosted on
Alibaba Cloud. Our dynamic analysis confirms that most connections remain within China. Custom permissions tied
to JPush indicate a full replacement of Firebase Cloud Messaging with a domestic alternative. Anker primarily uses
Chinese-regulated endpoints but uses endpoints in other countries as well. It distributes its traffic across Huawei
[33] cloud regions in Asia and Europe, supplemented by limited AWS [34] and Google activity.

The static and dynamic network connectivity analysis we conducted across our app test set suggests some
interesting trends: A small set of global providers—Amazon, Google, Microsoft, Alibaba, and Cloudflare—provide
remote services for these products; this concentrates security risk. Use of CDNs and SaaS intermediaries improve
app performance but introduce additional layers of complexity where misconfigurations or data-handling errors
can occur and increase security risk. Some more specific observations were made while conducting our analysis:
The Bluetti and EcoFlow apps include dev- and test- environment endpoint references inside their production
APKs. These endpoints could connect to internal APIs that could present a significant security concern if they have
not been properly restricted.

Conclusion
Our analysis of this set of Android applications used in consumer battery and energy management systems
identified clear trends in third-party dependency usage, permission requests, network communications, and
obfuscation techniques. Together, these findings show that understanding the supply-chain security of mobile IoT
applications requires comprehensive security testing. Such testing clarifies how apps interact with global
infrastructure and broader potential security concerns.

Applications such as Tesla, Base Power, EcoFlow, and BLUETTI exhibited signs of R8-based obfuscation, including
shortened class names and stripped debug information, while others like Goal Zero and Dakota retained
descriptive identifiers and showed little or no evidence of code protection. The widespread reliance on third-party
libraries—particularly Firebase, Google Play Services, and analytics SDKs—raises privacy considerations, especially
when paired with access to sensitive permissions such as location, camera, and storage. Apps established
connections to domains hosted in the United States, China, Europe, and other countries, with infrastructure tied to

 23

providers like AWS, Google Cloud, and Alibaba, reinforcing concerns around data sovereignty and operational
transparency.

Our summary findings clarify how these applications manage user data and interface with remote systems. They
also highlight the importance of dynamic analysis to uncover behaviors that static methods may not reveal,
including runtime data flows, component exposure, and third-party SDK behavior.

The next phase of this research will involve more dynamic analysis of each application’s behavior. These tests will
focus on identifying undocumented third-party SDK activity, real-time data handling operations, and any
unexpected interactions with remote servers. Testing will emphasize analyzing Bluetooth and network
interactions, exported components, biometric input flows, and boot-time behaviors. Dynamic testing will also help
assess whether sensitive permissions are actively used or exposed during unexpected states.

Ultimately, these investigations aim to illuminate the complex and layered ecosystems that support mobile energy
apps. Building an understanding of where vendor responsibility ends and third-party influence begins should be
central to continued evaluations, so these highly useful products and their control software can be trusted, remain
resilient, and ensure their users remain safe.

This work sets the stage for follow-up testing aimed at validating security assumptions and identifying potential
vulnerabilities in live operational contexts.

Goal Zero Yeti

The Goal Zero Yeti application is a mobile companion application developed by Goal Zero, LLC, a U.S.-based
company headquartered in Bluffdale, Utah, specializing in portable power stations and off-grid energy solutions
[2]. The app is designed to interface with Goal Zero’s line of Yeti Lithium and Yeti X power stations. Through the
application, users can remotely monitor and control their power station via Bluetooth or Wi-Fi, depending on the
model. The app displays key information such as battery state of charge (SOC), input/output wattage,
temperature, and allows users to toggle individual ports on or off.

The Yeti application is available for Android and iOS devices. The application’s user interface allows for clear
visibility into real-time energy metrics and system health, and users can initiate over-the-air firmware updates
when available. However, user reviews suggest some challenges with connection reliability, especially in
Bluetooth-only configurations or when pairing multiple devices. Reports of firmware update delays or intermittent
disconnects are common among users relying on Bluetooth rather than Wi-Fi [35]. These issues tend to be device-
or setup-specific and are usually resolved with manual firmware updates or close-range reconnection procedures.

The application is particularly useful for van dwellers, recreational vehicle (RV) owners, off-grid homeowners, and
mobile professionals who require remote visibility into their energy systems [36] While the app reliably reports
battery level and the status of the device’s physical output ports; such as AC outlets, USB ports, or DC charging
ports, some users report occasional delays in how quickly the app reflects changes when those outputs are turned
on or off. Goal Zero regularly releases app and firmware updates to address these issues, and user feedback
indicates incremental improvements over time. Although the core functionality remains solid, users managing
mission-critical power applications may prefer supplementing app-based monitoring with direct device checks or
use of Wi-Fi- over Bluetooth for better consistency.

The Goal Zero Yeti application follows standard mobile security practices to protect user data and ensure safe
communication between the application and Yeti devices [37]. Communication with Yeti power stations is secured
via encrypted Bluetooth or Wi-Fi channels, depending on the connection method used by the specific model. While
Goal Zero has not publicly released- detailed security white papers, the app requires user authentication via Goal
Zero account credentials. Information collected by the application may include battery performance data, device
identifiers, firmware version, and account-related metadata. According to Goal Zero’s privacy policy, this data is
used for diagnostics, app functionality, and customer support [37].

One area of concern noted by users is the app’s request for location permissions on Android devices. This
requirement is tied to Android’s system-level handling of Bluetooth scanning, which mandates access to location
services for Bluetooth Low Energy (BLE) device discovery. While this is a technical limitation imposed by the
Android operating system, Goal Zero has not provided detailed documentation explaining how location data is
handled or whether it is retained. Some users have expressed concern about granting location access when it
appears unnecessary for the app’s core functions beyond Bluetooth pairing [36].

As of this writing, there have been no publicly disclosed security vulnerabilities affecting the Yeti app itself or its
communication with Goal Zero hardware. However, some users have reported reliability issues during firmware
updates, which in rare cases can result in devices becoming temporarily unresponsive or requiring manual resets.
These issues appear to be related to update execution rather than deliberate security flaws [38]. The company
states that user data may be disclosed when legally required or in the event of a business acquisition.
