Multi-paradigm Logic Programming in the E {\mathcal{}E} rgoAI System
MICHAEL KIFER Stony Brook University, USA, and Coherent Knowledge, USA, THERESA SWIFT Coherent Knowledge, USA

Abstract
E {\mathcal{}E} rgoAI is a high level, multi-paradigm logic programming language and system developed by Coherent Knowledge Systems as an enhancement of and a successor to the popular F {\mathcal{}F} lora-2 system. E {\mathcal{}E} rgoAI is oriented towards scalable knowledge representation and reasoning, and can exploit both structured knowledge as well as knowledge derived from external sources such as vector embeddings. From the start, E {\mathcal{}E} rgoAI (and F {\mathcal{}F} lora-2 before it) were designed to exploit the well-founded semantics for reasoning in a multi-paradigm environment, including object-based logic (F-logic) with non-monotonic inheritance; higher order syntax in the style of HiLog; defeasibility of rules; semantically clean transactional updates ; extensive use of subgoal delay for handling unsafe queries and for better performance; and optional support for bounded rationality at a module level. Although E {\mathcal{}E} rgoAI programs are compiled into XSB and adopt many Prolog features, E {\mathcal{}E} rgoAI is altogether a different language and system. Under consideration in Theory and Practice of Logic Programming (TPLP).

3.3
Type Checking

A type in
{\mathcal{}E}
rgoAI can be any class in the classification
hierarchy. Remembering that the class membership (the

Dynamic

complex cases, it is often a highly useful aid to program
development.. To perform dynamic type checks, one can easily express
different type type
violation
as queries that return type
violations as

to type correctness.

Although the semantics needed for signatures is sometimes
program-specific, many type inconsistencies
are common, including 1) that an object has an attribute value

checking can be particularly important when complex objects are
inserted in a dynamic setting, as will be discussed in
Section
8
.

Here is an example of type violations expressed as a query that
identifies attributes and values for instances that violate properties

type_error(?Obj,?Attr,?R,?D) :-
%% Values that violate typing
?Obj[?Attr->?R], ?Obj[?Attr=>?D],
\backslash
naf ?R:?D
;
%% Defined methods that do not have type information
?Obj[?Attr->?R],
\backslash
naf ?Obj[?Attr=>?_D].

?- type_error(?Object,?Attr,?Result,?Class).

To save the user the trouble of writing type constraints for common
cases of type violations,
{\mathcal{}E}
rgoAI provides the
\backslash
typecheck

supports the above type checkers so that the user can simply query:

\backslash

Details can be found in the
{\mathcal{}E}

3.4
{\mathcal{}E}
rgoAI Frame Compilation.

The compilation of
{\mathcal{}E}
rgoAI frames into Prolog predicates follows the
general design of
[
20
]
and consists of two parts: 1) frames
are translated into Prolog predicates; and 2)
closure rules
are
added to support the object-oriented semantics of frames. In this
section, we describe a few aspects of
{\mathcal{}E}
rgoAI compilation to give the
reader an idea of the compilation process.

Both instance and class frames are translated into Prolog in a similar
manner, so we take as an example the following instance frame. which
is to be added to
{\mathcal{}E}
rgoAI’s knowledge base. The frame is
complex

as it has multiple attribute-value pairs, because its identifier
includes an inheritance predicate (

/2), and because it has a
set-valued attribute.

Mary : employee[age->29, salary(1998)->100000, kids->{Tim,Leo}].

As described in
[
20
]
, frame compilation begins with
translating
complex
frames (like the above) into a conjunction
of
atomic
frames. As part of this process, attribute values
that are sets are split into conjunction of singletons, and the
membership statement for
Mary
is factored out of the frame::

Mary : employee,Mary[age->29],Mary[salary(1998)->100000],
Mary[kids->Tim],Mary[kids->,Leo].

These atomic frames are then translated to Prolog facts that are then
asserted to the XSB database as
tries

[
36
]
.

isa(Mary,employee).
mvd(Mary,age,29). mvd(Mary,salary(1998),100000).
mvd(Mary,kids,Tim). mvd(Mary,kids,Leo).

The
wrapper predicate

mvd/3
(which stands for multi-valued
data) is used for the translation of attributes with behavioral
inheritance. Query frames must undergo the same translation as
program frames for resolution to work properly. For instance the
query

Mary:?Class[kids->?Kid].

would be translated to

isa(Mary,?Class),mvd(Mary,kids,?Kid).

so that the query would have two solutions, one with
{?Class=employee,?Kid=Leo}
and another with
{?Class=employee,?Kid=Tim}
.
{\mathcal{}E}
rgoAI’s compiler mangles the names of the
actual wrapper predicates to include the module of the file or query.

{\mathcal{}E}
rgoAI rule frames must be encoded in a more complex manner than fact frames,
and require generation of
closure rules
to:

•

Compute the transitive closure of
::
/
2
in a manner that
supports runtime warnings about cycles in the subclass hierarchy.

•

Compute the closure of
:

/2
with respect to
::

/2
, i.e.,

if
X : C
and
C :: D
then
X : D
.

•

Perform inheritance. In particular, monotonic inheritance must
detect and propagate multiple type values; while non-monotonic
inheritance must detect and override object value conflicts.

•

Provide an infrastructure to treat undefined methods as
exceptions. Unlike Prolog, undefined predicates in
{\mathcal{}E}
rgoAI do not
throw errors by default. However when checks for undefinedness are turned on, code
to raise appropriate errors is injected into the closure rules.

The above closure rules are specified statically in special files that
get included in the compiled Prolog code after the appropriate
preprocessing that makes these files compliant with
{\mathcal{}E}
rgoAI’s dynamic

4
HiLog

The previous section showed how complex frames, called
frame

contained logical terms such as the object id
claim(13344)
and
the occurrence of

in the body of a rule.
{\mathcal{}E}
rgoAI fully
supports HiLog
[
8

which gives a higher-order syntax to
Prolog-style resolution. The idea behind HiLog can be explained
easily.
For instance, the HiLog fact

p(fact(7))(a,f(b,b),[3,?X])

is schematically translated to Prolog as:

apply(apply(p,fact,7),a,apply(f,b,b,[3,?X])
.

where every non-list compound term
T
is translated into a term with
functor
apply/n
and
T
as its first argument. By similarly
translating a query such as

?- p(?X)(a,f(b,b),[3,foo])

to

?- apply(apply(?X),a,apply(f,b),[3,?X])
,

the query can be resolved against the fact with either tabled or
non-tabled Prolog-style resolution. To be more specific a HiLog term
is defined as follows and this semantics is equivalent to the
model-theoretic view of HiLog
[
8
]
.

Definition 1

A
HiLog atomic constant
is an atom. A
base HiLog term

is a HiLog atomic constant, a list, a variable, or an arithmetic
expression.

A
general HiLog term
is a base HiLog term, or has the form

T(\overline{Args})
where
T
is a general HiLog term, and

\overline{Args}
is an argument list of general HiLog terms.

HiLog is sometimes said to have a higher-order syntax but a
first-order semantics. Specifically HiLog semantics is based on a
translation into Prolog.

Definition 2

The
HiLog transform

tr_{H}
is defined as follows.

If
Term
is a base HiLog term, then
tr_{H}(Term)=Term
. Otherwise
if
Term=Term_{1}(\overline{Arg})
then

tr_{H}(Term)=apply(tr_{H}(Term_{1}),tr_{H}(\overline{Args}))

where
tr_{H}(tr_{H}(\overline{Args}))
simply applies
tr_{H}
to each
argument in the sequence.

It can easily be seen that by applying
tr_{H}
to a HiLog term produces
a Prolog term. As a result, if
tr_{H}
is applied both to HiLog programs and goals in a program
{\mathcal{}P}
, the model of
{\mathcal{}P}
is the model
of its translation. Operationally, we refer informally to resolution
of translated goals as
HiLog resolution
.

Since variables can appear nearly anywhere in HiLog terms,
HiLog is useful for exploring the structure of knowledge
bases.
Another use case is traditional higher-order programming.
Suppose we need to transitively close many different
binary relations, like
flight/2
,
edge/2
,

parent/2
. Some of these needs may arise in the future and not be
known at present. Instead of writing the usual 2-rule definition of the
transitive closure in each such case,
we could write just one pair of rules for all current and
future needs:

closure(?P)(?F,?T) :- ?P(?F,?T).
closure(?P)(?F,?T) :- closure(?P)(?F,?Mid),?P(?Mid,?T),

Note the implicit reliance on tabling for the second, left-recursive
rule. Now, to compute the transitive closure of
flight/2
and
of
edge/2
we can simply pose these two queries:

?- closure(flight)(?F,?T).
?- closure(edge)(?F,?T).

Avoiding name clashes:
In systems that are implemented via a
translation to a target system, name clashes with other components of

the HiLog

are usually hard to detect and debug.
{\mathcal{}E}
rgoAI addresses this problem by

{\mathcal{}E}

5
The Module System of
{\mathcal{}E}
rgoAI

In HiLog and F-logic, the number of unique predicates used for the
Prolog translations is small. As a result, it is easy to write a goal that
backtracks through all clauses in the program, a behavior that can
lead to
inefficiency. The salting
technique of the previous section prevents unintended resolutions
between
{\mathcal{}E}
rgoAI’s wrapper predicates and similarly named predicates from
other XSB programs that may be used in conjunction with
{\mathcal{}E}
rgoAI in the same
XSB pprocess. Without salting there could be name
clashes between the
mvd
and
apply
wrappers discussed
in previous sections and
mvd
or
apply
used in other
XSB programs (if XSB predicates are in the default
usermod
module).
But there is another problem: the separation of namespaces among the
wrappers
within
the
{\mathcal{}E}
rgoAI system. Such separation is necessary
to enable component-wise construction of large knowledge bases and to
reduce the chances of inadvertent interactions.As in most languages,
{\mathcal{}E}
rgoAI’s
module system addresses these and similar issues.

{\mathcal{}E}
rgoAI’s module system was designed to be dynamic and to
support a number of other unique features. Modules can be created “on
the fly” at runtime, and rules and data can be loaded into them,
inserted, or deleted at run time as well. Calls from one module to
another may also be constructed at run time. At the same time, any
module can prevent unwanted calls by encapsulating itself.
Encapsulation can happen at compile time or dynamically, via the
executable

export/1
directive (e.g.,
export{?[abc ->?],
pqr(?)}
or even
export{?[abc ->?], pqr(?)} >>
module1,module2
).
Furthermore, modules need not be instantiated within a goal; for instance
one can query the modules and argument values for which

is
true:

?- p(?X)@?M.

Some of the above features exist in various logic programming systems, but
others (variables over modules, support for non-predicate-based languages
like HiLog and F-logic), are unique to
{\mathcal{}E}
rgoAI.

The implementation of
{\mathcal{}E}
rgoAI modules elaborates on the idea of salting the
wrappers such as
apply/n
and
mvd/3
.
The goal is to ensure that when these wrappers are used
in
different
modules
they are translated using
different
salted wrappers.
For example, the statements

John[age->11]
and
Mary[age->12]
that appear in the

same
module would be related to each other because they would be
encoded using the same set of salted wrappers: like
’
salt
ˆ
mvd’
,

’
salt
ˆ
isa’
, or
’
salt
ˆ
apply’
.
In contrast, these same statements in
different
modules
would be encoded using
different
salted wrappers.

5.1
Module-aware Salting

Thus, the basic idea underlying the implementation of
{\mathcal{}E}
rgoAI modules is
that in the end, all HiLog and F-logic wrapper predicates are translated
with respect to a particular module, and the module symbol is used
only in the outermost functor of the translated wrapper predicates.
This restriction is made because ultimately the system determines the
truth values of the instances of the wrapper predicates only. For instance,
the module-specific version of HiLog’s
apply/n
is

’
salt
ˆ
modname
ˆ
apply’/n+1
.
Functors at inner levels become arguments to the outer wrappers— after the
HiLog and F-logic transforms, inner functors are no longer treated as
predicates, have no truth values, and their salting does not involve
modules. As a result, the arguments
conceptually play the role of shared object identifiers about
which logical assertions (facts and rules) are being made. Assertions
made in one module about a set of objects do not interact with the
assertions about that same set of objects in another module unless one
module
explicitly queries another module.

For example: suppose a database table named
p/1
exists both in module

foo
and module
bar

relationship between these two tables so their contents should be
considered to be unrelated. However, if we learn that module

then the version of

in

must necessarily have
all the tuples that the version of

p/1
in
bar
has.

Admittedly, salting only the outer functor of a term means
that we distinguish between

that appears as a call
and

that appears as an argument, which makes meta-programming
noticeably less elegant. This trade-off is well-known and analogous to
choosing between a Prolog with
a predicate-based module system and a Prolog with a functor-based module
system (e.g., Ciao Prolog vs. XSB).

5.2
Loading vs. Adding

Normally the user creates a file that includes facts, rules, and
queries. Then the user loads or adds that file to a
module (the module may or may not exist at the time), which causes
the file to be compiled
for that module
and the queries executed. The
user might pose additional queries,
load and/or add additional files into new or already existing modules,
or do many other things.

For concreteness, suppose we have a file called

myProgram.ergo
that contains the query and the rule
just discussed plus some data facts (i.e., bodiless rules). We can
load the file into some explicit module, e.g.,
mainRules
, or into the

current

?- [myProgram >> mainRules].
?- [myProgram].

The first form will create the empty module
mainRules
,, if it
did not exist before, compile
myProgram.ergo
for the module

mainRules
causing compiled salted Prolog rules to appear
in XSB’s memory. (If the module existed prior to the command it is

emptied out
of its old contents first.)
In
the second version of the load command,

myProgram.ergo
will be compiled for the
current
module
but the rest is the same as we just explained.

The current module dynamically changes during an
{\mathcal{}E}
rgoAI session. When
{\mathcal{}E}
rgoAI starts up, it automatically creates the module
main
which is the first current module.
If either of the above load commands executes next, it
executes with
main
as the current module. During the
compilation of
myProgram.ergo
using the first option, the
current module will be
mainRules
rather than
main
.
With the second version of the load command, the current module will
not change, of course, and will still be
main
. If

myProgram.ergo
includes another loading command, like

?- [myStuff >> miscRules]
, then when this command is
executed,
myStuff.ergo
will be compiled with

miscRules
as the current module.

Loading wipes out any existing contents of the target module, so
loading two different sets of rules into the same module is rarely
meaningful unless the first set of rules and data has become obsolete.
Such scenarios arise when dealing with streaming data, but are
unlikely in cases where working knowledge of an application evolves. For
such applications,
{\mathcal{}E}
rgoAI provides the

command, e.g.,

?- [+myAddlStuff >> mainRules].
?- [+myAddlStuff].

Using the add command resembles loading except that it does not erase
beforehand the contents of the module (
mainRules
in the first
form, the current module if the second form). The overall result of
{\mathcal{}E}
rgoAI’s
dynamic creation of modules, loading, and adding is that any given
file can either be loaded into any module or added at any
time.

In Prolog, files may be conditionally loaded into a

Until now, we remained silent about how the
placehholder for the current module,

gets replaced with the actual name of that module
within the context of a given execution.
This
is accomplished with the help of the GPP

16

https://github.com/logological/gpp

preprocessor used by C and C++, but includes features needed by

rgoAI that CPP does not support such as the ability to change syntax
on the fly and to perform macro evaluations inside quoted strings.

Because code files may be dynamically loaded or added into modules,

{\mathcal{}E}
rgoAI does not compile into the XSB Prolog syntax directly
but rather into a syntax where HiLog and frame wrappers are enveloped
with suitable GPP macros. For example, instead of compiling the

#mode nostring "\!#’"

#define SALT_WRAP(BaseWrap) ’PREFIX^BaseWrap’
#define MODSALT_WRAP(Mod,BaseWrap) ’PREFIX^Mod^BaseWrap’
#define CURRMOD_WRAP(BaseWrap) ’PREFIX^CRNT_MODULE^BaseWrap’

expressions:

MODSALT_WRAP(bar,apply)(SALT_WRAP(apply)(q,_X))

There are several interesting things to note about these macros.
First, the last three macro definitions refer to other macros such as

, and these referenced macros appear inside quoted

17
17

17

As far as we know, the CPP preprocessor in C/C++ cannot be
forced to evaluate such macros, but XSB’s GPP can.
The

those macros as we intended. Second, notice that

changes depending on the context where the reference to the current
module appears). In our example, the current module can be

module is solved because we can pass that name to GPP under the guise of

and XSB itself. In fact, nu-Prolog
[
29
]
implements subgoal
reordering for Prolog negation, although it does not assign the truth
value
undefined
to non-ground negative subgoals, nor does it
handle explicit negation or quantifiers.

7.2
Delay Quantifiers

The delay quantifiers

wish/1
and
must/1
cause dynamic reordering of subgoals
that do not fulfill argument binding requirements. These quantifiers
check conditions on variables in a subgoal and delay that subgoal if
these conditions fail. For example, the subgoal

must(ground(?X) or nonvar(?Y))
ˆ
?X[foo->?Y]

contains the delay quantifier
must/1
, and evaluation of the
subgoal delays evaluation of
?X[foo->?Y]
until either
?X

is ground or
?Y
is partially instantiated. If the desired
instantiation is unachievable, a runtime error results. The

wish/1
quantifier delays its subgoal in the same manner as

must/1
, but the subgoal is executed after no more delay is
possible, and no error is raised.

8
KRR in a Dynamic Setting

Most real-world knowledge changes over time. A
Claim
object, like that
in Figure
3
, may be added or modified. New rules
expressing beliefs, like those in Figure
5
, may be
designed by a knowledge engineer or learned. Knowledge must also
adapt to changing circumstances. For instance, if polls show that a
viral pandemic is not a high concern of voters, a number of rules may
be canceled in the sense of defeasible logic
(Section
6
).

In
{\mathcal{}E}
rgoAI,
every
rule and fact is treated as dynamic information,
so that any rule or fact may be inserted, deleted, enabled, or
disabled.
21
21

21

Unlike in Prolog, where every rule/fact is either
dynamic (deletable) or static, based on predicate-level declarations.

The changes made possible by such flexibility can give rise to
different issues. A new claim may need to be added

transactionally
so that either all necessary elements must be
added or none may be. Adding or canceling a rule can have complex
consequences especially when argumentation theories are used or when a
change is made to a program’s classification hierarchy. As a result,
assurance may be needed that certain conditions hold or do not hold
after an update.

{\mathcal{}E}
rgoAI addresses such issues through Transaction Logic

[
5
]

extended with integrity constraints.
22
22

22

{\mathcal{}E}
rgoAI also supports two other mechanisms for monitoring or managing change: latent queries, and alerts.

Returning to our running example about claims and beliefs, it may be
useful to distinguish between two classes of people who frequently
make claims: politicians and journalists. In fact, we might like to
ensure that no person is both a politician and a journalist within the
time frame covered by our knowledge base. It is easy to write a
rule to check for this:

occupationConstr(?Per):-

?Per:Person,?Per[occupation->journalist],?Per[occupation->politician].

How can this constraint be enforced?
One might try defeasible reasoning, as in
Section
6
, and set the two occupations in opposition,
but that could result in such persons having no occupation whatsoever
(depending on the argumentation theory).
In such cases, it is usually better to impose database-style
integrity
constraints
via this command:

?- +constraint{occupationConstr(?)}.

This activates a database constraint that tells
{\mathcal{}E}
rgoAI to check the query

?- occupationConstr(?Person).

after each transaction. In Logic Programming, such a constraint is
considered to be violated if this query returns any answers: such
answers are treated as objects that
violate
the constraint. In
our case by executing

?- insert{’Bunky Muntner’[occupation->politician]}.

the above query returns a
Person
object that has

journalist
and
politician
both listed as occupations
thereby violating the constraint.
Various options are available to handle such cases — from simple
warnings to transactional rollbacks to callbacks to routines for
handling the constraint violation.

Transactional rollbacks happen automatically, if updates are written using

Transaction Logic

[
5
]
.
At the practical level, this means that the user must use

transactional
update operators,
i.e.,
t_insert
,
t_delete

t_enable
,
t_disable

instead of
insert
,
delete
,
enable
,

disable
, etc.
For instance,

?- t_insert{’Bunky Muntner’[occupation->politician]}.

Operationally, one can think of such updates as
backtrackable

which provides the rollback functionality. Transactional updates are
committed when a goal returns to the interpreter level, or when
commit@
\db
is executed. A transactional update may be part
of a complex query that relies on extensive tabling. To address this,
whenever a transactional update is executed or rolled back (i.e.,
backtracked over), any inferences that have been made are reactively
adjusted via
{\mathcal{}E}
rgoAI’s
SLGR(A)
, which uses incremental tabling
(cf.
[
46
]
), ensuring
view consistency
of inferences with
respect to updates.

As a second example, consider a toy

At the theoretical level, Transaction Logic is a higher-order logic with a

Specifically, it treats elementary updates, like insert

Termination and Bounded Rationality in
{\mathcal{}E}
rgoAI.

As discussed in Section
2

{\mathcal{}E}
rgoAI’s use of
SLGR
resolution ensures termination and produces the correct well-founded
model for programs with the bounded term depth property. This
termination class includes Datalog and is far larger than the
termination class of Prolog using SLDNF. However assuming queries are
side-effect free, runtime
{\mathcal{}E}
rgoAI options can guarantee correct
termination for any query to a program that has a finite model, and

sound
termination on any query to any program.

9.1
Termination on Programs with Finite Models

Section
2
provided examples of SCCs of mutually
dependent subgoals that correspond to unfounded sets in WFS. Another
type of unfounded set is an
unfounded chain
, which can be
illustrated by the simple
{\mathcal{}E}
rgoAI program:

{\mathbf{P}_{FinModel}:}

p(?X) :- p(f(?X))

Using
{\mathcal{}E}
rgoAI’s default resolution method,
SLGR
, the goal
p(a)

to
P_{FinModel}
produces an infinite chain of goals,
p(f(a))
,

p(f(f(a)))
,
p(f(f(f(a))))
and so on. This is
because
SLGR
creates a new table entry for any goal that is not a
variant of a goal already in the table (cf. Section
2
).

{\mathcal{}E}
rgoAI can address such situations via
subgoal abstraction
, in
which subgoals are abstracted once they reach a maximum size. In

P_{FinModel}
, abstraction with subgoal depth 2 or more would rewrite
any goal that unified with
p(f(f(?X)))
to
p(f(?X))

ensuring that the evaluation will create only a finite number of
subgoals.

The use of subgoal abstraction guarantees powerful semantic
properties. Let us represent a three-valued well-founded model
M

using two sets: the set of atoms that are
true
in
M
and the set of
atoms that have truth value
u
in
M
. Since the well-founded
model of
P_{FinMod}
has no atoms with truth value
true
or

u
, its three-valued model is finite. In
[
38
]
, it is
shown that if SLG is extended with subgoal abstraction then it
correctly terminates for any program with a well-founded model that is
finite under the above definition.

In
{\mathcal{}E}
rgoAI, subgoal abstraction can be requested with the help of the

goalsize

restraint in the
setruntime
directive. Loading into
{\mathcal{}E}
rgoAI the small fragment
below,

?- setruntime{goalsize(4,abstract)}.
p(?X) :- p(f(?X)).
p(b).
p(f(c)).
?- p(?X). // the query

produces the following answers and terminates:

?X = b
?X = c
?X = f(c)

Without subgoal abstraction (
i.e.
, if the directive

setruntime{goalsize(4,abstract)}

is commented out) the above program will not terminate and will return
no answers. In our case, however, the
goalsize
parameter
tells the query subsystem to abstract subgoals larger than size 4,
which forces termination.
25
25

25

The actual size is computed by
taking into account the function symbols in the goal with their
arities in a prefix-style traversal that preserves termination
properties.
Subgoal abstraction is implemented by XSB’s tabling
subsystem.
Whenever a tabled goal is encountered, a ’subgoal
check/insert’ operation traverses the goal in order to determine
whether an existing table may be used or a new table must be created.
The declaration for subgoal abstraction activates an engine-level hook
that abstracts the goal as part of the traversal
[
38
]
.

9.2
Sound Termination on Programs with Infinite Models

A different source of non-termination arises from programs with infinite three-valued models, as when the query
p(?X)
is made to the following program.

{\mathbf{P}_{InfModel}:}

p(f(?X)) :- p(?X).

p(a).

Sound termination for WFS is possible using
restraint

[
18
]
a type of answer abstraction that sets the truth value
of abstracted answers to
u
. For instance, when using
restraint at term depth greater than or equal to two, the query
p(?Y)
posed to
P_{InfModel}
would produce
p(a)
and
p(f(a))

both as
true
answers, along with
p(f(f(?X)))
with truth value

u
. In this way, an informationally sound approximation to
the goal
p(?Y)
is provided. Specifically, when using restraint
to evaluate a query to a program
P
, all atoms proved
true
or
false
by
{\mathcal{}E}
rgoAI are
true
of
false
in the well-founded model of
P
.
However some atoms that are
true
or
false
in the well-founded model
may be
u
in
{\mathcal{}E}
rgoAI. Through restraint,
{\mathcal{}E}
rgoAI supports a fully
semantic approach to bounded rationality.

Answer abstraction can be requested with the help of the
answersize

restraint in the
setruntime
directive. Loading into
{\mathcal{}E}
rgoAI the
small program below,

?- setruntime{answersize(3,abstract)}.
p(f(?X)) :- p(?X).
p(a).
?- p(?X). // query

produces the following answers:

?X = a
?X = f(a)
?X = f(f(a))
?X = f(f(f(a)))
?X = f(f(f(?_h1945(?_h1946)))) - undefined

Without the answer abstraction (i.e., without the
setruntime

directive), the above query does not terminate.

9.3
Tripwires

From the viewpoint of
{\mathcal{}E}
rgoAI, both subgoal abstraction and restraint
based on answer abstraction are instances of
tripwires
. A
tripwire allows a developer to specify that a property of an
evaluation should cause some intervention from the system. The
intervention may be an automatic change in the resolution method, such
as with call abstraction or restraint; or the intervention could throw
an error; or suspend the computation for debugging.
{\mathcal{}E}
rgoAI also
supports a
max answers
tripwire that allows a user to set a
limit on the number of answers a given subgoal
S
may have. If this
limit is reached, a new answer
A_{S}
is added that is a variant of

S
, the truth value of
A_{S}
is set to
u
and
S
is
completed. Afterwards queries to
S
will return all of the derived
answers for
S
, as well as
A_{S}
. The effect is to change the
closed-world assumption for
S
from using
false
as default to using

u
as default. Another kind of tripwire is the ability to
time out a goal
G_{costly}
that may either call
{\mathcal{}E}
rgoAI or an external
system. The tripwire can be set either to add an answer
A
that is a
variant of
G_{costly}
with truth value
u
, or to throw an
exception. Finally, as mentioned in Section
7
, a
negative subgoal that cannot be ground via delaying its execution can
be given the truth value
u
instead of throwing an error.

In each of these types of tripwire a developer can weigh the benefit
of a bounded execution time against the possibility of deriving a set
of answers that are informationally sound but not complete. It is
because of such uses that we denote the third WFS truth value as

u
, since it can mean as
unknown
in addition to
undefined
.
26
26

26

In the case of procedural and other non-logical
modules, the action associated with a tripwire can be to throw an
error, or to call a user-defined handler.

Scalability and Performance

Because
{\mathcal{}E}
rgoAI is based on WFS it can be expected to be more
scalable than KRR systems such as ASP or description logic solvers
on transitive closure and other WFS-style queries. Indeed, a recent
paper benchmarks transitive queries, comparing XSB’s tabling both to
the ASP solver Clingo and to the Datalog system Soufflé, showing
excellent performance by tabling over a variety of
graphs
[
23
]
. One reason for this is that XSB, like
{\mathcal{}E}
rgoAI,

graph coloring can be directly coded in
{\mathcal{}E}
rgoAI in a declarative
manner,
{\mathcal{}E}
rgoAI’s search strategy will perform worse than that of
Clingo or other ASP systems.

Building on these results, we compare
{\mathcal{}E}
rgoAI’s scalability and
performance to that of XSB’s tabling. We demonstrate that despite the
overhead of HiLog, frames, instantiation delay,
support for dynamic KRR, and other features,
{\mathcal{}E}
rgoAI remains within an
order of magnitude of tabled Prolog.

12
Discussion

{\mathcal{}E}
rgoAI is a multi-paradigm logic programming system that makes
radically different choices from virtually all other logic programming
systems. We have presented a few of these features, including
frames and inheritance for object-oriented logic programming based on
a solid semantics; HiLog predicates and terms
integrated into a powerful module system;
argumentation theories, the handling of unsafe queries, logical
approach to updates and management of change, along with support for
termination and bounded rationality. We have not covered in detail
important features such as explanation; non-termination analysis;
user-defined functions; quantified logical formulas in rule bodies and
heads; typed variables and type constraints;
and many other features of the
{\mathcal{}E}
rgoAI language.

{\mathcal{}E}
rgoAI is a significant system in itself, but also a testbed for
features that may be suitable for Prologs or other logic programming
paradigms. For instance, the implementation of HiLog (Section
4
) may extend well to Prologs like SWI, whose
just-in-time indexing can adapt to the extra indexing burden required
by the HiLog and frame transforms
(Definition
2
). Transaction Logic
(Section
8
) with non-recursive update rules can be
implemented in Prolog via backtrackable dynamic code with hooks to
call integrity constraints. Indeed the implementation of
{\mathcal{}E}
rgoAI has
shown that backtrackable updates can be implemented on top of regular

assert/1
and
retract/1
quite efficiently.
However, a more complete implementation of
Transaction Logic requires tabling of the
execution traces
of
transactions.
This is hard
to do efficiently, although
[
15
]
is a good step in this
direction.
The F-logic frames and classification hierarchies, whose compilation
into Prolog was outlined in Section
3.4

mainly requires compiler and reader extensions rather than engine
modifications, particularly in Prologs with strong
tabling and indexing.
