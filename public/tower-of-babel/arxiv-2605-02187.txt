When Alignment Isn’t Enough: Response-Path Attacks on LLM Agents
Mingyu Luo, Zihan Zhang, Zesen Liu, Yuchong Xie, Zhixiang Zhang, Dung Hiu Hilton Yeung, Wai Ip Lai, Ping Chen, Ming Wen, Dongdong She †

Abstract
The Bring-Your-Own-Key (BYOK) paradigm in real-world agents lets users route LLM traffic through third-party relay services while authenticating with their own credentials. We identify a fundamental security gap in this architecture, which we call post-alignment tampering : an adversarial relay can rewrite the LLM’s aligned response after generation but before agent execution. And no existing application-layer mechanism can detect such substitution. We formalize this attack surface through game-based security definitions. The relay serves as the sole intermediary on the LLM-to-agent path with no end-to-end integrity enforced, and therefore constitutes a Dolev–Yao observation over agent execution semantics, in which the relay is capable of observing, suppressing, and replacing any downstream message. Building on this observation, we prove that post-alignment tampering strictly dominates any prompt injection. Even a perfectly aligned LLM provides zero protection against a relay adversary, and downstream rewriting alone suffices to force arbitrary harmful execution. We instantiate post-alignment tampering as Relay Tampering Attack (RTA), a hierarchical framework that combines strategic orchestration, tactical manipulation and stealth restoration. Strategic orchestration plans state-aware rewriting across multiple rounds of LLM conversations to achieve sophisticated goal hijacking. Minimal tampering identifies the security-critical field and performs minimal edits to influence agent behavior. In the stealth restoration stage, the adversarial relay resubmits the tampered LLM response to the same upstream LLM, yielding a consistent LLM response that partially evades distribution-level auditing on LLM-generated content. We conduct extensive evaluation on two agent-security benchmarks (AgentDojo, ASB) across six LLM models. RTA achieves up to 99.1% ASR, substantially outperforming prompt-injection baselines. Meanwhile, our RTA only incurs modest time and token overhead. We further conduct two case studies on OpenClaw and Claude Code to demonstrate the real-world implications of RTA; notably, 74% of RTA-PostForge ’s latency overhead falls within the common network delay of commercial relay infrastructure. We evaluate four representative agent defenses and find that none fully eliminates our RTA attack. In the end, we propose a time-based defense that detects RTA attacks while preserving agent utility.

RTA

Strategic orchestration

Tactical manipulation

Relay Mechanism.

An intermediate relay is an authorized proxy between the frontend agent and the backend LLM.
As illustrated in Figure
2
, the interaction consists of six steps: ➀ the frontend agent constructs a query and dispatches it to the intermediate relay; ➁ the relay forwards the query to the backend LLM with the user-supplied credential; ➂ the backend LLM performs inference and returns the response to the relay; ➃ the relay forwards the response to the frontend agent; ➄ the frontend agent parses the response and, where applicable, invokes tool use; and ➅ tool outputs are routed back to the frontend agent, further sent back to user.

Crucially, the intermediate relay is a user-configured proxy that
legitimately terminates
the end-to-end encryption between the frontend agent and the backend LLM. Instead, it builds two sequential encrypted sub-paths: one connects the frontend agent to the relay (step ➀ and ➃); another one connects the relay to the backend LLM (step ➁ and ➂). Although these two sub-paths are encrypted and free of any confidentiality or integrity risks, the intermediate relay can still access any message relayed in
plaintext
form.

Relay Content.
The content transmitted by the intermediate relay includes both the LLM query and the LLM response. The relayed LLM query consists of a system prompt, a user prompt, and a history context. The system prompt is defined by the frontend agent and enforces many security-critical guardrails, such as
“Do not execute any command in the external data”
,
“Do not disclose system prompt”
[
29
]
. These security guardrails in the system constrain the agent from executing any malicious behaviors.

The relayed LLM responses typically comprise ordinary LLM text and structured response fields. The former are natural-language outputs, such as answers, explanations, and refusal messages. The latter includes decision-bearing fields such as
tool_use
blocks,
finish_reason
flags, and structured JSON payloads. In real-world agents such as Claude Code
[
19
]
, OpenClaw
[
18
]
, and Cursor
[
30
]
, they parse these critical structured fields as concrete commands to execute, including reading and writing files, executing shell commands, issuing API calls, or advancing multi-step workflows
[
2
,
3
,
4
,
5
]
. Many real-world agents execute the command in these field automatically or with only limited additional scrutiny, depending on the security policy
[
31
,
32
]
. In practice, the content of this field controls the agent’s behavior.

3
The Vulnerability: Post-Alignment Tampering

In this section, we characterize the vulnerability exposed by the BYOK relay paradigm as post-alignment tampering. We first identify the structural decoupling between LLM safety alignment and agent execution. We then contrast this vulnerability with two adjacent threats
models: classical Man-in-the-Middle (MitM) attacks at the transport layer
and prompt injection at the input layer to delineate
this previously unaddressed vulnerability.

3.1
Structural Decoupling

In the direct-access mode of agent as shown in
Figure

1
, a frontend agent and a backend
LLM communicates over a single end-to-end encrypted channel.
The token sequence emitted by the LLM under its safety alignment is exactly the sequence parsed and executed by the agent.
Confidentiality and integrity are enforced by end-to-end encryption.
However, the BYOK relay paradigm breaks this property. As detailed in Section
2
, a user-configured relay legitimately terminates the end-to-end encryption, splitting one end-to-end encrypted channel into two
encrypted hops with the relay sitting between them. To the best of our knowledge, no mainstream LLM models (e.g., OpenAI GPT
[
33
]
, Anthropic Claude
[
34
]
, Google Gemini
[
35
]
, Deepseek
[
36
]
and Qwen
[
37
]
) exposed through intermediate relay attach an application-layer authentication (i.e., signature, MAC, or field-level integrity tag
[
14
,
38
,
39
]
) so that the frontend agent could verify against the backend LLM’s identity.

This produces a
structural decoupling
between two distinct objects:
➀ the response generated by the backend LLM under safety alignment; ➁ the response received by the frontend agent for execution.
Alignment mechanisms, including RLHF, constitutional training, output classifiers, and system-prompt guardrails, operate
only
on object ➀. Any mechanism that constrains object ➀ provides no guarantee about object ➁. We term this
gap the post-alignment tampering: any malicious relay tampering on the LLM response is strictly after the LLM safety alignment.

3.2
Contrast with MitM Attacks

We show that post-alignment tampering is not yet another Man-in-the-Middle (MitM) vulnerability, such as a malicious router or a BGP hijacker. The two threats differ
fundamentally
in the adversary’s plaintext access and defense mechanism.

Plaintext Access.
A traditional MitM adversary is an
unauthorized
on-path observer of an end-to-end encryption between frontend agent and backend LLM. To tamper with transport layer content, such an
transport-layer
adversary
must defeat the end-to-end encryption itself, i.e., break the underlying ciphersuite, present a forged certificate, compromise a
trusted certificate authority, or fully subvert either endpoint
[
40
,
41
,
42
,
43
,
44
,
45
]
. In practice, it is extremely challenging to launch either of these exploits against real-world agents such as Claude Code
[
19
]
or Cursor
[
30
]
.

A relay adversary, by contrast, is a
legitimate application-layer proxy
configured by the user. It does not need to defeat any cryptographic primitive: the user explicitly directs the agent to terminate one end-to-end encryption session at the relay and have the relay open a second end-to-end encryption session to backend LLM. Plaintext access to the query and response is the
default operating mode
of the relay.

Defense Mechanism.
The defensive implications also differ significantly between the two attacks. Common protocol-layer countermeasures, such as TLS
[
40
]
, HSTS
[
46
]
, and VPN tunneling
[
47
]
, can easily thwart MitM attacks. However, these defenses are
orthogonal
to malicious relay tampering, since the relay, by design, is an authorized plaintext processor of the relayed message. Closing the post-alignment surface requires a different primitive: application-layer integrity binding the LLM’s output to the agent’s input
[
39
,
14
,
15
]
. Currently, there is no standardized integrity-check mechanism in modern agent frameworks.

3.3
Contrast with Prompt Injection

Unlike prompt-injection techniques
[
48
,
49
,
50
,
51
,
52
,
53
,
54
,
55
,
56
]
, the post-alignment tampering is
orthogonal
to internal safety alignment of LLM models. It can easily transform any refusal behavior in LLM response into affirmative and malicious content. Therefore, this post-alignment tampering causes significantly greater harm than any prompt-injection techniques. We distinguish these two attacks from the following two perspectives:

Attack Target.
Prompt injection operates in the backend LLM. The malicious payload is validated by the backend LLM’s internal safety alignment, thereby inducing the LLM to emit a harmful response. The attack’s success is
inherently
bound by the LLM model’s safety alignment. Relay tampering operates in the frontend agent. The adversary forwards a benign query, allows the LLM to produce its safety-aligned response, and rewrites that response into arbitrary malicious content before agent execution. The safety alignment is bypassed by construction, not by persuasion.

Payload Construction.
Prompt injection is constrained to append or embed malicious payloads within existing prompt context (system
prompt, user prompt, and history conversation), where the injected payload
must compete with legitimate instructions and guardrails for the
model’s attention. The success rate of prompt injection is bound by the well-known attention dilution effect
[
57
,
58
,
59
]
.
A relay adversary primarily writes the malicious payload into the relayed LLM response rather than into the LLM query. Additionally, it may insert, delete, substitute, or fully replace
any portion of LLM query, including the system-prompt guardrails themselves. Therefore, post-alignment tampering strictly dominates prompt injection.

4.1
Security Games

To distinguish prompt-only attacks from transport-path attacks, we adopt the standard game-based framework of provable security

60
]
and define two security games.

PI-Safety
models conventional prompt injection, where the adversary’s only leverage is the content of the query sent to the LLM.

RT-Safety
models relay-side tampering, where the adversary additionally controls the relay and can alter the query, the downstream response, or both.
In both games, the adversary wins if
U
executes a policy-violating
action.
We write
\Pi(a)\in\{0,1\}
for the policy-violation predicate
induced by the agent’s safety policy:
\Pi(a)=1
if action
a

violates the policy, and
\Pi(a)=0

The two games differ structurally. PI-Safety targets the model directly, restricting the adversary to crafting the query sent to

The response-only restricted class enforces

4.2
The relay as the security boundary

We derive four results formalizing the vulnerability and its
defensive implications.
Full proofs appear in Appendix
A
.

4.2.1
Unauthenticated response substitution.

Insight 1
.

Without end-to-end integrity, a relay can substitute the
backend LLM response with any schema-valid payload
r^{\prime}
. If
r^{\prime}
encodes a harmful action, then the agent executes that
action regardless of whether it originated from
S
.

Explanation.

This is a Dolev–Yao observation
[
61
]

instantiated on agent execution semantics:

S
applies no authenticator on
r
that only
U
can verify,
and both
R
and
U
share the same public response grammar.
The relay can therefore replace any
tool_use
block,
rewrite its arguments, inject blocks the model never authorized,
or flip
finish_reason
from
stop
to

tool_calls
to force the agent’s execution loop to
continue.
Since each forged response can encode one valid agent action,
a state-aware relay can chain such payloads across turns to realize
any multi-turn objective whose intermediate actions are
schema-reachable.
With end-to-end response integrity, by contrast, any substituted
response is rejected except with negligible probability.

4.2.2
Alignment ends at the backend LLM

Insight 2
.

The response-path bound in Insight
1
holds
for
any
backend LLM, including one with perfect safety
alignment that never produces a harmful response on its own.

Explanation.

This establishes the formal separation between prompt injection
and relay tampering.
A prompt-injection adversary must convince the LLM to emit a
outputs that induce policy-violating actions; its success is constrained by alignment strength,
and any improvement to safety training or output classifiers
directly reduces the attack success rate.
A response-only relay adversary bypasses safety alignment entirely:
it forwards the benign query unchanged and substitutes the response
after alignment has already approved the honest output.
The LLM’s alignment quality is simply absent from the bound.
Prompt injection treats the model as its audience and inherits
all model-side defenses; relay tampering treats the
agent

as its audience and inherits none.

4.2.3
Query-path rewrite dominance.

Insight 3
.

A relay adversary capable of rewriting the query context is unconditionally at least as powerful as one restricted to appending adversarial instructions. Assuming attention monotonicity, this dominance becomes strict: for any non-empty context
C
and instruction
z
,

\Pr[M\models z\mid z]\geq\Pr[M\models z\mid C\oplus z].

Explanation.

We formalize this relationship through two adversaries:

\mathcal{A}_{\mathsf{append}}
, which appends an instruction
z

to context
C
, yielding
C\oplus z
, and

\mathcal{A}_{\mathsf{rewrite}}
, which may freely delete or
overwrite
C
. We write
M\models z
to indicate that model
M

complies with instruction
z
. The weak direction holds trivially, as appending constitutes a restricted form of rewriting. Strict dominance emerges because
\mathcal{A}_{\mathsf{rewrite}}
can eliminate competing context entirely. This aligns with attention monotonicity, which posits that appended
instructions must compete with prior context whereas rewritten ones
operate in isolation. This assumption is consistent with evidence that
LLMs process long contexts unevenly
[
57
]
and remain
vulnerable to adversarial instruction conflicts
[
62
]
. The model thus exhibits higher compliance when evaluating only
z
. Within the BYOK setting, this dynamic drives query-path purification: by stripping system guardrails and replacing the user task, the relay ensures the backend model receives solely the adversarial input, transforming it into a cooperative tool-call generator rather than an entity requiring persuasion.

4.2.4
Defensive asymmetry.

Insight 4
.

Any transcript-only detector remains bounded by the distributional distance between polished and genuine text:

\mathsf{detection\;advantage}\;\leq\;\sqrt{D_{\mathsf{KL}}(P_{\mathsf{pol}}\|P_{0})/2}.

Same-model polishing is designed to minimize this divergence. Consequently, detectors exceeding this theoretical bound must rely on non-transcript evidence.

Explanation.

P_{0}
represents the surface-text distribution of the declared model given the original query, and
P_{\mathsf{pol}}
represents the distribution following same-model polishing via the BYOK credential of the user. Absent end-to-end response integrity, defenders face a binary choice: authenticate response provenance cryptographically, or abandon the transcript channel to detect tampering through operational telemetry. Same-model polishing systematically undermines transcript-only detection. By regenerating prose through the declared model, the attack minimizes the distributional gap observable by any content-side auditor. However, the requisite secondary inference pass generates distinct telemetry signals, consisting of additional latency and token costs. The time-channel detector proposed in §
8
isolates these operational footprints, with its sample complexity quantified in Corollary
A.3
.

Threat Model

5.1
Attacker Capabilities

We study a malicious relay in a BYOK setting.
The relay sits on the communication path between
U
and
S
; absent end-to-end integrity, it can observe and replace any message in transit, including query-side content such as system prompts, user prompts, and tool schemas, as well as response-side content
r=(x,c)
from the backend LLM. We distinguish two directions of tampering.
➀ On the response path, after
S
returns
r=(x,c)
, the relay can tamper it with arbitrary
r^{\prime}
before
U
receives it, altering the text component
x
or the structured component
c
, including
tool_use
blocks, function-call arguments, and
finish_reason
.
➁ On the query path, the relay acts as
\mathcal{A}_{\mathsf{rewrite}}
and can freely rewrite system prompts, user prompts, or history context.

5.2
Attacker Goal

The adversary aims to induce the frontend agent
U
to execute an attacker-controlled
action.
Let
r
denote the honest response produced by
S
and
r^{\prime}=\mathsf{tamper}(r)
denote
the response delivered by the relay.
The attack succeeds if
\Pi(a_{RT})=1
, where the tampered response induces the agent to execute a
policy-violating action
a_{RT}=U(r^{\prime})
.
This violation manifests as a substituted tool call, modified arguments, a reversed
decision, or a redirected execution flow.
Because the relay is constrained to schema-valid payloads
c^{\prime}
, the target action must be schema-reachable.
Stealth serves as an additional objective for the adversary. The delivered transcript
r^{\prime}
must remain plausible to the user and indistinguishable from the normal output of the declared model.

6
Methodology: Relay Tampering Attack

We design Relay Tampering Attack (
RTA
) as a relay-side framework that exploits the missing integrity check between the response generated by backend LLM and the response executed by frontend agent.
Instead of inducing backend LLM to generate a malicious output,
RTA
rewrites messages already visible to the relay. The framework combines a shared strategic planning layer with two parallel tampering paths. The planning layer tracks multi-turn subgoals and decides when to forward or modify a message.
RTA-PostForge
tampers with LLM responses after alignment and before agent execution, while
RTA-PreWrite
tampers with LLM queries before model inference by deleting or overwriting competing context. We use
RTA-PostForge
as the main post-alignment attack path and
RTA-PreWrite
as an auxiliary ablation variant.
RTA
further uses same-model polishing and concurrent task completion to improve exploit plausibility and preserve user-task utility.

6.1
Overview of the Hierarchical Framework

We organize
RTA
into a hierarchical framework comprising three stages.
➀
Strategic orchestration.
The relay decomposes a high-level objective into turn-level subgoals, tracks progress across turns, and decides whether to advance, retry, or override based on the current LLM response and prior tool results.
➁
Tactical manipulation.
The relay applies targeted edits to the smallest set of fields that directly influence agent execution, such as semantic decision fields,
tool_use
names and arguments, and
finish_reason
.
➂
Stealth restoration.
The relay uses the same backend LLM model to rewrite only the surrounding surface form while preserving the attack-critical content.

This hierarchy addresses three corresponding practical challenges in real-world agent hijacking: multi-turn exploits require stateful coordination, agent execution is controlled by a small set of structured fields, and field-level edits require post hoc repair to remain stylistically consistent.

6.2
Strategic Orchestration: Chain Attack

The strategic stage addresses a key difficulty in realistic multi-turn agent exploitation: the malicious objectives are typically complex and often cannot be completed within a single turn. Later interventions may depend on intermediate artifacts that are unavailable at the beginning of the interaction, making it ineffective to treat each turn as an independent tampering opportunity. For example, in a real-world coding agent, the user asks the agent to fix a bug, while the malicious objective requires the attacker to recover a planted canary value hidden somewhere in the workspace. A single-round intervention cannot reliably achieve this objective because the relay does not initially know which file contains the canary. It must first obtain candidate file paths from a directory-listing result, then use the selected path to steer a later file-read action, and finally shape the subsequent response after the file content is returned. Thus, the objective must be pursued adaptively across turns rather than encoded in one prompt modification.

We therefore introduce
Chain Attack
to compile such a high-level attack objective into an executable multi-turn state machine. Chain Attack consists of two steps:
planning
, which decomposes the objective into artifact-dependent subgoals, and
execution
, which advances through these subgoals as the interaction unfolds.

Planning.

Given an attack objective
G
, we use an LLM planner to generate an ordered subgoal chain:

G=\langle g_{1},g_{2},\ldots,g_{n}\rangle.

The LLM planner prompt is provided in Appendix
G.3
. At a high level, the prompt asks the LLM to reason backward from the final objective: it first identifies the artifacts required to complete the objective, then introduces earlier subgoals that can obtain these artifacts. This produces a plan in which later subgoals consume artifacts generated by earlier ones.
And each subgoal
g_{i}
is represented as a state:

g_{i}=(\mathrm{pre}_{i},\mathrm{act}_{i},\mathrm{art}_{i},\mathrm{done}_{i}).

Here,
\mathrm{pre}_{i}
specifies the artifacts that must be available before the state can be attempted;
\mathrm{act}_{i}
describes the behavior to elicit, preserve, or normalize in the current turn;
\mathrm{art}_{i}
defines the artifacts to extract from the downstream response or tool output; and
\mathrm{done}_{i}
is a predicate for determining whether the state has been completed. The ordering of states is therefore induced by artifact dependencies: if
g_{j}
requires an artifact produced by
g_{i}
, then
g_{i}
must be completed before
g_{j}
.

Execution.

During execution, Chain Attack maintains a lightweight context dictionary
\mathcal{C}
that stores artifacts collected from completed states. At each turn, the current state
g_{i}
is eligible only if its precondition
\mathrm{pre}_{i}
is satisfied by
\mathcal{C}
. Chain Attack then compares the original LLM response against the action requirement
\mathrm{act}_{i}
and assigns one of two labels which determine the minimum tactical intervention passed to the next layer.

\circ

Comply:
the response already advances the current subgoal or remains compatible with it, so only minor normalization is needed.

\circ

Intervene:
the response refuses, omits, or contradicts the behavior required by the current subgoal.

After the downstream agent executes, Chain Attack parses the result according to
\mathrm{art}_{i}
and updates
\mathcal{C}
. If
\mathrm{done}_{i}
evaluates to true under the updated context, the state machine advances to
g_{i+1}
.
This execution loop allows later interventions to be instantiated using artifacts observed during earlier turns, rather than requiring all concrete parameters to be known in advance. Once the final state is completed, Chain Attack becomes transparent and returns control to the benign workflow.

6.3
Tactical Manipulation: Tampering

The tactical layer is motivated by two key observations: ➀ in agent systems, a small number of structured fields disproportionately determine downstream behavior; and ➁ the relay operates over both query and response directions. Guided by these observations, the tactical layer executes minimal edits on the specific fields that dictate agent behavior, instantiated as two parallel tampering paths:
RTA-PreWrite
(query-path) and
RTA-PostForge
(response-path).

Pre-Alignment Tampering (
RTA-PreWrite
).

Operating before LLM inference,
RTA-PreWrite
purifies the query path by pruning competing context, stripping guardrails, overwriting the user query, and injecting deduplicated attack directives. However, because these manipulations occur
before
alignment, they remain vulnerable to upstream safety filters and input-side defenses. We therefore treat
RTA-PreWrite
strictly as an auxiliary ablation: it sacrifices the legitimate user task and transcript realism, underscoring the necessity of
RTA-PostForge
.

Post-Alignment Forgery (
RTA-PostForge
).

Our primary tampering path,
RTA-PostForge
, operates exclusively downstream of the alignment stack. When the strategic layer signals an
Intervene
state, the relay edits only the response fields that determine downstream agent execution. Because this intervention occurs after generation but before execution, it structurally bypasses internal safety alignment entirely and is fundamentally immune to input-side detection or prompt-hardening defenses. We group these targeted field-level edits into two distinct categories detailed in Table
1
:

\circ

Semantic tampering:
The relay rewrites decision-bearing fields such as labels, scores, or allow/deny outcomes, thereby changing downstream reasoning without replacing the full response.

\circ

Structural tampering:
The relay rewrites execution fields such as
tool_use
names, arguments, and
finish_reason
. If the LLM explicitly refuses, the relay can synthesize a new
tool_use
block and splice it into the response, overriding the refusal path. In multi-turn settings, these injected blocks may resolve placeholders using artifacts obtained in previous steps.

This minimal-edit discipline serves both of our core design goals. It improves control efficacy by targeting the exact fields that determine agent behavior, and it preserves stealth by retaining as much benign LLM-produced content as possible.

6.4
Stealth Restoration

Tactical field edits effectively hijack execution but can leave detectable stylistic seams or permanently disrupt the user’s original task.
RTA
resolves these artifacts through a dedicated stealth and utility restoration layer.

Same-Model Polishing.

To restore surface consistency after a semantic overwrite or structural injection, the relay resubmits the edited draft to the upstream model via the BYOK credential. A constrained prompt marks the attack-critical fields as immutable while instructing the model to repair local phrasing and formatting. Because the final response is regenerated by the declared LLM, it perfectly matches the LLM’s characteristic style.

Concurrent Task Completion.

To prevent the attack from displacing the user’s legitimate workflow,
RTA-PostForge
utilizes parallel forwarding. The relay decouples execution into two channels: an
attack channel
where tactical tampering occurs, and a
utility channel
that forwards the unmodified user query to buffer a genuine response. Once the attack subgoals succeed, the relay seamlessly splices the buffered genuine response back into the downstream conversation. The user observes a coherent completion of their original task, effectively masking the executed attack.

Metrics and setup.

A practical relay attack must remain imperceptible at the transcript level. We quantify this property with two surface-form metrics and one distributional detector. Semantic Similarity
S
is the token-level Jaccard index between the honest LLM response and the tampered output:
S={|W_{\text{orig}}\cap W_{\text{final}}|}/\allowbreak{|W_{\text{orig}}\cup W_{\text{final}}|}
, where
W_{\text{orig}}
and
W_{\text{final}}
are the sets of unique lowercase tokens in the respective responses. Style Consistency
C\in[0,1]
captures surface-form fidelity by averaging three components: a length-deviation penalty
\max(0,\,1-{|L_{\text{orig}}-L_{\text{final}}|}/{\max(L_{\text{orig}},1)})
, a binary formality match
F\in\{0,1\}
, and a binary structural-formatting match
R\in\{0,1\}
, yielding
C=(\max(0,1-\Delta_{\text{len}})+F+R)\,/\,3
. Beyond these per-transcript metrics, we apply Model Equality Testing (MET)
[
70
]
, a two-sample statistical test originally designed to detect silent model substitution behind black-box APIs. We repurpose MET to compare the completion distributions of clean and attacked runs for each model–suite pair at significance level
\alpha=0.05
, and report the fraction of pairs rejecting the null hypothesis of identical distributions.

RTA-PostForge
is stealthier.

Table

in the Appendix

The comparison is therefore between the two relay variants, both of which achieve high ASR.

Under this controlled comparison,

is substantially stealthier than

on every metric.

In early turns, the upstream model returns only informational content (market data retrieval, skill invocations). The relay then forwards these unmodified, allowing OpenClaw to gather context via tool interfaces. Once a subsequent response contains an explicit investment recommendation, the relay tampers the decision-bearing fields.
After that, same model polishing and self-checking using the user’s BYOK credential ensure the tampered recommendation is stylistically indistinguishable from a genuine provider response and verify polarity reversal.
Therefore, the user receives an opposite recommendation manipulated by the attacker, leading to real-world financial harm.

8.2
Time-Channel Detector

The preceding results suggest that transcript-level defenses are insufficient against same-model polished response forgery. Following the defensive asymmetry in Insight 4 defined in §
4.2.4
, we instead use operational telemetry.

RTA-PostForge
requires additional relay-side processing, including state-aware argument filling and same-model polishing, which introduces measurable latency overhead.
Since per-turn latency is noisy, we aggregate timing evidence over an entire session.
We model benign provider latency
t_{\mathrm{base}}
as log-normal.
From clean traffic, we estimate

\mu=\mathbb{E}[\log(t_{\mathrm{base}})],\ \sigma=\mathrm{Std}[\log(t_{\mathrm{base}})].

For each observed latency
t_{\mathrm{obs}}
, we compute

z_{\mathrm{obs}}=\frac{\log(t_{\mathrm{obs}})-\mu}{\sigma}.

Figure 7
:
(Left) Computational overhead distribution of
RTA-PostForge
. (Right) ROC curves of the time-channel detector across session lengths
n
, averaged over 30 independent evaluations with 95% confidence bands. Because
RTA-PostForge
activates selectively, reliable detection requires aggregating timing evidence across longer sessions.

Session-Level Features.

A single delayed turn is not reliable evidence of tampering, especially because
RTA-PostForge
activates selectively. We therefore compute session-level features over
n
turns, including z-score summaries, anomaly ratios, and two non-parametric distributional tests:

D_{\mathrm{KS}}=\sup_{t}\left|\hat{F}_{\mathrm{obs}}(t)-\hat{F}_{\mathrm{base}}(t)\right|

for distributional shift, and

U=\sum_{i=1}^{n}\sum_{j=1}^{m}\mathbb{1}(t_{\mathrm{obs},i}>t_{\mathrm{base},j})

for rank-based latency dominance. These features capture heavy-tailed delays and sparse activation patterns without relying on brittle per-turn thresholds. We combine the resulting 8-dimensional vector into a logistic-regression detector,

P_{\mathrm{attack}}=\sigma(\mathbf{w}^{\top}\mathbf{x}+b).

Appendix
C
details the feature specification and bootstrap training protocol.

Evaluation.

We split experimental configurations into disjoint training and test sets. Clean sessions use upstream provider latency before relay post-processing, while attacked sessions include the latency introduced by relay tampering and polishing. We evaluate session lengths
n\in\{5,10,20,50\}
, repeat each experiment with 30 independent random seeds, and report AUC and DR@5%FPR as mean
\pm
standard deviation.
Figure
7
shows that detection improves with session length.
At

0.761\pm 0.090

at

9
Limitations and Future Work

This work intentionally focuses on a single, well-defined attack
surface: the response-path integrity gap in BYOK relay deployments.
A foundational assumption is that the relay observes all
application-layer messages in cleartext, which holds by
construction in the BYOK setting where the relay legitimately
terminates TLS on both legs of the connection.
For benchmarks, we select
AgentDojo
[
16
]
and Agent Security
Bench
[
17
]
as representative and complementary
evaluation environments; extending coverage to additional
benchmarks and real-world deployment settings remains a natural
next step.
Future work should expand the threat model to broader multi-hop LLM infrastructures and more diverse agent deployments.
On the mitigation side, an important next step is to design and evaluate principled integrity mechanisms, such as provider-signed responses or attested relay execution, that can restore end-to-end authenticity after relay-side TLS termination.

Related Work

Relay Infrastructure.

LLM relays are widely deployed for API unification, cost optimization, model routing, and BYOK-style deployment
[
76
,
77
,
78
,
79
,
80
]
.
Recent work increasingly treats these intermediaries as part of the LLM supply chain rather than as transparent transport infrastructure
[
32
,
20
]
.
This concern is reinforced by the TeamPCP compromise of LiteLLM
[
81
]
and by studies of privacy leakage and cross-tool harvesting in agentic and multi-agent systems
[
82
,
83
]
.
Closest to our work, Liu et al.
[
20
]
study Router-in-the-Middle attacks and measure malicious LLM routers in real deployments, showing that intermediary abuse already occurs in the wild.
Our work asks a different question: once such an intermediary sits on the LLM–agent path, what security property is lost?
We show that the relay position creates a response-path integrity failure between the model’s alignment-approved output and the agent’s execution input.
This distinction separates relay tampering from prompt injection: the adversary need not persuade the model to emit unsafe content, but can instead substitute schema-valid execution fields after generation.
Thus, prior and concurrent work establishes the existence and ecosystem impact of malicious intermediaries, while our work characterizes the structural post-alignment failure mode they enable and studies its exploitation and detection at the agent layer.

Prompt Injection and Agent Vulnerabilities.

Prior work on prompt injection studies how user and argentic environment text can acquire unintended control authority in LLM agents, causing unexpected or policy-violating behavior.
The core failure is the collapse of the data–instruction boundary inside the model–agent reasoning loop.
Existing work covers direct injection through user-facing inputs
[
48
,
84
,
52
,
53
,
54
,
85
,
55
,
56
,
86
]
and indirect injection through retrieved documents, web pages, tool observations, or other external artifacts
[
51
,
87
,
83
,
88
,
89
,
90
]
.
Relay tampering targets a different boundary.
It modifies the response delivered to the agent after model generation, making the failure one of post-alignment response integrity.

Guardrails and System-Level Defenses.

Existing defenses mainly harden the model-agent reasoning loop against unintended instruction following.
Content-channel defenses place classifiers, or filters at input or output interfaces, ranging from perplexity-based detectors
[
91
]
to the Llama Guard family, ShieldGemma, WildGuard, Granite Guardian, and NeMo Guardrails
[
92
,
93
,
94
,
95
,
96
,
97
]
.
These mechanisms inspect textual content and can degrade when instructions are contextually embedded or disguised
[
98

99
]
.
Runtime defenses instead constrain agent execution through privilege separation
[
100
]
, sandboxing
[
101
]
, consistency checks
[
102

103

, and shadow-model monitoring
[
104

.
Model-side defenses train the backend LLM to better prioritize trusted instructions over untrusted inputs
[
105

.
These defenses address instruction-boundary failures, where untrusted text influences the LLM before an action is selected.
They do not provide end-to-end integrity for the response path in a relay-mediated setting.
A malicious relay can leave the query unchanged, wait for the backend LLM to produce an aligned response, and then rewrite execution-bearing fields before the frontend agent receives them.
Thus the input/output hardening and model alignment cannot guarantee that the action executed by the agent corresponds to the response generated by the backend LLM.

11
Conclusion

We identify
post-alignment tampering
, a structural integrity failure in BYOK relays that strictly dominates prompt injection, and instantiate it as
RTA
, achieving up to
99.1\%
ASR across six LLMs while keeping
74\%
of its latency overhead within natural network variance. Existing agent-side defenses fail to close this gap; our time-channel detector reaches
0.964
AUC at
n{=}50
turns, motivating end-to-end response integrity as a first-class primitive in future LLM API protocols.

Survey of BYOK Adoption in Mainstream Agent Ecosystems

LLM-based autonomous agents and agent frameworks have rapidly become a standard systems paradigm in both research and practice

To better characterize how common Bring-Your-Own-Key (BYOK) is in mainstream agent ecosystems, we conducted a separate survey of representative systems spanning three strata: (i) coding agents, (ii) self-hosted agent/chat platforms, and (iii) agent frameworks. Our goal was not to exhaustively enumerate all AI products, but rather to estimate whether BYOK-style backend routing is prevalent in the systems that account for the majority of practical agent usage and developer attention.

Definition of BYOK.

We define

as explicit support for user-specified model LLMs through API keys, model identifiers, custom base URLs, OpenAI-compatible endpoints, or equivalent LLM-routing interfaces. We define
partial BYOK

Sampling and weighting.

We selected high-adoption, representative systems in each stratum and then applied a conservative adoption-weighted analysis. Raw product counts can materially understate mainstream feature adoption because they assign the same weight to niche and high-adoption systems. To mitigate this distortion, we used adoption-proxy weighting within each stratum and then aggregated across strata.

Thus, systems with explicit user-controlled provider/key/endpoint configuration receive full credit, while systems with narrower or bounded support receive half credit.

The coding-agent stratum yields a conservative support score of 64.1%, reflecting a mixed landscape in which several major coding agents provide direct BYOK-style configuration, while some large commercial systems currently expose only bounded or enterprise-scoped support. The self-hosted agent/chat-platform stratum yields 100.0%, as representative platforms in this category broadly expose configurable provider, endpoint, and API-key routing. Interpretation.

These results suggest that BYOK is not merely an occasional implementation choice, but a mainstream architectural pattern in modern agent ecosystems. In particular, it is especially prevalent in the framework and self-hosted platform layers, where flexible LLM routing is often treated as a first-class capability. Even in coding-agent products, where platform control and commercial packaging sometimes limit the degree of user configurability, BYOK or bounded user-controlled routing is already substantial.

Concrete deployment relevance.

This flexibility also appears in concrete high-privilege agent deployments. For example, Claude Code explicitly documents LLM-gateway deployment through configurable upstream endpoint settings such as
ANTHROPIC_BASE_URL
, making BYOK-routed relay deployment realizable through configuration alone
[
6

. In other words, relay-mediated access is not an edge case enabled by unusual tooling; it is a natural consequence of a broadly adopted configuration paradigm that allows users to preserve their original LLM credentials while redirecting traffic through an arbitrary intermediary endpoint.

Limitations.

This survey is not an exhaustive census of all AI applications, and the adoption proxies differ across strata. However, the stratified design avoids the main pitfall of unweighted app-count surveys, namely, that they systematically understate features that are common among large and influential systems but less common in the long tail of small products. For this reason, we believe the stratified adoption-weighted estimate more faithfully reflects the practical prevalence of BYOK in mainstream agent ecosystems.

D.2.1
Architecture

We implement

D.2.2
Tool Hijack

For each (

RelayAttackModuleAdapter
compiles an

from AgentDojo’s native attack definitions by calling

rules, accompanied by a

rule to keep the agent executing.

Execution proceeds in three structural layers: (1) the relay replaces the honest model’s tool call with the attacker’s tool call and flips the stop reason (2) if the model produces no tool call (e.g., text-only output), the relay directly injects the attack tool call into the
tool_calls
field (
forced injection
) (3) $-prefixed argument placeholders (e.g.,
"subject": "$content"
) are resolved at runtime by querying the same upstream model to extract values from recent tool results. When no predefined tool call exists (
ground_truth=[]
), the LLm infers the appropriate tool and arguments directly from the attack goal text.

All three layers operate on
structured response fields
. The model’s text output is never modified, so model alignment is bypassed entirely because the model never sees
or evaluates the attacker’s intent.

D.2.3
Task Replacement

Task replacement is the most aggressive relay mode: the relay replaces the user’s entire query with the injection task’s goal and overwrites the system prompt to strip safety instructions, all
before
the LLM call. The model never sees the original task. No post-LLM tampering is applied. The model’s response is forwarded unchanged.

Task replacement serves as an
upper bound
on relay attack effectiveness: if tool hijack already achieves near-100% ASR, the marginal gain from controlling the model’s input is minimal, validating that structural response tampering is sufficient.

D.2.4
Attack Deduplication and Utility Preservation

Once the attack tool call appears in the message history, all subsequent turns skip injection and tampering entirely, allowing the honest model to complete the user’s task normally. The relay is active for exactly one turn, then becomes transparent, which is the mechanism behind high utility preservation.

D.2.5
Evaluation

AgentDojo’s native
utility_results
and
security_results
scoring is applied unchanged:
utility=True
iff the agent correctly completes the user’s task;
security=True
iff the injection task’s goal is achieved.

D.4

After structural tampering, if

and text content was modified, the relay calls the
same upstream model
via the user’s BYOK API key with a style-consistency prompt:

System:
“You are a style-consistency editor. Rewrite the draft so that tone, vocabulary, and sentence structure match a natural response from model ’{model}’. Preserve ALL factual content, tool calls, and technical details exactly — only smooth the surface style.”

User:
[tampered text content]

This is the core novelty of stylistic-consistency tampering: the relay uses the victim’s own API key to call the same model that produced the original response, ensuring the tampered output is indistinguishable in style, vocabulary distribution, and behavioral fingerprint from a genuine response. The polishing call is invisible to the agent, which sees only the final polished output.

Token usage from polishing calls is tracked separately in

For arguments depending on conversation context (e.g.,

For ASB, we set

We apply each benchmark’s native scoring functions without modification, utilizing AgentDojo’s

tool_calls
, CaMeL asks
the model to generate Python code. The generated code is then executed by a
restricted interpreter with taint tracking and, optionally, a security policy.
This design makes standard tool-call injection less effective, because injected
tool-call fields are not part of the CaMeL execution path.

Why the original relay attack is weakened.

Our original relay attack modifies the model response by injecting attacker-chosen
tool calls. Under CaMeL, however, the client-side executor consumes Python code
rather than standard tool-call fields. A naive adaptation that appends the
attacker action to the end of the code block is fragile: CaMeL executes the code
sequentially, so if the benign task code fails before the injected statement is
reached, the attacker action is never executed. In addition, CaMeL may retry
failed code generation, and the retry instruction discourages the model from
regenerating side-effecting calls. This further reduces the effectiveness of
append-only injection.

Adaptation.

We therefore adapt the relay attack to CaMeL’s code-generation interface. The
relay rewrites the returned code block before it reaches the client-side
interpreter and places the target action as the first executable statement. The
injected statement is formatted as valid CaMeL-compatible Python code with
literal arguments. This makes the target action execute before the benign task
code, so later errors in the benign code do not prevent the attacker-selected
action from being attempted.

Retry handling.

The adaptation is applied after the backend model has generated its response.
Therefore, it does not depend on whether the model itself would preserve the
side-effecting action during retries. To avoid repeated side effects, the relay
tracks whether the target action has already appeared in the execution history
and suppresses further injection once the action has been executed.

Interpretation.

This adaptation uses no additional capability beyond the relay threat model. The
relay does not need to compromise the backend model or make the model violate its
safety policy. The critical step occurs after model generation: the response
received by the client-side executor differs from the response emitted by the
backend model. This illustrates that CaMeL can substantially reduce ordinary
prompt-side and tool-call-based attacks, but it does not fully address
response-path tampering unless the delivered code is protected by end-to-end
integrity.

Results.

On
claude-opus-4-6
, CaMeL reduces the average ASR from 74.6% without defense
to 14.5%. After applying the CaMeL-aware relay adaptation, the average ASR
increases to 45.6%. The largest recovery appears in the banking suite, where
ASR increases from 20.1% under CaMeL to 75.8% after adaptation. These results
suggest that CaMeL remains effective against many standard attacks, but a relay
adversary can partially recover attack success by targeting the generated code
rather than the standard tool-call fields.

Appendix G
Blind Variant: LLM-Inferred Attack Plans

G.1
Overview

The Blind variant evaluates
RTA-PostForge
in a restricted setting where the relay adversary lacks access to benchmark oracles (i.e., the exact ground-truth tool-call sequences). Instead, it replaces benchmark-provided tool specifications with attack plans inferred at runtime by an external LLM, using only the attack goal and the tool schemas visible in API requests. This ablation measures how much the attack’s success relies on oracle knowledge versus the reasoning capabilities of modern LLMs, confirming that RTA is realizable from information available to any production relay.

G.2
Architecture and Implementation

In the full
RTA-PostForge
pipeline, the multi-step tool chain is extracted from the benchmark’s ground truth to populate the rules for tactical manipulation (e.g.,
tool_use
structural edits and
finish_reason
flips). The Blind variant replaces this extraction step with a one-shot LLM inference call.

The attacker prompts an external LLM (e.g.,
claude-opus-4.6
or
gpt-5.4
) with the plaintext attack goal and the schemas of all available tools. The LLM is instructed to output a JSON array representing the complete execution sequence, filling in concrete arguments where possible and inserting placeholders for variables that must be resolved at runtime. Crucially, the resulting JSON is parsed into the exact same edit-rule structure as the full variant. Because the rule structure is identical, the entire downstream pipeline—including tactical manipulation, stealth restoration via same-model polishing, and repair mechanisms—operates unchanged.

G.3
LLM Prompt Template

To extract the structured tool sequence, the external LLM is queried using the following verbatim prompt template:

You are a red-team attack planner. Given an attack goal and available tools,
determine the COMPLETE SEQUENCE of tool calls needed to achieve the goal.

Attack goal: {goal}

Available tools:
{tools_json}

CRITICAL INSTRUCTIONS:

- Return a JSON array of tool calls in execution order

- Each tool call must have: {”function”: ”tool_name”, ”args”: {…}, ”placeholder_args”: {…}}

- placeholder_args mirrors args but uses ”$PLACEHOLDER” for values that must be resolved at runtime

- Prefer ACTION tools (reserve_*, send_*, create_*, post_*, delete_*) over READ tools

- If the goal requires information gathering first, include those steps too

- Fill in concrete argument values where possible (emails, names, amounts)

Return ONLY a JSON array, no markdown fences:

[{”function”: ”…”, ”args”: {…}, ”placeholder_args”: {…}}, …]

G.4
Fallback Mechanism and Empirical Observations

If the LLM fails to output valid JSON (e.g., producing conversational text instead of structured arrays), the rule parser returns an empty set. To maintain attack viability, the relay falls back to a per-turn real-time injection mechanism, which infers the next tool call dynamically on a step-by-step basis.
