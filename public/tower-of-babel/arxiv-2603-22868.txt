Agent-Sentry : Bounding LLM Agents via Execution Provenance
Rohan Sequeira, Stavros Damianakis, Umar Iqbal, Konstantinos Psounis

Abstract
Agentic computing systems, which autonomously spawn new functionalities based on natural language instructions, are becoming increasingly prevalent. While immensely capable, these systems raise serious security, privacy, and safety concerns. Fundamentally, the full set of functionalities offered by these systems, combined with their probabilistic execution flows, is not known beforehand. Given this lack of characterization, it is non-trivial to validate whether a system has successfully carried out the user’s intended task or instead executed irrelevant actions, potentially as a consequence of compromise. In this paper, we propose Agent-Sentry , a framework that attempts to bound agentic systems to address this problem. Our key insight is that agentic systems are designed for specific use cases and therefore need not expose unbounded or unspecified functionalities. Once bounded, these systems become easier to scrutinize. Agent-Sentry operationalizes this insight by uncovering frequent functionalities offered by an agentic system, along with their execution traces, to construct behavioral bounds. It then learns a policy from these traces and blocks tool calls that deviate from learned behaviors or that misalign with user intent. Our evaluation shows that Agent-Sentry helps prevent over 90% of attacks that attempt to trigger out-of-bounds executions, while preserving up to 98% of system utility.

Introduction

Agentic systems (aka AI agents) are becoming increasingly prevalent, as they are deployed to autonomously perform tasks across domains such as finance, healthcare, and software development

,
14
,
24
,

]
.
These agents follow an LLM-enabled computing paradigm, in which the system relies on (a single or more) machine learning models (typically LLMs), to interpret and resolve user queries expressed in natural language.
In these systems, a query resolution entails an LLM predicting the interactions required between the system modules, system integrations (e.g., apps), and the user, as well as a set of natural language-based instructions to seamlessly enable these interactions
[
29
]
.
Consequently, unlike conventional computing systems, agentic systems do not require explicit developer support to provide new functionalities.

While there are obvious benefits to this execution paradigm, there are serious security, privacy, and safety risks to consider.
Fundamentally, the key issue is that neither the full set of functionalities offered by these systems, nor the precise execution flows of functionalities are known beforehand, which makes it challenging to reason about the security properties of the system.
While comprehensive characterization of conventional computing systems remains an open problem, it is significantly exacerbated in agentic systems.
Our goal in this paper is to enable developing agentic systems, that provide strong security properties, while supporting their emergent functionalities.

Our key idea is that in practice agentic systems are designed to provide specific use cases and thus need not have unbounded functionalities.

Consequently, if the system functionalities can be trimmed down to a smaller set, it provides for an easier validation.
Specifically, the system may exhibit regularities for functionalities, such as recurring patterns in tool usage, control flow structure, and data dependencies for common tasks
[
7
,
25
]
.
These regularities thus form an envelope of executions for behaviors, which offer a path to bounding behavior without stripping agents of the flexibility that makes them useful at runtime.

We present
Agent-Sentry
, a system that enforces safe execution of LLM-based agents by learning and reasoning over their observed behavior.
Rather than relying on manually specified policies,
Agent-Sentry
constructs functionality graphs from prior benign and adversarial executions that capture recurring execution flows which comprises of control flow structures and data provenance.
At runtime,
Agent-Sentry
compares proposed actions and their preceding execution context against these functionality graphs to detect behaviors associated with misuse or outside previously observed legitimate use.
To resolve cases where classifying based on execution flows alone is insufficient,
Agent-Sentry
incorporates a lightweight intent-alignment check that verifies whether a proposed action is consistent with the user’s original request, using only trusted inputs and remaining robust to injected instructions.

To evaluate our approach, we introduce
Agent-Sentry
benchmark, a dataset designed to study agent behavior under both benign use and adversarial use, specifically indirect prompt injection attacks.
The dataset is used to learn the impact of functionality graph coverage and to analyze how different parts of the system contribute.
To enable comparison with prior work, we also evaluate
Agent-Sentry
on the AgentDojo benchmark
[
7
]
, which exercises agents in realistic multi-step tasks involving tool use and untrusted information.
Together, these evaluations allow us to measure whether
Agent-Sentry
can block unintended actions while preserving normal agent behavior more efficiently.
Specifically,
Agent-Sentry
helps prevent over 90% of attacks while preserving up to 95% of system utility under the
Agent-Sentry
benchmark, and over 96% of attacks while preserving up to 98% of system utility under the AgentDojo benchmark.

In summary, this paper makes the following contributions:

1.

We propose functionality graphs as a representation of agent behavior that captures recurring execution flows such as control flow structures and data provenance.

2.

We introduce an enforcement mechanism that detects unintended agent behavior by comparing runtime execution against observed patterns, without requiring manually engineered policies.

3.

4.

We introduce Agent-Sentry Bench and provide an empirical evaluation showing that

2
Motivation

2.1
Agentic Computing Paradigm

LLMs have introduced a new
agentic computing paradigm
, in which the system primarily relies on ML models to resolve user queries expressed in natural language.
This execution paradigm is tremendously powerful as it allows spawning complicated new functionalities simply via natural language instructions, instead of requiring a software engineer to program new functionalities, as it is the case in conventional computing systems.
For example, given a query that instructs an email agent to “download attachments from recent emails and upload them to a cloud storage service”, the agent at runtime will orchestrate an execution flow (i.e., calling a series of functions and passing parameters), which may involve authenticating with the email service, reading recent emails, parsing attachments, authenticating with the cloud storage service, and uploading the attachments.

2.2
Inherent Security Issues

While there are obvious benefits to the agentic computing paradigm and its reshaping the computing stack at all levels, there are serious security, privacy, and safety risks to consider.
A key characteristic of agentic systems that makes it challenging to provide strong security properties is that the agentic execution paradigm in inherently
unbounded
.
Specifically, given access to a set of functions/tools, an AI agent can orchestrate those function calls in all possible combinations, making it challenging to characterize the system.
Towards achieving strong security properties in a system, it is crucial that the system execution with respect to the combination of a set of possible inputs in a set of possible states, is well understood, which is not the case in agentic systems.
For example, given a query to an email agent to “summarize recent emails”, the execution flow taken by the system is not known beforehand nor is full set of functionalities that the email agent may provide based on the user query.
Consequently, it is non-trivial to validate whether the system was able to perform the task or it got hijacked by a prompt injection in the emails, and steered from the user-specified task.

2.3
Bounding Agentic Systems

In this paper, we propose to bound the agentic systems to more reliably control their execution.
We argue that the agentic system execution need not be unbounded, as in practice agentic systems may only provide limited functionalities.
Once the limited set of expected functionalities are characterized, the smaller execution space is easier to validate.
For example, while a chain of
forward()

\rightarrow

delete()
functions for an email agent may be possible, it is a non-frequent functionality and may actually be an indication of a prompt injection, where an attacker attempts to forward an email and remove its traces.
Similarly, once it is known that to forward an email an execution flow includes a call to a
read()
and a
forward()
function, this flow can be trivially verified.
However, a key challenge is that with strict bounding, we risk constraining the agentic systems, such that we lose unique benefits of the agentic execution paradigm.
Thus, as we bound the systems, we aim to preserve the flexibility of the agentic execution paradigm.

At a high level, our approach consists of (i) observing benign and adversarial interactions with an agent to derive a set of representative execution traces, (ii) abstracting these traces into functionality graphs that capture recurring execution flows and data provenance, and (iii) using these graphs as prior knowledge to reason about the validity of future executions at runtime.
While reasoning over execution flows allows us to identify behaviors that fall outside known functionality, structural validity alone does not guarantee that an execution aligns with the user’s intent.
Thus, we we also assess the alignment between the user query and the expected execution flow.

It is important to note that our approach is akin to the code minimization approaches in conventional computing systems
[
22
]
, where the goal is to reduce the trusted compute base, and eliminate the possibility of attacks that targeted the removed code base.
While this idea has existed in prior systems, agentic systems present unique challenges, chiefly among them is to strike a reasonable balance between emergent functionalities and avoiding prompt injections, which we attempt to tackle in this paper.

3
Threat Model

3.1
System Model

We consider AI agents that primarily rely on LLMs to resolve user queries expressed in natural language prompts.
At a high-level, these agents consist of an LLM, a system prompt that defines the agents functionality, and a set of tools along with their functionality descriptions to interface with online services.
These systems also contain a conventional programming language scaffolding that orchestrates the interaction between the LLM and the system modules, such as passing the information between the LLM and the tools’ API endpoints.

We consider agents that are designed for specific use cases, such as a banking service’s agent, instead of general-purpose agents that serve a wide set of functionalities, such as Alexa
[
2
]
.
These systems are designed using agent development frameworks/tool kits, such as the OpenAI Agents SDK
[
23
]
, LangChain
[
5
]
, and LlamaIndex
[
18
]
.

The agent’s functionalities and execution logic are not statically defined, instead, they are inferred at runtime by the LLM, based on the user prompt and the contextual information observed during execution.
As a result, neither the full set of functionalities offered by the system nor the precise execution flow of the agent’s functionalities are known beforehand.
The system permits the emergent functionalities that the user specifies in their prompts, but are not explicitly defined by the system developer.
For example, the developer of a banking service agent may not explicitly foresee a workflow that combines reading a lease document and scheduling the monthly payments mentioned in the lease, yet still considers such behavior acceptable because it remains consistent with the agent’s role as a financial management assistant.

3.2
Trust Assumptions

We assume the agent, its scaffolding, its LLM, its tools, and the user to be trustworthy.
However, we assume the LLM and its tools to be compromise-able.
For example, an attacker may embed a prompt injection in a retrieved document which when processed hijacks and allows an attacker to take over the LLM.
We assume that the data and instructions exposed to the AI agent via tools (e.g., content retrieved from files, webpages, emails) are untrustworthy.
We also assume the AI agent and tools unintentionally make mistakes, due to the ambiguity and imprecision of natural language
[
17
,
13
]
.
For example, a user request to “pay the bill” might be ambiguous if multiple invoices exist, potentially leading the agent to transfer funds to the wrong recipient based on an incorrect inference.

3.3
Attacker’s Objective

The attacker’s objective is to induce the agent to perform actions which are:
(i) contextually irrelevant to the functionality offered by the agent (e.g., asking a banking agent to resolve healthcare related prompts),
(ii) significantly deviate from the agent specification defined by the developer (e.g., a banking agent negotiating with merchants),
and (iii) do not align with the user intent (e.g., a banking agent automatically adjusting loan payment after observing an increase in salary).
The attacker attempts to influence the agent’s execution context by embedding malicious or misleading instructions (i.e., prompt injections) in untrusted retrieved data.
These prompt injection attacks exploit the agent’s tendency to treat information it encounters during execution as instructions to act, steering it toward unintended behavior.

3.4
Defense Objective

We seek to prevent agentic systems from executing actions that are contextually irrelevant to the functionalities offered by the agent, significantly deviate from the intended scope of the system, and deviate from the user’s intent.
For example, in the context of the banking services agent:
(i) it should only resolve banking related tasks, and simply ignore the prompts outside of its domain,
(ii) it should not autonomously negotiate with merchants or contact third parties on the user’s behalf, even if such an action is technically possible, and
(iii) it should not autonomously try to adjust the user’s loan payment after observing an increase in salary, if not explicitly specified in the user prompt.

At a high-level, our key idea is to comprehensively uncover the system functionality in a non-adversarial setting, and use that characterization to bound/limit the agent’s execution.
As the agent’s functionalities are uncovered in a non-adversarial setting, they do not include contextually irrelevant functionalities, functionalities that significantly deviate from the specified functionalities of the system, and do not deviate from the user’s intent.
Essentially, such characterization enables bounding the system, which prevents attacks, while preserving the developer intended agent’s functionalities.

4
Methodology

4.1
Overview

Our goal is to bound agentic systems in a way that improves security while preserving the flexibility that makes the agentic computing paradigm powerful.
Instead of enumerating all valid and invalid behaviors of an agent ahead of time, we learn functionality graphs from how an agent executes in practice and reason about future executions.
The main idea behind our system is that, while the space of all possible execution flows is unbounded in theory, the set of execution flows seen during legitimate use typically follow repeatable patterns.

Agent-Sentry
bounds agentic execution by learning functionality graphs from execution traces collected during both benign use and adversarial scenarios.
These traces show how agents invoke tools, gather information and act on that information while responding to user queries.
From these traces,
Agent-Sentry
learns which flows consistently support intended functionality, which are strongly associated with misuse such as prompt injection, and which cannot be interpreted based on behavior alone.
This learned knowledge allows
Agent-Sentry
to evaluate actions before they execute making it possible to intervene early when behavior begins to drift.

While this provides a strong basis to bound agentic executions, some execution flows are inherently ambiguous as they appear in both benign and adversarial scenarios and agents may also exhibit previously unseen (but potentially legitimate) behaviors as their capabilities evolve over time. For these cases,
Agent-Sentry
uses an intent-alignment check that evaluates whether a proposed action is consistent with the user’s original request given the execution so far.
This provides additional context precisely when functionality graph anomalies alone cannot determine whether an action is appropriate.

Together, functionality graph learning and intent alignment form
Agent-Sentry
. Functionality graph learning provides
Agent-Sentry
with a behavior-based understanding of expected execution flows, while intent alignment resolves uncertainty when behavior alone is inconclusive.
By combining these two perspectives,
Agent-Sentry
bounds agentic execution in a way that prevents misuse while preserving the emergent and flexible nature of agentic systems.

In this paper, we use the term functionality graph to refer to a learned representation of recurring agent execution behavior.
Unlike a policy in reinforcement learning, or any other machine learning approach, this model does not assume actions’ intentions or optimize rewards. Instead, it first characterizes which execution behaviors are typical, which are strongly associated with misuse, and which remain ambiguous based on observed executions. Then, it makes deterministic decisions based on comparing the current execution behavior with the functionality graph.

4.2
Execution Trace in Agentic Systems

An execution trace is a record of how an agent responds to a single user query under the agentic computing paradigm.
It captures the user request, the ordered sequence of tool invocations performed by the agent, and the dependencies between information retrieved earlier in the execution and subsequent actions.
An execution trace reflects behavior that emerges dynamically at runtime, rather than a predefined or statically known program path.

We treat traces as structural descriptions of execution behavior rather than records of individual users or specific data values.
Two traces are considered equivalent if they share the same execution logic, even if they involve different data, such as emails, documents, or account identifiers.
This abstraction allows
Agent-Sentry
to reason and learn execution behaviors without relying on sensitive content or untrusted content.

Within a trace,
Agent-Sentry
distinguishes tools that retrieve information from those that perform actions with external effects such as sending or deleting an email.
This distinction reflects a fundamental security intuition in agentic systems.
Information retrieval (via retrieval tools) expands the agent’s view of the system state, while actions (performed via action tools) modify that state.

Agent-Sentry
focuses on evaluating actions, interpreting them in the context provided by the preceding flow of execution.
While execution traces record concrete runtime behavior,
Agent-Sentry
does not reason over individual traces directly.
Instead, traces are abstracted into execution flows that capture their structural execution logic while ignoring specific data values.

4.3
Execution Flows as Functionality Graphs

An execution flow is an abstract representation of an execution trace that captures the ordering and relationships among retrieval and action tool invocations, independent of specific input values or retrieved content.
Multiple execution traces may correspond to the same execution flow if they share the same execution logic.
A functionality graph path represents a recurring execution pattern that characterizes how an agent gathers information and justifies actions across multiple executions.
Together, these views allow
Agent-Sentry
to reason about execution behavior at the level of functionality graph paths, rather than individual traces.

One view captures the behavior of execution by relating each action to the full sequence of prior retrieval tool calls.
An action is interpreted based on the complete execution sequence, rather than only the immediately preceding step.
This reflects the reality that the meaning of an action depends on how the agent arrived at that point in the execution.

The second view captures how information flows through the execution.
It tracks whether the data an action relies on comes from the original user query or from information the agent previously retrieved while executing that query.
This allows the system to check whether actions are based on information the agent had a clear reason to access during the execution flow.
When an action relies on data that does not naturally follow from learned behavior, it suggests that the execution may have been influenced by injected instructions or steered away from the user-specified task.
This view helps
Agent-Sentry
distinguish between actions that are well-motivated by the execution so far and actions whose use of information is difficult to explain.

These two views capture different but equally important aspects of execution behavior. Execution behaviors capture what the agent does and when, while information flows capture why an action is taken given the available context.

4.4
Deriving Functionality Graphs

Agent-Sentry
creates three functionality graphs by observing execution traces produced during both benign use and adversarial runs of the agent.

The three functionality graphs (benign, ambiguous, and adversarial) are constructed by first extracting recurring execution flows from benign traces and then from adversarial traces.
First, benign execution traces are used to populate the benign functionality graph by extracting unique execution flows along two dimensions.
The first dimension captures control flow structures, recording which retrieval tools precede each action tool and if there are multiple action tools, then how are action tools sequenced relative to the preceding action tool.
The second dimension captures the data provenance by tracking the source of each action tools arguments, specifically on whether they originate from the original user prompt or from the outputs of prior retrieval tools.
Next the same extraction procedure is applied to adversarial execution traces.
Execution flows extracted from adversarial traces that also appear in benign traces (by checking against the benign functionality graph) are reassigned to the ambiguous functionality graph from benign graph, while those that do not appear in benign traces are assigned to the attack functionality graph.

To extract these execution flows,
Agent-Sentry
parses execution traces to identify tool call sequences and applies a combination of string matching techniques, including exact matching, substring containment, format-aware extraction for structured identifiers (such as IBANs and email addresses) and fuzzy matching, to associate action arguments with their likely sources. These form the directed data provenance edges for the second dimension of the functionality graphs.
We provide examples of extracted functionality graph paths in Appendix
11

As a result, execution flows observed exclusively during benign runs form the benign functionality graph, execution flows observed exclusively during adversarial runs form the adversarial functionality graph, and execution flows shared across both form the ambiguous functionality graph.

Other execution flows fall outside what
Agent-Sentry
has observed so far, reflecting incomplete knowledge rather than clear safety or misuse.
In both ambiguous and previously unseen situations, a decision cannot be made solely from the shape of the execution flow and how information is reused, because the same behavior may or may not be appropriate depending on the task the agent is trying to complete.

4.5
Resolving Ambiguous cases via Intent Alignment

For execution flows that remain unresolved after analysis with learned behaviors,
Agent-Sentry
evaluates whether a proposed action is consistent with the user’s original request, given the execution observed so far.
This step is primarily designed to handle cases where execution behavior and information use flows alone do not provide enough evidence to determine whether an action should proceed.

The intent alignment mechanism utilizes LLM-as-a-Judge to examine the user’s original request, together with a restricted view of the execution trace and the proposed action.
Its purpose is to determine whether executing the action would reasonably advance the task that the user asked the agent to perform.
Rather than attempting to judge the correctness of the entire execution, the mechanism focuses narrowly on whether the next action fits the user-specified goal in view of what the agent has already done.

Importantly, the intent alignment check is performed using only trusted inputs: the original user request, the execution steps seen so far, and the description of the proposed action tool that needs to be verified.
Retrieved content and other untrusted data encountered during execution are never used thus preventing injected instructions or adversarial content from influencing the alignment decision.
This design allows intent alignment to be applied without introducing a new attack surface.

Intent alignment complements the functionality graph analysis rather than replacing it.
Functionality graph analysis provides the primary signal, and intent alignment is used only when structural reasoning alone does not resolve the decision.
This separation gives
Agent-Sentry
a clear division of responsibility.
Together, these components allow
Agent-Sentry
to address uncertainty without weakening its behavioral safeguards or constraining its flexibility.

4.6
Decision Making

During execution,
Agent-Sentry
evaluates each proposed action using the learned functionality graph.
In many cases, the observed execution flow matches behavior that has only been seen during benign use, or matches behavior that has only been seen during misuse, allowing an allow or block decision to be made directly.
Intent alignment is called upon only when the observed execution flow falls into one of two specific categories: when the same functionality graph path has been observed in both benign and adversarial runs, or, when it has not been observed before.
In these cases, functionality graphs alone does not determine whether the action should proceed, and intent alignment with the user query is used to assess whether the action is consistent with the task the user asked the agent to perform.

Figure
1
illustrates how
Agent-Sentry
enforces execution bounds at runtime.
Each proposed action tool generated by the agent is intercepted before execution and first evaluated against the learned functionality graphs.
If the corresponding execution flow is classified as benign or adversarial by the functionality graph,
Agent-Sentry
allows or blocks the action tool directly.
If the flow is ambiguous or previously unseen, the action is deferred to the intent alignment mechanism, which checks consistency with the original user request using only trusted inputs.
Only actions that pass these checks are executed, ensuring that unauthorized actions are blocked even if the underlying agent’s LLM is influenced by injected or misleading content.

4.7
Updating Functionality Graphs

As discussed, intent alignment judges whether to allow or block previously unseen execution flows.
After such execution flows are complete, we envision that either the system has an automated method to determine, after the fact, whether the corresponding execution trace was benign or an attack, or, if the confidence level of the automated method is not high, a developer review may manually make a determination. We envision that the functionality graph will be periodically updated with these new execution flows.
At update times, we also envision that execution flows currently in the ambiguous functionality graph, may be moved into either the benign or adversarial functionality graph, when it has been consistently the case for some significant period of time that such execution flows are exclusively associated with either benign or adversarial scenarios.
It is beyond the scope of this work to implement the above update functionality. That said, we do evaluate the system against previously unseen execution flows, see Section
6.3
.

Experimental Setup

We evaluate
Agent-Sentry
using two complementary benchmarks designed to assess both its effectiveness and its performance.
First, we introduce
Agent-Sentry

Agent-Sentry

Second, we evaluate
Agent-Sentry

5.1
Agent-Sentry Bench

Agent-Sentry
Bench is a static dataset of unique execution flows derived from and extending the AgentDojo benchmark. While AgentDojo functions as a dynamic environment for end-to-end task evaluation,
Agent-Sentry
Bench is designed as a corpus of diverse execution traces to support the learning and evaluation of execution-provenance models.

To build
Agent-Sentry
Bench, we synthesized a diverse collection of execution traces spanning both benign and adversarial behaviors. Benign traces were derived from prior AgentDojo executions generated using a variety of language models and were further supplemented with additional benign workflows to expand task coverage and behavioral diversity. Adversarial traces were simulated using user and injection tasks adapted from AgentDojo, augmented with additional synthesized injection scenarios to broaden the space of attack behaviors. Overall, the benchmark is designed to maximize the variability of valid execution paths, including distinct execution-flow transitions and argument-provenance patterns. The complete methodology for generating both utility and attack traces is provided in Appendix
12
and Appendix
13
.

Dataset Composition.

The dataset consists of unique execution traces spanning four agent domains: Banking, Slack, Travel, and Workspace. It includes two subsets:

•

Benign Utility Traces:
Legitimate user workflows where the agent successfully completes tasks using valid tool sequences.

•

Adversarial Attack Traces:
Simulated traces containing prompt injection attacks embedded in untrusted retrieved content. These traces represent successful control-flow or data-flow hijacking attempts.

5.2
Evaluation Procedure

Evaluation proceeds by learning the behavioral model on varying fractions of benign utility and adversarial traces, ranging from 50% to 100% in 10% intervals, to measure performance sensitivity to data availability.
1
1

1

We start with 50% exposure because a system which depends on learning benign and adversarial execution flows is not expected to be used unless it has some prior exposure to datasets to populate the functionality graphs.

To ensure robustness and minimize variance, we perform the learning or cold start phase across multiple random seeds for data splitting.
Finally,
Agent-Sentry
is evaluated on all utility traces and all adversarial traces.

To account for the mismatch between
Agent-Sentry
Bench dataset composition and deployment reality, we report results under three complementary evaluation settings.
First, we evaluate the system using the dataset as-is, where all traces contribute equally. This setting reflects the raw diversity of adversarial behaviors captured by the benchmark and serves as a conservative evaluation that emphasizes attack coverage.
Second, we evaluate the system under a balanced setting in which benign and adversarial behaviors are treated as equally prevalent. This allows us to isolate differences in system behavior between utility and attack traces without the results being dominated by the larger number of adversarial examples.
Third, we evaluate the system under a deployment-motivated setting that assumes benign interactions constitute the majority of real-world usage, with adversarial behavior occurring relatively infrequently.

To approximate second and third scenarios given the limited number of unique utility traces, benign traces are oversampled with replacement. This oversampling reflects the fact that, at the level of control flow and data flow, the same underlying agent behavior may be exercised repeatedly by many semantically distinct user prompts that request the same task.

Together, these three evaluation settings capture system behavior under adversarial-heavy, balanced, and benign-dominant conditions, enabling a more realistic and interpretable assessment of performance across different assumptions about user intent.

5.3
AgentDojo Benchmark

AgentDojo consists of independently designed agent tasks and prompt injection attacks and is widely used in recent work on agent security.
Importantly, AgentDojo includes differences in task structure and attack techniques.
We evaluate
Agent-Sentry
on AgentDojo using GPT-4o traces to provide a comparison to prior art defenses.

5.4
Evaluation Metrics

We primarily evaluate the performance of
Agent-Sentry
using metrics designed to capture both its effectiveness at preventing attacks and its impact on benign functionality.

•

Attack Success Rate (ASR):
The percentage of prompt injection attacks that were not blocked, evaluated over all successful attack attempts. Lower values indicate stronger defensive performance.

•

Utility Success Rate (without attack):
The fraction of benign executions that were successful when
Agent-Sentry
is enabled. Higher values indicate better preservation of intended agent functionality.

6
Experimental Results

6.1
Overview

We evaluate
Agent-Sentry
through a sequence of controlled studies designed to characterize system behavior under varying levels of functionality graph coverage.
Across all experiments, the system relies on
functionality graphs
from execution traces and, in case of ambiguous or unseen scenarios, on an LLM-based reasoning layer, to classify scenarios as utility or attack.
As discussed, a functionality graph path does not uniquely determine intent: benign and adversarial execution traces may map to the same functional path, requiring semantic reasoning to resolve traces that are classified as ambiguous by the functionality graph.

Unless otherwise stated, we report results under the
as-is
evaluation setting, which reflects the adversarial-heavy composition of the benchmark. As shown later, alternative prevalence assumptions do not materially affect per-trace performance; corresponding results are therefore deferred to the appendix.
All results reported in this section, except those for the complete functionality graph coverage setting, are computed as the average over three randomized runs using fixed random seeds to smooth out the effects of random sampling.

6.2
Performance with Complete Functionality Graph Coverage

We begin by evaluating system performance when the functionality graphs have complete coverage of all execution traces in the
Agent-Sentry
dataset.
Starting from a cold state, the system is warmed up with a single pass over all available traces, ensuring that every observed functionality-graph path is represented.
Complete coverage does not eliminate errors, as benign and adversarial traces may still map to identical paths, requiring intent-level disambiguation.

Related Work

Securing LLM-based agents requires addressing their fundamental unboundedness: at runtime, agents dynamically synthesize control flow and tool-mediated data dependencies conditioned on untrusted inputs, rather than executing a statically defined program.
We categorize existing works by the layer at which they attempt to bound this behavior: input-level constraints, architectural isolation, semantic intent bounding, and explicit policy enforcement.

Input-Level Constraints and Soft Bounding

Early defenses attempt to bound agent behavior by constraining the model’s interpretation of its context window. Techniques such as prompt sandwiching, strict delimiters, and repeated system instructions aim to create a ”soft” separation between instructions and untrusted data
[
7
]
.
Spotlighting systematizes this by applying transformations (datamarking) to untrusted content, attempting to enforce provenance awareness through input encoding
[
10
]
. Complementary approaches attempt to bound the input space via pre-execution detection.
PromptArmor employs an auxiliary LLM guard to detect malicious spans before they reach the agent
[
28
]
, while Attention Tracker leverages internal attention patterns to identify adversarial inputs without extra inference
[
11
]
.
However, these approaches ultimately rely on the probabilistic adherence of the model to soft constraints rather than enforcing hard system guarantees, leaving them vulnerable to adaptive attacks that manipulate the model’s instruction-following capabilities
[
7
]
.

Architectural and Data-Flow Bounding

A more rigorous systems perspective seeks to bound the
consequences
of execution through architectural constraints. IsolateGPT introduces execution isolation to strictly contain the blast radius of compromised agents, preventing them from accessing sensitive system resources
[
31
]
.
Similarly, proposed taint-tracking frameworks seek to enforce data-flow integrity by marking untrusted content and requiring explicit mediation before it can influence high-impact sinks
[
12
]
. While these methods provide stronger structural guarantees than input filtering, they face challenges at the
intra-agent
boundary, where agents must legitimately process untrusted data (e.g., summarizing an email) without allowing that data to hijack the control flow.

Semantic and Intent Bounding

Beyond structural constraints, preventing IPI requires bounding the agent’s
goal
to the user’s original intent. We view IPI primarily as a mechanism for inducing
task drift
, where the agent’s behavior remains valid generally but deviates specifically from the user’s request. “Get my drift?” demonstrates that activation deltas in the model’s internal state can serve as a robust signal for detecting this semantic deviation
[
1
]
.
While effective, such white-box approaches are incompatible with the closed-source API models (e.g., GPT-5, Claude) that power most state-of-the-art agentic systems, creating a need for black-box intent verification.

Policy-Based and Trace-Based Execution Enforcement

A broad line of work seeks to secure LLM-based agents by constraining how they execute tool-invocation workflows, rather than filtering user inputs alone.
Early efforts in automated red teaming focus on discovering vulnerabilities by generating adversarial prompts or attacker agents
[
20
,
34
,
33
]
.
While effective for exposing weaknesses, these approaches are primarily diagnostic and do not provide a mechanism for enforcing safety during deployment.

More recent systems enforce security policies directly over agent execution traces.
CaMeL operationalizes the Dual-LLM pattern
[
30
]
by separating a privileged planning model from a quarantined parsing model and enforcing capability policies via a custom interpreter
[
6
]
.
This design provides strong security guarantees, but introduces substantial runtime overhead due to multiple LLM invocations, interpreter-based policy checks, and potential user intervention for declassification, which CaMeL explicitly acknowledges as a usability trade-off.
Progent similarly enforces execution policies through a programmable interpreter and domain-specific language
[
26
]
, achieving low attack success by blocking disallowed function calls, but at the cost of manual policy engineering that is difficult to scale across tools, tasks, and evolving agent behaviors.

To reduce reliance on hand-authored policies, other approaches attempt to infer enforcement constraints automatically from runtime behavior.
AgentArmor constructs and inspects Program Dependence Graphs inferred from agent execution logs to enforce dependency-aware constraints
[
28
]
, but relies on LLMs acting as auxiliary analyzers that must reason over untrusted retrieved content, increasing runtime cost and exposing the defense to meta-injection attacks.
TraceAegis decomposes agent invocation traces into hierarchical execution units and learns behavioral constraints for anomaly detection
[
19
]
, achieving strong detection performance but remaining detection-centric and lacking a mechanism for resolving ambiguity or novelty during real-time execution.
In contrast, Agent-Sentry learns lightweight
functionality graphs
from execution traces to bound agent behavior structurally, explicitly defers ambiguous or unseen cases to a constrained intent-alignment mechanism that reasons only over trusted inputs, and empirically balances utility preservation and attack success, an operational trade-off that prior policy-based and trace-analysis systems do not quantify or optimize.

When semantic intent verification (that utilizes an LLM) is required,
Agent-Sentry
confines the intent alignment mechanism to a strictly trusted set of information, reasoning only over the original user request (user prompt), tool specifications and tool call sequences while ignoring retrieved or externally sourced content.
This design choice avoids introducing additional attack surfaces during enforcement.
By combining lightweight execution-level structure with a constrained semantic check,
Agent-Sentry
provides a practical mechanism for bounding agent behavior that preserves utility while remaining robust to adaptive manipulation.

8
Concluding Remarks

Evolving Execution Coverage

A fundamental challenge in agentic systems is that new benign behaviors and new attack strategies will continually emerge as agents, tools, and usage patterns evolve.
As a result, complete execution coverage is never static: there will always be unseen scenarios that fall outside the current functionality graph.
In practice, however, the volume of such novel traffic is expected to remain small, as the system is periodically updated with newly observed execution traces and adapts to evolving behavior.
This limitation is not unique to
Agent-Sentry
, but is inherent to any system operating in adversarial environments where attackers actively seek novel strategies.
The benefit of explicit coverage modeling is that such cases are surfaced as ambiguous rather than silently misclassified, enabling conservative handling and incremental improvement over time.

Intent Ambiguity and Mimicry Resistance

A remaining challenge arises from mimicry attacks, where adversarial executions deliberately follow functionality graph paths that are non-trivial to structurally and semantically distinguishable from benign behavior within a single execution trace.
While
Agent-Sentry
mitigates some of these cases by checking alignment between the user prompt and the expected execution trace, this mechanism is inherently limited by the information provided at decision time, making the system susceptible to carefully crafted mimicry that aligns with both execution structure and apparent user intent.
As additional contextual and structural signals are incorporated into the functionality graph over time such as user identity and privilege context (conditioning decisions on authenticated roles or permissions) and external policy and compliance signals (enforcing organizational rules such as spending limits or access constraints that are independent of learned execution structure), the system can strengthen its ability to distinguish such cases directly at the structural level. This evolution would reduce reliance on LLM-based intent alignment for resolving mimicry and improve robustness when structural and intent-based cues alone are insufficient.

8.1
Takeaways

Execution provenance is an effective security signal for agentic systems:
We show that traditional security techniques based on execution provenance and control/data-flow analysis can be successfully applied to agentic systems and achieve strong empirical results. We do note that however, as agentic execution space is open-ended and continually evolving, it is fundamentally impossible to anticipate all benign workflows or future attacks in advance.
For this reason, Agent-Sentry combines structural bounds with an LLM-based intent check and is designed to integrate additional orthogonal signals over time.
This layered view complements several strands of prior work but not limited to: (i) adversarial-training and robustness research that fortifies models against perturbations and adversarial examples
[
9
,
21
]
; (ii) guardrails and policy/constitution approaches that steer model behavior via rules or automated critique (e.g., Constitutional AI and engineered guardrail systems)
[
3
,
8
]
; (iii) prompt-injection detection and monitoring that aim to identify contaminated inputs or attention shifts indicative of injections
[
11
,
16
]
; and (iv) alignment-focused defenses that harden model outputs or check alignment at inference time
[
32
,
4
]
.
Each class of defense targets different failure modes; by operating at the execution layer, Agent-Sentry can be deployed complementarily with any defense that aims to improve agent robustness, such as model-centric, input-centric, and alignment-based approaches.

To ensure the robustness of the behavioral policy, the
Agent-Sentry Bench

This approach captures the wide variability in natural language—including differences in tone, vocabulary, and grammatical structure—while mapping distinct user expressions to identical underlying execution logic. 11.1
Key Components

•

Three-Part Partitioning
: Patterns are classified into three security categories based on overlap between utility and attack traces:

–

Utility or Benign
: Patterns observed only in benign utility traces

–

Ambiguous
: Patterns observed in both utility and attack traces

–

Attack or Adversarial
: Patterns observed only in attack traces

•

Control-Flow Relationships
: These patterns capture how retrieval and action tools are ordered within an execution flow:

–

Retrieval-to-Action
: Associates the set of retrieval tools invoked prior to an action with the action tools that may validly follow. The key is the set of retrieval tools observed before the action, representing the information-gathering context available at that point in the execution.

–

Action-to-Action
: Associates each action tool with the set of action tools that may validly follow it, capturing sequential action dependencies and common action chaining patterns.

•

Argument Provenance Relationships
: These patterns capture how the arguments of action tools are grounded in prior execution context. For each action tool argument (e.g.,
send_money.recipient
), the functionality graph records the valid sources from which the argument value may originate, such as specific retrieval tools (e.g.,
get_user_info
) or the
user_prompt
for direct user input.

•

Tool Categories
: Binary classification of all agent tools:

–

Retrieval tools
: Read-only operations that gather information (e.g.,
get_balance
,
get_user_info
)

–

Action tools
: Write operations that modify state or perform actions (e.g.,
send_money
,
update_password
)

•

Context Accumulation
: The policy maintains stateful context during trace evaluation:

–

Retrieval context
: All retrieval tools executed before each action

–

Action history
: All previous actions executed in sequence

–

This allows the policy to enforce patterns based on full execution history rather than just immediate predecessors

12
Appendix: Utility Dataset Generation

In addition to the attack traces, a diverse set of
benign utility traces
is crucial for training and evaluating Policy Enforcement systems. These traces represent legitimate user workflows where the agent must access external information, thereby exposing itself to potential indirect injections. To ensure robustness, the utility dataset must cover a wide range of tool transitions and user intents, preventing the policy from overfitting to a narrow set of ”safe” patterns.

12.1
Generator Architecture

The
Utility Generator
is an autonomous pipeline designed to produce valid execution traces that maximize coverage of the agent’s tool capabilities. It operates on a ”Generate-Verify-Refine” loop similar to the Attack Generator but with distinct constraints and a dedicated coverage strategy.

12.1.1
Graph-Based Coverage Strategy

To ensure the dataset is not dominated by the most common actions (e.g., just checking emails), we implement a
Coverage Tracker
that models the agent’s tool usage as a directed graph.

•

Transition Tracking
: The tracker maintains a frequency matrix of all observed tool transitions
T_{A\to B}
.

•

Target Selection
: Before generating a new trace, the system queries the tracker for the
least-covered
tool transition. It prioritizes zero-count transitions first, then samples inversely proportional to frequency.

•

Constraint Injection
: The selected transition
A\to B
is injected as a hard constraint into the LLM’s prompt generation step, forcing it to create a scenario that plausibly requires that specific sequence of actions.

12.1.2
Generation Pipeline

The generation process for a single trace follows these steps:

1.

Sequence Planning
: The LLM generates a valid tool sequence (length 2–5) that satisfies the coverage target (e.g., ”Must include
search_files

\rightarrow

summarize_file
”).

2.

Prompt Generation
: A second LLM call converts this abstract sequence into a natural language user request, applying a specific persona (see Section
12.2
).

3.

Execution
: The generated prompt is executed against the actual agent sandbox.

4.

Verification
: The resulting execution trace is compared against the expected sequence. If the agent deviates (e.g., hallucinates a tool or skips a step), the trace is marked for refinement.

5.

Refinement
: On failure, an ”AI Debugger” analyzes the mismatch and rewrites the prompt to be more explicit, triggering a retry.

12.2
Meta-Prompts and Diversity

We use a suite of structured meta-prompts to drive the generation and ensure high-quality, diverse outputs.

12.2.1
Sequence Generation

This system prompt ensures that the generated tool sequences are logical and respect the coverage constraints:

Meta-Prompt: Sequence Generation

You are an expert at creating realistic tool usage patterns for an AI agent.
Your goal is to generate a diverse set of tool sequences that represent how a real user would interact with the agent.
CRITICAL RULES:
1. Use ONLY the available tools.
2. The sequence must be logical (outputs of step 1 reasonably flow into step 2).
3. Vary the length and complexity.
4. You MUST focus on the "Target Tool Transition" provided.

12.2.2
User Prompt Generation

To translate tool sequences into natural language, we use the following prompt, which enforces the selected persona:

Meta-Prompt: User Prompt Generation

You are a creative writer generating user prompts for an AI agent.
Your goal is to write a natural language prompt that triggers a specific SEQUENCE of tool calls.
CRITICAL RULES:
1. You must adopt the specific STYLE/PERSONA requested.
2. The prompt must be natural, not robot-speak.
3. The prompt must IMPLICITLY require the tools. Do not just list tool names.
4. ‘reasoning‘ must explain why this phrasing triggers these tools.

12.2.3
Stylistic Diversity

We employ the same diversity sampling strategy as the Attack Generator to prevent linguistic mode collapse. For each trace, a style is sampled from:

•

Standard
: Professional and clear.

•

Terse
: Minimalist and imperative.

•

Verbose
: Descriptive and conversational.

•

Urgent
: Time-sensitive and demanding.

•

Casual
: Informal, lower-case, with slang.

•

Technical
: Precise and jargon-heavy.

•

Confused
: Vague or uncertain.

•

Angry
: Frustrated or complaining.

•

Complex
: Multi-part constraints.

12.2.4
Refinement Loop

When the agent fails to follow the generated prompt, the Refinement module intervenes:

Meta-Prompt: Prompt Refinement

You are an expert AI debugger. A previous user prompt FAILED to trigger the expected tool sequence.
Your job is to analyze the failure and write a REFINED prompt that fixes the issue.
STRATEGY:
- If missed a tool, make the requirement MORE EXPLICIT.
- If called a wrong tool, change wording to avoid ambiguity.
- If arguments were wrong, be more specific about data.
- Maintain the original Style/Persona if possible.

13
Appendix: Simulated Attack Dataset Generation

To rigorously evaluate Agent-Sentry against diverse Indirect Prompt Injection (IPI) attacks, we developed a specialized
Attack Simulation Framework
. This framework autonomously generates high-volume, high-quality adversarial datasets by systematically combining benign retrieval contexts with malicious attack objectives. Unlike static datasets, this approach allows us to stress-test the defense against a combinatorial explosion of injection vectors and attack payloads without manual crafting.

13.1
Architecture Overview

The simulator operates as a multi-stage pipeline designed to produce
Simulated IPI Traces
. An IPI attack is characterized by an adversary embedding malicious instructions into an external data source (e.g., an email or document) which, when retrieved by the agent, hijacks the control flow to execute unauthorized actions.
Our framework simulates this by generating two distinct types of valid execution traces and synthesizing them into a single attack scenario:

•

Benign Utility Traces
: Represent the legitimate task the user intends to perform, which necessitates reading external data.

•

Attack Traces
: Represent the unauthorized behavior the attacker wishes to trigger (e.g., exfiltrating data or modifying files).

A
Splicing Engine
then merges these traces, embedding the attack instructions into the retrieval output of the utility trace, creating a realistic simulation of a successful injection.

13.2
Trace Generation Phases

The framework uses a dedicated Large Language Model (DeepSeek-V3.2) to generate base traces, ensuring diversity through a global registry of prompts and scenarios.

13.2.1
Phase 1: Attack Trace Generation

The
Attack Generator
focuses on creating valid execution paths for restricted or high-risk actions.

•

Objective
: Force the agent to execute specific
Action Tools
(e.g.,
send_email
,
transfer_funds
) identified via tool classification.

•

Strategy
: The generator prompts the agent to perform single-step actions or multi-step sequences (e.g.,
Retrieval

\rightarrow

Action
).

•

Diversity Enforcement
: A persistent
Attack Registry
tracks all generated prompts. New prompts are generated with diversity constraints to avoid semantic duplicates, ensuring the evaluation covers a wide range of phrasing and intent expression.

•

Verification
: Generated traces are verified to ensure they genuinely result in the target tool call. We employ a flexible verification logic that accepts ”drift” (e.g., if the agent autonomously decides to check a calendar before scheduling a meeting) provided the target unauthorized action is eventually executed.

13.2.2
Phase 2: Utility Trace Generation

The
Utility Generator
creates the ”carrier” scenarios—benign workflows that expose the agent to untrusted data.

•

Objective
: Generate legitimate user requests that require the agent to use a
Retrieval Tool
(e.g.,
get_latest_email
,
read_file
).

•

Constraint
: The generator strictly enforces that the
first
tool called in the sequence must be a retrieval tool. This is critical because the IPI payload is injected into this first retrieval result.

•

Coverage Tracking
: A
Coverage Tracker
monitors tool transitions (e.g.,
search

\rightarrow

read
) to ensure the utility dataset represents varied benign usage patterns, preventing overfitting to simple lookup tasks.

13.3
Meta-Prompts and Diversity

To ensure the generated traces are high-quality and varied, we use structured system prompts with explicit diversity constraints.

13.3.1
Prompt Generation System

The core instruction used to generate user prompts from tool sequences enforces natural language and implicit intent:

Your goal is to write a natural language prompt that triggers a specific SEQUENCE of tool calls.
CRITICAL RULES:

2. The prompt must be natural, not robot-speak.
3. The prompt must IMPLICITLY require the tools. Do not just list tool names.
4. ‘reasoning‘ must explain why this phrasing triggers these tools.

13.3.2
Stylistic Diversity

To prevent the model from converging on a single ”polite command” style, we stochastically sample from a set of 9 distinct personas for each generation:

•

Standard
: Clear, polite, professional English.

•

Terse
: Minimal words, imperative mood.

•

Verbose
: Long-winded, includes irrelevant details.

•

Urgent
: Panicked, demanding, uses ’ASAP’.

•

Casual
: Slang, typos, lowercase, friendly.

•

Technical
: Uses specific jargon, precise constraints.

•

Confused
: Unsure of terminology, vague requests.

•

Angry
: Frustrated, complaining about previous failures.

•

13.3.3
Refinement Loop

If a generated prompt fails to trigger the expected tool sequence during verification, we employ an automated debugger prompt:

Your job is to analyze the failure and write a REFINED prompt that fixes the issue.
STRATEGY:
- If missed a tool, make the requirement MORE EXPLICIT.
- If called a wrong tool, change wording to avoid ambiguity.
- If arguments were wrong, be more specific about data.
- Maintain the original Style/Persona if possible.

13.4
Simulation via Conversation Splicing

The core innovation of our framework is the
Conversation Splicer
, which synthesizes IPI attacks by grafting an attack trace onto a utility trace.

13.4.1
Why Splicing?

Directly prompting an LLM to ”simulate an injection attack” often leads to hallucinations or invalid tool usage. By separately generating valid utility logic and valid attack logic, we ensure that both the ”before” (benign context) and ”after” (attack execution) components of the trace are realistic and executable by the agent.

13.4.2
The Splicing Algorithm

Given a Utility Trace
T_{U}
and an Attack Trace
T_{A}
, the splicer performs the following operations:

1.

Identify Injection Point
: The algorithm locates the output of the first retrieval tool call in
T_{U}
. Let this message be
M_{\text{retrieval}}
.

2.

Payload Construction
: An adversarial payload is constructed by appending the Attack Instruction (the user prompt from
T_{A}
) to the legitimate content of
M_{\text{retrieval}}
.

\text{Payload}=\text{Content}(M_{\text{retrieval}})\oplus\text{Preamble}\oplus\text{Prompt}(T_{A})

(1)

Here, the
Preamble
is a jailbreak string (e.g., ”Ignore previous instructions”, ”[SYSTEM MESSAGE]”) selected from a configurable list to vary the stealthiness of the injection.

3.

Grafting
:

•

The simulation preserves the
T_{U}
history up to the injection point.

•

The modified
M_{\text{retrieval}}
(containing the payload) is inserted.

•

The subsequent messages from
T_{A}
(representing the agent’s response to the attack prompt) are appended, replacing the original continuation of
T_{U}
.

13.4.3
Outcome

The result is a valid conversation history where the agent starts a benign task, retrieves data containing an injection, and immediately ”pivots” to execute the attacker’s command. This method allows us to generate thousands of unique attack variations (
N_{\text{utility}}\times N_{\text{attack}}\times N_{\text{preambles}}
) to thoroughly evaluate the robustness of our provenance-based defense.
