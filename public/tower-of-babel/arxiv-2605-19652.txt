Abstract
. Tile-based programming frameworks are increasingly adopted to write high-performance GPU kernels in domains such as deep learning and scientific computing. While these frameworks enhance productivity and hardware utilization, their multi-stage compilation pipelines introduce distinct code generation bugs that are tightly coupled to input shapes, data types, and backend targets. These bugs often manifest as silent correctness or performance issues, making them difficult to detect using existing compiler testing tools. Additionally, the unique programming conventions of tile domain-specific languages complicate root cause identification, while fixing such bugs demands specialized knowledge of tile abstractions and compilation pipelines. Despite the growing adoption of tile-based systems, their code generation bugs remain largely unexplored. This paper presents the first systematic study of tile-program code generation bugs. We curate 401 bug reports from GitHub and identify 301 tile-program codegen bugs for analysis, categorizing the root causes, symptoms, input patterns, test oracles that trigger these bugs, and the strategies used to fix bugs. Our study provides foundational insights for building debugging, testing, and repair tools tailored to tile-based compiler infrastructures.

Background and Motivation

GPU kernels often require implementation decisions that are not fixed by the operator definition. Many kernels differ in correctness and efficiency based on how computation is partitioned into tiles, how data is staged across memory levels, and how parallel execution is coordinated. Tile programming
(

;

;

;

)
exposes these decisions at the kernel-construction level. Tile compilation then translates tile-level intent into a concrete implementation that satisfies hardware constraints. Figure

2.1.
Tile programs

A tile program represents a kernel as operations over blocked fragments of tensors. Each program instance operates on one or more tiles mapped to a GPU execution scope such as a thread block or a warp-aligned group. Compared with tensor graph representations, tile programs make three classes of choices explicit. First, they specify tile-level data movement, including how values are loaded, staged in registers or shared memory, reused across compute steps, and written back. Second, they specify tile-level parallel mapping, including how program instances cover the iteration space and how work is assigned to threads
(
50
;
48
)
. Third, they expose layout-sensitive access decisions, including vectorization, alignment, padding, and layout transforms that affect memory legality and access efficiency
(
83
)
. These properties place tile programs close to the executed kernel while retaining a structured representation that supports compiler analysis.

Tile compilation.
The tile compiler produces a correct and efficient kernel under hardware and resource limits. In contrast to compilation settings where control flow and memory behavior are fully specified by the input program, tile compilation often begins from abstractions that describe tiled computation and dataflow while leaving some kernel details unresolved. The compiler must determine concrete boundary handling, synchronization structure, and layouts, and must also select among many implementation alternatives.

2.2.
Comparison of Compiler Pipelines

Figure
1
contrasts three compilation pipelines and highlights why tile compilation warrants separate study. Traditional compilers lower source programs with explicit control and memory behavior through semantic analysis and IR transformations, then apply backend phases such as instruction selection and register allocation on explicit dependence and memory representations. Tensor graph compilers begin from fixed operator semantics, apply graph rewrites, and search a schedule space (e.g., tiling, fusion, layout) using cost models or measurements before emitting kernels. Tile compilers instead begin with tile abstractions that leave aspects of layout and coordination unresolved; the pipeline performs feasibility checks under resource constraints, synthesizes explicit boundary handling and synchronization, and then searches schedule and layout parameters subject to legality constraints before committing final kernel details. This structure introduces additional bug opportunities beyond conventional lowering and tensor scheduling, including errors in constraint reasoning, boundary/synchronization synthesis, and mismatches between legality checks and generated code, often triggered only by specific combinations of tile sizes, layouts, and resource usage.

3.1.
Data Collection

To investigate codegen bugs in real-world tile-based programming frameworks, we curated a dataset of verified bug reports from actively maintained open-source repositories. Our goal was to focus on bugs encountered in both research and production usage, ensuring that our analysis reflects the challenges faced by practitioners. The collection process comprises two main stages: (1) identifying relevant repositories and (2) extracting valid bug reports.

3.1.2.
Bug Report Extraction

From the selected repositories, we collected all GitHub issues filed between January 2022 and November 2025. This time window reflects the period of active adoption following the public release of key tile-programming frameworks, which became production-ready after mid-2021. Earlier reports were excluded to avoid noise from pre-release instability.

Our extraction process began with a total of 43,255 GitHub issues across the selected repositories. To identify relevant bug reports, we applied a multi-stage filtering strategy designed to ensure both accuracy and relevance: (1)
Closed and confirmed issues.
We filtered for issues marked as closed, under the assumption that resolved issues with discussions or commits are more likely to reflect confirmed bugs. This reduced the dataset to 3,283 issues;
(2)
Keyword and label-based filtering.
To isolate bug-related discussions, we applied both keyword filtering and label matching. Keywords such as “tile error”, “tile bug”, “index”, “compile”, “synchronization”, “warp”, “OOM”, “data type”, “indexing error”, “compile crash”, “warp mapping”, “incorrect IR”, “fix codegen”, and “fix” were used to match issue titles and descriptions. We also retained issues explicitly tagged with GitHub labels such as “bug”, “error”, or “fix”. This step narrowed the candidate set to 892 issues;
(3)
Fix availability.
To support downstream analysis of bug resolution patterns, we further restricted the dataset to issues that included a documented fix, either in a corresponding pull request, commit reference, or linked resolution discussion. This reduced the set to 579 issues; and (4)
Deduplication and relevance filtering.
Finally, we manually removed duplicates, redundant reports, and issues that were misclassified or irrelevant (e.g., feature requests or configuration questions). This resulted in a final curated dataset of 401 unique bug reports.

This multi-phase filtering strategy ensured high precision in our bug corpus, allowing us to focus on well-documented and contextually rich failures that accurately reflect the challenges of developing with the tile programming frameworks.

4.1.
Control Flow and Scheduling Bugs

This category comprises 5.32% of the observed codegen bugs and captures violations of compiler-synthesized tile control semantics.
Control flow and scheduling bugs arise when the compiler derives control logic—such as boundary guards, predicate masks, and synchronization placement—from high-level tile abstractions, and generates incorrect control behavior during lowering.
In tile compilers, control decisions (e.g., which threads are active, which iterations are valid, and when synchronization is required) are not explicitly programmed, but are automatically inferred from the tile iteration space, thread mapping, and shape specialization.
Errors in this synthesis, such as incorrect tile-edge predicates, misgenerated branch conditions, or improper instruction reordering across implicit synchronization points, can violate tile-level execution invariants.
These bugs typically manifest only under specific tile shapes, boundary configurations, or warp layouts, and often remain latent under full-tile execution.
They originate during lowering and scheduling stages, where high-level tile constructs (e.g., loop nests, thread mappings, and boundary guards) are translated into backend control flow and synchronization instructions (I2 in Table
1
).
Based on the synthesized semantic object being violated, we identify three subcategories:

(1) branch predication bugs
,
(2) instruction scheduling bugs
, and
(3) warp-level control bugs
.

Branch Predication Bugs.

Branch predication bugs arise when control flow expressed over logical tiles is incorrectly lowered to operate over physical threads.
In tile-based abstractions, constructs such as
if
-statements and boundary guards are intended to selectively predicate computation within a tile, rather than terminate or invalidate the execution of the underlying hardware thread.
Incorrect lowering of such predicates can cause valid tile instances to be skipped or incorrectly masked, leading to silent loss of computation.
A representative example is reported in the Triton compiler
(
76
)
, where the compiler generates incorrect predicate and tile-guard logic under specific warp configurations.
Although the high-level kernel is semantically valid, the control-flow synthesis pass infers inconsistent tile boundary conditions, resulting in invalid predication over partial tiles and incorrect execution behavior.

Instruction Scheduling Bugs.

In tile-based compilers, instruction scheduling bugs arise when backend reordering violates compiler-synthesized tile pipeline invariants, rather than explicit source-level data dependencies.
A representative example from Triton
(
77
)
shows that the AMD backend assumes a fixed per-tile ordering of
local_store
,
global_load
, compute, and
local_load
to implement local prefetching.
A later instruction reordering pass swaps
global_load
and
local_store
, preserving dependencies but breaking the intended tile pipeline.

Warp Control Bugs.

Warp control bugs in tile-based compilers arise from incorrect synthesis or propagation of warp-level execution metadata, rather than from programmer-written warp logic.
As a result, inconsistencies in warp-related metadata (e.g., mismatches between logical tile layouts and physical warp configurations) can invalidate warp-synchronous assumptions during codegen.
Because warp-related metadata is synthesized and propagated across multiple compiler stages, no single transformation validates global consistency between tile-level layout assumptions and backend warp configurations.
A representative example is reported in Triton
(
75
)
, where the
WSMaterialization
(warp specialization) pass modifies the module-level warp configuration by updating the number of warps, but leaves the
warpsPerCTA
field unchanged.
This partial update breaks the consistency between warp specialization metadata and the tile-level warp layout expected by subsequent lowering stages.
Although the generated code remains structurally valid, the compiler operates under incorrect assumptions about warp grouping within a tile, leading to miscompiled warp-level execution.

4.2.
IR Construction and Transformation Bugs

This category accounts for 16.28% of the observed bugs and captures violations of compiler-synthesized tile IR semantics that occur during IR construction and IR rewriting, prior to target-specific codegen (I3 in Table
1
).
In tile compilers, IRs do not merely encode control flow or data dependencies, but explicitly materialize tiling metadata such as per-tile buffers, memory layout descriptors, partial iteration coverage, and masked execution regions. These IR-level objects and invariants are automatically derived from tile shapes, scheduling parameters, and thread mappings, and are central to preserving the semantics of tile-structured execution.
IR-level bugs arise when the compiler incorrectly constructs or transforms these tile-aware IRs, violating semantic invariants that govern how logical tiles map to physical memory and execution resources. Such violations stem from inconsistent synthesis or preservation of implicit tile semantics, rather than from malformed IR or incorrect handling of explicit program constructs.
As a result, these failures predominantly arise in tile compilers, whose domain-specific IRs critically depend on consistent construction and transformation of tiling metadata across compiler stages.
Based on the stage at which synthesized IR semantics are violated, we identify two subcategories:

(1) IR construction bugs
and
(2) IR transformation bugs
.

IR Construction Bugs.

IR construction bugs arise during front-end lowering, where high-level tile programs are translated into tile-aware IRs that explicitly represent per-tile buffers, memory layouts, and layout-to-buffer bindings. At this stage, the compiler must deterministically create and associate IR objects corresponding to shared-memory tiles and their layout metadata.
In tile compilers, these IR objects are first-class and order-sensitive: even when the source program is unchanged, differences in how tile handles or layout mappings are constructed can alter the effective kernel semantics. IR construction bugs occur when the compiler introduces non-determinism or inconsistency in the creation or ordering of tile-level IR entities, leading to semantically unstable IRs.
A representative example is reported in TileLang
(
68
)
. In this case, a tiled FlashAttention kernel repeatedly produces different IRs because shared-memory tile handles (e.g.,
dv_shared
,
K_shared
,
dk_shared
) are created in a non-deterministic order. As a result, the
layout_map
attribute binds layout specifications to different tile handles across compilations, defeating kernel caching and causing logically identical kernels to be treated as distinct.

IR Transformation Bugs.

IR transformation bugs arise during mid-end optimization passes that rewrite tile IRs, such as control-flow simplification, predicate rewriting, or loop restructuring. These passes often reuse transformation logic originally designed for uniform or affine iteration spaces, implicitly assuming full domain coverage and unconditional execution.
In tile-based IRs, iteration spaces are explicitly structured into tiles with boundary conditions and masked regions. Transformation bugs occur when IR rewrites invalidate these tile-specific execution invariants, for example, by dropping boundary tiles, simplifying predicates under incorrect assumptions, or restructuring control flow in a way that excludes valid tile instances. Such violations may not trigger compilation errors, but instead silently reduce the effective iteration domain.
An illustrative example is reported in Halide
(
22
)
. After an IR transformation, the optimized IR computes
g(x)
only for a subset of the intended domain, skipping
x = 0
, despite the original tiled logic correctly covering the full loop extent. The optimizer rewrites control flow based on undefined-value assumptions, inadvertently eliminating boundary points introduced by tiling.

4.3.
Tile Mapping and Launch Bugs

This category accounts for 6.31% of the observed bugs and captures failures in how tile-level computations are mapped to the underlying GPU execution geometry (I4 in Table
1
). Unlike control-flow or IR-level bugs, tile mapping and launch bugs arise at the stage where logical tiles are concretized into physical execution parameters, including grid dimensions, block sizes, and thread–tile associations. Errors in this synthesis can lead to incorrect or invalid kernel launches, even when the source tile program is semantically valid.
We classify tile mapping and launch bugs into two subcategories:
(1) launch configuration bugs
and
(2) thread–block mapping bugs
, depending on whether the failure originates from incorrect launch geometry inference or from erroneous mapping between logical tiles and physical threads.

Launch Configuration Bugs.

Launch configuration bugs arise when the compiler miscomputes launch parameters such as grid size, block dimensions, or shared memory usage derived from tile-level abstractions.
Tile compilers infer these parameters from input shapes, tile sizes, and tile grouping constraints. As a result, incorrect assumptions during launch synthesis (e.g., implicit divisibility, warp alignment, or resource availability) can produce invalid or incomplete execution.
A representative example is reported in PyTorch’s Triton integration
(
55
)
, where setting
config.triton.max_tiles = 3
triggers a kernel launch failure.
This failure arises because the compiler synthesizes a non-standard launch geometry for grouping logical tiles, introducing internal launch parameters whose autogenerated identifiers conflict with a reserved namespace (e.g., a banned
z
-prefixed dimension).
While common tile groupings (e.g., one or two tiles per group) satisfy backend constraints, increasing the tile group size exposes inconsistencies between tile grouping semantics and the inferred grid geometry.

Thread-Block Mapping Bugs.

Thread–block mapping bugs arise when the compiler emits incorrect logic for mapping logical tiles to physical grid and block indices. Tile compilers frequently decompose multi-dimensional iteration spaces (e.g., batch, head, or sequence dimensions) into tiles, and then flatten or distribute these tiles across the limited grid axes supported by GPUs. Errors in this mapping process can lead to invalid grid dimensions, overlapping execution, or incomplete coverage of the logical iteration space.
An illustrative example is reported in PyTorch
(
56
)
, where a kernel fails due to invalid grid dimensions when mapping batch and head tiles to grid axes.
When tiling is enabled, the compiler must synthesize additional structure to map multiple logical tile dimensions onto physical grid axes. In this case, incorrect flattening and dimension assignment produce a grid configuration that violates backend constraints, causing the kernel to fail at launch.

4.4.
Memory Bugs

This category accounts for 19.27% of all observed bugs and captures failures in translating compiler-synthesized tile memory semantics into correct low-level memory operations (I1 in Table
1
). Unlike control-flow or mapping bugs, which govern execution and scheduling, tile memory semantics bugs arise when the compiler incorrectly derives how memory behavior is structured across tiles and tile execution stages.
In tile-based compilers, memory layouts, buffer lifetimes, and synchronization boundaries are derived from tile configurations and scheduling decisions, rather than explicitly specified in the source program. Errors in these derivations can therefore lead to silent data corruption or incorrect results even when the source tile program is semantically correct.
We classify tile memory semantics bugs into three subcategories:
(1) indexing and stride bugs
,
(2) resource allocation bugs
, and
(3) ordering and caching bugs
, based on which aspect of compiler-synthesized memory behavior is violated.

Indexing and Stride Bugs.

Indexing and stride bugs arise when the compiler incorrectly synthesizes address computations from logical tile indices. Tile programs typically express memory access in terms of tile-local indices, while the compiler is responsible for lowering these accesses into concrete global or shared memory addresses, including boundary masking and tail handling. Errors in this synthesis can cause incorrect memory accesses derived from tile-local index arithmetic, even though the source program does not explicitly perform invalid indexing.
A representative example is reported in Triton
(
73
)
, where an out-of-bounds read occurs due to incorrect index computation within a tile. The bug arises at runtime when threads attempt to read memory addresses derived from compiler-generated tile index arithmetic that fails to account for tile boundaries.

Resource Allocation Bugs.

Resource allocation bugs arise when the compiler incorrectly infers the lifetime or reuse of registers or shared-memory buffers across tile phases. Tile compilers aggressively optimize memory usage by overlapping tile computation stages, reusing registers, and minimizing shared-memory footprints. These optimizations rely on precise lifetime analysis across tile-parallel regions. When such analysis is incorrect, registers or buffers may be freed or reused prematurely, leading to incorrect computation.
An illustrative example is reported in TileLang

Ordering and Caching Bugs.

Ordering and caching bugs arise when the compiler mismanages tile-derived ordering or reuse assumptions during codegen. Tile compilers often emit synchronization primitives and caching decisions implicitly as part of pipelined tile schedules, rather than relying on fixed procedural barriers. Errors in this process can lead to stale data reads, missing memory fences, or reuse of incorrect cached results.

4.5.
Type and Operator Bugs

This category accounts for 48.84% of all observed bugs and captures failures in preserving numeric and operator semantics during tile-level lowering and specialization (I5 in Table
1
).
Unlike control-flow or memory bugs, these issues arise when the compiler synthesizes arithmetic behavior—such as value propagation, type promotion, and operator logic—based on tile shapes, masks, and fusion strategies, rather than relying on explicit source-level semantics.
As a result, subtle mismatches can silently corrupt results without triggering runtime errors.
We classify type and operator bugs into three subcategories:

(1) special-value handling bugs
,
(2) data-type semantics bugs
, and
(3) operator implementation bugs
.

Special-Value Handling Bugs.

Special-value handling bugs occur when the compiler mishandles floating-point edge cases such as NaN propagation, denormal values, or signed zeros during tile-level execution.
In tile compilers, these semantics often depend on synthesized masking, boundary handling, and layout assumptions rather than explicit control constructs.
As a result, incorrect interactions between tile sizes and memory layouts can introduce NaNs even when the high-level computation is well-defined.
A representative example is reported in NVIDIA Warp
(
43
)
, where NaN values are produced when the tile size does not align with the matrix dimensions expected by
tile_load
.
This failure arises from a mismatch between tile-level boundary assumptions and the inferred memory layout used during loading, causing some tile lanes to read from memory locations that are never initialized or properly masked.

Data-Type Semantics Bugs.

Data-type semantics bugs arise when incorrect type propagation or promotion breaks the mathematical structure of tile-level layout and index transformations.
Tile compilers frequently split, fuse, and remap iteration axes, constructing algebraic mappings between logical coordinates and physical memory locations.
When type constraints are violated in this process, the resulting mappings may become ill-defined even if the computation itself is type-correct.
An illustrative case is reported in Apache TVM
(
4
)
, where failures in
transform_layout
,
transform_block_layout
, and
IndexMap::NonSurjectiveInverse
are triggered by data-type mismatches.
These transformations exist specifically to support tiled layout algebra, such as remapping multi-dimensional indices (e.g.,
(n,y,x)\rightarrow n\times 64+y\times 8+x
).
A mismatched data type breaks the assumptions underlying these index maps, causing compilation failures.

Operator Implementation Bugs.

Operator implementation bugs arise when the compiler synthesizes incorrect logic for operators under tiling, masking, or fusion. In tile-based compilers, high-level operators are frequently lowered into tile-local algorithms whose control flow, reduction structure, and boundary handling are derived from tile shapes and execution strategies. Errors in this synthesis can violate operator semantics even when the source operator itself is well-defined.
A representative example is reported in Triton
(

4.6.
Device-Specific Bugs

This category accounts for 3.99% of the observed bugs and captures failures caused by incompatibilities between compiler-generated tile kernels and target GPU hardware constraints (I1 in Table
1
). In these cases, the tile program and its transformations are semantically valid, but the lowered code violates device-specific requirements related to execution units or resource layouts. Such bugs typically surface only at runtime and stem from implicit assumptions about hardware capabilities during tile lowering.

One example is reported in TileLang
(
67
)
, where a kernel fails due to incompatible tile dimensions for matrix-multiply-accumulate (MMA) operations. The tile program specifies a logical tile size that cannot be evenly partitioned into the MMA atom layout supported by the target GPU. While the tile-level computation is well-defined, the compiler assumes that the tile can be decomposed into hardware MMA fragments during lowering. This assumption breaks when the tile dimensions do not align with the device’s MMA execution units, resulting in invalid codegen.

Crashes occur when compilation or kernel execution terminates abnormally due to exceptions, segmentation faults, or device-side errors. Although multiple root causes may contribute to a crash, the associated error messages often provide meaningful signals about the responsible transformation phase. Front-end crashes typically arise from type and operator bugs or IR construction bugs, where unsupported operations, incomplete type inference, or invalid IRs trigger early failures, e.g.,
“Cannot infer type of
‘tl.where’
”
or
“Mismatched operand types for fusion”
. In contrast, mid-end and back-end crashes are more commonly induced by control-flow, scheduling, or tile mapping bugs, where errors emerge during tiling, vectorization, or lowering—e.g.,
“Expected mask of shape (X, Y), got (X, 1)”
or
“Shared memory allocation exceeds device limits”
. Runtime crashes, such as CUDA launch failures or invalid memory accesses, frequently indicate incorrect indexing, launch configuration bugs, or violations of hardware constraints. While overlapping causes can obscure attribution, error signatures often localize the bugs to a specific phase in the compiler pipeline (I9 in Table
1
).

Correctness violations arise when the program completes execution without an error but produces incorrect results such as silent numerical inaccuracies, shape mismatches, or violated mathematical contracts. Although these bugs stem from diverse root causes, the manifestation is typically exposed via oracle-based testing: for example, comparing the output of a Triton kernel against a trusted PyTorch baseline, sweeping input data types (e.g.,
float16
vs.
float32
) for the same computation, or running the same logic across varying tile shapes and launch configurations. Type and operator bugs often lead to precision loss or accumulation drift that only appears under certain
dtypes
or fusion patterns. Memory bugs such as incorrect indexing or buffer aliasing are revealed when the output shape or value pattern diverges under different tensor layouts. Control-flow and scheduling bugs can manifest as off-by-one errors or masked tile regions, particularly under partial-tile cases, while tile mapping bugs may result in duplicated or missing output when the same input is executed with different grid or block shapes. Although the output may appear superficially correct, detailed comparison against reference implementations or metamorphic variants typically reveals the semantic discrepancy (I10 in Table
1
).

Performance bottlenecks arise when a kernel compiles and returns correct results, but exhibits poor runtime characteristics such as prolonged execution time, high memory footprint, or underutilized hardware resources. These symptoms are exposed through profiling tools (e.g., Nsight Compute, PyTorch timers) and manifest as execution stalls, shared memory overuse, or low arithmetic intensity. Although multiple root causes may contribute, the most common causes are memory bugs such as uncoalesced loads, excessive shared memory allocation, or omitted synchronization and type and operator bugs, where poor type specialization (e.g., unnecessary upcasting or incorrect fusion of precision modes) leads to degraded compute throughput. For instance, failing to apply warp-level intrinsics correctly under predication may serialize execution, while unguarded vectorization across partial tiles can trigger performance bottlenecks. Unlike correctness issues, performance bugs do not violate semantics, but instead reveal inefficiencies in tile-to-hardware mapping or operator lowering, and are often shape-dependent or architecture-sensitive (I11 in Table
1
).

Bug Detection Strategies

Based on findings in Table

, our study identifies two key components for detecting codegen bugs:
test input generation
and
test oracles
. Input generation aims to trigger bugs by exploring both
predefined general inputs
and

6.1.
Test Input Generation

Our findings indicate that developers frequently rely on random modifications of predefined inputs to expose codegen bugs. Such manual efforts are limited in coverage and reproducibility. Developers start with predefined inputs and apply random perturbations, such as altering precision, to generate new inputs. This ad hoc approach can be systematically automated using fuzzing techniques, which offer a structured means of input variation to improve bug detection (F6 and I6 in Table
1
).

6.1.1.
Predefined General Inputs.

These inputs represent principled variations over common tile program parameters.
Tensor shapes
as inputs are crafted to explore edge cases such as (i) small sizes and singleton dimensions (e.g., 1D or 1-element tensors), (ii) boundary sizes near tile multiples (e.g., 31/32/33 or 63/64/65), which reveal loop mispredication and mask bugs, and (iii) large or irregular shapes (e.g., 65,537 or prime sizes like 17, 29), which stress indexing logic, grid bounds, and resource allocation.
Memory layouts
as inputs are non-contiguous or transposed tensors, channel-last formats, and offsetted views are used to uncover stride miscalculations and misaligned memory accesses.
Tile and launch parameters
as inputs systematically vary tile size, number of warps, vector width, and unroll factors to stress synchronization logic, shared memory allocation, and control-flow generation.
Data types and values
like mixed-precision types (e.g., float16, bfloat16, int8), boolean masks, and extreme values (e.g., NaNs, inf, signed zeros) help expose type handling and IEEE-754 compliance issues.

Feedback
-

These inputs leverage mutation techniques to systematically generate inputs to trigger codegen bugs. Such techniques include: shape dimensions are incremented, padded, or transposed; data types are altered or upcast; value ranges are modified to test numerical stability and overflow; or layout permutations are introduced to break hidden assumptions. This technique simulates how developers explore bugs iteratively, but can be automated using mutation engines or fuzzing. In particular, greybox fuzzing
(

Test oracles are essential for verifying the correctness of results in GPU programs.
Our study finds that correctness is initially confirmed by comparing tile program results with outputs from corresponding PyTorch programs using the same predefined inputs.
When discrepancies arise, customized inputs or manifestation strategies can be applied to further investigate codegen bugs (F7 and I7 in Table

Our study reveals that developers primarily validate codegen correctness through ad hoc comparisons, such as running alternative kernel configurations or reference implementations.

Developers corrected loop guards, branch predicates, and instruction scheduling to restore semantic alignment at tile boundaries. Fixes included adjusting conditional expressions such as

Fixing IR Construction and Transformation Bugs:

In several cases, transformation passes were updated to maintain type correctness, dominance relations, and predicate coverage.

Fixing Tile Mapping and Launch Bugs:

Repairs targeted launch configuration mismatches, tile size inconsistencies, and invalid thread–block mappings. Strategies included altering tile shapes, adjusting block sizes, and refining mapping logic to preserve complete iteration coverage, particularly under partial-tile and prime dimension shapes.

Memory-related fixes introduced bounds checks, corrected indexing logic, and ensured legal memory allocation. Fixes addressed backend mismatches by adding architecture-specific specializations (e.g., PTX versions, vector width constraints) and inserting device capability checks. Some patches adjusted register usage, alignment constraints, or shared memory allocation to meet instruction set architecture (ISA) requirements across GPU generations.

Across all categories, most fixes required modifying the compiler’s codegen logic or transformation passes, underscoring the tight coupling between tile-level abstractions and hardware-aware backend design. Fixes for memory and type bugs were often more localized, while control and IR-related fixes spanned multiple stages of the compiler pipeline.

8.
Threats to Validity

Our findings are derived from a manual analysis of 301 real-world codegen bug reports, filtered to ensure relevance, correctness, and fix confirmation. While our methodology included independent reviews and joint resolution of disagreements, several threats remain.

External validity.
Tile programming is a relatively new framework, and its ecosystem is still maturing. The number of publicly available repositories and bug reports is limited compared to established GPU ecosystems like CUDA or DL frameworks. As a result, our dataset may not fully represent the complete spectrum of bugs that will emerge as adoption grows. Additionally, the lack of prior studies on tile-specific codegen bugs constrains comparative generalizability.

Selection bias
. Our bug corpus was collected from official and community-tracked tile programming projects, relying on publicly available issues and confirmed fixes. This excludes silent failures or unreported bugs in private codebases. While we enforced strict criteria for bug validity (e.g., closed status and linked patches), some edge cases may have been missed due to incomplete descriptions or ambiguous metadata.

Construct validity.
Root cause classification was guided by prior work on CUDA and DL bug taxonomies but adapted to tile frameworks’ unique programming model. Though reviewed by multiple authors, categorization remains subject to interpretation, especially in cases where abstraction layers obscure the exact failure mechanism.

Scope limitations
. Our goal was not to exhaustively characterize all tile codegen bugs but to surface representative patterns of bugs, their causes, and fixes. Findings are qualitative and exploratory, offering a foundation for future tool development and empirical studies.

10.
Conclusion

In this work, we present the first empirical study of codegen bugs in tile-based programming frameworks, uncovering their root causes, manifestation patterns, and detection challenges. Our analysis spans 301 real-world bugs and reveals that many bugs arise from the interaction between high-level abstractions and low-level hardware constraints, leading to subtle bugs in control-flow, memory, tiling, and type handling. To facilitate detection, we summarize bug detection strategies leveraging test input generation and test oracles. We believe this study lays a foundation for future research on verification, testing, and tooling for next-generation accelerator compilers.
