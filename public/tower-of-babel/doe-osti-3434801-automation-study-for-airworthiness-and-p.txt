Introduction
This report summarizes the findings on the Lawrence Livermore National Laboratory (LLNL)
Software Analysis and Optimization (SAO) team Sept. 2025 through March 2026 on the
“Automation Study For Airworthiness and Program Protection Software Certification” program.

The goal of this first phase of the project was to identify and define automatic analysis
techniques that can be used to verify conformance of software packages to defined
requirements. The requirements under consideration fell under two main topics: program
protection and airworthiness guidance. These topics do not bear much similarity at the policy
level, but the technical requirements of verifying them are similar, so there is some synergy to
be exploited.

This work will identify the appropriate open-source or COTS tools to perform automated
analyses of software properties defined in the aforementioned requirements documents based
on the selected target applications. These analysis tools were assessed against the provided
target application and compared to documented analyses of that application performed using
existing manual techniques.

Application Targets
Our target applications were a mixture of codebases that are representative of different classes
of software: two were open-source firmware implementations that represent different
architectural models of firmware design, and the third was a modeling and simulation system
from the Sentinel project.

The modeling and simulation code was the primary target used for evaluating program
protection. On this target, and other targets we consider evaluating, a consistent issue was the
lack of any definitive knowledge of their program protection constraints. As a proxy, we mocked
protection properties based on key words (names, comments, strings) that had a strong
indication of national security or defense applications. We were then able to perform a manual
examination of the code related to property protection.

Airworthiness was a somewhat more straightforward property to consider. We selected the
Ardupilot open-source firmware for airworithness evaluation tool demonstration. Ardupilot that
has been a go-to target for software analysis by other groups within DoW (e.g., DARPA), so it
had demonstrated interest. We identified a set of safety critical functions as the subject of
analysis, such as the initiation of a parachute release. Like other safety critical signals, the signal
passed from the software to activate the hardware systems that execute the physical release.

Identification of relevant high-level software properties
In all cases, we determined that a core property in both program protection and airworthiness
safety critical functions is that of flow and reach. Specifically, we must determine flow properties
such as “the signal associated with a critical function must flow undisturbed from its source to its
sink” or “the protected code must not be reachable from unprotected code except via approved
interfaces”.

Another key property to airworthiness is that of state machine verification. Although this is not
as critical for program protection, we decided that it was also a valid area of research for this
project. It is a common pattern in safety critical control systems in which a state transition
system determines the allowed states that the machine can be in (e.g., ready to release, safety
latch released, relay fires): in this case, we wish to determine if state transitions that are
forbidden by the functional model are allowed by the software implementation (e.g.,
transitioning from “ready to release” to “relay fires” without passing through the “safety latch
released” state).

Study Results
State transition systems

 The CodeQL system provides a strong offering between inflexible classical static
 analysis tools and highly specialized and complex compiler frameworks. Our
 experiments found that it is highly capable and efficient at designing bespoke analyses for
 problem-specific certification activities.

Embedded systems typically implement a discrete state machine that defines the actions that a
system takes based on sensor and control signals that it receives. These state transition systems
precisely define the behaviors that a system shall implement (“when the system is in the ready
state and receives a valid activation message, it transitions to the active state within 50ms”). A
key part of certifying a system based on state machines is to ensure that the software
implements the state transition system as designed. Existing tools that are widely used in
commercial aerospace and automotive, such as MathWorks Stateflow / Simulink or Ansys
SCADE, are well suited to this problem. In both cases state machines are transcribed explicitly
(often diagrammatically) and the tools support either formal model checking or simulation-
based testing to check that the state machines are correct. Correctness in this context entails
checking that no state transitions occur that are not allowed (e.g., a weapon cannot reach the
armed state without a signal originating from human input) and that states that must be
reached are actually reachable.

An important distinction in the analysis of state transition system implementations is temporal
vs non-temporal properties. Most model checking tools provide strong evidence for
“eventually” or “never” properties where there is no explicit time bound required – they may
determine that a state will actually be reached but will not check that it will do so within a
specific real-time window. Simulation-based analyses not based on formal model checking that
these products support provide some assistance here.

In parallel with this project focused on program protection and airworthiness problem domains,
we have a separate project looking at certification of safety-critical systems in which a critical
signal flow is a key verification concern. In this work we encountered example programs where
the behavior of the system at the system design and requirements level is defined as a state
transition system, yet the implementation in the program code did not explicitly represent the
state machine and instead relied upon a set of implicit indicators about valid states and their
transitions. Our judgement was that this was very dangerous because the state machine could

not be easily checked (due to it only being implicit in the code without explicit states) and the
implementation was unnecessarily complex.

Our recommendation for this kind of code that likely will arise in airworthiness settings is to use
tools that facilitate “correct-by-construction” implementations with deeply integrated model
checking capabilities. In particular, our team is performing an exercise to prototype components
of this system within Ansys SCADE to demonstrate that their model checking and analysis tools
will address the deficiencies we found in the hand-coded existing implementation. While these
tools require an initial up-front cost to adopt them, they drastically impact the long-term
lifecycle cost of a system by removing the need to reconstruct verification evidence from
potentially complex code written in languages that are exceptionally difficult to reason about
(such as C++).

Tool qualification: when is this necessary?

 Tool qualification is an important consideration in airworthiness certification
 processes. Commercial offerings commonly meet this requirement or offer services to obtain
 such qualification. Open-source packages do not currently meet this qualification
 requirement, thus limiting where they can be used in the certification process.
A question that arose while we were surveying tools was whether it was necessary to consider
only tools that were “qualified” for a specific standard, such as DO-178C. Qualification as
defined by DO 330 requires establishing where a tool falls in the table shown in Figure 1:

 Figure 1: DO-330 Tool Qualification Level Matrix

The software level defines the consequences of failure of the software itself:

 Level A: Failure may cause a catastrophic failure to the aircraft (e.g., loss of the aircraft).

                                                 LLNL-TR-2023159                                        5

 Level B: Failure may cause a hazardous failure, resulting in serious or fatal injury to
 occupants.

 Level C: Failure may cause a major failure, resulting in discomfort or minor injury to
 occupants.

 Level D: Failure may cause a minor failure, resulting in a slight reduction in performance or
 comfort.

 Level E: Failure has no effect on safety or aircraft operation

The criteria define the role that a tool plays in the airborne software:

1. A tool whose output is part of the airborne software and thus could insert an error.

2. A tool that automates verification processes and thus could fail to detect an error, and
 whose output is used to justify the elimination or reduction of:

 2.1. Verification processes other than that automated by the tool, or

 2.2. Development processes that could have an impact on the airborne software.

3. A tool that, within the scope of its intended use, could fail to detect an error. Criteria 3 tools
 are always TQL-5.

Fundamentally, this taxonomy essentially relates to risk level of failure to the burden or
responsibility placed solely on the software. A tool that is part of aircraft software whose failure
could cause a complete loss of the aircraft must meet TQL1 whereas a tool used in the
verification process that may only cause minor injuries to humans would have a lower TQL5
rating.

In our assessment, all the tools and techniques used to assist humans as certification aids, where
the certification decision is performed by a human using tool results only as evidence to support
their decision, fall into the TQL-4 category (with some at TQL-5).

All commercial vendors that we reached out to for automated test generation and static analysis
tools advertised existing qualification primarily in the aerospace and automotive industries
where they are already widely used. Many vendors also are willing to conduct a qualification
activity for additional contexts should the existing qualifications not apply. Such an activity

                                           LLNL-TR-2023159                                              6

would likely be performed with an existing organization that conducts these qualifications
(e.g., TÜV SÜD).

It is worth noting that no known open-source static analysis tools have existing qualification
packages. Adoption of those tools would require performing the process of generating a
legitimate qualification package. Anecdotally, the Frama-C tool appears to have undergone
qualification within some organizations, but we could not find any open qualification packages
to support those claims.

Visualization and results presentation techniques

 Visualization is valuable technique for helping humans to understand software or the results
 of an analysis on software, but viz is difficult to apply at scale. Viz should not be relied upon
 as a necessary step in analysis, the true “answer” must be up to formal techniques,
 but carefully prepared viz can help humans understand the results.
Graphs have been a popular way to present and analyze software going back to the very earliest
days of software development. Autogenerating graphs, rather than hand drawing them,
promises a way to both ensure that the graphs match the “ground truth” of the software, and to
generate them quickly. Unfortunately, this promise largely remains elusive.

We have investigated multiple pieces of graph generation software and even developed some
of our own. Many software analyses involve internal graphs, e.g. Control Flow
Graphs. However, that is not the topic of this section, as those graphs are not primarily
intended for visualization. Naively visualizing them generally only creates confusion. Graphs can
be good ways to display results in a way that makes sense to users, but significant care is
required.

Graphs of complex software are very frequently unintelligible to human users simply because
they have too much stuff on them. Software is extremely complex, See: Figure 2. We have
experimented with two solutions to this.

 1. A graph intended for static visualization must contain some internal logic for tightly
 focusing the information intended for display. Figure 3 is a Machine Chart, which uses
 larger graphs, like the call graph, internally, but filters them out such that only
 the relevant information is displayed. (A machine chart is strictly concerned with
 communications between concurrent processes.)

                                              LLNL-TR-2023159                                        7

 2. A graph that cannot be made simple enough for static display can be made interactive
 such that the user only sees the pieces they wish to see at any given time. Figure 4
 is a complex call graph but limited to only nodes that the user has chosen to expand.
 This is a powerful technique but does make the graph more difficult to
 communicate. The interactivity requires a specialized application; the graph cannot be
 simply dropped into a static document.

An alternate solution to the problem of limiting the display is to allow AI to attempt to decide
which parts of the graph are worth displaying. AI does a fairly good job of limiting graph size
and keeping it intelligible. But, at the cost of any ability to do analysis, as the graph cannot be
trusted to contain the necessary information. Figure 5 is an example generated by a popular AI-
based software understanding tool, DeepWiki. The resulting graph is easy to read, and looks
useful at first glance, but the AI hallucinated relations that don’t exist. The resulting graph is
more misleading than illuminating.

Assurance Case Management Tools

 Safety case management tools could enable have great potential to
 accelerate DoW program timelines but are currently immature and difficult to use. It is
 in DoW’s interest to nurture and develop an assurance case management tool, with the
 subset of MBSE features required for DoW projects.

There is a rich body of work on assurance case management tools, which are software tools for
hosting, interpreting, and validating the safety and assurance arguments for
a cyberphysical system. These systems have many merits for certification: they enable a certifier
to automatically ingest qualification arguments, they enable automated exploration of the
strength and consistency of a certification case, and most notably, they directly connect the
implementation of a system under inspection with formal reasoning about its behavior. While
they are popular in some civilian domains (most notably at NASA and in the European railway
industry), and there have even been some seed projects by DARPA (e.g., as part of the ARCOS
program), they have so far not caught traction in DoD contexts. As part of this project, we
explored the area of assurance case management tools to identify potential technology transfer
opportunities, as well as potential capability gaps between DoD needs and existing
management tools.

The vision of this class of tools is to provide benefits to developers, system engineers, and
program stakeholders related to software verification, automation of evidence ingestion, and
formal reasoning about assurance cases themselves. Safety case management tools are
intended to enable direct verification of software implementations against the properties
necessary for assurance. The goal is to eliminate the gaps between certification requirements, a
certification model that represents system behavior (such as a CAMEO model), and the system
implementation in software and hardware.

A key aspect of supporting verification and certification that these tools intend to provide is
automated evidence ingestion. Several tools have explored an automated workflow where the
safety case is set up to ingest ad-hoc evidence artifacts from a variety of sources such as test
suites, static analysis tools, model checkers, and so on. This enables several different teams to
develop certification evidence in parallel. In the ideal case it would enable the certifying
authority and the system developer to use the same assurance tooling, reducing overall effort
and redundant work.

                                             LLNL-TR-2023159                                        13

Safety case management tools enable qualitative and quantitative reasoning about the strength
of the assurance case. This enables the system developer to identify certification issues early on,
without needing to go back-and-forth with a certification authority. This includes analysis of
requirements to understand gaps or contradictions in complex requirements.

While these systems have many promising goals, they have not seen broad uptake for a few
reasons. Model-based systems engineering (MBSE) tools have grown in adoption, but
specialized assurance case management tools are less flexible than state of the art engineering
management tools used in practice like CAMEO. MBSE tools are flexible enough to encode
requirements and assurance cases, but typically provide weaker out-of-the-box analyses as
described above. Assurance case management tools also tend to have a higher barrier to entry
than existing management tools. They require the assurance case to be captured in a flavor
of precise formal logic, which can be foreign to systems engineers used to working with simpler
modeling languages like SysML. Finally, many of these tools are low TRL prototypes with few, if
any, polished commercial offerings. The most mature tool that we
encountered is the NASA developed AdvoCate system.

This area has great potential for accelerating DoW program timelines by accelerating currently
onerous certification and by enabling more robust systems. As such it deserves DoW attention
to address the gaps in MBSE approaches with respect to requirements analysis, automation of
evidence capture, and requirements-driven software analysis. The next generation of systems
engineering tools should adopt ideas from the assurance case management
community. Specifically, they should focus on capturing sufficient semantic design information
to support automation of analysis of both requirements and the eventual software
implementation. It is in DoW’s interest to nurture and develop an assurance case management
tool, with the subset of MBSE features required for DoW projects. Given the extensive history
of work NASA has performed in this area, the DoW and the broader US Government systems
engineering community would both benefit from cross-pollination with NASA’s assurance
engineers.

 AI tools show promise but cannot provide reliable evidence in their current state. Future
 work must include the combination of AI techniques with classical, deterministic program
 analysis to establish ground truth. Any AI tool must
 be rigorously evaluated alongside misleading information to ensure the tool is not misled
 by superfluous data.

Integration of AI tools in certification activities

AI tools are appearing everywhere in software development, systems design and understanding,
and evaluation activities. While not a core focus of our work, we did explore where these tools
can potentially aid when combined with classical program analysis tools. One area we explored
was taking a codebase and using AI tools to aid in rapidly assessing likely regions of interest to
focus on for program protection or security concerns.

In this experiment, we used standard large language models (e.g., the OpenAI models available
across government and industrial institutions) to perform a grading of code given a structured
set of instructions. These instructions asked for an assessment of how important different
components of code were for protecting technical superiority, cyber security, and intellectual
property. The models were tasked with ranking components against this set of provided
categories, and to produce a set of keywords that best describe the components with respect to
these categories.

Unlike typical LLM applications, we did not simply provide the raw code to the model and ask
for its response. We instead built a prototype system using the ROSE compiler framework to
extract units of analysis (at the function level) to bundle into each prompt. This allowed us
to perform two important tasks: first, we were able to isolate each function to prevent pollution
of information from nearby code, and second, we were able to change each component in a way
that did not affect its behavior but changed what the model was able to see. This second
change allowed us to perform a disciplined study of how the representation of the code
influenced the behavior of the models. For example, using compiler tools, we can rename code
elements (e.g., functions and variables) to determine if a variable name that has contextual
meaning (“weaponControlUnitState”) will cause the model to change its interpretation when it is
replaced with a generic name (“xState”). Similarly, we can change values within the program
code to see if those values influence the analysis.

Our findings were not surprising: when code is modified to neutralize any text to remove all
domain-specific semantic content, the models struggle to classify its purpose. The models
appear to key heavily off of this domain-specific content – words like “missile”, “trajectory”, and
so on, signal the purpose and intended use of the code far strongly than the raw program
logic.

The primary takeaway from this activity is that an experiment of this form can only be performed
reliably by combining AI techniques with classical, deterministic program analysis and

transformation methods. Relying solely on AI tools to perform this lacks the assurance
foundation that we get from employing program analysis methods that are well understood,
explainable, and reproducible. In the context of program protection, the value of such an
activity is not simply in the analysis of the code itself, but the measurement of the response of AI
systems when presented the code.

Conclusion
The LLNL SAO team has done a survey of tools and techniques for software certification under
the “Automation Study For Airworthiness and Program Protection Software Certification”
program. The goal of this first phase of the project was to identify and define automatic analysis
techniques that can be used to verify conformance of software packages to defined
requirements. The requirements under consideration fell under two main topics: program
protection and airworthiness guidance. These topics differ at the policy level but have similar
certification requirements.

We developed several recommendations for further work, including:

 1. Future software products should start from systems that natively provide evidence for
 certification, such as Ansys SCADE or Mathworks Simulink. These kinds of tools greatly
 simplify the work of certifying the software.

 2. The DoW should develop an assurance case management tool, with the subset of MBSE
 features required for DoW projects. NASA’s AdvoCate system may be a good starting
 point.

 3. If the software was written without certification concerns integrated throughout the
 process, it is very difficult to certify. But tools such as CodeQL can provide bespoke
 analyses for problem-specific certification activities. These require expert users to
 develop the custom analysis but are easily integrated into CI/CD workflows.

 4. AI Tools show promise, but must be paired with classical, deterministic
 techniques. While the DoW should take a skeptical eye to any proposed AI-based
 certification tool, autoformalization shows great promise, and research should be pushed
 forward in it.

As a first step to pushing automation in program protection activities forward, we propose
formalization of Program Protection Plan policies, and a project to research methods
to express individual plans in a formal, mechanically analyzable form. These projects have

significant potential benefit for the DoW by addressing the cost and schedule for
implementing program protection policies, and by providing an assurance backstop to AI-based
automation that may be implemented in this area. This work should greatly lessen the human
burden of certifying the plans.
