1 Abstract
This report summarizes the activities, technical accomplishments, and outcomes of the RAPIDS2
Institute project at the University of Delaware (UD).
 The RAPIDS2 Institute was a large multi-institution project with the objective of assisting
SciDAC and Office of Science application teams in the use of DOE supercomputing resources to
achieve scientific breakthroughs. The UD team contributed to this effort through work on formal
software verification. This thrust aims to reduce software developer time and effort, especially re-
garding debugging and testing, and to increase confidence in the correctness of the results computed
by the software.
 The primary verification methods developed are based on model checking and symbolic ex-
ecution, and the primary tool used was the CIVL model checker [22]. The basic techniques of
CIVL were extended in a number of directions to enable verification of a wider range of scientific
software. Among the most important accomplishments were a new CIVL front-end for verifying
Fortran programs [25]; a new approach for effective model checking of programs using OpenMP
parallelization [24]; and a new contract system for precise specification and verification of programs
that use the Message Passing Interface (MPI) [17].

2 Background on CIVL
Producing reliable scientific software is challenging. A survey [10] conducted in the 1990s pre-
sented experiments on a number of scientific packages written in C or Fortran. This work found
various defects in those packages that can affect the quality of the applications using them. Many
subsequent studies have reached similar conclusions. With the introduction of parallelism and
the increasing complexity of modern applications, concern with the “correctness problem” in the
scientific community is growing. [7, 8, 11, 12].
 To help make scientific software more reliable, a variety of verification tools have been developed
(e.g., [2, 14, 16, 23]). The CIVL model checker is one such tool.
 CIVL [22] is designed with the goal of being able to continuously evolve by either supporting
more programming languages or using more advanced verification techniques. This goal is achieved
using an intermediate verification language, CIVL-C. The front-end of CIVL focuses on translating
different programming languages and their parallel dialects to CIVL-C. The back-end concentrates
on verifying CIVL-C programs. Each part can be modified or improved independently.
 CIVL targets C programs that may be accelerated using one or a mix of several concurrency
languages or APIs, including MPI, OpenMP, Pthreads and CUDA. Users can also program directly
in CIVL-C; this approach is appropriate for prototyping and verifying algorithms independent of a
particular implementation.
 Figure 1 gives an overview of the structure of the CIVL platform.
 The front-end, ABC, consumes a program that can comprise multiple translation units, each
of which is written in C or CIVL-C (and now Fortran) and builds an abstract syntax tree (AST).
A sequence of transformers are applied to the AST. Each transformer replaces some program
constructs with equivalent CIVL-C code for a specific purpose. For example, there is an MPI
transformer that deals with MPI primitives, and a transformer that produces CIVL-C code in
which all expressions are side-effect-free. After all the transformations, the AST is pure CIVL-C,
i.e., it contains no dialect-specific primitives or side-effect expressions. Figure 2 gives a list of the
transformers in the front-end.

 The back-end takes the transformed pure CIVL-C AST and builds a CIVL model, which is a
lower level guarded transition system representation of the program. The CIVL verifier consumes
this model and uses symbolic execution and model checking techniques to verify or refute various
correctness properties. CIVL’s symbolic execution engine uses symbolic algebra techniques to
manipulate and simplify complex symbolic expressions, and also automated theorem provers to
decide the validity of first order formulas involving those expressions.
 CIVL checks a range of standard properties by default, including absence of assertion violations,
deadlocks, memory leaks, invalid pointer operations, and out-of-bound array indexing. Each of the
properties can be individually disabled. In addition, CIVL checks API-specific properties for each
of the concurrency APIs. For example, CIVL will report an error if it detects a possible data race
in an OpenMP program or if there are inconsistent calls to collective functions in an MPI program.
Furthermore, CIVL is able to check the functional equivalence (i.e., “input-output” equivalence) of
two programs.
 As a model checker, CIVL has the ability to produce a minimal counterexample when an error
is found, which is very valuable for defect isolation and understanding. But CIVL also exhibits a
well-known limitation of model checking: some of the program inputs, as well as the number of
processes, have to be bounded within a small scope. A similar limitation is imposed by symbolic
execution: the number of loop iterations and the recursion depth must be finite. However, the user
may optionally provide loop invariants for any or all of the loops in the program, and CIVL will
attempt to use these to verify programs with potentially unbounded loops.
 CIVL is free, open source software, available at https://civl.dev.

3 Verification of Fortran Programs
Publication: [25]
 Fortran is a structured imperative programming language with a unique set of features, such as
common data blocks and array reshaping and sectioning, that support efficient numerical comput-
ing. Many scientific applications, especially those requiring high performance, are written entirely
in Fortran; others have core subroutines or rely on external components written in Fortran. A 2018
report from the European Performance Optimisation and Productivity Centre states that over half
of the 151 HPC programs the centre had analyzed over a two-year period were written in pure
Fortran or a combination of Fortran and C or C++ [5]. Likewise, 12 of the 33 HPC benchmark ap-
plications in the U.S. Department of Energy’s widely-used CORAL suite have components written
in Fortran [13].
 This award supported a project to extend CIVL’s front-end to support a large subset of Fortran
[25]. Unlike previous work that translates Fortran to C, LLVM IR, or other intermediate formats
before verification, this work allows CIVL to directly consume Fortran source files. We extended
the parsing, translation, and analysis phases to support Fortran-specific features such as array
slicing and reshaping, and to find program violations that are specific to Fortran, such as argument
aliasing rule violations, invalid use of variable and function attributes, or defects due to Fortran’s
unspecified expression evaluation order. We demonstrate the usefulness of our tool on a verification
benchmark suite and kernels extracted from a real world application, Nek5000 [21].

4 Efficient Model Checking of Parallel Programs using OpenMP
Publication: [24]

 4

 OpenMP is a widely-used directive-based system for shared-memory parallelism. Like many
multithreading models, OpenMP specifies a significant language subset with the “sequential consis-
tency for data race-free programs” guarantee. In short, this means that if all sequentially consistent
executions of a program P are data race-free, then all executions of P are sequentially consistent.
Hence the programmer need only understand sequentially consistent semantics, both when trying
to ensure P is race-free, and when reasoning about other aspects of the correctness of P .
 In [24], we showed that such programs are also easier to verify. Specifically, there is a model
checking optimization which drastically reduces the number of states that need to be explored in
order to determine if the program has a data race. Moreover, if the program does not have a data
race, the same exploration is guaranteed to find violations to other standard properties, such as
assertion violations or out-of-bound array indexes.
 We evaluated this technique on a large subset of the DataRaceBench benchmarks [15], as well
as 10 additional C/OpenMP programs based on widely-used concurrency patterns. The accuracy
and performance of CIVL was compared with that of a leading static analysis tool for OpenMP,
LLOV [4]. On DataRaceBench, the tools are comparable in accuracy but LLOV is significantly
faster. However on the additional programs, which use “unstructured” concurrency primitives,
CIVL is able to correctly verify or refute many programs that LLOV cannot analyze.

5 A Contract System for MPI
Publication: [17]
 Procedure contracts [9, 19, 20] are a well-known way to decompose program verification. In
this approach, each procedure f is specified independently with pre- and postconditions or other
invariants. To verify f , one needs only the contracts, not the implementations, of the procedures
called by f . Contract languages have been developed for many programming languages. These
include the ANSI C Specification Language (ACSL) [3] for C.
 In this paper, we investigated ways to extend these techniques to parallel programs using MPI.
Our contracts apply to collective-style procedures in these programs. These are procedures f called
by all processes and that are communication-closed : any message issued by a send statement in f
is received by a receive statement in f , and vice-versa. The processes executing f coordinate in
order to accomplish a coherent change in the global state. Examples include all of the standard
blocking MPI collective functions [18, Chapter 5], but also many user-defined procedures, such as a
procedure to exchange ghost cells in a stencil computation. These procedures are typically specified
informally by describing the effect they produce when called by all processes, rather than the effect
of an individual process. They should be formally specified and verified in the same way.
 We developed a formal theory of collective contracts for message passing programs, including a
sound technique for verifying a collective procedure satisfies its contract. We realized this theory
in an extension to ACSL which incorporates concepts from MPI. The CIVL model checker was
also extended to read these contracts and verify collective procedures with small bounds on the
number of processes. This tool was applied to a variety of collective routines, including various
implementations of MPI collectives, diffusion equation simulation code, and code from the hypre
library [6].

6 Other Activities
Training and professional development. Professional training was an important part of the
project. A graduate student research assistant led developments in CIVL’s Fortran and OpenMP

 5

support, and was the first author on the two papers dealing with those topics. The work on
the CIVL MPI/contract system was the topic of another graduate’s student Ph.D. thesis. These
students also benefited from meetings with the FLASH personnel and our partners at Argonne
National Laboratory.

Verification competitions. The enhanced version of CIVL was used by the PI in an interna-
tional verification competition, VerifyThis 2022, in which CIVL won second place. PI Siegel also
presented the CIVL results at the competition.1 Siegel also participated in VerifyThis 2025 with a
graduate student, and together they won a recognition for Innovative Tool Feature: Model checking
based on symbolic execution.2

VSS 2025. The project partially supported the organization of a new workshop, the International
Workshop on Verification of Scientific Software, held as part of the ETAPS 2025 conference.3 PI
Siegel and Professor Ganesh Gopalakrishnan organized the workshop and edited the post-workshop
proceedings, which were published as volume 432 in the EPTCS series. The award also supported
work on a paper [1] co-authored by Siegel in that workshop. The paper deals with the question of
applying formal methods in climate modeling software and includes a relevant CIVL example.

SIMD instructions. Progress has been made on extending CIVL to verify programs that use
OpenMP SIMD operations. The first challenge was determining the precise semantics of the SIMD
directive. The OpenMP Specification is not clear on this issue; it refers to the preservation of
“lexical forward dependencies,” a term that is not defined. Questions directed to the OpenMP
standardization committee led to a wide-ranging ongoing discussion on this issue, which is still
not resolved. In the meantime, we have engineered CIVL to allow a user to explicitly label the
dependencies in their code, so that verification can take place under different interpretations of this
notion.

Education. The enhanced CIVL tool was used in a course, CISC 475/675: Principles & Practices
of Software Engineering, at the University of Delaware in Spring 2024. The course had about 35
advanced undergraduates and beginning graduate students. All of these students used CIVL to
specify and verify simple C programs that manipulate arrays. One of these students, an under-
graduate, elected to participate in summer research projects with Dr. Siegel working on CIVL and
creating a new, parallel (multithreaded) model checking kernel for CIVL.

Dissemination. The work supported by this project has been disseminated through participation
in conferences and meetings, in addition to publications. PI Siegel presented the work on OpenMP
verification at CAV 2023 (the International Conference on Computer-Aided Verification) and during
a RAPIDS2 virtual meeting on October 18, 2023, and at a FastMath virtual meetings on November
2, 2023. He presented the work on MPI contracts at CAV 2024. A graduate student presented the
work on Fortran at TACAS 2022. The VSS workshop mentioned above resulted in wide-ranging
discussions between formal methods researchers and scientific software experts. A graduate student
presented a paper demonstrating how CIVL can be used to verify sparse matrix algorithms, and the
work on climate modeling was presented by a co-author. The CIVL web site was also significantly
enhanced during this period, providing a much more detailed user manual and more examples.
