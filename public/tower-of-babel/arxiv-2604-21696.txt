Towards Universal Tabular Embeddings: A Benchmark Across Data Tasks [Experiment, Analysis & Benchmark]
Liane Vogel, Kavitha Srinivas, Niharika D’Souza, Sola Shirai, Oktie Hassanzadeh, Horst Samulowitz

Abstract
. Tabular foundation models aim to learn universal representations of tabular data that transfer across tasks and domains, enabling applications such as table retrieval, semantic search and table-based prediction. Despite the growing number of such models, it remains unclear which approach works best in practice, as existing methods are often evaluated under task-specific settings that make direct comparison difficult. To address this, we introduce TEmBed, the T abular E mbedding Test B ed , a comprehensive benchmark for systematically evaluating tabular embeddings across four representation levels: cell, row, column, and table. Evaluating a diverse set of tabular representation learning models, we show that which model to use depends on the task and representation level. Our results offer practical guidance for selecting tabular embeddings in real-world applications and lay the groundwork for developing more general-purpose tabular representation models.

1.
Introduction

Representation Learning on Relational Data.

Tabular data is a core data modality in database systems and remains the dominant format for structured data management in practice.
Consequently, representation learning for relational and tabular data has become an important research direction at the intersection of databases and machine learning.
The goal is to embed tables in a way that captures semantic, structural, and statistical properties such that the resulting embeddings are reusable for downstream applications.
As shown in Figure
1
, tabular embeddings must capture four different levels of structural information, each of which is useful for different tasks; e.g., duplicate detection requires row-level embeddings, while table discovery requires table-level embeddings.

Figure 1
.
Overview of TEmBed. We systematically evaluate tabular embeddings covering four representation levels: cell, row, column, and table on a diverse set of tasks across 69 datasets.

Tabular Foundation Models.

Recently, a growing number of table foundation models
(
37
;
18
;
6
)
have been introduced with the goal of learning universal representations of tabular data that transfer across tasks, domains, and datasets without requiring additional training.
These models leverage large-scale pretraining on heterogeneous data sources, enabling them to produce cell-, row-, column-, or table-level embeddings for any new table.

Similar developments in natural language processing have been accompanied by standardized evaluation frameworks, most notably the Massive Text Embedding Benchmark (MTEB)
(
36
)
, which enables systematic comparison of general-purpose text embedding models across diverse tasks and is the de facto standard for the field.
However,
no analogous benchmark exists for tabular embeddings
. As a result, existing evaluations are narrow, task-specific, and use different embedding levels with incompatible protocols, making it difficult to comprehensively compare models
(
2
)
.

Assessing the semantic and structural quality of learned embeddings is inherently challenging, as it often requires ground truth signals that vary across tasks and domains. For tabular models, this challenge is exacerbated by the different granularity levels of embeddings required for tables, which may require fundamentally distinct evaluation criteria: a good table-level embedding must capture global schema and content, while a good cell-level embedding must reflect local value semantics in context.

Contributions.

As our core contribution, we introduce
TEmBed
, a comprehensive benchmarking framework for tabular embeddings.
Our framework evaluates models across cell-, row-, column-, and table-level tasks using a diverse collection of datasets, including some newly developed benchmarks. Further, TEmBed provides an open-source toolkit to easily extend both the supported models and benchmark datasets, enabling consistent measurements of model performance, time efficiency, and resource consumption across diverse tasks.
By providing a common evaluation framework, TEmBed enables meaningful cross-task comparison, supports informed model selection, and establishes a foundation for developing more general-purpose tabular representation models.

Our main contributions are:

(1)

We introduce the first comprehensive benchmarking framework for tabular embeddings that spans multiple datasets, tasks, and embedding levels (cell, row, column, table). We incorporate multiple existing public datasets and complete this selection by introducing multiple new datasets.

(2)

We provide an extensible open-source test bed with efficiency measurements that works across a large diversity of different embedding models.

(3)

We perform an comprehensive empirical study of state-of-the-art tabular embedding models, assessing their performance, computational cost, generalization across tasks, and offer practical guidance for model selection.

2.
Background

2.1.
Tabular Data Representations

Table Encoders.

Learning representations of tabular data has been an active research area over the past years, as surveyed by
2
.
Early work applied the pre-training and fine-tuning paradigm to relational web-tables, using objectives such as masked entity recovery
(
11
)
, corrupt cell detection
(
21
)
or jointly training on tables and surrounding text
(
50
)
.
Most of these models targeted specific downstream tasks, such as table question answering
(
17
)
or column type annotation
(
43
)
.
More recent work such as HyTrel
(
6
)
takes a more universal perspective, modeling tables as hypergraphs to produce representations at all four granularity levels - cells, rows, columns and tables.
A simpler but widely adopted approach to produce tabular embeddings foregoes tabular-specific pretraining altogether: table content is serialized into a flat text sequence, typically by concatenating column headers and cell values, and passed to a general-purpose text embedding model
(
22
;
3
)
.

LLMs for Generative Table Reasoning.

A parallel line of work adapts large language models to tabular data for generative and conversational reasoning tasks.
Models such as TableLlama
(
51
)
and Table-GPT
(
30
)
are fine-tuned to support natural language interaction with tables, enabling question answering, SQL generation, summarization, and interactive data processing.

These models target tasks end-to-end generative use cases and operate in a prompt-driven setting, making them complementary to the task-agnostic embeddings evaluated in this benchmark.

Tabular Prediction.

A distinct line of work focuses on tabular prediction, the task of predicting a target column from the remaining columns of a table, analogous to classical supervised learning on structured data.
Traditionally dominated by gradient-boosted tree methods such as XGBoost
(
7
)
, this field has seen growing interest in foundation model approaches.
TabPFN
(
18
)
pioneered in-context learning for tabular prediction, training a Transformer on synthetic and real-world data to perform classification or regression at inference time without gradient updates.
TabICL
(
37
)
extended this paradigm with improved scalability to larger datasets.
Other approaches fine-tune large language models on broad collections of real-world tables
(
14
)
by serializing rows as text.
Further approaches incorporate semantic signals — such as column headers and categorical value names — by encoding table content with pretrained text
(
41
)
or graph-based models or incorporating external knowledge
(
24
;
25
)
.

Although primarily optimized for predictive performance, these models produce intermediate row-level representations that can in principle be extracted and evaluated as general-purpose embeddings — a question we directly investigate in this work.

2.2.
Benchmarking Table Foundation Models

Existing task-specific benchmarks.

Existing benchmarks for tabular data are typically task specific.
For example the recent benchmark suite TARGET
(
22
)
focuses on table retrieval for generative tasks, evaluating retrieval performance of sparse and dense retrievers as well as their impact on downstream table question answering and text-to-SQL tasks.
For data discovery tasks over data lakes, LakeBench
(
42
)
provides benchmarks for Table Unionability and Joinability search.
In the field of tabular prediction, frameworks such as TabARENA
(
12
)
, TALENT
(
31
)
, and TabReD
(
39
)
offer extensive comparisons of models across many predictive datasets, but they are limited to predictive tasks, whereas our benchmark captures multiple tasks, including retrieval.

Broader Embedding Evaluations.

In parallel,
19
recently proposed a benchmark to evaluate task-agnostic embeddings from tabular foundation models, focusing on outlier detection and tabular prediction.
Compared to our work, they consider only row-level embeddings and only a small set of models.

Analytical Studies.

Other efforts, such as Observatory
(
9
)
, propose a formal framework to analyze embedding representations over tables by measuring properties like sensitivity to column order and sample fidelity, and are therefore orthogonal to our work.
Our benchmark focuses on performance on downstream tasks, therefore measuring model ability in real-world scenarios and supporting practitioners in selecting specific models for their tasks.

Evaluating LLMs on Table Tasks.

Additionally, there is an emerging field of benchmarks evaluating LLM capabilities on tables, including MMTU
(
49
)
, which spans dozens of tasks such as entity matching and table transformations, and
(
44
)
, which evaluates structural understanding tasks like cell lookup and row retrieval.
These benchmarks evaluate the reasoning capabilities of conversational LLMs rather than the quality of tabular representations.
While some tasks, like semantic-join detection, overlap with TEmBed, embeddings and conversational models serve fundamentally different use cases, making both approaches complementary.

Evaluation Criteria for Tabular Embeddings.

Besides measuring embedding quality based on down-stream performance, there are other approaches which try to measure more abstract qualities of embeddings.
One approach is to focus on the interpretability of the embedding space itself.
Methods such as TabEE
(
10
)
cluster embeddings and generate explanations for the formed groups, providing diagnostic insight into what structure a model has captured.
Our benchmark takes a more application-oriented view, measuring embedding quality through performance on concrete tasks with well-defined ground truth labels.

Overall, systematic evaluation frameworks analogous to text embedding benchmarks such as MTEB
(
36
)
are still missing for tabular embeddings, motivating our benchmark, which covers multiple embedding levels and tasks in a unified framework.

3.
Benchmark Overview

With TEmBed we introduce a framework to systematically evaluate tabular embedding approaches across a diverse range of tasks and datasets.
Recognizing that no benchmark can ever be fully comprehensive, we design the TEmBed framework to be easily extensible, allowing new approaches, tasks and datasets to be integrated with minimal effort.

A key design dimension of TEmBed is the level of granularity at which embeddings are computed.
We evaluate embedding approaches across row-, column-, cell-, and table-level tasks, though not all approaches are able to compute embeddings for every level.

Row embeddings
encode individual table rows into vectors and are widely used in retrieval tasks, such as recommending similar products or detecting duplicate customer records, and for predictive tasks like classification and regression.

Column Embeddings
encode individual table columns and are particularly relevant for data integration scenarios, including the discovery of related or joinable tables in data lakes and schema matching, where semantically equal columns from different schemas need to be found.

Cell Embeddings
operate at the level of individual values, enabling tasks such as error detection within tables or de-duplication of different surface forms within a column.

Table Embeddings
capture entire tables as vectors and support tasks such as table retrieval, for example, when answering questions over table data lakes, the relevant tables must first be found in order to answer the question.

Tasks and Datasets.

TEmBed currently includes six tasks across a total of 69 datasets, as listed in Table
1
and introduced in detail in Section
3.1
.
All datasets are publicly available: some are constructed by us, with code released alongside the benchmark, while others are downloaded from their respective repositories.
Evaluation is performed using deterministic test cases, reporting common task-specific metrics.
The extensible design of our framework makes it simple to add further datasets and tasks.

Configuration and Reproducibility.

Additional embedding approaches can be evaluated using TEmBed by implementing provided interfaces, enabling consistent evaluation across representation levels.
Using configuration files, different hyperparameters per approach can be easily evaluated and compared.
For the experiments in this paper, we use the default configuration per approach as stated in the respective papers and release the configuration files to ensure full reproducibility.

Performance and Resource Metrics.

In addition to task performance, in our framework we also track the runtime of the approaches and the resource consumption, namely CPU usage and required memory and GPU memory.
These measurements provide important insight into the efficiency and scalability of different approaches, particularly on large datasets.
To ensure comparability, all experiments reported in this paper were run on a machine with a single NVIDIA A100 GPU with 80 GB of VRAM, and an AMD EPYC 9554P 64-Core CPU (128 threads) @ 3.1 GHz and 792 GB of system memory.

3.1.
Included Tasks

TEmBed currently includes the following six different tasks:

Row Similarity Search

Retrieving the most similar rows in a table is a critical task in many real-world applications, used to recommend products in e-commerce or detect duplicate entries for data cleaning.
We include the task to evaluate the ability of tabular embedding approaches to map semantically similar rows to nearby vectors in the embedding space.
TEmBed contains nine different datasets, constructed from existing entity matching and clustering datasets.
Our experiments show that LLM based encoders perform best on this task, while row embeddings extracted from models trained for tabular prediction fall short.

Triplet-Based Row Evaluation

Triplet-based row similarity evaluation is a systematic way to measure whether row embeddings capture meaningful semantic relationships.
Given a query row, its embedding should be closer to embeddings of semantically related rows than to embeddings of unrelated rows.
We construct two new datasets leveraging Wikidata, which allows us to automatically generate structured triplets covering a wide range of semantic distances.
Our experiments show that LLM-based models again perform strongly on this task.
In contrast, tabular prediction models, while better than the random baseline, still exhibit notably weaker performance.

Tabular Prediction

Tabular prediction is a key challenge in many real-world applications, including risk assessment and credit scoring, where accurate classification and regression are critical for decision-making.
To evaluate the quality of row embeddings, we use them as input features for supervised learning tasks from the TabArena
(
12
)
benchmark.
Our findings indicate that dedicated tabular prediction models, such as TabICL and TabPFN, perform strongly, whereas embeddings derived from LLM-based models underperform relative to the XGBoost baseline, suggesting that they fail to retain sufficient information from the original table for this task.

Column Similarity Search

Finding semantically similar columns is the base for determining joinability and unionability of tables, as well as for performing schema matching between databases.
In TEmBed , we evaluate column embeddings in a similarity search task, aiming to identify semantically similar columns for a given query column, using four existing public datasets.
Our findings show, that text embedding models reach the highest performance.

Table Retrieval

Since retrieving tables is a major component in data discovery and many RAG pipelines, we have also included it as a task in TEmBed.
We construct a dataset based on GitTables
(
20
)
, focusing on retrieving tables that belong to the same GitHub repository.
Only few of the benchmarked models are able to compute table embeddings.
In our experiments, GritLM achieves the highest performance.
Interestingly, we observe that the impact of example data from the table on the results varies depending on the model, with some benefiting from additional information and others not.

Cell Level Semantic Retrieval

Cell level semantic retrieval is a fine-grained task that evaluates how cells referring to the same real-world entity are embedded from different tables.
For TEmBed, we construct a new dataset based on data from the S2abEL dataset
(
32
)
, focusing on cell-level semantic retrieval.
Our results show that the IBM Granite R2 model achieves the highest scores. Notably, while many models benefit from a clean version of the data, there are exceptions, including some models that remain unaffected by the additional formatting in the uncleaned data.

Overall, our experiments on TEmBed demonstrate that current embedding approaches are not universally applicable, and that the choice of model depends on the specific task and dataset.
This underscores the importance of carefully selecting the most suitable model for a given task and dataset, and highlights the ongoing need for research into more robust and adaptable embedding models.

4.
Benchmarking Row Embeddings

We benchmark the performance of row embedding models on three critical tasks, that underpin a wide range of applications: row similarity search for recommendation and duplicate detection, triplet tests to systematically assess embedding quality and tabular prediction for assisting decision-making by predicting outcomes.

4.1.
Row Similarity Search

Task Description.

The goal of row similarity search is to find the most similar rows in a table given a query row.
For example, in an e-commerce table containing sold products, the task could be to identify products similar to a given item that will then be displayed to a user, such as other red shoes from comparable brands.
Another use case is detecting duplicate rows that refer to the same product but appear multiple times due to data integration errors.
From an embedding perspective, a high-quality row embedding model should map semantically similar rows to nearby vectors in the embedding space, while mapping dissimilar rows farther apart.
Row similarity search therefore provides a suitable task for assessing the quality of row embeddings.

Dataset Construction.

Existing benchmarks do not directly target row similarity search.
To address this, we construct evaluation data based on datasets for entity matching and entity clustering, two closely related entity-centric tasks.
Entity matching identifies pairs of rows across tables that refer to the same real-world entity, while entity clustering groups multiple rows corresponding to the same entity.
Both tasks provide ground-truth annotations that define which rows are semantically equivalent, which we leverage to construct semantic search relevance labels.
For TEmBed, we adapt nine datasets: seven entity matching datasets
(
27
;
34
)
and two entity clustering datasets
(
40
)
.
In the seven entity matching datasets, the two tables always share the same schema, so that we can merge the data easily into a single table.
Each positive entity matching pair is used to create a test case: one row serves as the query and the other as the ground-truth relevant row.
For the entity clustering datasets, we select one row from each cluster randomly as the query, and all other rows in the cluster are treated as relevant.
This construction ensures that each query row has at least one relevant retrieval target, enabling meaningful evaluation of embedding-based similarity.

Evaluation Methodology.

For the experiments, we create a vector representation for every row in the table.
Given a query row embedding, we retrieve the most similar other row embeddings ranked according to cosine similarity.
We measure retrieval performance using standard information retrieval metrics.
Mean Reciprocal Rank (MRR) captures how highly the first relevant row is ranked for each query.
We use a cutoff of 50 in our experiments.
For the clustering based datsets, if multiple ground-truth rows appear as a contiguous block we collapse that block to its earliest rank.
We also report Recall@k for
k\epsilon\{1,3,5,10\}
, which measures the fraction of queries for which at least one relevant row is retrieved among the top-k candidates.

Experiments

The results of benchmarking the different embedding approaches for row similarity search are shown in Figure

.
Surprisingly, the universal text embedding models GritLM, IBM Granite R2 and MiniLM achieve the strongest performance in this task, while embeddings extracted from the models developed for tabular prediction perform substantially worse.
This indicates that representations optimized for row-level prediction encode different aspects of the data than those needed for effective similarity-based retrieval.

4.2.
Triplet-Based Row Embedding Evaluation

While row similarity search provides a natural benchmark for evaluating embeddings on real-world entity matching and clustering datasets, these datasets are limited in the diversity of semantic relationships they capture.
To complement this evaluation and enable a broader, more systematic assessment of embedding quality, we propose to include benchmarks where the ground-truth similarity between rows is rooted in hierarchical relationships.
For example, in a product dataset, a smartphone and a laptop (both under
electronics
) are more similar than a smartphone and a jacket (
electronics
vs.
clothing
), reflecting their positions in the hierarchy.
Such hierarchies provide a structured ground truth and allow us to automatically generate structured test cases covering varying degrees of semantic similarity.

In this work, we propose to construct such hierarchies and associated tables leveraging Wikidata
(
46
)
, a large-scale, openly available knowledge base that contains structured data from various domains.
For TEmBed, we build two of such hierarchies, as visualized in Figure
3(a)
.
One hierarchy using literary genres, and one of astronomical objects (including classes such as
star system
,
galaxy
or
quasar
).
We chose the books domain, because genres provide a natural and interpretable hierarchical structure for semantic similarity.
The astronomical domain was selected because objects contain many numerical properties, such as
distance from earth
or
radial velocity
.
This allows us to evaluate models’ ability to represent and reason over numeric as well as textual information.

Task Description.

Triplet-based evaluation provides a systematic way to measure whether row embeddings capture meaningful semantic relationships.
The core idea is simple: given a query row, its embedding should be closer to embeddings of semantically related rows than to embeddings of unrelated rows.
To formalize this, we construct triplets (x,y,z), where x is the query row, y is a “closer” row with stronger semantic similarity, and z is a “more distant” row with weaker or unrelated semantics.
A triplet is considered correct if the embedding similarity satisfies sim(x,y)>sim(x,z), and incorrect otherwise.

To create concrete test cases, we leverage hierarchical relationships between classes in Wikidata.
Figure
3(a)
visualizes such a hierarchy build for genres of literary work items included in Wikidata.
Rows associated with nearby classes (e.g. books from
Fantasy
and
Science Fiction
genres) in the hierarchy are treated as “closer” (y), while rows from more distant classes are treated as “more distant” (z).
This allows us to automatically generate structured triplets covering a wide range of semantic distances, enabling fine-grained evaluation of row embedding quality.

Dataset Construction.

We construct our dataset by collecting class items for the hierarchies from Wikidata, specifically retrieving all
literary work (Q7725643)

genre (Q483394)
classes and recursively all
subclassOf (P279)
property classes of the
astronomical object (Q6999)
item.
The hierarchy is then constructed incrementally, starting from a predefined root structure, and classes are inserted one by one based on their superclass information.
To address potential issues with greedy insertion decisions, we perform a reordering step to relocate nodes to deeper positions whenever a more specific valid superclass path becomes available.
As final outputs, we obtain a genre hierarchy with 111 genre classes and an astronomical object classes hierarchy with 113 included classes.
For each class included in the hierarchy, we then collect real instances (concrete books or astronomical objects) from Wikidata along with their properties, creating tables as outlined in
(
45
)
.
As the approach results in very broad and sparse tables, we prune columns where more than 95% of the column values are missing and keep only items wich have an English label.
As final outputs, we obtain a table containing books with 1203 rows and 281 columns, and a table with astronomical objects, with 8034 rows and 41 columns.
We then construct evaluation test cases, by generating triplets based on hierarchical relationships between entities.
In the books domain, test cases are created by pairing books with similar genres, while in the astronomy domain, test cases are generated by pairing objects within the same semantic branch, resulting in 903 and 2000 test cases, respectively.

Evaluation Methodology.

Triplet evaluation compares embeddings of three rows (x,y,z), expecting that sim(x,y)>sim(x,z) according to cosine similarity in embedding space.
The fraction of correctly satisfied triplets is reported as triplet accuracy, providing a direct measure of how well the embeddings preserve hierarchical semantic relationships.

4.3.
Tabular Prediction

Beyond capturing semantic or hierarchical relationships, embeddings should preserve information useful for downstream prediction tasks.
For example, in a product table, embeddings may be used to predict whether a product will sell well or its likely price range.
In general, higher-quality embeddings should retain more of the information contained in the original row, enabling downstream models to learn more accurate predictors on top of them.
To complement the similarity-focused benchmarks, we therefore evaluate embeddings on standard tabular prediction tasks, including classification and regression, and use prediction performance as an additional indicator of overall embedding quality.

Task Description.

We evaluate row embeddings on standard tabular prediction tasks, to assess how well they preserve information from the original table that is useful for supervised learning.
Since not all embedding models provide a native prediction head (e.g., Hytrel and sentence-transformer models), we use the learned embeddings as input features for a downstream classifier, as visualized in Figure
4(a)
.
This allows us to compare their ability to support predictive modeling.

Dataset.

We evaluate on all 51 datasets from the TabArena-Lite benchmark
(
12
)
, a curated collection of real-world tabular classification and regression tasks spanning diverse domains.
For each dataset, we follow the pre-defined TabArena-Lite splits (fold 0, the “lite” setting) and adhere to the standard evaluation protocol.
We report
ROC AUC
for binary classification,
log-loss
for multiclass classification, and
RMSE
for regression tasks.

Evaluation Methodology.

For each dataset, we first embed all rows of the training set using the evaluated model.
We then train a downstream classifier on these embeddings

TabPFN

and
SAP-RPT-1

The prediction performance on the test set reflects how much task-relevant information is preserved in the embeddings.
This evaluation protocol follows prior work

48

5.
Benchmarking Column Embeddings

5.1.
Column Similarity Search

Task Description.

Column similarity search aims to identify, for a given query column, other columns in a collection of tables that are semantically similar.
This task plays a central role in many data management and analytics scenarios, including dataset discovery, schema alignment, and data integration.
For example, given a column containing product identifiers in a sales table, column similarity search may retrieve columns such as
item_id
or
product_code
from other datasets, enabling data enrichment or feature transfer.
Similarly, a column describing customer locations may be matched with
city
or
region
columns from external sources.
In such cases, similar columns are expected to represent comparable concepts and exhibit compatible value distributions, even if they differ in naming conventions or formatting.
Column similarity search therefore goes beyond exact string or value matching and requires models to capture both semantic meaning and data characteristics.
As a result, it provides a natural benchmark for evaluating the quality of column representations and their suitability for downstream analytical tasks such as schema matching or joinability detection.

Datasets.

We evaluate column similarity search using four publicly available joinable column benchmarks drawn from prior work on join discovery and dataset matching. These datasets provide ground truth annotations for which pairs of columns across tables are joinable.

Nextia
JD

(
13
)
comprises collections of tables obtained from open data repositories such as Kaggle and OpenML labeled with join quality for column pairs.
Building on the work of
8
, we incorporate the small and medium testbeds from Nextia
JD
, comprising datasets with file sizes ranging from
1
to
100
MB, and
100
MB to
1
GB respectively.

The
Valentine
benchmark
(
28
)
defines schema/attribute matching scenarios for dataset discovery and includes column pairs that are joinable under exact or noisy matching conditions, providing a good basis for column similarity evaluation.
We use the
semantically-joinable
subset in our evaluations.

The
OpenData
benchmark
(
26
)
contains heterogeneous tables from open government and web sources, annotated with semantic joinability ground truth that captures both syntactic and semantic column relationships based on human annotations.

The
WikiJoin
dataset from the LakeBench suite
(
42
)
provides additional join discovery testbeds drawn from web table corpora, where joinable columns are annotated across loosely structured sources.
We subset the original data lake to 659 tables to make it more tractable for testing embedding models, and refer to this subset as
WikiJoin-Small
.

Evaluation Methodology.

We frame column similarity search as a retrieval problem: given a query column from one table, the task is to rank all candidate columns from a corpus of tables according to their joinability with the query. For each dataset, ground truth joinable column pairs define which candidate columns should be considered relevant.
Each evaluated model computes an embedding or similarity score for every column. We then rank candidate columns by cosine similarity to the query.
Retrieval effectiveness is measured using standard IR metrics such as Mean Reciprocal Rank (MRR) and Recall@k, which capture how well joinable columns are prioritized in the ranking.

6.
Benchmarking Table Embeddings

Table embeddings are represent entire tables as dense vectors, enabling efficient and scalable solutions for critical data management tasks.
In enterprise repositories, they facilitate semantic search, allowing analysts to quickly locate relevant data, such as retrieving all customer transaction tables following a corporate merger.
In data governance, table embeddings support classification and anomaly detection, such as flagging tables containing personally identifiable information (PII).

6.1.
Table Retrieval

Task Description.

Table retrieval is the task of identifying and ranking tables relevant to a given query, which may be expressed as a natural language description or an example table.
This task is foundational for data discovery in large repositories, such as enterprise data lakes or open data portals.
High-quality table embeddings are essential for capturing both the semantic content and structural properties of tables, thereby enabling accurate and efficient search.

Dataset.

For TEmBed, we construct a new table retrieval dataset based on GitTables
(
20
)
.
GitTables consists of CSV tables extracted from public GitHub repositories and provides a large collection of real-world tables from diverse domains.

From GitTables, we select 20 topic-specific subsets (referred to as
data lakes
), each corresponding to a single high-level table topic provided in the dataset metadata (e.g.
orbit period
, or
inflation rate
).
Restricting each data lake to a single topic ensures that retrieval cannot rely solely on coarse domain differences and instead requires identifying semantically related tables within a domain.

For each data lake we include all available tables of the selected topic, each containing a few hundred tables.
To construct retrieval test cases, we select query tables from repositories containing at least five tables to ensure a sufficient number of relevant targets.
For each query table, the remaining tables from the same repository are treated as ground-truth relevant tables.
In total we construct 348 test cases.

Evaluation Methodology.

For each data lake, embeddings are computing for all tables using the evaluated approach.
Given a query table, we retrieve the most similar tables from the same data lake using cosine similarity between embeddings, excluding the query table itself.
We report standard information retrieval metrics.
Recall measures the fraction of relevant tables retrieved among the results, where
k
equals the number of ground-truth tables.

Mean Reciprocal Rank (MRR)
measures the rank of the first relevant table, and
Mean Average Precision (MAP)
evaluates the overall ranking quality.

7.
Benchmarking Cell Embeddings

Cell embeddings are useful whenever fine-grained semantic information needs to be caputred at the level of individual table entries.
For example, in a data integration scenario, one might want to identify all mentions of the same entity across multiple tables in a data lake, even when the values are written differently, such as
NYC
and
New York City
.
Accurately representing cells in an embedding space enables tasks like entity resolution, deduplication, and semantic search at the cell level.

7.1.
Cell Level Semantic Retrieval

In TEmBed, we include a cell-level semantic retrieval task, to assess whether embeddings of cells that refer to the same real-world entity are close to each other in the vector space, despite variations in surface form or formatting.

Task Description.

Given a query cell from a table, the task is to retrieve the top-k most semantically similar cells from a corpus of tables.
The benchmark does not impose restrictions on how embeddings are generated: some models may encode only the cell content, while others may incorporate row, column, or table context.
By measuring retrieval performance, we can directly assess the ability of different embedding approaches to capture fine-grained, entity-level semantics.

Dataset.

We construct a benchmark based on data from the S2abEL dataset
(
32
)
, originally developed for entity linking in scientific tables.
S2abEL contains 732 result tables extracted from 327 machine learning papers, with cells manually labeled with links to the PaperswithCode
3
3

3

https://paperswithcode.com/
taxonomy.
These annotations provide a semantically grounded relevance signal for our cell level semantic retrieval task: cells linked to the same entity are considered equivalent for retrieval purposes, as visualized in Figure
6(a)
.

In the original S2abEL release, the cell contents often contain LaTeX commands and formatting artifacts, for example,
\textbf
{
BERT
}
, reflecting how tables appear in scientific papers.
To support different evaluation scenarios, we construct two versions of the data: a “clean” version, where LaTeX commands and formatting are removed, and a “dirty” version, which retains the original content.
This allows evaluation of models both on preprocessed, uniform text and on realistic, noisy inputs as they appear in the wild.

For evaluation, we generate cell-level retrieval test cases from the S2abEL entity linking annotations.
Each test case consists of a query cell, a set of tables containing the same entity, and the corresponding ground-truth cells, which are all other cells annotated with the same entity in those tables.
The number of ground-truth cells varies per test case depending on the tables included.

To maintain a manageable yet representative set of scenarios, we limit each test case to at most three tables, always including the table containing the query cell.
Entities linked to only a single table are excluded, ensuring that each test case involves at least one relevant cell outside the query table.
From this pool, we sample a total of 1000 test cases to form the benchmark.

Evaluation Methodology

For each test case, embeddings are generated for all cells of the test case tables, including header cells.
Next, we compute cosine similarity between the query cell embedding and all candidate cell embeddings, excluding the query cell itself.
The top-k most similar cells are retrieved, where k corresponds to the number of ground-truth cells associated with the query.
We report mean top-k accuracy across all test cases, where accuracy for each test case is defined as:

accuracy=(\#\text{ of correct cells in top-k retrieved})/k

This metric directly evaluates how well an embedding approach can identify semantically related cells across tables, reflecting the quality of the learned representations for cell-level table understanding.

8.
Discussion

8.1.
Overall Rankings

Other multi-task benchmarks, such as MTEB
(
36
)
or MMTU
(
49
)
report overall model performance by aggregating task scores, as their tasks share comparable evaluation metrics (e.g., accuracy or F1).
In contrast, TEmBed includes a diverse set of tasks with heterogeneous metrics, including ranking-based measures (e.g. MRR, Recall@k), classification accuracy, and regression errors (where lower values indicate better performance).
Directly averaging such scores would require metric normalization and introduce additional assumptions about scale and comparability.
To avoid these issues, we adopt a rank-based aggregation strategy.
For each task, models are ranked according to their primary evaluation metric, and the overall score is computed as the mean rank across tasks, as reported in Table
5
.
Each task contributes equally, regardless of the number of associated datasets, to avoid structural bias in the benchmark.

Not all embedding approaches support every task and every dataset, as some models are restricted to specific embedding levels or to datasets below a certain number of rows.
If a model produces partial results for a task, missing dataset values are imputed with a worst-case metric before aggregation, penalizing incomplete performance while still enabling comparison.
If a model cannot perform a task at all, it is assigned a penalty rank worse than the lowest observed rank, ensuring it is consistently placed below valid approaches.
This treatment favors models with broad task coverage, reflecting our goal of evaluating general-purpose embedding models.
We observe, that no embedding model consistently achieves the best performance on every task.
The universal text embedding models (
GritLM
,
IBM Granite R2
and
MiniLM
) currently achieve the highest aggregate rankings.

8.3.
Variation Studies

The TEmBed framework allows systematic evaluation of how dataset characteristics affect embedding quality.
Table
6
reports triplet-based row embedding accuracy (Section
4.2
) across controlled variations of the two datasets, keeping the test cases exactly the same.
For the
astronomical objects
dataset, removing all numeric columns (text-only variant, 27 of 41 columns were numeric), has minimal impact on performance for most models, suggesting that textual content dominates the embeddings.
For the
books
dataset, we remove column names (replacing them with
col0, col1, …
), simplify them by omitting the wikidata property ID from the column names, exclude the
genre

).
These manipulations reveal that column names and key attributes like genre substantially influence the accuracy of many models.
Interestingly, only
TabuLa-8B
remains robust across the variations, all other models show noticeable changes in performance.
The models react very differently to the variations.
For instance,
IBM Granite R2
and
SAP-RPT-1
perform substantially better on the small five-column books table, while
TabICL v2
performs worse.
By enabling controlled dataset variations, TEmBed facilitates detailed analysis of model sensitivity to table content and schema, guiding users in selecting models best suited to their specific use cases.

8.4.
Discussion

Our experiments highlight clear differences between general-purpose embeddings and table-specialized models.
The main observation is, that across tasks, no single embedding model consistently excels.
Instead, the results indicate that at least two distinct types of embedding models are currently required to cover the range of downstream tasks: (1) semantic similarity-oriented models and (2) prediction oriented models, optimized for classification and regression tasks.
This distinction is somewhat surprising, as it suggests that predictive models encode information fundamentally different from what is required for structural or semantic similarity.
Consequently, specialized models for tabular prediction do not generalize to similarity-based tasks, and vice versa.
We further observe that similarity-based tasks can often be solved effectively by general-purpose text embeddings, outperforming specialized tabular models such as
HyTrel
or
TabuLa-8B
.
Similar findings have been reported by
5
for table union search.
They attribute it to current benchmarks being insufficiently semantically challenging, as they mostly contain vocabulary well-represented in models with strong language understanding.
At the same time, prior work shows that large language models struggle with enterprise data characterized by domain-specific schemas and terminology
(
4
)
, suggesting that general-purpose embeddings may face limitations in these settings.

Overall, these results suggest that achieving a universal table embedding remains an open challenge.
Future work should explore hybrid approaches, combining embeddings optimized for similarity and prediction, as well as light-weight task-adaptive fine-tuning strategies to bridge the gap between general-purpose language understanding and tabular semantics.

9.
Conclusion

We introduce TEmBed, the Tabular Embedding Test Bed, to evaluate tabular embeddings across a diverse set of application oriented tasks on different embedding levels.
Our evaluation of different embedding models shows, that currently no single model consistently performs best across all tasks and levels.
Instead, performance depends strongly on the target application, with a clear distinction between models that excel at semantic similarity tasks and those optimized for predictive settings.
With our work, we guide users in selecting suitable models and we hope to provide the groundwork for the development of more general-purpose tabular representation models.

A.2.
Approaches - Evaluation Details

HyTrel

(
6
)

Hyperparameters.
For HyTrel, we use the model checkpoint trained on contrastive loss, made available with the source code on
Github
, which provides us with a 768 dimensional output embedding for rows, columns, tables and cells. Since HYTREL relies on sentence embedding inputs for the cell content as input to the hypergraph, we keep its default pre-processing pipeline for text serialization and tokenization before the model forward pass. This process cleans up cells which are textual to extract content and converts numerical inputs to scientific notation before text tokenization. Input column hyper-edge embeddings are the column names, and the table hyper-edge embeddings are obtained from tokenzing the table caption/header. Row embeddings need to be randomly initialized and acts as conduits for information filtering during the forward pass. Embedding representations for HYTREL do not require access to labels during inference or in-context learning.

Extracting Embeddings.
HYTREL is based on SetTransformer operations, applied to nodes (table cells) and hyperedges (column, row, and table identities of each cell) obtained from the table grid. HYTREL takes as input the entire table, and outputs filtered node embeddings (for cell content) and hyper-edge embeddings (row, column, table) of the same size as the input sentence transformer embeddings. At inference, the final output embeddings are designed to be context-aware (i.e aware of the underlying grid structure in the table) and are permutation equivariant (agnostic to ordering of information in the rows/columns). During evaluation, row, table, and column embedding based tasks perform a single forward pass through the HYTREL model.

The base HYTREL model was not directly fine-tuned for predictive ML tasks due to which we evaluate the ability of the row embeddings to serve as representations needed for prediction. Therefore, one forward pass through the model is performed during the training to obtain the row-embedding input for the training data-points used to fit XGBoost (and other predictors in the benchmark). A second forward pass is performed on the table where test data points are appended to the training data to obtain test row embeddings for inference. This two-phase procedure ensures consistency in comparison with the in-context learning setting for the transformer based foundation models such as TabICL, TabPFN, SAP-RPT-OSS, and TabuLA.

TabuLa

(
14
)

Hyperparameters.
TabuLA processes inputs with a maximum sequence length of 512 tokens ensure proper context handling. For predictive modeling tasks, we evaluated on 32 (limit specified by compute memory infrastructure) randomly selected training examples as few-shot demonstrations. Text generation uses sampling with a temperature of 0.1 and generates up to 50 new tokens per prediction. The model leverages AutoModelForCausalLM architecture, which provides both embedding extraction capabilities through its base transformer layers and text generation for direct prediction tasks.

Extracting Embeddings.
For row embeddings, each table row is converted to a structured string format where column-value pairs are concatenated with separators (e.g., "col1: val1 | col2: val2"). The model tokenizes these strings and extracts embeddings from the last hidden state of the base transformer using average pooling across sequence positions, producing fixed-dimensional row representations, which can be used for row-based tasks. TabuLA-8b does not provide a mechanism to expose cell, row, or table embeddings, due to which we skipped those tasks

For predictive ML tasks, TabuLA-8B operates in few-shot mode: it constructs prompts containing 32 randomly sampled training examples with their labels, followed by the test instance requiring prediction. The model generates predictions autoregressively, producing class labels for classification tasks or numerical values for regression. This approach leverages the model’s pre-trained knowledge of tabular data patterns without requiring task-specific fine-tuning, enabling zero-shot generalization across diverse tabular datasets while maintaining computational efficiency through batched processing and GPU acceleration. However, we noticed that the output of the model often fails to adhere to the required format needed to parse labels reliably, or produces skewed outputs (always predicts majority class due to sampling bias) leading to poor performance for downstream evaluation. Such issues with instruction following and bias were also noted in other studies
(
15
)
on TabuLA-8b. Therefore, we chose to report predictive performance based on row embeddings and not few-shot prompting, as it was more reliable in experiment.

TabPFN v2.5

(
18
)

Hyperparameters.
TabPFN (Tabular Prior-Fitted Networks) is a transformer model pre-trained on synthetic tabular datasets that performs in-context learning for tabular prediction tasks. Our implementation leverages TabPFN for both row embedding extraction and direct predictive modeling. For both tasks, we keep the default hyperparameters which use multiple ensembles (n estimators = 32) during the forward pass. During pre-processing, categorical columns are converted into numerical codes via label encoding with missing values filled by -1 and NaNs set to 0. TabPFNv2.5 also has a constraint in terms of allowing a maximum of 10000 training samples and 100 columns, due to which some evaluations cannot be completed.

Extracting Embeddings.

For row-embedding tasks such as entity matching and the triplet based evaluation (where no ground truth label exists), row embeddings are extracted through the models get-embeddings() API. Since this requires specifying labels which are not available for this task, we set row labels to 0s. Due to its alternating row-column grid attentional structure, TabPFN does not implement methods for obtaining column, table or cell embeddings in its implementation, due to which these tasks were skipped.

Predictive modeling with the TabPFNv2.5 code is straightforward, with a call to model.fit() on the training data, followed by model.predict() on the test samples. For row embedding extraction, TabPFN’s API requires that labels be specified for both train and test data. We also experiment using row-embeddings from TabPFN chained with predictors such as XGBoost for predictive ML. In this experiment, to prevent data-leakage from test labels, we tried two settings. In the first, real labels are given for the training data and zeros are provided for the testing examples. In the second setting, both training and testing data are given dummy zero labels (constant zero embedding bias during encoding). We observed that using row embeddings from the latter results is better performance-wise, likely due to the posterior predictive distribution being less distorted by the differential label encoding for training and test. We report only these results in the main manuscript.

TabICL

(
37
)

Hyperparameters.
TabICL also uses an ensemble of 32 estimators (default) with the tabicl-classifier-v2-20260212.ckpt checkpoint for classification tasks and tabicl-regressor-v2-20260212.ckpt for regression tasks. Our benchmark also allows for configuring the v1 checkpoint (which supports all tasks available with v2 except regression) with a single change to the model yaml file. TabICLv2 processes tabular data after converting categorical and string columns to numerical codes via label encoding after applying outlier removal and standard scaling. All missing values are filled with zeros. The model architecture includes a column embedder that generates contextualized representations for each cell and a row interactor that aggregates column embeddings into row-level representations. All tasks except regression use the classifier checkpoint for embedding extraction For memory efficiency, the implementation supports batched processing with configurable batch sizes (default: 8)

Extracting Embeddings.
TabICL requires a call to model.fit() with provided labels (or dummy 0 labels similar to tabpfn). It then extracts embeddings through a two-stage process: the column embedder generates cell-level representations by processing the input table as tensors. This produces embeddings of shape (batch, rows, columns, embedding dim) using its column embedder. Next, TabICL’s row interactor aggregates these column embeddings across the feature dimension to produce final row embeddings. Thus, cell and column representations from the column embedder before and after mean pooling are used for cell and column level tasks respectively, while row-embedding based tasks can use the outputs of the row extractor. As with other transformer based architectures, labels need to be provided to the model to extract embeddings due to which we provide 0 as the dummy label for non-predictive ML tasks. Table-level embeddings are not supported by TabICL as its in-context learning is table specific.

For predictive ML tasks, TabICL operates in direct prediction mode where the model as fitted against the training labels generates class probabilities for classification (returning logits) or continuous values for regression using its predictproba() and predict() methods respectively. The v2 checkpoints support both classification and regression, while v1 checkpoints only support classification. For the experiments evaluating row-embeddings for prediction, during inference, a train size parameter needs to be provided before embedding extraction. The model then fits on the first train size rows (masking attentions between test-points and labels) and extracts embeddings for the remaining test rows, enabling proper train-test separation during in-context learning. As with TabPFN, we experimented by providing real and dummy 0 labels for the row-embedding extraction for prediction and observed the same representational collapse with the mismatched setting for train and test. The results we report on row-embedding based prediction supply 0 as the label for both test and train data.

SAP-RPT-1

(
41
)

Hyperparameters.
The SAP-RPT-1-OSS (formerly ConTextTab) implementation uses a semantics-aware in-context learning approach with configurable bagging and context size parameters. The model operates bagging=8 (ensemble of 8 models) and supports context sizes of 8192 tokens (for optimal performance on high-memory GPUs). All input data is preprocessed by converting all columns to string format to preserve semantic information, as SAP-RPT-1-OSS is designed to work with textual representations of tabular data. The model maintains separate classifier and regressor instances, each initialized with the specified bagging and max-context-size parameters. For all embedding extraction cases, labels (real or dummy) need to be provided to the model API.

Extracting Embeddings.
For row embeddings, SAP-RPT-1-OSS employs an in-context learning paradigm where the model tokenizes the input table into context (training rows with labels) and query (test rows) portions. The tokenizer processes both portions through the model’s embedding layer, followed by a multi-layer in-context encoder with attention mechanisms that allow query rows to attend to context rows. Cell embeddings are extracted from the encoder’s output by taking the query portion’s representations (excluding the target column token), averaging across feature column tokens produces fixed-dimensional row embedding vectors for row embedding tasks. Due to the symmetric nature of the architecture, an analogous procedure can be used to extract query column embeddings. Dummy 0 labels are provided to the API for each of these tasks. Table embeddings are not supported by SAP-RPT-1-OSS.

For predictive ML tasks, the model operates in direct prediction mode: after fitting on training data with provided labels, it generates class probabilities for classification via predictproba() or continuous predictions for regression via predict(). At train time, all rows serve as both context and query with real labels, while during inference, the training rows provide labeled context for embedding the remaining test rows. For the row-embedding based evaluation for predictive ml tasks, we followed the same experimental protocol as TabICL and TabPFN and observed better performance when dummy labels were provided consistently to train and test.

Extracting Embeddings.

Textual inputs for each embedding level are constructed as follows:

Row Embeddings:

Each row is embedded individually by concatenating column headers and cell values into a single string
:

’<header_text_0>: <column_value_0>; ...;

<header_text_n>: <column_value_n>’
.

Column Embeddings:

For each table, we embed every column individually by concatenating the column header with all distinct column values in the following way:

’<header_text>: <column_value_0> | ... | <column_value_n>’

Table Embeddings:

To create table embeddings, we linearize each table into a markdown string, similar to
(
22

.
For the variants that include example table rows, we include the first 100 rows from the table.

Cell Embeddings:

For each table, we embed every cell individually by converting the cell value to a string and combining it with the column header in the following way:

’<header_text>: <cell_value>’
.

A.4.
Wikidata Hierarchies - Details on Dataset Construction

In this section, we explain in detail how we construct the hierarchies and associated tables for the dataset proposed for the triplet-based row embedding evaluation in Section
4.1
.

For the dataset, we leverage hierarchical relationships between classes in Wikidata
(
46
)
, as visualized in Figure
3(a)
.
We first build each hierarchy, one for literary genre data and one about astronomical object classes, and then the associated tables.

Collecting classes for the hierarchies

Each hierarchy consists of
class items
, that are structured into a tree-structure to define parent-child relationships between the classes, as visualized in Figure
3(a)
.
To prepare the construction of a hierarchy from Wikidata, a list of classes is needed, as well as the relationships between these classes.
For the genre hierarchy, therefore first all possible literary genres are retrieved from Wikidata.
Unfortunately, it’s not straightforward to identify literary genres, as e.g. subclasses of
genre (Q483394)
,
fiction (Q8253)
or
non-fiction (Q213051)
not only include literary genres but also genres used in other art forms.
We therefore go a different route and collect books first and extract genres from concrete book items:
To identify all literary genres, all items that have the property
instance of (P31)

literary work (Q7725634)
are retrieved using the Wikidata SPARQL endpoint.
From each of the retrieved items, we extract the value for the property
genre (P136)
to get a list of all literary genres.
Wikidata is stored in a document-oriented database, its triplets do not form one connected graph.
Therefore we experienced, that not all of the genre classes we retrieved in the previous step actually are connected to the the
genre (Q483394)
class, which we will handle in the next section.
We filter the list to keep only genre items that have an English label, and for genres that are connected to at least three books in Wikidata.
Next, we recursively retrieve the superclasses of each genre class by querying for its
subclass of (P279)
values.
We end up with 608 possible genres that could be included in the hierarchy.
For astronomical objects the process is easier, as we can directly perform a breath-first-search over all subclasses of the
astronomical object (Q6999)
item in Wikidata, resulting in 143 possible astronomical object classes for the hierarchy.

Building the hierarchies

From the previous step, we obtain a set of candidate classes for the hierarchy together with their associated superclass relations, which form the basis for constructing the hierarchy.
For the genre hierarchy, we explicitly enforce a predefined root structure where the root node
genre (Q483394)
has two direct children,
fiction (Q8253)
and
non-fiction (Q213051)
, to ensure a clear and consistent top-level split that facilitates the creation of reliable test cases.

To construct the hierarchy, we first identify all classes that appear as superclasses of at least one other class.
These classes are treated as internal nodes, whereas classes that never occur as superclasses are considered leaf nodes.

The hierarchy is then constructed incrementally. Starting from the predefined root structure, classes are inserted one by one based on their superclass information.
For each class, we determine the deepest valid insertion path in the current hierarchy by matching its superclasses, preferring the longest compatible path when multiple options exist.
Classes that cannot yet be placed are revisited in subsequent iterations until no further insertions are possible.

Because insertion decisions are made greedily, some classes may initially be placed higher in the hierarchy than appropriate. To address this, we perform a reordering step in which nodes are iteratively relocated to deeper positions whenever a more specific valid superclass path becomes available.
This process continues until no further improvements can be made.

As final outputs, we obtain a genre hierarchy with 111 genre classes and an astronomical object classes hierarchy with 113 included classes.

Building the associated tables

We leverage Wikidata to build a table with real-world data associated to each of the two hierarchies.
Corresponding to the literary genre hierarchy, we construct a table with information about books.
Analogous, we also build a table containing concrete astronomical objects.
We follow the process to create tables outlined in
(
45
)
.
The first step of the dataset creation already gave us a list of books from Wikidata, we discard books that are annotated with multiple genres.
For the astronomical objects data, we retrieve all items from Wikidata where the
instance of (P31)
property is the respective astronomical object, again keeping only items with an English label.
These items are the rows for our tables.
For each of the items, we collect all properties and values, which we use to fill the columns of the tables.
As the approach results in very broad and sparse tables, we prune columns where more than 95% of the column values are missing.

As final outputs, we obtain a table containing books with 1203 rows and 281 columns, and a table with astronomical objects, with 8034 rows and 41 columns.

Constructing Test cases

Based on the constructed hierarchies and tables, we generate evaluation test cases for the two domains.
Each test case follows a triplet format, as described in Section
4.2
.

For the books domain, we explicitly split the hierarchy during construction into
fiction
and
non-fiction
.
Each book is assigned to one of these high-level categories based on its genre annotation and the hierarchy structure.

To ensure consistency, we remove ambiguous cases where an author has written both fiction and non-fiction works.
In such cases, only the majority category per author is retained and the other books are discarded from the table.
This step avoids conflicting signals within the dataset.

After cleaning, the dataset is shuffled deterministically, and test cases are generated using the hierarchy. Specifically, pairs of books are considered similar if they share closely related genres within the hierarchy, while dissimilar pairs are sampled from different branches (e.g., fiction vs. non-fiction or distant subgenres). The hierarchy thus directly defines the notion of semantic similarity.

For the astronomy domain, we construct test cases based on high-level semantic branches derived from object types (e.g., galaxies, nebulae, star clusters, and variable stars).

Test cases are then generated by pairing objects within the same branch as similar examples, while dissimilar examples are drawn from different branches. To ensure diversity and reproducibility, pairs are generated deterministically and distributed across branches in a balanced manner.

In total, we create 903 test cases for the books table and 2000 for the astronomical objects table.
