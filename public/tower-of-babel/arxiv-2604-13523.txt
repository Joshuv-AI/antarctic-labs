ATLAAS: Automatic Tensor-Level Abstraction of Accelerator Semantics
Ruijie Gao, Haoran Jin, Jirong Yang, Nathaniel Bleier

Abstract
. Numerous tensor accelerator designs have been proposed in academia and industry, yet most lack well-documented ISAs and compiler backends. As a consequence, the majority of new designs are only evaluated on a handful of operators or synthetic kernels. Recent work (e.g., TAIDL and the ACT ecosystem) has shown that given a tensor-level ISA specification, complete software stacks including test oracles and compiler backends can be automatically generated. However, writing such specifications remains a manual, expert-driven process. We present ATLAAS, the first end-to-end MLIR-based pipeline that lifts RTL-extracted accelerator semantics to TAIDL-like tensor ISA specifications. Building on prior architecture-level model extraction that produces bit-level LLVM IR, ATLAAS introduces an 8-pass MLIR semantic lifting pipeline that progressively recovers high-level tensor structure, including MAC idioms, saturation semantics, multi-dimensional buffer organizations, and data layout transformations. The pipeline emits specifications in the TAIDL formalism, immediately enabling automatic software stack generation through the ACT ecosystem. We evaluate ATLAAS on Gemmini, a systolic-array accelerator, extracting all hardware instructions semantics across 127 MLIR files. The lifting pipeline collapses the extracted bit-level MLIR by up to 92.9% on processing elements (686 → \to 49 lines, of which only 17 encode the tensor computation core) and by 24–34% on controller modules, with the residue being irreducible control logic (FSMs, address computation, and instruction muxing). ATLAAS discovers hardware features omitted from the hand-written reference, including multi-bank DMA configuration, pooling engine semantics, and im2col hardware support. Correctness is validated through Z3 SMT equivalence proofs. We further confirm generality on TVM’s VTA tensor processor, where the same pipeline lifts all four datapath modules without accelerator-specific changes, with extracted semantics formally verified against the underlying RTL. By feeding the extracted specification into the ACT compiler framework, ATLAAS enables an automated path from RTL to a performance-competitive compiler backend, eliminating the need to manually write tensor-level ISA semantics.

2.
Background

2.1.
Hardware-Software Interfaces in Tensor Accelerators

Tensor accelerators occupy a fundamentally different point in the design space than scalar or vector processors.
Rather than executing fine-grained instruction streams over flat register files and cache-coherent memory, they expose
coarse-grained
operations that consume and produce multi-dimensional tensors and replace implicit caches with
explicitly managed
on-chip memories (scratchpads, accumulator banks).
Gemmini
(
13
)
, Berkeley’s open-source systolic-array generator, is representative: it attaches to a Rocket core
(
3
)
via the Rocket Custom Coprocessor (RoCC) interface
(
2
)
with non-standard RISC-V custom instructions, and its programmer-visible state consists of a row-addressed scratchpad and an accumulator.
Its ISA exposes only configuration, DMA data-movement, and matrix-multiply execution instructions—every operation simultaneously specifies
what
to compute,
where
operands live in a private memory hierarchy, and
how
data should be staged.

This distinctiveness places heavy demands on compiler infrastructure.
ML frameworks feed tensor IR (StableHLO, Linalg, TOSA) into backends such as XLA
(
39
)
, TVM
(
5
)
, or IREE
(
42
)
, which must lower high-level operations to the accelerator’s native instructions.
Doing so correctly requires tiling and fusing loop nests to fit scratchpad capacity, scheduling explicit DMA transfers, allocating scratchpad regions, and orchestrating double-buffering—all of which presuppose a precise model of what each instruction does to which piece of tensor state.

Consider lowering a single XLA
dot

C{=}A{\cdot}B
for matrices exceeding Gemmini’s
16{\times}16
tile.
The backend must emit a tiled sequence:
config_ex
/
config_ld
/
config_st
to set dataflow and stride parameters;
mvin
/
mvin2
to stage tiles of
A
and
B
into the scratchpad;
preload
followed by
compute_preloaded
(or
compute_accumulated
) to fire the systolic array for each output tile; and
mvout
to drain results.
Generating this sequence requires the backend to know, for every instruction, which tensor tile it touches, which scratchpad region it occupies, and how its output composes with subsequent operations.

This is precisely where most accelerators fall short.
Mapping tensor IR to an instruction sequence presupposes a
machine-readable
ISA that specifies both the binary encoding and the
tensor-level semantics
of each instruction.
For Gemmini, semantics live informally in prose documentation, the Chisel RTL, and a hand-written Spike functional model; most open-source accelerators offer only RTL and perhaps a driver.
Building a backend today therefore remains largely an exercise in
manual reverse-engineering of the RTL
.

2.2.
Automated Compiler Generation and the Specification Bottleneck

Recent work has shown that the main barrier to end-to-end software support for tensor accelerators is not only backend engineering effort, but the lack of a precise, machine-readable Instruction Set Architecture (ISA) specification. TAIDL
(
21
)
(Tensor Accelerator ISA Definition Language) addresses this problem by providing a domain-specific language for describing accelerator data models and instruction semantics at the tensor level. A key design choice in TAIDL is that instruction behavior is expressed using tensor operators close to XLA High Level Optimizer (XLA-HLO)
(
39
)
, such as
reshape
,
transpose
,
convert
,
dot
, and
add
. This abstraction level is high enough to capture programmer-visible tensor semantics compactly, while remaining close enough to tensor compiler intermediate representations to support downstream automation.

This example illustrates the semantic granularity expected by TAIDL: the author must specify the tensor buffers exposed by the accelerator, the instruction operands, and the exact tensor-level effect of the instruction, but not the underlying Register-Transfer Level (RTL) control or datapath implementation. In published TAIDL examples
(

)
, even more complex instructions such as Intel Advanced Matrix Extensions (Intel AMX)
(
19
)

are modeled by composing layout transformations (
reshape
,
transpose
), type conversion, tensor contraction, accumulation, and write-back in the same style.

Built on top of such specifications, ACT
(
22
)
(Accelerator Compiler Toolkit) automates what comes after the ISA description. Given a TAIDL specification, ACT automatically generates compiler backends by combining equality saturation for instruction selection with constraint-programming-based memory allocation. The result is an ISA-driven compilation flow in which much of the backend logic is synthesized rather than handwritten. This is particularly attractive for tensor accelerators, whose instructions often operate on parameterized tensor tiles and explicitly managed on-chip memories that are difficult to support using conventional backend-generation techniques.

However, the automation boundary is also the key limitation: TAIDL and ACT automate everything downstream of the ISA specification, but they do not automate the creation of that specification itself—someone must still write the TAIDL model by hand, a task that requires deep knowledge of the hardware/software interface. This front-end specification burden is the gap that ATLAAS addresses.

2.3.
RTL Extraction and MLIR-Based Semantic Lifting

A natural baseline for recovering ISA semantics from hardware is architecture-level model extraction from RTL.
The relevant starting point is the autoGenILA line of work
(
50
;
49
)
, which first identifies the architectural state variables (ASVs) that persist across instructions and then derives the corresponding state update functions for each instruction directly from RTL.
This removes the need to manually write an Instruction-Level Abstraction (ILA)
(
17
)
model and yields an architecture-level interface that is consistent with the hardware implementation by construction.
In ATLAAS’s workflow, autoGenILA serves exactly this role: it is the extraction backend that converts accelerator RTL into per-instruction semantic functions, providing the raw material for later lifting.

The problem is that these extracted models are still too low-level for tensor compiler generation.
autoGenILA captures hardware behavior faithfully, but the output remains a flattened, bit-level scalar model in which high-level tensor intent is obscured by the structure of the datapath
(
50
;
49
)
.
As illustrated in Figure
2
, a single Gemmini processing element may initially appear as hundreds of primitive operations—dominated by sign-extension chains, truncations, bitwise composition, and scalar arithmetic—before later passes recover the underlying
dot + add + clamp
semantics.
Such an output is appropriate for bit-accurate reasoning, but it is not yet suitable for TAIDL
(
21
)
, which requires tensor-visible semantics: buffer reads and writes, structured layout transformations, multiply-accumulate patterns, reductions, and saturation behavior.
In other words, autoGenILA solves the
extraction
problem, but not the
semantic abstraction
problem.

This is where MLIR (Multi-Level Intermediate Representation) becomes the key enabling substrate.
The advantage of MLIR is not any hardware-specific frontend, but its support for multi-level, progressive abstraction within one compiler framework
(
26
)
.
In ATLAAS’s implementation, the extracted semantics are materialized as low-level MLIR in the
arith
and
memref
dialects, and are progressively raised through structured passes that leverage MLIR’s dialect-aware rewriting infrastructure
(
26
;
30
)
.

More importantly, MLIR provides the right semantic stepping stones between bit-level arithmetic and tensor-level intent:
arith
for scalar operations,
memref
for explicit memory accesses,
scf
for structured control flow, and
linalg
for tensor computations
(
30
;
28
;
29
)
.
Because MLIR supports rewrite-driven and partially legalized transformations, ATLAAS can progressively raise the representation rather than jumping from RTL-level behavior to tensor semantics in one step (Section
3
).

3.
ATLAAS Pipeline

Figure 3.

ATLAAS transforms an unannotated RTL design into a TAIDL specification through three stages (Figures
1
and
3
):

Stage 1 (§
3.1
)
symbolically extracts per-instruction behavior from the RTL into bit-level MLIR;

Stage 2 (§
3.2
)
progressively lifts that bit-level representation to tensor-level semantics via an eight-pass rewrite pipeline;

Stage 3 (§
3.3
)
assembles the lifted MLIR into a TAIDL specification with XLA-HLO-style semantics.
The entire pipeline takes a directory of SystemVerilog files and a top-module name as input, and produces a complete TAIDL specification consumable by the ACT ecosystem.

3.1.
Stage 1: RTL-to-MLIR Extraction

Stage 1 builds on autoGenILA
(
50
;
49
)
, which symbolically unrolls a Verilog design for each (instruction, architectural state variable) pair, producing a function that maps current state and inputs to next state—provably bit-equivalent to the RTL by construction.
However, autoGenILA’s LLVM IR backend destroys two structural properties that tensor-level reasoning requires.
First, conditional updates are lowered into branches and
phi
nodes, erasing the if/else structure that encodes hardware mode selection.
Second, RTL signal names—which identify whether an input carries activations, weights, or an accumulator—are discarded during lowering.

ATLAAS replaces the LLVM IR backend with an MLIR code generator that preserves both.
Conditional updates become
scf.if
regions; memory accesses remain as indexed
memref
loads; and original RTL signal names are attached as structured metadata that downstream passes consult to classify arguments semantically.
A second design choice packs the time series of each input signal across unroll cycles into a single
memref
argument rather than flattening them into hundreds of independent scalars—this grouping is what later enables loop reconstruction (§
3.2
) to recover MAC chains as indexable reductions.
An automation layer generates flattening scripts, enumerates architectural state variables, and discovers instruction encodings from the RTL decoder, reducing the per-design manual input to two items.
The original LLVM IR backend is retained unchanged as a verification oracle (§
4
).

The output is a corpus of MLIR files, one per (instruction, ASV) pair, provably bit-equivalent to the RTL.
As Figure
2
illustrates, even a single Gemmini PE produces 686 lines at this stage, with the core multiply–accumulate buried under hundreds of sign-extension and bit-packing operations.

3.2.
Stage 2: Semantic Lifting

Stage 2 is the analytical core of ATLAAS: an eight-pass MLIR pipeline that progressively recovers tensor-level semantics from the bit-level Stage 1 output.
The passes fall into four phases (Table
2
).

Phase A (canonicalization)
collapses the bit-by-bit sign-extension chains that arise from Verilog
$signed
contexts into single cast operations, and folds redundant width round-trips—the dominant source of code reduction.

Phase B (idiom detection)
identifies three patterns: multiply–accumulate, by tracing each addition back through width casts to a multiplier; dead hardware modes, by constant-folding the fixed control inputs of the instruction under analysis; and fixed-point saturation, by recognizing the
ext(trunci(x))
idiom.

Phase C (loop reconstruction)
chains MAC-annotated operations whose accumulator output feeds the next MAC’s input into
scf.for
reductions, then verifies that each loop matches the canonical dot-product shape (single iterator, two memref loads at the induction variable, multiply–add–yield) and tags it accordingly.

Phase D (metadata emission)
classifies each
memref
argument by its access pattern, labels scalar arguments as control attributes, and emits structured
taidl.*
attributes consumed by Stage 3.

Two properties make the pipeline robust.
First, with the exception of loop reconstruction, passes

Second, the pipeline is accelerator-agnostic: the structural cues it relies on—sign-extension chains, MAC fan-in, fixed-point clamp idioms, accumulator def–use chains—are properties of common RTL synthesis patterns, not of any particular ISA.
The same binary lifts Gemmini’s PE and DMA controllers, and VTA’s TensorGemm and TensorAlu without modification.

On the running Gemmini PE example, the eight passes reduce 686 lines of bit-level MLIR to 49, of which only 17 encode the computation core
clamp(dot(%A,%B)+%C)
.

3.3.
Stage 3: TAIDL Assembly

Stage 3 assembles the annotated MLIR from Stage 2 into a complete TAIDL specification (Listing
1
).
It first merges the per-(instruction, ASV) functions back into per-instruction groups, then dispatches on the recognized tensor operation through two paths.
The
compute path
maps each tensor op to an XLA-HLO template:
dot_product
expands to
convert + dot + add
(with optional
clamp
),
pool
to
reduce(max)
, and
im2col_matmul
to
reshape + dot + add
; when the RTL encodes an activation function, the corresponding HLO operation is inserted (e.g.,
maximum(result, 0)
for ReLU).
The
DMA path
classifies memory-port roles (DRAM address vs. scratchpad address) from the annotated metadata and emits a
load
or
store
body accordingly.

For CISC-style loop macros that orchestrate sequences of primitive instructions behind a single invocation (e.g., Gemmini’s
loop_ws
), ATLAAS recovers the primitive instruction vocabulary and loop-bound configuration registers from the controller’s RTL, then composes the primitive tensor operation over the extracted bounds into a whole-program HLO body.
Instruction ordering constraints—e.g., that
compute_preloaded
may only fire after
preload
—are recovered by analyzing FSM register updates across instruction groups and folded into the specification as structured metadata.

(§

4.4.
Specification Completeness

ATLAAS extracts TAIDL specifications for all hardware instructions decoded and executed by Gemmini’s three controllers (ExecuteController, LoadController, StoreController).

Comparison with hand-written reference.

We compare ATLAAS’s extracted specification against the TAIDL MICRO 2025 artifact
(
20
)
, which provides a hand-written Gemmini specification.
ATLAAS captures strictly richer semantics in three areas:

•

Multi-bank DMA configuration.

The hand-written reference models each DMA load variant (
mvin_spad
,
mvin_acc
, etc.) with a single
@a.stride
parameter, implicitly assuming all three load engines share one configuration.
In practice, Gemmini’s LoadController maintains
three independent banks
, each with its own
stride
,
scale
,
shrink
,
block_stride
, and
pixel_repeat
registers (5 parameters
\times
3 banks = 15 registers total), with the active bank selected by the
state_id
field (
rs1[4:3]
) of the instruction encoding.
This means the hand-written TAIDL cannot correctly simulate programs that use
mvin
and
mvin2
with different strides simultaneously—a real use case in tiled matrix multiplication where the A-tile and B-tile load from DRAM with different access patterns.
ATLAAS’s per-ASV extraction sees all three banks automatically because autoGenILA traces every register independently, and the assembler groups them by their indexed base name (e.g.,
strides_0
,
strides_1
,
strides_2
).

•

Pooling engine semantics.

ATLAAS extracts 12 pooling configuration registers from the StoreController (
pool_size
,
pool_stride
,
pool_upad
,
pool_lpad
,
pool_orows
,
pool_ocols
, etc.) and generates
reduce(max) + clamp
semantics.
The hand-written reference does not model the pooling engine.

•

Im2col hardware support.

ATLAAS extracts 9 im2col output ports from the ExecuteController and generates
reshape + dot
semantics, capturing the hardware’s ability to perform im2col transformation on-the-fly during convolution execution.

We note that the hand-written reference also includes four entries—
softmax
,
GELU
,
layernorm
, and fused add-with-transpose—that are
not
hardware ISA primitives.
These are software-composed multi-instruction sequences that use the host CPU’s FPU for operations such as
exp()
and
divide()
.
No Gemmini RTL modules implement these operations.
ATLAAS correctly identifies this hardware/software boundary by extracting only instructions that correspond to actual RTL decoder entries.

A natural question is why we do not directly compare compiler backends generated from the two specifications.
The reason is that the TAIDL MICRO 2025 artifact targets a
functional simulator
, not a compiler backend.
Its specification describes how individual hardware instructions move data between scratchpad and accumulator at per-tile (16
\times
16) granularity—exactly the level of detail a cycle-accurate or functional simulator needs to replay an instruction trace.
However, a compiler backend requires a different abstraction: per-
kernel
granularity that maps an entire HLO
dot
or convolution onto the hardware.
The MICRO 2025 artifact’s per-instruction patterns are too granular for ACT’s instruction selection, which expects CISC-level macro-instructions (e.g.,
loop_ws
matching a whole matrix multiply,
loop_conv_ws
matching a whole convolution).
ATLAAS’s specification provides this macro-level abstraction (Stage 3, §
3.3
), enabling ACT to generate a functional compiler backend as evaluated in the next section.

Methodology.

We take ATLAAS’s extracted TAIDL specification and pass it to ACT, which generates an XLA-compatible compiler backend using equality saturation for instruction selection and constraint programming for scratchpad memory allocation.
Completing the path from specification to executable binary required engineering contributions to ACT: HLO frontend support for JAX-produced operations (e.g.,

(

For each benchmark, we compare the Spike cycle count of the ACT-compiled binary against the hand-written C kernel from gemmini-rocc-tests, ensuring identical workload parameters: layer shapes, weight-stationary dataflow, activation functions, scaling, and batch sizes.
The benchmark suite spans MLP, convolutional, and transformer workloads ranging from 2-layer networks (1,501 cycles) to full ResNet-50 (5,544,077 cycles) and MobileNet (3,408,414 cycles).

5.
Related Work

Formal accelerator interfaces and model extraction.

Instruction-Level Abstraction (ILA)
(
17
)
established a software-visible specification framework for accelerators and processors, while the subsequent autoGenILA work
(
50
;
49
)
showed how architecture-level models can be derived automatically from RTL designs.
3LA
(
16
)
further demonstrated how such formal interfaces can support application-level validation of accelerators.
ATLAAS builds directly on this line of work but differs in its target abstraction: rather than stopping at scalar architectural state updates or validation-oriented interfaces, it lifts extracted semantics to tensor-visible instruction behavior suitable for software-stack generation.

Tensor-accelerator specification and backend automation.

TAIDL
(
21
)
introduced a domain-specific language for expressing tensor-accelerator ISA semantics, and ACT
(
22
)
showed that compiler backends can be generated automatically from such specifications.
These efforts automate the downstream path from ISA description to tooling but assume that a tensor-level specification already exists.
ATLAAS addresses this missing front-end step by recovering TAIDL-like semantics from RTL-derived low-level models.

MLIR and hardware IR semantics.

At the compiler-infrastructure level, our work is enabled by MLIR
(
26
)
as a progressive abstraction framework, and is adjacent to hardware-oriented MLIR efforts such as CIRCT
(
11
)
.
Recent work on K-CIRCT
(
52
)
and first-class verification dialects for MLIR
(
12
)
further highlights the value of giving hardware and compiler IR dialects explicit semantics.
ATLAAS differs from these efforts in emphasis: rather than defining semantics for an existing IR or hardware dialect, it uses MLIR as the staging ground for semantic lifting from extracted hardware behavior to tensor-level ISA descriptions.

Top-down accelerator programming and generation.

ATLAAS should be distinguished from top-down frameworks such as HeteroCL
(
25
)
, Calyx
(
34
)
, and Exo
(
18
)
.
Those systems help users design, program, or compile for accelerators from higher-level descriptions, whereas ATLAAS is a bottom-up approach that starts from an existing RTL implementation and reconstructs the software-visible tensor interface.
In that sense, ATLAAS also has some affinity with semantic lifting and raising work in binary analysis
(
10
)
, but its end goal is not generic decompilation to compiler IR; it is recovery of structured tensor semantics that can be consumed by accelerator-specific tooling.

6.
Conclusion

We presented ATLAAS, the first end-to-end pipeline that automatically lifts RTL-extracted accelerator semantics to tensor-level ISA specifications, addressing the manual specification bottleneck that has prevented automated compiler generation tools from reaching the vast majority of tensor accelerator designs.
By introducing an 8-pass MLIR semantic lifting pipeline—spanning bit-manipulation canonicalization, MAC pattern detection, control-flow specialization, saturation recovery, loop reconstruction, linalg lifting, and structured metadata emission—ATLAAS bridges the abstraction gap between gate-level hardware behavior and the tensor-level semantics required by specification languages like TAIDL.

Evaluated on Gemmini and VTA, ATLAAS processes 156 MLIR files totaling over 1.2 million lines of bit-level IR, achieving up to 92.9% reduction on compute-dominated modules and recovering hardware features—multi-bank DMA configuration, pooling engine semantics, and im2col support—that were absent from hand-written references.
All lifted semantics are formally verified equivalent to the underlying RTL via Z3 SMT proofs, and the same pipeline generalizes across accelerator architectures without modification.
By feeding the extracted specification into ACT, ATLAAS enables a fully automated path from RTL to a performance-competitive compiler backend, achieving a geometric mean speedup of
1.014\times
over hand-written kernels on workloads up to ResNet-50 and MobileNet.

More broadly, ATLAAS closes the frontmost gap in the RTL-to-framework pipeline: the step from hardware design to machine-readable ISA semantics that has historically required deep architectural expertise and manual effort.
With this gap filled, the complete automated path—RTL through ATLAAS to TAIDL specification, then through ACT to an XLA-compatible compiler backend—is now possible, lowering the barrier for new accelerator designs to achieve full software-stack integration.
