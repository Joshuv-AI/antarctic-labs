An Agentic Evaluation Framework for AI-Generated Scientific Code in PETSc
Hong Zhang, Barry Smith, Satish Balay, Le Chen, Murat Keceli, Lois Curfman McInnes, Junchao Zhang

Abstract
While large language models have significantly accelerated scientific code generation, comprehensively evaluating the generated code remains a major challenge. Traditional benchmarks reduce evaluation to test-case matching, an approach insufficient for library code in HPC where solver selection, API conventions, memory management, and performance are just as critical as functional correctness. To address this gap, we introduce petscagent-bench , an agentic framework built on an agents-evaluating-agents paradigm. Instead of relying on static scripts, petscagent-bench deploys a tool-augmented evaluator agent that compiles, executes, and measures code produced by a separate model-under-test agent, orchestrating a 14-evaluator pipeline across five scoring categories: correctness, performance, code quality, algorithmic appropriateness, and library-specific conventions. Because the agents communicate through standardized protocols (A2A and MCP), the framework enables black-box evaluation of any coding agent without requiring access to its source code. We demonstrate the framework on a benchmark suite of realistic problems using the PETSc library for HPC. Our empirical analysis of frontier models reveals that while current models generate readable, well-structured code, they consistently struggle with library-specific conventions that traditional pass/fail metrics completely miss.

Evaluating these dimensions requires more than static test scripts.

3
An agentic evaluation framework for HPC libraries

3.1
Design Principles

Traditional code-generation benchmarks follow a simple pipeline: present a prompt, collect the generated code, and run it against test cases.
This approach works well for self-contained Python functions but breaks down for scientific HPC code that must be compiled against external libraries,
linked with MPI, executed in a parallel environment, and assessed along dimensions beyond functional correctness.
A significant engineering challenge is that the evaluation infrastructure itself must manage library installations, handle compilation failures gracefully, and orchestrate multiple evaluation steps.

An agentified architecture addresses this challenge by decoupling the model
under test and the evaluator into independent agents and making the evaluator an autonomous agent rather than a static test harness.
In particular, our
agents-evaluating-agents
architecture stands on three principles:
(1) role-based separation, where the evaluator and the model under
test are independent agents that interact solely through A2A, and any agent
speaking this protocol can be easily plugged into the evaluation
infrastructure;
(2) sandboxed execution, where generated code is compiled and run in a
sandboxed PETSc/MPI environment through MCP tools; and
(3) modular extensibility, where adding a benchmark problem requires
only a JSON specification and adding an evaluator requires implementing a single Python class.

3.2
Component Overview

The system consists of three major components as shown in Fig.
1
:

•

Green agent (evaluator).

The Green agent is an assessment manager that orchestrates the benchmark. It loads problem specifications from JSON files, dispatches each problem to a Purple Agent through A2A messages, receives generated code and auxiliary information, invokes MCP tools for compilation and execution, runs the 14-evaluator pipeline
(see Sec.
4
), and prepares structured reports for a web-based leaderboard.

•

Purple agent (model under test).

The Purple agent is an LLM-based code-generation agent that receives a natural-language problem description through A2A and returns one or more C source files together with metadata including the entry-point file, dependencies, and command-line arguments.

•

MCP server (tool provider).

The server provides a sandboxed execution environment exposing compilation and execution tools to the Green agent through MCP.
It manages a custom PETSc installation, updates build
recipes, compiles uploaded source files, runs the
resulting binaries with MPI, and returns outputs (including errors and exit codes).

3.3
Protocol Usage

The interaction between the Green agent and Purple agent is governed by the
A2A protocol
[
15
]
.
The Green agent creates a
task
containing the problem
description and the Purple Agent responds with
artifacts
, such as source files and metadata.
This decoupled setup allows the two agents to run on different machines, to sit behind firewalls, or be hosted as cloud services.

The MCP
[
1
]
protocol governs the Green agent’s
access to the compilation and execution environment.
The MCP Server exposes two primary tools: (1)
compile
, which builds the uploaded code against PETSc,
and (2)
run
, which executes the binary with specified MPI ranks and
command-line arguments.
It is deployed for free public access. See
https://mcp.petsc-ai.org
for details.

4
Evaluation Pipeline

The evaluation pipeline contains three sequential stages:
gates
,

metrics
, and
quality assessments
.
If any gate fails, evaluation terminates immediately with a zero score, so only compilable and executable code proceeds to the later stages, which involve more expensive analysis.
Independent of the stages, each evaluator is attributed to one of
five
scoring categories
that group similar dimensions for
aggregation:
correctness
(syntactic, functional, semantic, and numerical),

performance
(execution time),

code
(readability, style, documentation),

appropriateness
(algorithm and solver selection), and

library-specific
(API conventions, error handling, parallel awareness).

summarizes all evaluators.

4.1
Stage 1: Gates

Gates act as hard filters: evaluation continues only if the generated code passes all the following gates:

•

Compilation
. The C/CUDA/Kokkos source files compile against PETSc using PETSc’s Makefile system.

•

Execution
. The compiled binary runs to completion without crashes or errors.

•

Memory safety.
The submitted code must have no leaks or invalid memory accesses. This gate leverages runtime analysis tools (e.g., Valgrind) or PETSc’s own memory tracking features to detect memory issues.

•

API usage.
The code must follow correct PETSc patterns (e.g.,
bracketing of
PetscInitialize
/
PetscFinalize
, using PETSc public header files).

4.2
Stage 2: Metrics

Each metric evaluator produces a numerical score in
[0,1]
.

Numerical accuracy.

The program’s numerical output is compared against reference values provided
in the problem specification.
First, we compute the relative error as

\varepsilon=\|y_{\text{output}}-y_{\text{ref}}\|/\|y_{\text{ref}}\|
.
Then, we calculate a normalized score based on the error using an exponential decay:

s_{\text{acc}}=\min\!\bigl(1,\;e^{-\varepsilon/\tau}\bigr),

(1)

where
\tau
is a configurable tolerance with a default value of
10^{-6}
.

Execution time.

Runtime performance is scored by using piecewise linear interpolation
across four configurable thresholds in seconds (
t_{1}\!=\!1
s,
t_{2}\!=\!5
s,
t_{3}\!=\!15
s,
t_{4}\!=\!60
s by default): score=1.0 for
t\leq t_{1}
; linear decay through 0.8, 0.6, 0.2 at
t_{2}
,
t_{3}
,
t_{4}
; and score=
0.2\,t_{4}/t
for
t>t_{4}
.

4.3
Stage 3: Quality Assessments

This final stage is typically the most expensive.
It involves eight evaluators (Table
1
) producing scores in
[0,1]
and spanning the
code
,

appropriateness
and
library-specific
categories.
Six out of the eight evaluators rely on LLM judgment, optionally
augmented by static analysis or heuristics; the remaining two evaluators are library-specific and use deterministic checks.
The rule of thumb is that we use LLM-based evaluators only for subjective or semantic dimensions that cannot be checked easily with deterministic techniques.
In addition, deterministic evaluators can run in parallel via
asyncio.gather
within each stage for efficiency.

4.4
Score Aggregation

Individual evaluator scores are aggregated in two steps to produce the final composite score in
[0,100]
.

Step 1: Category Scores.

Each evaluator
j
in category
c
gives a score
s_{j}
in
[0,1]
with confidence

\alpha_{j}
.
The scores are weighted by confidence and aggregated into a single category score
S_{c}
for each of the five categories:

S_{c}=\frac{\sum_{j\in c}\alpha_{j}\,s_{j}}{\sum_{j\in c}\alpha_{j}}.

(2)

Confidence is a variable returned by the LLM for LLM-based evaluators and a fixed value for deterministic evaluators.

Step 2: Composite Score.

Scores across the categories are rescaled to 0–100 and then combined with configurable
weights
w_{c}
to produce the final composite score:

S_{\text{composite}}=\sum_{c}w_{c}\,S_{c}.

(3)

The default weights are

correctness
0.35,

performance
0.15,

code
0.15,

library-specific
0.20,

appropriateness
0.15.
Correctness and library-specific are weighted highest to reflect their importance in production scientific code.

6
Evaluation Results and Analysis

This section presents a rigorous, reproducible evaluation of agent performance on our benchmark.
We analyze how different models perform across the problems, categories, and failure modes.
The results reveal category-level strengths and weaknesses and offer practical guidance for improvement.

Figure 2:
Per-problem composite scores averaged over three runs per model.

6.1
Evaluation Settings

Each agent uses a frontier LLM (Claude Opus 4.6, Gemini 2.5 Pro, or GPT-5.2) and is given only one shot to generate code to solve each problem.
Each test is repeated three times under identical conditions to account for variability in LLM outputs.
The Green agent uses GPT-5.2 for LLM-based quality evaluators since it is known for its versatility.
All models are used with temperature set to 0 to facilitate reproducibility.
All problem specifications, evaluation code, and configuration files are publicly available at
https://github.com/petsc/petscagent-bench
.

6.2
Overall Performance

All models achieve only modest average composite scores. Gemini 2.5 Pro leads at
46.4
,
followed by Claude Opus 4.6 at
42.4
and GPT-5.2 at
39.9
.
Across 54 total attempts, 21 score zero due to gate failures,
while 17 exceed 80.

6.3
Per-Problem Analysis

A clear difficulty gradient can be seen in Figure
2
.
The easy problems, Rosenbrock and Vec/MPI Scatter, score
82–93 when gates are passed, although Claude fails all three Vec/MPI attempts.
Medium problems exhibit greater variability: 1D Advection averages
56–83, while Robertson ODE ranges from 16 to 67.
The hard problems, Darcy Flow and 2D Navier–Stokes, defeat
nearly all models, and only Claude passes gates on Darcy Flow
with an average score of 49.

Interestingly, all three models fail on the Navier–Stokes problem, but for distinct reasons.
Gemini 2.5 Pro fails at compilation in all three runs, passing
incorrect argument types to
DMStagCreate2d
, for example
supplying
NULL
where PETSc expects a
PetscInt

stencil width, indicating a fundamental misunderstanding of the
DMStag API. Claude Opus 4.6 and GPT-5.2 both compile successfully but then crash at
runtime.
In five of the six runs, PETSc complains about
“Matrix is missing diagonal entries,” indicating that the Jacobian
assembly omits some grid points.
One of GPT-5.2’s attempts fails with

DIVERGED_NONLINEAR_SOLVE
, implying a problematic nonlinear solver configuration.
Overall, these behaviors indicate that this test case remains beyond the capabilities of current frontier models.

6.4
Gate Failure Analysis

Gate pass rates are
67%
for Claude,
61%
for Gemini,
and
56%
for GPT-5.2.
Claude thus attains the highest pass rate.
We observe that every program that compiles passes
all the subsequent gates, indicating that the primary bottleneck is
generating code that compiles against PETSc rather than
subtle memory or API-compliance errors.

6.6
Qualitative Findings

Our multi-dimensional evaluation highlights several informative cases.
For the Vec/MPI Scatter problem, Claude triggers segmentation faults in three attempts despite otherwise high-quality code.
On the stiff Robertson ODE problem, Gemini 2.5 Pro produces clean, well-structured code but poor numerical accuracy due to loose integrator tolerances it selects.
Error handling scores are especially low (0.30 in 27 of 33 gate-passed attempts) since most models do not wrap PETSc calls in
PetscCall()
.
This suggests that current LLMs have learned PETSc usage from older versions (pre-3.17) that used the legacy

CHKERRQ()
style.

7
Discussion

Why library-based evaluation matters.

The dimensions that separate high from low scores (error-handling
conventions, solver selection, and resource-management patterns) are
inherently library-specific and do not arise in from-scratch
implementations.
By targeting PETSc,
petscagent-bench
evaluates the skill that matters for
production HPC code: composing scalable building blocks rather than
reimplementing known algorithms.
Our results show that models struggle at two levels.
The widespread use of the outdated
CHKERRQ()
macro points to
training data staleness as a key bottleneck.
In contrast, failures in assembling Jacobians for finite-element methods and in choosing tolerances appropriate to problem stiffness
reflect deeper gaps in knowledge and reasoning about numerical methods and solvers.

Implications for agent design.

The fact that compilation errors dominate gate failures suggests
multi-turn agents with compile–fix loops could substantially improve pass rates, as compiler
diagnostics are often informative enough to guide corrections.
The staleness we observe in error handling patterns indicates that enriching library-specific context for LLMs, e.g. with retrieval augmentation over up-to-date PETSc documentation, may be effective.
Our framework supports easy integration of new agents,
providing a natural testbed for assessing whether these architectural
improvements lead to better generated code.

Limitations.

The benchmark does not yet cover PETSc’s full breadth, such as GPU kernels
and multiphysics, but can be easily extended.
Also, LLM-based evaluators may vary across runs due to the inherent stochasticity of LLMs, though this is mitigated by temperature 0 and confidence weighting.

8
Conclusion and Future Work

We introduced
petscagent-bench
, an
agents-evaluating-agents
framework
for AI-based scientific code generation that targets
library-based

HPC programming rather than from-scratch implementations.
By making the evaluator a tool-augmented agent that compiles, executes,
measures, and judges code while communicating with the model under test via
standardized protocols, the framework enables
multi-dimensional, black-box evaluation that goes beyond traditional
pass/fail benchmarking.

Our evaluation of Claude Opus 4.6, Gemini 2.5 Pro, and GPT-5.2 shows
that frontier LLMs can sometimes generate readable, well-structured scientific code but
fall short on correctness and library-specific metrics.
Our findings highlight the value of multi-dimensional evaluation for scientific code generation.
They could serve as baselines for future research on developing more effective coding agents, e.g., those with multi-turn interactions, retrieval augmentation, or tool use.
For future work, we are expanding the benchmark to include GPU test problems.
