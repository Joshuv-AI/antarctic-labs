 I. Introduction
This document is the milestone delivery report for the ASC 2025 L2 milestone (See Table 1) for
advanced I/O capabilities for El Capitan via Flux Workload Manager support and the new I/O
hardware designed for El Capitan, the Rabbit Storage System. In this document we describe the
design of the Rabbit Storage System and how it is managed by Flux. We evaluate the performance
and usability of Rabbit using ARES, IOR, and an AI inference workload. Overall, we find that Rabbit
shows good scalability, especially in node-local storage configurations, and is more scalable than
the global Lustre parallel file system.

II. Background
The Rabbit storage system is an important component of El Capitan designed to meet the evolving
Input/Output (I/O) demands of next-generation supercomputing workloads.

The performance of I/O is a critical factor for HPC applications, particularly at larger scales, where
vast amounts of data must be read, written, and transferred efficiently. As HPC systems grow in size
and complexity, the ability to handle I/O operations without bottlenecks becomes essential to
ensure overall system performance. Poor I/O performance can lead to significant delays, as
compute nodes may spend more time waiting for data than performing actual computations,
thereby underutilizing expensive hardware resources. This is especially important in data-intensive
applications, such as scientific simulations and machine learning, where massive datasets are
processed and stored. At scale, efficient I/O strategies are crucial to minimize latency and
maximize throughput, ensuring that the system can handle growing workloads without
compromising performance.

To address the challenge of managing the I/O of ever-growing data-intensive workloads, several
advanced approaches have been developed to optimize I/O performance and mitigate bottlenecks.
One of the most widely used solutions is parallel file systems, such as Lustre, GPFS (IBM Spectrum
Scale), and BeeGFS. These systems distribute data across multiple storage servers, enabling
simultaneous access by many compute nodes. By allowing parallel read and write operations, they
provide high throughput and scalability, making them ideal for large-scale HPC workloads.
However, parallel file systems can still experience contention and performance degradation when
faced with highly concurrent or unoptimized I/O patterns.

Node-local storage is another approach that leverages high-speed storage devices, such as NVMe
SSDs, located directly on compute nodes. This method provides extremely low-latency, high-
bandwidth access to data, and eliminates the need to traverse the network to access shared
storage. Node-local storage is particularly useful for applications with temporary or intermediate
data, such as checkpointing or scratch storage, as it reduces the load on shared file systems.
However, its localized nature can make data management more complex, requiring explicit
coordination to aggregate or move data between nodes or to persistent storage.

III. The Rabbit Approach and Design
To address the challenges and limitations of current HPC I/O systems discussed in the previous
section, we designed the Rabbit Storage System for El Capitan. The Rabbit storage system is
designed as a near-node, high-performance storage tier to complement the slower, large-capacity
global Lustre file system by addressing the immediate, high-speed data needs of applications. This

 5

innovative storage solution ensures flexibility, efficiency, and scalability, enabling El Capitan to
handle the enormous data volumes and diverse workloads expected in modern HPC environments.

Rabbit is engineered to support a wide range of workloads, including traditional I/O operations such
as defensive I/O, checkpointing, reading input files, and writing output, while maintaining
compatibility with existing codes to minimize disruption for users. At the same time, Rabbit
empowers domain scientists to explore emerging computing paradigms, such as machine learning,
artificial intelligence, complex simulation workflows, and in situ analysis and data reduction. By
delivering exceptional performance and integrating with Livermore Computing (LC) I/O libraries and
tools, Rabbit enables El Capitan to address the challenges of changing I/O patterns in HPC
applications, ensuring both legacy and new workloads can run efficiently.

With its near-node design, Rabbit minimizes latency and maximizes throughput, providing a flexible
and high-speed storage solution that supports the growing complexity of modern HPC workflows.
This system not only enhances El Capitan’s ability to handle traditional and novel workloads but
also fosters innovation by making it easier for scientists to experiment with new computational
approaches. Rabbit is a foundational element of El Capitan’s storage architecture, ensuring the
system can meet the demands of exascale computing while delivering unmatched performance
and efficiency.

Rabbit Design
The key goals and functionality provided by Rabbit include performance, scalability, and ease of
use. Below we detail several of the primary design features of Rabbit.

Performance
The Rabbit storage system offers significant performance advantages by leveraging near-node local
storage to minimize latency and maximize I/O throughput. Its design integrates high-speed NVMe
flash storage (also called Near Node Flash, NNF) directly into the compute chassis, connected via
PCIe networks which enables rapid data movement between storage and compute nodes. This
proximity reduces the reliance on traditional, centralized storage systems, alleviating bottlenecks
and improving overall system efficiency.

Ephemeral and Persistent Storage

A key design objective for the Rabbit storage was to maximize the utility of the limited amount of
expensive, high-performance NVMe storage in the system. Each of the configurable Rabbit storage
modes described below can be instantiated as ephemeral or persistent. Ephemeral file systems
only exist for the duration of the job and offer significant advantages by providing a high-speed,
near-node storage tier optimized for temporary data storage and processing. This design enables
applications to access and manipulate data with minimal latency, making it ideal for workloads
requiring rapid I/O, such as checkpointing, in situ analysis, and real-time data reduction. Persistent
file systems exist for a fixed duration of time (determined by the compute center) and provide
access to the near-node storage tier for a team to use over the course of project or campaign. This
mode is useful in cases where it would be inefficient to restage data from the capacity tier to Rabbit
storage. For example, when running a campaign, the same datasets may be needed repeatedly for
the simulation workflow.

Flexibility in Storage Configuration

The design of the Rabbit hardware allows a shared pool of high-performance NVMe storage to be
dynamically reconfigured to meet applications requirements.

Rabbit storage can be configured in three different modes of operation, each of which can be
instantiated as ephemeral or persistent, to support various I/O use cases:

• Lustre: A private Lustre file system can be provided that spans storage across one or more
  Rabbit nodes. The private Lustre file system configuration is the easiest for users because it
  mimics the use of the system-wide parallel file system. The I/O traffic in this configuration
  travels over El Capitan’s high-speed network, so it potentially could interfere with application
  MPI communication.

• Private Node-local Storage: Direct-attached block storage is made available to the compute
  nodes over a PCIe interface and mounted as a local file system private to each compute node.
  This storage model scales directly with the available compute nodes and is optimal for providing
  low latency access to the storage, critical for workloads like AI/ML which depend heavily on
  small read/write I/O performance. We have chosen to use XFS as our default file system for this
  mode. Raw block storage may also be requested and used with an alternate file system type.

• Shared Node-local Storage: Shared file systems such as GFS2 allow direct access to storage
  blocks from both the Rabbit and computes node directly over the PCIe bus. This bypasses the
  overhead of traditional file-sharing protocols resulting in reduced latency and eliminates
  network contention between the application MPI traffic and I/O requests on behalf of the
  application. Furthermore, this design allows for services such as checkpointing or real-time
  data analysis to be offloaded to the Rabbit node while maintaining the scalability and low-
  latency advantages of direct attached block storage.

Automated data movement

Automated data movement between Rabbit and the global Lustre file system is a critical aspect of
Rabbit functionality when using the storage with an ephemeral file system. By automating the
transfer of data to and from Rabbit, users can focus on their scientific workflows without worrying
about manually managing data placement, which can be time-consuming and error prone. This
automation not only simplifies the user experience but also optimizes resource utilization, ensures
data persistence when needed, and maintains the high-performance capabilities of the Rabbit
storage system. Ultimately, this combination of ephemeral storage and automated data movement
enhances both system efficiency and user productivity in high-performance computing
environments. Users access the data movement functionality either through DataWarp (DW)
directives in their batch script or via a data movement service interface available on the compute
nodes. The batch directives enable a user to specify a directory or files that should automatically be

copied out to the global Lustre file system or copied into the Rabbit file system before the job. The
service interface is implemented as a library and provides finer-granularity control on what files are
transferred and when. The library interface for staging in and out data is only available when using
Rabbit in shared node-local storage or ephemeral Lustre modes.

Support for advanced workflows
A key design feature of the Rabbit nodes is that data management and analysis tools can run in
containerized environments on the Rabbit nodes. Running tools on the Rabbit nodes enables
application processes to immediately return to compute tasks while data activities are performed
in parallel on the Rabbit nodes. This feature will benefit several current and emerging workload
scenarios, including:

 • Checkpoint/restart. Here, application processes can write their data to Rabbit storage and
 checkpoint/restart daemon processes running on Rabbit can access the checkpoint data
 and process it in the background, e.g. make redundant copies of the data or move it to the
 global parallel file system.

 • Compression or in situ analysis. In this scenario, compression or in situ analysis daemons
 running on Rabbit nodes can access data written by applications and perform data
 reduction activities on the data. This enables the daemons to perform advanced and
 possibly slow and complex data reduction techniques on the data without interrupting or
 slowing the application processes.

 • Complex workflows. Complex workflows contain components with multistage data
 dependencies, e.g. a simulation stage component may output data that is read in by a data
 analysis or AI inference stage component. Workflow component processes can benefit
 from Rabbit storage because it has better scaling performance than the global parallel file
 system. Additionally, steering (or other) components of the workflow can run on the Rabbits
 themselves and use the knowledge of the data output by the different stages to determine
 next steps in the workflow cycle.

For this use case, application processes can use Rabbit storage in either shared node-local mode
(using GFS2) or ephemeral Lustre mode since mount points for those storage modes can be made
available to application processes on the compute nodes and the tool daemons on the Rabbit
nodes concurrently. (Note: private node-local mode using XFS will not work for this use case). The
mount point(s) for each compute node are made available to the tool's daemons on Rabbit nodes
by DW/Flux (described in a later section). Tools daemons can operate independently on each
Rabbit node assigned to the job or can operate cooperatively, e.g. by using MPI to communicate
with other tool daemons and make collective decisions about how to act on the application
processes’ data.

Container support
The container environment used to support user tools and advanced workflows on the rabbit is
Kubernetes (https://kubernetes.io/). Kubernetes is an open source system for automating
deployment, scaling, and management of containerized applications. Kubernetes is used widely in
the cloud computing community and provides a well-established standard environment for user
container workloads. While not originally designed for HPC systems, a full Kubernetes stack has
been integrated as a component into the TOSS-based HPC environment.

Flux Scheduler and DataWarp
The Flux Workload Manager is a next-generation resource and job management system designed to
address the scalability and flexibility challenges of modern HPC systems. Unlike traditional
workload managers, Flux is built around a hierarchical and composable architecture, allowing it to
efficiently manage resources at extreme scales while providing fine-grained control over job
scheduling. Each job in Flux operates within its own isolated instance of the workload manager,
enabling nested scheduling and dynamic resource allocation. This design allows users to create
custom workflows, optimize resource usage, and run complex workloads, such as ensembles or
workflows with dependencies, without requiring external tools.

Flux is unique among workload managers in that it provides the ability to schedule arbitrary
resources. This is particularly useful for El Capitan, where compute resources need to be
scheduled concurrently with Rabbit resources. Co-scheduling compute and Rabbit resources is
challenging because of the locality constraints of the near-node Rabbit storage. When scheduling,
Flux must select resources which can satisfy not only the compute node requirements but also
consider the storage requirements of the job and track the capacity and availability of near-node
local storage provided by the attached Rabbit node.

HPE’s DataWarp (DW) is a high-performance storage interface designed to optimize I/O
performance in large-scale HPC systems via tiered storage. DataWarp was first available on Cray
XC40 systems, including LANL’s Trinity supercomputer. HPE has continued development on
DataWarp for the Rabbit Storage System. DataWarp can be configured to provide node-local
storage or shared storage pools, depending on workload requirements, and supports advanced
features like dynamic allocation, data staging, and checkpointing. DataWarp has been architected
as containerized Kubernetes application. LLNL worked closely with HPE to co-design Rabbit’s
Kubernetes interfaces to support Flux, including the addition of interfaces for exposing resource
granularity, resource discovery, resource request translation, resource allocation, and performance
degradation notification.

Flux securely interacts with DataWarp using a well-defined REST API which was co-designed with
HPE to be highly flexible. The API is designed using Kubernetes best practices, relies on standard
components, and is backed by a redundant etcd configuration. Etcd is a reliable key-value store

commonly used in Kubernetes environments to store and manage configuration data, metadata,
and state information for a distributed system. Using this API, Flux can control the DataWarp
software by creating a set of Kubernetes resources which fully describe the storage requirements.
This includes the file system type, detailed physical layout of file system components on the
designated rabbit nodes, and a profile describing how the file system should be configured.
Additionally, a workflow resource is created to manage the life cycle of the storage allocated. When
a job is ready to run, Flux and the Rabbit software work together to move the workflow through a
series of stages, to provision the storage on the Rabbit nodes, create the requested file systems,
stage-in application data, and finally mount the file systems on the compute nodes. When a job
completes Flux updates the workflow to instruct DataWarp to unmount the file systems, stage-out
any data to the global Lustre, destroy the file systems and release the storage.

ARES End-to-end Functionality with Rabbit Storage System
The purpose of the tests in this section is to demonstrate at scale the end-to-end functionality of
the Rabbit Storage system with a multiphysics code, ARES.

ARES is one of LLNL's flagship codes for advancing understanding in high-energy-density physics.
It is primarily used for solving problems in radiation hydrodynamics, which involves the interaction
of radiation with matter in high-energy-density physics scenarios. ARES is designed to handle
complex simulations in areas such as astrophysics and inertial confinement fusion (ICF). The ARES
code is a workload of interest to LLNL scientists which has been integrated with the Scalable
Checkpoint/Restart (SCR) library which allows ARES to be run in various modes to demonstrate the
I/O capabilities of the Rabbits.

ARES was run at 1024 nodes on El Capitan exercising the various Rabbit configurations described in
detail in Table 2. We used the same input deck for each ARES test case and configured ARES to
frequently dump checkpoints to evaluate the I/O functionality. Detailed checkpoint I/O timings are
not reported by the ARES code without additional instrumentation which was unavailable when
these tests were run. For all tests that use SCR, SCR executed on the compute nodes only. At the
time of this writing, SCR had not yet been ported to execute in a container on the Rabbit nodes.

The purpose of the tests in this section is to demonstrate the functionality of the data offloading

We identified the following problems in our evaluation of the NNF-DM library:

1. The NNF-DM library depends on Google protobufs to interact with the Kubernetes Data
 Workflow Services (DWS) software. This is problematic for many HPC applications because
 protobufs are not well supported in common HPCs languages, because they require a large
 number of dependencies which increases application binary size and are complex to integrate
 with applications.

2. The NNF-DM library directly interacts with the Kubernetes API server to orchestrate the data
 movement requests. For large systems this has been shown to be a performance bottleneck
 limiting the rate at which data movement requested can be processed.

HPE is addressing these issues by removing the use of protobufs and providing a thin lightweight C
library which can provide the language bindings required by HPC applications. Scalability will be
improved by modifying the NNF-DM daemons to directly communicate with the data movement
services running on the Rabbit nodes.

de facto I/O benchmark used for understanding basic performance characteristics of file systems.
IOR can be used to simulate the behavior of common HPC workloads, most importantly bulk
synchronous reads and writes (e.g., to simulate checkpointing) and random reads (e.g., to simulate
AI training).

V. Challenges
As with any new component on a supercomputer, we encountered several significant challenges
along the way and learned several valuable lessons. Here we detail a few of the more impactful
challenges:

 • PCIe switch stability. The design of each Rabbit node contains a PCIe switch that connects
 the NVMe SSDs to the compute nodes. The switch provides flexibility to allow the NVMe
 namespaces to be allocated and formatted from the Rabbit node, detached from the Rabbit
 node, and then attached to the correct compute node and mounted for the job. This allows
 the Ephemeral Node Local modes of operation to use the PCIe connection instead of the
 high-speed Slingshot network. While the idea of the PCIe switch has its advantages, in
 practice major bugs were discovered in the PCIe switch firmware due to the highly dynamic
 way in which they are used. These bugs could only be reconciled with HPE and the PCIe
 switch vendor but could not be reliably reproduced at a small scale. This required us to
 deploy multiple rounds of debug firmware to El Capitan to root cause the issues. At the time
 of this writing, many of the major bugs have been fixed, but we are still working through
 some remaining issues.

 • Rabbit hardware rework. When testing the first large batch of Rabbits delivered to LLNL it
 was discovered that it was no longer possible to reliably boot all of the attached compute
 nodes at the same time. They would often hang early in the BIOS and report a PCIe failure.

 17

 This issue was not caught early in the hardware development because it only manifested
 itself on a small percentage of the Rabbit nodes, and only when the chassis was fully
 populated with compute blades. HPE was able to identify the problem using one of the
 production Rabbits which more reliably reproduced the issue and reworked the delivered
 Rabbit hardware to correct the flaw. This resolved the issue but significantly delayed our
 efforts to integrate and test the Rabbits.

 • Kubernetes complexity and debugging. Kubernetes is inherently complex due to its
 distributed architecture and the multitude of components required to orchestrate large-
 scale containerized applications. Unexpected interactions between components, complex
 overlay networks, little visibility into running pods, and a lack of debugging tools combine to
 make it more challenging to analyze and resolve issues in Kubernetes environment than in a
 traditional HPC environment.

 • Kubernetes scalability. Kubernetes was not designed for HPC and as a result we have
 encountered a variety of bottlenecks. At the scale of El Capitan the Kubernetes API server
 can get overwhelmed by bursts of traffic generated by the Rabbit software which results in
 request throttling and long latencies. To mitigate these issues, additional Kubernetes
 control plane nodes have been configured, and the Kubernetes API service network policy
 has been tuned to better handle the load. We’ve worked with HPE to identify these
 bottlenecks as they are encountered and to iterate with them on the rabbit software to
 reduce the load of the Kubernetes API servers.

 • NNF-DM scalability. As shown in Section IV, initial data movement tests with HPE’s Near
 Node Flash Data Movement library (NNF-DM) show scalability challenges. In Version 1 of
 the library all data movement requests were handled by the Kubernetes API servers, this
 was not scalable. HPE is developing a Version 2 of the library where compute nodes directly
 connect to their attached Rabbit node to manage the data movement and address this
 scalability issue.

 • Reliability for large scale jobs. We have encountered challenges with Rabbit failures,
 largely due to the instability of the PCIe switch firmware. Unfortunately, when there is a PCIe
 switch failure, it takes down all compute nodes connected to the Rabbit node with the
 failure, i.e. an entire chassis of compute nodes. As noted above, HPE is working with the
 PCIe switch vendor to improve the reliability of the PCIe switches.

VI. Future Work
One item of future work is to showcase the new capabilities the Rabbit nodes offer for data
management and analysis tools, where tool daemons can run on the Rabbit nodes and access the
data produced by the application processes on the compute nodes (described in Section III). Our

demonstration tool for this capability is SCR. Currently, SCR is a library that runs in the memory
space of the application on the compute nodes. To demonstrate the new capability, we will
separate the data management functionality of SCR and run it in a Kubernetes container on the
Rabbit node. We will use the shared ephemeral file system mode of the Rabbits using GFS2, where
the application code will write checkpoints to node-local GFS2 mount points on the compute
nodes and SCR running on the Rabbit node will read the checkpoint data. With this mechanism,
SCR can perform its data management operations without perturbing the application processes. To
date, we have begun the port of SCR to the Rabbit nodes, but the porting process has been slowed
due to early instability of the Rabbit nodes.

Another item of future work is to perform a comprehensive performance evaluation of the Rabbit
Storage System, including scalability and best configurations for all Rabbit configuration modes.
We have performed some initial testing as described in Section IV but still have more to do before
we fully understand the best ways for our applications and workflows to use the Rabbits.

Finally, HPE has a small number of outstanding features in progress. In addition to the revised data
movement library (NNF-DM), they are implementing the code to handle a drive replacement. This
includes recreating the required NVMe namespaces on the new device and initiating a RAID array
rebuild for any long-lived persistent file systems which were striped over that device.

VII. Conclusion
In summary, we have successfully deployed and performed an initial evaluation of the Rabbit
Storage System of El Capitan. Our evaluation shows that Rabbit benefits numerous workloads that
are important for modern HPC, including checkpoint/restart and AI inference workloads. The Rabbit
Storage System shows good scalability, especially in node-local storage configurations, and is more
scalable than the global Lustre parallel file system. While we still have more testing and evaluation
to perform, the results to date show that Rabbit will benefit ASC applications, workflows, and
advanced data management and analysis tools.
