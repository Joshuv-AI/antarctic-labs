Section 2 Background
This section provides background information on why monitoring is needed. It discusses the
background of the monitoring in LC, the current state of monitoring, and the goal of this L2.

Why is Monitoring Important?
Monitoring is essential to understanding and making informed decisions in LC for a broad range
of areas including security, procurements, and performance. In the security realm, monitoring of
logs is important to know who is accessing the systems and to detect anomalies. In the
performance realm, metrics can be used to gauge how efficiently system resources are utilized.
Finally, understanding system needs is critical to right-sizing procurements.

In LC, there have been several distinct monitoring efforts. The sonar project focused on
collecting performance metrics for users, procurement teams, and researchers with limited
resources for the scope of the problem. Security operations (SecOps) teams used Splunk to
monitor logs. System administrators used Skummee, in addition to Splunk, to monitor the health
of systems.

This L2 is the beginning of an effort to unify the different monitoring infrastructure into a
converged data repository. The teams standardized into an Elasticsearch, Logstash, and Kibana
(ELK) stack with Kafka data transport pulling from various data sources. The monitoring efforts
covered in this milestone include the historically separate efforts for security logs and system
administration data, system and user performance and utilization data, and facilities data.

Section 3 Monitoring Overview
This section describes the work completed in this milestone including converging the center-
wide monitoring, data sources, and enablement of insights via the converged monitoring.

Converging Center-wide Monitoring
We built the converged data store by evaluating data sources and requirements from each of
the existing monitoring solutions. In order to converge the infrastructure, we assessed which
tools were being used in security operations monitoring, sonar project monitoring, and facilities
monitoring areas and made decisions on which components to keep or cull for the converged
infrastructure. We then connected the components and made adjustments as different needs
appeared.

The monitoring infrastructure of each area were as follows. The security operations monitoring
stack included Splunk, as well as the Elasticseach database, Elastic Agents, Log Stash, and
Kibana visualization set of tools, commonly known as the ELK stack. The sonar monitoring
stack included the Apache Cassandra database, Kafka data transport, Caliper application
profiling tool, Lightweight Distributed Metric Service (LDMS) data collection tool from Sandia
National Laboratories, and Jupyter notebooks. The facilities data is comprised of various
hardware sensors that store information in the AVEVA PI System.

The converged stack, as seen in figure 1, consists of Caliper, LDMS, Kafka, and Jupyter from
the Sonar Project, the ELK stack and Splunk from the SecOps monitoring, and the AVEVA PI
System from facilities. Data is collected from the facilities via sensors to the AVEVA PI System.
This includes information related to the cooling towers, power going to the systems, and other
facilities level data. Caliper collects data from the applications and is in progress to be
connected with LDMS. While we finish work on streamlining the data flow between Caliper and
LDMS, we have another route for applications to drop CSV files that are picked up and put into
Elasticsearch. The LDMS and Redfish data are the larger data sources for performance metrics
that are being pulled from the production clusters. The last data source is the Elastic Agent,
which collects logs and sends them up to both Kafka and Logstash.

The majority of the data movement is done by Kafka, and is sent to the Elastic Databases. A
portion of the data is processed by Logstash and sent up to both Elastic and Splunk. Splunk is
used by a few groups due to some functionalities not being available yet in Elastic and Kibana.
The goal is to move away from Splunk once those requirements can be met. Elastic is the
converged data repository for the center-wide monitoring that enables correlation and analysis
across the historically disparate data sources. The analysis tools that we are using include
Kibana, which has close ties with Elastic, and Jupyter, which data must be exported to utilize a
different set of capabilities than Kibana.

Data Sources
In this section, we discuss the data sources in more detail. Data sources covered will be the
security operations logs, LDMS/Redfish, application provided metrics, and facilities operational
data.

Security operations logs are collected across the systems and include different granularities
such as node, process, and network. The logs are a significant source of data. As seen in figure
2, we collect over 100,000,000 logs in a 24 hour period. A breakdown of the log volume by disk
usage shows that system syslog, netflow, and system authorization logs make up over half of
the logs at the point this graph was generated.

Figure 2. This figure shows two charts: a 24hr count of collected logs in Elastic and a breakdown of the

The next significant source of data is LDMS and Redfish. LDMS runs on all systems in LC,
including El Capitan and Tuolumne, however not all clusters are currently exporting their data to
Elastic. The combination of LDMS, Redfish, and other data from El Capitan and other smaller
clusters into one Elastic is 1.5PB of data. Combined across the CZ and RZ, the clusters
Tuolumne, RZAdams, and Hetchy have contributed roughly 46TB of LDMS data and about 7TB
of Redfish telemetry data.

Applications can also submit app-specific data to the converged data repository. The Ares
applications drops CSV files into specified write-only directories. Data in the CSV files is specific
and based on the needs of the users and group, and it is manually ingested in bulk to Elastic.
Once this data is in Elastic, it can be used to build dashboards in Kibana in order to decide such
things as which packages to optimize. In the future we plan to use Caliper, Kafka, and other LC
tools to automate producing and transferring this type of data into Elastic.

The final data source we discuss in this summary, is the facilities operational data. Historically
this data was collected from physical sensors and collected into the AVEVA PI System. This was
separate from the LC resources and needed to be accessed via a specific Windows system that
was set up in a particular way. In order to enable the data transfer via Python scripts, a
connection between the PI data source and LC has been opened via the system RZSlic. Data
includes such metrics as power and energy usage by full systems from meters, information
about cooling for the systems, and more which will be explored further in the future. Data is
manually brought over, but with plans for automation.

Enabling Insights
This section discusses how the converged monitoring infrastructure provides analytics and
enables insights into the disparate data sources of the central data repository.

The Kibana interface is the first stop for exploring the data in Elastic. In particular, there is a
section called Discover, as shown in figure 3, that allows the user to select the data of interest
and see an initial view with selectable fields, a portion of the data entries, and a visual of how
many entries have been collected within a selectable timeframe.

Figure 3. This figure shows an example of the Kibana Discover interface with the LDMS meminfo
information shown.

After assessing which fields are of interest, visualizations can be created individually and added
to a dashboard that shows sets of visualizations together. An example of a simple dashboard
can be seen in figure 4.

Figure 4. This figure shows an example of the Kibana Dashboard interface with average GPU Utilization
information shown.

While these dashboards can be set up relatively quickly, they do not offer as much flexibility
when trying to make more complicated visualizations. One example downside of the version of
Elastic we are using is that it does not have the typical “join” capability.

To address the inflexibilities of Elastic and Kibana, we use Python in conjunction with Pandas
data frames and Jupyter notebooks to do analysis and visualizations. When large amounts of
data are being queried, we use the Elastic scroll API since not all data is returned at once from
Elastic. The query is formatted via JSON and we specify time range and field values to match.
To limit the fields returned, which increases the performance of otherwise time consuming large
queries, a list can be specified as well. Once the data has been obtained from Elastic, it can be
put into Pandas data frames or other tools to do more complex analyses. The data can then be
visualized via Jupyter notebooks and potentially fed back into Elastic to allow for dashboards to
be made based on the processed data.

Section 4 Conclusion
The convergence of the center-wide monitoring infrastructure at LC has enabled analyzing and
gaining insights from historically disparate data sources. It brought together teams from security
operations, Sonar, and facilities. Based on requirements the ELK stack, Kafka, and multiple data
sources were selected to address current monitoring and analysis needs. While more work is
needed to streamline processes, automate, and tune the infrastructure for performance, the
creation of new dashboards and analyses is now possible with the convergence to the single
data repository.
