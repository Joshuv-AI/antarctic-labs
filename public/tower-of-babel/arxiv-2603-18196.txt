Abstract
. Investigating cybersecurity incidents requires collecting and analyzing evidence from multiple log sources, including intrusion detection alerts, network traffic records, and authentication events. This process is labor-intensive: analysts must sift through large volumes of data to identify relevant indicators and piece together what happened. We present a RAG-based system that performs security incident analysis through targeted query-based filtering and LLM semantic reasoning. The system uses a query library with associated MITRE ATT&CK techniques to extract indicators from raw logs, then retrieves relevant context to answer forensic questions and reconstruct attack sequences. We evaluate the system with five LLM providers on malware traffic incidents and multi-stage Active Directory attacks. We find that LLM models have different performance and tradeoffs, with Claude Sonnet 4 and DeepSeek V3 achieving 100% recall across all four malware scenarios, while DeepSeek costs 15 × \times less ($0.008 vs. $0.12 per analysis). Attack step detection on Active Directory scenarios reaches 100% precision and 82% recall. Ablation studies confirm that a RAG architecture is essential: LLM baselines without RAG-enhanced context correctly identify victim hosts but miss all attack infrastructure including malicious domains and command-and-control servers. These results demonstrate that combining targeted query-based filtering with RAG-based retrieval enables accurate, cost-effective security analysis within LLM context limits.



1.
Introduction

Security Operations Centers operate under increasing pressure: cyber threats grow in both volume and complexity, yet the analyst workforce has not kept pace. Modern Security Information and Event Management (SIEM) deployments routinely generate thousands of alerts per day, but empirical studies show analysts can only examine a small subset, resulting in fatigue and overlooked incidents
(
18
;
10
;
20
)
. Investigating a security incident (identifying compromised assets, tracing attacker actions, understanding intrusion mechanisms) demands synthesis of evidence spread across intrusion detection systems, network telemetry, and endpoint logs. This labor-intensive work strains limited analyst capacity, motivating research into intelligent systems that can accelerate incident analysis.

Current detection mechanisms depend heavily on signatures and static rules, which cannot generalize to previously unseen attack patterns. Sophisticated adversaries exploit this gap through techniques like misconfigured certificate template abuse (e.g., ESC1
(
16
)
), Kerberos ticket forgery
(
14
)
, and stepwise lateral movement through network trust relationships. Such attacks can progress over hours or days, depositing forensic artifacts across disparate log sources (Suricata alerts, Zeek connection records, Windows authentication events) where no individual entry reveals the complete attack chain. Recent machine learning approaches address alert triage and anomaly scoring
(
19
;
22
)
, but these methods yield classifications or rankings, not the narrative reconstruction that incident responders require.

Large language models are well-positioned to address this problem: they can interpret unstructured text, integrate scattered facts into coherent narratives, and communicate findings in natural language
(
23
)
. Feeding raw security logs directly into an LLM, however, is impractical. A single incident may produce millions of log entries, vastly exceeding model context limits
(
4
)
. These logs mix genuine attack indicators with overwhelming volumes of routine activity (normal authentications, benign connections, spurious alerts), burying the attack signal. Additionally, incident response often demands rapid turnaround, while LLM inference remains comparatively slow. These challenges motivate the design of new AI-enabled security systems that extract relevant events from such large volumes of logs and generate incident reports interpretable by security analysts.

We present a RAG-based system for security incident analysis that extracts relevant threat indicators by running targeted queries on security logs, mapping the attack indicators to the MITRE ATT&CK framework, and feeding the subsequent results to a LLM with context augmented by semantically similar events to generate interpretable reports of security incidents. The framework operates in two modes: forensic question-answering and attack reconstruction. In the first mode, analysts pose specific questions (identifying infected hosts, command-and-control (C2) servers, or initial compromise vectors) and receive evidence-backed reports with explainable answers. In the second mode, the system reconstructs attack sequences by associating distinct forensic events into causal narratives of attack progression over time. Central to our approach is a security-aware context construction pipeline. Rather than pass raw logs to the LLM, we extract through targeted queries Indicators Of Compromise (IOCs), compute aggregates of log data, and organize results into semantically meaningful chunks that preserve cross-event relationships. The RAG architecture is essential in extracting the most relevant information from multiple security logs for inclusion in the LLM context, enabling the model to generate interpretable incident reports for security analysts.
Our general architecture supports multiple LLM providers—both cloud APIs and locally deployed models—enabling organizations to balance performance, cost, and data sensitivity.

We make the following contributions:

Problem formulation for LLM-based incident analysis.
We frame security incident analysis as two complementary tasks: (a) structured question-answering with type-specific matching functions that handle the semantics of security answers (IP addresses, hostnames, domain sets), and (b) attack sequence reconstruction that correlates discrete forensic events into causal narratives of attack progression.

Security-aware RAG architecture with cross-event semantic reasoning.
We design a retrieval pipeline tailored to security data: targeted queries extract indicators, aggregators compress thousands of events into patterns, and semantic chunking preserves cross-event relationships. This enables LLMs to identify attacks requiring correlation across discrete events, such as the detection of Active Directory certificate abuse by recognizing Subject/SAN mismatches across certificate request and issuance operations. This demonstrates contextual interpretation that distinguishes coordinated exploitation from individually legitimate activities.

LLM provider evaluation with cost-effectiveness analysis.
We evaluate eight LLM configurations spanning cloud APIs (Claude Sonnet 4, DeepSeek V3, GPT-4, GPT-4o, GPT-5-mini, GPT-5.2) and local deployment (Llama 3.1:70b, Cisco Foundation-Sec-8B) on malware traffic and Active Directory attack scenarios. The best-performing configurations (Claude Sonnet 4, DeepSeek V3) achieve 100% recall across all four malware scenarios that we analyzed, while attack step detection on Active Directory scenarios reaches 100% precision and 82% recall. DeepSeek achieves accuracy equivalent to Claude at 15
\times
lower cost ($0.008 vs. $0.12 per analysis), making it the most cost-effective cloud provider. Local deployment (Llama) provides data privacy with acceptable accuracy (95% recall) for environments with strict data governance requirements. Notably, the security-specialized Cisco Foundation-Sec-8B model does not outperform general-purpose models at 90% recall, suggesting that reasoning capability matters more than domain-specific pretraining for complex forensic tasks. The system completes malware analysis in 1–2 minutes per incident with cloud providers, while Active Directory attack analysis runs in under 1 minute per 5-minute window with local deployment, demonstrating real-time feasibility for both scenario families.

To support reproducibility, we will release our implementation, including the query library, RAG pipeline, and evaluation scripts, along with detailed results for the malware traffic scenarios. The malware traffic datasets are publicly available
(
7
)
; the Active Directory data originates from a private red team exercise and has not been publicly released.

Related Work

LLMs for Cybersecurity.
Large language models have emerged as tools for cybersecurity automation, with recent surveys cataloging applications across vulnerability detection, malware analysis, threat intelligence, and incident response
(
23
)
. This body of work demonstrates both the potential and limitations of LLMs for security tasks.

Early efforts adapted pre-trained models to cybersecurity text. SecureBERT
(
1
)
introduced a domain-specific BERT model trained on cybersecurity corpora, demonstrating improved performance on tasks involving MITRE ATT&CK terminology. CySecBERT
(
2
)
adopted domain adaptive pre-training to BERT on a large scale cybersecurity corpus to improve performance on cybersecurity NLP tasks such as Named Entity Recognition and Cyber Threat Intelligence. For threat taxonomy mapping, TRAM fine-tunes SciBERT to map reports to MITRE ATT&CK techniques
(
15
)
. These models provide strong semantic representations for classification and embedding tasks.

Log-based anomaly detection represents a key application area. LogLLM
(
9
)
combines BERT for semantic extraction with Llama for sequence classification on system log datasets. LogPrompt
(
13
)
explores zero-shot anomaly detection through prompt engineering. These approaches focus on system logs (e.g., HDFS, Linux) and binary anomaly labels rather than security-specific logs with multi-stage attack patterns.

Recent work explores Multi-agent LLM systems to cyber security tasks such as insider threat detection (Audit-LLM
(
19
)
demonstrates reduced false positives for insider threat detection) while SOC-specific systems like CORTEX
(
22
)
propose specialized agents for alert triage. Work on CTI automation
(
21
)
develops agents that extract Indicators of Compromise from threat reports. These systems advance alert-level processing but focus on triage and summarization rather than answering specific questions about detected incidents.
Examining operational use, Singh et al. analyzed queries from 45 SOC analysts, finding that LLMs function as cognitive aids that augment rather than replace expertise
(
18
)
.

In contrast to prior work focusing on alert triage or classification, our work addresses end-to-end incident analysis formulated as question-answering over heterogeneous security logs, processing data from intrusion detection systems, network monitors, and authentication events.

Retrieval-Augmented Generation.
Retrieval-Augmented Generation (RAG) addresses limitations of LLMs—hallucination, outdated knowledge, and opacity—by conditioning generation on external evidence retrieved at inference time
(
12
)
. RAG has become the dominant paradigm for knowledge-intensive tasks where accuracy and traceability are required. Surveys categorize RAG architectures into retriever-centric, generator-centric, and hybrid designs, with recent advances in adaptive retrieval, iterative refinement, and self-reflection
(
8
;
17
)
.

Recent work applies RAG to security tasks. CyberRAG
(
3
)
presents an agentic framework for cyber attack classification, using iterative retrieval over domain-specific knowledge bases to reduce false positives and generate explanations. AgCyRAG
(
11
)
combines knowledge graph retrieval with vector search for security log analysis, orchestrating specialized agents to integrate structured threat intelligence with security log data. Work on threat intelligence automation
(
21
)
uses RAG to extract Indicators of Compromise from CTI reports and generate regular expressions to assist security analysts in establishing SIEM correlation rules.
GraphRAG-based approaches
(
5
)
leverage ontology-backed knowledge graphs constructed from network logs to support LLM-driven query generation for network security monitoring.
These systems demonstrate RAG’s applicability to security data, primarily focusing on attack classification and threat intelligence extraction.

Our work applies RAG to a different task: answering structured security questions over heterogeneous log sources (Suricata alerts, Zeek connections, Windows events). This requires smart chunking strategies tailored to security data
and retrieval that supports reasoning about attack progression across multiple log sources.

3.
Problem Formulation

We formalize security incident analysis as a question-answering task and define the evaluation metrics used throughout our experiments.

3.1.
Security Incident Analysis as Question Answering

Let
I\in\mathcal{I}
denote a
security incident
, characterized by a collection of security logs
L_{I}
(e.g., Suricata alerts, Zeek connection logs, Windows event logs). We formulate incident analysis as question-answering: given an incident’s logs, the system must answer forensic questions about the attack.

Definition 3.0 (Evaluation Questionnaire).

A
questionnaire

Q\sim\mathcal{Q}(I)
is a finite collection of
question-answer pairs drawn from the space of possible questionnaires over
incident
I
:

Q=\{(q_{i},a_{i},\tau_{i})\}_{i=1}^{M}

where:

•

q_{i}\in\mathcal{Q}
is a natural language question

•

a_{i}\in\mathcal{A}_{\tau_{i}}
is the reference answer

•

\tau_{i}\in\mathcal{T}
is the
answer type
(defined below)

•

M
is the number of questions in the questionnaire

Answer Types.

We define

\mathcal{T}=\{\texttt{ip},\texttt{hostname},\texttt{user},\texttt{domain\_set},\texttt{ip\_set}\}

to capture the structure of expected answers. This distinction is important because different answer types require different matching functions (Section
3.3
).

Concrete Questionnaire.

Throughout our experiments, we use a questionnaire of M = 5 questions targeting the essential information incident responders need to scope and contain an attack:

(1)

What is the IP address of the potentially infected internal host in the LAN? (
\tau=\texttt{ip}
)

(2)

What is the hostname of the potentially infected machine in the LAN? (
\tau=\texttt{hostname}
)

(3)

What is the Windows user account name of the potentially infected machine in the LAN? (
\tau=\texttt{user}
)

(4)

What are the likely fake or suspicious domains / URLs for initial infection? (
\tau=\texttt{domain\_set}
)

(5)

What are the suspicious external IP addresses contacted, which might be involved in command-and-control (C2) communication? (
\tau=\texttt{ip\_set}
)

Questions 1—3 identify affected assets, question 4 determines the initial compromise vector, and question 5 pinpoints command-and-control infrastructure. These represent core forensic questions common across incident types. The framework naturally extends to additional questions (e.g., "What MITRE ATT&CK techniques were used?" or "What files were dropped?") without modification to the underlying architecture.

Beyond forensic identification, we also evaluate attack reconstruction: deducing the attack path a malicious actor took over a given timeframe. For this task, we pose a compound question ("What did the attacker do? What defenses should be implemented?") and evaluate responses using precision (fraction of reported attack steps matching reference) and recall (fraction of advised remediations matching reference). This formulation unifies both modes within the question-answering framework, although attack recreation requires richer evaluation against known attack timelines (Section
7
).

3.2.
Security Analyzer

The Security Analyzer is a
compound AI system
that takes raw security
logs as input and produces answers to security questions. We decompose it into
two main components.

Definition 3.0 (Security Analyzer).

A
Security Analyzer

SA
is a function:

SA:\mathcal{L}\times\mathcal{Q}\rightarrow\mathcal{R}

where
\mathcal{L}
is the space of security logs,
\mathcal{Q}
is the question
space, and
\mathcal{R}
is the response space. For an incident
I
with logs

L_{I}\in\mathcal{L}
and questionnaire
Q=\{(q_{i},a_{i},\tau_{i})\}_{i=1}^{M}
:

SA(L_{I},Q)=\{r_{i}\}_{i=1}^{M}\quad\text{where }r_{i}=SA(L_{I},q_{i})

Following the compound AI systems paradigm
(
24
)
, we decompose the Security Analyzer into independently optimizable components:

Security Context Extraction

(
SCE:\mathcal{L}\times\mathcal{Q}\rightarrow\mathcal{C}
): This component interfaces with the SIEM platform to retrieve logs and applies a library of predefined IOC queries
\mathcal{F}=\{f_{1},\ldots,f_{K}\}
to extract security-relevant features such as Suricata alerts, suspicious certificates, high-volume connections, authentication anomalies. A RAG retrieval function then selects the top-k most relevant chunks for each question based on semantic similarity.

RAG-LLM Analysis

(
LLM:\mathcal{C}\times\mathcal{Q}\rightarrow\mathcal{R}
): Given the retrieved context and a question, the LLM produces a structured response with supporting evidence.
This modular structure allows each component to be optimized independently: the query set
F
determines detection coverage, the embedding model controls retrieval quality,
k
governs context size, and the LLM provider affects reasoning accuracy.

3.3.
Matching Functions

A key challenge in evaluating security analysis systems is defining appropriate matching functions. Unlike standard QA benchmarks where exact string matching can be sufficient, security answers have structure that must be respected.

Definition 3.0 (Type-Specific Matching).

For each answer type
\tau\in\mathcal{T}
, we define a matching function

match_{\tau}:\mathcal{A}_{\tau}\times\mathcal{R}\rightarrow[0,1]
. Let
R
denote the reference answer and
A
denote the model’s answer:

\displaystyle match_{\texttt{ip}}(R,A)

\displaystyle=\mathbf{1}[R=A]

\displaystyle match_{\texttt{hostname}/\texttt{user}}(R,A)

\displaystyle=\mathbf{1}[\text{normalize}(R)=\text{normalize}(A)]

\displaystyle match_{\texttt{domain\_set}/\texttt{ip\_set}}(R,A)

\displaystyle=\frac{|R\cap A|}{|R|}

where
\text{normalize}(\cdot)
performs case-insensitive comparison.

Remark 3.1 (Non-Triviality of the Task).

The matching function reveals why this task is non-trivial. Consider a baseline
that generates random answers:

•

For
\tau=\texttt{ip}
(private IPv4):
P(\text{random correct})=\frac{1}{2^{24}}\approx 6\times 10^{-8}

•

For
\tau=\texttt{hostname}
: The space of valid Windows hostnames grows in the billions of elements.

•

For
\tau=\texttt{domain\_set}
: Random domain generation has negligible success probability given that there are hundreds of millions of registered domains.

This contrasts with
k
multiple-choice QA where random baselines achieve
1/k
accuracy; for
k=4
a random baseline would be correct
25\%
of the time. Our task requires the system to
generate
structured answers from unstructured logs.

4.1.
Design Principles

Five principles guided our architectural decisions.

1) Filter before analysis.

LLMs are too slow to process large volumes of raw logs and perform poorly on noisy data. We first extract security-relevant information using targeted IOC queries, allowing the system to scale to tractable log volumes and generate interpretable reports.

2) Embed once, query many times.

Extracted data is semantically embedded into a vector database and cached to disk. The index is built once per dataset and can be queried repeatedly with different questions, LLM providers, or prompt strategies without reprocessing.

3) Periodic analysis.

Rather than invoking the LLM on every event, the system performs analysis at defined intervals, batching related activity into coherent time windows.

4) Provider-agnostic design.

LLM interactions are abstracted behind a common interface, enabling substitution of providers to balance cost, latency, and privacy requirements.

5) Extensible IOC query library.

Detection queries are maintained as a separate library with associated MITRE ATT&CK techniques, allowing extension without modifying the core pipeline.

The system integrates with existing network monitoring infrastructure through standard APIs. Our implementation uses Security Onion, an open-source platform that aggregates network traffic using Suricata and Zeek, communicating through ElasticSearch REST API calls. The architecture generalizes to any SIEM exposing a query API.

4.3.
RAG-LLM Analysis

The RAG-LLM Analysis component transforms extracted security information into actionable incident reports. Given a set of security questions, it retrieves relevant context from the embedded document store and prompts an LLM to produce evidence-based findings. This design decouples index construction from analysis, enabling rapid experimentation with different questions, providers, and prompt strategies without reprocessing the source data.

Data Processing and Embedding.

The Security Context Extraction component produces structured output containing aggregations and log entries from the SIEM platform. Before embedding, this output is split into semantically meaningful chunks rather than arbitrary text segments. The data chunks usually consist of aggregate results, which summarize patterns across many events.

Chunks are embedded using a pre-trained sentence embedding model and indexed in a vector store for fast similarity search.
1
1

1

Our implementation uses all-mpnet-base-v2 and FAISS; other embedding models and vector stores could be substituted.
The complete index—chunks, metadata, and embeddings—is serialized to disk, allowing the embedding phase to run once per dataset.

Retrieval and Prompt Construction.

Given a security question, the system retrieves relevant chunks from the embedding index using semantic similarity search. The question is embedded using the same model as the indexed chunks, and nearest neighbors are retrieved based on vector similarity.
This retrieval-augmented approach grounds LLM responses in actual log data, reducing hallucination and enabling evidence-based reasoning that analysts can verify.

The prompt establishes the LLM’s role as a cybersecurity analyst, presents the question, and provides brief network context with topology information (address ranges, domain name, key infrastructure). Retrieved chunks appear next, each tagged with its source file to support attribution. The prompt concludes with an instruction to answer based on the provided evidence or indicate when information is insufficient. We provide the base prompt template in Appendix
B
and a sample network context in Appendix
C
.

Security Questions.

The system supports different categories of security questions depending on the analysis goal (Appendix
D
).
Identification questions
focus on indicators of compromise: infected hosts, compromised accounts, malicious domains, and command-and-control servers.
Timeline questions
focus on attack progression: what steps did the attacker take, in what order, and when.
Remediation questions
focus on defensive actions: what steps should be taken to contain the incident and prevent further damage. All question types use the same retrieval and prompting pipeline, with the LLM adapting its response format based on the question framing.

Multi-LLM Support.

Following design principle number 4, the system abstracts LLM interactions behind a common interface, allowing different providers to be substituted without modifying the analysis pipeline. Currently supported providers include Anthropic, OpenAI, and DeepSeek as cloud APIs, and Llama and Cisco as locally-deployed options.

Output Generation.

The system produces a structured incident report containing findings for each security question, with responses that include specific evidence (IP addresses, hostnames, timestamps) and attribute findings to source files (Appendix
E
). A summary section follows, condensing the findings into a brief overview: attack type, key indicators, and recommended actions. The report concludes with metadata for reproducibility: the LLM provider, the number of chunks analyzed, the retrieval settings, and the timing information.

Experimental Overview

Research Questions.
We explore the following questions:

RQ1 (Feasibility):

Can a RAG-based system achieve acceptable performance on security incident analysis?

RQ2 (Provider Comparison):

How do different LLM providers compare in performance, latency, and cost?

RQ3 (Context Sensitivity):

How does the number of retrieved chunks

Evaluation Metrics.

We evaluate against reference sets derived from published scenario solutions and manual log analysis. Let
R
denote the reference set and
A
denote the model’s answer set. We compute:

\text{Precision}=\frac{|A\cap R|}{|A|},\quad\text{Recall}=\frac{|A\cap R|}{|R|}

For single-value questions (e.g., infected host IP), precision equals recall and scoring is binary. For set-valued questions (e.g., C2 indicators), models receive partial credit proportional to the fraction of reference indicators found.

The malware evaluation primarily reports recall, as the reference answers capture
confirmed
malicious indicators from published solutions rather than an exhaustive enumeration of all suspicious activity. Reference answers were validated by two analysts who independently reviewed the raw data using Wireshark and the Security Onion Kibana dashboard.
Models may identify additional indicators (Appendix
I
) that are legitimately suspicious but absent from the reference set. Appendix
H
provides detailed precision-recall breakdowns showing that several reported indicators not in the reference set exhibit genuinely suspicious characteristics.
The AD evaluation reports both precision and recall, as its reference timeline was manually extracted through exhaustive log review and cross-checked by two analysts.

7.
Active Directory Attack Analysis

Data.
The attack data originates from a controlled red team exercise against an Active Directory environment. The scenario simulates a sophisticated attacker (Red) attempting to compromise a Windows domain while defenders (Blue) respond in real-time.

Red Team Actions:
Initial compromise via Metasploit, certificate request with Administrator SAN, certificate enumeration, Kerberos TGT and service ticket requests, PSExec lateral movement to Domain Controller, malicious user creation, and ultimately SSH access to SCADA with service disruption (attack objective).

Blue Team Actions:
Certificate revocation, KRBTGT reset, Domain Controller restart, password reset, and user account disable. With defensive response, Blue successfully prevented SCADA compromise.

Evaluation.

Unlike the malware scenarios with discrete question-answer pairs, the AD evaluation uses the attack recreation task: given a timeframe, identify attack steps and recommend defensive actions. We evaluate on 5-minute sliding windows (15:30–15:35, 15:35–15:40, etc.), simulating real-time analysis. The reference attack steps in the timeline were manually extracted through exhaustive log review via the Security Onion Kibana dashboard, enabling evaluation of both precision and recall. Each data filtering query produces a compact result fitting in a single chunk; with 9 queries generating 9 chunks, all relevant context is retrieved simultaneously.

7.4.
Operational Feasibility

The system completes analysis in approximately 61 seconds per 5-minute window: 466ms for query execution (9 queries) and under 60 seconds for LLM analysis using locally-deployed Llama 3.1:70b. This represents 20% of the window duration, leaving time for analyst review and response actions before the next analysis cycle.

This AD scenario represents a fast-moving attack with core exploitation compressed into 60 seconds. The 5-minute window suited this pace, but attack timescales vary widely: ransomware may complete encryption in under 5 minutes, while APT campaigns spread lateral movement over days. Window size must be tuned to threat characteristics. More fundamentally, analysis latency should be measured against response latency rather than attack speed. Defensive actions may require several minutes to execute, and coordinated responses involve human decision-making and approval workflows that typically dominate total incident response time.
The system’s sub-minute analysis latency makes detection a small fraction of end-to-end response.

8.
Conclusion

We presented a retrieval-augmented generation system for security incident analysis that combines targeted query-based filtering with LLM semantic reasoning. Evaluation across eight LLM models on malware and Active Directory scenarios demonstrates that RAG preprocessing is essential (no-RAG baselines miss all attack infrastructure), provider selection dominates retrieval tuning, and DeepSeek V3 achieves Claude-equivalent accuracy (100% recall) at 15
\times
lower cost. Notably, security-specialized models (Cisco Foundation-Sec-8B) do not outperform general-purpose LLMs, suggesting that reasoning capability matters more than domain-specific pretraining for forensic analysis. Our system’s key capability is cross-event semantic reasoning: distinguishing coordinated exploitation from individually legitimate operations by correlating evidence across discrete forensic events.
Our evaluation covers four malware scenarios and one Active Directory attack; while results are consistent across these cases, validation on a broader set of attack types and larger-scale deployments remains future work.

These patterns illustrate a fundamental trade-off in LLM-assisted security analysis. DeepSeek optimizes for precision, reducing analyst workload by filtering noise but risking missed indicators if its filtering is overly aggressive. Appendix I
IcedID Dataset Complexity

Here we present some aspects that make the IcedID malware particularly challenging, and how our system uncovers attack indicators.

Multi-Host Environment with Mixed Traffic.

The capture contains traffic from three Windows hosts in an Active Directory environment, with only one confirmed compromise.
DESKTOP-SFF9LJF (10.4.19.136) follows the documented IcedID chain: Firebase-hosted installer, HTTP binary retrieval, persistent HTTPS C2 beaconing, and BackConnect activity.
Other hosts in the environment (including DESKTOP-RETP4BU at 10.4.19.138) generate background traffic that includes DNS queries and web requests unrelated to the IcedID infection.
This multi-host traffic creates analytical noise, as there is no structural boundary separating the infected host’s footprint from routine AD activity.

Volume as a Misleading Signal.

Domain join sequences and routine AD operations from uninfected hosts produce heavy Kerberos and LDAP bursts that are volumetrically louder than the infected host’s quieter but diagnostically significant IcedID C2 beaconing, making raw traffic volume an unreliable primary indicator in this capture.

Reference Set Scope.

The Unit 42 reference answers cover six IOCs for a single host.
During evaluation, our system surfaced additional indicators confirmed valid upon manual investigation:

•

Additional C2 domain.
Our system cited
spakernakurs.com
resolving to
104.168.53.18
, identical to
askamoshopsi.com
—and absent from the Unit 42 writeup. Manual lookup confirmed the domain resolves to shared IcedID infrastructure, consistent with a rotation or replacement C2 domain.

•

Beaconing regularity.
Our system’s classification of
skansnekssky.com
as persistent C2 activity prompted tshark verification, confirming
{\sim}
302-second intervals with sub-second jitter across 69+ sessions, a pattern unquantified in the reference answers.

Query Adaptation.

The IcedID installer delivery via Firebase Storage (
firebasestorage.googleapis.com
) required query modification: the standard
*googleapis.com*
exclusion for noise reduction would suppress the entire infection vector.
We replaced broad wildcards with surgical per-subdomain exclusions and added two aggregations: (1) direct-IP TLS connections, recovering BackConnect C2 at 193.149.176.100, and (2) HTTP requests to raw IP hosts, recovering the redirect server at 80.77.25.175.
This adaptation illustrates how attackers exploit common filtering heuristics and the need for dataset-aware query refinement.
