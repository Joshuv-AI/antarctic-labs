1 Introduction
 SPCA-ANL is a simulation tool used to perform deterministic analyses of sodium spray and
pool fires. Development of the SPCA-II (Spray Pool Combustion Analysis) code began in the mid-
1980s as part of the Clinch River Breeder Reactor (CRBR) Project. At that time, development of
SPCA-II [1], which was led by Rockwell International, was focused on treatment of large-scale
sodium spray, stream, and pool fires that were anticipated to be prototypic of the steam generator
building cells in CRBR. Under more recent DOE NE programmatic activities, the SPCA-II code
was recovered from existing literature and underwent minor modifications to generate a stable
executable. This recovered version of the code was not formally released. As part of the Versatile
Test Reactor (VTR) Project in the 2010s, the SPCA-II code underwent key modifications to
improve stability, address modeling deficiencies, improve consistency between the code manual
and software, and address numerous bugs. At this point, SPCA-II was renamed SPCA-ANL [2].
Given that SPCA-II served as the original basis for SPCA-ANL, both codes share an integrated
history. Following termination of the VTR Project, the DOE NE Fast Reactor Program resumed
support of the software with the goal of building and maintaining software infrastructure that can
enable commercial-grade dedication of SPCA-ANL by an end user. Version 1.0, the first external
release of SPCA-ANL, was released in June 2024, followed by code Version 1.0.1 which was
released in March 2025.
 This report summarizes the development and maintenance activities completed for SPCA-
ANL in FY26. This year’s work was focused on continuing to improve quality and usability of the
code to address users feedback and support commercial grade dedication of the code. The Software
Quality Assurance (SQA) program was formally implemented and is used to guide implementation
of infrastructure improvements, code development, bug fixes, and code releases, as described in
the following sections of this report. SPCA-ANL Version 1.1 was also released in FY26.

2 Current Repository and Supporting Infrastructure
 The SPCA-ANL source code is stored in a Subversion (SVN) [3] version control repository
that is integrated with Trac [4], a web-based software management tool that can be used to track
software issues and enhancements. The repository stores the main development line of the code
along with development branches and tags of previously released versions of the code. A Makefile
and a Visual Studio project file are both stored in the repository, providing two methods to compile
the source code into an executable using Intel Fortran. The input and output files for the test cases
described in Chapter 4 of the code manual [2] are also stored in the repository, as well as tools that
allow for automated execution and comparison of test case results with reference solutions. The
SVN/Trac system is also used to maintain the tickets system for code development.
 Since FY25, the code manual is also stored in the SPCA-ANL version control repository and
is being updated along with the code developments.

3 Code and Infrastructure Improvements
 The focus of the SPCA-ANL developments in FY26 was on continuing to improve the code
quality and usability by means of improving the code infrastructure, code developments to address
users feedback and support future commercial grade dedication, and finalizing the SQA program.
The infrastructure, code, and SQA developments in FY26 are described in the corresponding
subsections below.

3.1 Infrastructure Improvements
 The SPCA-ANL supporting infrastructure consists of SVN/TRAC, the acceptance test suite
and associated tools, and the code compilation tools. A robust infrastructure is needed to facilitate
efficient, collaborative code development under the SQA procedures.

3.1.1 Acceptance Test Suite Improvements
 In FY25, the acceptance test suite was migrated from a Makefile-based script to a more robust
Python tool. Previously, the Makefile used shell commands to run each test and compare its output
against reference solutions. The new Python-based framework was developed to support future
expansion of the test suite and to enable more advanced automated checks, including comparisons
against analytical solutions. The Python tool automatically discovers test cases throughout the
directory tree, eliminating the need to manually add new tests to the script. It also supports running
separate tools after each individual test and after the full test suite completes. This added flexibility
creates opportunities to expand the SPCA-ANL acceptance testing infrastructure with convenience
tools such as automatic reference-solution updates and code coverage reporting.
 In FY25, the example problem and its reference output were stored in two places within the
SVN repository: with the code manual and within the acceptance test suite. As a result, whenever
a code change affected the example problem output, the reference results had to be updated in both
locations, creating unnecessary work and increasing the risk of inconsistencies. In FY26, the
duplicate copy associated with the code manual was removed, and a new test suite distribution
script was developed to extract the example problem from the test suite into a separate folder for
release to users. The new distribution tool is organized around two easy-to-maintain lists of test
problems: those distributed with the code and those designated for the verification test suite, which
is anticipated to become a separately licensed set in the future. At present, only one test problem
is distributed with the code, and the verification test suite list is empty.

3.1.2 Code Compilation and Infrastructure Improvements
 Early in FY26, during code improvement efforts, it was observed that several test cases did not
produce fully consistent results across all supported platforms (Windows, Linux, and macOS),
especially when very small values were printed in the output files. To improve cross-platform
consistency, several compiler options were added to the code compilation Makefile.
 These options direct the compiler to use value-safe optimizations, preventing changes in the
order of operations and disabling optimizations such as altered division or square root evaluation
and fused multiply-add operations that round only once at the end. Although these optimizations
can improve performance, they may also introduce small numerical differences across platforms.
Because SPCA-ANL already runs very quickly, these performance gains are not valuable enough
to justify the loss of cross-platform consistency which is crucial to supporting multiple platforms.
Additional options were used to enforce evaluation precision based on the variable types declared

in the source code, rather than hardware-dependent defaults. The compiler was also configured to
use consistent math library functions across supported hardware platforms.
 Based on user feedback, additional information was added to the SPCA-ANL output file to
support quality assurance by making it easier to distinguish outputs from different runs and to
identify the executable and the platform that generated a given result. The following items were
added to the output file:
 • the executable filename (excluding the full path),
 • the date and time when the simulation begins and ends, and
 • the total elapsed simulation time.
 To make the executable name more useful in the output file, the code compilation Makefile
was also updated to assign platform-specific executable names, using suffixes such as “_Win”,
“_Linux”, and “_Mac”, along with the extensions “.exe” for Windows and “.x” for Linux and
macOS. This change also eliminates the need to rename executables when preparing a distribution
package and provides users with immediate information about the platform on which the case was
run. These quality assurance printouts in the output file are excluded from acceptance testing
comparison, to allow using same reference solution files across platforms and independent of when
the tests were run.

3.1.3 Code Coverage Analysis
 The code compilation Makefile was updated to add a target for building an instrumented
executable. This executable can be used when running test cases to collect the data needed for code
coverage analysis. In addition, new tools were integrated into the acceptance test suite to generate
code coverage reports for each individual test case as well as a cumulative report summarizing
coverage across the full set of executed tests.
 Intel’s code coverage tool reports coverage at three hierarchical levels: file, function, and
block. Files contain functions, and functions contain blocks of executable logic. The tool also
identifies specific lines of source code that were not executed by the test cases. Review of the
current test suite’s coverage results showed that three source files were completely unused by the
code, i.e., they were unreachable and never called because their functionality had been moved into
other routines. These files were removed, which simplified the source code and eliminated obsolete
duplicate functionality. It was confirmed that the results of acceptance testing were not affected
by the removal of the files. A high-level summary of the current test suite’s code coverage statistics
is provided in Table 3.1.

 Notably, the 96% file coverage in the first two sets in Table 3.1 is due to not using subroutine
CATCH1 for Q-deck fire suppression system in any of these tests. The remaining 8% of functions

implemented logic while also identifying clear opportunities for future test expansion. Detailed
review of the uncovered code blocks was not performed in FY26, but examples of uncovered
blocks included checks for negative sodium and oxygen masses (and adjusting burning rates to
avoid such conditions), exceeding a maximum number of droplet generations, checking for
negative flow areas, etc., i.e., guardrails that exit in the code but were not triggered in the existing
test cases. The infrastructure created to easily generate code coverage information allows for
further detailed review to be conducted in the future.

3.2 Software Improvements
 The code developments completed in FY26 were focused on addressing user feedback and
supporting the code infrastructure improvements described in the previous section. In addition,
work started in FY26 to provide support for commercial grade dedication of SPCA-ANL by a
vendor. Although that work was carried out outside of the Fast Reactor Program, and thus is not
included in this report, several issues with the code have been identified in that work. Since fixing
these code issues would benefit all code users, the code fixes implemented in FY26 are briefly
described in this report.
 All the code developments in FY26 were carried out in the Trac ticket system and followed
the SQA program described in Section 3.3.

3.2.1 Undeclared and Unused Variables
 To improve quality and repeatability of the code’s calculations, several changes were made in
how the variables are handled in the code. “IMPLICIT NONE” Fortran compile directive was
added to all code subroutines to require explicit declaration of all variables and function types. A
compiler option was added to check for unused variables, mostly to check for typos in variable
names. To check for undefined variables, a compiler option to initialize variables to zero was
removed. Without this option, it is now required to explicitly assign a value to each variable before
use.
 It was verified that no issues were observed with these code changes, and no errors or warnings
were generated during execution of the acceptance test suite. In this suite, all checks passed without
change in numerical results. It was also verified that the code successfully compiles and runs on
all supported platforms (Windows, Linux, and Mac) with the new compiler options and directives.

3.2.2 User Input Table Extrapolation
 Several changes were made to how the code handles input tables, such as sodium leak rate
versus time. A common function was created to handle interpolation and extrapolation of all tables.
In that function, a flat extrapolation was introduced, meaning that if a table value outside the input
range for time is requested, the function would return either the last table value (if time exceeds
the time inputs in the table) or the first value in the table (if time is less than the first time input).
 These changes were made for two main reasons. First, it ensures that no unexpected
extrapolation is obtained in using the tables, such as computing a negative value for a leak rate. If
all leak rate values in the input table are non-negative, the function will either interpolate between
these values or use the first or last non-negative values from the table. In all cases, the function
results will be either positive or zero. Second, this treatment eliminates a requirement that the table
cover the entire simulation period. Previously, if a table input was shorter than the simulation time,
an array bounds violation resulted in code crashes. Now, the last table value input will be used for
all times exceeding the last time input in a table.
 The user manual was updated accordingly to document that the input tables are linearly
interpolated between time points and flat-extrapolated outside the user-defined time range.
 In addition, a new global variable was introduced to define a common maximum size for all
input tables. This value is currently set to 25, as input tables in previous examples of SPCA-ANL
simulation have at most 5 entries.

3.2.3 Calculations at End of Simulation Time
 A small change was introduced to define how the code behaves at the end of the simulation.
Previously, the calculations continued until the next time the results are printed in the next user-
defined number of steps between printings. Now, if the time at the end of a time step is calculated
to exceed the input for the simulation time, the time step is adjusted (reduced) to match the
simulation time at the end of that time step. A limit on the time step size is introduced to avoid
calculations with a very small time step, which could lead to numerical issues in some rate
equations. When the simulation time is reached, the code results are always printed to the output
files.

3.2.4 Changes to Input and Output Files
 To improve the user’s experience of working with the code, several changes were implemented
in the input and output files.
 A feature was introduced in the code to allow the user to define the input file name and folder
location where the output files would be printed. These are optional features and if not used the
standard input file (Input.txt) will be used and the output files will be printed to the same directory
as the input file. If the user defines an input file name, all the output file names will be augmented
with the name of this input file, for example, Inp1_Output.txt main output file for Inp1.txt input
file.
 The input file formatting was extended to allow for comments and blank lines. The comment
lines are defined to start with the “#” symbol. This feature will be used, for example, to more
conveniently describe the variable name for each input and to separate the input into blocks.

 Several changes were introduced in the output files. First, several typos were fixed in the output
printouts, and changes were made to the output file to ensure consistency between all units in
outputs.
 Next, all variables that were printed in the main output file were added to the tabulated output
files. These variables include source and leak rate for aerosols, as well as heat sink, side wall, side
wall insulation, and Q-deck grating temperatures. These variables are now reported on each printed
time step. Accordingly, the main output file was modified to report the heat sink, side wall, and
side wall insulation temperatures at each printout, rather than a single printout at the end of
calculations.
 In another change, a new output variable, IVENT, was introduced to the output files to report
which venting models are activated during the code calculations, as several venting modes could
be active in parallel in the code. This variable also clarifies the state of small and large venting
models, where a transition between these modes is triggered by certain pressure flags in the code.
 Several changes were implemented for the additional output files. A new tabulated output file,
Output_O2.txt, is created to report local oxygen concentrations in each gas node. In the droplet
output file, Drop_Output.txt, unit conversion was implemented to be consistent with the user input
in OUTUNIT variable and other output files. For the droplet velocity output, VD_Output.txt, a
user requested printing frequency is applied as in other output files.
 The acceptance testing tool was modified to account for the changes described above to include
the new files and to compare the files with possibly different number of reported columns.
 The SPCA-ANL user manual was updated accordingly to describe all these changes. In
addition, the manual was updated to provide clearer explanation of some of the inputs and outputs,
as well as more detailed description of all output files. Also, installation and code run instructions
were included in the manual.

3.2.5 Oxygen Mass and Concentration Inconsistency
 A user reported an issue with code behavior where the sodium fire was stopped due to lack of
oxygen but there was still some oxygen mass remaining in the room. The issue was investigated
and was related to inconsistency between the local oxygen mass and the concentration in each
axial node, which are used for local sodium burning rates, and the global oxygen mass and
concentration, reported by the code. Several code changes were implemented to ensure that local
and global oxygen and gas masses are consistent, including how the node volumes are calculated
in steady-state initialization and how oxygen concentration in each node is calculated in the
transient. A mass balance check was added to the code to compare global oxygen and gas masses
with the sum of local node values. A warning is now displayed in the code when there is an
inconsistency in either oxygen or gas mass. No warning is currently displayed for all test suite
cases with the implemented changes.
 Because local oxygen concentrations affect spray and pool burning rates, modifications in
how local oxygen concentrations are calculated resulted in changing of, effectively, all the code
results. However, the inconsistency between local and global oxygen masses and concentrations
were relatively small in the original code, resulting in relatively small changes in the results for
the verification and validation (V&V) cases described in the SPCA-ANL manual. Nevertheless,
all V&V results in the manual, as well as the reference output files for the example problem, were
updated.

3.2.6 Aerosol Outputs
 Several changes were implemented to the outputs for aerosol variables. As described in Section
3.2.4, the aerosol source and leak rate results were added to the tabular output. With this change,
a unit conversion for the aerosol source was implemented according to the user input in OUTUNIT,
consistent with all other results. Although no unit conversion for the leak rate was needed, as this
result is displayed in 1/s units, an error was discovered and fixed in the internal unit conversion
for some for the variables used for leak rate calculations. None of these changes affect any of the
V&V results, as the aerosol results are only reported, but not used, by the code.

3.2.7 Code Bug Fixes
 Several issues in the code were identified and fixed during the code preparation for commercial
grade dedication by a vendor. The code fixes described in this section were discovered in
verification calculations, but were found not to affect the results of the V&V cases in the SPCA-
ANL manual.
 It was discovered that for the small vent model, when calculating what fraction of a vent is
located in each axial node, a wrong equation was used for the case when the vent window is located
fully within one node. In addition to fixing the issue, the calculations for the vent fractions were
moved from the transient part of the code to the steady-state initialization section. Because the
vent location never changes, calculating the fractions only once, instead of at each time step, saves
unnecessary computational effort. It was also confirmed that the rest of the vent fractions
calculations are correct for other possible window positions with regard to axial nodes.
 Another bug in the code was identified related to the oxygen mass between the Q-deck and the
catch pan in the fire suppression system. Even though the code equations rely on this mass to
calculate the pool burning rate, the manual was written under an assumption that the corresponding
variable meaning is oxygen mass consumed, rather than mass remaining, below the Q-deck.
Correspondingly, this variable was initialized to zero, rather than the actual oxygen mass. It was
confirmed that after fixing the issue, sodium burning in the pool below the Q-deck is sustained
until all oxygen is consumed.
 It was discovered that for the heat transfer in the first node of both the wall and ceiling, the
wall/ceiling liner thermal conductivity was used, even if this optional liner is not present. The code
was fixed to use liner conductivity only if there is a liner, and use concrete conductivity if there is
no liner in that node.

3.3 Formal Implementation of SQA Program
 Given the long-term goal of this work to develop an infrastructure for SPCA-ANL that enables
commercial grade dedication of the code by an end user, efforts continued this fiscal year to mature
an SQA Program that would align with the aforementioned goal. The key activity in this area in
this year focused on formal implementation of the provisional SQA Program that was developed
in the prior year. To that end, as part of the formal implementation, the SQA Program
documentation was formally reviewed by the Division QA Representative and associated Lab-
level QA personnel for consistency, accuracy, and compliance with Lab-wide requirements. Minor
changes, mainly related to editorial clarifications or revisioning of related references, were
requested as part of this review process and were implemented accordingly. The SPCA-ANL SQA
Program was formally implemented in January 2026.

4 Latest Release
 On February 4, 2026, SPCA-ANL Version 1.1 was released. The code changes since the
previous release (Version 1.0.1), are described either earlier in this report or in the previous year
report [8], and are summarized here:
 • Code functionality
 ▪ Implemented code version specification in the code and in the input file. Code
 version is now required on the first line of the input file and should match the
 internal code version.
 • Code improvements
 ▪ Required declaration of all variables and implemented a check for unused variables.
 ▪ Modifications were introduced in how input tables are used. The tables are more
 accurately interpolated between the time points. Also, flat table extrapolation was
 introduced to use either the first or last input outside the table range.
 ▪ The code calculations are now stopped when total time in FINTME input is
 reached.
 ▪ Cross-platform compiler consistency was improved by more strict rules on floating
 point operations.
 ▪ Modifications were made to the code manual to reflect changes described in this
 report and other identified issues. The manual now includes directions on how to
 use the code, as well as description of all output files. Also, typos in the output file
 were fixed.
 • Bug fixes
 ▪ Reinstated the user input for cell volume variable VCELL. In previous versions,
 VCELL was overwritten by the code with CHT*CAREA. That calculation is now
 included as an option, if the user specifies VCELL=0, otherwise the user input for
 VCELL is retained independently of CHT and CAREA.
 ▪ Inconsistencies in internal calculations of local (by node) and global calculations
 of oxygen content and mass were identified and fixed.
 ▪ An error in unit conversions for the aerosol generation printout was fixed. Also, the
 aerosol source printout was modified to be consistent with user-selected output
 units.

 Other code changes and improvements described in this report, but not listed here, will be
included in the next release.

5 Summary and Path Forward
 The FY26 work on development of SPCA-ANL was focused on continuing to improve quality
and usability of the code, continuing to collect and address user feedback, and preparation for
commercial grade dedication of the code. The improvements to the SPCA-ANL supporting
infrastructure included migrating the acceptance testing tool to Python, creating a tool for
generating the distribution test suite, improvements in code compilation flags to ensure consistency
across platforms, and adding quality assurance stamps to the output file. In addition, a code
coverage tool was developed, and the coverage reports were generated and analyzed, resulting,
among other results, in deleting duplicate and obsolete subroutines. Implemented software
improvements include a requirement for type declaration for all variables and functions,
modifications to the interpolation and extrapolation of the input tables, more accurate handling of
the approach of ending the simulation time, and changes in the input and output files to enhance
user’s experience. Additionally, several code bugs identified in parallel work on verification
testing for commercial grade dedication were fixed. The code manual was updated according to
the implemented code changes and to include instructions on code installation and use. The
Software Quality Assurance (SQA) program has been formally implemented and is now used to
guide infrastructure improvements, code developments, bug fixes, and code releases.
 SPCA-ANL Version 1.1 was released in FY26, with the main improvement over the previous
release (Version 1.0.1) being the requirement that the input file specifies and matches the code
version of the executable file. The release also includes recent improvements in the code and
infrastructure, as described in this report, in addition to some changes implemented in FY25 work.
 Future activities will include continuing implementation of code and infrastructure updates
identified in previous years, including feedback from external code users. There will also be an
increased focus on implementing the code and infrastructure changes required to support
commercial grade dedication of SPCA-ANL. Some of these future needs are already documented
and planned in corresponding tickets that were created in the Trac system for future
implementation. All the code developments will continue to be done according to the implemented
SQA program.
