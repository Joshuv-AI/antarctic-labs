Space-Efficient Lock-Free Linear-Probing Hash Table
Hagit Attiya, Rotem Oshman, Noa Schiller

Abstract
Linear probing is one of the simplest and most space-efficient approaches to hash table design, and is widely used in sequential settings due to its compact memory layout. However, designing a concurrent linear-probing hash table with strong liveness guarantees has proved difficult, and only a handful of such algorithms have been proposed, all of which either restrict concurrency or rely on large per-entry metadata, thereby compromising space efficiency. We present a lock-free linear-probing hash table with wait-free lookups that retains the core advantages of sequential linear probing while handling contention gracefully. Our design uses only a small amount of metadata per table entry: a constant number of additional bits when using 𝖫𝖫 / 𝖲𝖢 \mathsf{LL}/\mathsf{SC} , or a logarithmic number of bits when using 𝖢𝖠𝖲 \mathsf{CAS} . The algorithm is linearizable and lock-free, supports insert, delete, and wait-free lookup operations, and is able to safely reclaim space used by deleted elements without rebuilding the table. We analyze the amortized step complexity of our hash table assuming no concurrent insertions of the same key, and show that each operation has expected amortized step complexity matching that of sequential linear probing, up to the point contention per key.

Introduction

Linear probing
is an approach to hash table design
where the table consists of a contiguous array of memory cells,
and each key
v
is stored either in its hash location
h(v)

or, if this location is taken,
in the first free cell following
h(v)
.
To search for key
v
, we start at location
h(v)

and scan forward, until we either find
v

or we reach an empty cell.
This simple design avoids pointer indirection and benefits from contiguous memory layout.
When the parameters are tuned properly, a typical operation may access only a single cache line.

While there is a vast literature on
sequential
linear probing hash tables, only a few
concurrent
hash tables are based on linear probing
[
18
,
7
,
3
,
6
,
14
]
,
or indeed, on any form of
open addressing
,
where the hash table is one contiguous array, and any key can be stored in any memory location, so that the hash table is “full” only when the entire array is full.
This may be due to the fact that implementing a lock-free linear-probing hash table in the concurrent setting is much more challenging than in the sequential setting.
To our knowledge, virtually all concurrent hash tables proposed so far either use pointers and indirection (e.g.,
[
8
,
19
,
15
,
17
]
),
rely on locks to coordinate concurrent relocation of keys (e.g.,
[
9
]
),
limit concurrency (e.g.,
[
20
]
),
require frequent rebuilding (e.g.,
[
7
,
14
]
),
and/or use heavyweight concurrency control mechanisms that make them space-inefficient (e.g.,
[
18
]
).

Much of the appeal of linear probing comes from its compact, contiguous memory layout:
accessing the hash table requires no indirection and exploits the structure of modern memory hierarchies.
Storing large descriptors, timestamps, or auxiliary pointers in each cell undermines these advantages by increasing space usage and memory traffic.
In this paper we present the first lock-free linear-probing hash table that
uses
bounded per-cell metadata
,
and safely reuses memory previously used by deleted elements.
Our hash table enjoys nearly all the benefits of sequential linear probing while handling contention gracefully,
and we prove that its expected amortized step complexity nearly matches that of
sequential
linear probing.

We give two versions of our hash table:
one using the
\mathsf{LL}/\mathsf{SC}
synchronization primitive
and constant metadata per hash table cell,
and one using
\mathsf{CAS}
and logarithmic metadata per cell.
Let
U
be the size of the key domain,

n
be the number of processes,
and
m
be the size of the hash table (i.e., the maximum number of keys that may be in the dictionary simultaneously);
our main result is the following:

Theorem 1
.

There is a lock-free linearizable concurrent linear-probing hash table
with wait-free
\mathsf{lookup}
s,
where each memory cell stores

\lceil\log U\rceil+O(1)
bits when using the
\mathsf{LL}/\mathsf{SC}
primitive; or

\lceil\log U\rceil+\min\{\lceil\log m\rceil,\lceil\log n\rceil\}+O(1)
bits when using the
\mathsf{CAS}
primitive.

We analyze the expected amortized runtime of operations in our hash table when there are no concurrent insertions of the same key.
This assumption is used only to simplify the runtime analysis, and is not needed for linearizability or lock-freedom.
We show that in any execution that includes at most
(1-1/x)m
insertions, with no two insertions of the same key overlapping in time and at most
c
operations on any given key overlapping in time, the expected amortized runtime of each operation is
O(x^{2}+c)
.
This matches the classical analysis of linear probing due to Knuth
[
12
]
, up to an additive
point contention
term of
c
.

To our knowledge, ours is the first lock-free linear-probing hash table that uses bounded memory cells and does not require rebuilding the table,
as long as the number of
cells occupied by keys
does not exceed the size of the table.
Concurrent insertions of the same key may temporarily take up space in the hash table, but this space is made available for reuse immediately upon the return of the redundant insert operations.

Using tombstones in concurrent linear-probing hash tables.

A key design choice in implementing a linear-probing hash table is how to handle deletions.
One option is to shift elements to fill the resulting hole; however, shifting is difficult to implement correctly under concurrency, and synchronizing it often requires substantial metadata
(for example, in
[
3
]
).
Another option is to use
tombstones
,
a special symbol that marks
cells previously occupied by a deleted element,
so that lookups continue traversing past them.
However, tombstones may accumulate and degrade performance unless the table is periodically rebuilt (as in, e.g.,
[
7
,
14
]
).

Our hash table uses tombstones, but it allows inserts to
reuse
tombstones, effectively treating them as empty cells where new keys can be inserted.
This introduces a new challenge: concurrent inserts of the same key may observe different tombstones and temporarily create multiple copies of the same key in the table (we give an example of this in Figure
2

below).
Our main algorithmic contribution is a mechanism that resolves such conflicts using only bounded metadata per cell.

In our hash table,
operations perform steps only “on their own behalf” and do not attempt to help other operations to complete.
Rather than ensuring that other inserts of the same key complete,
operations are allowed to withdraw and return before ascertaining which copy is the “final winner”.
This helps us avoid large metadata, but it requires delicate synchronization between concurrent operations on the same key.
For example,
a challenging aspect of our design is that an ultimately
unsuccessful
insert operation may force the key to be treated as present by subsequent operations, even though there has not been a successful insert yet.
The linearizability proof addresses this challenge by introducing the notion of

insert sequences
, defined as chains of insert operations where the tentative copy of one operation is eliminated by the next in the sequence.
The final copy in the sequence is successful (i.e., returns
true
).
Even with this notion in hand, ordering insert operations is subtle,
because there can be several insert sequences
on the same key
that overlap in time.
In particular,
unsuccessful
insert operations are not necessarily ordered after the “final winner” in their own insert sequence.

Purcell and Harris
[

present one of the earliest
lock-free open-addressing hash tables.
Their algorithm uses quadratic probing and, instead of marking deletions with tombstones, stores an upper bound on the probe length at each cell.
Their use of quadratic probing appears orthogonal to the synchronization mechanisms used to manage duplicate copies.

Like ours, the algorithm of
[
18
]
allows multiple copies of the same key to coexist
temporarily; however,
it resolves conflicts using helping together with rich
per-cell metadata.
Duplicate copies are eliminated dynamically based on probe order:
when an insertion encounters an earlier copy, it withdraws its own
copy and helps complete the earlier one.
As a result, insert operations return only after ensuring that some copy has been finalized.
This helping mechanism relies on unbounded timestamps to avoid the
ABA problem.

Removing timestamps completely from the hash table of
[
18
]
appears difficult
due to the requirements of the helping mechanism.
In particular, because
helping may require tracking and finalizing
multiple
tentative
copies simultaneously,
a naïve attempt to replace timestamps by
\mathsf{LL}/\mathsf{SC}
would result in

improperly-paired

\mathsf{LL}/\mathsf{SC}
reservations,
where several
\mathsf{LL}
reservations are simultaneously pending.
This is incompatible with current architectures that
allow only one active
\mathsf{LL}
reservation at a time
.
(For example, the ARM architecture explicitly prohibits mismatched addresses between its
\mathsf{LL}/\mathsf{SC}
equivalents,
and violating this results in unpredictable behavior
[
2
, Section B2.12.5]
.)
One might also think of using process identifiers to help manage the ABA problem instead of using timestamps,
but this makes it difficult to distinguish between old and new copies created by the same process.

In other lock-free open-addressing implementations that use tombstones to
mark deletions
[
7
,
14
]
,
tombstones are not reused (or are reused only for the same key), preventing duplicate copies from arising during
overlapping insertions of the same key.
This restriction simplifies synchronization and eliminates the need for per-entry metadata, but causes tombstones to accumulate over time, increasing table occupancy beyond the number of stored keys and requiring periodic rebuilding.
Our construction is the first lock-free linear-probing hash table to combine tombstone reuse with bounded per-cell metadata.
We believe that the dynamic resizing mechanism integrated in these concurrent open-addressing hash tables can be used with our hash table.

As mentioned in Section
1
,
the alternative to tombstones is to shift keys backwards
to take up the space freed up by deleted keys.
Concurrent linear probing with backward-shift deletion is significantly harder
as it requires updating multiple cells in the hash table.
In
[
3
]
, a concurrent Robin Hood hash table
uses improperly-paired
\mathsf{LL}/\mathsf{SC}
to emulate two-word synchronization primitives; this hash table also stores two keys in each cell,
halving its capacity.
Shun and Blelloch
[
20
]
implement backward-shift deletion in the

phase-concurrent
setting, where inserts and deletes are
not allowed
to overlap.

While a
\mathsf{CAS}
-based version of our hash table
can be obtained by using a general-purpose simulation
to replace
\mathsf{LL}/\mathsf{SC}
by
\mathsf{CAS}
,
this would incur high memory overhead:
these simulations either increase the size of each memory cell
by at least
n
bits
[
16
,
10
]
,
or utilize auxiliary memory arrays, thereby reducing data locality
[
5
,
1
,
11
]
.
In contrast,
the
\mathsf{CAS}
-based version of our hash table requires
only
\lceil\log n\rceil
additional bits per cell compared to the
\mathsf{LL}/\mathsf{SC}
version.

3
Preliminaries

We use the standard asynchronous shared memory model, in which
n
processes communicate through shared
memory cells
.
The shared memory is accessed by executing
primitive operations
.
The
\mathsf{LL}
/
\mathsf{SC}
primitive supports the following operations:

\mathsf{LL}(x)
returns the value stored in
memory cell
x
, and
\mathsf{SC}(x,\mathit{new})
writes the value
\mathit{new}
to
x
,
if it was not written since the
last time the process performed an
\mathsf{LL}(x)
operation (otherwise,
x
is not modified).
\mathsf{SC}
returns
true
if it writes successfully, and
false
otherwise.

\mathsf{LL}/\mathsf{SC}
operations should be
properly-paired
:
an
\mathsf{LL}(x)
is eventually followed by
\mathsf{SC}(x,\_)
on the same memory cell
x
, without an intervening
\mathsf{LL}
or
\mathsf{SC}
to a different memory cell.
The
\mathsf{CAS}
primitive supports the operation
\mathsf{CAS}(x,\mathit{old},\mathit{new})
,
which atomically checks if the current value of the memory cell
x
is
\mathit{old}
, and if so, replaces it by
\mathit{new}
and returns
true
;
otherwise, the operation leaves the value unchanged,
and returns
false
.
Memory cells also support read operations.

An implementation of an abstract data type specifies,
for each process, a program for each operation;
when receiving an
invocation
of an operation,
the process takes
steps
according to its program.
Each step by a process consists of some local computation,
followed by a single primitive operation on the shared memory.
The process may change its local state after a step, and it
may return a
response
to the operation.

A
configuration

C
specifies the state of every process and every memory cell.
An
execution

\alpha
is an alternating (finite or infinite) sequence of configurations and steps, starting with a configuration.
Operation
o_{1}

precedes
operation
o_{2}
in
\alpha
, if
o_{1}
’s response precedes
o_{2}
’s invocation in
\alpha
; in this case, we also say
that
o_{2}

follows

o_{1}
.

An execution
\alpha
induces a
history

H(\alpha)
,
consisting only of the invocations and responses of higher-level operations.
An invocation
matches
a response if they both belong to the same operation.
An operation
completes
in
H

if
H
includes both the invocation and response of the operation;
if
H
includes the invocation of an operation, but no matching response,
then the operation is
pending
.
A history
H
is
sequential
if every invocation is immediately
followed by a matching response.

A
completion
of history
H
is a history
H^{\prime}
whose prefix
is identical to
H
, and whose suffix includes zero or more responses
of pending operations in
H
.
Let
\mathrm{comp}(H)
be the set of all of
H
’s completions.
A sequential history
H^{\prime}
is a
linearization
of an execution
\alpha
if (1)
H^{\prime}
is a permutation of a history in
\mathrm{comp}(H(\alpha))
, (2)
H^{\prime}
matches the sequential specification of the implemented object, and (3)
H^{\prime}
respects the real-time order of non-overlapping operations in
H(\alpha)
.
An execution
\alpha
is
linearizable
if it has a linearization,
and an implementation of an abstract object is linearizable
if all of its executions are linearizable.

An implementation is
lock-free
if whenever there is a pending operation,
some operation returns in a finite number of steps of all processes; it is
wait-free
if whenever there is a pending operation by process
p
,
this operation returns in a finite number of steps by
p
.

4
The Hash Table Construction

A hash table implements a
dictionary
,
which represents an unordered set of elements,
and supports the operations

\mathsf{insert}(v)
,
\mathsf{delete}(v)
and
\mathsf{lookup}(v)
.
Each operation takes a
key

v
and returns
true
or
false
:

\mathsf{lookup}(v)
and
\mathsf{delete}(v)
return
true

if
v
is in the set,
while
\mathsf{insert}(v)
returns
true
if
v
is not in the set.
An
\mathsf{insert}
may return a special value,
\mathsf{ABORT}
, indicating that no available slot was found to insert the key (i.e., the hash table is “full”).
Aborts are expected to be a rare event and they should trigger a rebuild of the hash table using standard techniques, which we do not treat here
(see Section
4.3
for further discussion).

\mathsf{ABORT}
s do not affect the logical state of the hash table;
in terms of the sequential semantics, we model them by allowing
\mathsf{insert}
operations to nondeterministically return
\mathsf{ABORT}
at any point, without modifying the table.

4.1
High-Level Overview

The main challenge in a concurrent linear-probing hash table that reuses tombstones
is handling overlapping insertions of the same key,
because such insertions may temporarily create multiple copies of the key in the table.
We must handle these copies in a way that ensures that

exactly one copy
eventually survives (barring deletion of the key).

The key invariant underlying the algorithm is that surviving copies of a key
can move only toward earlier positions in the probe sequence beginning at
h(v)
.
Intuitively, among multiple copies of a key
v
,
copies that are closer to
h(v)
have priority over later copies.
This probe-order priority prevents cycles of competing eliminations.
A similar approach was taken in
[
18
]
,
but here we avoid helping and large metadata.

To realize the invariant,
an insert operation first places a
tentative copy
of the key in the table.
Tentative copies may subsequently be finalized, withdrawn, or eliminated by competing operations.
Operations searching for the key treat tentative copies as logically present,
even before the surviving copy is determined.
This behavior is essential for linearizability, and is formalized later using the notion of
insert sequences
(see Section
5.2.2
).

We focus first on the version of the algorithm that uses the
\mathsf{LL}/\mathsf{SC}
primitive,
in which each memory cell stores a key together with only a constant number of tag bits.
At the end of Section
4.2
we show how to modify the hash table to use
\mathsf{CAS}
, by storing an index of a cell or a process within each cell (an additional
O(\min(\log m,\log n))
bits).

Using metadata to handle duplicates.

We use constant-size metadata to manage the competition between overlapping
\mathsf{insert}
s, as well as the interaction with concurrent
\mathsf{delete}
and
\mathsf{lookup}
operations on the same key.
A key
v
is first inserted into the table as a
tentative copy
,

\langle v,\mathsf{tentative}\rangle
.
The tentative copy reserves the cell for the inserting operation, although other operations may still modify the metadata in the cell in order to communicate with the inserting process.
There are several ways the insertion can proceed from here (see Figure

Validating a tentative copy by checking for duplicates.

After writing a tentative copy of its key into some location
i
, an
\mathsf{insert}
operation re-scans from location
h(v)
to the end of the run
(the maximal contiguous sequence of non-
\mathsf{EMPTY}
cells starting from
h(v)
),
searching for other copies of
v
.
If a competing copy of
v
is found
before
location
i
(i.e., between
h(v)
and
i
),
then the other copy “wins”, and the insert operation attempts to withdraw its tentative copy and convert it into a tombstone.
This may fail if another process signals that it has seen the tentative copy, causing the operation to restart the validation process.
If a competing tentative copy of
v
is found in some location
j

after
location
i
,
then the copy in the earlier location
i<j
“wins”, and the inserting process
eliminates
the copy in location
j
by writing
\mathsf{COLLIDED}
into location
j
(see more on this process below).
This, too, may fail — if the copy in location
j
is already finalized before the value
\mathsf{COLLIDED}
can be written, then location
j
becomes the final copy,
and the
\mathsf{insert}
operation for location
i
will give up and try to delete its own tentative copy.

Although we refer to them as
tentative copies
,
if there is a tentative copy of key
v
in the table,
all later operations must behave as though
v
is logically present in the table.
The “tentative” aspect is only regarding
which copy will win
, not regarding
whether
v
is inserted
.

Because each tentative copy can only (try to) eliminate other tentative copies that precede it in the hash table,
a chain of attempted inserts of the same key
v
that eliminate each other goes

backwards
through the hash table, towards location
h(v)
.
We refer to such chains as
insert sequences
,
and the fact that surviving copies can only move “up the table” towards
h(v)
is crucial to the correctness of the algorithm.

Safely eliminating tentative copies.

A critical part of the algorithm is the safe elimination of later tentative copies of the same key.
Before eliminating another copy of
v
,
an
\mathsf{insert}(v)
operation must ensure that its own
tentative copy has not been concurrently deleted:
without this check, an
\mathsf{insert}
that already “lost” (i.e., been deleted by a concurrent
\mathsf{delete}(v)
operation,
or had its copy eliminated by a concurrent
\mathsf{insert}(v)
)
could erroneously eliminate
tentative copies belonging to future insertions that began after it had already lost.
This could lead to
no copies of
v
surviving
, even though “logically”,
v
has been re-inserted into the table after being deleted.

Why revalidation is required.

As we said above, a
\mathsf{lookup}(v)
or
\mathsf{insert}(v)
operation that encounters a tentative copy of
v

will signal the inserting operation to revalidate, i.e., stop withdrawing the copy if it is currently doing so, and check again for duplicates.
Subsequently, the
\mathsf{lookup}
or
\mathsf{insert}
operation treats the tentative copy of
v
as though it were finalized —
\mathsf{lookup}(v)
returns
true
, and
\mathsf{insert}(v)
returns
false
.

Requesting revalidation is necessary because the
\mathsf{lookup}
or
\mathsf{insert}

i
,
but then found another tentative copy in location
h(v)<j<i

i

Before

can write a tombstone to location

the preceding copy of
v
in location

Then a
\mathsf{lookup}(v)
or
\mathsf{insert}(v)

and finds the copy of

Operation

is about to finalize its copy or withdraw it, and does not wait around to see;
instead, it treats the key as though it is bound to be finalized, and signals to
I
that it has done so by requesting revalidation.
This “resurrects” the key in location
i
and causes
I
to resume trying to finalize it.

Detailed Description

We now describe how these ideas are realized in the code.
We provide two versions of the algorithm.
The first uses the
\mathsf{LL}
/
\mathsf{SC}
primitive to safely verify and delete tentative copies.
The second uses the more common
\mathsf{CAS}
primitive,
emulating the required behavior with a small amount of additional
per-cell metadata. Both implementations have the same high-level structure, and we encapsulate the use of the two different synchronization primitives by using a few primitive-specific functions (Algorithm

/
\mathsf{SC}

\mathsf{Modify}
in the code.
When using

/
\mathsf{SC}

the keyword

and
\mathsf{Modify}

in the

and
\mathsf{Modify}

We use modular arithmetic that wraps at the

Data structures.

The table is a single array

or one of a few internal cleanup states

\mathsf{CAS}

these values can be encoded using

\mathsf{LL}
/
\mathsf{SC}

In the code, the function

Searching for a key.

All operations begin by

First, operations execute a

which begins at location

\mathsf{EMPTY}

If the key was not found during the forward scan,

Since a sequence of tentative copies that eliminate one another moves back through the table towards location

a backward scan ensures that at least one of these copies is eventually encountered, provided at least one remains in the table.

At any point during the forward and the backward scan, if key

\mathsf{insert}(v)

We remark that “finding key

if the copy that is found is not finalized (i.e., not

\mathsf{insert}(v)

Operations

\mathsf{lookup}(v)

At the end of the backward scan, upon returning to location

or
\mathsf{TOMBSTONE}

4.3
Insert Operations that Return
\mathsf{ABORT}

An
\mathsf{insert}
operation that returns
\mathsf{ABORT}
(in line
3
of Algorithm
3
)
has no effect on the abstract state of the dictionary.
Inserts only abort if they complete
a full scan of the hash table without finding an available cell (either
\mathsf{EMPTY}
or
\mathsf{TOMBSTONE}
).

An
\mathsf{insert}
that aborts
does not necessarily imply that the table is “logically full”.
This is because
\mathsf{insert}
operations of the same keys may temporarily take up space in the table by creating duplicate copies (which will be eliminated prior to their return), or concurrent
\mathsf{delete}
operations may clear up space during the scan.
However,
\mathsf{insert}
operations do not abort spuriously when space
is available:
if an
\mathsf{insert}(v)
operation starts running when the table
has free space, and the table does not already contain key
v
,
then some available cell must be used up by a key before the
\mathsf{insert}
completes.
This is formalized in the next proposition:

Proposition 2
.

If an
\mathsf{insert}(v)
operation is invoked at a configuration in which
at least one cell in the table is empty or contains a tombstone,
and no cell contains the key
v
,
then some available cell in the table is reclaimed by a key
before the operation returns.

In particular, if the table contains a tombstone or an empty cell,
then an
\mathsf{insert}
operation running solo from a quiescent configuration
will not abort.
Aborts suggest that
the hash table is full or nearly full.
Repeated
\mathsf{ABORT}
responses may therefore trigger a resize operation,
which can also be initiated preemptively before the table becomes full.

Correctness Proof

In this section, we prove that the hash table is linearizable and lock-free, and analyze its amortized runtime complexity.
Let
U
be the size of the key domain,

n
the number of processes,
and
m
the size of the hash table.

See
1

5.1
Basic Properties

We begin by showing that the linear-probing structure is preserved and that, among concurrent insertions of the same key, at most one copy can be fully inserted.
The proof abuses terminology and says that an operation performs a step
when the process executing it performs the step.

A cell is
non-empty
if it does not contain
\mathsf{EMPTY}
;
a cell contains the key
v
if its value is one of
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{final}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
.

We observe that our algorithm preserves the following key property of sequential linear probing.
This property implies that if a key is in the table, it will be found by scanning the table starting from the key’s initial hash position until either the key is found or an empty cell is encountered. Moreover, two copies of the same key are part of the same run.

Proposition 3
.

If a cell
i
contains the key
v
,
then all cells
j
,
h(v)\leq j\leq i
,
are not empty.

Our algorithm ensures that, at any point in the execution, at most one insert
operation can become the current
winner
,
i.e., the one whose copy may be promoted to
\langle v,\mathsf{final}\rangle

(formalized in Lemma
4
below).
This invariant yields a well-defined ordering of successful insert
and delete operations, whose linearization points are defined in
Section
5.2.1
.

Consider an
\mathsf{insert}(v)
operation
op
that writes
\langle v,\mathsf{tentative}\rangle

to a cell in the table.
This value can be overwritten with
\langle v,\mathsf{final}\rangle
,
\mathsf{DELETED}
,
\mathsf{COLLIDED}
,
\mathsf{TOMBSTONE}
or
\langle v,\mathsf{revalidate}\rangle
;
in the
\mathsf{CAS}
version it can also be overwritten with
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle

If it is overwritten with one of the first three values,
that value can be subsequently overwritten only with
\mathsf{TOMBSTONE}
.
If it is overwritten with
\langle v,\mathsf{revalidate}\rangle

or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle

\langle v,\mathsf{tentative}\rangle

Each value in the sequence
\langle v,\mathsf{tentative}\rangle

\langle v,\mathsf{revalidate}\rangle

op
.
The sequence cycles through these states with restricted transitions: while
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
may transition to either
\langle v,\mathsf{tentative}\rangle
or
\langle v,\mathsf{revalidate}\rangle
,
\langle v,\mathsf{revalidate}\rangle
is restricted to transition only back to
\langle v,\mathsf{tentative}\rangle
.
The cell in which the copies of
op
are written is called
op
’s cell.
A copy of
op
is
inserted
if it is overwritten with
\mathsf{DELETED}
or
\langle v,\mathsf{final}\rangle
.
If a copy is overwritten with
\langle v,\mathsf{final}\rangle
,
we call it the
inserted copy
of operation
op
.
A copy of
op
is
deleted
if it is overwritten with

\mathsf{DELETED}
,
\mathsf{COLLIDED}
or
\mathsf{TOMBSTONE}
,
or if the inserted copy of
op
is overwritten with
\mathsf{TOMBSTONE}
.
Note that only the last copy written by
op
can be inserted or deleted.

The next lemma formalizes a key invariant mentioned in Section
4.1
, namely, that among all simultaneous attempts to insert duplicate copies of
v
, only one can be successful.
Intuitively, this is because before succeeding, an insert scans
the probe sequence and observes that no copy closer to the start of the probe sequence exists.
In this scan, the insert ignores copies with the flag
\mathsf{revalidate}
or
\mathsf{marked}
.
It can do so as the other insert operation must first rewrite the copy with the flag
\mathsf{tentative}
and then scan the table, ensuring it will observe the current operation’s copy.

Lemma 4
.

At any point in the execution, for any key
v
,
at most one cell in the table contains
\langle v,\mathsf{final}\rangle
.

Proof.

Assume, by way of contradiction, that two cells

and
j
,
i\neq j
,
contain
\langle v,\mathsf{final}\rangle
at the same point in
\alpha
.
Let
op_{i}
and
op_{j}
be the
\mathsf{insert}(v)
operations that
write these
\langle v,\mathsf{final}\rangle
values to cells
i
and
j
, respectively.
Assume, without loss of generality, that
op_{i}
writes
\langle v,\mathsf{final}\rangle

to cell
i
before
op_{j}
writes
\langle v,\mathsf{final}\rangle
to cell
j
.

An
\mathsf{insert}
writes
\langle v,\mathsf{final}\rangle
to a cell only after it writes
\langle v,\mathsf{tentative}\rangle
to that cell.
Consider the last time
op_{i}
writes
\langle v,\mathsf{tentative}\rangle
to cell
i
,
and note that it then scans a run starting from

before writing
\langle v,\mathsf{final}\rangle
to cell
i
.
We next assume the run includes cell

and consider the possible values

reads from cell
j
.

First, assume that
op_{i}
reads
\langle v,\mathsf{tentative}\rangle
written by
op_{j}
from

.
If cell

is closer to the initial hash than cell

(that is,
j-\mathsf{h}(\mathit{v})<i-\mathsf{h}(\mathit{v})
),
then
op_{i}
deletes its own copy and never writes
\langle v,\mathsf{final}\rangle
to cell

.
Otherwise,
op_{i}
tries to delete the copy of
op_{j}
.
Regardless of whether
op_{i}
succeeds in deleting the copy,
the value in cell

changes.
Since

did not write
\langle v,\mathsf{final}\rangle
to cell

yet and is the first operation to write
\langle v,\mathsf{final}\rangle
among the two,
the value of cell

cannot change to
\langle v,\mathsf{final}\rangle
and may only change to
\mathsf{COLLIDED}
,
\mathsf{DELETED}
,
\langle v,\mathsf{revalidate}\rangle
, or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
.
The first two values are not possible,
since cell

is eventually overwritten with
\langle v,\mathsf{final}\rangle
.
Hence, either
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle

are written in cell

after
op_{i}
reads cell
j
.

Otherwise,
op_{i}
reads from cell
j

either
\langle v,\mathsf{revalidate}\rangle
copy of
op_{j}
,
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
copy of
op_{j}
,
or the first write of
\langle v,\mathsf{tentative}\rangle
to cell
j
by
op_{j}

follows the read of cell
j
by
op_{i}
.
In all cases, the last write of
\langle v,\mathsf{tentative}\rangle
to cell
j
by
op_{j}

(which exists since this last copy is overwritten with
\langle v,\mathsf{final}\rangle
)
follows
op_{i}
’s read of cell
j
.

If the run excludes cell
j
and
op_{i}
does not read cell
j
, by Proposition

, the first time
op_{j}
writes
\langle v,\mathsf{tentative}\rangle
to cell

follows the last time
op_{i}
writes
\langle v,\mathsf{tentative}\rangle
to cell
i
.

Regardless of whether
op_{i}
reads cell

or not,

reads cell

after the last time
op_{i}
writes
\langle v,\mathsf{tentative}\rangle
to cell
i
.
The last such read of cell

by

occurs after
op_{j}
writes
\langle v,\mathsf{tentative}\rangle
to cell

for the last time.
Since this is the last such write and

writes
\langle v,\mathsf{final}\rangle

to cell

\langle v,\mathsf{final}\rangle
.
This read returns either
\langle v,\mathsf{tentative}\rangle

or
\langle v,\mathsf{final}\rangle
written by

to cell

.
This is because

already performed its last write of
\langle v,\mathsf{tentative}\rangle
to cell

\langle v,\mathsf{final}\rangle
.
Furthermore, by our initial assumption, once

to cell

If

reads

,

Otherwise (

and deletes its own copy.
Since we assume that the read of cell

of

to cell

In all cases,

∎

5.2
Linearizability

Let
\alpha
be a finite execution.
An
\mathsf{insert}
operation may return
\mathsf{ABORT}
if it completes a full scan of the hash table and does not find an available cell.
We ignore
\mathsf{insert}
operations that return
\mathsf{ABORT}
, as they do not affect the sequential specification; thus, they can be linearized at any point, provided they respect the real-time order.

We construct the linearization
\pi_{v}
of the remaining

\mathsf{insert}
,
\mathsf{delete}
and
\mathsf{lookup}
operations in
\alpha
.
Let
H(\alpha)|_{v}
be the projection of the history
H(\alpha)
onto key
v
; that is, the subsequence of operations in
H(\alpha)
involving the input key
v
.
Our proof proceeds by constructing independent linearizations
\pi_{v}
of
H(\alpha)|_{v}
, for each key
v
.
This is sufficient since the locality theorem of linearizability
allows to obtain the linearization of the whole execution
by merging per-key linearizations while respecting real-time order.

For the rest of the linearizability proof, fix a key
v
.

By Lemma
4
,
at most one winner can fully insert its copy at any point in the execution.
Only after a fully-inserted copy is deleted, a new copy can be crowned the new winner.
This gives us a well-defined order for successful insert and delete operations.
When a delete operation deletes a partially inserted key,
a successful insert and delete happen simultaneously.
When there is also a fully inserted copy of the key at the same time,
we first place the delete and then the insert.
This ensures that the ordering ends with a successful insert at such a point.
Otherwise, the insert is placed before the delete.

Ordering unsuccessful insert and delete operations,
as well as lookup operations, is more challenging.
When a lookup or insert operation finds a partially inserted copy of the key,
there are three possibilities:
(a) the copy is eventually fully inserted,
(b) the copy will be deleted because of a later full insertion, or
(c) the copy will be deleted because of an earlier full insertion.
If the future successful insertion is not yet linearized,
there is a pending insert operation,
which we can treat as successful in the linearization.
Later, when the actual winner is determined,
the operation’s response is updated accordingly.

An operation
op
is a
mutator
if it is
either an
\mathsf{insert}(v)
operation whose copy is inserted,
or a
\mathsf{delete}(v)
operation that deletes a copy of some insert operation.
In the latter case, this means that
op
overwrites
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle

with
\mathsf{DELETED}
or
\langle v,\mathsf{final}\rangle
with
\mathsf{TOMBSTONE}
.
Let
\mathsf{mop}
be the set of all mutator operations
in
\alpha
with key
v
.

Note that a mutator operation does not necessarily complete in
\alpha
,
however, if it does, it returns
true
.
If an insert
(v)
observes a partial copy before a winner exists,
all later operations should treat
v
as present.
In the linearization, we let one ongoing insert serve as the successful insert,
even if it eventually returns
false
.
This captures the forced-success behavior of unsuccessful inserts described in
Section
4.1
.

We begin by ordering the mutator operations
(Section
5.2.1
).
Next (Section
5.2.2
), we introduce
insert sequences

and prove key properties that will be used (in Section
5.2.3
)
to place non-mutator operations in between mutator operations.

5.2.1
Ordering the Mutator Operations

We construct the permutation
\mu_{v}
of the mutator operations,
by assigning a
linearization point
to each mutator operation
op
, which is a step in
\alpha
,
between the invocation and the response of
op
.
Two mutator operations may be linearized at the same step, in which case they are ordered,
by marking them with
\left\{1,2\right\}
,
namely, which of them is first and which is second.

If
iop\in\mathsf{mop}
is an
\mathsf{insert}(v)
operation,
then a copy of
iop
is overwritten with
\langle v,\mathsf{final}\rangle
or
\mathsf{DELETED}
.
Let
\mathit{pt}
be the point in the execution where this overwrite happens.
If the copy of
iop
is overwritten with
\langle v,\mathsf{final}\rangle
,
we define
\mathit{lin}(iop)=\langle\mathit{pt},1\rangle
.
Otherwise, a copy of
iop
is overwritten with
\mathsf{DELETED}
.
If at
\mathit{pt}
there is a cell in the table containing
\langle v,\mathsf{final}\rangle
, we define
\mathit{lin}(iop)=\langle\mathit{pt},2\rangle
.
Otherwise, at
\mathit{pt}
no cell in the table contains
\langle v,\mathsf{final}\rangle
and we define
\mathit{lin}(iop)=\langle\mathit{pt},1\rangle
.

If
dop\in\mathsf{mop}
is a
\mathsf{delete}(v)
operation,
then
dop
overwrites
\langle v,\mathsf{final}\rangle
with
\mathsf{TOMBSTONE}
, or
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
with
\mathsf{DELETED}
.
Let
\mathit{pt}
be the point in the execution where this overwrite happens.
If
dop
overwrites
\langle v,\mathsf{final}\rangle
with
\mathsf{TOMBSTONE}
, we define
\mathit{lin}(dop)=\langle\mathit{pt},1\rangle
.
Otherwise,
dop
overwrites
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
, or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
with
\mathsf{DELETED}
.
If there is a cell in the table containing
\langle v,\mathsf{final}\rangle
at
\mathit{pt}
, we define
\mathit{lin}(dop)=\langle\mathit{pt},1\rangle
.
Otherwise, at
\mathit{pt}
no cell in the table contains
\langle v,\mathsf{final}\rangle
and we define
\mathit{lin}(dop)=\langle\mathit{pt},2\rangle
.

Note that at points where a copy is overwritten with
\mathsf{DELETED}
we linearize both an
\mathsf{insert}(v)
operation and a
\mathsf{delete}(v)
operation.
If during this overwrite there is a cell in the table containing
\langle v,\mathsf{final}\rangle
,
we linearize the delete first and then the insert.
Otherwise, we linearize them in reverse order,
first the insert then the delete.
This ensures that a key is considered to be in the table if and only if it is stored in a cell with the flag
\mathsf{final}
.
We formalize this invariant below in Lemma
5
.

We say that
\langle\mathit{pt}_{1},i_{1}\rangle

precedes

\langle\mathit{pt}_{2},i_{2}\rangle
if either
\mathit{pt}_{1}
precedes
\mathit{pt}_{2}
in
\alpha
, or
\mathit{pt}_{1}=\mathit{pt}_{2}
and
i_{1}<i_{2}
.
Let
\mu^{\prime}_{v}
be a permutation of the operations in
\mathsf{mop}
,
ordered such that
{op}_{1}
precedes
{op}_{2}
in
\mu^{\prime}_{v}

if and only if
\mathit{lin}({op}_{1})
precedes
\mathit{lin}({op}_{2})
.
All mutator operations, including those that did not return in
\alpha
,
are assigned the response
true
in
\mu^{\prime}_{v}
.

We next formalize the behavior described in Section
4.1
,
where an insert operation that observes a partial copy may force the key to be treated as present, even if no insert has yet completed.
We construct
\mu_{v}
by possibly extending
\mu^{\prime}_{v}
.
If at the end of
\alpha
:
(1) there is a cell in the table containing
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
,
(2)
\mu^{\prime}_{v}
does not end with an
\mathsf{insert}(v)
operation, and
(3) there is no mutator
\mathsf{insert}(v)
operation with a linearization point that occurs at the last step of
\alpha
, we append such an operation as follows.
Note that, by the code, the
\mathsf{insert}(v)
operation this copy belongs to is pending.
Among all pending
\mathsf{insert}(v)
operations that write
\langle v,\mathsf{tentative}\rangle
in
\alpha
,
let
op
be the one invoked the earliest.
We obtain
\mu_{v}
by appending
op
to
\mu^{\prime}_{v}
with response
true
.
Furthermore, we add
op
to
\mathsf{mop}
, and define its linearization point to be the last step in the execution.
If these conditions are not met, we simply define
\mu_{v}=\mu^{\prime}_{v}
.

Next, we show that, when ignoring the last insert possibly appended to
\mu_{v}
,

is logically in the table if and only if the table contains
\langle v,\mathsf{final}\rangle
.

Lemma 5
.

\mu^{\prime}_{v}
ends with
\mathsf{insert}(v)
if and only if
some cell contains
\langle v,\mathsf{final}\rangle
after
\alpha
.

Proof.

We prove the lemma by induction on the number of steps in an execution
prefix
\alpha^{\prime}

that
either overwrite
\langle v,\mathsf{tentative}\rangle
with
\langle v,\mathsf{final}\rangle
,
or overwrite
\langle v,\mathsf{final}\rangle
with
\mathsf{TOMBSTONE}
,
or overwrite
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
with
\mathsf{DELETED}
.
We note that this suffices since these

are the only steps that append an operation to
\mu^{\prime}_{v}
.
The base case, when no such steps appear in

, is trivial.

Assume the lemma holds for an execution prefix
\alpha^{\prime}
,
and consider the possible cases.

If
\langle v,\mathsf{tentative}\rangle
is overwritten with
\langle v,\mathsf{final}\rangle
,
then
\mathsf{insert}(v)
is appended to
\mu^{\prime}_{v}
.
Since
\langle v,\mathsf{final}\rangle
is written,
there is a cell containing
\langle v,\mathsf{final}\rangle
.

If
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
are overwritten with
\mathsf{DELETED}
,
then an
\mathsf{insert}(v)
and a

are appended to

.

\alpha^{\prime}
there is a cell containing
\langle v,\mathsf{final}\rangle
,

is appended first followed by
\mathsf{insert}(v)
.
Since the
\langle v,\mathsf{final}\rangle

until the next overwrite, a cell containing
\langle v,\mathsf{final}\rangle
remains.
If at the end of
\alpha^{\prime}
there is no cell containing
\langle v,\mathsf{final}\rangle
,

\mathsf{insert}(v)
is appended first and then
\mathsf{delete}(v)
.
Since no
\langle v,\mathsf{final}\rangle
value is written,
until the next overwrite, no cell contains
\langle v,\mathsf{final}\rangle
.

If
\langle v,\mathsf{final}\rangle
is overwritten with
\mathsf{TOMBSTONE}
,

\mathsf{delete}(v)
is appended to

.

\langle v,\mathsf{final}\rangle

and by Lemma

no other cell also contains

\langle v,\mathsf{final}\rangle
.

.

\mu_{v}
respects the sequential specification of a dictionary.

Proof.

Consider first

and assume by way of contradiction,
that it does not respect the sequential specification of a dictionary.

be the first operation in
\mu^{\prime}_{v}

that violates the sequential specification.
If

is an
\mathsf{insert}(v)
, then it appears after another
\mathsf{insert}(v)
.
If
op
is a
\mathsf{delete}(v)
, then it is not preceded by an
\mathsf{insert}(v)
.
Consider the overwrite in
\alpha
that determines the placement of

.

If a
\langle v,\mathsf{tentative}\rangle
is overwritten by
\langle v,\mathsf{final}\rangle
,
then
op
is an
\mathsf{insert}(v)
.
By Lemma

,
no cell contains
\langle v,\mathsf{final}\rangle
before this overwrite,
and by Lemma

,
\mu^{\prime}_{v}
constructed up until before

,

If a
\langle v,\mathsf{final}\rangle

\mathsf{TOMBSTONE}
,

.

,
\mu^{\prime}_{v}
constructed up until before this overwrite, ends with an

Finally, assume

.

5.2.2
Insert Sequences

A copy of an insert operation is either still present in the table, inserted, or is deleted because of a different copy of
v
.
This yields a sequence of insert operations where a copy of each operation is deleted due to the next one in the sequence;
the sequence ends when a copy of the final insert operation is successfully inserted.

A copy of an
\mathsf{insert}(v)
operation
op_{1}
is deleted because of an
\mathsf{insert}(v)
operation
op_{2}
, denoted
op_{2}~{\leadsto}_{\mathsf{del}}~op_{1}
,
if either (1)
op_{2}
overwrites a copy of
op_{1}
with
\mathsf{COLLIDED}
, or
(2)
op_{1}
overwrites its own copy with
\mathsf{TOMBSTONE}
after finding a (possibly inserted) copy of
op_{2}
.
By the code,
op_{2}
writes its first copy before
op_{1}
’s copy is deleted.

Lemma
7
shows a stronger property:
a copy cannot be deleted by an insert operation whose copy has already been deleted.
The details of the next proof are the main place where
the correctness proof differs between the LL/SC and the
CAS versions of the algorithm.

Lemma 7
.

Let
op_{1}
and
op_{2}
be two
\mathsf{insert}(v)
operations such that
op_{2}~{\leadsto}_{\mathsf{del}}~op_{1}
. Then either a copy of
op_{2}
and the last copy of
op_{1}
are both present in the table at the same time, or the last copy of
op_{1}
is a
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
value and a copy of
op_{2}
and the second-to-last copy of
op_{1}
are both present in the table at the same time.

Proof for the
\mathsf{LL}/\mathsf{SC}
version.

If
op_{1}
deletes its own copy, it does so after reading a copy of
op_{2}
.
Consider the last such read by
op_{1}
, then
op_{1}
’s next step is to overwrite its copy with
\mathsf{TOMBSTONE}
.
Assume that the copy of
op_{1}
that is in the table during this last read is overwritten before a copy is deleted.
Then, as
op_{1}
’s copy is not deleted yet, and this overwrite is not performed by
op_{1}
,
it can only be overwritten with
\langle v,\mathsf{revalidate}\rangle
.
This copy cannot be overwritten until
op_{1}
’s next step.
However,
\langle v,\mathsf{revalidate}\rangle
cannot be overwritten with
\mathsf{TOMBSTONE}
, in contradiction.

If
op_{2}
deletes a copy of
op_{1}
, then it begins by reading
op_{1}
’s copy with an
\mathsf{LL}
.
Then, it reads its own cell and gets
\langle v,\mathsf{tentative}\rangle
.
Lastly, it overwrites
op_{1}
’s copy with an
\mathsf{SC}
.
If the
\mathsf{SC}
succeeds, then it overwrites the same copy that it initially read with the
\mathsf{LL}
.
Therefore, this copy is the last copy of
op_{1}
.
In between, it read its own copy, ensuring that a copy of
op_{2}
is present in the table at the same time as
op_{1}
’s last copy.
∎

Proof for the
\mathsf{CAS}
version.

Assume that
op_{1}
deletes its own copy.
Consider the last read of
op_{2}
’s copy by
op_{1}
, then
op_{1}
’s next step is to overwrite its copy with
\mathsf{TOMBSTONE}
.
If
op_{1}
’s copy that is in the table during this last read is overwritten, it must be with
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
.
This is because
op_{1}
’s copy is not deleted yet, and this overwrite is not performed by
op_{1}
.
We already showed for the
\mathsf{LL}
/
\mathsf{SC}
version that an overwrite with
\langle v,\mathsf{revalidate}\rangle
is not possible,
as the overwrite with
\mathsf{TOMBSTONE}
must fail.
Assume that the copy is overwritten with
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
.
Since
op_{1}
deletes its own copy, only
op_{1}
can overwrite this value.
Any other overwrite would mean that some other operation deleted this copy, which cannot happen.
Thus,
op_{1}
overwrites this copy with
\mathsf{TOMBSTONE}
,
and we get that
op_{2}
’s copy is present in the table at the same time as
op_{1}
’s second-to-last copy.

If
op_{2}
deletes a copy of
op_{1}
, it first overwrites
op_{1}
’s copy with
\langle\langle v,i\rangle,\mathsf{marked}\rangle
, where
i
is
op_{2}
’s cell.
Then, it reads
\langle v,\mathsf{tentative}\rangle
from its own cell.
Finally, it overwrites the value
\langle\langle v,i\rangle,\mathsf{marked}\rangle
in
op_{1}
’s cell with
\mathsf{COLLIDED}
.
At any point during the execution, only a single insert operation owns a given cell.
This means that only
op_{1}
and
op_{2}
can overwrite the
\langle\langle v,i\rangle,\mathsf{marked}\rangle
copy of
op_{1}
.
Since
op_{2}
is the only operation that can write the cell number
i
to the table,
the value
\langle\langle v,i\rangle,\mathsf{marked}\rangle
written by
op_{2}
is the same one overwritten with
\mathsf{COLLIDED}
, and this is the last copy of operation
op_{1}
.
In between,
op_{2}
read its own copy, ensuring that a copy of
op_{2}
is present in the table at the same time as
op_{1}
’s last copy.
∎

An
insert sequence

op_{k}~{\leadsto}_{\mathsf{del}}~\ldots~{\leadsto}_{\mathsf{del}}~op_{1}
,
k\geq 1
,
has ended
if a copy of operation
op_{k}
is inserted.
The insert sequence is
maximal
if it has ended or
if a copy of operation
op_{k}
is still present in the table at the end of
\alpha
, that is, its final copy is neither deleted nor inserted.
This is denoted by
op_{k}~{\leadsto}^{*}_{\mathsf{del}}~op_{1}
.

Let
c_{j}
be the cell of
op_{j}
,
1\leq j\leq k
.
We next show that a copy is deleted only if its cell is further from the start of the probe sequence than the cell of the deleting operation (with the possible exception of the final deletion).

Lemma 8
.

Consider a maximal insert sequence
op_{k}~{\leadsto}_{\mathsf{del}}~\ldots~{\leadsto}_{\mathsf{del}}~op_{1}
,
k\geq 1
.
If
1\leq j<k-1
, then

\left(c_{j+1}-\mathsf{h}(\mathit{v})\right)<\left(c_{j}-\mathsf{h}(\mathit{v})\right)
.
Furthermore, if the sequence has not ended, or if a copy of operation
op_{k}
is overwritten with
\mathsf{DELETED}
, then

\left(c_{k}-\mathsf{h}(\mathit{v})\right)<\left(c_{k-1}-\mathsf{h}(\mathit{v})\right)
.

Proof.

Note that no copy of
op_{j+1}
is overwritten with
\langle v,\mathsf{final}\rangle
.
By the code and since
op_{j+1}~{\leadsto}_{\mathsf{del}}~op_{j}
,
a copy of
op_{j}
is deleted after
op_{j}
finds a copy closer to the start of the probe sequence, or
op_{j+1}
deletes a copy further from the start.
Therefore,

\left(c_{j+1}-\mathsf{h}(\mathit{v})\right)<\left(c_{j}-\mathsf{h}(\mathit{v})\right)
,
as needed.
If the sequence has not ended, or if the copy of
op_{k}
is overwritten with
\mathsf{DELETED}
, a copy of
op_{k-1}
cannot be deleted after
op_{k-1}
finds an inserted copy of
op_{k}
.
As before,
c_{k}
is closer to the start of
v
’s probe sequence than
c_{k-1}
.
∎

The next lemma is a key property of an insert sequence.

Lemma 9
.

Consider a maximal insert sequence
op_{k}~{\leadsto}_{\mathsf{del}}~\ldots~{\leadsto}_{\mathsf{del}}~op_{1}
,
k>1
.
If a copy of operation
op_{k}
is not inserted,
then among all operations
op_{j}
that have already written a copy to the table, no copy of the operation with the minimal distance

\left(c_{j}-\mathsf{h}(\mathit{v})\right)
is deleted.

Proof.

The proof is by induction on the number of writes
of the first copies of
op_{1},\ldots op_{k}
,
before the copy of
op_{k}
is inserted.
For the base case, note that the first
\langle v,\mathsf{tentative}\rangle
copy
is deleted only because of a copy that is written after it.
Thus, until the next write, the cell contains either
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
, or a copy of the operation is inserted,
implying that
op_{k}
’s copy is inserted.

For the induction step, assume that the lemma holds until the

j
-th write and that the copy of
op_{k}
is not overwritten
with
\langle v,\mathsf{final}\rangle
or
\mathsf{DELETED}
.
Consider the next,
j
th write of a first copy.
By Lemma
8
,
a copy is deleted due to an
\mathsf{insert}(v)
operation
only if it is further from the start of the probe sequence than the copy of the deleting operation.
Therefore, the copy residing in the cell closest to the start is deleted only because of a copy that is written after it.
In the next write, the cell contains either
\langle v,\mathsf{tentative}\rangle
,
\langle v,\mathsf{revalidate}\rangle
or
\langle\langle v,\ast\rangle,\mathsf{marked}\rangle
, or a copy of the operation is inserted, implying that
op_{k}
’s copy is inserted.
∎

5.2.3
Placing the Non-Mutator Operations

We can now construct the permutation
\pi_{v}
by
going through the rest of the completed operations,
in the order in which they are invoked in the execution,
and inserting them between the mutator operations,
already placed in
\mu_{v}
.
We place each such operation
op

immediately
before or after a mutator operation
op^{\prime}
;
in the latter case, we place
op
immediately before the next mutator operation that follows
op^{\prime}
in
\mu_{v}
,
or at the end of the permutation if no such operation exists.
This strategy ensures that operations placed after the same mutator operation respect the real-time order among them.

Let
\mathsf{nop}
denote the set of the non-mutator operations that complete in
\alpha
,
and it has two subsets:

\mathsf{nop}^{+}
are the operations that
find the key
, that is,
\mathsf{insert}(v)
operations that return
false
and
\mathsf{lookup}(v)
operations that return
true
,
while
\mathsf{nop}^{-}
are the operations that
do not find the key
, that is,
\mathsf{delete}(v)
and
\mathsf{lookup}(v)
operations that return
false
.

We place these non-mutator operations by examining where the mutator operations are linearized. Specifically, for an operation in
\mathsf{nop}^{+}
(respectively,
\mathsf{nop}^{-}
), we search for the earliest valid placement between the last mutator linearized before the operation begins and the first mutator linearized after it ends, such that
v
is present (respectively, absent) according to the sequential specification.

We start with the operations in
\mathsf{nop}^{+}
.
If there is a cell containing
\langle v,\mathsf{final}\rangle

when an operation
op
in
\mathsf{nop}^{+}
is invoked,
we place
op
in
\pi_{v}
after the mutator operation with the latest linearization point occurring before
op
’s invocation.
If there is a mutator
\mathsf{insert}(v)
operation with a linearization point occurring between
op
’s invocation and response,
we place
op
after the earliest such point.
If none of these two cases hold, we prove that there is
an
\mathsf{insert}(v)
in
\mathsf{mop}
whose linearization point occurs after
op
’s response.
Among these operations, let
iop
be the operation whose linearization point is the earliest;
we place
op
in
\pi_{v}
after
iop
.

Lemma
10

shows that whenever a non-mutator
insert or lookup operation returns after observing a key and attempting to replace it with a
\mathsf{revalidate}
indication
and the first two cases do not hold,
there is an insert sequence whose final operation is ordered after it.
This is used to show that the ordering of operations in
\mathsf{nop}^{+}

is well defined.
The lemma also provides additional properties
that are later used to prove that the ordering of these operations respects the real-time order.

Lemma 10
.

Consider
op\in\mathsf{nop}^{+}
,
and assume no cell contains
\langle v,\mathsf{final}\rangle
when

is invoked, and there is no mutator
\mathsf{insert}(v)
operation with a linearization point between the invocation and the response of

Then,
(a) there is a mutator
\mathsf{insert}(v)
operation with a linearization point occurring after
op
returns.

Furthermore, let

be the
\mathsf{insert}(v)

’s response.
Then,
(b)
iop
does not follow
op
, and
(c) a cell containing key

op
’s response and

Proof.

We pick an
\mathsf{insert}(v)
operation

that writes

If

.

wop
.

Otherwise, if

is an
\mathsf{insert}(v)
that returns

\langle v,\mathsf{tentative}\rangle

be operation
op
itself.
Let

be the final operation in the maximal insert sequence starting with

We start by proving (a).

If no copy of

is ever inserted, a copy of

is present in the table at the end of
\alpha
.
By construction, either

\mathsf{insert}(v)

Next, we assume that a copy of

’s invocation.
In other words, a copy of

is inserted before

’s invocation.
Since no cell contains
\langle v,\mathsf{final}\rangle
when

is invoked,

’s copy is deleted before the invocation of

op
.

We show that

reads the cell of
op_{k}

op_{k}
.
However, since no new copy is written after a copy in inserted,

is inserted before the invocation of
op
.

First, we show that the read of

from the cell of
iop
,
in its forward scan, precedes

iop

(which is its only copy if

has only one copy).
If

, this holds since

If

and it reads

.

\langle v,\mathsf{final}\rangle

\langle v,\mathsf{revalidate}\rangle

Then, either another copy of the same operation is written to the cell,

Assume that for some

If

,

.

.
Therefore, since a copy of

Finally, we prove (c).

is inserted after

or a copy of

{op}_{k}
is inserted.

The linearization of

5.3
Liveness

It is easy to see that
\mathsf{lookup}
operations are wait-free.
For
\mathsf{delete}(v)
and
\mathsf{insert}(v)

operations, the only cases in which these operations
take infinitely many steps without returning
are:

•

For
\mathsf{delete}(v)
: the operation repeatedly attempts and fails to overwrite a tentative copy of
v
at a specific cell with
\mathsf{DELETED}
;

•

For
\mathsf{insert}(v)
: the operation
writes a tentative copy into some cell,
but is then forced to revalidate it infinitely often
by signals from other processes.

In both cases,
the operation attempts infinitely many times to modify
a specific cell containing a copy of
v
.
Thus, to prove lock-freedom, we show that
this scenario arises only if infinitely many other operations complete.

Since
\mathsf{lookup}
and
\mathsf{delete}
operations modify a memory cell only once during their execution, their interference is naturally bounded.
The difficult case is
\mathsf{insert}
operations, for which we prove two lemmas:
one bounds the interference from copies of other operations,
and the other shows that an operation either rewrites its copy
a bounded number of times or infinitely many operations complete.

Lemma 15
.

An
\mathsf{insert}(v)
operation
op
performs at most a bounded number of modifying instructions on cells containing a copy of
v
belonging to other operations.

Proof.

From the code,

modifies a cell containing a tentative copy
of a different operation

(1)

overwrites a tentative copy with
\langle v,\mathsf{revalidate}\rangle

(2) in the
\mathsf{CAS}

Next, consider the case where

5.4
Amortized Step Complexity

In this section, we analyze the runtime of our algorithm
under the simplifying assumption that at any point in time, there is at most one active
\mathsf{insert}
operation for any given key. (Multiple concurrent operations on the same key are permitted, as long as only one of them is an insertion.)
Without this assumption, the adversary can force the creation of tombstones (as demonstrated in Fig.
2
), though we note that it can only deterministically force
O(n)
tombstones in any given run in the hash table.

We recall that the classical analysis of Knuth
[
12
]
for sequential linear-probing hash tables shows that after any sequence of
k
insertions,
if we represent the resulting load factor on the table by
k/m=1-1/x
for
x>0
, then for any key
v
,
the expected distance from
h(v)
to the end of
v
’s run is at most
O(x^{2})
.

Mapping to a sequential execution.

Knuth
[
12
]
did not address tombstones in his analysis (in fact, he addressed only insertions, but his analysis holds if deletions are implemented by reordering the remaining keys to take the empty place of the deleted key, rather than using tombstones).
To address this gap we perform a pessimistic analysis that ignores the possibility that an inserted key will take the place of a previously deleted one:
we assume that any inserted remains in the hash table,
ignoring the possible re-use of tombstones that are left behind by successful deletions.

To map concurrent executions to sequential ones, we define the
effective insertion schedule
of an execution
\alpha
. This schedule consists of the subsequence of
\mathsf{insert}
operations in
\alpha
that perform a write of
\langle\ast,\mathsf{tentative}\rangle
, ordered by the time of that write.
This implies the following:

Proposition 20
.

Let
\alpha
be an execution consisting only of
\mathsf{insert}
operations, where no two concurrent operations have the same key. Then, the state of the table at the end of
\alpha
is identical to the state after the sequential execution of the effective insertion schedule of
\alpha
.

Consider a sequential execution of all the insert operations in the batch.
By Knuth’s analysis the expected run length for any given key is
O(x^{2})
.
Crucially, this holds regardless of the execution order.
Thus, the specific effective insertion schedule determined by the concurrent execution is irrelevant to the expected run length.

As in the sequential algorithm, our
\mathsf{delete}
and
\mathsf{lookup}
operations never occupy a cell that was previously empty, and therefore they can never extend an existing run or cause two adjacent runs to merge; only
\mathsf{insert}
operations can increase the run length.
By Proposition
20
, provided there are no concurrent
\mathsf{insert}
operations targeting the same key, the sequential analysis suffices to determine the expected run length.
Consequently, the expected length of any scan over consecutive non-empty cells in the concurrent execution is also
O(x^{2})
.

We define a
c
-bounded fixed-workload scheduler
as an adversary that manages a batch of operations that is fixed in advance,
before the hash function is chosen.
The scheduler is worst-case, and determines the invocation order dynamically: whenever a process is free, the scheduler may choose
any
of the remaining operations in the batch to run next,
subject to
(a) a maximum
point contention
of
c
per key, that is, the maximum number of concurrent operations targeting the same key at any point in time is at most
c
;
and
(b) a maximum of one
\mathsf{insert}
operation active on any given key at any time.
Under this scheduling model, we establish the following bound on the step complexity, applicable to both the
\mathsf{LL}/\mathsf{SC}
and
\mathsf{CAS}
versions of our algorithm.

Theorem 21
.

Let
m
be the size of the table, let
x>1
be a real number,
and fix any batch of operations that includes at most
(1-{1}/{x})m

\mathsf{insert}
operations.
Under a
c
-bounded fixed-workload scheduler, the expected amortized step complexity per operation in both the
\mathsf{LL}/\mathsf{SC}
and
\mathsf{CAS}
versions is
O(x^{2}+c)
.

Proof.

We design a
charging scheme
that charges each step taken by process
p
to some operation, either its own operation or a different one.
Recall that because concurrent insert operations operate on distinct keys, the state
\langle\langle\ast,\ast\rangle,\mathsf{marked}\rangle
(required in the
\mathsf{CAS}
version for colliding insertions) is never written. Consequently, the analyses of the
\mathsf{LL}/\mathsf{SC}
and
\mathsf{CAS}
implementations coincide, and we treat them together.

Lookup operations:

A lookup operation performs at most one forward and one backward scan, each traversing expected
O(x^{2})
cells, as established earlier.
Each step of a scan takes a constant number of read and modify instructions, which are charged to the lookup itself.

Delete operations:

A delete operation performs at most one forward and one backward scan. However, it may execute a super-constant number of instructions on a single cell if it repeatedly encounters a value
\langle v,\mathsf{tentative}\rangle
or
\langle v,\mathsf{revalidate}\rangle
and fails to update it.

•

The initial read of a cell and any successful modify instructions are charged to the delete operation itself.

•

If the delete operation reads a value that does not contain the key
v
(or contains
\langle v,\mathsf{final}\rangle
), it stops re-reading the cell and proceeds. This read is charged to the delete operation itself.

•

Any subsequent pair of modify and read instructions representing a failed attempt to update the cell is charged to the
interfering
insert or lookup operation that wrote the value triggering the retry.

1.

If the value is
\langle v,\mathsf{revalidate}\rangle
, the pair is charged to the operation that wrote this value.

2.

If the value is
\langle v,\mathsf{tentative}\rangle
and it is the first such value written by the current insert operation, the pair is charged to that insert operation.

3.

If the value is
\langle v,\mathsf{tentative}\rangle
but it overwrites a
\langle v,\mathsf{revalidate}\rangle
, the pair is charged to the operation that wrote the preceding
\langle v,\mathsf{revalidate}\rangle
.

A delete operation is charged expected
O(x^{2})
of its own steps. Steps are charged to other operations only when the delete operation re-reads a cell. Consequently, the operation that triggers this retry must be concurrent with the delete operation.
An insert or lookup operation restarts at most one other operation (by writing
\langle v,\mathsf{revalidate}\rangle
exactly once). Since there are at most
c
concurrent operations targeting key
v
, at most
c-1
delete operations can read this
\langle v,\mathsf{revalidate}\rangle
and charge the writer.
Similarly, if
\langle v,\mathsf{revalidate}\rangle
is subsequently overwritten by
\langle v,\mathsf{tentative}\rangle
, this write can cause at most
c-1
additional concurrent delete operations to restart.
Separately, an insert operation that writes
\langle v,\mathsf{tentative}\rangle
is charged with the retries of at most
c-1
concurrent delete operations that read this value.
Thus, an insert or lookup is charged with at most
O(c)
steps from concurrent delete operations.

Insert operations:

An insert operation begins by searching for the key by performing at most one forward and one backward scan. If found, it terminates. If not, it performs a forward scan to find an empty slot. Since the table is not full, a slot is guaranteed to be found.
This initial phase comprises at most three scans. With constant work per cell, the expected cost is
O(x^{2})
, charged to the insert operation itself.

In the second phase, the insert repeatedly performs forward scans to finalize the insertion.
If an insert operation attempts to delete its own copy, it succeeds in modifying the cell after a finite constant number of attempts, unless the cell is marked with
\mathsf{revalidate}
. This holds because
once the operation’s cell transitions to a cleanup state (
\mathsf{DELETED}
or
\mathsf{COLLIDED}
), only the owner can modify it.

A forward scan is repeated only if a different insert or lookup restarts this operation.

•

The first forward scan is charged to the insert operation itself.

•

Any subsequent scans are charged to the operation that triggered the restart.

Since an insert or lookup restarts at most one other operation, it is charged with at most one additional forward scan of a different insert operation, adding expected
O(x^{2})
steps.

Each operation is charged with expected
O(x^{2})
steps for its own execution, at most
O(c)
steps from interfering deletes, and at most
O(x^{2})
steps from a restarted insert.
The total expected amortized step complexity is therefore
O(x^{2}+c)
.
∎

6
Summary and Discussion

We present a lock-free linear probing hash table that minimizes memory overhead:
it uses only 2 bits of metadata per entry with
\mathsf{LL}
/
\mathsf{SC}
, and
O(\min(\log m,\log n))
bits using
\mathsf{CAS}
.
Our hash table supports wait-free lookups,
and in the relatively uncontended scenario where keys are not inserted more than once at the same time,
it has roughly the same performance as sequential linear probing,
up to an additive term of the point contention on any given key.

In the world of
sequential
data structures,
much effort is devoted to designing
succinct data structures
,
whose memory footprint matches the information-theoretic lower bound on the abstract data type they represent, up to lower-order terms.
For hash tables (or rather, for dictionaries) such constructions have been known for over two decades,
and the precise tradeoff between memory and query time has recently been completely resolved
[
13
,
4
]
.
For concurrent dictionaries, however, no succinct lock-free construction is known; to our knowledge, our construction
appears to come closest,
at
m(\lceil\log(U)\rceil+2)
bits in total (in the
\mathsf{LL}
/
\mathsf{SC}
version).
Obtaining succinct lock-free dictionaries is an interesting open problem.
