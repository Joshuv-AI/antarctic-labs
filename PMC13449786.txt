ACSCull: visibility-aware triangle elimination for skinned characters under an admissible Camera Set
Authors: Jos Timanta Tarigan
Published: 2026

ABSTRACT
Top-down mobile games render skinned characters under a tightly bounded cinematic envelope yet ship meshes authored as if every face could be observed from any direction. Triangles outside that envelope are rasterised every frame at no visual benefit. We describe ACSCull, an offline pre-pass that removes such triangles for pre-composed skinned characters. The method formalises the game's cinematic envelope as an Admissible Camera Set (ACS) — a five-tuple of pitch, yaw, distance, field of view, and aspect — and identifies the visibility set by rendering K cameras × P poses sampled from a low-discrepancy sequence over the ACS into an R32UI render target with per-triangle identifiers carried as flat-interpolated vertex attributes. Non-visible triangles are eliminated and the geometry is re-emitted as standard glTF Binary, drop-in compatible with mobile NDK and WebGL runtimes.Removes 27–55% of triangles from skinned characters by visibility; composable with conventional mesh simplifiers.Output is standard glTF Binary; runtime renderer requires no changes.Held-out SSIM ≥ 0.9999 in-ACS and ≥ 0.9997 under ±5° pitch / ±25% distance perturbation.

Background

Top-down action and role-playing games on mobile devices restrict the player's camera to a narrow band of pitch angles (typically 55°–70° below horizontal), permit a small distance window between the camera and the character, and use a fixed field of view. Skinned-character art, however, is authored for general use: triangles facing away from any plausible camera, hidden inside layered costume meshes, or occluded by attached props remain in the index buffer and are submitted to the GPU every frame. On thermally constrained mobile hardware, the cost of rasterising these triangles is non-trivial, particularly when multiple characters appear on screen, yet it produces no observable image-space contribution.

Existing approaches do not address this gap directly. Geometric simplification methods [[4], [5], [6], [7]] trade polygon count for shape fidelity without respecting camera constraints and can degrade silhouettes that the trained envelope does in fact reveal. Runtime decimation defers the cost rather than eliminating it. Static occlusion data structures presume rigid geometry and do not apply to skinned meshes that deform per pose. Pre-composed wardrobe meshes — common in mobile titles to avoid runtime SkinnedMesh proliferation — are merged after authoring and therefore retain every per-part triangle in a single index buffer where they cannot be batched away.

We propose to exploit the camera constraint directly. By rendering the candidate mesh from a dense, low-discrepancy sample of the Admissible Camera Set, and by reading back per-triangle visibility, the set of triangles that ever contribute a pixel is precisely measurable. The complement — triangles never seen under any admissible camera or pose — can be removed offline with no runtime cost and no change to the rendering pipeline. The output is a standard glTF Binary file; the runtime simply loads a smaller mesh.

Method details

The pipeline is structured in four stages: merge, bake setup, visibility sampling, and elimination. The reference implementation runs as a headless Electron application that re-uses the runtime's own Three.js [3] renderer and skinning shader pipeline, so that vertex positions during baking match those produced at runtime numerically.

Preprocessing

The input is a composed character: one base SkinnedMesh and N attached SkinnedMeshes — costume parts, props — that share the base skeleton's bones by name but each carry their own bindMatrix and per-bone inverseBindMatrices inherited from their source FBX. Merge produces a single SkinnedMesh with a single BufferGeometry as expected downstream. Correctness of bind-space reconciliation is the single most consequential numerical step. If it is wrong, vertex positions during baking will differ from those produced at runtime and the visibility set will be unsound. The implementation tests it explicitly by rendering both the pre-merge composed scene and the merged mesh at the bind pose and at an animated pose, and asserting SSIM ≥ 0.999 against the runtime renderer.

Bake setup: triangle identifier attribute

WebGL2 [6] does not expose gl_PrimitiveID to the fragment shader, so per-triangle identification is achieved by attribute rather than by intrinsic. For each triangle t with indices (i₀, i₁, i₂) the bake emits three new vertices carrying the attribute values of i₀, i₁, and i₂ respectively, each additionally stamped with aTriId = t, and three new consecutive indices (3t, 3t+1, 3t+2). The resulting baking geometry has 3 * triangle_count vertices and the same triangle count. All skinning attributes — skinIndex and skinWeight — are preserved through duplication so the runtime skinning path produces correct posed positions. aTriId is declared as Uint32Array of itemSize 1 and bound to a vertex shader input declared as in uint aTriId. The baking geometry is bake-only and is never exported.

A custom ShaderMaterial replicates Three.js's standard skinning vertex shader pipeline by including the engine's shader chunks (common, skinning_pars_vertex, skinbase_vertex, skinning_vertex), so that vertex positions agree with the runtime renderer numerically. aTriId is passed through as flat out uint vTriId; the fragment shader writes uvec4(vTriId + 1 u, 0 u, 0 u, 0 u) to an R32UI render target. The +1 u offset reserves 0 as a sentinel for "no triangle here".

The render target is a Three.js WebGLRenderTarget sized at render_resolution × supersample, with UnsignedIntType colour, RedIntegerFormat externalFormat, R32UI internalFormat, and a matching DepthTexture using DepthFormat and UnsignedIntType. Nearest-neighbour filtering is used and no mipmaps are generated. The required EXT_color_buffer_integer extension is verified at startup; the absence of this extension is reported as a fatal error.

Visibility sampling

The Admissible Camera Set is parameterised as a five-tuple of pitch in [pitch_min, pitch_max], yaw in [yaw_min, yaw_max], distance in [d_min, d_max], horizontal field of view, and aspect ratio, together with a target_offset and a list of named pose animations to sample. K camera samples are generated from a three-dimensional Halton sequence [2] with bases (2, 3, 5) mapped to (pitch, yaw, distance) within the configured ranges; each sample yields a PerspectiveCamera positioned on the spherical shell around target_offset and looking at target_offset.

P pose samples are gathered from the named animations by stepping each clip at (1 / animation_fps) · pose_sample_stride seconds, concatenating, and uniformly subsampling down to P. The bind pose (t = 0 of the first animation) is always included so that the rest pose is always represented. For each (camera, pose) pair the pipeline (i) advances the merged SkinnedMesh's AnimationMixer to the pose time, (ii) clears the R32UI target to zero, (iii) renders the baking geometry with the identifier shader, (iv) reads back the integer colour attachment via readRenderTargetPixels into a Uint32Array, and (v) for each non-zero pixel value v, sets bit (v − 1) of a triangle_count-bit visibility bitset. After K·P renders, the bitset contains the visibility set for the configured ACS.

The default ACS used throughout this study is pitch 55°–70°, full 360° yaw, distance 8–12 world units, 60° horizontal field of view, 16:9 aspect, K = 64 cameras, P = 20 poses, render_resolution = 512², and supersample = 2 × . Sampler bias was checked by repeating selected bakes with Halton bases (7, 11, 13); the resulting visibility sets agree with the (2, 3, 5) sampler up to triangles with one-pixel coverage.

The visibility-detection loop in compact form:

input: merged_mesh, ACS, K, P.

output: visibility_bitset[triangle_count].

cameras = halton_samples(ACS, K, bases=(2,3,5)).

poses = sample_poses(ACS.animations, P).

bitset = zeros(triangle_count).

for k in 1..K, p in 1..P:

pose_skeleton(merged_mesh, poses[p]).

render(baking_geometry, cameras[k]) -> R32UI buffer.

for each non-zero pixel value v in buffer:

bitset[v - 1] = 1.

return bitset.

The total bake cost is dominated by K · P render-readback cycles, each O(supersample² · render_resolution²) on the GPU; after the per-vertex duplication step in stage 2, runtime is independent of the source triangle count. Elimination and output

The bitset is converted to a boolean kept[triangle_count] mask. A new index buffer is emitted containing only kept triangles; a vertex remap is constructed on the fly during this walk, producing new attribute buffers that copy only the referenced vertices. Geometry groups are rebuilt by counting kept triangles within each original group's range; empty groups and their unused materials are dropped. The reduced SkinnedMesh is exported via Three.js's GLTFExporter to a standard glTF Binary [8] file. From the runtime's perspective, the output is indistinguishable from a normal export of the same mesh.

Alongside the reduced GLB the bake emits a sidecar file in JSON with extension .acsbake.json. The sidecar records the full ACS configuration used for the bake, the K and P sample counts actually drawn, render_resolution and supersample, the original and kept triangle counts, the reduction ratio, the bake wall time, the GPU device fingerprint as reported by the GL renderer string, and the bake timestamp. Together with the source mesh and the reference implementation at the version recorded in CITATION.cff, the sidecar is sufficient to reproduce the reduction exactly.

Reference implementation

The pipeline is implemented as a headless Electron application in approximately two thousand lines of JavaScript [9], comprising a bundle-aware bake entry point (cull.js), a validation harness (validate.js), nine bake modules (mergeSkinned, acsConfig, bakingGeometry, bakeShaderMaterial, cameraSampler, poseSampler, visibilityPass, triangleElimination, sidecarWriter), and three validation modules (heldOutCameras, ssim, validationRunner). Unit tests cover the bake-geometry construction and the SSIM implementation; integration tests requiring a GPU run locally. The repository is at https://github.com/jttarigan/acscull [10] and is released under Apache-2.0 with an explicit patent grant; an archival snapshot of v0.1.0 is available at doi:10.5281/zenodo.20207414.

Method validation

Validation is performed by an independent harness (validate.js) that does not share code paths with the bake. The harness consumes the pre-elimination merged GLB — emitted by the bake under the –save-merged flag — and the reduced GLB. Both are rendered to RGBA8 framebuffers under matched cameras using the runtime's normal colour shader, not the identifier shader.

Held-out cameras are generated by a Halton sequence with bases (7, 11, 13), prime-coprime with the bake sampler's (2, 3, 5), and distributed over the same ACS ranges. The default validation budget is 128 cameras. For each camera, both meshes are rendered, the pixels are read back to RGBA8 Uint8Arrays, and the harness computes the structural similarity index [1] between them with an 11 × 11 Gaussian window, K₁ = 0.01, K₂ = 0.03, and L = 255, together with the per-channel maximum absolute difference.

An adversarial pass repeats the same procedure with pitch extended by ±5° and distance extended by ±25% beyond the trained ACS, providing a second SSIM distribution that quantifies behaviour outside the certified envelope. Per-pose validation is supported in principle and is left as a straightforward extension; the present version certifies the bind pose only.

ACSCull is a visibility-based pre-pass and is orthogonal to the geometry-based mesh-simplification methods commonly used in mobile pipelines (meshoptimizer [6], Draco [7], quadric-error simplification [4,5]). Those methods reduce triangle count by collapsing vertices that contribute little to the mesh's geometric shape, with no awareness of the camera envelope; ACSCull removes triangles that are never visible from any admissible camera, with no impact on geometric fidelity of the visible surface. The two are therefore complementary: ACSCull can be applied as a prefix stage before any standard simplifier, with the simplifier's error budget then spent only on visible geometry. We have not measured the combined reduction empirically; quantifying the cascade is left to future work.

Limitations

The current implementation treats all materials as opaque for visibility purposes. Triangles authored with MASK or BLEND alpha modes should be forced into the visibility set unconditionally and are not yet handled; this extension is planned for the next version.

Shadow-caster geometry is reduced together with the camera-visible geometry. For top-down cameras whose shadows are short and predominantly on-screen this is acceptable, but steeper sun angles or a stylised long-shadow art direction would warrant a separate shadow-only mesh derived from the original.

The pipeline assumes a single Admissible Camera Set per title. Multi-mode cameras — photo mode, cinematics — would require either a union over modes at bake time or per-mode reduced meshes selected at runtime.

Numerical agreement between Three.js's GPU skinning and a downstream cgltf-based runtime was confirmed empirically rather than analytically. If a runtime later exhibits a measurable discrepancy on a given platform, the pipeline supports a CPU-skinning fall-back at bake time in which posed vertex positions are evaluated in JavaScript and the bake shader is non-skinned.

Bake-time peak VRAM is approximately three times the merged geometry's vertex buffer because of triangle-duplicated vertex expansion. This has not been a constraint for character-sized meshes; environment-scale inputs would need to be tiled.

Beyond these implementation gaps, ACSCull is not the right tool for several broader use cases. First-person and third-person free-camera games have an effectively unbounded camera envelope and would lose nothing by skipping the pre-pass. Titles with photo modes, cinematics, or other camera modes outside the gameplay envelope must either union the modes into one ACS or ship per-mode reduced meshes. Assets whose runtime camera envelope is not known at build time — generated content, modder-driven cameras, or shared asset libraries — cannot benefit. The method targets games whose camera envelope is fixed at ship time and significantly narrower than the full sphere.

Supplementary material and/or additional information [OPTIONAL]

Eight per-bake reproducibility sidecars (.acsbake.json) and the corresponding eight validation summaries (.validation_summary.json) are provided as supplementary files. Each sidecar records the exact ACS configuration, K and P sample counts, render resolution and supersample, original and kept triangle counts, GPU device fingerprint, and bake timestamp. Each validation summary records held-out SSIM (mean, p05, min, max) and maximum per-channel absolute pixel difference, in-ACS and adversarial.
