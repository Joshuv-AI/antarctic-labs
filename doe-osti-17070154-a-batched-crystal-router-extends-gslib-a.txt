 Summary
Distributed lookup, mesh redistribution, and interpolation in Nek5000 and NekRS all rest on the
same irregular all-to-many exchange, carried by the crystal router (CR) in gslib. CR delivers records
in O(log P ) rounds by forwarding them through intermediate ranks, trading data movement for a
small number of message startups. That trade was favorable while each rank held modest amounts
of data. Moving to exascale GPU systems has changed it: local data per rank has grown from
roughly 8 × 103 reals on a CPU rank to 5 × 106 reals on a GPU rank, and because forwarded
records pile up at intermediate ranks, a single exchange can now exceed the 2 GiB count limit of
conventional MPI calls or demand more memory than a node can provide. The failure can happen
even when the initial and final distributions are balanced.
 This report addresses that bottleneck by batching the exchange at three levels. Batched CR
(bCR) divides an oversized transfer into chunks that each fit within the MPI count limit, using
64-bit counts and a collective agreement on the chunk size. Batched restart (bRestart) reads a
checkpoint in bounded batches and schedules redistribution into receive rounds sized to a fixed
buffer, so peak memory no longer scales with the checkpoint. Batched gfldr (bGfldr) processes
target elements in batches, reducing the records that enter CR at once. Together they lower both
the inbound data and the peak traffic downstream, without altering how the router works.
 To see where that traffic concentrates, we added runtime logging of per-round transfer sizes
and a visualization of the resulting flow, which attributes the peak to the ranks and rounds that
create it. Our case study applies gfldr to couple an OpenMC neutronics calculation to a Nek
simulation of the ITER WCLL blanket, a transfer no unbatched path completes. The logs show that
batching the router alone is not enough and trace the excess to candidate-rank fanout in findpts.
Combining bCR with bGfldr does complete the transfer, but not cheaply: every batch rereads and
reconverts each reader’s full share of the source fields, so file input and point routing repeat once
per batch. The result is correct and fits in memory, yet its cost grows with the number of batches,
and batches are precisely what the peak traffic forces us to add. The expense is acceptable here
only because it is paid once, before the interpolated fields are written to a checkpoint.
 That trade motivates the improvements we outline last. Batching keeps each transfer inside
the MPI count limit, but the volume delivered to a given rank is set by findpts rather than by the
router, and it can still approach the 16 GiB limit at which 32-bit accounting in gslib fails. Pushing
that peak down by batching alone only buys more batches and more repeated work. The more
promising direction is to produce fewer speculative copies to begin with, so that the peak falls
without the extra passes.

1 Introduction
A common collective communication pattern in distributed PDE solvers is an all-to-many exchange.
Each rank starts with a collection of records, each assigned to a destination rank. All ranks take
part, but the number of records exchanged between any pair of them is irregular. Such solvers
balance work across ranks, so the initial and final record distributions are typically near-uniform.
The traffic between individual pairs is not.
 In Nek5000 [1] and NekRS [2] the pattern supports three operations. Distributed lookup routes
a key to the rank holding the relevant data and returns a result, as in the vertex matching performed
by parCON, which ships with parRSB [3]. Redistribution moves elements during partitioning and
field data during parallel I/O. Distributed interpolation uses findpts [4, 5] to locate the source
elements containing a set of query points. The owning ranks then evaluate the field and return the
values, as in mesh-to-mesh transfer and NekNek coupling [4]. More generally, the same routing
assigns irregular work to whichever ranks hold the data it needs.
 The irregular exchange can be expressed with MPI Alltoallv, but its count and displacement
arrays require O(P ) entries per rank, and common implementations use linear communication
schedules [6]. That overhead is costly when each rank exchanges with only a small subset of the P
ranks. We therefore use the crystal router (CR) [7, 8] as implemented by gslib [5], which forwards
records toward their destinations in O(log P ) rounds with one partner per rank per round, limiting
message startups for sparse exchanges. These kernels have been measured at more than 106 MPI
ranks [4, 9].
 CR trades fewer message startups for additional data movement. A record can cross up to
log2 P links, and paths from different origins converge at intermediate ranks, so a rank transiently
 more than it began with. For P = 2d and m0 bytes per rank initially, that peak grows to

carry more than 231 − 1 bytes, just under 2 GiB, since conventional point-to-point calls take a signed
int count. Nor can a rank accumulate more than roughly 16 GiB across an exchange, since gslib
accounts for received rows in 32-bit arithmetic. The first binds each message, the second the rank.
 Both limits yield to the same idea applied at two levels. The first is a property of a single
call, so it is enough to divide an oversized transfer into chunks that each fit within the count and
send them one after another. The route is unchanged and no rank holds less data than before. The
second is a property of the rank, so relieving it requires fewer records in flight at once: the exchange

 We apply both in this work. Inside the router, bCR chunks any transfer that exceeds the count

2 New Methods for Managing Large Exchanges
2.1 Scope of the Three Methods

Before describing the methods individually, we set out how they relate. All three address the same
bottleneck, but they sit at different levels of the call stack, so each benefits a different set of callers.
Figure 1 shows the arrangement.

 CR (gslib) → bCR

 findpts (gslib) restart (Nek5000) → bRestart

 NekNek gfldr → bGfldr

Figure 1: Dependency diagram of each methods. Every all-to-many exchange in Nek5000 and
NekRS reaches the crystal router, so bCR benefits all of them. findpts sits between CR and the
two callers that route point queries, while the application-level methods each serve one caller.

 bCR is the widest of the three. Restart, NekNek and gfldr all route their data through the
same gslib crystal router, differing only in the entry point they call and in what they place in each
record, so raising the per-call limit benefits every one of them. bRestart (Section 2.3) and bGfldr
(Section 2.4) each address a single caller.
 The three callers reach the limit at different problem sizes, in proportion to how much data
they move per call and how unevenly it is distributed. Restart moves the least and distributes it
most evenly, so it overflows only at large rank counts. NekNek routes point queries through findpts
and is uneven at the receiving rank. gfldr moves the most data and is the most uneven, which is
why it is the first application to encounter the limit in practice, and why it serves as the case study
in Section 3. It is the leading edge of a constraint the others meet later, not a special case.
 This arrangement also indicates where further work is best directed. Because gfldr and
NekNek both obtain their destinations from findpts, reducing the records that findpts generates
would benefit both, whereas an improvement confined to gfldr would help neither the other callers
nor the router. We return to this point in Section 4.
 The remainder of this section describes each method in turn, from the router outward, beginning
with bCR in Section 2.2. The vocabulary shifts with the level. At the router we speak of records
carried in messages, split where necessary into chunks that each fit one MPI call. At the application
level the unit is the element and the outer loop proceeds in batches.

2.2 Batched Crystal Router Exchanges

The crystal router (CR) routes irregular messages through a sequence of rank group splits [7, 5].
Each message carries its own destination and a rank may submit many of them. We call the contents
of one message a record. For P = 2d , each round separates every active group into two equal halves.
A rank sends the messages addressed to the other half and keeps those addressed to its own. Writing
each rank index in d-bit binary, round j resolves destination bit d − 1 − j, beginning with the
most significant. This is the reverse of the classical hypercube router [7], which resolves the least
significant bit first. After d rounds every group contains one rank, so every message has arrived,
having possibly passed through intermediate ranks along the way.
 Algorithm 1 summarizes the implementation in gslib. The active group G contains consecutive
ranks. Ranks in its lower and upper halves are paired in reverse order. For example, with eight
ranks, the first round pairs rank 0 with rank 7, rank 1 with rank 6, and so on. These reflected
partners need not differ in only one binary digit. When a group has odd size, the lower half contains
one extra rank. That rank sends to the first upper rank without receiving, so the first upper rank
receives from two ranks.

Messages are stored as uint words, but gslib sends their raw bytes with MPI UNSIGNED CHAR, so
sending m words passes m sizeof(uint) as the MPI count. That is four times the word count, and it
is what brings the 2 GiB ceiling of a signed int [10, 11, 12] within reach of a single round. A count
exchange that succeeds can therefore report a transfer too large for the call that must carry it.
 MPI 4 introduced large count variants such as MPI Isend c and MPI Irecv c, whose counts use
MPI Count [12]. Support in deployed libraries differs. Open MPI 5, for example, reports complete
MPI 3.1 support but only partial MPI 4 support [13], and the vendor MPI on the Cray systems
used here is likewise a moving target across releases. We therefore retain the conventional calls, so
that the exchange also works on MPI 3 installations [14].
 In batched CR (bCR), the word counts exchanged at line 20 use ulong. After this hand-
shake, each rank compares every outgoing and incoming count with the predefined limit L =
⌊B/ sizeof(uint)⌋ words, where the byte limit B is below INT MAX. If all counts fit, line 22 sends
one message per partner in a single MPI call. If a transfer contains m > L words, it is divided into
⌈m/L⌉ consecutive chunks of at most L words each, with waits when the bounded request pool fills.
This limits the count passed to each MPI call.
 The chunks reuse the same partners and a single payload tag, which is distinct from the tag
carrying the count handshake. Every chunk of a transfer therefore shares one message envelope, and
nothing in the kth chunk distinguishes it from the jth. They pair correctly because MPI messages
are non-overtaking: two sends from the same origin that match the same receive are delivered in the
order they were posted. This guarantee has been part of the standard since MPI 1.1 [15], so bCR
depends on nothing newer than the rest of the exchange does. It holds here because the router is
single-threaded and names an explicit peer on every call, rather than receiving with MPI ANY SOURCE.
Sender and receiver must also divide a transfer identically, so bCR verifies collectively that L agrees
on every rank before routing begins. The group splits and the full buffer reservation at line 21
remain unchanged.
 bCR removes the 2 GiB ceiling on a single MPI call, raising the size of a workable exchange
by roughly eight times without a proportional cost in runtime, since the chunks of one transfer
are nonblocking and overlap. What it does not remove is the per-rank limit, and two bounds near
16 GiB remain in its place. They differ in kind. One is per message: the length field m of the wire
format is a uint, so a single message cannot exceed UINT MAX words. The other is per rank and
is an accounting limit rather than a capacity, in that sarray transfer requires its total received
word count to fit a uint once routing is done, its row bookkeeping being 32-bit. A rank may hold
more than that during an intermediate round, provided it forwards the excess before the check runs.
 Whether 16 GiB per rank is affordable is a separate question from whether it is representable.
On a node where 12 ranks share 128 GiB of CPU memory, a 16 GiB routing buffer is already
substantial alongside the send buffer and the solver’s own data. Exchanges beyond this point call
for staging the records that enter CR, rather than enlarging the buffer that holds them, which is
the approach taken in the two sections that follow.

2.3 Batched Restart Redistribution

Restart reads a checkpoint whose file ownership need not match the current mesh partition. Reader
ranks take elements in file order through MPI I/O, then redistribute them to their owning ranks

 4

through CR or MPI RMA. Each owner gathers its incoming elements in a temporary buffer and
copies or interpolates their values into the solution fields. Reading, redistribution and assignment
are three separate passes over the data.
 Keeping them separate obliges every rank to hold its entire incoming field at once. That field
is not bounded by the solution it will become. A checkpoint may carry a higher polynomial order
than the current mesh, or store 64-bit values where the solver keeps 32-bit ones, so the arriving
data can exceed the fields they are read into. Reserving a buffer of that size, for a phase that runs
once at startup, is a poor use of memory that the solver needs for the run itself.
 Batched restart (bRestart) interleaves the three passes instead of separating them. Each reader
keeps its original assignment of checkpoint elements but loads them a batch at a time, and each
batch is redistributed and assigned before the next is read. A batch need not be balanced across
destinations, so an owner may still be sent more elements than its receive buffer holds. A handshake
settles this before any data moves, and it is itself two CR exchanges. In the first, each reader
sends one small tuple per owner, reporting how many elements it holds for that owner, so every
owner learns who will write to it and how much. The owner places the arrivals in a combined order,
divides that order into rounds that fit its buffer, and assigns each sender a base offset within the
stream. The second exchange routes those offsets back. Readers then know which elements to send
in which round, and after each round the owner assigns the received values and reuses the buffer.
The handshake moves only counts and offsets, so its cost does not scale with the element data it
schedules.

 The two loops are independent. The read batch bounds how much of the file is resident, while

2.4 Batched Field Interpolation with gfldr

Nek5000’s general file reader, gfldr, interpolates fields from a checkpoint mesh (source) onto the
current simulation mesh (target). Algorithm 4 summarizes its workflow: read the source mesh,
locate all target points, then read and evaluate each requested field. Algorithm 3 expands the setup,
location, and evaluation stages of findpts [16, 4, 5]. Setup divides the global source bounding box
into hash cells and distributes a table from cells to candidate source ranks. A rank registers with a
cell when any of its elements reaches into it, judged by the element’s axis-aligned bounding box
(AABB), enlarged by a small tolerance so that points on a face are not missed.
 Point location narrows a query in three steps. The global table gives the candidate ranks for its
cell, and the query is copied to each. A rank-local hash then gives the candidate elements, which are
tested against their oriented bounding boxes (OBBs) before Newton iteration finds the containing
element and the reference coordinates. An OBB follows the element it encloses, so it wastes far less
space than an AABB on a curved or oblique element and rejects a false candidate the AABB would
admit [16]. Only these last steps see one. Both hashes are built from AABBs, because a cell records
a union of boxes, and only the axis-aligned union is itself a box. An element therefore claims whole
cells it does not fill, and every rank registered with a cell receives a copy of every query landing
there. The first field evaluation sends these locations to their source element owners and caches
them there. Subsequent fields reuse the cache, so each costs a single return transfer rather than a
round trip.
 Every one of these stages moves its data through CR, so a single gfldr call issues at least six
exchanges, and one more for each field after the first. They are not the same size. A query that the
hash cannot resolve to a single owner is copied to every candidate rank registered with its cell, so
the stage that forwards queries to candidates carries several times the records that entered it. That
stage is the one that overflows first, and Section 3.2 measures by how much.
 Batched gfldr (bGfldr) leaves the source side untouched and batches only the target side, as
shown in Algorithm 5. The source mesh is read once and findpts setup builds its hash once, over
the whole mesh. What repeats is the query: target elements are divided into batches, and each
batch is located and evaluated before the next begins. All ranks agree on the number of batches
beforehand, since findpts and findpts eval are collective. Fewer queries enter CR at once, so
both the size of each transfer and the peak a rank holds mid-route fall in proportion.
 The batch size is supplied by the caller rather than derived from L, so it must be chosen small
enough for the intended rank count, and a size that works at one scale need not work at another.
The cost is paid in reading. Because a batch is a subset of the targets but not of the sources, every
batch needs the whole source field again, so each reader rereads its full share from the checkpoint
and converts it once per batch even though only one batch of targets consumes it. File input and
point routing are therefore repeated b times while the source field buffers keep their original size.

3 Case Study: OpenMC-to-Nek
3.1 The Transfer

In the ITER WCLL blanket calculation, OpenMC [17] supplies spatial heating and isotope production
rates for the Nek simulation. It stores these fields as cell-centered data, one field per file, on 5,706,830
tetrahedra, and converting each tetrahedron into four linear hexahedra yields 22,827,320 source
elements. We use gfldr to interpolate them onto 162,313,460 spectral elements of polynomial
degree N = 3. At (N + 1)3 = 64 points per element, that is 10,388,061,440 point queries, counting
points shared between neighboring elements.
 Because the meshes differ in resolution and element size, queries from many target ranks map
to the same hash cell, and so to the same candidate source ranks. Point location concentrates CR
traffic even though the target mesh is balanced. In the unbatched run the exchange that copies
queries out to their candidate ranks, line 5 of Algorithm 3 and known in gslib as src pt, is the first
to exceed the 2 GiB MPI count limit. It is the stage Section 2.4 predicted would overflow first.

3.2 Diagnosing the Peak

bCR raises the supported capacity eightfold, and this case still exceeds the per-rank accounting
limit. The run that failed used P = 1,200 ranks. To find where the data collected, we logged the
sender, receiver and transfer size in every CR round of that run, and Figure 2 plots the result, panel
(a) over all rounds and panel (b) enlarging the last five. Each column gives the packed data held by
each rank entering a round, the leftmost being the initial record volume, and dot area scales with
that volume. Arrows are transfers, labelled in the enlargement with their size and, where a transfer
was split, the number of MPI chunks. Values labelled “GB” in the plots are in GiB. Read left to
right, the picture is of a load that starts even and ends concentrated on a few rows.
 Each record holds three double-precision coordinates and three 32-bit integer fields, which
structure padding rounds from 36 to 40 bytes. One record per target point would then need
40E(N + 1)3 /(P 230 ) = 0.322 GiB per rank. The measured starting volume is 2.23–2.88 GiB per
rank, a mean of 2.54 GiB and roughly eight times the estimate. The excess is candidate-rank fanout.
Each source rank registers with every hash cell its element AABBs touch. For a query in that cell,
the hash owner makes one copy for each distinct candidate source rank, yielding 7.89 routed copies
per hashed query on average. Thus, several ranks registered with the same cell increase the record
count even if some of their elements do not contain the query point. The OpenMC elements are
not ordered spatially in the file, so a reader rank owns elements scattered across the domain and
registers with cells all over it. The log cannot separate how much of the fanout this contributes
from how much comes from AABB overlap.
 The routed data then accumulate unevenly. A rank retains some records each round and
receives others, and the sum is what it holds going into the next. Rank 39 in Figure 2(b) shows the
pattern over its last six rounds, holding 5.0, 7.4, 12, 13, 8.5 and finally 18 GiB. The volume climbs
well past what the rank began with, and several of the transfers feeding it were large enough that
bCR had to split them, in one case into five chunks.
 Rank 41 climbed further, to 25.72 GiB, and the run aborted there on the UINT MAX check in
sarray transfer, which guards the 32-bit row accounting and corresponds to just under 16 GiB.

3.3 Batched gfldr with Batched CR

Because bCR alone could not keep rank 41 below the per-rank limit, a later run combined it with
batched gfldr (bGfldr), which reduces the records entering the router in the first place. On 250
Frontier nodes (P = 2,000), bGfldr was given a batch of 8,192 target elements per rank, or 524,288
query points at N = 3. The target mesh then took about ten batches, and the transfer completed
in 775.974 s. This is a preprocessing step and is performed only once. As soon as the fields reach
the target mesh we write a checkpoint on that mesh, so every later run reads it with the ordinary
bRestart path at a cost of 4.00992 s, with no interpolation repeated. The large timing gap motivates
the future improvements discussed in Section 4.

4 Conclusion and Future Improvements
Section 3 leaves two costs unaccounted for. The router carried far more than any rank began with,
and findpts generated far more records than there were query points. These are separate problems
at separate levels, so we take them in turn: what could be changed inside CR, and what could be
changed in the stage that feeds it.

4.1 Improving CR

Radix-r CR. Splitting the active group into r parts per round instead of two reduces the round
count from log2 P to logr P , at the cost of r − 1 partners per round rather√ than one. This is the
classical radix generalisation of logarithmic all-to-all [18], for which r ≈ P is near optimal [19]
and a tunable-radix non-uniform variant already exists [6]. Applied to CR it would trade message
startups against messages per round in the usual way.
 Peak occupancy is the less familiar consideration, and it does not favour a large radix. Suppose
every rank enters a round holding V bytes with destinations otherwise uniform. It retains about
V /r and receives (r − 1)V /r, so a rank that receives twice its share finishes holding

the cut order so as to minimise the largest retained-plus-received volume in any round. Partitioning

 A full bisection tree computed in advance is not the only option. The split point, the partner,
and the membership test are all local arithmetic on the current group bounds, so a group could
equally be divided by a greedy choice made in the round itself, using the traffic the rank can already
see. The result would be suboptimal for the recursion as a whole, since a choice that flattens one
round may leave a worse group for the next, but it avoids building and distributing a tree. What
matters for cost is only that each split stays even: any balanced bisection keeps the round count at
log2 P , and rank ordering is merely the cheapest way to obtain one. The price is that halves would
no longer be contiguous rank intervals, so the single comparison that decides whether a record
moves must become a set membership test.

Two-level CR. Node-aware decomposition is well established for MPI all-to-all and MPI Alltoallv [6,
23, 24, 25]. What we propose is its application to CR. The node-local all-to-all would run first,
each of the eight ranks on a Frontier node passing records to the local rank whose ID matches the
destination’s node-local ID. Eight CR channels would then carry one rank per node, and a record
would travel only within its channel, with no node-local exchange afterwards. The channels are the
lane communicators of [23] in a different setting. Moving the local exchange to the front should
reduce the late-round peaks that dominate Figure 2, and shrinks each channel’s communicator
from all ranks to one rank per node, though the early exchange may itself create an uneven load.
Schliephake and Laure give measured motivation, reporting CR taking 59% longer at a stride that
places every partner off-node [8].
 None of these three changes the volume that finally arrives at a given rank. Routing determines
the path, not the destination, and in the gfldr case study it is findpts that assigns records
unevenly to candidate source ranks. Rank 41 would still receive 25.72 GiB, and would still exceed
the accounting limit, under any of them.

4.2 Improving gfldr

Since routing cannot change what arrives, the remaining lever is to generate fewer records. Two
strategies would do so, both acting on the candidate list that Section 2.4 describes.

Order the candidate search. findpts already searches locally before routing a query, and
omits the originating rank when making remote copies, so the observed 7.89 copies per hashed
query is what remains after those optimisations. The global hash records only whether a rank has
an element AABB touching a cell. Recording the number of such AABBs would allow a query
to be sent first to the candidate with the largest count, stopping there on an interior match and
continuing in count order otherwise. This uses source-mesh information already available when the
hash is built, and needs no knowledge of which rank will succeed.
 Whether it pays depends on the first-candidate hit rate, which we would measure along with
the resulting receive-load distribution. A large AABB count does not guarantee a match, least
of all for thin or oblique elements whose boxes cover little of the cell they claim. Turning one

 11

speculative broadcast into a ranked sequential probe also appears to cost latency, although evidence
from selective search in distributed retrieval suggests ranked probing can improve both latency and
throughput over an exhaustive scan [26, 27]. A tighter element bound is a third possibility, but
not at this stage: oriented boxes already reject candidates after a query arrives, and Section 2.4
explains why a hash cell can record only axis-aligned ones.

Partition the source mesh. Repartitioning the checkpoint source mesh with recursive coordinate
bisection (RCB) would give each rank spatially nearby elements, so that neighbouring elements
sharing a hash cell produce one candidate-rank entry instead of several. Making point location local
by repartitioning is the rendezvous algorithm of Plimpton et al. [28], realised as a library in [29].
What we describe is narrower. Classical rendezvous builds a third decomposition covering both
meshes and removes the remote search altogether, at the cost of holding mesh copies, which is the
memory this case cannot spare. Repartitioning the source alone keeps the global hash and targets
only the candidate-rank count per cell.
 RCB does not change individual element AABBs, so it cannot remove false candidates caused
by thin or oblique elements, and its benefit depends on how much of the observed fanout comes
from scattered ownership rather than from box overlap. Implementation would mean reading the
source mesh, computing the partition with parRSB [3], and redistributing elements and field values
through CR. A variant balancing physical volume rather than element count could, for spatially
uniform queries, balance the successful locations and the interpolation that follows, though not the
speculative searches. Either variant suits repeated transfers, which amortise the repartitioning, and
neither suits NekNek, where the source mesh must keep its existing partition.
 The same over-approximation appears in other remap libraries. Portage found that a single
bounding box per source partition could migrate nearly the whole source mesh onto one rank, and
replaced it with a depth-tunable tree, cutting migrated cells by about an order of magnitude [30].
A finer geometric description of the source is therefore a third lever, alongside ordering the search
and repartitioning.

4.3 Conclusion

Batching let an exchange that had previously failed run to completion. Chunking inside the router
removed the 2 GiB limit on a single MPI call and benefits every caller, while batching at the
application level kept restart and gfldr within their buffers. The runtime traffic log was what made
the remaining failure legible, attributing it to candidate-rank fanout in findpts rather than to the
router carrying the records.
 That diagnosis also orders the five proposals above. The three router changes would move
records more evenly but cannot alter how many arrive, so none of them would have saved the
case study. The two findpts changes act on the 7.89 copies per query that the router is merely
delivering, and because findpts serves NekNek as well, a reduction there benefits both callers, as
Section 2.1 anticipated. Of the two, repartitioning the source mesh looks the more promising here.
The OpenMC elements are not ordered spatially in the file, so a reader rank owns elements scattered
across the domain and registers with hash cells all over it, which is exactly the condition a compact
partition would remove. Ordering the candidate search remains the cheaper experiment, confined to
the hash table and its use, with a first-candidate hit rate that can be measured before anything is
