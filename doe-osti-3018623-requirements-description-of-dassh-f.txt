1 Introduction
 This report reviews the modeling and simulation capabilities of Argonne National Laboratory’s
DASSH [1] code that is used in present reactor analysis activities. These capabilities will be used
to establish the set of verification tasks necessary to verify DASSH for use on commercial projects.
A similar approach was taken for the PERSENT [2], REBUS [3] and DIF3D [4][5][6][7] software
packages.
 The DASSH program is a thermal analysis code designed to rapidly allow a reactor design
engineer to obtain flow rates requirements that satisfy peak temperature constraints in the domain.
DASSH is a follow-on development to the SE2-ANL software [8] and SUPERENERGY-2 [9]
software that it is based upon. DASSH was designed to account for both neutron and gamma
heating and is inherently connected to the GAMSOR [10] part of the ARC suite of fast reactor
analysis software [11]. SE2-ANL is a developed piece of software from the 1980s while DASSH
is a modern implementation with notable improvements in geometry handling. The most important
upgrade of DASSH relative to SE2-ANL is that it can analyze multiple time points in a single run
where SE2-ANL can only treat a single time point. This allows the user to understand the impact
of and search the flow distribution for the entire operational period of a reactor design considering
pressure drop, peak coolant and fuel temperatures, and thermal striping.
 DASSH has three input paths that have to be verified. The first input path builds the geometry
and power distribution based upon the DIF3D model but ignores the gamma heating aspects of the
problem. The second input path also builds the geometry from the DIF3D model but it takes the
neutron and gamma heating distributions from GAMSOR. The third input path is to take the
geometry and power distribution directly from user input (i.e. not coupled to DIF3D or GAMSOR).
DASSH also has many built in correlations for material properties along with a user defined
specification of the fuel, structure, and coolant properties. There are correlations for flow split,
mixing, pressure drop, and heat transfer coefficients (subchannel rather than a direct
methodology). In total, verification of DASSH will require an extensive testing to cover all
possible user features of the software.

2 Commercial Usage of the DASSH Software
 The DASSH program is part of the ARC (Argonne Reactor Code) system [11], and its usage
by commercial entities is application dependent. Figure 1 shows the preferred connection path of
DASSH in ARC for fast reactor analysis, noting that it is a necessary component if the overall goal
is to perform safety analysis of a proposed reactor design in the ARC system. With regards to using
DASSH, the ARC pathway shown is not a necessary component unless the commercial entity
chooses to make it part of their workflow, which would be covered by their own version of Figure
1. The breakdown in identifying the critical engineering outputs of the DASSH software normally
starts by looking at which outputs from DASSH are being used by the analysts in the design
process. For DASSH, the connected outputs are indicated, but its actual usage by users in the
design process is well beyond the simplicitity of Figure 1.

 2.1 DASSH Inputs and Outputs to Verify
 Beyond the DASSH input file, the additional files that DASSH can link to for any calculation
are shown in Figure 2. This figure shows the three inputs paths to defining a problem which can is
visualized as the three columns of files. All other inputs in the DASSH input file apply equally to
each input path shown here although some features are not available in the hand made power input
(right most column in Figure 2). The two columns on the left of Figure 2 show the files necessary
to connect DASSH to DIF3D. The ISOTXS and PMATRX files are produced by MC2 [12] for
most fast reactor applications with DASSH and more details can be found in [10],[13]. The
remaining files are outputs of DIF3D (or REBUS) noting that DASSH is only setup to connect to
DIF3D-VARIANT for the flux solution. The central column using the PMATRX is the expected
usage of DASSH in the workflow shown in Figure 1.

 Figure 2. DASSH External Input File Connection

 Many of the files listed in Figure 2 can be provided for several time points [1]. DASSH is a
steady state solver and the time point terminology refers to a set of snapshots evaluated as part of
regular fuel cycle analysis. In that regard, the user might want to provide power distribution
information for beginning, middle, and end of multiple consecutive cycles. The advantage of using
DASSH is that it can determine the orifice (assembly) flow rates that meet a set of temperature
constraints applied across all of the time points provided by the user.
 For convenience, the phrase “axial geometry mesh” will refer to both the axial geometry setup
when DASSH is connected to DIF3D or when those axial mesh sizes are specified with user_geom
inputs. Thus if the DIF3D model has 12 axial meshes, each of those will be referred to as axial
geometry meshes in this document. This is done because DASSH needs to define temperature
solution meshes within each of those axial geometry meshes that will be referred to as solver
meshes in this document.

 The TIME_OUTPUT input allows the user to redirect the screen output from DASSH for each
time point to a separate file. This is particularly important feature to use in flow search problems
with multiple time points. In the regular operation of DASSH, the iterative search on the flow will
simply dump all output to the screen and the user must then ignore a large amount of non-

                                                   4                                     ANL/NSE-26/1

converged output to find the output they are interested in. By using the TIME_OUTPUT option,
the iterative aspects are discarded for the coolant and pin temperature parts of each time point and
only the final converged result is provided. The easiest way to verify this feature is to not use
TIME_OUTPUT in a model and rerun using it and compare the final results which should be
reported identically in the outputs of the two runs.
 The PIN_POWER_2D and PIN_POWER_MONO output options will not be verified as they
are are duplicative of and inferior to the EXPORT_POWER interface file output of DASSH. In
that regard, EXPORT_POWER will be the primary focus for verification of the power distribution.
When connected to DIF3D, DASSH calls VARPOW as a subroutine and thus all aspects of how
the neutron and gamma heating distribution are defined in DASSH can be found in [13]. The
spatial dehomogenization of the power is covered in the DASSH manual [1]. It is difficult to
directly verify a detailed power distribution from DIF3D and thus the DIF3D interface files for
NHFLUX and GHFLUX will be manipulated to verify the power distribution that DASSH
computes. Most of the DASSH verification work will focus on using hand defined power
distributions via the POWER_IMPORT option of DASSH.
 The PYTHON_OUTPUT option must be verified as users will invariably rely upon the
pictorial representations it produces, rather than rely upon converting the DASSH screen output to
a similar capability. Because there is a one-to-one correspondence between the screen output in
DASSH to the outputs that appear in the Python script outputs and pictures that they generate, this
is a minor verification effort.
 The NUBOW_OUTPUT option must be verified as users that connect the DASSH outputs to
NUBOW will rely upon these outputs files to be correct. The output itself consists of geometry,
duct temperature, and duct fast flux details. The first two should be easy to verify against the
outputs of DASSH or the known geometry setup of a DASSH problem. The fast flux one can also
be done but will require use of EvaluateFlux [13].
 The DASSH output is quite extensive and the manual has sufficient examples of the output
that they are not repeated here. As a substitute, Table 2 lists all of the figure numbers from the
DASSH manual that detail the output of DASSH along with the page number to find the figure.
Many figures from the manual are not included because they are duplicates of those that were
identified here. The table summarizes the output from DASSH as a table name and the right most
column indicates what level of verification will be done on those outputs. For Figures 4.3 through
4.7, the output generated by DASSH is mostly just listing the input or outputs that are directly tied
to the geometric input the user provides. As an example, the pin area of a given assembly type is
produced which requires very little effort to confirm it is correct.
 Figures 4.8 through 4.11 in Table 2 are calculated results based upon the flow and expected
temperature rise for each assembly and thus is a calculated quantity for DASSH. The output in
Figures 4.9 through 4.11 are evaluated based upon the correlations built into DASSH and they
require independent verification against the expected results for the correlations to ensure the
results produced by DASSH are correct.
 For Figures 4.12 and 4.13, the output details are either not verifiable or not entirely important.
As an example, the power balance output is useful to understand how much power was delivered
to each assembly and how much was removed by coolant flowing through the assembly, but
verification of this detail is next to impossible to do because it requires more control over the

interassembly heat transfer than what can be achieved via user input. While interassembly heat
transfer can be disabled via input and even manipulated in a fashion that the trend matches the
expected behavior, calculating the exact number is entirely unrealistic.
 The active core outlet temperature results in Figures 4.14 and 4.15 can be verified directly
against the subchannel temperature output obtained from EXPORT_SCTEMP. However, being
able to hand compute it is very difficult again. While the input can be manipulated to make it an
analytic result by subchannel, it is not trivial to be able to compute a temperature distribution. In
that regard, the input can be manipulated and the verification of the trend away from isolated
channels can be confirmed. This inability impacts the verification of all other outputs from DASSH
and thus verification of the output against the full results obtained from EXPORT_SCTEMP is
used to confirm the output is consistent with the calculated results.

 The thermal striping output table in Figure 4.16 is rather straightforward to verify given the
bulk temperature output in Figure 4.14 is verified via the EXPORT_SCTEMP and displayed
subchannel flow rates. For the assembly temperature map outputs in Figures 4.14 through 4.15,
the output is again directly verifiable against the EXPORT_SCTEMP results provided by DASSH.
Because of the reduced accuracy of the output, the temperature maps will only be spot checked for
some assemblies of a few test problems rather than fully inspected.
 The peak fuel pin temperature and clad inner wall temperature results should be hand
calculatable given the EXPORT_SCTEMP result but for real problems with complex power
distributions this would be very difficult. It is noted that DASSH does not presently provide the
fuel conductivity used in the calculation when derived from a correlation, but this aspect can be
controlled and manipulated via input. In that regard, both the power profile, coolant temperature
profile, and material properties can be manipulated to allow the result to be verified completely.
Doing verification for the full results in an EXPORT_PINTEMP output from DASSH is again too
cumbersome and impractical to carry out although doable. Because a single pin from each
assembly can be detailed in the DASSH output both radially and axially in Figure 4.23, this will
have to be done for at least one full fuel pin and the various radial temperature profiles in Figures
4.22 and 4.33 will also have to both be hand calculated and verified against the
EXPORT_PINTEMP results. The outputs for Figures 4.19 and 4.20 will be simply verified against
the EXPORT_PINTEMP results provided by DASSH rather than explicitly recalculating them.
 The peak 2-sigma results in Figures 4.20 and 4.21 results require independently applying the
hot channel factor calculation on the pin being reported. Because DASSH does not check every
axial point in every pin, but only focuses on the observed peak point, a calculation will be done to
assess how much error is actually occurring because of this approach. In the recent switch to using
a clad mid-wall based hot channel temperature to a clad inner wall based hot channel temperature,
the axial location of the peak temperature was observed to move axially by ~1 cm in realistic
problems. As a consequence, it would not be surprising to find out that the 2-sigma hot channel
factor temperature has some amount of “error” associated with it because of the methodology used
in DASSH.
 The outputs in Figures 4.26 and 4.31 are just summary details of the preceding DASSH output
and are relatively easy to verify. From all of the above, the most time intensive aspects to verify
are the correlation evaluations and the subchannel and pin temperature calculations. These will
primarily be verified by manipulating the input to make the detail hand calculable.

 2.2 DASSH Identified Verification Tasks
 From the preceding output summary, there are a considerable number of outputs from DASSH
to verify. The preceding dissection and identification of the output informs a set of tasks to
accomplish as part of the verification work. Table 3 gives the identified task list for the verification
work where the category number refers to a specific capability of DASSH. As seen, the set of
verification tasks correspond to each output coming from DASSH and the outputs appearing in
each task category are listed as verifiable tasks. As this pertains to the entire engineering output
available from DASSH, no additional discussion is needed. In practice, the companion verification
document will work through each verification test problem that is created and selectively
demonstrate how the above tasks are satisified by the verification problem and which output from
DASSH is being verified.

3 Conclusion
 This manuscript described the DASSH capabilities that can be used by commercial entities.
The engineering output created by the DASSH capabilities were discussed where heavy reliance
on the manual was used to avoid duplication of the figures. These engineering outputs helped
define requirements from the software that were used to create a verification task list. No proposed
verification problems are discussed in this report and it should be clear that a majority of the
verification will rely upon contrived or manipulated inputs such that available analytic solutions
can be used. For the various correlations, contrived inputs that are consistent with the measurement
or reported results in the references for the correlation will have to be constructed for the
verification work.
 The verification work will be carried out on the latest release of DASSH and collected into a
final report similar to that done for DIF3D [14]. That report will be updated with each consecutive
version of DASSH. It is unlikely that any existing features identified here for verification will be
removed at this time but it is likely that new features will be added that require modifications to
this document and the verification report that is linked to it. The verification work will yield a set
of new verification test problems that will be included in the routine verification of the software
such that it is both repeated and distributed for all future DASSH releases and operating
environments.
