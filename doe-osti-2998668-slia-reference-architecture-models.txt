Executive Summary
The SLIA Reference Architecture Models project, sponsored by the DOE CESER Energy CyberSense
Program (Oct 2024–Sep 2025), advanced LLNL’s PySCES simulation tool to better support CyTRICS
Prioritization and Initial Risk Assessment (PIRA) reference architectures. Key achievements include
enhancements to the PySCES transmission substation facility model, expanded asset coverage,
and enhancements to the PySCES code base. Software improvements reduced code complexity,
migrated PySCES to Python version 3.11, introduced an object-oriented design, and added a
schema database for easier updates and validation. New features support device criticality
assessments and a more precise parametric simulation mode. Remaining gaps include model
validation, workﬂow limitations, Monte Carlo convergence issues, full device criticality metric
implementation, model ﬁdelity, and general software improvements. Continued development is
recommended to address these gaps and fully align PySCES with CyTRICS PIRA requirements.

Introduction
This document describes the work undertaken and results of the System Level Impact Analysis
(SLIA) Reference Architecture Models project. The project is sponsored by the Department of
Energy (DOE), Ohice of Cybersecurity, Energy Security, and Emergency Response (CESER) Energy,
CyberSense Program, and the period of performance was October 2024 – September 2025. This
document is organized as follows: the background of the project is discussed ﬁrst, followed by a
discussion of model enhancements, code enhancements, and a brief outline of device criticality
metrics. The report concludes with a discussion of gaps and next steps.

Background
The purpose of the SLIA Reference Architecture Models project is to develop modeled
representations of Cyber Testing for Resilient Industrial Control Systems (CyTRICS) Prioritization
and Initial Risk Assessment (PIRA) reference architectures, incorporating new asset types and
enhanced depth models for sensitivity analyses in Lawrence Livermore National Laboratory’s
(LLNL) Python Simulator for Cyber Event Scenarios (PySCES) tool. These incremental
improvements to PySCES models and software are necessary to address the need for a systematic,
analytically informed prioritization method for CyTRICS analyses, moving beyond reliance on
individual Subject Matter Export (SME) knowledge.

PySCES is a Python-based simulation tool for assessing cyber-attack impacts on industrial control
systems in Critical Infrastructure (CI). It uses vendor-agnostic models, integrates with commercial
energy simulators, and rapidly simulates vulnerabilities from Common Vulnerabilities and Exposure
(CVE), Common Weakness Enumeration (CWE), and MITRE Adversarial Tactics, Techniques, and
Common Knowledge (ATT&CK) frameworks. PySCES provides system-level risk metrics and
supports quick, large-scale analysis to inform users of infrastructure resilience and risk mitigation.

In PySCES, CI devices and facilities are modeled with MathWorks’ Simulink tool, while larger-scale
systems are modeled in commercial simulators such as PowerWorld and Synergi Gas. Users
typically invoke PySCES from a command-line, which launches either an interactive Graphical User
Interface (GUI), or a non-interactive, batch-oriented session. PySCES simulations generally
proceed as follows:

 1. Consume user input that describes the speciﬁc device manipulations representative of a
 cyber-attack of interest,

 2. Obtain the steady state solution of the system level model (e.g., a collection of connected
 electric substations), populate the state of the facility and device models based on the

 11

 system level model state, and compute a variety of metrics of the system in this pre-
 attacked state,

 3. Apply user-speciﬁed device manipulations and re-compute the facility states,

 4. Propagate facility states to the system level model, obtain its solution under the augmented
 conditions, and re-compute the system metrics in the post-attacked state,

 5. Compute the diherence between the pre-attack and post-attack metrics and return them to
 the user.

While minimally complete to support rudimentary system analysis, PySCES facility models do not
include some components from the CyTRICS PIRA reference architectures, nor does PySCES
explicitly implement support for speciﬁc device criticality assessments; both limitations may ahect
the use of PySCES in the context of CyTRICS risk assessment processes. Thus, enhancements to
PySCES are needed to better align it with the PIRA reference architectures and use cases. The next
section describes the model enhancements undertaken in this project.

Model Enhancements
To align PySCES with the CyTRICS PIRA reference architectures, the PySCES modeling team
implemented several enhancements to the PySCES-Simulink facility models. The enhancements
focus primarily on the PySCES model of a transmission substation. The following sections detail the
adaptation of the PySCES transmission substation facility model to the PIRA reference
architectures. This includes a review of existing components, the rationale and selection of new
components, implementation and integration of these components with the PowerWorld simulator,
and the application of cyber-attacks to assess potential impacts. Modiﬁcations to the PySCES
model topology to support larger substation instances are also described.

Justiﬁcation of Model Adjustments
Several components were missing from the PySCES transmission substation model that PIRA has
highlighted as relevant to the operation of a substation. In this review, transformer tap changers and
static var controllers (SVC) were identiﬁed as the most signiﬁcant for the intended purpose and
application of PySCES. Although SVC was not implemented at this stage, it is identiﬁed as a
promising candidate for future model enhancements and would likely be incorporated in a manner
similar to the approach taken with tap changers.

Transformer Tap Changer: Tap change controllers in power grids are critical components that
regulate voltage levels by adjusting transformer tap positions, ensuring stable and ehicient power
delivery. According to recent studies, these controllers are increasingly vulnerable to cyber-attacks
due to their integration with digital communication networks and remote-control capabilities.
Attackers can exploit security weaknesses in protocols and software to gain unauthorized access,
manipulate tap settings, and disrupt voltage regulation, potentially causing equipment damage,
system instability, or widespread outages. The literature highlights that insuhicient authentication,
lack of encryption, and outdated ﬁrmware further expose tap change controllers to threats such as
denial-of-service attacks, malicious command injection, and coordinated assaults targeting grid
reliability (Tusher, Rahman, & Islam, 2024), (Chakrabarty & Sikdar, Detection of Hidden Transformer
Tap Change Command Attacks in Transmission Networks, 2020), (Anwar, Mahmood, & Ahmed,
2015).

In the PySCES PowerWorld model, transformers were operating at ﬁxed tap change ratios and not
implementing voltage regulation features such as LTC or MVAR. The PySCES-Simulink Transmission
substation model did not include a tap changer or tap change controller. Incorporating this device
into the PySCES framework would allow users to examine the impact of various cyber
vulnerabilities like blocking command messages, modify parameters to alter tap changer
operation, or false data injections on voltage feedback measurements, which can potentially
impact controller logic and tap changer setpoints.

SVC: Static Var Compensators (SVCs) are designed to provide rapid reactive power control, both
injection and absorption, using a thyristor-controlled reactor (TCR) and thyristor switched capacitor
(TSC). However, as with tap changers, their increasing reliance on digital control systems and
networked communications makes them susceptible to cyber-attacks. Cyber attackers targeting
SVCs can disrupt their operation, leading to voltage instability, reduced power quality, and even
cascading failures across the grid. The existing literature emphasizes that without robust
cybersecurity measures, such as secure ﬁrmware, encrypted communications, and regular system
monitoring, SVCs remain exposed to threats that could compromise grid reliability and safety
(Chen, Butler-Purry, Nuthalapati, & Kundur, 2104), (Chakrabarty & Sikdar, Detection of Malicious
Command Injection Attacks Against Static Var Compensators in Smart Grids, 2024).

 SLIA Reference Architecture Models – Project Report 16

In PowerWorld, SVCs are currently modeled as switched shunts with automatic control, regulating
either voltage or generator MVAR, and there is an option to enable SVC-speciﬁc control. Potential
vulnerabilities include reporting attacks, where measurements sent to the SVC are intercepted and
altered, and command attacks, where ﬁring angle commands to TSCs or TCRs are modiﬁed or
blocked. There are several questions that need to be addressed, such as whether the control is
centralized or local (closed-loop feedback), which measurements are most relevant for SVC
operation, and how ehectively the fast response to transients, like voltage ﬂicker, can be captured
in PowerWorld’s load ﬂow analysis. Additionally, it is important to understand how SVC control
interacts with on-load tap changers (OLTC).

Omitted components: Certain components present in the PIRA model of a transmission
substation were determined to be beyond the intended scope of PySCES. These can be classiﬁed
as passive infrastructure, maintenance-related elements, or components that are not considered
primary attack vectors. Passive infrastructure, such as lightning arresters, do not present direct
cyber vulnerabilities because they are not digitally connected. Maintenance activities often involve
devices like motor operated disconnect switches (MODS), which are typically used to isolate parts
of the substation during servicing. While an attack on MODS could result in incorrect portions of the
grid being de-energized, their function is adequately represented in the model by the circuit
breakers and relays. Video cameras serve mainly to monitor and detect threats, but they are not
essential for real-time operations. If these cameras are tampered with, operators may miss attacks
on other components, but the cameras themselves are not critical. The dissolved gas analyzer
(DGA) in a transformer is another component that could be targeted; an attack could suppress
alarms during maintenance issues, provide misleading information for lifetime prediction, or trigger
false alarms. The ﬁrst two scenarios could lead to transformer failure, while the third might cause
unnecessary equipment shutdowns for maintenance checks. In PySCES, the impact of such an
attack can be simulated as a transformer failure or shutdown but modeling the operation and a
direct attack on a DGA was determined to be out of the scope of the PySCES tool. The summary of
these ﬁndings is presented in Table 2.

Transformer Tap Change Controller
Tap change controllers play a critical role in power grids by adjusting the tap ratio of transformers to
regulate voltage levels and manage power ﬂow between diherent parts of the network. These
devices, found in load-tap-changing (LTC) and tap-changing-under-load (TCUL) transformers,
ensure stable voltage and reliable operation by automatically responding to voltage deviations.
However, as these controllers become more automated and interconnected, they are more
vulnerable to cyber-attacks. If compromised, attackers could manipulate tap settings or spoof
measurements, potentially causing voltage instability, equipment damage, or widespread
disruptions in the power grid. In this context, the PySCES tool would be useful to explore the system
level impacts of a compromised tap controller in a substation.

Previously, the PySCES model of a transmission substation did not include transformer control: the
PowerWorld model used ﬁxed tap change ratios for transformers and did not implement voltage
regulation features like LTC or MVAR control. To incorporate a transformer and tap changer
controller into PySCES, several key questions need to be considered:

 • Which transformers in the PowerWorld model could be targeted in an attack?

 • How can transformer tap controllers be simulated accurately, including the type of control,
 required parameters, and necessary measurements?

 • Finally, how can simulated cyber-attacks on the tap controller be modeled?

Tap Controllers in PowerWorld

The PowerWorld solver involves three nested loops: the Power Flow Loop (red), Voltage Control
Loop (green) and MW control loop (blue) which are responsible for solving the basic power ﬂow
equations, adjusting the devices regulating voltage (i.e., transformer tap changers, generators,
shunt capacitors) and balancing area interchanges to meet system objectives, respectively. The
solver starts with an initial guess then iterates through these loops to update the guess until the
solution converges.

Figure 2 – The PowerWorld solver is implemented as a series of nested loops that compute power ﬂow,
control voltage, and control power generation.

In the Voltage Control Loop, PowerWorld implements tap controllers for voltage regulation by
allowing transformers to automatically adjust their tap positions in response to changes in system
voltage. The software models load tap-changing (LTC) transformers, which monitor the voltage at a
speciﬁed bus and change the tap ratio to maintain the voltage within a deﬁned range. Users can
conﬁgure control parameters such as target voltage, deadband, and tap step size. When the
monitored voltage deviates from the setpoint, the tap controller raises or lowers the tap position to
restore the voltage to the desired level, simulating real-world automatic voltage regulation in power
systems. Note that while PowerWorld can iteratively compute the tap value of a transformer, the
Simulink model of the tap changer only performs a single calculation and does not incorporate any
voltage feedback.

Modifying transformers in PowerWorld: Transformers in PowerWorld can be conﬁgured as Fixed,
LTC, MVAR, or Phase. To manually adjust its tap value, the transformer must be operating in Fixed

 19

mode. To change the controller type between Fixed and LTC, PowerWorld must be in EDIT mode (as
opposed to RUN mode), which can be set programmatically via SimAuto1.

Selecting only sensitive transformers: PowerWorld automatically disables LTC transformers that
do not signiﬁcantly impact the voltage at the regulating bus. This is quantiﬁed by a voltage-to-tap
(V2T) sensitivity which indicates how much the voltage magnitude at a regulated bus changes in
response to a change in the transformer's tap ratio. A high sensitivity value (closer to 1.0) indicates
the transformer is ehective at controlling voltage, while a value near 0 signiﬁes the transformer is
largely inehective. Initially, there was no means to calculate this value on the ﬂy via the Python
SimAuto add-on. One strategy to overcome this blocker is to compute the V2T sensitivity for all
buses relative to all transformers directly in PowerWorld’s “multiple meters, multiple control
change sensitivity” panel. The resulting matrix (number of buses x number of transformers) could
then be exported to Python and the regulating bus with the largest positive V2T for a given

Transmission Substation Model Expansion
In addition to adding the tap change controller to the PySCES-Simulink Transmission substation
model, the model was expanded from supporting 10 buses to 20 buses to address limitations
identiﬁed during system-level and facility-level simulations. In synthetic grid models, many
substations have more than 10 connected elements—including generators, loads, branches, and
shunts—each occupying a bus space in the Simulink model. The previous 10-bus limit caused the
exclusion of additional model sub-elements when populating simulation parameters, leading to
incomplete facility representations. This resulted in inaccurate simulation outcomes, such as
inﬂated impact results from cyberattacks or unexpected impacts during normal, steady-state
operation.

A review of PowerWorld system models showed that many facilities have more than 10 connected
elements. Table 6 summarizes bus characteristics for ﬁve publicly available synthetic PowerWorld
models, including the number and percentage of facilities with more than 20 connected elements.
Smaller models often have a higher percentage of nodes exceeding the 10-element threshold.
Without expanded bus capacity, PySCES cannot accurately simulate these substations, which
increases the risk of false positives and misrepresenting cyber-attack impacts. Figure 10 shows the
top-level of the expanded 20-element Simulink substation facility model.

The expansion from 10 to 20 buses required several technical changes:

 • Extensive rewiring and creation of new connections to support additional buses, resulting in
 hundreds of new signals and signal routing paths.

 blocks, Figure 11.

 • Updates to all six ICS device models to manage new signals and routing requirements,

 • Rewiring of simulated protection relays to integrate with the increased bus capacity.

 • Modiﬁcations to the PySCES code to ensure elements are properly assigned to buses in the

These upgrades are critical for the accurate simulation of device-level manipulations and their

that a bus will be incorrectly modeled, as shown in Table 6. This ensures that analysts can conduct

PySCES Code Enhancements
The PySCES software development team produced eight releases between December 2024 and
September 2025. The releases closed a total of 38 issues related to code refactoring, unit testing,
continuous integration, bug ﬁxes, and new features. Average cyclomatic complexity of the
codebase was reduced from 13.1 to 4.3, which indicates reduced risk of bugs and improved
structure. PySCES was also migrated from Python version 3.7 to 3.11.

To enable a device criticality feature in PySCES, the team migrated PySCES to an object-oriented
design and designed a new parametric mode for more precise control over simulation behavior.
This enhancement was necessary because the existing PySCES “batch mode” relies heavily on
random sampling from a uniform distribution, resulting in stochastic outcomes. To improve
ﬂexibility and maintainability, a schema database was introduced to separate the hard-coded
structural details of entities such as facilities, attacks, devices, simulators, and others. These
entities are now deﬁned within the database, and a dedicated programming layer was created to
access this information. This approach streamlines updates, as structural changes to the PySCES
schema will no longer require code modiﬁcations; it also enables validation of data used by
parametric mode. Additionally, new data abstraction and validation layers were developed to
support device criticality assessments. Finally, a prototype implementation of the PySCES
parametric mode was started.

The following sections describe a subset of features that were designed and/or implemented in
PySCES during the project: speciﬁc facility targeting, data abstraction and validation layers, and
parametric mode.

Speciﬁc Facility Targeting
A new feature was implemented in PySCES to give analysts the option to directly select which
facilities or sets of facilities to target during simulations. Previously, facility selection was based
solely on a Monte Carlo process, which randomly chose facilities for each run. With this
enhancement, analysts can choose between the traditional random approach and a targeted
method, allowing for greater ﬂexibility and control of simulation input parameters. This change
improves coordination with external tools that identify critical infrastructure, making it easier to
focus on high-priority facilities. As a result, PySCES is better suited to additionally support projects
that require detailed assessment of speciﬁc or defense-critical infrastructure.

Data Abstraction and Validation Layers
PySCES currently operates in one of two modes: interactive or batch. Interactive mode enables
users, through a specialized user interface, to specify the exact system, facilities, devices, and

 31

attacks to simulate. However, interactive mode is not well-suited to running multiple simulations
due to its sequential nature and the time required to set up each scenario in the user interface.

Batch mode, in contrast, allows users to specify systems, facilities, devices, and attacks to
simulate from a command line interface, but only at a coarser granularity compared to interactive
mode. Batch mode is well-suited for executing many sequential simulations without user input, but
it is limited in its ability to provide ﬁne-grained control over speciﬁc attack parameters. In batch
mode, device attacks are simulated by randomly selecting values for device settings from a uniform
distribution, with no detailed control over how PySCES chooses these random values.

Device criticality studies using PySCES may beneﬁt from techniques in sensitivity analysis to
uncover relationships between simulation inputs such as parameters of cyber-attacks on devices,
and outputs such as loss of load or safety. However, neither interactive mode nor batch mode are
ideal for this type of study.

To address this limitation, the PySCES development team introduced a mechanism to expose ﬁne-
grained control over all simulation parameters to external systems. This allows systems as complex
as professional sensitivity analysis toolkits or as specialized as user-developed code to interact
programmatically with PySCES. Data abstraction and data validation layers were developed in
PySCES to support this level of control. The data abstraction layer deﬁnes a data input format and
an application programming interface (API) that allows external programs to construct PySCES
simulation input data. The data validation layer provides routines to ensure that data supplied via
the abstraction layer aligns with the PySCES data schema. Figure 14 describes the relationship
between PySCES, external tools, the data abstraction and validation layers, and the underlying
data.

Parametric Mode
Parametric mode is a new operational mode in PySCES. The goal of parametric mode is to allow
analysts to construct speciﬁc cyber-attack scenarios on infrastructure systems by expressing, in a
data ﬁle, the ﬁne-grained manipulations of model parameters. This mode is accessed from the
command-line via a new “parametric” subcommand. A partial implementation of parametric mode
is available in the PySCES source code repository.

As described previously, parametric mode is fundamentally diherent from the existing interactive
and batch modes; in parametric mode, PySCES is treated as a programmatically controlled
simulator driven by speciﬁc model parameters rather than an interactive exploratory tool
(interactive mode) or a tool designed purely for Monte Carlo experiments (batch mode). In the
parametric input data ﬁle, analysts specify one or more runs, and each run can manipulate one or
more model parameters. A time component is associated with each manipulation; this component,
to be used in a future PySCES release, was added to address a limitation that forces all
manipulations to occur simultaneously, thus improving the ﬁdelity of PySCES simulations. Table 7

Deﬁning Device Criticality for PySCES and CyTRICS PIRA
The ﬁrst step in evaluating the criticality of industrial control system IEDs is to deﬁne what “critical”
means. This section brieﬂy describes two approaches to measuring IED criticality using PySCES.
Neither approach is currently implemented in PySCES.

One relatively simple approach to this task is to adapt an existing reliability index to PySCES
simulation outcomes. For example, the Average System Interruption Frequency Index (ASIFI) (IEEE
Guide for Electric Power Distribution Reliability Indices, 2022), designed to calculate reliability
based on load at the power distribution level, could be computed and tracked with each IED.
Concretely, during the evaluation of system level impacts of cyber-attacks on individual devices, a
per-device ASIFI value based on the attack-induced load loss can be computed and stored. After all
simulations are completed, IEDs are sorted by their average ASIFI score; devices with a higher
average ASIFI score are considered more critical than others.

Another approach is to develop an entirely new deﬁnition that is aligned to both the operation of
PySCES and its use in the context of the CyTRICS PIRA process, where both information from SMEs
and PySCES should be combined. To begin building this deﬁnition, several factors are deﬁned:

 1. Impact Factor: Quantiﬁes the operational consequence of IED compromise. Assign a value
 based on the device’s role (e.g., protection relay = 5, RTU = 3, meter = 1).

 2. Exposure Score: Measures network accessibility. Assign values based on network
 segmentation and external connectivity (e.g., directly routable from external network = 5,
 internal only with strong segmentation = 1).

 3. Vulnerability Score: Assesses susceptibility to novel network-based attacks. Use CVSS
 base metrics if available, otherwise assign based on device age, patch status, and protocol
 robustness (e.g., legacy protocol with no encryption/authentication = 5, modern protocol
 with full security features = 1).

These factors capture intrinsic features of devices driven by information from both SMEs and
speciﬁc facility deployments. Given these three factors, a new criticality metric can be deﬁned as
follows:

 SLIA Reference Architecture Models – Project Report 36

 IED Criticality Metric (ICM) = Impact Factor * Exposure Score * Vulnerability Score

A larger ICM indicates a higher criticality. This metric is then augmented with information from
PySCES. Three additional factors are deﬁned, combined, and applied to the ICM:

 1. Local Disruption: Fractional change in substation operational capability due to IED
 compromise (e.g., loss of protection, incorrect switching).

 2. Systemic Disruption: Fractional change in regional or grid-level performance metrics (e.g.,
 load loss, frequency deviation, cascading failures) attributable to the compromised IED.

 3. alpha, beta: Weighting factors reﬂecting the relative importance of local versus systemic
 ehects, determined by system operator priorities or regulatory requirements.

Deﬁne the Simulation Impact Modiﬁer (SIM) as follows:

  Simulation Impact Modiﬁer (SIM) = 1 + (alpha * Local Disruption + beta * Systemic Disruption)

The SIM component captures both the local and global ehects of IED cyber-attacks as calculated in
PySCES. Finally, the ICM and SIM are combined into the ﬁnal criticality metric:

 Device Criticality = ICM * SIM

This metric of device criticality combines information from SMEs and results from PySCES
simulations. It ohers the ability to tune the importance of facility and system-level disruptions. The
ICM component can be tailored to suit any available information from the CyTRICS PIRA process.

Gaps and Next Steps
Many gaps remain in the development of PySCES and its general use in the CyTRICS PIRA process.
Areas for improvement include:

 1. Model validation and correctness,
 2. PySCES-PowerWorld iterative workﬂow limitations that inhibit the simulation of certain
 types of attacks and induce problematic power imbalances,
 3. Monte Carlo method convergence limitations necessitating integration with uncertainty
 quantiﬁcation and sensitivity analysis tools, completion of parametric mode, and
 parallelization of PySCES simulations,
 4. Implementation of device criticality metric,
 5. Continued augmentation of PySCES-Simulink models to align with CyTRICS PIRA
 processes,
 6. Improvement of cyber-attack simulation ﬁdelity through integration of communications
 models and implementation of the time domain,

 7. General software architecture and resolution of bugs.

Model Validation
A key gap in the PySCES tool is a comprehensive understanding of the correctness of the facility
and device models. To address this gap, the PySCES model development team is currently
executing a model veriﬁcation and validation (V&V) process. The initial focus of this ehort is on the
Simulink substation facility model, where V&V ehorts are underway to ensure accurate signal
routing, correct block behavior under varied inputs, and realistic simulation of both electrical-
physical and cyber-attack scenarios. This process has already identiﬁed important changes that
will enhance the accuracy and reliability of PySCES simulations.

PySCES-PowerWorld Iterative Workﬂow Issues
As mentioned in the Attacking a Tap Controller section, while implementing the tap changer
controller in PySCES, a limitation was identiﬁed due to the tool’s workﬂow. The PySCES simulation
workﬂow involves these steps: (1) running an initial simulation in PowerWorld, (2) using the results
as input for a Simulink facility simulation, (3) attacking the Simulink model, and (4) sending the
results of the attack back to PowerWorld for a post-attack simulation. This workﬂow prevents the
simulation of certain attack types, such as block message and block command attacks, on devices
like the tap changer controller. These attacks require a system change to trigger the device’s
response. For example, the current setup cannot simulate a situation where a natural system
change prompts the tap controller to adjust the tap ratio to regulate voltage, but a malicious user
blocks this adjustment, causing the system to operate with an incorrect tap value during the
change. Signiﬁcant changes to the PySCES workﬂow are required to address this limitation.

Power Imbalance Issues with Simulink Substation Modeling
During V&V of the Simulink substation facility model, the PySCES model development team
observed signiﬁcant power ﬂow imbalances following successful simulated cyberattacks. The
dynamic load block, which models power ﬂow into or out of the substation facility-level model,
exhibited poor electrical waveform quality only after an attack resulted in the disconnection of one
or more breakers and no generator was present. In these post-attack scenarios, electrical
waveforms became highly erratic and deviated from the expected three-phase sinusoidal pattern.
In un-attacked states, waveform quality remained normal. The imbalance triggered protection
relays, causing all circuit breakers and ﬂow branches to disconnect.

To address these imbalances, a new algorithm is proposed for the facility-level simulation portion
of PySCES that integrates the PowerWorld energy solver with the Simulink facility-level model. This
recommended solution would iteratively balance power ﬂow after each simulated cyberattack
impact that results in a successful element disconnection, using PowerWorld to resolve facility-
level imbalances. Each iteration would incrementally adjust the system-level electrical
transmission model, introducing a time factor that better reﬂects real-world scenarios. Preliminary
testing on the ERCOT 2000 bus synthetic grid model indicates this approach could signiﬁcantly
reduce the severity of facility-level impacts, shifting outcomes from complete substation
disconnection to degraded operational states. The system-level cascading impact modeling would
remain unchanged, as power limits would still be enforced within PySCES. This solution is in the
proposal phase and has not yet been implemented.

Integrating Sensitivity Analysis with PySCES
PySCES batch mode can currently be used in a Monte Carlo (MC) method setting to identify trends
and vulnerabilities for risk assessment processes. Determining device criticality with unguided use
of MC is intractable due to the very large PySCES model parameter space and the associated slow
convergence (the “curse of dimensionality” phenomenon) – hundreds of thousands of simulations
are likely required to evaluate even moderately-sized systems. A more computationally tractable
approach is to utilize methods from the ﬁeld of Sensitivity Analysis to intelligently guide the
sampling of the model parameter space to determine input/output relationships. SA is necessary
but not suhicient for the device criticality task.

In addition to SA, a device criticality metric must be implemented in PySCES, and parametric mode
must be completed to enable integration with SA toolkits. Large-scale PySCES analyses are
currently limited by the speed of its down-stream simulators (i.e., Simulink, PowerWorld), and the
availability of simulator licenses (as this limits the available parallelism). Thus, to improve the
speed of these analyses, parallelization of PySCES simulations must be explored – this could
involve migrating PySCES to open-source simulators with HPC support.

Alignment of PySCES-Simulink Models with CyTRICS PIRA Reference
Architectures
This project evaluated the PySCES-Simulink transmission substation model for alignment with the
PIRA reference architecture, implemented a new device type in the PySCES-Simulink model, and
integrated it with PowerWorld. Several PySCES-Simulink facility models remain, each with
potentially several new device types. This model alignment work must continue, and methods for
improving the ehiciency of this alignment process must be studied so that new device types can be
rapidly added to PySCES-Simulink models.

Improving Cyber-Attack Simulation Fidelity
PySCES simulations currently do not involve the time domain. This implies that all device
manipulations associated with cyber-attacks occur simultaneously, which is unrealistic and likely
to produce inaccurate results. The time domain must be incorporated into PySCES to improve
simulation ﬁdelity; this will ehectively transform PySCES into a discrete event simulator. The
parametric mode design accommodates the time dimension, so completion of the implementation
of this mode should be prioritized.

Additionally, PySCES does not currently model communication networks. Many cyber-attacks
operate by accessing and/or manipulating the state of IEDs and telecommunication equipment
through communication networks. Thus, the lack of a communication network model reduces the
ﬁdelity of PySCES simulations because telecommunication equipment and connectivity between
devices and facilities is not accounted for in an attack. To improve the ﬁdelity of cyber-attacks, a

 41

communications model should be incorporated into PySCES. This task is relatively lower in priority
than others.

Improving General Software Architecture
PySCES was originally developed with a highly procedural design. This design introduced signiﬁcant
technical challenges to maintainability, modularity, and re-use. This project implemented several
design changes to migrate PySCES to an object-oriented design. This work must continue so that
the PySCES software architecture is easier to maintain and extend in the future.
