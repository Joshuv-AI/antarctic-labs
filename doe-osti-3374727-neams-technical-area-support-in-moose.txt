 1. EXECUTIVE SUMMARY

 The Multiphysics Object-Oriented Simulation Environment (MOOSE) framework is a

foundational capability used by the Nuclear Energy Advanced Modeling and Simulation

(NEAMS) program to create over 15 different simulation tools for advanced nuclear reactors. Due

to this ubiquity, improvements to the framework in support of modeling and simulation goals

are critical to the program. These improvements can take many forms, including optimization,

improved user experience, streamlined application programming interfaces (APIs), parallelism,

and other new capabilities. The work described in this report was conducted in direct support

of the simulation tools and has already been deployed. The capabilities outlined in this report

include implementing hash table matrix assembly for efficient sparsity pattern construction

for contact in BISON, developing re-step testing infrastructure for ensuring the viability of

overlapping domain coupling between SAM and Pronghorn, allowing unique preconditioners for

single-input multi-system solves, supporting multi-system in MOOSE’s workhorse executioners,

and many more smaller feature enhancements and bug fixes.

 2. INTRODUCTION

 The NEAMS program aims to develop simulation tools in support of the nuclear industry.

These tools are meant to accelerate reactor design, licensing, demonstration, and deployment.

The program is split into five Technical Areas (TAs): Fuel Performance, Thermal Fluids, Structural

Materials and Chemistry, Reactor Physics, and Multiphysics Applications. The physics related

TAs are responsible for delivering simulation tools to vendors, laboratories, and licensing

authorities, while the Multiphysics Applications TA creates foundational capabilities for the

program and exercises the tools to test them and ensure their usability for the intended purpose.

 Reactors are inherently multiphysical: heat conduction, neutronics, solid mechanics, fluid

flow, chemistry, and material evolution all combine to create a complex system that needs to

be simulated. To tackle that problem, the NEAMS program utilizes the MOOSE platform [1–3]

to develop interoperable physics applications. Over 15 MOOSE-based physics applications are

being developed within the program, with at least one in every TA. Each physics application

focuses on a particular aspect of reactor simulation (e.g., BISON [4] for nuclear fuel performance

 1

and Griffin [5] for neutronics).

 It is therefore critical to the program that MOOSE continues to be enhanced and supported.

Capabilities and optimizations made to the framework are instantly available to all the NEAMS

applications, making for a large return on investment.

 2.1 MOOSE

 The MOOSE platform enables rapid production of massively parallel, multiscale, multiphysics

simulation tools based on finite-element, finite-volume, and discrete ordinate discretizations. The

platform was developed as open-source software on GitHub [6] and utilizes the lesser general

public license (LGPL) 2.1, which allows for a large amount of flexibility. It is an active project,

with dozens of code modifications merged weekly.

 The core of the platform is a pluggable C++ framework that enables scientists and engineers

to specify all the details of their simulations. Certain interfaces include: finite-element/finite-

volume terms, boundary conditions, material properties, initial conditions, and point sources. By

modularizing numerical simulation tools, MOOSE allows for an enormous amount of reuse and

flexibility.

 Beyond the core framework, the MOOSE platform also provides myriad supporting

technologies for application development. This includes a build system, a testing system for both

regression and unit testing, an automatic documentation system, visualization tools, and many

physics modules. The physics modules are a set of common physics utilizable by application

developers. Some of the more important modules are the solid mechanics, heat conduction, fluid

flow, chemistry, and phase-field modules. All of this automation and reuse accelerates application

development within the NEAMS program. In the following sections, we outline changes made to

the MOOSE framework and its modules in order to support the various TAs.

 3. GENERAL SUPPORT

3.1 Removing the libMesh namespace from the main MOOSE headers

 See PR https://github.com/idaholab/moose/pull/28842

 To make coding in MOOSE as easy as possible, numerous coding concepts were historically

 2

simplified for developers. For example, additional headers were added to the main MOOSE

headers, leading to downstream developers not having to worry about including the headers

they actually needed. Along with unity combined builds, this made missing a header #include

a rather rare occurrence. This simplification was removed over time, with the inclusion of a

non-unity build in the continuous integration suite notably. Another item was the inclusion of the

libMesh namespace everywhere in MOOSE, by importing it in the main MOOSE headers. This

made numerous classes, notably libMesh’s Elem or Node, not require a libMesh:: namespace

prefix when used in MOOSE, and would avoid novice developers getting compilation errors

from forgetting the prefix. As compilers got smarter, this is no longer necessary as the compiler

will mention a prefix should be added. Even so, ubiquitous inclusion of the libMesh namespace

became cumbersome as the ecosystem grew. With developers linking new libraries such as

libTorch or NEML2, we can no longer import the entire libMesh namespace and not generate a

name conflict between classes from other namespaces.

 To remedy this, the libMesh namespace import was removed from the main Moose.h header,

and replaced with forward declaration as well as individual and very reduced imports of various

libMesh classes. Conflicts can now be handled on a per-item basis. The removal of a single item

from the Moose.h header to enable compatibility with another library is now a reasonably small

task compared to the removal of the entire namespace.

 3.2 Removing excessive compilation warnings on Apple Silicon

 See PR https://github.com/idaholab/moose/pull/29010

 When compiling on the MacOS Apple Silicon machines with a recent XCode installed, we use

a recent version of Clang for compiling the C and C++ code, and gFortran for the Fortran code.

With these compilers selected, MOOSE-based applications trigger thousands of linking warnings

related to compact unwinding from their Fortran dependencies included with PETSc. Compact

unwinding relates to exception handling and stack unwinding during runtime. It is a space-

efficient representation of unwind information in the compiled binary. It is used by the LLVM

tool suite, which refers to Clang and the linker here. It is intended to reduce the binary size and

speed up exception handling. However, it is not supported by this combination of compilers at

this time, hence the generation of the warnings.

 3

 These warnings hinder development. There is no simple flag to pass to the linker to silence

them, and disabling compact unwinding has to be performed throughout the entire stack to avoid

entirely disabling exception handling at the same time. To remove the warning, logic was added

in the main MOOSE Makefiles to silence them. This improved the developer experience across

the ecosystem.

4.1 Re-stepping capabilities to support domain overlapping coupling
 research

 See PR https://github.com/idaholab/moose/pull/30301

 In thermal hydraulics simulations, it is common for the nonlinear solve of a timestep to

fail due to diverging iterations, exceeding the maximum iteration count, poor preconditioning,

or similar issues. MOOSE handles such failures (for all simulation types, not just fluids) by

repeating the timestep with a smaller timestep size. To ensure fidelity when repeating a timestep,

all “stateful” data must be restored to its state at the beginning of that timestep. Stateful data

includes information computed in the previous timestep that is reused and overwritten in the

current timestep. Examples include solution vectors, material properties, global data such as

Postprocessors, and metadata stored within C++ objects. Because repeating timesteps and

restoring stateful data has been largely untested across the framework and its applications

(including Pronghorn), this work introduces a new approach.

 Rather than adding numerous test cases for timestep repetition (an impractical task given the

breadth of capabilities), a new testing scheme, restep, was developed. When an input file is

executed with restep, the Transient executioner selects the midpoint timestep of the simulation

 4

and artificially triggers a solve failure. The timestep is then repeated following the same logic as a

real failure, except the timestep size remains unchanged. Successful restep runs demonstrate that

the resulting solution or post-processed data is identical with and without the repeated timestep.

Any test in the framework or application suite can be run with restep via:

./run_tests --restep <other test options>

If the repeated timestep produces results that differ from the baseline (non-restep) run, the test

will fail. For debugging, individual inputs can be executed with:

<application>-(opt|oprof|devel|dbg) -i input.i --test-restep

Tests may opt out of restep by specifying restep = false in their specification.

 restep testing is now automatically triggered in MOOSE pull requests through the continuous

integration (CI) pipeline. This hook has already uncovered several deficiencies in the framework’s

handling of failed solves. Notable improvements prompted by restep include:

 • Restoration of Postprocessor, VectorPostprocessor, and Reporter data (when the old

 state is available).

 • Proper updating of displaced meshes when adaptivity is applied.

 • Correct use of the old ∆t for second-order backward difference formula (BDF2) time

 integration.

The Postprocessor restoration and BDF2 fix also exposed issues in several MOOSE-based

applications, including Griffin, Grizzly, Marmot, SAM, and TMAP8.

 As of this writing, no MOOSE-based applications run restep testing in their own CI

workflows. However, the MOOSE team recommends enabling it to identify bugs related to failed

timesteps and to improve application robustness.

 This work was performed to support the Domain Overlapping Coupling research [9]

performed in the NEAMS Thermal Hydraulics area. In the course of studying this numerical

technique, it was observed that quantities computed in the OverlappingDomainCouplingAction

were not reset when one of the solvers was failing a time step. Some of these quantities were

integrals, and thus were incremented incorrectly on failed time steps. Making these quantities

restartable data and this fix for the re-stepping behavior of restartable data addresses the issue.

 4.2 Creating an executioner base class for making the PIMPLE
 executioner a derived class

 See PR https://github.com/idaholab/moose/pull/29155

 After the development of the SIMPLE solve algorithm [10], a transient solver was to be

implemented using the PIMPLE algorithm. Such a development requires a new executioner

which would share considerable capability with the regular Transient executioner. The handling

of the time stepping, the time bounds, the shorthand creation of a time integrator, the steady

detection, etc. are all basic needs for a transient solver that should not be re-implemented

between various executioners. However, the current version of Transient is hard-coded to use

a FEProblemSolve which does not organize the solve for a SIMPLE algorithm but rather for a

Newton-like solve.

 In order to avoid the code duplication, much of the features in Transient were migrated to

a common base executioner class TransientBase, ahead of the implementation of PIMPLE. The

PIMPLE algorithm was developed by the TH technical area [11], inheriting the TransientBase.

 4.3 Allowing the use of non-AD variables in AD functor-consuming
 objects

 See PR https://github.com/idaholab/moose/pull/29572

 Automatic differentiation is used to propagate derivatives during computations of the

residual, in order to form the Jacobian simultaneously [12], with a reduced computational cost.

In the functor-system [13], AD-functors are used to obtain quantities while keeping track of the

derivatives with regards to the nonlinear variables. A Functor, introduced in [14], is a base

class for Functions, Variables, Postprocessors, SpatialUserObjects and Functor material

properties with several routines, such as evaluate, evaluateGradient or evaluateDot which

permit the computation of any of these quantities for all of these systems.

 In the new SIMPLE-based solver in the Navier Stokes module of MOOSE [15], we do not form

a Jacobian matrix, simply a sparse linear system matrix. We form this matrix explicitly and do not

use automatic differentiation. As a result the variables used are not AD-functors. Previously, all

variables in MOOSE were considered to be AD-functors. This meant only AD-FunctorMaterials

 6

could consume them, as FunctorMaterials error if AD-functors are passed in a non-AD object, in

order not to discard derivatives accidentally.

 With the changes made, developers of the linear finite volume solvers to be used in Pronghorn

can now create non-AD FunctorMaterials to compute their quantities, for example the turbulent

conductivity or viscosity, and have these materials consume the non-AD variable functors.

 4.4 Selecting the preconditioner on a per-solver-system basis

 See PR https://github.com/idaholab/moose/pull/29072

 With the introduction of multi-system capabilities in [16], came the need to adapt numerous

other systems to this new capability. The ability to use multiple time integrators was notably

already taken care of in [17]. Convergence criteria on a per-system basis were added through

the Convergence system introduced in [18]. The last item was the selection of different

preconditioning methods. Using different preconditioning enables additional flexibility, which

was used to study the numerical performance of the segregation of the solve for the passive scalar

advection of delayed neutron precursors.

 5.1 Execution schedule of siblings transfer

 See PR https://github.com/idaholab/moose/pull/31106

 In the course of setting up coupled Griffin-Subchannel-Duct thermo-mechanics simulations for

the Sodium Fast Reactor AppDriver, we had to modify the execution schedule of sibling transfers.

Sibling transfers were initially set to execute on every execution schedule. This ensured the

transferred data was always as updated as it could be, but was not desirable due to the potential

cost and lack of necessity in most cases. With a slight modification, sibling transfers were made to

only execute on the user-specified schedule.

 5.2 Ensure postprocessors are computed during linear solves with
 PJFNKMO

 See PR https://github.com/idaholab/moose/pull/29027/

   Griffin users often wish to specify a custom | Bx | normalization when solving generalized

eigenvalue problems. This was previously supported for the classic Preconditioned Jacobian-Free

Newton-Krylov (PJFNK) solve type. However, support was missing for the matrix-only variant

in which residuals are computed using matrix-vector products. PR #29027 added the necessary

postprocessor computation calls to compute | Bx | within matrix-only code paths.

  5.3 Preserve subdomain names by default when stitching meshes
 during generation

 See PR https://github.com/idaholab/moose/pull/30802/

 Griffin users often generate complex reactor meshes stitched together from collections of

simpler meshes of subcomponents. Previously, subdomain ids on all components were expected

to match, and subdomain names were expected to be all defined on the first component stitched.

Griffin users reported the user-unfriendly consequence, that subdomain names only defined on

latter stitching inputs were silently discarded. After PR #30802, by default, MOOSE preserves

any subdomain name defined on any input to mesh stitching, and if different names apply to the

same numeric id on different inputs, the output treats names as first-class identifiers and remaps

numeric ids as necessary.

 5.4 Fix asymptotic performance of FormattedTable output

 See PR https://github.com/idaholab/moose/pull/30842/

 The MOOSE FormattedTable implementation had a quadratic cost, O( N 2 ), when outputting

N time steps. This was still a trivial additional cost for typical MOOSE applications where each

time step of a large PDE is itself costly, but Griffin users looking at ODE problems with tens of

thousands or more relatively-cheap time steps quickly noticed that their computations would slow

down as they progressed. MOOSE developers identified the culprit code and fixed it in PR #30842

to use an O( N ) algorithm; even the relatively simple test case produced by Griffin developers was

 8

sped up more than ten-fold.

 5.5 Fix file reads with extremely short file names

 See PRs https://github.com/libMesh/libmesh/pull/4222/ and https://github.com/

idaholab/moose/pull/31141/

 Griffin developers reported a failure to read a particular matrix file, which upon investigation

turned out to be a failure to read any file with an extremely short (3 letter) file name. This was

fixed in libMesh PR #4222, after the incorrect string parsing code was determined to be a library

bug (older than MOOSE itself!). The fix was integrated with MOOSE in PR #31141.

 5.6 Expanded test coverage, fixes, and capability enhancements to
 boundary sync methods

 See PRs https://github.com/libMesh/libmesh/pull/4180/, https://github.com/

libMesh/libmesh/pull/4182/, https://github.com/libMesh/libmesh/pull/4188/, and

https://github.com/idaholab/moose/pull/30791/

 Griffin has started to make use of the libMesh BoundaryInfo::sync() methods, which take

specified sideset ids from a source mesh and construct side elements for those side sets, either to

add to another mesh or to the source mesh itself, maintaining interior-parent links from the new

lower-dimensional elements to the elements from which they were generated. Unfortunately,

Griffin developers discovered multiple bugs and multiple unimplemented features during this

process: some element types did not set interior-parent links correctly when generated, and some

combinations of replicated and distributed meshes either were not compatible with the boundary

sync process or did not properly handle interior-parent links after certain operations such as

distributed-mesh serialization. libMesh PRs #4180, #4182, and #4188 fixed the identified bugs

and added the required compatibility with other features, added extensive test coverage to other

untested feature combinations, and fixed any issues identified via those tests. The improved

methods were integrated with MOOSE in PR #30791.

 6.1 Hash table matrix assembly

 Preallocation of matrix memory for applications in which the sparsity pattern dynamically

changes, such as thermomechanical contact, has been an issue in MOOSE for over eight years,

see #7901. With an inaccurate initial preallocation, inserting new nonzeros can lead to dramatic

simulation slowdowns, acute enough that users report their simulations as ”hung”. One theorized

strategy for circumventing accurate matrix memory preallocation was based on hash tables, see

PETSc issue #852. Hash table matrix assembly uses a hash table to store maps from ij doubles

to values and then builds a compressed row storage (CSR) matrix only upon matrix assembly. It

does not require any pre-knowledge about couplings between degrees of freedom.

 Over the years hash table support in PETSc developed to a point that it became the default

when users did not supply preallocation. However, a couple of additional developments had to

take place to meet MOOSE’s needs. In #7939 we added the ability to copy from a hash table matrix

into a CSR matrix. This development was necessary because some MOOSE contact algorithms

require the ability to inspect the Jacobian in the middle of its evaluation; as an example, kinematic

node-face contact essentially takes the residual/Jacobian from the secondary node and projects it

onto the primary face, leaving the secondary node ”free” for applying the zero-penetration contact

constraint. In #7988 we added the ability to reset matrices to a hash table state. As mentioned

previously, after matrix assembly the hash table representation is converted to CSR. However,

this is problematic for thermomechanical contact in which the sparsity pattern is liable to change

between Jacobian evaluations. With the new MatResetHash API added in #7988 we can now reset

the matrix to a hash table state prior to each Jacobian evaluation.

 The PETSc development was captured downstream first in libMesh #3983 and finally in

MOOSE #28979 which introduced a Problem/use hash table matrix assembly parameter.

Using this parameter set to true in one BISON assessment case saw a reduction in initial Jacobian

 10

evaluation time from a couple hours to 50 seconds.

 6.2 Increased support for online mesh modification

 As part of modeling objectives of the Advanced Fuels Campaign (AFC), BISON should handle

fuel and clad geometries being modified in place, without remapping stateful material properties

such as strain when switching the fuel from one configuration to another. These different

geometries occur during the course of multiple steps of an irradiation campaign. Previously, the

solution from the model of the previous step would be loaded in either a SolutionUserObject or

through a Checkpoint file, and then projected onto a field in the new simulation. This projection

incurs an error, which in the case of strain and eigenstrain material properties, can cause both a

deformation of the fuel at initialization and a non-equilibrium state to be resolved with further

deformation in the first time step. A sketch of the geometry modification is shown in Fig. 1a

and 1b.

 To enable this modification of the geometry without re-projecting the material properties, we

rely on the MeshModification system. This new system, derived from the UserObject system,

can perform element subdomain modification and sideset migration onto the new subdomains.

Many of these capabilities were developed over time at ANL by Dr. Hu and externally to the

program. After mesh modification, the FEProblemBase::meshChanged() routine is called to

reinitialize numerous quantities given the altered state of the mesh. Then various options are

triggered for variable re-initialization.

 As part of the Technical Area Support effort, support was added for modifying lower

dimensional meshes using the MeshModifiers and re-initing mortar functors after doing so.

Effectively, this enabled the use of mortar constraints with mesh modification. Notably, mortar

constraints are to model contact between the fuel and the clad in a PWR.

 7. CARDINAL SUPPORT

 Please refer to [21] for more information on the Cardinal code.

 7.1 Adjusting field transfer diagnostics

 See PR https://github.com/idaholab/moose/pull/30597

 Cardinal performs data transfers between the Nek mesh and the MOOSE mesh of the same

geometry to perform conjugate heat transfer (CHT). There are multiple options to perform CHT,

depending on the boundary conditions chosen on the solid and fluid side. Both sides can impose

either a heat flux (Neumann), a wall temperature (Dirichlet) or a hybrid of the two (Robin) as a

boundary condition at the CHT interface. The two meshes are not coincident, being on opposite

sides of the fluid-solid interface and because of different discretization requirements of their

respective physics, so the shape evaluation transfer is not an option. Instead the nearest-location

algorithm is used to transfer the fields. The mismatch between meshes causes a projection error

to occur, which is mostly recovered by renormalizing the heat fluxes.

 In the field transfers [22] in MOOSE specifically used for this, the default setting was to have a

diagnostic for ill-posedness in nearest-location transfers. Ill-posedness occurs when two nearest-

nodes or nearest-centroids are close to the same target point. Target points are nodes for variables

that have all their degrees of freedoms at nodes, element centroids for constant monomials, and

a series of points computed by the GenericProjector for all others. This ill-posedness occurs

regularly in those transfers, but is not deemed an issue by the Cardinal developers. To their

request, an option was previously added to silence the warnings [16]. For cases involving a

transfer from a constant monomial to a first order Lagrange field, another option was to perform

a projection before the transfer [13]. However, this was not enough as the diagnostic is expensive

and does not scale to large simulations. This is an issue because many Cardinal simulations are

performed on high performance computing clusters.

 Thus the ill-posedness diagnostics are now turned off by default. In order to conserve the

overall safety of using field transfers in MOOSE, another diagnostic was turned on by default in

exchange. This other diagnostic makes sure that every target point finds a valid value by default.

Target points could be set to a default value if no valid value were found, and this occurs generally

 13

when meshes do not overlap. Unlike ill-posedness, this is very easy to discover when examining

the target field manually in the output files. The additional information when receiving an error

from the diagnostics helps the user figure out the correct setup faster.

 7.2 Execution of user objects, and postprocessors, during transfers

 See PR https://github.com/idaholab/moose/pull/30694 and https://github.com/

idaholab/moose/pull/31106

 A Cardinal user was attempting to keep track of the number of fixed point iterations to

vary the behavior of the child application based on that quantity. This number is computed in

the parent application using a NumFixedPointIterations postprocessor and can be sent to the

child application using a MultiAppPostprocessorTransfer. However, that quantity was never

updated as expected.

 If computed at the beginning of the time step, it would remain 0 for the entire fixed point

iteration because the TIMESTEP BEGIN execution occurs before the iterations. If computed at

the end of the time step, it would get restored to its original value when resetting the applications

after a multiapp fixed point iteration. The additional execution schedules added at the beginning

and end of multiapp iterations also did not fit the need [13].

 To resolve the issue, the TRANSFER execution flag was extended to all postprocessors and

user objects. This facilitates computing transferred information right before it is transferred,

removing any concern for a lag. A lag could notably cause a degradation in the order of

convergence of a time integration scheme.

 Additionally, a warning was added to check the execution schedule of the user objects and

postprocessors used in transfers. If the execution schedule is likely to lead to a lag in information,

the transfer warns about this potentiality.

 7.3 Boundary restriction of nodal positions

 See PR https://github.com/idaholab/moose/pull/31334

 The Positions system [13] introduced the gathering of a list of points in the geometry to

perform various subsequent acts such as: creating sub-applications at these points, performing

reductions in regions centered around these points, or sampling functors at these points.

 14

The system was expanded to include numerous ways of gathering these positions, from the

centroids of groups of elements, to evaluating functors for each coordinate of the positions, to

downselecting existing positions with a parsed expression. To support a Cardinal-based research

project, we introduced the boundary restriction of NodePositions. The positions of nodes can

now be gathered on a selected boundary or group of boundaries.

 8. SAM SUPPORT

 Please refer to [23, 24] for more information on the SAM code.

 8.1 Deploying multi-system capabilities in the main MOOSE
 executioners

 See PR https://github.com/idaholab/moose/pull/29021

 The SAM team has investigated multi-system capabilities for the transport of delayed neutron

precursors in system codes. Delayed neutron precursors (DNPs) are passive scalar quantities,

generally grouped in 6 or 8 groups, which are advected by the flow velocity field but do not

affect the velocity field directly. They affect it indirectly through their influence on the total

power distribution of the reactor, modifying the temperature, and thus affecting velocities through

buoyancy. Segregating the scalar precursors in a separate numerical solve improved the solve

performance at no loss in the accuracy. These capabilities were added to SAM using custom

executioners that were placed in SAM.

 In a parallel effort, for similar motivations, multi-system capabilities were investigated by

the Pronghorn team for multi-dimensional computational fluid dynamics simulations of molten

salt reactor cores, notably the pool-type designs such as the SAMOFAR Molten Salt Fast Reactor

design. These studies, performed first with MultiApps, see [25], then with multi-system, showed

the solve run time to be about 3X faster with a segregated setup. The performance improvement

becomes greater with the size of the system, as the preconditioning method for this advection

dominated problem does not scale.

 In order to bring these capabilities to both codes alike, and to the rest of the community, the

main SolveObject class, the FEProblemSolve, which is used by both the Steady and Transient

 15

executioners, was modified to incorporate multi-solver system capabilities. The default

parameters trigger a single sequential solve of each system. This suffices for one-way coupled

systems such as the passive scalar advection problem. For two-way coupled problems, additional

parameters may be passed to trigger an unaccelerated, unrelaxed fixed point iteration between

the solver systems. Note that further developments may be performed to add acceleration or

trivially add relaxation.

 Note that multi-system capabilities, initially developed in [22], were further improved this

year with per-system convergence criteria and per-system preconditioning, see 4.4.

 9. CONCLUSION

 This report highlighted various improvements made to the MOOSE framework in direct

support of NEAMS applications. Some of the highlights include implementing hash table

matrix assembly for efficient sparsity pattern construction for contact in BISON, developing

re-step testing infrastructure for ensuring the viability of overlapping domain coupling between

SAM and Pronghorn, allowing unique preconditioners for single-input multi-system solves,

and supporting multi-system in MOOSE’s workhorse executioners. Due to the frequency and

number of improvements, technical area support remains a very popular item among application

developers in the NEAMS program.
