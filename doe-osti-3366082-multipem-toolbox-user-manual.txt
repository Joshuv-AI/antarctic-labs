1 Introduction
This document explains use of the Multi-Phenomenology Explosion Monitoring (Multi-
PEM) Toolbox, a collection of R scripts for estimating the unknown device parameters of
a new event with uncertainty quantification. The methodology and application used for il-
lustration in this user manual are published in Geophysical Journal International 1 and fully
documented in a Los Alamos National Laboratory technical report2 hereafter designated
“WPA” for reference. Additional details on the application are found in a recent journal
article3 . Two assessment types are available: rapid and complete.
Rapid assessments are conducted in two stages, as described in Section 2. In the first stage,
benchmark data are used to estimate forward and error model parameters (WPA, §4.1)
and (if relevant) errors-in-variables yield values for benchmark sources (WPA, §2, Equa-
tion (3)). Forward model parameters can be of two types: specific to signature within
phenomenology and even emplacement condition, or global across more than one signature
within phenomenology or across phenomenologies. In the second stage, new event data are
used to estimate the unknown new event device parameters (WPA, §4.2) with uncertainty
quantification.
Two options for treating the inferred first stage parameters in second stage Bayesian anal-
ysis are available: fixing them at their maximum likelihood estimate (default), or multiple
imputation4 . Multiple imputation involves utilizing several posterior samples (imputations)
of the first stage parameters as fixed values in the second stage posterior sampling of the
new event device parameters. Second stage sampling is conducted across imputations in
parallel to improve computational efficiency. This method produces improved uncertainty
quantification of the new event device parameters compared with the default treatment of
the first stage parameters, at the expense of additional computation.
Complete assessments are conducted in a single stage, as described in Section 3. Benchmark

As the name suggests, rapid assessments generally run substantially faster than complete
assessments (even with multiple imputation), because the results of first stage analysis can
be stored and incorporated into estimating a relatively low-dimensional space of new event
device parameters whenever relevant new event data becomes available. On the other hand,
complete assessments must be run on the full set of model and device parameters with
benchmark and new event data every time the latter becomes available.

1.1 Running An Application in MultiPEM Toolbox
MultiPEM Toolbox applications can be run directly in R, or through Docker. The latter is
useful if a common run environment is desired for multiple users. Details are provided here
for the former, followed by brief remarks on the latter in the next subsection.
Begin with the following initial steps for a direct, native R run. The repository does not
enforce a native R version or package lock. The reproducible Docker runtime described in
Section 1.2 uses R 4.4.3 and pinned package versions; using R 4.4.3 is therefore recommended
when a native run is intended to match that runtime.
 • Install R. A C/C++ build toolchain is also required when the NUTS sampler is selected,
 because its implementation compiles Code/nuts core.cpp with Rcpp.
 • Install the following auxiliary R packages used by the illustrated application and shared
 code:
 – Matrix
 – numDeriv
 – doFuture
 – future
 – adaptMCMC
 – FME
 – Rcpp and RcppEigen (required for NUTS)
 – ramcmc and iterators (required for Sequential Monte Carlo (SMC) sampling)
 For example, to install the Matrix package, run the command
 > install.packages("Matrix")
 inside an R session. Install application-specific packages in addition to this list when
 its forward models require them. The illustrated runMPEM 0.r selects "FME", while its
 first-stage and complete-assessment runMPEM.r files select "RAM". These are run-file

 choices, not fallback rules based on the installed R version. The calculation functions
 also support "NUTS"; calc bayes 0 additionally supports "SMC".
 • The future package places a limit of 500 MiB on the size of global variables that can
 be exported to parallel processes. This can be overridden by placing the following
 command
 options(future.globals.maxSize = Inf)
 in the .Rprofile file located in the user’s home directory, or by adding it to the
 preprocessing component of the runMPEM.r and runMPEM 0.r files.
 • Clone the open source MultiPEM Toolbox repository from GitHub:
 % git clone https://github.com/lanl/MultiPEM_Toolbox.git
There are three MultiPEM analyses contained in the illustrative application (WPA, §5),
named 2-Phen-oc, 2-Phen-sa, and 4-Phen. The first estimates new event device parameters
based on fusion of data from the optical and surface effects phenomenologies; the second
fuses data from the seismic and acoustic phenomenologies; and finally the last performs this
same task but with data fusion across all four phenomenologies.

1.2 Running MultiPEM Toolbox Through Docker
The Runfiles-Docker workflow runs any registered analysis under Runfiles in a single
versioned runtime. It creates a private, auditable job snapshot and starts the calculation
in a detached container by default. The portable launcher is mpem.R; ./mpem is only an
optional /bin/sh convenience wrapper on Unix-like systems.
The host requires R 4.0 or newer with Rscript on PATH, a Docker command-line client
connected to a running engine configured for Linux containers, permission to bind-mount
the repository and results locations, at least one logical CPU, and sufficient disk space and
memory. No host R packages, shell, Docker Compose installation, or compiler is required.
The runtime image uses R 4.4.3, an immutable base-image digest, and package versions
recorded in Runfiles-Docker/renv.lock.
From MultiPEM Toolbox/Runfiles-Docker, diagnose the host, build the runtime, list avail-
able analyses, and start an analysis as follows:
% Rscript mpem.R doctor
% Rscript mpem.R build
% Rscript mpem.R list
% Rscript mpem.R run IYDT-gsrp/Seismic/I-SUGAR-hob
Without --results, each invocation creates a uniquely named results directory under
Runfiles-Docker/results. A job contains copies of the selected run files, shared code,
application code, and application data; calculations write to this snapshot rather than to
the source tree. Use the printed job name with the lifecycle commands
% Rscript mpem.R jobs
% Rscript mpem.R status JOB
% Rscript mpem.R logs -f JOB
% Rscript mpem.R wait JOB
% Rscript mpem.R stop JOB
% Rscript mpem.R clean JOB
The default full stage runs runMPEM.r and then runMPEM 0.r, when the latter exists. The
calibration and event stages may instead be run separately:
% Rscript mpem.R run ANALYSIS --stage calibration \
 --results results/calibration-case
% Rscript mpem.R wait JOB
% Rscript mpem.R run ANALYSIS --stage event \
 --results results/calibration-case
After a successful calibration for an analysis having an event deck, the workflow copies the
resulting .RData byte-for-byte to RESULTS/.mpem/checkpoints/calibration.RData and
records its SHA-256 checksum. This checkpoint is distinct from the working .RData. Every
event invocation restores the checkpoint before running runMPEM 0.r, so changes saved by
one event do not alter the pristine calibration. A future event-only analysis may use the
same calibration in a new results directory:

 10

% Rscript mpem.R run APPLICATION/PHENOMENOLOGY/NEW-EVENT-0 \
 --stage event \
 --workspace \
 results/calibration-case/.mpem/checkpoints/calibration.RData \
 --results results/new-event
The workflow caps the effective worker pools associated with ncores mle, ncores map,
ncores mc, and ncores smc at the CPU capacity visible to the container. The logical values
remain unchanged to preserve chains, seeds, samples, and initial states. If a requested pool
is reduced, a warning records the effective assignment in the Docker stream, the combined
job log, the deck output, and a CPU-adjustment log. The optional --cpus N and --memory
SIZE arguments impose Docker resource limits.
The durable combined log is multipem-job.out; each deck also produces runMPEM.out or
runMPEM 0.out, a corresponding CPU-adjustment log, and a status file in the snapshot’s
analysis directory.
To add an application:
 • place its decks under Runfiles/APPLICATION;
 • place its code under Applications/Code and its data under Applications/Data; and
 • add its mapping to the tab-separated file Runfiles-Docker/applications.tsv.
Paths in a deck must be relative to its analysis directory. Use the standard ncores* variables
and corresponding ncor* function arguments so job preparation can guard worker plans. A
source-only application needs no rebuild if the runtime already contains its required packages
and system libraries. Full commands and details of the result tree, registration, maintenance,
and troubleshooting are in Runfiles-Docker/README.
As with the native analyses of Section 1.1, complete all required single-phenomenology jobs
before creating a MultiPEM job. Docker jobs have separate snapshots, so an optimization
file remains in the results directory of the job that produced it. Its location is
RESULTS/work/APPLICATION/PHENOMENOLOGY/ANALYSIS/opt.RData
Copy every completed optimization file from its job snapshot to the corresponding canonical
Runfiles destination shown in Section 1.1. Create the Opt directory if necessary. Only then
invoke mpem.R run for the MultiPEM analysis; job creation will include the staged files in
its new snapshot. For example, if the complete seismic job used results/seismic, stage
its result as follows from Runfiles-Docker. The example uses Unix-like shell syntax; on
Windows, use the equivalent directory-creation and file-copy operations.
% mkdir -p ../Runfiles/IYDT-gsrp/4-Phen/Opt
% MPEM_OPT=results/seismic/work/IYDT-gsrp/Seismic
% cp "$MPEM_OPT/I-SUGAR-hob/opt.RData" \
 ../Runfiles/IYDT-gsrp/4-Phen/Opt/opt_1.RData
Repeat the copy for the acoustic, optical, and crater results, using the mappings in Sec-
tion 1.1, before starting the four-phenomenology job. Do not reuse a single-phenomenology

2 Rapid Assessment
Rapid assessments will be illustrated by examining the run files associated with a multi-
phenomenology analysis in which signals from four phenomenologies are combined to infer
the log-yield and height-of-burst (HOB) of a near-surface nuclear explosion (WPA, §5).
% cd ./Runfiles/IYDT-gsrp/4-Phen/I-EIV-SUGAR-hob-0
Rapid assessments consist of two stages. In the first stage, benchmark data are employed to
estimate forward model parameters (e.g. regression coefficients) and error model parameters
(e.g. source bias, path bias, observational error covariance), and (if relevant) errors-in-
variables yield values of benchmark sources. This stage may be run for one or multiple
scenarios of interest upon identification of relevant historical data for each scenario, and the
resulting .RData file(s) stored for later use in processing new event data.
In the second stage, new event data are processed to infer unknown device parameters (e.g.
yield, HOB/DOB, geolocation, event time) with uncertainty quantification. In Bayesian
analysis, forward and error model parameters, and (if relevant) benchmark source errors-in-
variables yields, may be treated in two ways:
 • Fixed at values obtained from the first stage, or
 • Imputed using posterior samples from the first stage5 .
Either approach results in rapid assessments being executed with far less compute time than
complete assessments. The first approach has the potential consequence of underestimating
uncertainty in the unknown device parameters of interest for the new event, which is avoided
by selecting the second approach with the expense of additional compute time.

2.1 First Stage
The first stage analysis is defined in the runMPEM.r file, provided in the first three sections of
Appendix A with line numbers referred to in the ensuing discussion. Appendix A.1 provides
the preprocessing component of the first stage, Appendix A.2 provides the code employed to
maximize the likelihood function of the benchmark data with respect to the parameters of
the forward and error models, while Appendix A.3 provides the code employed to optionally
sample the posterior distribution of these parameters.
The first stage analysis is run in batch mode as follows,
% R CMD BATCH runMPEM.r runMPEM.out &
The main features of the output file runMPEM.out are provided in Appendix A.4.

3 Complete Assessment
Complete assessments are illustrated with the four-phenomenology analysis that infers log-
yield and height-of-burst (HOB) for a near-surface nuclear explosion (WPA, §5):
% cd ./Runfiles/IYDT-gsrp/4-Phen/I-EIV-SUGAR-hob
% R CMD BATCH runMPEM.r runMPEM.out &
Unlike a rapid assessment, a complete assessment uses benchmark and new-event data in one
joint calculation. It estimates the applicable forward-model, error-model, errors-in-variables
yield, and new-event device parameters simultaneously. Appendix B contains the exact run
file and its line numbers; Appendix B.4 contains selected output.
The benchmark-data definitions, variance-component construction, forward models and Ja-
cobians, optimization controls, calibration priors, and MCMC controls are the same concepts
documented for rapid-assessment calibration in Section 2.1. The new-event data, transfor-
mations, bounds, forward-model derivatives, priors, and reported new-event quantities are
the same concepts documented for rapid-assessment event inference in Section 2.2. This
section therefore documents only how the complete workflow combines those components
and gives the complete functions’ exact interfaces. The cross-references describe concepts,
not a sequence of rapid-assessment calls: a complete assessment calls prepro, calc mle, and
calc bayes directly and performs joint inference.
