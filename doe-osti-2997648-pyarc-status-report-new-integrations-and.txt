 Executive Summary

PyARC was initially developed as an open source tool to support fast reactor analyses using the
Argonne Reactor Computation (ARC) code suite as a part of the Nuclear Energy Advanced Mod-
eling and Simulation (NEAMS) Workbench initiative in FY17. The goal of this initiative is to
provide a common user interface for model generation, real-time validation, execution, output pro-
cessing, and visualization for all integrated codes. This is accomplished through the reliance on
tools available in the Workbench framework and runtime environment.
 While initially developed to support the ARC codes, PyARC was extended in FY22 to wrap
other NEAMS and non-ARC codes, including Griffin and OpenMC, in the supported other neu-
tronics workflows, and support users in the adoption of NEAMS-supported high fidelity analysis
codes. Most recently, NUBOW-3D, a recently adopted ARC code, was integrated to support re-
actor bowing calculations as well. Integration of these codes into the NEAMS Workbench directly
benefits the advanced reactor modeling community by:

  Providing a set of controlled, maintained, documented and validated scripts to generate in-
 puts, which promotes best practices, reduces the learning curve, and facilitates project col-
 laboration.
  Improving the user experience: the Workbench interface provides assistance for building an
 input through auto-completion, real-time validation, document navigation, and geometry and
 results visualization.
  Automating complex calculations and workflows for reactor analysis.
  Helping users transition to using high-fidelity NEAMS codes along-side the ARC codes.

 In FY22, a progress report was published that described the state of each of the tools integrated
into PyARC. Since then, there have been many enhancements and upgrades to the existing inte-
grations as well as entirely new code integrations as well. This report details all new integrations
and major developments in PyARC since the version 2.0.0 release highlighted in the FY22 report.
Specifically, this report will primarily cover:

  backend upgrades to use the new Language Server Protocol (LSP) capability from Workbench
 as a means to enhance the user experience and improve the reliability of input processing
 (Section 3).
  several new OpenMC capabilities, including tallies, depletion, and multigroup cross sections
 (MGXS) generation (Section 4).
  upgrades to the Griffin integration to enhance reliability of the workflow and support multi-
 group cross sections (MGXS) generation using OpenMC (Section 5).
  support for displacements per atom (DPA) calculations using the ARC codes (Section 6).
  conversion of the DASSH integration to use a newly adopted version of the code (Section 7).
  the all new integration of the NUBOW-3D code to support core bowing calculations (Section
 8).

1 Introduction

PyARC [1] was launched as a part of the Nuclear Energy Advanced Modeling and Simulation
(NEAMS) Workbench [2] initiative in FY17 to facilitate the deployment of the high-fidelity codes
developed within the NEAMS program [3]. PyARC was originally developed as an open source
workflow management tool for the Argonne Reactor Computation (ARC) [4, 5] codes and has
since expanded to cover other NEAMS and non-ARC codes. Since its initial development, PyARC
has been used by industry, academia, and national labs to perform complex multiphysics analysis
workflows of fast reactors and perform reliable code-to-code verification. Because of its wide reach
and range of developmental work, primary funding for PyARC has come from both the Department
of Energy (DOE) Advanced Reactor Technologies (ART) Fast Reactor Program (FRP) and the
DOE NEAMS Multiphysics Technical Area (TA), with additional support from a Technology
Commercialization Fund (TCF) with Westinghouse.

 PyARC wraps the ARC code suite that includes neutronics, thermal hydraulics, safety, and fuel
behavior analysis codes: MC2 -3 [6] and TWODANT [7] for region-wise multigroup cross section
processing, DIF3D [8] for flux calculation, REBUS-3 [9] for depletion and equilibrium calculations,
PERSENT [10] for perturbation theory calculations (perturbation, sensitivity and uncertainty
quantification), GAMSOR [11] for gamma heating calculations, DASSH [12] for subchannel analysis,
and, most recently as of this fiscal year, NUBOW-3D [13] for structural analysis and core bowing
calculations. Since initiation, additional other codes have been integrated into PyARC, forming
what is known as the “extended suite of ARC codes.” This extended suite includes the non-ARC
codes: ORIGEN-S [14] for detailed depletion calculations, PROTEUS-Nodal [15] transport solver,
OpenMC [16] for Monte Carlo (MC) neutronics [17], and Griffin [18] for high-fidelity deterministic
neutronics (originally through the integration of PyGriffin [19]). The complete set of workflows
supported by PyARC for these integrated codes, as of the v3.0.0 release in September 2025, is
shown in Fig. 1.1.

 Since the last official progress report on PyARC in FY22 [20], which highlighted the newest
capabilities in v2.0.0 of PyARC, there have been several more releases that include new workflows
and integrated codes. This report serves to present all new major capabilities and developments
that have gone into PyARC since the v2.0.0 release (up through the current release of v3.0.0). Each
of the following developments are discussed in detail in the rest of this report:

  Upgrading the backend language server for more reliable input processing and an enhanced
 user experience (Section 3).

  OpenMC upgrades (Section 4): support for different types of tallies, depletion calculations,
 and MGXS generation.

  PyGriffin upgrades (Section 5): use of Reactor Geometry Mesh Builder (RGMB) [21] and
 PyHIT [22] for Griffin input creation, advanced post-processing capabilities, deprecation of
 PyGriffin as a standalone code, and support for using OpenMC MGXSs.

  Displacements per atom (DPA) calculations using the ARC codes (Section 6).

 3

  Conversion of the DASSH integration from the Python version [23] to the Fortran version [12]
 (Section 7).

  The new integration of NUBOW-3D [13] for core bowing analysis (Section 8).

2 The Workbench/PyARC Framework

Workbench [2] is a graphical user interface (GUI) and runtime environment (RTE) developed at
Oak Ridge National Laboratory (ORNL) designed to be a common user interface for model creation,
real-time validation, execution, output processing, and visualization for integrated codes. PyARC
relies on the Workbench modules and RTE for base-level validation, input processing, and execution.

 4

PyARC is deployed within Workbench with each release (the latest v3.0.0 release of PyARC being
deployed with the latest v5.6.0 release of Workbench), and so users can use the latest capabilities
almost immediately within the contained environment, pending any code-specific setup that may be
required. An example of what the GUI might look like when using PyARC within Workbench is
shown in Fig. 2.1.

Figure 2.1: The Workbench GUI highlighting some of the capabilities available to PyARC: (A)
input file navigation panel; (B) SON input file; (C) PyARC summary output file (post-processed
results); (D) geometry input visualization; and (E) results plotting/visualization.

2.1 The PyARC Module

PyARC is an Argonne National Laboratory (ANL)-developed module that relies on Workbench to
support a “black box” approach to using the extended suite of ARC codes. It requires only one
common user input file (the Standard Object Notation (SON) input) as described in Section 2.1.1
and then automatically performs input validation, code-specific input generation, code execution,
and post-processing for all specified workflows in the input file (see Fig. 1.1 for a visual available
workflows).

2.1.1 Common SON Input and Schema

The Workbench input format adopted by PyARC is described as the “common input” since it is used
to generate inputs for all the tools integrated into PyARC. The main benefits of the common input
strategy is to ensure every native input uses consistent information and to facilitate code-to-code

 5

interfacing. The common input is designed specifically for reactor geometries and is intended to
be intuitive and flexible for users. It uses Workbench’s open source Workbench Analysis Sequence
Processor (WASP) SON [24] format that enables the autocompletion, real-time input validation, and
access to templates, through the Workbench interface. The common input parameters are defined
by a single Workbench-supported “schema” file in PyARC. The schema definition relies on some
level of code-independent inherent input validation provided by the Hierarchical Input Validation
Engine (HIVE) module, the built-in input validation capability from WASP [24]. It is important to
note, that the real-time input validation performed by HIVE is limited to common logical rules, and
does not provide the capability for more complex code-specific input validation, which occurs in the
precheck stage of PyARC execution (Section 2.1.2). The schema also provides users with several
input templates and autocompletion that can be populated directly in the Workbench GUI during
input creation. While the common SON input structure remains for PyARC, the schema is being
replaced with a PyARC-dedicated language server using Workbench’s Language Server Protocol
(LSP) capability (Section 2.2) for an improved user experience and more reliable input processing
(see Section 3 for a full description of this upgrade).

 The PyARC input contains two main input blocks: the geometry input and the calculations
input. The former is a single input definition that is created to be used across all calculation
workflows specified. The calculations block is where each code and their runtime parameters are
specified for the desired computational workflow. In the spirit of using a common input, as much
information as possible is reused in PyARC across the various calculation specifications, meaning
users do not have to redefine simulation parameters that are identical for multiple codes in a single
workflow. This reduced level of user input and reuse of the specified input are key characteristics of
PyARC that support the user-friendliness and reliability and reduces the potential for human error.

2.1.2 Workflow Management

The PyARC workflow is completed in four main stages:

 1. Precheck: performs additional diagnostics beyond what HIVE can provide and verifies a
 compatible RTE is available.

 2. Prerun: generates any code-specific input required.

 3. Run: executes the integrated code(s).

 4. Postrun: post-processes output, if the run stage was successful, into user-friendly, PyARC-
 standardized notation.

This sequence is triggered by PyARC execution, not during input creation, which means the precheck
stage is not performed until after an input has been fully created and validated by the first stage
of HIVE validation. If the precheck fails, then PyARC will stop and not perform the remaining
stages of execution. There is opportunity to streamline the initial precheck stage by using the new
language server (Section 2.2) to perform all input-based validation during input creation to provide
even more detailed real-time validation, leaving any runtime-based validation to be performed in

 6

the precheck stage at execution. The details of this improved validation approach are described in
Section 3.1.1.

2.2 Language Server Protocol

Microsoft’s Language Server Protocol (LSP) [25] was first introduced into Workbench for support
of MCNP analysis in 2018 [26] and formally integrated in 2019 as a feature available for all tools
that rely on the Workbench system [27]. The LSP facilitates and simplifies the connection between
input processing, user communication, and code development. Workbench in particular supports
the following capabilities to be implemented via a server class in any tool [28]:

  input diagnostics via interactive checking

  input navigation via symbol tree hierarchy

  input autocompletion via app introspection

  input definitions via key lookup locations

  input formatting via standardization rules

The schema implementation (Section 2.1.1) provides for some of these capabilities to a degree
already. However, the mechanisms for these features are less robust (some details of these features
are not available in the schema implementation) and do not directly communicate with the PyARC
module at runtime, which requires additional input processing steps. A more detailed comparison
of the LSP implementation and the schema implementation is provided in Section 3.

3 Language Server Upgrade (v3.0.0)

This work was completed in FY25 through funding from the DOE-NEAMS Multiphysics TA.

 Implementing a new language server into PyARC aims to simplify input processing and enhance
user experience through the NEAMS Workbench [2] by adopting Workbench’s LSP capability [27]
(Section 2.2). This upgrade will eventually entirely replace the schema-based input processing
described in Section 2.1.1. Previously, PyARC used a three-step process to load a SON input file
and convert it into a Python object that could be accessed throughout the PyARC code. First, the
user input in SON format was checked against PyARC’s schema to ensure HIVE-based validity.
The validated input was converted into an XML object, which was then turned into a Python object
using the xml2obj module from Workbench’s WASP Python module wasppy [24]. The new language
server upgrade introduces a more efficient path to Python object creation. Instead of applying an
XML conversion, PyARC uses WASP’s new C++ Python bindings to directly transform the SON
input file into a Python database. This Python database validates the input and transforms the SON
parse tree into a Python object layer, simplifying the object loading process while preserving common
schema checks and requirements. In other words, the input reading, validating, and processing
is more accessible through Python, providing for a more robust and efficient implementation and
access to both PyARC RTE and its new language server.

3.1 Graphical User Interface Enhancements

Besides streamlining input processing in PyARC, the new language server also provides more
advanced user-interface features in the Workbench GUI through additional diagnostics, an improved
navigation panel, hovering definitions, “goto definition”, “find references”, and autocompletion
capabilities. The previous grammar interpretation in PyARC already supported “goto definition”,
which is when a user can right-click on a variable/ID being used somewhere and go to the location
in the file where that was defined (see Fig. 3.1), hovering over an input parameter to view the
description of that input (see Fig. 3.2), and autocompletion with custom templates. Both the
“goto definition” and hovering features remain in the language server implementation, but the
autocompletion using custom templates has not yet been fully implemented (see Section 3.3 for
more information). These rest of the listed features are new and described in more detail in the
following sections.

3.1.1 Diagnostics and Validation

Just as the previous schema provided some level of real-time validation, the Python database can
do so as well through the language server. However, with the language server’s expanded ability to
interpret diagnostics, the validation procedures can be much more robust and detailed. Previous
validation rules implemented in the PyARC schema were limited to the logic provided by WASP’s
built-in HIVE-based validation tool [24]. With the integrated language server, the logic for the
real-time validation is provided directly in the Python database (coded as Python logic directly)
and can therefore include any arbitrarily complex validation rules and be much more code-specific.
Historically, PyARC has been developed such that the first stage of execution at runtime is the
precheck stage. This stage is a secondary check stage at runtime which includes both additional
detailed input validation, beyond what can be provided by HIVE, as well as RTE checks. By
using a Python database through the language server, this first set of precheck validations that
do additional input validation can be moved to the database directly and be provided to the user

4 OpenMC Upgrades

Important note: previous versions of PyARC included PyMCSim as a module. This module has
been renamed to PyOpenMC in v3.0.0 and will be referred to as such moving forward.

 OpenMC [16] was added into PyARC as a MC neutronics code in v2.0.0 for eigenvalue and
stochastic volume calculations on the explicit heterogeneous reactor geometry [29]. Since then, the
PyOpenMC module has been upgraded [30] to include support for tallies, depletion calculations,
and MGXS generation. This section will elaborate on each of these new integrations.

4.1     Tallies (v2.2.0)

This work was completed in FY23 through funding from the DOE-ART FRP.

 Three types of OpenMC tallies are supported by PyARC: surface tallies, mesh tallies, and region
tallies. Each type of tally can take a variety of parameters to tally different scores over specific
materials, nuclides, and energy bins (some limitations exist for surface tallies). The different type of
scores that can be tallied and their units are:

  flux [particle-cm/source]

  heating [eV/source]

  damage energy [eV/source]

  current (surface tallies only) [particle/source]

  various reaction rates [reactions/source] available in OpenMC [16]

 The tally results from OpenMC are then processed and returned to the user in the PyARC
summary files using the common PyARC notation for assemblies and pin locations or a VTK data
file for mesh tallies. Mesh and some region tallies can be further visualized using the OpenMC
Plotter tool [31], which is a OpenMC-specific GUI for viewing models and tally results, and it is
installed as a part of the Workbench RTE during the PyARC setup. Specific instructions for how
to use the OpenMC Plotter to visualize each of these types of tallies, as well as more detailed input
specifications, is provided in the PyARC tutorial [32].

4.1.1 Surface Tallies

For surface tallies, the user must simply provide the name of the surface (defined in the geometry
block of the SON input) and the net current will automatically be scored (no other types of scores
are allowable for surface tallies) on that surface. If the current over the entire outer surface of the
full reactor geometry is desired, users can specify this as well. Surface tallies can be further refined
by tallying over specific energy bins. The output from the surface tallies is the tally result for the

 14

net current at each surface for each energy bin. For cases where a surface specified is a composite
surface (i.e., squares and hexagons), each individual surface of the composite will be reported.

4.1.2 Mesh Tallies

For mesh tallies, the user defines a Cartesian mesh grid on which to tally for the spatial domain.
Mesh tallies can be further refined with specifying the tally score(s) (required), energy bins, specific
nuclides, and materials. The output from the mesh tally is a VTK file which can be visualized
directly in the OpenMC Plotter [31]. An example of what mesh tally results might look like in the
Plotter can be seen in Fig. 4.1.

Figure 4.1: Example of results obtained from a mesh tally that can be viewed in the OpenMC
Plotter GUI.

4.1.3 Region Tallies

Region tallies are much more versatile because the “region” can be a set of pins, assemblies, or
the full core. A core-averaged tally is one that uses the entire geometric domain of the core as
the spatial domain, considering it as a single homogenized region. For assembly-level tallies, each
individual assembly of the assembly types specified is uniquely tallied (each assembly is treated as
a homogenous domain for the tally). For pin-level tallies, each individual pin (and regions within
the pin) in each specified assembly types is uniquely tallied, preserving full heterogeneity of the
geometry. Just like mesh tallies, a region tally can be further refined with specifying the tally score(s)
(required), energy bins, specific nuclides, and materials. As well, the results from pin-level and
assembly-level tallies can be visualized in the OpenMC Plotter [31]. Examples of an assembly-level
tally and pin-level tally are shown in Fig. 4.2 and Fig. 4.3, repectively.

4.2   Depletion (v2.6.0)

This developmental work was completed in FY24 through funding from the DOE-ART FRP.

 Depletion calculations with OpenMC [33] were added in v2.6.0 and expose nearly all options
available in OpenMC to users in PyARC [34]. OpenMC depletion calculations are fully heterogeneous,
meaning that the calculations are pin-resolved, as opposed to the subassembly-level homogenization
that is required of REBUS [9] when using the ARC workflow for depletion. At a minimum, users
must specify timestep or depletion steps, power information, reaction rate calculation method
(further explained below), and an OpenMC-formatted data file for the depletion chain (available

 16

directly from OpenMC [35]).

 OpenMC supports three different types of reaction rate calculation methods for depletion analysis:
direct tally, flux tally, and hybrid. When using the direct tally method, all nuclides will be tallied
for all reaction rates that are present in the chain file. The second method is the flux tally method.
This method does not do any direct tallying of reaction rates but rather tallies the flux over the
specified energy groups and calculates the reaction rates at the end of the simulation. Generally
speaking, the direct tally method is more accurate but can take a long time to run, whereas the flux
method is much quicker but may be inaccurate. The hybrid method is a combination of both these
methods where one can specify that certain reactions rates to be direct tallied for certain nuclides,
and energy groups to use for the flux tally. [33]

 The runtime settings of the depletion calculation can be further fine-tuned with various depletion
calculation-specific options such as solver methods, integrator methods, and normalization mode
[33]. Each of these options are explained in more detail in the PyARC tutorial [32].

 The depletion calculation output that is returned in the PyARC summary files can also be
highly customized. By default, only k-effective over time and tally results for the first and last time
steps (if there are any tallies present) are included. Additional information users can request to be
reported include:

  reaction rates for specific nuclides in specific materials over time;

  nuclide masses in specific materials over time;

  decay heat in a specific material over time; this can be reported as total decay heat or
 individually for each nuclide in the material;

  specific time steps for which to report tally data (only the first and last time steps are reported
 by default).

4.2.1 Verification on a Lead Fast Reactor Benchmark

This verification work was completed in FY25 through funding from the TCF with Westinghouse
Electric Company.

 This new OpenMC depletion capability was verified in the continuation of the depletion bench-
mark analysis of a lead fast reactor (LFR) model [34, 36]. The full set of results and analysis
is available in [34], but a summary of the work is provided here. Previous analysis of this LFR
using PyARC was performed using the ARC codes and ORIGEN-S [14] integrations to compute
k-effective over the 10-year core lifetime, shutdown decay heat, and compute the end of life (EOL)
heavy metal inventory, and then compare these to an independent depletion analysis using Serpent
[37]. Additionally, the OpenMC integration in PyARC had been used to compare beginning of life
(BOL) k-effective using different data libraries to quantify the effect of different data on the results
(OpenMC requires ENDF/B-VII.1 [38], whereas the ARC codes rely on ENDF/B-VII.0 [39]).

 17

 This new analysis performs the same set of aforementioned depletion analyses using OpenMC in
PyARC. The results of this analysis (provided in detail in [34]) showed that the lifetime k-effective
calculated by OpenMC agreed within ±0.10% with the previous Serpent results and within ±0.20%
with the previous ARC results (the differences in the latter can be attributed to differences in the
data libraries used). The results for the shutdown decay heat analysis also agreed well overtime,
with the only discrepancy in the OpenMC results appearing at the start of shutdown, and this
difference was able to be traced back to a likely bug within the OpenMC code, and not PyARC.
Finally, the EOL heavy metal inventory calculated with OpenMC was compared to the ARC results
using REBUS [9] and the coupled REBUS/ORIGEN-S [14] results. The heavy metal inventories
calculated by OpenMC agreed within ±10% for all major isotopic inventories. Overall, the analysis
performed in [34] showed good agreement with previous results, indicating a reliable implementation
of OpenMC’s depletion capability in PyARC.

4.3 Multigroup Cross Section Generation (v3.0.0)

This work was completed in FY25 through funding from the DOE-ART FRP.

 Deterministic transport codes, such as Griffin [18], require multigroup cross sections (MGXS)
due to their discretized representation of phase space. There are two primary methods for generating
MGXS data for reactor neutronics analysis: using lattice physics codes and using MC codes. Lattice
physics codes, a subset of deterministic methods, numerically solve the neutron transport equation.
These codes generally use ultrafine group (UFG) (thousands) or hyper fine (hundreds of thousands)
energy groups, and reduce the reactor geometry into 1D unit cells. Lattice physics codes are widely
utilized because they can produce good, energy-dependent results for regular geometries in a timely
manner. However, there are some limitations, primarily due to the spatial homogenization. This
homogenization means that heterogeneous detail is lost where these codes cannot capture highly
heterogeneous media well, and can only produce region-wise cross sections. An alternative method
to generating MGXS data is the use of MC codes. The advantage that MC codes have over lattice
physics codes is that they do not need to compromise on the spatial or angular representation of
the geometry (i.e., heterogeneity can be preserved). However, the disadvantage of using MC codes
for MGXS generation is that it can be computationally expense to achieve the desired statistical
accuracy for large systems. In particular, for fast reactor systems, accurately capturing thermal
cross sections often requires variance reduction techniques [40].

 PyARC was originally developed to use the MC2 -3 [6] lattice physics-based cross section
generation code as the sole method for MGXS generation method for fast reactor analysis for both
the ARC codes and Griffin [18]. Although PyARC was originally intended to be a tool specifically
for fast reactor analyses using the ARC codes, with the addition of both Griffin and OpenMC, it is
no longer limited to fast neutron spectrums. In other words, PyARC now supports analysis of any
reactor type that uses a regular lattice geometry, regardless of neutron spectrum, because Griffin and
OpenMC are not inherently fast nor thermal spectrum analysis codes. Because MC2 -3 is specifically
designed for fast neutron spectrums, having the capability to generate MGXS with OpenMC for
any neutron spectrum expands the type of reactors that can be analyzed using Griffin in PyARC,
such as some types of high temperature gas-cooled reactors (HTGRs) which have thermal neutron
spectrums and can have regular lattice geometries.

 18

 In FY25, PyOpenMC was upgraded to include the option for both microscopic and macroscopic
MGXS generation either as a standalone generation process to use the cross sections externally
or for use with Griffin (described in Section 5.5). The standalone cross section generation process
using OpenMC is what is described here, as the general features and capabilities are more extensive
than what is allowable for use in Griffin (see Section 5.5).

4.3.1 Input Description

To generate MGXS data with OpenMC, users specify at a minimum the type of spatial domain,
information about the energy groups to use for the cross sections, and information about what types
of cross sections to generate. The types of spatial domains that can be specified are the following:

  subassembly by type: generate cross sections for each type of subassembly in the geometry,
 similar to MCC3. In this domain, each repeated subassembly in the geometry is considered a
 collective single tally region.
  subassembly by instance: generate cross sections for every individual subassembly in the
 geometry, treating each instance of a type of subassembly as a unique domain. This is more de-
 tailed and accurate than subassembly by type, but can be significantly more computationally
 expensive.
  material: generate cross sections on a per-material basis. With this domain type, there is no
 distinction of where the material is located in the geometry, meaning that all instances of a
 single material are tallied collectively. This domain type provides the least amount of detail.

For energy group information, PyOpenMC includes support for various common predefined energy
group structures, including any supported by OpenMC, as well as the ANL groups structures (ANL9,
ANL33, ANL70, and ANL230). Alternatively, users can provide a list of custom energy group
bounds. The final minimum required input is list of reactions for which to produce cross sections.
Various types of scattering (requires additional information about how to process the scattering
cross sections), absorption, fission, transport, and (n, x) reactions are supported (detailed in the
PyARC tutorial [32]).

 Users can further customize the MGXS library to include:

  Cross section information for delayed neutron precursors
  Microscopic cross sections for a provided list of nuclides (macroscopic cross sections are
 produced otherwise)
  Temperature dependent cross sections for specific materials at various temperatures. Note,
 one OpenMC simulation will run for every combination of material temperatures.

 Additionally, users can improve the fidelity of the MGXS results by specifying relative error
triggers, meaning the simulation will continue beyond the original number of batches specified (up
to a specified maximum) until the error in all MGXS tallies is below the specified threshold.

 19

 A full detailed description of all of this input can be found in the PyARC tutorial [32].

4.3.2 Output Description

Upon completion of the OpenMC run, binary files containing the MGXS data will be returned as a
zip folder to users, which can then be used in other applications. As well, the k-effective results will
be provided to the user in the summary file just like a standard PyOpenMC run. If temperature
dependent cross sections were requested, a table with each set of detailed k-effective results from
the different combinations of material temperatures will be provided as shown in Fig. 4.4.

Figure 4.4: Example k-effective output from a temperature-dependent OpenMC MGXS simulation.

 Additional optional output that can be provided is information about zero-value cross sections.
If requested, warnings are issued and recorded for which domains and which cross sections return a
value of zero. This is primarily provided as information for debugging issues in models, and can be
quite lengthy, so this option is not turned on by default.

5.3 PyGriffin Deprecation (v3.0.0)

This work was completed in FY25 through funding from the DOE-NEAMS Multiphysics TA.

5.5 OpenMC Multigroup Cross Sections (v3.0.0)

This work was completed in FY25 through funding from the DOE-ART FRP.

 As described in Section 4.3, PyOpenMC was upgraded to include the capability to generate
multigroup cross sections (MGXS). As previously noted, PyARC was originally developed to use
MC2 -3 [6] as the sole method for MGXS generation for fast reactor analysis for both the ARC codes
and Griffin. The ARC codes still require MC2 -3 in PyARC, but this newly developed connection
between OpenMC and Griffin allows for users to choose their MGXS generation method depending
on their needs. Currently, the PyOpenMC-PyGriffinConnect workflow offers identical features to
the PyMCC3-PyGriffinConnect workflow: stead-state simulation of full hexagonal lattice cores using
subassembly-level cross sections. And beyond this, all solver types offered by PyGriffinConnect are
supported in both workflows.

 As noted in Section 4.3, PyOpenMC supports three types of domain specifications for generating
cross sections: subassembly by type (equivalent to the domain type used by MC2 -3), subassembly -
by instance, and material. Currently, only subassembly by type and subassembly by instance
domains are supported for connection to Griffin due to limitations in how OpenMC tallies are
performed and the information required by Griffin. If a material domain is specified for tallying in

 23

OpenMC, all the instances of that material are tallied together. For heterogeneous use in Griffin,
these tallied cross sections should be done for each instance of the material, which requires knowledge
of the material volume in every relevant geometric cell. This volume information is not easily
available and was deemed to be too developmentally complex to implement effectively in PyARC.
Therefore, material domains are not supported for Griffin. Similarly, microscopic cross sections from
OpenMC are not supported in the PyARC workflow for Griffin due to this same volume knowledge
that must be applied to determine nuclide density in the heterogeneous regions.

 If a user wishes to use OpenMC to generate MGXS data for Griffin, they just need to provide
the relevant multigroup xs block in the PyARC OpenMC input instead of the mcc3 input block.
The PyARC workflow will automatically generate the appropriate OpenMC geometry and input for
the specified MGXS domain type and run the OpenMC simulation to produce the cross section data
specified. Note, there are some restrictions and requirements on which types of cross sections are
generated for Griffin, but PyGriffinConnect has implemented various checks and automatic input
adjustment to ease this complexity for users. These restrictions and requirements are also described
in detail in the PyARC tutorial [32]. For both OpenMC and MC2 -3 cross sections, users have the
option to provide pregenerated cross section files to PyGriffinConnect. PyGriffinConnect will then
produce the ISOXML input file for Griffin that specifies using the OpenMC-generated cross sections.
This workflow makes use of Griffin’s native ability to convert OpenMC-generated cross sections into
Griffin-usable ISOXML-formatted cross sections [45, 46], meaning the MGXS data is not directly
translated by PyARC, but instead just provided as input to Griffin. Griffin execution will then
occur in the same manner as before, regardless of the source of the cross sections, and produce
the same output for k-effective and what is described in Section 5.2. For the OpenMC workflow,
additional information is provided to the user in the summary file that maps the PyARC domain to
the Griffin ISOXML ID for easier cross referencing and debugging.

6 DPA Calculations (v3.0.0)

This work was completed in FY25 through funding from the TCF with Westinghouse Electric
Company.

 Radiation damage is quantified using displacements per atom (DPA), which measures the average
number of times an atom is displaced from its lattice site due to neutron irradiation. High DPA levels
can cause swelling, embrittlement, and other forms of material degradation, limiting the lifespan
of fuel cladding, core internals, and other critical components. Therefore, reliable DPA estimates
are essential for assessing component durability, optimizing fuel cycle lengths, and evaluating new
materials for advanced reactor concepts.

 A previous common approach to calculating DPA has been to use a separate tool to prepare a
conversion factor that translates fast fluence into DPA for a specific material in a target application.
This conversion factor is then used to estimate DPA for various scenarios during analysis. In
previous LFR optimization work [47, 48], the conversion factor was prepared using the OpenMC
[16] Monte Carlo code and applied to calculate DPA from fast fluence data obtained by the ARC
code suite during the optimization process. To eliminate the need for pre-calculation and reduce
associated errors, the DPA evaluation capability has been integrated directly into the ARC code
suite and incorporated into the PyARC [49] through the connection of three relevant ARC codes:
MC2 -3 [6] for cross section generation, DIF3D [8] for neutron transport calculations, and REBUS
[9] for depletion calculations.

6.1 Method and Workflow

This section describes updates made in MC2 -3 and PyARC. The final quantity provided by PyARC
is DPA per second (DPA/s) at each region and depletion point, and the time integrated quantity
(DPA) can then be calculated by a user for their needs.

6.1.2 PyARC Implementation

This DPA post-processing routine was implemented in the existing GAMSOR procedure [11] of
PyARC. After the entire REBUS depletion calculation is finished, the neutron and gamma coupled
calculation is performed for each depletion step. After the coupled calculation at each step, region-
wise DPA/s values are calculated and returned to the user in the summary files for the corresponding
step. Materials and subassemblies of interest can be specified by a user. If a subassembly is not
specified, the DPA/s distribution of the selected material in the entire domain is provided. Detailed
descriptions of the user input and example input can be found in the PyARC tutorial [32].

6.2 Verification on a Lead Fast Reactor Benchmark

The material DPA cross section calculated by the ARC suite has been verified using the Westinghouse
LFR core problem addressed in the previous work [47, 48]. Details of this verification work is provided
in [49], but a summary follows. The MOX-fueled LFR core was employed without modification and
DPA was calculated using the same multigroup fluence and irradiation under full power conditions.
The average DPA value for the cladding material in the active middle core region was calculated
using both this new DPA method in PyARC and with OpenMC tallies through PyARC (which were
additionally post processed to calculate DPA), and the results were compared. From the analysis
in [49] it was shown that both methods for calculating DPA in cladding of the middle core region
agrees within 0.26%, indicating high confidence in the newly implemented DPA method in PyARC.

7 DASSH Conversion (v3.0.0)

This work was done over the course of FY24 and FY25 through funding from the DOE-ART FRP.

 A Fortran version [12] of the Ducted Assembly Steady-State Heat Transfer (DASSH) software
was recently developed with the intention of replacing the previously developed Python version
[23] in ARC workflows. PyARC had previously integrated the Python version [20], but due to the
replacement in workflows with the Fortran version, a conversion of the PyDASSH integration in
PyARC was initiated in FY24 to convert to using the newly adopted Fortran version of DASSH. The
Fortran version of DASSH was intentionally developed to support the same basic input parameters
as the Python version, but uses a different input syntax and was initially developed with stricter
geometric requirements than the Python version. As such, PyARC’s PyDASSH module was rewritten
to include additional geometric restrictions and change the methods in which the input was being
generated and executed and the output post-processed.

 Despite the major changes that were required directly in the PyDASSH module, the user-input
side of things remained largely unchanged, with the exception of providing additional options for the
DASSH geometric input to ease the user input burden (elaborated on in Section 7.1) and removal of
any defunct input options. That is to say, the intention of this upgrade was to maintain backwards
compatibility as much as possible such that users who previously had PyARC input developed for
the Python version integration could still use the input, with minor revisions, with the Fortran
version integration. During this conversion process and updating the geometry requirements, it
became apparent that some of the previously required pieces of user input for DASSH could be
automatically inferred from other parts of the input file, which could reduce the user burden. As
such, a secondary goal of this upgrade became to reduce the user input burden for DASSH. A
summary of these changes is given below while a detailed description of the user input is available
in the PyARC tutorial [32].

7.1 Geometry Restrictions and Input

As of the version of DASSH that was released in ARC v12.1.0, several geometric restrictions were
imposed:

 1. Only three unique axial zones may be defined in each assembly. Axial zones tend to correspond
 to the subassemblies, but they can differ.

 2. If an assembly has more than one pin bundle present, they each must be defined with the
 same overall dimensions/geometry (i.e. identical pin pitch, diameter, number of rings in the
 lattice, wire wrap, etc.), though the material and physics properties can differ.

 3. All subassemblies located at the same axial zone across the core must be all defined as a pin
 bundle, or they must all be defined as a simple/porous body.

 4. Each assembly in the core must be divided by the same sets of axial planes across then entire
 core.

 28

 Because of these geometry restrictions, additional detailed input validation checks were imple-
mented in the precheck stage of PyDASSH. To prevent users from having to redefine their geometry
entirely, logic and additional simplified user input options were put in place to automatically redefine
the axial zones in the geometry and to auto-define the DASSH geometry based on the geometry
input block of the SON input file.

 Subassemblies in DASSH can be defined as one of two types:

  pin detail: the subassembly will be treated as a pin bundle with the provided dimensions
 and properties.

  simple: the subassembly will be treated as a homogenous body (also known as a porous body)
 with the provided bulk properties.

To reduce user input and allow the geometry to easily comply with the geometry restrictions listed
above, the PyARC input block allows for users to specify if a subassembly should:

  inherit from another subassembly, meaning all geometry and physical properties are identical;

  combine with another subassembly, meaning the axial zone of the specified adjacent sub-
 assembly will be extended to include this subassembly;

  or be ignored entirely from the simulation (ignore).

 Additionally, for any subassemblies that are defined as detailed pin bundles, a new option was
introduced to use pin geometry which would automatically generate an identical DASSH pin lattice
geometry from the subassembly definition in the main geometry input block of the SON input file,
if possible. A feature of this same input is that a subassembly could be defined to use the geometric
parameters of an entirely different subassembly, thus allowing easier compliance with restriction
#2 above. Previously, if a subassembly was to contain a pin bundle for DASSH simulation, it was
required that the geometry of the pin bundle be completely redefined, because it could differ from
the original geometry in order to be suitable for the DASSH calculation. The option still remains
to manually define an entirely different geometry, but these new input options should ease the
input generation process and improve the reliability where the DASSH geometry is identical to the
original PyARC geometry. To highlight the importance of providing this feature, Fig. 7.1 below
shows the previous input syntax required to define a DASSH pin lattice assembly, and the new
option to simply use what is already provided in the geometry input.

7.2 Other Input

Additional DASSH-related input in PyARC includes information regarding core-wide properties,
flow rate or temperature assignments, custom material properties, and output options. The first two
sets of input remained largely unchanged from the previous implementation that used the Python
DASSH version [20, 23].

 The support for custom material properties to be defined directly in the PyARC SON input was

 The previous implementation using the Python version included extensive plotting options to

7.3 Future Work

Recent developments to the DASSH code in FY25 removed all geometric restrictions that are listed
in Section 7.1, allowing for free-form geometry. As such, the majority, if not all, of the prechecks that
were established in PyDASSH (prior to these changes in DASSH) to support the former geometry
restrictions can be removed, allowing users more input freedom. Because this version of DASSH has
not yet been released with the ARC code suite, the geometric restrictions in PyARC will remain
until a new version of DASSH is released.

8 NUBOW-3D Integration (v3.0.0)

This work was completed in FY25 through funding primarily from the TCF with Westinghouse
Electric Company and additional support from the DOE-ART FRP.

 The NUBOW-3D code [13] predicts in-reactor deformation (or “bowing”) of hexagonal fuel
assembly ducts under thermal expansion, irradiation swelling and creep, and computes resulting
contact forces, clearances and reactivity effects. Most analysis workflows rely on output from DASSH
[12] to provide the necessary input files for the fast flux, temperature distributions, and translated
geometric information to NUBOW-3D. Therefore, NUBOW-3D was integrated into PyARC via the
PyNUBOW module and connected to PyDASSH (Section 7) for easier bowing analysis workflows.
A high-level description of this new integration is provided here, and additional details can be found
in the PyARC tutorial [32].

8.1 Duct Definitions

In order to accurately calculate bowing, detailed properties about the ducts of the reactor are
required that go beyond what is available in the standard PyARC geometry input definition.
Specifically, ducts are fixed by their bottom (nozzle) to the grid plate, and are supported by point
contacts using restraint rings (which are located at the same position as load pads). The total
bowing is the sum of the combined effects of each of these duct components:

  Grid plate thermal expansion

  Bowing due to thermal gradient across the duct cross section

  Inelastic strains over time

  Restraints imposed by duct to duct contact as well as due to the restraint rings

 Therefore, duct types have to be specifically defined with material properties and additional
detailed geometric input. In NUBOW-3D, a duct is made up of three elements:

  Load pad: a small contact surface on each duct face; it transmits forces between adjacent
 ducts under reactor conditions.

  Restraint ring: an outer boundary element; it limits radial duct movement, maintaining core
 geometry.

  Nozzle: a lower assembly extension; it connects the assembly to the support (grid plate) for
 inlet flow.

Furthermore, each duct must have 1-4 restraint ring definitions with unique axial locations, and
there are typically two load pads and restraint rings per duct. Details for how the geometric and
mechanical properties are defined for load pads, restraint rings, nozzles, and grid plates is provided

 31

in the PyARC tutorial [32]. From the input provided for these duct components, in conjunction with
the main geometry input, the appropriate axial mesh dimensions for the NUBOW-3D simulation is
automatically determined. This axial mesh information is necessary for the DASSH simulation as
described below (Section 8.2).

 An important note regarding the dimensions of the NUBOW-3D geometric and duct input is
that NUBOW-3D expects these to be the dimension at the specified fabrication temperature, which
is usually different from the temperature and dimensions specified in the main PyARC geometry
input. Therefore, to simplify this for users, the “fabrication temperature” in NUBOW-3D is set
to the inlet temperature specified in the DASSH input as this is expected to correspond to the
dimensions specified in the main geometry input. Options are provided to the user to change this
“fabrication temperature,” but it is then their responsibility to ensure all dimensions are adjusted
accordingly.

8.2 Workflow

PyNUBOW is the module that was developed in PyARC to support the NUBOW-3D workflow and
is connected to PyDASSH for passing relevant information between each of the codes. NUBOW-3D
requires three types of output files from DASSH to be provided as input:

  temperatures distributions (one per DASSH time step)

  fast flux distributions (one per DASSH time step)

  duct adjacency information (i.e., the core geometry)

These files can be provided directly as pre-generated input files to the NUBOW-3D input block,
thus bypassing the PyDASSH run step, or they will be automatically generated during runtime by
PyDASSH and provided to PyNUBOW. In order for PyDASSH to generate these files, information
about the axial mesh dimensions must be provided so that the distributions are calculated at
the appropriate axial locations during runtime; this information is gathered from the PyNUBOW
precheck stage and given to PyDASSH to use all the way through the post-run stage. After
PyDASSH runs and post-processes the results to produce the necessary input for NUBOW, the files
and calculated pressure drop are provided to the PyNUBOW prerun to complete the rest of the
workflow. A visual depiction of this workflow is shown in Fig. 8.1.

8.3 Future Work

The NUBOW-3D code is under active development. One of the key developmental areas currently is
changing the structure and content of the output. Because of this, the PyNUBOW implementation
in PyARC does not yet post-process the results and return any information to the user in the
summary files. Instead, the raw output files from NUBOW-3D are returned. When the output
from NUBOW-3D has stabilized in form and content, the post-run stage for PyNUBOW will be
implemented to be able to return data back to the user in PyARC standard format.

9 Additional Enhancements

PyARC is continuously adding features or making minor improvements to enhance the user experi-
ence, improve workflows, and improve quality assurance. Below are some recent improvements that
are worth noting that have become available in recent PyARC releases.

WATTS Connection Enhancements (v2.1.0, v2.2.0) The Workflow and Template Toolkit for
Simulation (WATTS) [52] is an open source Python toolkit that provides a simple interface to
systemically run many simulations with varying inputs, such as for optimization or sensitivity
studies, or to provide the information to a subsequent integrated code as part of multi-disciplinary
workflows. WATTS operates on the basis of “plugin” Python classes for specific codes or applications
that build the input, launch simulations, and then reads in the output. The post-processed output
from PyARC is provided via a Python user object.results object to WATTS. Original support
for WATTS integration was introduced in PyARC v2.0.0 and enhanced in v2.1.0 and v2.2.0 by
adding more output results to this user object.results object. The additional output added
for this connection includes area and peak power (radial and axial) as calculated by DIF3D [8],
nuclide inventory as tracked by REBUS [9], decay heat and activity calculated by REBUS and
ORIGEN-S [14], and detail k-effective results from perturbation theory analysis with PERSENT
[10]. Additionally, all new code integrations since the WATTS connection was established provide
post processed results in the user object so that it is available to the WATTS plugin as well.

Versioning Information (v3.0.0) PyARC relies on the existence of a configuration file, which can
exist in the PyARC directory or in one’s home directory. This file tells PyARC where to find the
various executables at runtime. Previously, the information in the configuration file was not retained
as output from a run at all, meaning that it was possible to run an input, change the executables in
the configuration file, and then run it again without any record of the changed executables. This
can lead to quality assurance issues with analysis and replicating results. Therefore, PyARC has
added executable and data library version info to the runtime output and the user info output
file, allowing for this key RTE and configuration information to be retained. In all cases, the real
absolute paths to executables and libraries are provided (i.e., if the configuration file points to a
link to an executable, the actual executable path, not the link, will be printed). And if version
information is obtainable from an executable, it is also provided. This information will increase
reproducibility of results for users.

Preprocess Only Option (v3.0.0) A runtime option was added to PyARC to run just the
preprocessing stages (precheck and prerun), stopping just before execution (see Section 2.1.2).
Activated by using --preproc-only at the command line, the execution will stop just before the
run stage, returning the contents of the working directory in a zip folder. This can be helpful for
users to check input generation or gather input files to use elsewhere, rather than having to go
through the entire execution, which can be lengthy in some cases.

10 Future Work

PyARC is under continuous development by integrating new codes or workflows to adapt to user
and industry needs. While there have been many new developments presented here, a few were
noted to have outstanding tasks in order to be fully completed. As well, there are a number of
enhancements to existing code integrations planned to support additional workflows.

Language Server Upgrade Completion Section 3 presented a detailed overview of the current
state of the language server upgrade, noting that the upgrade is still in progress and has entered
the schema deprecation stage (Section 3.3). In FY26, the language server upgrade is planned to
fully deprecate the schema with the implementation of templates and autocompletion through the
server. Should time and funding allow, parts of PyARC’s current precheck stage will be migrated
to the Python database of the language server. This migration of the precheck is not required for
fully converting to use of the language server instead of the schema, but it will greatly enhance user
experience in the GUI by taking advantage of LSP-specific features.

Continued PyOpenMC MGXS Development Section 4.3 presented the new MGXS capability in
the PyOpenMC module. The current implementation is supported for connection to the Griffin
code, but there is also a possibility to connect this to the ARC codes as well. Just as in the Griffin
implementation, the OpenMC-generated MGXS data would replace the MC2 -3-generated cross
sections in the ARC workflow. To do this effectively, it would be wise to use an ANL in-house
developed code that converts various MGXS data structures into the ARC ISOTXS form. This
code is currently closed source, but to make it more effective as a PyARC dependency, open source
licensing will be pursued. This can then be used to implement the connection between OpenMC
MGXS and the ARC codes in PyARC.

 Additional future OpenMC MGXS work involves implementing support for variance reduction.
Currently, the MGXS generation process can be costly to obtain reasonably good statistics in all
phase space of the reactor geometry. To improve the MGXS data produced and speed up the
simulation time, variance reduction techniques should be introduced. In FY25, progress was made
in integrating OpenMC’s The Random Ray Method (TRRM) [53] as a means for variance reduction,
but due to incompatibility between dependencies in the Workbench RTE and the required version
of OpenMC to support this, development was put on hold. However, the conflict of dependencies in
the RTE should be resolvable, and thus development can continue on this feature in the future.

PyDASSH Free-Form Geometry Support As noted in Section 7.3, the DASSH conversion was
developed to support the highly restricted geometry configuration requirements present in the
original Fortran version of the DASSH code. Since the development in PyARC, DASSH has been
upgraded to remove these geometry restrictions and allow for more free-form geometry definitions.
The PyDASSH module in PyARC will be revised to remove many of the restrictions and prechecks
in place currently, to support this free-form definition when a new version of DASSH is available
that contains this feature.

11 Summary

PyARC is an open source workflow management tool that relies on the Workbench framework to
support complex fast reactor analysis and code-to-code verification of the “extended suite of Argonne
Reactor Computation (ARC) codes.” Integration of these codes into PyARC and Workbench directly
benefits the advanced reactor community by:

  Providing a set of controlled, maintained, documented and validated scripts to generate codes’
 inputs, which promotes best practices, reduces the learning curve, and facilitates project
 collaboration.

  Improving the user experience: the Workbench interface provides assistance for building an
 input through auto-completion, real-time validation, document navigation, and geometry and
 results visualization.

  Automating complex calculations and workflows for reactor analysis.

 Since its FY22 release of version 2.0.0, PyARC has seen many new additions and enhancements to
support additional analyses. Presented in this report were the details on several major developments

 38

which have all made available in the most recent v3.0.0 release (September 2025), or earlier.
Specifically, the following developments were presented:

  The progress of upgrading PyARC to use Workbench’s Language Server Protocol (LSP)
 capability in a new language server (Section 3). This upgrade is still in progress but is
 expected to be completed in FY26.

  Various new capabilities available in the OpenMC integration (Section 4): support for tallies
 [30], depletion calculations [30, 34], and multigroup cross sections (MGXS) generation. The
 depletion capability was used successfully in a continuation of an LFR neutronics benchmark
     analysis [34, 36].

  The Griffin integration was upgraded in several different ways (Section 5) [30]: use of the
 analogous RGMB input form, adoption of PyGrffin into PyARC directly, advanced post-
 processing output, use of MOOSE’s PyHIT for more reliable input generation, and connection
 to OpenMC for MGXS use.

  The ability to calculate displacements per atom (DPA) with MC2 -3 was added and verified on
 an LFR model (Section 6) [49].

  The DASSH integration was updated to use the new Fortran version of the code, replacing
 the previous Python version (Section 7) [30].

  NUBOW-3D was integrated as an entirely new code to support core bowing analysis (Section 8).

 PyARC development will continue to focus on finalizing some of the new developments presented
and enhancing workflows by developing new connections between existing integrated codes for
additional types of analyses.
