SUMMARY

This project developed the LAPIS compiler framework, built on the Multilevel Intermediate Repre-
sentation (MLIR), to optimize sparse linear algebra operations and support performance portability
across diverse architectures. The main innovation of LAPIS is the Kokkos dialect, which allows
for lowering codes from a high productivity language to different architectures in an elegant way.
The dialect also allows the conversion of lower-level MLIR code to C++ Kokkos code, facilitating
the integration of scientific machine learning (SciML) models into applications.
To extend LAPIS for distributed memory architectures, a new partition dialect was created to
manage the distribution of sparse tensors and express communication patterns for sparse linear
algebra operations. This dialect also supports the distributed execution of operators and includes
algorithmic optimizations to minimize communication to improve performance.
The project also demonstrates that MLIR can enable effective linear algebra-level optimizations,
improving performance on different GPUs for both sparse and dense linear algebra kernels. Key
applications of LAPIS include sparse linear algebra and graph kernels, TenSQL, a relational
database management solution built on GraphBLAS, and the development of subgraph isomorphism
and monomorphism kernels, showcasing performance portability.
In summary, the LAPIS framework supports productivity, performance, portability, and distributed
memory execution, while also enabling linear algebra-level optimizations that are challenging in
traditional programming languages, with successful applications ranging from simple sparse linear
algebra to complex graph kernels.

1. INTRODUCTION

Optimizing sparse linear algebra using compilation techniques has been the holy grail of compiler
development for decades. Substantial progress has been made in several directions using recent
frameworks such as TACO [77], SpDISTAL [144], LegateSparse [146], and Comet [99]. These
works differ in their goals, capabilities, and the frameworks they are built upon. Meanwhile, the
Computational Science and Engineering community has largely relied on traditional programming
languages such as FORTRAN and C++. To support portability across different computer archi-
tectures, the community has coalesced around directive-based approaches such as OpenMP and
OpenACC, as well as template meta-programming approaches like Kokkos [131]. Sparse linear
algebra operations are explicitly handwritten using native programming models (e.g., CUDA),
directives, or meta-programming approaches. Libraries like Kokkos Kernels [111] exemplify a
sparse linear algebra library that utilizes the Kokkos meta-programming framework. This option
is performance portable, allowing developers to write a sparse linear algebra kernel using Kokkos
that achieves good performance across a variety of CPUs and GPUs. When evaluating the afore-
mentioned approaches based on performance, portability, productivity and extensibility as the four
metrics, all approaches fall short in at least one of these four areas, particularly for sparse linear
algebra use cases.
One of the recent developments that motivated this project is the flexible and extensible Multilevel
Intermediate Representation [85] (MLIR) compiler infrastructure. The project aims to build a sparse
linear algebra-aware compiler that can optimize operations at the linear algebra level and support
performance-portable linear algebra operations written in a high-productivity front end. We sought
to create an approach that maps from the high-productivity language to shared-memory CPUs,
accelerators such as GPUs, modern data flow hardware, and distributed memory architectures. The
final goal of extensibility required us to minimize the changes needed within MLIR itself to support
the objectives.
We also aim to demonstrate our new compiler infrastructure on a suite of applications, including
sparse linear algebra, graph attention networks, GraphBLAS, and subgraph isomorphism kernels,
to name a few. The popularity of scientific machine learning (SciML) approaches has created
an additional requirement for us: we want to use this compiler infrastructure to lower a SciML
model to a level where it can be seamlessly integrated into another SciML code written using a
programming model such as Kokkos.
This project achieved all of these objectives in a systematic manner. The central piece of the project
is LAPIS [90], a new open-source compiler framework built on top of MLIR. The main innovation
in LAPIS is a new dialect called the Kokkos dialect, which is performance portable. Chapter 2
describes LAPIS in detail and demonstrates its performance on several sparse and dense linear
algebra operations. LAPIS also allows for the MLIR code in the Kokkos dialect to be emitted as
Kokkos C++ code. This functionality enables the lowering of SciML models to the Kokkos dialect

 15

and their subsequent raising back to C++ code that can be integrated into a computational science
application. We demonstrate such a use case with the SciML code MALA [38], which serves as
an ML surrogate for density functional theory calculations.
To extend LAPIS for lowering code to distributed memory architectures, we had to architect the
distributed memory sparse computation mechanisms within MLIR. We developed a new partition
dialect (see Chapter 3) that allows for the distribution of sparse tensors and provides a clear way
to express the communication patterns needed for sparse linear algebra operations. Distributed
memory execution also requires the partitioning of different operators, which is managed by the
partitioning dialect. We demonstrate the use of this partition dialect in a distributed execution
of a graph attention network example (see Chapter 4). The partition dialect also incorporates
algorithmic innovations to utilize the operator graph to identify the maximal communication-free
subgraph, thereby improving the performance of the lowered code.
The idea that a compiler infrastructure such as MLIR can enable compiler optimizations at the
linear algebra level has been established in theory. We demonstrate that this can indeed improve
performance on different types of GPUs in practice for both sparse and dense linear algebra kernels
(see Chapter 5). Finally, we conclude with two overarching examples. First, TenSQL is a relational
database management solution constructed on top of GraphBLAS (see Chapter 6). Second, we
develop subgraph isomorphism and subgraph monomorphism kernels using GraphBLAS and lower
them using LAPIS to demonstrate performance portability (see Chapter 7).
Altogether, we have developed the LAPIS compiler framework with Kokkos and Partition dialects
to support productivity, performance, portability, and distributed memory architectures. We have
also demonstrated that, using such a framework, one can perform linear algebra-level optimizations
that are nearly impossible in a programming language like C++. Additionally, we have showcased
the use of LAPIS across a range of use cases, from simple sparse linear algebra to complex graph
kernels.

ABSTRACT
Portability, performance, and productivity are three critical dimensions for evaluating a program-
ming model or compiler infrastructure. Several modern programming models for computational
science focus on performance and portability. On the other end, several machine learning focused
programming models focus on portability and productivity. A clear solution that is strong in all
three dimensions has yet to emerge. A second related problem arises when use cases from compu-
tational science converge with machine learning. The disparate popular frameworks of these fields
require programmers to manually integrate codes written in different frameworks. We present
LAPIS, an MLIR-based compiler that addresses both challenges. We demonstrate that LAPIS
can automatically lower sparse and dense linear algebra kernels from computational science and
artificial intelligence use cases. We also show how LAPIS facilitates the integration of codes
between PyTorch and Kokkos. Finally, we compare kernel performance with the default MLIR
implementations on diverse architectures to demonstrate portability.

2.1. Introduction

While programming framework designs can be evaluated using many dimensions, portability,
performance, and productivity remain three critical ones for long term adoption. The computational
science community focusing on traditional high performance computing relies heavily on traditional
programming languages such as C++ and Fortran. Programming models such as MPI, OpenMP,
OpenACC or frameworks such as Kokkos [131], Legion [20], RAJA [23], are commonly used.
Higher level frameworks such as Trilinos [96] and PETSc [18] provide one more level of abstraction
for linear algebra to the computational scientists. The most widely used frameworks like Kokkos
focus on performance and portability and less on productivity (Figure 2-1).

On the other end, emerging fields of artificial intelligence or machine learning (AI/ML) rely on
productivity and portability focused frameworks such as PyTorch [104], JAX or Tensorflow [11].
These frameworks rely on manual interfacing to hand optimized libraries such as cuBLAS or
rocBLAS for performance. Such a dependence leads to “hardware/software lottery” [64] which
results in a narrow co-evolution of algorithms, libraries and hardware limiting fundamental scientific
progress. The heavy reliance on dense transformer-style architectures is one recent example of such
co-evolution.

We hypothesize a compiler framework that can support performance, portability, and productivity
will improve productivity of computational science and rapid high performance algorithmic devel-
opment within AI/ML. The development of such a compiler framework based on the lessons learned

from developing Kokkos [131], a performance portable programming framework for computational
science and engineering (CSE), is the first of two challenges addressed in this work.
Among AI/ML uses, physics-informed AI/ML is becoming another tool in the tool box in the
hard sciences like biology, classical mechanics, magnetohydrodynamics, density functional theory,
molecular dynamics, and chemistry. Several of these applications focus on numerical simulation
of some physical phenomena. Such simulations are computationally demanding especially for high
fidelity needs.

2.2. Background

Kokkos Kokkos [131] is a programming framework focused on performance portability. Kokkos
enables single source performance portable codes by providing a portable programming framework
for CPUs and GPUs. It has been adopted widely in multiple CSE applications and demonstrated on
petascale and exascale platforms [26, 67, 128]. Kokkos has specific abstractions for execution and
memory spaces. Execution spaces are selected at compile time based on the target architectures
(e.g., OpenMP/Serial for CPUs, or CUDA for NVIDIA GPUs). Memory spaces represent host and
accelerator memory, as well as temporary scratchpad (e.g., CUDA shared memory for use by a
team of threads). The fundamental parallel patterns in Kokkos are parallel kernels belonging to one

 19

of three patterns parallel_for, parallel_reduce and parallel_scan. The fundamental data structure
is a multi-dimensional arrays (Kokkos::View). These constructs and the View are templated on
how they have to be run (Serial, OpenMP, CUDA), and where memory is located (host, device, or
shared memory). Kokkos also provides the DualView, which manages the case when data must be
replicated in two different MemorySpace (Host and Device). Users are responsible for managing
where the most recent updates happened and synchronizing explicitly. This performance focused
option is one missing piece in the memory constructs of MLIR framework. Our custom kokkos
dialect in LAPIS introduces the notion of DualView as a memory space for better performance
of lowered code in heterogeneous systems, but without incurring significant overhead in single-
memory (CPU and APU) systems.

MLIR MLIR (Multi-Level Intermediate Representation) is an open-source compiler infrastruc-
ture project [85]. The focus is to make it easy to build domain-specific compilers and support
multiple heterogeneous hardware architectures. The infrastructure primarily relies on intermediate
representations that are flexible concepts ranging from high level mathematical abstractions to low
level abstractions for hardware architectures. MLIR is organized into dialects, each with its own
operations, attributes and types. Dialects such as tensor or linalg (linear algebra) describe
high level operations. For example, a matrix-matrix multiplication can be expressed with a single
“instruction” from the linear algebra dialect, linalg.matmul. Compared to a low-level IR like
LLVM, MLIR retains high-level information about code behavior, enabling powerful compiler
optimizations (e.g. fusion of linear algebra operations) that would otherwise be very difficult to
perform safely on scalar LLVM code. In addition to the dialect specifications, MLIR includes built-
in compiler transformations to replace instructions with equivalent but lower-level code (lowering).
For example, a linalg.matmul instruction might be replaced with a triply-nested for loop which
computes the result matrix one element at a time with scalar arithmetic.
Python’s popular ML frameworks like PyTorch [104] and TensorFlow [11] are two early users
of MLIR. An existing extension for PyTorch called torch-mlir [93] provides the functionality to
generate an MLIR function from an ML model. Many built-in MLIR dialects such as x86vector
and amdgpu are focused on specific architectures. Others can represent general programming
models like OpenMP and OpenACC, but MLIR lacks passes that can finish lowering from these
dialects to an executable or source code. The fundamental gap addressed by this work is a pipeline
that is automatic, end-to-end, and performance-portable.

2.3. LAPIS Framework

The LAPIS framework provides two main features. First, it provides an automatic lowering pipeline
from high-level MLIR to portable, parallel Kokkos C++ source code. Second, it provides a custom
Kokkos dialect with operations that allow Kokkos constructs to be represented directly in MLIR.
Generally, the high-level MLIR that LAPIS accepts as input should conform to the linalg-on-tensors
set of dialects. This is one of the main “backend contracts” supported by torch-mlir [93], but it
is broad enough to describe programs beyond just ML models. It represents computations and
tensors using the linalg and tensor dialects, respectively. Attributes from the sparse_tensor

 20

dialect can also be used with tensor types to specify various sparse formats. The func, scf and
math dialects define control flow and provide common numerical functions.

2.3.1. Kokkos Dialect

LAPIS includes a custom kokkos dialect to represent common Kokkos constructs directly in MLIR.
Like Kokkos itself, this dialect uses portable abstractions for execution and memory. In Kokkos,
the basic abstraction for executable kernels is the parallel_for which executes over a policy.
The policy can describe a multidimensional rectangular iteration space. A parallel loop can also
perform one or more reductions using an associative join operator, making it a parallel_reduce.
Top-level policies are templated on execution space, which describes where the kernel should
run (i.e., GPU or CPU). These parallel loops can also nest up to three levels deep. On GPUs,
Kokkos maps this maximum level of nesting to grid, block, and thread dimensions (using CUDA
terminology). On CPUs, the first two dimensions map to threads and the innermost dimension
maps to vectorizable for-loops. In Kokkos, the policies corresponding to the three nesting levels
are called TeamPolicy, TeamThreadRange and ThreadVectorRange. Parallel loops without
nesting can use the simpler RangePolicy for 1D iteration spaces and MDRangePolicy for higher-
dimensional spaces. The kokkos dialect in LAPIS provides three operations for parallel loops,
as well as attributes to specify nesting levels. Together, these cover all possible policy and loop
nesting structures allowed by Kokkos.

 • range_parallel: a RangePolicy or
 a MDRangePolicy. Accepts executionSpace attribute and parallelLevel attribute to
 specify nesting level.

 • team_parallel: a TeamPolicy loop, for the outermost loop of a nested kernel. Accepts
 optional team size and vector length hints as operands, which allow these policy parameters
 to be computed at runtime based on heuristics.

 • thread_parallel: Represents a recurring pattern in Kokkos for two-level parallelism: a
 TeamPolicy and
 a TeamThreadRange that iterates over a space together and allow the inner loop to use
 ThreadVectorRange. This also accepts a vector length hint operand.

Furthermore, the following operations are defined in the kokkos dialect for synchronization:

 • single: execute a block only once within a team, or within a thread. The level is controlled
 with an attribute.

 • team_barrier: synchronize all the threads within a team.

 22

2.3.2. Lowering to Kokkos Dialect

Lowering from the built-in scf dialect to kokkos takes place over three passes. These are the final
three passes in the overall pipeline, and result in IR that is compatible with the Kokkos emitter.

 • parallel-unit-step: rewrite each scf.parallel to start iterating at 0 and increment by
 1.

 • kokkos-loop-mapping: replace each scf.parallel operations with one of the Kokkos
 parallel loop types above.

 • kokkos-dualview-management: insert operations to manage lazy migration between het-
 erogeneous memory spaces (this is detailed in Section 2.3.3).

kokkos-loop-mapping is responsible for choosing how to map scf.parallel loops to Kokkos,
computing heuristic values for team size and vector length, and automatically inserting synchro-
nization operations.

In the first step, the pass decides whether a given parallel loops can be executed on a GPU at all.
Any loop that performs explicit memory management (e.g., memref.alloc) must be run on the
CPU. Next, the rewriting of scf.parallel loops to Kokkos loops is decided based on nesting
depth:

 • 1: Use range_parallel.

 • 2: Use thread_parallel for the outer loop, and a ThreadVector-level range_parallel
 for the inner loop.

 • 3 or more: Use team_parallel for the outer loop, a TeamThread-level range_parallel
 for the second loop, and a ThreadVector-level range_parallel for the innermost loop. All
 loops between the second and last are converted to sequential for-loops.

In the case with nesting level of at least 3, we always make the innermost loop parallel to improve
memory coalescing on GPUs.

In the second step, we analyze how a loop’s iteration bounds are computed and try to estimate
how much parallelism it uses. This is crucial for generating performant Kokkos, especially for
the vector length argument of team_parallel and thread_parallel. If the vector length is
too small, GPU code that could benefit from memory coalescing will use only a portion of each
cache line. But if the vector length is too large for the workload, then some threads in each warp
will sit idle. In MLIR, iteration bounds may be compile-time constants, which makes this esti-
mation straightforward. But in other common cases, the bounds may depend on the dimensions
of dynamically-shaped memrefs. In this case, we can detect common patterns and insert code to
compute this estimate at runtime. An especially beneficial pattern is the CSR-like iteration pattern,
shown in pseudocode below. Recall that the previous pass has rewritten all parallel loops to start at 0.

 23

scf.parallel %i from #0 to %N {
  %i_plus_one = arith.add %i, #1
  %begin = memref.load %offsets[%i]
  %end = memref.load %offsets[%i_plus_one]
  %len = arith.sub %end, %begin
  scf.parallel %j from #0 to %len {
 %index = arith.add %begin, %j
 %val = memref.load %values[%index]
 ...
  }
}

This is the basic code structure that is generated for compressed-sparse row (CSR) or compressed-
sparse column (CSC) parallel traversal. In the case of the sparse linalg.matvec operation with
the CSR format:
 • %N: the number of rows
 • %i: the current row
 • %len: the number of entries in the current row
 • %index: the index at which to read the matrix value and column index
In this case, our best estimate for the parallelism of the inner loop (which will become a ThreadVector
range_parallel) is the average number of entries per row, rounded up. Let 𝑘 = %offsets[%N].
Then this average is simply ⌈𝑘/𝑁⌉, or equivalently (𝑘 + 𝑁 − 1)/𝑁. This value can be arbitrarily
large while the actual vector length is limited by hardware in most backends (for example, the warp
size 32 on CUDA), so we later insert C++ code to clamp the vector length to the maximum for
the enabled backend. If no hint for team size and/or vector length could be found, then the default
value of 0 is used in the IR. In the generated C++ code, this becomes the Kokkos-defined default.
The last step of kokkos-loop-mapping is to insert synchronization operations. Kokkos::single()
is used in Kokkos to ensure that code with side effects is executed exactly once within a team or
thread. After deciding how to map the scf.parallel loops, we look for operations with side
effects that are inside some parallel loop but not inside the innermost parallel loop. These opera-
tions are moved inside a new single operation. We also conservatively generate team_barrier
operations inside team_parallel bodies, after each TeamThread-level range_parallel opera-
tion that does not perform a reduction. (as reductions imply synchronization already). This is not
necessary for ThreadVector-level loops since they have implicit (SIMD-like) synchronization on
all Kokkos backends.

2.3.3. Kokkos inspired memory references

MLIR’s memref dialect supports an optional memory space attribute as part of the memref type.
When lowering to a heterogeneous target system, this can explicitly mark a buffer as living in

 24

host or device memory. However, MLIR has only limited built-in capabilities for automatically
managing the migration of memory between spaces, either at compile-time or runtime. The
sparse-gpu-codegen pass lists the buffers accessed by a GPU kernel, and copies all of them
from host to device before launching the kernel. Then it copies all possibly-modified buffers back
to host after the kernel finishes. This generates redundant host-device transfers for programs with
multiple GPU kernels, since in a real-world program many consecutive kernels may need to access
the same data on device without any intervening usage on host.
LAPIS solves this problem with LAPIS::DualView, a lightweight runtime data structure to effi-
ciently manage a buffer that may be used on both host and device. Like the existing Kokkos::
DualView, on heterogeneous backends LAPIS::DualView contains a host buffer and device buffer
with the same data type and dimensions. On backends with only one memory space, the host and
device buffers are the same. DualView also contains flags for whether each buffer has modifications
that are not reflected in the opposite buffer.
Like sparse-gpu-codegen, the final pass in the LAPIS pipeline kokkos-dualview-management
scans the program for where each memref is accessed. Along with host and device, DualView
is a memory space attribute defined in the Kokkos dialect. Each memref is assigned one of these
spaces. Instead of generating eager data copies, our pass inserts lazy copies (kokkos.sync) that
only occur if the source buffer has actually been modified since the previous sync. And instead
of eagerly copying modified buffers back to host after a GPU kernel (or host access), we insert
the corresponding kokkos.modify operation to set the modified flag. When no data transfer is
actually necessary, the overhead of a sync operation is that of checking a boolean flag.
LAPIS::DualView also handles memory management and memref dialect subviewing and casting
operations. The subview or cast buffer (“child”) must alias the original buffer (“parent”) for correct
semantics, so LAPIS::DualView stores the tree of parent-child relationships. To ensure that mul-
tiple children with the same parent maintain consistent contents, children share modified flags with
their parents. Calling sync on a child DualView will call sync on its parent. LAPIS::DualView
also uses reference-counting with std::shared_ptr to make sure that the underlying memory
allocation (owned by some parent) stays in scope as long as any of its children are alive.

2.3.4. Kokkos Emitter

After lowering a program to the Kokkos dialect, the last step in the end-to-end pipeline is to convert
the MLIR to C++. MLIR includes a C++ emitter for non-parallel code, and we used this as a
starting point for our Kokkos emitter. Like the built-in C++ emitter, our Kokkos emitter performs
an in-order walk of the MLIR syntax tree and emits the C++ code for one instruction at a time. The
SSA form of MLIR makes this straightforward – we simply store the result of each instruction in a
new C++ variable, and later rely on the C++ compiler’s optimization to keep variables alive for only
the duration they are needed. The one exception is that for scalar constants (arith::constant),
each reference to the SSA variable is replaced by its value as a literal. This improves performance on
GPU backends because the compiler does not propagate host constants into device code. Assigning
one Kokkos::View to another, or one LAPIS::DualView to another, does an inexpensive shallow
copy operation with reference counting, so memory safety is maintained.

 25

Kokkos needs to be explicitly initialized before using its functionality, and finalized before a program
exits. Globally scoped Views (such as the weights of a model) also need to be allocated and popu-
lated before running inference, and Views in GPU memory cannot be allocated until after Kokkos
has been initialized. The Kokkos emitter generates additional functions lapis_initialize()
and lapis_finalize() to perform these steps, and it is the user’s responsibility to call them in
their own C++ program.
The overall LAPIS pipeline is complete once the Kokkos C++ code has been written to a file.

2.3.5. User Interface

The LAPIS software provides two interfaces into the pipeline. One is a pair of command-line utilities
lapis-opt (for lowering linalg-on-tensors IR to the Kokkos dialect) and lapis-translate (for
running the Kokkos emitter). These two utilities support the same basic interface as the built-in
tools mlir-opt and mlir-translate, including the ability to read input from stdin and write
output to stdout. Given some valid input IR, the pipeline can be executed as:

cat input.mlir |\
lapis-opt --sparse-compiler-kokkos |\
lapis-translate -o output.cpp

In addition to the command-line interface, LAPIS provides a Python package with a KokkosBackend
class to drive the lowering pipeline and the compilation of the generated C++ into native code. A
ctypes-based Python wrapper is also generated to allow this native code to be called directly from
Python. This is functionally a drop-in replacement for the RefBackend in torch-mlir [93], as long
as Kokkos is installed ahead of time (the environment variable KOKKOS_ROOT is used to locate the
desired installation). This fully end-to-end mode is useful for testing LAPIS and the correctness of
the generated code in one script.
Given a Torch module m and a set of input tensors (here a, b, c), the following Python code will
perform the entire end-to-end compilation process on the module’s forward method, and then

2.4. Demonstration of AI/ML integration with CSE codes

The goal of this sub-section of work is to investigate whether LAPIS could enable Python-C++
interoperability, especially for use cases such as in multiscale simulations utilizing surrogate models
as sub-components. This allows us to focus primarily on inference. For example, a surrogate for
a high-fidelity simulation can be trained offline in several cases. An active learning loop is an
exception but we assume offline training for this demonstration. In such cases, the trained model
has to be deployed within a lower-fidelity simulation framework.
To show that LAPIS approach is actually feasible, we set out to construct a working compilation
pipeline that can automatically expose some non-trivial machine learning functionality to a C++
application. We use the ResNet18 architecture as an example to do this demonstration. ResNet-
18 [63] is a deep convolutional neural network (CNN) architecture. The ResNet family of models
use skip connections to train deep convolutional neural networks for image processing tasks. We use
the lowering of ResNet18 as an exemplar for the use case when images from scientific experiments

 27

are analyzed using traditional ML approaches within a larger code base integrating experimental
analysis with other methods. While we show the conventional ML approach as an exemplar here,
the same steps work for the production scientific machine learning use case for electronic structure
calculations in the MALA framework [38].
Creating an MLIR module from Python code (or code in any other programming language) is
the responsibility of an external front end. torch-mlir provides a full example where the pre-
trained ResNet18 image classification model is converted from PyTorch to freestanding MLIR,
progressively lowered through a pipeline of built-in MLIR transformations, and finally just-in-time
(JIT) compiled to native serial code using LLVM. Here, “freestanding” means that the MLIR code
has no external dependencies - it no longer involves Python and it includes all constant data needed
by the model such as the CNN weight matrices. Our objective was to replicate this example, but
generating parallel, Kokkos-based C++ code that is also performance portable.
For the purposes of testing the generated C++ code from the Kokkos emitter, a Kokkos backend
class was created in Python. This backend works as a drop-in replacement for the JIT RefBackend
of torch-mlir. Given an MLIR module from the PyTorch frontend and a location where Kokkos is
installed, our backend automatically goes through the steps needed to actually run the generated
code:
 • Execute the lowering pipeline described above
 • Emit Kokkos C++ to a file in a known location
 • Compile the Kokkos C++ into a shared library with the addition of a CTypes-friendly wrapper
 (tensors are in the form of raw host pointers and sizes, and function names are not mangled)
 • Generate a Python wrapper module using the CTypes API, which accepts tensors as NumPy
 arrays
 • Import the module (this loads the shared library) and call lapis_initialize().
This extended pipeline is useful for testing because the resulting wrapper module provides an
identical interface to the example PyTorch to the RefBackend (LLVM-based JIT) backend. In the
case of the ResNet18 example, using our code is as simple as:

import kokkosModule
probabilities = kokkosModule.forward(image)

where “image” is a preprocessed NumPy array representing the pixel values of the input, and
“probabilities” is the resulting vector of probabilities that the image belongs to each class. This
vector can be directly compared with the one returned by the interpreted PyTorch model, or the
LLVM JIT version of the model. Figure 2-3 outlines the overall pipeline, and also shows the full
annotated source code of the Python wrapper module for ResNet18.
For integration of a model into an scientific application, it is desirable to generate code with a
dynamic batch size so that the same code can be called with varying problem sizes. In the case of
ResNet18, the resulting function signature is:

Unlike Torch, Kokkos does not allow mixed static and dynamic dimensions in any order, so

2.6. Related Work

Domain specific compilers for sparse and dense operations is a rich field with several recent ef-
forts. The Tensor Algebra Compiler or TACO [77] is a compiler that focuses on sparse/dense
tensor operations with C++ and Python interfaces. While TACO has support for generating CUDA
code, it does not support AMD GPUs. COMET [99, 129] is an MLIR based compiler for sparse
tensor linear algebra. COMET allows for different storage for sparse matrices with support for
several front ends. COMET primarily focuses on CPU architectures. MPACT [127] is a new
compiler framework built on top of MLIR and LLVM. We support the MPACT frontend in LAPIS.
Triton [130] is an MLIR based compiler framework developed by OpenAI for ML use cases, espe-
cially highly optimized dense matrix multiplications. Our work, in mapping Kokkos hierarchical
parallelism on GPUs, could be seen as sharing the basic principles for extracting GPU performance.
However, by developing a performance portable dialect LAPIS provides more generality on what
accelerators are supported. Triton focuses on CUDA/HIP and hence on NVIDIA and AMD ac-
celerators. Data-Centric (DaCe) programming environment, uses Stateful DataFlow multiGraph
(SDFG) an intermediate representation so programss can be separated from optimizations. DIS-
TAL [143], SpDistal [144] are compilers that target distributed memory for dense and sparse tensors
respectively. LegateSparse [146] distributes sparse matrices on distributed CPUs/GPUs with SciPy
code as the frontend. These codes do not target performance portability and require significant
development effort from the compiler developers to support new accelerators.

2.7. Conclusion and Future Work

We demonstrate that a compiler framework, LAPIS, using MLIR can automate the process of
integration between CSE and AI/ML codes. Furthermore, we demonstrate that LAPIS can generate
performance, portable code from high-productivity language like python. As a result, LAPIS,
retains the performance portability advantages of frameworks like Kokkos and productivity of
PyTorch. LAPIS allows domain scientists to exchange data seamlessly between simulation codes in
C++ and machine learning models from Python. Our compiler can take a general PyTorch model

 36

and generate parallel, portable C++ source code that uses the Kokkos programming model, making
it trivial to integrate into existing Kokkos-based applications that can run on different CPUs and
GPUs.
LAPIS, with its performance portable Kokkos dialect, new lowering passes for hierarchical par-
allelism, an emitter for parallel, performance portable, C++ codes, and new performance-focused
lazy-copying memory references adds significant new capabilities to MLIR. All of these features
can impact multiple domain specific compilers that are built using MLIR.
Another result of this work is the confirmation that a compiler-based approach can be used to bridge
the language gap between ML frameworks in Python and scientific applications in C++. To the best
of our knowledge, this project is the first example of a compiler that maps high-level operations
like convolutions to a portable programming model like Kokkos. Our Kokkos emitter is general
enough to work with any MLIR program that has been transformed into the subset of dialects our
emitter expects (scf, arith, memref, etc.).
In the future, other frontends beyond PyTorch and torch-mlir can be supported. TensorFlow [11] and
JAX [33] can both be compiled to high-performance native code through the IREE compiler [126],
which is also based on MLIR. As in this work, we could compile Python programs to Kokkos
C++ source code by using the right sequence of lowering transformations and our Kokkos emitter.
Alternatively, the full capabilities of IREE could be used to produce native binaries and a separate
MLIR pass could generate interfaces for seamless integration with scientific applications.
Another area needing improvement is the efficiency of the generated code. Although linear algebra
and tensor operations can be expressed as multidimensional parallel for loops, such implementations
do not make effective use of caches or GPU scratchpad memory. Hand-optimized tensor kernels
that use explicit tiling could be a major improvement (e.g. the cuDNN library). Rather than lower
every tensor and linear algebra operation to a parallel loop, an extra transformation could be inserted
to detect the operations for which optimized kernels are available and replace them with calls to
those kernels instead.

3. PARTITION DIALECT

MLIR (Multi-Level Intermediate Representation) [85] is a popular framework for implementing
domain-specific compilers for optimizing matrix/tensor computations. However, no support cur-
rently exists in MLIR for distributed sparse tensor computations. We have developed a new MLIR
dialect for high-level specification of distributed sparse tensor computations. This specification is
then lowered to MPI-based code for distributed execution. We illustrate the expressiveness of the
new dialect using a Graph Attention Network computation with multiple sparse tensor operators.

3.1. Introduction

Sparse tensor computations are used widely in scientific computing, machine learning, and data
analytics. Compiler techniques for optimizing such computations have been studied in prior work
(e.g., [50,77,92,113,129]). The goal of our work is to enable high productivity in the development
of distributed computations on sparse tensors. The common practice in developing distributed
algorithms is to use a partitioned-address-space programming model like MPI (Message Passing
Interface), which requires tedious and explicit partitioning of matrix/tensor data structures by the
programmer into locally held slices by each process, and orchestration of data movement between
the processes.
To enable higher productivity, we develop the PartTensor dialect in the popular MLIR [85] compiler
framework to provide a more convenient global partitioned view of distributed sparse tensors and
computations on them. MLIR provides functionality for representing and manipulating sparse
tensors [27], based on code generation derived from the TACO [77] compiler. However, there are
no facilities for expressing computations on distributed sparse tensors. We develop such facilities,
together with several essential techniques for code generation. This work allows, for the first time,
the implementation of distributed sparse tensor computations in MLIR. This functionality provides
productivity and performance benefits for the active community of developers of domain-specific
compilers in the MLIR ecosystem.
MLIR dialect. The first contribution of our work is the design and implementation of an MLIR
dialect for implementing distributed algorithms for sparse tensor computations. The dialect defines
MLIR data types for distributed sparse tensors and operations to access and update such tensors.
These types and operations, together with the existing MLIR sparse_tensor dialect for non-
distributed sparse tensors [27], allow the implementation of a variety of distributed algorithms.
Code generation and run-time support. A related contribution, which supports the dialect definition,
is the design and implementation of MLIR code lowering components, together with relevant run-
time support for multi-node execution of dialect operations.

 39

Design of distributed operators on sparse tensors. The third contribution of this work is an
approach for synthesizing distributed implementations of sparse tensor operators. Each operator
is decomposed into a collection of local applications of that same operator. Here “local” refers
to execution in a single process in a distributed system, with operands that are fully available in
local memory. Each such operand correspond to a hyper-rectangular slice of some distributed
sparse tensor. Our dialect is used to construct the necessary local operands (by communicating
with other nodes), while the existing MLIR sparse_tensor dialect is used to implement the
local application of the operator. The high-level primitives of the dialect hide the complexity
of orchestrating MPI-based data movement between nodes, thus simplifying the development of
MLIR-based domain-specific compilers for distributed tensor computations.
Use cases: popular sparse tensor operators. We illustrate the expressiveness and performance
of the proposed MLIR dialect on a Graph Attention Network (GAT) computation, a popular
architecture for graph neural networks. The GAT computation uses several sparse tensor operators
that highlight the features of our dialect. Experimental evaluation demonstrates the scalability of
the generated distributed operator implementations.

3.3.1. Key Dialect Features

The developed PartTensor dialect provides MLIR types and operations that enable specification and
code generation for distributed sparse tensor operators. To specify types for partitioned tensors,
we use part_tensor.encoding constructs (e.g., #partCsr at the start of Figure 3-2) that are
wrappers around the already-existing constructs sparse_tensor.encoding discussed earlier.

3.3.1.1. Tensor Partitions

Each tensor that is involved in an operator is conceptually defined by a set {𝑀0 , . . . , 𝑀𝑚−1 } of
modes, where 𝑚 is the order of the tensor. A mode 𝑀𝑖 corresponds to a dimension in the data space

 42

of the tensor and is a set of index values 𝑀𝑖 = {0, . . . , 𝑁𝑖 − 1}, where 𝑁𝑖 is the mode extent. For a
partitioned tensor, the Cartesian product 𝑀0 × . . . × 𝑀𝑚−1 is partitioned into disjoint 𝑚-dimensional
hyper-rectangles, referred to as tensor partitions. For that tensor, each process in the distributed
execution stores one such partition.
The PartTensor dialect is agnostic of the partitioning scheme; for example, the partitions can be
non-uniform. The only assumption is that the entire data space of a partitioned tensor is covered
by disjoint hyper-rectangular partitions. This provides freedom for application developers to select
suitable partitioning based on their knowledge of sparsity patterns of domain-specific datasets. A
direction for future work is to develop automated techniques for selecting such partitioning schemes,
based on sparsity analysis and communication cost modeling.
Example. In Figure 3-1, tensor 𝑇 has three modes, with mode 𝑀0 corresponding to data dimension
𝑑0 in the #csrv specification, and 𝑀1 and 𝑀2 corresponding to 𝑑1 and 𝑑2 in #csrv, respectively.
The corresponding partitioned tensor 𝑇 in Figure 3-2 is defined by the #partCsrv specification,
which is a wrapper around #csrv. The data space of 𝑇, defined by 𝑀0 × 𝑀1 × 𝑀2 , is partitioned
into disjoint 3D hyper-rectangles. Each process can obtain the specification of its own partition
using operation part_tensor.get_my_partition. This operation produces a buffer %T_spec
(whose MLIR type is memref<?xindex>) containing the coordinates of the hyper-rectangle. For
𝑇, the buffer contains 𝑑0_low, 𝑑1_low, 𝑑2_low, 𝑑0_high, 𝑑1_high, 𝑑2_high which specify the
lower and upper bound in each data dimension.

3.3.1.2. Reading Tensor Slices

To perform the local computation at a particular process, it may be necessary to obtain arbitrary
hyper-rectangular slices of a partittioned tensor’s data space. In general, such a tensor slice may
intersect with multiple partitions of that tensor. Operation part_tensor.get_slice takes as
operands a partitioned tensor and a specification of the desired slice, and orchestrates the commu-
nication with relevant processes to obtain the necessary data elements. These data elements are
then assembled into a local sparse tensor that is indistinguishable from “normal” sparse tensors.
Example. Figure 3-2 shows four uses of this operation. For example, the last get_slice op-
eration is applied to partitioned tensor %A:tensor<?x?xf32,#partCsr>. The second operand
is the specification %A_spec of slice boundaries. The result is a standard MLIR sparse tensor
%A_slice:tensor<?x?xf32,#csr>. It is important to note that the slice specification uses
“global” coordinates (i.e., values from 𝐴’s data space 𝑀0 × 𝑀1 ), while the result of get_slice
uses zero-based “local” coordinates. Thus, the obtained data slices can be directly used in a
local operator—in this case, the exact same BSDDMM linalg.generic described earlier in
Figure 3-1.
The abstraction provided by get_slice hides the significant complexity of the underlying MPI-
based communication across nodes. A single get_slice operation in the MLIR code produces
a data structure—a “normal” sparse tensor—that can be immediately used in an existing local
operator. This functionality makes it easy to transition from an existing non-distributed computation
to a distributed version, thus increasing productivity and providing performance benefits. We note
that get_slice is a blocking collective operation, where each rank performs the operation to

 43

populate a local tensor with a copy of the hyper-rectangular slice of the partitioned tensor needed
by it. The operation is implemented in a runtime support library which uses MPI all-to-allv
collective communication. Implementation details are discussed further in Section 3.3.2.

The dialect does not expose MPI functionality at the MLIR level. In addition, the dialect does
not provide functionality for non-blocking communication or for scheduling communication earlier
than related computation. Such features for overlapping com-munication and computation present
opportunities for future work.

3.3.1.3. Modifying Tensor Slices

In addition to obtaining slices from partitioned tensors, the dialect allows writes from local tensors
into hyper-rectangular slices of a partitioned tensor. This is illustrated by part_tensor.set_slice
in the running example. This operation writes the produced local tensor %T_result into the corre-
sponding slice of the partitioned tensor—that is, each data element in the slice is assigned the value
of the corresponding element of %T_result. The implementation of this operation maps the local
zero-based coordinates in %T_result back to the global coordinates in 𝑇. Note that the written-to
slice of 𝑇 is defined by %T_spec, which itself is obtained from get_my_partition. Since each
process has a disjoin partition of 𝑇, the writes from different processes are non-conflicting.

With set_slice, it is expected that all participating processes write into non-overlapping slices
of the partitioned tensor. For any process that executes this operation, the written-to slice could
potentially span multiple partitions that reside across a set of other processes. As with get_slice,
the implementation is in the runtime support library and employs MPI all-to-allv collective commu-
nication. A related dialect operation update_slice allows a process to perform an accumulation
update into a slice of a partitioned tensor. Here the written-to slices could overlap, in which case
the updates from the multiple writers are accumulated at the host process of the corresponding
updated tensor elements. These slice modification operations provide convenient primitives that
hide all details of orchestrating MPI-based communication.

Since get_slice, set_slice, and update_slice are collective operations involving all pro-
cesses, and they are the only means of inter-rank data movement, any arbitrary sequence of these
operations is guaranteed to be race-free.

3.3.1.5. Reducing Communication Volume

In general, any get_slice operation (and similarly set_slice or update_slice) issued by
a process may require communication with other processes. To reduce the frequency and volume
of such communication, the partitioning schemes among several tensors could be designed to be
compatible. For example, suppose that 𝑇 in Figure 3-2 is 1D partitioned along dimension 𝑑0: that is,
a particular process stores a partition defined by the hyper-rectangle 𝑑0_low, 0, 0, 𝑑0_high, 𝑁, 𝐻.
Here 𝑁 and 𝐻 are the extents of the corresponding data dimensions. (Iteration indices 𝑛1 and
𝑛2 also have extents 𝑁, while iteration index ℎ has extent 𝐻.) Each process stores a disjoint
interval [𝑑0_low, 𝑑0_high) in the partitioned dimension of 𝑇. Next, suppose that 𝑄, 𝐾, and 𝐴
are partitioned in exactly the same way: 1D partitoning along their first data dimension, with
the same disjoint interval [𝑑0_low, 𝑑0_high) along that dimension. In this scenario, all data for
constructing %T_slice, %Q_slice, and %A_slice is available locally to the process. Thus, these
three local tensors, which are used in the local BSDDMM operator, can be constructed without any
communication.

3.3.1.6. Sparsity Masks for Reduced Communication

Under the partitioning described above, the construction of %K_slice does require communication,
since the necessary slice is 0, 0, 0, 𝑁, 𝐷, 𝐻; that is, the entire tensor 𝐾 needs to be communicated.
To reduce the volume of this communication, we note that not all elements of 𝐾 are used in

be communicated only if there exists some non-zero element 𝐴𝑛1,𝑛2 with a matching value of 𝑛2.

3.3.2. Dialect Implementation

Next, we provide details about the MLIR lowering of our dialect, together with the necessary
runtime support.

3.3.2.1. MLIR code lowering

At compile time, the MLIR module with PartTensor operations is lowered to an MLIR module
without any PartTensor operations or types, using a PartTensor conversion pass. Some of the
PartTensor operations are converted into function calls to the PartTensor runtime library routines.
The module is then further lowered by the existing sparse_tensor dialect lowering passes. The
sparse_tensor passes perform TACO-inspired [77] code generation for linalg operations oper-
ating on tensors with sparsity annotations, as illustrated in Figure 3-1. Further lowering passes map
the loops generated by earlier passes (expressed in the MLIR scf control-flow dialect) to operations
representing Kokkos [131] primitives for portability and performance of local execution.

3.3.2.2. PartTensor runtime library

For efficient and convenient implementations of PartTensor operations, we take an approach similar
to the support provided by the SparseTensorRuntime for the existing sparse_tensor dialect.
The current implementation of the runtime library uses MPI and utilizes MPI collective operations.
An implementation of PartTensor operations using other collective communication libraries is
also feasible. Below we provide a brief description of some of the important PartTensor runtime
operations.
NewPartTensor: This operation is given (1) a list of coordinates and their corresponding numeric
values, and (2) a hyper-rectangle specifying the boundaries of the partition that will reside at this
particular process. The operation filters out elements not in the given hyper-rectangle and then
produces a new tensor partition. The operation is assumed to be called by each MPI rank before
calls to any MLIR kernels that use PartTensor operations.
GetSlice: The GetSlice operation, given a PartTensor and a slice specification, (1) fulfills the request
if it can be satisfied using data of the local partition, or (2) requests sub-slices from other MPI ranks
which own the parts of the slice. In the second case, the obtained sub-slices are assembled into a
single local sparse tensor. This involves an all-to-all operation to communicate slice specifications

 46

of the requests, a local packing operation, and then actual communication of slices (values) using
an all-to-allv operation.

GetSliceForActiveMask: This variant of GetSlice takes an additional argument, ActiveMask. Ac-
tiveMask denotes which indices are needed along one of the dimensions of slice specification. It
hence avoids communication of elements of slice which are not needed by the consumer of the
slice. The operations involves: (1) collective all-to-all call to determine what sub-slices and how
many non-zeros (active elements) are being requested; (2) all-to-allv operation to communicate
active masks among processes; (3) packing operation to pack hyper-rectangular slices for which
the mask is true; (4) all-to-allv operation to communicate the packed slices; (5) local unpacking
operation.

3.4. Use Case: Graph Attention Networks

To illustrate the expressiveness and performance of the new dialect, we have used it to implement
the core components of the Graph Attention Network (GAT) computation. This use case applies
several tensor operators to a mix of sparse and dense tensors. We use the GAT example to highlight
features of the PartTensor dialect and to illustrate the scalability of our implementation.

3.4.1. Graph Attention Networks

Graph attention networks (GATs) [35,136] are a popular and highly successful graph neural network
(GNN) architecture that apply the concept of self attention from transformer networks [134] to graph
data. In GATs, each node attends to its neighbors using a trainable query, key, value framework
similar to that used by transformers for sequence mapping. The key distinction is that for GATs,
rather than ordered sequences of symbols the input consists of node data, and instead of masking
the attention by symbol order it is instead masked by the (usually sparse) graph topology.

A common method to implement a GAT is to adapt the multi-head attention (MHA) mechanism
proposed by [134] to graph data. The input to the computation is a graph on 𝑁 nodes such that
each node 𝑛 contains additional feature data 𝑥 𝑛 ∈ R𝐹 , or equivalently 𝑋 ∈ R𝑁×𝐹 , where 𝐹 is the

our implementation, we consider 𝐹 = 𝐹 ′. The layer is configured by two parameters: DH, the size
of the internal node representation dimension, and NH, the number of independent attention heads,
such that DH × NH = 𝐹. Trainable weight matrices WQ, WK, and WV are also provided as input
to the computation. These matrices are used to linearly project the input data 𝑋 to the query 𝑄, key
𝐾, and value 𝑉 representations.

sparsity patterns of ogbn-arxiv and ogbn-products. With ogbn-arxiv, the fraction of active column-

research is to predict the better choice for a GetSlice operation based on the non-zero sparsity
pattern of the tensor used to generate the ActiveMask.

3.6. Related Work

3.6.1. Distributed Computations in MLIR

The mpi MLIR dialect [97] aims to expose MPI primitives to other MLIR dialect. As such, it
provides a partitioned-address-space programming model, which requires explicit management of
partitioned data structures over multiple processes, and orchestration of data communication across
those processes. The PartTensor dialect aims to provide a higher-level of abstraction, by realizing
a global-address-space model for distributed sparse tensors and hiding the low-level details of MPI
communication. This approach has several advantages for developer productivity and software
evolution/correctness. Similarly, the Stencil dialect [30] provides higher level abstractions than
those provided by the mpi dialect, specifically for optimizing stencil computations.

The shard MLIR dialect [98] provides functionality for dense tensor partitioning (“sharding”) and
relevant device communication. The dialect defines collective operations (e.g., all-gather, all-to-all)
for communication among a grid of devices. Unlike this approach, the PartTensor dialect completely
hides the details of communication and provides a high-level get/set-slice abstraction. Further,
the shard dialect targets dense tensors and their uniform partitioning with equally-sized/shaped
partitions across a hyper-rectangular grid. The PartTensor dialect is designed to work with arbitrary
non-uniform partitioning for distributed sparse tensors. The Shardy MLIR-based tensor partitioning
system in OpenXLA [101] takes inspiration from GSPMD [142] and PartIR [13], both of which
are used to optimize machine learning frameworks. GSPMD is discussed in more detail in the next
subsection.

3.6.2. Distributed Sparse Tensor Computations

SpDISTAL [144] is a stand-alone compiler for generating distributed sparse tensor computations.
Our MLIR dialect also targets such tensor computations, but is designed to be a building block
of flexible MLIR-based compiler toolchains, and to be inter-operable with the rich variety of
other MLIR dialects. Given a high-level specification of sparse formats and data/computation
mapping, SpDISTAL generates a Legion-based [21] implementation. SpDISTAL relies on the

 51

TACO compiler [77] for specifying sparse formats and for local (intra-node) computation. We use
the sparse_tensor MLIR dialect (which is also based on TACO) for the same purposes.
Data partition specifications need to be provided by the SpDISTAL user as part of the compi-
lation process. These specifications allow a tensor mode to be uniformly distributed across a
dimension of a node grid; alternatively, by fusing multiple tensor modes and distributing based
on non-zero patterns, load-balanced partitioning can be achieved. Our approach is agnostic of
the data partitioning scheme and does not require data partition specifications at compile time:
our only assumption is that the multi-dimensional index space of a tensor is partitioned into dis-
joint non-uniform hyper rectangles, which allows for more general partitioning schemes than the
ones provided by SpDISTAL and is better suited for application-defined partitioning based on the
sparsity of domain-specific datasets.
Distributed computation has been introduced in machine learning frameworks and compilers such
as TensorFlow and JAX. The primitives for distributed computations in these frameworks are
inspired by GSPMD [142] (as is the shard MLIR dialect described earlier). The partitioning of
data is specified across one or more of the tensor dimensions. The processing elements are also
considered to be part of multidimensional mesh. The work distribution is specified as the mapping
of processor dimension to the tensor dimensions. To the best of our knowledge, these approaches
do not consider sparse computations. Furthermore, our approach allows specifications of partitions
that are not split uniformly across tensor dimension. This non-uniform partitioning can help
with load balancing of sparse computations when the application developers have domain-specific
knowledge of sparsity structure in their data.
Computational science and engineering frameworks such as Trilinos [96] and PETSc [18] provide
abstractions for distributed linear algebra operations. The Petra object model implemented in
the Tpetra package of Trilinos uses a Map construct for expressing ownership of sparse matrix
rows/columns and import/export operations before a local compute. These features are similar to
the sparsity masks and get/set-slice operations in our MLIR dialect.

3.7. Conclusions

The proposed MLIR dialect provides a convenient global view of distributed sparse tensors. A
distributed tensor operator can be implemented using high-level get/set-slice dialect operations,
together with local instances of that same operator. We demonstrate the features of the dialect and
the performance of the generated computations using a graph attention networks computation. This
design effort and the prototype dialect implementation provide a basis for future development of
MLIR-based DSL compilers for distributed sparse tensor computations. As the next step toward this
development, the next chapter proposes a novel approach for optimizing such computations based
on cost models for communication cost of various tensor/computation partitioning schemes.

4. OPTIMIZATIONS FOR PARTITION DIALECT OPERATOR
 GRAPHS

The PartTensor MLIR dialect described earlier provides features to express computations over
distributed sparse tensors. However, in order to define efficient distributed algorithms to be
implemented with the help of the dialect, it is essential to optimize the data communication across
a series of operators. Below we present a novel approach for analyzing and optimizing tensor
partitioning schemes and their data communication costs. The approach is illustrated using the
GAT (Graph Attention Networks) computation.

4.1. Problem Statement

Consider an entire directed acyclic graphs (DAGs) of tensor operators over distributed sparse
tensors. Naive code generation for such a DAG would select some topological sort and then
construct a partitioned tensor for each intermediate produced by a graph node. This approach
has two disadvantages: (1) excessive memory consumption due to intermediate tensors, and (2)
unnecessary communication to construct these intermediates. Our goal is to develop a systematic
approach for optimizing away such intermediates. We start with definitions that capture essential
properties of a given non-partitioned operator DAG, and then describe our algorithm to generate
an optimized partitioned scheme.

4.1.2. Problem Statement

We aim to develop an algorithm that partitions the tensor modes and the iterations space dimensions
for all operators in a given operator GAG, with the goal of reducing the volume of communication.
A key idea of our partitioning approach is to attempt to co-locate in the same process a producer
Slice(Op.𝑖), a consumer Slice(Op′ .𝑘), and the corresponding data slice Slice(𝑋. 𝑗). This enables
the work defined by the two iteration slices to be performed without communication of slices of 𝑋.
Further, such compatibility is considered across the entire DAG of operators, as described later.

To achieve this goal, we define a compatibility graph representation of relationships between
iteration dimensions and tensor modes. This compatibility graph captures the producer-consumer
relationships in the underlying operator DAG. Certain maximal connected subgraphs of this graph
correspond to the desired partitioning schemes. To illustrate this approach, we first introduce
an operator DAG from the GAT computation, and then present its compatibility graph and the
corresponding graph analysis.

  4.3.4. Reducing Local Memory Footprint

  The partitioning approach described so far allows for large tensors to be represented and manipulated
  across a collection of nodes in a distributed system. For very large tensors, it may be impossible
  to store the entire tensor in local memory on a single node. Through tensor partitioning, the
  local memory footprint can be reduced as needed. For example, the partitioning of In outlined in
  Figure 4-3 stores (𝑁 ∗ 𝐹)/𝑃 tensor elements per node, where 𝑃 is the number of nodes. Similar
  reasoning applies to the footprint of compatibly partitioned tensors 𝑄, 𝐴, 𝑇1, 𝑇2, 𝑇3, and Out.
  With a sufficiently large 𝑃, local memory footprints can be adjusted as necessary.

5. FUSION

Kernel fusion [56, 59, 62, 84, 89, 108, 137], inspired by loop fusion [51, 72], is an optimization
technique that aims to increase data locality and reduce kernel launch overhead by combining
kernel definitions. Current vendor-supplied compilers do not support kernel fusion, so kernels
must be fused prior to using a vendor-supplied compiler. Our approach implements kernel fusion
as a transformation pipeline in the Multi-Level Intermediate Representation (MLIR) [86] compiler
framework.

5.1. Kernel fusion pipeline

As an overview of the process, we first build a graph of kernel calls found in the IR of the original
program that are marked as fusion candidates by a user. Fusion sets are collections of kernel calls
to be fused and are generated by partitioning the kernel call graph based on user-provided metadata.
After fusion sets have been created, the IR is rewritten so that arguments and results make sense in
the context of the fused kernels. Then, Linalg operations are reordered using algebraic identities to
minimize computational and storage costs. Finally, we materialize and fuse loops represented by
Linalg operations.

5.1.1. Graph creation

To begin, we gather all calls found in a particular entrypoint in an MLIR module. An edge is
inserted between two kernels if there is an input dependence or a true dependence. An input
dependence means two kernels rely on the same input data. In this case, we can utilize fusion to
reduce the number of times common data is loaded from global memory. A true dependence means
that one kernel produces a result that another kernel consumes, necessitating the materialization of
the produced result. By fusing, we can eliminate materialization.

An example of source code and the corresponding graph are included in Figure 5-1. Since there is a
read-write dependence between kernel 0 and kernel 1, there is an edge connecting them. Similarly,
there is a read-write dependence between kernel 1 and kernel 4, kernel 2 and kernel 4, and kernel
3 and kernel 4 represented by an appropriate edge in the graph.

5.1.2. Generating fusion sets

Once we have generated a graph of kernel calls, the graph is partitioned based on user-provided
metadata and fusion sets are generated from partitions. During fusion set creation, we check that
kernels are legal to fuse with all other kernels in a partition. Legality is determined by both data
dependencies and the loop bounds implicitly represented by the Linalg ops. The data dependence
check is straightforward since we are operating at a high level of abstraction. The loop bounds
check is a bit more involved. First, we infer the loop nests that will be materialized by each Linalg
op in a fusion set. Next, we check that there is a non-empty subset of loops in a fusion set that
share loop bounds with the kernel under consideration. If both the data dependence check and loop
fusion check pass, the kernel is added to the fusion set. Otherwise, the kernel is left unchanged.

5.1.3. Fusing kernels

The final step in our fusion pipeline is to fuse together all kernels in a fusion set. We first move all

and results are remapped to the fused kernel call, removing duplicates arguments and unnecessary
result materializations. Once we have finished processing the fusion sets, we inline each subkernel
call into the fused kernel. Then, we perform a reordering pass to minimize computational cost and

further reduce storage requirements. Lastly, we materialize and fuse the parallel loops represented
by the linear algebra operations to finalize the fused kernel.

5.1.4. Linalg op reordering pass

After all subkernel calls have been inlined and before materializing loops, a reordering pass
is run over each fused kernel. This pass works by reinterpreting all “generic" linear algebra
operations using the Einstein summation convention. The Einstein summation convention is a way
 Í
of interpreting indices in linear algebra expressions like 𝑦𝑖 = 𝑗 𝐴𝑖 𝑗 𝑥 𝑗 . Elements whose indices
appear in the input and do not appear in the output are assumed to be summed over, while elements
whose indices which appear on both the input and output are assumed to be multiplied. Many
Python numerical packages provide a routine that implements the Einstein summation convention,
like Numpy and PyTorch.
The reordering pass works by first converting all compatible linear algebra operations to individual
einsum specifications. Then, we create a fused einsum specification, representing the action of the
entire fused kernel. Finally, we use a brute force solver to find the least costly pair-wise order to
perform the contractions.
For example, given two 𝑛 × 𝑛 matrices 𝑨, 𝑩 and an 𝑛−long vector 𝒙, consider the operation 𝑨𝑩𝒙.
Suppose this is implemented as two distinct operations 𝑪 = 𝑨𝑩 and 𝒚 = 𝑪𝒙. The corresponding
einsum specifications would be 𝐶𝑖 𝑗 = 𝐴𝑖𝑘 𝐵 𝑘 𝑗 and 𝑦𝑖 = 𝐶𝑖 𝑗 𝑥 𝑗 . The summation symbol is excluded
since we are implicitly summing over 𝑘 and 𝑗 by convention.
We first combine these einsum specifications by substitution beginning with the final result, i.e.

 𝑦𝑖 = 𝐶𝑖 𝑗 𝑥 𝑗 = ( 𝐴𝑖𝑘 𝐵 𝑘 𝑗 )𝑥 𝑗 .

In this form, it is clear that we can exploit the associativity and commutativity of addition and
multiplication to reinterpret the expression as

 𝑦𝑖 = 𝐶𝑖 𝑗 𝑥 𝑗 = 𝐴𝑖𝑘 (𝐵 𝑘 𝑗 𝑥 𝑗 ).

 65

Our pass implements this interpretation of the expression by splitting the fused einsum specification
into two distinct linear algebra operations, 𝑧 𝑘 = 𝐵 𝑘 𝑗 𝑥 𝑗 and 𝑦𝑖 = 𝐴𝑖𝑘 𝑧 𝑘 . This reduces the total
computational cost from 𝑂 (𝑛3 ) to 𝑂 (𝑛2 ). Additionally, our intermediate is now a vector instead of
a matrix, saving on storage. Once the pass finishes, the linear algebra operations are transformed
to their loop representations and the parallel loops are fused together.

5.3. Conclusion

We have presented a platform-agnostic method for fusing kernels to improve the data locality in a
program. Our approach relies on user-provided metadata to choose candidate kernels for fusion.
We have shown that our method achieves the expected results on a variety of architectures. A
weakness of the current implementation is that if a user does not provide input, then no kernels will
be fused. However, our approach is designed so that any method for determining fusion candidates
can be dropped in. Hence, a topic of future work is the construction of a cost model that leverages
computational cost as a profitability model for the entire kernel fusion pipeline and additional
transformations, such as tiling.
The reordering transformation has strict requirements. Specifically, the iteration of the reordering
pass presented in this paper is only valid for operations such that the reduction operator is addition are
addition and the parallel operator is multiplication. However, this can be generalized (+, ×) to any
(⊕, ⊗) such that ⊕ is commutative and associative and ⊗ is associative. Using this generalization,
the reordering pass will work for more than tensor contractions.

6. TENSQL

ABSTRACT
Relational Database Management Systems (RDBMS) have been the most prominent form of
database in the world for several decades. While relational databases are often applied within high-
frequency/low-volume transactional applications such as website backends, the poor performance
of relational databases on low-frequency/high-volume queries often precludes their application to
big data analysis fields like graph analytics. This work explores the construction of an RDBMS
solution that uses the GraphBLAS API to execute Structured Query Language (SQL) in an effort
to improve performance on high-volume queries. Tables are redefined to be collections of sparse
scalars, vectors, matrices, and more generally sparse tensors. The explicit values (nonzeros) in
these sparse tensors define the rows and NULL values within the tables. A prototype database
called TenSQL was constructed and evaluated against several SQL implementations including
PostgreSQL. Preliminary results comparing the performance on queries common in graph analysis
applications offer performance improvements as high as 1,400x over PostgreSQL for moderately
sized datasets when returning results in a columnar format.

6.1. Introduction

Research and development (R&D) of data science systems, especially those involving graph an-
alytics often leverage non-distributed systems. On the other hand, the data they analyze is often
retrieved from distributed data storage solutions and cached locally to improve performance. In
implementing these local caches, modern relational database management systems (RDBMS) such
as PostgreSQL and SQLite are often eschewed in favor of less feature-rich but more performant
storage options such as flat-files containing raw data dumps and Hierarchical Data Format version
5 (HDF5).
As data science tools transition towards production, moderately sized teams sometimes cobble
together custom data storage solutions from several databases in order to accelerate particular
portions of their data processing pipelines. For example, some teams leverage in-memory Redis
databases to alleviate performance bottlenecks within RDBMS solutions. However, this practice
makes it challenging to ensure atomicity and consistency among incoherent data stores.
In an effort to improve the data consistency issues plaguing federated R&D environments that rely
heavily upon cached data, we propose re-purposing the abstract sparse linear algebra concepts for
graph algorithms pioneered by the GraphBLAS community [73,94] to implement a new generation
of RDBMS solutions optimized for the high-throughput/low-frequency workloads common to data
science R&D. This work describes a proof-of-concept database called TenSQL that was constructed
and benchmarked against several competitors to estimate potential performance improvements over

 71

existing industry standard RDBMS solutions. TenSQL was built upon the pygraphblas [105] module
which internally leverages the SuiteSparse [46] reference implementation of the GraphBLAS C
API [95]. While GraphBLAS has been used to express algorithms like pagerank, tringle counting,
k-truss, and triangle centrality [45,106], we demonstrate its utility in construction of RDBMS query
engines as well.

Our primary contributions are:

 • Describing how to represent columnar RDBMS tables as collections of sparse tensors.

 • Describing a method to execute a subset of SQL using the GraphBLAS API.

 • Demonstrating that executing SQL queries using GraphBLAS operators can outperform
 industry standard databases by several orders of magnitude.

6.2. Related Work

First described in 2013, GraphBLAS describes a standardized set of linear algebra building blocks
(kernels) that are useful for constructing graph analysis algorithms [94]. These kernels are exposed
in libraries as highly optimized sparse linear algebra functions generalized to encompass alternative
abstract algebra semirings. The flexibility to define semirings offered by GraphBLAS broadens
its applicability to a much wider set of fields than traditional linear algebra packages. The first
GraphBLAS C API specification was released in 2017 [95]. Since then, much effort has gone into
building scalable and efficient GraphBLAS implementations for CPUs and GPUs [147].

Early in the development of GraphBLAS its progenitors discussed methods to use high performance
implementations to build scalable user-friendly query engines for databases containing enormous
datasets. For example, the Graphulo [60] project offers a set of sparse linear algebra operators
for the Apache Accumulo database. Additionally, Amossen [15], Kernert [75], and Qin [110]
suggested borrowing optimizations from linear algebra to accelerate specific RDBMS queries. In
contrast, TenSQL implements a new RDBMS solution from the ground up built upon sparse linear
algebra and GraphBLAS.

Traditional RDBMS implementations such as PostgreSQL rely upon a relational model traditionally
defined in terms of relation instances (tables) that are sets of tuples (rows) [115]. In contrast,
TenSQL reasons about tables as a collection of columns, each represented by a sparse tensor. This
attribute makes TenSQL a columnar relational database, similar to Amazon Redshift [14]. Whereas
Redshift was built on top of PostgreSQL, TenSQL is built from scratch using Python and C libraries
implementing the GraphBLAS API.

TileDB [102, 103] has a philosophically similar focus of storing datasets as tensors, although they
prefer the term “array". TenSQL seeks to move beyond storage and retrieval of tensors by enabling
native querying and processing of tensors using compute graphs built on linear algebra operators.

 72

6.3. Mapping SQL Tables to Sparse Tensors

We use the following notation: A tensor 𝐴 of order 𝐷 𝐴 ∈ Z≥0 is described via three components: a
shape vector 𝑆 𝐴 ∈ N𝐷 𝐴 , an index set 𝑋 𝐴 ⊂ (Z≥0 ) 𝐷 𝐴 , and a value function 𝑓 𝐴 : 𝑋 𝐴 → 𝜏. Traditional
notation would describe such a tensor as 𝐴 ∈ 𝜏 (𝑆 𝐴)1 ×...×(𝑆 𝐴) 𝐷 𝐴 .
In TenSQL, each table 𝑡 is represented by several tensors of order 𝐷 𝑡 that have the same shape
𝑆𝑡 ∈ N𝐷 𝑡 . TenSQL sets each of the entries of this shape vector to 260 by default, which is the largest
size of tensor dimensions in SuiteSparse. Additionally, because the GraphBLAS API only handles
scalars, vectors, and matrices, TenSQL requires 𝐷 𝑡 ∈ {0, 1, 2}.
Each row in every table is uniquely identified by a vector of integer primary key values of the form
𝑥 ∈ 0.. (𝑆𝑡 ) 1 − 1, ..., 0.. (𝑆𝑡 ) 𝐷 𝑡 − 1 called the index of the row it identifies. Every entry in these
index vectors corresponds to a column annotated with PRIMARY KEY. Therefore, 𝐷 𝑡 is equal to the
number of primary key columns in 𝑡.
The collection of all row indices within a table is used to build a table’s stencil 𝜒𝑡 with shape 𝑆𝑡
and value function 𝑓 𝜒𝑡 (𝑥) := true. The index of each nonzero element in 𝜒𝑡 uniquely identifies
exactly one row in the table. If a table has no primary keys then it may contain at most one row
identified by ∅.
For each column 𝑐 within a table 𝑡 that is not annotated with PRIMARY KEY, we instantiate one
tensor 𝑉𝑐 of shape 𝑆𝑡 . The TenSQL prototype permits columns that are not primary keys to be
integers, floats, or strings of various types. The type of column 𝑐 determines the type of values
stored in each explicit element (i.e. nonzero) of 𝑉𝑐 . The set of indices corresponding to nonzero
elements within 𝑉𝑐 is required to be a subset of its table’s stencil: indices (𝑉𝑐 ) ⊆ indices ( 𝜒𝑡 ).
An index in the stencil 𝑥 ∈ indices ( 𝜒𝑡 ) that is absent from the column’s tensor 𝑥 ∉ indices (𝑉𝑐 )
indicates a value of NULL in column 𝑐 of the row identified by 𝑥. Therefore, if 𝑐 is marked with
NOT NULL, then we impose the requirement that indices (𝑉𝑐 ) = indices ( 𝜒𝑡 ).
The TenSQL prototype implements string datatypes using the User Defined Type (UDT) feature of
the GraphBLAS specification. Strings are allocated in Python, and references to their corresponding
Python objects are stored as integer pointers within the table. When a string is added to a table the
reference counter for the string is increased by one. An internal hash table mapping each Python
objects’ pointer to a 64-bit integer is used to track the number of times the same Python object is
referenced within a table. Implementing strings this way enables TenSQL to provide unicode string
functionality that is consistent with Python functionality.
The TenSQL prototype implements durability via functions that can save and load entire databases
to and from HDF5 [125] files using the h5py Python module.

6.4.1. Query Intermediate Representation

TenSQL does not implement a query parser. Instead, the user’s Python script builds an abstract
syntax tree (AST) in the format of an internal query intermediate representation (QIR). The
QIR AST gets translated into internal Linar Algebra Intermediate Representation (LAIR) prior to
execution. The QIR AST for the example query is shown in Figure 6-4.

 75

 Figure 6-4. An Example Query Intermediate Representation

6.4.2.     JOIN Plan

TenSQL currently only implements INNER JOIN. It also requires that join conditions must only
rely upon equality of primary key columns and AND conjunctions thereof. This restriction simplifies
the process of developing join plans into identifying the connected components of an undirected
graph where nodes are primary key columns and edges are equality constraints. Each connected
component defines a primary key within the result table. The join plan for the exemplar query has
three connected components. These are: (A.ridx), (A.cidx, B.ridx), and (B.cidx).

6.4.3. WHERE Evaluation

The QIR to LAIR translator uses the precomputed join plan to broadcast the tables referenced by the
WHERE clause (if provided) onto a shared stencil. LAIR code is generated to evaluate the boolean
expression described by the WHERE clause, and is then used to mask the shared stencil. Details of
the broadcast operation are described in Section 6.6. The example query has no WHERE clause, so
this masking is skipped.

6.4.4. Stencil Evaluation

If a GROUP BY clause is not provided, then the masked version of the shared stencil computed by
the WHERE Evaluation phase is used as the output stencil. Otherwise, LAIR code is generated
to reduce the shared stencil along axes whose associated primary key connected components are
absent from the GROUP BY clause.

In the unoptimized LAIR of the example query (see Figure 6-5), the stencils of 𝐴 and 𝐵 are
broadcast together by an InnerBroadcast operator. The GROUP BY clause results in a Reduction via
logical OR over axis 2 of the stencil.

 76

6.4.5. SELECT Expression Evaluation

Every SELECT clause must begin with one primary key column chosen from each of the join plan’s
connected components, except those omitted by the optional GROUP BY clause. If no GROUP BY
clause is provided, the number of primary keys prefixing the SELECT statement must be equal to
the number of connected components in the join plan.
For each of the remaining columns in the SELECT statement, LAIR code is generated to execute the
requested arithmetic, boolean, and/or reduction operations using variants of the input columns that
are broadcast to the shared stencil calculated by the Stencil Evaluation phase. Section 6.6 describes
the broadcast procedure. The LAIR translation is now complete.
In the unoptimized LAIR for the example query (see Figure 6-5), the broadcasting process introduces
InnerBroadastMask operators that expand the matrices representing A.value and B.value into
tensors of order 3. These sparse tensors are then multiplied in an elementwise fashion before
summing over the final dimension using a reduction, resulting in sparse matrices. Without further
optimization, this would not be executable using GraphBLAS because of the intermediate result
tensors of order 3.

 Figure 6-5. Example LAIR (Unoptimized)

6.4.6. LAIR Optimizer

The generated LAIR AST is then optimized using two dataflow analysis passes and simple pattern
matching algorithms. The first dataflow analysis pass, forward index set analysis, tracks inter-

 77

sections and unions of individual dimensions of tensor indices. Intersections arise from LAIR
operators such as ElementwiseMultiply and unions arise from operators such as ElementwiseAdd.
The second dataflow analysis pass, reverse index set analysis, uses the results of the forward index
set analysis to trace back which indices will eventually be intersected and unioned with other
indices. Taken together, in the event that the forward index set and reverse index set computed
for InnerBroadcastMask, ElementwiseMultiply, and Mask nodes using certain monoids are equal,
then those nodes are considered redundant and excised from the LAIR AST. This frequently allows
the LAIR AST for SELECT expressions to be separated from the the LAIR AST generating output
stencils, resulting in significant simplification.

Pattern matching is used for peephole optimizations, but is more importantly used to recognize
applicability of GraphBLAS operators MxM and MxV within the LAIR AST. Special cases where
INNER JOIN operations are combined with GROUP BY clauses and aggregation functions (e.g.
SUM and COUNT) can result in InnerBroadcast operators followed by Reduction operators. In such
cases, depending upon the number of primary keys in the tables of the columns referenced by
the InnerBroadcast operator(s), this group of nodes can be replaced with a DotMxM, DotMxV, or
DotVxM operator along with PermuteIndices operators for transpositions where necessary.

Optimizing the example query results in the LAIR AST visualized in Figure 6-6. The InnerBroad-
castMask operations are eliminated because they are redundant with the ElementwiseMultiply that
follows. Doing so decouples the stencil computation AST from the expression evaluation AST.
However, the tensors must be promoted to order 3 according to the join plan, so the Elementwise-
Multiply is simultaneously replaced with an InnerBroadcast operator. Finally, the pattern of an
InnerBroadcast operator (with an appropriate broadcast pattern) followed by a Reduction operator
is recognized, so two instances (one in the stencil AST and one in the expression evaluation AST)
are replaced with DotMxM. This makes the final optimized AST executable, because all order-3
intermediate tensors are eliminated. This trick cannot be performed in every case, so queries
resulting in order-3 tensors or higher must be detected and rejected by the TenSQL prototype.

6.7. Limitations and Divergences

Although the TenSQL prototype implements a large subset of SQL, it omits some significant
features. Descriptions of several of these limitations follow.

 1. OUTER JOIN operations are not yet implemented because primary key columns are not
 allowed to contain NULL values. Creating matrices or vectors whose index sets contain NULL
 values is not well defined in traditional linear algebra. We plan to work around this issue by
 breaking column tensors into several tensors, each storing rows whose primary keys contain
 a particular combination of NULL values.
 2. ORDER BY is not yet implemented because TenSQL’s index sets are inherently unordered.
 We plan to add an optional ROWID sparse tensor to tables’ metadata to track the ordering of
 tables’ rows.
 3. Join conditions are currently required to be composed of conjunctions of equality constraints
 on primary keys.
 4. A SQL text parser, Data Description Language (DDL) queries such as UPDATE and DELETE,
 subqueries, transactions, foreign keys, unique constraints and indexing other than PRIMARY KEY
 are not yet implemented.

 81

  5. TenSQL natively returns results in a columnar format. Converting results to be row-wise
 requires an additional processing step.

  6. All TenSQL operations currently take place in memory, with no support for out-of- processing.

6.8. GraphBLAS Challenges

TenSQL also inherits some challenges from current GraphBLAS API design. Descriptions of some
of these limitations and how TenSQL handles these follow.

  1. The GraphBLAS API cannot manipulate sparse tensors of order greater than two. Therefore
 TenSQL’s tables, result sets, and intermediate results are limited to at most two primary keys
 so that 𝐷 𝑡 ∈ {0, 1, 2} for all tensors. Provided a sufficient level of expertise, this restriction
 can often be worked around when crafting SQL schemas and queries, but it makes some use
 cases difficult or even impossible to implement. Sparse tensor extensions to the GraphBLAS
 API would resolve this challenge.

  2. The GraphBLAS API has no inner broadcast operator. TenSQL works around this limitation
 through composition of other operators such as mxm and apply_bind_first. However, doing
 so requires a series of if statements with more than 20 branches to account for various tensor
 orders and transpositions, which will not scale to higher order tensors.

  3. The GraphBLAS API does not offer string datatypes for tensor elements. TenSQL works
 around this limitation by casting python objects containing strings to integer pointers and
 internally counting references to these objects for garbage collection purposes.

  4. The GraphBLAS API does not provide for certain operations on scalars (e.g. apply,
 eWiseAdd, and eWiseMult). To work around this limitation, scalars frequently need to
 be handled in dedicated code branches. Compounding the problem, the GraphBLAS API
 does not provide a mechanism to call operators directly, so TenSQL re-implements these
 existing operators in Python code. This leads to potential inconsistences in how things like
 rounding, floating-point exceptions, and integer overflow are handled depending upon the
 order of the tensor.

6.10. Future Work

Follow-on efforts are likely to include building and benchmarking tools that translate additional
query languages to LAIR. Such efforts may lead to a multi-lingual database capability that can exe-
cute relational queries via SQL or dataframes, graph queries via SPARQL Protocol and RDF Query
Language (SPARQL) or Neo4j’s Cypher Query Language (CQL), and linear algebra operations
via MATLAB syntax or similar. CQL, in particular, was recently implemented in the RedisGraph
extension to the Redis database using GraphBLAS operators [37]. Experiments with using GPUs
to accelerate queries translated to LAIR may also follow, given SuiteSparse’s support for GPUs.

6.11. Conclusion

We described the design, construction, and prototyping of Structured Query Language (SQL)
operations on top of GraphBLAS API compliant sparse linear algebra libraries. Although many
features of SQL are not implemented by the current prototype, it offers a framework for compiling
practically useful portions of SQL into sparse linear algebra building blocks. When implemented
using the SuiteSparse reference implementation of GraphBLAS and returning columnar results, the

 86

prototype executes certain queries as much as 1,400x faster than PostgreSQL on relatively modest
graph datasets. Further work in this direction may make it feasible to rapidly implement practically
useful subsets of SQL on additional hardware and software systems using GraphBLAS.

Graph pattern matching is an important topic within graph analytics because it forms the foundation
of user friendly graph query languages such as Cypher and SPARQL underpinning graph databases
like Neo4j and Amazon Neptune. A core problem within these languages is subgraph monomor-
phism, where the graph held by the database is searched for subgraphs matching a structure of
edges and vertices specified by each query, often referred to as syntactic filtering. Queries can
further refine results by requiring specific properties and labels for the edges and vertices in the
matching subgraphs, which is called semantic filtering. Open source databases implementing graph
pattern matching using GraphBLAS already exist (e.g. RedisGraph), but there is little documen-
tation available and few benchmark comparisons against non-database implementations. In this
paper we provide recipes for implementing subgraph monomorphism and subgraph isomorphism
algorithms using GraphBLAS while allowing for semantic filtering. We then provide benchmarks
comparing these GraphBLAS implementations with other popular implementations of subgraph
monomorphism and subgraph isomorphism. Our benchmarks show the potential for speedups of
up to 330x on simple graph motifs over state-of-the-art subgraph isomorphism implementations
found in igraph and NetworkX at the expense of increased memory utilization.

7.1. Introduction

Subgraph monomorphism is a fundamental problem in graph theory and computer science with
applications spanning cybersecurity, bioinformatics, logistics, social network analysis, and database
querying. The more commonly discussed subgraph isomorphism problem refers to the task of
finding subgraphs within a graph data structure that are isomorphic (contain the same edge structure)
to a query graph. Subgraph monomorphism is a closely related problem that allows the discovered
subgraphs to contain additional edges that are absent from the query graph, and is central to graph
database query languages.

In terms of use cases, there is significant ongoing effort to integrate knowledge graphs with
large language models (LLM). This effort seeks to combine the natural language capabilities
of LLM’s with the interpretability and verifiability of knowledge graph databases. Therefore
improvements to the querying capabilities of large graph databases might someday contribute
significant improvements in the practical application of those models.

Although widely applicable, both subgraph isomorphism and subgraph monomorphism are compu-
tationally very expensive. Subgraph isomorphism is a widely known example of an NP-Complete

 89

problem, while enumerating matching subgraphs is NP-Hard. The theoretical significance, practi-
cal utility, and computational complexity of these problems necessitate the development of highly
efficient algorithms and implementations to apply to large-scale datasets.

By leveraging the mathematical principles of sparse linear algebra, the GraphBLAS API enables
efficient and scalable implementations of graph algorithms, making it a compelling choice for
addressing both subgraph isomorphism and subgraph monomorphism. However, these recipes are
largely absent from the GraphBLAS discourse and we perceive a lack of published documentation
for how to solve these problems using the GraphBLAS API.

We begin by providing an overview of the subgraph isomorphism problem and its significance
in various application domains. Next, we introduce the GraphBLAS API, highlighting its key
features and advantages for graph algorithm development. We then detail our implementation
strategy, including the representation of subgraph candidates, the construction of the matching
algorithm, and the specific GraphBLAS operations employed. To demonstrate the effectiveness of
our approach, we present experimental results on a range of benchmark datasets, comparing the
performance of our implementation with existing methods.

7.2. Related Work

A generalization of subgraph monomorphism to multigraphs is the foundation of graph database
query languages [17] such as Cypher [58] and SPARQL (SPARQL Protocol and RDF Query Lan-
guage) [76]. Users describe query graphs within these languages by specifying the edge structure
necessary for syntactic filtering and the non-structural vertex and/or edge property requirements for
semantic filtering. Graph databases search for these graph patterns within previously constructed
multigraphs. They also provide a final layer of functionality similar to SQL (Structured Query
Language) to perform transformation and aggregation operations on the resulting subgraphs.

RedisGraph was a particularly noteworthy example of an open source graph database that relied
upon GraphBLAS [36]. Originally released in November 2018, RedisGraph was an extension to
the widely used in-memory database Redis that leveraged the SuiteSparse: GraphBLAS library to
execute Cypher queries. However, active development of the project was discontinued in 2023, and
the package is considered to be in a deprecated state at the time of writing [82].

Many existing implementations of subgraph monomorphism and subgraph isomorphism leverage
the VF2 algorithm described by Cordella et. al. in 2004 [44]. For example the C library igraph
and the widely utilized Python package NetworkX [100] both provide implementations of VF2.

In addition to VF2, other notable algorithms and frameworks have been developed to address
subgraph matching problems. Ullmann’s algorithm [132] is one of the earliest and best-known
methods for subgraph isomorphism, employing a backtracking approach with pruning techniques
to reduce the search space. More recent approaches, such as the LAD algorithm [123], focus
on improving the efficiency of subgraph isomorphism implementations by leveraging constraint
satisfaction techniques.

 90

In contrast to VF2, which implements subgraph matching using depth first search (DFS) directly,
our approach based on GraphBLAS leverages sparse linear algebra to process larger chunks of
work during each iteration. In effect, at each search depth the algorithm explores multiple paths
simultaneously (as opposed to the single path explored by pure DFS) and taking the opportunity
to deduplicate the search horizon prior to exploration, which eliminates a portion of otherwise
duplicative work. The main downside to this approach is increased memory utilization caused by
exploring multiple paths simultaneously.

7.3.2.      GraphBLAS

The GraphBLAS API is a specification for libraries implementing a standard set of sparse lin-
ear algebra functions. There are several advantages to leveraging GraphBLAS implementations
including:
 1. High performance - As with the Basic Linear Algebra Subprograms (BLAS), GraphBLAS
 implementations provide a limited set of highly optimized (and often parallelized) primitives
 for linear algebra.
 2. Portability - Although few GraphBLAS implementations exist today, it promises the ability
 to translate well from one hardware platform to another. If a GraphBLAS implementation
 exists for a given hardware platform, then it should be possible to execute analytics that
 exclusively leverage GraphBLAS functions on that platform.
 3. Language Compatibility - GraphBLAS bindings are available for a number of different
 programming languages. When used in concert with other libraries written in low level
 languages, GraphBLAS makes it possible to scale graph analytics to large datasets despite
 being orchestrated by a slower high productivity language like Python.
 4. Brevity - As we will demonstrate below, implementations of graph analytics using Graph-
 BLAS are often much shorter and have simpler control flows than low-level implementations.
Our implementation uses the following functions from the GraphBLAS API. For brevity we some-
times drop the distinction between matrices and vectors in function names and do not adhere strictly
to the function parameters defined in the GraphBLAS specification. Instead our psuedocode uses
notational signifiers to differentiate between matrix (e.g. M), vector (e.g. 𝑣®), and scalar (e.g.
𝑠) arguments to clarify which specific function within the GraphBLAS C specification and/or
SuiteSparse extensions were utilized.

 1. GrB_apply(op, A, s) - Applies the binary operator op to every element of the matrix or vector
 A, with a scalar s bound as the second argument. This maps to the GrB_*_apply_BinaryOp2nd_*
 functions in Suitesparse: GraphBLAS.
 2. GrB_eWiseMult(op, A, B) - Performs pointwise multiplication using op on the elements

and subgraph monomorphism can be exponentially large with respect to the number of edges in
the query graph, the runtime and memory requirements of these algorithms can quickly become
impracticably large. Users often ameliorate this concern by carefully crafting highly specific

 99

semantic requirements, but implementations must still find a balance between memory usage
and runtime for an optimal user experience. Further, because the distinction between subgraph
isomorphism and subgraph monomorphism was previously nebulous, some implementations only
implement one algorithm or the other.

With this in mind, we compared the benchmarked implementations on the percentage of query
motifs to return results (A) without resulting in Out-Of-Memory errors on our systems with 256GB
of RAM and (B) finishing within 4 days of runtime. These percentages on different problem
variants are presented below.

 Figure 7-1. Percent of Successful 4-Vertex Motifs

All implementations succeeded at processing 100% of 3-vertex motifs for their allowable problem
variants on both the Twitter and Enron datasets. However, all implementations experienced failures
for 4-vertex motifs. In particular, all algorithms struggled to complete “NoLabel” problem variants
without semantic filtering using vertex color partitions. The chart includes data from both the
Enron and Twitter datasets.

NetworkX had the strongest showing in this respect, with implementations of all problem variants
based on the memory-efficient VF-2 algorithm. With semantic filtering, its only failures stemmed
from exceeding the 4-day runtime limitation. The GBSubMono implementation successfully
processed all graph motifs with semantic filtering, but run out of memory significantly more
often without semantic filtering. All of the GBSubMono implementation failures stemmed from
exceeding memory usage limitations, rather than exceeding runtime limitations.

7.4.7. Relative Speedups

To compare the runtime performance of the implementations special measures had to be taken to
succinctly summarize the high dimensional results with missing data points. We calculated the
relative speedup of the GBSubMono algorithm compared to each competing implementation using
the following calculation. We calculated the relative speedup by taking the competing algorithm’s
runtime and dividing it by the GBSubMono runtime for each problem variant and each query graph
motif. We then averaged those per-query speedups for all queries for which both algorithms met
the success criteria described above, and present those results below for each problem variant.

We start by comparing the runtimes using 3-vertex query motifs. The number of isomorphism-
distinct motifs for an undirected graph with 3 vertices is 2 if the edges are undirected and 6 if the
edges are directed. These motifs were enumerated by brute force using the is_isomorphic provided
by NetworkX.

 Figure 7-2. Average Speedup for Enron Dataset (3-vertex motifs)

Figure 7-2 compares runtimes on 3-vertex motifs using the Enron dataset. Despite being named
after isomorphism, the igraph library only provides functions for monomorphism as defined in this
paper. For the sake of time, the Neo4j benchmarks were only run on the 3 vertex problem variants,
while semantic filtering and isomorhpism were likewise not implemented in time for publication.
igraph-LAD failed to finish any query motifs on the “NoLabel” problem variants without semantic
filtering. For the problems that did finish, GBSubMono was able to outperform igraph-VF2 by as
much as 5.7x, NetworkX by as much as 330x, and Neo4j by as much as 40x on the Enron dataset.

 Figure 7-3. Average Speedup for Twitter Dataset (3-vertex motifs)

Figure 7-3 compares runtimes on 3-vertex motifs using the Twitter dataset. GBSubMono performed
similarly well on the Twitter dataset, taking a slightly larger lead over igraph-VF2 of 8.4x, while its
lead over NetworkX dropped to 319x.

Next we compare the runtimes for the Enron and Twitter datasets using only the 4-vertex query
motifs. The number of isomorphism-distinct motifs for an undirected graph with 4 vertices is 13 if
the edges are undirected and 199 if the edges are directed.

 Figure 7-4. Average Speedup for Enron Dataset (4-vertex motifs)

Figure 7-4 compares runtimes on 4-vertex motifs using the Enron dataset. GBSubMono lost some
of its runtime advantage on the 4-vertex motifs with its average speedups on the most favorable

7.4.8. GraphBLAS Challenges

The current GraphBLAS API lacks the ability to enumerate the entries of vectors and matrices,
as implemented in the EnumerateRowIndices and EnumerateVectorIndices. It also lacks the
ability to quickly concatenate matrices, as performed by ConcatenateRows above. Although we
were able to work around these issues using the GrB_import() and GrB_export() functions, this
restriction forces the GraphBLAS implementation’s memory management system to lose control
of large-scale graph data. This could have a disastrous impact on performance and/or program
stability if the underlying GraphBLAS implementation leverages remote (e.g. GPU VRAM) or
distributed memory. Further, it forces a break in the lazy evaluation mechanisms that may otherwise
optimize execution of internal linear algebra expressions.

7.5. Conclusion

In this paper, we have presented detailed implementations of subgraph isomorphism and subgraph
monomorphism using the GraphBLAS API.
To evaluate the performance of our implementation, we conducted extensive benchmarks for sub-
graph monomorphism and subgraph isomorphism, comparing our GraphBLAS-based solution with
the widely used implementations. The results demonstrate that our GraphBLAS implementation
improves upon state-of-the-art implementations in NetworkX and igraph, achieving a speedup of
up to 8x compared to igraph’s VF2 implementation and 385x compared to NetworkX in some
favorable problem variants. The substantial performance gains highlight the power of using high
performance GraphBLAS implementations to handle large-scale graph computations.
However, this performance improvement comes at the cost of increased memory usage. Our
benchmarks indicate that the GraphBLAS implementation requires significantly more memory
than pure VF2 implementations. This trade-off between speed and memory usage is an important
consideration for practitioners and researchers, and is particularly note-worthy in the context of the
frequently memory-bound problems of subgraph isomorphism and subgraph monomorphism. This
implies that GBSubMono is best suited to problems that apply heavy semantic filtering, and also
implies that GBSubMono would significantly benefit from a distributed memory implementation of
the GraphBLAS API. Reduced memory usage can also be achieved at the cost of increased runtime
by tuning the chunk_size setting.
Despite the higher memory requirements, the dramatic speedup achieved by the GraphBLAS
implementation makes it a compelling choice for applications where speed is paramount. The
ability to quickly search for patterns in large graphs can enable new possibilities in fields such as
social network analysis and cybersecurity, where timely analysis of complex graph structures is
crucial.
Future work minimizing memory utilization of the subgraph isomorphism and subgraph monomor-
phism implementations. A distributed memory implementation of GraphBLAS might also dramat-
ically expand the capabilities of the GBSubMono algorithm. Further, implementing a graph query
engine would enable better semantic filtering of subgraph matches, facilitate direct comparison to

 103

state of the art graph databases like Neo4j, and significantly improve the algorithm’s real-world
utility.
In summary, this paper has further demonstrated the potential of the GraphBLAS API to address the
challenges of subgraph isomorphism and subgraph monomorphism. Our findings underscore the
advantages and challenges of using sparse linear algebra techniques for complex graph analytics and
make significant contributions to discourse surrounding the GraphBLAS API by providing step-
by-step instructions on how GraphBLAS can be used to implement complex graph analytics.

8. CONCLUSION

In conclusion, the LAPIS compiler framework represents a significant advancement in optimizing
sparse linear algebra operations through the integration of the Kokkos and Partition dialects within
the MLIR infrastructure. By enabling performance portability, distributed memory execution
and facilitating the seamless integration of scientific machine learning models, LAPIS addresses
critical challenges in the Computational Science and Engineering community. The successful
demonstration of LAPIS across various applications, including sparse linear algebra, TenSQL
and graph attention networks, highlights its effectiveness in achieving performance portability for
variety of applications that is difficult to attain with traditional programming languages. As we
continue to refine and expand the capabilities of LAPIS, we anticipate further contributions to the
efficiency and performance of computational applications in diverse domains.
