 Using graph databases for machine learning data-driven conflict forecasting models

 Abstract

 This project is a subsection of a larger project that involves using an AI machine learning model to

predict instability and conflicts. The goal of this project is to use a graph database to store and organize

information that the data team has collected about various datasets to improve data accessibility and thus

machine learning model performance. Currently, the data team is storing their information about datasets they

are using or planning to use in an Excel spreadsheet. By using a python parsing script and a free software, a

graph database based on the information stored in the excel spreadsheet was created. The main benefit of the

graph database is that users can write queries to retrieve specific information that can be used for addressing

data coverage issues. The graph database proved successful in retrieving key information, showing potential for

increased data accessibility and organization. Ultimately, the insights from the graph database could be used to

improve the performance of the machine learning model, which is necessary for the project’s success.

 1

 I. INTRODUCTION

 Machine learning models have become a staple tool for making predictions. These

predictions are heavily data reliant and require adequate coverage to make accurate predictions.

For a conflict prediction model, it is important to have datasets representing various conflict

prediction factors and proper spatial and temporal coverage. More than that, the information

about these datasets needs to be easily accessible so that the team can make informed decisions

about how the model can be improved based on the data it is using. Currently, an Excel

spreadsheet is storing the information about the datasets that are being used or are planning to be

used by the model. As the size and complexity of the project increases, tabular structures such as

an Excel spreadsheet become difficult to use for navigation and locating key information. This

paper proposes a supplemental graph database that allows users to quickly and easily retrieve

necessary information about their datasets through queries.

 2

 II. BACKGROUND

 Excel spreadsheets are a common way to collect, organize, and exchange structured

information. They use an intuitive row-and-column format that can be processed by a wide range

of software and tools. Each row represents an individual record, while each column describes an

attribute associated with that record. However, a tabular format such as this can become difficult

to navigate throughout a project’s lifetime due to an increase in data and complexity. Converting

the source data into a graph-based representation provides support for more flexible forms of

retrieval. A graph-based data model organizes information as entities and the relationships

connecting them. Through this format, queries can be written to pull specific information from

the database using those connections.

 Ontologies are the powering factor behind creating the connections and classifications in

a graph database. An ontology is a structured representation of the concepts, properties, and

relationships that exist within a particular subject area. Ontologies can define things such as

classes representing types of entities, datatype properties representing attributes, and object

properties representing relationships between entities.¹ These consistent definitions provided by

the ontologies create a machine-readable semantic structure for the data.

 The Resource Description Framework (RDF) is a standard model for representing

information as a graph. RDF describes information through subject-predicate-object statements

known as triples. The Subject identifies a resource, the predicate defines an attribute or

relationship, and the object identifies another resource or a literal value.² The ontologies used in

this project provided the semantic model for the conversion process from spreadsheet data to

RDF. More specifically, these ontologies defined how the concepts represented in the CSV file

would appear in RDF and established the relationships that could exist among those concepts.

 3

 The ontologies and vocabularies used by the Python parsing script were specifically

chosen to capture datasets, provenance, metadata, people, and more. To accomplish this, the

script used the following ontologies and vocabularies, the Data Catalog Vocabulary (DCAT),³

Dublin Core Metadata Terms (DCTERMS),⁴ the simple Knowledge Organization System

(SKOS),⁵ the PROV ontology (PROV-O),⁶ the Friend of a Friend vocabulary (FOAF),⁷ and a

custom project ontology to address any concepts and properties not addressed by the existing

listed vocabularies.

 To retrieve data from a graph database, the query language SPARQL was used. SPARQL

can retrieve and manipulate RDF data using written queries that describe patterns that match data

within the graph. For example, SPARQL queries could retrieve all records connected to a

selected dataset category, identify people who worked with or entered certain datasets, or locate

records that satisfy certain conditions. This is a novelty for data accessibility because unlike a

standard spreadsheet search, a SPARQL query can follow relationships from different resource

types rather than searching only for values constrained in individual cells.

 III. METHEDOLOGY

 First, the Excel spreadsheet was converted into a CSV as an input file for the Python

parsing script. Then, the script executed using the CSV file and the fields from the spreadsheet

were mapped to classes and properties defined by the selected ontologies and vocabularies,

creating an RDF output file with the appropriate triples. Next, the RDF file was loaded into a

free software called GraphDB which was used to create the graph database, allowing for

SPARQL queries to be used to search for information.⁸ Finally, various SPARQL queries were

written and executed on the database, returning outputs containing information about the datasets

stored in the Excel spreadsheet.

 4

 IV. RESULTS

 The Python parsing script executed successfully and converted the dataset metadata

contained in the CSV file into valid RDF. Each spreadsheet record was presented as a dataset

resource and was connected to its associated metadata through RDF properties. The RDF file

imported successfully into GraphDB, creating the graph database with all the dataset resources

connected to associated categories, data hunters, metadata contributors, spatial/temporal

information, and other descriptive properties. The database was queryable using SPARQL, and a

list of query results are included along with their explanations.

 A SPARQL query was written to determine the number of datasets associated with each

data category. The query connected each dataset to a category through the dcat:theme property

and retrieved the human-readable category name through the skos:prefLabel property. The

datasets were then grouped by category, and the number of datasets in each group was

calculated. The query returned the number of RDF dataset resources associated with each data

category. The complete query is provided in Appendix A, and the output of the query is presented

in Table 1. As shown in Table I, the complete query output contained 11 data categories and 209

datasets counted, with Human Demographics being the largest category at 70 datasets.

 Another SPARQL query was developed to retrieve metadata for datasets classified under

the Human Population data category. The query selected resources typed as dcat:Dataset and

identified their categories through the dcat:theme property. A case-insensitive filter was applied

to the category label so that only datasets associated with the Human Population category were

returned. Along with the dataset title and URI, the query also retrieved the purchase requirement,

data format, spatial domain, spatial resolution, and temporal resolution when available. The

OPTIONAL query patterns allowed a dataset to remain in the results even if they were missing

 5

one or more of the metadata fields. The complete query is provided in Appendix B, and the

output is presented in Table II. Table II shows additional information about the Human

Population datasets, such as the title, dataset URL, purchase status, data format, spatial domain,

spatial resolution, and temporal resolution. The query results show that all the datasets in the

Human Population category do not need to be purchased and have a global spatial domain, along

with other important details.

 V. DISCUSSION

 The results from the SPARQL queries show that large amounts of key information can be

retrieved flexibly using querying. The efficiencies offered by the graph database could be used to

support dataset coverage discoveries that are useful for model performance analyzation and

improvements. Using the graph database effectively could help guide the data hunters to locate

other datasets based on existing dataset coverage. That said, one limitation of the graph database

is that users must understand SPARQL and the structure of the RDF model to construct effective

queries. However, generative artificial intelligence tools may help reduce this barrier by

translating natural-language questions into draft SPARQL queries. Using a combination of

generative artificial intelligence tools and human input can help to ensure that any AI developed

queries are valid and useful. Future work for this project aims to directly compare search

efficiency and speed for both a spreadsheet search and SPARQL queries. Also, more future work

includes creating a graph database for the data inside of these datasets rather than just the

metadata of each dataset.

 6

 VI. CONCLUSION

 The project demonstrated that an ontology-based RDF graph database could successfully

retrieve and organize key dataset metadata through SPARQL queries. These findings suggest that

the graph-based approach could support improved data accessibility, organization, and

relationship-based discovery, which may help identify coverage gaps, guide dataset selection,

and ultimately contribute to improved machine learning model performance.

APPENDIX A: SPARQL QUERY FOR THE NUMBER OF DATASETS PER DATA

CATEGORY

The following query retrieved a count for the number of datasets in each data category, from

highest to lowest.

PREFIX dcat: <http://www.w3.org/ns/dcat#>
PREFIX skos: <http://www.w3.org/2004/02/skos/core#>

SELECT ?categoryLabel (COUNT(?dataset) AS ?count)
WHERE {
 ?dataset dcat:theme ?category .
 ?category skos:prefLabel ?categoryLabel .
}
GROUP BY ?categoryLabel
ORDER BY DESC(?count)
