 ABSTRACT
The Argonne Reactor Code (ARC) software system supports users in their fast reactor design goals
by providing neutronic, thermal-hydraulic, and structural analysis capabilities. DIF3D plays a
pivotal role in the ARC system as the primary homogenized assembly neutronic calculation
methodology for fast reactor problems. Over its 40 years history, ARC software usage with DIF3D
has been applied to numerous fast and thermal spectrum reactor analysis projects with good to
excellent comparison against experiments.
With continued improvement of computation resources, many of the geometry modeling
capabilities in DIF3D that were primarily used in low order schemes are not really needed anymore.
Today, the diffusion and transport capabilities of DIF3D-VARIANT are primarily used in the
reactor design process with some scattered usage of DIF3D-FD and DIF3D-Nodal. In recent work,
the DIF3D software verification was completed for DIF3D-FD and DIF3D-VARIANT on the
geometry options used in the Versatile Test Reactor project. While we can be confident that these
capabilities of DIF3D are well used and thus trusted, it does not demonstrate that all possible input
options of DIF3D are actually working, but just those that were tested as part of VTR are and that
they are correct.
Thus, the purpose of the present work is to identify a set of test problems for DIF3D and assess the
code coverage of DIF3D for those test problems. The goal is to document what parts of the existing
DIF3D code are touched by the set of test problems and which are not. Because the verification
work done on DIF3D-VARIANT and DIF3D-FD was focused on the most common uses of DIF3D
for fast reactor analysis, the code coverage assessment of those capabilities is the highest priority.
This will ensure that nothing is being missed by the existing verification test problems that DIF3D
relies upon. The DIF3D-Nodal capability will also be inspected for code coverage as part of this
work to further ensure that regular regression testing of DIF3D will trap any likely errors the end
user might experience with the DIF3D software.
The code coverage analysis of DIF3D was performed with the Code Coverage Tool of the Intel
Fortran compiler which requires modifications to the compilation of DIF3D. The detailed coverage
tables are given for each submodule of DIF3D separately, and for the submodules which are
primarily developed for DIF3D, most of the source files could be at least partially touched. Most
of the uncovered parts/files could be easily ignored, because they are either for error message and
debugging output or obviously not needed by DIF3D. Out of the entire source codes of DIF3D,
only a few uncovered modules deserve further investigation.

1. Introduction
The Argonne Reactor Code (ARC) software package consists of 13 primary and many secondary
pieces of software that are connected through interface files. The ARC software suite supports users
in their fast reactor design goals by providing neutronic, thermal-hydraulic, and structural analysis
capabilities. Over the past decades, the ARC software suite has been applied to numerous fast and
thermal spectrum reactor analysis projects. For those cases with experimental measurements, ARC
performed exceptionally well, yielding results of consistent accuracy to those produced by the
Monte Carlo method at a fraction of the cost. At present, the ARC software suite is primarily used
for the analysis of advanced reactors. The typical design process workflow for the fuel cycle
analysis is shown in Figure 1.1, with the cited codes named in orange boxes, and as can be seen,
DIF3D [1]-[6] is central to the entire ARC system.

 Figure 1.1 ARC Software Connections for Fast Spectrum Fuel Cycle Analysis

The ARC Software Quality Assurance (SQA) Program [9] is aimed to provide the controls and
processes necessary to enable software improvement while meeting user and program sponsor
requirements. The Software QA Plan (SQAP) delineates the SQA Program framework for the ARC
software by describing the Program activities, organization, and documentation, and by clearly
defining the interconnection of all program items. The analysis presented in this report is part of
the SQAP for each piece of the ARC software.

Much of the ARC software, including DIF3D, has its origins in the1960s with many components
added or upgraded over the following 60 years of continuous development. With continued
improvement of computational resources, many of the geometry modeling capabilities in DIF3D
that were primarily used in low order methodologies suited for the computational capabilities at the
time are not really needed anymore. Today, the diffusion and transport capabilities of DIF3D-
VARIANT are primarily used in the reactor design process with some scattered usage of DIF3D-
FD and DIF3D-Nodal. Some of these not often used capabilities might still be useful to users even
if they are rarely used in the modern reactor design work and thus this code coverage assessment
will consider the DIF3D code as a whole.
The purpose of the present work is to identify a set of test problems for DIF3D and document the
code coverage of DIF3D for those test problems. Because DIF3D is distributed with a regression
test suite and many are included as part of the verification work [8], the set of test problems for the
code coverage assessment will be chosen from that test suite. Because the DIF3D verification work
done as part of the VTR program [8] added many test cases to the test suite of DIF3D, running all
of the test suites is not necessary as many of the tests will effectively be duplicative testing of the
underlying source code.
In the following sections, the parts of the existing DIF3D coding which are or are not touched by
the set of test problems are documented. The code coverage analysis was performed using the Code
Coverage Tool of the Intel Fortran compiler (gprof and codecov). To use this capability, the
compilation of DIF3D must be modified to create a special DIF3D executable which is different
from the production executable. The existing regression test suite will be used to verify that the
new executable is correct, in addition to serving as the code coverage assessment test cases. A
detailed code coverage report is generated by the Intel Code Coverage Tool, which shows the
coverage of subroutines/functions, blocks within each subroutine/function, and the frequency of
execution of each subroutine/function. With this code coverage report, it is easy to figure out which
subroutines/functions are fully covered, fully uncovered or partially covered in DIF3D. A review
of the DIF3D source files that are not fully covered was performed and some indication is reported
here for the lack of coverage and its importance for the DIF3D code usage.
It is important to note that previous code coverage work only dealt with a serial version of DIF3D
and an older compiler. With the switch to a newer compiler and focus on threading, the Intel tool
behavior has changed. The primary change occurs when the source code files in DIF3D contain
multiple subroutines. With the previous version, all subroutines that were called would be listed
individually. That same behavior only conditionally happens in the current version. For those cases
where the subroutines within a file are only called by one subroutine in that file, the subroutines
will not be listed individually. Because the first subroutine is typically the one consistent with the
file name, the number of calls will only be reported for that one subroutine, even if the number of
calls to the other subroutines within the file can be substantially more. When it occurs, the number
of calls provided here is set to the number of the primary subroutine calls and highlighted for
distinction.

2. DIF3D Overview
The DIF3D code (DIFfusion 3D) has been a workhorse of fast reactor analysis work at Argonne
National Laboratory for over 50 years [3][6]). DIF3D was primarily built as a three-dimensional
solver of the multi-group diffusion equation for semi-structured grid geometries [3][1]. The
diffusion equation, with proper cross section data, has proven to be a reliable means to predict the
fuel cycle behavior of thermal and fast spectrum nuclear reactors. The DIF3D code was built in the
late 1970s using a finite difference spatial differencing methodology applied to the diffusion
equation which we refer to today as DIF3D-FD. Later, in the early 1980s, a transverse integrated
nodal methodology, referred to as DIF3D-Nodal [4][2], was built into DIF3D to improve the
performance on large scale reactor problems. Finally, to support a research design goal of
developing fast spectrum reactors that promote non-proliferation by eliminating blanket assemblies,
the DIF3D-VARIANT solver [5][6] was added to DIF3D in the mid-1990s that extends the concept
of DIF3D-Nodal to a functional three-dimensional transport code based upon spherical harmonic
expansions in angle.
Over its more than 40 years history, DIF3D has been applied to numerous fast and thermal spectrum
reactor analysis projects. For those cases with experimental measurements, DIF3D performed
exceptionally well, yielding results of consistent accuracy to those produced by the Monte Carlo
method at a fraction of the cost. With all of these successes, it is important to point out that DIF3D
does have limitations for general purpose usage for geometrically non-regular systems.
The current capability of DIF3D can treat slab and cylindrical one-dimensional (1D) domains,
Cartesian, hexagonal, and R-Z 2D domains, and Cartesian, hexagonal-Z, triangular-Z, and R-Z-θ
three-dimensional (3D) domains. The DIF3D-FD diffusion solver can be applied to every geometry
type in DIF3D except for hexagonal and hexagonal-Z geometries, where a triangular-Z mesh
geometry is instead used to represent hexagonal reactor designs. The DIF3D-Nodal diffusion and
DIF3D-VARIANT solvers only support 2D and 3D dimensional Cartesian and hexagonal
geometries.
Although DIF3D has various capabilities for geometry and solver options, many of them are out of
date and rarely used in the current world. For example, the finite difference-based diffusion solver,
which is using low order methodology, is almost extinct in the current reactor analysis. The
triangular-Z geometry concedes to hexagonal-Z geometry, due to the latter’s convenience in
representing the real reactor system, and the recent code development has been prioritized for the
hexagonal-Z geometry. This fact would be discussed in the following sections.

3. DIF3D Coverage Assessment
Because of the limited computational capabilities, the DIF3D code was developed to be a series of
executables that are called in sequence which is termed the modular system. The executables passed
information via interface files and had specific roles as part of the DIF3D execution (e.g., input
processing, flux solution, and output processing). Today the structure of the DIF3D modular form
is maintained but it is not used, as the driver routines of each non-driver module were converted to
subroutines of the driver module. While the approach still uses interface files to transfer information
between modules of DIF3D, the maintenance and use of the DIF3D software is much easier. All of
the modules used in DIF3D are listed in Table 3.1 where the arcmodules folder was a major addition
from DIF3D 9.0 to DIF3D 10.0 as part of the development of the software.

When DIF3D is compiled, in many cases, all the source files in each module (directory) are
compiled and linked as part of the executable to avoid complicated compiling procedures. However,
it should be noted that not all of the files in each directory are actually used by DIF3D. In particular,
some subroutines were developed for other ARC codes and are not usable in DIF3D. Or, as is the
case with LINPACK and LAPACK, they are generic linear algebra packages which DIF3D only
uses a few subroutines from even though the interface of the modules have input switches to allow
access to most of the included subroutines (branches of the module). This code coverage analysis
is thus also an important reference if a streamlined code compilation is desired.
DIF3D is distributed with 56 fast running test cases and 48 longer running tests that were created
as part of the verification work [7]. The 56 fast running test cases were built by the developers of
DIF3D and designed to rapidly ensure consistent results from the DIF3D software as it was being
developed. Most of them have been in use since at least the 1990s and thus they are chosen as the
base set of test cases for the code coverage assessment. The remaining 48 test cases were added as
part of the software verification of DIF3D and typically do not run quickly.

3.1 Primary subroutines and driver of the DIF3D code
The primary subroutines of the DIF3D code are stored in the directory source in addition to the
driver routine. The code coverage of all of the files is shown in Table 3.1.1, Table 3.1.2 and Table
3.1.3. For the uncovered or partially-covered subroutines, a description of the uncovered parts is
also given in the table. For the covered source files, the number of calls by the test package (50
benchmark problems) are also listed, showing the usage frequency of each source file.
Starting with the code coverage of the driver and module subroutines in Table 3.1.1, one can see
that all of them are either fully covered or only missing coverage of debugging outputs that are not
important for regular DIF3D usage. As was discovered in the VTR software verification, some of
these debugging edits and regular output edits are not actually working properly as no one actually
uses them. In that regard, it is possible that the uncovered debugging edits are not working properly
in these uncovered sections but since they are not used by the present developers they can be
ignored.
For the partially-covered subroutines listed in Table 3.1.2, one can see that most of the uncovered
parts are because of error messages or debugging outputs which are not normally reached in a
working verification problem and thus we conclude they can be ignored. In other cases, some
tailored output edits from the subroutine or modules are not covered which we choose to ignore as
they are unlikely to be used. In other cases, some special aspects of the iterative algorithm are not
tested as the test cases do not have the properties to trigger the acceleration features or failures. We
choose to ignore these as the 41 test cases chosen are typical fast reactor problems and not math
problems. Not all of the different space-angle approximations or geometry options are covered in
DIF3D-Nodal. The adjoint module in DIF3D-Nodal is also not covered nor is there a case where
upscattering is tested (it is fully tested in DIF3D-VARIANT). Because the core of the nodal solution
algorithm is being rigorously tested, we choose to ignore these code coverage aspects at this time.
Other code coverage issues that we choose to ignore are those that require either a very memory
limited environment (which does not exist today) or an extremely large memory burden that
requires storing data to binary files (not practical for regression testing).
The more serious partially covered subroutines include the lack of coverage on Slab, Cylinder, R-
Z, Theta-R, and R-Z-Theta geometries. These are considered part of the low order methodologies
for modeling a reactor and we choose to ignore the lack of coverage on them. It was determined as
part of this work that the 30 degree symmetry hexagonal-z geometry option of DIF3D-VARIANT
is unreachable via input and thus the lack of code coverage can be ignored. While the 45 degree
symmetry option in Cartesian geometry of DIF3D-VARIANT is also not presently covered, it is
known to be working and is ignored for this assessment as it is not used in regular reactor analysis
as most designs focus on full core models given today’s computational resources. The same logic
applies to the 180 degree periodic symmetry case which we also choose to ignore. Some other
uncovered sections are associated with discontinuity factors which are not presently used for
advanced reactor analysis, and we choose to ignore those at this time. Finally, there are several

features that are only used when DIF3D is used as a subroutine or part of another part of ARC, such
as REBUS, PERSENT, GAMSOR, VARI3D, or DIF3D-K and thus are either not reachable or
usable by DIF3D alone.
The fully uncovered subroutines are listed in Table 3.1.3, and after a detailed inspection, we can
conclude that most of them do not need further testing. In fact, some subroutines can be removed
as they have either been deprecated or were never part of the code. The only uncovered subroutine
that might warrant additional testing is the alpha-eigenvalue capability, but this does not presently
appear to be reachable with the existing DIF3D input (likely a DIF2D carryover which was not
connected due to lack of use).

3.2 Source code in the directory arcmodules/source
The Fortran coding in the directory arcmodules/source primarily provide self-contained memory
allocation and reading/writing of the binary interface files created in the ARC suite of codes.
Because the approach taken to create them is somewhat consistent with modern object coding, each
file can contain both the data structure and many subroutines/functions that operate on that data
structure. The various modules and subroutines in the directory were developed to support many
parts of the ARC software suite and thus not all subroutines of a given module are used in DIF3D.
Not all of the files in the directory are presently compiled as part of DIF3D and the code coverage
summary of those which are is given in Table 3.2.1 and Table 3.2.2.
From Table 3.2.1, one can identify that the Ne_Kind, LMA, and NonZeroStorage modules (data
structure based sub-programs) are being used by DIF3D. A survey of the subroutines in those
modules indicate that many subroutines are not actually used in DIF3D. These can be ignored as
they are unreachable parts of the module. For most of those subroutines which are partly covered,
the only parts that are not covered are debugging and error output messages which can be ignored.
The primary exceptions are LMA subroutines which perform memory to disk operations. As the
notes in the table indicate, to access the uncovered parts of these subroutines requires enormous
DIF3D inputs which take a very long time to complete. These are not practical for a code coverage
assessment and these parts of the LMA module should be tested external to DIF3D.

3.3 Source code under the directory variantbasis/source
The directory variantbasis/source stores source files that construct the spatial and angular basis
functions and matrices for the DIF3D-VARIANT solver. The original DIF3D-VARIANT used
hard-wired spatial and angular matrices and the updates from DIF3D 9.0 to 10.0 introduced these
routines to allow higher order space-angle approximations to be investigated. They were moved
external to the src_DIF3D directory as they needed to be accessed by other parts of the ARC
software system such as PERSENT, DASSH, and EvaluateFlux. They are almost entirely
programmed in Fortran 77 but the extensions were changed to Fortran 90 because of problems with
the GNU Fortran compiler and the actual Fortran 90 functionality being used. The original design
of the software was to perform the basis and matrix computation work for Cartesian, hexagonal,
and triangular-Z geometries and thus only a few subroutines are called from DIF3D with different
input switches to select the angular, spatial, and geometry options. The code coverage summary of
the source files in this directory is listed in Table 3.3.1 and Table 3.3.2.
Starting with the covered or partially covered subroutines in Table 3.3.1, one can see that a majority
of the code coverage issues are due to error messages that are not reached as the test problems do
not fail or debugging output that cannot be reached because it has to be manually switched on.
There are also several cases with files that have multiple subroutines and some of those subroutines
are simply not used or reachable by DIF3D. Several of the files have branches for triangular-Z
geometry which are unreachable as DIF3D-VARIANT does not presently have the triangular-Z
geometry option coded into it. All of these issues can be ignored. The ones that really have coverage
problems are the lack of testing of the “special” interface angular functions accessed in DIF3D via
A.DIF3D angular inputs of (use 30303 instead of 10303 in card 12 of A.DIF3D). These basis
functions are really meant for the developers of DIF3D-VARIANT and are not recommended for
regular use even though the DIF3D input allows the user to use them and the manual covers them.
These were originally to be covered by the VTR project but were eliminated after it was determined
they were unlikely to ever be used. As they should give an identical solution to the regular basis
functions, the lack of coverage will be ignored at this time.
The uncovered files are listed in Table 3.3.2 and all of them are for geometry or input
approximations that are not possible in DIF3D. In that regard, these can be considered developer
subroutines which are not presently usable by DIF3D-VARIANT or any other part of ARC and that
they do not need coverage.

3.4 Source code under the directory gnip4c_hmg4c/source
The directory gnip4c_hmg4c contains the GNIP4C and HMG4C submodules of DIF3D. The
GNIP4C program imports the A.NIP3 input data and packages it into the GEODST, NDXSRF,
ZNATDN, LABELS, ISOTXS, and FIXSRC interface files. The HMG4C program generates the
COMPXS file given the presence of GEODST, NDXSRF, ZNATDN, LABELS and ISOTXS files.
The coverage summary of G4CH4C is shown in Table 3.4.1 and Table 3.4.2. A review of the
partially covered subroutines in Table 3.4.1 indicates that most of the partial code coverage cases
are due to untouched error message branches and output edit options that are not used. In the VTR
project, all of the output edit options are turned on and thus it is highly likely that tests 42-89 would
fully cover all of the output edit options of these source files. Because these output edits are
generally not used, we choose to ignore the lack of coverage as the existing test suite in DIF3D
should fully check all output obtainable for DIF3D in these two modules.
Other partially covered subroutines occur because the inputs do not contain fixed format inputs for
A.NIP3 or A.HMG4C. The reported DLAYXS associated coverage issues are not reachable by
DIF3D as those are only used as part of VARI3D and DIF3D-K. Burnup dependent cross sections
and dynamic control rods are not usable in DIF3D unless it is part of REBUS and thus those are
unreachable parts of the code. The special boundary conditions and geometry options were
discussed in previous sections and are considered obsolete options that will not be checked. The
remaining code coverage issues can be summarized as wholly unused by the user base and
potentially unreachable in some cases. With all of these issues, we choose to ignore the lack of
complete coverage as they will either be tested by other codes of ARC or they are simply not used.
The fully uncovered subroutines listed in Table 3.4.2 are mostly the old graphics generating section
of the ARC code suite which has been deprecated. Some of the subroutines are only used by
VARI3D and DIF3D-K and thus unreachable with normal DIF3D usage. The subroutine that
processes the alpha eigenvalue for SRCH4C is not tested primarily because the alpha eigenvalue
solution algorithm appears to be unreachable via DIF3D input and thus it can be ignored. This
leaves the one subroutine remaining that only gets used when the available memory in HMG4C is
set too low. Because the memory level in HMG4C is hardwired to a number way beyond that which
is required to trigger this subroutine, we can safely say it is unreachable today and can ignore its
lack of code coverage.

3.8 Source code under the directory seglib/source
The files in directory seglib/source were developed as a common location separate from SYSLIB
for a variety of ARC codes. It primarily contains the SUMMAR and RODPOS subprograms of
ARC. SUMMAR produces isotopic reaction rate summary data for a given DIF3D input while
RODPOS is used by REBUS to adjust the control rod positions at each time step. The subroutines
with full or partial code coverage are listed in Table 3.8.1, while Table 3.8.2 lists the subroutines
with no coverage.
For the partially covered files, most of the uncovered portions are for error message output, and no
further test is needed. The exception is for calc.f, where the partially covered subroutines are
primarily only reachable from REBUS or unimportant because its functionalities are unreachable
debugging and output errors or additional output options that are simply not used by DIF3D. For
calc.f, the existing algorithm allows SUMMAR to operate in a low memory environment by
partitioning the memory to disk. In that regard, the disk operations to load data from disk are not
called by the existing verification test suite of DIF3D. It is unlikely today that this will be important
as the SUMMAR operation requires very little memory compared with the mainline DIF3D solvers
and this lack of coverage can be ignored. Because SUMMAR is called by REBUS, the tests there
should be used to determine whether this capability of SUMMAR is covered.
For the uncovered files in Table 3.8.2, they are either not used or only reachable by REBUS. No
further coverage tests are needed for these files.

4. Summary and Conclusions
In the preceding analysis the coverage report for each submodule of DIF3D was given. The
submodule refers to separable libraries (LINPACK, LAPACK, G4CH4C, etc.) that are included
either partially or fully as part of DIF3D even though the development of the source coding was
not specific to DIF3D. For the DIF3D specific source code (DIF3D and VARIANT_basis), most
of the subroutines were fully or partially covered to the point where additional testing is not
necessary (geometry options are simply not present or important). The LINPACK and LAPACK
submodules form a bulk of the uncovered subroutines in DIF3D which occurs because they are
simply not used by DIF3D. A bulk of the partially covered subroutines occur because of
unreachable debug or output error messages that only occur with failing inputs or input options that
are specific to the developers and thus they can be ignored.
The primary exceptions to the code coverage occur in the arcmodules/source, variantbasis/source,
and syslib/source directories of DIF3D. For arcmodules/source, many of the partially covered
functionality can be identified as not used by DIF3D but used by other parts of ARC. The LMA
module is the only one of concern as it should be tested externally to DIF3D as it is only reachable
in DIF3D via extremely large problems (run time greater than 1 day on vtr machine). The only
subroutines that were identified to need further coverage were in Table 3.3.1 for variantbasis/source
and Table 3.5.1 for syslib/source. For Table 3.3.1, the identified subroutines are needed for a
specific angular basis which is usable by the user although rarely if ever actually needed (or useful).
The Table 3.5.1 issue dealt with some parts of the DIF3D solver on large problems to partition the
memory to disk. Similar to LMA, these routines should be tested as they can be reached on large
user problems but it is not clear how to accomplish this.
