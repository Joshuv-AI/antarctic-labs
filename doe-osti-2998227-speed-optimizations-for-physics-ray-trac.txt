 i

 Abstract
 Ray tracing is a process used commonly in computer graphics and in physics to
track light photons and particles, respectively. Much research was found on improving
execution times for the computer graphics applications; however, in the short time frame
of this literary review, almost no research was found on improving the execution times
for the physics applications that were relevant to this problem. Two ray trace algorithms,
a STL raytrace and a conebeam raytrace, were optimized using OpenMP and CUDA.

 The STL raytrace algorithm achieved up to a 13.41x speedup using OpenMP.
CUDA was not used for this algorithm due to the large amounts of memory allocations
required in the algorithm. The conebeam raytrace used both OpenMP and CUDA along
with general coding knowledge to improve the execution time. The algorithm was able to
improve the runtime by 14.3x using the most optimized OpenMP. There was an
unexpected result using CUDA, in which the first calculation of the executable file took
around 200ms extra to run, causing different runtimes for the first calculation in the
executable file and each calculation after. Using the most optimized CUDA code, the
algorithm achieved a 13.87x speedup on the first calculation and an 18.5x speedup for
each calculation after. The CUDA optimization also allowed for answers an average of
8.5% more accurate than the original sequential code when comparing the computed
results to the actual results.

 Both algorithms achieved an improvement in execution time using the different
methods. Each algorithm was unique in the way they needed to be parallelized and tested.
These differences help broaden the knowledge on how the execution times of physics ray
trace algorithms can be improved.

 1 Introduction
 Ray tracing is a tool that is used in both physics applications and computer

graphics applications. While in the short time of the literary review for this project, many

resources were found on improving the execution time of computer graphics ray tracing

algorithms, however, limited resources were found on improving the execution time of

physics ray tracing algorithms. It can be reasoned that the more complex the data and the

larger the data set, the longer the execution time required to perform the ray trace. While

some people might not mind the extra calculation times, it can be safely assumed that

most people would prefer to have it completed as quickly as possible.

 Figure 1-1. Representation of 3D triangular shape

 The two algorithms proposed for optimization are an STL file raytrace algorithm

and a conebeam raytrace algorithm. STL files are commonly used for 3D modeling of

objects. They store the objects as a series of triangles and the number of triangles

representing the object tends to correlate to the resolution of the object, show above in

 2

Figure 1-1[1]. The ray trace on STL data uses a detector plane and a point where the rays

originate from. Then, each ray is iterated over the triangles, checking for ray triangle

intersections and if so, the distance the ray goes before hitting another triangle, or before

hitting the detector. A conebeam raytrace uses a cone-shaped beam to project towards the

detector. If any part of the beam is obstructed by an object, then a calculation is done to

determine the percentage of the beam that goes through the object and can reach the

detector. A diagram of how the raytrace is competed is shown below in Figure 1-2[2]. The

STL raytrace also has a conebeam effect, with the main difference being the conebeam

raytrace uses voxels for calculations while the STL raytrace completes the calculations

using ray-triangle intersections. These two algorithms were chosen because of their

importance in the application used for this project.

 Figure 1-2. Basics of Flash X-Radiography

 The focus of this research project will be to improve the time it takes to compute

the different ray trace algorithms as much as reasonably possible. By improving the

 3

execution time of the ray trace calculation, many people will be able to get the results

they need in a more efficient and favorable time frame.

 2 Background
 Ray tracing is a technique for creating a 2-D image of a 3-D object by tracking

light photons in computer graphics[3]. However, in physics, ray tracing is a method for

calculating the path of waves or particles through a system. Most research and resources

found for this literary review use computer graphics ray tracing. This is done by placing

an object between a detector and a light source and tracking where light photons, or rays,

hit the detector around the object. A common example of ray tracing is the pinhole

camera model shown in Figure 2-1[3] below. In this model, a photographic film is placed

on the back of a light-proof box with a pinhole in the front of the box. When an item is

held outside the box and in front of the pinhole, only certain light rays are allowed to pass

through the pinhole creating a flipped 2-D version of the object shown in Figure 2-2[3].

 Figure 2-1. The pinhole camera model

 5

  Figure 2-2. A reflection of a pencil appears in the film when the pencil is placed in front of the pinhole

 Looking at Figure 2-2 as an example, an object can be found in the scene by

testing if there is an intersection between the ray and the object[4]. To calculate an

intersection between a ray and an object, the object’s surface must first be broken into a

collection of triangles. Then, it can be determined if the ray intersects a single triangle

and the location of intersection (Q) given the ray’s source and direction vectors (P and d

respectively) and the vertices of the triangle (A, B, and C) demonstrated in Figure 2-3[5].

That calculation is repeated for each of the triangles of the object where the path of the

ray can then be traced. This process is referred to as ray tracing on triangular meshes.

 Figure 2-3. A ray intersecting triangle ABC at point Q

 6

 Some of the current applications of ray tracing include computer graphics

shading, solid modeling, and X-ray simulations. When looking at shading in computer

graphics, it is important to look at the source(s) of light and their distances from the

object. While a point light creates a hard shadow boundary, area lights result in softer

shadows[4]. Ray tracing allows for different light sources and shadows to be represented

realistically. Solid modeling is computer modeling of 3D solid objects. In this instance of

solid modeling, ray casting is used rather than ray tracing. Ray tracing results in highly

accurate visuals while ray casting focuses on finding the nearest object along a ray. Ray

casting is used in solid modeling to complete line drawings (drawing the visible edges of

the solid), shade the pictures, and compute the volume of a solid model[6]. X-ray tracing

focuses on the absorption of the rays rather than the bouncing of the rays due to tracking

only the primary X-rays. This type of ray tracing uses the rays that hit the detector to get

an image that shows where the objects in the ray’s path are and how many of the rays are

absorbed which can be seen in Figure 2-4[7]. Typically, ray tracing is a singular step in a

chain of calculations, with the chain being repeated thousands of times, proving why it is

so important to be able to do this process in an efficient time frame.

 Figure 2-4. An X-ray of various items

 There are currently several different solutions to improve the execution time of

ray tracing, although no open source solutions directly applicable to this problem.

NVIDIA’s CUDA has been used with ray tracing for computer graphics and has shown a

significant speedup compared to their equivalent sequential code[8]. OpenMP (OMP) has

also been used with ray tracing for computer graphics with it showing a slight speedup

with large data sets[9].

 8

 Figure 2-5. Diagram of an OptiX program’s structure

 The most common solution is by using NVIDIA’s OptiX ray tracing engine[7],

[10], [11], [12], [13]. OptiX enables a large set of ray tracing algorithms and applications

including interactive and offline rendering, collision detection systems, scientific

simulations, and more[10]. The structure of a program using OptiX is shown above in

Figure 2-5[14] with dark gray being fixed functions and grey being user functions. This is

an option to look further into; however, OptiX is not able to be considered in the timeline

of this research. CUDA was shown in computer graphics to have up to a 143x speedup

compared to the sequential code using only a single kernel, but was able to accomplish a

speedup of 1852x using further CUDA optimizations[8]. While OMP had higher

executing times than sequential for smaller computer graphics scenes, the larger scene

achieved up to a 1.43x speedup [9]. Using OptiX, one source achieved an average

speedup of 4x over sequential code[10], another achieved a speedup of 3x-300x over the

sequential code[12], and another one accomplished a 15x speedup over the CUDA

equivalent[11]. A couple sources provided runtimes but nothing to compare them to[7],

[13], while the rest did not include any runtime data. The vast variation of results

 9

demonstrates the need for more research in this area. For this research project, OpenMP

and CUDA will be used to apply computer graphics ray tracing advancements to both X-

ray tracing algorithms to decrease execution times.

 OpenMP is a model that allows programmers to make their applications parallel

in a simple and flexible way[15]. To use OpenMP, directives or constructs are added to

the base syntax in the form #pragma omp directive-specification. The most

common usage of OpenMP is to parallelize sequential loops. A common way to do that is

to place the command #pragma omp parallel for with any of the optional clauses

appended to the end of the command directly above the for loop being parallelized. The

parallel construct of the command is used to create individual threads that the work

will be divided between[15]. The structure of the OpenMP threads is shown below in

Figure 2-6[16] where, in the diagram, OpenMP is shown being used three separate times

with each time using different numbers of threads, and one including a nested parallel

region. There are several optional clauses that can follow this construct including

num_threads(nthreads), private(list), shared(list), and reduction. These

clauses allows the number of threads to be created and used on the loop to be specified,

the variables for which each thread needs a separate copy, which variables all threads

need to be able to edit, and identify when all threads perform an operation (i.e., +,-

,·,/,&&,||) that modifies a single shared variable, respectively.

 10

 Figure 2-6. Diagram of threads for OpenMP

 The for construct of the command specifies that the iterations of the loop will be

executed in parallel by the threads created by the parallel construct[15]. Two of the

optional clauses include collapse(n) and schedule(kind). The collapse clause allows

for nested for loops of n dimensions in which all of them are parallelized and the

schedule clause allows users to input how the iterations of the loop should be divided up

before given to the threads. The standard command #pragma omp parallel for is used

in this research project with testing of several different clause options to determine what

is most efficient for this specific application.

 CUDA(Compute Unified Device Architecture) is a programming model and

platform for parallel computing created by NVIDIA[17]. GPUs are used in CUDA to

accelerate applications by dividing the work of the application up for different

multiprocessing units, which in turn contain threads, to execute at the same time. A

CUDA kernel is a global function that will execute on the GPU by each thread. When the

CUDA kernel is called, grid size and block size are provided either as a single integer or a

 11

3-dimensional array. The grid size represents the number of blocks, or multiprocessing

units, to use and the block size represents the number of threads to be created and used

for each block. A visual of the CUDA kernel architecture is shown below in Figure 2-

7[18].

 Figure 2-7. Diagram of CUDA kernel architecture

 Every thread calls the kernel, and the index number of the thread combined with

the index number of the block allows each thread to be able to determine where it is at

and how many times it needs to repeat the loop based on the total number of threads to

ensure all the work gets done. Before a CUDA kernel can access any pointers or arrays

being passed into the function call, memory must be allocated onto the GPU from the

CPU, then, the data needs to be put into the space allocated. Because CUDA kernels must

return void, any result that is computed in the kernel must have the memory copied back

onto the CPU from the GPU once the kernel is finished with its tasks. Finally, the

memory allocated to the GPU is freed before the end of the CPU function. Depending on

how large the data set is, the process of allocating and transferring the data can take a lot

 12

of time; however, the amount of threads that are available to the GPU compared to the

CPU can make the execution time of the kernel small enough that the cost to allocate and

transfer the memory is still less than the cost to do it entirely on the CPU. The basis of a

CUDA program can be seen below in Figure 2-8.

 __global__ void kernel(float* result){
 // do operation
 }

 int main(){
 // declare result arrays for both device and host
 float *result, *d_result
 // allocate space on the device for the result array
 cudaMalloc((void**)&d_result)
 // call the kernel function
 kernel<<< blocks, threads >>> (d_result)
 // transfer the memory from d_result into result
 cudaMemcpy(result, d_result, n*sizeof(float),
 cudaMemcpyDeviceToHost)
 return
 }

 Figure 2-8. General idea of CUDA program

 Tools used to aid in finding execution time optimizations for this research project

include NVIDIA’s Nsight Systems and Nsight Compute. Nsight Systems is a performance

analysis tool designed to help users determine the best places for performance increases

and allow them to visualize their application[19]. Some of the important information that

can be gained from using Nsight Systems include visualizing how the CPU and GPU

work together and tracking GPU activity, such as kernel calls, memory allocations,

memory copies, and freeing memory. Nsight Systems was very helpful for viewing the

timing of memory allocations and how they related to the time to compute the kernel.

 13

 Nsight Compute is used for CUDA or OptiX as an interactive profiler providing a

detailed performance metric to help users analyze their work[20]. A couple key features

of Nsight Compute are the ability to inspect the memory usage and a guided analysis,

including tools to figure out the ideal number of threads for maximum occupancy. The

occupancy of a kernel is the ratio of active warps on a Streaming Multiprocessor to the

number of active warps supported by the Streaming Multiprocessor, with warps being

groups of adjacent threads within a block[21]. If the occupancy is low, it could be either

there are not enough warps to hide latency between dependent instructions due to not

enough threads being used, or because there are not enough resources per thread caused

by too many threads being used. That is why using Nsight Compute to help determine the

optimal number of threads is so important.

 3 Methodology
3.1 Abstract

 The STL raytrace uses three STL objects with different resolutions to best reflect

the standard execution time compared to the resolution of the STL object. Methods to

improve the execution time were having OpenMP added to the CPU code, or a GPU

kernel created to complete the calculation, with other options for improvement with a

larger time frame being discussed.

 When testing the execution time improvements on the conebeam raytrace, the

time tests occurred on the same size input and output grids with the change occurring in

the number of iterations of the calculation. The methods used for time improvements

were altering the amount of branching in the loops, adding OpenMP to the CPU code,

and creating GPU kernels to process the calculations.

3.2 STL Raytrace

 The execution time of this algorithm was tested by using three different sized STL

objects to ray trace. The first was a square with a hole with 32 triangles, the second was a

hollow sphere with a hole containing 4,276 triangles, and the third was a hollow sphere

with 271,008 triangles. This allowed better reflection on how the execution time was

affected by different resolutions of STL images, although performing the tests on the

same STL object with varying triangles would allow for the most accurate execution time

trends. The expected results of the STL raytrace showing thickness of each STL object

for each resolution is shown in Figure 3-1 below. These results are dependant on

 15

parameters such as source position, detector size, or number of pixels. The final

implementation of the STL raytrace can be found in Appendix A at the end of the thesis.

 Figure 3-1. Expected results for 32 triangle (left), 4276 triangle (center), and 271008 triangle (right) STL

 NVIDIA’s Nsight Systems was used to obtain the average sequential execution

time of the STL raytrace. Then, OpenMP code was added to the function and Nsight

Systems was used to calculate the average OpenMP execution time. In the OpenMP code,

the base statement #pragma omp parallel for using several different schedule options

was tested to determine the most efficient scheduling type. While only the main loop was

looked at for this project, there were several other smaller loops that could have had

OpenMP added to them to decrease the execution time that were not within the time

constraints of this project.

 To create the GPU version of the code, the idea was to transfer most of the main

loop directly from the sequential code and then use Nsight Compute to further optimize

the execution time of the kernel. There were several changes made to the code put in the

 16

kernel due to the standard libraries and class function calls being unavailable on the GPU.

This included finding or creating replacements for everything using the standard library

and switching dynamically allocated arrays to fixed size pointers that took up more

memory to ensure there was enough space allocated for each array.

 Given more time, the main loop could have been optimized even further by

addressing the amount of branching that occurred inside the loop. There are an extremely

large number of if-else statements and for loops, including some that are triple nested

inside the loop. While this might require a slight logic change in the code to complete, it

would be worth looking into due to the potential speedup gains. Depending on the logic

changes, if less memory would be allocated in the main loop, then that would also open

the possibility of a CUDA kernel being used to achieve an even greater execution time

optimization.

3.3 Conebeam Raytrace

 When measuring the execution time of this algorithm, an input grid of size

800x800x800 pixels was used with an 800x800 pixel output grid. Because of the general

usage of this algorithm, time tests were taken on both individual execution times and total

execution times after 100 iterations of the raytrace. When using testing with the 100

iterations, a new instance of the class was created each iteration to better demonstrate and

understand the time frame that will occur in the general use of this algorithm. The

expected output of the conebeam raytrace is shown in Figure 3-2 below. The final

 17

implementation of the conebeam raytrace can be found in Appendix B at the end of the

thesis.

 Figure 3-2. Expected result for conebeam raytrace

 There were three different methods used to optimize this conebeam raytrace. The

first included reducing the number of branches that happened within the loops being

optimized. This was done by taking out a double nested loop for filling a 2x2 array of

floats and unrolling it so instead there were four float variables with no extra branching.

This also allowed for the conditional statements inside the nested loops to be removed

and replaced with inline conditional statements to populate the values. These changes

were especially useful because they were able to be combined with both the OpenMP

 18

optimizations and the GPU optimizations for an even greater improvement in execution

times.

 To implement the OpenMP improvements to the execution time, the standard

OpenMP command was used, and several schedule types and block sizes were tested to

make sure the most efficient was being used. Once the speedup from using OpenMP was

calculated, the nested loops were unrolled and made to use the inline conditional

statements. This allowed the execution time to improve beyond what would have been

possible with OpenMP alone.

 Implementing the GPU optimizations included taking the two functions of the

calculation and putting them into a GPU kernel. Although the CUDA kernel could have

been split into one kernel per function, putting them on the same CUDA kernel reduced

the amount of total memory transfers. The CUDA kernel was called by only allocating

blocks and threads in one direction. This increased the optimization because when they

are used in either the two or three directions, the product of those numbers must equal the

ideal number of threads exactly, otherwise the kernel cannot reach full occupancy.

However, if threads are only allocated in one direction, it is easier to ensure the kernel

will have the highest occupancy possible. One portion of the kernel held a significantly

higher proportion of the execution time, so that is where most of the focus for improving

the execution time went. This portion was a nested loop of depth two with the inside loop

doing the largest amount of work. Two methods of parallelizing these loops were tried.

First, the outside loop was given all of the threads and each thread completed the entirety

 19

of the inside loop. And second, all of the threads were given to the inside loop so each

thread completed the outside loop and the threads divided the work of the inside loop

 4 Results
4.1 Abstract

 The execution time improvement for the STL raytrace provided a couple different

results. By using OpenMP, a speedup of 13.41x was achieved when using dynamic

scheduling for the threads. Accuracy testing of the optimized OpenMP calculations

showed that it had the same accuracy as the original code. However, using CUDA for this

raytrace turned out to be unfeasible due to the amount of memory copies occurring in the

kernel.

 All methods of improvements tried for the conebeam raytrace yielded positive

results. By refactoring the code, a 2.06x speedup was achieved over the original

sequential code. The final optimized OpenMP, which used static scheduling and

contained the refactored code, was able to achieve a 14.3x speedup compared to the

starting sequential code. Using the optimized CUDA provided the highest improvement

in execution time with a 14.63x speedup on the first calculation of each executable file

and a 17.95x speedup on every following calculation in an executable file. The use of the

optimized CUDA also proved to be 8.5% more accurate than the original code when

compared to the actual result. The code was then tested on real-world examples with

results showing an improvement on execution time for those situations as well.

4.2 STL Raytrace

 Using OpenMP for this raytrace provided good results. The use of #pragma omp

parallel for, the standard OpenMP command, allowed for an average of an 8.07x

 22

speedup with the maximum speedup being 12.98x more efficient than the original code.

After testing different scheduling methods, it was found that dynamic scheduling

provided the highest improvement on the execution time. With dynamic scheduling, a

speedup of 9.32x was averaged with a maximum speedup of 13.41x being achieved. In

both cases, the higher the resolution, the higher the speedup achieved. The optimized

OpenMP had a higher execution time than the regular OpenMP in the case of the 32

triangle STL file. In typical use cases, that low of a resolution would not be used and

when it does, there is still a speedup from the sequential time and the difference in

execution times between the two would be hard to tell without timing the calculation.

 Creating a GPU version of the algorithm turned out to be substantially more

difficult than originally expected. Due to the nature of the algorithm, a large amount of

memory must be allowed for each thread because each iteration of the loop needs arrays

declared independent of all other threads. The length of the kernel substantially increased

due to the amount of memory allocation checks needed and having to rewrite any class

functions used from inside the kernel. Unfortunately, the large memory allocations caused

the GPU to crash because it didn’t have enough space available. This problem will not be

able to be fixed without a change to the base idea of the algorithm.

 Testing the accuracy of the STL raytrace was done by comparing the original

result to the results obtained by the OpenMP computation. The results were equivalent,

meaning the accuracy of the calculation was maintained through the decrease in

execution time.

4.3 Conebeam Raytrace

 Refactoring the raytrace to unroll nested loops and remove unnecessary branching

in the main loops of the calculation allowed for a speedup that was stackable on top of

other execution time optimization techniques. Using the refactored code, the execution

time was 2.06x faster to complete the calculation allowing for a 1.95x speedup for the

entire executable file which included creating the class instance, setting the input grid and

all the variables, and the calculating of the raytrace. This optimization allowed for a

higher speedup with OpenMP and CUDA because with the unnecessary branching

removed, the threads do not have to wait for each individual thread to complete their

branches for the program to move forward, allowing for a calculation more suitable for

parallel execution.

 The use of OpenMP allowed for significant speedups in the conebeam raytrace.

With the use of the standard command alone, the execution time of the calculation

became an average of 8.24x faster causing an average speed up of 6.27x for the execution

time of the executable file. Then, the refactored version was taken and OpenMP was

 24

added to it. Several different schedule methods of OpenMP were tested and it was found

that the static scheduling method improved the execution time the most. Using both the

refactored code and OpenMP commands, it was found that an average of 6.94x speedup

on the calculation was achieved compared to the refactored code alone and 1.73x speedup

on the calculation was achieved compared to the OpenMP code alone. These changes

allowed for an average of 14.3x faster for the calculation and 9.25x faster for the

executable file to run in comparison to running the original sequential code.

 The highest execution time improvement came from implementing CUDA. When

writing the kernels, decisions had to be made on how to call the main kernel and how the

threads would be used. The largest speedup occurred when putting the entire nested loop

into the kernel and only using the threads on the inside loop which completed the most

 5 Conclusions
5.1 STL Raytrace

 Improving the execution time for the STL raytrace was only viable using OpenMP

within the timeframe of this project. The algorithm was not suited for parallel

computation on a CUDA kernel. Much more work could be done to further decrease the

execution time, but it would most likely consist of rewriting the algorithm. Using

OpenMP for this raytrace showed the highest levels of improvement at the highest

resolution of the STL file due to how the cost of overhead corresponds to the size of data.

Applying OpenMP to the STL raytrace allowed for an improvement to the execution time

while still maintaining the original accuracy.

5.2 Conebeam Raytrace

 The conebeam raytrace was very well suited to parallelization. Using the

refactored code inside the CUDA kernels resulted in the highest speedup, especially when

multiple calculations are computed in the same executable file. A small amount can still

be done to try to further improve the execution times when using CUDA, but the results

from the improvements seem to be small enough that it would most likely not be worth

the time it would take to implement them. Therefore, the execution time of conebeam

raytrace is as fast as reasonably achievable. Implementing CUDA allowed for increased

accuracy results and all three methods used for optimization provided an execution time

improvement in the calculation.

5.3 Future Work

 Future work for improving the execution time can be accomplished with

improvements to the STL raytrace. The main loop could have been optimized even

further by addressing the amount of branching that occurred inside the loop. There are an

extremely large number of if-else statements and for loops, including some that are

triple nested inside the loop. While this might require a slight logic change in the code to

complete, it would be worth looking into due to the potential speedup gains. Depending

on the logic changes, if less memory would be allocated in the main loop, then that would

also open the possibility of a CUDA kernel being used to achieve an even greater

execution time optimization. Rewriting the STL Raytrace algorithm to take advantage of

RTX raytracing technology would also provide a substantial increase in speed. Future

work will include writing the STL Raytrace to take advantage of the RTX hardware and

comparing against optimized general GPU implementations.

std::array<double, 3> cross_product(const std::array<double, 3>& a,
 const std::array<double, 3>& b) {
 return {
        a[1]*b[2] - a[2]*b[1],
        a[2]*b[0] - a[0]*b[2],
        a[0]*b[1] - a[1]*b[0]
 };

bool intersect(std::array<double, 6> bounds,
 std::array<double, 3UL> direction, float source[3]){
 double tmin = -INFINITY, tmax = INFINITY;
    double min[3] = {bounds[0], bounds[2], bounds[4]};
    double max[3] = {bounds[1], bounds[3], bounds[5]};
    for (int i = 0; i<3; ++i){
 double t1 = (min[i]-source[i])/direction[i];
 double t2 = (max[i]-source[i])/direction[i];
 tmin = std::max(tmin, std::min(t1,t2));
 tmax = std::min(tmax,std::max(t1,t2));
 }

 bool intersect = tmax > std::max(tmin, 0.0);
 return intersect;
}
